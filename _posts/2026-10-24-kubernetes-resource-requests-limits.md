Kubernetes에서 `resources.requests`와 `resources.limits`를 넣으면 “컨테이너에 CPU와 메모리를 배정했다”고 생각하기 쉽습니다. 실제로는 서로 다른 질문에 답합니다. request는 Pod를 어느 노드에 배치할 수 있는지 판단할 때 필요한 최소 예약량에 가깝고, limit은 실행 중 컨테이너가 넘지 못할 상한입니다. 이 둘의 차이를 모르면 Pod가 Pending인 이유, 노드는 남아 보이는데 배치가 안 되는 이유, 배포 뒤 API가 느려진 이유, OOMKilled가 반복되는 이유를 엉뚱한 곳에서 찾게 됩니다.

리소스 설정은 비용 절감용 숫자 맞추기가 아니라 서비스가 어떤 부하와 실패를 견딜지 선언하는 운영 계약입니다. 이 글은 CPU와 메모리가 왜 다르게 제한되는지, scheduler와 QoS(Quality of Service)가 어떤 관계인지, 실제 관찰값으로 값을 조정하는 절차를 초보자도 따라갈 수 있게 정리합니다.

## 먼저 알아둘 기반 기술

### Node, Pod, Container와 allocatable

Node는 Kubernetes가 Pod를 실행하는 서버입니다. Node의 CPU와 메모리가 모두 애플리케이션 Pod에 쓸 수 있는 것은 아닙니다. 운영체제와 kubelet, 시스템 DaemonSet이 쓸 몫을 제외한 allocatable 리소스가 있고, scheduler는 Pod의 request 합계가 이 범위에 들어가는지를 보고 배치를 시도합니다. 화면의 CPU 사용률이 낮아도 request 합계가 충분히 커서 배치가 안 될 수 있는 이유입니다.

Pod는 하나 이상의 컨테이너를 묶는 실행 단위입니다. 각 컨테이너에 request와 limit을 둘 수 있고, Pod 전체의 요구량은 컨테이너들의 값과 init container 특성을 고려해 계산됩니다. Sidecar가 있다면 본 컨테이너만 보고 숫자를 정하면 안 됩니다. 프록시, 로그 수집기, 보안 에이전트도 CPU·메모리를 쓰므로 Pod가 실제로 필요로 하는 자원에 포함해야 합니다.

### CPU 단위와 메모리 단위

Kubernetes CPU는 보통 코어 단위 또는 millicore로 표현합니다. `500m`은 코어 하나의 절반을 뜻합니다. 메모리는 `Mi`, `Gi`처럼 바이트 단위로 표현합니다. CPU는 압축 가능한 자원입니다. 경쟁이 생기면 처리량과 지연이 나빠질 수 있지만 프로세스가 즉시 죽는 것은 아닙니다. 메모리는 압축하기 어려운 자원입니다. 컨테이너가 메모리 한계를 넘으면 Linux 커널의 OOM(Out Of Memory) 처리로 프로세스가 종료될 수 있습니다. 이 차이 때문에 CPU와 메모리를 같은 여유율로 관리하면 안 됩니다.

### cgroup과 Linux 자원 격리

컨테이너의 CPU·메모리 제한은 Linux control group(cgroup) 같은 커널 기능을 바탕으로 합니다. Kubernetes는 선언한 리소스를 컨테이너 런타임과 kubelet을 통해 cgroup 설정으로 연결합니다. 최근 cgroup v2 환경에서는 리소스 제어와 관찰 방식이 더 통합되어 있지만, 애플리케이션 팀이 먼저 알아야 할 핵심은 단순합니다. limit은 “권장값”이 아니라 커널 수준에서 실행에 영향을 주는 경계이고, 잘못된 값은 코드가 바뀌지 않아도 지연과 종료를 만들 수 있습니다.

## request와 limit은 각각 무엇을 바꾸나

request는 scheduler에게 “이 Pod를 안정적으로 실행하려면 이 정도가 필요하다”고 알립니다. 세 노드 각각에 2 CPU의 allocatable이 남아 있고 새 Pod의 CPU request가 3 CPU라면, 전체 클러스터에 6 CPU가 남아도 한 노드에 들어가지 못해 Pending이 될 수 있습니다. 반대로 CPU request가 지나치게 낮으면 scheduler는 많은 Pod를 한 노드에 배치하고, 피크 순간 실제 사용량이 몰리면서 지연이 생길 수 있습니다.

limit은 실행 중 상한입니다. CPU limit을 넘는 컨테이너는 throttling을 경험할 수 있습니다. 애플리케이션은 오류 없이 동작해도 요청 처리가 길어지고, 큐가 쌓이고, 타임아웃이 늘어날 수 있습니다. 메모리 limit을 넘으면 프로세스가 OOMKilled될 수 있으며, 재시작 정책 때문에 Pod가 다시 뜨더라도 사용자 요청은 실패할 수 있습니다. OOMKilled는 메모리를 더 달라는 단순한 신호가 아니라 누수, 캐시 정책, 동시성, 입력 크기, limit 설정 중 무엇이 원인인지 조사해야 하는 사건입니다.

다음은 웹 API 컨테이너에 명시적으로 값을 준 예시입니다. 이 값은 특정 서비스의 권장값이 아니라 필드의 의미를 설명하기 위한 예시입니다.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

이 선언은 scheduler가 250m CPU와 512Mi 메모리를 기준으로 배치할 수 있게 하고, 컨테이너는 최대 1 CPU와 1Gi 메모리 경계를 갖게 합니다. 숫자를 정할 때는 평균만 보지 말고 피크·기동·캐시 워밍·대량 요청·배치 작업에서의 사용량을 봐야 합니다. 평균 100Mi인 서비스도 특정 보고서 요청에서 900Mi를 쓸 수 있습니다.

## QoS와 우선순위의 관계

Kubernetes는 request와 limit 조합을 보고 Pod에 QoS 클래스라는 분류를 부여합니다. Guaranteed, Burstable, BestEffort 같은 분류는 노드 메모리 압박에서 어떤 Pod가 먼저 축출될 가능성이 있는지와 관련됩니다. 모든 컨테이너의 CPU와 메모리 request가 limit과 같으면 Guaranteed가 될 수 있고, request 또는 limit이 하나라도 설정되었지만 같지 않으면 보통 Burstable이며, 둘 다 없으면 BestEffort입니다. 정확한 규칙은 Kubernetes 버전과 문서를 확인해야 하지만, 핵심은 리소스 선언의 유무가 노드 압박 시 생존 가능성에도 영향을 준다는 점입니다.

QoS는 서비스 중요도를 대신 표현하지 않습니다. 결제 API가 중요하다면 PriorityClass, replica 분산, PDB, autoscaling, 충분한 capacity가 함께 필요합니다. BestEffort가 나쁘고 Guaranteed가 항상 좋다는 식의 단순화도 위험합니다. 모든 Pod를 Guaranteed로 만들면 scheduler가 예약해야 할 자원이 커져 클러스터 효율이 떨어질 수 있습니다. 서비스의 중요도와 부하 특성에 맞는 정책을 고르는 것이 목적입니다.

## 관찰에서 값으로 가는 절차

리소스 값을 정할 때 가장 먼저 필요한 것은 실제 관찰입니다. CPU 사용량, 메모리 사용량, 재시작 횟수, OOMKilled 이벤트, CPU throttling, 요청 지연, 큐 길이를 같은 시간 축에 놓습니다. CPU가 제한에 자주 닿으면서 지연이 커진다면 limit과 request, 애플리케이션 동시성, HPA(Horizontal Pod Autoscaler) 정책을 함께 봅니다. 메모리가 계속 오르다 limit에서 죽는다면 무작정 limit을 올리기 전에 힙 덤프, 캐시 크기, 대용량 입력, 누수 가능성을 조사합니다.

관찰 기간도 중요합니다. 평일 낮 트래픽만 보고 정하면 월말 배치, 새벽 동기화, 프로모션 같은 다른 패턴을 놓칠 수 있습니다. 서비스별로 정상 피크와 예외 피크를 문서화하고, 변경 뒤에는 같은 지표를 다시 비교합니다. request를 올려 Pod Pending이 늘었다면 클러스터 용량이나 autoscaler 최소 노드 수가 함께 바뀌어야 할 수 있습니다. 리소스 변경은 한 Pod YAML만 고치는 작업이 아니라 배치·확장·비용의 균형을 바꾸는 일입니다.

### 구체적 업무 예시: 이미지 변환 API

이미지 변환 API는 평소 작은 썸네일 요청을 처리하다가, 가끔 사용자가 큰 원본 파일을 올리면 메모리를 많이 씁니다. 평균 메모리만 보고 256Mi limit을 두면 큰 파일에서 OOMKilled될 수 있습니다. limit을 4Gi로 높이는 것만으로 해결하면 한 노드에 동시에 여러 변환 Pod가 배치됐을 때 노드 메모리 압박이 커질 수 있습니다. 더 나은 접근은 업로드 파일 크기와 해상도 제한, 작업 큐, 변환 동시성, 캐시 수명, Pod당 request·limit, HPA와 노드 autoscaler를 함께 설계하는 것입니다.

테스트 환경에서 대표 크기의 파일과 경계 크기 파일을 처리해 메모리 그래프와 종료 상태를 확인하고, 운영에서는 OOMKilled 이벤트와 입력 크기 분포를 관찰합니다. 큰 파일은 별도 worker pool로 보내거나 처리량을 제한하는 선택도 가능합니다. 리소스 limit은 애플리케이션 설계의 실수를 숨기는 값이 아니라, 그 설계가 감당할 수 있는 경계를 명시하는 값입니다.

## 한계와 적용 기준 Q&A

### Q. CPU limit을 아예 두지 않는 팀도 있던데 괜찮나요?

A. 워크로드 특성과 클러스터 정책에 따라 다릅니다. CPU limit은 noisy neighbor를 막는 장점이 있지만, throttling이 지연에 미치는 영향을 고려해야 합니다. 중요한 것은 팀의 근거 없이 관례만 복사하지 않는 것입니다. request·limit·PriorityClass·노드 격리 정책이 어떤 위험을 다루는지 문서화하고 관찰값으로 검증하세요.

### Q. OOMKilled면 메모리 limit만 올리면 되나요?

A. 일시적인 피크가 정상이고 여유가 있다면 조정이 필요할 수 있지만, 메모리 누수나 무제한 캐시, 비정상 입력이 원인이라면 limit을 높여도 나중에 같은 문제가 재발합니다. 종료 시점의 로그, 힙·RSS, 입력 크기, 재시작 패턴을 확인해 원인을 분리해야 합니다.

### Q. request가 낮으면 비용이 절감되나요?

A. 낮은 request는 더 많은 Pod가 같은 노드에 배치되게 해 표면적인 밀도를 높일 수 있지만, 실제 피크에서 경쟁과 축출이 늘면 비용과 장애가 커집니다. 비용 최적화는 안정적인 사용량 관찰, autoscaling, 불필요한 idle capacity 정리와 함께 해야 합니다.

## 용량 계획에서 request를 읽는 방법

클러스터 용량 계획은 노드의 물리 CPU 합계만 더하는 작업이 아닙니다. scheduler가 보는 것은 allocatable과 Pod request의 합계이므로, 팀은 서비스별 최소 복제본과 request를 곱해 정상 상태의 예약량을 먼저 계산해야 합니다. 예를 들어 API가 최소 세 복제본이고 Pod당 메모리 request가 1Gi라면, 장애·업데이트 중 추가 Pod가 생기는 상황까지 고려해 그보다 큰 여유가 필요합니다. 노드 한 대가 빠졌을 때 남은 노드가 기존 Pod와 대체 Pod를 수용할 수 있는지도 같은 계산으로 확인합니다.

이 계산은 정확한 미래 예측이 아니라 위험을 드러내는 도구입니다. request가 실제 관찰보다 지나치게 낮으면 계산은 낙관적이고, 지나치게 높으면 모든 서비스가 과도한 예약을 요구해 autoscaler가 불필요하게 많은 노드를 만들 수 있습니다. 그래서 리소스 권장 도구의 출력도 그대로 적용하지 말고, 관찰 기간·백분위 기준·기동 피크·업무 피크가 무엇인지 확인해야 합니다. 추천값은 결정의 출발점일 뿐 서비스 책임자가 확인한 운영 계약이 아닙니다.

### HPA와 request의 상호작용

HPA가 CPU 사용률을 기준으로 확장할 때, CPU 사용률은 request와 연결되어 해석될 수 있습니다. request를 바꾸면 같은 실제 CPU 사용량도 퍼센트가 달라지고, 확장 시점이 달라질 수 있습니다. 따라서 request를 낮춰 배치 밀도를 높인 뒤 HPA가 너무 늦게 또는 너무 빨리 반응한다고 느끼는 일이 생길 수 있습니다. 리소스 설정과 autoscaling을 별개 YAML로 보지 말고, 부하에서 복제본이 언제 늘고 줄어드는지 함께 검증해야 합니다.

메모리 기반 확장도 비슷합니다. 메모리 사용량이 캐시 워밍 뒤 천천히 상승하는 애플리케이션이라면 단순한 평균 비율만으로 확장하면 늦을 수 있습니다. 반대로 일시적 burst만 보고 확장하면 비용이 급증할 수 있습니다. 큐 길이, 처리 대기 시간, 동시 작업 수처럼 사용자 영향에 더 가까운 지표가 있는지 검토하고, 리소스 지표는 그 원인을 설명하는 보조 지표로 씁니다.

### namespace 정책과 LimitRange

조직이 여러 팀과 namespace를 함께 운영하면 일부 Pod가 request와 limit 없이 배포되는 일을 막고 싶을 수 있습니다. LimitRange는 namespace 안에서 기본값·최소값·최대값을 정하는 데 쓸 수 있고, ResourceQuota는 namespace가 사용할 수 있는 총량을 제한하는 데 사용됩니다. 이 정책은 안전망이지만, 개발 팀에 보이지 않는 기본값으로 작동하면 왜 배포가 거절됐는지 알기 어렵습니다. 정책 문서, 오류 메시지, 배포 템플릿을 함께 제공해야 합니다.

Quota에 걸린 Pod가 Pending이 아니라 생성 단계에서 거절되는지, request 부족으로 스케줄이 안 되는지, limit을 넘어 OOMKilled되는지는 서로 다른 사건입니다. 세 상태를 모두 ‘리소스 부족’이라고 부르면 해결이 늦어집니다. 이벤트와 admission 오류, Pod 상태, Node 압박 상태를 분리해 보는 runbook을 준비하면 온콜 담당자도 우선순위를 정하기 쉽습니다.

## 배포 전과 배포 후의 검증

새 리소스 값을 적용하기 전에는 대표적인 정상 요청, 최대 입력, 기동 직후, 롤링 업데이트, 노드 하나가 빠진 상황을 생각해 봅니다. 모든 상황을 완벽히 재현할 수 없더라도, 무엇을 검증하지 못했는지 명확히 남겨야 합니다. 특히 Java나 Node.js처럼 런타임 내부 힙·스레드·버퍼가 메모리를 쓰는 애플리케이션은 애플리케이션 설정과 container limit의 합이 맞는지 확인해야 합니다. 힙 최대값만 limit보다 작다고 안전한 것은 아닙니다.

배포 후에는 Ready 개수와 요청 성공률뿐 아니라 throttling, 재시작, 메모리 working set, node pressure, Pending 이벤트를 관찰합니다. CPU limit을 올렸는데 p95 지연이 그대로라면 병목이 CPU가 아닐 수 있습니다. 메모리 request를 올렸는데 OOMKilled가 사라졌다면 원인을 확인하지 않은 채 성공으로 결론내리지 말고, 입력과 캐시의 증가 패턴도 봐야 합니다. 변경의 효과와 부작용을 동시에 보는 것이 리소스 운영의 핵심입니다.

## CPU throttling을 읽을 때의 주의점

CPU limit이 있는 컨테이너는 필요한 순간에만 제한을 넘는 것이 아니라, 짧은 burst가 반복될 때도 응답 지연을 경험할 수 있습니다. 웹 API는 요청 하나를 처리할 때 JSON 변환, 암호화, 압축, 템플릿 렌더링처럼 짧지만 CPU가 몰리는 구간을 가질 수 있습니다. 평균 CPU 사용률이 낮다는 사실만으로 throttling이 사용자 영향이 없다고 단정할 수 없는 이유입니다. 요청 지연이 튀는 시간과 컨테이너의 throttling 지표를 함께 비교해야 합니다.

하지만 throttling 카운터가 증가했다고 즉시 CPU limit을 제거하는 것도 성급합니다. 같은 노드의 다른 핵심 워크로드가 CPU를 필요로 할 수 있고, 무제한 burst를 허용하면 noisy neighbor 문제가 생길 수 있습니다. 먼저 어떤 endpoint, 어떤 요청 크기, 어떤 동시성에서 지연이 발생하는지 확인하세요. 애플리케이션의 worker 수를 줄이거나, 비싼 작업을 비동기 큐로 옮기거나, HPA가 더 빨리 확장되게 하는 선택이 limit 변경보다 적절할 수 있습니다.

CPU request와 limit이 크게 차이 나는 Pod는 평소에는 적은 예약만 하고 순간적으로 많은 CPU를 쓰려는 설계를 표현합니다. 이 방식이 맞는지는 노드에 동시에 burst할 서비스가 얼마나 많은지에 달려 있습니다. 마케팅 알림, 정산, 이미지 변환처럼 같은 시간대에 피크가 오는 작업들이 한 노드에 모이면 모두가 limit보다 적은 CPU만 얻어 지연될 수 있습니다. workload를 분리하거나 node pool과 affinity를 쓰는 것이 숫자를 계속 미세 조정하는 것보다 나은 경우도 있습니다.

### 메모리 사용량은 RSS만으로 끝나지 않는다

컨테이너 메모리를 볼 때 RSS(Resident Set Size) 또는 working set 같은 지표를 보게 됩니다. 런타임, 파일 캐시, native library, page cache가 어떤 방식으로 집계되는지에 따라 화면의 숫자와 OOM 사건의 관계가 단순하지 않을 수 있습니다. 특히 JVM은 heap 최대값 외에도 metaspace, thread stack, direct buffer를 쓸 수 있고, Python이나 Node.js도 native extension과 buffer를 사용합니다. 애플리케이션 런타임의 메모리 옵션을 container limit보다 여유 있게 정하는 것이 아니라, 둘의 합리적 관계를 이해하고 실험해야 합니다.

기동 시점도 따로 봅니다. 캐시를 한 번에 읽거나, 대형 설정을 파싱하거나, JIT 컴파일을 하는 서비스는 평소보다 시작 직후 메모리가 높을 수 있습니다. rolling update 때 여러 새 Pod가 동시에 기동하면 노드의 일시 사용량이 커집니다. 이 경우 Deployment의 surge 설정, Pod 시작 순서, 노드 여유, readiness가 통과하기 전의 리소스 사용을 함께 검토해야 합니다. 운영에서 한 Pod만 수동 재시작해 본 결과를 전체 배포의 안전성 근거로 쓰면 안 됩니다.

## 문제 상황별 조사 예시

### Pod가 Pending이고 `Insufficient memory`가 보일 때

이벤트에 메모리 부족이 보이면 실제 메모리 사용률부터 보기보다 먼저 새 Pod의 memory request와 각 Node의 allocatable, 이미 배치된 Pod request 합계를 확인합니다. 노드가 실제로는 여유 메모리를 쓰고 있더라도 예약 기준이 부족하면 scheduler는 배치하지 않습니다. 해결책은 request를 근거 없이 낮추는 것이 아니라, 필요 용량을 가진 노드를 늘리거나, 비핵심 workload를 다른 pool로 옮기거나, Pod의 최소 복제본과 request가 현실적인지 재검토하는 것입니다.

### Pod가 반복해서 OOMKilled될 때

재시작 횟수만 보지 말고 종료 직전 입력, 로그, 메모리 곡선, heap 또는 runtime 진단 정보를 확인합니다. 큰 요청 한 번에만 죽는다면 입력 제한·스트리밍 처리·동시성 제어가 후보입니다. 시간이 지날수록 계속 상승하면 누수나 캐시 해제가 후보입니다. 새 버전 뒤에만 나타나면 코드와 의존 라이브러리 변화를 비교합니다. limit 증가는 사용자 영향을 줄이는 임시 조치가 될 수 있지만, 원인 가설과 후속 검증을 남겨야 합니다.

### 노드가 메모리 압박 상태일 때

한 Pod의 limit을 넘지 않았어도 Node 전체가 memory pressure를 겪을 수 있습니다. kubelet은 축출 정책에 따라 Pod를 종료할 수 있고, QoS와 우선순위가 영향을 줄 수 있습니다. 이 문제는 개별 컨테이너가 “내 limit 안이다”라고 말해도 해결되지 않습니다. 노드에 어떤 workload가 함께 있었는지, DaemonSet과 시스템 예약이 충분했는지, burst 시점이 겹쳤는지, autoscaler가 용량을 제때 늘렸는지 조사해야 합니다.

## 리소스 설정을 코드와 같이 관리하기

CPU·메모리 값은 Helm values나 Deployment YAML의 부수 정보가 아니라 서비스 동작의 일부입니다. 애플리케이션 코드 리뷰와 분리해 숫자만 변경하면 왜 바꾸는지와 어떤 테스트를 했는지가 사라집니다. 변경 요청에는 관찰한 지표, 대상 환경, 예상되는 request·limit 변화, HPA와 replica 영향, 배포 뒤 확인할 지표를 함께 적는 습관이 좋습니다. 이렇게 하면 다음 담당자가 과거 값을 복사하는 대신 그 수치의 배경을 이해할 수 있습니다.

환경별 값을 다르게 둘 때도 원칙은 같습니다. 개발 환경이 작다는 이유로 request를 지나치게 낮추면 production에서만 나타나는 배치 문제를 놓칠 수 있습니다. 반대로 개발 클러스터가 작아 production과 같은 최소 replica를 유지하지 못할 수 있습니다. 차이를 숨기지 말고 어떤 테스트가 어느 환경에서 가능한지 명시하세요. production 리소스 값의 정확한 복제가 목표가 아니라, 중요한 실패 모드를 조기에 발견하는 것이 목표입니다.

정기적인 리뷰에서는 서비스별 request 대비 실제 사용량, limit 근처 사건, OOMKilled, throttling, Pending, 노드 autoscaler 대기를 함께 볼 수 있습니다. 숫자를 자동으로 일괄 변경하는 것보다, 반복적으로 과대·과소 설정된 서비스와 이유를 찾는 것이 안전합니다. 관찰·가설·작은 변경·재관찰의 루프가 리소스 운영을 안정시킵니다.

## 실무에서 자주 나오는 질문들

### init container는 어떤 값을 기준으로 잡아야 하나

init container는 애플리케이션 컨테이너보다 먼저 실행되어 설정 파일을 만들거나 마이그레이션을 확인합니다. 짧게 실행된다는 이유로 리소스를 생략하면, 대량 다운로드나 압축 해제 중에 노드 압박을 만들 수 있습니다. 반대로 큰 request를 주면 Pod 배치 때 그 시작 조건을 만족할 노드가 필요합니다. init container의 피크와 일반 컨테이너의 지속 사용량을 각각 측정하고, Pod 계산에서 어떤 값이 지배적인지 Kubernetes 문서와 배포 도구의 동작을 확인하세요.

### sidecar는 누가 책임져야 하나

서비스 mesh 프록시, 로그 수집기, 인증 보조 컨테이너 같은 sidecar는 플랫폼 팀이 주입해도 애플리케이션 Pod의 용량에는 포함됩니다. 애플리케이션 팀이 본 컨테이너 request만 계산하고 플랫폼 팀이 sidecar를 별도 비용으로 보지 않으면, 실제 Pod 밀도가 예상보다 낮거나 메모리 압박이 높아질 수 있습니다. 기본 sidecar 프로파일을 제공하고, 특수한 트래픽·로그량이 있는 서비스는 예외를 검토하는 협업이 필요합니다.

### batch와 API를 같은 노드에 둬도 되나

배치는 짧은 시간 CPU·I/O·메모리를 크게 쓸 수 있고, API는 낮은 지연을 요구할 수 있습니다. request와 limit만으로 두 워크로드의 경쟁을 항상 해결할 수는 없습니다. node affinity, taint/toleration, PriorityClass, 별도 node pool, 실행 시간 분리를 검토하세요. 특히 월말 정산과 사용자 트래픽이 겹치는 사업에서는 정상 평균이 아니라 동시 피크가 용량 계획의 기준이 됩니다.

### memory limit과 애플리케이션 캐시

캐시는 DB 부하를 줄이지만 메모리 사용량의 상한을 불명확하게 만들 수 있습니다. size-based eviction, TTL, 최대 항목 수 중 무엇이 실제로 작동하는지 확인하고, 캐시가 여러 Pod에서 중복되는 비용도 계산해야 합니다. `limit` 바로 아래까지 캐시를 허용하면 작은 입력 burst에도 OOMKilled될 여유가 없습니다. 애플리케이션이 사용할 수 있는 메모리 예산을 cache·heap·buffer·thread로 나눠 설계하는 편이 안전합니다.

## 점진적으로 적용하는 방법

이미 수십 개 서비스가 request와 limit 없이 운영 중이라면 한 번에 엄격한 정책을 적용하지 마세요. 먼저 주요 서비스의 현재 사용량과 장애 이력을 수집하고, 템플릿에 보수적인 기본값과 설명을 추가합니다. 다음으로 새 서비스와 변경이 잦은 서비스부터 실제 관찰값을 근거로 값을 정하고, Pending·OOMKilled·throttling 사건을 리뷰합니다. 마지막에 LimitRange나 Quota 같은 강제 정책을 도입하면 배포 실패 원인을 설명할 준비가 됩니다.

이 과정에서 숫자가 계속 변하는 것은 실패가 아닙니다. 워크로드와 트래픽이 변하면 선언도 갱신되어야 합니다. 다만 값이 왜 바뀌었는지, 어떤 지표를 보았는지, 변경 뒤 어떤 결과가 나왔는지를 남기면 추측에 의존하지 않게 됩니다. 리소스 관리는 일회성 최적화가 아니라 서비스의 운영 특성을 학습하는 반복 과정입니다.

## 리소스 문제를 커뮤니케이션하는 방법

인프라 담당자가 “request를 올려야 한다”고 말할 때 애플리케이션 팀은 비용과 배포 지연을 걱정할 수 있습니다. 반대로 애플리케이션 팀이 “limit을 올려 달라”고 말할 때 인프라 팀은 노드 안정성을 걱정할 수 있습니다. 이 대화를 숫자 하나의 찬반으로 만들지 않으려면, 사용자 영향과 관찰 증거를 함께 제시해야 합니다. 예를 들어 특정 시간대에 OOMKilled가 발생했고 입력 크기와 재시작이 상관관계를 보인다는 사실, request를 올리면 필요한 노드 수가 얼마나 바뀌는지, 대안으로 입력 제한이나 queue를 둘 수 있는지를 함께 논의합니다.

서비스 수준 목표(SLO)가 있다면 리소스 지표를 그 목표와 연결합니다. CPU 사용률이 90%라는 사실 자체보다, 그 시점에 p95 응답 시간이 목표를 넘었는지, 오류율이 늘었는지, 자동 확장이 제때 일어났는지가 중요합니다. Node utilization이 낮아도 실제 장애가 없을 수 있고, utilization이 높아도 중요한 서비스가 격리되어 정상일 수 있습니다. 측정값의 맥락을 공유하면 불필요한 overprovisioning과 위험한 underprovisioning 둘 다 줄일 수 있습니다.

### 장애 후에는 무엇을 남길까

OOMKilled나 노드 압박 사고가 지나간 뒤에는 단순히 limit을 바꾼 커밋만 남기지 말고, 영향을 받은 workload와 시간, 실제 사용량, 종료 사유, 입력·배치·배포와의 관계, 즉시 조치와 장기 조치를 기록합니다. 즉시 조치는 replica 증가나 limit 조정일 수 있고, 장기 조치는 메모리 누수 수정, cache 상한, workload 분리, 용량 계획 개선일 수 있습니다. 둘을 구분하면 같은 사고가 반복될 때 임시 조치가 영구 해결책으로 오해되는 일을 막을 수 있습니다.

사고에서 확인한 request·limit 값은 다음 배포에서도 유효하다는 보장이 없습니다. 트래픽 증가, 의존 라이브러리 교체, 새로운 feature flag, 다른 node instance type이 리소스 형태를 바꿀 수 있습니다. 따라서 이벤트가 없어도 정기적으로 핵심 서비스의 관찰값을 검토하는 것이 좋습니다. 이 검토는 수치를 매번 바꾸기 위한 회의가 아니라, 선언과 현실의 차이를 조기에 발견하는 안전 점검입니다.

## 운영자가 바로 확인할 명령과 화면

문제가 난 Pod를 볼 때는 먼저 `kubectl describe pod`의 Events에서 스케줄 실패, OOMKilled, probe 실패, eviction 같은 사건을 확인합니다. 이어서 `kubectl get pod -o wide`로 어느 노드에 배치됐는지, Deployment의 replica와 Ready 수가 기대와 같은지 봅니다. Metrics Server 또는 조직의 모니터링 도구에서는 Pod·container별 CPU, memory working set, restart count를 확인합니다. 명령 하나의 출력만으로 원인을 단정하지 않고 이벤트·상태·시간 그래프를 맞추는 습관이 중요합니다.

노드 관점에서는 allocatable, requested resources, memory pressure, disk pressure, 실제 사용량을 구분합니다. Node가 `NotReady`가 된 사건과 특정 Pod의 OOMKilled는 같은 시간에 생겨도 인과관계가 아닐 수 있습니다. 배포, autoscaler, 대량 batch, 이미지 pull, 다른 namespace workload가 무엇을 했는지 타임라인을 확인하세요. 이 순서는 문제를 해결하기보다 먼저 증거를 잃지 않도록 합니다.

### 값 변경의 안전한 범위

한 번의 장애 뒤 모든 workload의 limit을 일괄로 두 배 늘리는 방식은 위험합니다. 우선 영향 Pod와 같은 형태의 Pod를 좁혀 수정하고, 충분한 클러스터 여유와 롤백 방법을 확인한 뒤 배포합니다. 값 변경이 HPA 비율, quota, node 수, 비용에 주는 영향을 적고, 배포 후 짧은 기간이라도 이전과 같은 지표를 봅니다. 작은 범위에서 증거를 쌓아 확장하는 방식이 큰 장애를 피합니다.

리소스 설정은 팀이 아는 실제 서비스 특성으로 계속 개선되어야 합니다. 중요한 것은 완벽한 첫 값이 아니라, 값이 틀렸을 때 사용자 영향 전에 알아채고 안전하게 고칠 수 있는 관찰과 변경 과정입니다.

### 문서화할 최소 정보

각 서비스 매니페스트에는 숫자만 남기지 말고, request와 limit을 정한 근거를 가까운 문서에 기록하세요. 어떤 부하 또는 입력 범위를 기준으로 했는지, sidecar를 포함하는지, HPA의 최소·최대 복제본은 무엇인지, OOM 또는 throttling이 생겼을 때 확인할 대시보드와 담당자는 누구인지 적으면 좋습니다. 이 정보는 신규 담당자가 값을 변경할 때 과거의 실험을 다시 반복하지 않게 합니다.

특히 비용 절감 작업에서는 request를 내리기 전 사용자 영향 지표와 노드 여유를 함께 합의해야 합니다. 절감 전후의 node 수만 비교하면 위험을 놓칠 수 있습니다. 지연, 오류, restart, autoscaling 대기를 일정 기간 비교하고 문제가 없는지 확인한 뒤 확장하는 방식이 안전합니다. 안정성과 비용은 둘 중 하나를 포기하는 선택이 아니라, 관찰 가능한 근거로 균형을 찾는 문제입니다.

## 마무리

request는 배치의 약속이고, limit은 실행의 경계입니다. CPU throttling과 메모리 OOMKilled가 서로 다른 실패 양상을 만든다는 점, QoS가 압박 상황의 우선순위와 연결된다는 점을 이해하면 리소스 숫자를 더 안전하게 다룰 수 있습니다. 평균값 하나로 결정하지 말고 실제 부하·기동·예외 입력을 관찰하고, Pod 설정과 노드 용량·autoscaling을 함께 검증하세요.
