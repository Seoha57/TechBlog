## 먼저 답하기

### Q. Kubernetes를 쓰면 서비스 메시가 반드시 필요한가요?

A. 아닙니다. Kubernetes의 Service와 DNS만으로도 많은 서비스는 통신할 수 있습니다. 서비스 메시(service mesh)는 서비스 간 통신에 인증, 암호화, 재시도, 타임아웃, 세밀한 트래픽 분배, 일관된 관찰성을 추가하고 싶을 때 선택하는 별도 계층입니다. 서비스 수가 적고 통신 규칙도 단순하다면, 애플리케이션 설정과 표준 네트워크 정책이 더 이해하기 쉽고 운영 비용도 낮을 수 있습니다.

### Q. 서비스 메시를 넣으면 보안과 장애 대응이 자동으로 해결되나요?

A. 아닙니다. 메시가 암호화와 정책을 적용할 수는 있지만, 어떤 서비스가 누구에게 접근할 수 있는지, 인증서를 어떻게 교체할지, 재시도가 중복 요청을 만들지 않는지, 장애 때 어느 지표를 볼지는 여전히 설계해야 합니다. 기능을 프록시에 옮긴다고 책임까지 사라지는 것은 아닙니다.

## 먼저 알아둘 기반 기술

### 서비스 간 통신과 동서 트래픽

웹 서비스는 외부 사용자의 요청을 받는 API 서버만으로 끝나지 않는 경우가 많습니다. 주문 서비스가 결제 서비스와 재고 서비스를 호출하고, 재고 서비스가 이벤트 브로커와 데이터베이스를 사용하며, 백그라운드 작업자가 다시 주문 상태를 갱신할 수 있습니다. 데이터센터 또는 클러스터 안에서 서비스끼리 오가는 통신을 동서(east-west) 트래픽이라고 부릅니다. 반대로 사용자가 인터넷에서 서비스로 들어오는 통신은 남북(north-south) 트래픽이라고 부르는 일이 많습니다.

Kubernetes에서 Service는 바뀌는 Pod 주소 대신 안정적인 이름과 가상 IP를 제공합니다. DNS로 `payment.default.svc.cluster.local` 같은 이름을 찾고, kube-proxy 또는 데이터 플레인이 Pod 엔드포인트로 요청을 보냅니다. 이 구조는 발견(discovery)과 기본 부하 분산에 유용하지만, 호출한 서비스의 신원, 요청별 재시도 규칙, 암호화, 상세 지연 시간 같은 요구를 자동으로 해결하지는 않습니다.

### 프록시와 제어 영역

서비스 메시의 데이터 영역(data plane)은 실제 요청을 전달하는 프록시 집합입니다. Sidecar 방식에서는 애플리케이션 Pod 옆에 프록시 컨테이너가 함께 실행되고, 애플리케이션이 보내고 받는 트래픽이 프록시를 지나도록 구성합니다. Envoy 같은 프록시는 TLS, 라우팅, 재시도, 메트릭 수집을 담당할 수 있습니다. 애플리케이션 코드가 모든 네트워크 세부 사항을 직접 구현하지 않아도 되는 장점이 있습니다.

제어 영역(control plane)은 프록시에 설정과 인증서 정보를 배포합니다. 어떤 서비스가 어떤 서비스로 갈 수 있는지, 어느 버전에 트래픽을 몇 퍼센트 보낼지, 인증서를 언제 갱신할지 같은 정책을 중앙에서 관리할 수 있습니다. 다만 중앙이라는 말은 단일 장애점이어도 된다는 뜻이 아닙니다. 제어 영역이 일시적으로 불안정할 때 이미 동작 중인 프록시가 어떤 설정을 계속 쓸지, 새 Pod가 필요한 설정을 받을 수 있는지, 운영자가 어떻게 상태를 확인할지 알아야 합니다.

### mTLS와 서비스 신원

TLS(Transport Layer Security)는 전송 중인 데이터를 암호화하고 서버의 신원을 확인하는 프로토콜입니다. mTLS(mutual TLS)는 서버뿐 아니라 클라이언트도 인증서를 제시해 서로의 신원을 확인하는 방식입니다. 메시에서 mTLS를 쓰면 "이 IP가 내부망에 있다"는 약한 믿음 대신, 워크로드가 가진 인증서와 서비스 계정을 이용해 통신 상대를 식별할 수 있습니다.

그러나 mTLS는 권한 부여 자체와 다릅니다. 주문 서비스가 재고 서비스임을 증명하더라도, 모든 재고 API를 호출해도 되는지는 별도 정책이 판단해야 합니다. 인증(authentication)은 누구인지 확인하는 일이고, 인가(authorization)는 그 주체가 특정 행동을 해도 되는지 결정하는 일입니다. 메시 정책과 애플리케이션의 업무 권한을 섞으면, 네트워크는 안전해 보여도 고객·조직·역할 단위의 규칙이 빠질 수 있습니다.

## 서비스 메시가 제공하는 핵심 기능

### 암호화와 인증서 수명주기

서비스 메시의 매력은 모든 팀이 각각 인증서를 발급하고 갱신하는 부담을 줄일 수 있다는 점입니다. 프록시가 mTLS 연결을 맺고 제어 영역이 짧은 수명의 인증서를 배포하면, 애플리케이션은 평문 HTTP처럼 보이는 로컬 연결만 처리하면서도 Pod 간 구간을 암호화할 수 있습니다. 하지만 "자동"이라는 설명만 믿으면 위험합니다. 루트 신뢰 체인, 인증서 발급 주체, 회전 실패 시 동작, 시간 동기화, 만료 경보, 외부 서비스와의 TLS 경계는 운영 설계가 필요합니다.

예를 들어 새 정책을 엄격한 mTLS 모드로 바꾸면 메시 프록시를 거치지 않는 오래된 작업자나 외부 배치가 통신하지 못할 수 있습니다. 따라서 처음부터 전체 클러스터에 강제하기보다, 현재 평문 통신과 예외 경로를 목록화하고 관찰 모드·제한된 네임스페이스·단계적 강제 같은 방법을 검토합니다. 암호화 적용 자체가 성공 기준이 아니라, 필요한 업무 트래픽이 안전하게 계속 흐르는지가 성공 기준입니다.

### 트래픽 분배와 점진적 배포

서비스 메시의 라우팅 규칙은 같은 서비스의 여러 버전에 트래픽을 나눌 수 있게 합니다. 예를 들어 결제 서비스 v2에 내부 사용자 요청만 보내거나, 전체 요청 중 작은 비율만 보내고 오류율과 지연 시간을 비교할 수 있습니다. 이 기능은 canary 배포와 실험에 유용하지만, 트래픽을 나눴다는 사실만으로 안전한 배포가 되지는 않습니다.

버전 간 데이터베이스 스키마 호환성, 메시지 이벤트의 중복 처리, 세션 고정, 캐시 키, 롤백 가능성이 함께 준비되어야 합니다. 특히 POST 같은 쓰기 요청을 네트워크 오류 뒤에 무조건 재시도하면 중복 결제나 중복 생성이 생길 수 있습니다. 프록시의 retry 설정은 멱등성(idempotency), 요청 시간 제한, 하위 서비스의 처리 능력과 연결해 정해야 합니다. 인프라 계층이 애플리케이션의 업무 의미를 완전히 알 수 없다는 점을 잊으면 안 됩니다.

### 타임아웃·재시도·서킷 브레이커

타임아웃은 요청을 얼마나 기다릴지 정하는 제한입니다. 재시도는 일시 실패를 다시 호출하는 정책이고, 서킷 브레이커(circuit breaker)는 실패가 많은 상대에게 계속 요청을 보내지 않고 빠르게 실패하거나 대체 동작을 선택하게 하는 패턴입니다. 이들은 독립적인 옵션처럼 보이지만 서로 강하게 연결됩니다. API gateway의 전체 요청 시간보다 프록시의 요청 시간 제한이 더 길면 사용자는 이미 연결이 끊긴 뒤에도 하위 호출이 계속될 수 있습니다. 여러 계층이 각각 세 번씩 재시도하면 한 사용자 요청이 수십 번의 하위 요청으로 증폭될 수도 있습니다.

따라서 시간 예산을 위에서 아래로 나눕니다. 사용자가 기다릴 수 있는 전체 시간, gateway 처리 시간, 애플리케이션 작업 시간, 데이터베이스·외부 API 호출 시간을 구분하고 각 단계가 앞 단계의 마감 시각을 넘지 않게 합니다. 재시도는 오류 유형과 읽기·쓰기 성격에 따라 다르게 둡니다. DNS 일시 오류와 429 제한 응답, 인증 실패와 유효성 검증 오류를 같은 방식으로 재시도하면 장애를 키울 수 있습니다.

### 관찰성과 공통 메타데이터

프록시는 요청 수, 오류 비율, 응답 시간, TLS 상태 같은 네트워크 레벨 메트릭을 일관되게 수집할 수 있습니다. trace context를 전달하면 한 사용자 요청이 gateway, 여러 서비스, 메시 프록시를 지나간 경로를 연결할 수도 있습니다. 이는 각 팀이 다른 HTTP 클라이언트를 사용하더라도 공통된 최소 관찰성을 얻는 장점입니다.

그렇지만 프록시 메트릭만으로 업무 성공을 알 수는 없습니다. HTTP 200이라도 결제가 대기 상태로 남았을 수 있고, 이벤트 발행이 누락됐을 수 있으며, 사용자가 기대한 재고 수량과 다를 수 있습니다. 메시 관찰성은 연결·지연·오류를 읽는 기반이고, 주문 완료·정산·권한 검증 같은 도메인 메트릭은 애플리케이션이 책임져야 합니다. 두 관점을 같은 trace ID나 요청 ID로 연결할 때 장애 조사가 쉬워집니다.

## Sidecar와 다른 배포 모델

Sidecar는 애플리케이션 Pod마다 프록시 컨테이너가 하나 더 생기는 모델입니다. 격리와 정책 적용 위치가 명확하고, 애플리케이션 언어와 무관하게 기능을 적용하기 쉽습니다. 반면 Pod당 메모리·CPU가 늘고, 시작 순서와 readiness, 디버깅 경로가 복잡해질 수 있습니다. 수백 개 Pod에서 작은 프록시 비용이 합쳐지면 클러스터 용량 계획에도 영향을 줍니다.

일부 구현은 노드 수준 프록시나 ambient 같은 모델을 제공해 모든 Pod에 sidecar를 넣지 않는 방향을 제시합니다. 이런 모델은 자원 오버헤드와 주입 과정을 줄일 수 있지만, 기능 범위, 보안 경계, 성숙도, 운영 도구가 Sidecar와 같다고 가정하면 안 됩니다. 새로운 배포 방식은 실제 지원하는 L7 정책, mTLS, trace, 디버깅 절차를 확인하고 제한된 워크로드에서 먼저 검증해야 합니다.

서비스 메시가 Kubernetes 전용 기술인 것도 아닙니다. VM이나 물리 서버 환경에서도 프록시 기반 통신 정책을 구성할 수 있지만, 워크로드 신원과 서비스 발견, 인증서 배포의 방식이 달라집니다. 반대로 Kubernetes에 이미 Gateway API, NetworkPolicy, 인증 프록시, 관찰성 도구가 있다면 메시가 제공하는 기능과 겹치는 부분도 있습니다. 도구의 이름보다 현재 아키텍처에서 해결하지 못하는 문제가 무엇인지 먼저 적어야 합니다.

## 업무 예시: 주문·결제·재고 서비스

전자상거래 시스템에서 주문 서비스가 결제와 재고를 동시에 호출한다고 가정하겠습니다. 결제는 외부 provider와 통신하고, 재고는 내부 데이터베이스를 갱신합니다. 배포 중 결제 v2에만 일부 트래픽을 보내고 싶고, 서비스 간 평문 통신을 줄이며, 특정 서비스가 재고 API를 호출하는 것을 제한하고 싶다는 요구가 나올 수 있습니다.

먼저 호출 그래프를 만듭니다. 누가 누구를 어떤 프로토콜로 호출하는지, 동기 호출인지 비동기 이벤트인지, 민감 정보가 포함되는지, 장애 시 가능한 대체 경로가 있는지를 기록합니다. 그 다음 메시가 담당할 경계와 애플리케이션이 담당할 경계를 나눕니다. 메시에는 워크로드 mTLS, 서비스 단위의 네트워크 인가, 결제 버전별 트래픽 분배, 공통 지연·오류 메트릭을 맡길 수 있습니다. 애플리케이션에는 고객 권한, 결제 멱등 키, 재고 예약 상태, 사용자에게 보여 줄 오류 문구를 남깁니다.

배포 전에 테스트 환경에서 v1과 v2가 같은 요청 계약을 지키는지, timeout 뒤 결제가 중복되지 않는지, 재고 서비스가 느릴 때 주문 서비스가 정해진 시간 안에 실패 또는 대기 상태를 반환하는지 확인합니다. 프록시의 재시도 횟수와 애플리케이션 SDK의 재시도가 겹치지 않는지도 봅니다. 장애 주입은 실제 결제 provider를 무작정 멈추는 대신, 제한된 테스트 환경에서 timeout·연결 거절·5xx를 만들어 관찰합니다.

운영에서 오류율이 늘면 메시 대시보드만 보지 않고, 어느 route와 어느 버전에서 증가하는지, DNS·TLS handshake·연결 풀·외부 provider 응답 중 어느 구간인지 trace와 로그를 대조합니다. 이후 트래픽을 v1로 되돌릴지, 특정 기능을 줄일지, provider 제한을 기다릴지 결정합니다. 메시가 빠른 라우팅 변경을 돕지만, 업무적 판단과 고객 커뮤니케이션을 대신하지는 않습니다.

## 정책을 선언으로 관리할 때의 주의점

메시 구현체는 가상 서비스, destination rule, authorization policy, peer authentication처럼 여러 선언 리소스를 제공합니다. 선언형 구성은 변경 내용을 코드 리뷰하고 버전 관리하기 좋지만, 리소스가 많아질수록 최종 효과를 한 파일만 보고 이해하기 어려워집니다. 같은 서비스에 namespace 기본 정책, 워크로드 선택자 정책, 예외 정책이 겹치면 어떤 규칙이 우선하는지 운영자가 알아야 합니다. 정책 이름과 라벨 규칙, 소유 팀, 적용 범위를 일관되게 정하는 이유입니다.

정책 작성자는 먼저 기본 거부인지 기본 허용인지 선택해야 합니다. 기본 허용은 도입 초기에 기존 통신을 덜 끊는 장점이 있지만, 새 서비스가 의도하지 않은 대상에 접근할 여지를 남깁니다. 기본 거부는 명시적 경계를 만들기 좋지만 호출 관계 목록이 불완전하면 업무 장애를 일으킬 수 있습니다. 실제 조직에서는 관찰과 문서화를 거쳐 특정 namespace부터 엄격한 정책으로 전환하는 식의 단계적 방법이 현실적입니다.

정책의 대상은 IP 주소보다 서비스 계정과 workload label처럼 배포에 따라 바뀌지 않는 식별자를 사용하는 편이 안전합니다. 다만 label은 임의로 붙일 수 있으므로, 누가 어떤 label을 변경할 수 있는지 Kubernetes RBAC와 admission 정책으로 함께 보호해야 합니다. 메시 인가 정책만 단단해도 workload가 신뢰받는 label을 마음대로 얻을 수 있다면 경계가 약해집니다. 인프라 보안은 한 리소스의 YAML이 아니라 배포 권한과 신원 체인의 조합입니다.

## 장애를 조사하는 계층적 순서

메시가 있는 환경에서 503을 본다고 해서 곧바로 프록시 결함이라고 판단하면 안 됩니다. 먼저 애플리케이션이 readiness를 통과했는지, Service selector가 예상 Pod를 선택하는지, EndpointSlice에 대상이 있는지 확인합니다. 그다음 DNS가 올바른 이름을 해석하는지, NetworkPolicy가 포트와 방향을 허용하는지, 프록시가 필요한 listener와 cluster 설정을 받았는지, mTLS 협상이 맞는지 차례로 좁힙니다. 마지막으로 애플리케이션 로그와 하위 의존성의 상태를 봅니다.

조사에 필요한 진단 도구와 로그 접근 권한은 평소에 정해 두어야 합니다. 장애 때 모든 개발자에게 클러스터 관리자 권한을 주는 방식은 빠를 수 있지만 장기적으로 위험합니다. 읽기 전용 상태 조회, 제한된 namespace의 프록시 설정 확인, 승인된 로그 검색처럼 역할별 도구를 제공하면 진단과 통제를 함께 유지할 수 있습니다. 또한 프록시 로그를 무조건 debug로 높이면 비용과 민감 정보 노출이 커질 수 있으므로, 표준 로그 수준과 임시 조사 절차를 구분합니다.

## 배포와 업그레이드 전략

서비스 메시 자체도 운영해야 하는 소프트웨어입니다. 제어 영역 버전과 프록시 버전의 호환성, Kubernetes 버전 지원 범위, CRD 변경, 사이드카 주입 webhook의 가용성을 확인해야 합니다. 프록시 이미지의 취약점 패치나 인증서 구성 변경은 애플리케이션 코드 변경 없이도 모든 Pod에 영향을 줄 수 있습니다. 따라서 애플리케이션 배포와 마찬가지로 작은 cluster 또는 namespace에서 먼저 적용하고, 메트릭·로그·새 Pod 기동 성공률을 관찰하며 확대하는 방식이 필요합니다.

업그레이드 전에는 현재 정책과 라우팅 구성이 새 버전에서도 같은 의미를 가지는지, 더 이상 지원되지 않는 필드가 없는지, rollback을 위해 어떤 이미지와 설정을 보관해야 하는지 확인합니다. control plane을 되돌릴 수 있어도 이미 새 프록시가 주입된 Pod와의 호환성이 문제가 될 수 있습니다. 문서의 빠른 설치 명령만으로 production에 적용하지 말고, 지원 매트릭스와 프로젝트의 업그레이드 안내를 기준으로 변경 계획을 만드세요.

## 도입 결과를 평가하는 질문

도입 뒤에는 프록시 수나 정책 파일 수를 성공 지표로 삼지 않습니다. 인증서가 자동 갱신되고 있는지, 평문 예외가 줄었는지, 중요한 서비스 호출의 오류·지연을 한 요청 단위로 조사할 수 있는지, 트래픽 변경을 되돌리는 시간이 줄었는지처럼 실제 문제를 해결했는지 봅니다. 반대로 Pod 시작 시간이 길어졌거나 resource request가 부족해 scheduling 실패가 늘었거나, 정책을 이해하는 사람이 너무 적어 변경이 막힌다면 비용을 함께 기록해야 합니다.

이 평가는 직접 운영 성과를 약속하는 내용이 아닙니다. 각 조직의 데이터와 제약이 다르므로, 시범 범위에서 기준선을 먼저 정하고 변화 전후를 같은 방식으로 보자는 제안입니다. 메시의 기능이 많다는 사실보다, 팀이 더 빠르게 안전한 결정을 내릴 수 있는지가 계속 사용할 이유가 됩니다.

## 테스트 환경에서 확인할 시나리오

서비스 메시 도입 테스트는 정상 요청 하나가 통과하는지로 끝나면 안 됩니다. 먼저 메시가 적용된 Pod와 적용되지 않은 Pod가 의도한 방식으로 통신하는지 확인합니다. 다음으로 잘못된 서비스 계정, 허용되지 않은 namespace, 잘못된 포트에서 요청했을 때 정책이 거절하는지 봅니다. mTLS를 강제한 뒤에는 오래된 client나 배치 작업이 예외 경로로 평문 통신하지 않는지, 인증서가 갱신된 뒤에도 연결이 지속되는지 살핍니다. 정책이 보안을 높이면서 필요한 업무를 끊지 않는지 확인하는 과정입니다.

트래픽 정책은 오류 상황에서 더 중요합니다. backend의 응답을 의도적으로 늦추고 timeout이 전체 요청 예산 안에서 작동하는지 확인합니다. 연결을 거절하거나 제한된 5xx를 반환해 재시도 횟수가 예상대로인지, 쓰기 요청에는 중복 실행 위험이 없는지 검토합니다. 일부 Pod를 readiness 실패로 만들었을 때 프록시가 준비되지 않은 대상으로 요청을 보내지 않는지, 한 zone을 비운 상황에서 scheduling과 traffic이 어떤 순서로 회복되는지도 볼 수 있습니다. 실제 운영 장애를 무작정 재현하기보다 격리된 환경에서 가설과 중단 기준을 두고 검증해야 합니다.

관찰성 테스트도 포함합니다. 하나의 테스트 요청에 공통 trace ID가 gateway와 서비스 로그, 프록시 메트릭에 연결되는지 확인합니다. 정책 거절과 인증 실패가 단순한 403·503 숫자만 남기지 않고, 권한 문제인지 handshake 문제인지 조사할 수 있는 신호를 제공하는지 봅니다. 그러나 요청 본문이나 인증 헤더가 trace에 그대로 남지는 않는지도 함께 확인해야 합니다. 관찰을 위해 비밀을 수집하는 실수를 피하는 것이 중요합니다.

## 서비스 메시 없이 해결하는 선택

메시 도입을 검토한 결과, 더 작은 해결책이 적합할 수 있습니다. 서비스 간 TLS가 필요한 것이 핵심이라면 애플리케이션 또는 ingress·gateway에서 인증서를 관리하는 방법부터 검토할 수 있습니다. Pod 간 통신 범위를 제한하는 것이 목적이라면 NetworkPolicy와 서비스 계정, RBAC가 충분할 수 있습니다. 공통 HTTP timeout과 retry가 필요하다면 조직의 클라이언트 라이브러리나 API gateway 정책으로 통일할 수도 있습니다. 분산 추적만 필요하다면 OpenTelemetry 계측을 먼저 도입하는 편이 메시 전체보다 단순할 수 있습니다.

이 대안들은 메시보다 열등하다는 뜻이 아닙니다. 필요한 문제에 가장 작은 도구를 쓰는 것이 운영 복잡성을 줄입니다. 다만 팀마다 다른 구현을 반복해 보안·재시도·관찰성이 계속 불일치하고, 다수 서비스의 공통 경계를 중앙에서 관리해야 하는 상황이라면 메시의 비용을 정당화할 수 있습니다. 도입 판단 문서에는 해결하려는 문제, 대안, 예상 비용, 되돌림 경로를 함께 써 두면 유행이나 제품 이름이 아니라 근거로 선택할 수 있습니다.

### 용량과 지연 시간의 현실적인 경계

프록시를 통과하면 직렬화, 연결 관리, TLS, 정책 검사 때문에 일정한 자원과 지연이 추가될 수 있습니다. 이 비용은 서비스마다 같지 않고 요청 크기, 연결 재사용, CPU 여유, 암호화 방식에 따라 달라집니다. 따라서 "메시는 항상 느리다" 또는 "오버헤드는 무시할 수 있다"처럼 단정하지 말고, 지연에 민감한 경로와 일반 API 경로를 나누어 용량 계획과 검증 기준을 세워야 합니다. 특히 CPU request가 너무 낮으면 프록시와 애플리케이션이 같은 Pod 안에서 자원을 경쟁해, 원인을 알기 어려운 tail latency가 생길 수 있습니다.

운영자는 Pod의 애플리케이션 컨테이너와 프록시 컨테이너 자원을 따로 관찰하고, HPA가 어떤 메트릭을 보고 스케일하는지도 확인합니다. 애플리케이션 CPU만 보고 replica를 늘렸는데 프록시 연결 수나 노드 네트워크가 병목이면 기대한 효과가 나지 않을 수 있습니다. 반대로 메시 지표 하나가 높다고 무작정 Pod를 늘리면 하위 데이터베이스와 외부 API를 더 압박할 수 있습니다. 서비스 메시도 전체 시스템 용량 안에서 운영해야 합니다.

### 팀 간 변경 절차

공용 메시 정책을 바꾸는 일은 네트워크 설정 변경이면서 여러 제품 팀의 배포에 영향을 줄 수 있습니다. 플랫폼 팀은 정책 변경의 대상 namespace와 예상 영향을 알리고, 서비스 팀은 필요한 호출·예외·업무 영향 정보를 확인하는 절차를 가져야 합니다. 긴 승인 회의가 목적이 아니라, 호출 관계를 모르는 사람이 조용히 통신을 차단하는 사고를 줄이기 위한 최소 협업입니다. 긴급 장애 대응에서는 임시 예외의 만료 시각과 사후 검토를 남겨 예외가 영구 규칙이 되지 않게 합니다.

변경 요청에는 호출 주체와 대상, 포트·프로토콜, 필요한 기간, 사용자 영향, 되돌림 방법을 적습니다. 이 정보가 있으면 리뷰어는 "통신을 허용해 달라"는 막연한 요청 대신 실제 경계를 판단할 수 있습니다. 정책을 적용한 뒤에는 허용·거절 로그와 핵심 업무 흐름을 확인하고, 예상치 못한 의존성이 발견되면 호출 관계 문서도 함께 고칩니다. 서비스 메시의 정책은 살아 있는 서비스 구조를 표현하는 문서이기도 합니다.

서비스 수가 늘수록 공통 규칙의 이름과 위치도 중요해집니다. 팀마다 timeout 단위와 retry 용어가 다르면 같은 정책을 읽고도 다른 기대를 가질 수 있습니다. 플랫폼 문서에는 기본값, 서비스 팀이 바꿀 수 있는 범위, 고위험 예외의 승인 기준을 명시하세요. 그렇다고 모든 값을 중앙에서 고정하면 서비스의 특수한 요구를 막을 수 있으므로, 변경 가능 범위와 책임자를 같이 적는 균형이 필요합니다.

마지막으로 정책은 배포 후에도 실제 호출 흐름과 비교해야 합니다. 사용하지 않는 예외는 제거하고, 새 서비스가 추가될 때 필요한 통신과 권한을 설계 단계에서 반영하세요. 이렇게 관리하면 메시가 보이지 않는 중간 계층이 아니라, 팀이 함께 유지하는 명확한 통신 계약이 됩니다.

새 규칙을 적용하기 전에는 해당 서비스 팀이 재현 가능한 확인 절차를 가지고 있는지도 살펴야 합니다. 정책 변경이 안전하려면 선언 파일과 실제 동작, 두 가지가 같은 약속을 표현해야 합니다.

## 도입 전에 확인할 비용

첫째는 자원 비용입니다. 프록시가 추가하는 CPU, 메모리, 연결 수, 인증서 갱신 트래픽, 로그·메트릭 저장 비용을 추산해야 합니다. 기본값을 모든 namespace에 넣기보다, 실제로 필요한 서비스 집합부터 시작하면 비용과 문제를 읽기 쉽습니다. 둘째는 운영 복잡성입니다. 애플리케이션 로그 외에 프록시 로그, 제어 영역 상태, 정책 CRD, 인증서 상태를 봐야 할 수 있습니다. 장애 대응자가 이를 이해하지 못하면 기능이 많아도 복구는 느려집니다.

셋째는 디버깅 비용입니다. 요청이 애플리케이션에 도달하지 않을 때 원인이 DNS, NetworkPolicy, 프록시 리스너, mTLS, route 규칙, 서비스 selector, readiness 중 어디인지 계층적으로 좁혀야 합니다. runbook에는 "메시를 끈다" 같은 광범위한 조치보다, 어떤 상태와 명령·대시보드로 어느 경계를 확인할지 적는 편이 안전합니다. 넷째는 팀 소유권입니다. 플랫폼 팀이 공통 정책을 관리하더라도, 서비스 팀이 자신의 timeout·retry·SLO를 이해하고 변경할 수 있는 절차가 필요합니다.

## 한계와 적용 기준 Q&A

### Q. NetworkPolicy가 있으면 서비스 메시 보안은 필요 없나요?

A. NetworkPolicy는 Pod와 포트 수준의 통신 범위를 제한하는 데 유용합니다. 그러나 워크로드 신원을 이용한 mTLS, HTTP·gRPC 같은 L7 정책, 서비스별 세밀한 telemetry는 별도 기능일 수 있습니다. 두 기술은 대체 관계라기보다 서로 다른 계층의 경계를 만들 수 있습니다. 다만 요구가 단순하다면 NetworkPolicy만으로 충분할 수 있으므로, 기능 중복을 확인해야 합니다.

### Q. 모든 재시도를 프록시에 모으면 애플리케이션이 단순해지나요?

A. 네트워크성 일시 오류의 공통 처리는 단순해질 수 있지만, 프록시는 주문 생성이나 결제 승인처럼 업무 멱등성을 알지 못합니다. 쓰기 요청의 재시도와 보상 처리, 사용자에게 보여 줄 상태는 애플리케이션이 책임져야 합니다. 프록시와 SDK의 재시도 정책을 한 문서에서 함께 관리하세요.

### Q. 작은 서비스에도 메시를 도입해야 하나요?

A. 서비스 수가 적고 호출 관계가 단순하며, 이미 TLS·관찰성·정책 요구를 충족한다면 도입하지 않는 편이 합리적일 수 있습니다. 반대로 여러 팀이 공통된 보안·트래픽·관찰성 규칙을 반복 구현하고 있다면, 제한된 namespace에서 시범 도입해 비용과 효과를 비교할 이유가 생깁니다.

### Q. mTLS를 켜면 애플리케이션의 인증 코드는 없애도 되나요?

A. 아닙니다. mTLS는 워크로드 간 신원을 증명하는 데 도움이 되지만, 최종 사용자·조직·업무 권한을 판정하지 않습니다. API token, 세션, OAuth, 도메인 권한 검사처럼 애플리케이션의 인가 규칙은 별도로 유지해야 합니다.

## 마무리

서비스 메시는 마술처럼 네트워크를 안전하게 만드는 제품이 아니라, 서비스 간 통신의 공통 기능을 프록시와 정책으로 정리하는 아키텍처 선택입니다. mTLS, 트래픽 분배, timeout, 재시도, 관찰성은 강력하지만 모두 업무 의미와 운영 절차에 연결해야 합니다. 지금 해결하려는 문제가 공통 통신 규칙의 반복인지, 단순한 설정으로도 해결 가능한지부터 확인하고, 작은 범위에서 비용과 장애 대응 방식을 검증하며 확장하세요.
