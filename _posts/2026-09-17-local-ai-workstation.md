“개인 AI를 구축한다”는 말은 대단한 모델을 직접 학습시키는 일처럼 들릴 수 있습니다. 하지만 처음에는 훨씬 작은 목표가 적절합니다. 내 PC 또는 워크스테이션에서 공개 모델을 실행하고, 필요한 문서를 제한된 범위에서 찾아 답변하게 하며, 나중에는 내 프로그램이 그 모델을 호출할 수 있게 만드는 것입니다. 이 정도만으로도 로컬 AI가 무엇을 해결하고 무엇을 해결하지 못하는지 충분히 배울 수 있습니다.

이 글에서 말하는 **로컬 LLM(Local Large Language Model)**은 모델 추론을 내 PC나 내가 관리하는 워크스테이션에서 수행하는 구성입니다. **추론(inference)**은 이미 학습된 모델이 입력을 받아 다음 토큰을 생성하는 과정입니다. 모델을 처음부터 학습하는 일과는 구분해야 합니다. **RAG(Retrieval-Augmented Generation)**는 모델이 문서를 새로 학습하는 대신, 질문과 관련된 문서 조각을 찾아 프롬프트에 함께 넣어 답변의 근거를 보강하는 방식입니다.

이 글은 특정 장비에서 직접 구축하거나 성능을 측정한 기록이 아닙니다. Ollama, LM Studio, Open WebUI의 공개 문서와 NIST의 생성형 AI 위험 관리 자료를 바탕으로, 구축 전에 알아둘 구성 요소와 선택 기준을 설명하는 학습 글입니다.

## 1. 개인 AI는 하나의 앱이 아니라 작은 시스템이다

로컬 AI를 처음 접하면 LM Studio나 Ollama 같은 이름을 하나 설치하면 끝나는 것처럼 보일 수 있습니다. 실제로는 서로 다른 역할을 하는 구성 요소가 함께 있습니다. 역할을 나눠 이해하면 도구를 바꿔도 구조를 유지할 수 있습니다.

| 구성 요소 | 하는 일 | 초보자에게 중요한 질문 |
| --- | --- | --- |
| 사용자 인터페이스 | 채팅, 문서 업로드, 대화 기록 제공 | 내가 문서를 어느 화면에 올리는가? |
| 로컬 실행기(runtime) | 모델을 메모리에 올리고 추론·API 요청 처리 | 모델은 어느 PC에서 실제로 실행되는가? |
| 모델 파일 | 질문에 답하고 요약·분류·생성을 수행 | 언어, 용도, 크기, 라이선스는 맞는가? |
| 문서 검색(RAG) | 관련 문서를 찾아 답변에 근거 추가 | 어떤 문서를 색인하고, 누가 접근하는가? |
| 연동 도구 | 파일·웹·API 같은 외부 기능 연결 | 읽기와 쓰기 권한은 분리됐는가? |

예를 들어 LM Studio는 데스크톱 앱에서 로컬 모델을 내려받아 실행하고, 문서와 대화하거나 로컬 서버를 열 수 있도록 안내합니다. [LM Studio 앱 문서](https://lmstudio.ai/docs/app)는 Windows·macOS·Linux에서 로컬 모델 실행, 문서 기반 대화, 로컬 API 사용을 각각 별도 기능으로 설명합니다. 즉 “대화가 된다”와 “내 프로그램에서 API로 부른다”, “내 문서를 검색한다”는 서로 다른 단계입니다.

Ollama는 모델 실행과 API 사용에 초점을 둔 도구입니다. Ollama API는 기본적으로 `http://localhost:11434/api`에서 제공되며, 로컬 프로그램이 모델에 요청하는 형태를 문서로 확인할 수 있습니다. [Ollama API 소개](https://docs.ollama.com/api/introduction) 이 주소에 요청할 수 있다는 사실은 편리하지만, 동시에 포트가 어떤 인터페이스에 열려 있는지와 다른 기기가 접근 가능한지 점검해야 한다는 뜻이기도 합니다.

## 2. “로컬”이라는 말의 경계를 먼저 정하기

로컬 AI에서 가장 흔한 오해는 “내 PC에서 보이니까 데이터도 모두 내 PC에만 있다”는 생각입니다. 실제로는 데이터 흐름을 나눠야 합니다.

1. **모델 다운로드**: 공개 모델 파일을 처음 내려받는 과정은 네트워크를 사용합니다.
2. **추론**: 내려받은 모델을 내 PC에서 실행하면 입력과 생성 과정은 로컬에서 처리할 수 있습니다.
3. **문서 RAG**: 문서를 어떤 프로그램이 읽고, 임베딩을 어느 모델이 만들며, 검색 색인을 어디에 저장하는지에 따라 데이터 위치가 달라집니다.
4. **외부 연결**: 웹 검색, 상용 LLM API, 원격 파일 저장소, MCP 서버를 붙이면 해당 요청과 필요한 맥락이 외부 서비스로 전달될 수 있습니다.

따라서 “로컬”은 제품 이름이 아니라 **각 단계의 데이터 경로를 확인하는 기준**으로 보는 편이 정확합니다. 예를 들어 개인 메모만 다루는 로컬 채팅은 비교적 단순합니다. 하지만 사내 문서를 RAG로 연결하고 외부 웹 검색까지 켜면 문서 내용, 검색 질의, 응답 로그가 어디에 남는지 확인해야 합니다.

NIST의 생성형 AI 위험 관리 자료도 AI의 신뢰성은 모델 자체뿐 아니라 시스템과 데이터의 보안·프라이버시·운영 맥락과 함께 검토해야 한다는 관점을 제시합니다. [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)와 [Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)은 개인 프로젝트에도 “무엇을 연결했고 어떤 위험을 감수하는가”를 기록하는 습관이 유용하다는 점을 보여줍니다.

## 3. 상용 앱 사용과 API 호출은 무엇이 다를까

브라우저에서 ChatGPT나 Claude 같은 상용 앱을 사용하는 것과, 내 PC의 프로그램이 해당 모델 API를 호출하는 것은 둘 다 클라우드 모델을 쓴다는 점에서는 같습니다. 하지만 누가 화면·요청 형식·도구·로그·비용 제한을 관리하는지가 다릅니다.

| 구분 | 상용 앱을 직접 사용 | 내 애플리케이션에서 API 호출 |
| --- | --- | --- |
| 사용자 화면 | 제공사가 만든 웹·데스크톱 화면 | 내가 만든 웹·스크립트·로컬 도구 화면 |
| 요청 구성 | 사용자가 화면에 입력 | 프로그램이 프롬프트·문서 조각·도구 정의를 조합 |
| 모델 호출 | 제공사 앱 내부에서 처리 | 내 프로그램이 API 키로 요청 |
| 도구 연결 | 앱이 제공하는 범위 안에서 사용 | 필요한 API·MCP 도구를 선택해 연결 |
| 운영 책임 | 제품 설정과 계정 정책을 따름 | 키 보관, 비용 제한, 로그, 오류 처리를 직접 설계 |

예를 들어 ChatGPT 화면에 기술 문서를 붙여 요약을 요청하는 것은 사용자가 상용 앱의 기능을 이용하는 일입니다. 반면 내가 만든 “개인 문서 요약기”가 문서를 로컬에서 검색한 뒤, 선택한 문서 조각과 질문을 OpenAI 또는 Anthropic API로 보내 답을 받는 것은 API 연동입니다. 후자의 경우 앱 화면이 내 PC에 있어도, API로 보낸 질문과 문서 조각은 외부 모델 추론에 사용됩니다. 따라서 사용자 인터페이스가 로컬이라는 사실만으로 데이터 처리가 로컬이라고 말할 수는 없습니다.

Anthropic의 Claude 모델은 공식적으로 API와 클라우드 플랫폼을 통해 접근하는 구조입니다. API 호출에는 계정과 API 키가 필요하며, 요청은 `https://api.anthropic.com`으로 전송됩니다. [Claude API 개요](https://platform.claude.com/docs/en/api/overview) OpenAI의 일반 API 모델도 같은 범주입니다. 이들은 내 앱에 연결할 수 있지만, 모델 가중치 자체를 내려받아 같은 PC에서 추론하는 방식은 아닙니다.

다만 OpenAI의 **gpt-oss**처럼 공개 가중치(open-weight)로 제공되는 모델은 예외입니다. gpt-oss는 Apache 2.0 라이선스로 모델 가중치를 내려받아 Ollama, LM Studio, vLLM 같은 실행기에서 내 인프라로 운영할 수 있습니다. 하지만 이것은 ChatGPT나 OpenAI API에서 제공되는 일반 GPT 모델과는 별도 모델이며, OpenAI API를 통해 제공되지 않습니다. [OpenAI gpt-oss 안내](https://help.openai.com/en/articles/11870455), [OpenAI Open Models](https://openai.com/open-models/)

### 3.1 로컬 전용, API 연동, 하이브리드의 선택 기준

개인 AI 구성은 보통 세 가지 중 하나입니다.

| 방식 | 모델 추론 위치 | 잘 맞는 상황 | 먼저 확인할 점 |
| --- | --- | --- | --- |
| 로컬 전용 | 내 PC·워크스테이션 | 공개 문서 요약, 오프라인 실험, 데이터 경계 학습 | 장비 자원, 모델 라이선스, 로컬 로그 |
| 상용 API 연동 | 제공사 클라우드 | 높은 품질 모델을 빠르게 사용, 기능 검증 | API 키, 비용, 전송 데이터, 서비스 정책 |
| 하이브리드 | 요청별 로컬 또는 클라우드 | 민감도·난이도에 따라 경로를 분리 | 어떤 기준으로 외부 전송을 허용하는가 |

하이브리드 구성이란 “로컬 모델과 상용 API를 둘 다 설치한다”는 말보다, 요청별로 모델 경로를 의도적으로 선택하는 방식입니다. 예를 들어 공개 기술 문서의 짧은 요약은 로컬 모델로 처리하고, 사용자가 외부 API 사용에 동의한 복잡한 코드 리뷰 요청만 상용 모델로 보내는 기준을 둘 수 있습니다. 이때 단순히 모델 이름을 바꾸는 것이 아니라, **어떤 요청이 왜 외부로 나갔는지**를 사용자가 알 수 있게 표시하고 로그에 남기는 것이 중요합니다.

```text
질문 수신
  ├─ 민감 문서 또는 외부 전송 금지 → 로컬 모델만 사용
  ├─ 공개 자료 + 고난도 작업 + 사용자 허용 → 상용 API 사용 가능
  └─ 판단이 모호함 → 외부 전송 전에 사용자에게 선택 요청
```

이 기준은 완벽한 자동 분류기가 아니라, 실수로 문서 내용을 외부 API에 보내지 않기 위한 첫 번째 안전장치입니다. 처음에는 자동 라우팅보다 “로컬 모델 사용”과 “상용 API로 보내기” 버튼을 분리하는 방식이 더 단순하고 검토하기 쉽습니다.

## 4. 시작 방식은 두 가지면 충분하다

처음부터 Ollama, Open WebUI, 벡터 데이터베이스, 에이전트, MCP 서버를 한 번에 조합할 필요는 없습니다. 구성 요소가 많아질수록 장애 원인과 데이터 경로를 분리하기 어려워집니다. 개인 학습의 시작점은 다음 두 가지 중 하나면 충분합니다.

### 4.1 GUI 중심: LM Studio로 로컬 모델과 문서 대화 이해하기

코드를 거의 쓰지 않고 시작하고 싶다면 LM Studio처럼 데스크톱 UI가 있는 도구가 편합니다. 모델을 내려받고 대화하는 단계와, 문서를 붙여 질문하는 단계를 화면에서 구분해 볼 수 있기 때문입니다. LM Studio 문서는 로컬 모델 실행과 문서 기반 대화, OpenAI 호환 형태를 포함한 로컬 서버 기능을 안내합니다. [LM Studio Developer 문서](https://lmstudio.ai/docs/developer)

이 방식에서의 첫 목표는 “가장 큰 모델을 실행한다”가 아니라 다음 세 가지를 확인하는 것입니다.

- 어떤 모델 파일이 내 장비의 메모리에 들어가는가
- 문서를 넣었을 때 답변이 어떤 근거를 사용했는가
- 대화 데이터와 모델 파일이 어느 경로에 저장되는가

예를 들어 공개 문서 한두 개만 넣고 “이 문서에서 요구하는 준비물은 무엇인가?”라고 질문해 볼 수 있습니다. 답변이 문서의 실제 내용과 맞는지, 문서 밖의 내용을 추측하지는 않는지를 확인하는 과정은 앞서 쓴 AI 평가 글의 작은 적용 사례가 됩니다. 이때 개인식별정보, API 키, 사내 기밀 문서는 넣지 않는 것이 기본입니다.

### 4.2 API 중심: Ollama로 로컬 모델 호출 흐름 이해하기

나중에 테스트 도구나 작은 웹 애플리케이션에서 모델을 호출하고 싶다면 Ollama처럼 로컬 API를 제공하는 도구가 이해하기 좋습니다. Ollama의 Quickstart와 API 문서는 로컬 모델을 실행하고 HTTP 요청으로 대화하는 기본 흐름을 제공합니다. [Ollama Quickstart](https://docs.ollama.com/quickstart), [Ollama API](https://docs.ollama.com/api/introduction)

아래 요청은 공식 API 형태를 단순화한 예시입니다. 모델 이름은 설치한 모델에 맞게 바꾸어야 하며, 실제 응답 구조와 옵션은 사용하는 버전의 문서를 확인해야 합니다.

```bash
curl http://localhost:11434/api/chat \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<local-model>",
    "messages": [
      {"role": "user", "content": "이 문장을 세 줄로 요약해줘."}
    ]
  }'
```

이 예시에서 중요한 것은 `localhost`입니다. 요청을 보낸 프로그램과 모델 실행기가 같은 PC에 있을 때만 접근되는지, 혹은 네트워크에 노출되도록 설정했는지에 따라 보안 범위가 달라집니다. 처음에는 같은 PC의 로컬 호출만으로 충분합니다. 다른 기기에서 쓰기 위해 포트를 열거나 터널을 구성하는 단계는 인증·방화벽·접근 제어를 별도로 설계할 때 추가하는 편이 안전합니다.

## 5. RAG는 “문서를 넣는 기능”보다 검색 설계에 가깝다

RAG는 Retrieval-Augmented Generation의 약자입니다. 일반적인 흐름은 문서를 작은 단위로 나누고, 질문과 가까운 문서 조각을 검색한 뒤, 그 내용을 모델 입력에 함께 제공하는 것입니다. Open WebUI 문서는 RAG를 여러 문서·웹 콘텐츠 등에서 관련 정보를 가져와 프롬프트에 추가하는 기술로 설명합니다. [Open WebUI RAG 문서](https://docs.openwebui.com/features/chat-conversations/rag/)

여기서 자주 생기는 오해를 정리해 보겠습니다.

| 오해 | 실제로 확인할 점 |
| --- | --- |
| 문서를 올리면 모델이 그 내용을 영구히 학습한다 | 대개는 문서 조각과 검색 색인을 만들고, 질문 때 관련 조각을 가져온다 |
| 로컬 RAG는 항상 정확하다 | 검색이 관련 문서를 찾지 못하거나, 모델이 문맥을 잘못 해석할 수 있다 |
| 문서를 많이 넣으면 무조건 좋아진다 | 오래된 문서·중복 문서·권한 없는 문서가 섞이면 근거 품질이 떨어질 수 있다 |
| 답변만 보면 충분하다 | 어떤 문서 조각을 근거로 삼았는지 확인해야 한다 |

예를 들어 “휴가 신청 마감일”을 묻는다고 해 보겠습니다. 문서 저장소에 2024년과 2026년 규정이 함께 있다면 최신 문서를 우선 찾도록 문서 메타데이터와 갱신일을 관리해야 합니다. 검색 결과에 오래된 규정만 들어오면 모델이 아무리 자연스럽게 답해도 내용은 틀릴 수 있습니다. 따라서 RAG의 품질은 모델 이름보다 문서 최신성, 분할 방식, 검색 범위, 출처 표시 방식에 크게 영향을 받습니다.

개인 학습 환경에서는 문서를 적게 시작하는 것이 좋습니다. 공개 매뉴얼 1~2개를 넣고, 답변마다 문서 제목이나 위치를 함께 확인합니다. 그다음 같은 질문을 표현만 바꿔 여러 번 해 보고, 관련 없는 문서를 가져오는지 관찰합니다. 이 작은 검증을 거친 뒤에야 문서 범위를 넓히는 편이 관리하기 쉽습니다.

## 6. 장비는 “권장 사양표”보다 작업 단위로 고르기

로컬 AI 장비 이야기는 곧바로 GPU 메모리 용량이나 모델 파라미터 수 비교로 흐르기 쉽습니다. 하지만 초보자가 먼저 정해야 할 것은 장비의 최고 사양보다 작업입니다. 짧은 문장 요약, 개인 문서 질의, 코드 보조, 여러 사용자의 동시 요청은 필요한 자원이 서로 다릅니다.

다음 요소가 서로 영향을 줍니다.

- **모델 크기**: 일반적으로 더 큰 모델은 더 많은 메모리를 요구할 수 있습니다.
- **양자화(quantization)**: 모델 가중치를 더 적은 비트로 표현해 메모리 사용을 줄이는 방식입니다. 품질·속도·메모리 사이의 선택이 필요합니다.
- **문맥 길이(context length)**: 한 번의 요청에 함께 넣을 수 있는 대화·문서의 양입니다. 문서 RAG에서 특히 중요합니다.
- **CPU·GPU·메모리**: 어떤 하드웨어를 쓰는지에 따라 추론 시간과 동시에 처리할 수 있는 요청 수가 달라집니다.
- **저장 공간**: 모델 파일, 문서 색인, 대화·로그가 누적될 수 있습니다.

그래서 “내 PC에 어떤 모델이 가장 좋을까?”보다 “내가 먼저 검증할 질문은 무엇이고, 그 질문에 필요한 문서와 응답 길이는 어느 정도인가?”를 정하는 편이 낫습니다. 예를 들어 개인 기술 문서 요약이 목표라면, 하나의 모델·한 폴더의 공개 문서·한 명의 사용자라는 작은 범위로 시작할 수 있습니다. 업무 팀이 함께 쓰는 서비스, 장시간 문서 검색, 여러 도구 호출은 그다음 단계의 문제입니다.

## 7. 문서·로그·도구 권한은 모델보다 먼저 정한다

개인 AI도 데이터를 다루기 시작하면 작은 운영 시스템이 됩니다. 다음 표는 로컬 AI를 켜기 전에 최소한 정리할 항목입니다.

| 항목 | 확인할 질문 | 초보자용 시작 기준 |
| --- | --- | --- |
| 입력 문서 | 어떤 문서를 업로드해도 되는가 | 공개 문서와 개인 비민감 메모만 사용 |
| 대화·로그 | 질문과 응답은 어디에 남는가 | 보관 위치와 삭제 방법을 먼저 확인 |
| 네트워크 | 외부 API·웹 검색을 쓰는가 | 기본은 로컬만, 외부 연결은 필요할 때만 |
| API 접근 | 로컬 포트가 누가 접근 가능한가 | 같은 PC의 `localhost`에서만 시작 |
| 도구 권한 | 파일 수정·티켓 생성 같은 행동이 가능한가 | 읽기 전용 도구부터, 쓰기는 나중에 분리 |
| 모델 출처 | 어떤 라이선스와 사용 조건이 있는가 | 모델 카드와 원문 저장소 확인 |

특히 “로컬 실행”과 “안전한 실행”은 같은 말이 아닙니다. 로컬 PC라도 브라우저 확장 기능, 네트워크 공유 폴더, 외부 API 키, 원격 접속 도구를 함께 쓰면 데이터 경계가 넓어집니다. NIST는 AI 시스템의 보안·회복력, 프라이버시, 투명성 같은 특성을 배포·사용·평가 전반에서 검토해야 한다고 설명합니다. [NIST AI RMF FAQ](https://www.nist.gov/itl/ai-risk-management-framework/ai-risk-management-framework-faqs)

처음에는 문서를 읽고 답하는 기능까지만 두고, 파일을 수정하거나 메일을 보내거나 이슈를 생성하는 도구는 연결하지 않는 편이 좋습니다. 다음 글에서 다룰 상용 에이전트·MCP 연계는 바로 이 “상태를 바꾸는 권한”을 어떻게 나눌지부터 시작해야 합니다.

## 8. 구축 순서를 작게 나누기

개인 AI를 한 번에 완성하려 하면 도구 설치에만 시간을 쓰게 됩니다. 아래처럼 작은 검증 단위로 나누면 각 단계에서 무엇이 문제인지 알기 쉽습니다.

1. **로컬 대화**: 공개 모델 하나를 실행하고 짧은 질문에 답하게 합니다.
2. **저장 위치 확인**: 모델 파일, 대화 기록, 로그가 저장되는 위치를 확인합니다.
3. **문서 RAG**: 공개 문서 한두 개만 넣고 답변 근거가 맞는지 확인합니다.
4. **로컬 API**: 같은 PC에서만 호출되는 API 요청을 하나 만들어 봅니다.
5. **평가 세트**: 자주 묻는 질문 5~10개로 답변·근거·금지 행동을 점검합니다.
6. **선택적 연동**: 필요성이 확인된 뒤에만 외부 API, 웹 검색, MCP 도구를 추가합니다.

이 순서는 “무조건 이 도구를 써야 한다”는 설치 가이드가 아닙니다. 문제가 발생했을 때 모델 실행 문제인지, 문서 검색 문제인지, API 노출 문제인지 분리하기 위한 순서입니다. 예를 들어 문서 답변이 부정확하다면 곧바로 더 큰 모델을 찾기보다, 먼저 검색된 문서 조각이 맞는지와 문서 버전이 최신인지 확인하는 편이 효과적일 수 있습니다.

## 마무리: 개인 AI의 첫 목표는 ‘작동’보다 경계 이해하기

개인 로컬 AI 구축의 첫 성과는 큰 모델을 실행하는 것이 아니라, 모델·문서·로그·외부 연결이 어디에 있는지 설명할 수 있게 되는 데 있습니다. 이 경계를 알아야 “이 문서는 로컬에만 남는가?”, “이 질문은 외부 API로 나가는가?”, “이 도구가 파일을 바꿀 수 있는가?” 같은 질문에 답할 수 있습니다.

처음에는 로컬 모델 하나와 공개 문서 몇 개로 충분합니다. 답변의 근거를 확인하고, 저장 위치를 확인하고, 같은 질문을 반복해 보며 한계를 기록해 보세요. 이 기록은 이후 구성 변경의 기준이 됩니다. 그 다음 단계에서 로컬 API를 연결하거나, 상용 AI·MCP 도구를 붙일 때도 어떤 기능을 추가하고 어떤 데이터 경계를 넓히는지 더 명확하게 판단할 수 있습니다.
