AI 챗봇에게 “우리 서비스의 장애 대응 절차를 알려 줘”라고 물었는데, 관련 문서를 모두 넣었더니 오히려 핵심을 놓치거나 오래된 규칙을 답하는 경험이 있을 수 있습니다. 모델의 컨텍스트 창이 길어졌다고 해서 모든 문서·모든 대화·모든 도구 결과를 한 번에 넣는 것이 좋은 답을 보장하지는 않습니다. 어떤 정보가 현재 작업에 필요한지, 어떤 정보는 이미 낡았거나 민감한지, 어떤 결과는 요약해서 남기고 어떤 원문은 다시 검색할지를 설계하는 일이 중요해집니다. 이를 **Context Engineering(컨텍스트 엔지니어링)** 이라고 부릅니다.

프롬프트 엔지니어링이 “모델에게 어떤 지시를 어떤 문장으로 줄까”에 집중한다면, 컨텍스트 엔지니어링은 “이번 추론에서 모델이 보게 할 정보의 전체 구성을 어떻게 만들까”를 다룹니다. 시스템 지시, 사용자 질문, 대화 이력, RAG 검색 문서, 장기 메모리, 도구 설명, 도구 실행 결과, 작업 계획, 평가 피드백이 모두 컨텍스트가 될 수 있습니다. AI 에이전트가 여러 단계로 작업할수록 이 정보는 계속 쌓이므로, 무작정 누적하지 않고 선택·압축·갱신·삭제하는 구조가 필요합니다.

이 글은 LLM을 처음 서비스에 연결하는 독자와, RAG 또는 에이전트를 만들어 봤지만 “문맥이 길어질수록 왜 불안정해지지?”라고 느낀 현업자를 위한 안내입니다. 특정 모델의 최대 토큰 수나 성능 수치를 일반화하지 않습니다. 모델과 API 버전, 요금, 컨텍스트 창, 도구 지원은 바뀔 수 있으므로 실제 구현 전 공식 문서를 확인해야 합니다. 핵심은 모델의 컨텍스트를 무한한 기억으로 오해하지 않고, 제한된 작업 메모리로 다루는 것입니다.

## 먼저 알아둘 기반 기술: LLM, 토큰, 컨텍스트 창과 추론 요청

**LLM(Large Language Model, 대형 언어 모델)** 은 입력된 토큰의 문맥을 바탕으로 다음 토큰을 예측해 답변·요약·분류·코드·도구 요청 등을 생성하는 모델입니다. 모델은 대화 밖의 정보를 자동으로 영구 저장하는 사람이 아닙니다. API 호출 때 전달된 정보와 모델이 학습한 패턴을 바탕으로 응답을 만들며, 다음 호출에서 이전 내용을 보려면 애플리케이션이 대화 이력이나 저장된 정보를 다시 전달해야 합니다.

**토큰(token)** 은 모델이 텍스트를 처리하는 단위입니다. 단어·문장·한국어 글자와 일대일로 같지 않으며, 같은 문장도 모델마다 토큰 수가 다를 수 있습니다. 입력 토큰에는 시스템 지시, 사용자 질문, 예시, 검색 문서, 도구 정의와 결과, 대화 이력이 모두 포함될 수 있습니다. 출력 토큰에는 모델의 답변이나 도구 호출 인자가 포함됩니다. 그래서 사용자가 짧은 질문을 했어도 애플리케이션이 긴 문서와 이력을 붙이면 실제 요청은 커질 수 있습니다.

**컨텍스트 창(context window)** 은 한 번의 모델 호출에서 모델이 함께 볼 수 있는 토큰 범위입니다. 이 범위를 넘으면 요청이 거절되거나, 일부 이력을 잘라 내거나, 출력 예산이 줄어들 수 있습니다. 하지만 한도 안에 들어간다고 해서 모델이 모든 문장을 똑같이 잘 활용한다는 뜻은 아닙니다. 긴 문서 안에서 중요한 조건을 찾는 능력, 정보의 위치, 문서 사이의 모순, 작업의 복잡도는 모델·프롬프트·평가 방식에 따라 달라집니다.

**추론(inference)** 은 학습이 끝난 모델에 입력을 넣어 출력을 생성하는 과정입니다. Context Engineering은 이 추론 직전에 “어떤 정보 묶음을 모델에 보낼 것인가”를 결정하는 설계입니다. 단순 챗봇에서는 시스템 메시지와 질문만 있을 수 있지만, 업무 에이전트에서는 사용자 권한, 현재 작업, 검색 결과, 도구 목록, 이전 실패, 검증 규칙이 함께 들어갑니다. 따라서 입력을 조립하는 코드는 프롬프트 문자열 하나가 아니라 서비스의 정책과 데이터 흐름이 됩니다.

## 프롬프트 엔지니어링과 Context Engineering의 차이

**프롬프트 엔지니어링(prompt engineering)** 은 모델이 원하는 형식·역할·추론 방향을 따르도록 지시를 작성·구성하는 기법입니다. 예를 들어 “답변을 JSON 형식으로 반환하라”, “근거가 없으면 모른다고 말하라”, “사용자의 언어로 답하라” 같은 지시를 설계합니다. 한 번의 분류나 짧은 요약 작업에서는 좋은 프롬프트가 품질에 큰 영향을 줄 수 있습니다.

Context Engineering은 이보다 넓은 질문을 합니다. 시스템 지시는 얼마나 길어야 하는가? 현재 사용자에게 허용된 문서만 어떻게 검색할 것인가? 지난 100턴의 대화를 그대로 넣을 것인가, 최근 몇 턴과 요약을 섞을 것인가? 도구 결과가 수천 줄이면 원문·요약·식별자 중 무엇을 전달할 것인가? 모델이 실패한 뒤 어떤 피드백을 다음 시도에 넣을 것인가? 즉, 모델이 매 단계에서 보게 되는 전체 정보 상태를 관리합니다.

Anthropic은 컨텍스트 엔지니어링을 제한된 컨텍스트 창에 들어갈 토큰을 계속 변화하는 정보 집합에서 선별·관리하는 일로 설명합니다. 이 관점은 특정 모델에만 해당하지 않습니다. OpenAI API 문서도 긴 프롬프트와 대화 상태를 다룰 때 컨텍스트 창, 토큰 한도, 상태 관리의 관계를 설명합니다. 모델 제공사가 달라도, 현재 작업에 필요한 최소한의 고신호 정보를 주려는 원칙은 유효합니다.

## 컨텍스트를 구성하는 다섯 층

실무에서 컨텍스트를 하나의 긴 문자열로 보지 말고 출처와 성격에 따라 나누면 설계·디버깅이 쉬워집니다. 첫째는 **고정 정책**입니다. 시스템 역할, 안전 규칙, 출력 형식, 도구 사용 원칙처럼 대부분의 요청에서 유지되는 내용입니다. 둘째는 **현재 작업 정보**입니다. 사용자의 질문, 선택한 서비스·프로젝트·문서 ID, 현재 단계 같은 내용입니다. 셋째는 **검색 지식**입니다. RAG가 찾은 문서 조각, 데이터베이스 조회 결과, 관련 코드·티켓입니다.

넷째는 **대화 이력과 작업 상태**입니다. 이미 합의한 요구, 직전 도구 호출의 결과, 아직 끝나지 않은 계획, 실패 이유가 해당합니다. 다섯째는 **장기 메모리**입니다. 사용자가 명시적으로 저장을 허용한 선호, 반복적으로 필요한 업무 설정, 검증된 사실처럼 여러 세션에서 쓰일 정보를 말합니다. 이 층을 구분하면 “왜 모델이 예전 지시를 따르지?” 또는 “왜 다른 사용자의 정보가 보이지?” 같은 문제를 어느 저장·조립 단계에서 조사해야 하는지 알 수 있습니다.

```text
고정 정책       : 역할, 안전·출력 규칙, 신뢰 경계
현재 작업       : 사용자 질문, 권한, 대상 리소스, 목표
검색 지식       : 현재 질문과 관련 있는 문서·데이터 조각
단기 상태       : 최근 대화, 작업 계획, 도구 실행 결과
장기 메모리     : 명시적으로 저장·검증·만료되는 선호와 사실
```

모든 층의 정보가 같은 신뢰도를 갖는 것은 아닙니다. 시스템 정책과 서버가 확인한 권한은 제어 정보에 가깝고, 사용자 입력·검색 문서·웹 페이지·도구 출력은 신뢰하지 않는 데이터일 수 있습니다. 프롬프트 인젝션 글에서 다룬 것처럼 외부 문서의 지시를 정책처럼 실행하면 안 됩니다. Context Engineering은 품질 설계이면서 동시에 출처·권한·민감도를 분리하는 보안 설계입니다.

## 긴 대화 이력: 자르기, 요약, 상태화의 선택

대화가 길어질 때 가장 단순한 방법은 최근 N개 메시지만 남기는 **슬라이딩 윈도(sliding window)** 입니다. 구현은 쉽고 최근 문맥을 잘 보존하지만, 초반에 합의한 중요한 제약이나 사용자 선호가 사라질 수 있습니다. 반대로 전체 이력을 계속 넣으면 토큰 비용·지연이 늘고, 오래된 잘못된 가정이나 이미 끝난 논의가 현재 작업을 방해할 수 있습니다.

**요약(summarization)** 은 이전 대화를 짧은 상태 메모로 압축하는 방법입니다. 예를 들어 “사용자는 한국어 답변을 원하며, 현재 프로젝트는 A이고, 로그인 기능은 완료되었으며, 결제 오류를 조사 중”처럼 다음 턴에 필요한 사실을 남길 수 있습니다. 하지만 요약도 모델이 만든 정보이므로 원문을 잘못 이해하거나 중요한 예외를 빼먹을 수 있습니다. 요약에는 출처·갱신 시각·불확실성을 기록하고, 중요한 결정은 원문 또는 구조화된 시스템 상태에서 다시 확인할 수 있어야 합니다.

**상태화(state externalization)** 는 대화 문장에만 의존하지 않고, 작업 상태를 명시적인 데이터 구조로 관리하는 접근입니다. 예를 들어 주문 지원 에이전트라면 `customer_id`, `order_id`, `authorized_actions`, `current_step`, `approval_status`를 서버 데이터로 유지하고, 모델에는 현재 단계에서 필요한 값만 전달합니다. 모델이 자연어로 “주문 123을 취소해도 된다”고 말한 것을 권한의 근거로 삼지 않고, 서버가 별도 권한 검사를 한 결과를 상태로 제공합니다.

```json
{
  "task": "refund-request-draft",
  "order_id": "O-123",
  "caller_authorized": false,
  "current_step": "explain-policy",
  "approval_required": true
}
```

구조화된 상태는 모델의 컨텍스트를 줄이고 디버깅을 쉽게 하지만, 모든 일을 JSON으로 표현하려 하면 또 다른 복잡성이 생깁니다. 변경·권한·재시도처럼 서버가 확실히 책임져야 하는 핵심 상태부터 분리하고, 설명·요약·아이디어처럼 자연어가 강한 영역은 모델에 맡기는 균형이 필요합니다.

## RAG는 검색이 아니라 선택과 조립의 문제다

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)** 는 질문에 답하기 전 관련 문서나 데이터를 찾아 모델 컨텍스트에 넣는 방식입니다. RAG를 도입하면 모델 학습 시점 뒤의 사내 지식이나 제품 문서를 활용할 수 있습니다. 하지만 “관련 문서 상위 10개를 그대로 붙인다”는 것만으로 좋은 Context Engineering이 되지는 않습니다. 검색 결과가 너무 많으면 중요한 문장이 묻히고, 다른 버전의 정책이 섞이며, 권한 없는 문서가 들어갈 수 있습니다.

문서 분할(chunking)은 중요한 선택입니다. 너무 큰 조각은 한 문서의 주제와 무관한 내용까지 많이 넣어 토큰을 낭비하고, 너무 작은 조각은 제목·예외·정의 같은 문맥을 잃습니다. 문서 제목, 버전, 섹션 경로, 적용 대상, 작성·갱신 시각 같은 메타데이터를 함께 저장하면 검색과 답변 근거를 개선할 수 있습니다. Anthropic의 Contextual Retrieval 사례처럼, 문서 조각이 전체 문서 안에서 무엇을 의미하는지 짧은 맥락을 덧붙이는 방법도 검토할 수 있습니다.

검색 결과는 재정렬(reranking)·중복 제거·최신성 필터·권한 필터를 거쳐야 할 수 있습니다. 질문이 “올해의 출장비 규정”이라면 제목에 비슷한 단어가 있는 오래된 문서보다, 현재 적용 중인 버전과 사용자의 조직에 맞는 문서가 우선되어야 합니다. 검색 품질은 벡터 임베딩 모델 하나의 문제보다 문서 수집·메타데이터·권한·질문 재작성·평가의 결합 문제입니다.

RAG 결과를 넣을 때도 출처를 표시합니다. 모델에게 문서 ID·버전·신뢰도·인용 규칙을 제공하고, 사용자에게는 가능한 범위에서 근거 링크를 보여 주면 검토하기 쉽습니다. 단, 검색된 문서는 지식 데이터이지 명령어가 아닙니다. 문서 안의 “관리자에게 메일을 보내라”는 문장을 모델이 도구 실행 지시로 해석하지 않도록 신뢰 경계를 유지해야 합니다.

## 메모리: 많이 저장하는 기능이 아니라 잊는 규칙까지 포함한다

AI 제품에서 “메모리”는 보통 여러 의미로 쓰입니다. 단기 메모리는 현재 대화나 작업 중 필요한 이력이고, 장기 메모리는 여러 세션을 넘어 유지하는 사용자 선호·사실·업무 설정일 수 있습니다. 벡터 데이터베이스에 대화 내용을 모두 임베딩해 저장하는 것만으로 좋은 메모리가 되지는 않습니다. 무엇을 저장할지, 언제 검색할지, 어떻게 수정·삭제할지, 누구에게 속하는지를 정의해야 합니다.

장기 메모리에 적합한 정보는 사용자가 명시적으로 허용한 안정적인 선호, 예를 들어 “답변은 한국어로 받고 싶다”처럼 비교적 오래 유지되는 항목입니다. 반면 일시적인 감정, 추측, 민감한 개인정보, 다른 사람의 정보, 검증되지 않은 모델 요약은 자동으로 영구 저장하기 위험합니다. 잘못 저장된 기억은 다음 대화에서 반복적으로 잘못된 답을 만들고, 삭제 요청에 대응하기도 어렵습니다.

메모리 레코드에는 최소한 소유자 또는 테넌트, 출처, 생성·갱신 시각, 만료 정책, 민감도, 삭제 상태를 연결하는 것이 좋습니다. 검색 시에는 현재 사용자가 해당 메모리를 읽을 권한이 있는지 먼저 필터링합니다. 모델에게 “다른 사용자 정보는 보지 마”라고 지시하는 것은 접근 제어가 아닙니다. 메모리 저장소와 검색 API에서 사용자·조직 경계를 강제해야 합니다.

## 도구 결과를 다루는 법: 원문보다 다음 행동에 필요한 사실

에이전트가 검색, 데이터베이스 조회, 파일 읽기, 브라우저 탐색, 코드 실행 같은 도구를 쓰면 결과가 빠르게 길어집니다. 2,000줄짜리 로그, 수백 개의 검색 결과, 긴 HTML 문서를 매 턴마다 다시 넣으면 모델이 중요한 오류를 놓치고 컨텍스트 창을 소모할 수 있습니다. 따라서 도구 결과는 원문 보관과 모델 전달을 분리하는 것이 좋습니다.

서버는 원문을 권한 있는 저장소에 요청 ID와 함께 보관하고, 모델에는 현재 단계에 필요한 구조화된 요약·식별자·오류 코드·상위 항목만 전달할 수 있습니다. 예를 들어 배포 로그에서는 실패한 단계, 오류 코드, 관련 파일 경로, 최근 20줄만 모델에 주고, 필요할 때 모델이 특정 범위를 다시 조회하도록 할 수 있습니다. 이 방식은 토큰을 줄일 뿐 아니라 민감한 로그 전체가 모델·대화 기록에 퍼지는 위험도 낮춥니다.

도구 설명 자체도 컨텍스트입니다. 도구가 많으면 모델은 어떤 도구를 언제 써야 할지 혼동할 수 있고, 각 도구의 JSON Schema와 예시가 토큰을 차지합니다. 현재 작업에 필요한 도구만 노출하고, 이름·설명·입력 필드를 명확하게 만드는 것이 좋습니다. Anthropic의 도구 작성 가이드도 모델이 암묵적으로 알아야 할 도메인 용어와 형식을 도구 설명에 명시하는 중요성을 다룹니다. 다만 모델의 도구 선택은 제안이며, 실행 서버는 앞서 다룬 권한·스키마·영향 검증을 반드시 다시 수행해야 합니다.

## Context Engineering의 평가: 좋은 답변보다 좋은 상태를 측정한다

컨텍스트를 바꿨을 때 “답변이 좋아 보인다”는 인상만으로 배포를 결정하면 위험합니다. 대표적인 질문·문서·사용자 권한·도구 상태를 포함한 평가 세트를 만들고, 변경 전후를 비교해야 합니다. 평가는 정확성, 근거 인용 정확성, 형식 준수, 권한 위반 여부, 도구 호출 적합성, 지연 시간, 입력·출력 토큰, 사용자 재질문 비율 같은 관점으로 나눌 수 있습니다.

예를 들어 고객 지원 RAG에서 검색 문서 수를 10개에서 4개로 줄였다면, 토큰 비용이 줄었는지뿐 아니라 답변이 현재 정책 문서를 더 자주 인용하는지, 예외 규칙을 놓치지 않는지, 권한 없는 문서가 섞이지 않는지 평가해야 합니다. 대화 요약을 도입했다면 이전에 합의한 제약을 잊는 비율, 요약이 잘못된 사실을 추가하는 비율, 긴 대화의 지연 개선을 함께 봅니다.

실패 사례는 평가 자산으로 남깁니다. “모델이 오래된 출장 규정을 인용했다”, “긴 로그에서 실제 오류가 아닌 경고를 원인으로 답했다”, “다른 조직의 메모리를 검색했다” 같은 사례는 다음 Context Engineering 변경이 고치려는 구체적인 목표가 됩니다. 모델·검색 인덱스·프롬프트·도구가 바뀌면 같은 사례를 반복 실행해 회귀를 확인합니다. 이는 기존 소프트웨어의 회귀 테스트와 비슷하지만, 입력 문서·권한·모델 비결정성을 포함한다는 점에서 더 넓은 관찰이 필요합니다.

## 업무 예시: 장애 대응 문서 에이전트의 컨텍스트 조립

가상의 장애 대응 도우미를 생각해 보겠습니다. 사용자가 “결제 API의 5xx 오류가 늘었는데 초기 조치를 알려 줘”라고 묻습니다. 좋은 설계는 모든 런북, 모든 과거 장애 채널, 모든 로그를 모델에 넣는 방식이 아닙니다. 먼저 인증·권한을 확인하고, 현재 서비스·환경·시간 범위를 구조화합니다. 그다음 현재 버전의 결제 런북, 최근 배포 이력, 관련 대시보드 요약, 최근 오류 코드 상위 항목을 검색합니다.

모델에는 “운영 중인 시스템에 직접 변경하지 말고, 관찰과 안전한 확인 단계를 우선 제안하라”는 고정 정책을 줍니다. 검색된 런북에는 버전·소유팀·갱신 시각을 붙이고, 오래된 문서는 낮은 우선순위로 둡니다. 로그 원문 전체 대신 오류 비율, 영향 endpoint, 최근 배포 SHA, 대표 오류 샘플을 제공합니다. 모델이 “롤백하라”고 제안하더라도 배포 도구 실행은 별도의 승인·권한 검사를 거칩니다.

이 구조에서는 모델 답이 틀려도 피해 범위를 줄일 수 있고, 왜 그 답을 만들었는지 조사할 수 있습니다. 반대로 모델에 문서·로그·권한을 한 덩어리로 넣고 “알아서 대응해”라고 하면, 토큰 비용뿐 아니라 오래된 지시·외부 문서·권한 오류가 복합적으로 섞입니다. Context Engineering은 모델을 더 똑똑하게 보이게 하는 요령이 아니라, 정보 흐름을 서비스 책임에 맞게 만드는 일입니다.

## 마무리: 컨텍스트는 프롬프트가 아니라 작업 메모리다

LLM 서비스에서 모델이 보는 컨텍스트는 답변 품질과 안전성에 직접 영향을 주는 작업 메모리입니다. 좋은 Context Engineering은 더 많은 문서를 넣는 일이 아니라, 고정 정책·현재 작업·검색 지식·단기 상태·장기 메모리를 출처와 목적에 따라 구분하고, 현재 작업에 필요한 고신호 정보만 조립하는 일입니다.

새 기능을 만들 때는 “이번 요청에서 모델이 왜 이 정보를 봐야 하는가?”, “이 정보는 얼마나 최신이고 누가 읽을 수 있는가?”, “다음 턴에도 남겨야 하는가?”, “모델이 잘못 해석해도 서버 정책이 피해를 막는가?”를 질문해 보세요. 이 질문에 답하는 구조를 만들면, 프롬프트 문장을 계속 덧붙이는 대신 평가·관찰·갱신이 가능한 AI 시스템을 설계할 수 있습니다.

## 컨텍스트 예산: 입력·출력·지연을 함께 배분한다

컨텍스트 창의 한도만 보는 것보다, 기능별 **컨텍스트 예산(context budget)** 을 정하는 편이 운영하기 쉽습니다. 예를 들어 고객 문의 답변 기능은 시스템 정책 1,000토큰, 사용자 질문과 최근 이력 2,000토큰, 검색 문서 4,000토큰, 도구 결과 1,000토큰, 모델 출력 1,000토큰처럼 대략적인 상한을 둘 수 있습니다. 이 숫자는 제품·언어·모델에 따라 달라지지만, 어떤 입력이 비용과 지연을 차지하는지 드러내는 효과가 있습니다.

입력 예산이 늘면 모델이 더 많은 정보를 읽을 수 있지만, 응답 생성에 쓸 수 있는 여유와 지연 시간이 줄 수 있습니다. 반대로 검색 문서를 너무 짧게 자르면 필요한 예외 조건이 빠질 수 있습니다. 따라서 문서 수를 고정하기보다 질문 유형에 따라 예산을 다르게 줄 수 있습니다. 단순 FAQ는 짧은 검색 결과로 충분할 수 있고, 계약서 비교처럼 근거를 많이 인용해야 하는 작업은 더 긴 문맥과 비동기 처리·사용자 검토가 필요할 수 있습니다.

토큰 초과 정책도 사용자 경험의 일부입니다. 문서가 너무 길면 조용히 앞부분을 잘라 답하는 대신, 어떤 범위를 읽었는지 안내하거나 사용자가 특정 섹션을 선택하게 할 수 있습니다. 대화가 길면 최근 이력과 검증된 요약을 사용하되, 이전 결정을 다시 확인해야 할 때는 원문을 검색하도록 만들 수 있습니다. 긴 요청을 자동으로 축약했을 때 법적·의료·금융처럼 누락의 영향이 큰 도메인에서는 사람이 원문을 검토할 수 있는 경로를 남겨야 합니다.

## 압축은 삭제가 아니라 재검색 가능한 인덱싱이다

대화·로그·문서를 요약하면 토큰을 줄일 수 있지만, 요약은 원문보다 정보가 적습니다. 좋은 압축 전략은 “요약만 남기고 원문을 버린다”가 아니라, 원문을 권한 있는 저장소에 식별자로 유지하고 모델에는 요약·핵심 사실·원문 위치를 전달하는 것입니다. 모델이 더 자세한 근거가 필요하면 `get_document_section(document_id, section_id)` 같은 읽기 전용 도구로 필요한 부분을 다시 가져오게 할 수 있습니다.

압축 내용에는 사실과 판단을 분리하는 것이 유용합니다. “배포는 14:00에 시작했다”는 이벤트 사실이고, “원인은 캐시 설정이다”는 아직 가설일 수 있습니다. 둘을 같은 확정 문장으로 요약하면 다음 단계의 모델이 가설을 사실로 받아들일 수 있습니다. 상태 구조에 `observed_facts`, `hypotheses`, `pending_checks`, `source_ids`처럼 구분을 두면, 긴 에이전트 작업에서 재조사와 반증이 쉬워집니다.

```json
{
  "observed_facts": ["14:05 이후 /pay 5xx 비율이 증가"],
  "hypotheses": ["최근 배포가 관련 있을 수 있음"],
  "pending_checks": ["배포 전후 오류 코드 비교"],
  "source_ids": ["dashboard:pay-5xx", "deploy:2026-10-05-1400"]
}
```

이처럼 구조화한 요약도 무조건 정확하지는 않습니다. 요약을 생성하거나 갱신한 모델 버전, 원문 범위, 갱신 시각을 기록하고, 중요한 의사결정 전에는 소스 데이터를 다시 확인해야 합니다. 특히 여러 사용자의 대화를 하나의 요약에 합치면 권한과 개인정보 경계가 흐려질 수 있으므로, 사용자·테넌트·프로젝트별로 저장과 검색 범위를 분리합니다.

## 컨텍스트 갱신 규칙: 오래된 정보가 새 지시를 이기지 않게 한다

문서·메모리·도구 결과는 시간이 지나면 낡습니다. 제품 정책 문서가 개정됐는데 이전 버전의 조각이 더 높은 검색 점수를 받거나, 사용자의 담당 프로젝트가 바뀌었는데 옛 메모리가 계속 주입되면 답변 품질과 신뢰가 떨어집니다. 따라서 각 정보에는 버전·발효일·만료일·소유자·신뢰도를 붙이고, 조립 단계에서 현재 시각과 작업 대상에 맞는지 필터링해야 합니다.

고정 시스템 지시도 예외가 아닙니다. 지시가 길어질수록 서로 충돌하거나 실제 제품과 달라질 가능성이 커집니다. Anthropic의 Context Engineering 글은 너무 세밀하고 취약한 규칙을 프롬프트에 하드코딩하는 것과 너무 모호한 지시 사이의 균형을 언급합니다. 변경이 잦은 규칙은 짧은 고정 지시보다 버전 관리된 정책 문서·구조화된 서버 규칙·도구 조회로 분리하는 편이 유지보수하기 쉬울 수 있습니다.

갱신 정책에는 삭제도 포함됩니다. 저장한 사용자 선호가 더 이상 맞지 않을 때 수정·삭제할 수 있어야 하고, 법적·계약상 보존 기간이 끝난 데이터는 적절히 제거해야 합니다. 모델에 제공할 정보가 줄어들면 비용도 줄지만, 더 중요한 이유는 오래된 정보가 새로운 작업을 오도하지 않게 하기 위해서입니다. “기억을 많이 가진 AI”보다 “현재 작업에 맞는 정보를 정확히 잊고 다시 찾는 AI”가 업무 도구에는 더 적합할 수 있습니다.

## 실험 설계: 컨텍스트 변경을 안전하게 배포하는 방법

검색 문서 수, 요약 방식, 시스템 지시, 도구 설명을 바꾸는 일은 모델 동작을 크게 바꿀 수 있습니다. 그래서 프롬프트 파일을 수정하고 곧바로 모든 사용자에게 적용하기보다, 대표 평가 세트와 제한된 트래픽에서 먼저 검증하는 편이 안전합니다. 기존 구성과 새 구성을 같은 입력에 실행해 근거 인용, 정확성, 형식 준수, 권한 위반, 입력 토큰, 지연, 도구 호출을 비교할 수 있습니다.

평가 데이터는 정상 질문만으로 구성하지 않습니다. 짧고 모호한 질문, 오래된 문서를 요구하는 질문, 서로 모순되는 문서, 권한 없는 리소스를 언급한 질문, 긴 로그, 오타·약어가 많은 질문, 외부 데이터에 악성 지시가 섞인 사례를 포함합니다. 실제 사용자의 민감한 원문을 그대로 평가 데이터에 복사하지 말고, 필요한 경우 비식별화·합성 데이터·권한 통제된 평가 환경을 사용합니다.

성공 기준도 하나의 자동 점수만 믿지 않습니다. 문서 기반 답변에서는 인용 문서가 실제 주장과 맞는지, 오류 대응에서는 안전하지 않은 실행 제안을 하지 않는지, 고객 지원에서는 정책과 다른 약속을 하지 않는지 사람이 표본 검토할 수 있습니다. 모델 판정 기반 평가를 쓴다면 그 판정 모델의 편향·오류 가능성도 인정하고, 명확한 규칙 검증과 사람 검토를 함께 둡니다.

롤백 가능성도 Context Engineering의 일부입니다. 새 검색 인덱스·임베딩 모델·프롬프트 버전·요약 방식에 식별자를 붙이고, 품질이나 보안 지표가 나빠지면 이전 구성을 복원할 수 있어야 합니다. 어떤 답변이 어느 컨텍스트 구성에서 나왔는지 추적하지 못하면, 사용자 신고가 들어왔을 때 원인을 재현하기 어렵습니다. 컨텍스트 조립 코드는 제품 로직이므로 일반 코드처럼 변경 관리와 관찰이 필요합니다.

## 역할 분담: 모델에게 맡길 판단과 서버가 맡을 판단

컨텍스트를 잘 조립해도 모델은 확률적 생성기입니다. 모델은 문서 요약, 질문 분류, 관련 섹션 후보 추천, 자연어 설명, 도구 호출 제안에 강할 수 있습니다. 반면 사용자 인증, 테넌트 격리, 결제 한도, 데이터 삭제 승인, 정책의 최종 집행은 서버 코드와 권한 시스템이 책임져야 합니다. Context Engineering은 모델에 더 많은 권한을 주는 방법이 아니라, 모델이 필요한 정보로 더 나은 제안을 하도록 돕는 방법입니다.

이 원칙은 도구 결과의 사용에도 적용됩니다. 모델이 “이 고객은 환불 가능하다”고 답해도, 실제 환불 API는 현재 주문 상태·결제 수단·사용자 권한·금액 한도를 다시 검사해야 합니다. 반대로 서버가 확정한 권한 결과를 모델 문맥에 제공하면, 모델은 사용자에게 왜 승인·거절되는지 이해하기 쉬운 설명을 만들 수 있습니다. 자연어 판단과 결정적 정책 집행을 구분할수록 AI 기능의 결과를 재현·감사·개선하기 쉬워집니다.
