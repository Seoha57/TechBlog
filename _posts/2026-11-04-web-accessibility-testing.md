## 먼저 답하기

### Q. 화면이 정상적으로 보이고 클릭도 되는데, 왜 접근성 테스트가 필요한가요?

A. 같은 화면이 모든 사람에게 같은 방식으로 사용되지는 않기 때문입니다. 마우스를 쓰기 어려워 키보드만 사용하는 사람, 화면을 읽어 주는 스크린 리더를 사용하는 사람, 글자 크기를 크게 확대하는 사람, 색을 구분하기 어려운 사람이 있습니다. 접근성 테스트는 특정 사용자를 위한 마지막 보정이 아니라, 입력·이름·상태·오류·순서 같은 인터페이스의 기본 계약이 실제로 전달되는지 확인하는 품질 활동입니다.

웹 화면은 보통 눈으로 보이는 배치만으로 완성됐다고 생각하기 쉽습니다. 그러나 버튼처럼 보이는 `div`는 키보드 초점을 받지 못할 수 있고, 아이콘만 있는 삭제 버튼은 스크린 리더에 이름이 전달되지 않을 수 있습니다. 빨간 글씨만으로 오류를 표시하면 색을 구분하지 못하는 사람에게는 실패 이유가 남지 않습니다. 이런 문제는 디자인을 조금 바꾸는 일이기도 하지만, 더 근본적으로는 사용자가 시스템에 입력하고 결과를 받는 경로가 끊긴 문제입니다.

## 먼저 알아둘 기반 기술

### 접근성, 보조기술, 의미 구조

웹 접근성은 서로 다른 능력과 환경의 사용자가 웹 콘텐츠와 기능을 인지하고 조작하며 이해할 수 있게 만드는 특성입니다. 여기서 보조기술(assistive technology)은 스크린 리더, 화면 확대기, 음성 입력, 스위치 입력 장치처럼 사용자의 입력이나 출력을 돕는 도구를 말합니다. 이 도구는 사람이 보는 픽셀을 추측해서 읽기보다 HTML의 제목, 링크, 버튼, 표, 폼 label 같은 의미 구조와 브라우저가 제공하는 접근성 트리를 이용합니다.

접근성 트리는 브라우저가 DOM(Document Object Model)을 보조기술이 이해할 수 있는 역할·이름·상태 정보로 바꾼 결과라고 생각하면 됩니다. 예를 들어 `button` 요소는 보통 버튼 역할과 키보드 동작을 기본으로 제공합니다. 여기에 `aria-label="주문 삭제"`를 주면 아이콘만 있어도 그 버튼의 이름을 전달할 수 있습니다. 반대로 클릭 이벤트만 붙인 일반 요소는 모양은 버튼이어도 역할, Tab 이동, Enter·Space 동작을 직접 빠짐없이 구현해야 합니다.

### WCAG와 성공 기준

WCAG(Web Content Accessibility Guidelines)는 웹 콘텐츠 접근성 지침입니다. 시험 문제의 정답 목록처럼 쓰기보다, 무엇을 확인해야 하는지 정리하는 공통 언어로 보는 편이 좋습니다. WCAG의 네 원칙은 인식 가능(Perceivable), 운용 가능(Operable), 이해 가능(Understandable), 견고함(Robust)입니다. 이미지에 대체 텍스트가 있는지는 인식 가능, 키보드만으로 메뉴를 닫을 수 있는지는 운용 가능, 오류를 고칠 방법을 알 수 있는지는 이해 가능, 표준 의미가 보조기술과 잘 호환되는지는 견고함과 연결됩니다.

제품 요구사항을 바로 수십 개의 성공 기준으로 옮기면 팀이 지치기 쉽습니다. 먼저 서비스의 중요한 사용자 흐름을 고르고 그 흐름에 맞는 기준을 매핑하는 것이 실용적입니다. 로그인, 검색, 장바구니, 결제 정보 입력, 주문 조회처럼 실패했을 때 사용자가 우회하기 어려운 흐름이 우선입니다. 디자인 시스템에 버튼, 입력 상자, 모달, 토스트 같은 공통 컴포넌트가 있다면 그 컴포넌트를 먼저 확인하는 편이 화면별로 같은 결함을 반복해서 찾는 것보다 효율적입니다.

### 키보드 초점과 순서

키보드 사용자는 대개 Tab과 Shift+Tab으로 초점을 이동하고 Enter 또는 Space로 동작을 실행합니다. 초점은 현재 키보드 입력이 도착하는 위치입니다. 마우스 사용자에게는 보이지 않던 초점 표시가 키보드 사용자에게는 현재 위치를 알려 주는 유일한 표식일 수 있습니다. 따라서 `outline: none`으로 기본 초점 표시를 없애고 대체 표시를 제공하지 않는 변경은 기능 결함이 됩니다.

초점 순서는 화면의 시각적 순서와 업무의 자연스러운 순서를 대체로 따라야 합니다. CSS의 `order`나 절대 배치로 화면만 재정렬했는데 DOM 순서가 다르면, 스크린 리더와 키보드 사용자는 눈에 보이는 흐름과 다른 순서로 이동합니다. 모달을 열었는데 뒤쪽 페이지의 링크로 Tab이 빠져나가거나, 모달을 닫은 뒤 초점이 원래 열기 버튼으로 돌아오지 않는 문제도 자주 발생합니다. 이런 결함은 자동 검사만으로 완전히 발견하기 어렵기 때문에 실제 키보드 시나리오가 필요합니다.

## 무엇을 테스트해야 하나

### 1. 이름·역할·값이 전달되는지 확인한다

모든 상호작용 요소에는 사용자가 알 수 있는 이름이 필요합니다. "검색", "장바구니에서 제거", "비밀번호 표시"처럼 행동과 대상을 함께 드러내면 좋습니다. 텍스트가 화면에 보이더라도 연결이 끊길 수 있습니다. `label`의 `for` 값과 입력 요소의 `id`가 다르면 화면에서는 가까이 붙어 있어도 스크린 리더는 입력 목적을 읽지 못할 수 있습니다. placeholder는 입력 예시를 보여 주는 보조 정보이지, label을 대체하는 이름이 아닙니다.

상태도 이름만큼 중요합니다. 펼쳐지는 메뉴 버튼이라면 열림·닫힘 상태가 전달되어야 하고, 선택된 탭이라면 어느 탭이 선택되었는지 알려야 합니다. 로딩 중에는 같은 버튼을 여러 번 누르지 않게 하고, 완료나 실패의 결과는 화면 변화만으로 숨기지 말아야 합니다. ARIA(Accessible Rich Internet Applications) 속성은 이런 상태를 보완하지만, 네이티브 HTML로 표현할 수 있는 것을 복잡한 ARIA 역할로 바꾸는 것은 보통 더 위험합니다. 먼저 올바른 요소를 선택하고, 부족한 상태 정보만 추가합니다.

### 2. 키보드만으로 업무를 끝낼 수 있는지 확인한다

테스트는 Tab을 한 번 누르는 데서 끝나면 안 됩니다. 예를 들어 회원 가입 흐름이라면 주소 입력, 우편번호 검색 모달 열기, 후보 선택, 약관 확인, 오류 수정, 제출 성공 메시지 확인까지 키보드만으로 수행해 봐야 합니다. 날짜 선택기나 자동완성 목록처럼 마우스 사용을 전제하기 쉬운 컴포넌트는 방향키, Escape, Enter의 동작과 초점 이동을 별도로 확인합니다.

다음은 주문 취소 모달을 점검하는 간단한 수동 시나리오입니다.

1. Tab으로 `주문 취소` 버튼에 도착했을 때 눈에 보이는 초점 표시가 있는지 확인합니다.
2. Enter로 모달을 연 뒤 첫 의미 있는 요소로 초점이 이동하는지 봅니다.
3. 취소 사유 선택, 취소·닫기 버튼까지 Tab과 Shift+Tab만으로 왕복합니다.
4. Escape 또는 닫기 버튼으로 모달을 닫은 뒤 초점이 `주문 취소` 버튼으로 돌아오는지 확인합니다.
5. 제출 뒤 성공·실패 메시지가 눈과 보조기술 모두에게 전달되는지 확인합니다.

이 시나리오에서 어느 한 단계라도 마우스를 요구한다면, 그 기능은 일부 사용자에게 완료 불가능한 상태입니다. 단순히 "Tab이 된다"가 아니라 업무 결과까지 도달하는지를 기준으로 삼아야 합니다.

### 3. 오류와 동적 변경을 읽을 수 있게 한다

폼 검증에서 흔한 실패는 색과 테두리만 바꾸는 방식입니다. 사용자는 어느 항목이 왜 틀렸는지, 어떻게 고칠지 알아야 합니다. 제출 뒤 오류 요약을 제공한다면 오류가 난 입력으로 이동할 수 있는 링크를 두고, 각 입력 근처에도 구체적인 메시지를 둡니다. "형식이 올바르지 않습니다"보다 "사업자 등록 번호는 숫자 10자리여야 합니다"가 수정에 도움이 됩니다.

비동기 변경도 같은 원칙을 따릅니다. 검색 결과가 0건이 됐거나 장바구니 수량이 바뀌었거나 저장이 실패했을 때, 시각적인 애니메이션만 보여 주면 보조기술 사용자는 변경을 놓칠 수 있습니다. 필요한 경우 `aria-live` 영역을 이용해 핵심 결과를 알리되, 자잘한 변경까지 모두 읽게 만들어 사용자를 방해하지 않도록 합니다. 무엇을 즉시 알려야 하는지, 사용자가 다시 확인해도 되는 정보가 무엇인지 업무 중요도로 나눕니다.

### 4. 확대·색상·반응형 상태를 확인한다

접근성은 스크린 리더만의 이야기가 아닙니다. 브라우저 확대에서 가로 스크롤이 강제되거나, 글자가 겹쳐 버튼을 누를 수 없거나, 고정 헤더가 오류 메시지를 가리는 문제도 실제 사용성을 해칩니다. 색 대비는 텍스트와 배경을 구분할 수 있는지의 문제이며, 상태를 색 하나로만 전달하지 않는 것도 중요합니다. 필수 입력 항목을 빨간 별표로만 표시하기보다 "필수"라는 텍스트나 스크린 리더용 설명을 함께 제공합니다.

다크 모드, 고대비 설정, 작은 화면은 별도의 장식 모드가 아니라 같은 기능이 다른 조건에서 사용되는 경우입니다. QA는 대표 해상도만 캡처해 비교하는 데서 멈추지 말고, 메뉴가 접히는 시점, 확대 시 줄바꿈, 오류 메시지의 위치, 터치 대상 간격을 확인해야 합니다. 다만 모든 조합을 한 릴리스에 수동으로 점검하려 하면 지속할 수 없으므로, 공통 컴포넌트와 결제·가입 같은 고위험 흐름을 우선합니다.

## 자동화와 수동 검토를 나누는 법

자동 접근성 검사 도구는 빠르고 반복 가능한 기본 규칙을 찾는 데 매우 유용합니다. 누락된 이미지 대체 텍스트, 잘못된 ARIA 속성 조합, 빈 버튼 이름, 낮은 색 대비처럼 구조로 판별 가능한 문제를 CI(Continuous Integration)에 넣을 수 있습니다. 예를 들어 Playwright 같은 브라우저 테스트와 axe-core 계열 검사기를 함께 쓰면 중요한 화면에서 정해진 규칙 위반을 변경마다 감지할 수 있습니다.

```javascript
// 예시: 테스트 환경에서 접근성 규칙 위반을 확인하는 형태
await page.goto('/checkout');
const results = await new AxeBuilder({ page }).analyze();
expect(results.violations).toEqual([]);
```

이 예시는 도구의 원리를 보여 주기 위한 형태입니다. 실제 프로젝트에서는 규칙 집합, 예외 사유, 실행 브라우저, 초기 데이터와 로그인 상태를 함께 관리해야 합니다. 특히 자동 검사 결과가 0건이라고 해서 접근성이 보장되는 것은 아닙니다. 자동 도구는 "취소 버튼을 눌러도 초점이 엉뚱한 곳으로 이동한다"거나 "사용자가 이 설명을 이해할 수 없다"처럼 맥락이 필요한 문제를 알기 어렵습니다.

수동 검토는 키보드와 스크린 리더를 실제로 사용하는 흐름을 대상으로 합니다. 모든 페이지를 매번 처음부터 끝까지 읽는 대신, 변경된 컴포넌트와 고위험 흐름을 정해진 체크리스트로 검사합니다. 디자인·개발·QA가 같은 용어를 쓰기 위해 발견 항목에는 화면 이름뿐 아니라 요소의 역할, 재현 키 입력, 기대하는 안내, 실제 안내를 기록하면 좋습니다. "접근성 안 됨"보다 "주소 검색 모달에서 Shift+Tab 시 배경 페이지의 링크로 이동한다"가 재현과 수정에 훨씬 유용합니다.

## 업무 예시: 주소 검색이 있는 회원 가입

회원 가입 화면에서 사용자가 이메일, 비밀번호, 주소를 입력하고 약관에 동의한다고 가정하겠습니다. 주소는 별도 모달에서 검색합니다. 이 기능의 테스트 대상을 API 응답 성공 여부로만 두면 화면은 통과할 수 있습니다. 그러나 접근성 관점에서는 다음과 같은 질문을 추가해야 합니다.

* 이메일 입력에는 목적을 알리는 label과 형식 오류 메시지가 연결되는가?
* 비밀번호 표시 전환 버튼은 현재 상태를 알리는가?
* 주소 검색 모달을 열면 초점이 모달로 들어오고, 닫으면 원래 버튼으로 돌아오는가?
* 검색 결과 목록은 방향키나 Tab으로 선택할 수 있고, 선택 결과가 입력란에 반영됐음을 알리는가?
* 약관 링크와 동의 체크박스의 관계가 읽히는가?
* 제출 실패 후 첫 오류 또는 오류 요약으로 이동할 수 있는가?

이 질문을 사용자 스토리의 완료 조건에 넣으면 접근성은 배포 직전의 별도 감사가 아니라 기능의 수용 기준이 됩니다. 개발자는 컴포넌트를 만들 때부터 네이티브 요소와 초점 복귀를 고려할 수 있고, QA는 시각적 캡처와 API 상태 코드뿐 아니라 같은 흐름의 키보드 결과를 기록할 수 있습니다. 제품 책임자는 어떤 흐름을 먼저 보장할지 위험 기반으로 결정할 수 있습니다.

## 결함을 분류하고 우선순위를 정하는 기준

접근성 이슈는 수가 많아 보이므로 우선순위가 중요합니다. 첫째, 사용자가 핵심 업무를 완료하지 못하게 하는가를 봅니다. 로그인 버튼을 키보드로 누를 수 없거나 결제 오류를 읽을 수 없는 문제는 높은 우선순위입니다. 둘째, 대체 경로가 있는가를 봅니다. 관리자가 다운로드한 보고서를 읽지 못하면 단순한 안내 문구보다 영향이 클 수 있습니다. 셋째, 공통 컴포넌트에서 발생하는가를 봅니다. 한 화면의 아이콘보다 모든 모달의 초점 이탈은 수정 범위가 넓지만 고치면 많은 흐름이 함께 개선됩니다.

수정 후에는 원래 재현 절차를 다시 수행해야 합니다. ARIA 속성을 추가했는데 실제 역할이 맞지 않거나, focus trap을 넣었는데 모달 내부의 닫기 버튼에 도달하지 못하면 다른 결함을 만든 것입니다. 접근성은 체크박스를 채우는 일이 아니라 사용자의 입력과 피드백 경로를 보존하는 일입니다. 재현 시나리오, 자동 검사, 수동 키보드 검토를 함께 남겨야 다음 디자인 변경에서도 같은 약속을 지킬 수 있습니다.

## 스크린 리더 검토를 현실적으로 시작하는 방법

스크린 리더를 처음 쓰는 팀은 모든 명령을 외워야 한다고 생각해 시작을 미루기 쉽습니다. 처음에는 그럴 필요가 없습니다. 운영체제와 브라우저 한 조합을 정하고, 제목으로 이동했을 때 페이지 구조가 이해되는지, Tab으로 상호작용 요소를 이동할 때 이름이 자연스러운지, 폼 입력에서 label과 오류가 읽히는지, 저장 결과가 알려지는지를 확인하면 됩니다. Windows에서는 NVDA와 브라우저 조합을, macOS에서는 VoiceOver와 Safari 조합을 대표 환경으로 삼을 수 있습니다. 이는 특정 도구가 모든 사용자를 대표한다는 뜻이 아니라, 적어도 의미 구조가 실제 보조기술에서 깨지지 않는지 반복 가능하게 확인하기 위한 기준입니다.

검토자는 화면을 보지 않고 시작해 보는 것이 도움이 됩니다. 먼저 제목을 훑어 "이 페이지가 주문 상세인지, 결제인지, 설정인지" 이해할 수 있어야 합니다. 다음으로 landmarks라고 부르는 header, navigation, main, footer 영역 사이를 이동했을 때 반복 메뉴를 지나 핵심 콘텐츠로 갈 수 있어야 합니다. 긴 목록은 목록 개수와 각 항목의 이름이, 표는 제목 셀과 데이터 셀의 관계가 전달되어야 합니다. 이 정보가 빠지면 사람은 화면 전체를 한 줄씩 듣거나 추측해야 합니다.

스크린 리더가 읽는 문장이 어색할 때 시각적인 문구를 무작정 늘리는 것은 좋은 해결이 아닐 수 있습니다. 먼저 요소가 어떤 역할로 노출되는지 개발자 도구의 접근성 트리에서 확인하고, 이름의 출처가 텍스트인지 `aria-label`인지 연결된 label인지 살펴보세요. 예를 들어 카드 전체를 링크로 만들고 내부에 또 다른 링크나 버튼을 넣으면 중첩된 상호작용 구조가 생겨 탐색이 복잡해질 수 있습니다. 화면 디자인의 편의 때문에 HTML의 기본 관계를 깨지 않았는지부터 돌아보는 편이 빠릅니다.

## 디자인 시스템에 넣을 최소 계약

같은 버튼과 모달이 수십 개 화면에 복사되는 제품이라면 개별 화면에서 결함을 고치는 방식은 오래가지 못합니다. 디자인 시스템이나 공통 UI 라이브러리에 접근성 계약을 넣는 편이 작은 변경으로 큰 범위를 보호합니다. 버튼 컴포넌트는 실제 `button`을 기본으로 사용하고 비활성 상태의 의미를 유지해야 합니다. 아이콘 버튼은 접근 가능한 이름을 반드시 받도록 API를 설계할 수 있습니다. 입력 컴포넌트는 label, 설명, 오류 메시지의 ID를 연결하고 오류 상태를 일관되게 드러내야 합니다.

모달 컴포넌트의 계약도 명확해야 합니다. 열릴 때 제목 또는 첫 입력 요소로 초점을 옮기고, 열려 있는 동안 배경 콘텐츠가 키보드 초점을 받지 않으며, 닫을 때 호출 지점으로 초점을 되돌립니다. 다만 모든 다이얼로그가 같은 첫 초점 위치를 가져야 한다는 규칙은 아닙니다. 삭제 확인처럼 위험한 동작에는 설명을 먼저 읽게 해야 할 수 있고, 긴 약관처럼 큰 콘텐츠에는 제목에 초점을 두는 편이 방향 감각을 유지하는 데 도움이 될 수 있습니다. 공통 컴포넌트는 이런 정책을 일관되게 적용하되, 업무 맥락이 다른 화면에 강제하지 않도록 제한된 escape hatch와 문서를 제공합니다.

디자인 토큰도 테스트 가능한 계약이 될 수 있습니다. 본문·보조 텍스트·링크·오류·성공 상태의 색 조합을 임의의 hex 값으로 화면마다 만들지 않고 토큰으로 제공하면 대비 검사를 한 곳에서 관리하기 쉽습니다. hover만으로 정보를 보여 주는 패턴에는 keyboard focus와 터치 환경의 대안을 함께 둡니다. 모션은 시선을 끄는 장점이 있지만, 자동 재생 배너나 짧은 시간 뒤 사라지는 알림은 사용자가 내용을 읽기 전에 사라질 수 있습니다. 줄이거나 멈출 방법, 충분한 시간, 모션 감소 환경을 함께 고려합니다.

## 접근성 결함을 테스트 케이스로 기록하는 형식

버그 보고가 수정 가능한 정보가 되려면 재현 절차가 구체적이어야 합니다. 환경에는 브라우저, 운영체제, 확대 비율, 보조기술 사용 여부를 적습니다. 재현 단계에는 "주문 상세에서 Tab을 여섯 번 누른다"처럼 사용자의 행동을 쓰고, 실제 결과에는 초점이 어디로 이동했는지 또는 어떤 문장이 읽혔는지를 기록합니다. 기대 결과에는 단순히 WCAG 번호만 붙이기보다, "취소 모달 안의 첫 컨트롤로 초점이 이동하고 배경 링크로 빠져나가지 않는다"처럼 제품의 사용 경험을 씁니다.

스크린샷은 시각적 문제에 유용하지만 키보드나 음성 출력 문제의 증거로는 부족합니다. 필요한 경우 짧은 화면 녹화, 읽힌 문구의 전사, 접근성 트리 캡처를 함께 남깁니다. 개인정보나 고객 데이터가 화면에 보일 수 있다면 합성 계정과 마스킹된 데이터를 사용해야 합니다. 접근성 결함을 재현하려다가 실제 고객 정보가 포함된 화면을 외부 이슈에 올리는 것은 다른 보안 문제를 만들 수 있습니다.

회귀 테스트 이름도 사용자 관점으로 씁니다. `modalFocusTest`보다는 `주문 취소 모달을 닫으면 주문 취소 버튼으로 초점이 돌아온다`가 실패의 의미를 설명합니다. 자동화에서 찾은 색 대비 위반은 어느 토큰과 어느 컴포넌트가 원인인지 연결하고, 수동 점검에서 찾은 의미 문제는 사용자 흐름과 연결합니다. 이렇게 쌓인 기록은 다음 릴리스에서 단순한 결함 목록이 아니라, 팀이 어떤 경험을 지키기로 했는지 보여 주는 기준이 됩니다.

## 릴리스에 적용하는 작은 운영 루프

접근성 테스트를 별도 전담 인력의 대규모 감사로만 생각하면 작은 팀은 시작하기 어렵습니다. 현실적인 첫 루프는 세 단계입니다. 첫째, PR에서 새 인터랙션 요소가 네이티브 HTML을 쓰는지와 키보드 초점이 보이는지를 코드 리뷰합니다. 둘째, CI에서 대표 페이지의 자동 규칙 검사를 실행합니다. 셋째, 릴리스 후보에서 변경된 핵심 흐름을 키보드로 한 번 끝까지 수행합니다. 기능이 많아질수록 이 세 단계를 공통 컴포넌트, 고위험 흐름, 분기별 넓은 점검으로 확장할 수 있습니다.

중요한 것은 통과 숫자를 성과로 오해하지 않는 것입니다. 자동 검사 0건은 좋은 신호지만, 검사가 실행된 페이지와 규칙 안에서만 의미가 있습니다. 수동 점검 횟수가 많아도 실제 사용자가 막히는 오류가 계속된다면 우선순위 기준이 잘못된 것입니다. 결함 추세, 핵심 흐름의 완료 가능 여부, 반복되는 컴포넌트 문제를 함께 보면 숫자가 의사결정을 돕는 정보가 됩니다.

외부 업체의 위젯, 지도, 결제 창, 문서 뷰어처럼 직접 고치기 어려운 영역도 있습니다. 이 경우 "외부 서비스이므로 제외"라고 끝내지 말고, 제공자가 지원하는 접근성 문서와 키보드 동작을 확인하고, 대체 경로가 필요한지 검토해야 합니다. 계약 단계에서 접근성 요구를 명시하고, 통합 뒤 실제 흐름을 검토하며, 결함이 발견되면 사용자 지원 경로와 공급사 개선 요청을 분리해 관리하는 것이 좋습니다. 책임을 전가하지 않는 대신 수정 권한의 경계도 정직하게 기록하는 방식입니다.

## 테스트 범위를 늘릴 때의 우선순위

접근성 테스트 항목은 끝없이 늘릴 수 있으므로, 먼저 실패했을 때 사용자가 서비스를 계속 이용할 수 있는지를 기준으로 범위를 정합니다. 계정 생성, 로그인, 결제, 예약 변경, 고객 지원 문의처럼 다른 사람의 도움 없이 완료해야 하는 흐름은 높은 우선순위입니다. 다음으로 공통 네비게이션, 검색, 알림, 파일 다운로드처럼 여러 페이지를 연결하는 요소를 봅니다. 마지막으로 마케팅성 페이지나 드물게 쓰는 관리 기능을 넓혀 갑니다. 이 순서는 덜 중요한 화면을 무시하자는 뜻이 아니라, 제한된 시간에 가장 큰 사용 불가 위험부터 줄이자는 뜻입니다.

모바일 앱과 모바일 웹도 같은 원칙을 적용합니다. 터치 대상이 너무 작아 오작동하는지, 화면 회전과 확대에서 입력이 가려지지 않는지, 가상 키보드가 올라왔을 때 제출 버튼에 도달할 수 있는지 확인합니다. 모바일 보조기술은 화면을 쓸어 넘겨 요소를 이동하고 두 번 탭해 실행하는 방식이 흔하므로, 화면에 보이는 순서와 접근성 포커스 순서가 다르면 더 큰 혼란을 줍니다. 데스크톱 Tab 테스트를 통과했다고 모바일 접근성이 자동으로 보장되지는 않습니다.

콘텐츠 자체도 테스트 대상입니다. 링크가 여러 개 있을 때 모두 "자세히 보기"라고만 읽히면 목록 탐색 중 목적을 구분하기 어렵습니다. 표의 복잡한 병합 셀, 자동으로 바뀌는 차트, 자막 없는 영상, 이미지로만 제공되는 오류 안내는 기능 코드가 없어도 접근 장벽이 될 수 있습니다. 콘텐츠 작성자와 QA가 공통 체크리스트를 공유하면 개발 완료 뒤에 대체 텍스트와 구조를 급히 붙이는 일을 줄일 수 있습니다.

마지막으로 테스트 환경도 실제 사용 조건을 흉내 낼 필요가 있습니다. 느린 네트워크에서 로딩 표시가 언제 읽히는지, 브라우저 확대에서 고정된 도움말이 입력을 가리지 않는지, 로그인 만료 뒤 다시 인증하는 경로가 키보드로 가능한지를 확인하세요. 접근성은 완성 화면 한 장의 속성이 아니라, 로딩·오류·권한 부족·재시도 같은 모든 상태를 통과하는 경험의 속성입니다. 이 관점을 두면 테스트 목록은 늘어나지만, 기능이 바뀌어도 무엇을 지켜야 하는지 더 분명해집니다.

처음부터 모든 환경을 같은 깊이로 확인할 필요는 없습니다. 대표 브라우저와 대표 보조기술 조합을 정하고, 새 컴포넌트나 중요한 흐름이 바뀔 때마다 같은 시나리오를 반복하세요. 반복 가능한 작은 검토가 가끔 하는 큰 점검보다 회귀를 빨리 발견하게 합니다.

## 한계와 적용 기준 Q&A

### Q. 자동 접근성 검사만 CI에 넣으면 충분한가요?

A. 충분하지 않습니다. 자동 검사는 빠른 안전망이지만 의미 이해, 자연스러운 초점 순서, 모달의 실제 사용감, 업무 용어의 명확성까지 판단하지 못합니다. 자동 검사로 기계적으로 발견 가능한 결함을 줄이고, 핵심 사용자 흐름에는 키보드와 필요한 보조기술을 이용한 수동 검토를 더하세요.

### Q. ARIA를 많이 넣으면 접근성이 좋아지나요?

A. 아닙니다. 이미 올바른 의미와 동작을 제공하는 HTML 요소를 먼저 쓰는 편이 안전합니다. ARIA는 네이티브 요소가 표현하지 못하는 상태와 관계를 보완할 때 사용합니다. 잘못된 role, 중복 이름, 실제 동작과 다른 상태 속성은 오히려 보조기술 사용자에게 혼란을 줍니다.

### Q. 모든 WCAG 기준을 한 번에 만족해야만 시작할 수 있나요?

A. 목표와 법·계약상 요구는 조직마다 다르지만, 시작을 미룰 이유는 아닙니다. 공통 컴포넌트와 로그인·가입·결제·검색처럼 중요한 흐름부터 기준을 적용하고, 발견한 결함을 제품 백로그와 컴포넌트 개선 작업으로 연결하세요. 단, 사용자를 막는 결함을 단순 개선 항목처럼 무기한 미루지 않는 기준은 필요합니다.

### Q. QA만 접근성 테스트를 하면 되나요?

A. QA의 확인은 중요하지만 혼자 해결할 수는 없습니다. 기획은 오류 문구와 완료 기준을, 디자인은 상태 구분과 초점 가시성을, 개발은 의미 구조와 키보드 동작을, QA는 흐름 검증과 회귀 기준을 함께 책임져야 합니다. 역할을 나누되 사용자에게 보장할 경험은 하나라는 점을 공유하는 것이 좋습니다.

## 마무리

접근성 테스트는 특별한 브라우저 옵션을 켜는 추가 업무가 아니라, 웹이 전달해야 할 이름·상태·입력·결과가 실제로 전달되는지 확인하는 테스트입니다. 표준 HTML을 우선하고, 키보드로 핵심 흐름을 끝까지 수행하며, 자동 검사를 회귀 안전망으로 두고, 사람의 맥락 검토를 남기면 시작할 수 있습니다. 다음 기능을 테스트할 때 화면이 보이는지만 묻지 말고, 마우스 없이도 목적과 결과가 전달되는지 함께 확인해 보세요.
