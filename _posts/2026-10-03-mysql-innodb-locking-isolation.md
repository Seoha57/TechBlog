MySQL을 사용하면서 “조회는 되었는데 왜 수정이 멈췄지?”, “같은 행을 동시에 바꾸면 무엇이 먼저 반영되지?”, “데드락은 장애인가?”라는 질문을 만나기 쉽습니다. 이 질문의 답은 애플리케이션 코드 한 줄보다 **InnoDB의 트랜잭션과 잠금 모델**에 더 가깝습니다. InnoDB는 MySQL에서 널리 쓰이는 기본 스토리지 엔진으로, 데이터의 영속성·트랜잭션·행 수준 잠금·복구를 담당합니다. SQL 문장은 같아 보여도 인덱스, 조건식, 격리 수준, 트랜잭션 경계에 따라 다른 범위가 잠기고 다른 결과가 나올 수 있습니다.

이 글의 목적은 “잠금은 나쁘니 피하자”가 아닙니다. 잠금은 여러 사용자가 같은 데이터를 안전하게 바꾸기 위해 필요한 장치입니다. 다만 잠금이 어디에, 언제, 얼마나 오래 잡히는지 모르면 대기·타임아웃·데드락을 설명하기 어렵습니다. 주문 재고를 차감하는 서비스, 관리자 화면에서 상태를 바꾸는 업무 시스템, 배치와 온라인 요청이 같은 테이블을 갱신하는 시스템을 예시로, InnoDB가 무엇을 지키고 어떤 선택지를 주는지 차근차근 정리합니다.

## 먼저 알아둘 기반 기술: DBMS, 트랜잭션, ACID와 인덱스

**DBMS(Database Management System, 데이터베이스 관리 시스템)** 는 데이터를 저장하고 여러 프로그램이 안전하게 읽고 바꾸도록 돕는 소프트웨어입니다. MySQL은 DBMS이고, InnoDB는 MySQL 안에서 테이블 데이터를 실제로 보관하고 동시성·복구 규칙을 구현하는 스토리지 엔진입니다. 같은 MySQL 서버에도 다른 엔진이 있을 수 있지만, 이 글의 잠금 설명은 InnoDB 테이블을 전제로 합니다. 먼저 실제 테이블 엔진과 MySQL 버전을 확인하는 습관이 필요합니다.

**트랜잭션(transaction)** 은 여러 SQL 작업을 하나의 업무 단위로 묶는 경계입니다. 쇼핑몰에서 주문을 확정할 때 재고를 줄이고, 주문 행을 만들고, 결제 상태를 기록하는 과정은 함께 성공하거나 함께 실패해야 합니다. 중간에 서버 오류가 나서 재고만 줄고 주문이 없다면 데이터는 업무 의미를 잃습니다. `START TRANSACTION` 또는 `BEGIN`으로 시작한 작업은 `COMMIT`으로 확정하고, 문제가 있으면 `ROLLBACK`으로 되돌립니다. autocommit이 켜진 상태에서는 개별 SQL 문장이 각각 짧은 트랜잭션이 될 수 있으므로, 여러 문장의 원자성이 필요할 때는 경계를 코드에서 명시해야 합니다.

트랜잭션의 성질은 흔히 **ACID**로 요약합니다. 원자성(Atomicity)은 전부 성공하거나 전부 취소되는 성질, 일관성(Consistency)은 제약 조건과 업무 규칙을 깨지 않는 성질, 격리성(Isolation)은 동시에 실행되는 작업이 서로의 중간 상태를 함부로 보지 않게 하는 성질, 지속성(Durability)은 커밋한 결과가 장애 뒤에도 남는 성질입니다. ACID는 버튼 하나로 켜지는 기능이 아니라 로그, 잠금, 복구, 제약 조건, 애플리케이션 설계가 함께 만드는 약속입니다.

**인덱스(index)** 는 책의 색인처럼 원하는 행을 빠르게 찾기 위한 자료 구조입니다. InnoDB에서 인덱스는 성능뿐 아니라 잠금 범위를 이해하는 핵심입니다. `WHERE status = 'READY'`가 수십만 행을 스캔해야 한다면, 잠금 읽기나 UPDATE가 더 넓은 인덱스 범위를 검사하고 잠글 수 있습니다. 반대로 `WHERE order_id = ?`에 유니크 인덱스가 있다면 정확한 레코드를 겨냥하기 쉬워집니다. “한 행만 수정했는데 왜 다른 요청이 기다리지?”라는 질문은 실행 계획과 사용한 인덱스를 함께 봐야 답할 수 있습니다.

## MVCC: 읽기와 쓰기가 무조건 서로 막히지 않는 이유

**MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)** 는 한 행의 과거 버전을 활용해 읽기와 쓰기가 불필요하게 서로 기다리지 않도록 하는 방식입니다. InnoDB는 행을 수정할 때 이전 값을 undo 로그에 남기고, 읽는 트랜잭션은 자신의 읽기 시점에 맞는 버전을 볼 수 있습니다. 그래서 일반적인 `SELECT`는 다른 트랜잭션이 아직 커밋하지 않은 변경을 기다리지 않고, 일관된 스냅샷을 읽을 수 있습니다.

예를 들어 운영자가 상품 이름을 수정하는 동안 고객이 상품 목록을 조회한다고 합시다. 고객 조회가 모든 수정이 끝날 때까지 멈춘다면 서비스 체감은 나빠집니다. MVCC는 고객 조회가 적절한 과거 버전을 보게 하여 읽기 작업을 계속할 수 있게 합니다. 그러나 이것은 “잠금이 전혀 없다”는 뜻이 아닙니다. UPDATE, DELETE, INSERT, 잠금 읽기는 다른 쓰기와 충돌할 수 있고, 오래 열린 읽기 트랜잭션은 오래된 버전을 정리하지 못하게 만들어 undo 공간과 purge 작업에 영향을 줄 수 있습니다.

MVCC를 이해할 때 중요한 구분은 **일반 읽기(consistent nonlocking read)** 와 **잠금 읽기(locking read)** 입니다. 일반 SELECT는 스냅샷에 맞는 버전을 읽는 것이 기본입니다. 반면 `SELECT ... FOR UPDATE`는 뒤이을 변경을 안전하게 준비하려고 현재 레코드와 관련 인덱스 범위를 잠급니다. `SELECT ... FOR SHARE`는 다른 트랜잭션이 레코드를 바꾸는 것을 막으면서 읽고 싶을 때 사용합니다. 이 잠금은 일반적으로 트랜잭션을 커밋하거나 롤백할 때 풀리므로, 잠금 읽기를 autocommit 상태의 단독 문장으로 쓸 때와 명시적 트랜잭션 안에서 쓸 때의 의미가 다릅니다.

MVCC는 읽기 성능 마법이 아닙니다. 장시간 보고서 쿼리를 트랜잭션 안에 계속 열어 두거나, 세션이 커밋하지 않은 채 방치되면 오래된 버전을 치우지 못할 수 있습니다. 따라서 “조회니까 트랜잭션을 오래 열어도 된다”는 판단은 위험합니다. 읽기 일관성이 필요한 최소 범위를 정하고, 외부 API 호출·사용자 입력 대기·파일 업로드처럼 긴 작업을 트랜잭션 안에 넣지 않는 것이 기본입니다.

## InnoDB 잠금의 단위: 행만 보는 것이 아니라 인덱스 범위를 본다

InnoDB의 잠금은 종종 **행 잠금(row lock)** 이라고 소개되지만, 실제 구현에서는 인덱스 레코드와 그 사이의 범위가 중요합니다. 대표적인 쓰기 잠금은 **배타 잠금(X lock)** 입니다. UPDATE·DELETE·INSERT와 `FOR UPDATE`는 다른 트랜잭션의 충돌하는 쓰기를 막기 위해 X 잠금을 사용합니다. **공유 잠금(S lock)** 은 `FOR SHARE`처럼 읽은 레코드가 다른 트랜잭션에 의해 바뀌지 않게 할 때 쓰입니다. 같은 대상에 대한 S 잠금은 공존할 수 있지만 X 잠금과는 충돌합니다.

유니크 인덱스의 모든 열을 정확한 동등 조건으로 찾는 경우는 비교적 이해하기 쉽습니다. 예를 들어 `PRIMARY KEY(order_id)`가 있고 `WHERE order_id = 501`로 잠금 읽기를 하면 특정 레코드에 집중할 수 있습니다. 반면 비유니크 인덱스, 범위 조건, 누락된 인덱스는 여러 인덱스 엔트리와 범위를 검사하게 합니다. InnoDB는 격리 수준과 쿼리 종류에 따라 **레코드 잠금(record lock)**, **갭 잠금(gap lock)**, **넥스트키 잠금(next-key lock)** 을 조합합니다.

갭 잠금은 인덱스 레코드 자체보다 레코드 사이의 빈 구간에 대한 제어를 뜻합니다. 넥스트키 잠금은 인덱스 레코드와 그 앞의 갭을 함께 다루는 개념입니다. 이것은 다른 트랜잭션이 같은 범위에 새 행을 넣어 결과 집합이 예상과 달라지는 현상, 이른바 팬텀을 제어하는 데 쓰일 수 있습니다. 이름만 보면 “존재하지 않는 행을 왜 잠그지?” 싶지만, 범위 조건의 일관성을 지키려는 장치라고 보면 됩니다.

다음 예시는 예약 가능한 좌석을 하나 고르는 업무를 단순화한 것입니다. 중요한 점은 `available = 1`만으로는 어떤 행을 잡을지와 동시 요청의 결과가 불명확하다는 점입니다.

```sql
START TRANSACTION;

SELECT seat_id
FROM seats
WHERE show_id = 1001
  AND available = 1
ORDER BY seat_id
LIMIT 1
FOR UPDATE;

UPDATE seats
SET available = 0,
    reserved_by = 42
WHERE seat_id = ?;

COMMIT;
```

이 패턴에서 `FOR UPDATE`는 “읽은 뒤 업데이트할 대상”을 보호합니다. 하지만 `show_id, available, seat_id`에 적절한 인덱스가 없으면 원하는 한 좌석을 찾기 위해 넓은 범위를 스캔할 수 있습니다. 또한 외부 결제 API를 호출하는 시간을 이 트랜잭션 안에 넣으면 다른 예약 요청이 오래 기다립니다. 보통은 짧게 좌석 상태를 확보하거나 임시 예약을 만들고, 외부 호출은 별도 상태 전이·만료 처리와 함께 설계하는 편이 낫습니다. 업무 요구가 단순한 SQL 예제보다 더 넓다는 점을 먼저 인정해야 합니다.

## 격리 수준: 무엇을 얼마나 일관되게 읽을지 정하는 선택

SQL 표준에서 널리 논의하는 격리 수준은 `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE` 네 가지입니다. InnoDB는 이 수준을 지원하며 기본값은 일반적으로 **REPEATABLE READ** 입니다. 이름의 높고 낮음만으로 우열을 판단하기보다, 한 트랜잭션 안에서 어떤 읽기 의미가 필요한지와 경합 비용을 함께 살펴야 합니다.

`READ UNCOMMITTED`는 아직 커밋되지 않은 변경을 볼 수 있는 더티 읽기 위험이 있어, 일반 업무 데이터에는 거의 선택하지 않습니다. `READ COMMITTED`는 각 일관 읽기가 그 시점에 커밋된 최신 데이터를 볼 수 있습니다. 같은 트랜잭션에서 같은 SELECT를 두 번 실행했을 때 중간에 다른 트랜잭션이 커밋하면 결과가 달라질 수 있습니다. PostgreSQL이나 Oracle을 사용해 온 사람이 MySQL을 설계할 때도 제품별 구현 세부가 다르므로, 같은 이름만 보고 동작을 동일시하면 안 됩니다.

`REPEATABLE READ`에서는 일관 읽기가 보통 트랜잭션 내 첫 읽기 시점의 스냅샷을 유지합니다. 같은 조건을 다시 읽어도 일관된 결과를 얻는 데 유리합니다. 다만 쓰기와 잠금 읽기에서는 현재 읽기와 인덱스 범위 제어가 관계되고, 갭·넥스트키 잠금이 관찰될 수 있습니다. 격리 수준을 바꿨다면 단위 테스트만이 아니라 실제 트랜잭션 경합, 인덱스, 재시도 정책, 보고서와 온라인 처리의 혼합을 함께 검증해야 합니다.

`SERIALIZABLE`은 동시 실행 결과가 마치 직렬로 실행된 것처럼 보이게 하는 더 강한 의미를 목표로 합니다. 그만큼 충돌·대기 가능성이 커질 수 있어, 모든 서비스에 기본으로 적용할 값은 아닙니다. 금융이나 재고처럼 강한 규칙이 필요한 경우에도 무조건 가장 높은 격리 수준을 택하기보다, 유니크 제약·조건부 UPDATE·원자 연산·업무 재시도와 어떤 조합이 가장 명확한지 검토해야 합니다.

격리 수준을 확인하고 세션에서 변경하는 예시는 다음과 같습니다. 운영 환경의 전역 값을 즉시 바꾸기 전에 애플리케이션 커넥션 풀, 트랜잭션 경계, 테스트 환경이 해당 값을 어떻게 상속하는지부터 확인해야 합니다.

```sql
SELECT @@transaction_isolation;

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
-- 이 트랜잭션에 필요한 SQL
COMMIT;
```

## FOR UPDATE는 언제 쓰고, 언제 피해야 하나

`SELECT ... FOR UPDATE`는 읽은 레코드를 나중에 바꾸겠다는 의도를 데이터베이스에 표현하는 도구입니다. 재고 수량을 확인한 뒤 차감하거나, 아직 처리되지 않은 작업 하나를 워커가 가져가거나, 상태 전이가 중복 실행되면 안 되는 경우에 적합할 수 있습니다. 핵심은 **조회와 변경 사이의 경쟁 구간**을 보호하는 것입니다. 단순히 화면에 보여 주기 위한 조회에는 쓰지 않는 편이 보통 더 낫습니다.

작업 큐를 여러 워커가 소비하는 예를 보겠습니다. MySQL 버전과 요구 사항에 따라 `SKIP LOCKED` 같은 선택지를 검토할 수 있지만, 잠긴 작업을 건너뛰는 것이 공정성·순서 보장·실패 복구 요구와 맞는지 별도 판단이 필요합니다. 기능을 쓸 수 있다는 사실과 업무에 맞다는 사실은 다릅니다.

```sql
START TRANSACTION;

SELECT job_id
FROM jobs
WHERE status = 'READY'
ORDER BY created_at
LIMIT 1
FOR UPDATE;

UPDATE jobs
SET status = 'RUNNING', started_at = CURRENT_TIMESTAMP
WHERE job_id = ?;

COMMIT;
```

이 SQL만으로 안정적인 큐가 완성되지는 않습니다. 워커가 커밋 뒤 죽었을 때 RUNNING 작업을 언제 재시도할지, 같은 메시지를 두 번 처리해도 안전한지, 처리 순서가 절대적인지, 실패 기록을 어디에 남길지를 설계해야 합니다. 잠금은 중복 선택을 줄이는 한 요소일 뿐이고, **멱등성(idempotency)** 과 상태 전이 규칙이 함께 있어야 운영에서 설명 가능한 시스템이 됩니다.

피해야 할 대표 사례는 잠금 범위가 불명확한 넓은 검색입니다. 관리자 검색 화면의 자유 조건에 `FOR UPDATE`를 붙이면, 의도하지 않은 많은 행이나 인덱스 범위를 잠글 수 있습니다. 또한 트랜잭션을 열고 사용자에게 승인 버튼을 누르게 기다리는 방식도 좋지 않습니다. 잠금은 사용자 경험을 기다릴 수 있도록 만든 기능이 아니라 짧은 데이터 변경을 안전하게 묶는 기능입니다.

## 데드락과 잠금 대기: 같은 현상처럼 보이지만 다르다

**잠금 대기(lock wait)** 는 한 트랜잭션이 다른 트랜잭션이 잡고 있는 잠금을 기다리는 정상적인 동시성 현상입니다. 앞선 UPDATE가 빨리 커밋되면 기다린 작업은 계속됩니다. 반면 **데드락(deadlock)** 은 트랜잭션 A가 B의 잠금을 기다리고, B가 A의 잠금을 기다리는 순환이 생겨 누구도 진행할 수 없는 상태입니다. 예를 들어 A는 주문 행을 먼저 잠그고 재고 행을 기다리며, B는 재고 행을 먼저 잠그고 주문 행을 기다리면 순환이 됩니다.

InnoDB는 데드락을 감지하면 보통 한 트랜잭션을 롤백하여 순환을 해소합니다. 따라서 애플리케이션에서는 데드락 오류를 “다시는 일어나면 안 되는 버그”로만 취급하기보다, 짧고 멱등적인 단위라면 제한된 횟수로 재시도할 수 있게 설계해야 합니다. 재시도는 무한 반복이 아니어야 합니다. 횟수 제한, 지수 백오프, 사용자에게 보일 오류 처리, 중복 실행 방지 키가 필요합니다. 이메일 발송이나 외부 결제처럼 같은 호출을 다시 하면 위험한 작업을 트랜잭션 재시도에 무심코 포함해서는 안 됩니다.

데드락을 줄이는 실무 원칙은 단순하지만 효과가 큽니다. 첫째, 여러 테이블이나 행을 바꿀 때 가능한 한 일관된 순서로 접근합니다. 둘째, 적절한 인덱스로 스캔과 잠금 범위를 줄입니다. 셋째, 트랜잭션을 짧게 유지하고 외부 호출을 제외합니다. 넷째, 한 번에 너무 많은 행을 갱신하는 배치를 작은 묶음으로 나눕니다. 다섯째, 오류 로그와 잠금 정보를 보고 실제 충돌 SQL을 확인합니다. “데드락이므로 격리 수준을 낮추자”는 결론은 분석 전에는 성급합니다.

다음은 두 트랜잭션이 서로 다른 순서로 계좌 행을 잠가 데드락을 만들 수 있는 단순한 그림입니다. 실제 송금 로직은 잔액 검증, 감사 기록, 제약 조건까지 포함해야 하지만 순서 문제를 보기에는 충분합니다.

```sql
-- 트랜잭션 A
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 10;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 20;
COMMIT;

-- 트랜잭션 B가 account_id = 20을 먼저, 10을 나중에 갱신하면 순환 대기가 가능하다.
```

두 계좌를 언제나 작은 ID부터 잠그도록 정하면 순환 가능성을 줄일 수 있습니다. 하지만 애플리케이션의 모든 경로, 배치, 관리자 도구가 이 규칙을 지키는지 확인해야 합니다. 그래서 데이터 접근 순서는 코딩 관례가 아니라 설계·리뷰·테스트 대상입니다.

## 관찰과 진단: 추측 대신 현재 잠금과 SQL을 연결하기

잠금 문제를 진단할 때 “DB가 느리다”는 말만으로는 부족합니다. 어느 세션이 무엇을 기다리는지, 어느 SQL이 어떤 인덱스를 스캔했는지, 오래 열린 트랜잭션이 있는지를 연결해야 합니다. MySQL은 Performance Schema의 `data_locks`, `data_lock_waits` 같은 테이블과 InnoDB 트랜잭션 정보를 제공하여 잠금 객체와 대기 관계를 관찰할 수 있습니다. 버전과 권한, 설정에 따라 확인 가능한 정보가 다르므로 공식 문서와 운영 환경을 함께 확인합니다.

```sql
SELECT * FROM performance_schema.data_lock_waits;

SELECT * FROM performance_schema.data_locks;

SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx;
```

이 결과를 볼 때는 개인정보·SQL 파라미터 노출 정책도 고려해야 합니다. 운영 화면에 전체 SQL이나 민감 값을 무제한으로 보여 주는 것은 보안 문제가 될 수 있습니다. 또한 관찰 쿼리 자체가 문제를 자동 해결하지는 않습니다. 대기 세션의 SQL, 블로커의 SQL, 실행 계획, 트랜잭션 시작 시각, 애플리케이션 요청 ID를 연결할 수 있어야 원인을 재현하거나 개선할 수 있습니다.

`EXPLAIN` 또는 `EXPLAIN ANALYZE`로 쿼리가 어떤 인덱스를 선택하는지도 확인해야 합니다. 다만 분석용 SQL을 운영에 그대로 실행하기 전에 비용과 버전 지원 여부를 확인합니다. 인덱스 하나를 추가하면 잠금 범위와 읽기 성능에는 도움이 될 수 있지만, INSERT·UPDATE 비용과 저장 공간도 늘어납니다. 인덱스는 “잠금 오류를 없애는 스위치”가 아니라 읽기·쓰기·운영 비용의 균형을 바꾸는 설계 결정입니다.

## 업무 예시: 재고 차감은 조건부 UPDATE로도 표현할 수 있다

재고가 1개 이상일 때만 하나를 차감하는 요구는 먼저 SELECT로 수량을 읽고, 애플리케이션에서 판단한 뒤 UPDATE하는 형태로 쉽게 작성됩니다. 그러나 그 사이 다른 요청이 수량을 바꾸면 경쟁 조건이 생깁니다. 필요한 규칙이 단순하다면 조건을 UPDATE에 함께 넣어 **원자적 갱신**으로 표현하는 방법을 검토할 수 있습니다.

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 7001
  AND quantity > 0;
```

영향받은 행 수가 1이면 차감에 성공했고, 0이면 품절이거나 대상이 없었다고 해석할 수 있습니다. 이 방식은 별도 읽기와 쓰기 사이의 창을 줄여 줍니다. 하지만 주문 행 생성, 쿠폰 사용, 결제 승인처럼 여러 규칙이 함께 움직이면 단일 UPDATE만으로 끝나지 않을 수 있습니다. 그때는 트랜잭션과 제약 조건, 잠금 읽기, 재시도, 상태 설계를 조합합니다. SQL 기법 하나를 모든 동시성 문제의 해답으로 과장하지 않는 것이 중요합니다.

테스트도 정상 동작만 확인해서는 부족합니다. 같은 `product_id`에 동시에 요청을 보내고, 수량이 0·1·여러 개인 경우를 나누며, 실패한 요청이 주문·결제·알림을 어떤 상태로 남기는지 확인해야 합니다. 잠금 대기와 데드락은 충분한 부하에서만 보일 수 있으므로, 테스트 환경에서 동시 실행 시나리오와 타임아웃·재시도 관찰 기준을 준비하는 편이 좋습니다. 단, 테스트에서 본 순서가 운영에서도 항상 재현된다고 가정하면 안 됩니다.

## 마무리: 잠금은 피할 대상이 아니라 읽고 설계할 대상이다

MySQL InnoDB의 잠금 문제는 단순히 “행이 잠겼다”는 수준에서 끝나지 않습니다. MVCC가 일반 읽기를 어떻게 분리하는지, 잠금 읽기가 왜 인덱스 범위를 보호하는지, 격리 수준이 어떤 읽기 의미를 선택하게 하는지, 데드락을 왜 재시도와 함께 다뤄야 하는지를 연결해서 봐야 합니다. 특히 인덱스와 트랜잭션 길이는 성능 튜닝 항목인 동시에 동시성 설계 항목입니다.

새 기능을 설계할 때는 다음 질문부터 시작해 볼 수 있습니다. 이 변경은 어떤 데이터 규칙을 지켜야 하는가? 한 SQL로 원자적으로 표현할 수 있는가? 여러 단계라면 트랜잭션 경계는 어디인가? 어떤 인덱스를 통해 대상 범위를 찾는가? 실패·데드락 뒤 같은 요청을 다시 실행해도 안전한가? 이 질문에 답할 수 있으면 잠금 오류가 생겼을 때도 감으로 설정을 바꾸는 대신, 업무 요구와 SQL·인덱스·관찰 정보를 연결해 판단할 수 있습니다.

## 배포 전 점검: 잠금 설계를 테스트 가능한 규칙으로 바꾸기

잠금 설계는 문서에 “동시성 고려”라고 적는 것으로 끝나지 않습니다. 실제로 어떤 요청이 동시에 들어올 수 있는지, 어떤 결과를 허용하고 어떤 결과를 금지하는지를 테스트 케이스로 바꿔야 합니다. 예를 들어 재고가 한 개인 상품에 두 요청이 동시에 들어올 때, 기대 결과는 “둘 중 하나만 주문을 확정하고 다른 하나는 품절로 끝난다”일 수 있습니다. 이 기대 결과에는 재고 수량뿐 아니라 주문 행, 결제 요청, 사용자 메시지, 재시도 상태가 포함됩니다.

동시성 테스트는 같은 SQL을 두 세션에서 실행하는 작은 재현부터 시작할 수 있습니다. 세션 A가 잠금 읽기 뒤 커밋을 늦추고, 세션 B가 같은 행을 수정하려 할 때 대기하는지 확인합니다. 이후 애플리케이션 수준에서는 여러 요청을 병렬로 보내고, 최종 데이터가 제약 조건을 지키는지 검사합니다. 여기서 응답 순서가 매번 같을 것이라고 가정하면 안 됩니다. 중요한 것은 특정 요청이 이겼는지가 아니라, 승패와 무관하게 데이터 규칙이 지켜졌는지입니다.

```text
검증 대상: 쿠폰은 사용자 한 명이 한 번만 사용할 수 있다
동시 요청: 같은 사용자·같은 쿠폰으로 요청 두 건
기대 결과: 성공은 최대 한 건, 사용 기록은 한 행, 잔여 수량은 음수가 아님
실패 처리: 실패한 요청이 결제·알림을 성공으로 표시하지 않음
관찰 항목: 잠금 대기 시간, 데드락 오류, 재시도 횟수, 요청 추적 ID
```

데이터베이스 제약 조건도 이 검증의 일부입니다. 애플리케이션 코드가 아무리 신중해도 여러 인스턴스·배치·관리자 도구가 같은 테이블을 바꿀 수 있습니다. 업무적으로 중복되면 안 되는 값에는 가능한 경우 유니크 제약을 두고, 수량이 음수가 되면 안 되는 규칙에는 갱신 조건과 검증을 고려합니다. 단, 모든 업무 규칙을 단일 CHECK 제약이나 유니크 키로 표현할 수 있는 것은 아닙니다. 표현하기 어려운 규칙은 트랜잭션과 서비스 로직으로 보완하되, 어느 층이 어떤 규칙을 책임지는지 명확히 해야 합니다.

커넥션 풀도 자주 놓치는 경계입니다. 애플리케이션이 세션 격리 수준이나 세션 변수를 바꾼 뒤 원상 복구하지 않으면, 같은 연결을 빌린 다음 요청에 의도치 않은 설정이 남을 수 있습니다. 프레임워크가 트랜잭션 종료 시 연결 상태를 어떻게 정리하는지, 읽기 전용 작업과 쓰기 작업의 연결을 어떻게 분리하는지 확인합니다. 운영에서 간헐적으로만 보이는 잠금 문제는 SQL 자체가 아니라 풀 설정·자동 커밋·예외 처리 경로에서 시작될 수 있습니다.

## 설계 선택 비교: 낙관적 제어와 비관적 제어를 섞어 보기

잠금 읽기는 흔히 **비관적 동시성 제어(pessimistic concurrency control)** 와 연결해 설명합니다. 충돌이 일어날 수 있다고 보고 변경 전에 대상을 잠가 다른 작업을 기다리게 하는 접근입니다. 반대로 **낙관적 동시성 제어(optimistic concurrency control)** 는 충돌이 드물다고 보고, 수정할 때 버전 번호나 수정 시각을 조건으로 함께 확인합니다. 예를 들어 `version` 값이 읽었던 값과 같을 때만 UPDATE하고, 영향받은 행이 0이면 다른 변경이 있었다고 알려 재조회·재시도하게 할 수 있습니다.

```sql
UPDATE documents
SET title = ?, body = ?, version = version + 1
WHERE document_id = ?
  AND version = ?;
```

영향받은 행 수가 0이라고 해서 언제나 충돌이라는 뜻은 아닙니다. 대상이 삭제되었거나 권한 필터로 보이지 않을 수도 있으므로 업무 의미를 분리해야 합니다. 또한 낙관적 제어는 충돌이 잦은 재고 차감처럼 재시도가 많이 발생하는 상황에는 불리할 수 있습니다. 반대로 사람이 몇 분 동안 편집하는 문서 화면에 긴 트랜잭션 잠금을 잡는 것보다, 저장 시 버전 충돌을 알려 주는 방식이 더 적합할 수 있습니다. 어느 하나가 절대적으로 좋은 것이 아니라 충돌 빈도, 작업 시간, 사용자 경험, 재시도 가능성으로 선택합니다.

비관적 제어를 선택했다면 잠금 획득 순서와 시간 제한이 중요합니다. 낙관적 제어를 선택했다면 충돌 메시지와 병합·재시도 흐름이 중요합니다. 두 방식 모두 데이터베이스 트랜잭션이 필요 없다는 뜻은 아닙니다. 실제 서비스에서는 핵심 수량에는 원자 UPDATE를 쓰고, 장시간 편집 데이터에는 버전 검사를 쓰며, 여러 상태 변경에는 짧은 트랜잭션을 쓰는 식으로 함께 사용합니다.

## 운영 대화에서 확인할 질문

잠금 경합을 발견했을 때 DBA, 개발자, 운영 담당자가 같은 방향을 보려면 질문을 구체화해야 합니다. “락이 걸렸다” 대신 다음을 확인합니다. 블로킹 트랜잭션은 언제 시작했고 왜 아직 커밋되지 않았는가? 기다리는 SQL은 어떤 인덱스를 사용하며 몇 행을 조사하는가? 해당 요청은 외부 호출이나 사용자 입력을 트랜잭션 안에 포함하는가? 오류가 난 뒤 애플리케이션은 재시도했고, 재시도가 중복 업무를 만들 수 있는가? 이 질문은 책임을 전가하기 위한 것이 아니라 재현 가능한 원인을 찾기 위한 공통 언어입니다.

특히 배치 작업은 온라인 요청과 다른 시간·범위를 가집니다. 수백만 행을 한 번에 UPDATE하면 잠금 시간과 undo·redo 부담이 커질 수 있습니다. 처리 대상의 정렬 기준과 체크포인트를 두고 작은 묶음으로 나누며, 업무 시간대와 겹치는지 검토하는 것이 좋습니다. 단순히 배치를 잘게 자르면 항상 안전한 것은 아닙니다. 중간 실패 뒤 어디까지 반영되었는지, 다시 실행하면 같은 결과가 나는지, 다른 작업이 새로 넣은 행을 어떻게 처리할지까지 정의해야 합니다.

잠금 대기 시간 제한을 낮게 설정해 오류를 빨리 돌려주는 선택도 가능하지만, 이 역시 사용자 경험과 재시도 정책에 따라 달라집니다. 너무 짧으면 정상적인 짧은 경합도 실패가 되고, 너무 길면 웹 요청 스레드와 커넥션이 쌓일 수 있습니다. 값 하나를 정답으로 외우기보다 서비스의 응답 시간 목표, 작업 특성, 관찰된 대기 분포, 실패 처리 능력을 근거로 정하고 변경 전후를 비교해야 합니다.
