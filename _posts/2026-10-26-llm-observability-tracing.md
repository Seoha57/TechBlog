LLM(Large Language Model) 기능을 제품에 붙이면 실패 모양이 달라집니다. 서버 오류가 없고 응답도 빨리 왔는데 사용자는 답을 신뢰하지 못할 수 있습니다. 검색이 관련 없는 문서를 가져왔거나, 모델이 도구 호출 결과를 잘못 해석했거나, 프롬프트 변경 뒤 특정 언어의 품질만 낮아졌을 수도 있습니다. 기존 웹 서비스의 HTTP 상태 코드와 CPU 사용률만으로는 이런 문제를 충분히 설명하기 어렵습니다.

LLM 관찰성(observability)은 모델의 내부 생각을 들여다보는 일이 아닙니다. 사용자의 요청이 애플리케이션을 지나 프롬프트 구성, 검색, 모델 호출, 도구 실행, 형식 검증, 최종 응답으로 이어지는 과정에서 무엇이 일어났는지 재구성할 수 있게 만드는 일입니다. 이를 통해 장애를 빨리 찾고, 품질 저하와 비용 증가를 구분하며, 개선이 실제 사용자 경험에 도움이 됐는지 판단할 수 있습니다.

## 먼저 알아둘 기반 기술

로그(log)는 특정 사건의 상세 기록입니다. “요청이 시작됐다”, “검색 결과가 세 개였다”처럼 문맥을 남깁니다. 메트릭(metric)은 시간에 따른 숫자입니다. 요청 수, 오류율, 첫 토큰까지 걸린 시간, 입력·출력 토큰 수처럼 집계해 추세를 볼 때 유용합니다. 트레이스(trace)는 하나의 요청이 여러 서비스와 작업을 거칠 때 그 흐름을 연결한 기록이며, 작은 작업 단위를 span이라고 합니다. trace ID를 공유하면 API gateway, RAG 검색기, 모델 provider, 도구 실행기의 사건을 한 사용자 요청으로 묶을 수 있습니다.

토큰(token)은 모델이 텍스트를 처리하는 단위입니다. 글자 수와 정확히 같지 않으며, 입력 프롬프트와 출력 응답의 토큰 수는 비용·지연·컨텍스트 창 사용량에 직접 영향을 줍니다. 컨텍스트 창(context window)은 모델이 한 번의 호출에서 참고할 수 있는 입력과 출력의 범위입니다. 긴 대화나 많은 RAG 문서를 무조건 넣으면 정보가 풍부해 보이지만 비용이 늘고, 중요한 근거가 묻히거나 최대 길이를 넘길 수 있습니다.

RAG(Retrieval-Augmented Generation)는 모델의 학습 지식만 믿지 않고, 질의와 관련된 문서를 검색해 프롬프트에 넣는 방식입니다. tool calling은 모델이 직접 데이터를 바꾸는 대신 애플리케이션이 정의한 함수나 API 호출을 요청하도록 하는 구조입니다. 모델은 확률적으로 다음 토큰을 생성하므로, 도구 호출 JSON이나 답변 형식도 애플리케이션에서 검증해야 합니다. 관찰성은 이 구성 요소들이 연결된 한 번의 업무 흐름을 보게 합니다.

## 무엇을 한 요청 단위로 볼 것인가

가장 먼저 사용자 행동과 LLM 실행을 구분합니다. 사용자가 “이번 달 장애 요약을 보여 줘”라고 입력한 행동은 하나지만, 시스템은 의도 분류 모델 호출, 검색 쿼리 생성, 여러 문서 검색, 답변 생성, 표 형식 검증을 여러 번 수행할 수 있습니다. 상위 trace는 사용자 요청을 대표하고, 하위 span은 이 작업을 분해합니다. 이렇게 하면 최종 응답이 느린 이유가 모델 생성인지 검색 지연인지 외부 도구 대기인지 찾을 수 있습니다.

trace에 무작정 모든 값을 넣는 것은 좋지 않습니다. 최소한 요청 시각, 익명화된 사용자 또는 조직 식별자, 기능 이름, 모델 이름과 버전, 프롬프트 템플릿 버전, 입력·출력 토큰 수, 지연 시간, 결과 상태, 도구 이름, 문서 ID 같은 구조화된 속성을 정합니다. 이 속성은 이후 대시보드와 장애 조사에서 같은 의미로 쓰여야 합니다. `model=gpt-x`처럼 뭉뚱그린 값보다 provider·배포 모델·파라미터 정책을 구분할 수 있는 값이 원인 분석에 도움이 됩니다.

사용자에게 보여 준 최종 답변과 모델의 중간 실행 결과도 구분합니다. 검색 결과가 10개였다는 사실, 선택된 문서 ID, 도구 호출이 성공했는지는 관찰할 가치가 있지만, 전체 문서 본문이나 모든 대화 원문을 일반 로그에 넣을 필요는 없습니다. 민감도를 기준으로 요약·해시·분류 태그로 충분한 곳과, 제한된 디버깅 저장소에 안전하게 보관해야 하는 곳을 나눕니다.

## Trace 설계: 모델 호출만 보지 않기

LLM 호출 span에는 모델 provider, 모델 식별자, 요청 시작·종료 시각, 입력·출력 토큰 수, 중단·timeout 여부, 응답 형식 검증 결과를 남길 수 있습니다. 이 정보만으로도 특정 모델 교체 뒤 비용이나 지연이 변했는지 볼 수 있습니다. 그러나 답변 품질 문제의 상당수는 모델 이전 단계에서 발생하므로, 검색과 도구 span을 반드시 연결하는 편이 좋습니다.

RAG span에는 질의 정규화 버전, 검색 대상 컬렉션, 반환 문서 수, 선택된 문서 ID, reranking 적용 여부, 검색 지연을 남깁니다. 문서 본문 전체 대신 문서 버전·출처·권한 등급을 기록하면, 나중에 “어제는 맞았는데 오늘 틀렸다”는 신고가 있을 때 인덱스 변경·권한 필터·문서 갱신과 연결할 수 있습니다. 검색 결과가 없을 때 모델이 추측해서 답하는지, 모른다고 말하는지도 별도 결과 상태로 봅니다.

도구 호출 span에는 허용된 도구 이름, 검증된 인자 형식, 호출 시작·종료, 결과 크기, 오류 종류, 재시도 여부를 남깁니다. 도구 인자에 고객 정보나 비밀 키가 포함될 수 있으므로 원문 전체를 trace attribute로 기록하지 않는 것이 기본입니다. 필요한 경우 민감 필드를 마스킹하고, 도구가 실제 변경을 했는지와 변경 전 사용자 확인을 받았는지는 별도 감사 로그에서 관리합니다. 관찰 로그와 권한 감사 로그는 목적과 접근 권한이 다릅니다.

## 구체적 업무 예시: 사내 장애 지식 도우미

운영자가 “어제 결제 지연 원인과 대응 절차를 알려 줘”라고 질문하는 도우미를 생각해 보겠습니다. 시스템은 사용자의 조직 권한을 확인하고, 장애 보고서와 runbook에서 관련 문서를 검색한 뒤, 몇 개의 근거 문서를 프롬프트에 넣어 답을 생성합니다. 답변에는 출처 링크를 붙이고, 사용자가 “해결됐다” 또는 “도움 안 됐다” 피드백을 남길 수 있습니다.

이 요청의 trace에는 기능 이름 `incident-assistant`, 권한 필터 성공 여부, 검색한 컬렉션, 선택 문서 ID와 버전, 모델 이름, 입력·출력 토큰 수, 첫 토큰 지연, 전체 완료 시간, 출처 링크 생성 여부, 형식 검증 결과를 남길 수 있습니다. 사용자의 질문 전문과 장애 보고서 본문은 기본 trace에 넣지 않습니다. 원문이 꼭 필요한 제한된 디버깅 환경이라면 보존 기간·접근 승인·마스킹 규칙을 별도로 둡니다.

사용자가 “답변이 틀렸다”고 평가했다면 trace ID로 당시 검색 문서와 템플릿 버전을 찾습니다. 검색 결과가 오래된 runbook만 포함했는지, 최신 문서가 권한 필터에서 제외됐는지, 모델이 출처에 없는 내용을 덧붙였는지 구분합니다. 이렇게 하면 단순히 모델 온도를 바꾸는 대신 문서 갱신·검색 필터·답변 정책 중 어디를 고쳐야 하는지 근거를 갖게 됩니다.

## 품질 지표는 한 숫자가 아니다

품질을 별점 하나로만 보면 개선의 방향을 잃기 쉽습니다. 사실성, 근거 포함, 작업 완료 여부, 형식 준수, 안전한 거절, 사용자 만족도는 서로 다른 성질입니다. 예를 들어 답변이 짧아져 평균 지연이 줄었지만 근거 링크가 사라졌다면, 속도만으로는 품질 개선인지 판단할 수 없습니다. 기능의 목적에 맞춰 소수의 지표를 선택하고, 서로 충돌할 수 있음을 인정해야 합니다.

오프라인 평가는 미리 준비한 질문·문서·기대 기준으로 프롬프트나 모델 변경을 비교하는 방식입니다. 일관되게 비교할 수 있다는 장점이 있지만, 실제 사용자의 새 질문을 모두 대표하지는 않습니다. 온라인 신호는 실제 클릭, 재질문, 작업 완료, 피드백을 볼 수 있지만 사용자 상황과 UI 변화의 영향을 함께 받습니다. 두 종류를 함께 보되, 약한 신호 하나로 모델이 좋아졌다고 단정하지 않습니다.

평가셋의 각 사례에는 업무 영역, 난이도, 필요한 출처, 허용 가능한 답변 방식, 실패 유형을 붙이면 회귀를 더 자세히 볼 수 있습니다. “정답인가”만 묻기보다 “출처가 실제 주장과 맞는가”, “권한 없는 문서를 노출하지 않았는가”, “도구 실행 전 확인을 요구했는가”처럼 제품 위험에 맞는 기준을 둡니다. 자동 채점은 빠르지만 모호한 사례와 높은 영향의 작업에는 사람 검토를 남겨야 합니다.

## 비용과 지연을 함께 읽기

LLM 비용은 모델 호출 횟수와 입·출력 토큰 수에 크게 영향을 받습니다. 기능별, 조직별, 모델별로 입력·출력 토큰과 호출 수를 집계하면 예상치 못한 급증을 발견할 수 있습니다. 다만 비용이 높다는 사실만으로 낭비라고 할 수는 없습니다. 복잡한 보고서 생성처럼 긴 근거와 긴 답이 필요한 기능은 비용이 들 수 있으며, 중요한 것은 그 비용이 사용자 가치와 정책에 맞는지입니다.

지연은 전체 응답 시간과 첫 토큰까지의 시간으로 나누어 봅니다. 스트리밍 UI에서는 첫 토큰이 빠르면 사용자가 기다리는 느낌이 줄 수 있지만, 검색·도구 호출이 오래 걸리면 최종 완료는 여전히 늦을 수 있습니다. p50 평균뿐 아니라 p95 같은 높은 지연 구간, timeout 비율, 취소율, 재시도율을 봐야 일부 사용자만 겪는 문제를 놓치지 않습니다.

비용을 줄이기 위해 무조건 작은 모델이나 짧은 프롬프트를 쓰면 품질·안전이 나빠질 수 있습니다. 먼저 중복 문서 제거, 불필요한 도구 호출 방지, 적절한 검색 개수, 캐시의 정확성, 모델별 라우팅 조건을 관찰값으로 확인합니다. 예를 들어 단순 분류에는 작은 모델이 충분하고, 근거가 필요한 긴 요약에는 다른 모델이 필요할 수 있습니다. 이 정책은 가설이므로 평가와 trace로 계속 검증해야 합니다.

## 개인정보와 비밀 정보의 경계

LLM 관찰 데이터에는 프롬프트·응답·검색 문서·도구 인자가 섞일 수 있어 개인정보와 비밀 정보가 들어갈 가능성이 큽니다. 따라서 수집 전에 “문제 조사에 꼭 필요한 필드는 무엇인가”를 정하고, 원문보다 길이·문서 ID·오류 분류·토큰 수 같은 메타데이터를 기본값으로 합니다. 이메일, 전화번호, 계좌 정보, access token, 소스 코드 비밀 값은 마스킹 대상이며, 모델 provider로 보내기 전에도 별도의 정책이 필요합니다.

보존 기간도 설계의 일부입니다. 디버깅을 위해 무기한 원문을 쌓아 두면 유출 범위가 커집니다. 운영 지표는 장기 집계로 남기고, 원문 trace는 짧은 기간과 제한된 접근 권한으로 관리하는 식으로 목적을 나눌 수 있습니다. 삭제 요청, 조직 탈퇴, 법적 보관 요구가 있을 때 어떤 데이터가 어디에 남는지 알 수 있어야 합니다.

접근 통제는 대시보드 화면만 가리는 것으로 끝나지 않습니다. export, 알림, 오류 추적 도구, 개발 환경 복사본에도 같은 규칙이 적용되는지 확인해야 합니다. 특히 trace ID를 공유해 문제를 조사할 때는 필요한 사람만 제한된 세부 정보를 보게 하고, 접근 자체를 감사할 수 있어야 합니다. 편한 디버깅과 안전한 데이터 처리는 서로 반대가 아니라, 필요한 정보를 처음부터 구조화해 수집할 때 함께 가능해집니다.

## 프롬프트·모델 변경을 배포처럼 다루기

프롬프트 템플릿, 시스템 지시, 검색 필터, 모델 버전, tool schema 변경은 모두 사용자 결과를 바꿀 수 있습니다. 코드 변경처럼 버전 식별자를 붙이고 trace에 기록하면, 특정 변경 이후 오류·비용·사용자 피드백이 어떻게 움직였는지 비교할 수 있습니다. 문자열 한 줄을 바꿨다고 가볍게 배포하면, 나중에 어떤 실행이 어떤 정책을 사용했는지 찾기 어렵습니다.

변경 전에는 대표 평가셋으로 형식·근거·안전성·도구 호출을 확인하고, 변경 후에는 제한된 트래픽에서 온라인 지표를 봅니다. 되돌릴 기준도 미리 정합니다. 예를 들어 schema validation 실패율이 올라가거나 권한 관련 거절이 비정상적으로 줄면 즉시 이전 템플릿으로 되돌릴 수 있어야 합니다. 단, 사용자마다 질문이 다르므로 작은 표본의 좋아 보이는 결과만으로 확정하지 않습니다.

실험을 할 때는 사용자가 같은 대화에서 서로 다른 정책을 경험해 혼란스럽지 않게 배정 단위를 정합니다. 모델·프롬프트·검색 인덱스를 동시에 바꾸면 결과 차이의 원인을 알기 어려우므로, 가능한 한 하나의 가설을 검증하는 변경으로 나눕니다. 관찰성은 모든 변경을 느리게 만들려는 절차가 아니라, 되돌릴 수 없는 품질 저하를 빠르게 알아차리기 위한 장치입니다.

## 오류 분류를 제품 언어로 만들기

LLM 기능의 오류를 모두 `model_error`로 묶으면 개선할 곳을 찾기 어렵습니다. 입력이 정책상 허용되지 않아 차단된 경우, 검색 결과가 없는 경우, provider timeout, 응답 JSON 형식 오류, 도구 권한 거절, tool timeout, 사용자 취소, 최종 품질 검토 실패는 서로 다른 대응이 필요합니다. 오류 코드는 운영자만 이해하는 기술 메시지가 아니라, 사용자에게 어떤 다음 행동을 안내할지 결정하는 제품 계약이기도 합니다.

예를 들어 검색 결과가 없을 때는 모델이 답을 꾸며 내는 대신 “연결할 근거를 찾지 못했다”고 알려 줄 수 있습니다. tool timeout은 사용자가 다시 시도할 수 있는 일시 오류일 수 있지만, 권한 거절은 관리자 승인 또는 다른 계정으로 해결해야 할 수 있습니다. JSON schema 검증 실패는 provider 오류처럼 보이지만 프롬프트·모델·schema 변경의 호환성 문제일 수 있습니다. trace에 오류 유형과 발생 span을 남기면 같은 500 또는 200 뒤에 숨은 다른 원인을 구분할 수 있습니다.

오류 문구에는 내부 provider 이름, 원문 프롬프트, stack trace, 권한 정책 세부 정보를 그대로 노출하지 않습니다. 사용자에게는 현재 요청이 완료되지 않았다는 사실, 다시 시도해도 되는지, 대체 경로가 있는지를 알려 주고, 운영자는 안전한 실행 ID로 세부 진단을 찾게 합니다. 이 분리는 보안뿐 아니라 지원 효율에도 도움이 됩니다. 고객 지원이 trace ID와 시각만으로 사건을 넘기면 민감 원문을 여러 채널에 복사할 필요가 줄어듭니다.

## 도구 실행은 결과와 영향으로 측정하기

도구 호출이 가능한 AI 에이전트에서는 모델의 텍스트 답변보다 실제 side effect가 더 중요할 수 있습니다. 읽기 전용 검색 도구, 티켓 초안 생성, 캘린더 조회, 배포 실행은 모두 같은 “도구 호출”처럼 보여도 위험 수준이 다릅니다. 관찰 데이터에는 도구 이름, 읽기·쓰기 구분, 사용자 승인 여부, 검증된 인자 범주, 성공·실패·취소 결과, 영향 받은 업무 객체 수를 남겨야 합니다. 단, 티켓 내용이나 고객 데이터처럼 원문이 민감하면 객체 ID나 안전한 요약으로 충분한지 먼저 검토합니다.

쓰기 도구는 특히 “모델이 호출했다”와 “업무 변경이 확정됐다”를 구분해야 합니다. 모델이 배포 요청을 만들었지만 정책 검증에서 거절됐는지, 사용자 승인을 기다리는지, 실제 배포가 시작됐는지, 롤백됐는지는 서로 다른 상태입니다. 이 상태를 하나의 성공 metric으로 합치면 실패한 자동화가 성공처럼 보이거나 반대로 안전하게 차단된 요청이 오류율을 불필요하게 올릴 수 있습니다. 상태 전이와 감사 기록을 명확히 나누는 이유입니다.

도구 호출 품질은 횟수가 적다고 항상 좋은 것도, 많다고 항상 나쁜 것도 아닙니다. 필요한 문서를 세 번 조회해 정확한 답을 만든다면 합리적일 수 있지만, 같은 검색을 반복하거나 실패한 도구를 무한 호출하면 비용과 지연이 커집니다. 기능별로 예상 가능한 도구 호출 수와 최대 실행 시간을 정하고, 이 범위를 벗어난 trace를 조사 대상으로 삼습니다. 제한은 모델을 벌주는 장치가 아니라 시스템이 폭주하지 않게 하는 운영 경계입니다.

## RAG 품질 저하를 진단하는 순서

RAG 답변이 나빠졌다는 보고를 받으면 모델을 먼저 교체하기보다 검색 경로를 분해해 봅니다. 질의가 어떤 검색어와 embedding으로 변환됐는지, 어느 컬렉션을 선택했는지, 권한 필터가 어떤 문서를 제외했는지, 상위 문서가 reranker에서 어떻게 바뀌었는지, 최종 프롬프트에는 어느 조각이 들어갔는지를 순서대로 봅니다. 각 단계의 문서 ID와 버전이 trace에 있으면 현재 인덱스만 보고 과거 사건을 추측하지 않아도 됩니다.

문서 전처리 변경도 품질 변화의 원인이 될 수 있습니다. 청크 길이를 바꾸거나 PDF 파서, OCR, 메타데이터 규칙을 바꾸면 같은 문서라도 검색 결과가 달라집니다. 따라서 인덱스 이름·문서 파싱 버전·청크 전략·임베딩 모델 버전을 실행 속성으로 남기고, 큰 변경은 대표 질의로 회귀 평가합니다. 단순히 검색 hit 수가 많아졌다고 좋은 것은 아닙니다. 답변에 실제로 필요한 근거가 상위에 왔는지와, 불필요한 문서가 컨텍스트를 차지하지 않는지를 함께 봐야 합니다.

검색 실패를 모두 품질 결함으로 다루지 않는 것도 중요합니다. 접근 권한이 없는 문서는 보여 주지 않아야 하며, 조직 정책상 공개되지 않은 정보는 올바른 답변에 포함되면 안 됩니다. 따라서 권한 필터가 문서를 제외한 것은 보안 성공일 수 있습니다. 관찰성은 retrieval recall을 높이는 것뿐 아니라, 필요한 때에 안전하게 모른다고 말했는지 검증하는 도구여야 합니다.

## 알림은 사용자 영향 중심으로 설계하기

모든 토큰 증가나 단일 provider 오류에 알림을 보내면 담당자는 곧 알림을 무시하게 됩니다. 알림은 사용자 영향이 크고 조치 가능한 신호에 연결합니다. 예를 들어 특정 기능의 timeout 비율이 지속적으로 높아지고, final answer 생성 실패가 늘며, fallback 모델도 실패하는 경우는 조사가 필요할 수 있습니다. 반면 일시적인 retry 한 번이나 저트래픽 기능의 작은 비용 변동은 대시보드에서 추세로 확인하는 편이 나을 수 있습니다.

알림 메시지에는 범위와 행동을 담습니다. 어느 기능·모델·조직에서 언제부터 문제가 생겼는지, 오류가 어느 span에서 났는지, 최근 템플릿·인덱스·provider 설정 변경이 있었는지, 확인할 대시보드와 runbook이 무엇인지 알려 주면 당번자가 빠르게 시작할 수 있습니다. 원문 프롬프트나 비밀 값은 알림에 넣지 않습니다. 알림은 상황을 완전히 설명하는 보고서가 아니라 안전한 조사 진입점입니다.

비용 알림도 절대 금액 하나보다 기준선 대비 변화, 기능별 분포, 사용량 급증 원인을 함께 봐야 합니다. 새 고객 온보딩이나 합법적인 대량 작업으로 증가했는지, retry 폭주·프롬프트 중복·루프가 원인인지 구분해야 합니다. 비용을 줄이려는 조치가 품질을 망치지 않았는지 평가 지표를 다시 확인하는 루프를 두면, 운영 목표가 한쪽으로 치우치는 것을 막을 수 있습니다.

## 다중 모델과 fallback의 관찰

서비스는 가용성·비용·지역 규정 때문에 여러 모델이나 provider를 쓸 수 있습니다. fallback이 있는 경우 trace에는 원래 선택한 모델, fallback으로 전환한 이유, 실제 사용한 모델, 각 시도의 지연·토큰·오류를 남겨야 합니다. 그렇지 않으면 사용자에게는 성공한 요청이지만, 뒤에서 비싼 fallback이 계속 쓰여 비용이 늘어나는 현상을 놓칠 수 있습니다.

fallback은 기능을 계속 제공하는 데 유용하지만 결과 품질과 형식이 같다고 보장하지 않습니다. 특정 모델이 구조화 출력을 더 잘 지키거나 특정 언어에서 더 좋은 결과를 낼 수 있으므로, fallback 경로도 같은 평가셋과 schema 검증을 통과해야 합니다. 사용자에게 모델명을 과하게 노출할 필요는 없지만, 응답 정책이 달라질 수 있는 고영향 작업에서는 재검토 또는 제한된 기능 모드가 필요한지 제품이 결정해야 합니다.

라우팅 규칙을 바꿀 때도 실험의 원칙이 적용됩니다. 토큰 길이, 기능 종류, 민감도, SLA를 기준으로 어떤 모델을 고를지 명시하고, 예외·fallback 비율·성공률·사용자 만족도를 연결해 봅니다. 모델 이름을 환경 변수 하나로 바꾸는 방식은 빠르지만, 문제 발생 시 어떤 요청이 어떤 정책을 탔는지 복원하기 어렵습니다. 관찰 가능한 routing은 운영 가능성의 일부입니다.

## 사람이 검토해야 하는 신호

자동 지표는 빠르지만 의미를 완전히 해석하지는 못합니다. 재질문이 많다고 해서 항상 답변이 나쁜 것은 아닙니다. 사용자가 더 깊이 탐색하고 있을 수도 있고, UI가 후속 질문을 유도했을 수도 있습니다. 반대로 별점이 높아도 사용자가 답을 실제 업무에 쓰지 않았을 수 있습니다. 높은 영향의 답변, 새 도메인, 평가 기준이 모호한 기능에는 표본을 사람 검토로 읽고 자동 신호가 무엇을 놓치는지 확인해야 합니다.

사람 검토에는 일관된 rubric이 필요합니다. 근거의 정확성, 질문 충족, 불확실성 표현, 안전 정책 준수, 문체와 형식처럼 평가 항목을 정하고, 검토자가 원문에 접근할 권한과 마스킹 규칙도 정합니다. 검토 결과는 개인을 감시하기 위한 지표가 아니라 제품 개선의 입력으로 사용해야 합니다. 어떤 실패 유형이 반복되는지 분류해 평가셋과 프롬프트·검색 정책에 반영하면, 일회성 피드백이 재현 가능한 개선으로 이어집니다.

## 한계와 적용 기준 Q&A

### Q. 모든 프롬프트와 응답을 저장하면 품질 분석이 쉬워지지 않나요?

A. 분석은 쉬워질 수 있지만 개인정보·영업 비밀·보존 비용과 위험이 커집니다. 기본값은 최소 수집이어야 합니다. 원문이 꼭 필요한 고장 분석은 사전 동의, 마스킹, 짧은 보존 기간, 좁은 접근 권한을 갖춘 별도 절차에서 수행하세요.

### Q. 모델이 200 응답을 주고 형식 검증도 통과하면 성공 아닌가요?

A. 기술적 성공일 뿐 업무 성공은 아닐 수 있습니다. 근거 없는 답, 잘못된 권한의 문서 노출, 불필요한 도구 실행, 사용자의 재질문은 모두 별도로 봐야 합니다. 기능 목적에 맞는 품질 지표와 사용자 피드백을 함께 연결해야 합니다.

### Q. OpenTelemetry만 설치하면 LLM 관찰성이 끝나나요?

A. OpenTelemetry는 trace·metric을 공통 형식으로 보내는 기반이 될 수 있지만, 어떤 속성을 수집할지, 민감 정보를 어떻게 보호할지, 품질을 무엇으로 평가할지는 제품이 결정해야 합니다. 표준 도입은 시작점이지 판단 기준을 대신하지 않습니다.

### Q. 관찰 비용이 너무 크면 무엇부터 줄여야 하나요?

A. 원문 프롬프트를 무제한 저장하거나 모든 요청을 고해상도 trace로 남기는 방식부터 줄이세요. 기능별 표본 수집, 메타데이터 중심 기록, 짧은 원문 보존 기간, 오류·고영향 요청 우선 수집을 조합할 수 있습니다. 다만 비용을 줄이면서 오류 유형·모델 버전·토큰·지연 같은 최소 진단 정보까지 없애면 장애와 품질 회귀를 설명할 수 없게 됩니다.

## 시작을 위한 최소 계측

처음부터 모든 모델과 도구를 완벽하게 계측하려 하지 않아도 됩니다. 한 기능을 골라 상위 요청 ID, 모델 호출 시간과 토큰, 검색 문서 ID, 도구 성공·실패, 최종 검증 결과를 연결하는 것부터 시작하세요. 그 뒤 실제 장애와 사용자 피드백에서 자주 필요한 속성을 추가합니다. 이 순서는 과도한 개인정보 수집과 사용되지 않는 대시보드를 피하면서도, 가장 중요한 질문인 “이 답은 어떤 경로로 만들어졌는가”에 답할 기반을 만듭니다.

## 운영 체크리스트

정기적으로 관찰 스키마도 검토하세요. 더 이상 쓰지 않는 속성은 수집을 줄이고, 새 기능에서 필요한 오류 분류와 버전 식별자는 추가합니다. 수집 항목의 목적·민감도·보존 기간을 문서화하면 관찰성이 시간이 지날수록 개인정보 저장소로 변하는 것을 막을 수 있습니다.

새 LLM 기능을 출시하기 전에 요청 단위와 trace 경계를 정하고, 모델·프롬프트·검색·도구·검증 단계가 각각 span으로 연결되는지 확인합니다. 기능 이름과 버전, 토큰, 지연, 오류 분류, 결과 상태 같은 최소 속성을 정하되 민감 원문은 기본 수집에서 제외합니다. 사용자 피드백과 평가 결과가 trace ID 또는 안전한 실행 ID로 연결되는지도 점검합니다.

장애가 발생하면 먼저 provider 오류인지, 모델 호출 지연인지, 검색·도구·검증 중 어느 단계인지 분류합니다. 이어서 같은 시간의 배포·모델 변경·인덱스 갱신·트래픽 증가를 확인하고, 영향 받은 조직과 기능 범위를 파악합니다. 프롬프트 원문을 바로 넓게 열람하기보다 구조화된 속성과 안전한 샘플로 가설을 좁히는 편이 데이터 보호와 조사 속도에 유리합니다.

LLM 관찰성의 목표는 대시보드를 많이 만드는 것이 아닙니다. 사용자가 받은 결과, 그 결과를 만든 근거와 도구, 비용과 지연, 변경 이력을 연결해 “왜 이런 답이 나왔는가”에 답할 수 있게 만드는 것입니다. 그 연결이 있어야 모델을 바꾸거나 RAG를 개선할 때 감이 아니라 검증으로 품질과 운영 위험을 다룰 수 있습니다.
