## 먼저 답하기

### Q. 보안 점검은 코드 정적 분석으로 충분하지 않나요?

A. 정적 분석(SAST, Static Application Security Testing)은 소스 코드를 읽어 위험한 패턴을 찾기 때문에 개발 초기에 유용하지만, 코드에는 보이지 않는 문제를 놓칩니다. 예를 들어 운영 서버 설정에서 빠진 보안 응답 헤더, 배포된 환경에서만 드러나는 쿠키 속성 오류, 프록시와 프레임워크가 합쳐져 생긴 노출 경로는 코드만 봐서는 알 수 없습니다. **동적 애플리케이션 보안 테스트(DAST, Dynamic Application Security Testing)** 는 실제로 실행 중인 애플리케이션에 HTTP 요청을 보내 응답을 분석하므로, 배포된 모습 그대로의 문제를 찾습니다. 두 방식은 서로 대체가 아니라 보완 관계입니다. 이 글은 오픈소스 DAST 도구인 ZAP(Zed Attack Proxy)을 기준으로 설명하며, 예시 명령과 출력은 설명을 위한 것이고 제가 특정 서비스에 직접 실행해 얻은 결과가 아닙니다.

### Q. 그럼 ZAP을 CI에 걸어 두면 보안이 확보되나요?

A. 그렇지 않습니다. ZAP의 기본 스캔은 응답을 관찰하는 패시브 분석 중심이라 헤더·쿠키 같은 "관찰 가능한 결함"에 강하고, 비즈니스 로직 결함(남의 주문을 조회할 수 있는 권한 우회 등)은 잘 찾지 못합니다. 또 자동 도구는 오탐(false positive, 문제가 아닌데 문제로 보고함)과 미탐(false negative, 문제가 있는데 못 찾음)을 모두 냅니다. 그래서 ZAP은 "자주, 싸게, 반복해서 기본 위생을 확인하는 안전망"으로 두고, 인증·권한·업무 로직은 사람의 침투 테스트와 설계 검토로 보완하는 것이 현실적인 역할 분담입니다. 또한 액티브 스캔은 실제 공격 요청을 보내므로 반드시 허가된 격리 환경에서만 실행해야 합니다.

## 먼저 알아둘 기반 기술

이 절은 본문을 읽는 데 필요한 사전 개념을 가장 기초적인 것부터 ZAP 직전까지 쌓습니다. HTTP 요청·응답과 헤더·쿠키에서 시작해, 프록시와 중간자, 취약점 분류와 위험도, 크롤링과 인증 세션, CI 종료 코드 순서입니다. 각 소절 끝에 본문의 어느 절로 이어지는지 적었고, 절 마지막에 연결 지도를 표로 정리했습니다.

### HTTP 요청·응답, 헤더와 쿠키

HTTP(HyperText Transfer Protocol)는 브라우저와 서버가 요청(request)과 응답(response)을 주고받는 규칙입니다. 요청에는 메서드(`GET`은 조회, `POST`는 전송), 주소, 헤더(header, 요청에 붙는 부가 정보), 본문이 담기고, 응답에는 상태 코드(200 성공, 404 없음, 500 서버 오류 등), 헤더, 본문이 담깁니다. 식당 주문서(요청)와 영수증(응답)에 비유하면, 헤더는 주문서 귀퉁이에 적는 "알레르기 있음" 같은 부가 메모입니다.

보안과 관련된 중요한 응답 헤더가 몇 가지 있습니다. `Content-Security-Policy`는 페이지가 불러올 수 있는 스크립트의 출처를 제한해 악성 스크립트 삽입(XSS, Cross-Site Scripting) 피해를 줄이고, `X-Content-Type-Options: nosniff`는 브라우저가 파일 형식을 멋대로 추측하지 못하게 하며, `Strict-Transport-Security`는 이후 접속을 HTTPS로 강제합니다. **쿠키(cookie)** 는 서버가 브라우저에 맡겨 두는 작은 정보 조각으로 로그인 세션 식별자를 담는 경우가 많고, `Secure`(HTTPS에서만 전송), `HttpOnly`(스크립트가 읽지 못함), `SameSite`(다른 사이트에서 온 요청에 쿠키를 붙일지 제한) 속성으로 보호합니다.

이 개념을 모르면 본문에서 ZAP이 보고하는 "헤더 누락", "쿠키에 HttpOnly 없음" 같은 알림이 무엇을 뜻하는지 알 수 없습니다. 이 개념은 아래 「패시브 스캔: 보내지 않고 관찰한다」 절에서 응답 헤더·쿠키 점검으로, 「결과 읽기와 오탐 규칙 관리」 절에서 알림 해석으로 쓰입니다.

### 프록시와 중간자: 대화 사이에 끼어드는 도구

프록시(proxy)는 클라이언트와 서버 사이에 놓여 요청과 응답을 대신 전달하는 중계자입니다. 사내 인터넷 프록시처럼 접근을 통제하는 용도로도 쓰지만, 보안 테스트에서는 **가로채기(intercepting) 프록시**로 쓰입니다. 브라우저의 모든 요청이 먼저 프록시를 거치게 설정하면, 프록시는 요청과 응답을 기록하고 보여 주고 필요하면 수정해서 전달할 수 있습니다. 우편물을 배달 전에 사무실에서 열어 보고 사본을 만든 뒤 다시 봉해 전달하는 중간 사무소와 같습니다.

ZAP의 이름 "Zed Attack Proxy"가 바로 이 구조에서 왔습니다. HTTPS는 암호화되어 있으므로 프록시가 내용을 보려면 브라우저가 프록시가 만든 인증서(CA 인증서)를 신뢰하도록 설정해야 하고, 이는 반드시 테스트용 브라우저 프로필에서만 해야 합니다. 이 개념은 아래 「ZAP의 구성: 프록시를 중심에 둔 도구상자」 절에서 ZAP의 핵심 구조로, 「수동 탐색으로 시작하기」 절에서 브라우저 연동으로 쓰입니다.

### 취약점 분류와 위험도: OWASP Top 10과 알림 등급

OWASP(Open Worldwide Application Security Project)는 웹 애플리케이션 보안 지식을 공개하는 비영리 커뮤니티이며, 그 대표 산출물인 **OWASP Top 10**은 웹 애플리케이션에서 흔하고 영향이 큰 위험 범주를 정리한 목록입니다. 접근 통제 실패, 암호화 실패, 인젝션(injection, 입력값을 이용해 의도하지 않은 명령을 실행시키는 공격) 같은 범주가 들어 있으며, 도구의 점검 항목을 이런 분류에 맞춰 설명할 때 기준이 됩니다. 또 CWE(Common Weakness Enumeration)는 소프트웨어 약점의 번호 체계라서 보고서에서 "CWE-693"처럼 표기되면 약점 종류를 뜻합니다.

ZAP은 발견한 문제를 **알림(alert)** 으로 보고하고 위험도(risk)를 High, Medium, Low, Informational로, 탐지 확신도(confidence)를 별도로 표시합니다. 위험도는 "문제가 실제라면 얼마나 위험한가"이고, 확신도는 "ZAP이 이 판단을 얼마나 믿는가"이므로 둘을 구분해서 읽어야 합니다. 이 개념을 모르면 본문에서 어떤 알림은 CI를 실패시키고 어떤 알림은 경고로만 두는 기준을 이해하기 어렵습니다. 이 개념은 아래 「결과 읽기와 오탐 규칙 관리」 절에서 FAIL·WARN 분류로, 「한계와 적용 기준 Q&A」 절에서 Top 10 대응 범위로 쓰입니다.

### 크롤링, 인증 세션, 컨텍스트

크롤러(crawler)는 페이지의 링크를 따라가며 사이트의 주소 목록을 만드는 프로그램입니다. 스캔 도구는 점검할 대상 주소를 알아야 하므로 먼저 크롤링으로 "이 사이트에 어떤 경로가 있는가"를 파악합니다. ZAP에서는 이를 스파이더(spider)라고 부릅니다. 다만 링크가 자바스크립트로 동적으로 생성되는 화면은 일반 스파이더가 보지 못하므로 브라우저를 실제로 구동하는 AJAX 스파이더가 따로 있습니다. API는 링크로 연결되지 않으므로 OpenAPI 정의 문서를 읽어 경로 목록을 얻는 방식을 씁니다.

로그인이 필요한 영역은 세션을 유지한 채 접근해야 합니다. **컨텍스트(context)** 는 ZAP에서 스캔 범위(어느 주소 패턴이 대상인지)와 인증 방식, 사용자 정보를 묶어 정의하는 단위입니다. 범위를 정하지 않으면 로그아웃 링크를 눌러 세션이 끊기거나 외부 사이트까지 스캔하는 사고가 생길 수 있으므로 컨텍스트는 안전장치이기도 합니다. 이 개념은 아래 「스파이더와 범위 설정」 절에서 탐색 범위로, 「인증이 필요한 영역」 절에서 세션 유지 전략으로 쓰입니다.

### CI 파이프라인과 종료 코드

CI(Continuous Integration, 지속적 통합)는 코드가 바뀔 때마다 자동으로 빌드와 테스트를 실행하는 방식이고, 그 순서를 정의한 것이 파이프라인입니다. 명령행 프로그램은 끝날 때 숫자 하나, **종료 코드(exit code)** 를 운영체제에 돌려주며 관례적으로 0은 성공, 0이 아니면 실패를 뜻합니다. CI는 종료 코드가 0이 아니면 그 단계를 실패로 처리하고 이후 단계를 중단합니다. 따라서 ZAP 같은 도구를 CI에 연결한다는 것은 "알림 분류 결과를 종료 코드로 번역해 통과·실패를 결정한다"는 뜻입니다.

도커(Docker) 컨테이너는 애플리케이션과 실행 환경을 하나로 묶은 단위이고, 도구를 내 PC에 설치하지 않고 공식 이미지를 내려받아 바로 실행할 수 있게 해 줍니다. ZAP은 공식 도커 이미지를 제공하므로 CI에서 이미지를 실행하는 한 줄로 스캔을 돌립니다. 이 개념은 아래 「baseline 스캔 실행하기」 절에서 도커 명령으로, 「CI 게이트로 연결하기」 절에서 종료 코드 처리로 쓰입니다.

### 기반 개념과 본문 연결 지도

| 기반 개념 | 쓰이는 본문 절 | 그 절에서의 역할 |
|---|---|---|
| HTTP 헤더와 쿠키 | 패시브 스캔: 보내지 않고 관찰한다, 결과 읽기와 오탐 규칙 관리 | 알림이 가리키는 헤더·쿠키 결함의 의미 |
| 프록시와 중간자 | ZAP의 구성: 프록시를 중심에 둔 도구상자, 수동 탐색으로 시작하기 | ZAP의 기본 구조와 브라우저 연동 |
| OWASP Top 10과 알림 등급 | 결과 읽기와 오탐 규칙 관리, 한계와 적용 기준 Q&A | FAIL·WARN 기준과 탐지 범위의 한계 |
| 크롤링·인증 세션·컨텍스트 | 스파이더와 범위 설정, 인증이 필요한 영역 | 탐색 범위와 로그인 세션 유지 |
| CI와 종료 코드 | baseline 스캔 실행하기, CI 게이트로 연결하기 | 스캔 결과를 통과·실패 판정으로 변환 |

## DAST가 맞는 자리: SAST·침투 테스트와의 비교

보안 점검에는 여러 층이 있고 각각 보는 대상이 다릅니다. 어느 층이 어떤 문제를 잡는지 알아야 DAST에 과한 기대를 하지 않게 됩니다.

| 구분 | 보는 대상 | 실행 시점 | 잘 찾는 것 | 놓치기 쉬운 것 |
|---|---|---|---|---|
| SAST(정적 분석) | 소스 코드 | 커밋·빌드 | 위험한 코드 패턴, 하드코딩된 비밀 | 배포 설정, 런타임 상호작용 |
| SCA(오픈소스 구성 분석) | 의존 라이브러리 | 빌드 | 알려진 취약 버전 | 우리 코드의 로직 결함 |
| DAST(동적 분석) | 실행 중인 앱 | 배포 후 테스트 환경 | 헤더·쿠키 설정, 반사형 입력 문제, 노출된 경로 | 코드 내부 경로, 복잡한 업무 로직 |
| 침투 테스트(수동) | 앱과 업무 흐름 | 릴리스 전후 정기 | 권한 우회, 로직 결함, 복합 시나리오 | 반복 실행 비용이 큼 |

DAST의 장점은 언어와 프레임워크에 상관없이 HTTP만 통하면 쓸 수 있다는 점과, 실제 배포 구성을 점검한다는 점입니다. 단점은 실행 환경이 필요해 개발 후반에야 쓸 수 있고, 문제의 소스 위치를 알려 주지 못하며, 크롤러가 닿지 못한 영역은 점검하지 못한다는 점입니다.

## ZAP의 구성: 프록시를 중심에 둔 도구상자

ZAP은 오픈소스 보안 테스트 도구로, 2010년대 초 OWASP 프로젝트로 시작해 현재는 Checkmarx가 후원하는 프로젝트로 계속 오픈소스로 개발되고 있다고 공식 사이트에 안내되어 있습니다. 핵심은 앞서 기반 기술에서 본 가로채기 프록시이며, 그 위에 여러 기능이 얹혀 있습니다.

### 주요 구성 요소

- **프록시(History)**: 브라우저 또는 도구가 지나가는 모든 요청·응답을 기록합니다. 보안 테스터는 이 기록을 보며 어떤 요청이 오가는지 파악합니다.
- **스파이더와 AJAX 스파이더**: 링크를 따라가며 주소 목록(Sites 트리)을 만듭니다.
- **패시브 스캐너**: 프록시를 지나가는 응답을 분석해 문제를 찾되 서버에 추가 요청을 보내지 않습니다.
- **액티브 스캐너**: 찾은 입력 지점마다 공격용 값을 직접 넣은 요청을 보내 취약 여부를 확인합니다.
- **알림(Alerts)**: 위의 모든 결과가 모이는 곳이며 위험도와 확신도, 증거(요청·응답), 해결 방향이 붙습니다.
- **Automation Framework**: YAML 계획 파일로 컨텍스트·스파이더·스캔·리포트 과정을 자동화하는 기능으로 CI에 적합합니다.

### 패시브 스캔: 보내지 않고 관찰한다

패시브 스캔은 ZAP이 이미 받은 응답만 분석합니다. 새로운 공격 요청을 만들지 않으므로 운영 환경에 가까운 곳에서도 비교적 안전하게 쓸 수 있습니다. 앞서 기반 기술에서 본 응답 헤더와 쿠키 속성을 예로 들면, 응답에 `Content-Security-Policy`가 없다, 쿠키에 `HttpOnly`가 없다, 오류 페이지에 서버 내부 정보가 노출됐다 같은 항목을 찾습니다. 단점은 입력값을 실제로 바꿔 보내지 않기 때문에 SQL 인젝션처럼 "공격을 시도해야만 드러나는" 문제는 찾지 못한다는 점입니다.

### 액티브 스캔: 공격 요청을 직접 보낸다

액티브 스캔은 파라미터마다 SQL 인젝션 문자열, 스크립트 삽입 문자열, 경로 조작 문자열 등을 넣어 응답 변화를 관찰합니다. 이 과정에서 데이터가 생성·수정·삭제될 수 있고, 서버 부하와 로그 오염이 발생하며, 잘못 설정하면 운영 서비스를 장애에 빠뜨릴 수 있습니다. 그래서 액티브 스캔은 **자신이 소유하거나 서면으로 허가받은 시스템의 테스트 환경에서만** 실행해야 합니다. 허가 없는 대상에 스캔을 돌리는 것은 법적 문제가 될 수 있습니다.

| 구분 | 패시브 스캔 | 액티브 스캔 |
|---|---|---|
| 서버로 추가 요청 | 보내지 않음(관찰만) | 공격 페이로드 포함 다수 전송 |
| 위험 | 매우 낮음 | 데이터 오염·부하 가능 |
| 탐지 범위 | 헤더·쿠키·정보 노출 위주 | 인젝션·XSS 등 입력 처리 결함 포함 |
| 권장 실행 위치 | 개발·스테이징 CI | 격리된 테스트 환경, 별도 일정 |
| 소요 시간 | 짧음 | 길어질 수 있음 |

## 수동 탐색으로 시작하기

자동화에 앞서 한 번은 ZAP 데스크톱 화면에서 직접 확인해 보는 것이 이해에 도움이 됩니다. 테스트 대상은 반드시 본인이 허가받은 환경이어야 하며, 연습용으로는 일부러 취약하게 만든 학습용 애플리케이션(예: OWASP Juice Shop)을 로컬 도커로 띄워 쓰는 방법이 있습니다.

```bash
# 학습용 취약 앱을 내 PC에서만 접근 가능하게 실행 (127.0.0.1에만 바인딩)
docker run --rm -p 127.0.0.1:3000:3000 bkimminich/juice-shop
```

그다음 ZAP 데스크톱을 실행하고 "Manual Explore"에서 대상 주소(`http://localhost:3000`)를 입력해 ZAP이 설정된 브라우저를 엽니다. 브라우저에서 앱을 직접 클릭하며 사용하면 프록시 기록에 요청이 쌓이고 패시브 스캐너가 알림을 만듭니다. 이 단계에서 "내가 사용하는 화면에서 오가는 요청이 이렇게 생겼구나"를 눈으로 확인하는 것이 중요합니다. 이후 자동 스캔이 무엇을 보는지 이해하는 바탕이 되기 때문입니다.

## baseline 스캔 실행하기

ZAP 공식 도커 이미지에는 CI용 스크립트가 들어 있습니다. 그중 `zap-baseline.py`는 스파이더로 주소를 짧게 수집한 뒤 패시브 스캔만 수행하고 리포트를 만듭니다. 공식 문서는 이 스캔이 공격 요청을 보내지 않아 비교적 빨리 끝나고 CI에 적합하다고 안내합니다.

```bash
# 결과 파일을 저장할 작업 디렉터리 준비
mkdir -p zap-work && chmod 777 zap-work

docker run --rm -v "$(pwd)/zap-work:/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py \
    -t https://staging.example.internal \
    -r baseline-report.html \
    -J baseline-report.json \
    -m 2
echo "exit code: $?"
```

주요 옵션의 뜻은 다음과 같습니다. `-t`는 대상 주소, `-r`과 `-J`는 HTML·JSON 리포트 파일 이름, `-m`은 스파이더가 탐색할 최대 분(minute)입니다. `-v`로 연결한 `/zap/wrk` 디렉터리에 리포트가 저장됩니다. 예시의 주소 `staging.example.internal`은 가상의 값이므로 본인의 허가된 스테이징 주소로 바꿔야 합니다. 이미지 태그는 `stable` 외에 특정 버전으로 고정하면 스캔 규칙이 갑자기 바뀌어 CI 결과가 흔들리는 일을 줄일 수 있습니다.

### 출력 예시

```text
WARN-NEW: Content Security Policy (CSP) Header Not Set [10038] x 12
WARN-NEW: Cookie without SameSite Attribute [10054] x 3
WARN-NEW: X-Content-Type-Options Header Missing [10021] x 8
PASS: Cookie No HttpOnly Flag [10010]
FAIL: 0   WARN: 3   IGNORE: 0   PASS: 52
```

위 출력은 도구 출력 형식을 설명하기 위한 예시로, 규칙 번호와 이름은 공식 문서의 규칙 목록 형식을 따랐지만 실제 값은 버전과 대상에 따라 다릅니다. 각 줄은 `상태: 알림 이름 [규칙 번호] x 발생 횟수` 형태이고, 마지막 줄이 상태별 개수 요약입니다.

## 스파이더와 범위 설정

스파이더가 닿지 못한 영역은 점검되지 않습니다. 그래서 "무엇이 스캔됐는가"를 확인하는 것이 결과만큼 중요합니다. 리포트의 사이트 목록이 기대한 주소 수에 비해 너무 적다면, 로그인 뒤에만 보이는 화면이거나 자바스크립트로 만든 링크라서 스파이더가 놓친 것입니다.

### 범위를 좁히는 이유

범위를 정하지 않은 스캔은 로그아웃 링크나 외부 사이트 링크까지 따라갈 수 있습니다. 앞서 기반 기술에서 본 컨텍스트로 대상 주소 패턴을 지정하고, 제외 패턴으로 로그아웃·삭제·결제 같은 위험한 주소를 뺍니다. 특히 액티브 스캔은 "삭제" 버튼이 있는 주소를 실제로 호출할 수 있으므로 제외 설정이 더욱 중요합니다.

### Automation Framework로 계획 작성하기

여러 옵션을 명령행에 늘어놓는 대신 YAML 계획 파일로 관리하면 변경 이력이 남고 리뷰가 가능합니다. 아래는 Automation Framework 계획의 예시 구조이며, 정확한 항목과 작업(job) 이름은 사용하는 ZAP 버전의 공식 문서를 확인해야 합니다.

```yaml
env:
  contexts:
    - name: staging-app
      urls:
        - https://staging.example.internal
      includePaths:
        - https://staging.example.internal/.*
      excludePaths:
        - https://staging.example.internal/logout.*
        - https://staging.example.internal/admin/delete.*
  parameters:
    failOnError: true
    progressToStdout: true
jobs:
  - type: spider
    parameters:
      context: staging-app
      maxDuration: 3
  - type: passiveScan-wait
    parameters:
      maxDuration: 5
  - type: report
    parameters:
      template: traditional-html
      reportDir: /zap/wrk
      reportFile: automation-report
```

```bash
docker run --rm -v "$(pwd)/zap-work:/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap.sh -cmd -autorun /zap/wrk/plan.yaml
```

이 계획은 컨텍스트로 범위를 정하고, 스파이더를 최대 3분 돌리고, 패시브 스캔이 끝나기를 기다린 뒤, HTML 리포트를 만듭니다. 액티브 스캔을 포함하려면 `activeScan` 작업을 추가하되, 앞서 설명한 이유로 별도 일정과 격리 환경에서만 사용하세요.

## API 스캔: OpenAPI 정의를 입력으로

백엔드 API는 화면이 없어 스파이더가 쓸 링크가 없습니다. 이 경우 OpenAPI 정의 문서가 "모든 경로와 파라미터의 목록" 역할을 합니다. `zap-api-scan.py`는 OpenAPI·SOAP·GraphQL 정의를 읽어 경로를 만들고 스캔합니다. 이미 게시한 글 「OpenAPI 계약 린팅」에서 다룬 정의 문서가 여기서 보안 스캔의 입력으로도 재활용됩니다.

```bash
docker run --rm -v "$(pwd)/zap-work:/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py \
    -t https://staging.example.internal/openapi.json \
    -f openapi \
    -r api-report.html
```

`-f openapi`는 정의 형식을 알려 주는 옵션입니다. 이 스크립트는 기본적으로 액티브 스캔을 포함하므로 실행 대상이 테스트 환경인지 먼저 확인해야 하며, 패시브 위주로 쓰고 싶다면 문서의 옵션을 확인하세요. 정의 문서에 인증 방식이 필요한 API라면 요청 헤더에 테스트용 토큰을 넣는 설정이 추가로 필요합니다.

## 결과 읽기와 오탐 규칙 관리

스캔 결과에서 가장 시간이 드는 일은 알림 분류입니다. 알림 수십 개를 매번 눈으로 보면 팀이 곧 리포트를 열지 않게 됩니다. 앞서 기반 기술에서 본 위험도와 확신도를 기준으로 분류 규칙을 파일로 관리합니다.

### 규칙 설정 파일

`zap-baseline.py`는 `-c` 옵션으로 규칙 설정 파일을 받습니다. 파일의 각 줄은 `규칙번호  동작  (설명)` 형태이며 동작은 `IGNORE`(무시), `INFO`(정보로만 표시), `WARN`(경고, 기본값), `FAIL`(실패 처리) 중 하나입니다.

```text
# zap-rules.tsv (탭으로 구분)
10038	FAIL	(Content Security Policy Header Not Set)
10054	WARN	(Cookie without SameSite Attribute)
10021	FAIL	(X-Content-Type-Options Header Missing)
10096	IGNORE	(Timestamp Disclosure - 로그 시각은 공개 정보로 합의, 2026-11 검토)
```

```bash
docker run --rm -v "$(pwd)/zap-work:/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t https://staging.example.internal \
    -c zap-rules.tsv -r baseline-report.html
```

규칙 파일은 소스 저장소에 두고 변경을 코드 리뷰로 다룹니다. 특히 `IGNORE`는 "이 위험을 누가, 왜, 언제까지 받아들였는가"를 설명에 남겨야 합니다. 사유 없이 쌓인 `IGNORE`는 시간이 지나면 진짜 위험을 가리는 구멍이 됩니다.

### 알림을 읽는 순서

1. 위험도가 High·Medium이면서 확신도가 높은 알림부터 봅니다.
2. 알림 상세의 요청·응답 증거를 열어 실제로 재현되는지 확인합니다. 브라우저 개발자 도구나 `curl`로 같은 요청을 보내 확인할 수 있습니다.
3. 재현되면 담당 팀에 이슈로 등록하고, 문제가 아니라면 규칙 파일에 사유와 함께 `IGNORE`로 남깁니다.
4. 같은 알림이 여러 주소에서 반복되면 공통 원인(예: 프록시 설정에서 헤더가 빠짐)일 가능성이 높으므로 한 곳에서 고칩니다.

```bash
# 알림 재현 확인 예: 응답 헤더에 CSP와 nosniff가 실제로 있는지 직접 확인
curl -sI https://staging.example.internal/ | grep -iE 'content-security-policy|x-content-type-options|set-cookie'
```

## 인증이 필요한 영역

대부분의 중요한 기능은 로그인 뒤에 있습니다. 로그인하지 않은 상태의 스캔은 공개 화면만 점검하므로 실제 위험의 일부만 봅니다. 인증을 다루는 방법은 크게 세 가지입니다.

| 방법 | 설명 | 장점 | 주의점 |
|---|---|---|---|
| 토큰·헤더 주입 | 테스트 계정으로 발급한 토큰을 요청 헤더에 고정 | 설정이 단순, API에 적합 | 토큰 만료 시 스캔이 중간에 실패 |
| 폼 기반 로그인 | 컨텍스트에 로그인 요청과 로그인 여부 판단 규칙 설정 | 일반 웹 앱에 적합 | 로그인 상태 판단 지표를 잘못 잡으면 세션이 풀린 채 스캔 |
| 브라우저 기반 로그인 | 브라우저 스크립트로 복잡한 로그인(SSO 등) 수행 | 복잡한 흐름 대응 | 설정과 유지보수 비용이 큼 |

반드시 지킬 원칙은 **운영 계정이 아닌 전용 테스트 계정**을 쓰는 것입니다. 스캔 계정은 최소 권한으로 만들고, 가능하면 서로 다른 권한의 계정 둘을 준비해 "일반 사용자가 관리자 주소를 호출할 수 있는지" 같은 권한 검증은 별도 테스트 케이스나 수동 점검으로 확인합니다. 자동 DAST가 권한 우회를 잘 찾지 못한다는 한계를 이 방식으로 일부 보완합니다.

## CI 게이트로 연결하기

스캔을 CI 단계로 넣을 때는 종료 코드의 의미를 알아야 합니다. ZAP 공식 문서에 따르면 baseline 스크립트는 FAIL 알림이 하나라도 있으면 1, WARN만 있으면 2, 스캔 오류 등 그 밖의 경우 3, 모두 통과하면 0을 돌려줍니다. 팀이 정한 정책에 따라 이 값을 해석합니다.

```yaml
# .github/workflows/zap-baseline.yml (구조 예시)
name: zap-baseline
on:
  pull_request:
  schedule:
    - cron: "0 18 * * 1-5"
jobs:
  baseline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy staging for test
        run: ./scripts/deploy-staging.sh
      - name: ZAP baseline scan
        run: |
          mkdir -p zap-work && chmod 777 zap-work
          set +e
          docker run --rm -v "$(pwd)/zap-work:/zap/wrk/:rw" \
            ghcr.io/zaproxy/zaproxy:stable \
            zap-baseline.py -t "$STAGING_URL" -c zap-rules.tsv -r report.html
          code=$?
          # 0 통과, 2 경고만 있으면 통과로 처리하고 1(FAIL)과 3(오류)은 실패
          if [ "$code" -eq 1 ] || [ "$code" -eq 3 ]; then exit "$code"; fi
        env:
          STAGING_URL: https://staging.example.internal
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: zap-report
          path: zap-work/report.html
```

이 설정은 풀 리퀘스트마다 패시브 baseline을 돌리고, 평일 저녁에도 정기 실행하며, 리포트는 실패해도 아티팩트로 남깁니다. `set +e`로 종료 코드를 직접 받아 팀 정책(경고는 허용, FAIL과 오류만 차단)에 맞게 변환했습니다. 이 YAML은 구조를 설명하는 예시이고, 배포 스크립트와 주소는 가상의 값입니다.

### 종료 코드를 느슨하게 쓰는 옵션과 그 위험

공식 문서의 옵션 목록에는 경고가 있어도 실패 코드를 돌려주지 않게 하는 `-I`가 있습니다. 도입 초기에 파이프라인이 매번 빨갛게 변하는 것을 피하려고 쓸 수 있지만, 이 옵션을 켠 채로 잊으면 경고가 영영 쌓이기만 하고 아무도 보지 않는 상태가 됩니다. 그래서 `-I`를 쓴다면 만료일을 정해 두고, 그 기간 안에 알림 분류를 끝내 `FAIL` 규칙으로 전환하는 일정을 이슈로 남기는 편이 좋습니다. 반대로 종료 코드를 직접 해석하는 위 스크립트 방식은 "경고는 허용하되 리포트는 반드시 보관한다"는 정책을 코드로 드러내므로, 팀원이 정책을 읽고 바꾸기 쉽다는 장점이 있습니다.

### 도입 순서의 현실적 권장안

처음부터 모든 규칙을 `FAIL`로 두면 기존 결함이 한꺼번에 터져 팀이 도입을 거부합니다. 먼저 모든 규칙을 `WARN`으로 두고 한두 주 결과를 모아 현황을 파악하고, 새로 추가된 코드에서 생기는 알림부터 `FAIL`로 올립니다. 기존 알림은 이슈 목록으로 옮겨 점진적으로 줄이는 방식입니다. 이렇게 "새 위험을 막는 게이트"와 "기존 위험을 줄이는 백로그"를 분리하면 도입 저항이 줄어듭니다.

## 안전한 운영 기준

DAST는 공격 도구의 성격이 있으므로 운영 기준을 문서로 정해 두어야 합니다.

- **허가와 범위**: 스캔 대상 주소와 시간대를 사전에 합의하고, 타사 서비스·공유 인프라가 대상에 섞이지 않도록 컨텍스트로 제한합니다.
- **격리 환경**: 액티브 스캔은 운영 데이터가 없는 별도 환경에서 실행하고, 실행 후 데이터를 초기화합니다.
- **부하 관리**: 스캔 중 서버 지표를 같이 보고, 스레드 수와 요청 간격을 조절해 정상 사용자 시험을 방해하지 않게 합니다.
- **알림 연락 체계**: 스캔 때문에 경보가 울리는 것을 보안 관제팀이 오해하지 않도록 실행 일정과 출발지 주소를 공유합니다.
- **리포트 취급**: 리포트에는 요청·응답 원문과 토큰이 들어갈 수 있으므로 접근 권한을 제한하고 보관 기간을 정합니다.

## 업무 예시: 신규 API 릴리스 전 보안 위생 점검

가상의 사내 주문 서비스에서 새 API 버전을 릴리스한다고 가정하겠습니다. 이 시나리오는 설명을 위한 가상 예시이며 제가 실제 운영에서 수행한 사례가 아닙니다. 개발팀은 풀 리퀘스트마다 스테이징에 앱을 배포하고 baseline 스캔을 돌려, `Content-Security-Policy` 누락과 쿠키 속성 문제를 `FAIL`로 막습니다. 첫 도입 주에는 12건의 `WARN`이 나왔고, 그중 10건은 리버스 프록시 설정 한 곳에서 보안 헤더를 추가해 한 번에 해소했으며, 나머지 2건은 사유를 적어 `IGNORE`로 남겼다는 식의 흐름이 됩니다. 릴리스 전 주간에는 격리된 테스트 환경에서 OpenAPI 정의를 입력으로 한 API 스캔을 별도로 돌리고, 결과의 High·Medium 알림만 사람이 재현해 담당자에게 배정합니다. 권한 우회처럼 자동 도구가 못 찾는 영역은 테스트 설계 단계에서 "일반 사용자 토큰으로 다른 사용자 주문 조회 시 403이 나오는가" 같은 API 테스트 케이스로 따로 작성합니다.

## 한계와 적용 기준 Q&A

### Q. ZAP이 OWASP Top 10을 전부 찾아 주나요?

A. 그렇지 않습니다. 보안 설정 오류, 일부 인젝션과 XSS, 취약한 구성 요소 일부는 탐지할 수 있지만, 접근 통제 실패(남의 데이터 조회)나 설계 결함 같은 범주는 업무 문맥을 이해해야 하므로 자동 스캔의 탐지가 약합니다. Top 10 전체를 "ZAP 통과"로 증명할 수는 없으며, 설계 검토·코드 리뷰·수동 침투 테스트와 함께 구성해야 합니다.

### Q. 오탐이 너무 많으면 어떻게 하나요?

A. 확신도와 위험도로 먼저 걸러 읽고, 재현으로 실제 여부를 확인한 뒤, 문제가 아닌 것은 규칙 파일에 사유를 적어 `IGNORE`로 처리합니다. 같은 오탐이 반복되면 규칙 자체를 `INFO`로 낮추는 것도 방법입니다. 다만 오탐을 줄이려고 규칙을 일괄 비활성화하면 미탐 위험이 커지므로 소수의 규칙만 조정하고 변경 이력을 남기세요.

### Q. 운영 환경에도 스캔해도 되나요?

A. 패시브 baseline도 스파이더가 실제 요청을 보내므로 운영 환경에서는 사전 합의와 범위 제한 없이 실행하지 않습니다. 액티브 스캔은 운영에서 하지 않는 것이 기본입니다. 데이터 오염과 장애 가능성 때문에, 운영과 같은 구성을 가진 별도 환경에서 점검하는 방식이 안전합니다.

### Q. SPA(Single Page Application)처럼 자바스크립트가 많은 앱은 어떻게 하나요?

A. 일반 스파이더는 자바스크립트가 생성한 링크를 보지 못하므로 AJAX 스파이더를 함께 쓰거나, 브라우저 자동화 테스트(예: 이미 게시한 글에서 다룬 Playwright 기반 E2E)의 트래픽을 ZAP 프록시로 통과시켜 실제 사용 흐름을 기록하게 하는 방법이 있습니다. 이 방식은 화면 테스트와 보안 점검이 같은 시나리오를 공유해 효율적이지만, 프록시를 거치는 설정을 CI에 추가해야 합니다.

### Q. 스캔 시간이 너무 길어지면요?

A. 스파이더 최대 시간(`-m`)과 범위를 줄이고, 풀 리퀘스트에는 패시브 baseline만, 액티브 스캔은 야간·주간 정기 일정으로 분리합니다. 변경된 경로만 대상으로 삼는 방식은 도구가 기본 제공하지 않으므로 컨텍스트 범위를 팀이 직접 나눠 관리해야 합니다.

### Q. 스캔 결과를 어떻게 추적해야 하나요?

A. 리포트를 CI 아티팩트로 보관하고, 확인된 결함은 이슈 트래커에 위험도·재현 방법·담당자·기한과 함께 등록합니다. 규칙 파일의 `IGNORE` 항목은 정기적으로 재검토해 사유가 여전히 유효한지 확인합니다.

## 마무리

DAST는 실행 중인 애플리케이션을 바깥에서 점검해 배포 설정과 런타임 상호작용에서 생기는 문제를 찾아 줍니다. ZAP은 프록시를 중심으로 스파이더, 패시브·액티브 스캐너, Automation Framework를 갖춘 오픈소스 도구라서 CI에 연결해 "기본 보안 위생을 반복 확인하는 안전망"으로 쓰기 좋습니다. 핵심은 세 가지입니다. 첫째, 패시브 baseline을 기본으로 하고 액티브 스캔은 허가된 격리 환경과 별도 일정으로 분리합니다. 둘째, 알림은 위험도·확신도·재현으로 분류하고 `IGNORE`에는 사유를 남깁니다. 셋째, 종료 코드를 팀 정책에 맞게 해석해 새 위험을 막는 게이트로 쓰되, 권한과 업무 로직은 사람의 검토와 테스트 케이스로 보완합니다.
