API(Application Programming Interface) 테스트에서 가장 어려운 지점은 “응답이 200이면 통과”라고 말하기엔 실제 사용자가 기대하는 약속이 훨씬 많다는 데 있습니다. 모바일 앱은 `user.name`이라는 필드가 늘 문자열로 온다고 가정하고 화면을 만들었는데, 서버가 어느 날 필드를 `fullName`으로 바꾸면 HTTP 상태 코드는 200이어도 앱은 깨질 수 있습니다. 외부 협력사와 연동하는 API라면 더 늦게 발견될 수도 있습니다. 상대 시스템이 새 버전을 배포하는 시점까지 문제를 알아차리지 못하기 때문입니다.

**OpenAPI**는 이런 API의 약속을 기계가 읽을 수 있는 문서로 표현하는 표준입니다. 경로, HTTP 메서드, 요청 본문, 응답 상태 코드, 필드 타입, 인증 방식, 예시를 YAML 또는 JSON으로 적습니다. 많은 팀이 OpenAPI를 문서 페이지를 만들기 위한 재료로만 생각하지만, QA 관점에서는 변경을 비교하고 자동 검사하는 **계약(contract)** 으로 더 유용하게 쓸 수 있습니다.

이 글은 특정 조직에서 OpenAPI 린트나 계약 테스트를 실제 도입해 얻은 성능 수치가 아닙니다. [OpenAPI Initiative의 공식 명세](https://spec.openapis.org/oas/latest.html), [OpenAPI Learn](https://learn.openapis.org/), [Spectral 문서](https://docs.stoplight.io/docs/spectral/), [Pact 문서](https://docs.pact.io/)를 바탕으로, API 테스트 경험이 있는 독자가 명세 기반 검증을 어떻게 이해하고 시작할지 정리한 학습 글입니다.

## 1. 먼저 알아둘 기반 기술: HTTP와 REST API의 약속

OpenAPI를 이해하려면 먼저 HTTP 요청과 응답이 무엇을 약속하는지 알아야 합니다. 웹이나 앱이 서버에 데이터를 요청할 때 보통 **HTTP 메서드**와 **URL 경로**, **헤더**, **본문(body)** 을 보냅니다. 서버는 상태 코드와 응답 본문을 돌려줍니다. `GET /users/42`는 사용자 조회, `POST /orders`는 주문 생성처럼 메서드와 경로가 행동의 의미를 전달합니다. REST는 이런 HTTP 자원을 중심으로 API를 설계하는 널리 쓰이는 방식입니다. 다만 REST는 하나의 엄격한 제품 규격이 아니라 설계 원칙의 묶음이므로, 실제 계약은 팀이 구체적으로 정해야 합니다.

예를 들어 주문 조회 API가 아래처럼 응답한다고 가정해 보겠습니다.

```json
{
  "id": "order-42",
  "status": "PAID",
  "totalAmount": 32000
}
```

클라이언트는 적어도 세 가지를 가정합니다. `id`가 존재하는지, `status`가 정해진 상태 값 중 하나인지, `totalAmount`가 숫자인지입니다. 이 가정은 소스 코드 여기저기에 숨어 있을 수 있습니다. OpenAPI는 그 가정을 서버와 소비자가 함께 보는 명세 파일로 옮깁니다. 즉 “문서 작성”은 설명을 예쁘게 만드는 일이면서 동시에 암묵적인 가정을 명시적인 계약으로 바꾸는 일입니다.

**스키마(schema)** 는 데이터 구조의 규칙입니다. 위 응답에서 `type: string`, `type: number`, `required` 같은 선언이 스키마에 해당합니다. **상태 코드(status code)** 는 요청 처리 결과의 종류를 나타냅니다. `200 OK`는 정상 조회, `201 Created`는 새 리소스 생성, `400 Bad Request`는 입력 형식 오류, `401 Unauthorized`는 인증 필요, `403 Forbidden`은 권한 부족, `404 Not Found`는 대상 없음처럼 의미가 다릅니다. 상태 코드만 맞고 본문의 스키마가 바뀌어도 계약은 깨질 수 있으며, 반대로 본문이 맞아도 상태 코드 의미가 달라지면 소비자의 오류 처리 로직이 흔들릴 수 있습니다.

## 2. OpenAPI 문서는 무엇을 담는가

OpenAPI 문서는 보통 `openapi`, `info`, `servers`, `paths`, `components` 같은 큰 구조로 구성됩니다. 처음에는 모든 키를 외울 필요가 없습니다. QA나 API 리뷰에서 가장 자주 보는 것은 경로별 요청과 응답, 공통 스키마, 인증 요구사항입니다.

```yaml
openapi: 3.1.0
info:
  title: 주문 API
  version: 1.0.0
paths:
  /orders/{orderId}:
    get:
      summary: 주문 한 건 조회
      parameters:
        - name: orderId
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          description: 주문 조회 성공
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
        '404':
          description: 주문을 찾을 수 없음
components:
  schemas:
    Order:
      type: object
      required: [id, status, totalAmount]
      properties:
        id: { type: string }
        status: { type: string, enum: [PAID, CANCELED] }
        totalAmount: { type: number }
```

이 예시에서 `paths`는 API가 제공하는 URL과 행동을, `parameters`는 URL에 포함되는 입력을, `responses`는 가능한 결과를, `components.schemas`는 재사용할 데이터 구조를 나타냅니다. `$ref`는 같은 문서의 공통 스키마를 참조하는 표기입니다. 주문 생성·목록 조회·결제 취소가 모두 `Order` 구조를 사용한다면 중복해서 쓰는 대신 하나의 정의를 참조할 수 있습니다.

명세에는 성공 응답만 적지 않는 편이 좋습니다. 사용자가 존재하지 않는 주문 번호를 보냈을 때, 권한이 없는 주문을 조회했을 때, 입력 형식이 틀렸을 때 서버가 무엇을 반환하는지도 소비자에게는 중요한 계약입니다. 오류 본문까지 통일하면 앱·웹·외부 파트너가 서로 다른 예외 처리를 만들 가능성이 줄어듭니다. 예를 들어 모든 오류를 `{"code":"ORDER_NOT_FOUND","message":"..."}` 형태로 정한다면, 클라이언트는 상태 코드와 코드 값을 조합해 안정적으로 처리할 수 있습니다.

## 3. 명세 기반 검증은 세 층으로 나눈다

OpenAPI를 활용한 검증은 한 가지 테스트가 아닙니다. 최소한 다음 세 층을 구분하면 도구 선택이 쉬워집니다.

<figure class="article-figure"><img src="{{ '/assets/images/openapi-contract-lint-flow.svg' | relative_url }}" alt="OpenAPI 명세를 정적 린트와 실행 계약 테스트로 연결하는 검증 흐름"><figcaption>이미지 출처: 직접 제작</figcaption></figure>

| 검증 층 | 주로 묻는 질문 | 실패 예시 |
| --- | --- | --- |
| 명세 린트 | 문서가 일관된 규칙을 지키는가 | 모든 경로에 설명이 없고 오류 응답 형식이 제각각 |
| 호환성 검사 | 이전 명세와 비교해 소비자를 깨는 변경이 있는가 | 필수 응답 필드 삭제, enum 값 제거 |
| 실행 계약 검사 | 실제 서버 응답이 현재 명세와 맞는가 | `totalAmount`가 문자열로 반환되거나 404 본문이 다름 |

**린트(lint)** 는 코드의 문법 오류만 찾는 컴파일러와 다르게, 팀이 정한 품질 규칙을 검사하는 과정입니다. 예를 들어 모든 API에 `summary`를 적어야 한다, 성공 응답은 반드시 `description`을 가져야 한다, 경로 이름은 kebab-case로 쓴다, `GET` 요청에는 요청 본문을 쓰지 않는다 같은 규칙을 자동으로 확인할 수 있습니다. Spectral은 OpenAPI와 JSON/YAML 문서를 대상으로 이런 규칙을 실행할 수 있는 린터입니다. [Spectral 공식 문서](https://docs.stoplight.io/docs/spectral/)

**호환성 검사(backward compatibility check)** 는 새 명세가 이전 소비자를 깨는지를 봅니다. 응답에 선택 필드를 추가하는 변경은 대부분 기존 소비자에게 안전할 가능성이 높습니다. 반면 기존에 필수였던 필드를 지우거나, 문자열을 숫자로 바꾸거나, 허용하던 `PAID` 상태 값을 없애는 변경은 위험합니다. 물론 “항상 안전한 변경”은 없습니다. 소비자가 알 수 없는 필드를 실패로 처리하거나, 숫자의 단위가 달라지는 의미 변경은 스키마만으로 발견하지 못합니다. 그래도 기계적으로 확인 가능한 파괴적 변경을 PR 단계에서 막는 것만으로도 큰 도움이 됩니다.

**실행 계약 검사** 는 테스트 환경에서 실제 API를 호출해 명세와 대조합니다. 요청 필수값 누락 시 400이 반환되는지, 200 응답에 약속한 필드가 있는지, `Content-Type`이 맞는지, enum 밖의 값이 나오지 않는지 확인합니다. 이것은 API 테스트 도구로 이미 해 온 요청·응답 검증을 명세와 연결하는 방식이라고 보면 됩니다.

## 4. 린트 규칙은 스타일보다 사고 예방에 쓴다

처음 린트를 도입할 때는 들여쓰기나 따옴표보다 **오해를 줄이는 규칙**부터 고르는 편이 좋습니다. 아래는 팀이 검토할 만한 예입니다.

| 규칙 | 왜 필요한가 | 예시 |
| --- | --- | --- |
| 모든 작업에 `operationId` 지정 | 자동화·문서·테스트에서 작업을 식별 | `getOrder`, `createOrder` |
| 모든 응답에 설명 추가 | 200/400/404의 업무 의미를 남김 | `주문을 찾을 수 없음` |
| 오류 스키마 통일 | 클라이언트 오류 처리의 분기를 줄임 | `code`, `message`, `traceId` |
| 예시 제공 | 실제 값의 형식·단위를 빠르게 이해 | 금액은 원 단위 정수인지 명확화 |
| 보안 요구사항 표시 | 인증 없는 엔드포인트와 혼동 방지 | Bearer token 또는 OAuth scope |

예를 들어 날짜 필드를 `string`으로만 선언하면 소비자는 `2026-09-18`, `2026/09/18`, `2026-09-18T10:00:00Z` 중 무엇이 오는지 모릅니다. `format: date` 또는 `format: date-time`과 예시를 함께 넣으면 의도가 드러납니다. 금액도 `number`만으로는 소수점 허용 여부와 통화 단위를 알기 어렵습니다. `integer`, `minimum: 0`, 설명문에 “KRW 원 단위”를 적는 식으로 약속을 좁혀야 합니다.

다만 린트가 API 품질 전체를 보장하지는 않습니다. “설명문이 있다”는 규칙을 통과해도 설명이 틀릴 수 있고, 데이터베이스 트랜잭션이 올바른지나 권한 검사가 충분한지는 다른 테스트가 확인해야 합니다. 린트의 역할은 리뷰어가 반복적으로 잡는 형식·일관성 문제를 자동화해, 사람이 업무 의미와 위험한 변경에 더 집중하게 만드는 데 있습니다.

## 5. API 변경을 안전/주의/파괴로 분류하기

변경 리뷰에서 가장 먼저 할 질문은 “이 변경을 아직 이전 버전을 쓰는 소비자가 받아들일 수 있는가?”입니다. 이를 아래처럼 단순 분류로 시작할 수 있습니다.

| 변경 | 일반적인 판단 | 이유와 주의점 |
| --- | --- | --- |
| 선택 응답 필드 추가 | 대체로 안전 | 소비자가 알 수 없는 필드를 무시한다는 전제 필요 |
| 새 경로 추가 | 대체로 안전 | 기존 호출에 영향을 주지 않아야 함 |
| 필수 요청 필드 추가 | 파괴적 | 기존 클라이언트가 값을 보내지 않음 |
| 응답 필수 필드 삭제 | 파괴적 | 화면·후속 로직이 필드를 기대할 수 있음 |
| 필드 타입 변경 | 파괴적 | 파싱과 비교 로직이 달라짐 |
| enum 값 추가 | 주의 | 소비자가 모든 값을 열거해 처리할 수 있음 |
| 오류 코드 의미 변경 | 파괴적에 가까움 | 재시도·알림·사용자 안내가 달라질 수 있음 |

`enum` 값 추가가 왜 무조건 안전하지 않은지 예를 들어 보겠습니다. 주문 상태가 `[PAID, CANCELED]`였을 때 앱은 두 상태만 처리하도록 화면을 만들었을 수 있습니다. 서버가 `REFUNDED`를 추가하면 서버 입장에서는 표현력이 늘어난 좋은 변경이지만, 앱은 기본 분기에서 “알 수 없는 상태” 오류를 낼 수 있습니다. 따라서 명세 비교 도구의 결과를 절대적인 판정으로 쓰기보다, 소비자의 구현 방식과 릴리스 전략을 함께 보아야 합니다.

파괴적 변경이 꼭 나쁜 것은 아닙니다. 잘못 설계된 필드나 보안상 위험한 동작을 영원히 유지할 수는 없습니다. 이때는 기존 동작을 조용히 바꾸기보다 새 버전 경로(`/v2/...`) 또는 명시적 버전 협상을 제공하고, 사용 기한·마이그레이션 방법·변경 목록을 안내하는 편이 낫습니다. 중요한 것은 “변경이 있다”는 사실을 늦게 발견하지 않도록 명세 차이를 PR에서 보이게 하는 것입니다.

## 6. 계약 테스트와 OpenAPI 검증은 경쟁하지 않는다

**계약 테스트(contract testing)** 는 API를 제공하는 쪽(provider)과 사용하는 쪽(consumer)이 기대하는 상호작용을 검증하는 방식입니다. 앞서 쓴 Pact 글처럼 소비자는 “이 요청을 보내면 이 형태의 응답이 필요하다”는 계약을 만들고, 제공자는 자신의 구현이 그 계약을 만족하는지 확인할 수 있습니다. OpenAPI는 제공자가 공개하는 전체 API의 공용 규격에 가깝고, 소비자 계약은 특정 소비자가 실제로 의존하는 사용 사례에 가깝습니다.

예를 들어 OpenAPI에는 주문 조회 응답의 모든 필드가 선언되어 있을 수 있습니다. 하지만 배송 앱은 `id`, `status`, `deliveryAddress`만 쓸 수 있습니다. 소비자 계약 테스트는 배송 앱이 실제로 쓰는 필드와 요청을 보호하는 데 적합합니다. 반면 신규 파트너에게 API 전체를 설명하고, 인증 방식·오류 형식·모든 경로를 일관되게 관리하려면 OpenAPI가 적합합니다. 둘 중 하나를 버리는 대신, 공용 명세와 핵심 소비자 계약을 함께 두면 범위가 다르다는 점을 활용할 수 있습니다.

QA 관점에서는 다음처럼 역할을 나누면 실용적입니다. OpenAPI 린트는 PR마다 빠르게 실행해 문서 품질을 확인합니다. 명세 비교는 릴리스 전 파괴적 변경을 알립니다. 서버 계약 검사는 테스트 환경에서 명세와 구현의 차이를 잡습니다. 소비자 계약 테스트는 특히 중요한 앱·외부 연동의 실제 사용 가정을 보호합니다. E2E 테스트는 로그인부터 주문 완료까지 여러 시스템을 통과하는 흐름을 확인합니다. 어느 하나가 다른 하나를 완전히 대체하지 않습니다.

## 7. CI에서 가장 작은 자동화부터 시작하기

처음부터 모든 API를 완벽히 명세화하고 수백 개의 규칙을 적용하려 하면 팀이 피로해질 수 있습니다. 아래처럼 작게 시작하는 순서가 현실적입니다.

1. 가장 많이 쓰이는 API 한 개의 성공·대표 오류 응답을 OpenAPI로 적는다.
2. PR에서 명세 파일의 문법과 공통 린트 규칙을 실행한다.
3. 이전 명세와 비교해 필수 필드 삭제·타입 변경을 경고한다.
4. 테스트 환경에서 핵심 요청 하나를 보내 응답 스키마를 검증한다.
5. 실제 소비자가 많은 API부터 계약 테스트 범위를 넓힌다.

아래 명령은 Spectral CLI를 사용하는 예시입니다. 실행 환경과 규칙 파일 구성은 조직마다 다를 수 있으므로, 이 명령 자체를 그대로 운영 환경에 적용했다는 뜻은 아닙니다.

```bash
npx @stoplight/spectral-cli lint openapi.yaml --ruleset .spectral.yaml
```

린트 결과가 실패했다고 바로 배포를 막을지, 처음에는 경고로 둘지도 팀 상황에 따라 다릅니다. 보안 스키마 누락, 공개 API의 파괴적 변경, 인증 없는 민감 경로 같은 규칙은 실패로 다루는 근거가 큽니다. 반면 설명문의 어조나 태그 정렬은 경고부터 시작해도 됩니다. 기준을 너무 빠르게 강제하면 명세를 우회하는 행동이 생길 수 있으므로, 왜 필요한 규칙인지와 고치는 방법을 함께 제공하는 편이 좋습니다.

## 8. 테스트 케이스를 명세에서 꺼내는 방법

명세가 있다고 테스트 케이스가 자동으로 충분해지는 것은 아닙니다. 그러나 명세는 무엇을 빠뜨렸는지 찾는 체크리스트가 됩니다. 주문 조회 API라면 다음을 생각할 수 있습니다.

| 시나리오 | 명세에서 확인할 항목 | 실제 검증 질문 |
| --- | --- | --- |
| 정상 조회 | 200 스키마, 필수 필드 | 약속한 타입과 값 범위가 반환되는가 |
| 없는 주문 | 404 응답 정의 | 오류 코드와 메시지가 일관적인가 |
| 잘못된 ID | path parameter 규칙 | 형식 오류를 400으로 구분하는가 |
| 다른 사용자 주문 | security, 403 정의 | 존재 여부를 불필요하게 노출하지 않는가 |
| 서버 장애 | 5xx 또는 공통 오류 규칙 | `traceId`로 운영 조사에 연결되는가 |

여기서 “명세에 없는 경우”는 곧 테스트가 필요 없다는 뜻이 아니라, 계약이 비어 있다는 신호일 수 있습니다. 예를 들어 페이징 목록 API에 `limit` 최대값이 없으면, 클라이언트가 100만 건을 요청했을 때 어떻게 되는지 알 수 없습니다. 명세에 `minimum`, `maximum`, 기본값, 다음 페이지 토큰의 의미를 적고 그 경계를 테스트해야 합니다.

테스트 데이터를 만들 때는 성공 사례만 복사하지 말고, 타입 경계·권한 경계·상태 전이·빈 결과·중복 요청을 넣어야 합니다. OpenAPI의 `example`은 이해를 위한 예시이고, QA 테스트 데이터는 실패 가능성이 높은 조건을 탐색하기 위한 재료입니다. 같은 값으로 충분하지 않으므로 둘의 목적을 구분하는 것이 좋습니다.

## 9. 변경 요청 하나를 끝까지 리뷰해 보기

명세 기반 검증이 실제로 어떤 질문을 줄여 주는지 보기 위해, 주문 API에 `discountAmount` 필드를 추가하는 변경을 가정해 보겠습니다. 개발자는 할인 금액을 보여 주기 위해 응답에 숫자 필드를 하나 더 추가하려고 합니다. 처음에는 “필드 하나 추가인데 문제없다”라고 생각하기 쉽습니다. 그러나 QA, API 제공자, 소비자 입장에서는 확인할 점이 서로 다릅니다.

먼저 업무 의미를 정해야 합니다. `discountAmount`가 주문 전체에 적용된 할인인지, 상품별 할인 합계인지, 쿠폰·포인트·프로모션을 모두 포함하는 값인지가 불명확하면 소비자는 다른 계산을 할 수 있습니다. 통화는 무엇인지, 취소·부분 환불 뒤 값이 바뀌는지, 할인이 없으면 `0`인지 `null`인지도 계약입니다. 단순히 `type: number`만 추가하는 것보다 설명과 예시를 함께 두는 편이 낫습니다.

```yaml
discountAmount:
  type: integer
  minimum: 0
  description: 주문 시점에 적용된 총 할인 금액이며 KRW 원 단위다.
  example: 3000
```

그 다음에는 호환성을 봅니다. 선택 응답 필드이므로 많은 JSON 소비자에게는 안전할 수 있습니다. 그러나 어떤 소비자는 응답 객체의 키 목록을 비교하거나, 엄격한 스키마 검증에서 추가 속성을 거부할 수 있습니다. 외부 파트너 SDK가 자동 생성된 모델을 쓰는 경우도 확인 대상입니다. “일반적으로 안전”이라는 분류는 리뷰를 생략하라는 뜻이 아니라, 어떤 위험을 먼저 확인할지 알려 주는 출발점입니다.

테스트 케이스도 업무 상태에 맞춰 늘어납니다. 할인 없는 주문에서는 `discountAmount: 0`이 오는지, 할인 주문에서는 총액과 할인액의 관계가 맞는지, 취소 뒤 기존 주문 조회에 어떤 값이 남는지, 권한 없는 사용자가 다른 사람의 할인 정보를 볼 수 없는지를 봅니다. 여기서 총액 계산 자체가 다른 결제 서비스의 책임이라면, 주문 API 테스트는 계산식을 재구현하는 대신 받은 값을 정확히 전달하고 상태별 계약을 지키는지에 집중해야 합니다.

마지막으로 릴리스 커뮤니케이션을 봅니다. 새 필드가 즉시 제공되는지, 특정 API 버전부터 제공되는지, 이전 주문에도 계산되어 채워지는지, 캐시된 응답에는 언제 반영되는지를 소비자가 알아야 합니다. 이 정보는 OpenAPI의 설명, 변경 로그, 릴리스 노트 중 적절한 곳에 남길 수 있습니다. 중요한 것은 구현 PR 안에서만 알고 끝내지 않는 것입니다.

이 과정을 한 필드마다 매우 길게 할 필요는 없습니다. 하지만 리뷰 템플릿에 “업무 의미, 타입·단위, null/기본값, 호환성, 권한, 상태별 예시, 소비자 공지”를 두면 자주 반복되는 질문을 놓치지 않을 수 있습니다. 명세는 개발자만 쓰는 산출물이 아니라 기획·QA·운영·파트너가 같은 변경을 다르게 해석하지 않게 하는 공용 언어가 됩니다.

## 10. 운영 환경에서 명세와 구현이 어긋나는 흔한 이유

명세를 만들었는데도 실제 장애가 나는 이유는 대개 명세가 없어서가 아니라 **변경 경로가 여러 개**이기 때문입니다. 서버 코드를 수정한 뒤 명세 파일을 갱신하지 않을 수 있고, 게이트웨이가 응답 헤더를 덧붙이거나 제거할 수 있으며, BFF(Backend For Frontend)가 여러 내부 API 결과를 조합하는 과정에서 필드 이름을 바꿀 수 있습니다. 긴급 패치가 문서와 테스트를 우회하는 경우도 있습니다.

그래서 명세 파일의 소유자를 한 명으로만 정하기보다, 변경 흐름에 명세 검토를 넣는 것이 중요합니다. API 구현을 바꾸는 PR에는 명세 변경 또는 “명세 영향 없음”이라는 근거가 함께 있어야 하고, 명세만 바꾸는 PR도 실제 서버가 따라갈 계획을 가져야 합니다. CI에서 린트를 돌리는 것은 최소 장치이고, 테스트 환경의 실제 응답 검사와 릴리스 전 변경 로그 검토가 그 다음 장치가 됩니다.

특히 API Gateway, CDN, 직렬화 라이브러리, 날짜 시간대 설정은 명세와 구현의 미세한 차이를 만들기 쉽습니다. 예를 들어 서버 내부에서는 `OffsetDateTime`을 사용하지만 게이트웨이 변환 뒤 시간대 정보가 사라질 수 있습니다. 응답 예시와 실제 테스트가 `2026-09-18T09:00:00+09:00`처럼 시간대까지 확인해야 하는 이유입니다. 숫자도 JSON에는 숫자로 보이지만, 자바스크립트의 큰 정수 정밀도 문제나 통화 반올림 방식이 소비자마다 다를 수 있습니다.

운영 로그에서 같은 경로의 4xx가 갑자기 늘어났다면, 애플리케이션 버그만 보지 말고 최근 명세·SDK·클라이언트 배포와 함께 보아야 합니다. 반대로 새 필드를 추가한 뒤 오류가 없다고 해서 소비자가 실제로 새 기능을 이해했다는 뜻은 아닙니다. API 품질은 서버의 성공률뿐 아니라 소비자가 약속을 올바르게 사용할 수 있는지까지 포함합니다.

## 11. 팀의 출발 규칙 예시

처음 도입하는 팀은 거창한 거버넌스보다, 아래 정도의 작고 측정 가능한 규칙으로 시작할 수 있습니다.

1. 외부 또는 다른 팀이 사용하는 API는 OpenAPI 경로·성공 응답·대표 오류를 갖춘다.
2. 새 필수 요청값, 응답 필수 필드 삭제, 타입 변경은 파괴적 변경 후보로 표시한다.
3. 명세 PR은 린트를 통과하고, 핵심 경로는 테스트 환경의 응답 검사를 통과한다.
4. 보안이 필요한 경로는 인증 방식과 필요한 scope를 명세에 적고, 401·403 사례를 테스트한다.
5. 변경의 업무 의미와 소비자 조치가 필요한지 릴리스 노트에 남긴다.

이 규칙은 API를 느리게 만드는 절차가 아니라, 변경을 발견하는 시간을 앞당기기 위한 것입니다. 특히 QA가 명세를 읽을 수 있으면 구현이 끝난 뒤에야 테스트를 시작하는 대신, 설계 단계에서 모호한 오류 처리와 권한 조건을 질문할 수 있습니다. 개발자도 반복된 문의를 줄이고, 운영자는 장애 시 어떤 응답이 정상인지 판단할 근거를 얻습니다.

### 명세 리뷰에서 바로 물어볼 질문

리뷰어가 API 설계를 처음 볼 때는 다음 질문을 그대로 사용해도 좋습니다. “이 경로를 누가 호출하는가?”, “정상 응답 외에 사용자가 실제로 마주칠 오류는 무엇인가?”, “값이 없을 때 `null`, 빈 문자열, 0 중 무엇을 반환하는가?”, “날짜·금액·식별자의 형식과 단위가 설명돼 있는가?”, “다른 팀이 이미 이 필드를 쓰고 있다면 변경 뒤 무엇을 해야 하는가?” 같은 질문입니다. 답이 문서와 예시에 남으면 이후의 테스트 케이스도 자연스럽게 구체화됩니다.

보안 관련 질문도 따로 둡니다. 인증이 필요한 API라면 인증되지 않은 요청과 권한 없는 요청을 구분하는가, 리소스가 존재하지 않는 경우와 권한이 없어 보이지 않는 경우를 어떤 정책으로 처리하는가, 오류 본문에 내부 경로나 SQL 오류처럼 민감한 정보가 새지 않는가를 확인합니다. OpenAPI의 `security` 선언은 “인증이 필요하다”는 사실을 표현하지만, 실제 구현이 각 요청에서 권한을 검사하는지까지 보장하지는 않습니다. 명세·단위 테스트·통합 테스트가 함께 필요한 이유입니다.

성능도 명세와 무관하지 않습니다. 응답 필드를 수십 개 추가하거나 목록 API의 기본 limit를 크게 바꾸면, 스키마상 호환성이 있어도 모바일 네트워크와 서버 비용에 영향을 줄 수 있습니다. 페이지네이션, 정렬 기준, 최대 요청 크기, 타임아웃, 비동기 작업의 202 응답 여부처럼 소비자가 호출 방식을 결정하는 정보는 필요할 때 명세와 운영 가이드에 함께 정리하는 편이 좋습니다. 성능 수치를 임의로 약속하기보다, 어떤 제한과 재시도 정책을 적용하는지부터 분명히 하는 것이 안전합니다.

문서에 모든 세부 사항을 한 번에 넣지 못하더라도 괜찮습니다. 가장 위험한 모호함부터 줄이면 됩니다. 외부 연동 API라면 인증·오류·버전 정책을, 결제나 주문 API라면 상태 전이와 멱등성 키를, 조회 API라면 권한 범위와 페이징을 우선합니다. 명세는 한 번 작성하고 끝나는 파일이 아니라, 실제 소비자 질문과 장애 사례를 반영하며 살아 있는 계약으로 다듬어 가는 것이 목적입니다.

이 과정에서 QA는 문서의 맞춤법만 확인하는 역할에 머물지 않습니다. 모호한 요구를 재현 가능한 입력·기대 응답·권한 조건으로 바꾸고, 소비자 관점에서 깨질 수 있는 변경을 질문하는 역할을 할 수 있습니다. 명세가 충분히 구체적일수록 개발·테스트·운영 사이의 확인 비용이 줄어듭니다.

작은 변경도 같은 기준으로 기록하는 습관이 쌓이면, 나중에 큰 버전 변경을 준비할 때도 팀이 이미 합의한 언어와 테스트 자산을 활용할 수 있습니다.

결국 좋은 API 명세는 개발 속도를 늦추는 문서가 아니라, 변경의 위험을 일찍 보이게 하는 안전장치입니다.

명세와 테스트를 함께 갱신하는 작은 습관은, 시간이 지날수록 API를 사용하는 사람 모두에게 더 큰 예측 가능성을 제공합니다.

## 마무리: API 문서를 테스트 가능한 약속으로 바꾸기

OpenAPI의 가장 큰 가치는 문서 한 장을 만드는 데 있지 않습니다. API를 사용하는 사람이 무엇을 보내고 무엇을 받을지, 변경하면 누가 영향을 받을지를 같은 형식으로 토론하게 만드는 데 있습니다. 명세 린트는 빠진 약속과 불일치를 줄이고, 호환성 검사는 파괴적 변경을 미리 드러내며, 실행 계약 검사는 실제 서버가 약속을 지키는지 확인합니다.

처음에는 핵심 API 하나만 골라 성공·대표 오류·인증 요구사항을 명확히 적어도 충분합니다. 그 명세에 작은 린트 규칙 하나와 응답 스키마 테스트 하나를 연결하면, API 검증은 “200이 왔는가”에서 “소비자가 의존하는 약속을 지켰는가”로 한 단계 넓어집니다.
