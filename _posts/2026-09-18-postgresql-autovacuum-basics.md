PostgreSQL을 운영하거나 개발 환경에서 오래 쓰다 보면 “테이블 용량은 계속 커지는데 삭제한 데이터는 어디로 갔지?”, “UPDATE가 많은 테이블만 점점 느려지는 것 같은데 왜지?”, “autovacuum이 떠 있는데 디스크가 줄지 않는데 고장 난 건가?” 같은 질문을 만나기 쉽습니다. 이 질문의 출발점은 PostgreSQL이 행을 수정할 때 기존 행을 단순히 덮어쓰는 데이터베이스가 아니라는 점입니다.

PostgreSQL은 여러 트랜잭션이 동시에 읽고 쓸 때 서로를 덜 막기 위해 **MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)** 를 사용합니다. 행을 UPDATE하거나 DELETE해도, 다른 트랜잭션이 이전 시점의 데이터를 볼 수 있어야 할 수 있으므로 기존 행 버전이 즉시 사라지지 않습니다. 더 이상 어떤 트랜잭션에도 필요하지 않게 된 이전 버전을 흔히 dead tuple이라고 부릅니다. 이 dead tuple을 정리해 공간을 다시 쓸 수 있게 하고, 쿼리 플래너용 통계를 갱신하는 핵심 백그라운드 기능이 **autovacuum**입니다.

이 글은 특정 데이터베이스에서 autovacuum 파라미터를 조정해 성능을 측정한 사례가 아닙니다. [PostgreSQL 공식 Routine Vacuuming 문서](https://www.postgresql.org/docs/current/routine-vacuuming.html), [VACUUM 명령 문서](https://www.postgresql.org/docs/current/sql-vacuum.html), [autovacuum 설정 문서](https://www.postgresql.org/docs/current/runtime-config-autovacuum.html)를 바탕으로, DBA 업무를 처음 접하는 독자가 기반 개념과 점검 순서를 이해하기 위한 학습 글입니다.

## 1. 먼저 알아둘 기반 기술: 트랜잭션과 MVCC

**트랜잭션(transaction)** 은 여러 SQL 작업을 하나의 논리적 단위로 묶는 방식입니다. 주문을 만들고 재고를 줄이고 결제 상태를 기록하는 작업 중 일부만 반영되면 데이터가 어긋날 수 있으므로, 모두 성공하면 COMMIT하고 문제가 있으면 ROLLBACK하는 경계를 둡니다. 여러 사용자가 동시에 같은 데이터를 볼 때는 “누가 어느 시점의 데이터를 볼 수 있는가”도 중요해집니다.

MVCC는 각 트랜잭션에 일관된 데이터 스냅샷을 제공하는 방식입니다. 사용자 A가 주문 상태를 읽는 동안 사용자 B가 같은 주문을 UPDATE하더라도, A가 갑자기 중간 상태를 보지 않도록 이전 행 버전과 새 행 버전을 함께 관리합니다. PostgreSQL 공식 문서가 설명하듯 일반적인 UPDATE와 DELETE 뒤 기존 행은 곧바로 물리적으로 사라지지 않고, VACUUM이 처리할 때까지 남아 있을 수 있습니다. [PostgreSQL VACUUM 문서](https://www.postgresql.org/docs/current/sql-vacuum.html)

간단한 예를 들어 보겠습니다. `orders` 테이블에 주문 42번의 상태가 `PAYMENT_PENDING`으로 저장돼 있습니다. 결제가 끝나 `PAID`로 UPDATE하면, PostgreSQL은 개념적으로 기존 버전과 새 버전을 구분해 관리합니다. 오래 실행 중인 조회 트랜잭션이 있다면 그 트랜잭션은 아직 이전 버전을 볼 권리가 있을 수 있습니다. 모든 관련 트랜잭션이 끝나 이전 버전이 더 이상 보일 필요가 없어졌을 때, 그 공간은 정리 대상이 됩니다.

이 구조는 읽기와 쓰기의 불필요한 충돌을 줄이는 장점이 있습니다. 반면 UPDATE와 DELETE가 잦은 테이블에서는 이전 버전이 쌓일 수 있습니다. 이를 **테이블 bloat**라고 부르기도 하지만, dead tuple이 있다는 사실만으로 즉시 장애나 성능 문제라고 단정할 수는 없습니다. 문제는 정리 속도가 변경 속도를 따라가지 못하거나, 오래 열린 트랜잭션이 정리를 막거나, 통계가 오래돼 플래너가 나쁜 실행 계획을 고르는 상황입니다.

## 2. VACUUM과 ANALYZE는 서로 다른 일을 한다

이름이 자주 같이 나오지만 VACUUM과 ANALYZE의 목적은 구분해서 이해해야 합니다. **VACUUM**은 더 이상 필요하지 않은 행 버전이 차지하던 공간을 향후 INSERT·UPDATE가 재사용할 수 있도록 처리합니다. 또한 트랜잭션 ID가 너무 오래 누적돼 발생할 수 있는 wraparound 위험을 막는 유지보수와도 연결됩니다. **ANALYZE**는 테이블의 행 수 추정치, 컬럼 값 분포, null 비율 같은 통계를 모아 쿼리 플래너가 조인 순서·인덱스 사용 여부를 선택할 수 있게 합니다.

예를 들어 `WHERE status = 'PAID'` 조건의 주문이 전체의 1%일 때와 90%일 때는 좋은 실행 계획이 다를 수 있습니다. 통계가 오래되면 플래너는 드문 값이라고 생각해 인덱스를 택했는데 실제로는 대부분의 행을 읽는 계획이 될 수 있습니다. 이런 문제는 SQL 문법 오류가 아니라 데이터 분포와 통계의 차이에서 발생하므로, 느린 쿼리만 보고 인덱스를 무조건 추가하기 전에 통계 상태도 함께 확인해야 합니다.

`VACUUM (ANALYZE)`는 정리와 통계 갱신을 함께 요청하는 형태입니다. 하지만 이것이 “성능이 나빠지면 항상 실행할 명령”이라는 뜻은 아닙니다. 어떤 테이블이 왜 바뀌었는지, autovacuum이 실제로 실행되고 있는지, 장기 트랜잭션이나 잠금이 있는지를 모른 채 반복 실행하면 원인을 가릴 수 있습니다. 특히 운영 환경에서 수동 유지보수는 I/O와 리소스를 사용하므로 일정·부하·권한을 고려해야 합니다.

## 3. autovacuum은 어떤 방식으로 일하는가

autovacuum은 하나의 마법 같은 명령이 아니라 launcher와 worker로 구성된 백그라운드 기능입니다. launcher는 데이터베이스들을 살피며 작업이 필요한 테이블을 찾고, worker는 실제 VACUUM 또는 ANALYZE 작업을 수행합니다. PostgreSQL은 기본적으로 autovacuum을 활성화하며, 공식 문서도 일반적인 설치에서는 autovacuum을 사용해 주기적인 정리를 자동화하는 방식을 권장합니다. [Routine Vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html)

autovacuum이 테이블을 언제 처리할지는 단순한 시계 시간이 아니라 변경량과 설정값의 조합으로 판단합니다. 대표적으로 삭제·수정 관련 VACUUM 임계값은 아래 형태로 이해할 수 있습니다.

```text
vacuum 대상 판단량 ≈ autovacuum_vacuum_threshold
                 + autovacuum_vacuum_scale_factor × 테이블 추정 행 수
```

예를 들어 기본 임계값이 50이고 scale factor가 0.2인 상태에서 추정 행 수가 100만이라면, 단순화한 계산상 약 20만 건 이상의 변경이 기준에 영향을 줄 수 있습니다. 큰 테이블과 작은 테이블에 같은 비율을 적용하면 큰 테이블은 너무 늦게, 작은 테이블은 너무 자주 처리될 수 있습니다. 그래서 전체 설정을 무작정 바꾸기보다 UPDATE·DELETE가 집중되는 테이블에 테이블별 설정을 검토하는 이유가 생깁니다.

하지만 이 공식만 보고 숫자를 즉시 낮추면 안 됩니다. 실제 작업 시점은 insert 관련 임계값, analyze 관련 임계값, worker 수, 비용 제한, 데이터베이스 수, 시스템 부하, 긴 트랜잭션 등 여러 요소에 영향을 받습니다. 공식 문서에 나온 각 설정값의 의미와 사용하는 PostgreSQL 버전을 먼저 확인해야 합니다. [autovacuum configuration](https://www.postgresql.org/docs/current/runtime-config-autovacuum.html)

## 4. dead tuple이 많아지는 대표 상황

dead tuple은 UPDATE와 DELETE의 자연스러운 결과입니다. 특히 다음 패턴은 관찰 대상으로 삼기 좋습니다.

| 업무 패턴 | 왜 누적되기 쉬운가 | 먼저 확인할 것 |
| --- | --- | --- |
| 상태 컬럼을 자주 UPDATE | 같은 행의 새 버전이 반복 생성 | 변경량, 인덱스 수, autovacuum 시각 |
| 대량 DELETE | 많은 이전 행 버전이 한꺼번에 생김 | 배치 크기, 트랜잭션 길이, 디스크 여유 |
| 대량 적재 뒤 데이터 정정 | INSERT와 UPDATE가 짧은 시간에 집중 | ANALYZE 필요성, worker 경쟁 |
| 오래 열린 세션 | 이전 스냅샷이 정리 가능 시점을 늦춤 | `xact_start`, idle in transaction 여부 |
| 인덱스가 많은 테이블 | 행 변경이 인덱스 유지 비용도 만듦 | 실제 사용 인덱스, write 부담 |

예를 들어 로그성 테이블에 매일 수백만 건을 넣고, 상태 변경을 위해 대량 UPDATE를 반복한다면 단순 조회 테이블보다 유지보수 요구가 높을 수 있습니다. 반면 INSERT만 하고 거의 수정하지 않으며 파티션을 기간별로 교체하는 테이블은 접근 방식이 다를 수 있습니다. 파티셔닝은 만능 해결책이 아니지만, 오래된 데이터를 `DELETE`로 한 줄씩 지우는 대신 파티션 단위로 분리·제거할 수 있는 업무 패턴에서는 유지보수 전략에 영향을 줍니다.

장기 트랜잭션은 특히 자주 놓치는 원인입니다. 애플리케이션 연결이 트랜잭션을 열어 둔 채 외부 API 응답을 오래 기다리거나, BI 도구가 긴 조회를 유지하면 PostgreSQL은 그 스냅샷에 필요할 수 있는 이전 버전을 쉽게 제거할 수 없습니다. 따라서 autovacuum이 오래 걸린다는 현상을 보면 worker 설정만 만지기 전에 오래 실행 중인 트랜잭션과 `idle in transaction` 세션을 조사해야 합니다.

## 5. 먼저 관찰하고, 그다음에 조정한다

autovacuum 문제를 “껐다가 수동 VACUUM을 돌리자”로 해결하려 하면 유지보수 책임이 사람에게 넘어가고, transaction ID wraparound 같은 더 큰 위험을 만들 수 있습니다. 먼저 현재 상태를 관찰하는 것이 좋습니다. PostgreSQL 통계 뷰는 테이블별 dead tuple 추정치와 autovacuum·autoanalyze 시각을 확인하는 데 도움을 줍니다.

```sql
SELECT
  relname,
  n_live_tup,
  n_dead_tup,
  last_autovacuum,
  last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

이 결과는 정확한 물리 행 개수를 보장하는 계측기가 아니라 통계 추정치라는 점을 기억해야 합니다. 따라서 `n_dead_tup` 하나만으로 즉시 조치하지 말고, 테이블 증가 추세, 쿼리 지연, autovacuum 로그, 디스크 사용량, 장기 트랜잭션을 함께 봅니다. 대량 배치 직후 일시적으로 수치가 커진 것과 며칠간 계속 증가하는 것은 의미가 다릅니다.

현재 실행 중인 작업과 트랜잭션을 보는 예시는 다음과 같습니다. 권한과 뷰의 세부 컬럼은 PostgreSQL 버전에 따라 확인해야 하며, 민감한 쿼리 텍스트를 운영 화면에 그대로 노출하지 않도록 주의해야 합니다.

```sql
SELECT pid, usename, state, xact_start, query_start
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

이 조회에서 오래 열린 트랜잭션을 발견했다고 바로 세션을 종료하면 애플리케이션 오류나 데이터 작업 중단을 만들 수 있습니다. 어떤 서비스가 연결했는지, 정상 배치인지, 비정상적으로 기다리는 세션인지 확인한 뒤 서비스 담당자와 절차를 정해야 합니다. DBA의 안전한 조치는 “수치를 보고 즉시 kill”이 아니라 영향과 원인을 확인해 재발하지 않게 하는 것입니다.

## 6. 설정을 만질 때의 원칙

테이블별 autovacuum 설정은 `ALTER TABLE ... SET (...)`으로 둘 수 있지만, 구체적 값은 워크로드와 버전에 따라 달라집니다. 여기서는 특정 숫자를 정답처럼 제시하지 않고 판단 원칙을 정리합니다.

1. 전체 서버 설정을 바꾸기 전에 문제 테이블과 변경 패턴을 특정한다.
2. 큰 테이블의 비율 기반 임계값이 너무 늦게 작동하는지, 작은 테이블이 불필요하게 자주 작업되는지 확인한다.
3. 더 자주 돌게 만드는 설정은 I/O와 CPU 사용량을 늘릴 수 있으므로 피크 시간과 경쟁을 본다.
4. worker 수를 늘려도 디스크 I/O가 병목이면 기대와 다른 결과가 날 수 있다.
5. 설정 변경 전후에는 dead tuple 추세, 작업 시간, 쿼리 지연, 에러를 같은 기간 기준으로 비교한다.

**비용 기반 지연(cost-based vacuum delay)** 은 VACUUM이 시스템 자원을 독점하지 않도록 속도를 조절하는 장치입니다. 너무 보수적으로 제한하면 정리가 변경량을 따라가지 못할 수 있고, 너무 공격적으로 풀면 사용자 쿼리와 I/O를 경쟁할 수 있습니다. 따라서 “autovacuum이 느리다”는 말만으로 비용 제한을 크게 바꾸기보다, 실제 worker가 실행 중인지, 어떤 테이블에서 얼마나 오래 걸리는지, 디스크가 포화인지부터 확인해야 합니다.

**VACUUM FULL**은 일반 VACUUM과 다릅니다. 일반 VACUUM은 테이블 파일 안의 공간을 재사용 가능하게 하지만, VACUUM FULL은 테이블을 다시 작성해 파일 크기를 줄일 수 있습니다. 그 대가로 강한 잠금이 필요할 수 있고 작업 중 여유 공간과 시간도 고려해야 합니다. 그래서 “디스크를 줄여야 한다”는 긴급 요구가 있을 때도 단독 명령으로 판단하지 말고, 대상 테이블·잠금 영향·백업·복구 계획·작업 창을 먼저 검토해야 합니다.

## 7. 자주 하는 오해를 정리하기

첫째, autovacuum 로그가 보이면 문제가 발생했다고 해석하는 경우가 있습니다. autovacuum은 정상적인 유지보수 기능이므로 실행 자체는 건강한 신호일 수 있습니다. 반대로 로그가 전혀 없다고 무조건 좋다고도 할 수 없습니다. 작업이 필요 없는 것인지, 설정이나 권한 문제로 실행되지 않는 것인지 구분해야 합니다.

둘째, 테이블 파일 크기가 줄지 않으면 VACUUM이 실패했다고 생각하기 쉽습니다. 일반 VACUUM의 주요 목적은 내부 공간 재사용과 오래된 행 버전 처리입니다. 재사용 가능한 공간이 생기면 이후 INSERT·UPDATE에서 파일 증가를 늦출 수 있지만, 운영체제가 보는 파일 크기가 바로 감소한다는 약속은 아닙니다. 파일 축소는 별도의 비용과 잠금 영향을 가진 결정입니다.

셋째, `n_dead_tup`이 높으면 항상 성능이 나쁘다고 보는 오해입니다. 통계 값은 추정치이고, 테이블 크기·인덱스·캐시·쿼리 패턴에 따라 영향이 다릅니다. 다만 지속 증가, autovacuum 지연, 쿼리 지연, 디스크 압박이 함께 보이면 원인 분석의 좋은 출발점이 됩니다.

넷째, autovacuum을 비활성화하면 쓰기 성능이 즉시 좋아질 것이라는 생각입니다. 단기적으로 유지보수 I/O가 줄어 보일 수 있지만 dead tuple, 통계 노후화, wraparound 위험을 누적시키는 방식일 수 있습니다. 특히 프로덕션에서 무작정 끄는 것은 문제를 해결하는 대신 나중에 더 어려운 작업을 남기는 선택이 될 수 있습니다.

## 8. 장애·성능 조사에서 사용할 질문

PostgreSQL 지연을 조사할 때 autovacuum은 가능한 원인 중 하나입니다. 아래 질문을 순서대로 확인하면 한 가지 설정에 성급히 결론내리는 일을 줄일 수 있습니다.

| 질문 | 확인하려는 이유 |
| --- | --- |
| 언제부터 어떤 쿼리가 느려졌는가 | 배포·데이터 급증·배치와 시간 상관을 찾기 위해 |
| 해당 테이블의 UPDATE·DELETE 패턴은 어떤가 | 이전 행 버전이 쌓일 가능성을 보기 위해 |
| autovacuum과 autoanalyze의 마지막 시각은 언제인가 | 유지보수가 밀렸는지 보기 위해 |
| 장기 트랜잭션이 있는가 | 정리 가능 시점을 막는 원인을 찾기 위해 |
| 실행 계획과 통계는 최근 데이터 분포를 반영하는가 | 인덱스 문제와 통계 문제를 구분하기 위해 |
| 디스크 I/O·CPU·잠금은 어떤 상태인가 | worker 수나 비용 설정만의 문제가 아닌지 보기 위해 |

예를 들어 주문 상태 변경 배치가 새벽마다 실행되고, 그 직후 특정 조회가 느려졌다면 배치의 UPDATE 범위, 인덱스 영향, autoanalyze 시점, 캐시가 식는 시간 등을 함께 봅니다. “VACUUM을 돌렸더니 빨라졌다”는 관찰만으로 원인을 확정하지 말고, 어떤 통계나 공간 재사용, 잠금 해제가 영향을 줬는지 확인해야 같은 문제가 다시 왔을 때 더 안전하게 대응할 수 있습니다.

## 9. 대량 작업을 설계할 때 autovacuum을 고려하는 법

대량 데이터 정리는 애플리케이션 기능처럼 보이지만, 데이터베이스 유지보수와 직접 연결됩니다. 예를 들어 “1년이 지난 임시 데이터를 한 번에 DELETE한다”는 배치를 만들면, 대상 행뿐 아니라 인덱스 변경, WAL(Write-Ahead Log) 생성, 복제 지연, dead tuple, 이후 VACUUM 작업까지 함께 고려해야 합니다. 한 번의 SQL이 성공했다고 해서 운영 영향이 끝나는 것은 아닙니다.

가장 단순한 완화 방법 중 하나는 삭제를 작은 단위로 나누는 것입니다. 예를 들어 날짜 범위나 기본 키 범위로 나눠 일정 수의 행을 처리하고, 각 배치 사이에 관찰 지표를 확인할 수 있게 합니다. 이 방식도 항상 정답은 아닙니다. 트랜잭션을 너무 작게 자르면 애플리케이션 복잡도가 늘고, 너무 크게 잡으면 잠금과 I/O가 커질 수 있습니다. 중요한 것은 한 번에 얼마를 지울지에 대한 값보다, 중단·재개·오류·중복 실행을 어떻게 처리할지와 데이터베이스가 감당할 수 있는 작업 창을 정하는 것입니다.

기간 단위로 오래된 데이터를 제거하는 테이블이라면 파티셔닝도 검토 대상이 될 수 있습니다. 월별 파티션을 사용한다면 오래된 달의 데이터를 대량 DELETE하는 대신, 업무·보관 정책이 허용할 때 파티션을 분리하거나 제거하는 접근이 가능합니다. 그러나 파티셔닝은 쿼리 조건, 인덱스, 백업, 복제, 운영 절차를 바꾸므로 dead tuple 하나를 해결하기 위해 무조건 도입할 기능은 아닙니다. 데이터 수명 주기와 조회 패턴이 명확할 때 의미가 커집니다.

대량 UPDATE도 비슷합니다. 상태를 바꾸는 작업에서 실제로 바뀐 행만 대상으로 좁히는 조건이 있는지, 같은 행을 짧은 시간에 여러 번 갱신하지는 않는지, UPDATE가 불필요한 인덱스 변경을 만들지는 않는지를 봅니다. 예를 들어 값이 이미 `PAID`인 행까지 다시 `PAID`로 UPDATE하면, 업무 결과는 같아 보여도 행 버전과 부하를 불필요하게 만들 수 있습니다. SQL 조건과 배치 멱등성은 애플리케이션 품질 문제이면서 autovacuum 부담을 줄이는 방법이기도 합니다.

## 10. 복제와 백업이 있는 환경에서의 관찰

운영 데이터베이스는 한 대의 서버만 있는 경우보다 스트리밍 복제, 읽기 복제본, 백업, 분석 작업과 연결된 경우가 많습니다. 이때 오래 열린 읽기 작업은 주 서버의 정리와 간접적으로 연결될 수 있고, 유지보수로 발생하는 WAL은 복제·아카이브 처리량에 영향을 줄 수 있습니다. 구성마다 동작과 설정이 달라 이 글에서 단일 처방을 제시할 수는 없지만, autovacuum을 조정할 때 주 서버 지표만 보지 말아야 한다는 점은 중요합니다.

예를 들어 복제 지연이 커진 시간과 대량 변경 또는 유지보수 작업 시간이 겹친다면, 단순히 “복제가 느리다”가 아니라 WAL 생성량, 네트워크, 복제본의 적용 속도, 디스크 I/O를 함께 확인해야 합니다. 반대로 읽기 복제본에서 긴 분석 쿼리가 실행된다고 해서 주 서버의 설정을 즉시 바꾸기보다는, 그 쿼리의 실행 시간·격리 수준·스케줄과 데이터 보관 요구를 확인해야 합니다. 관찰 범위를 넓히는 것은 원인을 단정하지 않기 위한 기본 태도입니다.

백업도 유지보수와 같은 시간대에 겹칠 수 있습니다. 백업이 디스크와 네트워크를 많이 사용하고, 배치 UPDATE와 autovacuum까지 동시에 실행되면 사용자 쿼리가 영향을 받을 수 있습니다. 따라서 일정 조정은 단순히 “새벽에 모두 돌리자”가 아니라, 실제 피크와 리소스 사용량을 보고 분산하는 방식으로 접근해야 합니다. 운영 환경의 시간대별 부하 그래프는 autovacuum 값 하나보다 더 먼저 보는 자료일 수 있습니다.

## 11. 안전한 변경 절차 예시

autovacuum 관련 설정을 바꾸기 전에는 다음과 같은 절차를 문서화해 두면 좋습니다. 먼저 문제 현상을 수치로 정의합니다. 예를 들어 특정 테이블의 dead tuple 추정치가 며칠간 증가하고, 마지막 autoanalyze가 오래됐으며, 같은 기간 해당 테이블 쿼리의 지연이 늘었다는 식입니다. 그 다음 변경 후보를 하나로 좁힙니다. worker 수, 테이블별 scale factor, 배치 시간, 긴 트랜잭션 정리 중 무엇을 바꿀지 정합니다.

변경 전에는 현재 설정값과 관찰 쿼리 결과를 저장합니다. 변경 뒤에는 같은 지표를 같은 시간 구간에서 보고, 예상하지 못한 I/O 급증·복제 지연·쿼리 지연·에러가 없는지 확인합니다. 문제가 생겼을 때 되돌릴 설정과 담당자, 중단 기준을 미리 적어 두는 것이 좋습니다. 이 과정은 autovacuum에만 해당하지 않습니다. 데이터베이스 설정 변경을 “효과가 있을 것 같은 값”이 아니라 검증 가능한 가설로 다루는 기본 방식입니다.

테스트 환경이 운영 데이터의 크기와 분포를 완전히 재현하지 못할 수 있다는 한계도 남습니다. 그래서 작은 범위의 테이블별 변경, 관찰 기간 확보, 피크 시간 회피 같은 보수적인 순서가 유용합니다. 값 자체보다 변경 과정의 안전성이 더 중요할 때가 많습니다.

## 12. 권한과 운영 책임도 함께 본다

VACUUM은 누구나 실행할 수 있는 무해한 명령으로 취급하면 안 됩니다. PostgreSQL 문서에 따르면 일반적으로 테이블을 VACUUM하려면 해당 테이블의 `MAINTAIN` 권한이 필요하며, 데이터베이스 소유자는 범위 내 테이블을 처리할 수 있습니다. 운영 자동화 계정에 필요 이상으로 넓은 권한을 주지 말고, 누가 어떤 유지보수 명령을 언제 실행할 수 있는지 구분해야 합니다. [VACUUM 권한 설명](https://www.postgresql.org/docs/current/sql-vacuum.html)

수동 명령을 실행한 기록도 남겨야 합니다. 대상 데이터베이스·테이블, 실행자, 목적, 시작·종료 시각, 관찰한 영향, 결과를 티켓이나 변경 기록에 남기면 이후 같은 현상이 생겼을 때 판단 근거가 됩니다. 특히 VACUUM FULL처럼 잠금 영향이 큰 작업은 애플리케이션 담당자와 작업 창을 합의하고, 실패했을 때 복구·재시도 판단을 따로 가져야 합니다.

이런 기록은 DBA만을 위한 문서가 아닙니다. 개발자는 어떤 배치가 변경량을 만들었는지 추적할 수 있고, 운영자는 지연 시간대와 작업의 관계를 볼 수 있으며, QA는 유지보수 중에도 서비스가 기대한 오류 처리와 복구 절차를 보이는지 확인할 수 있습니다. 데이터베이스 유지보수는 한 팀의 비밀 명령이 아니라 서비스 신뢰성과 연결된 공동 작업입니다.

### 운영 대시보드에 함께 두면 좋은 지표

autovacuum 상태를 한 개의 알림 임계값으로 만들기보다는, 원인과 영향을 나눠 보는 대시보드가 이해하기 쉽습니다. 원인 쪽에는 테이블별 INSERT·UPDATE·DELETE 추세, dead tuple 추정치, 마지막 autovacuum·autoanalyze 시각, 장기 트랜잭션 수, worker 실행 시간을 둘 수 있습니다. 영향 쪽에는 주요 SQL의 지연 시간, 디스크 사용률과 I/O 대기, 커넥션 수, 잠금 대기, 복제 지연을 둡니다. 이 두 화면을 같은 시간 축에서 보면 “작업이 있었기 때문에 느려졌다”와 “느려졌지만 작업은 정상 범위였다”를 구분하는 데 도움이 됩니다.

알림은 변화가 의미 있는 경우에만 울리도록 설계하는 편이 좋습니다. 예를 들어 마지막 autovacuum 시각이 오래됐다는 사실만으로는 테이블이 실제로 변경됐는지 알 수 없습니다. 반면 변경량이 계속 증가하고 dead tuple 추정치가 누적되며, 동시에 쿼리 지연이나 디스크 압박이 나타난다면 조사가 필요한 조합이 됩니다. 알림이 너무 많으면 결국 무시되므로, 단일 수치보다 여러 신호와 업무 중요도를 조합해 우선순위를 정하는 것이 좋습니다.

또한 작업 로그의 상세 내용을 보관할 때는 SQL 전문과 바인드 값에 개인정보나 비밀값이 섞일 수 있음을 고려해야 합니다. 성능 조사에 필요한 식별자·시간·실행 계획 요약을 남기되, 접근 권한과 마스킹 정책을 함께 정합니다. 관찰 가능성과 데이터 보호는 서로 반대되는 목표가 아니라, 어떤 정보를 누가 얼마나 오래 볼 수 있는지 설계해야 하는 같은 운영 문제입니다.

처음부터 모든 지표를 완벽하게 수집하지 못해도 됩니다. 가장 변경이 많은 테이블 몇 개와 사용자 영향이 큰 쿼리 몇 개를 연결해 보는 것부터 시작할 수 있습니다. 이후 장애나 성능 저하 사례가 생길 때마다 “그때 어떤 유지보수·배치·트랜잭션이 있었는가”를 추가하면, 대시보드는 숫자 모음이 아니라 운영 판단을 돕는 기록이 됩니다. autovacuum도 마찬가지로, 값 하나를 외워 적용하기보다 서비스의 데이터 변경 흐름 안에서 이해할 때 훨씬 안전하게 다룰 수 있습니다.

이처럼 관찰·가설·작은 변경·재확인을 반복하면, autovacuum을 블랙박스가 아니라 데이터베이스의 정상적인 운영 구성 요소로 다룰 수 있습니다.

업무 특성에 맞는 기준을 문서화하고, 변경 전후의 근거를 남기는 습관이 결국 가장 재현 가능한 데이터베이스 운영 방식이 됩니다.

### 버전과 환경 차이를 확인해야 하는 이유

PostgreSQL 유지보수 관련 문서는 사용하는 메이저 버전 기준으로 읽는 것이 중요합니다. autovacuum 파라미터의 기본값, 통계 뷰의 컬럼, VACUUM 옵션, 복제와 관련된 동작은 버전마다 달라질 수 있습니다. 인터넷에서 본 설정 예시가 현재 운영 버전에 그대로 맞는다고 가정하면 위험합니다. 운영 서버의 `SHOW server_version;` 같은 기본 정보를 확인하고, 같은 버전의 공식 문서에서 파라미터 설명과 제약을 다시 읽는 습관이 필요합니다.

스토리지 종류도 결과에 영향을 줍니다. 로컬 SSD, 네트워크 블록 스토리지, 공유 파일 시스템은 I/O 지연과 처리량 특성이 다르고, 백업·복제·다른 배치 작업이 같은 자원을 사용하면 autovacuum 작업 시간이 달라질 수 있습니다. 따라서 특정 수치를 외워 적용하기보다, 변경 전 관찰값과 변경 후 관찰값을 비교하는 것이 안전합니다. 문서의 권고는 출발점이고, 자신의 환경에서의 검증은 별도의 운영 작업입니다.

개발·스테이징 환경도 활용할 수 있습니다. 운영 데이터 전체를 복제하지 않더라도, 변경이 많은 테이블 구조와 대표적인 배치 패턴을 재현해 VACUUM·ANALYZE의 의미와 관찰 쿼리를 익힐 수 있습니다. 다만 테스트 환경의 데이터량과 동시성이 다르면 결과를 운영 성능 수치로 일반화하면 안 됩니다. 실습은 원리를 배우기 위한 것이고, 운영 변경은 별도 승인과 관찰 계획을 가진 작업이라는 경계를 유지해야 합니다.

## 마무리: autovacuum은 청소 기능이 아니라 동시성의 일부다

PostgreSQL의 autovacuum은 보이지 않는 백그라운드 작업처럼 보이지만, MVCC로 얻는 동시성의 대가를 관리하는 핵심 기능입니다. 이전 행 버전을 정리하고, 통계를 갱신하고, transaction ID 관련 위험을 예방합니다. 그래서 autovacuum을 단지 디스크 청소 기능으로 보거나, 지연이 생길 때 제일 먼저 끄는 대상으로 보면 안 됩니다.

처음에는 `pg_stat_user_tables`에서 변경이 많은 테이블과 마지막 autovacuum·autoanalyze 시각을 보는 것부터 시작해도 좋습니다. 그 뒤 긴 트랜잭션, 쿼리 계획, I/O, 배치 패턴을 함께 연결하면 “느린 DB”라는 현상을 보다 구체적인 점검 항목으로 바꿀 수 있습니다.
