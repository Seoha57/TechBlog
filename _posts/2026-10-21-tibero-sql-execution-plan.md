SQL이 느릴 때 인덱스를 하나 더 만들거나 힌트를 붙이는 일부터 시작하면 문제를 다른 곳으로 옮기기 쉽습니다. 느린 이유는 테이블이 커서일 수도 있고, 예상 행 수가 틀려서일 수도 있고, 조인 순서·조건식·정렬·잠금·디스크 대기·애플리케이션의 반복 호출 때문일 수도 있습니다. **실행 계획(execution plan)** 은 DBMS가 SQL을 처리하기 위해 선택한 접근 경로와 작업 순서를 보여 주는 지도입니다. 하지만 계획의 cost가 높다고 곧 오류는 아니고, 계획만 보고 실제 수행 시간을 단정할 수도 없습니다.

Tibero를 처음 다루는 DBA·개발자에게 실행 계획은 낯선 약어 목록처럼 보일 수 있습니다. TiberoStudio는 SQL Plan과 SQL Trace에서 operation, object, cost, cardinality, predicate, plan statistics 같은 정보를 확인할 수 있습니다. 이 글은 이 정보가 각각 무엇을 뜻하는지, 추정치와 실제 값을 왜 분리해야 하는지, 인덱스·조인·통계 문제를 어떤 순서로 확인해야 하는지 설명합니다. 특정 시스템에서 측정한 결과나 모든 버전에 그대로 적용되는 튜닝 명령을 제시하지 않습니다.

## 먼저 알아둘 기반 기술

**옵티마이저(optimizer)** 는 SQL을 어떻게 실행할지 후보 계획을 만들고, 통계와 비용 모델을 바탕으로 한 계획을 고르는 DBMS 구성 요소입니다. 같은 결과를 얻는 SQL도 테이블을 읽는 순서, 인덱스를 쓸지, 조인을 어떤 방식으로 할지에 따라 비용이 크게 달라집니다. 옵티마이저는 모든 데이터를 실제로 읽어 본 뒤 선택하지 않으므로, 객체 통계와 조건의 선택도에 의존합니다.

**카디널리티(cardinality)** 는 어떤 계획 단계가 반환할 것으로 예상하는 행 수입니다. 반면 실제 수행 정보의 rows는 실제로 흘러간 행 수에 가깝습니다. 예상이 10건인데 실제가 100만 건이면, 작은 입력에 적합한 nested loop 조인을 선택했다가 반복 I/O가 커질 수 있습니다. 실행 계획을 읽을 때 operation 이름만 보지 말고 예상 행 수와 실제 행 수의 차이를 보는 이유입니다.

**인덱스(index)** 는 특정 키나 순서로 데이터를 빠르게 찾기 위해 만든 보조 구조입니다. 인덱스가 있다고 무조건 사용되는 것은 아닙니다. 조건이 행 대부분을 선택하거나, 함수·형 변환 때문에 인덱스 키를 그대로 비교하지 못하거나, 테이블 행을 다시 찾는 비용이 큰 경우에는 다른 접근 경로가 더 나을 수 있습니다. 인덱스는 읽기를 돕는 대신 INSERT·UPDATE·DELETE의 유지 비용과 저장 공간을 늘립니다.

## 실행 계획은 SQL의 실제 실행 기록이 아니다

실행 계획은 보통 “이렇게 실행할 것이다”라는 선택입니다. SQL Trace나 plan statistics처럼 실제 수행 뒤 제공되는 정보는 “실제로 어떤 행과 대기가 있었는가”를 보완합니다. 둘을 섞으면 오해가 생깁니다. 예를 들어 계획의 cardinality가 100이고 cost가 낮아도, 실행 당시 블록 I/O가 오래 기다렸거나 동시 세션의 잠금 대기가 있었다면 응답 시간은 길 수 있습니다. 반대로 cost가 커도 대량 보고서처럼 예정된 배치라면 업무상 허용될 수 있습니다.

TiberoStudio의 SQL Plan은 tree와 text 형식으로 계획 정보를 볼 수 있고, operation, option, object, cost, cardinality, access predicate, filter predicate 등을 보여 줍니다. SQL Trace는 SQL ID, child number, plan hash value, autotrace stats, plan stats, predicate 정보를 함께 확인할 수 있습니다. 화면에서 버튼을 누르는 방법보다 중요한 것은 같은 SQL ID·실행 시각·바인드 값·데이터 상태를 연결하는 것입니다. 서로 다른 실행의 계획과 시간을 비교하면 원인을 잘못 짚을 수 있습니다.

계획은 보통 들여쓰기가 깊은 작업부터 입력을 만들고, 상위 작업이 그 결과를 소비하는 형태로 읽습니다. 다만 화면의 위아래를 기계적으로만 읽지 말고, 각 operation이 어떤 입력을 받아 몇 행을 내보내는지 따라가야 합니다. 정렬, group by, hash build, nested loop의 내부 접근처럼 중간 결과가 커지는 지점이 병목 후보가 됩니다.

## 가장 먼저 확인할 네 가지 질문

느린 SQL을 받으면 “인덱스가 있나?”보다 먼저 범위를 정합니다. 첫째, 사용자 요청의 어떤 화면·API·배치에서 느린가와 언제부터였는가를 확인합니다. 둘째, 단일 SQL이 느린가 아니면 같은 SQL이 수천 번 반복되는가를 구분합니다. 셋째, 해당 실행의 SQL text·바인드 값·SQL ID·계획 hash·실행 시간·반환 행 수를 보존합니다. 넷째, CPU·I/O·잠금·네트워크·애플리케이션 대기 중 어떤 종류의 시간이 늘었는지 확인합니다.

예를 들어 주문 상세 API가 느리다고 해서 주문 조회 SQL 하나만 문제라고 단정하면 안 됩니다. API가 주문 한 건을 가져온 뒤 상품·쿠폰·배송 정보를 각각 반복 조회하는 N+1 패턴일 수 있습니다. 개별 SQL은 2ms여도 500번 실행되면 사용자 경험은 나빠집니다. 반대로 하루 한 번 실행되는 분석 SQL이 수분 걸린다면 전체 스캔보다 정렬을 위한 임시 공간, 동시 배치, 스토리지 처리량이 더 중요할 수 있습니다.

문제 SQL을 재현할 때 운영 데이터를 무단으로 복제하거나, 운영에서 무거운 explain·trace를 무분별하게 실행하면 안 됩니다. 권한과 부하 영향을 확인하고, 가능하면 승인된 스테이징·마스킹 데이터·제한된 샘플로 재현합니다. 운영에서 증거가 필요하면 조직의 진단 절차와 Tibero 버전 문서를 우선합니다.

## 접근 조건과 필터 조건을 구분한다

**access predicate** 는 데이터를 찾기 위해 접근 경로를 결정하는 조건입니다. 예를 들어 복합 인덱스 `(customer_id, created_at)`가 있고 `customer_id = :id`와 기간 조건을 함께 쓸 때, 조건 일부가 인덱스 범위를 좁히는 데 쓰일 수 있습니다. **filter predicate** 는 이미 읽어 온 행에 추가로 적용하는 조건입니다. filter가 있다고 잘못은 아니지만, 너무 많은 행을 읽은 뒤 대부분 버린다면 접근 경로 또는 조건식이 개선 후보가 됩니다.

다음 두 조건은 논리적으로 비슷해 보여도 인덱스 사용 가능성이 다를 수 있습니다. 날짜 컬럼에 함수를 적용하면 DBMS가 인덱스 키 범위를 쉽게 계산하지 못할 수 있습니다.

```sql
-- 열의 원래 값 범위를 비교하기 쉬운 형태
where created_at >= :from_at
  and created_at < :to_at

-- 함수와 형 변환이 접근 조건을 어렵게 만들 수 있는 형태
where to_char(created_at, 'YYYY-MM-DD') = :day
```

그렇다고 함수를 없애는 것이 유일한 답은 아닙니다. 업무 요구가 날짜 문자열 비교라면 입력을 적절한 timestamp 범위로 바꾸거나, 제품과 버전이 지원하는 함수 기반 인덱스·파생 컬럼을 검토할 수 있습니다. 어떤 선택이든 NULL 처리, 시간대, 경계 시각, 기존 쿼리와 쓰기 비용을 테스트해야 합니다.

복합 인덱스 순서도 “선택도가 높은 컬럼을 무조건 앞에”라는 규칙 하나로 끝나지 않습니다. 동등 조건과 범위 조건의 조합, 정렬 요구, 조인 키, 자주 함께 쓰는 조건, 쓰기 비용이 영향을 줍니다. 인덱스를 추가하기 전에는 실제 SQL 패턴과 중복 인덱스, DML 부하, 공간·백업 영향까지 확인합니다.

## 조인 방식은 입력 크기와 데이터 분포의 선택이다

조인은 두 집합을 연결하는 작업입니다. **nested loop join** 은 바깥 입력의 각 행마다 안쪽 입력을 찾는 방식으로, 바깥쪽이 작고 안쪽에 효율적인 인덱스 접근이 있을 때 유리할 수 있습니다. **hash join** 은 한쪽 입력으로 해시 구조를 만든 뒤 다른 쪽을 탐색하는 방식으로, 비교적 큰 집합을 등가 조건으로 결합할 때 후보가 될 수 있습니다. **sort merge join** 은 정렬된 입력을 병합하는 방식이며, 정렬 비용과 입력 순서가 중요합니다. 어떤 방식이 항상 우위인 것은 아닙니다.

문제는 조인 이름보다 입력 행 수의 오차입니다. 고객 한 명의 주문을 찾는다고 예상했는데 조건이 넓어져 수십만 주문이 바깥 입력이 되면 nested loop의 안쪽 접근이 수십만 번 반복됩니다. 반대로 아주 작은 결과에 hash table을 만들면 준비 비용이 낭비일 수 있습니다. 계획의 각 단계에서 예상 cardinality가 어디서 갑자기 커지는지, 실제 rows가 예상과 얼마나 다른지 찾아봅니다.

조인 조건이 빠져 카테시안 곱에 가까운 결과가 생기는 경우도 있습니다. ORM이 만든 SQL, 동적 조건 조합, nullable key, 형 변환 때문에 의도한 조인 조건이 빠지거나 효력이 약해질 수 있습니다. 결과 행 수가 비정상적으로 커졌다면 먼저 업무상 필요한 관계와 키의 유일성을 확인합니다. 힌트로 조인 순서만 바꾸면 논리 오류를 숨길 수 있습니다.

## 통계는 옵티마이저가 보는 데이터 지도다

옵티마이저는 테이블 행 수, 컬럼 값의 분포, distinct 값 수, 인덱스 정보 같은 통계를 이용해 선택도를 추정합니다. 통계가 오래됐거나 데이터가 특정 값에 심하게 몰렸거나, 서로 관련된 컬럼 조건을 독립이라고 가정하면 cardinality가 틀릴 수 있습니다. 월말에만 특정 상태 값이 급증하는 주문 테이블에서 오래된 통계로 계획을 고르면 평소와 다른 접근 경로가 선택될 수 있습니다.

통계 갱신은 느린 SQL을 만날 때마다 무조건 실행하는 응급 처치가 아닙니다. 대량 적재·파티션 교체·대규모 삭제처럼 분포가 바뀌는 변경과 연결하고, 어떤 객체·컬럼이 대상인지, 갱신 중 부하와 계획 변화가 어떤지 검토합니다. 통계만 갱신해도 해결되지 않는다면 쿼리 조건, 데이터 모델, 인덱스, 애플리케이션 호출 패턴을 다시 봐야 합니다.

특히 바인드 변수는 좋은 재사용성을 주지만, 값마다 선택도가 크게 다른 경우 하나의 계획이 모든 값에 적합하지 않을 수 있습니다. 고객 ID처럼 대부분 소량인 값과, 특별 계정처럼 대량 데이터를 가진 값이 같은 SQL 형태로 들어올 수 있습니다. 이 문제를 발견했다고 값을 문자열로 붙여 SQL을 만드는 것은 SQL injection과 plan cache 문제를 만들 수 있습니다. 사용 중인 Tibero 버전의 바인드·커서·통계 기능과 애플리케이션의 입력 검증을 함께 검토합니다.

## 계획과 실제 수행 정보를 나란히 비교한다

SQL Trace의 plan statistics, autotrace stats, predicate 정보는 계획 추정과 실제 작업을 연결하는 데 도움이 됩니다. 예를 들어 특정 테이블 스캔 단계에서 예상 100행·실제 200만 행이라면 통계·조건·바인드가 우선 조사 대상입니다. 예상과 실제 행 수가 비슷한데 시간이 길다면 I/O 대기, 정렬·해시를 위한 메모리와 임시 공간, 잠금 대기, 네트워크 왕복을 더 살펴야 합니다.

plan hash value는 계획 형태가 바뀌었는지 추적하는 실마리입니다. 같은 SQL ID가 느려진 시점에 plan hash가 바뀌었다면 통계 갱신, 데이터 증가, 객체 변경, 파라미터 변경, 바인드 값 분포를 비교할 수 있습니다. 하지만 plan hash가 같아도 저장소가 느리거나 다른 세션의 잠금을 기다리면 시간은 나빠질 수 있습니다. 반대로 hash가 달라도 결과와 응답 시간이 허용 범위라면 무조건 되돌릴 필요는 없습니다.

SQL ID, child number, plan hash만으로 사용자 영향이 모두 설명되지는 않습니다. API trace ID, 배포 버전, 호출 횟수, 오류율, DB 세션 대기와 시간을 같은 타임라인에 놓아야 합니다. DBA와 개발자가 서로 다른 화면만 보면 “DB는 정상”, “API는 느림”이라는 결론으로 끝나기 쉽습니다. 관찰 항목을 공동으로 정하면 병목 범위를 더 빨리 좁힐 수 있습니다.

## 안전한 개선 순서

첫 단계는 문제를 재현 가능한 문장으로 만드는 것입니다. 예를 들어 “월말 09:00~10:00에 특정 고객군의 주문 목록 API p95가 목표를 넘고, SQL ID X의 실제 rows가 추정보다 크다”처럼 범위와 증거를 적습니다. 둘째, SQL text와 바인드·계획·통계·객체 정의를 읽고, 조건식·조인·호출 횟수 중 어느 가설을 검증할지 하나 정합니다. 셋째, 스테이징 또는 승인된 검증 환경에서 변경 전후 결과 건수·정렬·NULL 처리·실행 정보와 쓰기 부작용을 확인합니다.

개선 후보는 인덱스 추가만이 아닙니다. 불필요한 열과 행을 덜 읽도록 쿼리를 바꾸고, 페이지네이션 조건을 명확히 하고, 반복 호출을 합치고, 집계 결과를 적절히 캐시하거나 사전 계산하고, 데이터 보관·파티션 정책을 조정하는 방법도 있습니다. 그러나 결과 정확성을 바꾸는 최적화는 성능 개선이 아닙니다. 주문 목록에서 과거 주문을 빠르게 보이게 하려고 기간 조건을 임의로 줄이면 사용자 요구를 위반할 수 있습니다.

변경은 작은 범위로 배포하고 롤백 기준을 둡니다. 새 인덱스는 생성 시간과 저장 공간, DML 영향, 백업·복구 창에 영향을 줄 수 있습니다. SQL 변경은 결과 집합의 row count와 대표 사례를 비교하고, 계획이 좋아 보여도 lock·timeout·오류가 늘지 않는지 관찰합니다. 힌트는 마지막 수단에 가깝게 다룹니다. 꼭 필요하다면 적용 이유, 전제 데이터 분포, 제거 조건, 재검토 시점을 남겨 영구적인 미스터리가 되지 않게 합니다.

## 한계와 적용 기준 Q&A

### Q. 실행 계획에서 cost가 가장 큰 줄만 고치면 되나요?

A. 아닙니다. cost는 단계별 실제 소요 시간을 보장하지 않습니다. 상위 단계의 cost가 커 보이는 이유가 하위 단계의 대량 입력일 수 있고, 실제 병목은 잠금·I/O 대기일 수 있습니다. cardinality, actual rows, predicate, 대기 정보를 연결합니다.

### Q. Full Table Scan이 나오면 인덱스를 추가해야 하나요?

A. 필요한 행 비율이 높거나 작은 테이블이라면 전체 스캔이 적절할 수 있습니다. 인덱스가 있어도 테이블 접근 비용이 더 크면 사용하지 않을 수 있습니다. 먼저 결과 행 수와 조건 선택도, 호출 빈도, 쓰기 비용을 확인합니다.

### Q. 운영에서 EXPLAIN이나 trace를 실행해도 되나요?

A. 허용 범위는 제품 버전, 권한, SQL 특성, 운영 절차에 따라 다릅니다. 진단 자체가 부하를 주거나 민감한 바인드 정보를 노출할 수 있으므로, 조직의 runbook과 승인된 도구를 따르고 가능하면 스테이징에서 재현합니다.

### Q. 계획을 고정하면 성능 문제가 끝나나요?

A. 데이터 규모·분포·통계·하드웨어·동시 부하는 계속 바뀝니다. 계획 고정이나 힌트는 특정 상황의 선택을 보호할 수 있지만 미래에도 최적이라는 보장은 없습니다. 적용 사유와 모니터링·재검토 기준을 남깁니다.

## 마무리

Tibero 실행 계획은 느린 SQL의 정답지가 아니라, DBMS가 어떤 가정으로 어떤 작업을 선택했는지 보여 주는 출발점입니다. operation 이름에만 반응하지 말고 예상·실제 행 수, access·filter predicate, 조인 입력 크기, 통계의 신선도, 대기와 호출 횟수를 함께 읽어야 합니다. 작은 SQL 하나를 계획과 trace로 설명할 수 있게 되면, 인덱스 추가나 힌트보다 먼저 어떤 질문을 해야 하는지 판단할 수 있습니다. 이것이 안전한 SQL 성능 개선의 시작입니다.

## 정렬, 집계, 임시 공간을 읽는 법

조회 조건에 맞는 행을 찾는 데 성공해도, 그 뒤의 정렬과 집계가 큰 비용을 만들 수 있습니다. 화면에서 최근 주문을 날짜순으로 보여 주기 위해 `ORDER BY created_at DESC`를 사용한다고 해 봅시다. 조건·정렬과 맞는 인덱스가 있으면 일부 경우 정렬 단계를 줄일 수 있지만, 조인 뒤 계산한 값으로 정렬하거나 대량 결과를 모두 정렬해야 하면 별도 sort가 필요할 수 있습니다. 페이지의 첫 스무 건만 필요한데 애플리케이션이 전체 결과를 가져와 정렬·자르는 구조라면 SQL과 호출 방식을 함께 바꿔야 합니다.

`GROUP BY`, `DISTINCT`, 윈도 함수도 중간 결과와 메모리·임시 공간 사용을 늘릴 수 있습니다. 중복 제거가 실제 업무 요구인지, 조인 조건이 잘못돼 중복이 생겨 뒤에서 지우는 것인지 먼저 구분합니다. 집계 보고서에서 수천만 행을 매 요청마다 계산한다면 인덱스만 추가하기보다 요약 테이블, 승인된 materialized view, 배치 사전 계산, 캐시 중 어떤 방식이 최신성 요구와 맞는지 검토합니다. 빠른 결과를 위해 오래된 집계를 보여 주는 것이 허용되는지 제품 책임자와 합의해야 합니다.

임시 공간 부족이나 I/O 대기는 실행 계획의 한 줄만으로 확정할 수 없습니다. SQL Trace의 실행 통계, DB와 OS의 디스크 지표, 동시 배치 여부를 함께 봅니다. 대용량 정렬이 예상된 작업이라면 실행 시간·공간·중단 기준을 사전에 정하고, 업무 피크와 겹치지 않게 계획합니다. 운영에서 임시 파일을 임의로 지우거나 파라미터를 즉시 늘리는 대응은 복구와 다른 세션에 영향을 줄 수 있으므로 runbook을 따릅니다.

## 페이징과 반복 조회에서 생기는 병목

SQL 하나의 실행 시간이 짧아도 호출 방식이 전체 지연을 만들 수 있습니다. offset 기반 페이지네이션은 뒤쪽 페이지로 갈수록 앞 행을 건너뛰는 비용이 커질 수 있습니다. 정렬 키가 안정적이고 업무 요구가 허용한다면 마지막으로 본 키를 기준으로 다음 페이지를 찾는 keyset 방식이 후보가 될 수 있습니다. 그러나 동점 정렬, 새 데이터 삽입, 삭제, 사용자별 권한 필터 때문에 결과가 달라질 수 있으므로 `created_at` 하나가 아니라 유일한 보조 키와 일관된 정렬 계약을 함께 설계합니다.

N+1 문제도 계획 화면만으로 놓치기 쉽습니다. 목록 쿼리 하나 뒤에 각 행의 상세를 조회하는 SQL이 반복되면, 각 계획은 좋아 보여도 총 왕복 횟수가 커집니다. 애플리케이션 trace에서 요청 하나가 호출한 SQL 수와 SQL ID 분포를 보고, 필요한 열을 한 번에 가져올지, 제한된 batch 조회를 할지, 캐시를 둘지 판단합니다. 반대로 모든 관계를 거대한 join 하나로 합치면 중복 행·메모리·복잡성이 커질 수 있으므로 반환 모델과 데이터 크기를 기준으로 선택합니다.

## 잠금과 대기는 다른 종류의 느림이다

실행 계획은 CPU와 I/O 중심의 접근 선택을 설명하지만, SQL이 기다리는 모든 이유를 보여 주지는 않습니다. UPDATE나 DELETE가 느릴 때 다른 세션이 같은 행 또는 관련 자원을 오래 점유하고 있을 수 있습니다. 이 경우 인덱스나 조인 방식을 바꿔도 근본 원인이 해결되지 않습니다. 트랜잭션 시작·종료 시각, blocking 세션, 현재 SQL, 대기 이벤트, 애플리케이션의 재시도와 커넥션 사용 방식을 연결해야 합니다.

긴 트랜잭션은 잠금뿐 아니라 undo·복구·동시성에도 영향을 줄 수 있습니다. 사용자 입력을 기다리는 동안 트랜잭션을 열어 두거나, 외부 HTTP 호출을 DB 트랜잭션 안에서 수행하면 대기 시간이 불필요하게 길어집니다. 가능한 경우 DB 변경의 원자적 범위를 짧게 정의하고, 외부 작업은 커밋 뒤 신뢰할 수 있는 이벤트·재처리 방식으로 분리합니다. 하지만 업무 원자성을 깨뜨리는 분리는 데이터 불일치를 만들 수 있으므로 제품 계약과 보상 절차를 함께 설계해야 합니다.

TiberoStudio의 세션·트랜잭션 화면에서 현재 SQL, 실행 계획, 대기와 block 정보를 함께 보는 이유도 여기에 있습니다. 단일 SQL의 text를 복사해 스테이징에서 빠르다고 확인해도, 운영의 동시 실행과 잠금 경합은 재현되지 않을 수 있습니다. 운영 진단에서는 민감 SQL과 사용자 정보를 보호하고, 세션을 강제로 종료하기 전에 영향 범위와 승인 절차를 확인합니다.

## 튜닝 변경을 검증하는 체크리스트

성능 변경은 기능 변경입니다. SQL을 고친 뒤에는 대표 입력뿐 아니라 빈 결과, NULL, 경계 날짜, 중복 키, 권한 필터, 페이지 마지막, 대량 입력에서 결과가 같은지 비교합니다. 인덱스를 추가했다면 생성과 유지 중 DML 지연, 저장 공간, 백업 시간, 다른 SQL 계획 변화를 확인합니다. 통계를 갱신했다면 의도하지 않은 다른 핵심 SQL의 계획이 바뀌지 않았는지 표본을 봅니다.

측정도 단일 실행의 숫자로 결론 내리지 않습니다. 캐시가 비어 있던 첫 실행인지, 데이터가 워밍업된 뒤인지, 동시 부하가 있는지, 바인드 값은 무엇인지, 반환 행 수는 같은지 기록합니다. 평균 시간만 좋고 p95가 나빠졌거나 오류가 늘면 개선이라고 말하기 어렵습니다. 실제 운영 성능 수치를 이 글의 예시로 가정하지 말고, 자신의 서비스 목표와 검증 환경을 기준으로 비교해야 합니다.

롤백 계획도 변경 전 작성합니다. 새 인덱스를 제거할 수 있는지, 이전 SQL을 즉시 되돌릴 수 있는지, 배포 중 어떤 지표에서 중단할지, 계획 hash 변화가 예상과 다를 때 누가 판단할지를 정합니다. 이렇게 준비하면 느린 SQL을 발견했을 때 위험한 즉석 변경 대신 증거를 기반으로 작은 변경을 반복할 수 있습니다.

## 개발자와 DBA가 공유할 최소 정보

개발자는 느린 요청의 API 이름, 발생 시각, 사용자 영향, 요청 수, trace ID, 바인드 값의 민감 정보 처리 상태를 제공할 수 있습니다. DBA는 해당 시각의 SQL ID, child number, plan hash, 계획과 trace 통계, 대기·잠금·객체 통계 상태를 연결할 수 있습니다. 둘 중 한쪽이 모든 답을 갖고 있지 않다는 전제로, 재현 조건과 변경 결과를 같은 문서에 남기는 것이 좋습니다.

예를 들어 “인덱스를 썼다”는 보고보다 “특정 범위 조건에서 예상 50행이 실제 20만 행이었고, 통계 갱신 뒤 계획이 바뀌었으며 결과 건수와 오류율은 유지됐다”는 보고가 다음 판단에 유용합니다. 계획을 읽는 역량은 도구 화면의 모든 컬럼을 외우는 능력이 아니라, 데이터·SQL·사용자 영향 사이에 검증 가능한 설명을 만드는 능력입니다.

## 계획을 비교할 때 놓치기 쉬운 조건

계획을 비교할 때 SQL text가 같다는 사실만으로 같은 조건이라고 볼 수는 없습니다. 바인드 값, 세션 설정, schema 변경, 통계 시점, 파티션 범위, 병렬 실행 여부, 캐시 상태가 다르면 다른 선택이나 다른 시간이 나올 수 있습니다. 따라서 전후 결과에는 최소한 실행 시각, 대상 환경, 반환 행 수, 바인드 유형, SQL ID와 plan hash를 남깁니다. 민감한 고객 식별자와 원문 값은 마스킹하거나 접근이 제한된 기록에 보관해야 합니다.

개발 환경의 작은 데이터로 인덱스가 좋아 보였다고 운영에서도 좋다는 보장은 없습니다. 데이터가 커질수록 랜덤 I/O와 테이블 접근 비용, 값 분포, 동시성의 비중이 달라집니다. 반대로 운영의 계획을 그대로 복제하기 어려운 경우에는 행 수·분포·핵심 인덱스·대표 바인드 값을 가능한 범위에서 재현하고, 차이를 문서에 명시합니다. 재현이 완벽하지 않다는 사실을 숨기는 것보다, 어떤 결론까지 신뢰할 수 있는지 밝히는 편이 안전합니다.

SQL 성능은 데이터 모델과도 연결됩니다. 자주 조인하는 키의 타입과 의미가 다르거나, 상태 값을 여러 문자열로 중복 저장하거나, 같은 사실을 여러 테이블에서 매번 조합해야 한다면 쿼리 튜닝만으로 한계가 있습니다. 정규화와 비정규화 중 무엇이 맞는지는 읽기 패턴, 쓰기 일관성, 갱신 비용, 복구·감사 요구에 따라 다릅니다. 성능 문제를 계기로 무조건 모델을 뜯어고치기보다, 반복되는 접근 패턴과 제품 요구를 근거로 단계적으로 판단합니다.

## 처음 계획을 읽는 사람의 연습 방법

작은 조회 SQL 하나를 골라 조건을 하나씩 바꿔 보며 계획과 결과 행 수가 어떻게 달라지는지 관찰하는 연습이 좋습니다. 동등 조건, 범위 조건, 정렬, 조인, 존재 여부 확인을 각각 분리하고, 결과가 같은 두 SQL이 왜 다른 작업을 선택하는지 설명해 봅니다. 단, 운영 테이블을 대상으로 무거운 실험을 하지 말고 교육·검증용 데이터와 승인된 환경을 사용합니다.

그 다음 SQL Plan에서 object, operation, predicate, cardinality를 읽고 SQL Trace에서 실제 통계와 plan hash를 연결합니다. 모르는 컬럼은 추측하지 말고 사용 중인 Tibero 버전의 참조 문서와 DBA에게 확인합니다. 실행 계획은 암기 시험이 아니라 가설을 세우고 증거로 좁혀 가는 도구입니다. 이 태도를 지키면 낯선 제품이나 복잡한 SQL을 만나도 성급한 인덱스·힌트 변경보다 안전한 진단을 할 수 있습니다.

## 운영 점검 기록의 예시

느린 SQL 조사는 다음 질문에 답하는 짧은 기록으로 시작할 수 있습니다. 어떤 기능에서, 어느 시각부터, 어떤 사용자 범위가 영향을 받았는가? SQL ID와 plan hash는 무엇이며, 반환 행 수와 바인드 유형은 무엇인가? 예상 cardinality와 실제 rows가 처음 어긋나는 단계는 어디인가? 그 시점에 잠금·I/O·CPU·네트워크 중 어떤 대기가 있었는가? 마지막으로 변경 전후에 결과 정확성, 오류율, 쓰기 부하, 다른 핵심 SQL이 어떻게 달라졌는가를 적습니다.

이 기록은 특정 도구 화면의 스크린샷보다 오래 쓸 수 있습니다. 다른 담당자가 같은 SQL을 보거나 한 달 뒤 데이터 분포가 바뀌었을 때도 당시 가설과 근거를 이해할 수 있기 때문입니다. 원인이 확정되지 않았으면 확정된 것처럼 쓰지 않고, 다음 검증 항목과 위험을 분리합니다. SQL 성능을 안전하게 다루는 문화는 빠른 답 하나보다 재현 가능한 판단 과정을 남기는 데서 시작합니다.

정기 점검에서는 가장 비싼 SQL 목록만 보지 말고, 실행 횟수가 급증한 SQL, plan hash가 자주 바뀌는 SQL, 반환 행 수가 갑자기 커진 SQL, lock wait와 함께 나타나는 SQL을 함께 봅니다. 이 목록은 자동으로 인덱스를 만들기 위한 것이 아니라, 다음 배포·통계 변경·데이터 증가 전에 확인할 우선순위를 정하기 위한 것입니다. 업무 중요도와 사용자 영향이 큰 흐름부터 작은 범위에서 개선하고 검증합니다.

계획 분석 결과는 변경 요청에도 연결합니다. 인덱스·통계·SQL·데이터 모델 중 무엇을 바꾸는지, 영향을 받을 객체와 서비스는 무엇인지, 검증할 결과와 롤백 조건은 무엇인지 적습니다. 이렇게 하면 성능 개선이 개인의 경험에만 의존하지 않고, 다른 담당자가 검토하고 다음 변경에서 다시 활용할 수 있는 운영 지식이 됩니다.
