데이터베이스 서버 한 대가 충분히 빠르더라도, 그 한 대가 멈추면 서비스가 함께 멈출 수 있습니다. CPU·메모리·디스크 용량을 키우는 수직 확장만으로는 장애 지점 하나를 없애기 어렵고, 데이터베이스를 여러 대로 복제하면 읽기 분산은 쉬워도 여러 노드가 같은 데이터를 동시에 갱신할 때 일관성을 설계해야 합니다. **TAC(Tibero Active Cluster)** 는 여러 Tibero 노드가 하나의 데이터베이스 워크로드를 처리하는 Active-Active 클러스터 구성으로, 가용성과 처리 능력을 함께 고려하는 Tibero의 클러스터 기술입니다.

TAC를 처음 들으면 “서버 두 대가 있으니 무조건 두 배 빠르고 절대 멈추지 않는다”라고 이해하기 쉽습니다. 실제 운영은 더 복잡합니다. 노드뿐 아니라 공유 스토리지, 노드 간 통신, 클러스터 관리, 클라이언트 연결, 장애 감지, 애플리케이션의 재시도와 트랜잭션 경계가 함께 맞아야 합니다. 한 노드가 살아 있어도 연결 문자열이나 커넥션 풀이 장애를 올바르게 처리하지 못하면 사용자는 오류를 볼 수 있습니다. 반대로 데이터베이스 클러스터가 있어도 단일 로드 밸런서·단일 네트워크 경로·단일 외부 API가 남아 있으면 서비스 전체의 단일 장애 지점은 계속 존재합니다.

이 글은 Tibero를 처음 다루는 취업 준비생과, 단일 DBMS 운영 경험은 있지만 클러스터 구조가 낯선 현업자를 위해 TAC의 역할과 한계를 정리합니다. 특정 조직에서의 성능 수치나 운영 경험을 주장하지 않습니다. 제품 버전과 구성에 따라 설치 절차·지원 기능·파라미터는 달라질 수 있으므로 실제 적용 전에는 해당 버전의 공식 문서를 기준으로 검증해야 합니다.

## 먼저 알아둘 기반 기술: DBMS, HA, 클러스터와 복제

**DBMS(Database Management System, 데이터베이스 관리 시스템)** 는 데이터를 저장·조회·갱신하고 트랜잭션·동시성·복구를 제공하는 소프트웨어입니다. Tibero는 관계형 DBMS(RDBMS)이며, SQL을 통해 테이블·인덱스·트랜잭션·권한을 관리합니다. 애플리케이션이 데이터베이스에 연결해 SQL을 실행할 때, 단순히 한 프로세스에 요청을 보내는 것이 아니라 인증·세션·트랜잭션·락·버퍼 캐시를 거치는 복합적인 흐름이 생깁니다.

**고가용성(HA, High Availability)** 은 서비스가 장애 상황에서도 계속 또는 빠르게 복구되어 이용 가능하도록 설계하는 목표입니다. 가용성은 장비 개수만으로 결정되지 않습니다. 장애를 감지하는 시간, 대체 경로로 전환하는 시간, 데이터 손실 허용 범위, 애플리케이션의 재연결 방식, 운영자가 복구를 검증하는 절차가 모두 영향을 줍니다. “다운타임이 없을 것이다”라는 선언보다 어떤 장애에서 어떤 수준의 연결 끊김·재시도·데이터 복구를 허용하는지 명시하는 편이 현실적입니다.

**클러스터(cluster)** 는 여러 서버가 협력해 하나의 서비스 역할을 수행하는 구성입니다. 데이터베이스 클러스터에는 여러 모델이 있습니다. Active-Passive는 평소 한 노드가 서비스를 처리하고 대기 노드가 장애 때 역할을 넘겨받는 형태입니다. Active-Active는 여러 노드가 평소에도 요청을 처리합니다. Shared-nothing 구조에서는 각 노드가 자신의 저장소를 가지고 데이터를 분할·복제할 수 있고, shared-storage 또는 shared-disk 구조에서는 여러 노드가 공통 저장소의 데이터에 접근할 수 있습니다. 제품별 구현이 다르므로 이름만 같다고 동작이 같지는 않습니다.

**복제(replication)** 는 데이터의 변경을 다른 위치로 전달하는 기술입니다. 재해 복구(DR, Disaster Recovery), 읽기 부하 분산, 지역 간 데이터 보호에 유용할 수 있습니다. 하지만 복제 지연, 쓰기 충돌, 전환 절차를 고려해야 합니다. TAC 같은 클러스터와 복제는 서로 배타적인 선택이 아닙니다. 한 데이터센터 안에서 노드 장애에 대응하는 클러스터와, 다른 지역·센터의 재해에 대응하는 복제를 함께 설계할 수 있습니다. 각각이 막는 장애 범위가 다르다는 점이 중요합니다.

## TAC의 큰 그림: 여러 Active 노드와 하나의 DB 워크로드

TAC는 Active-Active 형태로 여러 Tibero 인스턴스가 하나의 데이터베이스 워크로드를 처리하도록 구성합니다. 각 노드는 클라이언트 요청을 받을 수 있고, 노드별로 CPU·메모리·버퍼 캐시를 사용합니다. 따라서 읽기와 쓰기 요청을 한 노드에만 몰아넣지 않고 분산할 여지가 생깁니다. Tibero 지원 문서에서는 TAC가 Active 노드의 수평 확장과 Global Cache를 통한 디스크 I/O 최소화를 설명합니다.

그러나 여러 노드가 같은 데이터 블록을 각자의 메모리에 캐시한다면, 한 노드가 바꾼 내용을 다른 노드가 언제 어떻게 알아야 할까요? 바로 이 지점에서 **Global Cache** 와 노드 간 통신이 필요합니다. 노드 A가 특정 블록을 수정하려는데 노드 B가 그 블록의 최신 버전을 캐시에 갖고 있다면, 클러스터는 블록 소유·전송·동시 접근을 조정해야 합니다. 이는 단일 인스턴스의 버퍼 캐시와 달리 노드 간 통신 비용과 경합을 고려해야 하는 이유입니다.

TAC에서 공용 데이터 파일을 다루기 위해서는 구성에 맞는 공유 스토리지 계층이 필요합니다. Tibero Active Storage(TAS)는 TAC 구성에서 공유 디스크를 제공하기 위한 기술 중 하나입니다. 공유 스토리지는 여러 노드가 같은 데이터베이스 파일에 접근하게 해 주지만, 그 자체가 성능·가용성 문제를 자동 해결하지는 않습니다. 스토리지 경로, 이중화, 지연, 장애 격리, 펜싱과 같은 운영 조건을 함께 점검해야 합니다.

다음은 개념적 흐름입니다. 실제 설치 구성에는 전용 네트워크, 스토리지 설정, 클러스터 관리 구성 요소와 버전별 파라미터가 추가됩니다.

```text
애플리케이션 / 커넥션 풀
          │  (연결·재시도·로드 밸런싱)
          ▼
  ┌───────────────────────────────┐
  │ Tibero 노드 A  ↔  Tibero 노드 B │
  │ 버퍼 캐시·Global Cache·노드 통신 │
  └───────────────┬───────────────┘
                  ▼
        공유 데이터 파일 / 공유 스토리지
```

## Global Cache를 이해하는 법: 캐시가 여러 개일 때의 일관성

단일 DB 인스턴스에서도 버퍼 캐시는 디스크보다 빠르게 데이터 블록을 읽기 위해 필요합니다. TAC에서는 노드마다 버퍼 캐시가 있으므로, 같은 데이터 블록을 여러 노드가 읽거나 한 노드가 갱신하는 상황을 조정해야 합니다. Global Cache는 노드 사이에서 데이터 블록과 상태를 관리하여 불필요한 디스크 접근을 줄이고 일관된 접근을 돕는 개념으로 이해할 수 있습니다.

이 구조는 워크로드 배치가 중요하다는 뜻이기도 합니다. 특정 테이블의 몇 행을 여러 노드가 매우 자주 동시에 업데이트하면, 디스크가 빨라도 노드 간 블록 전송·동기화와 락 경합이 병목이 될 수 있습니다. 반대로 고객 ID나 업무 키에 따라 요청이 어느 정도 분산되고, 읽기 비중이 높거나 노드별 작업이 비교적 독립적이라면 클러스터 자원을 활용하기 쉬울 수 있습니다. “노드를 추가했는데 왜 빨라지지 않지?”라는 질문에는 SQL 실행 계획뿐 아니라 어떤 블록을 어느 노드가 반복해서 소유·갱신하는지도 포함됩니다.

예를 들어 모든 주문이 하나의 순번 테이블 행을 갱신해 번호를 얻는 구조는 핫스팟(hot spot)을 만들 수 있습니다. 노드가 늘어도 이 한 행을 갱신하려는 요청이 모이면 락과 캐시 이동이 집중될 수 있습니다. 시퀀스의 캐시 설정, 키 생성 전략, 파티셔닝, 업무 단위의 분산 방식을 검토하는 이유입니다. 반대로 “클러스터이니 충돌은 사라진다”라고 생각하면 SQL·스키마 설계에서 보이는 병목을 놓칠 수 있습니다.

Global Cache의 세부 구현과 관찰 지표는 제품·버전에 따라 달라집니다. 따라서 블록 전송이나 노드 간 통신을 추측으로 해석하기보다, 해당 버전의 뷰·통계·관리 도구에서 제공하는 값을 확인해야 합니다. 운영 문서에는 “어떤 수치가 높으면 문제가 있다”는 고정 임계값만 적기보다, 평소 워크로드와 비교해 어떤 변화가 생겼는지, 어떤 SQL·노드·데이터 객체와 함께 나타나는지를 조사하는 절차를 담는 편이 좋습니다.

## 연결과 로드 밸런싱: DB 노드가 여러 개여도 앱은 한 곳만 보면 안 된다

TAC를 구성해도 애플리케이션이 한 노드의 IP만 바라본다면 그 노드 장애 때 연결 오류가 납니다. 클라이언트 연결 계층에는 여러 주소를 전달하고, 장애 시 다른 노드로 재접속할 수 있게 해야 합니다. tbJDBC는 일반 연결 또는 TAC 구성에서 연결이 끊겼을 때 다른 노드에 재연결하는 failover 기능을 제공하며, 설정값에 따라 세션·일부 읽기 전용 ResultSet 복구 범위를 설명합니다. 하지만 드라이버 기능이 있다고 해서 모든 작업이 투명하게 이어지는 것은 아닙니다.

특히 트랜잭션 중 노드 장애가 나면 애플리케이션은 해당 트랜잭션이 커밋됐는지, 롤백됐는지, 응답만 유실됐는지를 확실히 알기 어려운 경우가 있습니다. 이른바 **모호한 결과(ambiguous outcome)** 문제입니다. 사용자는 결제 요청이 실패했다고 보지만 DB에는 이미 주문이 기록되었을 수 있고, 반대로 재시도했을 때 중복 처리될 수 있습니다. 따라서 장애 조치의 핵심은 커넥션을 다시 여는 것만이 아니라, 요청을 다시 보내도 안전한 **멱등성(idempotency)** 을 업무 수준에서 설계하는 데 있습니다.

예를 들어 주문 생성 API에 클라이언트가 만든 idempotency key를 두고, 같은 키로 다시 들어온 요청은 기존 결과를 반환하게 할 수 있습니다. 데이터베이스에는 이 키에 유니크 제약을 두고, 외부 결제·알림과의 순서를 명확히 해야 합니다. TAC는 노드 장애의 영향을 줄이는 기반이지만, 중복 결제·중복 메시지·부분 실패를 막는 업무 규칙을 대신 구현하지는 않습니다.

커넥션 풀도 함께 점검합니다. 풀에 이미 끊긴 연결이 남아 있으면 장애 뒤 첫 요청들이 연속 실패할 수 있습니다. 연결 검증 시점, 최대 수명, 유휴 연결 정리, 재시도 횟수와 백오프, 요청 타임아웃이 DB 장애 감지 시간과 어떻게 맞물리는지 확인합니다. 재시도를 무제한으로 하면 장애 중에 요청과 연결이 폭증할 수 있으므로, 제한 횟수·지수 백오프·서킷 브레이커 같은 상위 보호 장치가 필요할 수 있습니다.

## 장애 조치: 자동 전환과 업무 복구는 다른 문제다

노드·OS·네트워크 장애가 감지되었을 때 클러스터가 정상 노드로 서비스를 유지하거나 복구하려는 것을 장애 조치(failover)라고 합니다. TAC의 Active 노드 구성은 특정 노드 장애가 전체 DB 중단으로 곧바로 이어지는 위험을 줄이는 데 목적이 있습니다. 그러나 실제 사용자 영향은 장애 감지, 클러스터 내부 복구, 클라이언트 재연결, 진행 중 요청의 처리, 상위 로드 밸런서 상태까지 여러 단계의 합입니다.

장애 조치 테스트는 “서버를 껐다가 켜 본다”로 끝나지 않습니다. 어떤 노드가 멈췄는지, 네트워크 단절로 노드가 서로 보이지 않는 상황인지, 공유 스토리지가 느려진 상황인지에 따라 위험이 다릅니다. 특히 네트워크 분할(network partition)에서는 각 노드가 상대방을 장애로 오해할 수 있습니다. 두 노드가 동시에 같은 공유 자원에 쓰기를 계속하면 데이터 손상으로 이어질 수 있으므로, 클러스터가 어떤 방식으로 멤버십과 자원 접근을 통제하는지 이해해야 합니다. 이 영역은 제품 설치 가이드와 인프라 설계를 함께 검토해야 합니다.

장애 훈련에서 확인할 수 있는 질문은 다음과 같습니다.

```text
1. 노드 A 장애 뒤 새 연결은 어느 노드로 얼마나 빨리 가는가?
2. 이미 실행 중인 읽기·쓰기 요청은 각각 어떤 오류 또는 결과를 받는가?
3. 애플리케이션의 재시도는 중복 주문·중복 메시지를 만들지 않는가?
4. 모니터링은 장애 원인·전환 시각·영향 요청을 추적할 수 있는가?
5. 복구된 노드를 다시 클러스터에 넣을 때 데이터·설정·버전 기준은 무엇인가?
```

테스트 환경에서 장애를 재현할 때는 실제 고객 데이터나 운영 네트워크를 사용하지 않고, 격리된 환경과 합의된 절차를 사용해야 합니다. 장애 조치의 성공 여부도 단순 ping 응답이 아니라, 대표 업무 트랜잭션·읽기 경로·쓰기 경로·모니터링 경보·복구 절차까지 확인해야 합니다. 특히 테스트 결과를 “무중단 보장”으로 일반화하지 말고, 검증한 장애 유형·조건·남은 위험을 기록합니다.

## TAC와 다른 HA 전략을 비교하는 관점

TAC는 모든 상황에서 유일한 정답이 아닙니다. 단일 인스턴스와 백업·복구 체계가 비용과 복잡도 측면에서 적합한 서비스도 있고, Primary-Standby와 데이터 복제가 더 단순한 서비스도 있습니다. 읽기 요청이 압도적으로 많고 쓰기 일관성 요구가 다르다면 읽기 복제본을 고려할 수 있습니다. 지역 전체 장애가 중요한 경우에는 다른 센터의 DR 전략이 더 직접적인 답이 될 수 있습니다.

비교할 때 “몇 대를 쓰는가”보다 먼저 RTO(Recovery Time Objective, 복구 목표 시간)와 RPO(Recovery Point Objective, 복구 목표 시점)를 묻습니다. RTO는 장애 뒤 서비스를 어느 정도 시간 안에 복구해야 하는지, RPO는 어느 시점까지의 데이터 손실을 허용하는지를 말합니다. TAC는 같은 클러스터 영역 안의 노드 장애 대응에 도움을 줄 수 있지만, 공유 스토리지 전체 장애나 데이터센터 재해까지 자동으로 해결한다고 가정해서는 안 됩니다. 백업, 아카이브 로그, 복제, 다른 지역의 복구 계획은 별도로 필요할 수 있습니다.

또한 운영 역량도 설계 조건입니다. 클러스터는 단일 인스턴스보다 설치·패치·모니터링·장애 분석이 복잡합니다. 노드 수를 늘릴수록 패치 순서, 버전 호환성, 네트워크 설정, 스토리지 경로, 드라이버·클라이언트 설정을 관리해야 합니다. 가용성 요구가 낮은 내부 도구에 복잡한 클러스터를 도입하면 얻는 이익보다 운영 위험이 커질 수 있습니다. 반대로 핵심 업무라면 클러스터가 주는 장애 격리와 확장성이 투자 가치가 있을 수 있습니다.

## 업무 예시: 배치와 온라인 요청이 함께 있는 결제 시스템

가상의 결제 시스템을 생각해 보겠습니다. 낮에는 온라인 주문이 상태를 조회·갱신하고, 밤에는 정산 배치가 많은 주문을 집계·수정합니다. TAC의 여러 노드는 온라인 요청을 분산 처리할 수 있지만, 정산 배치가 광범위한 테이블을 오래 잠그거나 같은 인덱스 범위를 반복 갱신하면 온라인 요청과 경합할 수 있습니다. 노드를 하나 더 추가해도 잠금과 데이터 블록 경합이 자동으로 사라지지는 않습니다.

이 경우 설계자는 배치를 작은 단위로 나누고, 인덱스·파티션·처리 순서를 검토하며, 온라인 트랜잭션을 짧게 유지하는 방법을 먼저 고려할 수 있습니다. 애플리케이션은 어떤 요청을 어느 노드에 연결했는지보다, 데이터 일관성과 재시도 가능성을 우선 설계합니다. 인프라 팀은 노드별 CPU·메모리·네트워크, 스토리지 지연, 클러스터 통신 상태를 관찰하고, DBA와 개발자는 느린 SQL·락 대기·핫 블록 가능성을 함께 조사합니다.

장애가 나면 커넥션 풀은 다른 노드로 재연결할 수 있어야 하고, 요청 ID와 멱등 키는 사용자가 같은 주문을 다시 눌렀을 때 중복 청구를 피하게 해야 합니다. 이처럼 TAC는 하나의 기능이 아니라 DBMS·애플리케이션·네트워크·스토리지·운영 절차가 만나는 구조입니다. 각 계층의 책임을 분명히 할수록 장애 상황에서 추측 대신 확인 가능한 근거로 대응할 수 있습니다.

## 마무리: 노드를 늘리는 일보다 장애 경계를 설계하는 일

Tibero Active Cluster를 이해하는 핵심은 여러 DB 노드가 있다는 사실보다, 여러 노드가 같은 데이터에 접근할 때 일관성과 장애를 어떻게 다루는지에 있습니다. Global Cache와 공유 스토리지는 클러스터의 기반이고, 드라이버 failover·커넥션 풀·멱등성·장애 훈련은 애플리케이션이 실제 서비스를 계속 제공하기 위한 기반입니다.

도입을 검토한다면 먼저 업무의 RTO·RPO, 현재 병목, 단일 장애 지점, 장애 시 재시도 가능한 작업을 정리하세요. 그 뒤 대표 워크로드와 격리된 장애 시나리오로 연결·전환·복구를 검증하고, 노드·스토리지·네트워크·애플리케이션의 관찰 지표를 함께 마련하면 됩니다. TAC는 복잡도를 없애는 기술이 아니라, 필요한 가용성과 확장성을 얻기 위해 복잡도를 관리 가능한 경계로 나누는 기술입니다.

## 설치 전 설계: 노드 수보다 장애 도메인을 먼저 그린다

TAC 설계를 시작할 때 서버 두 대의 사양부터 정하면 중요한 장애 경계를 놓치기 쉽습니다. 먼저 어떤 구성 요소가 함께 실패할 수 있는지 그려 봅니다. 두 노드가 같은 랙의 전원 장치, 같은 스위치, 같은 스토리지 컨트롤러, 같은 DNS, 같은 로드 밸런서를 공유한다면 노드를 이중화해도 그 공통 요소는 단일 장애 지점이 될 수 있습니다. 반대로 모든 장비를 무조건 분리하면 비용과 운영 복잡도가 커집니다. 서비스의 RTO·RPO와 장애 영향도에 맞춰 어느 계층까지 분리할지 결정해야 합니다.

네트워크는 특히 중요합니다. 클라이언트가 접속하는 public network와 클러스터 노드끼리 상태·캐시 정보를 교환하는 통신 경로는 지연·대역폭·장애 특성이 다를 수 있습니다. 노드 간 네트워크가 느리거나 불안정하면 Global Cache 관련 처리와 장애 감지가 영향을 받을 수 있습니다. 설치 전에는 IP·호스트명·이름 해석, 방화벽 포트, NIC 이중화, 시간 동기화, 패킷 손실 관찰, 네트워크 변경 절차를 인프라 팀과 합의합니다. 실제 요구 포트와 설정은 Tibero 버전 문서를 기준으로 확인해야 합니다.

공유 스토리지도 “공유된다”는 말만으로는 충분하지 않습니다. 데이터 파일·로그 파일·아카이브·백업이 어느 경로에 놓이는지, 디스크 장애를 어떻게 견디는지, 성능이 필요한 I/O와 대역폭이 필요한 I/O를 어떻게 분리하는지, 스토리지 지연이 높을 때 어떤 알림이 발생하는지 확인해야 합니다. 모든 데이터 파일을 여러 노드가 보게 하는 편리함은 공유 스토리지 문제의 영향 범위가 넓어진다는 뜻이기도 합니다. 따라서 스토리지 백업·복구·점검 절차는 TAC와 별개가 아니라 같은 설계의 일부입니다.

## 패치와 구성 변경: 가용성 기능도 변경 관리가 필요하다

클러스터를 운영하면 DBMS 패치, OS 보안 업데이트, 드라이버 교체, 스토리지 펌웨어 변경, 네트워크 설정 변경처럼 노드별로 적용되는 작업이 생깁니다. Active-Active 구조라고 해서 모든 변경을 업무 시간에 안전하게 할 수 있다고 가정하면 안 됩니다. 현재 버전 조합에서 rolling patch가 지원되는지, 노드 간 버전 혼재가 허용되는지, 어떤 작업은 전체 중단이 필요한지 공식 지원 문서와 유지보수 계약 범위에서 확인해야 합니다.

변경 전에는 현재 클러스터 상태와 서비스 연결 분포, 백업 가능 여부, 롤백 기준을 기록합니다. 한 노드를 유지보수 모드로 빼기 전에 새 연결이 다른 노드로 가는지, 기존 연결을 어떻게 드레인(drain)할지, 배치·스케줄러가 해당 노드에 의존하지 않는지 확인합니다. 변경 뒤에는 단순히 노드 프로세스가 올라왔는지뿐 아니라 대표 SQL, 애플리케이션 로그인, 쓰기 트랜잭션, 장애 감지, 모니터링 지표를 점검합니다.

파라미터 변경도 같은 원칙을 따릅니다. TAC 관련 파라미터에는 클러스터 구성 여부, 인스턴스 식별, 통신·자원 관리와 관계된 값이 있을 수 있습니다. 운영 환경에서 값을 한 번 바꿔 보고 결과를 기다리는 방식보다, 변경 목적·대상 노드·재기동 필요 여부·예상 영향·되돌리는 방법을 사전에 기록합니다. 인스턴스 간 설정이 달라져도 되는 값과 반드시 일치해야 하는 값을 구분하지 않으면, 장애가 아닌 설정 불일치 때문에 조사 시간이 길어질 수 있습니다.

## 관찰 가능성: 노드별 지표와 클러스터 전체 지표를 연결한다

단일 DBMS에서는 CPU 사용률, 메모리, 디스크 I/O, 세션 수, 느린 SQL, 잠금 대기 같은 지표를 주로 봅니다. TAC에서는 이것을 노드별로 나누어 보고, 노드 간 불균형도 함께 봐야 합니다. 노드 A의 CPU만 지속적으로 높거나, 특정 노드의 세션·실행 SQL이 유독 많다면 로드 밸런싱 또는 애플리케이션 연결 설정을 의심할 수 있습니다. 반대로 모든 노드가 비슷하게 바쁘면서 공유 스토리지 지연이 높다면 문제의 위치가 다를 수 있습니다.

클러스터 통신·Global Cache 관련 지표, 노드 멤버십 변화, 장애 감지 이벤트, 재연결 실패, 클라이언트 타임아웃도 공통 시간 축에 모아야 합니다. 어느 고객 요청이 실패했는지 확인할 때 애플리케이션 요청 ID, JDBC 연결 오류, DB 세션 정보, 노드 상태, 네트워크 이벤트를 연결할 수 있으면 원인 분석이 빨라집니다. 단, SQL 전문과 바인드 값·개인정보를 모니터링 시스템에 과도하게 남기지 않도록 마스킹과 접근 권한을 설정해야 합니다.

경보는 노드 한 대의 짧은 CPU 상승에 무조건 페이지를 보내는 방식보다, 서비스 영향과 지속 시간·추세를 반영하는 편이 좋습니다. 예를 들어 노드 이탈 이벤트, 모든 노드에서 동시에 증가하는 로그인 실패, 공유 스토리지 오류, 일정 시간 이상 유지되는 연결 대기는 우선 조사 대상일 수 있습니다. 실제 임계값은 하드웨어·워크로드·SLA에 따라 다르므로 다른 회사의 숫자를 그대로 복사하지 않고 정상 상태의 기준선을 먼저 수집합니다.

## 용량 계획: 확장성은 수치가 아니라 가설을 검증하는 과정

TAC의 Active 노드를 늘릴 때는 “노드를 한 대 더 넣으면 처리량이 몇 배가 될까?”라는 가설을 대표 워크로드로 검증해야 합니다. 읽기·쓰기 비율, 동시 세션 수, 데이터 분포, 핫 테이블, 인덱스 구조, 트랜잭션 길이, 네트워크와 스토리지 성능이 결과에 영향을 줍니다. 읽기와 독립적인 작업이 많다면 확장 효과를 기대할 수 있지만, 하나의 카운터 행이나 순차 번호처럼 집중된 자원을 모두가 갱신하면 노드 간 경합이 늘 수 있습니다.

용량 테스트에서는 평균 처리량만 보지 말고 p95·p99 지연, 오류율, 대기 시간, 노드별 부하, 스토리지 I/O, 네트워크 사용량, 캐시 관련 활동을 함께 관찰합니다. 평균이 좋아졌어도 가장 느린 요청이 서비스 목표를 넘거나, 특정 배치 시간에 경합이 급증하면 사용자는 개선을 느끼지 못할 수 있습니다. 테스트 데이터의 크기·분포·동시성·SQL 패턴이 실제와 얼마나 다른지도 결과 해석에 포함합니다.

증설은 하드웨어 작업만이 아닙니다. 새 노드가 클러스터에 들어온 뒤 애플리케이션 연결이 실제로 분산되는지, 백업·모니터링·권한·패치 자동화가 새 노드를 포함하는지, 장애 훈련 시나리오가 달라지는지 확인해야 합니다. 노드를 추가한 뒤에도 모든 요청이 기존 노드로 향한다면 가용성은 일부 좋아질 수 있어도 용량 계획의 목표는 달성하지 못합니다.

클러스터의 효과를 설명할 때는 측정 환경과 기준을 분리합니다. 개발 환경의 단순 조회 성능이 좋아졌다는 결과를 운영의 결제·정산·장애 조치 시간에 그대로 적용할 수는 없습니다. 테스트한 데이터 크기, 동시 사용자 수, SQL 비율, 스토리지 종류, 네트워크 조건, 캐시 초기 상태를 함께 기록해야 다음 증설이나 장애 분석에서도 결과를 비교할 수 있습니다.
