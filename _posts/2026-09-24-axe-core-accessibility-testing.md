화면이 정상적으로 보이고 버튼도 눌린다면 테스트가 끝난 것처럼 느껴지기 쉽습니다. 하지만 마우스를 쓸 수 없는 사용자가 키보드만으로 주문을 완료할 수 있는지, 화면을 읽어 주는 보조 기술이 버튼의 목적을 이해할 수 있는지, 색을 구분하기 어려운 사람이 오류 메시지를 알아볼 수 있는지는 별도의 질문입니다. 기능 테스트가 “요청한 결과가 나왔는가”를 묻는다면, 접근성 테스트는 “서로 다른 조건의 사용자가 그 결과에 도달할 수 있는가”를 묻습니다.

**axe-core**는 HTML 기반 사용자 인터페이스를 분석해 접근성 문제를 자동으로 찾는 오픈 소스 엔진입니다. 브라우저에 실제로 렌더링된 DOM(Document Object Model)을 읽어 이미지 대체 텍스트, 입력 필드 라벨, 버튼 이름, ARIA 속성, 제목 구조, 색 대비처럼 기계적으로 판단할 수 있는 규칙을 검사합니다. 기존 단위 테스트나 Playwright 같은 브라우저 E2E(End-to-End) 테스트에 붙여, 기능 시나리오를 통과한 화면을 접근성 규칙으로도 검사하게 만들 수 있습니다.

다만 자동화가 접근성 인증을 뜻하지는 않습니다. axe-core 프로젝트는 자동으로 찾을 수 있는 WCAG(Web Content Accessibility Guidelines) 이슈의 평균 비율을 약 57%라고 설명하며, 판단이 확실하지 않은 항목은 `incomplete` 결과로 돌려 수동 검토가 필요함을 드러냅니다. 그러므로 목표는 “axe 결과가 0개면 접근성을 보장한다”가 아니라, 반복적으로 찾을 수 있는 결함을 CI에서 빠르게 막고 사람이 확인해야 할 흐름을 남겨 두는 것입니다.

이 글은 특정 서비스에서 접근성 테스트를 직접 수행한 결과가 아닙니다. axe-core, W3C의 접근성 안내와 공개 문서를 바탕으로, QA와 개발 팀이 자동 검사를 어떤 품질 기준으로 연결할지 설명합니다. 법적 적합성이나 장애인의 실제 사용 경험을 도구 한 번 실행으로 판정할 수는 없으므로, 조직의 서비스·국가·계약에 필요한 기준은 접근성 전문가와 별도로 검토해야 합니다.

## 먼저 알아둘 기반 기술: 웹 접근성, DOM, WCAG, 보조 기술

**웹 접근성(web accessibility)** 은 장애 유무나 사용하는 장치·환경이 달라도 웹 콘텐츠와 기능을 이해하고 사용할 수 있게 만드는 특성입니다. 접근성은 디자인의 마지막 장식이나 특정 브라우저 옵션이 아닙니다. 예를 들어 로그인 입력창에 화면상으로만 “이메일”이라는 글자가 있고 프로그래밍 방식의 label이 없다면, 화면 낭독기는 그 입력창의 목적을 제대로 전달하지 못할 수 있습니다. 반대로 `label`과 적절한 입력 타입을 사용하면 브라우저 자동 완성, 모바일 키보드, 음성 입력에도 도움이 됩니다.

**DOM**은 브라우저가 HTML을 트리 구조의 객체로 해석한 결과입니다. 사람이 보는 픽셀 화면과 DOM은 관련 있지만 같지는 않습니다. 화면에 종이비행기 아이콘만 보이는 전송 버튼이 있어도 DOM에 접근 가능한 이름이 없다면 보조 기술에는 “이름 없는 버튼”처럼 보일 수 있습니다. CSS로 `display: none` 처리한 메뉴는 보통 접근성 트리에서도 사라지고, 화면 밖으로 숨긴 안내 문구는 보조 기술에 남을 수 있습니다. 접근성 자동화 도구는 대개 이 렌더링된 구조와 접근성 트리를 기반으로 판단합니다.

**보조 기술(assistive technology)** 은 사용자가 디지털 콘텐츠를 인식하거나 조작하도록 돕는 기술의 묶음입니다. 대표적으로 화면을 음성·점자로 읽는 스크린리더, 키보드만으로 탐색하는 방식, 화면 확대, 음성 제어, 대체 입력 장치가 있습니다. 어떤 사용자는 마우스 대신 Tab과 Enter로 이동하고, 어떤 사용자는 화면의 시각적 순서가 아닌 헤딩·랜드마크·폼 요소 목록으로 이동합니다. 따라서 “내 마우스로는 잘 눌렸다”는 확인은 중요한 시작점일 뿐 충분한 검증은 아닙니다.

**WCAG**는 W3C Web Accessibility Initiative가 제시하는 웹 콘텐츠 접근성 지침입니다. 흔히 인식 가능(Perceivable), 운용 가능(Operable), 이해 가능(Understandable), 견고함(Robust)의 네 원칙인 POUR로 요약합니다. 대체 텍스트나 색 대비는 인식 가능성, 키보드 조작과 충분한 시간은 운용 가능성, 예측 가능한 오류 메시지는 이해 가능성, 표준 HTML·보조 기술 호환은 견고함과 연결됩니다. WCAG에는 A·AA·AAA라는 적합 수준이 있고, 많은 조직이 실무 목표로 AA를 검토하지만 실제 목표 수준은 서비스 성격과 요구사항에 따라 달라집니다.

마지막으로 **ARIA(Accessible Rich Internet Applications)** 를 알아둘 필요가 있습니다. ARIA는 HTML만으로 표현하기 어려운 동적 UI의 역할·상태·관계를 보조 기술에 설명하는 속성 체계입니다. 예를 들어 탭 UI에 선택된 탭 상태를 알릴 수 있습니다. 그러나 ARIA가 일반 HTML을 대체하는 만능 태그는 아닙니다. 실제 `button`을 쓸 수 있는 자리에 클릭 가능한 `div`를 만들고 `role="button"`을 덧붙이면 키보드 동작, 비활성 상태, 폼 동작까지 직접 구현해야 합니다. 가능하면 의미에 맞는 HTML 요소를 먼저 선택하는 것이 더 안전합니다.

## axe-core는 무엇을 검사하고 어떤 결과를 내는가

axe-core는 페이지에 포함된 JavaScript로 실행되거나, 테스트 도구가 브라우저 컨텍스트에 주입해 실행할 수 있습니다. 엔진은 규칙(rule)마다 검사할 DOM 노드를 고르고, 하나 이상의 check를 수행해 결과를 냅니다. 예를 들어 이미지 요소에 대체 텍스트가 있는지, 입력 요소가 접근 가능한 이름을 갖는지, ARIA role과 속성 값의 조합이 유효한지를 확인합니다. 규칙에는 WCAG 버전과 성공 기준, 영향도, 카테고리 같은 태그가 붙어 있어 실행 범위를 선택할 수 있습니다.

결과는 단순한 성공·실패 두 종류보다 세밀합니다. **violations**는 도구가 문제라고 판단한 항목입니다. 각 항목에는 규칙 ID, 영향도(`minor`, `moderate`, `serious`, `critical` 등), 설명, 대상 DOM 노드, 수정 안내 URL이 포함될 수 있습니다. **passes**는 해당 규칙이 적용됐고 통과한 노드이며, **inapplicable**은 검사 대상이 없거나 적용되지 않은 규칙입니다. 특히 중요한 것은 **incomplete**입니다. 도구가 충분한 근거로 통과·실패를 확정하지 못해 사람이 검토해야 하는 경우입니다.

예를 들어 이미지에 `alt` 속성이 비어 있으면 장식 이미지인지 의미 있는 이미지인지 문맥에 따라 판단해야 할 수 있습니다. “더 보기” 링크가 페이지마다 서로 다른 목적을 가질 때, DOM 문자열만으로 의도를 100% 판단하기 어렵습니다. 색 대비는 계산할 수 있어도 배경 이미지·투명도·hover 상태처럼 복잡한 경우와 실제 콘텐츠의 의미 전달은 추가 검토가 필요합니다. `incomplete`를 무시하면 자동화의 한계를 감춘 채 통과 숫자만 남깁니다. 반대로 모든 `incomplete`를 즉시 CI 실패로 만들면 팀이 경고에 익숙해져 검사 자체를 끌 위험이 있습니다.

axe-core의 장점은 기능 테스트 흐름에 자연스럽게 붙는다는 데 있습니다. 주문 버튼을 누르는 Playwright 시나리오가 이미 있다면, 성공 화면이 나타난 직후 접근성 검사를 실행할 수 있습니다. 이렇게 하면 “정상 페이지”만 스캔하는 것이 아니라 로그인 오류, 장바구니 비어 있음, 쿠폰 적용 실패, 모달 열림처럼 상태가 달라진 화면을 각각 검사할 수 있습니다. 동적 UI는 사용자가 보게 되는 상태가 렌더링된 뒤에 검사해야 하며, 숨겨진 메뉴나 닫힌 모달을 한 번 실행으로 검사했다고 가정하면 안 됩니다.

## 기능 E2E 테스트와 접근성 자동 테스트를 연결하는 흐름

Playwright는 실제 브라우저를 자동화해 사용자의 행동과 화면 결과를 확인하는 도구입니다. 접근성 엔진은 브라우저가 렌더링한 페이지에서 실행되어야 하므로 Playwright와 axe-core를 함께 사용하는 조합이 자주 쓰입니다. 여기서 핵심은 “모든 URL을 열어 axe 한 번 실행한다”가 아니라 **업무 시나리오의 의미 있는 화면 상태마다 검사 지점을 정하는 것**입니다.

가령 회원 가입 흐름을 생각해 보겠습니다. 첫 화면에서는 각 입력 필드와 라벨, 필수 항목 표시, 비밀번호 도움말을 확인합니다. 잘못된 이메일을 제출한 뒤에는 오류 메시지가 시각적으로만 빨갛게 보이는지, 해당 입력과 오류 설명이 연결됐는지, 포커스가 문제 위치로 이동하거나 오류 요약으로 안내되는지를 확인해야 합니다. 약관 모달을 열었다면 모달이 열린 동안 포커스가 뒤의 페이지로 빠져나가지 않는지와 닫은 뒤 원래 버튼으로 돌아오는지도 별도 상태입니다. 기능 시나리오 하나가 접근성 검사 하나와 일대일로 대응하지 않을 수 있는 이유입니다.

다음 코드는 Playwright 테스트에 `@axe-core/playwright` 같은 통합 패키지를 사용한다는 가정의 개념 예시입니다. 프로젝트가 사용하는 패키지·버전에 따라 API는 확인해야 하며, 이 코드만 복사해 모든 규칙을 무조건 실패 처리하라는 뜻은 아닙니다.

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('로그인 오류 상태는 기본 접근성 규칙을 만족한다', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('이메일').fill('wrong-address');
  await page.getByRole('button', { name: '로그인' }).click();

  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])
    .analyze();

  expect(results.violations).toEqual([]);
});
```

`withTags`는 모든 규칙을 한꺼번에 실행하기보다, 팀이 우선 삼는 WCAG 범위를 명시하는 방법입니다. 예를 들어 WCAG 2.2 AA 항목까지 검토하려면 해당 버전의 axe-core가 지원하는 태그와 규칙을 확인해야 합니다. 규칙을 임의로 제외할 때도 “테스트가 불안정해서”가 아니라 어떤 컴포넌트의 어떤 상태가 왜 예외인지 이슈·기한·대체 검토 방법을 남겨야 합니다. 예외 목록은 시간이 갈수록 품질 부채가 되기 쉽습니다.

단일 페이지 전체가 아니라 특정 영역만 검사할 수도 있습니다. 외부 결제 위젯이나 제3자 채팅 도구처럼 팀이 즉시 수정할 수 없는 영역이 있을 때, 검사 범위를 명확히 하되 사용자 흐름 전체의 위험을 문서화해야 합니다. 특정 selector를 제외했다고 해서 그 영역이 접근성 책임에서 사라지는 것은 아닙니다. 공급사에 개선을 요청하거나, 대체 경로를 제공하거나, 계약·도입 검토 시 품질 조건에 포함하는 문제가 됩니다.

## 기준선, 실패 정책, 보고서를 어떻게 운영할까

이미 오래 운영된 화면에 axe-core를 처음 적용하면 기존 위반이 한꺼번에 쏟아질 수 있습니다. 이때 모든 결과를 한 PR에서 없애려 하면 기능 개발이 멈추고, 반대로 결과를 숨기면 도입 의미가 없습니다. 실무적인 첫 단계는 **기준선(baseline)** 을 만드는 일입니다. 현재 위반을 페이지·규칙·영향도·담당 컴포넌트별로 기록하고, 새 위반이 추가되는 것은 CI에서 막으며, 기존 위반은 우선순위와 일정에 따라 줄입니다.

영향도는 고정된 업무 우선순위가 아닙니다. `critical`이라는 도구 분류가 고객 영향도·법적 위험·사용 빈도를 자동으로 결정하지는 않습니다. 그러나 로그인·결제·계약·장애 안내 같은 핵심 여정에서 스크린리더 사용자가 버튼을 식별하지 못하거나 키보드로 다음 단계에 갈 수 없다면, 눈에 덜 띄는 장식 문제보다 먼저 다뤄야 할 가능성이 큽니다. QA는 규칙 ID만 전달하는 사람이 아니라 어떤 사용자 여정이 막히는지 재현 조건을 연결하는 역할을 할 수 있습니다.

CI에서는 보통 PR 단계와 정기 점검을 나눕니다. PR에서는 변경된 컴포넌트 또는 핵심 smoke 시나리오에서 violations가 새로 생기지 않는지 빠르게 봅니다. 매일 또는 릴리스 전에는 더 넓은 계정·권한·언어·오류 상태를 순회해 보고서를 만듭니다. 시각 회귀 테스트와도 연결할 수 있지만, 스크린샷이 같다고 접근성 트리가 같다는 보장은 없고, axe가 통과했다고 디자인의 정보 계층이 이해하기 쉬운 것도 아닙니다. 각 도구의 질문을 혼동하지 않는 것이 좋습니다.

보고서는 개발자가 수정할 수 있는 정보로 구성합니다. 규칙명만 “color-contrast”라고 쓰기보다, 페이지 URL 또는 시나리오, 대상 selector, 현재 접근 가능한 이름 또는 색상 값, 예상되는 사용자 영향, 관련 컴포넌트 owner, 재검사 방법을 남깁니다. 다만 selector는 CSS 변경에 약하므로 가능하면 안정적인 테스트 ID와 사람이 읽을 수 있는 UI 설명을 함께 둡니다. 로그에 사용자의 개인정보나 비밀값이 섞이지 않도록 테스트 계정과 마스킹도 별도로 관리해야 합니다.

## 자동 검사로 대신할 수 없는 수동 검토

첫째, **키보드만으로 끝까지 이동하는 경험**은 사람이 확인해야 합니다. Tab 키를 눌렀을 때 포커스 순서가 화면의 논리적 흐름을 따르는지, 포커스 위치가 눈에 보이는지, 드롭다운·모달·날짜 선택기에서 Escape와 방향키가 기대대로 작동하는지 살펴야 합니다. DOM 순서가 시각적 CSS 배치와 달라지면 axe가 특정 규칙 위반을 찾지 못해도 사용자는 엉뚱한 순서로 이동할 수 있습니다.

둘째, **이름과 설명의 품질**은 문자열 존재 여부를 넘습니다. `aria-label="버튼"`은 이름이 있다는 검사에는 통과할 수 있어도, 주문 취소인지 주소 검색인지 알려 주지 않습니다. 대체 텍스트도 “이미지”보다 “9월 한정 할인 배너, 최대 30%”처럼 해당 이미지가 전달해야 하는 정보를 담아야 합니다. 반대로 순전히 장식인 이미지에 장황한 텍스트를 넣으면 스크린리더 사용자의 탐색을 방해할 수 있습니다. 이 판단에는 화면의 업무 맥락이 필요합니다.

셋째, **오류 복구와 시간 제한**을 봐야 합니다. 세션 만료 안내가 나타났을 때 무엇이 사라졌는지, 입력한 주문 정보가 보존되는지, 재로그인 뒤 어디로 돌아가는지, CAPTCHA나 본인 인증이 대체 수단을 갖는지는 규칙 목록만으로 충분히 알기 어렵습니다. 자동 테스트는 오류 상태 화면을 열어 구조를 검사할 수 있지만, 실제 사용자가 이해하고 복구할 수 있는지는 시나리오 기반 검토와 사용성 테스트가 더 적합합니다.

넷째, 대표적인 스크린리더와 브라우저 조합을 선정해 핵심 흐름을 확인하는 것이 좋습니다. 모든 기기 조합을 완벽히 재현할 수는 없으므로 지원 대상과 위험을 정해야 합니다. W3C 지침·브라우저 표준·도구 지원 범위는 계속 바뀌며, ARIA 속성이 사양상 유효해도 실제 보조 기술 조합에서 기대대로 읽히지 않을 수 있습니다. 자동 도구 결과와 실제 보조 기술 사용을 경쟁시키지 말고 서로 다른 빈틈을 메우게 해야 합니다.

## 컴포넌트 시스템과 접근성 회귀를 줄이는 방법

접근성 결함을 페이지마다 고치기 시작하면 같은 버튼·모달·입력 컴포넌트의 문제가 반복됩니다. 재사용 가능한 디자인 시스템이나 컴포넌트 라이브러리가 있다면, 기본 버튼은 실제 `button` 요소를 쓰고, Input은 label 연결을 강제하며, Dialog는 포커스 관리와 닫기 동작을 기본 제공하도록 만드는 편이 효과적입니다. 한 번 올바르게 만든 공통 컴포넌트는 수십 페이지의 수정 비용을 줄일 수 있습니다.

여기서 “공통 컴포넌트가 통과했으니 페이지 테스트는 불필요하다”는 결론도 조심해야 합니다. 페이지가 컴포넌트를 어떤 순서와 문구로 조합하는지, 로딩·오류·권한 없음 상태에서 무엇을 숨기고 보여 주는지에 따라 새로운 문제가 생깁니다. 컴포넌트 수준에서는 고정된 상태의 규칙을 빠르게 검사하고, E2E 수준에서는 실제 사용자 여정을 검사하며, 수동 검토에서는 의미·맥락·보조 기술 경험을 보는 식으로 층을 나눌 수 있습니다.

새 컴포넌트를 도입할 때 확인할 최소 질문을 정해 두는 것도 도움이 됩니다. 기본 HTML 요소로 해결 가능한가? 키보드로 열고 닫고 선택할 수 있는가? 포커스가 어디에서 어디로 이동하는가? 상태 변화가 보조 기술에 알려지는가? 오류 메시지와 입력 항목은 연결되는가? 밝은·어두운 배경과 비활성 상태에서 대비가 유지되는가? 이 질문을 디자인 리뷰와 PR 템플릿에 작은 체크 항목으로 넣으면, 테스트가 실패한 뒤에만 접근성을 떠올리는 흐름을 줄일 수 있습니다.

## 결과를 고치는 순서: 규칙 ID보다 사용자 막힘을 먼저 본다

접근성 리포트가 나오면 규칙 ID 수를 줄이는 데만 집중하기 쉽습니다. 그러나 같은 열 개의 violation이라도 사용자가 겪는 위험은 다릅니다. 결제 버튼에 이름이 없어 스크린리더 사용자가 다음 단계로 갈 수 없는 문제와, 관리 화면의 덜 중요한 보조 문구에 문서 언어 속성이 누락된 문제는 모두 수정 대상이지만 긴급도는 다를 수 있습니다. QA·개발·디자인이 함께 볼 때는 도구의 impact 값, 노출된 사용자 여정, 영향 받는 사용자, 수정 난이도와 재발 가능성을 같이 기록하는 편이 좋습니다.

가장 먼저 확인할 후보는 보통 **조작 불가**와 연결되는 항목입니다. 키보드 포커스가 보이지 않거나, 포커스가 모달 뒤로 빠지거나, 클릭 가능한 요소가 키보드로 실행되지 않으면 사용자는 흐름 자체를 완료할 수 없습니다. 그다음은 입력·오류·버튼의 이름처럼 업무 결정을 할 때 필요한 정보를 잃게 하는 문제입니다. 색 대비와 헤딩 순서도 결코 사소하지 않지만, 같은 릴리스에서 무엇을 먼저 고칠지 판단할 때는 “이 사용자는 어디에서 멈추는가”로 번역해 보는 것이 도움이 됩니다.

수정 티켓에는 자동 결과를 그대로 복사하기보다 재현 가능한 문장을 남깁니다. 예를 들어 `button-name` 위반이라면 “주문 취소 아이콘 버튼이 접근 가능한 이름을 갖지 않아 스크린리더 요소 목록에서 목적을 알 수 없음”처럼 적습니다. 대상 화면의 상태, 역할, 필요한 변경의 방향, 다시 실행할 테스트도 함께 둡니다. 이렇게 하면 프론트엔드 개발자가 CSS selector만 보고 추측하지 않아도 되고, 디자이너는 아이콘만으로 의도를 전달하는 화면 설계가 어디에서 문제가 되는지 이해할 수 있습니다.

**false positive(오탐)** 처리는 특히 조심해야 합니다. axe-core는 명확히 판별 가능한 규칙을 중심으로 설계됐지만 버그, 브라우저 차이, 프레임워크가 만든 DOM, 팀의 특수한 UI 때문에 결과가 기대와 다를 수 있습니다. 한 규칙을 전역적으로 끄기 전에 해당 노드가 실제 보조 기술에서 어떻게 읽히는지 확인하고, 도구 버전·규칙 설명·최소 재현 예제를 검토해야 합니다. 예외가 필요하다면 범위를 한 컴포넌트와 한 규칙으로 좁히고, 사유·검토일·제거 조건을 남기는 편이 전체 신호를 버리는 것보다 낫습니다.

반대로 자동 검사가 통과했지만 수동 테스트에서 결함이 나오면 “도구가 쓸모없다”가 아니라 검사 질문이 달랐다고 받아들이는 편이 좋습니다. 예를 들어 모달 안에서 포커스가 순환하는지, 자동 완성 목록을 화살표 키로 탐색할 수 있는지, 오류 문구가 실제로 이해되는지는 규칙 검사보다 사용자 상호작용에 가깝습니다. 해당 결함을 컴포넌트 테스트·E2E 테스트·수동 회귀 목록 중 어디에 남길지 결정하면 다음 릴리스에서 같은 문제를 다시 찾기 쉬워집니다.

## 화면 상태와 테스트 데이터가 접근성 결과를 바꾼다

접근성 테스트도 테스트 데이터에 영향을 받습니다. 주문 목록이 비어 있을 때만 보이는 빈 상태 화면, 재고가 없을 때만 나타나는 대체 구매 안내, 본인 인증이 실패했을 때의 재시도 모달, 관리자가 아닌 사용자에게 보이는 권한 없음 페이지는 일반적인 happy path에서 놓치기 쉽습니다. 각 상태가 DOM을 다르게 만들기 때문에, 기본 페이지 한 장을 검사했다고 해서 모든 중요한 UI가 검사된 것은 아닙니다.

특히 국제화(i18n, internationalization)된 서비스는 언어·길이·방향 차이도 확인해야 합니다. 한국어에서는 한 줄인 버튼 문구가 독일어·프랑스어·영어에서는 줄바꿈될 수 있고, 숫자·날짜·통화 표현이 달라집니다. 자동 도구는 `lang` 속성 같은 구조적 힌트를 확인할 수 있지만, 번역된 문장이 실제로 명확한지나 긴 문구 때문에 포커스 순서가 어색해졌는지는 별도 검토가 필요합니다. 지원 언어가 많다면 모든 조합을 매 PR에서 실행하기보다 핵심 언어 smoke test와 정기적인 전체 언어 검사를 나눌 수 있습니다.

권한도 화면 상태를 바꿉니다. 운영자에게만 보이는 삭제 버튼이 일반 사용자 DOM에 숨겨져 있는지, 권한 부족 안내가 heading과 페이지 제목을 갖는지, 비활성화된 버튼이 왜 비활성인지 설명되는지 확인해야 합니다. `disabled` 속성은 마우스 클릭을 막을 수 있지만, 사용자가 다음 행동을 알게 해 주지는 않습니다. “배송지를 선택하면 결제할 수 있습니다” 같은 안내가 연결돼 있어야 오류가 아니라 다음 단계로 읽힙니다. 이처럼 테스트 데이터와 권한 매트릭스는 보안 테스트와 접근성 테스트 모두의 입력입니다.

UI 라이브러리가 portal을 사용해 모달을 `body` 마지막에 렌더링하거나, Shadow DOM 안에 컴포넌트를 넣거나, iframe으로 외부 위젯을 표시할 때는 검사 단위가 달라집니다. axe-core는 렌더링된 문서를 기준으로 동작하지만 iframe 내부는 해당 프레임의 문서에서 별도 실행해야 할 수 있고, 닫힌 Shadow DOM이나 교차 출처 iframe은 도구 접근에 제한이 생길 수 있습니다. 테스트 설계 단계에서 페이지 구성도를 보고 “어느 코드가 어느 DOM을 소유하는가”를 파악하지 않으면, 검사 결과가 없는 영역을 통과로 오해하기 쉽습니다.

## 처음 도입하는 팀을 위한 작은 운영 절차

첫 주에는 서비스의 모든 화면을 목표로 잡지 말고, 로그인 또는 주문처럼 핵심 여정 하나를 선택합니다. 그 여정에서 기본 상태·입력 오류 상태·성공 상태·모달 상태를 목록으로 만들고, 각 상태를 Playwright로 재현할 수 있는지 확인합니다. 그다음 axe-core를 붙여 WCAG A·AA 태그 범위의 violations를 저장합니다. 이 단계에서 처음 나온 수치를 품질 점수로 비교하기보다, 어떤 규칙과 화면이 많은지를 이해하는 기준선으로 씁니다.

둘째 주에는 새 위반 방지 정책을 정합니다. 기존 위반이 20개라면 그 20개를 허용 목록에 영구 보관하는 대신, 21번째가 생기는 PR을 막는 식이 아닙니다. 기존 결과를 명시적으로 기준선 파일이나 이슈 목록에 연결하고, 변경된 컴포넌트에서 새로 생긴 violation을 감지하도록 합니다. 기준선의 항목도 해결되면 반드시 제거해야 하며, 팀이 “통과시키기 위한 ignore”를 쉽게 추가하지 못하게 리뷰 기준을 둡니다.

셋째 주에는 30분짜리 수동 점검을 정례화할 수 있습니다. 마우스를 치우고 Tab·Shift+Tab·Enter·Escape로 핵심 흐름을 끝까지 이동해 보고, 지원 대상 중 하나의 스크린리더와 브라우저로 제목·버튼·오류를 읽어 봅니다. 전문 접근성 감사의 완전한 대체는 아니지만, 자동 도구가 보지 못하는 큰 사용성 결함을 조기에 발견하는 데 도움이 됩니다. 발견된 항목은 도구 결과와 한 목록에 섞기보다 “자동 위반”, “수동 키보드”, “보조 기술 검토”로 출처를 구분해 관리하면 원인과 재검증 방법이 선명해집니다.

마지막으로 변화 자체를 측정합니다. CI에서 검사한 시나리오 수, 새 violation 수, 기준선에서 해결한 수, critical·serious 항목의 평균 해결 시간, 수동 점검에서 발견된 반복 결함을 보면 도입이 실제로 개선을 만드는지 알 수 있습니다. 단, 지표를 팀 평가의 벌점으로만 쓰면 숨기기와 제외가 늘 수 있습니다. 목표는 숫자를 낮추는 것이 아니라, 더 많은 사용자가 핵심 업무를 막힘없이 수행하게 하는 것입니다.

## 마무리

axe-core는 접근성을 “출시 막판에 눈으로 한번 보는 항목”에서 반복 가능한 품질 신호로 바꿔 줍니다. 그러나 도구가 찾은 violation은 수정해야 할 후보이고, 도구가 찾지 못한 항목은 안전하다는 증명이 아닙니다. WCAG 범위를 명시하고, 실제로 열린 화면 상태에서 검사하며, 새 결함은 막고 기존 결함은 계획적으로 줄이고, 키보드와 보조 기술의 실제 경험을 수동 검토로 보완하는 흐름이 중요합니다.

처음에는 로그인·가입·결제·검색처럼 사용 빈도와 실패 비용이 큰 여정 하나를 고르는 것이 좋습니다. 그 여정의 기본 상태와 오류·모달 상태에 axe 검사를 연결하고, violations·incomplete·수동 점검 결과를 분리해 기록해 보세요. 이 작은 기준선이 쌓이면 접근성은 별도 프로젝트가 아니라 테스트 자동화와 컴포넌트 설계에 자연스럽게 포함될 수 있습니다.
