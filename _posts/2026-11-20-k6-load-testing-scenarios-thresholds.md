## 먼저 답하기

### Q. 부하 테스트는 "동시 사용자 몇 명"만 정하면 되나요?

A. 그렇지 않습니다. 같은 "100명"이라도 서버가 느려졌을 때 요청을 계속 보내는 방식과 요청 속도를 줄이는 방식은 결과가 전혀 다릅니다. 가상 사용자(VU, Virtual User) 수를 고정하면 응답이 느려질수록 시간당 요청 수가 줄어듭니다. 반면 초당 도착 건수를 고정하면 서버가 느려져도 요청이 계속 들어옵니다. 그래서 부하 테스트를 설계할 때는 사용자 수보다 "어떤 패턴으로 요청이 도착하는가"와 "무엇을 합격으로 보는가"를 먼저 정해야 합니다. k6는 이 두 가지를 JavaScript 코드의 `scenarios`와 `thresholds`로 선언할 수 있게 해 주는 부하 테스트 도구입니다.

### Q. 부하 테스트가 끝나면 무엇을 보고 통과를 판단하나요?

A. 눈으로 그래프를 보고 "괜찮아 보인다"고 판단하면 팀마다 결론이 달라집니다. k6의 Threshold(임계값)는 "p95 응답 시간이 500ms 미만이고 오류율이 1% 미만"처럼 기준을 코드에 적어 두고, 기준을 어기면 테스트 프로세스가 실패 종료 코드로 끝나게 합니다. 이렇게 하면 CI(지속적 통합) 파이프라인에서 자동 판정을 할 수 있습니다. 다만 기준 숫자는 도구가 알려 주지 않습니다. 서비스 수준 목표(SLO, Service Level Objective)나 업무 요구에서 가져와야 합니다. 이 글의 수치는 설명을 위한 가정이며, 직접 측정한 결과가 아닙니다.

## 먼저 알아둘 기반 기술

이 절은 본문에서 설명 없이 쓰이는 개념을 가장 밑바닥부터 순서대로 정리합니다. 앞 소절의 개념을 뒤 소절이 이어받으므로 처음 접한다면 위에서부터 읽는 편이 좋습니다. 각 소절 끝에는 그 개념이 본문의 어느 절에서 다시 쓰이는지 적어 두었고, 섹션 마지막에 전체 연결 지도를 표로 정리했습니다.

### HTTP 요청과 응답, 상태 코드

HTTP(HyperText Transfer Protocol, 하이퍼텍스트 전송 규약)는 웹 브라우저나 앱이 서버에 무언가를 요청하고 답을 받는 약속입니다. 식당에 비유하면 손님이 주문서(요청)를 내고 주방이 음식과 영수증(응답)을 돌려주는 과정입니다. 요청에는 `GET`(조회), `POST`(생성) 같은 메서드와 주소(URL), 헤더가 들어가고, 응답에는 상태 코드와 본문이 들어갑니다. 상태 코드는 세 자리 숫자로 결과를 요약합니다. `200`은 성공, `201`은 생성 성공, `401`은 인증 실패, `500`은 서버 내부 오류를 뜻합니다. 본문은 보통 JSON(JavaScript Object Notation, 키와 값으로 이뤄진 텍스트 데이터 형식)으로 오고, 인증이 필요한 API는 `Authorization: Bearer <토큰>` 같은 헤더로 "로그인한 사용자"임을 증명합니다.

```bash
curl -i https://staging.example.com/health
# HTTP/1.1 200 OK
# Content-Type: application/json
# {"status":"UP"}
```

이 글에 이 개념이 필요한 이유는 k6가 측정하는 거의 모든 값이 "HTTP 요청 하나가 얼마나 걸렸고 어떤 상태 코드로 끝났는가"에서 출발하기 때문입니다. 상태 코드와 본문의 차이를 모르면 "200인데 왜 실패로 봐야 하는가"를 이해하기 어렵고, 토큰 헤더를 모르면 로그인 흐름을 왜 따로 설계하는지 감이 오지 않습니다. 또한 사람이 응답을 읽고 다음 버튼을 누르기까지의 간격, 즉 생각 시간(think time)도 요청과 요청 사이의 빈 시간이라는 점에서 이 개념 위에 있습니다. 이 개념은 아래 「가장 작은 k6 스크립트」 절에서 `http.get`과 상태 코드 검사로, 「현실적인 시나리오 작성」 절에서 토큰 헤더로, 「Check를 잘 설계하는 법」 절에서 상태 코드와 본문을 함께 검사하는 근거로, 「페이싱과 생각 시간」 절에서 요청 간격 설계로 쓰입니다.

### 응답 시간 분포: 평균, 백분위, 처리량, 오류율

응답 시간은 요청을 보낸 뒤 응답을 다 받기까지 걸린 시간이고, 처리량(throughput)은 단위 시간당 처리한 요청 수(예: 초당 50건, `50/s`), 오류율은 전체 요청 중 실패한 비율입니다. 응답 시간은 하나의 숫자가 아니라 분포입니다. 요청 100개 중 95개가 50ms, 5개가 2,000ms라면 평균은 약 147ms로 "괜찮아" 보이지만, 5명의 사용자는 2초를 기다렸습니다. 그래서 백분위(percentile)를 씁니다. p95(95번째 백분위)는 "요청을 빠른 순서로 줄 세웠을 때 95% 지점의 값"으로, p95가 300ms라면 요청의 95%가 300ms 이내에 끝났다는 뜻입니다. 시험 점수에 비유하면 평균 점수보다 "하위 5% 학생의 점수"를 따로 보는 것과 비슷합니다.

이 글에서 합격 기준은 대부분 백분위와 비율로 표현됩니다. `p(95)<500`이나 `rate<0.01` 같은 표현이 무엇을 뜻하는지 모르면 Threshold 문법 자체가 암호처럼 보입니다. 또 처리량과 응답 시간이 서로 영향을 준다는 점, 즉 서버가 느려지면 같은 사용자 수로도 처리량이 떨어질 수 있다는 점은 뒤에서 닫힌 모델과 열린 모델을 비교하는 출발점이 됩니다. 이 개념은 아래 「가장 작은 k6 스크립트」 절에서 결과 요약을 읽는 법으로, 「Threshold로 합격 기준을 코드화하기」 절에서 `p(95)`·`rate` 조건으로, 「결과 해석에서 자주 생기는 오해」 절에서 "평균이 빠르면 괜찮다"는 오해를 바로잡는 근거로, 「결과 보고서에 남길 내용」 절에서 보고할 숫자로 쓰입니다.

### 동시성, 대기열, 서버 자원의 포화

동시성(concurrency)은 같은 시점에 처리 중인 요청의 수입니다. 서버는 요청을 처리할 스레드, 데이터베이스 연결을 미리 만들어 두고 나눠 쓰는 커넥션 풀(connection pool), CPU와 메모리 같은 자원을 한정된 양만 갖고 있습니다. 자원이 모두 사용 중이면 새 요청은 대기열(queue)에서 순서를 기다리고, 기다린 시간만큼 응답 시간이 늘어납니다. 은행 창구가 세 개뿐인데 손님이 계속 들어오면 창구 직원의 업무 속도는 같아도 번호표 대기 시간이 길어지는 것과 같습니다. 이 상태를 포화(saturation)라고 합니다. 처음 몇 분은 캐시(cache, 자주 쓰는 데이터를 빠른 메모리에 보관해 두는 장치)가 비어 있어 느리고, 캐시가 채워진 뒤에는 빨라지는 현상도 같은 자원 관점에서 이해할 수 있습니다.

이 개념은 부하 테스트에서 "왜 느려지는가"를 설명하는 바탕입니다. 요청이 도착하는 속도가 처리 속도를 넘으면 대기열이 쌓이고, 요청을 보내는 쪽이 응답을 기다렸다가 다음 요청을 보내는지 아닌지에 따라 결과가 달라집니다. 그리고 포화는 서버만의 일이 아닙니다. 요청을 만들어 내는 부하 생성기(load generator)도 CPU, 메모리, 네트워크 소켓(연결 하나를 표현하는 운영체제 자원)이 한정되어 있으므로 먼저 포화될 수 있습니다. 이 개념은 아래 「닫힌 모델과 열린 모델: Executor 선택」 절에서 느려진 서버에 요청이 쌓이는 이유로, 「서버 지표와 함께 읽기」 절에서 스레드·커넥션 풀·락 대기를 보는 이유로, 「데이터 상태와 사전 준비」 절에서 캐시 워밍업으로, 「부하 생성기 자체를 신뢰하는 조건」 절에서 생성기 자원 점검으로 쓰입니다.

### 부하 테스트와 SLO가 무엇이고 왜 필요한가

부하 테스트(load testing)는 시스템에 일정한 요청을 보내면서 응답 시간, 오류율, 처리량이 요구 수준을 만족하는지 확인하는 테스트입니다. 기능 테스트가 "한 번 호출하면 올바른 결과가 나오는가"를 본다면, 부하 테스트는 "많이, 오래, 갑자기 호출해도 허용 범위 안에 있는가"를 봅니다. 기능이 모두 맞아도 동시 요청이 늘어나면 데이터베이스 연결이 고갈되거나, 락 경합이 생기거나, 캐시가 비어 있을 때 지연이 커지는 문제가 드러납니다. 이런 문제는 단위 테스트로는 보이지 않습니다. 이때 "요구 수준"을 숫자로 적은 것이 SLO(Service Level Objective, 서비스 수준 목표)입니다. 예를 들어 "주문 생성 API는 한 달 동안 요청의 95%가 800ms 이내에 응답하고, 오류율은 1% 미만"처럼 적습니다. 놀이공원의 "대기 시간 30분 이내"라는 운영 목표와 비슷합니다.

이 글은 "무엇을 합격으로 볼 것인가"를 코드로 적는 방법을 다루는데, 그 숫자는 도구가 아니라 SLO와 업무 요구에서 옵니다. SLO 개념이 없으면 Threshold 숫자가 왜 500ms인지 설명할 수 없고, 스모크·부하·스트레스 같은 테스트 유형이 서로 다른 질문에 답한다는 점도 흐려집니다. 이 개념은 아래 「테스트 유형별 설계」 절에서 유형마다 다른 합격 질문으로, 「업무 예시: 주문 API 릴리스 전 검증 계획」 절에서 SLO를 Threshold로 옮기는 과정으로 쓰입니다.

### CI, 종료 코드, 환경 변수

CI(Continuous Integration, 지속적 통합)는 코드가 바뀔 때마다 빌드와 테스트를 자동으로 실행하는 파이프라인입니다. 파이프라인은 각 단계의 성공·실패를 프로그램의 종료 코드(exit code)로 판단합니다. 관례상 `0`은 성공, 그 밖의 값은 실패입니다. 셸에서는 직전 명령의 종료 코드를 `$?`로 볼 수 있습니다. 환경 변수(environment variable)는 프로그램 밖에서 주입하는 설정 값으로, 같은 스크립트를 개발·스테이징에서 주소만 바꿔 실행하거나 비밀번호를 코드에 쓰지 않고 전달할 때 씁니다.

```bash
BASE_URL=https://staging.example.com ./run-test.sh
echo $?   # 0이면 성공, 0이 아니면 파이프라인이 이 단계를 실패로 처리
```

이 글에서 부하 테스트를 "사람이 그래프를 보고 판단하는 일"이 아니라 "자동으로 판정되는 단계"로 만들 수 있는 근거가 바로 종료 코드입니다. 또 예시 스크립트마다 등장하는 `__ENV.BASE_URL`, `__ENV.LT_PASSWORD`는 환경 변수를 읽는 코드입니다. 이 개념을 모르면 Threshold 실패가 왜 배포를 막는지, 비밀번호를 왜 스크립트에 쓰지 말라고 하는지 연결되지 않습니다. 이 개념은 아래 「가장 작은 k6 스크립트」 절에서 `-e BASE_URL=...` 실행 옵션으로, 「CI에 연결하기」 절에서 종료 코드와 요약 파일로, 「스크립트 품질 점검 목록」 절에서 비밀 값 관리 항목으로 쓰입니다.

### k6가 무엇인가

k6는 Grafana Labs가 관리하는 오픈소스 부하 테스트 도구입니다. 테스트 스크립트를 JavaScript로 작성하지만, 실행 엔진은 Go로 만들어져 있어 Node.js에서 도는 코드가 아닙니다. 따라서 npm 패키지를 그대로 가져다 쓰는 방식이 아니라 k6가 제공하는 모듈(`k6/http`, `k6/metrics` 등)을 사용합니다. 스크립트는 명령줄에서 `k6 run script.js`처럼 실행하며, 결과는 터미널 요약, JSON 파일, 외부 시계열 저장소 등으로 내보낼 수 있습니다. 기존의 GUI(Graphical User Interface, 그래픽 화면) 중심 도구와 달리 스크립트가 텍스트 파일이므로 Git으로 변경 이력을 관리하고 코드 리뷰를 받을 수 있다는 점이 장점입니다. 요리에 비유하면 손으로 그때그때 만드는 대신 레시피를 문서로 남겨 누구나 같은 맛을 재현하게 하는 셈입니다.

이 글의 모든 예제는 k6 스크립트이므로, "JavaScript 문법을 쓰지만 브라우저나 Node.js가 아니다"라는 점을 먼저 알아야 `import http from 'k6/http'` 같은 코드가 낯설지 않습니다. 또한 k6가 측정하는 값은 요청을 보내는 쪽, 즉 클라이언트에서 본 값이라는 점도 중요합니다. 서버 내부에서 무슨 일이 일어났는지는 k6가 직접 알려 주지 않습니다. 이 개념은 아래 「가장 작은 k6 스크립트」 절에서 첫 실행과 결과 요약으로, 「서버 지표와 함께 읽기」 절에서 클라이언트 관측의 한계로 쓰입니다.

### 스크립트의 생명주기

k6 스크립트는 네 단계로 이뤄집니다. 먼저 init 단계는 스크립트 최상위 코드로, 모듈을 불러오고 옵션과 데이터를 준비합니다. 다음으로 `setup()`은 테스트 시작 전에 한 번 실행되어 데이터를 준비하고, 반환값을 이후 단계에 넘깁니다. `default` 함수(또는 시나리오별로 지정한 함수)는 각 VU가 반복해서 실행하는 본체입니다. 마지막으로 `teardown()`은 테스트가 끝난 뒤 한 번 실행되어 정리 작업을 합니다. 공연에 비유하면 init은 무대 설치, `setup()`은 리허설 직전 한 번의 점검, `default`는 매회 반복되는 공연, `teardown()`은 철수입니다.

```javascript
// init: 모듈과 옵션 준비 (VU마다 한 번)
export function setup() { /* 한 번: 토큰 발급 */ return { token: 'abc' }; }
export default function (data) { /* 반복: data.token 사용 */ }
export function teardown(data) { /* 한 번: 정리 */ }
```

이 구분을 모르면 "로그인을 `default`에서 매번 하느라 로그인 서버만 시험한 꼴이 되었다"처럼, 의도하지 않은 부하를 만들 수 있습니다. 또 init 단계 코드는 VU마다 실행되므로, 큰 파일을 init에서 그냥 읽으면 VU 수만큼 메모리를 쓰게 됩니다. 이 개념은 아래 「현실적인 시나리오 작성」 절에서 `setup()`으로 토큰을 한 번만 받고 `SharedArray`로 데이터를 공유하는 이유로, 「데이터 상태와 사전 준비」 절에서 워밍업과 측정 시나리오를 나누는 바탕으로 쓰입니다.

### VU, Iteration, Scenario, Executor

VU(Virtual User, 가상 사용자)는 스크립트를 반복 실행하는 가상 실행 단위이고, Iteration(반복)은 `default` 함수를 한 번 실행하는 것입니다. Scenario(시나리오)는 부하 패턴과 실행 함수를 묶은 단위이며, Executor(실행기)는 시나리오가 VU와 반복을 언제 얼마나 시작할지 정하는 스케줄 방식입니다. 쇼핑몰에 비유하면 VU는 손님 한 명, Iteration은 손님이 장바구니를 한 번 담는 행동, Scenario는 "평일 오전 조회 트래픽", Executor는 "매장 안 손님 수를 10명으로 유지"하거나 "1초에 손님 5명씩 입장"시키는 입장 규칙입니다.

| 용어 | 뜻 | 쉬운 예 |
| --- | --- | --- |
| VU (Virtual User) | 스크립트를 반복 실행하는 가상 실행 단위 | 쇼핑몰에 접속한 손님 한 명 |
| Iteration | `default` 함수를 한 번 실행하는 것 | 손님이 장바구니를 한 번 담는 행동 |
| Scenario | 부하 패턴과 실행 함수를 묶은 단위 | 평일 오전 조회 트래픽 |
| Executor | 시나리오가 VU와 반복을 스케줄하는 방식 | 인원 고정 또는 도착률 고정 |

이 글의 핵심 주장인 "사용자 수보다 도착 패턴을 먼저 정하라"는 바로 Executor 선택의 문제입니다. 앞 소절의 대기열 개념과 합치면, 인원을 고정하는 Executor는 서버가 느려질 때 요청을 덜 보내고, 도착률을 고정하는 Executor는 계속 보낸다는 차이가 나옵니다. 이 개념은 아래 「닫힌 모델과 열린 모델: Executor 선택」 절에서 Executor 비교와 `dropped_iterations` 해석으로, 「테스트 유형별 설계」 절에서 스트레스 테스트의 `ramping-arrival-rate`로, 「페이싱과 생각 시간」 절에서 VU 기반 페이싱의 한계로 쓰입니다.

### Check, Threshold, Metric, Tag

Metric(메트릭)은 k6가 수집하는 측정값으로, `http_req_duration`(요청 지연), `http_req_failed`(실패 비율), `checks`(Check 성공 비율) 같은 내장 메트릭과 직접 만드는 사용자 정의 메트릭이 있습니다. Check(검사)는 개별 응답이 기대와 맞는지 확인하는 함수이고, Threshold(임계값)는 메트릭 전체에 거는 합격 기준입니다. Tag(태그)는 요청에 붙이는 이름표로, `{ name: 'list_orders' }`처럼 붙이면 같은 메트릭을 이름표별로 나눠 볼 수 있습니다. 이름표마다 시간 순서로 쌓이는 값의 줄을 시계열(time series)이라고 하는데, 이름표 값이 무한히 많아지면 시계열도 무한히 늘어납니다. 학교 시험에 비유하면 Check는 문항별 채점, Metric은 성적표, Threshold는 "평균 60점 이상이면 통과" 같은 합격선, Tag는 과목 구분입니다.

여기서 Check와 Threshold를 혼동하기 쉽습니다. Check는 개별 응답을 검사하고 결과를 `checks`라는 메트릭에 기록할 뿐, 실패해도 테스트를 중단하거나 실패로 끝내지 않습니다. 테스트의 합격·불합격은 Threshold가 결정합니다. 즉 Check로 "무엇이 틀렸는지 기록"하고 Threshold로 "그 비율이 허용 범위를 넘으면 불합격 처리"하는 두 단계가 필요합니다. 이 개념은 아래 「Threshold로 합격 기준을 코드화하기」 절에서 Threshold 문법과 태그별 기준으로, 「Check를 잘 설계하는 법」 절에서 Check 설계로, 「업무 지표를 사용자 정의 메트릭으로 만들기」 절에서 Counter·Trend 같은 사용자 정의 메트릭으로, 「결과 해석에서 자주 생기는 오해」 절에서 `dropped_iterations` 메트릭 확인으로 쓰입니다.

## 가장 작은 k6 스크립트

### 첫 스크립트

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 5,
  duration: '30s',
};

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/health`);
  check(res, {
    'status is 200': (r) => r.status === 200,
  });
  sleep(1);
}
```

이 스크립트는 5개의 VU가 30초 동안 `/health`에 앞서 기반 기술에서 본 HTTP GET 요청을 반복해서 보냅니다. `__ENV.BASE_URL`은 앞서 본 환경 변수처럼 실행할 때 밖에서 주입하므로 같은 스크립트를 개발·스테이징 환경에 재사용할 수 있습니다. `sleep(1)`은 사용자의 생각 시간(think time)을 흉내 냅니다. sleep이 없으면 VU가 응답을 받자마자 다시 요청을 보내므로 같은 VU 수로도 훨씬 큰 부하가 걸립니다. 실제 사용자가 화면을 읽고 클릭하는 간격을 업무 로그에서 추정해 넣는 것이 좋습니다.

### 실행과 결과 읽기

```bash
k6 run -e BASE_URL=https://staging.example.com script.js
```

앞서 기반 기술에서 본 것처럼 k6는 명령줄에서 실행하며, 실행이 끝나면 터미널에 요약이 출력됩니다. 아래는 읽는 방법을 보여 주는 형식 예시이며 실제 측정값이 아닙니다.

```text
     ✓ status is 200

     checks.........................: 100.00% ✓ 150      ✗ 0
     http_req_duration..............: avg=42ms  min=30ms  med=40ms  max=120ms  p(90)=55ms  p(95)=63ms
     http_req_failed................: 0.00%   ✓ 0        ✗ 150
     http_reqs......................: 150     4.9/s
     iterations.....................: 150     4.9/s
     vus............................: 5       min=5      max=5
```

주목할 지표는 `http_req_duration`(요청을 보낸 뒤 응답을 다 받기까지의 시간), `http_req_failed`(실패한 요청 비율), `http_reqs`(총 요청 수와 초당 요청 수)입니다. 앞서 기반 기술에서 본 응답 시간 분포처럼, 평균(avg)만 보면 일부 느린 요청이 가려지므로 p(95)나 p(99) 같은 백분위를 함께 봅니다. p(95)가 63ms라는 것은 요청의 95%가 63ms 이내에 끝났다는 뜻입니다.

## 닫힌 모델과 열린 모델: Executor 선택

### 두 모델의 차이

k6 문서는 부하 모델을 닫힌 모델과 열린 모델로 구분해 설명합니다. 닫힌 모델(closed model)은 VU 수를 정하고, 각 VU가 한 반복을 끝낸 뒤 다음 반복을 시작합니다. 서버가 느려지면 한 반복이 길어지므로 시간당 요청 수가 줄어듭니다. 열린 모델(open model)은 초당 몇 건이 도착할지를 정하고, 이전 요청이 끝났는지와 관계없이 새 반복을 시작합니다. 서버가 느려져도 요청은 계속 도착하므로, 앞서 기반 기술에서 본 은행 창구의 번호표처럼 대기열이 쌓입니다.

현실의 공개 API는 사용자가 서로 독립적으로 도착하므로 열린 모델에 가깝습니다. 사내 업무 시스템처럼 정해진 직원이 순서대로 일하는 환경은 닫힌 모델에 가깝습니다. 서버 포화를 확인하려는 목적이라면 닫힌 모델은 "서버가 느려지면 부하가 알아서 줄어드는" 효과로 문제를 덜 드러낼 수 있습니다. 이 현상은 부하 테스트에서 지연 측정이 실제보다 낙관적으로 나오는 원인으로 자주 논의되므로, 응답 시간 분포를 해석할 때 모델을 함께 적어 두는 편이 좋습니다.

### 주요 Executor 비교

| Executor | 모델 | 고정하는 값 | 쓰는 상황 |
| --- | --- | --- | --- |
| `constant-vus` | 닫힘 | VU 수와 시간 | 단순한 일정 부하 |
| `ramping-vus` | 닫힘 | 단계별 VU 수 | 점진적 증가·감소 |
| `constant-arrival-rate` | 열림 | 초당 반복 수 | 일정한 도착률 검증 |
| `ramping-arrival-rate` | 열림 | 단계별 도착률 | 스트레스·스파이크 |
| `per-vu-iterations` | 닫힘 | VU당 반복 수 | VU마다 정해진 작업량 |
| `shared-iterations` | 닫힘 | 전체 반복 수 | 정해진 총량을 끝내는 시간 |

앞서 기반 기술에서 본 Executor를 "입장 규칙"으로 떠올리면 선택 기준은 단순합니다. 사용자 수가 고정된 환경이면 VU 기반, 외부에서 독립적으로 도착하는 요청이면 도착률 기반을 씁니다. 반복 횟수 기반(`per-vu-iterations`, `shared-iterations`)은 시간이 아니라 작업량이 기준일 때 유용합니다. 예를 들어 "1만 건 데이터를 모두 한 번씩 호출한다"는 시나리오입니다.

### 도착률 기반 시나리오 예시

```javascript
export const options = {
  scenarios: {
    steady_orders: {
      executor: 'constant-arrival-rate',
      rate: 50,            // timeUnit 동안 시작할 반복 수
      timeUnit: '1s',      // 초당 50건
      duration: '5m',
      preAllocatedVUs: 30, // 미리 확보할 VU
      maxVUs: 100,         // 부족하면 늘릴 수 있는 상한
      exec: 'createOrder',
    },
  },
};
```

`rate`와 `timeUnit`은 도착률을 정하고, `preAllocatedVUs`와 `maxVUs`는 그 도착률을 만들기 위해 쓸 수 있는 VU 풀입니다. 응답이 느려져 VU가 모두 사용 중이면 k6는 `maxVUs`까지 VU를 늘립니다. 그래도 부족하면 새 반복을 시작하지 못하고 `dropped_iterations` 메트릭에 기록합니다. 이 값이 0보다 크다는 것은 "의도한 도착률을 만들지 못했다"는 신호이므로, 서버가 포화했거나 부하 생성기 자원이 부족하다는 의미입니다. 이 값을 확인하지 않으면 "50건/초 테스트를 통과했다"는 결론이 실제로는 30건/초만 보낸 결과일 수 있습니다.

## Threshold로 합격 기준을 코드화하기

### 기본 문법

```javascript
export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'],          // 오류율 1% 미만
    http_req_duration: ['p(95)<500', 'p(99)<1200'], // 지연 기준
    checks: ['rate>0.99'],                   // check 성공률
  },
};
```

각 메트릭에 조건식 배열을 붙이며, 하나라도 어기면 테스트는 실패로 끝납니다. 이때 k6 프로세스는 0이 아닌 종료 코드를 반환하므로 CI에서 단계 실패로 처리할 수 있습니다. `checks: ['rate>0.99']`는 앞서 기반 기술에서 본 Check와 Threshold의 역할 분담을 하나로 연결하는 전형적인 방법입니다. 이 설정이 없으면 응답 본문이 잘못되어도 테스트가 통과할 수 있습니다.

### 태그로 API별 기준 나누기

모든 요청에 같은 기준을 쓰면 안 됩니다. 조회 API와 결제 API의 허용 지연은 다릅니다. 요청에 `tags`나 `name`을 붙이면 하위 메트릭에 별도 기준을 걸 수 있습니다.

```javascript
import http from 'k6/http';

export const options = {
  thresholds: {
    'http_req_duration{name:list_orders}': ['p(95)<400'],
    'http_req_duration{name:create_order}': ['p(95)<800'],
  },
};

export default function () {
  http.get(`${__ENV.BASE_URL}/orders?page=1`, { tags: { name: 'list_orders' } });
  http.post(
    `${__ENV.BASE_URL}/orders`,
    JSON.stringify({ item: 'A-100', qty: 1 }),
    { headers: { 'Content-Type': 'application/json' }, tags: { name: 'create_order' } }
  );
}
```

앞서 기반 기술에서 본 태그와 시계열의 관계처럼, `name` 태그를 일부러 지정하는 이유는 URL에 주문 번호 같은 가변 값이 들어갈 때 메트릭 종류가 무한히 늘어나는 것을 막기 위해서입니다. `/orders/1001`, `/orders/1002`를 각각 다른 시계열로 만들면 결과 해석과 저장 비용이 모두 나빠집니다.

### 조기 중단

```javascript
thresholds: {
  http_req_failed: [
    { threshold: 'rate<0.05', abortOnFail: true, delayAbortEval: '30s' },
  ],
},
```

`abortOnFail`을 켜면 기준을 어기는 즉시 테스트를 중단합니다. 장애 상태에서 몇 분간 더 부하를 걸 이유가 없을 때 유용합니다. `delayAbortEval`은 초기 몇 초의 불안정한 값 때문에 곧바로 중단되지 않도록 평가를 늦춥니다. 단, 스트레스 테스트처럼 한계점을 찾는 목적이라면 조기 중단이 오히려 정보를 줄이므로 목적에 맞게 선택하세요.

## 테스트 유형별 설계

k6 문서는 스모크, 평균 부하, 스트레스, 스파이크, 소크(장시간) 등의 테스트 유형을 소개합니다. 이름은 달라도 모두 앞서 기반 기술에서 본 부하 테스트와 SLO의 관점, 곧 "어떤 부하 형태로 어떤 질문에 답하는가"의 구분입니다.

| 유형 | 질문 | 부하 형태 | 합격 기준 예시 |
| --- | --- | --- | --- |
| Smoke | 스크립트와 환경이 동작하는가 | 아주 낮은 VU, 짧은 시간 | 오류 0건 |
| Load | 평소 예상 부하를 감당하는가 | 평균 도착률 유지 | SLO 이내 |
| Stress | 어느 지점부터 무너지는가 | 단계적 증가 | 한계점 기록 |
| Spike | 갑작스런 급증에서 회복하는가 | 짧은 급증 후 복귀 | 회복 시간 |
| Soak | 장시간에 누수·저하가 있는가 | 평균 부하를 오래 유지 | 시간에 따른 추세 |

### 스모크 테스트

스모크 테스트는 본 테스트 전에 스크립트 오류, 인증 만료, 잘못된 환경 주소 같은 기본 문제를 걸러 내는 단계입니다. 부하 자체가 목적이 아니므로 VU 1~2개, 1분 안팎이면 충분합니다. 이 단계를 건너뛰면 30분짜리 테스트가 시작 1분 만에 인증 오류로 의미를 잃는 일이 생깁니다.

```javascript
export const options = {
  vus: 1,
  duration: '1m',
  thresholds: { http_req_failed: ['rate==0'] },
};
```

### 스트레스 테스트: 단계적 증가

```javascript
export const options = {
  scenarios: {
    stress: {
      executor: 'ramping-arrival-rate',
      startRate: 10,
      timeUnit: '1s',
      preAllocatedVUs: 50,
      maxVUs: 400,
      stages: [
        { target: 50,  duration: '3m' },
        { target: 100, duration: '3m' },
        { target: 150, duration: '3m' },
        { target: 0,   duration: '2m' },
      ],
    },
  },
  thresholds: { http_req_failed: ['rate<0.05'] },
};
```

도착률을 단계적으로 올리면서 어느 지점에서 지연이나 오류가 급증하는지 관찰합니다. 이때 각 단계의 시각을 기록해 두고, 서버 쪽 지표(CPU, 연결 수, 대기열)와 같은 시간축에서 비교하세요. k6 결과만으로는 "무엇이 병목인지"를 알 수 없습니다. 병목 판단은 애플리케이션 모니터링과 데이터베이스 지표를 함께 보아야 합니다.

### 스파이크와 소크

스파이크는 짧은 시간에 도착률을 크게 올렸다가 내리는 패턴으로, 이벤트 오픈이나 캠페인 알림 직후의 급증을 모의합니다. 합격 기준은 급증 중 성능뿐 아니라 급증이 끝난 뒤 지연이 평소로 돌아오는 시간입니다. 소크는 평균 부하를 수 시간 유지해 메모리 누수, 연결 누수, 로그 디스크 증가 같은 느린 문제를 찾습니다. 소크 테스트는 시간이 길어 비용이 크므로, 먼저 짧은 부하 테스트에서 기본 기준을 통과한 뒤에 실행합니다.

## 현실적인 시나리오 작성

### 로그인과 데이터 준비

모든 반복에서 로그인하면 인증 서버가 병목이 됩니다. 실제 사용자는 한 번 로그인하고 여러 요청을 합니다. 앞서 기반 기술에서 본 스크립트 생명주기처럼 `setup()`은 테스트 전에 한 번만 실행되므로, `setup()`에서 토큰을 한 번 받거나, VU별 초기화를 활용하세요.

```javascript
import http from 'k6/http';
import { check } from 'k6';

export function setup() {
  const res = http.post(`${__ENV.BASE_URL}/login`,
    JSON.stringify({ user: 'loadtest', password: __ENV.LT_PASSWORD }),
    { headers: { 'Content-Type': 'application/json' } });
  check(res, { 'login ok': (r) => r.status === 200 });
  return { token: res.json('token') };
}

export default function (data) {
  const res = http.get(`${__ENV.BASE_URL}/orders`, {
    headers: { Authorization: `Bearer ${data.token}` },
    tags: { name: 'list_orders' },
  });
  check(res, { 'orders 200': (r) => r.status === 200 });
}
```

비밀번호는 스크립트에 쓰지 말고 환경 변수로 전달하세요. 토큰 하나를 모든 VU가 공유하면 서버 쪽 캐시나 속도 제한이 실제 사용자 분포와 다르게 동작할 수 있습니다. 중요한 시나리오라면 테스트 전용 계정 여러 개를 CSV나 JSON으로 준비해 VU마다 다른 계정을 쓰도록 구성합니다.

### 데이터 파일 공유

```javascript
import { SharedArray } from 'k6/data';

const users = new SharedArray('users', function () {
  return JSON.parse(open('./users.json'));
});

export default function () {
  const user = users[(__VU - 1) % users.length];
  // user.id 등을 요청에 사용
}
```

`SharedArray`는 모든 VU가 하나의 읽기 전용 데이터를 공유하게 해 메모리 사용을 줄입니다. 큰 데이터를 VU마다 복사해 올리면 부하 생성기의 메모리가 먼저 바닥날 수 있습니다. 이 점은 서버가 아니라 테스트 도구가 병목이 되는 대표적 사례입니다.

### 그룹화와 사용자 흐름

사용자 행동은 여러 요청의 묶음입니다. 상품 조회, 장바구니, 결제를 하나의 흐름으로 만들면 업무 기준으로 결과를 읽을 수 있습니다.

```javascript
import { group } from 'k6';

export default function () {
  group('browse', () => { /* 목록·상세 조회 */ });
  group('checkout', () => { /* 장바구니·결제 */ });
}
```

흐름별 지연이나 오류율을 따로 보면 "결제 단계만 느리다"처럼 구체적인 결과가 나옵니다. 다만 `group` 안에서 비동기 호출을 쓰는 등 제한이 있으므로 문서를 확인하세요.

## CI에 연결하기

### 종료 코드와 요약 내보내기

Threshold가 실패하면 k6는 0이 아닌 종료 코드를 반환합니다. 파이프라인은 이를 단계 실패로 보고 배포를 막을 수 있습니다.

```bash
k6 run --summary-export=summary.json -e BASE_URL=$TARGET script.js
echo "exit=$?"
```

`summary.json`은 메트릭 요약을 담으므로 이전 실행과 비교하는 자동화에 활용할 수 있습니다. 상세 시계열은 `--out` 옵션으로 JSON 파일이나 외부 저장소에 내보냅니다. 요약을 보관해 두면 "지난 릴리스보다 p95가 20% 나빠졌다"는 추세를 확인할 수 있습니다.

### 환경별 기준

스테이징 환경은 운영보다 작은 경우가 많으므로, 절대 처리량을 운영 수치와 비교하면 안 됩니다. 대신 같은 환경에서 이전 빌드와 비교한 상대 변화를 기준으로 쓰는 방식이 안전합니다. 예를 들어 "직전 릴리스 대비 p95가 10% 이상 나빠지면 실패"라는 기준은 환경 크기와 무관하게 회귀를 잡습니다. 단 스테이징에서의 결과가 운영 성능을 보장하지는 않는다는 점은 문서에 남겨 두세요.

### 운영 환경 테스트의 주의

운영 환경에 부하를 걸면 실제 사용자가 영향을 받을 수 있습니다. 승인된 시간대, 호출 대상 API 범위, 쓰기 요청의 테스트 데이터 격리, 즉시 중단 절차가 갖춰진 경우에만 진행하세요. 외부 결제나 문자 발송처럼 되돌릴 수 없는 호출은 반드시 모의 서버나 샌드박스로 대체합니다. 허가 없이 타인의 서비스에 부하를 거는 것은 허용되지 않으며, 이 글의 예시도 본인이 관리하는 환경을 전제로 합니다.

## 결과 해석에서 자주 생기는 오해

| 오해 | 실제 | 대응 |
| --- | --- | --- |
| 평균이 빠르면 괜찮다 | 소수의 느린 요청이 가려짐 | p95·p99 함께 확인 |
| 오류가 없으니 통과 | `dropped_iterations`로 부하 미달일 수 있음 | 실제 도착률 확인 |
| VU를 늘리면 부하도 늘어난다 | 응답이 느리면 요청률은 오히려 줄 수 있음 | 도착률 executor 검토 |
| 한 번 통과하면 안전하다 | 데이터 양·캐시 상태에 따라 달라짐 | 데이터 규모를 운영과 비슷하게 |
| k6가 병목을 알려 준다 | 클라이언트 측 관측만 제공 | 서버 지표와 함께 분석 |

특히 부하 생성기 자체가 병목인 경우를 주의해야 합니다. 부하 생성기의 CPU가 포화하면 서버가 아니라 테스트 도구가 느려지고, 측정된 지연에 그 영향이 섞입니다. 부하 생성기의 CPU·메모리·네트워크를 함께 모니터링하고, 필요하면 여러 대로 분산해 실행합니다.

## Check를 잘 설계하는 법

### 상태 코드만 검사하면 놓치는 것

응답이 200이어도 본문이 비어 있거나, 오류 메시지가 JSON 안에 담겨 있는 API가 있습니다. 상태 코드만 확인하면 서버가 "성공"이라고 말하는 잘못된 응답을 통과시킬 수 있습니다. 부하가 높을 때 일부 서비스는 기본값이나 빈 목록을 돌려주는 방식으로 열화(degrade)되기도 하므로, 업무적으로 의미 있는 필드를 함께 검사해야 합니다.

```javascript
check(res, {
  'status is 201': (r) => r.status === 201,
  'has order id': (r) => !!r.json('orderId'),
  'under 1s': (r) => r.timings.duration < 1000,
});
```

위 세 번째 검사는 응답 시간을 Check로도 기록한 예입니다. 다만 시간 기준의 최종 판정은 Threshold에 맡기는 편이 낫습니다. Check는 개별 요청의 통과 여부를 비율로 남기고, Threshold는 전체 분포의 백분위로 판단하므로 목적이 다릅니다. 같은 기준을 두 곳에 중복해서 쓰면 한쪽만 수정하는 실수가 생깁니다.

### 실패 원인을 남기는 방법

Check가 실패하면 어떤 요청이 왜 실패했는지 알아야 원인 분석이 가능합니다. 실패한 응답의 상태 코드와 일부 본문을 로그로 남기되, 부하 상황에서 로그를 과하게 출력하면 부하 생성기 자체가 느려집니다. 모든 실패를 출력하지 말고 일정 횟수만 샘플링하세요.

```javascript
let logged = 0;
export default function () {
  const res = http.get(`${__ENV.BASE_URL}/orders`);
  const ok = check(res, { 'status is 200': (r) => r.status === 200 });
  if (!ok && logged < 5) {
    logged += 1;
    console.error(`status=${res.status} body=${String(res.body).slice(0, 200)}`);
  }
}
```

여기서 `logged`는 VU마다 따로 존재하는 변수이므로 전체 로그 수는 VU 수에 비례해 늘어납니다. 정확한 전체 상한이 필요하면 별도의 카운터 메트릭을 사용하거나 로그 수집 쪽에서 제한을 거세요. 또한 응답 본문에 개인정보나 토큰이 들어 있을 수 있으므로 로그에 남기기 전에 마스킹 여부를 확인해야 합니다.

## 업무 지표를 사용자 정의 메트릭으로 만들기

기본 메트릭은 HTTP 수준의 측정값입니다. "주문 생성에 성공한 건수"나 "결제 승인까지 걸린 전체 시간"처럼 업무 의미가 있는 값은 직접 정의할 수 있습니다. k6는 Counter(누적 합), Gauge(마지막 값), Rate(비율), Trend(분포) 네 가지 종류의 사용자 정의 메트릭을 제공합니다.

```javascript
import { Counter, Trend } from 'k6/metrics';

const ordersCreated = new Counter('orders_created');
const checkoutTime  = new Trend('checkout_flow_ms', true);

export const options = {
  thresholds: {
    orders_created: ['count>1000'],
    checkout_flow_ms: ['p(95)<2500'],
  },
};

export default function () {
  const start = Date.now();
  // ... 장바구니 담기, 결제 요청 ...
  const created = true; // 실제로는 응답 검사 결과를 사용
  if (created) ordersCreated.add(1);
  checkoutTime.add(Date.now() - start);
}
```

이렇게 하면 "요청 하나의 지연"이 아니라 "사용자가 결제를 끝내는 데 걸린 시간"으로 합격 기준을 세울 수 있습니다. 사용자가 느끼는 품질은 개별 요청보다 흐름 전체에 가깝기 때문입니다. 단, 사용자 정의 메트릭이 많아지면 결과 해석이 복잡해지므로, 릴리스 판단에 실제로 쓰는 몇 개만 남기세요.

## 페이싱과 생각 시간

닫힌 모델에서 `sleep`을 쓰면 요청 간격이 "응답 시간 + sleep"이 되어 서버가 느릴수록 간격이 늘어납니다. 일정한 반복 주기를 원한다면 도착률 기반 executor를 쓰는 것이 간단합니다. 그렇지 않고 VU 기반으로 일정한 주기를 맞추려면 반복 시작 시각을 기준으로 남은 시간만큼 쉬는 방식(페이싱)을 직접 구현해야 하며, 구현이 복잡하고 오류 가능성이 높으므로 가능하면 도착률 executor를 우선 고려하세요.

생각 시간은 고정값보다 분포를 두는 것이 현실적입니다. 모든 VU가 정확히 1초마다 요청하면 요청이 같은 순간에 몰리는 인공적인 패턴이 생깁니다. 다음처럼 범위 안의 임의 값을 쓰면 도착이 흩어집니다.

```javascript
import { sleep } from 'k6';
sleep(1 + Math.random() * 2); // 1~3초
```

다만 임의 값을 쓰면 실행마다 결과가 조금씩 달라지므로, 재현성이 중요한 회귀 비교에서는 같은 분포를 계속 쓰고 분포 자체를 문서에 남겨야 합니다.

## 서버 지표와 함께 읽기

k6는 클라이언트 입장에서 본 값을 측정합니다. 응답이 느려진 이유가 애플리케이션 스레드 부족인지, 데이터베이스 락인지, 네트워크 지연인지는 서버 쪽 관측으로 확인해야 합니다. 부하 테스트 실행 시각을 기록해 두고, 같은 시간대의 애플리케이션 응답 시간, 데이터베이스 연결 수, CPU, 가비지 컬렉션, 대기열 길이를 나란히 비교하세요. 시계가 어긋나면 비교가 무의미해지므로 부하 생성기와 서버의 시간 동기를 확인하는 것이 선행 조건입니다.

| 관측 위치 | 보는 값 | 알 수 있는 것 |
| --- | --- | --- |
| k6 (클라이언트) | 지연, 오류율, 도착률 | 사용자 관점의 결과 |
| 애플리케이션 | 스레드·커넥션 풀, 에러 로그 | 앱 내부 포화 여부 |
| 데이터베이스 | 세션 수, 락 대기, 느린 쿼리 | 저장소 병목 |
| 인프라 | CPU, 메모리, 네트워크 | 자원 한계 |
| 부하 생성기 | CPU, 메모리, 소켓 | 테스트 도구의 한계 |

이 표의 마지막 줄이 가장 자주 빠집니다. 결과가 이상할 때 서버만 의심하지 말고 부하 생성기의 상태를 먼저 확인하세요.

## 데이터 상태와 사전 준비

같은 도착률이라도 데이터베이스에 데이터가 10만 건인지 1억 건인지에 따라 결과가 크게 달라집니다. 인덱스가 메모리에 올라와 있는지, 캐시가 비어 있는지도 첫 몇 분의 지연을 바꿉니다. 그래서 측정 구간 앞에 워밍업 구간을 두고, 워밍업 구간의 결과는 합격 판단에서 제외하는 방식이 흔히 쓰입니다. 시나리오를 둘로 나누고 시작 시각을 어긋나게 하면 이를 표현할 수 있습니다.

```javascript
scenarios: {
  warmup: {
    executor: 'constant-arrival-rate', rate: 10, timeUnit: '1s',
    duration: '2m', preAllocatedVUs: 20, exec: 'readOrders',
    tags: { phase: 'warmup' },
  },
  measure: {
    executor: 'constant-arrival-rate', rate: 30, timeUnit: '1s',
    duration: '10m', startTime: '2m', preAllocatedVUs: 50, maxVUs: 150,
    exec: 'readOrders', tags: { phase: 'measure' },
  },
},
thresholds: {
  'http_req_duration{phase:measure}': ['p(95)<500'],
},
```

`startTime`으로 측정 시나리오를 워밍업 뒤에 시작하고, `phase` 태그로 측정 구간의 메트릭만 따로 판정합니다. 쓰기 테스트에서는 테스트가 만든 데이터가 쌓이므로, 반복 실행 전에 데이터를 정리하거나 매번 초기 상태로 복원하는 절차도 필요합니다. 그렇지 않으면 두 번째 실행부터는 시작 조건이 달라져 비교가 어긋납니다.

## 결과 보고서에 남길 내용

부하 테스트 결과를 공유할 때는 숫자뿐 아니라 해석에 필요한 조건을 함께 적어야 합니다. 다음 항목이 빠지면 몇 달 뒤 결과를 재현하거나 비교할 수 없습니다.

- 대상 빌드 버전과 환경 구성(인스턴스 크기, 데이터 규모)
- 사용한 스크립트의 커밋과 시나리오 설정(executor, rate, 시간)
- 합격 기준과 각 기준의 통과 여부
- `dropped_iterations`, 부하 생성기 자원 사용량
- 서버 쪽 관측 결과와 병목 가설
- 후속 조치와 담당자

숫자는 같아도 조건이 다르면 의미가 달라지므로, 보고서의 첫 문단에 "어떤 조건에서 어떤 기준으로 판단했는가"를 적는 습관이 좋습니다.

## 부하 생성기 자체를 신뢰하는 조건

### 부하 생성기 사양과 배치

부하 생성기는 서버와 같은 호스트에서 돌리지 않는 것이 기본입니다. 같은 장비에서 실행하면 CPU와 네트워크를 서로 나눠 쓰므로 측정값이 오염됩니다. 가능하면 서버와 같은 네트워크 구간의 별도 장비에서 실행하되, 실제 사용자와 같은 경로를 시험하려는 목적이라면 외부 위치에서 실행하는 방식도 고려합니다. 어느 쪽이든 "생성기가 어디에 있었는가"가 결과 해석의 일부이므로 보고서에 적어야 합니다.

### 사전 용량 확인

본 테스트 전에 생성기 하나가 감당하는 도착률의 상한을 확인하는 리허설을 해 두면 좋습니다. 예를 들어 응답이 매우 빠른 단순 엔드포인트로 도착률을 올려 보고, 생성기의 CPU가 일정 수준을 넘는 지점을 기록합니다. 그 지점을 넘는 본 테스트 계획은 생성기를 여러 대로 나누거나 스크립트의 연산을 줄여야 합니다. 이 확인을 건너뛰면 "서버가 느리다"는 잘못된 결론으로 불필요한 튜닝을 시작할 수 있습니다. 아래는 생성기 상태를 확인하는 간단한 명령 예시입니다.

```bash
# 테스트 중 생성기의 CPU·메모리·소켓 상태를 5초 간격으로 기록
vmstat 5 | tee generator_vmstat.log
ss -s
```

이 로그는 테스트 결과와 같은 시간축으로 비교할 수 있도록 함께 보관하세요. 기록이 없으면 이상 징후가 생겼을 때 원인이 서버인지 생성기인지 구분할 방법이 없습니다.

## 업무 예시: 주문 API 릴리스 전 검증 계획

가상의 주문 서비스가 새 릴리스를 앞두고 있다고 가정하겠습니다. 이 계획은 설명용이며 실제 수행 결과가 아닙니다.

1. 업무 로그에서 평소 피크 시간대의 주문 생성 도착률을 확인합니다. 예를 들어 초당 30건이 피크라고 가정합니다.
2. SLO가 "주문 생성 p95 800ms 이내, 오류율 1% 미만"이라면 이를 Threshold로 옮깁니다.
3. 스모크 테스트로 스크립트와 계정을 확인합니다.
4. 도착률 30건/초를 10분 유지하는 부하 테스트를 실행하고, `dropped_iterations`가 0인지 확인합니다.
5. 도착률을 45건/초, 60건/초로 올려 여유 폭을 확인합니다. 이 단계의 목적은 합격이 아니라 한계 파악이므로 실패해도 기록이 남아야 합니다.
6. 결과 요약과 서버 지표를 함께 릴리스 판단 문서에 첨부합니다.

이 계획에서 핵심은 "한 번의 통과"가 아니라 "기준과 증거를 남긴다"는 점입니다. 다음 릴리스에서 같은 스크립트를 재실행하면 비교 기준이 됩니다.

## 스크립트 품질 점검 목록

- 환경 주소와 비밀 값은 코드가 아니라 환경 변수로 받는가?
- 사용자 대기 시간(`sleep`)이 업무 흐름에 맞는가?
- `name` 태그로 가변 URL을 묶었는가?
- `checks`에 Threshold가 걸려 있는가?
- `dropped_iterations`를 합격 판단에 포함하는가?
- 테스트 데이터가 운영 데이터와 격리되어 있는가?
- 결과 요약과 실행 조건(버전, 환경, 시각)을 함께 보관하는가?

이 목록은 코드 리뷰 때 그대로 쓸 수 있도록 짧게 구성했습니다. 사고가 나면 팀 상황에 맞는 항목을 추가하세요.

## 한계와 적용 기준 Q&A

### Q. k6 결과가 좋으면 운영에서도 문제없나요?

A. 보장할 수 없습니다. 테스트 환경의 크기, 데이터 양, 캐시 상태, 네트워크 경로, 외부 의존 서비스가 운영과 다르면 결과도 다릅니다. k6 결과는 "이 조건에서 이 기준을 만족했다"는 증거일 뿐이며, 조건을 함께 기록해야 의미가 있습니다. 운영과의 차이는 위험으로 문서화하세요.

### Q. 브라우저 사용자 경험도 k6로 측정되나요?

A. 기본 k6 HTTP 테스트는 프로토콜 수준의 요청과 응답을 측정하며, 브라우저가 화면을 그리는 시간은 포함하지 않습니다. 화면 렌더링 같은 프런트엔드 성능은 별도의 브라우저 기반 측정이 필요합니다. k6에는 브라우저 테스트용 모듈도 있으나 적용 범위와 비용이 다르므로 목적에 따라 선택하세요.

### Q. Threshold 숫자는 어떻게 정하나요?

A. 도구가 정해 주지 않습니다. SLO, 이전 릴리스의 측정값, 사용자 불만이 생기는 기준, 업무 요구에서 가져옵니다. 근거 없는 숫자는 너무 느슨하면 회귀를 놓치고 너무 엄격하면 늘 실패해서 무시됩니다. 처음에는 현재 수치를 기록하는 용도로 시작해 안정되면 기준으로 올리는 방법도 있습니다.

### Q. 부하 테스트를 얼마나 자주 해야 하나요?

A. 모든 커밋마다 전체 부하를 거는 것은 비용이 큽니다. 스모크는 자주, 대표 시나리오의 짧은 부하 테스트는 릴리스 후보마다, 소크·스트레스는 주요 변경이나 정기 일정으로 나누는 것이 현실적입니다. 빈도는 변경 위험과 환경 비용으로 정하세요.

### Q. 부하 테스트 중 서버가 죽으면 실패인가요?

A. 목적에 따라 다릅니다. 평균 부하 검증에서는 실패이지만, 스트레스 테스트에서 한계점을 찾는 것이 목표라면 어디서 무너지고 어떻게 회복하는지가 핵심 결과입니다. 시작 전에 "무너져도 되는 범위"와 중단 절차를 합의해 두세요.

## 마무리

k6로 부하 테스트를 설계할 때는 도구의 문법보다 두 가지 질문이 먼저입니다. 요청이 어떤 패턴으로 도착하는가(닫힌 모델인가 열린 모델인가), 그리고 무엇을 합격으로 볼 것인가(Threshold)입니다. 시나리오와 Executor로 부하 형태를 정하고, Check와 Threshold로 합격 기준을 코드에 남기며, `dropped_iterations`와 서버 지표로 결과의 신뢰도를 점검하세요. 그러면 부하 테스트가 일회성 이벤트가 아니라 릴리스마다 반복 가능한 증거가 됩니다.
