## 먼저 답하기

### Q. 단위 테스트가 많고 E2E 테스트가 적으면 항상 좋은 테스트 전략인가요?

A. 아닙니다. 테스트 피라미드는 빠르고 고립된 검증을 많이 두고 느리고 불안정한 검증을 꼭 필요한 곳에 두자는 방향을 보여 주지만, 숫자 비율 자체가 목표는 아닙니다. 결제 금액 계산처럼 코드 안에서 결정되는 규칙은 단위 테스트가 잘 맞고, 로그인 연동이나 브라우저 접근성처럼 실제 경계를 확인해야 하는 위험은 통합 또는 E2E(End-to-End, 사용자 흐름 전체) 테스트가 필요합니다. 중요한 것은 테스트 수가 아니라 어떤 위험을 어느 단계에서 가장 빨리 믿을 만하게 발견하는가입니다.

### Q. E2E 테스트가 느리고 자주 깨지니 없애도 되나요?

A. 없애기보다 역할을 좁혀야 합니다. E2E 테스트는 화면·서버·인증·배포 설정이 함께 연결되는 대표 흐름을 확인하는 데 가치가 있습니다. 다만 모든 분기를 브라우저로 반복하면 실행 시간이 길어지고 실패 원인을 찾기 어려워집니다. 계산 규칙과 오류 처리처럼 더 낮은 층에서 확인할 수 있는 항목은 그곳으로 내리고, E2E에는 실제 연결이 아니면 알 수 없는 핵심 여정만 남기는 편이 낫습니다.

## 먼저 알아둘 기반 기술

### 테스트 피라미드란 무엇인가

테스트 피라미드는 자동화 테스트를 실행 범위와 비용에 따라 나누어 생각하는 모델입니다. 아래쪽에는 함수·클래스·도메인 규칙처럼 작은 범위를 빠르게 검증하는 단위 테스트(Unit Test)를 둡니다. 중간에는 데이터베이스, HTTP API, 메시지 큐, 파일 시스템처럼 구성 요소 사이의 약속을 확인하는 통합 테스트(Integration Test)를 둡니다. 위쪽에는 사용자가 브라우저나 앱에서 실제로 밟는 흐름을 확인하는 E2E 테스트를 둡니다.

피라미드라는 그림은 보통 아래가 넓고 위가 좁습니다. 작은 테스트는 준비할 데이터와 외부 의존성이 적고, 실패했을 때 어느 규칙이 깨졌는지 찾기 쉬우며, 변경마다 반복하기 좋기 때문입니다. 반대로 E2E는 실제와 가까운 신호를 주지만 브라우저, 네트워크, 인증, 테스트 계정, 비동기 처리 등 실패 원인이 많아질 수 있습니다. 그림의 핵심은 "단위 테스트를 무조건 많이 써라"가 아니라 비용과 신뢰도가 다른 신호를 구분하라는 데 있습니다.

### 테스트 범위와 테스트 더블

테스트 범위(scope)는 한 번의 검증이 실제 시스템의 어디까지 포함하는지를 말합니다. 할인 금액을 계산하는 함수 하나를 호출하면 범위가 작고, 주문 생성 API가 데이터베이스와 재고 서비스까지 부르면 범위가 넓어집니다. 범위가 넓다고 자동으로 더 좋은 테스트는 아닙니다. 범위가 넓어질수록 실제 배포에서만 보이는 문제를 찾을 가능성은 커지지만, 준비·실행·실패 분석 비용도 커집니다.

작은 범위에서 외부 의존성을 대신하는 객체를 테스트 더블(test double)이라고 부릅니다. stub은 정해진 값을 돌려주고, fake는 단순화된 동작 구현을 제공하며, mock은 호출 방식에 대한 기대를 검사할 수 있습니다. 더블은 외부 결제사의 일시 장애나 느린 네트워크 때문에 할인 규칙 테스트가 실패하지 않게 도울 수 있습니다. 하지만 더블이 실제 API의 인증 방식·응답 형식·timeout을 증명하지는 않으므로, 실제 경계를 확인하는 통합 또는 계약 테스트를 별도로 둬야 합니다.

### 피드백 시간, 결정성, 관찰 가능성

테스트 전략에서는 세 가지 질문이 반복됩니다. 첫째, 개발자가 결과를 얼마나 빨리 받을 수 있는가입니다. pull request를 올릴 때마다 40분이 걸리는 신호는 가치가 있어도 자주 무시될 수 있습니다. 둘째, 같은 코드와 입력에서 같은 결과가 나오는가입니다. 시간·랜덤 값·공유 계정·네트워크 상태에 따라 흔들리는 테스트는 실제 결함과 잡음을 구분하기 어렵게 만듭니다. 셋째, 실패했을 때 원인을 좁힐 수 있는가입니다. 로그·입력·응답·trace가 없으면 통과/실패 숫자만 남고 수정은 추측이 됩니다.

이 세 기준은 테스트 층을 선택하는 데 도움을 줍니다. 단위 테스트가 빠르지만 실제 SQL 문법 오류를 잡지 못한다면 통합 테스트가 필요합니다. E2E가 실제 로그인 경로를 보지만 불안정하다면, 고정된 test account·명시적인 대기 조건·실패 시 trace를 추가하고, 같은 규칙을 API 또는 component 테스트로 내려야 할지 검토합니다. 테스트 피라미드는 한 번 그려 놓는 구조도가 아니라 피드백 품질을 바꾸는 의사결정 도구입니다.

## 비율 대신 위험에서 출발하기

인터넷에서 "단위 70%, 통합 20%, E2E 10%" 같은 숫자를 볼 수 있습니다. 출발점으로 참고할 수는 있지만 모든 서비스에 적용되는 정답은 아닙니다. 대규모 금액 계산 엔진은 많은 도메인 규칙을 작은 테스트로 검증할 이유가 크고, 데이터 변환 파이프라인은 실제 데이터베이스·파일 형식·스케줄러와의 통합이 더 큰 위험일 수 있습니다. 모바일 앱이나 복잡한 접근성 요구가 있는 서비스는 대표 UI 흐름의 비중도 높아질 수 있습니다.

먼저 기능을 다음 질문으로 나눠 봅니다. 실패하면 누가 어떤 피해를 보는가? 규칙은 순수한 입력과 출력으로 표현할 수 있는가? 외부 시스템과의 약속이 핵심인가? 실제 브라우저·권한·배포 설정이 아니면 발견할 수 없는가? 실패가 나면 빠르게 원인을 볼 수 있는가? 답을 적으면 테스트를 어느 층에 둘지 더 분명해집니다.

예를 들어 쿠폰 할인 금액, 최소 주문 금액, 만료 날짜 비교는 입력·출력이 명확한 도메인 규칙이므로 단위 테스트 후보입니다. 쿠폰을 한 번만 사용하게 하는 제약은 데이터베이스 transaction과 동시성에 의존하므로 실제 DB를 포함한 통합 테스트 후보입니다. 고객이 쿠폰을 입력하고 결제 직전 할인 금액을 보고 주문을 완료하는 흐름은 UI·API·세션이 연결되므로 제한된 E2E 후보입니다. 같은 "쿠폰 기능"도 위험의 위치에 따라 테스트 층이 달라집니다.

## 각 층이 답해야 하는 질문

### 단위 테스트: 업무 규칙이 정확한가

단위 테스트는 보통 외부 I/O 없이 작은 코드 단위의 판단을 확인합니다. 좋은 단위 테스트는 구현 세부 사항보다 관찰 가능한 업무 규칙을 말합니다. 예를 들어 "주문 금액이 30,000원 이상이고 유효한 10% 쿠폰이면 최대 5,000원을 할인한다"는 규칙은 입력과 기대 결과가 명확합니다. 경곗값, 음수·0, 시간대, 반올림, 이미 사용한 쿠폰 같은 사례를 표로 만든 뒤 테스트 이름에도 의도를 담을 수 있습니다.

```text
주문 금액 29,999원 + 10% 쿠폰 → 할인 0원
주문 금액 30,000원 + 10% 쿠폰 → 할인 3,000원
주문 금액 80,000원 + 10% 쿠폰(최대 5,000원) → 할인 5,000원
만료된 쿠폰 → 적용 거절
```

이 층은 매우 빠른 피드백을 줄 수 있지만, mock이 실제와 같은지를 증명하지 않습니다. repository mock이 주문 저장에 성공했다고 돌려줘도, 실제 schema의 NOT NULL 제약이나 transaction 격리 수준이 맞는지는 알 수 없습니다. 따라서 단위 테스트의 목표를 "외부 환경을 빼고도 확실히 말할 수 있는 규칙"으로 제한해야 합니다. 외부 시스템의 행동까지 mock으로 복제하려고 하면 테스트 코드가 또 하나의 불완전한 시스템이 됩니다.

### 통합 테스트: 경계의 약속이 실제로 맞는가

통합 테스트는 둘 이상의 실제 구성 요소가 함께 동작하는지 확인합니다. 애플리케이션과 실제 DB의 migration·query·transaction을 확인하거나, HTTP handler와 직렬화·인증 미들웨어를 확인하거나, 메시지 producer와 consumer의 event 형식을 확인하는 테스트가 여기에 들어갑니다. 이 테스트의 가치는 개발자가 만든 가정과 실제 기술 요소의 가정이 만나는 지점을 확인하는 데 있습니다.

통합 테스트를 신뢰하려면 test data와 상태 초기화가 중요합니다. 이전 테스트가 만든 주문이 남아 있거나 여러 실행이 같은 고객 계정을 쓰면, 실패가 코드 결함인지 순서 의존성인지 알기 어렵습니다. 테스트마다 고유 식별자를 만들고, 필요한 fixture만 준비하고, transaction rollback·임시 schema·격리된 database 중 프로젝트에 맞는 정리 방식을 고릅니다. 정리 실패를 조용히 무시하면 시간이 지날수록 테스트 환경이 실제와 다른 미지의 상태가 됩니다.

실제 외부 결제·문자·지도 서비스까지 매번 연결할 필요는 없습니다. 비용·속도·권한·재현성 때문에 provider sandbox나 승인된 emulator를 쓸 수 있습니다. 다만 sandbox가 production과 같은 rate limit, 사기 탐지, 지역별 규칙을 가진다고 가정하면 안 됩니다. 무엇을 실제로 확인했고 무엇을 대체했는지 기록하면, 통합 테스트의 신호를 과대해석하는 일을 줄일 수 있습니다.

### 계약 테스트: 독립 배포의 호환성이 유지되는가

서비스가 나뉘면 데이터 형식과 오류 처리가 중요한 경계가 됩니다. 계약 테스트(contract test)는 소비자가 필요한 요청·응답·상태 코드를 명시하고 제공자가 그 약속을 만족하는지 확인합니다. 이는 전체 시스템을 띄우지 않고도 필드 이름 삭제, enum 값 변경, 오류 body 변화처럼 다른 팀의 배포를 깨뜨릴 변경을 빨리 찾게 해 줍니다.

계약 테스트는 통합 테스트와 경쟁하지 않습니다. 계약은 "주문 서비스가 결제 서비스에 어떤 JSON을 기대하는가"를 확인하고, 통합 테스트는 "우리 handler가 실제 DB와 인증 미들웨어를 포함해 그 JSON을 만드는가"를 확인할 수 있습니다. 계약의 범위를 모든 endpoint의 모든 조합으로 넓히면 유지비가 커지므로, 실제 소비자가 쓰는 흐름과 실패 시 영향이 큰 오류 응답부터 다룹니다. 계약을 통과했다고 결제 provider의 실제 승인이나 네트워크 장애까지 안전하다고 말할 수는 없습니다.

### E2E 테스트: 사용자의 대표 여정이 연결되는가

E2E 테스트는 브라우저가 로그인하고 화면을 조작하며 backend와 통신해 결과를 확인하는 식으로 사용자 여정을 봅니다. 회원 가입, 로그인, 상품 검색, 주문 생성, 관리자 권한 변경처럼 사용자 가치가 큰 흐름에서 특히 유용합니다. API 단위에서는 정상인데 화면의 버튼이 비활성화됐거나 CSRF 설정 때문에 요청이 막히거나 route 배포가 빠진 문제는 E2E가 더 잘 드러낼 수 있습니다.

그러나 E2E에 모든 예외를 넣으면 suite가 느리고 취약해집니다. 하나의 핵심 여정에는 정상 경로와 반드시 막아야 하는 권한·결제·데이터 손상 경계만 남기고, 세밀한 입력 조합은 단위·통합 테스트로 옮깁니다. selector는 보이는 문구나 CSS 구조보다 역할·label·안정적인 test id를 우선해 UI 스타일 변경에 덜 흔들리게 합니다. 임의의 `sleep` 대신 화면이나 API의 준비 상태를 기다리고, 실패 때 screenshot·trace·console log를 남겨 원인 분석 시간을 줄입니다.

## 테스트 피라미드를 망가뜨리는 신호

첫 번째 신호는 작은 규칙을 검증하려고 매번 브라우저와 여러 서비스를 띄우는 경우입니다. 로그인 화면을 통해 할인 함수의 한 경곗값을 확인하면, 실패가 났을 때 쿠폰 계산·브라우저·테스트 계정·네트워크 중 어디를 봐야 하는지 알기 어렵습니다. 이 경우 E2E를 고치는 것보다 규칙을 분리하고 단위 테스트를 추가하는 편이 근본적인 개선일 수 있습니다.

두 번째는 단위 테스트가 내부 메서드 호출 횟수만 지나치게 검사하는 경우입니다. 구현을 리팩터링할 때 사용자 행동은 그대로인데 테스트만 대량으로 깨진다면, 테스트가 계약이 아니라 현재 구현의 복사본이 되었을 수 있습니다. 외부에 보이는 결과와 중요한 협력 경계만 검증하고, 불필요한 interaction expectation은 줄입니다.

세 번째는 통합 환경을 "공유된 검은 상자"로 두는 경우입니다. 누구나 같은 staging DB에 데이터를 넣고 테스트하며, 배포 시간마다 환경이 달라지면 결과는 신뢰하기 어렵습니다. 모든 환경을 완벽히 개인별로 만들 수 없더라도, 중요한 테스트가 사용하는 version·fixture·외부 dependency 상태와 초기화 경로를 명시해야 합니다. 환경 공유는 비용을 줄이지만 숨은 상태의 비용을 만들 수 있습니다.

## 업무 예시: 주문 취소 기능을 층으로 나누기

주문 취소는 단순히 상태 값을 바꾸는 기능처럼 보이지만 결제·재고·배송·알림과 연결됩니다. 먼저 단위 테스트에서는 취소 가능한 상태 전이, 취소 수수료 계산, 부분 취소 가능 여부, 이미 환불된 주문의 거절 같은 업무 규칙을 검증합니다. 이 규칙은 timestamp와 주문 금액, 상태를 입력으로 받아 예상 상태와 금액을 비교할 수 있습니다.

통합 테스트에서는 실제 database transaction 안에서 주문 상태와 재고 예약이 함께 바뀌는지, 같은 취소 요청이 재시도되어도 이중 환불 상태가 생기지 않는지, 권한 없는 사용자가 다른 사람 주문을 취소하지 못하는지를 봅니다. 결제 provider는 sandbox 또는 adapter double로 대체할 수 있지만, 내부 DB 제약·outbox event·API 직렬화는 가능한 실제 구성으로 확인합니다.

계약 테스트에는 취소 API의 성공 응답뿐 아니라 401·403·409 같은 오류 의미를 넣습니다. 프런트엔드가 409를 받았을 때 이미 처리된 주문이라는 안내를 보여 준다면 그 상태 코드와 body는 사용자 경험의 계약입니다. 마지막으로 E2E에서는 로그인한 고객이 취소 가능한 주문을 열고 취소를 확정한 뒤 목록과 상세 화면에서 상태가 일관되게 보이는 대표 흐름을 확인합니다. 외부 환불의 모든 실패 조합을 브라우저에서 만들려 하기보다, 그 조합은 통합·계약 계층에서 더 빠르게 다룹니다.

이렇게 나누면 어떤 테스트가 실패했는지가 곧 조사 출발점이 됩니다. 규칙 테스트 실패는 도메인 계산을, 통합 테스트 실패는 schema·transaction·인증 경계를, 계약 실패는 독립 서비스의 호환성을, E2E 실패는 배포된 사용자 흐름을 먼저 보게 합니다. 하나의 만능 테스트로 모든 것을 증명하려는 것보다 훨씬 빠르게 결함 위치를 좁힐 수 있습니다.

## CI 실행 순서와 품질 게이트

모든 테스트를 모든 commit에서 같은 방식으로 실행할 필요는 없습니다. 보통 formatter·lint·단위 테스트·작은 component 테스트처럼 빠른 신호는 pull request마다 실행합니다. 실제 DB migration, 서비스 간 통합, 브라우저 E2E처럼 준비 비용이 큰 검증은 변경 영역이나 배포 후보에 맞춰 실행할 수 있습니다. 이것은 느린 검증을 생략한다는 뜻이 아니라, 개발자의 피드백 속도와 출시 전 신뢰 신호를 분리하는 방법입니다.

실행 순서를 정할 때는 실패 확률과 진단 비용을 고려합니다. 문법 오류나 순수 규칙 오류를 먼저 발견하면 비싼 E2E runner를 불필요하게 쓰지 않아도 됩니다. 반대로 권한·금전·데이터 migration처럼 영향이 큰 변경은 변경 파일 수가 적어도 통합 검증을 건너뛰면 안 됩니다. 변경 경로에 따라 테스트를 선택하는 규칙은 사람이 기억하는 체크리스트가 아니라 CI 설정과 코드 리뷰 기준에 드러나야 합니다.

품질 게이트는 단순히 "빨간색이면 병합 금지"인 버튼이 아닙니다. 어떤 테스트가 차단 조건인지, flaky한 테스트가 실패했을 때 재실행을 허용하는 기준은 무엇인지, 환경 장애와 product 결함을 누가 분류하는지, 긴급 수정의 예외를 어떻게 기록하는지 합의해야 합니다. 무작정 재실행해 초록색만 만들면 실제 회귀를 놓칠 수 있고, 반대로 알려진 환경 장애가 팀을 계속 막으면 게이트는 신뢰를 잃습니다.

## 실패를 테스트 층으로 분류하는 방법

테스트가 실패했을 때 가장 비싼 행동은 모든 실패를 같은 방식으로 다루는 것입니다. 단위 테스트가 실패하면 보통 입력, 기대 결과, 변경한 규칙, 시간·난수 같은 숨은 의존성부터 살핍니다. 같은 commit에서 여러 단위 테스트가 동시에 깨졌다면 공통 library·locale·시간대·빌드 도구 변경처럼 공통 원인을 의심할 수 있습니다. 반면 특정 테스트만 실패했다면 그 테스트가 표현하는 업무 규칙과 코드 변경의 관계를 먼저 확인합니다.

통합 테스트 실패는 product 결함, migration 누락, test fixture 오염, container 시작 실패, 권한 설정 문제를 나눠 봐야 합니다. 예를 들어 `foreign key violation`이 나왔다면 실제 기능의 저장 순서가 틀렸을 수 있지만, 다른 테스트가 cleanup하지 않은 참조 row 때문일 수도 있습니다. 실패 시 SQL, schema version, test data 식별자, service log, 실행 순서를 남기면 재실행만 반복하는 일을 줄일 수 있습니다. 로그에 실제 비밀번호나 access token을 남기지 않는 원칙은 이때도 지켜야 합니다.

E2E 실패는 화면만 보면 원인을 알기 어렵습니다. browser screenshot, DOM snapshot, network 요청과 응답 상태, console error, trace, 서버 요청 ID를 연결하면 UI 문제인지 API 오류인지 인증 만료인지 좁힐 수 있습니다. 특히 버튼을 찾지 못했다는 오류가 selector 변경 때문인지, 앞 단계 API가 실패해 버튼이 렌더링되지 않은 것인지는 전혀 다른 문제입니다. E2E를 신뢰하려면 실행 결과뿐 아니라 실패 조사의 입력도 자동으로 남겨야 합니다.

분류 결과는 테스트 전략의 개선 재료입니다. 매주 같은 E2E가 timeout으로 실패한다면 retry 횟수를 늘리는 대신 비동기 작업의 완료 신호·test data 격리·환경 자원을 검토합니다. 같은 API schema 변경으로 여러 소비자가 깨진다면 계약 검증을 더 이른 단계에 둡니다. 브라우저까지 가야만 발견되는 계산 오류가 반복된다면 도메인 규칙을 분리해 작은 테스트로 옮길 기회입니다. 피라미드는 테스트 수를 세는 도표가 아니라 반복 실패가 어디에 쌓이는지 보고 구조를 조정하는 도구입니다.

## 테스트 목록을 제품 위험과 연결하기

테스트가 수백 개가 되면 이름만 보고 왜 존재하는지 알기 어렵습니다. 모든 테스트에 장문의 문서를 붙일 필요는 없지만, 고위험 기능에는 요구사항·위험·테스트 층·실행 위치를 연결한 간단한 목록이 도움이 됩니다. 예를 들어 "주문 취소는 결제 중복 환불을 막아야 한다"는 위험에는 금액 계산 단위 테스트, transaction 통합 테스트, API 오류 계약, 대표 취소 E2E가 각각 어떤 질문을 답하는지 적을 수 있습니다.

이 목록은 커버리지 표와 다릅니다. 코드 줄이 실행됐는지를 보여 주는 대신, 업무 실패가 어느 사용자에게 어떤 영향을 주는지에서 출발합니다. 권한 변경은 관리자 화면의 성공 경로 하나보다 다른 조직 데이터를 볼 수 없는지, 감사 기록이 남는지, 권한 철회가 즉시 반영되는지처럼 위험을 나눕니다. 데이터 migration은 새 열의 읽기·쓰기만이 아니라 이전 버전과의 호환성, backfill 중단, rollback 가능성을 검증 항목으로 둡니다.

변경 요청을 리뷰할 때는 새 테스트를 몇 개 추가했는지보다 다음을 묻습니다. 이번 변경이 깨뜨릴 수 있는 기존 약속은 무엇인가? 그 약속은 어느 테스트가 이미 보호하는가? 새로 생긴 위험 중 가장 큰 것은 무엇이고, 왜 이 층에서 확인하는가? 아직 확인하지 못한 것은 무엇인가? 답이 없다면 더 많은 E2E를 추가하기 전에 요구사항과 경계를 분명히 해야 합니다. 테스트 전략은 QA만의 산출물이 아니라 제품·개발·운영이 공유하는 위험 지도입니다.

## 구현 구조가 테스트 층을 좌우한다

테스트 피라미드가 이상해지는 원인은 종종 테스트 도구가 아니라 코드 구조입니다. HTTP handler 안에서 입력 검증, 권한, 할인 계산, SQL, 외부 결제 호출, 이벤트 발행을 모두 처리하면 작은 규칙을 테스트하려 해도 서버를 띄워야 합니다. 도메인 규칙을 명시적 입력과 출력이 있는 함수나 service로 분리하고, 외부 I/O를 adapter 경계 뒤로 보내면 단위 테스트와 통합 테스트가 자연스럽게 나뉩니다.

분리는 테스트만을 위한 추상이 아닙니다. 업무 규칙을 읽고 변경하기 쉬워지고, 외부 provider를 교체하거나 오류를 처리할 위치가 명확해집니다. 다만 모든 코드를 작은 interface로 쪼개라는 뜻은 아닙니다. 단순한 조회 화면까지 과도하게 계층을 만들면 오히려 흐름이 숨겨집니다. 반복해서 E2E에서만 검증되는 중요한 규칙, mock을 만들기 지나치게 어려운 의존성, 많은 테스트가 같은 준비 코드를 복사하는 부분처럼 실제 고통이 있는 곳부터 구조를 개선하는 편이 낫습니다.

시간과 난수도 설계 경계입니다. 만료 시각을 현재 시간에 바로 의존해 계산하면 자정·timezone·DST 같은 경계에서 테스트가 흔들릴 수 있습니다. clock을 입력으로 주거나 테스트 가능한 시간 provider를 두면, 운영에서는 실제 시간을 쓰고 테스트에서는 고정 시각을 쓸 수 있습니다. 주문 번호처럼 난수가 필요한 값도 생성기를 통제하면 기대 결과를 안정적으로 확인할 수 있습니다. 이런 결정성은 production 동작을 가짜로 만드는 것이 아니라, 테스트가 조건을 명확히 표현하게 하는 방법입니다.

## 테스트 데이터와 계정의 수명주기

E2E와 통합 테스트는 데이터 없이는 실행되지 않습니다. 여기서 흔한 실수는 모든 테스트가 `qa@example.com` 같은 하나의 계정을 공유하는 것입니다. 병렬 실행 중 한 테스트가 비밀번호를 바꾸거나 주문을 취소하면 다른 테스트의 시작 조건이 사라집니다. 고유한 사용자·조직·주문 식별자를 만들고, 테스트 종료 뒤 정리하며, 실패했을 때 어떤 데이터가 남았는지 추적할 수 있게 합니다.

하지만 정리만 믿는 전략도 위험합니다. 테스트가 강제 종료되거나 CI runner가 끊기면 cleanup hook은 실행되지 않을 수 있습니다. 전용 tenant·임시 database·짧은 TTL(Time To Live, 자동 만료 시간)·주기적인 삭제 작업처럼 실패 뒤에도 경계를 회복하는 장치를 고려합니다. production 데이터를 test에 복사해야 한다면 개인정보·비밀·결제 정보의 마스킹과 접근 승인을 먼저 다루고, 편의 때문에 운영 계정을 테스트에 사용하지 않습니다.

테스트 계정의 권한도 시나리오에 맞아야 합니다. 일반 사용자, 관리자, 읽기 전용 감사자처럼 서로 다른 역할을 준비하면 권한 우회와 화면 분기를 확인할 수 있습니다. 단, 계정이 늘수록 credential 관리도 복잡해집니다. CI secret에 어떤 값을 두는지, 누가 갱신하는지, 유출 시 어떻게 폐기하는지, 로그와 screenshot에 노출되지 않는지 정합니다. 테스트 자동화도 실제 시스템의 사용자와 데이터를 다루는 소프트웨어이므로 보안 경계를 가볍게 보면 안 됩니다.

## 새 기능을 피라미드에 배치하는 짧은 절차

새 기능을 시작할 때 다음 순서로 논의하면 "나중에 E2E 하나 붙이자"는 습관을 줄일 수 있습니다. 먼저 사용자가 얻는 결과와 실패해선 안 되는 조건을 한 문장으로 적습니다. 다음으로 순수 규칙, 내부 저장 경계, 다른 서비스 계약, 실제 UI·배포 환경의 위험을 나눕니다. 그 뒤 각 위험에 가장 빠르고 결정적인 검증을 하나씩 배정합니다. 마지막으로 자동화하기 어려운 사항과 출시 뒤 관찰할 신호를 기록합니다.

예를 들어 파일 업로드 기능이라면 파일 크기·확장자·권한 판단은 단위 테스트, 실제 object storage에 저장된 뒤 metadata가 transaction과 맞는지는 통합 테스트, 바이러스 검사 서비스의 응답 형식은 계약 또는 sandbox 테스트, 사용자가 화면에서 파일을 선택해 다운로드할 수 있는지는 대표 E2E로 배치할 수 있습니다. 대용량 파일·네트워크 단절·브라우저별 동작까지 전부 매 pull request에서 E2E로 만들 필요는 없습니다. 영향이 큰 조합은 별도 환경이나 release candidate에서 계획적으로 확인합니다.

이 절차의 산출물은 복잡한 아키텍처 문서일 필요가 없습니다. pull request 설명에 위험·테스트·미확인 항목을 몇 줄 적고, 고위험 기능에는 재사용할 수 있는 checklist를 두는 것으로 시작할 수 있습니다. 시간이 지나 동일한 빈틈이 반복되면 그때 shared test helper, contract suite, 환경 개선처럼 더 큰 투자를 판단합니다. 작은 기록이 쌓이면 팀의 피라미드는 유행어가 아니라 실제 실패 이력에 근거한 구조가 됩니다.

## 한계와 적용 기준 Q&A

### Q. 피라미드 모양이 역삼각형이면 테스트 전략이 실패한 건가요?

A. 자동화된 E2E가 많다는 사실만으로 실패라고 단정할 수는 없습니다. 제품이 UI 중심이고 외부 SaaS를 연결하는 일이 핵심이라면 상위 층의 검증이 필요할 수 있습니다. 다만 작은 규칙까지 E2E에 몰려 있는지, 실행 시간이 피드백을 막는지, 실패 원인을 설명할 수 있는지를 점검해야 합니다. 비율 자체보다 각 테스트가 맡은 위험과 비용이 설명 가능한지가 기준입니다.

### Q. 단위 테스트에서 mock을 전혀 쓰지 않는 편이 좋나요?

A. 아닙니다. 시간·난수·네트워크·외부 API처럼 결정성을 해치는 의존성을 대체하면 작은 규칙을 빠르게 검증할 수 있습니다. 문제는 mock이 실제 시스템의 모든 동작을 흉내 내며 진짜 경계를 대신할 때입니다. 중요한 DB·HTTP·메시지 계약은 통합 또는 계약 테스트로 확인하고, mock은 테스트 목적을 좁히는 도구로 사용하세요.

### Q. E2E 테스트가 간헐적으로 실패하면 재시도만 늘리면 되나요?

A. 재시도는 일시적 네트워크 오류를 완화할 수 있지만, 실패 원인을 제거하지는 않습니다. 테스트 데이터 충돌, 준비되지 않은 비동기 상태, 공유 환경, 불안정한 selector, 실제 product 결함을 분류해야 합니다. 재시도 횟수와 실패 artifact를 기록하고, 반복되는 실패는 pass 처리하지 말고 근본 원인을 고쳐야 합니다.

### Q. 커버리지 비율이 높으면 테스트 피라미드도 건강한가요?

A. 커버리지는 실행된 코드 위치를 알려 주는 보조 지표일 뿐, 중요한 업무 결과·오류 처리·권한·통합 경계를 검증했다는 뜻은 아닙니다. 낮은 커버리지가 항상 나쁜 것도 아닙니다. 고위험 요구사항이 어떤 테스트로 보호되는지와, 변경이 실제 사용자 흐름에 미치는 영향을 함께 보세요.

## 마무리

테스트 피라미드는 단위·통합·E2E를 정해진 숫자로 나누는 규칙이 아닙니다. 빠르고 설명 가능한 신호는 아래쪽에 충분히 두고, 실제 경계와 사용자 여정에서만 알 수 있는 위험은 위쪽에서 확인하는 설계 원칙입니다. 기능의 영향, 외부 의존성, 피드백 시간, 결정성, 조사 가능성을 기준으로 각 테스트가 답해야 할 질문을 정하면, 느린 suite를 무작정 늘리지 않으면서도 출시 판단에 필요한 증거를 만들 수 있습니다.
