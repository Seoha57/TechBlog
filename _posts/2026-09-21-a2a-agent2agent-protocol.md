AI 에이전트가 다른 에이전트에게 일을 맡기는 장면이 늘어나면서 “모델끼리 대화하면 된다”는 설명만으로는 부족해졌습니다. 서로 다른 회사와 프레임워크가 만든 에이전트가 어떤 능력을 제공하는지 발견하고, 긴 작업의 상태를 공유하고, 파일과 구조화된 결과를 전달하고, 인증과 권한을 적용해야 하기 때문입니다. A2A(Agent2Agent) 프로토콜은 이 문제를 에이전트 사이의 상호운용성 표준으로 다룹니다.

이 글은 A2A를 특정 SDK 사용법으로 한정하지 않고, 기본 기술부터 운영 경계까지 설명합니다. 공식 사양의 용어를 기준으로 하며, 실제로 연결하지 않은 시스템을 연결했다고 주장하지 않습니다. A2A는 에이전트의 내부 추론이나 도구 구현을 공유하라고 요구하지 않습니다. 오히려 서로 불투명한 에이전트가 선언된 능력과 메시지 계약을 통해 협업하도록 만드는 것이 핵심입니다.

## 기본 기술: 에이전트, API, 프로토콜

에이전트는 단순한 함수와 다릅니다. 사용자의 목표를 해석하고, 계획을 세우고, 도구나 사람과 상호작용하며, 결과를 만들 수 있습니다. 그러나 “에이전트”라는 이름이 붙었다고 해서 서로 연결되는 것은 아닙니다. 한 제품의 내부 객체 이름, 다른 제품의 JSON 필드 이름, 세 번째 제품의 스트리밍 이벤트 형식이 서로 다르면 통합자는 매번 전용 어댑터를 작성해야 합니다.

API는 호출 방법을 정하지만, 프로토콜은 호출의 의미와 상태 전이를 더 넓게 정합니다. HTTP 메서드와 JSON 문법만 맞추는 것으로는 작업이 언제 끝났는지, 중간 결과가 무엇인지, 재시도해도 되는지, 인증 범위가 무엇인지 설명하기 어렵습니다. A2A는 데이터 모델, 추상 연산, 프로토콜 바인딩을 나누어 이 문제를 다룹니다.

MCP는 도구와 데이터의 사용을 에이전트에 연결하는 데 적합합니다. 예를 들어 보고서 에이전트가 사내 DB 조회 도구와 파일 저장 도구를 MCP로 사용할 수 있습니다. A2A는 그 보고서 에이전트가 외부 번역 에이전트나 규정 검토 에이전트에 작업을 맡기는 경로를 표현합니다. 즉 “에이전트가 무엇을 사용할까”와 “에이전트가 누구에게 어떤 일을 맡길까”는 다른 질문입니다.

## A2A의 핵심 객체

Agent Card는 에이전트의 디지털 명함입니다. 이름, 설명, 제공자, 서비스 URL, 지원 인터페이스, 프로토콜 버전, 능력, 인증 요구사항, 입력·출력 모드, 스킬 같은 정보를 선언합니다. 클라이언트는 카드를 보고 해당 에이전트가 자신이 원하는 일을 할 수 있는지, 어떤 전송 방식과 인증을 요구하는지 판단합니다.

사양은 표준화된 발견 경로로 `.well-known/agent-card.json`을 사용할 수 있게 합니다. 조직 내부에서는 레지스트리나 직접 설정을 사용할 수도 있습니다. 중요한 점은 Agent Card가 자격 증명을 담는 비밀 저장소가 아니라는 것입니다. 카드에 토큰을 하드코딩하면 발견 문서가 곧 비밀 유출 경로가 됩니다. 공식 안내처럼 동적 자격 증명과 HTTPS, 필요할 때 서명 검증을 설계해야 합니다.

Message는 에이전트 사이의 의사소통 단위입니다. 메시지에는 발신 역할과 여러 Part가 들어갈 수 있고, Part는 텍스트, 파일, 구조화된 데이터처럼 서로 다른 표현을 담을 수 있습니다. 단순 텍스트만 생각하면 파일 참조의 만료, 미디어 타입, 크기, 무결성, 다운로드 권한 같은 운영 문제를 놓치게 됩니다.

Task는 시간이 걸리는 목표의 수명 주기를 나타냅니다. 클라이언트가 메시지를 보내고 서버가 처리 중인 작업을 만들면, 클라이언트는 현재 상태를 조회하거나 스트리밍 업데이트를 받을 수 있습니다. 작업이 완료되거나 실패하거나 취소되는 상태를 명시하면, 사용자는 화면을 닫았다가 다시 열어도 진행 상황을 이어서 확인할 수 있습니다.

Artifact는 작업의 결과물입니다. 답변 텍스트, 파일, JSON 보고서, 중간 산출물 등 실제로 소비할 결과를 표현합니다. 메시지와 결과물을 구분하면 “요청에 대한 대화”와 “저장·전달해야 하는 산출물”을 서로 다른 정책으로 다룰 수 있습니다. 예를 들어 최종 PDF는 오래 보관하지만 중간 추론 텍스트는 저장하지 않는 규칙을 만들 수 있습니다.

## A2A 작업 흐름을 단계별로 보기

첫 단계는 발견입니다. 클라이언트 에이전트가 검토 에이전트의 Agent Card를 읽고 이름, 설명, 스킬, 입력 형식, 출력 형식, 인증 방식, 엔드포인트를 확인합니다. 여기서 스킬 설명을 자연어 문구 하나로만 판단하지 말고, 허용 입력과 실패 조건을 조직의 카탈로그와 대조해야 합니다.

두 번째는 인증과 인가입니다. 클라이언트는 카드에 표시된 방식에 따라 토큰이나 다른 자격 증명을 준비합니다. 서버는 “A2A 요청인가”만 보지 않고, 호출 주체가 이 스킬을 사용할 권한이 있는지, 특정 테넌트 데이터에 접근해도 되는지, 요청된 결과 범위가 정책에 맞는지 확인합니다. 인증이 성공했다고 모든 작업이 허용되는 것은 아닙니다.

세 번째는 메시지 전송입니다. 짧은 질문이라면 `message/send`와 같은 동기 흐름으로 결과를 받을 수 있습니다. 긴 문서 분석이나 사람 승인 대기라면 서버는 Task를 만들고 처리 중 상태를 반환할 수 있습니다. 클라이언트는 응답이 늦었다는 이유만으로 같은 요청을 무조건 재전송하면 안 됩니다. 멱등성 키와 작업 ID를 사용해 중복 실행을 구분해야 합니다.

네 번째는 상태 관찰입니다. 폴링은 구현이 단순하지만 요청 수가 늘고 지연이 생깁니다. 스트리밍은 진행 상태를 빨리 보여줄 수 있지만 연결 유지, 재연결, 이벤트 중복, 마지막 이벤트 복구를 설계해야 합니다. 푸시 알림은 서버가 클라이언트에 상태 변화를 알리는 방식이지만, callback endpoint의 인증과 위조 요청 방어가 필요합니다.

마지막은 결과 검증과 종료입니다. 성공 Task라고 해서 결과가 업무적으로 옳다는 뜻은 아닙니다. 스키마 검증, 출처 확인, 파일 바이러스 검사, 정책 필터, 사람 승인 단계를 둬야 할 수 있습니다. 서버는 작업이 완료되었다는 상태와 실제 Artifact의 접근 권한을 별도로 관리해야 합니다.

## 전송 바인딩과 선택 기준

A2A의 추상 모델은 특정 네트워크 기술에 묶이지 않습니다. 공식 사양과 생태계 문서에는 JSON-RPC, HTTP+JSON/REST, gRPC 같은 바인딩이 등장합니다. 핵심 데이터 모델과 작업 의미가 같더라도 전송에 따른 헤더, 오류, 스트림 표현, 연결 관리 방식은 다를 수 있습니다.

HTTP+JSON은 브라우저, API gateway, 관찰 도구와 결합하기 쉽습니다. 인증 프록시와 rate limit을 기존 HTTP 인프라에 넣기 편하고, 운영자가 요청을 재현하기도 상대적으로 쉽습니다. 반면 긴 스트림은 proxy timeout과 buffering 설정의 영향을 받습니다. JSON-RPC는 메서드와 요청 ID가 분명해 에이전트 호출 의미를 표현하기 좋지만, 일반 HTTP 관례와 오류 매핑을 팀이 이해해야 합니다.

gRPC는 강한 스키마와 효율적인 스트리밍을 제공할 수 있지만, 브라우저 직접 호출과 기업 네트워크 중간 장비에서 추가 고려가 필요합니다. 한 조직이 내부망 에이전트만 연결한다면 gRPC가 자연스러울 수 있고, 외부 파트너와 공개적으로 연결한다면 HTTP+JSON이 운영 경계에 맞을 수 있습니다. A2A를 도입한다고 모든 바인딩을 동시에 구현할 필요는 없습니다.

바인딩 선택은 “가장 최신인 것”이 아니라 소비자와 운영 환경으로 결정합니다. 기존 observability가 HTTP 요청과 SSE를 잘 수집한다면 그 경로부터 시작할 수 있습니다. 여러 언어의 SDK가 gRPC를 안정적으로 지원하고 내부 네트워크가 통제된다면 gRPC를 선택할 수 있습니다. 중요한 것은 Agent Card의 supported interfaces에 실제로 지원하는 바인딩과 버전을 정확히 선언하는 것입니다.

## 메시지와 데이터 계약 설계

텍스트 메시지만으로 빠르게 시작할 수 있지만, 업무 결과가 구조화되어 있다면 JSON 스키마를 함께 정의해야 합니다. 예를 들어 규정 검토 에이전트가 반환하는 결과에는 문서 ID, 규정 조항, 심각도, 근거 위치, 권고 조치, 검토 상태가 필요할 수 있습니다. 자연어 설명만 저장하면 이후 집계와 재검토가 어렵습니다.

파일 Part에는 파일의 목적과 미디어 타입을 명확히 합니다. “보고서.pdf”라는 이름만으로는 콘텐츠가 신뢰된다는 보장이 없습니다. 크기 제한, 다운로드 URL 만료, SHA-256 해시, 문서 소유 테넌트, 악성 파일 검사 결과를 별도 메타데이터로 둘 수 있습니다. 외부 에이전트가 반환한 URL을 서버가 내부 네트워크에서 그대로 가져오게 만들면 SSRF 위험이 생기므로 허용 도메인과 네트워크 정책을 적용해야 합니다.

확장 필드는 사양의 기본 의미를 깨뜨리지 않는 방식으로 사용해야 합니다. 사양이 정의하지 않은 필드를 임의로 필수화하면 다른 구현과 상호운용되지 않을 수 있습니다. 조직 전용 확장을 만들 때는 이름공간, 버전, 선택 여부, 실패 시 동작, 개인정보 포함 여부를 문서화합니다. 클라이언트와 서버가 확장을 협상하거나 지원하지 않는 요청을 명확한 오류로 거절해야 합니다.

## 장시간 작업, 스트리밍, 사람 승인

에이전트 작업은 일반 API보다 오래 걸릴 수 있습니다. 대용량 PDF 분석, 여러 시스템 조회, 승인 대기, 외부 배치 실행이 포함되기 때문입니다. 이때 HTTP 요청 하나를 끝까지 잡고 있는 구조는 timeout과 리소스 점유 문제를 만듭니다. Task를 먼저 만들고 상태를 저장하는 구조가 확장에 유리합니다.

상태는 서버의 내부 프롬프트나 추론 토큰이 아니라 클라이언트가 이해할 수 있는 업무 상태여야 합니다. 예를 들어 submitted, working, input-required, completed, failed, canceled 같은 의미를 화면과 재시도 정책에 매핑합니다. `working`이라는 상태만 계속 보내면 사용자는 실제 진척을 알 수 없으므로, 가능한 경우 현재 단계와 예상하지 않은 대기 이유를 Artifact 또는 상태 메시지로 전달합니다.

스트리밍에서는 마지막으로 받은 이벤트를 기록해야 합니다. 네트워크가 끊긴 뒤 처음부터 모든 이벤트를 다시 받으면 중복 결과가 생길 수 있습니다. 이벤트 ID 또는 Task 상태 조회를 사용해 클라이언트가 현재 상태를 재동기화하도록 설계합니다. SSE는 양방향 통신이 아니므로 클라이언트의 추가 입력은 별도 요청으로 보내야 합니다.

사람 승인이 필요한 Task는 승인 주체와 만료 시각을 명시합니다. “사람이 확인했다”는 문자열만 저장하는 대신, 누가 어떤 권한으로 어느 버전의 입력과 결과를 승인했는지 감사 기록을 남깁니다. 승인 전에 Artifact가 바뀌면 기존 승인과 새 결과를 연결하지 않아야 합니다. 에이전트 간 자동화라도 고위험 행동은 사람의 명시적 확인을 요구할 수 있습니다.

## 오류, 재시도, 멱등성

분산 호출에서 timeout은 성공과 실패를 동시에 의미할 수 있습니다. 클라이언트가 응답을 받지 못했다고 서버가 작업을 실행하지 않았다는 뜻은 아닙니다. 따라서 요청 ID와 멱등성 키를 서버에 저장하고, 같은 키의 재요청이 기존 Task를 반환하게 만드는 설계가 중요합니다.

재시도할 오류와 재시도하지 않을 오류를 구분합니다. 일시적인 네트워크 오류, rate limit, 서비스 일시 중단은 지수 백오프와 jitter를 사용할 수 있습니다. 잘못된 입력, 권한 없음, 지원하지 않는 미디어 타입은 같은 요청을 반복해도 해결되지 않습니다. 인증 만료는 토큰 갱신 후 재시도할 수 있지만, 갱신 실패를 무한 재시도로 만들면 안 됩니다.

서버는 실패를 단순한 “500”으로만 표현하지 말고, 클라이언트가 다음 행동을 판단할 수 있는 오류 범주와 안전한 설명을 제공합니다. 내부 stack trace, 프롬프트, 비밀값, 다른 테넌트의 식별자를 오류 메시지에 넣지 않습니다. 클라이언트 로그에도 전체 입력 문서나 토큰을 그대로 남기지 않도록 합니다.

작업 취소도 실제 취소와 취소 요청 접수를 구분해야 합니다. 이미 외부 결제나 배치가 시작되었다면 네트워크 요청을 끊는 것만으로 되돌릴 수 없습니다. 서버는 취소 가능 시점과 보상 작업을 정의하고, 취소 불가능한 상태에는 사용자에게 정확한 안내를 합니다.

## 보안과 신뢰 경계

A2A는 다른 에이전트의 출력을 자동으로 신뢰하라는 프로토콜이 아닙니다. 원격 에이전트가 반환한 텍스트는 데이터일 수 있고, 그 안에 추가 도구 호출을 지시하는 프롬프트 인젝션이 들어 있을 수 있습니다. 오케스트레이터는 외부 결과와 시스템 지시를 분리하고, 민감한 도구 호출은 정책 엔진이나 사람 승인을 거쳐야 합니다.

Agent Card도 입력입니다. 카드의 스킬 설명이나 문서 URL을 모델 프롬프트에 그대로 넣으면 악성 지시가 전파될 수 있습니다. 카드의 JSON 스키마와 허용 URL을 검증하고, 길이와 필드 수를 제한하며, 정책에 맞는 에이전트만 레지스트리에 등록합니다. 카드 서명을 사용한다면 서명 검증 실패 시 안전한 기본 동작을 정의해야 합니다.

테넌트 격리는 엔드포인트 수준만으로 충분하지 않습니다. 같은 A2A 서버가 여러 테넌트를 서비스한다면 Agent Card와 요청의 tenant 필드, 토큰의 주체, Task 소유자, Artifact 접근 권한이 일관되게 묶여야 합니다. 추측 가능한 Task ID를 사용하더라도 다른 테넌트의 작업이 조회되지 않도록 서버 측 인가를 매번 수행합니다.

관찰 데이터에도 민감정보가 들어갑니다. 프롬프트, 파일 이름, Artifact 내용, 오류 메시지, Agent Card가 로그와 trace에 수집될 수 있습니다. 수집 목적과 보관 기간을 정하고, 기본은 최소 필드로 두며, 운영 디버깅이 끝나면 샘플링이나 마스킹을 적용합니다. 분산 trace의 상관 ID는 유용하지만 사용자 메시지나 비밀 토큰을 ID로 쓰면 안 됩니다.

## 에이전트 레지스트리와 신뢰 수준

조직에 에이전트가 많아지면 `.well-known` 주소를 하나씩 설정하는 방식만으로는 운영이 어려워집니다. 레지스트리는 Agent Card의 위치와 소유자, 검토 상태, 제공 환경, 버전, 신뢰 수준을 관리할 수 있습니다. 다만 레지스트리에 등록되었다는 사실이 모든 입력과 출력이 안전하다는 뜻은 아닙니다. 등록 심사와 호출 시점 검증을 분리해야 합니다.

신뢰 수준을 나눌 때는 “내부”, “승인된 파트너”, “외부 공개”처럼 네트워크 위치만 보지 않습니다. 데이터 접근 범위, 외부 도구 사용 가능성, 결과가 사람 승인 없이 행동으로 이어지는지, 보안 담당자가 카드와 구현을 검토했는지를 함께 봅니다. 내부망에 있다는 이유만으로 외부 결과를 신뢰하면 공급망 경계가 약해집니다.

카드의 버전과 스킬 버전도 운영 자산입니다. 동일한 URL에서 카드의 스킬 설명과 입력 요구사항이 갑자기 바뀌면 클라이언트가 잘못된 형식의 요청을 만들 수 있습니다. 카드 변경을 배포 변경으로 취급하고, 호환 가능한 필드 추가와 호환되지 않는 필드 변경을 구분합니다. 새 버전이 준비되면 일정 기간 이전 인터페이스를 함께 제공하는 방식이 안전합니다.

## 오케스트레이션과 책임 분배

A2A를 여러 에이전트의 자유로운 대화로 설명하면 책임이 불명확해집니다. 오케스트레이터가 있다면 어떤 에이전트를 왜 선택했는지, 입력을 어떤 범위로 줄였는지, 최종 결과를 누가 승인했는지 기록해야 합니다. 각 에이전트가 서로를 무한히 호출할 수 있게 두지 말고 최대 깊이와 최대 호출 수를 둡니다.

작업 위임은 데이터 최소화부터 시작합니다. 원본 문서 전체가 아니라 필요한 문단과 업무 ID만 보내고, 원격 에이전트가 결과에 원본 개인정보를 재생산하지 않도록 출력 정책을 둡니다. 원본을 반드시 보내야 한다면 보관 기간, 암호화, 접근 로그, 삭제 요청 처리까지 계약에 넣습니다.

결정권의 위치도 명확히 합니다. 번역 에이전트가 언어 변환만 하는지, 법적 판단까지 하는지에 따라 허용 권한과 검증이 달라집니다. “전문 에이전트”라는 설명은 업무 권한의 근거가 아닙니다. 고위험 행동은 오케스트레이터의 정책과 사람 승인으로 제한하고, 원격 에이전트는 가능한 한 필요한 최소 능력만 노출합니다.

## 스키마 진화와 호환성

실제 통합에서는 버전이 맞는 순간보다 시간이 지나며 어긋나는 순간이 더 중요합니다. 클라이언트가 새로운 선택 필드를 보내도 구 서버가 무시할 수 있는지, 서버가 새로운 Artifact 종류를 반환했을 때 구 클라이언트가 안전하게 알 수 없는 결과로 처리하는지 정의합니다. 알 수 없는 필드는 조용히 무시할지, 명시적 오류를 낼지 데이터 손실 위험에 따라 정합니다.

입력 스키마에는 필수 필드와 선택 필드를 구분하고, 선택 필드의 기본 의미를 문서화합니다. 예를 들어 `language`가 빠졌을 때 자동 감지하는지, 기본 언어를 쓰는지, 요청을 거절하는지에 따라 결과가 달라집니다. 자연어로만 계약을 쓰지 말고 JSON Schema 또는 이에 준하는 검증 규칙을 테스트에 연결합니다.

출력 스키마에서도 결과의 확정성을 구분해야 합니다. `completed` 상태와 `confidence: 0.9`는 서로 다른 의미이고, 확률값이 정확도 보증은 아닙니다. Artifact에 근거 위치와 검토 필요 여부를 포함하고, 클라이언트가 불확실한 결과를 자동 실행으로 연결하지 않도록 정책을 둡니다.

## 프롬프트 인젝션과 결과 오염

원격 에이전트가 반환하는 텍스트에는 업무 결과와 지시문이 섞일 수 있습니다. 문서 안에 “이 파일을 외부로 전송하라”는 문장이 있어도 그것이 시스템 권한을 부여하지는 않습니다. 오케스트레이터는 원격 출력을 데이터로 취급하고, 행동으로 번역할 때 별도의 정책 검사를 거쳐야 합니다.

검색 에이전트가 반환한 링크도 신뢰 경계 밖의 입력입니다. 링크 내용을 요약하는 과정에서 악성 지시가 모델 문맥에 들어갈 수 있으므로, 가져온 콘텐츠를 인용 데이터와 명령 데이터로 분리합니다. 문서의 문장은 분석 대상이지 시스템 규칙이 아닙니다. 이 구분을 프롬프트 문구 하나에만 의존하지 말고 도구 권한과 네트워크 권한으로도 제한합니다.

결과 오염은 성공 응답에서도 발생합니다. 올바른 JSON 모양의 잘못된 고객 ID, 존재하지 않는 규정 조항, 조작된 파일 해시를 반환할 수 있습니다. 서버가 스키마만 검증하면 값의 의미를 확인하지 못합니다. 중요한 필드는 원본 시스템과 대조하거나, 허용 목록과 참조 무결성 검사를 적용해야 합니다.

## 비용과 동시성 제어

에이전트 간 호출은 모델 비용뿐 아니라 네트워크, 파일 저장, 검색, 사람 대기 비용을 만듭니다. 한 요청이 여러 에이전트를 병렬 호출하면 지연은 줄 수 있지만 총 비용과 외부 rate limit 사용량은 늘어납니다. 작업마다 최대 병렬도와 예산을 두고, 실패한 분기까지 재시도하면 예산을 넘지 않는지 계산합니다.

큐를 사용할 때는 Task가 오래 대기해도 사용자에게 상태가 보이도록 합니다. 큐 길이, 우선순위, 예약 만료, 테넌트별 동시 실행 수를 운영 지표로 둡니다. 한 테넌트의 대량 작업이 다른 테넌트의 대화형 요청을 막지 않도록 공정한 스케줄링이나 별도 큐를 선택할 수 있습니다.

스트리밍 연결을 많이 유지하면 웹 서버와 프록시의 파일 디스크립터, 메모리, heartbeat 비용이 증가합니다. 연결 타임아웃과 재연결 backoff를 정의하고, 스트림이 끊겨도 Task 자체가 취소되지 않는지 계약에 명시합니다. 클라이언트가 화면을 닫았다는 이유로 서버 작업을 중단할지 여부도 UX와 비용 정책의 결정입니다.

## 구현 스켈레톤을 읽는 법

다음은 특정 SDK에 종속되지 않는 개념적 요청 예시입니다.

```json
{
  "jsonrpc": "2.0",
  "id": "req-20260921-001",
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "parts": [{"kind": "text", "text": "이 문서의 규정 위반 항목을 구조화해 주세요."}]
    },
    "metadata": {"tenant": "example", "idempotency_key": "work-123"}
  }
}
```

이 예시는 실제 사양의 모든 필드를 다 보여주지 않습니다. 중요한 부분은 요청 ID와 멱등성 키를 혼동하지 않는 것입니다. 요청 ID는 RPC 응답을 대응시키는 값이고, 멱등성 키는 재전송이 같은 업무 작업인지 판단하는 값입니다. 서버는 둘을 별도의 의미로 저장해야 합니다.

응답이 Task라면 클라이언트는 결과가 바로 없다고 오류로 처리하지 않습니다. Task ID를 저장하고, 서버가 요구하는 방식으로 상태를 조회하거나 스트림을 구독합니다. `input-required`와 같은 상태가 오면 사용자의 추가 입력을 받아 같은 Task에 연결하고, 완료되면 Artifact를 다운로드하고 검증합니다.

서버 구현에서 중요한 부분은 모델 호출 코드보다 경계 코드입니다. Agent Card 생성, 인증 미들웨어, 입력 스키마 검증, 파일 제한, Task 저장, 상태 전이, 오류 매핑, 감사 로그를 분리합니다. 내부 모델을 바꾸더라도 외부 A2A 계약이 안정적이면 클라이언트가 매번 변경되지 않습니다.

## 품질 평가의 최소 단위

A2A 시스템의 평가는 에이전트 단위와 대화 단위를 함께 봐야 합니다. 단일 에이전트가 좋은 답을 내는지와, 오케스트레이터가 올바른 에이전트를 선택하는지는 다른 측정입니다. 또한 중간 에이전트가 내놓은 결과를 최종 에이전트가 잘못 해석하는 상호운용성 오류가 있을 수 있습니다.

평가 데이터에는 정상 요청, 빈 입력, 모호한 입력, 권한 없는 요청, 큰 파일, 악성 문서, 중복 요청, 부분 장애, 사람 승인 대기를 포함합니다. 결과 정확도 외에 올바른 오류를 냈는지, 민감한 데이터를 누설하지 않았는지, 불필요한 호출을 만들지 않았는지도 점수에 넣습니다.

회귀 테스트는 Agent Card 변경과 함께 실행합니다. 스킬 설명을 바꾸거나 입력 모드를 추가한 뒤 기존 클라이언트가 계속 동작하는지 확인하고, Task 상태가 바뀌었을 때 UI와 자동화가 멈추지 않는지 검증합니다. 모델 버전 변경도 프로토콜 계약 테스트와 분리하지 말고 같은 배포 검증 흐름에 포함합니다.

## MCP와 A2A를 함께 배치하는 예

문서 검토 오케스트레이터를 예로 들어 보겠습니다. 오케스트레이터는 MCP로 내부 문서 저장소와 티켓 시스템을 사용합니다. 법무 검토 에이전트와 번역 에이전트는 A2A로 발견하고 호출합니다. 오케스트레이터가 문서를 읽어 필요한 부분만 원격 에이전트에 보내고, 원격 결과를 검증한 뒤 내부 티켓을 업데이트하는 구조입니다.

이 구조에서 원격 에이전트는 내부 저장소에 직접 접근하지 않습니다. 필요한 문서 Part와 제한된 메타데이터를 전달받고, 검토 결과 Artifact를 반환합니다. 이렇게 하면 데이터 경계가 분명해지고, 원격 에이전트의 도구 구현을 오케스트레이터가 알 필요가 없습니다. 반대로 모든 에이전트에 내부 DB 자격 증명을 공유하면 A2A가 있어도 격리 효과가 사라집니다.

실패 시 오케스트레이터는 세 가지 상태를 나눕니다. 원격 에이전트가 입력을 거절한 경우는 사용자에게 수정 요청을 보여주고, 일시적인 통신 오류는 재시도 큐로 보내며, 결과 검증이 실패한 경우는 사람 검토로 보냅니다. 각 상태가 같은 “실패”로 합쳐지면 운영자는 어느 레이어를 고쳐야 할지 알 수 없습니다.

## 도입 순서와 테스트

처음부터 여러 에이전트를 자동으로 연결하지 않습니다. 먼저 하나의 읽기 중심 작업을 선택하고, Agent Card의 최소 필드와 한 가지 바인딩, 동기 메시지, 구조화 결과를 구현합니다. 이후 긴 Task와 상태 조회를 추가하고, 필요할 때 스트리밍과 사람 승인을 붙입니다. 범위를 작게 하면 프로토콜 적합성과 업무 정확성을 분리해서 검증할 수 있습니다.

계약 테스트에는 카드 스키마, 지원 프로토콜 버전, 필수 입력 모드, 인증 실패, 권한 거부, 잘못된 Part, 너무 큰 파일, 중복 요청, Task 재조회, 취소, 서버 재시작 후 상태 복구를 포함합니다. 성공 응답만 테스트하면 상호운용성의 가장 중요한 부분을 놓치게 됩니다.

장애 테스트는 네트워크 단절, 지연, 중복 전달, 순서 역전, 스트림 재연결, 원격 에이전트의 부분 장애를 포함해야 합니다. 테스트 결과는 “재시도했다”가 아니라 중복 작업이 생성되지 않았는지, 데이터가 다른 테넌트로 가지 않았는지, 최종 Artifact가 무결성을 유지했는지로 판단합니다.

보안 테스트에서는 카드의 악성 URL, 프롬프트 인젝션, 권한 상승 요청, SSRF, 파일 폭탄, 로그의 비밀값 노출을 확인합니다. 에이전트가 외부 시스템을 조작할 수 있다면 dry-run과 승인 경로를 테스트 환경에 둡니다. 모델이 합리적인 답을 했는지뿐 아니라 프로토콜 경계가 지켜졌는지가 검증 대상입니다.

## 운영 지표와 비용

A2A의 운영 지표는 모델 품질만으로 구성되지 않습니다. Agent Card 조회 성공률, 인증 실패율, Task 생성 수, 상태별 체류 시간, 완료율, 취소율, 재시도율, 스트림 재연결 횟수, Artifact 다운로드 오류, 원격 호출별 비용을 수집해야 합니다. 에이전트별로 나누고 테넌트 개인정보를 직접 라벨에 넣지 않는 방식이 좋습니다.

지연시간은 전체 요청 하나의 값으로만 보지 않습니다. 발견 시간, 인증 시간, 큐 대기 시간, 모델 처리 시간, 외부 도구 시간, Artifact 생성 시간, 클라이언트 전달 시간을 분리합니다. 그래야 “A2A가 느리다”는 모호한 결론 대신 어느 구간을 개선할지 판단할 수 있습니다.

비용 제한도 Agent Card와 정책에 반영할 수 있습니다. 요청자별 최대 실행 시간, 최대 파일 크기, 허용 모델, 외부 호출 횟수, 일일 예산, 사람 승인 기준을 둡니다. 원격 에이전트가 비용을 직접 알지 못하더라도 오케스트레이터가 Task를 생성하기 전에 예산을 예약하고, 결과를 받은 뒤 실제 비용을 기록할 수 있습니다.

A2A는 에이전트를 마법처럼 협업시키는 프레임워크가 아니라, 서로 다른 에이전트가 능력을 발견하고 작업을 요청하고 상태와 결과를 교환하기 위한 공통 경계입니다. 시작할 때는 하나의 스킬과 하나의 결과 계약으로 작게 만들고, Task 수명 주기와 오류·멱등성·보안을 먼저 검증하는 편이 좋습니다. MCP는 도구 접근, A2A는 에이전트 간 협업이라는 구분을 유지하면 시스템의 책임 경계도 선명해집니다.
