같은 버튼을 눌렀고 같은 문구가 화면에 보인다고 해서 화면 품질까지 같다고 말할 수는 없습니다. 긴 상품명이 가격을 밀어 냈을 수 있고, 배포 뒤 폰트가 바뀌어 표가 두 줄로 접혔을 수 있으며, 결제 버튼의 색 대비가 약해져도 DOM(Document Object Model, 브라우저가 화면을 객체 구조로 표현한 것) 검사만으로는 놓치기 쉽습니다. 사람의 눈으로 모든 화면과 모든 화면 크기를 매번 비교하는 일은 오래 걸리고, 무엇을 지난 배포와 비교했는지도 남기기 어렵습니다.

**시각 회귀 테스트(visual regression testing)** 는 이전에 승인한 화면 이미지와 현재 실행한 화면 이미지를 비교해, 의도하지 않은 시각적 변화를 찾는 테스트입니다. 여기서 회귀는 새 기능을 넣은 뒤 기존에 맞던 모양이나 동작이 깨지는 현상을 뜻합니다. Playwright는 브라우저 자동화 도구이며, Playwright Test는 `toHaveScreenshot()`으로 기준 이미지와 현재 스크린샷을 비교하는 기능을 제공합니다. 이 글은 특정 서비스에서 성능이나 안정성을 측정한 결과가 아니라 Playwright 공식 문서를 바탕으로 테스트를 설계하는 방법을 정리한 학습 글입니다.

## 먼저 알아둘 기반 기술: 브라우저 렌더링, DOM, 픽셀, E2E 테스트

웹 브라우저는 HTML(HyperText Markup Language, 문서 구조를 표현하는 언어), CSS(Cascading Style Sheets, 모양과 배치를 표현하는 규칙), JavaScript(웹페이지 동작을 구현하는 언어)를 받아 화면을 그립니다. HTML의 버튼 요소가 존재하는지 보는 테스트와, 그 버튼이 실제로 어느 위치·크기·색으로 그려졌는지 보는 테스트는 질문이 다릅니다. 전자는 DOM 구조에 가깝고 후자는 브라우저가 계산한 최종 픽셀에 가깝습니다.

**픽셀(pixel)** 은 화면을 구성하는 작은 점입니다. 시각 비교는 기준 이미지와 현재 이미지의 같은 좌표를 비교하여 다른 픽셀을 찾습니다. 다만 “픽셀이 하나라도 다르면 실패”라는 단순 규칙만 쓰면 글자 가장자리의 미세한 안티앨리어싱, 운영체제의 폰트 처리, GPU(Graphics Processing Unit, 그래픽 처리 장치) 렌더링 차이까지 결함으로 보게 됩니다. 그래서 비교 도구는 허용 오차와 차이 픽셀 비율 같은 기준을 제공하지만, 수치를 크게 잡아 진짜 버튼 위치 이동까지 통과시키면 검사의 의미가 사라집니다.

**E2E(End-to-End, 처음부터 끝까지) 테스트** 는 사용자가 브라우저에서 페이지를 열고 입력하고 결과를 보는 흐름을 실제에 가깝게 확인하는 테스트입니다. Playwright는 페이지 이동, 요소 클릭, 입력, 대기, 스크린샷 촬영을 자동화할 수 있습니다. 스크린샷 비교는 E2E 시나리오 중 “이 단계의 화면이 이전 승인본과 같은가”를 묻는 검사 하나입니다. 로그인 API가 성공했는지, 데이터베이스에 주문이 하나만 저장됐는지 같은 사실은 API·통합 테스트로 따로 증명해야 합니다.

**기준선(baseline 또는 golden image)** 은 팀이 정상이라고 승인한 이미지입니다. 첫 실행에서 생성된 파일이 저절로 품질 기준이 되는 것은 아닙니다. 예를 들어 새 장바구니 페이지를 구현한 뒤 QA가 가격, 할인 문구, 모바일 줄바꿈을 검토하고 승인한 이미지가 기준선이 됩니다. 다음 실행에서 현재 이미지가 그 기준선과 다르면 테스트는 차이 이미지와 함께 실패를 알려 줍니다. 기준선은 테스트 코드와 마찬가지로 변경 이력과 리뷰 대상에 포함하는 것이 좋습니다.

## 왜 DOM 검사만으로 부족한가

DOM 기반 검사는 빠르고 의도가 분명합니다. `button`이 활성화됐는지, 오류 메시지가 노출됐는지, 폼 필드에 값이 들어갔는지를 정확히 물을 수 있습니다. 하지만 CSS의 `display`, `overflow`, `z-index`, `font-size`, 반응형 미디어 쿼리(media query, 화면 조건에 따라 스타일을 바꾸는 CSS 규칙) 문제는 요소가 DOM에 존재해도 사용자가 보지 못하게 만들 수 있습니다. 모달 뒤에 버튼이 깔리거나 긴 문장이 잘리거나, 모바일에서 두 개의 카드가 겹치는 문제는 최종 화면을 함께 봐야 발견하기 쉽습니다.

예를 들어 주문 완료 화면에서 DOM 테스트가 “주문 번호” 텍스트가 존재한다고 확인했다고 합시다. CSS 변경으로 좁은 화면에서 주문 번호가 푸터 아래로 밀려나거나 흰 글자가 흰 배경에 놓이면 텍스트는 여전히 존재합니다. 반대로 시각 비교만으로 주문 번호가 서버가 준 값과 맞는지 알 수는 없습니다. 좋은 테스트는 DOM 검사에 “정확한 주문 번호를 표시하는가”를, 시각 비교에 “그 정보가 지정한 화면 크기에서 읽을 수 있게 배치되는가”를 맡깁니다.

시각 검사가 특히 유용한 영역은 공통 UI입니다. 헤더, 디자인 시스템의 버튼·입력창, 오류 배너, 표, 카드, 다국어 문장이 들어가는 영역처럼 한 번의 CSS 변경이 여러 기능에 영향을 주는 곳입니다. 반면 실시간 차트, 지도, 동영상 프레임, 사용자마다 달라지는 추천 목록처럼 본래 결과가 매번 달라지는 화면은 별도 고정 전략 없이 전면 이미지 비교에 넣기 어렵습니다. 테스트 대상 전체를 무작정 캡처하는 것보다 실패했을 때 사람이 판단 가능한 영역부터 고르는 편이 낫습니다.

## Playwright의 스크린샷 비교는 어떻게 동작하나

Playwright Test에서 `await expect(page).toHaveScreenshot('checkout.png')`처럼 작성하면 테스트 러너는 현재 페이지를 안정된 상태로 캡처하고, 같은 이름의 기준 이미지를 찾아 비교합니다. 기준 이미지가 없으면 처음 실행은 새 스냅샷을 만들었다고 알려 줍니다. 이후 실행은 현재 이미지, 기대 이미지, 차이 이미지를 결과물로 남겨 리뷰자가 어느 영역이 달라졌는지 확인할 수 있게 합니다. 기준 이미지의 경로와 파일명은 테스트 파일, 브라우저 프로젝트, 운영체제별 설정에 따라 달라질 수 있으므로 팀은 저장 규칙을 정해 두는 편이 좋습니다.

```ts
import { test, expect } from '@playwright/test';

test('결제 확인 화면의 주요 정보가 읽히게 배치된다', async ({ page }) => {
  await page.setViewportSize({ width: 1440, height: 900 });
  await page.goto('/checkout/complete?order=sample');
  await expect(page.getByRole('heading', { name: '주문이 완료되었습니다' })).toBeVisible();
  await expect(page).toHaveScreenshot('checkout-complete-desktop.png', {
    fullPage: true,
    maxDiffPixelRatio: 0.001,
  });
});
```

이 예시에서 화면 크기를 고정한 이유는 반응형 레이아웃의 입력 조건을 명시하기 위해서입니다. `fullPage: true`는 보이는 창만이 아니라 스크롤 가능한 문서 전체를 하나의 긴 이미지로 비교합니다. 긴 문서에 편리하지만, 페이지 아래의 추천 상품이나 날짜처럼 변동 요소까지 포함될 수 있습니다. 상단 요약 카드만 중요한 경우에는 전체 페이지가 아니라 `locator`로 특정 요소의 스크린샷을 찍는 편이 실패 원인을 더 좁게 보여 줍니다.

`maxDiffPixelRatio`는 다른 픽셀의 비율 허용 한도입니다. 값은 팀의 렌더링 환경과 화면 특성에 맞춰 실험적으로 정해야 하며, 인터넷에서 본 값을 그대로 복사하면 안 됩니다. 비율을 높이면 폰트의 작은 차이에는 덜 흔들리지만, 작은 아이콘이나 얇은 테두리의 실제 결함도 놓칠 수 있습니다. 먼저 환경을 고정하고, 어떤 정상 차이를 허용할지 문서화한 뒤 최소한의 한도를 선택합니다. 숫자는 테스트를 안정시키는 마법이 아니라 품질 위험을 팀이 어디까지 받아들이는지 드러내는 정책입니다.

## 기준선을 만들기 전 고정해야 할 조건

첫째, 브라우저와 운영체제 환경을 가능한 한 동일하게 맞춥니다. Playwright 공식 문서는 호스트 OS, 브라우저 버전, 설정, 하드웨어, 전원 상태, 헤드리스(headless, 창을 띄우지 않는 실행 방식) 여부가 렌더링 결과에 영향을 줄 수 있다고 설명합니다. 개발자의 Windows 노트북에서 만든 기준선을 Linux CI(Continuous Integration, 코드 변경 때 자동 검사하는 환경)에서 비교하면 글자와 그림자가 달라질 수 있습니다. 기준선 생성과 비교를 같은 CI 이미지에서 수행하는 방식이 흔한 이유입니다.

둘째, 데이터와 시간을 통제합니다. “오늘의 추천”, 현재 시각, 환율, 무작위 정렬, 외부 광고, 원격 프로필 사진은 테스트 실행 때마다 달라질 수 있습니다. 테스트 전용 API 응답을 준비하거나 네트워크 요청을 가로채 고정 응답을 돌려주고, 시계와 난수의 입력을 고정해야 합니다. 단, 실제 운영 API를 완전히 흉내 낸 고정 응답만 쓰면 계약 변화가 가려질 수 있으므로, API 계약 테스트나 통합 테스트를 별도로 유지하는 것이 좋습니다.

셋째, 웹 폰트가 모두 로드된 뒤 촬영합니다. 폰트가 늦게 내려오면 브라우저는 임시 폰트로 먼저 그렸다가 나중에 다시 배치합니다. 이를 FOUT(Flash of Unstyled Text, 스타일 없는 글자가 잠시 보이는 현상) 또는 글꼴 교체에 따른 레이아웃 이동으로 경험할 수 있습니다. 페이지 이동 직후 즉시 이미지를 찍으면 어떤 실행에서는 정상이고 어떤 실행에서는 줄바꿈이 다른 결과가 나올 수 있습니다. 네트워크가 조용해졌다는 사실만으로 웹 폰트와 애니메이션이 모두 안정됐다고 단정하지 말고, 테스트 대상의 준비 조건을 명시합니다.

넷째, 애니메이션과 전환 효과를 다룹니다. 버튼이 천천히 이동하거나 로딩 스켈레톤이 깜빡이는 중에 캡처하면 실행 시점에 따라 서로 다른 픽셀이 생깁니다. 검증 목적이 애니메이션 자체가 아니라면 CSS에서 테스트 전용으로 전환을 줄이거나, Playwright가 제공하는 안정화 옵션을 검토할 수 있습니다. 반대로 애니메이션이 사용자 경험의 핵심이면 정지 이미지만으로 검증하지 말고 시작·종료 상태와 접근성의 `prefers-reduced-motion` 대응을 별도로 테스트합니다.

## 업무 예시: 관리자 표가 좁은 화면에서 깨지는지 확인하기

사내 관리자 화면에 주문 목록 표가 있고, 상태·주문 번호·고객명·금액·처리 버튼이 한 행에 있다고 가정해 봅시다. 데스크톱에서는 문제가 없지만 768px 너비에서 고객명이 길면 처리 버튼이 화면 밖으로 나갈 수 있습니다. 이 문제는 기능 API가 정상이어도 사용자가 일을 완료하지 못하게 합니다. 테스트는 대표적인 긴 이름과 짧은 이름을 포함한 고정 데이터를 준비하고, 데스크톱과 태블릿 너비를 각각 명시한 뒤 표 영역을 비교합니다.

```ts
test('주문 목록은 태블릿 너비에서도 처리 버튼을 보인다', async ({ page }) => {
  await page.setViewportSize({ width: 768, height: 900 });
  await page.route('**/api/orders*', route => route.fulfill({ path: 'tests/fixtures/orders-long-name.json' }));
  await page.goto('/admin/orders');
  await expect(page.getByRole('button', { name: '처리' }).first()).toBeVisible();
  await expect(page.locator('[data-testid="order-table"]')).toHaveScreenshot('orders-table-tablet.png');
});
```

여기서 중요한 것은 버튼의 존재를 먼저 DOM으로 확인했다는 점입니다. 이미지 차이가 없다는 결과만으로 버튼의 접근 가능한 이름이나 클릭 가능 상태를 증명할 수 없기 때문입니다. `data-testid`는 테스트가 찾을 수 있도록 의도적으로 붙인 안정적인 식별자입니다. 클래스 이름이나 화면 문구는 디자인 변경과 번역에 따라 바뀔 수 있으므로, 테스트가 꼭 필요한 위치에서만 이런 식별자를 쓰는 편이 유지보수에 유리합니다.

리뷰에서는 차이 이미지를 보고 “표의 열 폭 변경은 의도한 반응형 개선인가”, “처리 버튼이 오른쪽에서 아래로 이동한 것은 허용되는가”, “금액 열이 잘린 것은 결함인가”를 판단합니다. 기준선을 업데이트하는 사람과 변경을 승인하는 사람이 같은지, PR(Pull Request, 코드 변경 검토 요청)에 차이 이미지를 어떻게 남기는지 정하면 테스트 실패가 단순한 빨간 표시가 아니라 디자인·제품·QA가 대화하는 근거가 됩니다.

## 오탐을 줄이는 방법과 흔한 잘못된 해결책

**오탐(false positive)** 은 실제 결함이 없는데 테스트가 실패라고 알리는 경우입니다. 시각 테스트의 오탐은 주로 환경, 시간, 데이터, 외부 리소스의 불안정성에서 시작합니다. 실패할 때마다 허용 오차를 키우거나 스냅샷을 갱신하는 것은 문제의 원인을 가리는 잘못된 해결책입니다. 먼저 차이 이미지에서 달라진 영역을 봅니다. 글자 전체가 흐리게 달라졌다면 폰트 또는 운영체제 차이일 수 있고, 특정 카드만 달라졌다면 데이터 또는 스타일 변경일 수 있으며, 페이지 일부가 빈 칸이면 로딩·네트워크 준비 문제가 의심됩니다.

동적 영역을 숨기는 방법도 절제해야 합니다. 테스트 전에 광고 배너나 현재 시각만 마스킹(masking, 비교 대상에서 가리는 처리)하는 것은 합리적일 수 있습니다. 그러나 실패가 자주 난다는 이유로 헤더·본문·버튼처럼 중요한 영역까지 넓게 마스킹하면 테스트는 아무 것도 감시하지 못합니다. 마스킹한 영역과 이유는 코드에 남기고, 그 영역의 데이터 계약이나 표시 여부는 다른 테스트에서 확인해야 합니다.

기준선 파일을 운영체제별로 무작정 여러 벌 만드는 것도 마지막 수단입니다. 지원해야 할 브라우저별 표현 차이가 제품 요구 사항이라면 프로젝트별 기준선이 필요할 수 있습니다. 하지만 같은 브라우저를 같은 CI에서 돌리는데 기준선이 계속 늘어난다면 문제는 환경 통제가 약한 데 있을 가능성이 큽니다. 기준선 개수보다 “어떤 사용자 환경을 공식 지원하고 그 환경에서 무엇을 보장하는가”를 먼저 정합니다.

실패 보고서의 보관도 생각해야 합니다. 스크린샷에는 이름, 주문번호, 내부 URL, 입력값처럼 민감할 수 있는 정보가 보일 수 있습니다. 테스트 계정과 가짜 데이터를 사용하고, CI 결과물의 접근 권한·보존 기간을 확인합니다. 오류를 분석하기 위해 모든 운영 화면을 캡처해 외부 저장소에 올리는 방식은 QA 편의성보다 정보 노출 위험이 커질 수 있습니다.

## 언제 도입하고 언제 피해야 하나

시각 회귀 테스트는 디자인 시스템, 고객 화면의 핵심 여정, 관리 화면의 복잡한 표, 다국어·반응형 레이아웃처럼 사람이 보는 모양이 품질 기준인 곳에서 효과가 큽니다. 작은 CSS 변경이 넓은 화면에 영향을 주는 팀, 여러 개발자가 공통 컴포넌트를 바꾸는 팀, 수동 화면 검토 시간이 큰 팀은 대표 화면부터 도입해 볼 만합니다. 특히 이미 Playwright E2E 테스트가 있다면 새 실행기 대신 같은 시나리오에 한두 개의 비교를 추가하는 길이 가장 짧습니다.

반대로 화면 요구가 자주 바뀌는데 승인 절차가 없거나, 테스트 데이터와 실행 환경을 통제할 수 없거나, 실패 이미지를 검토할 사람이 없는 상황에서는 기대보다 관리 비용이 커질 수 있습니다. “모든 페이지를 찍으면 품질이 올라간다”는 생각도 위험합니다. 수백 장의 기준선이 바뀌면 리뷰자는 중요한 변화와 사소한 변화 사이를 구분하기 어렵습니다. 우선 장애가 잦았던 화면, 구매·가입처럼 사용자가 이탈하면 비용이 큰 흐름, 공통 컴포넌트부터 시작해 범위를 늘립니다.

## 기준선 변경을 코드 변경처럼 리뷰하는 흐름

시각 테스트를 CI에 넣으면 실패는 보통 두 종류입니다. 첫째는 코드 변경이 기준선과 다르지만 그 변화가 의도되지 않은 경우입니다. 이때 개발자는 스타일을 되돌리거나 요구 사항에 맞게 수정하고, 기준선은 그대로 둡니다. 둘째는 요구 사항에 따라 화면을 의도적으로 바꾼 경우입니다. 이때도 기준선 파일을 바로 덮어쓰기보다 현재 이미지와 차이 이미지를 PR에 첨부해, 문구·정렬·빈 상태·작은 화면을 확인한 뒤 갱신합니다. 같은 실패 표시라도 판단 과정이 다릅니다.

리뷰 체크리스트는 짧을수록 좋습니다. 예를 들어 “변경된 픽셀은 요구한 컴포넌트 안에 있는가”, “대표 작은 화면에서 정보나 조작 버튼이 가려지지 않는가”, “의도하지 않은 공통 헤더·푸터 변화는 없는가”, “기준선이 테스트 환경에서 다시 재현되는가” 정도면 시작할 수 있습니다. 수십 개 항목을 매번 읽게 하면 아무도 지키지 않게 됩니다. 대신 중요한 법적 고지, 결제 금액, 접근성 같은 항목은 해당 기능의 별도 테스트와 제품 검토 절차로 다룹니다.

기준선의 소유자도 정해야 합니다. 화면을 구현한 개발자가 이미지를 만들 수는 있지만, 제품 문구나 디자인 규칙의 최종 판단까지 혼자 해야 한다는 뜻은 아닙니다. 작은 팀이라면 PR 작성자와 리뷰어가 차이 이미지를 함께 확인하는 것만으로도 충분합니다. 디자인 담당자가 따로 있는 팀은 공통 컴포넌트 기준선 변경에만 검토자를 연결할 수 있습니다. 핵심은 누가 승인했는지보다, “왜 이 이미지가 정상 상태인가”를 커밋과 리뷰에서 나중에도 설명할 수 있는가입니다.

테스트 이름도 화면 이름만 적기보다 사용자 가치와 조건을 포함하면 좋습니다. `home.png`보다 `비로그인-모바일-긴 공지-홈-상단`처럼 상태와 화면 크기를 나타내는 이름이 실패를 읽기 쉽습니다. 단, 파일명에 실제 고객명·주문번호·토큰을 넣지 않습니다. 기준 이미지가 수백 장으로 늘면 디렉터리를 제품 영역과 화면 크기로 나누되, 초기에 복잡한 생성기나 추상화를 만들 필요는 없습니다. 테스트 파일 가까이에 같은 이름으로 보관하는 단순 규칙부터 시작해도 충분합니다.

## 화면 크기와 브라우저 조합을 고르는 법

반응형 웹은 하나의 화면 폭만 통과해서는 충분하지 않습니다. 그러나 지원 가능한 모든 휴대폰, 모든 브라우저, 모든 확대 비율을 이미지로 전수 비교하는 것은 비용이 너무 큽니다. 우선 서비스 분석이나 지원 정책을 바탕으로 대표 구간을 정합니다. 예를 들어 모바일의 좁은 폭, 태블릿 또는 작은 노트북의 중간 폭, 일반 데스크톱 폭을 골라 각 구간에서 가장 위험한 화면을 검사합니다. CSS가 특정 분기점에서 두 열을 한 열로 바꾸는 경우에는 그 분기점 바로 앞뒤 너비도 후보가 됩니다.

브라우저 프로젝트도 같은 원칙입니다. Chrome, Firefox, WebKit 엔진에서 픽셀까지 같은 모양을 무조건 보장하겠다는 정책은 현실적이지 않을 수 있습니다. 제품이 여러 엔진을 지원한다면 기능·접근성 테스트는 여러 브라우저에서 실행하고, 시각 기준선은 엔진별로 따로 관리하거나 대표 엔진에서 공통 레이아웃을 먼저 확인하는 방식을 선택할 수 있습니다. 선택은 제품의 지원 약속에 맞아야 합니다. 사용자가 Safari에서 서비스를 쓰는데 Chromium 기준선만 통과했다고 품질 문제가 사라지는 것은 아닙니다.

고해상도 화면도 생각해야 합니다. CSS 픽셀 기준으로 같은 너비를 지정해도 장치 픽셀 비율(device pixel ratio)이 다르면 이미지 파일의 실제 해상도와 글자 가장자리가 달라질 수 있습니다. CI 프로젝트에서 브라우저 버전·뷰포트·장치 배율을 명시하는 이유가 여기에 있습니다. 해상도 문제를 발견했을 때는 “차이 허용값을 올릴까”보다 “기준선 생성 환경과 비교 환경이 같은가”를 먼저 확인합니다. 환경이 정리되지 않은 상태에서 기준선 여러 벌을 만들면 원인을 추적하기 더 어려워집니다.

## 시각 비교와 접근성·기능 테스트를 연결하기

같은 시나리오 안에서 검사를 여러 층으로 나누면 실패의 의미가 선명해집니다. 로그인 폼을 예로 들면, 먼저 역할(role)과 이름으로 이메일 입력창과 제출 버튼을 찾아 접근 가능한 요소가 있는지 확인합니다. 다음으로 잘못된 비밀번호에서 오류 메시지가 화면에 보이고 포커스가 적절히 이동하는지 검증합니다. 마지막으로 데스크톱과 모바일에서 폼 전체 또는 오류 영역의 스크린샷을 비교합니다. 한 테스트에 모든 사실을 몰아넣는 것이 아니라, 같은 사용자 여정에 서로 다른 질문을 붙이는 것입니다.

색 대비도 좋은 예입니다. 시각 비교는 버튼 색이 갑자기 바뀌거나 경고 배너가 사라진 사실을 잡는 데 도움을 줍니다. 하지만 사람이 읽기 충분한 대비 비율인지, 색 외의 텍스트·아이콘으로 오류를 구분하는지는 픽셀만으로 판정하기 어렵습니다. 자동 접근성 검사와 수동 키보드·스크린 리더 검토를 보완해야 합니다. 반대로 접근성 검사만 통과해도 실제 디자인이 의도대로 배치됐다는 보장은 없습니다. 도구의 강점을 섞되, 같은 실패를 여러 도구에 중복 구현하지 않는 것이 유지보수에 좋습니다.

네트워크 실패·빈 상태·권한 없음 상태도 기준선 후보입니다. 정상 데이터가 꽉 찬 화면만 찍으면 장애 때 사용자가 보는 빈 영역, 재시도 버튼, 안내 문구의 품질을 확인할 수 없습니다. 다만 실패 상태는 API 응답을 고정해야 재현이 쉬우므로, 테스트가 어느 요청을 어떤 응답으로 바꾸는지 읽기 쉽게 작성합니다. 실제 네트워크를 끊는 방식보다 의도한 오류 응답을 주입하는 방식이 빠르고 결정적일 때가 많습니다. 그 대신 실제 인프라 장애 대응은 별도의 통합·복구 훈련 범위로 남깁니다.

## 작은 범위에서 시작하는 도입 순서

처음부터 전 화면의 기준선을 만들지 말고, 최근 CSS 변경으로 문제가 났던 화면 하나를 고릅니다. 첫 주에는 데스크톱과 모바일 한 너비씩, 정상 상태와 빈 상태 정도만 준비해도 됩니다. 다음으로 CI에서 같은 브라우저 프로젝트를 실행하고, 실패 시 현재·기대·차이 이미지를 PR에서 볼 수 있는지 확인합니다. 이 단계에서 이미지가 자주 흔들리면 대상 화면을 늘리지 말고 데이터, 폰트, 애니메이션, 브라우저 버전을 먼저 고정합니다.

안정된 뒤에는 공통 버튼, 표, 모달처럼 영향 범위가 큰 컴포넌트에 검사 하나씩을 추가합니다. 테스트 실패가 실제 결함을 찾아낸 사례와 단순 환경 문제였던 사례를 함께 기록하면, 팀은 어떤 화면이 비용 대비 효과가 큰지 판단할 수 있습니다. 기준선 갱신 명령을 아무나 실행하지 못하게 복잡한 시스템을 도입할 필요는 없습니다. PR 리뷰에서 이미지 결과를 확인하고, 승인된 변경만 저장소에 넣는 기본 흐름이면 충분합니다.

시각 회귀 테스트는 디자이너의 검토를 자동화해 없애는 기술도, QA가 모든 CSS를 소유하게 하는 기술도 아닙니다. 반복적으로 놓치던 표현 문제를 기계가 먼저 알려 주고, 사람은 그 변화가 사용자에게 맞는지 판단하게 만드는 협업 장치에 가깝습니다. 이 경계를 이해하면 실패 수를 줄이는 것보다 중요한 화면 품질을 지키는 데 도구를 쓸 수 있습니다.

마지막으로 기준선은 문서이기도 합니다. 새 팀원이 테스트 이미지를 보면 서비스가 어느 화면 크기를 중요하게 보고, 긴 데이터와 오류 상태를 어떻게 보여 주기로 했는지 빠르게 이해할 수 있습니다. 그래서 기준선을 단순한 생성 파일로 취급하지 말고, 읽기 쉬운 테스트 이름과 고정 데이터, 짧은 변경 이유를 함께 남깁니다. 그렇게 하면 화면이 바뀌었을 때 “왜 실패했는가”뿐 아니라 “무엇을 지키기로 했는가”까지 답할 수 있습니다.

테스트 도입의 성공 기준도 실패 건수만으로 잡지 않습니다. 배포 전에 발견한 레이아웃 결함, 리뷰에서 확인한 의도된 변경, 흔들리는 테스트를 고치기까지 걸린 시간을 함께 보면 실제 효용을 판단할 수 있습니다. 기준선은 한 번 만들어 두고 방치하는 산출물이 아니라 제품과 함께 갱신하는 품질 계약입니다.

따라서 테스트가 실패했을 때 가장 먼저 할 일은 기준선을 갱신하는 것이 아니라, 차이 영역이 사용자에게 어떤 영향을 주는지 읽는 일입니다.

작은 차이라도 사용자의 선택을 막으면 우선순위는 높아집니다.

판단 근거를 남깁니다.

시각 회귀 테스트의 핵심은 스크린샷을 많이 저장하는 데 있지 않습니다. 기준선이 무엇을 보장하는지, 변동 요소를 어떻게 통제하는지, 실패를 누가 어떤 근거로 승인하는지를 정하는 데 있습니다. DOM·API·접근성 검사로는 놓치기 쉬운 “사용자에게 실제로 어떻게 보이는가”를 작고 안정적인 비교로 보완하면, CSS 한 줄의 영향도 배포 전에 더 빨리 발견할 수 있습니다.
