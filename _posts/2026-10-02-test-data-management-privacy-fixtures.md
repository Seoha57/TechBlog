테스트가 불안정한 이유를 코드에서만 찾기 쉽습니다. 그러나 같은 테스트가 오늘은 통과하고 내일은 실패하거나, 개발자마다 다른 결과가 나오는 문제의 상당수는 **테스트 데이터**에서 시작합니다. 이미 누군가 만든 주문이 남아 있어 수량이 달라지고, 외부 시스템의 공유 계정 상태가 바뀌고, 운영 데이터 사본의 고객 정보가 의도하지 않게 테스트 화면에 나타나는 식입니다. 테스트 데이터는 단순히 입력값 몇 줄을 준비하는 보조 작업이 아닙니다. 재현성, 개인정보 보호, 테스트 속도, 장애 분석 가능성을 함께 좌우하는 품질 기반입니다.

이 글에서 말하는 테스트 데이터 관리는 특정 제품을 도입하는 방법이 아니라, 어떤 데이터가 어떤 테스트에서 왜 필요한지 설명하고 안전한 경계를 세우는 방법입니다. 실제 조직의 운영 데이터를 복제하거나 특정 환경에서 측정했다는 경험을 주장하지 않습니다. OWASP Web Security Testing Guide가 테스트 환경을 운영 환경과 분리하고 목적에 맞는 데이터를 준비하라고 안내하는 취지도 함께 참고합니다. 중요한 결론부터 말하면, 테스트에 현실성이 필요하다고 해서 운영 데이터 전체가 필요한 것은 아니며, 편리하다고 해서 개인정보를 테스트 저장소와 로그에 흘려보내도 되는 것은 아닙니다.

## 먼저 알아둘 기반 기술: 상태, 데이터베이스, 테스트 피라미드

애플리케이션 테스트에서 **상태(state)** 는 현재 시스템이 기억하는 값의 묶음입니다. 로그인한 사용자가 누구인지, 장바구니에 무엇이 담겼는지, 주문이 결제 대기인지 완료인지, 재고가 몇 개인지가 모두 상태입니다. 함수에 숫자 두 개를 넣고 결과를 확인하는 단위 테스트는 비교적 작은 상태만 다루지만, 웹 서비스의 통합 테스트는 데이터베이스·캐시·파일 저장소·메시지 큐·외부 API처럼 여러 상태 저장소를 건드립니다. 그래서 입력 한 줄이 같아도 시작 상태가 다르면 결과가 달라집니다.

**데이터베이스 트랜잭션(transaction)** 은 여러 변경을 하나의 작업 단위로 묶는 방법입니다. 주문 생성 중 재고 차감과 결제 요청이 함께 일어나야 한다면, 일부만 반영되고 일부가 실패했을 때 어떻게 되돌릴지 정해야 합니다. 테스트도 마찬가지입니다. 테스트가 만든 사용자와 주문을 다음 테스트가 보게 두면 실행 순서가 품질의 일부가 됩니다. 가능한 경우 테스트 시작 전 데이터를 만들고 종료 뒤 되돌리거나 삭제해, 각 테스트가 독립된 상태에서 출발하게 설계합니다. 단, 외부 결제·이메일·비동기 작업까지 데이터베이스 하나의 트랜잭션으로 되돌릴 수 있는 것은 아니므로 경계를 분명히 해야 합니다.

**테스트 피라미드(test pyramid)** 는 빠르고 작은 테스트를 많이, 실제 구성 요소를 넓게 연결하는 테스트를 상대적으로 적게 두자는 사고방식입니다. 단위 테스트에서는 메모리 안의 작은 객체나 고정된 픽스처로 규칙을 확인합니다. 통합 테스트에서는 실제 데이터베이스나 컨테이너를 붙여 SQL, 제약 조건, 직렬화가 맞는지 확인할 수 있습니다. 엔드투엔드 테스트에서는 브라우저에서 로그인·주문 같은 흐름을 검증합니다. 아래층으로 갈수록 데이터의 양보다 제어 가능성과 속도가 중요하고, 위층으로 갈수록 실제와 비슷한 연결 관계가 중요해집니다. 모든 단계에 운영 데이터가 필요한 것은 아닙니다.

**픽스처(fixture)** 는 테스트가 기대하는 시작 상태를 준비하는 데이터, 객체, 파일, 설정을 뜻합니다. 예를 들어 `VIP 회원`, `품절 상품`, `쿠폰이 만료된 주문`을 코드나 JSON으로 선언해 두면 테스트 이름만 보고도 어떤 조건을 검증하는지 알 수 있습니다. 반면 **시드(seed) 데이터**는 개발 서버나 데모 환경을 처음 만들 때 넣는 공통 초기 데이터에 가깝습니다. 둘을 같은 파일로 운영할 수도 있지만 목적은 다릅니다. 픽스처는 특정 테스트의 독립성과 의도를, 시드 데이터는 사람이 둘러볼 환경의 기본 형태를 우선합니다.

## 테스트 데이터가 품질을 좌우하는 이유

좋은 테스트 데이터는 정상 입력만 많이 담은 데이터가 아닙니다. 업무 규칙의 경계가 보이도록 설계된 데이터입니다. 할인 정책을 예로 들면, 회원 등급이 일반·VIP라는 두 값만 있으면 규칙의 일부만 볼 수 있습니다. 가입일이 정확히 기준일인 회원, 쿠폰이 자정에 만료되는 주문, 재고가 정확히 0이 되는 상품, 배송지가 비어 있는 주문처럼 경계값을 준비해야 “조건문이 우연히 통과했는가”가 아니라 “정책의 경계가 구현됐는가”를 확인할 수 있습니다.

데이터가 불안정하면 실패 원인도 흐려집니다. 같은 `test@example.com` 계정을 여러 사람이 공유하고 한 테스트가 비밀번호를 바꾼다면, 실패는 코드 결함인지 이전 실행의 흔적인지 알기 어렵습니다. 시간에 따라 변하는 현재 날짜, 난수, 외부 환율, 실시간 재고를 기대값에 그대로 넣어도 같은 문제가 생깁니다. 이때 해법은 실패할 때마다 재실행 버튼을 누르는 것이 아니라 시간·난수·외부 응답을 주입 가능한 값으로 만들고, 테스트가 소유한 데이터를 고유하게 생성하고, 끝난 뒤 정리하는 것입니다.

테스트 데이터는 결함 발견뿐 아니라 결함 설명에도 쓰입니다. 버그 보고에 “주문이 이상합니다”라고 쓰는 대신 `재고 1개, 장바구니 수량 2개, 동시 요청 두 건`이라는 최소 데이터를 남기면 개발자와 QA가 같은 문제를 재현하기 쉬워집니다. **최소 재현 사례(minimal reproducible case)** 는 가능한 한 적은 데이터와 단계로 문제를 보여 주는 사례입니다. 운영 덤프 수십 기가바이트보다 작고 명확한 데이터 세트가 협업에는 더 강한 경우가 많습니다.

## 데이터 유형을 먼저 나누기: 합성, 참조, 마스킹, 익명화

**합성 데이터(synthetic data)** 는 실제 사람이나 거래에서 가져오지 않고, 테스트 목적에 맞게 새로 만든 데이터입니다. `홍길동`, `example.test` 도메인, 테스트용 카드 토큰, 가상의 상품 코드처럼 의미와 관계만 보존합니다. 장점은 안전하게 버리고 다시 만들 수 있다는 점입니다. 다만 실제 업무의 분포나 예외가 빠질 수 있으므로, 도메인 담당자와 함께 어떤 조합이 중요한지 정해야 합니다. 합성 데이터가 가짜라서 품질이 낮은 것이 아니라, 어떤 업무 규칙을 대표하게 만들었는지가 품질을 결정합니다.

**참조 데이터(reference data)** 는 국가 코드, 통화 코드, 상품 분류, 권한 역할처럼 시스템 전반에서 공통으로 쓰는 비교적 안정적인 값입니다. 이를 테스트마다 제각각 만들면 개발 환경과 운영 환경의 규칙이 달라질 수 있습니다. 참조 데이터는 버전 관리하거나 공식 원천과 동기화하는 방식을 정하되, 테스트가 외부 네트워크에 매번 의존하지 않도록 필요한 스냅샷을 관리할 수 있습니다. 단, 실제 고객·거래 정보와 참조 데이터를 섞어 “공통 데이터”라는 이름으로 넓게 복제하는 일은 피해야 합니다.

**데이터 마스킹(data masking)** 은 민감한 값을 규칙에 따라 바꾸거나 가려서 원본을 직접 보지 못하게 하는 방법입니다. 예를 들어 이메일의 로컬 부분을 바꾸고, 전화번호의 일부를 대체하고, 주민번호·카드번호처럼 높은 위험 데이터는 정책에 맞게 제거할 수 있습니다. 하지만 `kim***@company.com`처럼 일부만 가리는 것이 항상 충분한 것은 아닙니다. 다른 컬럼과 조합하면 원래 사람을 다시 추정할 수 있고, 동일 사용자의 주문과 고객 정보를 연결해야 하는 테스트에서는 행 간 관계도 유지해야 합니다.

**익명화(anonymization)** 는 개인을 합리적으로 다시 식별할 수 없도록 처리하려는 더 강한 목표를 가리키는 말로 쓰입니다. 어떤 처리가 법적·조직적으로 익명화에 해당하는지는 관할 법령, 결합 가능한 다른 데이터, 재식별 위험, 조직 정책에 따라 달라집니다. 따라서 개발팀이 문자열 몇 글자를 바꿨다고 “완전히 익명”이라고 단정하면 안 됩니다. 이 글은 법률 자문이 아니며, 실제 데이터 반출과 처리에는 개인정보·보안 담당자의 정책과 승인이 필요합니다.

## 픽스처는 업무 언어로 읽혀야 합니다

픽스처 파일의 이름과 필드는 테스트 목적을 말해 주어야 합니다. `user1`, `order2`, `data-final`처럼 번호만 붙인 데이터는 시간이 지나면 아무도 의미를 알 수 없습니다. 반대로 `vip-member-with-expired-coupon`, `out-of-stock-product`, `refund-after-settlement`처럼 상태를 이름으로 표현하면, 테스트를 읽는 사람이 요구 사항을 이해하기 쉽습니다. 다만 이름이 너무 많은 구현 세부를 반복하면 변경 때마다 대량 수정이 필요하므로, 업무적으로 중요한 상태만 드러냅니다.

다음은 주문 할인 규칙을 위한 작은 합성 픽스처의 예입니다. 실제 스키마나 개인정보 형식이 아니라 테스트 의도를 보여 주는 예시입니다.

```json
{
  "member": {
    "id": "member-vip-boundary",
    "grade": "VIP",
    "joinedAt": "2026-01-01T00:00:00Z"
  },
  "coupon": {
    "code": "TEST-EXPIRED-0001",
    "status": "EXPIRED",
    "expiresAt": "2026-10-01T23:59:59Z"
  },
  "product": {
    "sku": "TEST-STOCK-ONE",
    "stock": 1,
    "price": 10000
  }
}
```

이 데이터는 “VIP면 항상 할인”을 확인하기보다, 만료 쿠폰이 VIP 상태보다 우선해서 거절되는지, 재고 1개일 때 수량 2개 요청이 실패하는지를 분리해 검증하도록 돕습니다. 하나의 거대한 `happy-path.json`에 모든 경우를 넣으면 테스트가 무엇 때문에 실패했는지 알기 어려워집니다. 픽스처는 작고 목적이 명확할수록 수정과 폐기가 쉽습니다.

## 관계와 제약 조건을 깨뜨리지 않는 방법

현실적인 데이터가 필요한 이유 중 하나는 테이블 사이의 관계입니다. 주문은 존재하는 고객을 가리키고, 주문 항목은 존재하는 상품을 가리키며, 결제는 주문 상태와 맞아야 합니다. 고객 이름만 무작위로 바꾸고 주문의 고객 식별자를 그대로 둔다면 개인정보는 남을 수 있고, 반대로 모든 ID를 독립적으로 난수화하면 외래 키 관계가 깨질 수 있습니다. 그래서 데이터 생성 규칙은 컬럼 하나가 아니라 엔터티 관계 단위로 설계합니다.

먼저 도메인의 불변 조건을 적습니다. 예를 들어 `주문 항목 수량은 0보다 커야 한다`, `환불 금액은 원결제 금액을 넘을 수 없다`, `삭제된 회원은 신규 주문을 만들 수 없다` 같은 조건입니다. 이 조건은 데이터베이스 제약 조건, 애플리케이션 검증, 테스트 생성기 모두에 영향을 줍니다. 정상 데이터는 이 조건을 만족하게 만들고, 오류 처리를 검증할 때만 한 조건을 의도적으로 깨뜨립니다. 모든 값이 무작위인 데이터는 오류가 어디서 왔는지 알기 어렵습니다.

시간 관계도 중요합니다. 주문 생성 시각보다 환불 시각이 앞서거나, 쿠폰 발급일보다 만료일이 빠른 데이터가 우연히 생기면 비즈니스 규칙과 무관한 실패가 됩니다. 테스트에서 현재 시간을 직접 읽는 대신 `2026-10-02T09:00:00Z` 같은 고정 시계를 주입하면, 날짜 경계와 만료 규칙을 반복 가능하게 검증할 수 있습니다. 실제 시간대와 일광 절약 시간제처럼 복잡한 경우에는 UTC 저장·표시 시간대 변환·경계 날짜를 별도 테스트 데이터로 준비합니다.

## 격리 전략: 공유 환경을 기본값으로 두지 않기

테스트 격리에는 하나의 정답이 없습니다. 단위 테스트는 메모리 객체를 매번 새로 만들면 충분할 수 있습니다. 데이터베이스 통합 테스트는 테스트마다 트랜잭션을 시작하고 종료 뒤 롤백하는 방법을 쓸 수 있습니다. 하지만 별도 프로세스가 커밋하거나 메시지 큐·파일·외부 API를 건드리면 롤백만으로 충분하지 않습니다. 이때는 테스트 전용 데이터베이스, 실행마다 고유한 스키마 또는 네임스페이스, 컨테이너로 띄운 일시적 의존성, 명시적 정리 작업을 조합합니다.

공유 QA 환경은 사람이 화면을 보며 확인하기에는 편하지만, 자동화 테스트의 유일한 기반으로 삼기에는 위험합니다. 다른 팀의 배포와 데이터 수정, 예약 작업, 외부 연동이 결과를 바꿀 수 있기 때문입니다. 공유 환경에서만 재현되는 통합 문제는 별도로 다루되, 매 커밋마다 수행하는 회귀 테스트는 가능한 한 자신이 소유한 상태에서 실행하는 편이 좋습니다. “환경이 비어 있을 때만 테스트가 통과한다”는 조건은 자동화의 신뢰도를 낮춥니다.

테스트가 생성한 자원에는 식별 가능한 접두사와 수명 주기가 필요합니다. 예를 들어 `e2e-run-<실행ID>`라는 주문·파일·큐 메시지 이름을 쓰면 실패 뒤 남은 흔적을 찾기 쉽습니다. 다만 실행 ID에 실제 사용자 이메일이나 비밀 값을 넣지 않습니다. 정리 작업은 성공 경로에만 두지 말고 실패·시간 초과·취소 뒤에도 실행되도록 설계합니다. 그래도 정리가 실패할 수 있으므로, 일정 기간이 지난 테스트 자원을 안전하게 탐지·삭제하는 별도 정책과 권한 경계를 둡니다.

## 운영 데이터가 꼭 필요한 상황의 판단 기준

실제 데이터의 형태가 결함과 직접 연결되는 경우는 있습니다. 예를 들어 오래된 문자 인코딩, 매우 긴 주소, 희귀한 상품 조합, 축적된 계정 관계가 특정 오류를 재현할 수 있습니다. 이때도 첫 질문은 “운영 데이터 전체가 필요한가”입니다. 문제를 일으킨 구조만 최소화해 합성 데이터로 재현할 수 있는지, 필요한 컬럼과 기간만 줄일 수 있는지, 승인된 비운영 환경에서 처리할 수 있는지 검토합니다.

운영 데이터를 사용해야 한다고 판단되면 기술적 편의보다 접근 통제가 앞섭니다. 누가 요청하고 승인하는지, 어떤 필드를 마스킹·삭제하는지, 원본과 사본이 어디에 저장되는지, 누가 읽을 수 있는지, 언제 폐기되는지, 로그와 백업에 다시 남지 않는지를 문서화합니다. 개발자의 개인 장비, 개인 클라우드, 소스 저장소, 이슈 첨부 파일에 운영 데이터를 두는 방식은 재현 편의와 관계없이 위험합니다. 테스트 환경도 운영과 분리된 접근 권한과 감사 경로가 필요합니다.

마스킹은 한 번 실행하고 끝나는 스크립트가 아니라 변경 관리 대상입니다. 스키마에 새 민감 컬럼이 추가됐는데 마스킹 규칙이 갱신되지 않으면, 다음 복제에서 원본 값이 새어 나갈 수 있습니다. 컬럼 분류표, 마스킹 규칙, 샘플 검사, 접근 로그를 함께 검토합니다. 데이터 품질을 위해 관계를 유지해야 하는 컬럼과 반드시 제거해야 하는 컬럼을 구분하는 일은 QA 혼자 결정할 수 없습니다.

## API와 화면 흐름에서 데이터의 경계를 확인하기

API 테스트는 요청과 응답의 형태를 빠르게 확인할 수 있습니다. 하지만 화면에서 시작된 업무 흐름에는 API 명세만으로 보이지 않는 제약이 있을 수 있습니다. 예를 들어 웹 화면은 특정 상품을 장바구니에 넣기 전에 배송지·약관 동의·쿠폰 발급 상태를 확인하고, 일부 값은 서버에서만 계산해 요청에 넣지 않을 수 있습니다. 이 경우 API 단독 테스트용 데이터가 응답 코드 관점에서는 맞아도, 실제 사용자가 밟는 시나리오를 대표하지 않을 수 있습니다.

그래서 테스트 데이터를 설계할 때는 “이 API에 어떤 JSON이 필요한가”와 “사용자가 이 상태에 도달하려면 앞에서 어떤 행동을 했는가”를 함께 기록합니다. 주문 API를 직접 호출하는 테스트에는 최소한의 필수 데이터가 필요하고, 브라우저 흐름 테스트에는 회원가입·로그인·장바구니·배송지·결제 대역까지 연결된 데이터가 필요할 수 있습니다. 두 테스트를 하나로 합치지 말고, 각각이 검증하려는 계약과 업무 흐름을 구분해야 실패 원인을 빠르게 좁힐 수 있습니다.

테스트가 응답 전문을 로그로 남길 때도 데이터 경계가 필요합니다. 실패 분석을 위해 요청·응답을 저장하는 것은 유용하지만, 인증 토큰·비밀번호·주소·연락처가 CI 로그와 테스트 리포트에 남으면 접근자가 넓어집니다. 민감 필드를 필터링하고, 실패 스크린샷·네트워크 트레이스·동영상의 보관 기간과 접근 권한을 정합니다. “테스트 결과물”이라는 이름이 개인정보 보호의 예외가 되지는 않습니다.

## 실무 예시: 주문 취소 규칙을 작은 데이터 세트로 검증하기

가상의 쇼핑 서비스에서 주문 취소 규칙을 검증한다고 해 봅시다. 규칙은 결제 대기 상태는 즉시 취소할 수 있고, 배송 준비 상태는 특정 시각 전까지만 취소할 수 있으며, 배송 완료 상태는 반품 절차로 넘어가야 한다고 가정합니다. 이 규칙을 확인하려고 고객 백만 명과 지난 1년치 주문을 복사할 필요는 없습니다. 상태 전이와 경계 시간을 대표하는 다섯에서 열 개 정도의 주문을 의도적으로 만듭니다.

```text
주문 A: PAYMENT_PENDING, 결제 대역 응답 성공, 즉시 취소 기대
주문 B: PREPARING, 취소 마감 1분 전, 취소 기대
주문 C: PREPARING, 취소 마감 정확히 지난 시각, 취소 거절 기대
주문 D: DELIVERED, 일반 취소 요청, 반품 안내 기대
주문 E: 이미 CANCELLED, 재시도 요청, 멱등 응답 또는 정의된 오류 기대
```

여기서 **멱등성(idempotency)** 은 같은 요청을 여러 번 보내도 의도하지 않은 추가 효과가 생기지 않게 하는 성질입니다. 네트워크 재시도 때문에 취소 요청이 두 번 도착할 수 있으므로, 테스트 데이터에는 이미 취소된 주문도 필요합니다. 다만 실제 결제 수단이나 실제 주소를 넣을 이유는 없습니다. 결제 대역은 테스트용 성공·실패·지연 응답을 반환하고, 배송지는 의미 없는 안전한 값으로 만듭니다. 핵심은 실제 사람을 닮게 만드는 것이 아니라 업무 상태 전이를 빠뜨리지 않는 것입니다.

## 데이터 생성 코드를 제품 코드처럼 다루기

테스트 데이터 생성기는 시간이 지나면 작은 라이브러리가 됩니다. 여러 테스트가 같은 `createOrder` 도우미를 쓰고, 그 도우미가 기본 상태와 관계를 만들기 시작하면 변경 영향도 커집니다. 그렇다고 처음부터 복잡한 데이터 생성 플랫폼을 만들 필요는 없습니다. 우선은 읽기 쉬운 팩터리 함수나 빌더와 소수의 명시적 픽스처로 시작하고, 반복되는 관계와 기본값만 공통화합니다.

생성기의 기본값은 안전해야 합니다. 기본 사용자가 관리자 권한을 갖거나, 기본 결제 상태가 성공이거나, 기본 날짜가 현재 시간이면 테스트가 뜻하지 않게 중요한 경계를 건너뜁니다. 가장 흔한 상태를 기본값으로 두되, 권한·금액·시간·상태처럼 결과를 바꾸는 값은 테스트에서 드러내게 만듭니다. `createUser({ role: 'ADMIN' })`처럼 중요한 선택이 코드에 보이면 리뷰에서도 권한 검증 여부를 읽기 쉬워집니다.

난수 생성도 재현 가능해야 합니다. 실행마다 무작위 이메일을 만들 수는 있지만, 실패한 실행의 시드(seed)를 기록하면 같은 값을 다시 생성할 수 있습니다. 테스트 프레임워크가 병렬 실행을 지원하면 ID 충돌을 피하기 위한 접두사와 시드를 조합합니다. 단, 난수로 우연한 경우를 많이 만드는 방식은 속성 기반 테스트 같은 별도 기법의 목적일 수 있으므로, 일반 회귀 테스트의 명확한 픽스처와 섞어 실패 설명을 어렵게 만들지 않습니다.

## CI에서 데이터 수명을 관리하는 방법

**CI(Continuous Integration, 지속적 통합)** 는 변경을 합친 뒤 자동으로 빌드와 테스트를 실행해 빠르게 문제를 발견하려는 방식입니다. CI의 테스트 데이터는 개발자 노트북의 데이터보다 더 짧은 수명과 더 분명한 소유권을 가져야 합니다. 한 실행이 시작되면 필요한 데이터베이스와 저장소를 만들고, 실행 ID를 기록하고, 성공·실패와 관계없이 정리합니다. 실패한 경우에는 분석에 필요한 최소 결과물만 일정 시간 보관하고, 운영 데이터나 비밀 값이 결과물에 포함되지 않았는지 확인합니다.

병렬 실행에서는 특히 같은 데이터의 공유를 피해야 합니다. 브랜치 A와 브랜치 B가 같은 `qa-user-1`을 수정하면, 한쪽 테스트가 다른 쪽 결과를 바꾸는 경쟁 조건이 생깁니다. 실행마다 별도 데이터베이스를 만드는 것이 가장 명확할 수 있지만 비용이 클 수 있습니다. 그때는 스키마, 테넌트 키, 실행 접두사처럼 격리 단위를 정하고, 데이터베이스의 행 수준 권한이나 애플리케이션 필터가 실제로 그 경계를 지키는지 검증합니다. 단순히 이름 앞에 접두사를 붙였다고 보안 격리가 되는 것은 아닙니다.

CI 로그는 데이터 정책의 일부입니다. 테스트가 실패했을 때 프레임워크가 요청 본문과 데이터베이스 오류를 모두 출력할 수 있습니다. 테스트 데이터가 합성 값이어도 접근 토큰이나 내부 주소가 섞일 수 있으므로, 로그 마스킹 규칙과 리포트 열람 권한을 설정합니다. 개발자가 다운로드한 실패 아티팩트를 언제 삭제하는지까지 자동화하기 어려울 수 있지만, 보관 기간과 공유 범위를 정해 두면 임시 파일이 장기 데이터 저장소로 변하는 일을 줄일 수 있습니다.

## 결함에서 회귀 데이터로 돌아오는 과정

운영 또는 QA 환경에서 결함이 발견됐을 때 가장 가치 있는 산출물은 원본 데이터 덤프가 아니라, 결함을 일으킨 조건을 설명하는 회귀 픽스처입니다. 예를 들어 특정 고객의 이름이 아니라 이름 길이와 문자 조합이 문제였다면, 그 특성을 가진 가상 사용자로 바꿉니다. 특정 주문 번호가 아니라 할인과 환불 상태의 조합이 문제였다면, 그 상태 전이를 작은 데이터로 만듭니다. 이렇게 바꾼 회귀 테스트는 민감 정보를 복사하지 않고도 이후 변경에서 같은 결함이 돌아오는지 계속 확인하게 해 줍니다.

이 과정은 처음에는 시간이 듭니다. 로그에서 원인을 분리하고, 최소 조건을 찾고, 기존 테스트가 왜 놓쳤는지 설명해야 하기 때문입니다. 그러나 원본 백업을 복사해 두고 "그 데이터에서만 난다"고 남기는 방식보다 장기적으로 협업에 유리합니다. 회귀 픽스처에는 결함 번호나 짧은 배경을 연결해 두되, 고객 이름·계정 번호·내부 비밀을 식별자로 쓰지 않습니다. 데이터가 테스트의 문서가 되도록 만들면 새 팀원도 과거 결함의 경계를 이해할 수 있습니다.

## 테스트 데이터 체크리스트와 마무리

새 테스트를 추가할 때는 먼저 이 테스트가 소유하는 상태가 무엇인지 적어 봅니다. 어떤 사용자·상품·권한·시간·외부 응답이 필요한지, 정상·경계·오류 조건이 무엇인지, 실행 뒤 무엇을 지워야 하는지를 확인합니다. 다음으로 실제 개인정보나 비밀 값이 들어갈 이유가 있는지 묻습니다. 대부분은 테스트용 식별자와 합성 값으로 대체할 수 있습니다. 마지막으로 실패했을 때 다른 사람이 같은 데이터를 만들어 재현할 수 있는지 확인합니다.

데이터 관리는 화려한 자동화 도구보다 먼저 설계해야 하는 습관입니다. 작은 픽스처를 업무 언어로 이름 붙이고, 시간과 외부 응답을 통제하며, 환경과 권한을 분리하면 테스트는 더 빨라질 뿐 아니라 실패를 설명할 수 있게 됩니다. 반대로 큰 운영 사본 하나에 모든 테스트를 얹으면 처음에는 편해 보여도 개인정보 위험과 상태 의존성이 누적됩니다. 좋은 테스트 데이터는 현실을 무작정 복제하는 데이터가 아니라, 필요한 현실을 안전하고 반복 가능하게 표현하는 데이터입니다.
