테스트가 느리거나 자주 실패하면 팀은 종종 “Mock을 더 쓰자” 또는 “실제 환경과 똑같이 붙이자” 중 하나를 고릅니다. 두 답은 모두 일부 상황에서 맞지만, 문제는 가짜 객체의 이름이 아니라 어떤 위험을 어느 경계에서 검증할지입니다. 주문 금액 계산을 확인하려는데 원격 결제사 API까지 호출하면 네트워크와 계정 상태가 테스트 결과를 흔듭니다. 반대로 JSON 직렬화와 실제 데이터베이스 제약 조건을 모두 Mock으로 대체하면 배포 뒤에만 드러나는 연결 오류를 놓칠 수 있습니다.

테스트 더블(test double)은 테스트에서 실제 협력 객체를 대신하는 모든 객체를 가리키는 말입니다. 영화 촬영에서 배우를 대신하는 대역이라는 비유에서 나온 이름입니다. 하지만 대역도 장면마다 역할이 다르듯, Dummy·Stub·Fake·Spy·Mock은 제공하는 정보와 검증하는 대상이 다릅니다. 이 글은 프레임워크 문법보다 먼저, 각각을 언제 고르고 언제 피해야 하는지를 결제 승인 같은 업무 사례로 설명합니다.

## 먼저 알아둘 기반 기술

### 단위 테스트와 협력 객체

단위 테스트(unit test)는 보통 작은 규칙 또는 컴포넌트가 기대한 결과를 내는지 빠르게 확인합니다. 여기서 단위는 반드시 함수 하나라는 뜻은 아닙니다. 주문 서비스처럼 여러 객체가 함께 동작해도, 테스트가 통제할 수 있는 경계 안에 있다면 하나의 단위로 볼 수 있습니다. 문제는 그 단위가 데이터베이스, 메시지 브로커, HTTP API, 현재 시각, 난수처럼 외부 상태에 의존할 때 생깁니다. 이런 대상을 협력 객체(collaborator)라고 부르며, 테스트 더블은 협력 객체를 원하는 방식으로 대체합니다.

예를 들어 `OrderService`가 재고 저장소와 결제 게이트웨이에 의존한다고 해 보겠습니다. 주문 금액과 할인 규칙을 확인하는 테스트라면 저장소가 실제 Oracle이나 Tibero에 연결될 이유가 없습니다. 저장소는 “재고가 3개 남았다”라는 답만 주면 됩니다. 반면 저장소 쿼리가 올바른 격리 수준과 제약 조건으로 실행되는지 확인하려면 실제 DBMS와의 통합 테스트가 필요합니다. 같은 코드라도 테스트의 질문이 바뀌면 적절한 협력 객체도 바뀝니다.

### 상태 검증과 상호작용 검증

테스트는 크게 두 방식으로 결과를 확인합니다. 상태 검증(state verification)은 호출 뒤에 반환값이나 객체 상태가 기대와 같은지 봅니다. 장바구니에서 쿠폰을 적용한 뒤 총액이 9,000원인지 검사하는 것이 예입니다. 상호작용 검증(interaction verification)은 어떤 협력 객체가 어떤 인자로 몇 번 호출되었는지 봅니다. “결제 승인 요청을 한 번만 보냈는가”, “재고가 없으면 이메일 발송을 하지 않았는가”가 예입니다.

Mock은 상호작용 검증에 특히 어울립니다. Martin Fowler의 [Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)는 Mock과 Stub의 차이를 상태 검증과 행위 검증의 관점에서 설명합니다. 그렇다고 Mock이 더 고급이거나 언제나 정확하다는 뜻은 아닙니다. 외부에 꼭 일어나야 하는 부수 효과를 검사할 때는 강력하지만, 내부 메서드 호출 순서까지 지나치게 검증하면 구현을 조금만 정리해도 테스트가 깨집니다.

### 테스트 피라미드와 격리의 목적

모든 테스트를 실제 환경으로 만들면 사용 흐름에 가까워 보이지만 느리고 불안정하며 실패 원인을 좁히기 어렵습니다. Google Testing Blog의 [end-to-end 테스트 중심 전략에 대한 글](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)은 큰 통합 테스트가 외부 환경과 파트너 장애 때문에 신호를 잃을 수 있음을 보여 줍니다. 반대로 모든 것을 더블로 만들면 프로토콜, SQL, 직렬화, 권한 같은 실제 연결의 실패를 놓칩니다. 테스트 피라미드는 아래층의 빠르고 격리된 검증을 많이 두고, 위층의 실제 연결 검증을 더 적은 핵심 시나리오에 쓰자는 균형의 모델입니다.

## 다섯 가지 테스트 더블을 구분하기

### Dummy: 자리를 채우지만 결과에는 쓰지 않는 값

Dummy는 호출에 필요한 인자 자리를 채울 뿐, 테스트의 결과에 영향을 주지 않는 값입니다. 예를 들어 감사 로그 객체를 생성자에 전달해야 하지만 이번 테스트는 할인 계산만 확인한다면, 실제 동작이 없는 빈 감사 객체를 둘 수 있습니다. Dummy를 지나치게 똑똑하게 만들 필요는 없습니다. 결과에 관여하지 않는 객체가 복잡해지면 테스트 독자는 무엇이 중요한지 알기 어려워집니다.

다만 Dummy가 사실은 호출되는 순간 문제가 생길 수 있습니다. null을 넣고 우연히 지금은 호출되지 않는다고 가정하는 방식은 리팩터링 뒤 `NullPointerException`을 만들 수 있습니다. 타입 시스템이나 간단한 no-op 구현으로 명시적인 Dummy를 두면 의도가 낫습니다. “이 협력자는 이 시나리오의 관심사가 아니다”라는 표시가 되기 때문입니다.

### Stub: 테스트에 필요한 답을 돌려주는 객체

Stub은 미리 정한 값을 돌려줘 테스트가 특정 분기로 가게 합니다. 재고 저장소 Stub이 상품 A에는 5개, 상품 B에는 0개가 있다고 응답하면 주문 서비스가 재고 충분·부족 경로를 각각 확인할 수 있습니다. Stub의 핵심은 호출한 뒤 무엇이 몇 번 일어났는지가 아니라, 테스트 대상이 받는 입력을 통제한다는 점입니다.

```java
InventoryPort inventory = productId ->
    productId.equals("A-100") ? 5 : 0;

OrderResult result = service.place("A-100", 2);

assertThat(result.status()).isEqualTo(ACCEPTED);
```

이 테스트에서 관심사는 주문 규칙의 결과입니다. inventory가 데이터베이스 쿼리를 어떤 SQL로 만들었는지, 몇 번 호출됐는지는 관심사가 아닙니다. 그런 세부 사항까지 검사하면 할인 규칙을 바꾸는 테스트가 저장소 구현 변화까지 함께 품게 됩니다. Stub은 가능한 한 시나리오에 필요한 응답만 표현하는 편이 좋습니다.

### Fake: 단순하지만 동작하는 대체 구현

Fake는 실제 구현보다 단순하지만 기능적으로 동작하는 구현입니다. 대표적인 예는 메모리 안에 데이터를 저장하는 저장소입니다. `InMemoryOrderRepository`는 SQL과 트랜잭션을 쓰지 않지만 `save`, `findById` 같은 인터페이스를 실제처럼 제공합니다. 테스트 여러 단계에서 데이터 상태가 변하는지 보고 싶을 때 Stub 여러 개보다 읽기 쉬울 수 있습니다.

Fake는 편리한 만큼 위험도 있습니다. 메모리 Map은 DBMS의 unique constraint, 동시성, 정렬 규칙, null 처리, 트랜잭션 롤백을 똑같이 흉내 내지 않습니다. Fake가 실제 구현과 다른 동작을 하는데도 테스트가 모두 통과하면 거짓 확신이 생깁니다. 그래서 Fake는 도메인 규칙과 흐름을 빠르게 검증하는 용도로 두고, 저장소 계약 자체는 실제 DBMS를 붙인 통합 테스트로 따로 확인합니다. Fake의 한계는 주석이나 테스트 이름에 숨기지 말고 팀이 알 수 있게 문서화해야 합니다.

### Spy: 나중에 관찰할 수 있는 기록기

Spy는 협력 객체가 받은 호출을 기록해 테스트가 나중에 확인할 수 있게 합니다. 예를 들어 주문이 승인됐을 때 알림 발송 요청이 만들어졌는지를 보고 싶다면, `NotificationSpy`가 받은 메시지를 목록에 쌓도록 할 수 있습니다. Mock 프레임워크의 `verify`와 비슷해 보이지만, Spy는 보통 단순한 구현 안에 기록을 남기고 테스트가 그 상태를 읽는 방식입니다.

Spy는 “부수 효과가 발생했는가”를 확인할 때 유용합니다. 단, 구현 세부 사항을 모두 기록하려고 하면 테스트가 로그 분석처럼 변합니다. 사용자에게 실제로 보낼 메시지의 종류와 수신자, 중요한 도메인 이벤트 정도만 검증하고, 내부 헬퍼 호출 순서까지 고정하지 않는 편이 유지보수에 좋습니다.

### Mock: 기대한 상호작용을 검증하는 객체

Mock은 테스트 전에 기대한 호출을 선언하고, 테스트 후 그 기대가 만족됐는지 검증합니다. 예를 들어 재고 예약에 성공한 주문만 결제 게이트웨이를 호출해야 한다는 정책은 Mock으로 명확하게 표현할 수 있습니다. 실패 경로에서 결제가 호출되지 않았음을 보이는 것도 중요합니다.

```java
verify(paymentGateway).authorize(orderId, Money.won(9000));
verifyNoMoreInteractions(paymentGateway);
```

그러나 `verifyNoMoreInteractions`는 강한 주장입니다. 실제 비즈니스 요구가 “승인 요청을 정확히 한 번 보낸다”라면 적절할 수 있지만, 추후 추적용 조회나 idempotency 키 확인을 추가했을 때 기능은 맞아도 테스트가 깨집니다. Mock 검증은 외부 계약, 비용이 큰 부수 효과, 보안 경계처럼 호출 자체가 의미일 때에 집중하세요. 내부 구현의 협력 방식까지 Mock으로 고정하면 테스트가 설계를 안내하는 대신 설계를 묶어 버립니다.

## 무엇을 실제로 연결하고 무엇을 대체할까

결정 기준은 “가짜냐 실제냐”가 아니라 실패했을 때 알고 싶은 사실입니다. 할인 정책의 경계값이 맞는지 알고 싶다면 시간과 저장소를 통제한 단위 테스트가 빠르고 명확합니다. JDBC 드라이버와 스키마, 인덱스, 제약 조건이 맞는지 알고 싶다면 실제 DBMS를 쓰는 통합 테스트가 필요합니다. 외부 결제사의 계약이 바뀌지 않았는지는 sandbox 또는 계약 테스트가 더 적합합니다. 브라우저에서 로그인부터 주문 완료까지 되는지는 적은 수의 E2E 테스트로 확인할 수 있습니다.

시간도 자주 놓치는 의존성입니다. `now()`를 코드 여기저기서 직접 읽으면 월말, 자정, 만료 시점 테스트가 불안정해집니다. Clock 인터페이스나 명시적인 시간을 인자로 받아 테스트에서 고정하면 Stub처럼 입력을 통제할 수 있습니다. 난수, UUID, 환경 변수, 파일 시스템도 같은 원리입니다. 다만 프로덕션 인터페이스를 무작정 늘리기보다 실제로 변동성이 테스트 결과를 흔드는 경계에만 주입하세요.

HTTP 클라이언트의 더블도 응답 코드 하나만 반환하는 수준에서 끝나면 위험할 수 있습니다. 타임아웃, 재시도, 중복 요청, 429 제한, 잘못된 JSON, 인증 실패가 서비스 행동에 중요한 경우에는 Stub 시나리오에 포함해야 합니다. 그리고 실제 HTTP 직렬화와 헤더, 인증 스킴은 별도의 통합 또는 계약 테스트에서 확인해야 합니다. 더블은 외부 시스템 전체를 복제하는 수단이 아니라, 우리 코드가 외부 실패를 어떻게 해석하는지 확인하는 도구입니다.

## 구체적 업무 예시: 주문 승인과 결제 요청의 경계

온라인 주문 서비스가 있다고 가정해 보겠습니다. 주문을 받으면 상품 재고를 확인하고, 할인 쿠폰을 적용하고, 결제 승인 요청을 보내고, 성공하면 주문 상태를 `PAID`로 바꾸며, 실패하면 재고 예약을 해제합니다. 이 흐름 전체를 실제 DB와 결제 sandbox, 메시지 브로커까지 붙여 테스트하면 실제와 가깝지만, 쿠폰의 1원 반올림 오류 하나를 찾는 데 수 분이 걸릴 수 있습니다.

도메인 단위 테스트에서는 재고 포트를 Stub으로 두고, 결제 포트는 Spy 또는 Mock으로 둡니다. 재고가 부족한 경우 결과가 `REJECTED`이고 결제가 호출되지 않았는지를 확인합니다. 쿠폰이 만료된 경우에는 Clock을 고정해 결과 금액을 검사합니다. 이 테스트들은 주문 규칙을 설명하는 실행 가능한 문서가 됩니다. 반면 `OrderRepository`의 unique constraint와 트랜잭션 롤백은 Testcontainers 같은 격리된 실제 DB 환경의 통합 테스트에서 확인합니다. 결제사에 보내는 요청의 필드와 응답 해석은 제공자 계약 또는 sandbox 테스트로 확인합니다.

이렇게 나누면 결제 sandbox가 불안정한 날에도 할인 규칙 테스트가 모두 실패하는 일을 줄일 수 있습니다. 동시에 “Mock이 통과했으니 실제 결제도 된다”라는 착각을 피합니다. 실패가 나면 어느 층이 깨졌는지 바로 좁힐 수 있고, 각 테스트가 보호하는 위험도 설명할 수 있습니다.

## 테스트 더블이 만드는 흔한 함정

첫째, Mock을 과도하게 사용해 내부 호출 순서를 테스트의 계약으로 만들어 버리는 경우입니다. 리팩터링으로 두 메서드를 합치거나 캐시를 추가했는데 사용자 결과는 같아도 수십 개 테스트가 깨지면, 테스트는 회귀를 잡는 안전망보다 변경 비용이 됩니다. 결과 상태로 충분한 테스트는 상태를 검증하고, 반드시 외부로 나가야 하는 효과만 상호작용 검증으로 남기세요.

둘째, Fake를 실제 시스템과 동일하다고 믿는 경우입니다. 메모리 저장소는 동시 트랜잭션 충돌을 재현하지 못하고, 가짜 메시지 큐는 소비 순서·중복 전달을 다르게 처리할 수 있습니다. Fake가 편하다는 사실은 실제 통합 테스트를 없애는 근거가 아닙니다. 차이를 목록화하고, 실제 구현의 중요한 계약을 검증하는 테스트를 유지해야 합니다.

셋째, 더블이 테스트 내부 구현을 그대로 복제하는 경우입니다. 프로덕션 코드와 같은 알고리즘으로 예상값을 계산하면 둘이 같은 실수를 공유할 수 있습니다. 특히 세금·할인·환율처럼 계산이 중요한 영역은 테스트 예상값을 단순하고 독립적인 방식으로 작성하거나, 대표 케이스를 업무 담당자와 합의한 표로 관리하는 편이 낫습니다.

## 실패 원인을 빨리 찾게 만드는 테스트 경계

좋은 테스트 경계는 성공할 때보다 실패할 때 가치를 드러냅니다. 단위 테스트가 실패하면 보통 도메인 규칙 또는 그 주변 코드의 원인을 바로 의심할 수 있어야 합니다. 통합 테스트가 실패하면 SQL, 직렬화, 마이그레이션, 네트워크 설정처럼 실제 연결 경계를 조사할 수 있어야 합니다. E2E 테스트가 실패하면 사용자 흐름의 회귀를 알려 주되, 모든 원인을 혼자 증명하려 들지 않아야 합니다. 이 역할 분담이 없으면 한 브라우저 테스트의 실패가 프런트엔드·백엔드·DB·외부 인증·테스트 환경 중 어디에서 생겼는지 몇 시간씩 추측하게 됩니다.

테스트 더블은 외부 실패를 없애기 위해서만 쓰는 것이 아니라, 어떤 신호를 받고 싶은지 선명하게 하기 위해 씁니다. 예를 들어 세금 계산 서비스가 환율 API를 호출하는데 응답이 느릴 때 재시도 정책을 검증하고 싶다면, Stub은 성공·타임아웃·429·잘못된 형식 같은 응답을 즉시 재현할 수 있습니다. 이때 테스트가 검증할 것은 HTTP 라이브러리의 구현이 아니라 우리 서비스가 제한 시간 뒤 어떤 오류를 사용자에게 돌려주고, 중복 요청을 만들지 않으며, 어떤 로그와 메트릭을 남기는가입니다.

반면 외부 API에 보내는 HTTP header, signature, JSON 스키마가 맞는지는 Stub만으로 보장할 수 없습니다. 이를 위한 테스트는 실제 서버 또는 제공자가 제공하는 sandbox와 제한된 계약 테스트로 분리합니다. 계약 테스트가 많아질수록 모든 사용 흐름을 복제하려 하지 말고, 우리가 의존하는 요청·응답 필드와 오류 규약을 우선합니다. 더블로 빠른 피드백을 받고 실제 경계에서 적은 수의 강한 검증을 두는 구조가 핵심입니다.

### 테스트 데이터는 더블의 일부다

더블 설계에서 값의 이름도 중요합니다. `user1`, `item2`, `true` 같은 값만 쓰면 왜 그 경로를 검증하는지 읽기 어렵습니다. `expiredCoupon`, `outOfStockProduct`, `paymentDeclined`처럼 업무 의미가 있는 fixture를 만들면 테스트가 요구사항을 드러냅니다. 다만 모든 테스트가 거대한 공통 fixture에 의존하면 한 데이터 변경이 수십 테스트를 깨뜨립니다. 각 테스트가 필요한 최소 데이터만 만들고, 여러 테스트가 같은 복잡한 도메인 상태를 필요로 할 때만 builder나 factory로 올리는 편이 좋습니다.

민감한 운영 데이터를 Fake나 fixture로 복제해서는 안 됩니다. 주민등록번호, 실제 고객 이메일, 결제 토큰이 들어간 샘플은 테스트를 편하게 만들지라도 유출 위험을 늘립니다. 의미를 유지한 합성 데이터, 마스킹된 값, 고정된 식별자를 사용하고, 로그와 실패 출력에도 비밀 값이 남지 않게 확인해야 합니다. 테스트 더블은 통제성을 주는 도구이므로 데이터 보호까지 통제 범위에 넣어야 합니다.

### 비동기 작업과 재시도는 별도 경계로 보자

메시지 큐, 이벤트, 비동기 작업은 테스트 더블을 특히 조심해서 써야 하는 영역입니다. 프로세스 안에서 바로 콜백을 호출하는 Fake 큐는 빠르지만 실제 브로커의 중복 전달, 순서 변경, 지연, 소비자 재시작을 표현하지 못합니다. 단위 테스트에서는 “이 이벤트를 발행하라는 의도”와 이벤트 payload를 Spy나 Mock으로 확인할 수 있습니다. 그러나 소비자가 같은 메시지를 두 번 받았을 때도 안전한지, 재처리와 멱등성이 맞는지는 실제 브로커 또는 그 특성을 충분히 재현한 통합 환경에서 확인해야 합니다.

재시도도 호출 횟수만 검사해서는 충분하지 않습니다. 어떤 오류는 재시도해야 하고, 어떤 오류는 즉시 실패해야 하며, 언제 중단하고 사용자에게 어떤 상태를 남길지가 정책입니다. Clock과 Stub을 함께 쓰면 첫 실패 뒤 대기 시간, 최대 시도, circuit breaker 상태 전환을 빠르게 검증할 수 있습니다. 하지만 재시도 간격이 실제 운영에서 외부 제공자의 제한과 맞는지는 관찰 환경에서 검증해야 합니다. 빠른 테스트와 실제 조건의 검증을 혼동하지 않는 것이 중요합니다.

## 팀에서 일관되게 쓰는 규칙 만들기

프로젝트마다 더블 이름과 용법이 제각각이면 코드 리뷰가 어려워집니다. 팀은 거창한 프레임워크 표준 대신 몇 가지 질문을 합의할 수 있습니다. 이 테스트가 최종 상태를 검증하는가, 외부 부수 효과를 검증하는가, 실제 구현과의 계약을 어디서 검증하는가, Fake의 알려진 차이는 무엇인가를 PR 설명이나 테스트 이름에서 드러내는 식입니다. Mock을 금지하거나 권장하는 단순 규칙보다 이런 질문이 변화에 잘 버팁니다.

새로운 더블을 만들기 전에는 기존 테스트 유틸리티가 같은 문제를 이미 풀고 있는지도 확인합니다. 각 테스트가 자체 Fake 저장소를 만들면 동작 차이가 생기고, 어느 것이 실제 계약에 가까운지 알기 어렵습니다. 반대로 공용 Fake를 너무 복잡하게 만들면 작은 테스트까지 거대한 설정에 묶입니다. 반복되는 도메인 규칙만 공용화하고, 시나리오 특유의 응답은 해당 테스트에 가깝게 두는 균형이 필요합니다.

마지막으로 실패하는 테스트를 고칠 때 무조건 더블 기대값을 바꾸지 마세요. 요구사항이 바뀐 것인지, 구현이 잘못된 것인지, 더블이 실제 계약을 잘못 모델링한 것인지 구분해야 합니다. 특히 Mock의 호출 순서가 달라졌다는 실패는 기능 회귀가 아니라 리팩터링 신호일 수 있습니다. 테스트가 무엇을 보호해야 하는지 다시 읽고, 불필요한 구현 결합을 제거하는 기회로 삼는 편이 낫습니다.

## 코드 리뷰에서 확인할 질문

테스트 더블을 포함한 변경을 리뷰할 때는 우선 테스트 이름만 읽고 업무 규칙을 이해할 수 있는지 봅니다. `shouldCallX`보다 `재고가 없으면 결제를 요청하지 않는다`가 더 좋은 이름입니다. 다음으로 더블의 설정이 이 시나리오에 필요한 입력만 제공하는지 확인합니다. 필요하지 않은 호출까지 예외를 던지게 만들거나, 모든 메서드를 Mock으로 검증하면 테스트가 구현 구조에 과도하게 묶일 가능성이 큽니다.

또한 실제 통합 테스트가 어디에 있는지 연결해야 합니다. 새 저장소 포트가 추가됐다면 마이그레이션, SQL 변환, 제약 조건을 검증하는 테스트가 있는지, 외부 API 어댑터가 추가됐다면 인증과 직렬화를 검증하는 경로가 있는지 확인합니다. 한 PR 안에 모두 만들 필요는 없지만, “단위 테스트가 통과했으니 실제 연결도 안전하다”라는 빈틈은 남기지 않아야 합니다. 중요한 계약의 소유 테스트 위치를 README나 테스트 패키지 구조에 남기면 새 팀원도 경계를 이해하기 쉽습니다.

실패 메시지도 설계의 일부입니다. Mock 프레임워크가 긴 호출 목록을 출력할 때, 그것만 보고 어떤 업무 요구가 깨졌는지 알기 어려울 수 있습니다. assertion 앞에 시나리오를 드러내는 값과 설명을 두고, 하나의 테스트가 너무 많은 독립 행동을 검증하면 나누세요. 빠르게 실패하고, 실패를 읽는 사람이 바로 다음 조사 지점을 알 수 있는 테스트가 좋은 더블 사용의 결과입니다.

### 작은 의존성부터 실제와 맞추기

더블과 실제 구현의 간극은 하루아침에 커지지 않습니다. 인터페이스가 바뀌었는데 Fake가 옛 동작을 계속 제공하거나, 외부 API의 오류 코드가 추가됐는데 Stub 시나리오에 반영되지 않을 때 조금씩 벌어집니다. 변경 때마다 모든 조합을 테스트할 수는 없지만, 포트의 계약이 바뀌는 PR에는 Fake와 Stub, 통합 테스트를 함께 확인하는 습관이 필요합니다. 특히 null 가능성, 페이징, 정렬, 시간대, 예외 유형처럼 경계에서 자주 달라지는 항목을 체크하세요.

테스트 더블을 선택하는 일은 구현을 피하는 일이 아닙니다. 검증 비용을 가장 신뢰할 수 있는 층에 배치하는 일입니다. 단위 테스트가 빠른 실패 신호를 주고, 통합 테스트가 실제 기술 계약을 지키며, E2E 테스트가 사용자의 중요한 여정을 보호하도록 역할을 분리하면 테스트 수가 늘어도 원인과 책임이 선명해집니다.

처음에는 하나의 기능에서만 이 구분을 적용해도 충분합니다. 예를 들어 주문 취소 규칙의 성공·실패·중복 요청 세 경우를 Stub과 Spy로 빠르게 만들고, 실제 저장소의 취소 상태 전이는 통합 테스트 한두 개로 확인합니다. 이후 테스트가 읽기 쉬워지고 실패 원인이 좁혀지는 효과가 확인되면 다른 기능에 확장하세요. 모든 기존 테스트를 한 번에 Mock 스타일로 바꾸는 대규모 정리는 위험과 비용이 크고, 요구사항 회귀를 섞어 놓을 수 있습니다.

더블의 목적은 독자를 속이는 것이 아니라 불확실성을 통제하는 것입니다. 테스트가 통제하지 않는 시간, 네트워크, 데이터, 외부 계정을 분명히 표시할수록 결과를 해석하기 쉬워집니다. 그리고 실제 시스템에서만 확인 가능한 사실은 별도의 테스트와 관찰로 남겨야 합니다. 이 두 가지를 함께 지킬 때 빠른 테스트와 현실적인 검증은 경쟁하지 않고 서로 보완합니다.

테스트를 추가한 뒤에는 의도적으로 구현을 조금 정리해 보는 것도 좋은 확인 방법입니다. 결과가 같은 리팩터링만으로 여러 Mock이 깨진다면, 그 테스트가 외부 계약이 아니라 내부 절차에 매달렸을 가능성이 큽니다. 반대로 결제 요청이나 이벤트 발행처럼 반드시 유지되어야 할 호출이 사라졌을 때 테스트가 실패한다면, 그 더블은 올바른 경계를 지키고 있는 것입니다. 이 기준으로 테스트를 다듬으면 장기적으로 변경이 쉬워집니다.

테스트 더블의 선택을 코드 리뷰와 회고에서 짧게 공유하면 팀의 공통 언어도 자랍니다. “이 Stub은 입력 통제를 위한 것”, “이 통합 테스트는 실제 SQL 계약을 위한 것”처럼 목적을 설명할 수 있으면, 새 테스트를 추가할 때도 같은 균형을 재사용할 수 있습니다.

## 한계와 적용 기준 Q&A

### Q. 테스트마다 Mock 프레임워크를 쓰면 Fake가 필요 없나요?

A. 아닙니다. 상태가 여러 단계로 변하는 시나리오에서는 작은 Fake가 기대 호출을 길게 나열한 Mock보다 읽기 쉬울 수 있습니다. 반대로 외부 결제 요청처럼 호출 자체가 중요한 경계는 Mock이나 Spy가 더 명확할 수 있습니다. 구현 도구가 아니라 테스트가 설명하려는 행동으로 선택하세요.

### Q. 실제 DB 통합 테스트가 느리면 전부 Stub으로 바꿔야 하나요?

A. 먼저 어떤 DB 계약을 검증해야 하는지 분리하세요. 도메인 규칙은 Stub 또는 Fake로 빠르게 확인하고, SQL·마이그레이션·제약 조건·잠금처럼 실제 DBMS가 중요한 테스트만 좁혀 실행합니다. 느린 통합 테스트를 줄이는 목표는 실제 검증을 없애는 것이 아니라 필요한 곳에 집중하는 것입니다.

### Q. Mock 검증은 몇 번 호출됐는지까지 항상 써야 하나요?

A. 호출 횟수가 업무 요구일 때만 쓰는 편이 좋습니다. 결제 승인처럼 중복 호출이 금전 사고를 만들 수 있는 곳은 정확히 한 번이 중요한 계약입니다. 단순 조회나 내부 변환은 호출 횟수보다 최종 결과가 더 안정적인 검증일 수 있습니다.

### Q. 테스트 더블이 많아지면 구현보다 테스트 코드가 복잡해집니다. 어떻게 하나요?

A. 도메인 모델이 너무 많은 외부 세부 사항을 직접 알고 있는지 살펴보세요. 포트와 어댑터처럼 외부 경계를 작게 만들고, 테스트 데이터 빌더를 재사용하며, 한 테스트가 하나의 의사 결정을 설명하게 쪼개면 복잡도가 줄어듭니다. 더블 수가 계속 늘면 설계의 결합도가 높다는 신호일 수 있습니다.

## 마무리

테스트 더블은 실제 시스템을 속이는 장치가 아니라, 테스트가 답할 질문을 선명하게 만드는 경계 도구입니다. Stub은 입력을 통제하고, Fake는 단순한 동작을 제공하며, Spy와 Mock은 중요한 부수 효과를 관찰합니다. 각 역할을 구분하면 단위 테스트는 빠르고 신뢰할 수 있게 유지하면서, 실제 데이터베이스·네트워크·브라우저의 계약은 필요한 통합 테스트에서 놓치지 않을 수 있습니다. 다음 테스트를 작성할 때 “무엇을 Mock할까?”보다 “이 실패가 나에게 무엇을 알려 주어야 하나?”를 먼저 질문해 보세요.
