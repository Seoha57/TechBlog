온라인 결제 버튼을 한 번 눌렀는데 화면이 늦게 반응하면 사용자는 다시 누릅니다. 모바일 네트워크가 끊겼다가 앱이 자동 재시도할 수도 있고, 로드 밸런서가 연결 오류를 만났을 때 클라이언트가 같은 요청을 다시 보낼 수도 있습니다. 서버가 요청 하나를 처리한 뒤 응답만 보내지 못했다면, 사용자는 성공을 모르고 재시도합니다. 이런 환경에서 “클라이언트는 한 번만 호출한다”는 가정은 안전하지 않습니다.

멱등성(idempotency)은 같은 의도를 가진 요청을 여러 번 처리해도 최종 효과가 한 번 처리한 것과 같게 만드는 성질입니다. 단순히 같은 JSON을 보내면 같은 응답을 준다는 뜻이 아니라, 주문이 두 번 생성되지 않고 결제가 두 번 승인되지 않으며 재고가 두 번 차감되지 않는다는 업무적 약속입니다. 이 글은 API 멱등성을 개발 규칙과 QA 테스트 시나리오로 바꾸는 방법을 다룹니다.

## 먼저 알아둘 기반 기술

HTTP는 요청과 응답을 주고받는 프로토콜입니다. GET은 보통 조회, POST는 새 작업 생성, PUT은 리소스의 지정 상태 설정, DELETE는 삭제에 사용됩니다. HTTP 의미론에서 PUT과 DELETE는 동일 요청을 여러 번 보내도 최종 서버 상태가 같아야 한다는 멱등적 성격을 가질 수 있습니다. 하지만 실제 업무 API에서는 메서드보다 구현이 중요합니다. `PUT /users/1`이 호출할 때마다 환영 이메일을 보낸다면 리소스 상태는 같아도 부수 효과는 중복됩니다.

재시도(retry)는 일시적 네트워크 오류나 timeout 뒤에 같은 요청을 다시 보내는 동작입니다. timeout은 서버가 아무 일도 하지 않았다는 증거가 아닙니다. 서버가 이미 DB 트랜잭션을 commit했지만 응답 패킷이 사라졌을 수 있습니다. 따라서 클라이언트·API gateway·메시지 소비자가 재시도하는 시스템에서는 중복을 정상적인 입력으로 다뤄야 합니다.

## Idempotency-Key의 역할

가장 널리 쓰이는 방식은 클라이언트가 작업 의도를 식별하는 임의의 키를 보내고, 서버가 그 키와 최초 처리 결과를 보관하는 것입니다. 결제 화면을 연 뒤 생성한 UUID를 `Idempotency-Key` 헤더로 전송하고, 같은 사용자·같은 endpoint·같은 키의 재요청은 새 결제를 만들지 않고 이전 결과를 돌려주는 식입니다. 키는 요청 본문 전체를 대신하는 보안 토큰이 아니며, 다른 사용자가 추측할 수 없게 충분한 엔트로피를 가져야 합니다.

```http
POST /payments
Idempotency-Key: 6a0a92f0-4f79-4c13-a2c5-8c7e5d2c5f11
Content-Type: application/json

{"orderId":"O-20261025-7","amount":12000}
```

서버는 키를 보자마자 단순히 “이미 봤다”고 응답하면 안 됩니다. 최초 요청이 처리 중이면 두 번째 요청이 어떤 상태를 받을지, 최초 요청이 실패했으면 실패 응답을 재사용할지, 키가 같은데 본문이 다르면 어떻게 거절할지 정해야 합니다. 보통 키·사용자·작업 종류와 요청 fingerprint를 함께 저장하고, 동일 키에 다른 의도가 오면 409 같은 명확한 오류를 반환합니다. 이 정책이 없으면 클라이언트 버그가 다른 주문을 이전 결과로 덮어쓸 수 있습니다.

## 경쟁 조건을 테스트하지 않으면 멱등성은 완성되지 않는다

가장 위험한 경우는 같은 키를 가진 두 요청이 거의 동시에 도착하는 상황입니다. 두 worker가 모두 ‘키 없음’을 읽고 각각 결제를 시작하면, 나중에 하나만 키 테이블에 저장해도 이미 외부 부수 효과는 두 번 일어났을 수 있습니다. 유니크 제약 조건, 트랜잭션, 원자적 insert, lock, outbox 같은 방법 중 시스템에 맞는 경계를 선택해야 합니다. 어떤 방법이든 동시성 테스트가 필요합니다.

테스트는 순차 요청만 보내는 데서 끝나면 안 됩니다. barrier를 써서 두 클라이언트가 같은 키로 동시에 API를 호출하게 하고, 결과가 하나의 payment ID를 가리키는지, 외부 결제 adapter 호출 횟수가 한 번인지, 주문 상태 전이가 한 번인지 확인합니다. 단위 테스트에서는 결제 adapter를 Spy로 두고 호출 횟수를 관찰할 수 있고, 통합 테스트에서는 실제 DB의 unique constraint와 transaction 경계를 확인합니다. 둘 중 하나만으로는 부족합니다.

## 구체적 업무 예시: 주문 결제 승인

주문 `O-17`의 결제 요청이 timeout 되었다고 해 보겠습니다. 사용자는 새로고침 후 같은 버튼을 누릅니다. 첫 요청은 payment provider에 승인 요청을 보내고 DB에 `PENDING` 레코드를 만들었지만, 응답 직전에 연결이 끊겼습니다. 두 번째 요청은 같은 Idempotency-Key를 보내며, 서버는 저장된 payment ID와 상태를 찾아야 합니다. provider를 다시 호출하지 않고 현재 상태가 `AUTHORIZED`라면 같은 성공 결과를 반환합니다.

테스트 표에는 정상 한 번, 같은 키 순차 두 번, 같은 키 동시 두 번, 같은 키 다른 본문, provider timeout 뒤 재시도, DB commit 뒤 응답 단절, 키 만료 뒤 재요청을 포함합니다. 각 경우에서 HTTP status만 보지 말고 주문 수, 결제 승인 수, 재고 예약 수, 이벤트 발행 수, 감사 로그를 확인합니다. 멱등성은 하나의 테이블만 중복되지 않는 성질이 아니라 전체 업무 흐름의 부수 효과가 한 번인지 검증하는 일입니다.

## 한계와 적용 기준 Q&A

### Q. 모든 POST에 Idempotency-Key가 필요한가요?

A. 조회나 중복되어도 영향이 없는 작업까지 무조건 넣을 필요는 없습니다. 금전, 재고, 예약, 이메일 발송, 외부 변경처럼 중복 비용이 큰 명령을 우선 분석하세요. 다만 ‘중복될 일이 없다’는 가정 대신 timeout·재시도 경로를 실제로 확인해야 합니다.

### Q. 키는 얼마나 오래 보관해야 하나요?

A. 클라이언트 재시도 창, 결제사 승인 조회 기간, 감사 요구, 저장 비용에 따라 다릅니다. 너무 짧으면 늦게 도착한 재시도를 새 요청으로 처리하고, 너무 길면 저장·개인정보 관리 비용이 늘 수 있습니다. 만료 정책과 만료 뒤의 응답을 API 문서에 명시하세요.

### Q. 메시지 큐도 멱등성이 필요한가요?

A. 필요합니다. 많은 브로커는 at-least-once 전달로 같은 메시지를 다시 보낼 수 있습니다. 소비자는 event ID 또는 업무 키를 기준으로 중복을 무해하게 처리해야 합니다. HTTP API의 키와 메시지의 deduplication은 같은 원리지만 저장 위치와 실패 경계가 다르므로 각각 테스트해야 합니다.

## 멱등성 저장소를 설계할 때의 선택

Idempotency-Key를 어디에 저장할지는 작업의 원자성에 큰 영향을 줍니다. 주문 레코드와 같은 관계형 데이터베이스에 키와 결과를 함께 저장하면, 업무 상태와 deduplication 상태를 같은 트랜잭션으로 묶기 쉬운 장점이 있습니다. 반면 고속 캐시에만 키를 저장하면 응답은 빠를 수 있지만 cache eviction이나 장애 뒤에 중복 방지 정보가 사라질 수 있습니다. 어떤 저장소를 쓰든 키가 없어지는 시점과 업무 결과가 남는 시점의 관계를 명확히 해야 합니다.

결제처럼 외부 provider 호출이 있는 작업은 데이터베이스 트랜잭션만으로 모든 부수 효과를 원자화하기 어렵습니다. DB commit 전 provider 승인에 성공하면 DB 실패 뒤 외부 결제가 남을 수 있고, DB commit 뒤 provider 호출에 실패하면 주문 상태와 결제 상태가 어긋날 수 있습니다. 이를 단순히 키 테이블 하나로 해결할 수는 없습니다. 보상 절차, provider 상태 조회, outbox pattern, 비동기 처리 중 무엇이 업무 요구에 맞는지 선택해야 합니다. 멱등 키는 중복 요청을 식별하는 핵심 도구지만 분산 트랜잭션의 모든 문제를 없애지는 않습니다.

키의 scope도 중요합니다. 같은 key가 서로 다른 endpoint에서 우연히 충돌하면 안 되고, 다른 사용자나 다른 tenant의 요청이 같은 결과를 보아도 안 됩니다. 보통 사용자 또는 고객 조직 식별자, operation 이름, key를 함께 유니크하게 다룹니다. API gateway가 key를 전달하는지, background worker가 이어받는지, 로그에서 key가 개인정보나 비밀처럼 취급되어야 하는지도 확인해야 합니다.

### 진행 중 요청을 만났을 때의 UX

첫 요청이 아직 처리 중일 때 두 번째 같은 키 요청이 오면 서버 정책은 여러 가지일 수 있습니다. 일정 시간 기다려 첫 결과를 돌려줄 수 있고, `in_progress` 상태와 retry-after 정보를 줄 수 있으며, 두 번째 요청을 구독자로 연결할 수도 있습니다. 어떤 선택이든 두 번째 요청이 새로운 provider 호출이나 재고 차감을 만들지 않는다는 보장이 우선입니다. 사용자는 화면이 멈춘 것처럼 느끼지 않게 처리 중 상태와 다음 행동을 알아야 합니다.

처리 중 레코드가 worker crash로 영원히 남는 문제도 생각해야 합니다. 상태를 만들기만 하고 완료·실패 전환이 없으면 같은 key의 재시도가 계속 막힐 수 있습니다. timeout, lease, 복구 작업, 감사 로그를 두고 어느 시점에 작업을 재개하거나 실패로 확정할지 정의해야 합니다. 자동으로 오래된 요청을 삭제하는 정책은 실제 외부 부수 효과가 끝났는지 확인하지 못하면 또 다른 중복을 만들 수 있으므로 보수적으로 설계합니다.

## 테스트를 계층으로 나누기

단위 테스트는 같은 key의 두 번째 호출이 저장된 결과를 반환하는지, 다른 payload는 거절하는지, provider 호출이 한 번인지 빠르게 검증합니다. 이 층에서는 provider와 clock을 Stub·Spy로 두고 상태 전이 자체를 읽기 쉽게 확인합니다. 하지만 이 테스트만으로 데이터베이스의 unique constraint나 isolation을 보장할 수 없습니다.

통합 테스트는 실제 데이터베이스에서 동시에 insert를 시도하고, 트랜잭션 rollback과 key 재사용이 기대대로 동작하는지 확인합니다. 테스트 환경에서 두 요청을 barrier로 동기화해 경쟁을 의도적으로 만들고, 최종 주문·결제 레코드 수와 key 상태를 확인합니다. HTTP 통합 테스트는 header가 API gateway와 application을 지나도 보존되는지, timeout 뒤 클라이언트가 key를 유지하는지 확인할 수 있습니다. 외부 provider sandbox 테스트는 실제 승인·조회 규약을 최소한의 시나리오로 검증합니다.

각 테스트가 어떤 위험을 막는지 이름과 설명에 남기면, 실패했을 때 원인을 좁히기 쉽습니다. “중복 결제 방지”라는 큰 이름 하나보다 “같은 key의 동시 요청은 하나의 provider 승인만 만든다”, “응답 단절 뒤 재시도는 기존 payment ID를 반환한다”처럼 구체적인 시나리오가 좋습니다. 테스트 데이터에는 실제 카드 번호·고객 정보 대신 합성 식별자를 사용하고, 실패 출력에도 민감 payload가 남지 않게 합니다.

## API 문서에 적어야 할 계약

클라이언트가 key를 올바르게 쓰려면 API 문서에 헤더 이름, 허용 형식, 생성 책임, 재사용 범위, 보관 기간, 같은 key에 다른 payload를 보냈을 때의 오류, 재시도 가능한 status를 적어야 합니다. 문서가 없으면 웹·모바일·배치 클라이언트가 각자 다른 방식으로 key를 만들고, 서버는 중복을 구분하기 어려워집니다. SDK가 있다면 재시도 시 원래 key를 유지하도록 도와줄 수 있지만, SDK가 없는 호출자도 계약을 이해할 수 있어야 합니다.

응답도 일관되어야 합니다. 최초 성공과 중복 재응답에서 같은 resource ID와 의미 있는 상태를 주고, 필요한 경우 응답이 재사용된 것인지 표시할 수 있습니다. 그러나 내부 DB 키나 provider 민감 정보를 노출할 이유는 없습니다. 사용자에게 중요한 것은 주문이 한 번만 만들어졌고 현재 어떤 상태인지, 다음에 무엇을 하면 되는지입니다.

## 관찰과 장애 대응

운영에서는 key 재사용률, payload 불일치 거절 수, 처리 중 요청 수, timeout 뒤 재시도율, provider 호출 수와 성공한 주문 수의 차이를 관찰할 수 있습니다. 갑자기 재사용률이 늘면 모바일 네트워크 또는 gateway timeout 문제가 있을 수 있고, payload 불일치가 늘면 클라이언트 버그나 key 생성 범위 문제가 있을 수 있습니다. 수치가 높다는 사실만으로 장애라고 결론내리기보다 배포·네트워크·사용자 흐름의 변화와 함께 봅니다.

사고가 나면 해당 key와 업무 ID를 통해 요청 타임라인을 재구성할 수 있어야 합니다. 어느 요청이 key를 만들었고, 어떤 worker가 처리했으며, DB 상태와 provider 상태가 무엇인지, 응답이 왜 사용자에게 전달되지 않았는지를 연결합니다. 이렇게 하면 재시도는 추측의 대상이 아니라 추적 가능한 정상 경로가 됩니다.

## 클라이언트 구현에서 지킬 점

멱등 키는 서버만의 기능이 아닙니다. 웹 화면은 사용자가 결제 버튼을 누른 순간 key를 만들고, 응답을 기다리는 동안 같은 의도에 그 key를 유지해야 합니다. 화면을 새로 고쳤을 때 key를 잃어버리면 서버는 새 작업으로 볼 수 있습니다. 반대로 완전히 다른 주문에도 이전 key를 재사용하면 payload 불일치 오류가 나거나 엉뚱한 결과를 받게 됩니다. key의 생성·보존·폐기 시점을 사용자 작업 단위와 맞추는 것이 중요합니다.

모바일 앱과 배치 클라이언트는 연결이 끊긴 뒤 재시도할 가능성이 높습니다. retry library가 새 요청 객체를 만들 때 header를 복사하는지, timeout과 cancel 뒤 같은 key를 쓰는지, 사용자가 명시적으로 새 작업을 시작했을 때만 새 key를 생성하는지 테스트해야 합니다. 백오프와 최대 시도 횟수도 서버의 보관 기간보다 길어지지 않게 설계합니다. 클라이언트가 무한히 재시도하면 서버가 멱등적이어도 사용자 경험과 비용은 나빠질 수 있습니다.

### 사용자에게 보여 줄 상태

결제나 예약의 결과를 즉시 확정하기 어려운 경우, UI는 단순 오류 대신 “요청을 확인 중입니다”라는 상태와 주문 조회 경로를 제공할 수 있습니다. 사용자가 같은 버튼을 반복해서 누르지 않게 disable 처리하는 것은 도움이 되지만, 이것만으로 서버 중복을 막을 수는 없습니다. 화면의 방어와 서버의 멱등성은 서로 다른 층이며 둘 다 필요합니다.

처리 결과가 이미 존재하는 key로 재시도됐다면 기존 주문 번호와 현재 상태를 보여 주는 편이 낫습니다. 다만 내부 승인 코드나 다른 사용자의 정보는 노출하지 않아야 합니다. 실패 상태도 재시도 가능한 일시 오류인지, 입력을 바꿔야 하는 영구 오류인지 구분해야 사용자가 올바른 다음 행동을 선택할 수 있습니다.

## 데이터 정합성의 경계

멱등성은 중복 레코드 방지와 같아 보이지만, 업무 정합성의 여러 규칙 중 하나입니다. 예를 들어 주문 생성이 한 번만 되더라도 재고가 다른 트랜잭션에서 이미 소진됐을 수 있고, 할인 쿠폰이 다른 주문에 사용됐을 수 있으며, 결제 provider의 상태가 지연되어 최신 값이 아닐 수 있습니다. 각 규칙은 유니크 제약, 조건부 update, 트랜잭션 격리, 상태 조회, 보상 처리처럼 다른 수단을 요구합니다.

그래서 테스트도 하나의 happy path에 집중하면 안 됩니다. 재고 부족과 중복 재시도가 겹친 경우, key는 같지만 사용자 인증이 바뀐 경우, 이전 요청이 실패한 뒤 외부 provider가 나중에 성공한 경우, 이벤트 전송만 실패한 경우처럼 복합 실패를 분류합니다. 모든 조합을 전수 탐색할 필요는 없지만, 금전·재고·권한처럼 위험이 큰 경계는 대표적인 조합을 명시적으로 선택해야 합니다.

### 상태 머신으로 표현하기

복잡한 작업은 `RECEIVED`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `UNKNOWN` 같은 상태를 명시하면 이해하기 쉬워집니다. state transition마다 누가 바꾸는지, 어떤 외부 효과가 이미 발생했는지, 재시도 요청이 어떤 상태에서 허용되는지 정합니다. `UNKNOWN`은 설계 실패가 아니라 응답 단절처럼 서버가 외부 결과를 확신할 수 없는 현실을 표현할 수 있습니다. 이 상태에서 무조건 새 결제를 만드는 대신 provider 조회나 운영 검토 경로를 두면 중복 비용을 줄일 수 있습니다.

상태가 많아지면 테스트도 전이 표로 정리합니다. 각 전이에 대해 입력, 기대 상태, 외부 호출 여부, 재시도 결과, 사용자에게 보일 메시지를 적습니다. 표는 요구사항을 개발·QA·운영이 같은 언어로 보는 도구가 됩니다. 코드 구현보다 먼저 전이를 합의하면, key 저장소와 retry 정책이 왜 필요한지 명확해집니다.

## 성능과 보관 비용의 균형

키 테이블은 모든 명령 요청에 쓰기가 발생할 수 있으므로 인덱스와 정리 정책을 고려해야 합니다. 만료된 key를 배치로 지울 때 업무 시간의 lock과 I/O에 영향을 주지 않는지, 파티션 또는 범위 삭제가 가능한지, 감사 목적의 요약 정보와 원문 payload를 얼마나 오래 분리해 보관할지 정합니다. 성능을 위해 결과를 캐시하더라도, 캐시가 비워졌을 때 DB의 영속 결과를 어떻게 조회할지 준비해야 합니다.

처리량이 높은 서비스에서는 key lookup 자체가 병목처럼 보일 수 있습니다. 그러나 중복 처리로 생기는 결제 사고와 수동 환불 비용을 고려하면, lookup 비용만 보고 멱등성을 생략하는 것은 위험합니다. 실제 병목이 생겼을 때는 key scope, 인덱스, 저장 형식, 비동기 처리, cache 계층을 관찰값으로 개선하세요. 안전 장치를 제거하는 대신 더 빠른 저장소와 명확한 만료 정책을 찾는 것이 올바른 최적화 방향입니다.

## 배포와 변경 관리

기존 API에 Idempotency-Key를 추가할 때는 key가 없는 기존 클라이언트를 어떻게 처리할지 결정해야 합니다. 일정 기간 optional로 두되 위험한 endpoint에서는 새 버전이나 명시적 오류를 사용할 수 있습니다. 서버 배포 중 여러 버전이 함께 실행될 때 key schema와 응답 형식이 호환되는지, key를 읽는 코드와 저장하는 코드의 순서가 안전한지 확인합니다. 데이터베이스 migration은 unique constraint가 적용되는 시점과 기존 데이터의 충돌 가능성도 고려합니다.

출시 뒤에는 제한된 트래픽에서 중복률·오류율·provider 호출 수를 관찰하고, 의도치 않은 payload mismatch나 장기 `PROCESSING` 상태가 없는지 확인합니다. 문제가 있다면 key 기능을 끄는 것보다 어떤 endpoint·클라이언트에서 계약이 어긋났는지 좁혀 수정하는 편이 안전합니다. 중복 방지 기능은 보이지 않을 때 가장 잘 동작하는 안전망이므로, 변경도 보수적으로 검증해야 합니다.

## 인증과 권한도 멱등성 범위에 넣기

같은 키라는 이유만으로 이전 응답을 아무에게나 반환하면 안 됩니다. 요청을 처음 처리한 사용자, 고객 조직, 권한 범위가 재시도 요청과 같은지 확인해야 합니다. 예를 들어 조직 관리자가 결제 요청을 시작한 뒤 권한이 회수되었거나 사용자가 다른 조직으로 전환했다면, 단순히 키만 보고 성공 응답을 재사용하는 동작은 정보 노출이나 잘못된 상태 확인으로 이어질 수 있습니다. 키의 고유성 범위에 인증 주체와 tenant를 포함하고, 응답을 돌려주기 전에도 현재 요청자가 그 결과를 볼 권한이 있는지 점검하는 편이 안전합니다.

이 규칙은 권한 확인이 재시도를 막아야 한다는 뜻은 아닙니다. 이미 승인된 결제를 취소할 권한이 사라졌다고 해서 과거 결제의 존재를 숨기면, 사용자는 timeout 뒤 어떤 일이 일어났는지 확인하지 못할 수 있습니다. 업무 정책에 따라 결과 조회와 새 명령 실행 권한을 구분해야 합니다. 즉, 멱등 키는 ‘동일한 작업인가’를 식별하고, 인가는 ‘이 사용자가 지금 그 작업을 볼 수 있거나 이어서 실행할 수 있는가’를 판단합니다. 두 책임을 하나의 키 존재 여부로 뭉치면 보안 규칙과 복구 규칙이 모두 모호해집니다.

테스트에는 로그인 세션이 갱신된 재시도, 다른 조직 계정의 같은 문자열 key, 권한 변경 뒤 결과 조회, 서비스 계정이 보낸 배치 요청을 사람 사용자가 조회하는 경우를 넣을 수 있습니다. 기대 결과는 서비스마다 다르지만, 적어도 다른 tenant의 결과가 섞이지 않고 새 부수 효과가 만들어지지 않는지는 공통으로 검증해야 합니다. 로그에도 원문 인증 토큰을 남기지 말고, 안전한 주체 식별자와 작업 식별자를 연결합니다.

## 비동기 경로에서 키를 이어 가는 방법

웹 요청 하나가 끝났다고 업무가 끝나는 시스템은 많지 않습니다. API가 주문을 기록한 뒤 메시지 큐에 이벤트를 넣고, 별도 worker가 재고 예약·알림·정산을 수행할 수 있습니다. 이때 HTTP의 `Idempotency-Key`가 worker까지 전달되지 않으면 앞단은 중복을 막았지만 뒷단 소비자가 같은 이벤트를 두 번 처리하는 빈틈이 생깁니다. 이벤트에는 별도의 event ID와 원래의 업무 ID를 함께 넣고, 소비자는 어느 식별자로 중복을 판단할지 명확히 정해야 합니다.

같은 이름의 키를 모든 계층에서 그대로 쓰는 것이 항상 정답은 아닙니다. 결제 요청 하나가 여러 개의 독립된 알림 이벤트를 만들 수 있고, 알림 재전송은 결제 재시도와 다른 정책을 가질 수 있기 때문입니다. 중요한 것은 부모 작업과 파생 작업의 관계를 추적할 수 있게 만드는 일입니다. 예를 들어 주문 ID, 요청 key, 이벤트 ID, 소비자 처리 ID를 기록하면 ‘API는 한 번 처리됐는데 이메일만 두 번 갔다’ 같은 사고를 분리해 조사할 수 있습니다.

QA는 브로커가 같은 메시지를 다시 전달하는 상황, consumer가 DB commit 직후 죽는 상황, API 응답 전 worker가 먼저 처리되는 상황을 각각 다룹니다. 테스트 목적은 모든 시스템을 한 번에 정확히 한 번 처리하게 만드는 것이 아니라, 적어도 한 번 전달될 수 있다는 현실에서 각 부수 효과가 중복되어도 안전한지 확인하는 것입니다. 전송 보장 수준과 소비자 중복 제거를 문서에 나누어 적으면 개발자가 ‘큐가 있으니 자동으로 한 번만 실행된다’고 오해할 가능성을 줄일 수 있습니다.

## 감사와 정합성 확인 절차

멱등성 구현이 있어도 장애가 발생하면 운영자는 이미 일어난 일을 복원해야 합니다. 이를 위해 결제·주문·재고처럼 금전 또는 수량에 영향을 주는 작업에는 업무 ID 기준의 대조 절차가 필요합니다. 예를 들어 하루에 한 번 주문 상태, 내부 결제 레코드, provider 조회 결과, 재고 이벤트 수를 비교해 누락·중복·미확정 상태를 찾는 방식입니다. 이 절차는 실시간 중복 방지의 대체물이 아니라, 예상 밖의 장애 경계를 발견하는 안전망입니다.

대조 결과에서 차이가 발견되었다고 곧바로 자동 환불이나 재처리를 실행하는 것은 위험할 수 있습니다. 먼저 상태가 지연된 것인지, 수집 시간이 다른 것인지, 실제 중복 승인인지 분류해야 합니다. 사람이 검토해야 하는 금액·계약 조건이 있다면 자동화가 만들 수 있는 조치와 운영자가 확정해야 하는 조치를 나눕니다. API 설계 단계부터 어떤 식별자와 상태가 있어야 이 대조가 가능한지 생각하면, 사고 뒤 로그를 모아 추측하는 시간을 줄일 수 있습니다.

테스트 환경에서도 작은 대조를 수행할 수 있습니다. 같은 key로 여러 번 호출한 뒤 `payment` 행 수, provider adapter 호출 기록, outbox 이벤트 수를 비교하고 모두 업무 규칙과 맞는지 assert합니다. 실패 시에는 key·요청 순서·상태 전이만 남겨 재현 가능하게 만들고, 고객 이름·카드 관련 정보 같은 민감한 데이터는 출력하지 않습니다. 이 검사는 기능 테스트가 통과했다는 사실과 별도로, 여러 저장소에 흩어진 결과가 같은 이야기를 하는지 확인합니다.

## 테스트 케이스를 유지 가능한 자산으로 만들기

멱등성 시나리오는 API가 늘수록 복사해 붙이기 쉬워 보이지만, 각 endpoint의 부수 효과가 다르기 때문에 단순한 공통 체크리스트만으로는 부족합니다. 먼저 ‘이 명령이 중복되면 무엇이 손해인가’를 적고, 그 손해를 관찰할 수 있는 결과를 선택하세요. 쿠폰 발급이면 발급 수와 사용 가능 상태, 회원 가입이면 계정 수와 환영 메시지 수, 파일 업로드면 객체 수와 메타데이터 상태가 검증 대상이 됩니다. HTTP status와 응답 본문은 그 결과를 향한 단서이지 최종 증거가 아닙니다.

테스트 데이터는 의도를 드러내는 고정 업무 ID를 사용하고, 같은 key·다른 key·다른 본문을 눈에 띄게 구분합니다. 동시 요청 테스트는 실행 순서에 의존하지 않도록 barrier를 두며, 재시도 테스트는 첫 응답만 끊거나 첫 저장만 실패시키는 식으로 실패 지점을 통제합니다. 외부 provider를 mock할 때는 호출 횟수만 세지 말고 같은 provider id를 반환했는지, 실패 후 조회가 가능한지까지 계약으로 표현합니다. 그래야 구현을 리팩터링해도 중요한 업무 규칙이 사라지지 않습니다.

마지막으로 API 변경 검토에 멱등성 질문을 넣습니다. 새 명령 endpoint인가, 클라이언트·gateway·worker 중 누가 재시도하는가, 중복의 비용은 무엇인가, key를 어디에 저장하고 언제 만료하는가, 외부 효과는 어떻게 대조하는가를 설계 문서와 테스트 계획에 함께 적습니다. 이 질문들은 모든 API에 복잡한 저장소를 강요하려는 것이 아니라, 중복이 실제 비용을 만드는 지점에서만 필요한 보호 장치를 선택하게 합니다.

요청 한 번을 예외적인 성공 사례로 보는 대신, 같은 의도가 여러 번 도착해도 설명 가능한 결과가 남는지를 완료 기준으로 삼으세요. 이 기준은 QA가 API의 상태 코드만 확인하는 역할에서 벗어나, 사용자·클라이언트·데이터베이스·외부 서비스가 만나는 실패 경계를 함께 검증하게 합니다. 처음에는 결제나 예약처럼 위험이 큰 명령 하나에 적용하고, 검증 표와 운영 지표가 안정되면 다른 변경 API로 넓히는 방식이 현실적입니다.

## 마무리

멱등성은 사용자가 버튼을 한 번만 누른다는 희망이 아니라, 재시도와 부분 실패가 정상인 네트워크에서 업무 상태를 보호하는 설계입니다. key 저장, 동시성 제어, 외부 부수 효과, 만료 정책을 함께 설계하고 순차·동시·부분 실패 시나리오로 검증하세요. 그러면 timeout 뒤 재시도는 위험한 중복이 아니라 안전하게 회복되는 정상 경로가 됩니다.
