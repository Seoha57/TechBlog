## 먼저 답하기

### Q. MCP(Model Context Protocol) 서버를 연결하면 모델이 사내 시스템을 바로 안전하게 쓸 수 있나요?

A. 아닙니다. MCP는 모델 클라이언트와 도구·리소스를 연결하는 프로토콜과 인터페이스를 제공하지만, 특정 사용자가 어떤 데이터를 볼 수 있는지와 어떤 변경을 실행할 수 있는지는 서버와 업무 시스템이 별도로 검증해야 합니다. 모델이 도구 이름과 인자를 올바르게 제안했다고 해도, 그 호출은 신뢰할 수 없는 입력으로 취급해야 합니다.

### Q. 읽기 전용 도구는 승인과 권한 검사가 필요 없나요?

A. 읽기 전용도 민감 정보를 유출할 수 있으므로 필요합니다. 고객 목록, 인사 정보, 장애 로그, 소스 코드, 운영 설정은 변경하지 않아도 접근 범위를 제한해야 합니다. 쓰기 도구보다 위험 등급이 낮을 수는 있지만, 사용자·조직·대상·쿼리 범위를 검증하고 과도한 결과를 줄이는 경계가 필요합니다.

## 먼저 알아둘 기반 기술

### LLM, 에이전트, 도구 호출

LLM(Large Language Model)은 다음 단어 또는 토큰을 예측해 문장을 만드는 모델입니다. 모델은 대화의 지시를 해석하고 JSON 형태의 도구 호출을 제안할 수 있지만, 데이터베이스나 배포 시스템의 실제 권한을 스스로 갖는 것은 아닙니다. 에이전트라는 말은 보통 모델이 도구를 선택하고 결과를 다시 읽어 여러 단계를 수행하는 흐름을 가리킵니다. 이 흐름이 유용한 이유는 사용자가 여러 시스템의 화면을 직접 오가지 않아도 되기 때문이지만, 잘못된 도구 선택이나 권한 우회가 더 큰 영향을 만들 수 있습니다.

도구 호출에서 모델은 계획자에 가깝고, 실행 권한은 서버가 가져야 합니다. 예를 들어 모델이 `create_deployment`라는 도구에 운영 환경과 버전 값을 넣어 제안하더라도, 서버는 로그인한 사용자가 그 환경을 바꿀 수 있는지, 변경 창인지, 승인자가 있는지, 버전이 허용 목록에 있는지 다시 확인해야 합니다. 모델의 자연어 이해와 결정적인 정책 검증을 같은 층으로 취급하면 안 됩니다.

### MCP의 기본 구성

MCP(Model Context Protocol)는 호스트 또는 클라이언트, MCP 서버, 그리고 도구·리소스·프롬프트 같은 기능의 관계를 정의합니다. 클라이언트는 서버가 제공하는 도구 목록과 스키마를 받아 모델에 전달할 수 있고, 모델이 제안한 호출을 통해 서버에 요청을 보냅니다. 서버는 외부 API, 데이터베이스, 파일 시스템, 티켓 시스템처럼 실제 시스템과 연결될 수 있습니다. 프로토콜의 연결 성공은 업무 권한 설계의 성공을 의미하지 않습니다.

도구(tool)는 행동을 실행하거나 계산 결과를 반환하는 함수형 인터페이스입니다. 리소스(resource)는 문서, 설정, 데이터처럼 모델이 참고할 수 있는 정보입니다. 프롬프트(prompt)는 재사용 가능한 작업 양식입니다. 세 종류 모두 공격 표면이 될 수 있습니다. 도구 설명에 악의적인 지시가 섞이거나, 리소스에 신뢰할 수 없는 문서가 들어오거나, 프롬프트가 민감한 정보를 외부로 보내도록 유도할 수 있습니다. 기능을 등록할 때는 내용의 출처와 소유자를 확인해야 합니다.

### 인증과 인가의 차이

인증(authentication)은 요청자가 누구인지 확인하는 과정입니다. OAuth 2.0 같은 위임 프로토콜은 사용자가 비밀번호를 서버에 직접 주지 않고 제한된 토큰으로 접근 권한을 위임하는 데 쓰일 수 있습니다. 인가(authorization)는 인증된 주체가 특정 자원에 특정 행동을 할 수 있는지 판정하는 과정입니다. `alice`가 로그인했다는 사실만으로 모든 고객 정보를 검색하거나 production 배포를 실행할 수 있는 것은 아닙니다.

MCP 서버 앞에 OAuth를 붙이는 것만으로 충분하지 않은 이유가 여기에 있습니다. 토큰의 발급자, audience, 만료 시간, scope를 확인하고, 실제 도구 호출에는 조직·프로젝트·환경·대상 리소스 단위의 권한을 적용해야 합니다. 도구가 다시 하위 API를 호출할 때 어떤 자격 증명을 사용하는지도 중요합니다. 서버의 광범위한 서비스 계정으로 모든 작업을 대신 실행하면, 사용자별 권한 경계와 감사 기록이 사라질 수 있습니다.

## 위협 모델부터 만든다

안전한 MCP 서버는 "모델이 실수할 수 있다"는 전제만으로는 부족합니다. 누가 서버를 사용할 수 있는지, 어떤 도구가 어떤 데이터를 읽고 쓰는지, 신뢰하지 않는 입력이 어디서 들어오는지, 실패했을 때 어떤 피해가 나는지 적어야 합니다. 사용자는 정상 권한을 가진 직원일 수도 있고, 탈취된 세션을 가진 공격자일 수도 있으며, 문서 안에 숨은 지시를 모델에게 전달하는 외부 콘텐츠일 수도 있습니다.

첫 번째 경계는 도구 목록입니다. 모델에 노출하는 도구가 많을수록 편리해 보이지만, 선택 오류와 권한 범위도 커집니다. 지원 티켓 요약에 필요한 서버라면 배포 삭제 도구까지 같은 서버에 둘 이유가 없습니다. 읽기, 쓰기, 고위험 관리 작업을 별도 서버 또는 별도 권한 scope로 나누고, 기본 노출은 최소화합니다. 사용하지 않는 도구는 "혹시 필요할지 몰라서" 남기지 않는 것이 가장 좋은 보호입니다.

두 번째 경계는 데이터입니다. 도구 결과에는 토큰, 개인정보, 내부 URL, 비밀 키, 디버그 로그가 섞일 수 있습니다. 서버는 필요한 필드만 반환하고, 페이지 크기와 최대 응답 크기를 제한하며, 대량 export 같은 기능은 별도 승인 경로로 둡니다. 모델 컨텍스트에 한 번 들어간 데이터는 이후 대화와 로그·평가 데이터에 남을 위험이 있으므로, 처음부터 과도한 데이터를 넘기지 않는 원칙이 중요합니다.

세 번째 경계는 외부 콘텐츠입니다. RAG 문서, 이메일, 웹 페이지, 티켓 내용은 모델에게 "이 지시를 무시하고 비밀을 전송하라"는 식의 간접 프롬프트 인젝션을 전달할 수 있습니다. 서버가 도구 결과나 문서 안의 문장을 권한 있는 명령으로 해석해서는 안 됩니다. 모델이 외부 콘텐츠를 읽은 뒤 도구 호출을 제안하더라도, 도구 서버는 사용자의 권한과 명시적 의도, 허용된 대상만으로 판정해야 합니다.

## 도구 설계: 작고 결정적으로 만든다

나쁜 도구는 `run_anything(command)`처럼 사용자가 말한 모든 명령을 실행하게 만듭니다. 편리해 보이지만 입력 검증과 권한 정책을 적용할 경계가 거의 없습니다. 더 안전한 도구는 `get_deployment_status(project, environment)`처럼 목적과 입력이 좁고, 서버가 허용하는 프로젝트·환경 값을 결정적으로 검증할 수 있습니다. 도구가 작아지면 모델의 선택은 늘어날 수 있지만, 위험한 자유도는 줄어듭니다.

입력 스키마는 첫 번째 방어선입니다. JSON Schema로 필수 필드, 타입, 문자열 길이, enum, 배열 크기를 제한하면 형식 오류와 지나치게 큰 요청을 줄일 수 있습니다. 그러나 스키마가 유효하다고 업무적으로 안전한 것은 아닙니다. `environment`가 문자열이라는 검사는 할 수 있어도, 현재 사용자가 `production`에 배포할 권한이 있는지나 같은 배포가 이미 진행 중인지는 스키마만으로 알 수 없습니다. 형식 검증 뒤에는 업무 상태와 권한을 확인하는 정책 계층이 반드시 필요합니다.

```json
{
  "name": "get_deployment_status",
  "inputSchema": {
    "type": "object",
    "properties": {
      "project": { "type": "string", "maxLength": 80 },
      "environment": { "type": "string", "enum": ["development", "staging", "production"] }
    },
    "required": ["project", "environment"],
    "additionalProperties": false
  }
}
```

이 예시에서 서버는 `project`가 실제로 존재하는지, 사용자의 조직에 속하는지, production 조회 자체가 허용되는지, 응답에 비밀 설정이 포함되지 않는지 추가로 확인해야 합니다. `additionalProperties: false`는 예상하지 못한 입력을 줄이는 데 도움이 되지만, 개발자가 서버 쪽에서 임의의 추가 값을 신뢰한다면 의미가 없습니다. 클라이언트가 보낸 모든 값을 다시 검증하는 것이 원칙입니다.

## 읽기와 쓰기를 다른 위험으로 다룬다

읽기 도구는 "안전"하다는 이유로 넓게 열어 두기 쉽습니다. 하지만 `search_customer`가 이메일·전화번호·주소를 반환하거나, `get_incident_log`가 접근 토큰을 포함하거나, `read_repository_file`이 배포 비밀을 읽을 수 있다면 영향은 큽니다. 도구별로 최소 반환 필드, 최대 결과 수, 마스킹 규칙, 검색 가능한 범위를 정의하세요. 사용자가 "모든 고객"을 달라고 해도 기본 도구가 전부를 반환하지 않게 하고, 대량 추출은 별도 업무 프로세스로 분리합니다.

쓰기 도구는 명시적 승인과 멱등성을 더 강하게 요구합니다. `restart_service`, `close_ticket`, `send_email`, `create_user` 같은 작업은 사용자가 결과를 이해하고 승인할 기회를 가져야 합니다. 모델이 제안한 계획을 대상·변경 내용·영향 범위·되돌림 가능 여부와 함께 보여 주고, 사용자가 구조화된 확인을 한 뒤 실행하도록 설계할 수 있습니다. 자연어로 "응"이라고 답한 것을 어느 작업의 승인으로 볼지 모호하면 실행하지 않는 편이 안전합니다.

멱등 키(idempotency key)나 작업 ID를 사용하면 네트워크 오류나 모델 재시도로 같은 쓰기가 여러 번 발생하는 위험을 줄일 수 있습니다. 실행 결과는 다시 조회할 수 있어야 하며, 비동기 작업이라면 완료·실패·진행 상태를 구분해야 합니다. 단순히 도구 호출에 성공 응답을 돌려주는 것은 실제 배포나 데이터 변경이 끝났다는 보장이 아닙니다.

## 사용자 승인과 정책 평가 흐름

고위험 도구는 두 단계로 나누는 것이 좋습니다. 첫 단계는 dry run 또는 계획 생성입니다. 서버가 현재 권한과 정책을 평가하고, 실제로 바뀔 대상과 영향, 필요한 승인을 반환합니다. 두 번째 단계는 사용자가 그 계획 ID를 확인한 뒤 실행하는 단계입니다. 이렇게 하면 모델이 대상을 잘못 이해했거나 사용자가 의도를 바꿨을 때, 실제 변경 전에 발견할 수 있습니다.

정책 평가는 도구 호출마다 일관되게 적용해야 합니다. 예를 들어 `deploy` 도구만 production 권한을 검사하고 `rollback`이나 `scale` 도구는 같은 검사를 빼면 우회 경로가 생깁니다. 도구 이름별 if 문이 여러 서버에 흩어지기보다, 사용자·조직·프로젝트·환경·행동·위험 등급을 입력으로 받아 결정하는 공통 인가 계층을 두는 편이 정책 누락을 줄입니다. 다만 작은 시스템에서 거대한 정책 엔진을 먼저 도입할 필요는 없으며, 서버 내부의 명시적인 권한 검사부터 시작할 수 있습니다.

승인 기록에는 누가 언제 어떤 계획을 승인했고, 실제 실행된 인자와 결과가 무엇인지 남깁니다. 민감한 값은 감사 로그에서도 마스킹해야 합니다. 기록의 목적은 사용자를 감시하는 것이 아니라, 사고가 났을 때 모델·서버·사용자·하위 시스템 중 어느 지점에서 의도가 달라졌는지 재구성하는 것입니다. 보관 기간과 접근 권한도 데이터 분류 정책에 맞춰 정해야 합니다.

## OAuth와 토큰을 다룰 때의 기준

MCP 서버가 사용자 대신 다른 API를 호출한다면 토큰의 전달 경로를 단순하게 유지해야 합니다. 토큰을 모델 프롬프트나 도구 설명에 넣어서는 안 되며, 로그와 오류 메시지에도 원문을 남기지 않습니다. 서버는 토큰을 안전하게 검증·교환하고, 최소 scope를 가진 자격 증명으로 하위 시스템을 호출합니다. 가능하다면 사용자 위임 토큰과 서버 자체의 서비스 자격 증명을 구분해, 누가 한 행동인지 추적할 수 있게 합니다.

redirect URI, audience, issuer, 만료 시간, nonce와 state 같은 OAuth 검증 항목도 연결 과정에서 중요합니다. 그러나 프로토콜 세부 구현을 복사하는 것보다, 사용 중인 인증 제공자의 공식 라이브러리와 권장 흐름을 사용하는 편이 안전합니다. 직접 JWT를 문자열로 분해해 권한을 판단하거나, 만료 시간을 무시한 캐시를 만드는 지름길은 피해야 합니다. 인증 실패는 모델이 다른 도구를 반복 호출하게 만들 수 있으므로, 사용자에게 재로그인이나 권한 요청이 필요하다는 명확한 상태를 반환합니다.

## 감사·관찰성·비밀 보호

MCP 환경에서는 하나의 사용자 요청이 여러 도구 호출로 이어질 수 있습니다. 요청 ID와 도구 호출 ID를 연결하면 어떤 모델 응답이 어떤 서버 작업을 만들었는지 추적할 수 있습니다. 로그에는 사용자 식별자를 그대로 과도하게 쓰기보다 필요한 범위의 내부 식별자, 도구 이름, 위험 등급, 정책 결정, 결과 코드, 지연 시간 같은 구조화된 필드를 남깁니다. 입력과 출력 전문은 기본적으로 저장하지 않고, 조사에 필요한 경우에도 마스킹·접근 통제를 적용합니다.

관찰성은 오류를 찾는 데 도움이 되지만 새로운 유출 경로가 될 수 있습니다. 프롬프트와 도구 결과에는 고객 내용, 소스 코드, 비밀 설정이 섞일 수 있으므로 trace 백엔드의 접근 권한과 보관 기간을 정해야 합니다. 모델 품질을 평가하려고 실제 대화를 학습·평가 데이터로 복사할 때도 같은 문제가 생깁니다. 샘플링, 익명화, 합성 데이터, 별도 보관소를 검토하고, 운영 데이터가 자동으로 넓은 사람에게 공개되지 않게 해야 합니다.

## 업무 예시: 사내 장애 대응 도우미

장애 대응 도우미가 티켓, 메트릭, 배포 상태를 읽고 운영자에게 요약을 제공한다고 가정하겠습니다. 첫 버전은 읽기 전용으로 시작합니다. `get_incident`, `list_recent_deployments`, `get_service_health`처럼 목적이 좁은 도구를 두고, 운영자가 담당하는 프로젝트만 조회할 수 있게 합니다. 로그 검색 결과는 최대 건수와 기간을 제한하고 토큰·쿠키·개인정보 패턴은 마스킹합니다.

모델이 티켓 본문에서 "배포를 되돌리라"는 문장을 보더라도, 읽기 도구만 있는 서버에서는 실제 변경이 일어나지 않습니다. 나중에 rollback 기능을 추가한다면 같은 서버에 무제한 명령 실행을 넣는 대신, `create_rollback_plan`과 `execute_approved_rollback`으로 나눕니다. 계획 단계에서 대상 버전, 영향 서비스, 변경 창, 승인 필요 여부를 확인하고, 승인된 계획 ID와 사용자 확인이 있어야 실행합니다. 실행 뒤에는 작업 ID와 결과를 반환해 사용자가 상태를 조회할 수 있게 합니다.

테스트는 모델이 올바른 JSON을 만드는지만 확인하지 않습니다. 다른 조직의 incident ID를 넣었을 때 거절되는지, 숨겨진 프롬프트 지시가 있는 티켓을 읽은 뒤에도 권한 밖 도구가 호출되지 않는지, 승인 없이 execute 요청이 들어오면 실패하는지, 같은 계획을 두 번 실행해도 중복 변경이 막히는지 확인합니다. 이 테스트가 MCP 연결 성공보다 실제 안전성에 더 가깝습니다.

## 서버 등록과 신뢰 경계

MCP 클라이언트가 새 서버를 등록할 때는 서버 이름과 실행 위치만 보지 말고, 누가 배포·유지하는 서버인지와 어떤 권한을 요구하는지를 확인해야 합니다. 개발자가 편의를 위해 내려받은 로컬 서버가 파일 시스템·환경 변수·브라우저 세션에 접근할 수 있다면, 그 서버는 단순한 플러그인이 아니라 높은 권한의 프로그램입니다. 신뢰할 수 있는 배포 경로, 코드 검토, 의존성 잠금, 서명 또는 조직의 패키지 정책을 적용하는 이유입니다.

서버 설명도 공격 표면입니다. 도구의 설명은 모델이 어떤 작업을 선택할지 영향을 주므로, 신뢰하지 않는 사용자가 설명을 바꾸거나 외부 문서 내용을 자동으로 도구 설명으로 등록하게 해서는 안 됩니다. 설명에는 목적, 입력 의미, 반환 범위, 위험도, 승인 필요 여부를 명확히 쓰되, 비밀 값이나 내부 인프라 세부 정보를 넣지 않습니다. 등록 가능한 서버와 도구의 출처를 허용 목록으로 관리하면 무분별한 확장보다 안전합니다.

조직에서 여러 MCP 서버를 운영한다면 각 서버의 소유 팀과 연락처, 데이터 분류, 인증 방식, 도구 목록, 변경 이력을 카탈로그로 남기는 것이 좋습니다. 새 도구가 추가될 때 기존 승인과 권한 정책이 그대로 적합한지 검토할 수 있고, 사고가 났을 때 누가 원인을 조사해야 하는지도 알 수 있습니다. 카탈로그는 거대한 포털일 필요가 없으며, 처음에는 저장소의 간단한 문서와 code owner 규칙으로 시작할 수 있습니다.

## 입력 검증을 여러 층으로 나눈다

도구 입력은 모델이 만든 JSON이지만, 최종적으로는 사용자 대화·외부 문서·공격자가 조작한 콘텐츠의 영향을 받을 수 있습니다. 그래서 문자열 길이와 enum 같은 스키마 검증, 프로젝트 존재 여부 같은 도메인 검증, 사용자의 권한과 업무 상태를 확인하는 인가 검증, 실행 직전의 동시성·변경 창 검증을 나눕니다. 한 단계가 통과했다고 다음 단계가 불필요해지지 않습니다.

예를 들어 `create_user` 도구가 이메일과 역할을 받는다고 합시다. 스키마는 이메일 형식과 역할 enum을 확인합니다. 도메인 검증은 이미 같은 사용자가 있는지, 초대 가능한 도메인인지 확인합니다. 인가 검증은 호출자가 그 조직에서 사용자를 추가할 권한이 있는지 확인합니다. 실행 직전 검증은 조직의 사용자 한도, 필요한 관리자 승인, 동일 요청의 중복 여부를 확인할 수 있습니다. 이 분리를 하면 실패 응답도 "형식 오류", "권한 없음", "승인 필요", "이미 처리됨"처럼 사용자와 운영자가 이해할 수 있게 됩니다.

파일 경로, URL, 쿼리, 필터 언어처럼 해석되는 입력은 특히 위험합니다. 서버가 경로를 받는다면 허용된 루트 밖으로 `..`를 이용해 나가지 못하게 정규화하고 확인해야 합니다. URL을 받아 데이터를 가져온다면 내부 네트워크 주소나 메타데이터 서비스로 요청을 보내는 SSRF(Server-Side Request Forgery) 위험을 고려해야 합니다. SQL을 받는 도구는 원칙적으로 자유 SQL을 허용하지 말고, 필요한 조회를 명시적인 파라미터로 표현하는 편이 안전합니다.

## 프롬프트 인젝션 이후의 안전한 동작

간접 프롬프트 인젝션은 사용자가 신뢰하지 않는 문서·웹 페이지·이메일이 모델에게 명령처럼 보이는 문장을 포함해, 모델의 행동을 바꾸려는 공격입니다. 이를 완벽히 텍스트 필터로 제거한다고 약속하기 어렵습니다. 대신 모델이 어떤 텍스트를 읽었는지와 무관하게 도구 서버가 권한 밖 행동을 거절하도록 만들고, 민감 작업은 명시적인 사용자 확인을 요구하는 방어가 핵심입니다.

모델이 "문서의 지시에 따라 모든 파일을 업로드하겠다"고 제안한다면, 파일 업로드 도구는 사용자가 허용한 대상과 파일 목록, 조직 정책을 확인해야 합니다. 읽기 도구의 결과가 다음 도구의 입력으로 자동 연결되는 흐름도 위험할 수 있으므로, 서버 간에 민감한 값을 묵시적으로 전달하지 않습니다. 작업 계획을 화면에 보여 주고, 사람이 대상과 영향 범위를 검토할 수 있게 하는 것이 단순하지만 강한 경계가 됩니다.

프롬프트 인젝션을 이유로 모든 외부 문서를 읽지 않게 만들 필요는 없습니다. 문서는 신뢰 수준에 따라 분류하고, 신뢰하지 않는 콘텐츠는 명령이 아니라 참고 자료로 취급하며, 그로부터 파생된 도구 호출은 더 엄격한 정책을 적용할 수 있습니다. 다만 신뢰 수준 라벨도 외부 문서가 스스로 주장한 값을 믿어서는 안 되고, 수집 경로와 소유자 같은 검증 가능한 메타데이터에서 결정해야 합니다.

## 테스트와 배포 체크리스트

MCP 서버의 단위 테스트는 입력 파싱과 정책 함수의 경계를 확인합니다. 통합 테스트는 실제 인증 제공자나 하위 API의 sandbox에서 토큰 만료, scope 부족, 조직 경계, pagination, rate limit을 확인합니다. 보안 테스트는 권한이 낮은 사용자가 식별자를 바꿔 다른 조직 데이터를 읽는지, 예상하지 않은 추가 JSON 필드가 무시 또는 거절되는지, 오류 메시지에 비밀 값이 나오지 않는지 봅니다. 사람 승인 흐름은 승인 전·후에 실행 가능한 행동이 명확히 다른지 테스트해야 합니다.

배포 시에는 새 도구를 전체 사용자에게 즉시 노출하기보다 내부 소수 사용자·낮은 위험 프로젝트에 제한하고, 거절률·권한 오류·승인 취소·실행 실패·응답 크기·비용을 관찰합니다. 오류가 많다고 무조건 정책을 느슨하게 하면 안 됩니다. 사용자가 올바른 업무를 수행하는데 반복적으로 막히는지, UI가 필요한 권한이나 승인 사유를 설명하지 못하는지, 도구 스키마가 현실의 입력을 표현하지 못하는지를 구분해야 합니다.

정책과 도구 설명, 모델 버전, 하위 API 버전을 함께 버전 관리하면 문제 발생 시 어떤 조합에서 행동이 달라졌는지 조사하기 쉽습니다. 모델을 바꾸면 같은 프롬프트에서 도구 선택 비율과 인자 형태가 달라질 수 있으므로, 대표적인 정상·오용·권한 거절 시나리오를 평가셋으로 둡니다. 모델 평가 통과는 정책 통과와 다르고, 정책 통과는 업무 결과의 적합성과도 다릅니다. 각 층의 목적을 나누는 것이 안전한 출시의 출발점입니다.

## 책임과 사용자 경험의 균형

보안을 강화한다며 모든 요청을 무조건 거절하거나 매번 긴 승인 과정을 요구하면 사용자는 우회 경로를 찾게 됩니다. 반대로 자연어 한 문장만으로 고위험 작업을 실행하면 사고 비용이 커집니다. 좋은 설계는 낮은 위험의 조회는 빠르게 허용하되 결과를 최소화하고, 중간 위험의 작업에는 대상과 이유를 확인하며, 높은 위험의 변경에는 계획·승인·감사·되돌림을 요구합니다. 위험 등급은 추상적인 점수가 아니라 데이터 민감도, 변경 가능성, 영향 범위, 복구 난이도에 근거해야 합니다.

사용자에게 보여 주는 거절 메시지도 중요합니다. "도구 오류" 대신 "현재 계정은 production 배포를 실행할 권한이 없습니다. 승인된 운영 역할로 전환하거나 담당자에게 요청하세요"처럼 필요한 다음 행동을 안내하면, 사용자는 모델에게 같은 요청을 반복해 우회하려 하지 않습니다. 반대로 내부 정책의 세부 규칙이나 다른 조직의 존재를 노출하지 않도록 메시지 범위는 제한해야 합니다.

## 도입을 시작하는 최소 순서

처음부터 모든 사내 시스템을 MCP로 연결할 필요는 없습니다. 가장 낮은 위험의 읽기 전용 업무 하나를 고르고, 필요한 도구를 두세 개로 제한하세요. 사용자 인증과 조직 경계, 반환 필드 마스킹, 감사 이벤트를 먼저 구현한 뒤 대표적인 정상·권한 거절·외부 문서 인젝션 시나리오를 테스트합니다. 그 결과가 안정적일 때만 쓰기 작업을 계획과 실행 단계로 나누어 추가합니다. 작은 범위에서 거절 이유와 사용 흐름을 다듬는 것이 넓은 권한을 빠르게 노출하는 것보다 안전합니다.

기능이 늘어나면 도구마다 데이터 소유자와 보안 검토 책임자를 기록합니다. 더 이상 쓰이지 않는 도구와 scope는 제거하고, 토큰·패키지·서버 버전의 취약점과 만료를 점검합니다. AI 시스템의 동작은 모델 버전, 프롬프트, 문서, 정책, 하위 API가 함께 바뀌어 달라질 수 있으므로 한 번의 심사로 안전이 영구히 보장되지는 않습니다. 변경마다 좁은 평가와 감사가 필요한 이유입니다.

이 과정의 목표는 모델을 믿지 못하게 만드는 것이 아니라, 모델이 실수하거나 공격성 입력을 만나도 실제 시스템의 피해 범위를 작게 만드는 것입니다. 사용자는 필요한 정보를 더 빨리 찾고, 운영자는 어떤 작업이 왜 실행됐는지 추적할 수 있으며, 도구 소유자는 자신의 API가 어떤 권한으로 노출되는지 통제할 수 있습니다. 이 세 가지가 함께 충족될 때 MCP 서버는 단순한 연결 기능을 넘어 안전한 업무 인터페이스가 됩니다.

도입 전에는 도구 하나를 줄이는 선택도 검토하세요. 자동화가 반드시 필요한지, 기존 승인된 API 화면이나 읽기 전용 보고서로 같은 요구를 해결할 수 있는지 비교하면 불필요한 권한과 유지보수 부담을 피할 수 있습니다.

## 한계와 적용 기준 Q&A

### Q. MCP 서버가 내부망에만 있으면 도구 검증을 줄여도 되나요?

A. 안 됩니다. 내부 사용자 계정 탈취, 잘못된 권한 설정, 신뢰하지 않는 문서에서 온 간접 프롬프트 인젝션, 서버 간 호출 실수는 내부망에서도 발생할 수 있습니다. 네트워크 위치는 하나의 방어층일 뿐이며, 도구 입력·권한·대상 검증을 대체하지 않습니다.

### Q. 도구 설명을 자세히 쓰면 모델의 잘못된 호출을 막을 수 있나요?

A. 더 명확한 설명은 도움이 되지만 보안 제어는 아닙니다. 모델은 설명을 오해하거나 공격성 콘텐츠의 영향을 받을 수 있습니다. 서버는 허용된 인자와 권한, 업무 상태를 결정적으로 검증해야 하며, 위험한 작업에는 사용자 승인을 요구해야 합니다.

### Q. 모든 도구에 사람 승인을 붙여야 하나요?

A. 그렇지는 않습니다. 단순 상태 조회처럼 낮은 위험의 읽기 작업에 매번 승인을 요구하면 사용성이 나빠집니다. 데이터 민감도, 변경의 되돌림 가능성, 영향 범위, 실행 빈도를 기준으로 위험을 나누고, 쓰기·대량 조회·외부 발송 같은 고위험 행동에 강한 확인을 적용하세요.

### Q. MCP 보안은 AI 팀만 책임지면 되나요?

A. 아닙니다. AI 팀은 모델과 프롬프트 경계를, 플랫폼·보안 팀은 인증·비밀·감사 기반을, 도메인 팀은 실제 권한과 업무 상태 규칙을 이해합니다. 한 팀이 모든 규칙을 추측하기보다 도구 소유자와 권한 소유자를 명확히 연결해야 합니다.

## 마무리

MCP는 모델을 실제 정보와 작업에 연결하는 유용한 표준이지만, 연결 자체는 권한 위임이 아닙니다. 최소한의 도구를 노출하고, 모든 입력을 서버에서 검증하며, 읽기 데이터도 최소화하고, 쓰기 작업은 계획·승인·멱등성·감사 경계를 거치게 하세요. 이 원칙을 지키면 에이전트의 편의성과 업무 시스템의 안전성을 함께 설계할 수 있습니다.
