## 먼저 답하기

**Q. 모든 입력값을 조합해 테스트해야 품질을 보장할 수 있나요?**
아닙니다. 값이 늘어날수록 가능한 경우의 수는 곱셈으로 증가하므로, 모든 조합을 실행하는 방식은 대부분의 웹 서비스와 업무 시스템에서 현실적인 계획이 되기 어렵습니다. 중요한 것은 적은 수를 무작정 고르는 일이 아니라, 결함을 잘 드러낼 조합을 근거 있게 고르고 빠진 위험을 따로 보완하는 일입니다.

**Q. Pairwise는 두 값만 테스트한다는 뜻인가요?**
아닙니다. Pairwise는 각 입력 조건의 값 쌍이 적어도 한 번은 함께 나타나도록 테스트 묶음을 만드는 방법입니다. 한 화면에 다섯 개의 선택 항목이 있더라도, 매 실행마다 두 항목만 입력한다는 뜻이 아닙니다. 각 테스트는 실제 업무처럼 여러 값을 한꺼번에 포함하고, 전체 묶음이 가능한 모든 값 쌍을 덮도록 설계합니다.

**Q. 그러면 Pairwise만 쓰면 충분한가요?**
충분하지 않습니다. 결함이 세 조건 이상이 맞물릴 때만 나타나거나, 금액·권한·개인정보처럼 실패 비용이 큰 경로라면 별도의 고위험 조합과 경계값 테스트가 필요합니다. Pairwise는 전체 테스트 전략을 대신하는 만능 도구가 아니라, 조합 공간을 정리하는 출발점입니다.

## 왜 조합 테스트가 필요한가

상품 주문 화면을 생각해 보겠습니다. 사용자는 회원 등급, 배송 지역, 결제 수단, 쿠폰 종류, 배송 옵션을 선택합니다. 각각의 값이 네 개, 세 개, 다섯 개, 여섯 개, 세 개라면 가능한 조합은 1,080개입니다. 여기에 로그인 방식, 앱 버전, 브라우저, 재고 상태까지 더하면 숫자는 금세 수만 개가 됩니다. 모든 경우를 사람이 직접 작성하고 매 배포마다 반복 실행하는 계획은 오래 유지되지 않습니다.

처음에는 "대표 케이스 몇 개"로 줄이기 쉽습니다. 하지만 대표라는 말에는 선택 근거가 빠져 있는 경우가 많습니다. 개발자는 정상 회원과 신용카드만 확인하고, 기획자는 쿠폰과 새벽 배송을 강조하고, 운영 담당자는 제주 지역과 재시도 결제를 걱정합니다. 각자의 중요한 경우가 달라서 테스트 목록은 길어지는데도 빈틈이 남습니다. 조합 테스트는 이 문제를 수학적으로 완전히 해결한다기보다, 무엇을 덮었고 무엇을 의도적으로 제외했는지를 팀이 설명할 수 있게 만듭니다.

많은 소프트웨어 결함은 한 기능의 단일 값보다 두 설정이 만나는 지점에서 발생합니다. 예를 들어 모바일 사파리와 특정 결제 창, 비회원 주문과 해외 배송, 읽기 전용 권한과 일괄 다운로드처럼 두 조건의 상호작용에서 조건문·변환 규칙·기본값이 어긋날 수 있습니다. 미국 국립표준기술연구소(NIST)의 조합 테스트 연구도 이러한 상호작용을 체계적으로 다루기 위한 방법과 도구를 소개합니다. 다만 "대부분의 결함이 두 조건에서 난다"는 일반 문장을 우리 서비스의 측정 결과처럼 말하면 안 됩니다. 실제 서비스의 위험은 도메인, 설계, 변경 이력으로 판단해야 합니다.

## 먼저 알아둘 기반 기술

### 테스트 조건, 값, 조합

**테스트 조건**은 결과에 영향을 줄 수 있어 구분해 보는 축입니다. 회원 등급, 운영체제, 언어, 결제 수단이 조건의 예입니다. **값**은 그 조건이 가질 수 있는 구체적인 선택지입니다. 회원 등급의 값은 일반·우수·사업자일 수 있고, 결제 수단의 값은 카드·계좌이체·간편결제일 수 있습니다. **조합**은 여러 조건에서 하나씩 고른 값들의 묶음입니다.

조건을 너무 크게 잡으면 필요한 차이가 묻힙니다. 예를 들어 "브라우저"라는 하나의 값 안에 렌더링 엔진, 쿠키 정책, 팝업 차단, 모바일 화면 크기가 섞여 있을 수 있습니다. 반대로 조건을 지나치게 작게 쪼개면 표가 읽기 어려워지고 관리 비용이 커집니다. 사용자에게 보이는 동작이나 시스템의 분기 기준이 달라지는 경계를 중심으로 조건을 정하는 편이 좋습니다.

### 동등 분할과 경계값 분석

**동등 분할(Equivalence Partitioning)**은 같은 방식으로 처리될 것으로 기대하는 입력들을 한 그룹으로 묶고 대표값을 고르는 기법입니다. 나이가 19세 이상이면 성인 요금이라는 규칙이 있다면 20, 35, 60을 모두 먼저 넣기보다 19 이상이라는 그룹의 대표값을 선택할 수 있습니다. **경계값 분석(Boundary Value Analysis)**은 오류가 조건의 경계에서 자주 생길 수 있다는 가정 아래 18, 19, 20처럼 경계의 안팎을 확인하는 기법입니다.

Pairwise는 이 기법들과 경쟁하지 않습니다. 먼저 각 조건에서 의미 있는 동등 분할과 경계값을 정한 다음, 그렇게 뽑힌 값들을 조합하는 데 Pairwise를 쓰는 순서가 자연스럽습니다. 0·1·최대값을 구분하지 않은 채 "수량"을 단지 정상과 비정상으로만 놓으면, 잘 만든 조합표도 경계 결함을 가릴 수 있습니다.

### 커버리지와 오라클

**커버리지(coverage)**는 무엇을 얼마나 확인했는지 나타내는 범위입니다. Pairwise 커버리지는 선택한 조건들에 대해 모든 값 쌍이 적어도 한 번 등장하는지를 말합니다. 이것은 코드 줄 실행률이나 요구사항 커버리지와 같은 말이 아닙니다. 서로 다른 지표이므로 하나가 높다고 다른 하나가 자동으로 높아지지 않습니다.

**테스트 오라클(test oracle)**은 결과가 맞는지 판단하는 기준입니다. 화면이 오류 없이 열렸다는 사실만으로 결제가 올바르게 처리됐다고 결론 내릴 수 없습니다. 쿠폰 할인 금액, 주문 상태, 재고 차감, 감사 로그처럼 각 조합에서 확인할 결과를 정해야 합니다. 조합 생성기가 테스트 데이터를 만들어 주더라도 오라클은 팀이 제품 규칙에서 찾아 작성해야 합니다.

## Pairwise는 어떻게 동작하는가

Pairwise는 보통 두 단계로 이해하면 쉽습니다. 첫째, 조건과 값 목록에서 아직 등장하지 않은 값 쌍을 찾습니다. 둘째, 한 테스트 행에 여러 값을 배치하면서 가능한 한 많은 미등장 쌍을 동시에 덮도록 행을 추가합니다. 모든 쌍이 한 번 이상 들어가면 멈춥니다. 같은 목표를 만족하는 표는 여러 개일 수 있으므로, 도구가 내놓은 행 순서가 유일한 정답은 아닙니다.

간단한 주문 예시를 표로 적어 보겠습니다. 여기서는 설명을 위해 회원 유형, 결제, 배송 세 조건만 사용합니다.

| 조건 | 값 |
| --- | --- |
| 회원 유형 | 회원, 비회원, 사업자 |
| 결제 | 카드, 계좌이체, 간편결제 |
| 배송 | 일반, 새벽 |

전수 조합은 3 × 3 × 2로 18개입니다. Pairwise 표는 모든 조건 쌍의 값 조합을 포함하도록 더 적은 행으로 구성할 수 있습니다. 그러나 "몇 행이면 된다"는 숫자를 문서의 성공 기준으로 삼아서는 안 됩니다. 새벽 배송이 제주 지역에서 불가능하다거나 사업자 회원은 특정 간편결제를 쓰지 않는다는 업무 제약이 있으면 가능한 조합 자체가 달라지기 때문입니다.

| 번호 | 회원 유형 | 결제 | 배송 | 확인 초점 |
| --- | --- | --- | --- | --- |
| 1 | 회원 | 카드 | 일반 | 일반 회원의 기본 주문 |
| 2 | 회원 | 계좌이체 | 새벽 | 결제·배송 상호작용 |
| 3 | 비회원 | 간편결제 | 일반 | 비회원 주문과 외부 결제 |
| 4 | 비회원 | 카드 | 새벽 | 연락처·약관·배송 분기 |
| 5 | 사업자 | 계좌이체 | 일반 | 세금계산서 및 계좌 결제 |
| 6 | 사업자 | 간편결제 | 새벽 | 허용 여부를 제약으로 확인 |

위 표는 학습용 예시일 뿐, 특정 도메인의 완전한 Pairwise 산출물이 아닙니다. 실제로는 생성 도구가 누락 쌍을 계산해야 사람의 실수를 줄일 수 있습니다. 중요한 점은 각 행을 읽을 때 "이 행이 어떤 두 값의 관계를 처음 덮는가"와 "이 행에서 무엇을 검증하는가"를 함께 적는 것입니다. 단순히 조합 번호만 남기면 실패했을 때 원인을 좁히기 어렵습니다.

## 조건을 고르는 일이 도구 선택보다 먼저다

조합 생성 도구에 아무 열이나 넣으면 그럴듯한 표는 만들어집니다. 하지만 품질은 도구보다 모델의 품질에 좌우됩니다. 다음 질문으로 조건 후보를 수집해 볼 수 있습니다.

- 업무 규칙이 갈라지는 입력은 무엇인가?
- API(Application Programming Interface, 프로그램끼리 요청과 응답을 주고받는 접점)의 요청 필드 중 결과를 바꾸는 것은 무엇인가?
- 권한, 테넌트, 국가, 통화, 시간대처럼 데이터 해석을 바꾸는 환경은 무엇인가?
- 최근 변경된 코드가 참조하는 플래그와 기본값은 무엇인가?
- 과거 장애나 고객 문의에서 함께 등장한 조건은 무엇인가?

조건 후보를 모두 채택할 필요는 없습니다. 예를 들어 화면의 글꼴 크기가 주문 금액 계산에 영향을 주지 않는다면 같은 조합 모델에 넣지 않는 편이 낫습니다. 반면 화면과 서버 양쪽에서 동작이 달라지는 언어 설정은 문자열 길이, 날짜 형식, 세금 표시까지 영향을 줄 수 있어 독립 조건으로 볼 가치가 있습니다. 어떤 조건을 넣고 뺐는지와 이유를 테스트 설계 문서에 남기면 다음 변경 때 재검토하기 쉽습니다.

값은 대표성보다 분기성을 먼저 봅니다. 카드 결제라는 하나의 값 안에도 일반 승인, 본인 인증, 승인 거절, 시간 초과, 중복 콜백이 숨어 있습니다. 이들이 시스템에서 다른 처리 경로를 탄다면 "카드" 한 값으로 합치지 말고 별도 조건 또는 별도 시나리오로 분리해야 합니다. 반대로 구현상과 업무상 모두 같은 길을 통과하는 값은 동등 분할로 묶어야 표가 불필요하게 커지지 않습니다.

## 불가능한 조합은 제약 조건으로 명시한다

**제약 조건(constraint)**은 현실에서 함께 올 수 없거나, 의도적으로 막아야 하는 값의 관계입니다. 예를 들어 `배송=새벽`과 `지역=도서산간`이 함께 선택될 수 없고, `회원유형=비회원`에게 사업자 전용 세금계산서 옵션이 보이면 안 된다고 합시다. 생성기에게 이 사실을 알려 주지 않으면 실행할 수 없는 행이 생기거나, 반대로 "불가능해야 한다"는 검증이 사라질 수 있습니다.

제약은 두 종류로 나누어 관리하면 혼동이 줄어듭니다. 첫째, 사용자 인터페이스에서 애초에 선택할 수 없는 조합입니다. 이것은 조합표에서 제외하는 것이 맞을 수 있습니다. 둘째, 요청을 조작하거나 오래된 앱이 보낸 경우 서버가 거절해야 하는 조합입니다. 이 경우는 정상 조합표에서 제외하더라도 별도의 음수 테스트로 남겨야 합니다. UI가 막는다는 이유만으로 API 검증을 생략하면 다른 클라이언트 경로가 남습니다.

예를 들어 다음과 같은 규칙을 문서와 코드에 같은 의미로 남길 수 있습니다. 문법은 사용하는 생성기에 따라 달라지므로, 아래 예시는 제약 자체를 설명하기 위한 의사 코드입니다.

```text
IF 배송 = 새벽 THEN 지역 != 도서산간
IF 회원유형 = 비회원 THEN 세금계산서 = 미신청
IF 통화 = KRW THEN 해외카드 = 사용안함
```

제약이 많아졌다는 것은 단순히 도구 설정이 길어졌다는 뜻이 아닙니다. 제품 규칙이 복잡해졌거나, 서로 다른 팀이 규칙을 다르게 이해하고 있을 가능성을 보여 주는 신호입니다. 제약을 추가할 때는 기획서, 서버 검증, 화면 비활성화, 오류 메시지가 같은 규칙을 말하는지도 함께 확인해야 합니다.

## 고위험 조합은 Pairwise 표 밖에서 더 깊게 다룬다

Pairwise는 모든 두 값 쌍을 덮지만, 세 값 이상의 상호작용이나 상태 전이를 보장하지 않습니다. 예를 들어 "만료 직전 쿠폰 + 포인트 전액 사용 + 부분 취소"는 금액 계산과 환불 정책 때문에 세 조건을 함께 봐야 할 수 있습니다. "관리자 권한 + 다른 테넌트 식별자 + CSV(Comma-Separated Values, 쉼표로 값을 구분하는 텍스트 형식) 내보내기"는 정보 노출 위험 때문에 정상 행 하나로 만족했다고 보기 어렵습니다.

그래서 실무에서는 Pairwise 표 뒤에 위험 기반 보완 목록을 둡니다. **위험 기반 테스트(Risk-Based Testing)**는 실패 가능성과 실패 영향이 큰 부분에 더 많은 테스트 노력을 배분하는 접근입니다. 법적·금전적·보안적 영향, 변경량, 복잡도, 외부 연동, 롤백 난이도를 기준으로 우선순위를 매길 수 있습니다. 점수는 절대적인 과학 공식이 아니라 팀의 대화를 구조화하는 도구라는 점을 분명히 해야 합니다.

| 위험 신호 | Pairwise 이후 추가할 확인 |
| --- | --- |
| 금액 계산과 환불 | 경계 금액, 복수 할인, 부분 취소, 재시도 |
| 접근 제어 | 권한 없음, 다른 조직 식별자, 직접 API 호출 |
| 외부 결제·배송 연동 | 지연, 중복 콜백, 순서 역전, 일시 실패 |
| 날짜와 시간대 | 자정, 월말, 일광 절약 시간 변경 지역, 예약 실행 |
| 데이터 이전 | 이전 버전 데이터, 누락 필드, 되돌리기 |

위험 조합은 일반 Pairwise 행에 억지로 끼워 넣기보다, 왜 세 개 이상을 함께 확인하는지 제목과 기대 결과를 분명히 한 별도 시나리오로 관리하는 편이 좋습니다. 그러면 실행자가 "표에 이미 있으니 됐다"고 오해하지 않고, 제품 책임자도 추가 비용의 이유를 이해할 수 있습니다.

## 업무 예시: 할인 쿠폰 API 테스트를 설계해 보기

온라인 쇼핑몰의 할인 계산 API를 가정해 보겠습니다. 이 API는 장바구니 금액, 회원 등급, 쿠폰, 포인트 사용, 배송비 정책을 받아 최종 결제 금액을 반환합니다. 첫 번째 실수는 모든 필드를 그대로 조건으로 만드는 것입니다. 주문 번호나 고객 표시 이름처럼 결과에 영향을 주지 않는 필드는 조합 축이 아닙니다. 반대로 금액 구간, 회원 정책, 쿠폰 상태, 포인트 잔액 구간, 배송비 면제 조건은 계산 분기를 바꿀 수 있습니다.

먼저 금액은 `최소 미만`, `최소와 같음`, `최소 초과`, `무료배송 경계`, `상한 초과`처럼 경계 중심의 값으로 분할합니다. 쿠폰은 `없음`, `정상`, `만료`, `최소금액 미달`, `중복 불가`로 나눕니다. 포인트는 `미사용`, `일부`, `전액`, `잔액 초과 요청`으로 나눕니다. 그런 다음 정상 처리 가능한 값으로 Pairwise 표를 만들고, 만료 쿠폰이나 잔액 초과처럼 거절을 기대하는 값은 오류 응답을 확인하는 음수 테스트 묶음으로 분리합니다.

테스트의 오라클은 "HTTP 200이 왔다"가 아닙니다. **HTTP(Hypertext Transfer Protocol, 웹에서 요청과 응답을 전달하는 규약)** 상태 코드, 최종 금액, 할인 항목별 금액, 반올림 규칙, 발급된 주문 초안의 저장 여부, 같은 요청을 다시 보냈을 때의 결과를 함께 확인해야 합니다. 특히 포인트와 쿠폰을 적용하는 순서는 도메인 정책이므로 테스트 코드의 계산식을 임의로 만들기보다, 합의된 정책 문서와 예시 표를 기준으로 기대값을 고정하는 편이 안전합니다.

다음은 실행 가능한 입력 조합을 데이터로 표현하는 간단한 예입니다. 이는 Pairwise 생성 자체가 아니라, 생성된 행을 자동화 테스트가 읽기 좋은 형태로 전달하는 방식입니다.

```json
{
  "cartAmount": 30000,
  "memberGrade": "gold",
  "coupon": "WELCOME_10",
  "pointUse": 5000,
  "shippingPolicy": "free-over-30000"
}
```

자동화는 이 요청을 보내고 응답 본문에 있는 할인 내역과 최종 금액을 확인할 수 있습니다. 하지만 자동화가 있다고 해서 탐색적 테스트가 불필요해지는 것은 아닙니다. 사람이 화면에서 쿠폰 선택을 바꾸고, 네트워크를 늦추고, 이미 다른 탭에서 주문을 진행한 상태를 관찰하면 조합표에 없던 상태 문제를 발견할 수 있습니다. 조합 테스트는 반복 가능한 회귀 테스트의 뼈대를 만들고, 탐색은 그 뼈대 밖의 가설을 넓히는 역할을 합니다.

## 생성 도구를 도입할 때의 기준

조합 생성기는 조건·값·제약을 입력받아 테스트 행을 만드는 도구입니다. 도입 전에 먼저 확인할 것은 도구가 아니라 산출물의 추적성입니다. 생성된 각 행이 어떤 버전의 모델에서 나왔는지, 제약이 왜 존재하는지, 생성 이후 사람이 추가한 고위험 케이스가 무엇인지 남길 수 있어야 합니다. 화면에서 한 번 생성하고 복사한 표만 남기면 다음 릴리스에서 모델이 바뀌어도 차이를 알기 어렵습니다.

오픈 소스 또는 상용 도구를 고를 때는 다음을 살펴볼 수 있습니다. 현재 사용하는 테스트 프레임워크에서 데이터를 읽기 쉬운 형식으로 내보낼 수 있는지, 금지 조합과 반드시 포함할 조합을 표현할 수 있는지, 생성 결과를 재현할 수 있는지, 팀이 모델 파일을 코드 리뷰할 수 있는지입니다. 도구 이름이 유명하다는 사실보다 모델과 결과를 팀이 이해할 수 있는지가 더 중요합니다.

생성기를 CI(Continuous Integration, 변경을 자주 합쳐 자동 검증하는 개발 방식)에 연결할 때는 모든 새 조합을 매번 실제 브라우저에서 실행할지 결정해야 합니다. 빠른 API 수준 검증에는 넓은 조합을 적용하고, 시간이 오래 걸리는 브라우저 시나리오는 고위험 대표 집합으로 제한하는 식의 계층화가 현실적일 수 있습니다. 이때 제한했다는 사실을 숨기지 말고, 어느 계층이 어떤 커버리지를 제공하는지 문서에 써야 합니다.

## 실패를 분석하는 법

조합 테스트 한 행이 실패했다고 해서 두 값의 관계가 원인이라는 뜻은 아닙니다. 그 행에는 여러 조건이 동시에 들어 있으므로 환경, 데이터 상태, 순서, 비동기 처리도 영향을 줄 수 있습니다. 우선 실패한 입력을 재현 가능한 요청과 데이터 상태로 보존하고, 같은 행을 단독 실행했을 때도 실패하는지 확인합니다. 그다음 한 번에 하나의 조건만 바꿔 결과가 달라지는 지점을 좁힙니다.

예를 들어 `사업자 + 계좌이체 + 일반배송 + 신규 앱`에서 오류가 났다면, 사업자와 계좌이체의 상호작용이라고 바로 단정하지 않습니다. 신규 앱이 누락한 헤더인지, 테스트 계정의 사업자 인증 상태인지, 배송비 계산 캐시인지 확인해야 합니다. 실패 기록에는 조합 번호만이 아니라 요청 본문, API 버전, 테스트 데이터 식별자, 기대 결과, 실제 결과, 실행 시각을 남깁니다. 민감한 정보는 마스킹하고, 재현에 필요한 최소 정보만 공유해야 합니다.

결함이 확인되면 Pairwise 모델에 무조건 새 조건을 하나 더 넣지 말고 원인을 분류합니다. 기존 값의 정의가 너무 넓었는지, 빠진 제약이 있었는지, 세 조건 이상의 위험 시나리오였는지, 단순한 데이터 준비 오류였는지에 따라 후속 조치가 달라집니다. 모델이 커질수록 실행 수가 늘어나므로, 학습을 반영하되 의미 없는 축을 누적하지 않는 절제가 필요합니다.

## 리뷰 가능한 조합 모델을 만드는 법

테스트 케이스 표는 보통 테스트 담당자만 보는 문서로 취급되지만, 조합 모델은 요구사항을 압축한 설계 산출물에 가깝습니다. 따라서 개발자·기획자·운영 담당자가 읽을 수 있어야 합니다. 가장 간단한 방법은 각 조건 옆에 "왜 이 축이 결과를 바꾸는가"와 각 값 옆에 "어떤 분기를 대표하는가"를 한 줄씩 쓰는 것입니다. `결제수단=카드`처럼 이름만 있는 표보다 `카드-본인인증 성공`, `카드-승인 거절`, `카드-콜백 지연`처럼 처리 흐름을 드러내는 값이 리뷰에 더 도움이 됩니다.

다음은 리뷰할 때 사용할 수 있는 질문입니다.

- 이 조건은 실제 요구사항·API 계약·데이터 모델 중 어디에서 왔는가?
- 두 값이 다른 이유는 화면 문구가 아니라 서버 결과 또는 업무 규칙의 차이인가?
- 정상 조합에서 제외한 제약은 누가 결정했고, 서버도 같은 규칙으로 거절하는가?
- 특정 조합을 고위험으로 승격한 근거는 금전·보안·변경량·장애 이력 중 무엇인가?
- 생성 결과가 바뀌었을 때 어떤 테스트가 새로 생기고 어떤 테스트가 사라졌는가?

이 질문을 코드 리뷰의 체크 항목처럼 쓰면, 테스트 개수를 줄이는 논의가 개인의 감이나 직급에 의존하는 일을 줄일 수 있습니다. 예를 들어 기획자가 "제주 새벽배송은 지원하지 않는다"고 말하면 QA는 이를 단순한 제외 규칙으로 끝내지 않고, 주문 API가 조작된 요청을 거절하는지와 오류 안내가 일관적인지를 물을 수 있습니다. 반대로 개발자가 "같은 코드 경로"라고 설명하면 테스트 담당자는 정말 동일한 기본값·권한·외부 연동을 쓰는지 확인할 수 있습니다.

모델 파일 자체를 저장소에서 관리하는 것도 좋은 선택이 될 수 있습니다. 값과 제약이 코드 리뷰에서 변경 이력으로 남으면, 특정 테스트가 언제 왜 사라졌는지 추적하기 쉽습니다. 다만 사람이 이해하기 어려운 생성기 전용 문법만 남기면 리뷰가 형식화될 수 있습니다. 모델 옆에 사람이 읽는 표나 짧은 설명을 두고, 생성된 테스트 데이터와 연결하는 정도가 적절합니다.

## 상태가 있는 기능에는 시간을 조건으로 추가해야 한다

Pairwise는 한 번의 입력 요청을 잘 정리하는 데 특히 유용합니다. 하지만 많은 업무 기능은 이전 요청의 결과에 따라 다음 요청이 달라지는 **상태 전이(state transition)** 문제입니다. 예를 들어 쿠폰은 발급됨, 사용 예약됨, 사용 완료됨, 취소됨, 만료됨 상태를 거칠 수 있습니다. "쿠폰 상태"라는 값을 한 행에 넣는 것만으로는 발급 뒤 두 탭에서 동시에 사용하거나, 결제 실패 뒤 예약이 풀리는 순서를 충분히 확인하지 못합니다.

이런 경우에는 먼저 상태 전이 표로 허용되는 이전 상태·이벤트·다음 상태를 정리합니다. 그다음 각 전이에서 영향을 주는 조건, 예를 들어 회원 등급·결제 결과·네트워크 재시도 여부에 Pairwise를 적용할 수 있습니다. 즉, 상태 전이 테스트와 조합 테스트를 병렬로 선택하는 것이 아니라, 상태 전이가 뼈대가 되고 조합은 각 전이의 입력 폭을 넓히는 방식입니다.

시간도 같은 이유로 독립된 위험이 됩니다. 쿠폰 만료 직전, 예약 발송 시작 시각, 월말 정산, 날짜 경계는 단순한 문자열 값이 아니라 시스템 시계·시간대·배치 작업과 관계됩니다. 모든 시간대를 Pairwise 열에 넣어 조합을 폭발시키기보다, 제품이 지원하는 시간대와 경계 시각을 명확히 하고 고위험 시나리오로 선택하는 편이 현실적입니다. 테스트에서 시간을 고정할 수 있다면 고정한 기준 시각과 시간대를 기록해 재현성을 높이세요.

## 자동화 계층을 나누는 기준

조합 결과가 열두 행이라고 해서 열두 행을 모두 같은 방식으로 실행할 필요는 없습니다. API 수준 테스트는 빠르게 많은 입력을 반복하기 좋고, 데이터베이스 검증까지 포함하면 계산·저장 규칙을 확인할 수 있습니다. 반면 실제 브라우저 테스트는 사용자가 선택할 수 있는지, 오류 문구가 이해 가능한지, 결제 창과의 연결이 끊기지 않는지 확인하는 데 강점이 있지만 일반적으로 비용이 더 큽니다.

한 가지 실용적인 분할은 다음과 같습니다. 값 쌍 커버리지는 API나 서비스 계층에서 넓게 실행합니다. UI에서만 가능한 선택 제약과 핵심 구매 흐름은 브라우저에서 대표 조합과 고위험 조합을 실행합니다. 외부 결제나 배송처럼 실제 연동 비용이 큰 부분은 계약 환경, 모의 응답, 소수의 승인된 통합 시나리오로 나눕니다. 어느 계층이 무엇을 검증하지 않는지도 명시해야 "자동화됐으니 다 확인됐다"는 오해를 막을 수 있습니다.

테스트 데이터도 계층에 따라 준비 전략이 달라집니다. API 테스트가 공유된 계정의 잔액을 바꾸면 다른 조합의 결과가 오염될 수 있습니다. 실행마다 독립 주문을 만들거나, 식별 가능한 테스트 테넌트를 두거나, 가능한 범위에서 정리 작업을 수행하는 이유가 여기에 있습니다. 정리 작업이 실패했을 때 데이터를 무조건 삭제하는 명령을 추가하기보다, 식별자와 보존 기간을 정한 뒤 안전하게 관리하는 절차가 필요합니다.

## Pairwise 적용 전후의 의사결정 기록

Pairwise를 도입하면 "테스트가 몇 개에서 몇 개로 줄었다"는 수치가 가장 눈에 띕니다. 하지만 장기적으로 더 유용한 기록은 테스트 수가 아니라 적용 전제입니다. 예를 들어 다음 문장을 남길 수 있습니다. "이 모델은 현재 웹·모바일 API가 같은 할인 규칙을 사용한다는 전제에서 만들었다." 이후 모바일 API가 독립 구현으로 분리되면, 이 전제는 재검토 신호가 됩니다.

또 다른 기록은 제외 이유입니다. 가령 구형 브라우저를 지원 범위에서 제외했다면 단순히 표에서 값을 지우지 말고 지원 종료 정책과 연결하세요. 비회원의 세금계산서를 음수 테스트로만 다룬다면, 사용자 화면·API·관리자 도구에서 각각 어떤 오류가 기대되는지 적으세요. 이런 기록은 담당자가 바뀌어도 조합 모델이 살아남게 합니다.

테스트 설계의 품질은 테스트 케이스 수로만 평가하기 어렵습니다. 좋은 조합 모델은 새 요구사항이 들어왔을 때 어느 조건과 제약이 영향을 받는지 빠르게 찾게 해 줍니다. 나쁜 모델은 행 수가 적어 보여도 값의 의미가 모호해 수정할 때마다 처음부터 다시 논의하게 만듭니다. 그래서 Pairwise의 목표는 최소 행 수가 아니라, 충분히 설명 가능하고 변경 가능한 행 수입니다.

## 한계와 적용 기준 Q&A

**Q. 입력 필드가 많은 모든 화면에 Pairwise를 적용해야 하나요?**
아닙니다. 서로 영향을 주지 않는 필드를 하나의 모델에 넣으면 표만 커지고 정보는 줄어듭니다. 계산, 권한, 표시, 검색처럼 독립적으로 검증할 수 있는 문제 영역을 먼저 분리하세요. 조건 간 상호작용이 실제로 존재하고 전수 조합이 부담스러운 곳에 적용하는 것이 좋습니다.

**Q. 모바일·브라우저 호환성도 Pairwise로 고르면 되나요?**
가능하지만, 지원 정책을 먼저 확정해야 합니다. 지원하지 않는 운영체제와 브라우저를 조합에 넣는다고 품질이 올라가지는 않습니다. 지원 대상 목록을 조건으로 모델링하고, 결제·파일 업로드·알림처럼 플랫폼 차이가 큰 기능에는 고위험 조합을 추가하세요. 실제 기기에서의 접근성, 네트워크, 화면 회전 문제는 조합표만으로 충분하지 않을 수 있습니다.

**Q. 세 조건 상호작용이 걱정되면 3-way로 올리면 되나요?**
3-way는 세 값의 모든 조합을 덮는 방식이며, 일반적으로 Pairwise보다 실행 수가 증가합니다. 위험 근거가 있는 작은 영역에 적용하는 것이 합리적입니다. 예를 들어 권한·테넌트·내보내기 형식처럼 세 조건이 함께 보안 경계를 이루면 3-way 또는 명시적 시나리오가 필요할 수 있습니다. 전 제품에 같은 강도를 적용하기보다 실패 영향과 변경 범위를 기준으로 결정하세요.

**Q. 조합표가 통과했는데도 버그가 나면 방법이 틀린 것 아닌가요?**
그렇지 않습니다. 조합 테스트는 상태 전이, 시간, 동시성, 데이터 크기, 사용성, 관찰되지 않은 요구사항을 모두 대신하지 않습니다. 버그를 계기로 어떤 축이나 제약, 오라클, 고위험 시나리오가 빠졌는지 배우는 것이 중요합니다. 통과한 표를 보증서로 보지 말고, 현재 가설에 대한 반복 가능한 증거로 해석하세요.

## 현업에서 바로 쓰는 설계 순서

1. 기능의 결정 규칙을 읽고 결과를 바꾸는 조건 후보를 모읍니다.
2. 동등 분할과 경계값 분석으로 각 조건의 의미 있는 값을 정합니다.
3. 불가능한 정상 조합과 서버가 거절해야 할 음수 조합을 분리합니다.
4. 제약을 모델에 명시하고 Pairwise 결과에서 모든 값 쌍이 덮였는지 확인합니다.
5. 금액·권한·외부 연동·최근 변경을 기준으로 고위험 시나리오를 별도로 추가합니다.
6. 각 행의 기대 결과와 데이터 준비 방법을 적어 자동화 가능 여부를 정합니다.
7. 결함과 정책 변경이 생길 때 조건·값·제약을 다시 검토합니다.

이 순서는 문서 작업을 늘리기 위한 절차가 아닙니다. 테스트를 줄일 때 무엇을 포기하지 않았는지 보여 주기 위한 최소한의 기록입니다. 팀이 "이 조합은 왜 빠졌나"에 답할 수 있다면, 짧은 테스트 목록도 신뢰할 수 있습니다.

## 마무리

조합 테스트의 핵심은 테스트 케이스 수를 멋지게 줄이는 데 있지 않습니다. 무한히 늘어나는 입력 공간을 조건, 값, 제약, 위험이라는 언어로 나누고, 반복 가능한 근거를 만드는 데 있습니다. Pairwise는 두 조건의 관계를 넓게 훑는 데 유용하지만, 경계값·상태 전이·보안·금전 규칙을 자동으로 보장하지는 않습니다.

처음 적용한다면 가장 복잡한 화면부터 시작하기보다, 조건이 세네 개이고 결과 규칙이 분명한 API 하나를 선택하세요. 전수 조합과 Pairwise 결과를 나란히 비교하고, 빠진 고위험 조합을 이유와 함께 추가해 보세요. 그 경험이 쌓이면 테스트 케이스를 많이 쓰는 사람보다, 위험을 설명하고 필요한 테스트를 고르는 QA 엔지니어에 가까워질 수 있습니다.
