테스트를 실행했는데도 “그래서 이 결과가 맞는가?”라는 질문에 답하지 못하는 경우가 있습니다. 요청이 200으로 끝났고 화면이 열렸어도 할인 금액, 권한 제한, 저장된 데이터, 후속 작업이 모두 맞았다는 뜻은 아닙니다. **테스트 오라클(Test Oracle)** 은 테스트가 관찰한 실제 결과를 무엇과 비교해 통과·실패를 결정할지 정하는 기준입니다. 이름은 거창하지만 `expect(total).toBe(27000)`의 기대값도 오라클이고, “재고는 음수가 될 수 없다”는 규칙도 오라클이며, 이전 버전과 새 버전의 결과를 비교하는 방식도 오라클입니다.

좋은 테스트는 요청을 한 번 보내 보는 일이 아니라 중요한 결과를 판정할 근거를 남기는 일입니다. 특히 웹 화면의 동작을 따라 API를 구성한 업무에서는 API 명세만으로 오라클이 충분하지 않을 수 있습니다. 명세에는 필드와 상태 코드가 있어도, 화면에서만 보이던 단계 순서, 선택 가능한 조합, 이미 처리한 요청의 재시도 규칙, 사용자 역할에 따른 버튼 노출 조건은 별도로 합의해야 하기 때문입니다. 이 글은 오라클을 “정답을 외워 두는 목록”이 아니라 제품 규칙을 테스트 가능한 언어로 바꾸는 설계 방법으로 다룹니다.

## 먼저 알아둘 기반 기술

**테스트 케이스(test case)** 는 준비 조건, 실행 행동, 기대 결과를 묶은 검증 단위입니다. 준비 조건은 회원 등급이나 재고처럼 시작 상태를 만들고, 행동은 API 호출·버튼 클릭·배치 실행이며, 기대 결과가 바로 오라클의 핵심입니다. **단언(assertion)** 은 그 기준을 코드로 적는 문장입니다. `status === 200`도 단언이지만, “주문 상태가 PAID이고 결제 승인 번호가 저장되며 재고가 한 번만 감소한다”는 여러 단언이 훨씬 넓은 계약을 표현합니다.

**명세(specification)** 는 API 요청·응답, 업무 규칙, 화면 정책처럼 시스템이 지켜야 할 약속입니다. OpenAPI는 경로와 필드 형식을 잘 표현하지만 “취소된 주문은 다시 결제할 수 없다” 같은 상태 전이나 “관리자만 정산 파일을 내려받을 수 있다” 같은 정책은 명세의 설명, 별도 규칙 문서, 화면 기획에 흩어질 수 있습니다. 테스트 담당자는 API 문서만 읽고 오라클을 끝내지 말고 사용자 흐름과 데이터 규칙을 함께 확인해야 합니다.

**관찰 가능성(observability)** 은 시스템 내부 상태와 결과를 외부에서 확인할 수 있는 정도입니다. 테스트에서 관찰 가능한 것은 HTTP 상태 코드만이 아닙니다. 응답 본문, 데이터베이스 레코드, 발행된 메시지, 감사 로그, 이메일 발송 요청, 파일 생성 여부도 확인 대상이 될 수 있습니다. 다만 내부 구현 세부 사항까지 고정하면 리팩터링 때 쓸데없이 깨지므로, 사용자와 다른 구성 요소가 실제로 의존하는 결과를 우선합니다.

## 오라클은 왜 별도로 설계해야 할까

사람은 화면을 보며 자연스럽게 정답을 판단합니다. 무료 배송 기준이 3만 원이면 결제 화면의 배송비가 0원인지 보고, 취소 버튼을 누른 뒤 상태가 취소로 바뀌었는지 봅니다. 자동화 테스트는 이런 판단을 스스로 추론하지 못합니다. 호출이 성공했다는 사실과 업무 결과가 옳다는 사실은 다르므로, 어떤 값·관계·변화가 성공을 의미하는지 명시해야 합니다.

예를 들어 `POST /orders/{id}/cancel`이 200을 반환해도 다음 경우는 모두 잘못일 수 있습니다. 이미 취소된 주문에서 재고가 두 번 증가할 수 있고, 다른 고객의 주문을 취소할 수 있고, 환불 요청 메시지가 발행되지 않을 수 있으며, 환불 금액이 할인 전 금액일 수 있습니다. 반대로 내부 테이블의 임시 컬럼 이름이 바뀌어도 고객이 보는 결과와 계약이 같다면 테스트가 실패할 이유는 적습니다. 오라클 설계는 이 둘을 구분하는 과정입니다.

테스트가 약해지는 흔한 이유는 개발자가 기능을 구현한 뒤 “정상 결과가 보인다”는 확인을 테스트로 옮길 때입니다. 이 방식은 행복 경로에는 빠르지만, 경계값·실패 처리·중복 실행·권한 없는 사용자를 놓치기 쉽습니다. 오라클을 먼저 적으면 구현 방식보다 업무 결과를 먼저 생각하게 됩니다. 테스트가 실패했을 때도 “무슨 값이 달랐는가”가 아니라 “어떤 약속이 깨졌는가”를 읽을 수 있습니다.

## 오라클의 네 가지 재료: 값·관계·변화·금지

가장 익숙한 것은 **예상 값 오라클**입니다. 세금 10%를 포함한 금액이 11,000원인지, 잘못된 쿠폰 코드에 `COUPON_NOT_FOUND`가 반환되는지 확인합니다. 입력과 결과가 작고 결정적일 때 읽기 쉽습니다. 다만 대형 응답 전체를 복사해 비교하면 필요한 규칙보다 우연한 필드 순서·시간·식별자에 묶일 수 있습니다. 핵심 필드와 의미 있는 부분을 골라 비교해야 합니다.

둘째는 **관계 오라클**입니다. 정확한 추천 순서를 모르더라도 결과 수가 20개 이하인지, 응답의 각 상품이 검색 조건을 만족하는지, 페이지를 이어 붙였을 때 중복 ID가 없는지를 검사할 수 있습니다. 셋째는 **상태 변화 오라클**입니다. 주문 취소 뒤 주문 상태와 재고 수량, 환불 요청이 함께 바뀌는지를 전후 비교합니다. 넷째는 **금지 오라클**입니다. 권한 없는 사용자는 데이터를 바꾸지 못하고, 실패한 요청은 메시지를 발행하지 않으며, 재시도는 중복 결제를 만들지 않아야 한다는 방식입니다.

이 네 재료는 함께 쓰입니다. 단순히 200을 확인하는 대신 “응답은 200, 상태는 CANCELLED, 재고는 한 번 증가, 결제 메시지는 한 번 발행, 타인의 주문은 변하지 않음”을 적으면 테스트가 실제 위험을 더 잘 설명합니다. 반대로 모든 결과를 하나의 E2E 테스트로 확인하면 실패 원인을 찾기 어려워집니다. 계산 규칙은 단위 테스트, API가 계약을 전달하는지는 통합 테스트, 사용자가 실제로 완료할 수 있는지는 대표 UI 흐름으로 나누는 편이 보통 더 빠르고 안정적입니다.

## 업무 규칙을 관찰 가능한 문장으로 바꾸기

오라클을 만들 때는 먼저 자연어 요구를 한 줄로 적습니다. “주문 금액이 30,000원 이상이면 일반 회원의 배송비는 0원이다.” 다음으로 경계값을 분해합니다. 29,999원은 유료, 30,000원은 무료, 30,001원은 무료여야 합니다. 그 뒤 관찰 지점을 정합니다. 계산 함수만 단위 테스트할지, API 응답의 `shippingFee`까지 볼지, 결제 화면의 표시까지 볼지는 해당 규칙이 깨질 수 있는 위치와 비용에 따라 정합니다.

```typescript
expect(calculateShippingFee({ member: 'NORMAL', total: 29999 })).toBe(3000);
expect(calculateShippingFee({ member: 'NORMAL', total: 30000 })).toBe(0);
expect(calculateShippingFee({ member: 'NORMAL', total: 30001 })).toBe(0);
```

이 예시는 `>=`가 `>`로 바뀌는 결함을 잡습니다. 하지만 API가 계산 값을 버리거나 다른 필드에 매핑하는 결함은 잡지 못합니다. 그래서 위험이 높은 경로에는 API 수준에서 `shippingFee`를 확인하고, 실제 구매 흐름에는 대표적인 한두 개의 화면 테스트를 둡니다. 같은 단언을 모든 층에 복제하는 것이 아니라 각 층이 다른 실패 원인을 잡도록 나눕니다.

또 하나의 방법은 규칙표를 만드는 것입니다. 회원 등급, 주문 금액, 쿠폰 사용 여부를 행과 열로 분리하고 기대 배송비·할인 가능 여부·오류 코드를 적습니다. 규칙표는 기획자와 개발자, QA가 서로 다르게 이해한 조합을 빨리 드러냅니다. 자동화 코드는 나중에 바뀌어도, 표에 적힌 오라클은 합의된 업무 규칙으로 남습니다.

## API 명세만으로 부족해지는 순간

OpenAPI 같은 계약은 요청의 타입, 필수 필드, 응답 상태 코드, 스키마 호환성을 확인하는 중요한 출발점입니다. 그러나 화면 기반 제품에서는 사용자가 임의의 API 호출 조합을 만들지 않습니다. 예를 들어 화면에서는 본인 인증을 끝낸 뒤에만 계좌 등록 버튼이 보이고, 심사 중인 신청서는 수정 버튼이 잠기며, 제출 뒤에는 취소 사유를 입력해야 할 수 있습니다. 백엔드 API가 이런 순서와 제약을 강제해야 하는지, 프론트엔드만 안내해도 되는지, 재시도는 어떻게 처리하는지는 API 형식만으로 결정되지 않습니다.

따라서 시나리오 오라클을 별도로 만듭니다. “신청서가 REVIEW 상태일 때 일반 사용자는 수정 요청을 보내도 409를 받고 데이터는 변하지 않는다”, “승인 전에는 계약서 다운로드 URL을 만들지 않는다”, “제출 요청을 같은 idempotency key로 두 번 보내도 계약은 하나만 생성한다”처럼 순서·권한·부수 효과를 포함해 적습니다. 이 문장은 API 검증의 부족을 비난하는 것이 아니라 화면과 업무가 추가한 계약을 테스트 자산으로 승격하는 일입니다.

여기서 특히 중요한 것은 화면에서 가능한 동작과 서버가 허용하는 동작을 구분하는 일입니다. 화면이 버튼을 숨겼다고 해서 API가 보호되는 것은 아닙니다. 반대로 업무상 실제 사용자가 만들 수 없는 조합까지 서버가 모두 처리할 필요가 있는지도 위험도와 보안 요구에 따라 판단해야 합니다. 테스트 오라클은 “사용자 화면이 이렇게 했으니 API도 이렇게 돼야 한다”는 단순 복사가 아니라, 어떤 제약을 서버 계약으로 강제할지 합의한 결과여야 합니다.

## 불변식: 정답 하나 대신 반드시 지켜야 할 성질을 확인한다

**불변식(invariant)** 은 입력이 달라도 항상 지켜져야 하는 성질입니다. 잔액은 승인되지 않은 출금으로 감소하지 않아야 하고, 할인 후 결제 금액은 음수가 될 수 없으며, 페이지 응답의 ID는 중복되지 않아야 합니다. 불변식은 날짜, 난수, 추천 알고리즘처럼 정확한 결과를 미리 쓰기 어려운 영역에서 특히 유용합니다.

다만 “결과가 비어 있지 않다”처럼 너무 약한 불변식은 오류를 놓칩니다. 반대로 구현 방식에 매달린 불변식은 변경을 막습니다. 예를 들어 정렬 알고리즘이 바뀌어도 최종 결과가 가격 오름차순이고 동일 가격의 정렬 정책이 명시된 대로라면 충분합니다. 어떤 내부 함수가 몇 번 호출됐는지를 기본 오라클으로 삼는 것은 협력 객체 계약을 검증해야 하는 특별한 경우에만 고려합니다.

불변식은 속성 기반 테스트와도 연결됩니다. 예를 들어 “정렬 결과는 원래 입력과 같은 원소를 포함한다”, “취소 API는 성공하든 실패하든 주문 금액을 새로 만들지 않는다”처럼 입력 여러 개에 공통인 성질을 적을 수 있습니다. 단, 무작위 입력 생성기가 오류를 재현할 수 있도록 seed와 최소 실패 사례를 남겨야 합니다. 생성한 입력이 실제 업무 도메인을 벗어나지 않는지도 함께 점검합니다.

## 참조 모델과 차분 비교

복잡한 계산에는 독립적인 간단한 **참조 모델(reference model)** 을 둘 수 있습니다. 실제 할인 엔진은 쿠폰·등급·행사·한도 때문에 복잡할 수 있지만, 테스트에서는 작은 입력 범위에 대해 명확한 규칙을 구현한 모델과 결과를 비교합니다. 핵심은 운영 코드를 복사하지 않는 것입니다. 같은 조건문을 두 번 복사하면 같은 오해를 두 번 구현할 위험이 큽니다.

**차분 테스트(differential testing)** 는 이전 안정 버전, 다른 구현, 신뢰할 수 있는 외부 계산기와 결과를 비교하는 방식입니다. DBMS 쿼리 최적화, 데이터 변환, 파일 파서처럼 출력이 방대할 때 도움이 됩니다. 하지만 이전 버전도 틀릴 수 있고 외부 서비스의 정책이 바뀔 수 있으므로, 차이는 자동으로 “새 버그”라고 단정하지 말고 검토 대기열로 보냅니다. 비교 대상의 버전·입력·허용 오차를 기록해야 나중에 재현할 수 있습니다.

참조 모델은 모든 업무 규칙에 필요하지 않습니다. 단순한 계산을 두 구현으로 유지하면 비용이 더 커질 수 있습니다. 금액·세금·포인트처럼 오류 영향이 크고 입력 조합이 많은 영역, 또는 새 엔진 교체 전후 결과를 대량 비교해야 하는 영역부터 고려하는 것이 현실적입니다.

## 시간·난수·외부 연동에서 오라클을 안정화하는 법

테스트가 매번 다른 시간을 읽으면 오늘 자정이나 만료 시각이 흔들립니다. 시간은 주입 가능한 clock으로 고정하고, 난수는 seed를 기록하며, 외부 결제·메일·지도 서비스는 팀이 관리하는 테스트 더블로 대체할 수 있습니다. **스텁(stub)** 은 미리 정한 응답을 돌려주는 대역이고, **스파이(spy)** 는 어떤 호출이 있었는지 기록하는 대역입니다. 이들은 외부 시스템을 흉내 내는 수단이지 오라클 자체가 아닙니다. 오라클은 그 호출이 필요한 조건에서 정확한 인자와 횟수로 발생했는지, 실패 시 호출되지 않아야 하는지를 판정합니다.

시간을 고정했다고 현실의 시간대·서버 시계·스케줄러 문제까지 사라지는 것은 아닙니다. 단위 테스트는 날짜 경계 규칙을 빠르게 검증하고, 통합 환경에서는 실제 타임존 설정과 예약 작업의 대표 사례를 별도로 확인합니다. 레이어마다 질문이 다르다는 점을 유지하면 지나친 모킹도, 불안정한 전체 연동 테스트도 줄일 수 있습니다.

외부 연동의 오라클은 응답 값뿐 아니라 요청 내용과 실패 처리도 포함해야 합니다. 예를 들어 결제 승인 요청에는 민감 정보가 로그에 노출되지 않아야 하고, 타임아웃 때 동일 결제를 무한 재시도하지 않아야 하며, 성공 응답을 받기 전에 주문을 완료 상태로 바꾸지 않아야 합니다. 이런 규칙은 단순한 API 상태 코드보다 운영 사고와 더 가까운 품질 기준입니다.

## 오라클을 리뷰하는 체크리스트

새 테스트를 리뷰할 때는 “이 테스트는 어떤 잘못을 실패로 만들까?”를 먼저 묻습니다. 정상 응답만 검사하는지, 경계값과 실패 경로가 있는지, 데이터 변경 전후를 보는지, 다른 사용자의 데이터가 보존되는지, 재시도와 중복 요청에 대한 기준이 있는지를 확인합니다. 입력을 많이 넣었다는 사실보다 각각의 입력이 어떤 규칙을 구분하는지가 중요합니다.

또한 테스트 이름에는 결과와 조건을 드러냅니다. `shouldWork`보다 `일반_회원은_30_000원_주문에서_배송비가_면제된다`가 오라클을 더 잘 전달합니다. 실패 메시지는 실제값·기대값·업무 맥락을 보여야 합니다. CI에서 실패한 사람이 요구 사항 문서를 다시 찾지 않아도 판단할 수 있도록 말입니다.

리뷰에서 테스트 구현 세부 사항에만 매달리지 않는 것도 중요합니다. “mock이 세 번 호출됐는가”보다 “중복 요청으로 환불이 세 번 생성되지 않는가”가 먼저입니다. 구현을 바꿔도 유지되어야 할 관찰 가능한 결과를 먼저 적고, 꼭 필요한 경우에만 내부 상호작용을 단언합니다.

## 테스트 계층별로 오라클을 나누는 기준

도메인 단위 테스트는 계산·상태 전이·권한 판단처럼 빠르고 결정적인 규칙을 확인하기 좋습니다. 이 계층의 오라클은 입력과 기대값, 금지된 변화가 분명해야 합니다. API 통합 테스트는 직렬화, 인증, DB 트랜잭션, 오류 변환처럼 구성 요소 사이의 계약을 확인합니다. 여기서는 상태 코드만이 아니라 응답 스키마와 영속 상태, 실패 시 롤백 여부를 봅니다. UI E2E 테스트는 사용자가 실제로 로그인하고 입력하고 완료하는 대표 흐름을 확인하지만, 모든 조합을 맡기기보다 화면 연결과 접근성, 브라우저 동작처럼 하위 계층이 보기 어려운 위험에 집중합니다.

이 분리를 하면 같은 할인 규칙을 세 번 복사하지 않아도 됩니다. 단위 테스트는 29,999·30,000·30,001원 같은 경계를 촘촘히 확인하고, API 테스트는 계산 결과가 계약 필드에 실리는지를 확인하며, UI 테스트는 실제 구매 화면에서 그 결과가 사용자가 이해할 수 있게 표시되는지를 확인합니다. 실패했을 때 어느 계층에서 규칙이 깨졌는지도 빨리 알 수 있습니다. 테스트 피라미드는 테스트 수의 모양보다 오라클의 책임을 적절한 비용으로 배치하는 방법입니다.

## 예시 기반 합의가 먼저인 이유

오라클을 정확하게 쓰기 어려운 가장 큰 이유는 코드가 복잡해서가 아니라, 요구가 예시 없이 표현됐기 때문인 경우가 많습니다. “빠르게 처리한다”, “적절한 할인”, “권한이 있는 사용자” 같은 문장은 사람마다 다른 결과를 떠올리게 합니다. 이를 ‘일반 회원이 A 조건에서 B를 요청하면 C를 볼 수 있고 D는 바뀌지 않는다’처럼 예시로 바꾸면, 테스트 케이스와 API 계약, 화면 정책이 같은 기준을 사용하게 됩니다. 예시는 구현을 제한하려는 장치가 아니라, 제품이 실제로 약속한 결과를 확인하는 가장 작은 언어입니다.

예시를 만들 때 정상·경계·금지 사례를 나란히 두면 더 좋습니다. 승인자는 보고서를 내려받을 수 있고, 일반 사용자는 같은 요청에서 권한 오류를 받으며, 퇴사 처리된 계정은 기존 세션으로도 접근할 수 없다는 식입니다. 세 사례는 단순히 테스트 수를 늘리는 것이 아니라 정책의 범위를 드러냅니다. 정책이 바뀌면 이 예시를 먼저 고친 뒤 자동화 오라클을 갱신해야 합니다.

## 측정 가능한 개선으로 연결하기

오라클 개선의 효과는 테스트 개수보다 살아남은 결함과 리뷰 대화에서 확인할 수 있습니다. 새 경계값 테스트가 실제 요구의 빈틈을 드러냈는지, 실패 메시지만으로 원인을 좁힐 수 있었는지, 같은 유형의 결함이 재발하지 않았는지를 짧게 기록합니다. 숫자를 목표로 삼기보다 위험 규칙의 판정 기준이 선명해졌는지를 팀의 품질 지표로 삼는 편이 안전합니다.

테스트가 통과한 이유를 한 문장으로 설명할 수 없다면 오라클을 다시 읽어 볼 신호입니다. 결과 값, 전제 조건, 금지된 변화 중 무엇을 지키는지 이름과 실패 메시지에 드러내면 인수인계와 장애 분석에서도 같은 기준을 재사용할 수 있습니다.

이 기준을 문서·코드·리뷰에서 같은 말로 사용하면 새 팀원도 테스트의 목적을 빠르게 이해할 수 있습니다.

테스트 실행 속도나 도구 선택이 달라져도, 제품 약속을 관찰 가능한 결과로 번역한다는 원칙은 변하지 않습니다. 이 원칙이 오라클 설계의 출발점입니다.

## 한계와 적용 기준 Q&A

### Q. 기대값을 많이 쓰면 테스트가 더 좋아지나요?

A. 무관한 필드까지 모두 고정하면 구현 변경에 취약해집니다. 금액, 권한, 상태, 외부 계약처럼 위험이 큰 결과를 우선 단언하고 임시 ID·생성 시각·표현 순서처럼 계약이 아닌 값은 필요할 때만 봅니다.

### Q. UI 테스트에서만 사용자 시나리오를 검증하면 되나요?

A. 아닙니다. UI는 대표 흐름을 확인하기 좋지만 실행 비용이 큽니다. 화면이 전제하는 권한·상태·재시도 규칙은 API와 도메인 테스트에도 표현해 우회 호출에서도 안전한지 확인해야 합니다.

### Q. 모킹한 외부 API 호출 횟수를 단언해도 될까요?

A. 결제 승인 중복 방지처럼 호출 횟수 자체가 계약이면 유효합니다. 단순 구현 세부 사항이라면 결과와 부수 효과를 확인하는 편이 더 오래가는 테스트가 됩니다.

### Q. 오라클이 애매하면 누가 결정하나요?

A. 테스트 담당자만의 추측으로 정하지 않습니다. 기획·개발·도메인 담당자가 사례와 예외를 합의하고, 그 결정을 명세·테스트·리뷰 기준에 함께 남겨야 합니다. 애매함을 발견한 것 자체가 중요한 품질 신호입니다.

### Q. 오라클을 자동화하지 못하면 수동 테스트로 남겨도 되나요?

A. 네. 시각적 인상, 새 기능의 탐색, 아직 합의되지 않은 정책처럼 자동 판정 기준이 성숙하지 않은 영역은 수동 검토가 더 적절할 수 있습니다. 다만 반복되는 판단은 체크리스트와 예시를 남기고, 안정된 규칙부터 자동화 후보로 옮기는 것이 좋습니다.

## 마무리

테스트 오라클은 자동화의 마지막 assert 한 줄보다 넓은 개념입니다. 사용자가 기대하는 결과, 시스템이 바꾸어도 되는 것과 바꾸면 안 되는 것, 화면 흐름이 암묵적으로 가진 제약을 관찰 가능한 기준으로 옮기는 작업입니다. 먼저 위험이 큰 규칙 하나를 골라 값·관계·상태 변화·금지 조건을 적어 보세요. 그 기준이 단위 테스트, API 계약, 사용자 시나리오에서 각각 어떤 역할을 해야 하는지 나누면 테스트 수를 늘리지 않고도 실패가 말해 주는 내용을 선명하게 만들 수 있습니다.

좋은 오라클은 테스트만 위한 문서가 아닙니다. 요구가 바뀌었을 때 어떤 결과를 다시 합의해야 하는지, 장애가 생겼을 때 어떤 상태를 확인해야 하는지, 면접에서 자신의 테스트 방법론을 어떻게 설명할 수 있는지를 함께 정리해 줍니다. 통과한 테스트의 수보다 “이 테스트는 어떤 제품 약속을 지키는가”를 설명할 수 있는지가 더 오래가는 품질 역량입니다.

## 실무에서 오라클을 도입하는 순서

처음부터 모든 테스트에 새로운 오라클을 붙이려 하면 기준이 너무 많아져 유지되지 않습니다. 먼저 장애 영향이 큰 규칙 하나를 고릅니다. 금액 계산, 접근 권한, 개인정보 마스킹, 상태 전이, 중복 결제 방지, 데이터 변환처럼 작은 판단 오류가 사용자·금전·보안에 직접 영향을 주는 영역이 좋은 출발점입니다. 그 규칙에 대해 정상 사례 하나와 실패 사례 하나, 경계 사례 하나를 먼저 적습니다.

다음에는 각 사례가 어떤 결과를 확인해야 하는지 나눕니다. 입력이 유효하면 반환값만 맞으면 되는지, DB 상태도 바뀌어야 하는지, 메시지가 한 번 발행되어야 하는지, 실패한 경우에는 무엇도 바뀌지 않아야 하는지를 구분합니다. 이 단계에서 테스트 데이터의 소유자와 정리 방법도 결정합니다. 서로 병렬로 실행되는 테스트가 같은 주문이나 같은 계정을 공유하면 오라클이 맞아도 결과가 흔들릴 수 있기 때문입니다.

세 번째는 실패를 읽을 수 있게 만드는 일입니다. `expected false to be true` 같은 메시지보다 `승인되지 않은 출금은 잔액을 바꾸지 않아야 한다: before=10000, after=9000`처럼 업무 언어로 실패를 남깁니다. 이 메시지는 QA만 보는 결과가 아니라 개발자·기획자·운영자가 같은 문제를 이해하는 단서가 됩니다. 오라클은 코드 한 줄이지만 실패 보고는 팀의 의사소통 도구이기도 합니다.

마지막으로 규칙이 변경될 때 오라클도 변경 요청의 일부로 리뷰합니다. 화면 문구나 필드 이름이 바뀌는 것과 달리, 배송 기준·권한 정책·상태 전이가 바뀌면 기존 기대값을 그대로 둔 테스트가 거짓 경보를 낼 수 있습니다. 요구 변경의 예시와 테스트 변경을 한 리뷰에서 같이 보면, 제품 계약이 언제 어떻게 바뀌었는지를 추적하기 쉽습니다.

## 데이터베이스와 비동기 처리에서 보는 오라클

데이터베이스를 포함한 테스트는 응답 본문만 확인하면 부족할 때가 많습니다. 예를 들어 회원 탈퇴 API가 204를 반환해도 개인정보가 남아 있거나, 연결된 주문 이력이 규정과 다르게 삭제되거나, 감사 기록이 누락될 수 있습니다. 반대로 내부 테이블의 모든 행을 직접 비교하면 마이그레이션과 인덱스 변경에 지나치게 민감해질 수 있습니다. 사용자가 보거나 다른 서비스가 의존하는 데이터 상태, 보존해야 하는 감사 기록, 절대 바뀌면 안 되는 소유권을 기준으로 선택합니다.

메시지 큐와 이벤트 기반 처리에서는 “응답 시점에 아직 결과가 완성되지 않는다”는 사실도 오라클에 포함합니다. 주문 생성 뒤 재고 예약 이벤트가 발행되어야 한다면, 이벤트의 타입·키·중복 처리 기준·최종 상태를 확인합니다. 비동기 처리를 기다리는 테스트는 무한 sleep 대신 제한된 시간 안에 원하는 상태에 도달하는지를 폴링하거나, 테스트 환경에서 완료 신호를 관찰하게 설계합니다. 시간 초과 자체도 오라클의 한 결과이며, 재시도 가능한 지연과 실제 유실을 구분할 근거가 필요합니다.

## 오라클 부채를 관리한다

코드에 기술 부채가 있듯, 테스트에는 **오라클 부채**가 생길 수 있습니다. 테스트는 많지만 성공 기준이 약하거나, 오래된 화면 흐름이 실제 정책과 달라졌거나, 외부 연동의 실패 결과를 확인하지 않는 상태가 이에 해당합니다. 이 부채는 커버리지 수치만으로 발견하기 어렵습니다. 장애 회고에서 “테스트가 있었는데 왜 막지 못했나”를 묻고, 빠진 판정 기준을 작은 개선 항목으로 기록하는 방식이 효과적입니다.

오라클 부채를 줄인다고 모든 테스트를 E2E로 올릴 필요는 없습니다. 오히려 가장 빠른 계층에서 업무 규칙을 명확히 하고, 필요한 통합 지점만 추가하는 편이 유지 비용이 낮습니다. 팀이 새 기능마다 ‘정상 결과·금지 결과·경계값·관찰 위치’를 짧게 합의하는 습관을 만들면, 자동화 도구의 종류와 무관하게 테스트 품질이 좋아집니다.
