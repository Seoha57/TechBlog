<section class="quick-answers"><h2>먼저 답하기</h2><p><strong>Q. 카오스 엔지니어링은 운영 환경을 일부러 망가뜨리는 테스트인가요?</strong><br>A. 무작정 장애를 만드는 일이 아닙니다. 정상 상태에 대한 가설을 먼저 세우고, 작은 범위에서 한 가지 실패를 주입하며, 사용자 영향 지표와 중단 조건을 관찰하는 실험 방식입니다.</p><p><strong>Q. 이미 단위·통합 테스트가 있으면 필요 없나요?</strong><br>A. 코드의 예상 동작을 검증하는 테스트와, timeout·의존성 지연·자원 압박·장애 조치처럼 실제 환경의 상호작용을 검증하는 실험은 역할이 다릅니다. 후자는 기존 테스트를 대체하지 않고 빈틈을 찾습니다.</p></section>

서비스 장애를 줄이려면 장애가 일어났을 때의 행동을 추측하지 않아야 합니다. 팀은 흔히 "재시도하니까 괜찮다", "부하 분산기가 다른 인스턴스로 보내 줄 것이다"라고 말합니다. 그러나 재시도가 동시에 몰리면 의존 서비스를 더 압박할 수 있고, 부하 분산기의 health check가 늦으면 죽은 인스턴스로 요청이 계속 갈 수 있습니다. 카오스 엔지니어링은 이런 믿음을 관찰 가능한 가설로 바꾸고, 작은 실패를 통해 사실인지 확인하는 방법입니다.

이 글에서 말하는 카오스는 랜덤한 불안정성이 아닙니다. 실험 대상, 실패 유형, 예상 결과, 관찰 지표, 중단 기준, 복구 방법을 미리 합의하는 품질 활동입니다. 처음에는 production이 아니라 로컬·테스트·staging에서 시작할 수 있으며, production 실험도 영향 범위를 아주 좁히고 즉시 멈출 수 있을 때만 검토합니다. 중요한 것은 실패를 주입한 횟수가 아니라, 시스템의 복원력 계약을 명확하게 만든 횟수입니다.

## 먼저 알아둘 기반 기술

복원력(resilience)은 장애가 절대 나지 않는 성질이 아니라, 일부 구성 요소가 실패해도 사용자가 받아들일 수 있는 수준으로 서비스를 계속 제공하거나 빠르게 회복하는 능력입니다. 예를 들어 상품 추천 서비스가 잠시 느려져도 주문 API가 정상이라면, 추천을 빈 목록으로 보여 주고 주문을 계속 받는 것이 복원력 있는 선택일 수 있습니다. 반대로 결제 승인 결과를 모르는 상태에서 무조건 재시도하면 중복 결제가 생길 수 있으므로, 모든 기능에 같은 복구 전략을 적용할 수는 없습니다.

SLO(Service Level Objective)는 서비스 수준 목표입니다. "월간 성공률 99.9%", "주문 생성의 95%가 500ms 안에 끝난다"처럼 사용자 관점의 목표를 수치로 표현합니다. SLI(Service Level Indicator)는 그 목표를 계산하는 실제 지표이고, error budget은 목표를 만족하면서 허용할 수 있는 실패 여유입니다. 카오스 실험은 CPU 사용률이 올랐다는 사실만 보는 대신, 실패 주입 전후에 중요한 SLI가 허용 범위에 있는지 확인해야 합니다. 그래야 실험이 시스템 내부의 소음이 아니라 사용자 영향 검증이 됩니다.

timeout은 응답을 얼마나 오래 기다릴지 정하는 시간 제한이고, retry는 실패한 요청을 다시 보내는 동작입니다. circuit breaker는 연속 실패가 발생하면 일정 기간 의존 서비스 호출을 열지 않아 추가 부하를 막는 패턴입니다. bulkhead는 한 기능의 자원 고갈이 다른 기능까지 번지는 것을 막기 위해 thread pool·connection pool·queue를 분리하는 방식입니다. 이 용어들은 모두 장애를 자동으로 해결하는 마법이 아닙니다. 시간 값, 재시도 횟수, 격리 범위가 업무 특성과 맞는지 실험으로 확인해야 합니다.

관찰성(observability)도 기반 기술입니다. 로그는 특정 사건의 상세 기록, 메트릭은 시간에 따른 숫자 변화, trace는 하나의 요청이 여러 서비스를 거치는 흐름입니다. 카오스 실험에서는 "실패를 넣었다"는 이벤트와 사용자 요청의 성공·지연·재시도·fallback이 같은 시간축에서 보여야 합니다. 원인을 모르는 오류율 상승을 실험 탓으로 넘기거나, 실험 때문에 발생한 문제가 경보에서 사라지는 일을 막으려면 실험 ID와 대상 범위를 로그·trace에 연결해야 합니다.

## 카오스 실험은 테스트 케이스와 무엇이 다른가

일반 테스트 케이스는 입력과 기대 결과를 비교하는 데 강합니다. 로그인 API에 잘못된 비밀번호를 보내 401이 나오는지, 할인 규칙에 경계값을 넣어 금액이 맞는지 검증합니다. 이 방식은 재현 가능하고 빠르며 CI에서 반복하기 좋습니다. 하지만 network packet이 일부 지연되고, cache node 하나가 응답하지 않고, autoscaling이 진행되는 동안 요청이 몰리는 상황처럼 여러 계층이 동시에 반응하는 문제는 단일 함수의 기대값으로 표현하기 어렵습니다.

카오스 실험은 정상 상태의 행동을 기준으로 잡습니다. 예를 들어 "평소 주문 생성 성공률은 99.95%이고 p95 지연은 350ms다"라는 기준을 측정합니다. 그 뒤 한 인스턴스의 database 연결을 제한한다는 변화를 넣고, "나머지 인스턴스가 트래픽을 처리해 성공률은 99.9% 이상이며 p95는 600ms 아래에 머문다"라는 가설을 검증합니다. 결과가 달라지면 시스템이 취약하다는 결론만 내리지 않고, health check·pool 크기·retry·fallback·알림 중 어느 계약이 깨졌는지 조사합니다.

그래서 카오스 실험의 산출물은 실패 스크립트 하나가 아닙니다. 가설, baseline, 영향 범위, 위험 승인, 관찰 대시보드, 중단 버튼, 발견한 결함, 수정 후 재실험 기록이 함께 있어야 합니다. 이 기록은 다음 담당자가 "왜 이 timeout은 2초인가", "왜 이 서비스는 cache 실패를 무시하는가"를 이해하는 근거가 됩니다. QA가 시나리오를 설계할 때도 기능 요구사항뿐 아니라 서비스가 실패를 어떻게 드러내고 복구해야 하는지 질문하게 됩니다.

## 가설을 작고 검증 가능하게 만들기

좋은 가설은 실패 원인과 기대 결과가 구체적입니다. "서비스는 장애에 강하다"는 너무 넓어서 측정할 수 없습니다. "결제 승인 provider의 2% 요청에 3초 지연을 넣어도 주문 API는 5초 뒤 같은 결제를 다시 승인하지 않으며, 사용자는 처리 중 상태와 재조회 방법을 본다"는 검증할 수 있습니다. 이 문장에는 대상, 실패 형태, 사용자 경험, 금지할 행동, 관찰 방법이 들어 있습니다.

가설을 만들 때는 가장 중요한 사용자 흐름을 하나 고릅니다. 회원 가입, 장바구니, 결제, 파일 업로드, 정산 배치처럼 실패했을 때 비용이 큰 흐름이 후보입니다. 그 흐름을 구성하는 의존성도 나눕니다. DNS, load balancer, application instance, database, cache, queue, 외부 API, object storage 중 어느 부분이 실패해도 같은 방식으로 복구할 수 없습니다. 먼저 의존성 지도와 데이터의 소유자를 그리면, 어떤 실패를 실험해야 할지 정하기 쉬워집니다.

baseline은 실험 전에 반드시 수집합니다. 평소에도 오류율이 흔들리고 p99 지연이 불안정하다면, 실험 뒤 변화가 실패 주입 때문인지 알 수 없습니다. 배포·트래픽 이벤트·정기 배치가 없는 시간에 최소한 성공률, 지연, saturation, queue depth, dependency error를 확인합니다. baseline은 "정상"을 선언하는 장식이 아니라 중단 기준을 정하는 입력값입니다. 예를 들어 p95가 이미 목표의 90%라면 지연 실험을 미루는 편이 안전합니다.

## 실패 주입의 종류를 이해하기

가장 낮은 위험의 실패 주입은 application 내부의 dependency mock 또는 proxy입니다. 특정 요청에만 500 오류, timeout, 잘못된 형식의 응답을 돌려주고 client가 올바르게 처리하는지 봅니다. 이는 CI나 integration test에서도 가능하며, 외부 provider의 실제 계정을 건드리지 않습니다. 다만 실제 DNS·connection pool·TLS·network retry 동작까지 재현하지 못하므로, 환경 계층의 문제를 찾는 데는 한계가 있습니다.

network 계층에서는 지연, packet loss, connection reset, DNS 응답 실패, 특정 egress 차단을 주입할 수 있습니다. 여기서 중요한 점은 "네트워크가 끊김"도 여러 모습이라는 사실입니다. 연결을 새로 만들 때만 실패하는지, 이미 열린 connection이 중간에 끊기는지, 응답만 느린지에 따라 client library의 행동이 달라집니다. timeout과 retry를 검증하려면 어떤 형태의 실패를 만들었는지 정확히 기록해야 합니다.

자원 계층에서는 CPU throttling, memory 압박, disk fullness, file descriptor 고갈, connection pool 소진을 다룹니다. CPU 사용률이 높다고 항상 오류가 나지는 않지만 GC pause, scheduler 대기, queue 적체로 지연이 길어질 수 있습니다. disk가 가득 찬 경우에는 log 기록, temporary file, database WAL, image pull이 서로 다른 방식으로 실패합니다. 이런 실험은 다른 workload에 퍼질 위험이 있으므로 namespace·container·한 인스턴스처럼 작은 경계에서 시작해야 합니다.

프로세스와 인프라 계층에서는 instance 종료, pod 재시작, node drain, cache replica 장애, message consumer 중지를 다룹니다. 이 실험은 autoscaling·readiness·leader election·replication·backlog 처리를 확인하는 데 유용합니다. 하지만 한꺼번에 여러 인스턴스를 죽이면 원인을 알기 어렵고 실제 장애와 구별하기도 힘듭니다. 한 번에 한 변수만 바꾸고, 복구 완료를 확인한 뒤 다음 변수를 다루는 것이 재현 가능한 품질 활동에 가깝습니다.

## 구체적 업무 예시: 주문 API의 결제 provider 지연

온라인 주문 서비스가 외부 결제 provider에 승인 요청을 보낸다고 가정해 보겠습니다. 사용자는 결제 버튼을 한 번 눌렀지만 browser가 응답을 받기 전에 network가 느려질 수 있습니다. application이 3초 timeout을 두고 재시도하면 provider는 첫 요청을 이미 처리했을 수 있습니다. 이때 단순히 "timeout이면 실패"라고 표시하면 사용자는 다시 결제하고, "재시도하면 성공"이라고만 하면 중복 승인이 생길 수 있습니다.

실험 가설은 다음처럼 세울 수 있습니다. provider 응답을 4초 지연시키되 실제 승인 결과는 정상으로 둔다. 주문 API는 request ID와 idempotency key를 provider에 전달한다. timeout이 발생하면 주문을 확정이나 실패로 단정하지 않고 `payment_pending` 상태로 저장한다. 사용자가 새로 고침하면 같은 결제 요청을 다시 보내지 않고 상태 조회를 수행한다. provider webhook 또는 조회 API가 승인 결과를 돌려주면 주문 상태는 한 번만 `paid`가 된다. 이 가설의 성공은 HTTP 200만으로 판단하지 않습니다.

관찰 지표에는 pending 주문 수, 같은 idempotency key의 provider 호출 수, 중복 승인 수, 결제 상태 전이 시간, 사용자가 본 오류 화면 비율이 포함됩니다. 중단 기준은 실제 승인 실패율이 허용 수준을 넘거나 pending backlog가 처리 용량을 넘는 경우처럼 사용자에게 손해가 생길 조건으로 정합니다. 실험 중에는 결제 담당자와 on-call이 대시보드·rollback 절차를 볼 수 있어야 하며, 고객에게 영향을 주는 production 실험이라면 소수의 내부 계정이나 canary traffic으로 제한합니다.

실험 후 발견할 수 있는 결함은 다양합니다. client timeout은 3초인데 load balancer timeout이 2초라서 application 로그가 남지 않을 수 있고, queue consumer가 재시작 뒤 같은 이벤트를 다시 처리할 수 있습니다. webhook signature 검증이 실패하면 pending이 영구히 남을 수도 있습니다. 중요한 것은 provider가 느렸다는 사실이 아니라, 시스템이 불확실한 상태를 데이터 모델·UI·재처리 절차에서 어떻게 표현했는지입니다. 이 결과를 기능 테스트, 모니터링 경보, 운영 runbook에 반영해야 다음 배포에도 효과가 남습니다.

## 안전 장치: blast radius와 중단 기준

blast radius는 실험으로 영향을 받을 수 있는 범위입니다. production에서 실험을 하려면 가장 먼저 이 범위를 줄입니다. 전체 region 대신 하나의 availability zone, 전체 사용자 대신 내부 계정, 모든 pod 대신 label이 붙은 canary pod, 모든 요청 대신 header가 있는 소량 요청처럼 경계를 정합니다. 격리할 수 없거나 영향 범위를 측정할 수 없다면 아직 production 실험을 할 준비가 되지 않은 것입니다.

중단 기준은 "문제가 생기면 멈춘다"보다 구체적이어야 합니다. 주문 성공률이 baseline 대비 0.2%p 이상 떨어짐, p99가 3초를 넘음, customer support alert가 발생함, queue lag가 10분을 넘음, on-call이 원인을 설명할 수 없음처럼 수치와 행동을 연결합니다. 기준을 실험 전에 정해야, 실험 중에 결과를 좋게 해석하려는 편향을 막을 수 있습니다. 자동 중단이 가능하면 좋지만, 수동 중단 권한을 가진 사람과 rollback 명령도 사전에 확인해야 합니다.

실험 시간도 안전 장치입니다. 새 배포 직후, 대규모 이벤트, 데이터 migration, 이미 경보가 울리는 시간에는 카오스 실험을 하지 않습니다. support·SRE·product owner가 대응할 수 있는 시간에 진행하고, 실험 시작과 종료를 관련 채널에 남깁니다. 이 공지는 실패를 숨기지 않기 위한 것이지, 실험을 실제 장애처럼 취급하기 위한 것은 아닙니다. 실험 ID와 time window가 있으면 경보를 무시하지 않고도 원인을 빠르게 분류할 수 있습니다.

## 테스트 자동화와 연결하는 방법

모든 실험을 사람이 dashboard를 보며 실행할 필요는 없습니다. 낮은 위험의 failure injection은 integration test에 넣을 수 있습니다. 예를 들어 HTTP client가 connection reset·429·timeout을 받았을 때 재시도 횟수가 제한되는지, circuit breaker가 열린 뒤 fallback 응답이 나오는지, idempotency key가 유지되는지 검증합니다. 이 테스트는 빠르게 반복되므로 변경으로 복원력 계약이 깨지는 회귀를 잡는 데 좋습니다.

반면 autoscaling, DNS, node replacement, 실제 queue backlog처럼 환경 의존성이 큰 실험은 별도 staging workflow가 더 적합합니다. CI job이 실험 환경을 만들고, baseline을 수집하고, 하나의 fault를 넣고, SLI와 로그를 artifact로 남긴 뒤 정리하도록 구성할 수 있습니다. 단, 자동화되었다고 위험이 사라지는 것은 아닙니다. target account·namespace·시간 제한·cleanup을 코드에 고정하고, production credential을 테스트 runner에 넓게 주지 않아야 합니다.

QA 관점에서 중요한 것은 결함 보고의 형태입니다. "실험 중 오류가 났다"보다 "cache 연결을 30초 차단했을 때 search API의 p99는 4.2초로 증가했고, fallback 대신 500을 반환했다. 기대 계약은 최근 결과를 읽기 전용 cache에서 제공하는 것이었다"처럼 조건·관찰·기대·영향을 남겨야 합니다. 재현 절차와 trace ID, dashboard 링크, 중단 여부를 포함하면 개발팀이 timeout 값만 바꾸는 대신 정확한 복구 경계를 수정할 수 있습니다.

## 무엇부터 실험할지 우선순위 정하기

실험 후보는 끝없이 많습니다. application instance를 종료할 수도 있고, database 응답을 늦출 수도 있으며, DNS를 실패시킬 수도 있습니다. 그러나 모든 failure mode를 같은 깊이로 다루려 하면 중요한 흐름도 검증하지 못한 채 실험 목록만 커집니다. 우선순위는 낯선 기술의 유행이 아니라 사용자 영향과 변경 빈도에서 정하는 편이 낫습니다. 사용자 수가 많고 실패 비용이 큰 흐름, 외부 의존성이 있으며 오류가 나면 상태가 불확실해지는 흐름, 최근 architecture 변경이 있었던 흐름부터 봅니다.

간단한 위험 표를 만들 수 있습니다. 세로축에는 주문·인증·검색·알림·정산 같은 사용자 흐름을 두고, 가로축에는 영향도·발생 가능성·탐지 가능성·복구 난이도를 둡니다. 예를 들어 검색 cache가 느려지면 결과가 늦게 보일 수 있지만 주문 데이터가 사라지지는 않습니다. 반면 결제 provider timeout은 사용자가 결과를 모르고 중복 시도할 수 있으므로 영향과 복구 난이도가 높습니다. 점수는 정답을 계산하는 도구가 아니라, 팀이 왜 이 실험을 먼저 하는지 합의하는 언어입니다.

변경 기반 우선순위도 유용합니다. 새 region을 열었거나 connection pool library를 바꿨거나 queue consumer를 autoscaling하도록 수정했다면, 해당 경계의 복원력 가설이 이전과 달라졌을 수 있습니다. release checklist에 "새 의존성의 timeout과 fallback은 무엇인가", "장애 시 데이터 상태는 어디서 확인하는가"를 넣으면 카오스 실험이 분기마다 하는 특별 행사 대신 architecture 변경의 검증 일부가 됩니다. QA는 release note에서 위험한 변경을 찾고, SRE·개발팀은 관찰과 rollback을 제공하는 식으로 역할을 나눌 수 있습니다.

반대로 이미 잘 이해한 낮은 위험의 경로를 반복적으로 흔드는 일은 우선순위가 낮습니다. 같은 pod kill 실험이 계속 성공한다면, 다음에는 node drain 중 connection draining이나 dependency timeout 뒤 queue 회복처럼 남아 있는 불확실성을 다뤄야 합니다. 실험 결과가 매번 "성공"인 것은 좋은 소식일 수 있지만, 가설이 너무 약하거나 관찰 지표가 사용자 영향을 보지 못하고 있다는 신호일 수도 있습니다. 성공한 실험도 어떤 위험을 줄였고 어떤 위험은 여전히 남았는지 기록해야 합니다.

## 데이터 정합성을 따로 검증하기

가용성과 데이터 정합성은 같은 문제가 아닙니다. 요청이 빠르게 200을 반환해도, background consumer가 이벤트를 두 번 처리하거나 실패한 상태 전이를 성공으로 표시하면 사용자에게 더 큰 문제가 생길 수 있습니다. 카오스 실험에서는 지연과 오류율뿐 아니라 데이터가 어떤 상태로 남는지를 확인해야 합니다. 특히 결제, 재고, 포인트, 예약, 계정 권한처럼 되돌리기 어렵거나 금전적 영향이 있는 흐름은 별도의 검증 항목이 필요합니다.

예를 들어 주문 생성과 재고 차감이 비동기 메시지로 연결돼 있다면 consumer를 잠시 중지하는 실험을 할 수 있습니다. 이때 성공 조건은 주문 API가 계속 응답한다는 것만이 아닙니다. backlog가 관찰 가능해야 하고, consumer가 재개되면 메시지가 순서·중복·실패 정책에 맞게 처리돼야 하며, 재고가 음수가 되거나 같은 주문이 두 번 차감되지 않아야 합니다. 메시지 ID, business key, 상태 전이 기록을 이용해 실험 전후 데이터를 비교하면 단순한 queue length보다 중요한 결함을 찾을 수 있습니다.

보상 트랜잭션도 신중히 다룹니다. 외부 API 호출 뒤 database 저장이 실패했다고 해서 항상 외부 작업을 취소할 수 있는 것은 아닙니다. 항공권 예약, 결제 승인, 이메일 발송처럼 이미 외부 효과가 발생한 작업은 취소 API의 실패와 지연도 고려해야 합니다. 실험 설계 문서에는 "실패하면 자동으로 되돌린다" 대신 어떤 상태를 pending으로 남기고, 누가 어떤 화면에서 재처리하며, 자동 보상은 어떤 조건에서만 가능한지를 적습니다. 불확실성을 숨기지 않는 데이터 모델이 복원력의 중요한 기반입니다.

테스트 데이터의 경계도 필요합니다. production과 같은 식별자·고객 정보를 실험에 쓰면 관찰 로그와 backup에 민감한 데이터가 퍼질 수 있습니다. staging에서는 가짜 고객과 sandbox provider를 사용하고, production canary가 필요하면 내부 계정 또는 사전에 동의한 제한된 트래픽만 사용합니다. 실험을 안전하게 한다는 것은 시스템 자원만 보호하는 것이 아니라, 사용자 데이터와 업무 결과를 보호하는 일이기도 합니다.

## 경보와 사람의 대응을 함께 시험하기

자동 복구가 있어도 사람의 대응이 필요 없는 서비스는 드뭅니다. 오류율이 증가했을 때 어떤 alert가 울리는지, 누가 이를 받는지, dashboard에서 영향을 어떻게 판단하는지, runbook에 실제 해결 절차가 있는지는 별도의 품질 속성입니다. 장애가 발생한 뒤에야 alert routing이 퇴사한 담당자에게 가거나, runbook 링크에 권한이 없어 열리지 않는 일을 발견하면 복구 시간은 길어집니다. 카오스 실험은 기술 동작뿐 아니라 이 운영 경로를 검증할 기회입니다.

실험 중에는 경보를 끄지 않는 편이 원칙입니다. 다만 experiment ID, target, 시간 창을 함께 기록해 on-call이 실제 외부 장애와 구분할 수 있게 합니다. 경보가 발생하면 담당자는 dashboard에서 SLI, dependency 상태, 배포 이력, 실험 범위를 확인하고 중단 또는 계속 여부를 결정합니다. 이 과정이 지나치게 많은 수동 검색을 요구한다면, 시스템이 복구되더라도 탐지·진단 설계에는 개선할 점이 있습니다.

사후 리뷰는 누군가를 평가하는 회의가 아니라 가설과 실제의 차이를 학습하는 자리여야 합니다. 예상한 fallback이 실행되지 않았는지, 경보는 너무 늦었는지, 중단 기준이 모호했는지, 데이터 확인에 필요한 query가 없었는지 정리합니다. action item은 "복원력을 개선한다"보다 timeout 소유자 명시, dashboard에 pending 상태 추가, alert에 runbook 링크 추가, idempotency test 추가처럼 완료를 판단할 수 있게 쪼갭니다. 다음 실험에서 이 항목이 실제로 해결됐는지 재검증하면 문서가 살아 있는 품질 기록이 됩니다.

## 자주 생기는 오해와 피해야 할 방식

첫 번째 오해는 장애를 크게 만들수록 실험이 더 가치 있다는 생각입니다. 범위가 큰 실패는 실제 고객에게 영향을 줄 가능성이 높고, 동시에 여러 방어선이 반응해 어떤 부분이 문제였는지 알기 어렵습니다. 작은 범위의 단일 failure mode로 가설을 검증한 뒤 단계적으로 넓히는 방식이 더 많은 학습을 제공합니다. production 전체를 끄는 용기는 복원력의 증거가 아닙니다.

두 번째 오해는 도구를 설치하면 카오스 엔지니어링이 시작된다는 생각입니다. fault injection platform은 대상 선택과 실행을 쉽게 하지만, baseline·SLO·중단 기준·rollback·데이터 검증을 대신 정해 주지 않습니다. 반대로 처음에는 proxy rule, 테스트 전용 feature flag, 한 pod의 restart처럼 단순한 수단으로도 좋은 실험을 할 수 있습니다. 도구보다 먼저 필요한 것은 팀이 실패를 안전하게 논의하는 계약입니다.

세 번째 오해는 실패를 발견하면 retry를 늘리면 된다는 생각입니다. retry는 transient failure에 도움이 되지만, 의존 서비스가 과부하일 때는 요청을 증폭시키고 latency를 길게 만들 수 있습니다. retry에는 최대 횟수, backoff, jitter, 전체 deadline, idempotency, circuit breaker가 함께 필요합니다. 실험에서 timeout이 나면 재시도 성공률뿐 아니라 downstream 호출 수, queue 적체, 사용자 대기 시간도 관찰해야 합니다.

마지막으로, 실험을 한 번 성공했다고 복원력이 보장되는 것은 아닙니다. traffic 패턴, dependency version, 배포 방식, team ownership이 바뀌면 기존 가설도 낡습니다. 가장 실용적인 접근은 주요 변경과 실제 incident 뒤에 관련 가설을 다시 보는 것입니다. 이때 실험은 부담스러운 의식이 아니라, 설계의 가정이 아직 맞는지 확인하는 짧은 회귀 테스트가 됩니다.

## 실험 결과를 제품 요구사항으로 되돌리기

카오스 실험에서 얻은 결과가 dashboard 한 장으로 끝나면 다음 기능 개발에서 같은 문제가 돌아옵니다. 발견한 복원력 계약은 사용자 스토리와 비기능 요구사항으로 옮겨야 합니다. 예를 들어 "외부 주소 검증 서비스가 2초 안에 응답하지 않으면 가입은 계속 진행하되, 주소 상태는 검증 대기로 저장한다"는 문장은 개발·QA·기획·지원팀이 함께 이해할 수 있습니다. 단순히 "timeout을 처리한다"라고 적는 것보다 사용자 경험과 데이터 상태가 명확합니다.

이 계약을 테스트 계층에도 나눠 넣습니다. 단위 테스트는 retry backoff 계산과 상태 전이 규칙을, 통합 테스트는 provider timeout과 idempotency key 전달을, staging 실험은 connection pool·경보·queue 회복을 확인합니다. 같은 시나리오를 모든 계층에서 복제하는 것이 아니라 각 계층이 가장 싸고 빠르게 발견할 수 있는 위험을 맡습니다. 이렇게 하면 카오스 실험은 느리고 특별한 테스트가 아니라, 상위 환경에서만 확인 가능한 가정을 보완하는 마지막 안전망이 됩니다.

사용자 지원 문구도 결과물입니다. 처리 중인 결제를 "실패"라고 단정하거나 사용자가 새로 시도하게 만들면 기술적으로 복구해도 신뢰를 잃습니다. pending 상태에서 언제 다시 확인할 수 있는지, 중복 요청을 피해야 하는지, 지원팀이 어떤 request ID로 조사할 수 있는지를 제품 화면과 도움말에 반영합니다. 복원력은 서버 안의 재시도 횟수만이 아니라, 불확실한 상태를 사용자와 팀이 안전하게 다루는 방식까지 포함합니다.

마지막으로 실험의 증거를 짧게 보관합니다. 가설, 실행 날짜, 대상 버전, baseline, 관찰 결과, 결함 링크, 수정 확인, 남은 위험을 남기면 새로운 팀원도 과거 결정을 이해할 수 있습니다. 상세 로그와 대시보드는 보존 정책에 따라 사라질 수 있지만, 왜 이 fallback이 존재하고 어떤 조건에서 중단해야 하는지는 architecture decision이나 runbook에 남아야 합니다. 좋은 카오스 실험은 장애를 연출한 기록이 아니라 다음 변경을 더 안전하게 만드는 설계 지식입니다.

실험을 평가하는 지표도 장기적으로는 바뀝니다. 처음에는 발견한 오류 수가 중요하지만, 시간이 지나면 같은 원인의 incident 재발이 줄었는지, rollback이 필요한 배포가 줄었는지, 새 담당자가 runbook만으로 중단·복구할 수 있는지가 더 의미 있는 신호가 됩니다. 숫자를 목표로 삼아 실험을 많이 실행하기보다, 실제 서비스의 불확실성을 줄이는 결함과 설계 결정을 남기는 데 집중해야 합니다.

## 한계와 적용 기준 Q&A

### Q. 작은 스타트업이나 단일 서비스에도 필요한가요?

A. 대규모 분산 시스템만의 활동은 아닙니다. 외부 결제·메일·storage·DNS처럼 하나라도 실패할 수 있는 의존성이 있다면, 가장 중요한 흐름 하나에서 timeout과 사용자 메시지를 검증할 가치는 있습니다. 다만 전용 플랫폼부터 만들 필요는 없습니다. staging에서 dependency timeout 하나를 주입하고, 기대한 fallback과 경보가 동작하는지 확인하는 작은 실험으로 시작하면 됩니다.

### Q. production에서 하지 않으면 현실적인 검증이 아닌가요?

A. production만 재현하는 신호도 있지만, 안전하지 않은 production 실험은 품질 활동이 아닙니다. 로컬·CI·staging에서 가설과 관찰 경로를 먼저 검증하고, 영향 범위·중단 기준·rollback·담당자가 준비된 경우에만 production canary를 고려합니다. production 실험을 하지 않아도 timeout, 재시도, 자원 제한, failover의 많은 결함을 발견할 수 있습니다.

### Q. 장애를 자주 주입하면 사용자 신뢰를 잃지 않나요?

A. 통제되지 않은 실험은 그렇습니다. 그래서 사용자 영향 SLI와 blast radius가 핵심입니다. 실험은 고객에게 보여 주기 위한 이벤트가 아니라, 실제 장애가 더 큰 범위로 번지기 전에 안전한 조건에서 복구 경계를 확인하는 방법입니다. 안전 장치를 갖추지 못했다면 실험 빈도를 높이는 대신 관찰성과 기본 테스트를 먼저 개선해야 합니다.

## 도입 체크리스트

첫 실험에서는 사용자 영향이 큰 흐름 하나와 의존성 하나만 고릅니다. baseline SLI, 실험 가설, 주입할 실패 형태, 대상 범위, 중단 기준, rollback 방법, 관찰 담당자를 한 문서에 적습니다. staging에서 timeout 또는 오류 응답을 주입해 재시도·fallback·경보·로그를 확인한 뒤, 발견 사항을 기능 테스트와 runbook에 반영합니다. production은 canary·명시적 승인·즉시 중단·사후 리뷰가 모두 가능할 때만 다음 단계로 둡니다.

카오스 엔지니어링의 목적은 시스템을 불안정하게 보이게 하는 것이 아닙니다. 실패가 발생해도 사용자가 무엇을 경험하고, 팀이 무엇을 관찰하며, 어떤 조건에서 자동·수동으로 복구하는지 설명 가능한 계약을 만드는 것입니다. 작은 가설과 좁은 범위에서 시작해 결과를 테스트·설계·운영 문서에 되돌리면, 장애 대응은 기억에 의존하는 일이 아니라 반복 가능한 품질 활동이 됩니다.
