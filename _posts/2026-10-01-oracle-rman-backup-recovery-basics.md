데이터베이스 백업은 파일을 한 번 복사해 두는 일처럼 보이지만, 실제 장애에서는 “어느 시점까지 되돌릴 것인가”, “그 시점의 변경을 재생할 로그가 있는가”, “복구한 데이터베이스가 정말 열리는가”가 함께 결정됩니다. 야간에 데이터 파일을 복사했더라도 낮에 주문이 추가됐고, 디스크가 오후에 손상됐다면 복사본 하나만으로 업무가 원하는 시점까지 돌아갈 수 없습니다. 반대로 백업 파일이 많아도 복구 절차를 실제로 검증하지 않았다면 그 파일이 필요한 순간에 읽히는지 알 수 없습니다.

**RMAN(Recovery Manager, 오라클 데이터베이스 백업·복구 관리 도구)** 은 Oracle Database가 데이터베이스의 물리 백업과 복구를 관리하도록 제공하는 도구입니다. RMAN은 데이터 파일, 제어 파일, 서버 파라미터 파일, 아카이브 로그의 관계를 알고 백업을 만들고, 복구할 때 필요한 파일을 찾아 적용할 수 있습니다. 이 글은 Oracle 공식 Backup and Recovery User's Guide를 바탕으로 RMAN의 개념과 운영 판단 기준을 설명하는 학습 글입니다. 특정 데이터베이스를 직접 백업·복구하거나 복구 시간을 측정한 경험을 주장하지 않습니다.

## 먼저 알아둘 기반 기술: 데이터 파일, 변경 로그, 일관성, 복구 목표

Oracle 데이터베이스의 실제 데이터는 **데이터 파일(datafile)** 에 저장됩니다. 테이블과 인덱스가 논리적으로 보이더라도 운영체제 관점에서는 여러 데이터 파일과 제어 파일, 로그 파일이 함께 데이터베이스의 상태를 구성합니다. **제어 파일(control file)** 은 데이터베이스 이름, 데이터 파일 목록, 백업과 로그에 관련된 핵심 메타데이터를 담는 중요한 파일입니다. **서버 파라미터 파일(server parameter file, SPFILE)** 은 인스턴스를 어떤 설정으로 시작할지 기록합니다. 이 파일들을 데이터 파일과 별개로 보호해야 하는 이유가 여기에 있습니다.

데이터베이스는 변경을 데이터 파일에 즉시 완성된 형태로만 쓰지 않습니다. 변경 내용을 먼저 **redo log(리두 로그)** 에 기록하고, 장애 뒤에도 일관성을 회복할 수 있게 합니다. 로그 스위치가 일어난 뒤 보관용으로 복사된 redo log가 **아카이브 로그(archived redo log)** 입니다. 아카이브 로그 모드에서 이 파일을 보관하면 과거 백업의 데이터 파일에 이후 변경을 순서대로 적용할 수 있습니다. 여기서 “로그가 있다”는 말은 단순한 애플리케이션 감사 로그가 아니라 데이터 블록 변경을 복구에 사용할 수 있는 데이터베이스 로그를 뜻합니다.

**일관성 있는 백업(consistent backup)** 은 복구에 필요한 파일들이 서로 맞는 시점의 상태를 이루는 백업을 말합니다. 데이터베이스를 정상 종료한 뒤 만든 오프라인 백업은 일관성 있는 상태가 될 수 있습니다. 그러나 서비스가 실행 중인 동안에는 데이터 파일마다 디스크에 반영되는 시점이 다를 수 있습니다. RMAN은 온라인 백업을 만들고 필요 시 redo와 아카이브 로그를 사용해 복구 과정에서 일관된 상태로 맞추게 합니다. 그래서 실행 중인 데이터베이스의 데이터 파일을 운영체제 복사 명령으로 제각각 복사하는 방식은 필요한 모드와 절차를 이해하지 않으면 위험합니다.

백업 전략의 출발점은 **RPO(Recovery Point Objective, 장애 때 허용하는 최대 데이터 손실 시간)** 와 **RTO(Recovery Time Objective, 서비스를 복구해 다시 사용할 수 있게 해야 하는 목표 시간)** 입니다. RPO가 24시간이면 하루 전 백업까지만 돌아가도 된다는 의미일 수 있고, RPO가 5분이면 그보다 촘촘한 로그 보호·전송·복구 체계가 필요할 수 있습니다. RTO가 짧으면 백업 파일이 있어도 너무 느린 테이프만으로는 부족할 수 있고, 복원 순서와 저장소 대역폭, 대기 인스턴스까지 고려해야 합니다. RPO와 RTO는 도구 옵션이 아니라 사업·업무와 합의해야 하는 요구 사항입니다.

## RMAN이 관리하는 백업의 종류

**전체 백업(full backup)** 은 선택한 데이터 파일의 모든 사용 블록을 백업하는 방식입니다. 용어가 직관적이지만, 전체 백업 하나가 데이터베이스의 모든 복구 문제를 해결한다는 뜻은 아닙니다. 제어 파일, SPFILE, 아카이브 로그, 암호화 키나 외부 구성도 복구 시 필요할 수 있습니다. 또한 백업이 만든 시점 뒤의 변경을 되살리려면 해당 기간의 로그가 필요합니다.

**증분 백업(incremental backup)** 은 이전 백업 이후 달라진 블록을 중심으로 저장하여 백업 시간과 저장소 사용량을 줄이려는 방식입니다. Oracle RMAN에서 level 0은 증분 전략의 기반이 되는 넓은 백업이고, level 1은 그 뒤 변경을 담는 방식으로 사용할 수 있습니다. level 0을 단순히 운영체제의 full copy와 완전히 같은 의미로 이해하면 복구 계획을 오해할 수 있습니다. 어떤 레벨을 언제 만들고, 복구 시 어떤 순서로 적용하며, 누락된 증분이 있을 때 어떻게 처리할지를 정책으로 정해야 합니다.

**백업 세트(backup set)** 는 RMAN이 백업 조각(piece)에 데이터 블록을 기록하는 논리적 묶음입니다. RMAN은 사용하지 않는 블록을 건너뛰거나 압축을 적용할 수 있어 물리 파일 복사보다 저장 공간을 줄일 수 있습니다. 반면 파일을 운영체제에서 바로 열어 테이블 내용을 보는 용도는 아닙니다. RMAN과 카탈로그 정보가 백업 세트의 위치와 내용을 알고 있어야 복구가 수월합니다. 백업 파일 이름만 복사해 두고 어떤 데이터베이스·시점·암호화 키에 대응하는지 기록하지 않으면 장애 때 찾기 어렵습니다.

**이미지 복사(image copy)** 는 데이터 파일과 비슷한 형태로 복사본을 만드는 방식입니다. 특정 복구·스위치 전략에서 유용할 수 있지만, 어떤 방식이 더 좋다는 일반 답은 없습니다. 저장소 구조, 백업 창, 복구 속도, 운영 도구 연동에 따라 백업 세트와 이미지 복사를 선택합니다. 중요한 것은 이름이 아니라 목표 복구 절차에서 그 형식이 얼마나 빨리 검증 가능하고 관리 가능한가입니다.

## 아카이브 로그가 복구 범위를 바꾸는 방식

데이터베이스가 아카이브 로그 모드라면 redo log가 재사용되기 전에 보관됩니다. RMAN은 데이터 파일 백업을 복원한 뒤 필요한 아카이브 로그를 적용하여 더 최근의 일관된 시점까지 복구할 수 있습니다. 이를 **미디어 복구(media recovery)** 라고 부릅니다. 디스크 손상으로 데이터 파일을 잃었을 때뿐 아니라, 특정 과거 시점으로 되돌리는 불완전 복구(incomplete recovery)에서도 로그의 연속성이 중요합니다.

예를 들어 자정에 level 0 백업을 만들고, 오전부터 오후까지 아카이브 로그가 정상 보관됐다고 가정합시다. 오후 3시에 데이터 파일이 손상되면, 자정 백업을 복원하고 오전부터 3시 전까지의 로그를 적용해 더 최근 시점으로 복구할 수 있습니다. 그러나 오후 1시부터 1시 20분 사이의 아카이브 로그가 삭제되거나 손상됐다면, 그 이후 변경을 연속으로 재생하지 못할 수 있습니다. “오늘 백업을 했으니 안전하다”보다 “복구 목표까지 필요한 로그 체인이 끊기지 않았는가”가 더 정확한 질문입니다.

아카이브 로그 저장소가 가득 차면 데이터베이스가 로그 스위치를 완료하지 못해 서비스에 영향을 줄 수 있습니다. 그렇다고 저장소를 비우기 위해 백업되지 않은 로그를 무작정 지우면 RPO를 깨뜨릴 수 있습니다. RMAN의 보존 정책과 아카이브 로그 삭제 정책은 백업이 다른 저장소에 안전하게 존재하는지, 복구에 필요한 기간이 얼마인지와 연결해 설정해야 합니다. 운영체제의 파일 삭제 명령으로 RMAN이 모르는 상태를 만들면 카탈로그와 실제 파일 상태가 어긋날 수 있습니다.

## RMAN 카탈로그와 제어 파일 기록의 역할

RMAN은 백업 메타데이터를 대상 데이터베이스의 제어 파일에 기록할 수 있습니다. 어떤 백업이 언제 만들어졌고 어떤 파일을 포함하며 어디에 있는지 알아야 `RESTORE`와 `RECOVER`에서 필요한 조각을 찾을 수 있기 때문입니다. 제어 파일의 기록 보존 한계, 제어 파일 자체 손상 가능성, 여러 데이터베이스 백업을 중앙에서 관리할 필요를 고려하면 **Recovery Catalog(복구 카탈로그)** 라는 별도 Oracle 데이터베이스를 쓸 수 있습니다.

복구 카탈로그는 백업 데이터 자체를 대체하는 저장소가 아닙니다. 카탈로그가 있어도 백업 조각과 아카이브 로그가 사라지면 복구할 수 없고, 백업 파일이 있어도 카탈로그만 믿고 제어 파일·DBID(Database Identifier, 데이터베이스 식별자)·암호화 정보를 잃으면 복구 절차가 복잡해질 수 있습니다. 카탈로그를 도입하는 이유는 메타데이터 관리, 기록 보존, 보고와 자동화의 편의성입니다. 카탈로그도 별도 데이터베이스이므로 그 자체의 백업·복구 전략이 필요합니다.

RMAN의 `CROSSCHECK`는 RMAN 기록과 실제 백업 미디어의 존재를 대조하는 작업입니다. 백업이 저장소에서 삭제됐는데 RMAN이 여전히 사용 가능하다고 믿으면 장애 때 잘못된 복구 계획을 세울 수 있습니다. 반대로 파일을 다른 위치로 옮겼거나 외부 저장소에서 가져왔다면 `CATALOG` 작업으로 RMAN에 알려야 할 수 있습니다. 이 명령들은 백업을 새로 만드는 명령이 아니라, “RMAN이 무엇을 알고 있는가”를 실제 상태와 맞추는 관리 작업입니다.

## 업무 예시: 월말 보고 전 데이터 파일 손상 대응

월말 마감 보고가 오전 10시에 시작되고, 전날 밤에는 level 0 백업과 정기적인 아카이브 로그 백업이 있다고 가정해 봅시다. 오전 9시 20분 특정 테이블스페이스의 데이터 파일에 I/O 오류가 발생했습니다. 이때 첫 판단은 “전체 데이터베이스를 가장 오래된 백업으로 되돌릴까”가 아니라, 손상 범위와 업무가 요구하는 복구 시점입니다. 데이터 파일 하나만 손상됐는지, 제어 파일·온라인 로그·다른 파일에도 문제가 있는지, 마지막으로 안전한 아카이브 로그는 언제인지 확인합니다.

개념적인 절차는 다음과 같습니다. 실제 명령과 종료·마운트 상태는 Oracle 버전, 손상 범위, 백업 형식에 따라 달라지므로 운영 환경에서 그대로 실행하면 안 됩니다.

```text
장애 범위와 마지막 정상 시점을 확인한다
해당 데이터 파일의 RMAN 백업과 필요한 아카이브 로그 존재를 확인한다
복구 목표 시점과 허용 데이터 손실을 업무 담당자와 합의한다
격리된 복구 환경 또는 승인된 절차에서 restore와 recover를 수행한다
데이터베이스를 열기 전 무결성·애플리케이션 연결·핵심 조회를 검증한다
장애 원인, 실제 복구 범위, 남은 위험을 기록한다
```

이 흐름에서 DBA가 혼자 “가장 최근까지 복구하겠다”고 결정하면 안 되는 지점이 있습니다. 오후 9시의 잘못된 삭제를 되돌려야 한다면, 단순히 가장 최신 로그를 적용하는 것이 오히려 원하는 결과를 되살릴 수 있습니다. **PITR(Point-In-Time Recovery, 특정 시점으로의 복구)** 은 시간을 기준으로 과거 상태로 되돌리는 방법이지만, 이후의 정상 변경도 함께 잃을 수 있습니다. 어떤 데이터가 복구 대상이고 어떤 최근 변경을 보존해야 하는지는 업무와 기술이 함께 판단해야 합니다.

## 백업 성공보다 중요한 복구 검증

백업 작업 로그에 `Finished backup`이 찍힌 것을 보는 일과 실제 복구 가능성을 검증하는 일은 다릅니다. 최소한 정기적으로 별도 서버 또는 격리된 환경에서 백업을 복원해 데이터베이스를 열 수 있는지 확인해야 합니다. 이때 운영 데이터가 포함될 수 있으므로 접근 권한, 네트워크 분리, 개인정보 마스킹, 복원본 폐기 정책을 함께 지켜야 합니다. 개발자가 아무 제약 없이 운영 백업을 개인 장비에 복원하는 방식은 복구 훈련이 아니라 정보 유출 위험이 될 수 있습니다.

검증 시나리오는 한 가지로 끝내지 않습니다. 전체 데이터베이스를 새 서버에 복원하는 경우, 특정 데이터 파일을 복원하는 경우, 제어 파일 복구가 필요한 경우, 아카이브 로그가 일부 없는 경우처럼 위험 모델이 다릅니다. 모든 경우를 매주 전수로 시험하기 어렵다면 업무 영향과 변경 빈도를 기준으로 우선순위를 정합니다. 예를 들어 백업 저장소를 옮겼거나 암호화 키 관리 방식을 바꿨거나 Oracle 버전 업그레이드를 했다면, 평소와 같은 백업 성공 결과만 보고 넘어가기보다 복원 호환성을 다시 확인해야 합니다.

복구 테스트의 결과에는 걸린 시간, 사용한 백업 시점, 적용된 로그 범위, 실패·우회한 단계, 데이터베이스가 열렸는지뿐 아니라 애플리케이션의 핵심 기능이 가능한지도 남깁니다. 단, 한 번의 테스트 시간을 모든 장애의 RTO라고 단정해서는 안 됩니다. 실제 장애에서는 저장소 손상 범위, 네트워크 부하, 담당자 호출, 승인 절차, 외부 의존성이 다를 수 있습니다. 테스트는 보장 수치가 아니라 현재 계획의 빈틈을 찾는 증거로 사용합니다.

## 보존 정책과 삭제를 설계하는 법

보존 정책(retention policy)은 어느 시점의 백업을 얼마나 오래 유지할지 정하는 규칙입니다. “최근 7일” 같은 기간 기준은 이해하기 쉽지만, 월말·분기 마감처럼 특정 시점 복구가 필요한 업무에서는 충분하지 않을 수 있습니다. 여러 세대의 복구 가능 지점을 유지하는 복구 윈도우 개념을 사용하면, 특정 기간 안의 어떤 시점으로도 돌아갈 수 있도록 필요한 백업과 로그를 남기는 방향으로 생각할 수 있습니다. 정확한 정책 값은 규정, 데이터 변경량, 저장소, RPO에 따라 정합니다.

삭제는 백업의 반대 작업이 아니라 복구 설계의 일부입니다. 저장소 비용을 줄이기 위해 중복 백업을 정리할 수 있지만, 다른 사이트나 오브젝트 스토리지에 복사됐다는 사실만으로 즉시 삭제해도 되는 것은 아닙니다. 복사본이 실제로 읽히는지, 암호화 키와 권한이 남아 있는지, 삭제 지연이나 보존 잠금이 정책과 맞는지 확인해야 합니다. 특히 랜섬웨어나 운영 실수로 원본과 백업이 함께 삭제되는 위험을 고려하면, 서로 다른 권한·계정·위치에 복구 사본을 두는 전략을 검토할 수 있습니다.

## 압축·암호화·저장소 복사본의 판단 기준

데이터베이스 백업은 대개 크기 때문에 압축을 검토하게 됩니다. **백업 압축**은 저장소 사용량과 전송량을 줄일 수 있지만, 백업과 복원 시 CPU를 더 사용할 수 있습니다. 그래서 “저장소가 싸니 압축하지 않는다” 또는 “파일이 작으니 항상 좋다”로 결정하지 않습니다. 백업 창에 CPU 여유가 있는지, 복구 때 압축 해제가 RTO에 어떤 영향을 주는지, 네트워크를 넘어 복사할 때 병목이 어디인지 측정·검토해야 합니다. 특히 대규모 데이터베이스는 압축 수준 하나를 바꾸는 일도 백업 서버와 저장소의 부하 패턴을 바꿀 수 있습니다.

**백업 암호화**는 백업 미디어를 읽을 수 있는 사람이 곧 데이터베이스 내용을 읽을 수 있는 위험을 줄입니다. 하지만 암호화 키나 지갑(wallet)을 잃으면 정상적인 백업 파일도 복원하지 못할 수 있습니다. 키를 데이터베이스 서버와 같은 디스크, 같은 관리자 계정, 같은 백업 작업에만 두면 장애나 권한 침해가 한 번에 둘을 가져갈 수 있습니다. 누가 키를 복구할 수 있는지, 키를 회전했을 때 오래된 백업은 어떻게 읽는지, 비상시에 필요한 접근 승인은 무엇인지가 백업 정책의 일부가 됩니다.

백업을 다른 저장소로 복사하는 일도 복구 가능성을 높일 수 있습니다. 예를 들어 운영 서버와 다른 장애 도메인에 사본을 두면 한 데이터센터의 화재·스토리지 장애·관리자 실수에서 거리를 둘 수 있습니다. 그러나 동기화 도구가 손상되거나 암호화된 파일을 그대로 복제했다면 “두 개가 있으니 안전하다”는 결론이 성립하지 않을 수 있습니다. 복사본의 생성 시점, 완료 여부, 접근 권한, 변경 불가능 보관 기능, 실제 읽기 검증을 구분해 기록합니다.

**3-2-1 원칙**은 일반적으로 데이터 사본을 여러 개 두고, 서로 다른 매체를 쓰며, 적어도 하나는 다른 위치에 두라는 백업 사고방식입니다. 모든 환경에 기계적으로 적용할 숫자 규칙이라기보다, 한 종류의 장애가 모든 사본을 함께 망가뜨리는지 묻는 질문으로 쓰는 편이 좋습니다. 같은 관리자 자격 증명으로 삭제 가능한 동일 클라우드 버킷 두 개는 위치가 달라도 권한 관점에서 같은 실패 지점을 공유할 수 있습니다.

## 복구 런북에 남겨야 하는 정보

**런북(runbook)** 은 반복되거나 긴급한 운영 작업의 절차와 판단 기준을 적은 문서입니다. RMAN 명령만 순서대로 적은 런북은 충분하지 않습니다. 복구를 시작할 권한이 있는 사람, 업무 담당자에게 RPO·RTO 영향을 알리는 방법, 백업 저장소와 키 관리 시스템 접근 경로, Oracle 홈과 버전, DBID, 파일 경로, 네트워크 분리 상태를 함께 남겨야 합니다. 담당자가 휴가이거나 장애가 야간에 발생해도 다른 사람이 같은 판단을 할 수 있어야 합니다.

런북에는 중단 조건도 필요합니다. 예를 들어 복구 목표 시점이 업무 담당자의 승인 없이 과거로 크게 이동하는 경우, 필요한 아카이브 로그가 없어서 더 오래된 시점으로만 가능한 경우, 복구 대상이 운영 시스템인지 격리된 조사본인지에 따라 다음 행동이 달라집니다. 기술자가 복구 명령을 실행하기 전에 “이 복구가 잃게 되는 거래는 무엇인가”를 확인하는 단계가 있어야 합니다. 빠른 실행이 중요한 사고에서도 잘못된 시점으로 데이터베이스를 여는 비용은 매우 클 수 있습니다.

복구 뒤 검증 항목도 런북에 넣습니다. 인스턴스가 시작되고 데이터베이스가 열렸는지, 필요한 테이블스페이스가 온라인인지, 주요 사용자 계정으로 연결되는지, 핵심 조회와 쓰기 작업이 가능한지, 백그라운드 작업이나 인터페이스가 예상치 않게 재처리되지 않는지 확인합니다. 단순한 `SELECT 1` 성공은 데이터베이스 엔진이 응답한다는 신호일 뿐 업무 복구 완료의 증거가 아닙니다. 반대로 모든 업무 기능을 한 번에 재현할 수 없다면 가장 영향이 큰 거래부터 우선순위를 정합니다.

## Data Guard와 백업의 관계를 혼동하지 않기

Oracle Data Guard는 주 데이터베이스의 변경을 대기 데이터베이스에 전송하고 적용해 가용성과 재해 복구에 쓰는 기술입니다. 대기 데이터베이스가 있다고 해서 RMAN 백업이 필요 없어지는 것은 아닙니다. 논리적 오류, 잘못된 삭제, 데이터 손상, 운영 실수는 변경 전송을 통해 대기 측에도 전달될 수 있습니다. 반대로 RMAN 백업만 있다고 해서 짧은 RTO를 만족하는 대기 전환 체계가 되는 것도 아닙니다.

두 기술은 서로 다른 질문에 답합니다. Data Guard는 주로 장애 시 서비스 전환과 최근 변경 보존에 도움을 줄 수 있고, RMAN은 과거 시점 복구와 장기 보존, 별도 복원 검증의 기반이 됩니다. 실제 설계에서는 redo 전송 지연, 대기 데이터베이스의 역할 전환 절차, 백업을 어느 위치에서 수행할지, 장애 때 어떤 사본을 복구 원본으로 할지를 함께 정합니다. 특정 기능을 도입했다는 사실보다, 어떤 장애에서 어느 순서로 사용할지 시나리오를 문서화하는 일이 더 중요합니다.

## 백업 정책을 변경할 때의 안전한 접근

백업 주기, 압축, 보존 기간, 저장소 위치, 암호화 옵션을 바꾸는 작업은 운영 영향이 큰 변경입니다. 처음부터 기존 정책을 지우고 새 정책만 남기기보다, 제한된 기간에 새 백업이 기대한 위치와 형식으로 생성되는지 확인하고 복원 시험을 합니다. 두 정책의 중복 기간은 저장소 비용이 들지만, 변경 오류로 복구 사본이 없는 공백을 만드는 위험을 줄일 수 있습니다. 다만 중복 기간과 폐기 날짜를 명확히 정하지 않으면 비용과 혼란만 커질 수 있습니다.

자동화도 결과를 확인해야 합니다. 스케줄러가 RMAN 명령을 실행했다는 로그만이 아니라 백업 크기가 비정상적으로 작지 않은지, 아카이브 로그 백업이 지연되지 않았는지, 보존 정책이 예상보다 최신 백업을 삭제하지 않았는지, 원격 복사가 완료됐는지를 점검합니다. 알림은 실패 한 건만 보내는 방식보다, 마지막 성공 시각과 복구 윈도우를 벗어나는 징후를 보여 주는 방식이 유용할 수 있습니다. 그러나 알림이 너무 많으면 실제 실패도 묻히므로 담당자가 대응 가능한 기준으로 다듬어야 합니다.

## 장애 전 연습이 남기는 운영 자산

복구 훈련은 기술 명령을 익히는 시간인 동시에 조직의 의존성을 찾는 시간입니다. 백업 저장소 접근 권한을 가진 사람이 한 명뿐인지, 암호화 키의 비상 접근 절차가 실제로 작동하는지, DNS나 애플리케이션 설정을 누가 복구하는지, 업무 담당자가 어떤 조회 결과를 정상으로 판단하는지 훈련에서 드러납니다. 이 정보는 RMAN 출력만으로는 얻을 수 없습니다.

훈련 후에는 실패를 숨기지 말고 런북을 고칩니다. 필요한 로그가 예상 위치에 없었다면 보관 정책을, 복원 서버 용량이 부족했다면 인프라 계획을, 복구 뒤 앱이 연결되지 않았다면 연결 정보와 비밀 관리 절차를 보완합니다. 다음 훈련에서 같은 문제를 다시 발견하지 않는 것이 백업 체계가 성숙하는 가장 현실적인 증거입니다. 이렇게 쌓인 기록은 새 DBA가 투입됐을 때도 복구 절차의 이유를 이해하게 해 줍니다.

복구 계획의 마지막 질문은 ‘어디까지 복구할 수 있는가’가 아니라 ‘복구한 뒤 누가 어떤 기준으로 서비스를 재개한다고 선언하는가’입니다. 기술 검증과 업무 검증의 책임을 나누고 연락 방법을 남겨 두면, RMAN 백업은 파일 모음이 아니라 실제 복구 능력이 됩니다.

## 오늘 바로 확인할 백업 질문

현재 환경에서 가장 먼저 답할 질문은 다섯 가지입니다. 최근 성공한 RMAN 백업은 정확히 언제인가, 그 백업에 제어 파일과 필요한 아카이브 로그가 포함됐는가, 백업 사본은 운영 장애와 다른 위치에 있는가, 암호화했다면 키를 누가 복구할 수 있는가, 최근에 실제 복원 시험을 한 날짜는 언제인가입니다. 이 질문에 명확히 답하지 못한다면 새 옵션을 추가하기보다 현황 목록과 복구 훈련 일정을 만드는 일이 먼저입니다.

백업 모니터링 화면에서 녹색 성공 표시가 보이더라도, 저장소 여유 공간과 아카이브 로그 증가량, 마지막 복사 성공 시각, 보존 정책 변경 이력을 함께 봅니다. 데이터베이스 용량이 늘거나 업무 시간이 바뀌면 기존 주기가 더는 RPO를 만족하지 않을 수 있습니다. 정책을 분기마다 검토하고 중요한 시스템 변경 뒤에는 복구 시험을 다시 수행하면, 백업은 오래된 설정이 아니라 현재 업무를 보호하는 운영 통제가 됩니다.

결국 백업의 신뢰도는 파일 수가 아니라 검증된 복구 경로의 명확성에서 나옵니다.

복구 범위와 의사 결정 권한을 미리 합의하면, 장애 중의 불필요한 추측과 재작업도 줄일 수 있습니다. 백업 담당자, 인프라 담당자, 업무 확인자가 같은 기록을 보면 복원 과정의 책임 경계가 더 분명해집니다.

준비가 핵심입니다.
