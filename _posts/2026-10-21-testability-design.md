기능은 정상인데 테스트만 어렵다는 말은 대개 테스트 코드의 기술 부족을 뜻하지 않습니다. 현재 시각을 코드가 직접 읽고, 결제·메일·파일·데이터베이스를 한 함수에서 바로 호출하고, 실패 결과를 로그에만 남기고, 내부 상태를 바꾼 뒤 무엇이 일어났는지 알 방법이 없다면 테스트는 자연스럽게 느리고 불안정해집니다. 이런 성질을 **테스트 용이성(testability)** 이라고 합니다. 테스트 용이성은 테스트 전용 기능을 덧붙이는 일이 아니라, 변경했을 때 동작을 관찰하고 위험을 좁은 범위에서 확인할 수 있게 만드는 설계 품질입니다.

좋은 테스트 용이성은 단위 테스트 개수를 늘리는 지름길이기도 하지만, 장애 분석과 코드 리뷰에도 도움을 줍니다. 입력, 의존성, 시간, 상태 변화, 결과가 분명하면 사람이 코드를 읽는 비용도 줄어듭니다. 반대로 private 메서드를 억지로 공개하거나 운영 API에 테스트 전용 우회 기능을 만드는 것은 해결책이 아닐 수 있습니다. 이 글은 어떤 구조가 테스트를 어렵게 만드는지, 의존성을 어떻게 경계로 바꾸는지, 시간·난수·비동기를 어떻게 다루는지, 언제 통합 테스트를 남겨야 하는지를 실무 예시로 정리합니다.

## 먼저 알아둘 기반 기술

**테스트 더블(test double)** 은 실제 협력 객체를 대신하는 테스트용 구현을 통칭합니다. 미리 정한 값을 돌려주는 **stub**, 호출 여부와 인자를 기록하는 **spy**, 실제와 비슷하게 동작하지만 통제 가능한 **fake** 가 대표적입니다. 결제 서비스가 응답을 늦게 주거나 비용을 발생시킬 수 있을 때, 주문 규칙 자체를 검증하는 테스트에서 실제 결제망까지 연결할 필요는 없습니다. 반대로 결제 요청의 서명·상태 코드·웹훅 형식이 맞는지는 별도 통합 또는 계약 테스트로 검증해야 합니다.

**의존성(dependency)** 은 코드가 일을 끝내기 위해 필요로 하는 다른 대상입니다. 데이터베이스, HTTP API, 파일 시스템뿐 아니라 현재 시간, 난수 생성기, 환경 변수, 프로세스 종료, 메시지 큐도 의존성입니다. 함수가 이들을 직접 새로 만들거나 전역에서 읽으면 테스트는 같은 결과를 만들기 어렵습니다. 호출하는 쪽에서 필요한 협력자를 전달하거나, 좁은 인터페이스 뒤로 감싸면 테스트는 통제 가능한 구현을 넣을 수 있습니다.

**관찰 가능성(observability)** 은 내부 상태를 무제한으로 노출하는 뜻이 아닙니다. 외부에서 결과와 중요한 사건을 보고 “무슨 일이 있었는가”를 추론할 수 있는 성질입니다. 주문 취소 함수의 좋은 관찰 결과는 `true` 하나보다 취소됨·이미 취소됨·권한 없음·결제 환불 실패 같은 의미 있는 결과일 수 있습니다. 운영에서는 구조화 로그·메트릭·trace가, 테스트에서는 반환값·저장된 상태·발행한 이벤트가 이 역할을 합니다.

## 테스트가 어려운 코드의 공통 모습

다음과 같은 주문 만료 처리를 생각해 봅시다. 함수 안에서 직접 현재 시간을 읽고, DB를 조회하고, 메일 API를 호출하고, 실패하면 콘솔에만 기록합니다. 호출자는 성공·실패의 차이를 거의 알 수 없습니다.

```javascript
async function expireOrders() {
  const orders = await database.query('select * from orders');
  for (const order of orders) {
    if (order.expiresAt < new Date()) {
      await database.cancel(order.id);
      await mailClient.send(order.email, '주문이 만료되었습니다');
    }
  }
}
```

이 코드는 실제로 동작할 수 있지만, 테스트에서 여러 질문이 엉킵니다. 자정 경계의 주문은 어떤가, DB 오류가 나면 다음 주문은 처리되는가, 메일 전송 실패 뒤 취소 상태는 유지되는가, 한 번 실행한 테스트 데이터가 다음 테스트에 남는가, 테스트 실행 시각에 따라 결과가 달라지는가를 한 번에 풀어야 합니다. DB·메일이 실제로 연결되면 속도와 비용도 커집니다. 그래서 작은 규칙 하나를 확인하려 해도 거대한 통합 환경이 필요해집니다.

문제는 `new Date()` 한 줄이나 SQL 자체가 아닙니다. 업무 규칙, 저장소 접근, 외부 알림, 실패 처리, 반복 제어가 한 단위에 섞여 있다는 점입니다. 테스트 용이성은 모든 코드를 작은 함수로 자르는 종교가 아니라, 서로 다른 실패 방식과 다른 속도로 검증해야 할 책임을 분리하는 일입니다.

## 먼저 결과와 경계를 정한다

개선은 mock 라이브러리부터 고르는 것으로 시작하지 않습니다. 먼저 함수가 어떤 결정을 하는지 문장으로 씁니다. 예를 들어 “현재 시각보다 만료 시각이 이른, 아직 취소되지 않은 주문은 만료 대상이다”는 순수한 규칙입니다. 이 규칙은 DB나 메일을 모르므로 입력 객체와 기준 시각만으로 빠르게 테스트할 수 있습니다.

```javascript
function shouldExpire(order, now) {
  return order.status === 'PENDING' && order.expiresAt <= now;
}
```

그 다음 “대상을 찾는다”, “상태를 바꾼다”, “알림을 보낸다”는 협력 작업으로 나눕니다. 이때 반환값도 설계합니다. 단순히 예외를 던지거나 성공 여부만 주면 호출자는 재시도·알림·감사의 판단을 하기 어렵습니다. 처리한 주문 수, 건너뛴 이유, 재시도 대상 같은 결과를 업무 언어로 정의하면 테스트도 그 계약을 검증할 수 있습니다.

경계를 나눈다고 외부 의존성이 사라지는 것은 아닙니다. DB와 메일은 여전히 필요합니다. 다만 도메인 규칙 테스트에서는 통제 가능한 fake를 쓰고, 저장소 구현 테스트에서는 테스트 DB를 쓰고, 실제 메일 서비스와의 계약은 좁은 시나리오만 실제 또는 샌드박스에서 확인할 수 있습니다. 빠른 피드백과 실제 연동 신뢰를 같은 테스트 한 개에 억지로 넣지 않는 것이 핵심입니다.

## 의존성 주입은 교체보다 의도를 드러낸다

의존성 주입(dependency injection)은 객체를 생성자·함수 인자·프레임워크 컨테이너로 전달하는 방식입니다. 흔히 mock을 넣기 위한 기법으로 소개되지만, 더 중요한 효과는 코드가 무엇에 의존하는지를 선언하게 만드는 데 있습니다. 다음 예시에서 `clock`, `orderRepository`, `notifier`는 기능이 필요로 하는 협력자를 이름으로 보여 줍니다.

```javascript
async function expirePendingOrders({ clock, orderRepository, notifier }) {
  const now = clock.now();
  const orders = await orderRepository.findPendingBefore(now);
  const outcomes = [];

  for (const order of orders) {
    await orderRepository.markExpired(order.id, now);
    await notifier.sendExpired(order);
    outcomes.push({ orderId: order.id, status: 'EXPIRED' });
  }
  return outcomes;
}
```

테스트에서는 `clock.now()`가 항상 같은 시각을 돌려주게 만들고, repository가 준비한 주문만 돌려주며, notifier가 받은 인자를 기록하게 할 수 있습니다. 그러나 모든 클래스를 인터페이스 한 겹으로 감쌀 필요는 없습니다. 날짜 형식 변환처럼 외부 효과가 없는 작은 함수에 주입 구조를 만들면 코드만 복잡해집니다. 불안정하거나 비용이 들거나 느리거나 통제해야 하는 의존성부터 경계로 만듭니다.

또한 인터페이스는 실제 사용에 맞게 좁아야 합니다. `Database`처럼 수십 가지 메서드를 노출하기보다 `findPendingBefore`, `markExpired`처럼 업무가 요구하는 작업을 표현하는 repository가 테스트와 구현 모두 읽기 쉽습니다. 단, 이름만 바꾼 거대한 추상화는 도움이 되지 않습니다. 구현이 서로 다를 수 있는 이유와 호출자가 필요로 하는 계약이 분명할 때 경계가 가치를 가집니다.

## 시간, 난수, 환경 값은 숨은 입력이다

테스트가 월말·자정·서머타임·토큰 만료에서만 깨지는 이유는 시간도 입력인데 코드가 이를 숨기기 때문입니다. 현재 시각을 직접 읽는 대신 `clock`을 통해 받으면, 만료 직전과 만료 직후를 밀리초까지 명시할 수 있습니다. 시간대도 계약으로 정합니다. 저장은 UTC로 하고 표시만 사용자의 시간대로 변환할지, 업무 마감은 특정 지역 시간으로 계산할지를 먼저 결정해야 합니다.

난수도 마찬가지입니다. 추천 순서처럼 정말 무작위여야 하는 기능은 분포 자체를 검사해야 할 수 있지만, 주문 번호·샘플 선택·재시도 지연처럼 재현이 중요한 곳은 seed 또는 난수 생성기를 주입할 수 있습니다. 실패한 테스트의 입력과 seed를 로그에 남기면 다시 같은 조건을 만들 수 있습니다. `Math.random()`을 금지해야 한다는 말이 아니라, 결과를 재현해야 하는 경계에서는 통제할 수 있어야 한다는 뜻입니다.

환경 변수와 전역 설정도 숨은 입력입니다. 테스트가 `process.env`를 직접 바꾸면 병렬 실행 중 다른 테스트와 충돌할 수 있습니다. 시작 시 설정을 읽어 검증한 뒤 명시적인 configuration 객체로 넘기면, 개발·테스트·운영이 어떤 값을 쓰는지 비교하기 쉽고 누락된 설정도 초기에 발견할 수 있습니다. 비밀 값은 테스트 로그에 출력하지 않고, 테스트 전용 안전한 값만 사용해야 합니다.

## 상태 변화는 전후 조건으로 관찰한다

테스트가 private 함수 호출 횟수에만 의존하면 리팩터링이 어려워집니다. 주문 만료 구현에서 반복문을 바꾸거나 SQL을 배치 처리로 합치는 것은 내부 개선일 수 있는데, 메서드 호출 순서를 고정한 테스트는 기능이 같아도 실패합니다. 먼저 사용자와 협력자가 관찰할 수 있는 전후 조건을 봅니다. 만료 대상은 `EXPIRED`가 되었는가, 대상이 아닌 주문은 바뀌지 않았는가, 알림은 정확히 한 번 요청되었는가, 실패 시 어떤 상태가 남는가가 더 중요한 계약입니다.

다만 내부 호출 검증이 항상 나쁜 것은 아닙니다. 결제 승인 전에 권한 확인을 해야 하거나, 멱등 키를 반드시 전달해야 하거나, 삭제 요청이 특정 조건에서 절대 실행되면 안 되는 경우에는 interaction 테스트가 필요합니다. 이때도 “구현 메서드 A 다음 B”보다 “외부 효과를 내는 경계에 어떤 요청이 있었는가”를 검증합니다. spy는 설계된 경계의 계약을 확인할 때 가장 유용합니다.

이벤트도 좋은 관찰 지점이 될 수 있습니다. `OrderExpired` 이벤트에는 주문 식별자, 발생 시각, 사유 같은 최소 사실을 담고, 메일 발송·포인트 회수 같은 후속 처리는 별도 소비자가 담당하게 만들 수 있습니다. 그러나 이벤트를 쓴다고 자동으로 테스트가 쉬워지는 것은 아닙니다. 중복 발행, 순서, 재시도, 실패 시 보관, 소비자의 멱등성을 정의하지 않으면 비동기 문제를 다른 곳으로 옮길 뿐입니다.

## 데이터베이스와 외부 API는 없애지 말고 층을 나눈다

테스트 더블만으로 저장소 SQL, 인덱스, 트랜잭션 격리, 제약 조건이 맞는지는 알 수 없습니다. 그래서 데이터베이스를 쓰는 코드는 실제와 가까운 테스트 환경에서 좁게 검증해야 합니다. migration을 적용한 빈 DB에서 repository의 조회·저장·rollback·제약 조건을 테스트하고, 각 테스트가 만든 데이터를 트랜잭션 rollback·격리된 schema·독립 컨테이너 등으로 정리합니다. 어떤 방식을 쓰든 병렬 실행과 실패 뒤 정리까지 고려해야 합니다.

외부 API도 비슷합니다. 단위 테스트는 fake HTTP client로 timeout·오류 응답·성공 응답을 통제하고, 제공자가 바꾼 필드나 인증 방식은 계약 테스트 또는 정기 통합 테스트로 잡습니다. 실제 고객 계정, 실제 결제, 실제 메일 수신자를 CI마다 쓰면 테스트가 위험해집니다. 테스트 계정·샌드박스·제한된 권한·명확한 정리 절차를 사용해야 합니다.

통합 테스트가 느리다는 이유로 전부 제거하면 안 됩니다. 단위 테스트는 빠른 원인 파악에, 통합 테스트는 우리가 만든 경계가 실제 시스템과 맞는지 확인하는 데 강합니다. 테스트 용이성의 목표는 “DB 없는 테스트만 많이 만들기”가 아니라, 어떤 실패를 어느 층에서 싸고 신뢰성 있게 잡을지 선택할 수 있게 만드는 것입니다.

## 비동기와 재시도는 완료 신호를 설계한다

큐에 메시지를 넣고 바로 반환하는 기능은 “함수가 끝났다”와 “업무가 끝났다”가 다릅니다. 테스트에서 임의의 `sleep`을 넣으면 CI 속도에 따라 flaky해집니다. 대신 처리 완료를 나타내는 이벤트, 상태 조회, promise, 테스트용 대기 조건 중 하나를 명시합니다. 예를 들어 메시지 소비자가 주문 상태를 `PROCESSING`에서 `COMPLETED`로 바꾼다면, 테스트는 그 상태 전이를 정해진 시간 안에 폴링하거나 테스트 큐를 동기 실행으로 대체할 수 있습니다.

재시도도 관찰 가능한 정책이어야 합니다. 몇 번까지, 어떤 오류에만, 어떤 간격으로 재시도하는지 정하지 않으면 테스트는 호출 횟수를 추측하게 됩니다. 실제 시간을 기다리지 않도록 scheduler 또는 delay 함수를 교체할 수 있게 만들고, 영구 오류에는 재시도하지 않는지, 최대 횟수 뒤 실패 상태와 알림이 남는지를 확인합니다. 재시도 자체가 중복 결제를 만들지 않도록 멱등 키와 상태 전이도 함께 검증합니다.

동시성 문제를 단위 테스트 하나로 완전히 증명할 수는 없습니다. 다만 공유 상태를 좁히고, 잠금·원자적 업데이트·유일 제약·멱등 키처럼 사용하는 보호 장치를 코드와 테스트에 드러낼 수 있습니다. 경쟁 조건을 발견한 경우에는 재현 가능한 동기화 지점이나 반복 시험을 만들되, 무작위 반복 횟수만 늘리고 원인을 숨기지 않습니다.

## 한계와 적용 기준 Q&A

### Q. 테스트하기 쉽게 만들면 운영 코드가 느려지지 않나요?

A. 의존성 경계와 명확한 결과 모델 자체는 보통 성능 문제가 아닙니다. 다만 모든 호출을 과도하게 감싸거나, 테스트 편의를 위해 운영 경로에 상세 진단을 무제한 저장하면 비용이 생길 수 있습니다. 성능이 중요한 경로는 측정과 프로파일링으로 판단하고, 관찰 데이터의 양·보존 기간·권한을 제한합니다.

### Q. 테스트 전용 endpoint나 플래그를 만들어도 되나요?

A. 운영 API가 인증을 우회하거나 임의 데이터를 초기화하는 테스트 전용 기능을 갖는 것은 위험합니다. 테스트 환경에만 존재하는 fixture 도구나 관리 인터페이스가 필요할 수는 있지만, 운영 배포물과 네트워크 경계에서 분리하고 접근 권한·감사·삭제 범위를 명확히 해야 합니다. 가능하면 제품의 정상 API와 공개된 관리 계약을 이용해 상태를 만들고 확인하는 편이 안전합니다.

### Q. mock이 많다는 것은 항상 나쁜 설계인가요?

A. 아닙니다. 외부 효과를 분리한 단위 테스트에는 mock이나 fake가 자연스럽습니다. 다만 하나의 테스트가 수많은 mock의 세부 호출 순서를 알아야 한다면, 기능 단위가 너무 많은 책임을 갖거나 경계가 잘못됐을 수 있습니다. 실제 구현과의 차이를 잡는 통합 테스트도 함께 둡니다.

### Q. 기존 레거시 코드에는 어디부터 적용하나요?

A. 전부 재설계하지 말고, 자주 바뀌거나 자주 장애가 나거나 테스트가 느려 배포를 막는 흐름부터 선택합니다. 현재 동작을 보호하는 특성화 테스트를 먼저 만들고, 시간·HTTP·DB 같은 한 의존성만 경계로 빼고, 작은 변경 뒤 회귀를 확인합니다. 테스트가 없는 부분을 한 번에 완벽하게 만들려는 시도는 위험합니다.

## 도입 순서: 다음 변경을 안전하게 만드는 작은 루프

첫째, 실패했을 때 무엇이 달라졌는지 알 수 없는 테스트를 하나 고릅니다. 둘째, 그 기능의 입력·결정·외부 효과·관찰 결과를 표로 적습니다. 셋째, 현재 시각이나 HTTP client처럼 가장 불안정한 의존성 하나를 명시적 인자로 바꿉니다. 넷째, 정상·경계·실패 사례를 빠른 테스트로 만들고, 실제 DB나 API와 만나는 좁은 통합 테스트를 남깁니다. 다섯째, CI에서 이 테스트가 실패했을 때 누가 어떤 정보로 원인을 판단할지 점검합니다.

이 과정은 큰 아키텍처 개편보다 다음 기능 변경의 위험을 줄이는 실용적인 방법입니다. 테스트하기 쉬운 코드는 의존성을 숨기지 않고, 결과를 의미 있게 말하며, 시간과 상태를 통제 가능한 입력으로 취급합니다. 그 결과 테스트 수가 늘어서가 아니라, 변경의 영향과 실패 원인이 더 빨리 보이기 때문에 품질이 좋아집니다.

## 실패 사례로 테스트 용이성을 진단하는 법

테스트가 어렵다는 말은 추상적이므로 최근 실패를 기준으로 질문을 바꾸면 좋습니다. “왜 이 테스트가 CI에서만 깨졌나”라고 묻기보다, 실패를 재현하는 데 무엇이 필요했는지 적어 봅니다. 실행 시각을 알아야 했는지, 다른 테스트가 남긴 데이터를 지워야 했는지, 외부 서비스의 상태를 기다려야 했는지, 로그를 사람이 읽어야만 결과를 알 수 있었는지를 기록합니다. 각 항목은 숨은 입력·공유 상태·불명확한 완료 신호·관찰 불가능한 결과라는 설계 문제로 연결될 수 있습니다.

예를 들어 쿠폰 발급 테스트가 가끔 두 번 발급된다면 우선 재시도 횟수를 줄이는 대신, 요청 식별자와 쿠폰 상태 전이를 관찰하게 만듭니다. 같은 식별자로 다시 요청했을 때 기존 결과를 돌려주는지, 서로 다른 식별자로 동시에 요청하면 유일 제약 또는 원자적 갱신이 지키는지, 실패 뒤 어떤 상태가 남는지 확인합니다. 이때 테스트는 DB의 특정 내부 쿼리 개수보다 발급 결과와 중복 방지 계약을 검증해야 합니다.

오류 메시지도 관찰 지점입니다. 모든 예외를 `처리 실패`로 감싸면 테스트와 운영 모두 원인을 잃습니다. 사용자에게 노출할 메시지는 안전하게 제한하되, 코드 내부에서는 입력 오류·권한 거부·일시적 외부 오류·영구적 데이터 오류를 구분한 오류 유형과 상관관계 식별자를 남길 수 있습니다. 테스트는 오류 문자열 전체가 아니라 유형, 상태 코드, 재시도 가능 여부, 변경되지 않아야 할 상태를 확인하면 문구 수정에 덜 취약합니다.

## API와 UI 경계에서 확인할 것

테스트 용이성은 백엔드 코드에만 해당하지 않습니다. UI가 네트워크 요청·로딩·오류·권한 없음·빈 결과를 구분하지 않고 화면에 바로 섞어 놓으면 브라우저 테스트도 불안정해집니다. 사용자에게 의미 있는 loading, error, empty, success 상태와 접근 가능한 이름을 부여하면 사람이 화면을 이해하기 쉬울 뿐 아니라 테스트도 임의의 CSS selector나 sleep 대신 상태를 기다릴 수 있습니다.

API는 성공 응답뿐 아니라 실패 계약을 명확히 해야 합니다. 동일한 요청에 언제 멱등한 결과를 돌려주는지, 검증 오류는 어떤 필드와 코드로 표현하는지, 비동기 작업은 어떤 식별자로 상태를 조회하는지, 페이지네이션의 정렬 기준은 무엇인지가 문서와 테스트에 있어야 합니다. 프런트엔드는 이 계약을 fake server로 빠르게 검증하고, 백엔드는 요청 검증과 서비스 규칙을 분리해 확인할 수 있습니다. 실제 브라우저와 실제 서버를 잇는 E2E는 이 계약들이 함께 맞는지 보는 소수의 대표 여정으로 남깁니다.

관찰을 위해 DOM에 테스트 전용 임의 속성을 과도하게 붙이면 구현과 테스트가 함께 굳을 수 있습니다. 우선 사용자가 실제로 인식하는 label, role, 제목, 상태 메시지로 찾을 수 있는지 확인합니다. 그래도 안정적인 식별자가 필요한 복잡한 컴포넌트에는 제한된 `data-testid`를 둘 수 있지만, 디자인 세부 구조를 그대로 흉내 내는 selector보다 기능 의미를 나타내는 이름을 사용합니다.

## 코드 리뷰에서 쓸 수 있는 질문

새 기능 PR을 볼 때 다음 질문은 테스트 용이성을 초기에 잡는 데 도움이 됩니다. 이 기능의 결정은 입력만으로 재현 가능한가? 현재 시간·난수·환경 값·네트워크 응답 중 숨은 입력은 무엇인가? 실패하면 호출자는 무엇을 알 수 있는가? 외부 효과는 어디서 한 번만 발생하는가? 재시도와 중복 요청이 오면 어떤 결과가 남는가? 실제 DB·큐·외부 API 계약은 어느 테스트가 맡는가? 이 질문에 답할 수 없으면 테스트 코드가 길어지기 전에 제품 계약을 보완할 기회입니다.

리뷰의 목적은 “mock을 쓰지 말라” 또는 “인터페이스를 더 만들라”는 규칙을 강제하는 것이 아닙니다. 한 함수가 읽기·판단·쓰기·알림·재시도·로그를 모두 책임져 테스트마다 거대한 설정이 필요한지, 변경이 내부 구조를 불필요하게 노출하는지, 예외가 데이터 불일치를 남길 수 있는지를 확인합니다. 작은 기능은 단순한 코드가 가장 테스트하기 쉬울 수 있습니다. 반면 경계가 많은 기능은 의도를 드러내는 구조가 장기적으로 더 단순할 수 있습니다.

테스트 용이성을 이유로 프로덕션 동작을 바꾸는 경우에는 보안도 함께 검토합니다. 테스트 데이터를 지우는 관리자 기능, 시간을 임의로 변경하는 endpoint, 인증을 생략하는 플래그는 편리하지만 운영에 남으면 공격 표면이 됩니다. 테스트 환경 전용으로 분리하거나, 역할 기반 권한·감사 로그·네트워크 차단을 두고, 배포 산출물에 포함되는지까지 검증합니다. 쉬운 테스트와 안전한 운영은 대립하는 목표가 아니라 같은 경계를 명확히 하는 일입니다.

## 테스트 피라미드와 테스트 용이성의 관계

테스트 피라미드는 빠르고 좁은 테스트를 넓게, 느리고 실제 의존성이 많은 테스트를 필요한 만큼 두자는 경험적 모델입니다. 그러나 피라미드 모양을 맞추려고 단위 테스트만 늘리면 의미가 없습니다. 도메인 규칙이 외부 시스템과 얽혀 있다면 fake가 실제 계약에서 멀어질 수 있고, 화면 흐름의 권한·라우팅·브라우저 차이는 단위 테스트로 보이지 않습니다. 테스트 용이성은 각 층을 없애는 것이 아니라, 각 층이 자신의 실패를 빠르고 명확하게 알려 주게 하는 기반입니다.

단위 테스트에서는 결정 함수와 오류 경로가 빠르게 재현되어야 합니다. 통합 테스트에서는 migration, serialization, 트랜잭션, 메시지 형식처럼 실제 구현과의 접점이 검증되어야 합니다. E2E에서는 사용자가 거치는 대표 흐름과 권한, 배포된 설정을 확인합니다. 같은 버그를 여러 층에서 복제하는 대신, 가장 싼 층에서 원인을 잡고 상위 층에서는 조합 오류를 잡는 식으로 역할을 나눕니다. 이 구조가 있으면 테스트 실패를 단순한 빨간 불이 아니라 다음 조사 위치를 알려 주는 신호로 읽을 수 있습니다.

## 변경 비용을 줄이는 설계 신호

테스트를 고칠 때마다 구현보다 fixture와 mock 설정을 더 많이 고쳐야 한다면 경계를 의심해 볼 수 있습니다. 예를 들어 배송비 계산 규칙 하나가 바뀌었는데 DB, HTTP, 메시지 큐, 브라우저를 모두 띄워야만 확인된다면 규칙이 외부 효과 속에 묻혀 있을 가능성이 큽니다. 반대로 단순 표시 문구를 바꿀 때 내부 service mock의 호출 순서가 깨진다면 테스트가 사용자가 아닌 구현을 검증하고 있을 수 있습니다. 실패의 고통은 설계의 결함을 찾는 신호가 될 수 있습니다.

좋은 테스트는 변경의 의도를 말합니다. `만료 주문은 한 번만 취소된다`, `권한 없는 요청은 외부 결제 호출을 하지 않는다`, `일시 오류는 정해진 횟수만 재시도한다`처럼 이름만 읽어도 업무 규칙을 이해할 수 있어야 합니다. 테스트를 통과시키기 위해 조건문을 덧붙이는 대신, 요구사항과 테스트 이름이 어긋나지 않는지 코드 리뷰에서 확인합니다. 테스트가 읽기 쉬우면 새 팀원도 안전하게 변경할 수 있습니다.

테스트 용이성 개선의 효과는 즉시 숫자로 나타나지 않을 수 있습니다. 그러나 CI 대기 시간, flaky 비율, 장애 재현 시간, 코드 리뷰에서 이해에 걸리는 시간, 배포 뒤 되돌림 횟수를 관찰하면 어느 경계가 계속 비용을 만드는지 알 수 있습니다. 수치를 목표로 조작하기보다, 반복되는 실패와 수정 비용을 다음 개선 대상의 근거로 씁니다.

결국 테스트하기 쉬운 구조는 미래의 변경을 위한 여유입니다. 모든 의존성을 가짜로 만들자는 것이 아니라, 실제 효과가 필요한 곳과 빠른 판단이 필요한 곳을 구분하자는 것입니다. 작은 경계 하나를 명확히 하고 그 계약을 테스트로 남기는 습관이 쌓이면, 기능은 계속 바뀌어도 검증을 처음부터 다시 만들 필요가 줄어듭니다.

## 팀의 테스트 자산으로 남기기

테스트 용이성은 개인의 코딩 스타일로 끝나지 않습니다. 새 기능을 만들 때 fixture를 어디에 두는지, 테스트 데이터는 어떻게 초기화하는지, 외부 API fake는 누가 관리하는지, 통합 환경의 실패를 어느 채널에서 보이는지 같은 팀 규칙이 필요합니다. 규칙은 길고 엄격한 문서일 필요가 없습니다. 새 테스트가 반복해서 같은 환경 설정을 만들고 있다면 공용 helper나 fixture로 올리고, helper가 너무 많은 업무 지식을 가지면 다시 기능 단위로 나눕니다.

테스트 실패 보고에는 실패한 요구사항, 재현 입력, 실제와 기대 결과, 관련 로그·trace 식별자, 환경 차이를 남깁니다. 스크린샷이나 콘솔 출력만 저장하면 다음 사람이 원인을 다시 추측해야 합니다. 반대로 민감 데이터와 토큰은 마스킹합니다. 좋은 실패 정보는 테스트를 고치는 시간을 줄이고, 운영 장애와 테스트 장애를 구분하는 데도 도움을 줍니다.

마지막으로 테스트 코드도 제품 코드처럼 정리합니다. 중복된 준비 절차를 줄이고, 불필요한 sleep을 제거하고, 의미 없는 assertion을 삭제하며, 더 이상 존재하지 않는 요구사항의 테스트는 근거를 확인한 뒤 갱신합니다. 통과하는 테스트가 많다는 사실보다, 실패했을 때 믿고 행동할 수 있다는 사실이 더 중요합니다.
