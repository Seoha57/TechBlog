머신러닝 학습 작업이 그래픽 처리 장치 한 개를 필요로 한다고 가정해 봅시다. 단순히 “GPU(Graphics Processing Unit, 그래픽 처리 장치) 한 개”라고 적으면, 어떤 모델의 GPU인지, 메모리가 충분한지, 특정 노드에서만 접근 가능한지, 다른 작업이 이미 사용 중인지를 어떻게 구분할까요? 같은 장치 이름으로 보이더라도 실제 성능과 연결 방식이 다를 수 있고, 사용 권한이나 준비 과정도 다릅니다. Kubernetes(컨테이너를 여러 서버에 배치·관리하는 플랫폼)가 CPU(Central Processing Unit, 범용 연산 처리 장치)와 메모리를 배분하듯 특수 장치를 숫자로만 세는 방식에는 이런 속성을 표현하는 데 한계가 있습니다.

**DRA(Dynamic Resource Allocation, 동적 자원 할당)** 는 Kubernetes에서 그래픽 처리 장치, 가속기, 네트워크 장치처럼 특수한 자원을 워크로드에 연결하는 API(Application Programming Interface, 프로그램이 기능을 요청하는 접점) 체계입니다. 장치 드라이버가 사용 가능한 장치와 속성을 게시하고, 워크로드는 필요한 종류와 조건을 선언합니다. Kubernetes 스케줄러는 조건을 만족하는 실제 장치와 그 장치에 접근할 수 있는 노드를 함께 고른 뒤, 할당 결과를 기록합니다. Kubernetes가 배치하는 컨테이너 묶음은 Pod라고 부릅니다. 핵심 API는 Kubernetes 1.34에서 안정 단계에 도달했습니다. 세부 확장 기능의 성숙 단계는 서로 다르므로 “DRA가 안정됐다”는 말을 모든 선택 기능이 안정됐다는 뜻으로 읽어서는 안 됩니다.

이 글은 Kubernetes 공식 문서와 프로젝트 발표를 바탕으로 DRA의 기본 동작과 설계 판단을 설명합니다. GPU 클러스터를 직접 운영하거나 특정 드라이버의 성능을 측정한 결과가 아닙니다. 실제 적용에서는 클러스터 버전뿐 아니라 사용하는 장치 드라이버와 운영 플랫폼이 필요한 기능을 지원하는지 확인해야 합니다.

## 먼저 알아둘 기반 기술: Pod, 스케줄러, GPU, Device Plugin

**Kubernetes**는 여러 서버에 컨테이너 애플리케이션을 배치하고 유지하는 플랫폼입니다. 컨테이너는 애플리케이션과 실행에 필요한 파일을 묶는 실행 단위이고, **Pod**는 Kubernetes가 함께 배치하고 관리하는 한 개 이상의 컨테이너 묶음입니다. 여러 서버 중 어느 서버에 Pod를 둘지 결정하는 구성 요소가 **스케줄러(scheduler)** 입니다. 스케줄러는 CPU·메모리 요청량, 노드 선택 조건, 이미 배치된 작업 등을 고려해 가능한 노드를 찾습니다. 조건에 맞는 노드가 없으면 Pod는 실행되지 않고 대기할 수 있습니다.

**GPU**는 그래픽 처리 외에도 병렬 계산에 쓰이는 가속 장치입니다. 인공지능 모델 학습이나 추론, 영상 처리, 과학 계산에서 활용됩니다. 같은 “GPU 1개”라도 메모리 크기, 연산 능력, 연결 구조, 드라이버 버전이 다르면 실행 가능 여부가 달라집니다. 예를 들어 모델 파일과 실행 중간값을 저장할 메모리가 24GiB 필요한 작업을 8GiB 장치에 배치하면, 장치 수는 맞아도 작업은 실패할 수 있습니다. GiB는 2의 거듭제곱 기준 용량 단위이며, 여기서는 필요한 장치 메모리를 설명하는 예입니다.

기존 **Device Plugin(장치 플러그인)** 모델에서는 제조사나 플랫폼의 플러그인이 노드의 장치를 Kubernetes에 확장 자원으로 알립니다. Pod는 `vendor.example/gpu: 1`처럼 자원 이름과 수량을 요청할 수 있습니다. 이 방식은 단순한 요구에 잘 맞습니다. 다만 “특정 속성을 가진 장치 한 개”, “같은 종류지만 서로 다른 두 장치”, “특정 설정으로 준비된 장치” 같은 요구는 자원 이름을 여러 개 만들거나 별도 배치 규칙을 결합해야 할 수 있습니다. DRA는 그런 요구를 장치의 속성, 선택 조건, 할당 결과로 표현하려는 방법입니다.

**드라이버(driver)** 는 여기서 장치 정보를 게시하고 할당된 장치를 노드에서 사용할 수 있게 준비하는 소프트웨어를 뜻합니다. Linux(서버에서 널리 쓰는 운영체제) 커널 드라이버만을 가리키는 말이 아니라 Kubernetes의 DRA와 연동하는 구성 요소를 포함합니다. 장치가 클러스터에 물리적으로 꽂혀 있어도 적절한 드라이버가 설치되지 않으면 DRA API만으로는 워크로드가 장치를 사용할 수 없습니다. Kubernetes는 할당을 조정하고, 장치별 구체적인 준비와 노출은 해당 드라이버가 맡는다고 이해하면 됩니다.

## 왜 장치 수량만으로는 부족했나

CPU와 메모리는 양을 숫자로 요청하기 좋습니다. 물론 CPU 종류와 메모리 대역폭도 현실에서는 차이가 있지만, 많은 서비스는 `500m` CPU와 `1Gi` 메모리 같은 양적 요청으로 배치할 수 있습니다. 반면 가속기는 장치별 속성과 토폴로지가 실행 조건이 되는 경우가 흔합니다. 어떤 모델은 특정 연산 기능을 요구하고, 어떤 작업은 높은 장치 메모리나 빠른 장치 간 연결을 요구합니다. 장치 두 개가 있어도 서로 통신하기 어려운 위치라면 필요한 학습 작업을 실행할 수 없을 수 있습니다.

기존 확장 자원 이름을 하드웨어 종류마다 세분화할 수도 있습니다. 예를 들어 큰 메모리 GPU와 작은 메모리 GPU를 다른 자원 이름으로 등록하는 방식입니다. 그러나 메모리, 제조사, 가속 기능, 노드 연결 방식, 드라이버 설정을 조합할수록 이름과 운영 정책이 복잡해집니다. 장치의 실제 목록과 속성을 스케줄러가 볼 수 있게 하고, 워크로드가 필요한 조건을 선언한다면 숫자 하나보다 정확한 선택이 가능합니다. 이것이 DRA가 등장한 주요 배경입니다.

다만 “정확한 선택”이 곧 “성능이 가장 좋은 장치를 자동으로 고른다”는 뜻은 아닙니다. 필요한 속성과 허용 범위를 워크로드가 명시해야 하고, 드라이버가 정확한 장치 정보를 게시해야 합니다. 스케줄러는 선언된 조건 안에서 할당 가능한 장치를 찾습니다. 데이터 위치, 모델 크기, 네트워크 비용, 업무 우선순위를 모두 자동으로 이해하는 최적화 엔진은 아닙니다. 하드웨어 도입 목적과 워크로드의 요구 조건을 먼저 정해야 DRA의 표현력이 실제 가치가 됩니다.

## DRA의 네 가지 핵심 객체

**ResourceSlice(자원 슬라이스)** 는 드라이버가 클러스터에 게시하는 장치 목록입니다. 어떤 자원 풀에 어떤 장치가 있는지, 장치가 어느 노드에서 접근 가능한지, 선택에 사용할 속성과 용량이 무엇인지를 나타냅니다. 사용자 애플리케이션이 보통 손으로 만드는 설정이라기보다 드라이버가 관리하는 가용 장치의 광고라고 생각하면 쉽습니다. 예를 들어 `gpu-a`는 노드 A에서 접근 가능하며 메모리 48GiB를 가진다고 게시할 수 있습니다. 이 정보가 오래되거나 잘못되면 스케줄러의 판단도 잘못될 수 있습니다.

**DeviceClass(장치 클래스)** 는 관리자나 드라이버가 정의하는 장치 종류와 기본 선택 조건입니다. “이 클러스터에서 추론용 GPU라고 부르는 장치 집합”처럼 사용자에게 요청 가능한 범주를 제공할 수 있습니다. 같은 클러스터에 여러 제조사의 장치가 있을 때 운영자는 장치 클래스 이름과 선택 규칙을 팀이 이해하기 쉬운 계약으로 만들 수 있습니다. DeviceClass가 실제 장치를 보관하는 것은 아닙니다. ResourceSlice에 게시된 장치를 어떤 기준으로 선택할지 정의하는 층입니다.

**ResourceClaim(자원 청구)** 은 워크로드가 필요한 장치를 요청하고, 실제 할당 결과를 담는 객체입니다. “추론용 클래스에서 메모리가 충분한 장치를 하나 달라”는 요구를 적고, Kubernetes가 어떤 장치를 배정했는지 상태로 기록합니다. Claim은 장치의 소유와 수명 주기를 명확히 합니다. 하나의 Claim을 여러 Pod가 직접 참조하는 방식은 의도적인 공유에 사용할 수 있지만, 실제 장치를 동시에 써도 되는지는 드라이버와 자원 특성을 확인해야 합니다. Claim을 공유한다는 API 사실만으로 물리 장치의 안전한 동시 사용이 보장되지는 않습니다.

**ResourceClaimTemplate(자원 청구 템플릿)** 은 여러 Pod가 각각 비슷한 장치를 독립적으로 요청해야 할 때 쓰는 틀입니다. 예를 들어 추론 서비스의 복제본 세 개가 각각 별도의 GPU를 사용해야 한다면, 배포 설정에서 템플릿을 참조해 Pod별 Claim을 만들게 할 수 있습니다. 직접 만든 ResourceClaim은 관리자가 수명을 관리하지만, 템플릿에서 생성된 Claim은 해당 Pod의 수명과 연결됩니다. “여러 Pod가 같은 장치를 쓸 것인가, 각 Pod가 다른 장치를 받을 것인가”가 Claim과 Template 선택의 가장 쉬운 기준입니다.

## Pod가 장치를 받기까지의 흐름

첫 단계는 클러스터 관리자가 DRA를 지원하는 드라이버를 설치하고 필요한 DeviceClass를 준비하는 것입니다. 드라이버는 ResourceSlice를 게시해 사용 가능한 장치와 노드 접근성을 알립니다. 두 번째 단계에서 워크로드 담당자는 ResourceClaim 또는 ResourceClaimTemplate에 필요한 DeviceClass와 선택 조건을 선언합니다. Pod 사양은 그 Claim을 참조하고, 장치를 사용할 컨테이너도 해당 Claim을 지정합니다. Pod가 Claim을 참조하지만 컨테이너의 자원 목록에 연결하지 않으면, 기대한 컨테이너에서 장치를 볼 수 없을 수 있습니다.

세 번째 단계에서 스케줄러는 Pod가 갈 수 있는 노드와 Claim을 만족하는 장치를 함께 찾습니다. 장치가 있는 노드가 다른 배치 규칙 때문에 금지돼 있거나, 맞는 장치가 이미 할당돼 있다면 Pod를 그 자리에 놓을 수 없습니다. 조건을 만족하는 조합을 찾으면 Claim 상태에 할당 결과가 기록되고, Pod가 해당 노드로 배치됩니다. 노드에서는 드라이버가 할당된 장치를 컨테이너가 사용할 수 있도록 준비합니다. “Claim이 생성됐다”, “장치가 할당됐다”, “컨테이너에서 장치를 사용할 수 있다”는 서로 다른 단계입니다.

실패 원인을 조사할 때도 이 단계 구분이 중요합니다. Claim 자체가 없으면 참조 오류를, ResourceSlice에 맞는 장치가 없으면 선택 조건이나 드라이버 게시 상태를, 할당은 됐지만 컨테이너가 시작하지 못하면 노드 준비와 드라이버 로그를 봐야 합니다. 무조건 GPU 수만 늘리는 것으로는 조건 불일치나 드라이버 오류를 해결하지 못합니다. 운영 대시보드에는 대기 중인 Pod 수뿐 아니라 Claim 상태, 선택된 DeviceClass, 장치 풀과 노드 정보가 함께 보여야 원인을 좁힐 수 있습니다.

## 업무 예시: 추론 서비스에 장치 메모리 조건 붙이기

사내 문서 검색 서비스가 큰 언어 모델을 사용하며, 한 복제본에 메모리 여유가 있는 GPU 한 개가 필요하다고 가정해 봅시다. 운영자는 추론에 허용할 장치를 DeviceClass로 묶고, 드라이버는 장치별 메모리 같은 속성을 ResourceSlice에 게시합니다. 애플리케이션 팀은 ResourceClaimTemplate에서 필요한 장치 클래스를 요청하고, 게시된 속성 중 모델 실행에 필요한 조건을 선택합니다. 같은 서비스의 Pod가 여러 개 뜨면 각각 독립 Claim을 갖게 합니다. 실제 속성 키와 값은 드라이버마다 다르므로 아래 예시는 문법을 복사해 실행하는 YAML(YAML Ain’t Markup Language, 들여쓰기로 구조를 나타내는 설정 형식)이 아니라 역할을 설명하는 형태입니다.

```text
드라이버: 노드별 장치와 메모리 속성을 ResourceSlice에 게시
운영자: 추론에 허용한 장치 집합을 DeviceClass로 정의
서비스: ResourceClaimTemplate에서 DeviceClass와 필수 조건 요청
Pod: 템플릿을 참조하고 장치가 필요한 컨테이너에 Claim 연결
스케줄러: 조건을 만족하는 장치와 접근 가능한 노드를 함께 선택
노드 드라이버: 배정된 장치를 컨테이너가 사용할 수 있게 준비
```

여기서 메모리 조건은 모델 파일 크기와 같게 정하면 부족할 수 있습니다. 추론 중 중간 계산과 요청 처리에 추가 메모리가 필요하고, 모델 버전이 바뀌면 요구량도 달라집니다. 반대로 모든 작업에 가장 큰 GPU만 허용하면 값비싼 장치가 작은 요청에 묶일 수 있습니다. 업무 담당자는 최소 조건, 허용 가능한 대체 장치, 서비스 복제본 수, 대기 허용 시간을 정해야 합니다. DRA는 그 결정을 클러스터에 표현하는 수단이지 용량 계획을 자동으로 대신하는 장치는 아닙니다.

배포 후 검증도 “Pod가 Running이다”에서 멈추면 안 됩니다. Claim 상태에 의도한 DeviceClass와 장치가 배정됐는지, 컨테이너가 실제 모델을 적재하는지, 부족한 메모리 오류가 나는지 확인해야 합니다. 노드를 교체하거나 장치를 점검할 때는 Pod 재배치와 Claim 수명이 어떻게 이어지는지 살펴봅니다. 새 복제본이 올라오지 않는 상황에서는 모델 서버 로그보다 먼저 장치가 실제로 남아 있는지와 Claim 선택 조건이 너무 좁지 않은지 확인하는 편이 빠를 수 있습니다.

## Device Plugin과 어떤 선택 기준으로 구분할까

Device Plugin의 확장 자원 요청은 단순하고 익숙합니다. 이미 드라이버, 모니터링, 배포 템플릿이 안정적으로 작동하며 워크로드가 “이 종류의 장치 N개”만 요구한다면 굳이 모든 매니페스트를 바꿀 이유가 없습니다. 특히 관리형 Kubernetes 서비스에서 DRA 드라이버 제공이 제한적이라면 API의 이론적 장점보다 현재 지원이 더 중요합니다. 운영팀이 이해하고 복구할 수 있는 경로가 실무에서 더 안전합니다.

DRA는 장치 속성으로 선택해야 하거나 할당을 명시적 객체로 추적해야 할 때 힘을 발휘합니다. 같은 클러스터에 서로 다른 GPU와 네트워크 장치가 있고, 팀마다 필요한 성질이 다른 환경을 생각해 보세요. 애플리케이션이 장치 클래스와 조건을 요청하고, 스케줄러가 실제 장치의 가용성과 노드 위치를 함께 본다면 “수량은 충분한데 엉뚱한 장치에 배치됐다”는 종류의 문제를 줄일 수 있습니다. 단, 선택 조건이 지나치게 촘촘하면 사용 가능한 대체 장치를 배제해 대기 시간이 길어질 수 있습니다.

둘은 동시에 존재할 수도 있습니다. 기존 워크로드는 확장 자원을 계속 쓰고, 새로 필요한 작업만 DRA Claim을 사용하도록 단계적으로 도입할 수 있습니다. 이때 같은 물리 장치를 두 경로가 중복으로 관리하지 않도록 드라이버와 운영 정책을 확인해야 합니다. 장치를 누가 게시하고 어떤 API가 할당 권한을 갖는지 불분명하면, 표면상 여유가 있어 보여도 실제로는 충돌하거나 장치가 누락될 수 있습니다. 마이그레이션은 YAML 문법 교체보다 장치 소유권과 관측 체계를 정리하는 작업에 가깝습니다.

## 공유, 권한, 격리에서 조심할 부분

하나의 ResourceClaim을 여러 Pod가 참조할 수 있다는 설명을 “모든 GPU를 여러 팀이 동시에 안전하게 나눠 쓸 수 있다”는 의미로 확대하면 위험합니다. 특정 장치가 동시 사용을 지원하는지, 드라이버가 자원을 어떻게 격리하는지, 메모리 초과나 오류가 다른 사용자에게 어떤 영향을 주는지는 장치별로 다릅니다. Kubernetes에는 장치 공유와 세분화를 위한 확장 기능도 있지만 기능 단계와 드라이버 구현을 확인해야 합니다. 처음부터 한 장치를 최대한 잘게 나눠 쓰는 목표보다, 한 작업에 어떤 장치가 배정됐는지 명확히 추적하는 것부터 시작하는 편이 좋습니다.

권한도 중요합니다. DeviceClass를 누가 만들고 바꿀 수 있는지, ResourceSlice를 어느 드라이버가 게시하는지, 누가 Claim을 생성하고 상태를 갱신할 수 있는지에 따라 다른 팀의 장치 사용을 간접적으로 바꿀 수 있습니다. **RBAC(Role-Based Access Control, 역할 기반 접근 제어)** 은 Kubernetes 객체에 대한 작업 권한을 역할로 제한하는 방식입니다. 관리자 권한이 필요한 장치 접근 기능을 일반 사용자에게 열지 않도록 하고, DRA 상태 변경 권한도 최소한으로 부여해야 합니다. Kubernetes의 DRA 보안 강화 안내는 이 경계를 별도로 다룹니다.

ResourceSlice에 기록된 장치 속성은 스케줄러의 판단 근거입니다. 따라서 드라이버가 과장된 용량을 게시하거나 오래된 상태를 남기면, 올바른 Claim을 썼어도 잘못된 배치가 나올 수 있습니다. 장치 재시작, 고장, 노드 분리 시 장치 정보가 갱신되는지 확인해야 합니다. 애플리케이션 팀이 Claim 조건만 책임지고 플랫폼 팀이 드라이버 상태를 보지 않는다면 장애 책임이 서로 떠다닐 수 있습니다. 운영 기준에는 드라이버 버전, 장치 재고, Claim 대기 원인, 준비 실패의 담당 범위를 포함하는 것이 좋습니다.

## 설치 전 점검과 작은 도입 순서

첫째, 클러스터 버전과 `resource.k8s.io/v1` API 지원을 확인합니다. 핵심 기능이 안정 단계라고 해도 사용하는 관리형 서비스의 버전과 설정이 다를 수 있습니다. 둘째, 실제 장치에 맞는 DRA 드라이버가 유지 관리되고 필요한 속성을 게시하는지 확인합니다. 셋째, DeviceClass와 Claim을 만들 권한을 정하고, 팀이 사용할 수 있는 클래스 이름과 의미를 문서화합니다. 넷째, 한 종류의 작업과 한 장치 풀을 골라 기존 배치 방식과 결과를 비교합니다. 이 단계에서 성능 수치를 꾸며 내기보다 원하는 장치가 선택되고 실패 원인을 추적할 수 있는지를 확인해야 합니다.

작은 검증에서는 성공뿐 아니라 실패도 만들어 봐야 합니다. 존재하지 않는 DeviceClass를 요청하면 어떤 상태와 이벤트가 나오는지, 너무 높은 메모리 조건을 걸면 Pod가 어떻게 대기하는지, 드라이버가 중단되면 새 Claim이 어떻게 처리되는지를 확인합니다. 실제 업무에서는 자원 부족 상황이 항상 생길 수 있으므로, 대기 시간과 사용자에게 보일 오류를 미리 정해 두는 편이 좋습니다. 이런 검증은 실제 클러스터에서 수행해야 하며, 이 글은 실행 결과를 보고하는 문서가 아닙니다.

확장 단계에서는 장치별 비용과 작업 우선순위를 함께 봅니다. 높은 메모리 장치가 필요한 작업만 그 풀을 쓰게 하고, 작은 추론 작업은 다른 클래스도 허용할 수 있습니다. 다만 대체 장치 선택이나 공유를 위한 세부 기능은 Kubernetes 릴리스별 단계가 다를 수 있으므로 운영 버전의 문서를 확인해야 합니다. 장치 할당의 목적은 GPU 이용률 숫자만 높이는 것이 아니라, 필요한 작업이 예측 가능한 시간에 올바른 장치에서 실행되고 실패할 때 원인을 알 수 있게 하는 것입니다.

## 마무리

DRA는 “GPU 1개”처럼 단순한 수량 요청을 넘어, 어떤 종류와 속성의 장치를 어떤 Pod가 사용할지 선언하고 추적하게 합니다. 드라이버가 ResourceSlice로 장치를 게시하고, DeviceClass가 선택 범주를 정하며, ResourceClaim이 요청과 할당 결과를 담습니다. 스케줄러는 장치와 노드를 함께 고르고, 노드 드라이버가 실제 사용 준비를 맡습니다. 이 역할을 구분하면 Pod가 대기할 때 어디부터 조사할지도 분명해집니다.

첫 적용은 기존에 장치 종류 때문에 배치가 자주 엇갈리는 한 작업에서 시작하면 좋습니다. 필요한 장치 속성을 적고, 실제 드라이버가 그 속성을 게시하는지, Claim 상태에서 할당을 볼 수 있는지, 실패를 설명할 수 있는지 확인하세요. 속성 선택이 필요하지 않은 작업은 기존 경로를 유지해도 됩니다. DRA의 안정 API와 선택 기능의 지원 단계, 장치 드라이버의 구현 범위를 별도로 확인하는 것이 핵심입니다.
