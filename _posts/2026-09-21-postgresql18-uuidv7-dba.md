PostgreSQL 18에서 `uuidv7()`이 기본 함수로 들어오면서 UUID를 식별자 문제로만 보던 관점이 바뀌었습니다. UUID는 충돌 가능성이 매우 낮은 전역 식별자이고, 여러 애플리케이션과 리전에서 생성하기 쉽습니다. 그러나 모든 UUID가 인덱스에 같은 방식으로 잘 맞는 것은 아닙니다. 완전한 난수형 UUIDv4를 큰 테이블의 B-tree 기본 키로 계속 추가하면 페이지 분할과 캐시 효율을 함께 고민해야 합니다. UUIDv7은 시간 정보를 앞쪽에 두고 뒤쪽에 랜덤성을 남겨, 생성 시각의 순서를 어느 정도 보존하는 선택지입니다.

이 글은 PostgreSQL 18을 직접 운영했다는 보고서가 아니라, 공식 문서와 공개 사양을 바탕으로 DBA가 UUIDv7 도입을 검토할 때 필요한 개념, 스키마, 마이그레이션, 관찰 지표를 정리한 글입니다. 특정 벤치마크 수치를 모든 환경에 적용하지 않고, 실제 workload에서 검증해야 한다는 원칙을 중심에 둡니다.

## 기본 기술: UUID, 버전, B-tree를 먼저 이해하기

UUID는 128비트 값을 표준 형식으로 표현하는 식별자입니다. 사람이 읽는 문자열은 보통 8-4-4-4-12 형태의 16진수 묶음으로 표시되지만, PostgreSQL의 `uuid` 타입은 문자열보다 작은 고정 길이 값으로 저장하고 비교합니다. 따라서 `text`에 UUID 문자열을 넣는 것과 `uuid` 타입을 사용하는 것은 같은 설계가 아닙니다. 인덱스와 비교 연산을 생각하면 식별자는 가능한 한 `uuid` 타입으로 선언하는 편이 명확합니다.

UUID 버전은 생성 규칙을 나타냅니다. UUIDv4는 난수 중심이고, UUIDv7은 Unix epoch 기반의 시간 순서 정보를 앞부분에 배치하며 나머지에 정렬을 보조하는 세부 시간과 랜덤 요소를 둡니다. 버전 번호가 있다는 말은 UUID 안에 애플리케이션의 모든 업무 정보가 들어 있다는 뜻이 아닙니다. UUID는 여전히 식별자이고, 주문일, 생성자, 테넌트 같은 검색 조건은 별도의 컬럼과 인덱스로 관리해야 합니다.

B-tree 인덱스는 값의 순서를 이용해 탐색합니다. 새로운 값이 인덱스 전체에 무작위로 흩어지면 여러 페이지가 갱신될 수 있고, 페이지가 가득 찼을 때 분할이 일어날 수 있습니다. 반대로 값이 대체로 증가하는 방향으로 들어오면 최근 페이지에 삽입이 집중될 가능성이 있습니다. 이것은 UUIDv7이 자동으로 모든 인덱스 비용을 없앤다는 뜻이 아니라, 키 생성 패턴이 B-tree의 물리적 동작과 더 잘 맞을 수 있다는 뜻입니다.

또 하나의 기본 개념은 논리적 순서와 물리적 순서의 차이입니다. `ORDER BY id`가 생성 시각의 정확한 순서를 보장한다고 가정하면 안 됩니다. 같은 밀리초에 만들어진 값의 세부 시간과 랜덤 부분이 어떻게 배치되는지, 여러 애플리케이션 서버의 시계가 어떻게 움직이는지, 트랜잭션이 언제 커밋되는지가 모두 다릅니다. 시간순 UUID는 정렬 힌트이지 감사 로그의 진실 원장이 아닙니다.

## PostgreSQL 18의 uuidv7 함수

PostgreSQL 18 공식 문서는 `uuidv7()`을 시간 정렬 UUID를 생성하는 함수로 설명합니다. 선택적 `shift` 간격을 주면 계산된 시각을 이동할 수 있지만, 운영 식별자에 임의의 미래 시간을 넣는 기능으로 남용해서는 안 됩니다. 문서는 UUIDv7의 48비트 밀리초 필드가 표현할 수 있는 범위도 설명합니다. 실무에서는 기본 인자 없는 `uuidv7()`을 사용하고, 테스트에서만 시간 이동을 제한적으로 쓰는 편이 이해하기 쉽습니다.

가장 간단한 테이블은 다음과 같습니다.

```sql
CREATE TABLE orders (
    order_id uuid PRIMARY KEY DEFAULT uuidv7(),
    customer_id bigint NOT NULL,
    ordered_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    status text NOT NULL CHECK (status IN ('ready', 'paid', 'cancelled')),
    amount numeric(12, 2) NOT NULL CHECK (amount >= 0)
);
```

여기서 `order_id`는 식별자이고 `ordered_at`은 업무 시각입니다. 두 컬럼을 분리하면 “ID를 정렬하면 주문일을 얻을 수 있다”는 잘못된 결합을 피할 수 있습니다. 조회 화면에서 최근 주문을 보여줄 때는 `ORDER BY ordered_at, order_id`처럼 업무 컬럼을 기준으로 삼는 것이 더 분명합니다. `order_id`는 동률을 안정적으로 정리하는 보조 정렬 키가 될 수 있습니다.

기본값은 삽입 시점에 데이터베이스에서 평가됩니다. 애플리케이션이 미리 UUID를 만들어 보내는 방식도 가능하지만, 서비스마다 생성기 구현과 시계가 다르면 운영 규칙이 흐려질 수 있습니다. 중앙 데이터베이스가 유일한 생성 장소라면 DB 기본값이 단순합니다. 오프라인 생성, 여러 리전의 사전 생성, 메시지 큐의 선행 식별자가 필요하다면 애플리케이션 생성과 DB 생성의 책임 경계를 문서화해야 합니다.

다음처럼 버전과 시각을 확인할 수 있습니다.

```sql
SELECT uuidv7() AS id,
       uuid_extract_version(uuidv7()) AS version;
```

같은 SELECT에서 두 번 호출한 값은 서로 다르므로 실제 비교에서는 하나의 결과를 CTE나 애플리케이션 변수로 잡아야 합니다. `uuid_extract_version()`은 값이 어떤 UUID 버전인지 확인하는 함수입니다. 이 검사는 운영 데이터 품질 점검이나 마이그레이션 검증에 유용하지만, 요청마다 실행할 필수 제약으로 만들 필요는 없습니다.

## 왜 DBA가 UUIDv7을 검토하는가

난수 키는 분산 환경에서 편리합니다. 서버가 서로 조정하지 않아도 ID를 만들 수 있고, 내부 순번을 외부에 노출하지 않는다는 장점이 있습니다. 하지만 대규모 삽입 테이블에서 난수형 기본 키가 만드는 인덱스 접근 패턴은 메모리와 디스크 쓰기 관점에서 불리할 수 있습니다. 페이지가 자주 바뀌면 버퍼 캐시의 유효성이 낮아지고, 인덱스가 테이블보다 빠르게 커지는 현상을 관찰할 수 있습니다.

UUIDv7은 이 문제에 대한 한 가지 설계 도구입니다. 앞부분이 시간에 따라 증가하므로 최근 삽입이 인덱스의 최근 영역에 모일 가능성이 있습니다. 그 결과 페이지 지역성, WAL 패턴, 캐시 재사용이 개선될 수 있습니다. 그러나 동시 삽입이 많고 여러 노드가 같은 시간 구간에 생성하는 경우에는 동일한 시간 프리픽스 안에서 값이 분산됩니다. 따라서 “완전한 순차 정수”와 같은 효과를 기대하면 안 됩니다.

키의 지역성은 기본 키 하나만의 문제가 아닙니다. 외래 키, 보조 인덱스, 복제 로그, 파티션 키, CDC 이벤트의 정렬 방식까지 영향을 받습니다. 예를 들어 UUIDv7을 기본 키로 바꾸었지만 `created_at` 조건 검색을 위한 인덱스가 없다면 최근 데이터 조회가 반드시 빨라지지 않습니다. 반대로 주요 조회가 테넌트와 상태를 기준으로 한다면 `(tenant_id, status, created_at)` 인덱스가 더 직접적인 해결책일 수 있습니다.

## 기존 UUIDv4 테이블에 적용하는 방법

첫 번째 선택지는 새 행에만 UUIDv7을 사용하고 기존 키는 그대로 두는 것입니다. 가장 안전하고, 외래 키와 외부 API 계약을 건드리지 않습니다. 다만 한 테이블 안에 생성 방식이 섞이므로 운영 문서에 전환 시점을 기록해야 합니다. 데이터 분석에서 ID의 버전을 기준으로 구간을 나누려면 `uuid_extract_version(id)`를 사용할 수 있지만, 업무 쿼리에서 매번 함수로 필터링하는 설계는 피하는 편이 좋습니다.

두 번째는 새 UUIDv7 컬럼을 추가하고 점진적으로 전환하는 방식입니다.

```sql
ALTER TABLE orders ADD COLUMN order_id_v7 uuid;
UPDATE orders SET order_id_v7 = uuidv7() WHERE order_id_v7 IS NULL;
ALTER TABLE orders ALTER COLUMN order_id_v7 SET NOT NULL;
CREATE UNIQUE INDEX CONCURRENTLY orders_order_id_v7_key ON orders(order_id_v7);
```

이 예시는 방향을 보여주는 것이며, 대형 운영 테이블에서 한 번의 `UPDATE`를 그대로 실행하라는 명령이 아닙니다. 대량 갱신은 WAL, 복제 지연, 테이블 팽창, 잠금 대기와 연결됩니다. 배치 크기와 휴지 시간을 정하고, 재시작 가능한 작업으로 나누며, 인덱스 생성 시간과 디스크 여유 공간을 확인해야 합니다. 새 컬럼에 값을 채우는 동안 동시 삽입 행을 놓치지 않도록 트리거 또는 애플리케이션 이중 기록 정책이 필요합니다.

세 번째는 기존 기본 키를 유지하고 UUIDv7을 시간 정렬 보조 키로 추가하는 것입니다. 외부 URL과 외래 키를 바꾸지 않으면서 삽입 지역성만 검토할 수 있다는 장점이 있습니다. 다만 테이블에 키가 두 개 생기므로 어느 키가 식별자이고 어느 키가 정렬 보조 키인지 명시해야 합니다. 사용하지 않는 인덱스까지 추가하면 저장 공간과 쓰기 비용이 늘어나므로 실제 쿼리와 유지보수 목적을 기준으로 선택합니다.

## 파티셔닝과 UUIDv7

UUIDv7의 시간 정보가 있다고 해서 UUID 컬럼만으로 파티셔닝을 결정하면 안 됩니다. PostgreSQL 파티션 프루닝은 파티션 키 조건을 얼마나 명확히 알 수 있는지에 좌우됩니다. 월별 보관, 개인정보 삭제, 오래된 데이터 아카이빙이 목적이라면 별도의 `created_at` 또는 이벤트 시각을 파티션 키로 두는 편이 운영 정책을 표현하기 쉽습니다.

예를 들어 주문 테이블을 월 단위로 나누고 기본 키는 각 행의 UUID로 유지할 수 있습니다. 이때 유일성 제약의 범위와 외래 키 제약의 지원 여부를 PostgreSQL 버전 및 설계 조건에 맞춰 확인해야 합니다. 파티션 키에 시각을 사용하면 애플리케이션이 시간 필터를 빼먹었을 때 전체 파티션을 읽을 수 있으므로, 쿼리 검토와 모니터링이 함께 필요합니다.

UUIDv7의 시간 부분을 추출해 파티션 경계에 직접 쓰고 싶다는 유혹도 있습니다. 하지만 UUID 내부 인코딩을 애플리케이션마다 재구현하면 버전 사양과 시간대 해석이 분산됩니다. PostgreSQL 공식 함수와 명시적인 시각 컬럼을 기준으로 설계하는 편이 장기적으로 안전합니다. 내부 시간 비트는 식별자 생성의 속성이며, 데이터 보존 정책의 선언문이 아닙니다.

## 인덱스와 성능을 검증하는 DBA 체크리스트

도입 전에는 대표 삽입량, 동시 세션, 행 크기, 인덱스 수, 저장장치 종류를 기록합니다. 가능하면 같은 스키마와 같은 데이터 분포에서 UUIDv4와 UUIDv7을 비교합니다. 단순히 초당 INSERT만 측정하지 말고, 인덱스 크기, 페이지 분할, WAL 증가량, checkpoint 시간, replica replay 지연도 함께 봐야 합니다.

조회 측정에서는 캐시 상태를 분리해야 합니다. 같은 데이터를 반복해서 읽은 warm cache 결과와 재시작 또는 충분한 데이터 범위를 사용한 cold cache 결과는 질문이 다릅니다. `EXPLAIN (ANALYZE, BUFFERS)`는 실행계획과 버퍼 사용량을 살펴보는 출발점이지만, 그 출력 하나만으로 저장장치 전체의 병목을 설명할 수는 없습니다.

인덱스가 작아졌다는 관찰도 신중해야 합니다. 같은 UUID 타입이면 값의 저장 크기가 UUID 버전에 따라 달라지지 않으므로, 크기 차이는 보통 인덱스 구조와 삽입·삭제·진공 상태의 결과입니다. `pg_relation_size`, `pg_indexes_size`, `pg_stat_user_indexes` 같은 지표를 시간에 따라 저장하고, 같은 행 수와 같은 인덱스 정의를 비교해야 합니다.

삭제와 업데이트가 많은 테이블에서는 UUIDv7의 삽입 지역성이 전체 비용을 결정하지 않습니다. 오래된 행이 여러 페이지에 흩어져 있고 HOT 업데이트가 실패하면 테이블 팽창이 더 큰 문제가 될 수 있습니다. fillfactor, autovacuum, 업데이트 컬럼, 인덱스 포함 여부를 함께 검토해야 합니다. 특정 키 생성 방식을 선택했다고 해서 VACUUM 설계를 생략할 수 없습니다.

## 애플리케이션 계약과 보안

UUID는 예측하기 어렵다는 느낌을 주지만, UUIDv7의 시간 부분은 생성 시점에 대한 정보를 일부 드러냅니다. 공개 URL에 UUIDv7을 쓰면 공격자가 리소스 생성 시기의 범위를 추정할 수 있습니다. 이것이 바로 취약점이라는 뜻은 아니지만, 접근 제어를 ID 난독화에 의존하면 안 된다는 뜻입니다. 인증, 권한 검사, 테넌트 경계, rate limit이 먼저입니다.

API 계약에서는 문자열 포맷과 대소문자, null 가능성, 잘못된 UUID의 오류 응답을 정의합니다. JSON의 UUID는 문자열로 전달되지만 데이터베이스에서는 `uuid` 타입으로 검증합니다. 사용자가 보낸 ID를 SQL 문자열로 이어 붙이지 말고 파라미터로 바인딩해야 합니다. URL 경로의 UUID가 존재하지 않을 때 404를 반환할지, 권한이 없는 리소스와 구분하지 않을지도 서비스 보안 정책에 포함해야 합니다.

시간 순서라는 특성은 개인정보 분류와도 관련될 수 있습니다. ID 자체에 정확한 업무 시각이 들어 있는 것은 아니지만, 여러 ID를 수집한 관찰자는 생성 시기의 흐름을 분석할 수 있습니다. 외부 노출 식별자와 내부 조인 키를 분리하거나, 민감한 도메인에서는 별도 토큰을 사용하는 선택지를 검토해야 합니다.

## 복제, CDC, 이벤트 정렬

논리 복제나 CDC 파이프라인에서 UUIDv7을 이벤트 순서로 착각하면 안 됩니다. 데이터베이스 트랜잭션의 커밋 순서, WAL 순서, 메시지 브로커 파티션 순서, 소비자 재처리 순서는 서로 다른 순서입니다. UUIDv7은 행이 생성된 시점의 힌트를 제공할 뿐, 트랜잭션의 인과관계를 표현하지 않습니다.

이벤트에는 별도의 `event_id`, `occurred_at`, `committed_at` 또는 단조 증가하는 오프셋을 두는 것이 좋습니다. 소비자는 중복 전달을 고려해 UUID를 멱등성 키로 사용할 수 있지만, 이벤트가 정말 한 번만 처리되었다는 증거로 사용해서는 안 됩니다. 장애 복구 뒤 늦게 도착한 이벤트가 UUID 순서상 오래된 것처럼 보일 수 있기 때문입니다.

분산 시스템에서 시계가 뒤로 조정되는 경우도 생각해야 합니다. UUIDv7 생성기는 표준에 맞춰 값을 만들더라도 NTP 보정, VM 시간 문제, 여러 리전의 지연 때문에 애플리케이션 관찰 순서와 DB 삽입 순서가 어긋날 수 있습니다. 정확한 순서가 필요하면 DB 시퀀스, 커밋 LSN, 브로커 오프셋 같은 목적별 순서를 별도로 사용합니다.

## 운영 전환 절차 예시

첫 단계는 목록화입니다. UUID를 사용하는 모든 테이블, 외래 키, 배치, API 문서, 캐시 키, 로그 파서, 데이터 웨어하우스 적재 작업을 찾습니다. 두 번째는 샘플 workload를 만듭니다. 대량 삽입, 단건 조회, 범위 조회, 삭제, 복제, 장애 복구를 각각 포함합니다. 세 번째는 관찰 지표와 중단 기준을 미리 정합니다.

네 번째 단계에서 PostgreSQL 18 테스트 인스턴스에 새 기본값을 적용합니다. `SHOW server_version;`으로 버전을 확인하고 `SELECT uuidv7();`로 함수 존재를 확인합니다. 운영과 같은 인덱스와 제약을 만들어야 비교가 의미 있습니다. 다섯 번째 단계에서는 애플리케이션이 DB가 만든 값을 올바르게 읽고, 재시도 시 중복 처리하며, 이전 버전 클라이언트와도 호환되는지 확인합니다.

마지막 단계는 점진 배포입니다. 새 행의 일부 트래픽에만 적용하고, 오류율과 지연시간, 인덱스 크기, WAL, 복제 지연을 관찰합니다. 문제가 생기면 새 값의 생성을 중단하고 기존 키 경로로 돌아갈 수 있어야 합니다. 이미 저장된 UUID를 무리하게 재작성하는 것보다, 새 데이터부터 정책을 바꾸고 장기간에 걸쳐 구 데이터를 정리하는 편이 대개 위험이 낮습니다.

## 흔한 오해와 실패 패턴

첫 번째 오해는 UUIDv7이면 `ORDER BY id DESC LIMIT 20`이 최근 업무 이벤트를 항상 반환한다는 생각입니다. 같은 시간 구간의 동시 삽입, 지연된 트랜잭션, 재처리, 서버 시계 차이가 있기 때문에 최근 화면은 `created_at` 또는 업무 시각을 기준으로 설계해야 합니다.

두 번째 오해는 UUID를 `varchar(36)`로 저장해도 같다는 생각입니다. 비교 규칙과 저장 공간, 잘못된 문자열 검증, 애플리케이션 변환 비용이 달라집니다. PostgreSQL의 `uuid` 타입을 사용하고 외부 경계에서 문자열을 변환하는 편이 역할 분리가 분명합니다.

세 번째 실패 패턴은 인덱스를 새로 추가한 뒤 기존 인덱스를 바로 지우는 것입니다. 실제 쿼리 플랜이 전환되었는지, 복제와 백업이 정상인지, 롤백에 필요한 컬럼이 남아 있는지 확인해야 합니다. 인덱스 삭제는 디스크를 줄일 수 있지만, 잘못된 삭제는 즉시 성능 장애로 이어질 수 있습니다.

## 스키마 리뷰에서 놓치기 쉬운 세부 항목

UUIDv7 도입 검토는 컬럼 하나의 기본값을 바꾸는 작업처럼 보이지만, 실제로는 스키마의 경계를 다시 읽는 작업입니다. 먼저 식별자의 생명 주기를 확인합니다. 행이 생성될 때 바로 ID가 필요한지, 임시 행과 최종 행이 같은 테이블에 들어가는지, 삭제 후 같은 ID를 재사용하지 않는지 확인합니다. UUID는 재사용하지 않는다는 원칙을 유지해야 캐시와 감사 기록의 의미가 흔들리지 않습니다.

다음으로 외래 키의 방향을 확인합니다. 자식 테이블이 부모 UUID를 문자열로 저장하거나, 일부 서비스만 숫자형 내부 ID를 저장하면 변환 코드가 여러 계층에 남습니다. 부모와 자식의 타입을 같은 `uuid`로 맞추고, 애플리케이션 DTO와 데이터베이스 타입 사이의 변환 지점을 한 곳에 두는 편이 좋습니다. 타입이 같은데도 애플리케이션이 전부 문자열 비교를 수행하면 DB의 타입 안전성을 살리지 못합니다.

기본값과 입력 검증도 구분해야 합니다. `DEFAULT uuidv7()`은 값이 빠졌을 때 데이터베이스가 생성하는 규칙입니다. 사용자가 임의의 UUID를 넣는 것을 막지는 않습니다. 내부 서비스만 쓰는 테이블이라도 배치와 수동 SQL이 존재한다면 잘못된 버전의 값이 들어올 수 있습니다. 모든 값을 UUIDv7으로 강제할지, 버전 혼합을 허용할지, 허용한다면 언제까지인지 마이그레이션 문서에 기록합니다.

검증 함수에 의존하는 CHECK 제약은 신중하게 선택합니다. 모든 ID가 UUIDv7이어야 한다는 도메인 규칙이 정말 필요한 경우에만 버전 검사를 제약으로 만들고, 외부 시스템에서 전달된 기존 UUIDv4를 잠시 허용해야 한다면 애플리케이션 검증과 데이터 품질 리포트로 단계적으로 관리합니다. 제약은 강력하지만, 잘못된 전환에서는 복구 비용도 큽니다.

## 백업과 복구 관점

새 키 생성 방식은 백업 파일의 내용보다 복구 뒤 동작에 영향을 줍니다. PITR로 특정 시점에 복구했을 때 복구된 행의 UUID와 외부 이벤트의 ID가 일치하는지 확인해야 합니다. 데이터베이스가 새 UUID를 자동으로 만들어 주는 것은 복구된 기존 행의 키를 다시 만든다는 뜻이 아닙니다. 복구 테스트에서는 기존 데이터, 새 삽입, 재시도 요청을 모두 포함합니다.

논리 백업을 텍스트 SQL로 내보낼 때 UUID 값은 문자열 리터럴로 표현될 수 있습니다. 대상 DB의 타입과 기본값이 달라도 기존 값이 그대로 복원되는지 확인해야 합니다. 복원 과정에서 기본값을 재평가하도록 스크립트를 만들면 외래 키와 CDC 기준이 달라질 수 있습니다. 복구는 새 생성이 아니라 기존 식별자의 보존을 우선해야 합니다.

시퀀스 기반 키는 백업과 복구 때 현재 값과 다음 값의 관계를 점검하지만, UUIDv7은 같은 종류의 시퀀스 동기화가 필요하지 않습니다. 그렇다고 운영 상태가 단순해지는 것은 아닙니다. 시계, 함수 존재 여부, 권한, 버전 호환, 애플리케이션의 UUID 파서가 새로운 값을 처리하는지 확인해야 합니다. 특히 구 버전 클라이언트가 UUID 버전을 검사해 거부하는 로직이 없는지 찾아야 합니다.

## 쿼리 설계와 페이지 지역성

최근 데이터 조회가 많다면 UUIDv7을 쓰는 것과 별개로 조회 조건을 명시해야 합니다. 다음 쿼리는 UUID 내부 순서를 업무 규칙으로 오해하지 않는 예입니다.

```sql
SELECT order_id, customer_id, ordered_at, amount
FROM orders
WHERE customer_id = $1
  AND ordered_at >= $2
  AND ordered_at < $3
ORDER BY ordered_at DESC, order_id DESC
LIMIT 50;
```

이 쿼리에서 어떤 인덱스가 좋은지는 데이터 분포와 선택도에 달려 있습니다. 고객별 주문이 작고 시간 범위가 넓다면 `(customer_id, ordered_at DESC, order_id DESC)`가 후보입니다. 전체 시스템의 최근 행을 찾는 쿼리라면 `ordered_at` 단독 또는 부분 인덱스를 검토할 수 있습니다. UUIDv7 기본 키가 있다고 해서 이 인덱스를 자동으로 대신하지는 않습니다.

페이지 지역성은 쓰기와 읽기의 양쪽에 나타날 수 있습니다. 삽입이 최근 인덱스 페이지에 몰리면 다른 형태의 경합이 생길 수도 있고, 고도의 병렬 쓰기에서는 한 영역이 병목이 될 수 있습니다. 난수 UUID가 모든 환경에서 나쁘고 시간 정렬 UUID가 모든 환경에서 좋다는 이분법을 피해야 하는 이유입니다. 측정에는 평균 처리량과 함께 경합, p99, CPU, WAL을 포함합니다.

인덱스만 보고 테이블 접근을 판단하면 안 됩니다. 기본 키 인덱스에서 찾은 뒤 테이블 힙 페이지를 랜덤하게 읽는다면, 키 정렬성이 전체 조회를 해결하지 못할 수 있습니다. 인덱스 전용 스캔이 가능한지, 필요한 컬럼을 INCLUDE할지, 테이블의 업데이트 패턴 때문에 visibility map이 유지되는지 함께 살펴봅니다. INCLUDE 컬럼은 저장 공간과 쓰기 비용을 늘릴 수 있으므로 실제 쿼리부터 선택합니다.

## 팀 운영 규칙으로 남길 문장

기술 선택은 코드보다 문서에서 더 오래 남습니다. 팀 표준에는 “UUIDv7은 내부 생성 시각의 힌트이며 업무 시각을 대체하지 않는다”, “외부 API의 권한은 ID 예측 가능성에 의존하지 않는다”, “키 버전 전환은 신규 행부터 진행한다” 같은 문장을 명시합니다. 이런 문장이 있으면 새 서비스가 UUID를 사용하면서도 정렬, 보안, 이벤트 순서를 혼동하는 일을 줄일 수 있습니다.

코드 리뷰 체크리스트에는 DB 기본값 사용 여부, 애플리케이션 재시도 시 ID 유지 여부, 문자열 타입 저장 여부, 외래 키 타입 일치 여부, 최근 조회의 정렬 기준, CDC 순서 필드, 로그 마스킹 여부를 넣습니다. 리뷰어가 “UUIDv7을 사용했는가”만 확인하면 핵심 위험이 남습니다. “이 ID가 어떤 의미를 가지지 않는가”를 묻는 편이 더 효과적입니다.

운영 런북에는 버전 확인 명령, 새 테이블 템플릿, 인덱스 지표 조회 방법, 전환 중단 기준, 롤백 절차를 남깁니다. 예를 들어 버전 업그레이드 후 함수가 존재하지 않으면 배포를 중단하고, 함수는 있지만 복제 대상의 호환성이 확인되지 않으면 애플리케이션 생성을 유지하는 식의 분기입니다. 런북은 이상적인 경로보다 실패했을 때의 행동을 명확히 해야 합니다.

마지막으로 성능 기대치를 숫자 하나로 약속하지 않습니다. “UUIDv7이면 인덱스가 작아진다”가 아니라 “우리의 삽입 workload에서 페이지 분할과 p99 지연이 개선되는지 측정한다”고 표현합니다. 공개 자료와 공식 문서는 선택의 근거가 되지만, 서비스의 승인 기준은 서비스 자체의 측정 결과여야 합니다.

## 운영 장애를 피하는 전환 순서

전환 당일에는 먼저 애플리케이션이 새 UUID를 읽고 쓰는지 확인합니다. 쓰기 경로만 바꾸고 읽기 경로가 예전 컬럼을 참조하면 새 행이 생성된 뒤 조회에서 사라지는 문제가 생길 수 있습니다. 읽기 경로를 이중으로 읽게 만들 때는 어느 값이 우선인지, 두 값이 다르면 어떤 값을 기록할지 명확히 합니다. 로그에는 원래 키와 새 키를 함께 남기되, 외부 노출 로그에는 필요한 식별자만 남깁니다.

배치 전환은 작은 범위에서 시작합니다. 한 번에 많은 행을 갱신하기보다 기본 키나 생성 시각 범위로 나누고, 각 배치 뒤에 행 수와 null 수를 확인합니다. 배치 사이에 복제 지연과 WAL 증가를 확인해 임계값을 넘으면 중지합니다. 중지한 배치를 다시 실행해도 이미 처리된 행을 건너뛰도록 조건을 만들면 운영자가 긴급히 작업을 멈추기 쉬워집니다.

인덱스와 제약의 활성화 시점도 나눕니다. 새 컬럼에 값을 채운 뒤 유일 인덱스를 만들고, 검증이 끝난 후 애플리케이션의 읽기 경로를 바꿉니다. 마지막에 외래 키와 기본 키를 전환하되, 잠금이 긴 작업은 트래픽이 낮은 시간에 진행합니다. 전환 중 오류가 나면 새 컬럼을 즉시 삭제하기보다, 기존 경로를 복구하고 원인을 확인한 뒤 데이터를 보존하는 것이 안전합니다.

전환 완료의 기준은 코드 배포 성공이 아닙니다. 일정 기간 동안 새 키의 null과 중복이 없고, 주요 쿼리의 지연이 기준선 안에 있으며, 복제와 백업이 정상이고, 외부 소비자가 새 값을 처리했는지 확인해야 합니다. 이 기준을 충족한 뒤에만 이전 컬럼과 인덱스의 제거 일정을 잡습니다. 제거 역시 별도 변경으로 기록하고 복구용 백업을 확인합니다.

점검표에는 담당자와 확인 시각도 남깁니다. 누가 어떤 환경에서 행 수, 인덱스 크기, 오류율, 복제 지연을 확인했는지 기록하면 나중에 성능 차이를 재현하기 쉽습니다. 짧은 전환이라도 증거를 남기는 습관이 장기 운영의 품질을 높입니다.

## DBA 적용 Q&A

  <p class="quick-label">한계와 적용 기준</p>
  <div class="quick-answer"><h3>Q. 신규 서비스면 무조건 UUIDv7로 시작해야 하나요?</h3><p>A. 아닙니다. 여러 노드에서 독립 생성하는 식별자와 인덱스 삽입 지역성이 필요하다면 후보가 됩니다. 단일 DB의 작은 테이블이나 순번이 더 자연스러운 도메인이라면 bigint가 단순할 수 있습니다.</p></div>
  <div class="quick-answer"><h3>Q. UUIDv4 데이터를 UUIDv7로 바꾸는 것이 최우선인가요?</h3><p>A. 대개 아닙니다. 실제 인덱스 팽창이나 쓰기 병목을 측정한 뒤 결정해야 합니다. 외부 계약과 외래 키가 많다면 새 행부터 전환하는 선택이 더 안전할 수 있습니다.</p></div>
  <div class="quick-answer"><h3>Q. UUIDv7만으로 이벤트 순서를 구현할 수 있나요?</h3><p>A. 안 됩니다. UUIDv7은 시간 정렬 힌트입니다. 커밋 순서, 메시지 오프셋, 도메인 버전 같은 순서가 필요하면 별도 값을 저장해야 합니다.</p></div>
  <div class="quick-answer"><h3>Q. 운영에서 반드시 모니터링할 값은 무엇인가요?</h3><p>A. 삽입 지연, 인덱스와 테이블 크기, WAL 생성량, checkpoint, autovacuum 지연, 복제 지연, 주요 쿼리의 p95·p99를 함께 봐야 합니다.</p></div>
</section>

PostgreSQL 18의 UUIDv7은 식별자 생성기 하나가 아니라 데이터베이스 물리 설계와 분산 애플리케이션 계약을 다시 점검하게 하는 기능입니다. 시간 순서가 인덱스에 도움이 될 가능성은 분명하지만, 업무 시각과 이벤트 순서를 대체하지는 않습니다. DBA의 역할은 기능을 켜는 데서 끝나지 않고, 키의 생성 위치, 인덱스의 실제 접근 패턴, 마이그레이션의 되돌림 지점, 외부 노출 위험을 함께 설계하는 데 있습니다.
