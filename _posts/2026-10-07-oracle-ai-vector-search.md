사내 규정 문서에서 “휴가 이월 기준”을 찾을 때, 제목과 정확히 같은 단어가 없어도 ‘남은 연차를 다음 해에 넘기는 조건’이라는 의미가 비슷한 문단을 찾고 싶을 때가 있습니다. 전통적인 DBMS(Database Management System, 데이터베이스 관리 시스템)의 `LIKE` 검색이나 전문 검색은 단어·형태·키워드에 강하지만, 표현이 달라진 의미의 가까움까지 자동으로 계산하지는 않습니다. **Oracle AI Vector Search**는 문장·문서·이미지 같은 데이터를 숫자 배열인 벡터로 표현하고, 그 거리로 의미적으로 가까운 데이터를 SQL로 찾도록 Oracle Database에 추가된 기능입니다.

벡터 검색을 들으면 별도의 벡터 데이터베이스를 새로 도입해야 한다고 생각하기 쉽습니다. Oracle의 접근은 관계형 데이터, 권한, 트랜잭션, SQL 필터와 벡터를 한 데이터베이스 안에서 결합하는 데 있습니다. 예를 들어 ‘한국 법인에 공개된, 2026년에 유효한 인사 문서’라는 관계형 조건으로 범위를 줄인 뒤 그 안에서 의미가 가까운 문단을 찾을 수 있습니다. 하지만 벡터 열을 하나 추가한다고 답변 품질이 자동으로 좋아지지는 않습니다. 임베딩 모델, 문서 분할, 거리 지표, 인덱스, 권한 필터, 갱신 주기, 평가 기준이 함께 맞아야 합니다.

이 글은 Oracle AI Vector Search를 처음 접하는 DBA와 개발자를 위해 기반 기술부터 정리합니다. 특정 버전·라이선스·성능 수치나 실제 운영 경험을 주장하지 않습니다. 기능 사용 가능 여부와 세부 DDL은 Oracle Database 버전, Release Update, `COMPATIBLE` 값, 배포 환경을 공식 문서로 반드시 다시 확인해야 합니다.

## 먼저 알아둘 기반 기술: 임베딩·벡터·거리·RAG

**임베딩(embedding)** 은 텍스트·이미지·음성 같은 비정형 데이터를 여러 숫자로 된 고차원 벡터로 바꾸는 과정 또는 그 결과입니다. 임베딩 모델은 비슷한 의미의 문장이 벡터 공간에서 가까워지도록 학습됩니다. 예를 들어 “비밀번호를 재설정하는 방법”과 “로그인 암호를 바꾸고 싶다”는 표면 단어는 달라도, 적절한 모델에서는 가까운 방향의 벡터가 될 수 있습니다. 반대로 임베딩은 사실 여부를 판단하거나 업무 규칙을 이해하는 완벽한 의미 엔진이 아닙니다. 어떤 언어·도메인·문서 형식으로 학습된 모델인지에 따라 품질이 달라집니다.

**벡터(vector)** 는 순서 있는 숫자 배열입니다. `[-0.12, 0.41, ...]`처럼 수백 또는 수천 개 차원을 가질 수 있습니다. 사람은 각 숫자의 의미를 직접 해석하기 어렵지만, 같은 모델·같은 전처리로 만든 벡터끼리는 거리 계산을 할 수 있습니다. 문서 저장 시 사용한 임베딩 모델과 질의 시 사용한 모델이 달라 차원 수·정규화·언어 특성이 달라지면 비교 결과가 무의미해질 수 있습니다. 그러므로 벡터 데이터에는 원문만큼이나 **모델 이름, 모델 버전, 차원 수, 생성 시각**을 관리해야 합니다.

**유사도 검색(similarity search)** 은 질의 벡터와 저장 벡터 사이의 거리를 계산해 가까운 k개를 찾는 작업입니다. 자주 쓰이는 지표는 코사인 거리(COSINE), 유클리드 거리(EUCLIDEAN 또는 L2), 내적 기반 DOT입니다. 코사인은 두 벡터의 방향이 얼마나 비슷한지 보며, 유클리드 거리는 공간에서의 직선 거리를 봅니다. 어느 지표가 적절한지는 임베딩 모델이 권장하는 방식에 맞춰야 합니다. ‘코사인이 기본값이니 항상 코사인을 쓴다’가 아니라, 모델 카드·평가 결과·인덱스 정의가 같은 기준을 사용해야 합니다.

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)** 는 LLM이 답변을 만들기 전에 외부 문서에서 관련 근거를 검색해 프롬프트에 넣는 구조입니다. RAG는 모델의 학습 지식만으로 답하지 않게 하고 최신 사내 문서를 참조하게 할 수 있습니다. 그러나 검색 결과가 틀리면 LLM은 틀린 근거를 더 그럴듯하게 설명할 수 있습니다. 그래서 RAG 품질은 LLM 선택만으로 정해지지 않으며, 문서 수집·청킹·임베딩·검색·권한·인용·평가가 연결된 데이터 제품으로 다뤄야 합니다.

## Oracle에서 벡터를 다룬다는 뜻: 관계형 행에 VECTOR를 더한다

Oracle AI Vector Search는 `VECTOR` 데이터 타입을 통해 벡터를 테이블 열로 저장하고, SQL 함수·연산자로 거리 계산과 검색을 수행합니다. Oracle 공식 문서에 따르면 VECTOR 기능을 쓰려면 `COMPATIBLE` 초기화 파라미터가 최소 요구 버전 이상이어야 합니다. 이는 단순한 애플리케이션 라이브러리 설치 문제가 아니라 데이터베이스 호환성·업그레이드·다운그레이드 계획과 연결된 DBA 검토 항목입니다.

가장 단순한 문서 테이블은 원문과 벡터, 그리고 관계형 메타데이터를 함께 둡니다. 실제 운영에서는 문서 전체보다 문단 또는 일정 길이의 조각(chunk)을 행으로 저장하는 경우가 많습니다.

```sql
CREATE TABLE knowledge_chunk (
  chunk_id       NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  document_id    NUMBER NOT NULL,
  tenant_id      NUMBER NOT NULL,
  visibility     VARCHAR2(20) NOT NULL,
  effective_from DATE,
  effective_to   DATE,
  chunk_text     CLOB NOT NULL,
  embedding_model VARCHAR2(100) NOT NULL,
  embedding      VECTOR(1536, FLOAT32) NOT NULL
);
```

`VECTOR(1536, FLOAT32)`의 1536은 예시 차원입니다. 임베딩 모델이 768차원을 만든다면 768이어야 하고, 모델을 바꾸면 단순히 열의 숫자를 바꾸는 것으로 끝나지 않습니다. 기존 벡터와 새 벡터를 같은 거리로 비교해도 되는지, 재임베딩 기간 동안 두 모델을 어떻게 구분할지, 인덱스를 언제 다시 만들지 설계해야 합니다. 모델을 교체하면서 예전 벡터와 새 벡터를 한 열에 섞는 것은 검색 품질과 재현성을 해칠 수 있습니다.

관계형 열을 함께 둔다는 점이 Oracle을 이미 쓰는 조직에서 중요한 이유입니다. `tenant_id`, 공개 범위, 문서 유효 기간, 문서 상태 같은 조건을 벡터 검색의 전후에 SQL로 적용할 수 있습니다. “의미가 비슷한 문서”보다 “이 사용자가 읽을 권한이 있으면서 현재 유효한 문서 중 의미가 비슷한 문서”가 실제 업무 질문에 더 가깝기 때문입니다. 권한 필터를 애플리케이션에서 검색 후 처리하면 권한 없는 문서가 후보나 LLM 프롬프트에 들어갈 위험이 있으므로, 가능한 한 검색 SQL의 조건으로 강제하는 편이 안전합니다.

## 문서 청킹과 임베딩 생성: 인덱스보다 먼저 정할 것

LLM 문서 검색에서 **청킹(chunking)** 은 긴 문서를 검색 가능한 작은 조각으로 나누는 일입니다. 문서 전체를 하나의 벡터로 만들면 한 문서 안에 여러 주제가 섞여 질의와의 관계가 흐려질 수 있습니다. 반대로 너무 작게 자르면 문맥이 끊겨 “이 예외는 앞 단락의 조건에서만 적용된다”는 정보를 잃을 수 있습니다. 청크 크기, 겹침(overlap), 표·코드·제목 처리 방식은 문서 유형에 따라 달라집니다.

Oracle AI Vector Search는 `VECTOR_CHUNKS`와 `VECTOR_EMBEDDING` 같은 Vector Utilities를 제공합니다. 데이터베이스 안에서 수행하는 방식은 SQL 파이프라인·권한·저장 위치를 한 곳에 모을 수 있다는 장점이 있습니다. 반면 임베딩 모델의 위치, GPU 사용, 외부 호출 비용, 민감 문서의 전송 경계, 대량 재처리 시간을 먼저 확인해야 합니다. 외부 애플리케이션에서 임베딩을 만들고 Oracle에 저장하는 방식도 가능하며, 이 경우에는 배치의 멱등성, 실패 재시도, 모델 메타데이터, 입력 텍스트 해시를 관리해야 합니다.

가상의 인사 규정 검색을 생각해 보겠습니다. PDF 한 권을 통째로 넣는 대신 제목·목차·본문 구조를 보존해 ‘휴가 이월’ 절의 각 문단을 청크로 저장합니다. 각 청크에는 원본 문서 ID, 페이지 또는 절 위치, 적용 조직, 유효 기간을 함께 저장합니다. 그러면 검색 결과를 LLM에 전달할 때 근거 문단과 출처 위치를 같이 보여 줄 수 있습니다. 사용자는 답만 받는 것보다 어느 규정의 어느 절인지 확인할 수 있고, 운영자는 잘못된 검색이 청킹 문제인지 임베딩 문제인지 추적하기 쉬워집니다.

## 거리 함수와 SQL: 검색식이 인덱스와 맞아야 한다

Oracle의 `VECTOR_DISTANCE`는 두 벡터 사이 거리를 계산하는 중심 함수입니다. 코사인 거리에는 `<=>`, 유클리드 거리에는 `<->`, 음의 내적에는 `<#>` 같은 축약 연산자도 있습니다. 검색은 보통 질의 벡터와 저장 벡터의 거리를 정렬하고 상위 k개를 가져오는 형태입니다.

```sql
SELECT chunk_id, document_id, chunk_text,
       VECTOR_DISTANCE(embedding, :query_vector, COSINE) AS distance
FROM knowledge_chunk
WHERE tenant_id = :tenant_id
  AND visibility = 'INTERNAL'
  AND CURRENT_DATE BETWEEN effective_from AND effective_to
ORDER BY VECTOR_DISTANCE(embedding, :query_vector, COSINE)
FETCH FIRST 8 ROWS ONLY;
```

이 예시는 설명용입니다. `effective_from`이나 `effective_to`가 NULL일 때의 정책, 시간대, 문서 폐기 상태, 권한 테이블 조인은 실제 요구에 맞게 설계해야 합니다. 중요한 점은 거리 지표입니다. Oracle 문서는 인덱스에 정의한 거리 지표와 SQL의 `VECTOR_DISTANCE` 지표가 충돌하면 해당 벡터 인덱스를 사용하지 않고 정확 검색으로 처리할 수 있다고 설명합니다. 즉, HNSW를 만들고도 쿼리에서 다른 metric을 명시하면 갑자기 느려질 수 있습니다. 성능 문제를 ‘Oracle이 인덱스를 무시한다’고 단정하기 전에 실행 계획, 인덱스 DDL, 실제 SQL의 지표를 함께 확인해야 합니다.

벡터 거리의 작은 값이 가까움을 의미하는 경우가 일반적이지만, 화면에 점수로 보여 줄 때는 거리와 유사도를 혼동하지 않아야 합니다. 거리 0.12와 0.32가 ‘12%와 32% 정답률’을 뜻하지는 않습니다. 사용자에게 표시할 신뢰도 점수는 별도 보정과 평가가 필요합니다. 검색 순위는 “후보를 우선 볼 순서”이지, 문서가 질문의 정답이라는 증명이 아닙니다.

## HNSW와 IVF: 정확 검색과 근사 검색의 선택

벡터가 적다면 모든 행의 거리를 계산하는 **정확 검색(exact search)** 도 단순하고 검증하기 쉽습니다. 벡터 수가 커지면 모든 행과의 거리를 계산하는 비용이 커지므로 **근사 최근접 이웃(ANN, Approximate Nearest Neighbor)** 인덱스를 고려합니다. 근사 검색은 모든 후보를 보지 않는 대신, 충분히 가까운 후보를 빠르게 찾는 방향으로 정확도와 지연을 교환합니다.

Oracle 문서에서 대표적인 벡터 인덱스는 **HNSW(Hierarchical Navigable Small World)** 와 **IVF(Inverted File Flat)** 입니다. HNSW는 여러 층의 이웃 그래프를 메모리 중심으로 탐색해 가까운 벡터를 빠르게 찾는 접근입니다. IVF는 벡터 공간을 여러 파티션 또는 클러스터로 나누고, 질의와 가까운 일부 파티션을 우선 탐색하는 방식입니다. 어느 것이 항상 우월한 것은 아닙니다. 데이터량, 메모리 예산, 갱신 비율, 허용 지연, 목표 재현율(recall), 운영·재빌드 방식에 따라 선택이 달라집니다.

```sql
CREATE VECTOR INDEX knowledge_embedding_hnsw
ON knowledge_chunk (embedding)
ORGANIZATION INMEMORY NEIGHBOR GRAPH
DISTANCE COSINE;
```

위 DDL은 개념 예시입니다. HNSW에는 `NEIGHBORS`, `EFCONSTRUCTION`, 목표 정확도 같은 선택지가 있고, IVF에는 파티션 수와 정확도에 영향을 주는 옵션이 있습니다. 값을 크게 하면 정확도가 좋아질 여지가 있지만 메모리·생성 시간·검색 비용이 늘 수 있습니다. DBA가 해야 할 일은 인터넷의 권장 숫자를 그대로 넣는 것이 아니라, 대표 질의 집합으로 정확 검색을 기준선으로 만들고 근사 검색의 recall·지연·메모리·재빌드 시간을 비교하는 것입니다.

HNSW는 Oracle에서 Vector Pool과도 연관됩니다. Oracle 문서는 `VECTOR_MEMORY_SIZE`가 CDB(Container Database)에서는 Vector Pool의 현재 크기, PDB(Pluggable Database)에서는 허용 최대 사용량과 관련된다고 설명합니다. 특히 Multitenant 환경에서는 한 PDB의 벡터 인덱스가 다른 PDB의 자원을 예기치 않게 압박하지 않도록 용량·테넌트 경계를 고려해야 합니다. 벡터 기능은 애플리케이션의 새 테이블 하나가 아니라 SGA(System Global Area) 메모리 계획과 연결된 DBMS 기능입니다.

## 하이브리드 검색: 의미와 정확한 단어를 경쟁시키지 않는다

벡터 검색은 동의어·자연어 질문에 강점이 있지만, 문서 번호 `HR-2026-17`, 오류 코드 `ORA-xxxxx`, 특정 제품 버전, 조항 번호처럼 정확한 토큰이 핵심인 질의에는 부족할 수 있습니다. 반대로 키워드 검색은 단어가 다르면 관련 문서를 놓칠 수 있습니다. **하이브리드 검색**은 Oracle Text의 전문 검색과 벡터 유사도 검색을 함께 써서 두 신호를 결합하려는 방식입니다.

예를 들어 “19c에서 Data Pump import가 실패할 때 ORA 오류”라는 질문은 버전과 오류 코드의 정확한 일치가 중요하면서도, 사용자가 오류 설명을 자연어로 바꿔 말할 수 있습니다. 키워드 결과와 벡터 결과를 단순히 붙여서 보여 주는 것보다, 어떤 점수로 합칠지·중복 문서를 어떻게 합칠지·권한 필터를 양쪽에 일관되게 적용할지 정해야 합니다. Oracle의 Hybrid Vector Index는 전문 검색과 벡터 검색의 결합을 지원하지만, 인덱스가 있다는 이유만으로 검색 정책이 완성되는 것은 아닙니다.

검색 품질 평가는 질문 세트와 정답 근거 문서가 있어야 합니다. 운영자가 자주 받는 질문, 지원 티켓, 실패한 검색, 짧은 키워드 질의, 긴 자연어 질의를 골고루 모으고, 상위 k개에 정답 문서가 들어오는 비율(Recall@k), 첫 유용한 문서의 순위, 권한 없는 문서가 섞이지 않는지, 인용이 실제 원문과 맞는지를 봅니다. LLM이 최종 답을 잘 썼는지와 검색이 맞았는지를 분리해 평가해야 원인을 고칠 수 있습니다.

## RAG 연계: 검색 결과를 답변의 근거로 쓰는 과정

Oracle AI Vector Search를 RAG에 연결하는 흐름은 보통 다음과 같습니다.

```text
문서 수집 → 구조 보존 청킹 → 임베딩 생성 → Oracle VECTOR 저장·인덱싱
사용자 질문 → 질문 임베딩 → 권한/기간 필터 + 유사도 검색
검색 청크·출처 → LLM 프롬프트 → 답변 + 인용 표시
```

각 화살표에는 실패 방식이 있습니다. 수집 단계에서 문서가 누락되면 검색하지 못하고, 청킹이 나쁘면 필요한 조건이 다른 청크로 찢어집니다. 모델을 바꾸고 일부만 재임베딩하면 같은 검색 공간에서 비교가 깨질 수 있습니다. 권한 필터가 LLM 호출 뒤에 적용되면 민감 텍스트가 이미 외부 모델에 전달될 수 있습니다. 답변 단계에서는 모델이 검색 청크에 없는 내용을 단정할 수 있습니다. 따라서 “근거에 없는 내용은 모른다고 답하라”, “출처 청크 ID를 답과 함께 저장하라”, “검색 결과가 약하면 사람 또는 원문 화면으로 안내하라” 같은 애플리케이션 정책이 필요합니다.

특히 개인정보, 영업 비밀, 인사 문서처럼 민감한 데이터를 임베딩할 때는 원문 권한만 보지 말고 벡터 자체도 민감 데이터 파생물로 다뤄야 합니다. Oracle의 VECTOR 데이터 타입에는 데이터 마스킹·redaction 제약이 있을 수 있으므로, 보안 설계를 뒤늦게 덧붙이지 말고 열 수준 권한, PDB 경계, 접근 감사, 외부 임베딩 API 전송 여부를 초기 설계에 포함해야 합니다. 벡터는 사람이 읽기 어렵다고 해서 무해한 데이터가 아닙니다.

## DBA 운영 체크포인트: 데이터·인덱스·메모리·갱신을 함께 본다

벡터 검색을 운영하는 DBA의 질문은 전통적 인덱스 운영과 닮아 있지만, 새 변수들이 있습니다. 첫째, 벡터의 차원 수와 자료 형식은 저장량과 메모리에 직접 영향을 줍니다. 둘째, 인덱스 정확도·지연·메모리 사이에 트레이드오프가 있습니다. 셋째, 임베딩 모델이 바뀌면 단순 통계 갱신이 아니라 대규모 재생성과 이중 운영 계획이 필요할 수 있습니다.

Oracle 문서는 IVF 인덱스가 기반 테이블의 DML(Data Manipulation Language, 데이터 변경)로 인해 시간이 지나면서 정확도가 낮아질 수 있으며, `DBMS_VECTOR`의 `INDEX_ACCURACY_QUERY`로 확인하고 필요 시 재빌드할 수 있다고 안내합니다. 이것은 ‘인덱스를 한 번 만들면 끝’이라는 생각이 맞지 않음을 보여 줍니다. 문서가 매일 추가·삭제되는 지식 베이스라면, 증분 처리 지연, 삭제된 문서가 검색 후보에 남는지, 인덱스 재구성 창, 롤백, 백업·복구 절차를 운영 문서로 정해야 합니다.

인덱스가 실제로 쓰이는지도 확인해야 합니다. 거리 지표 불일치, 함수로 감싼 거리식, 지원하지 않는 SQL 형태, 파티션 처리 방식에 따라 옵티마이저가 벡터 인덱스를 선택하지 않을 수 있습니다. 사용자는 ‘AI 검색이 느리다’고 말하지만 원인은 인덱스 미사용, 지나치게 넓은 권한 필터, 불필요하게 큰 k, 네트워크 왕복, 임베딩 생성 지연일 수 있습니다. 검색 API 전체를 분해해 DB 검색 시간과 임베딩 시간, LLM 응답 시간을 따로 관찰해야 합니다.

백업·복구·복제 관점도 빼놓을 수 없습니다. 벡터 열과 인덱스가 포함된 테이블은 기존 데이터 수명주기 정책 안에 들어가야 합니다. 특정 기능에는 Data Pump 또는 transportable tablespace 같은 도구의 제한이 있을 수 있으므로, 대규모 벡터 인덱스를 가진 환경에서 복구 리허설을 하지 않고 ‘평소 DB 백업이 있으니 된다’고 가정하면 안 됩니다. Oracle 공식 제한 문서와 해당 배포 버전의 관리자 가이드를 기준으로 검증해야 합니다.

## 모델 교체와 재임베딩: 데이터 마이그레이션으로 취급한다

임베딩 모델은 애플리케이션 라이브러리처럼 즉시 교체하기 쉬워 보이지만, 이미 저장한 벡터의 의미 공간을 바꾸는 변경입니다. 새 모델이 더 좋은 다국어 검색을 제공하더라도, 이전 모델의 768차원 벡터와 새 모델의 1536차원 벡터를 같은 열에서 비교할 수 없을 수 있습니다. 차원 수가 같아도 학습 방식과 정규화가 다르면 거리의 의미가 달라질 수 있습니다. 그러므로 모델 변경은 DB 스키마·데이터·인덱스·검색 API의 동시 변경으로 봐야 합니다.

안전한 전환의 한 방식은 새 모델용 벡터 열 또는 별도 청크 테이블을 만들고, 원본 문서를 재청킹·재임베딩한 뒤 평가 질의로 이전과 새 결과를 비교하는 것입니다. 전환 중에는 검색 API가 모델 버전별 인덱스를 명시적으로 선택하게 하고, 이전 인덱스를 바로 삭제하지 않습니다. 품질·지연·비용·권한 필터를 확인한 뒤 트래픽을 단계적으로 옮기고, 롤백 가능한 기간이 지난 뒤 이전 데이터를 폐기합니다. 이 과정은 일반적인 대규모 데이터 마이그레이션과 마찬가지로 대상 수, 실패 항목, 재처리 큐, 완료 기준을 기록해야 합니다.

청크 전략을 바꾸는 경우도 같습니다. 예를 들어 처음에는 1,000자 단위로 자르다가 표와 제목을 보존하는 구조 기반 청킹으로 바꾸면, 문서당 청크 수와 검색 순위가 달라집니다. 단순히 새 임베딩만 만들지 말고, 답변에 표시하는 페이지·절 위치, 인용 링크, 중복 제거 규칙까지 함께 검증해야 합니다. 특히 법무·인사·보안 문서에서는 한 문단만 보여 주면 예외 조항을 놓칠 수 있으므로, 검색 후 인접 청크를 함께 보여 줄지 같은 제품 정책도 필요합니다.

## 평가 세트와 장애 시나리오: ‘비슷함’을 업무 기준으로 바꾼다

벡터 검색의 품질은 임베딩 차원 수나 인덱스 이름으로 보증되지 않습니다. 평가용 질문과 기대 근거 문서를 먼저 만드는 편이 좋습니다. 질문에는 사용자가 실제로 쓰는 짧은 키워드, 오타·동의어가 있는 자연어, 여러 조건이 결합된 질문, 정답 문서가 존재하지 않는 질문을 섞습니다. 각각에 대해 적어도 하나의 유효한 근거 청크와, 절대 노출되면 안 되는 권한 밖 문서를 정의합니다.

검색 단계에서는 상위 3개·5개·10개 결과에 기대 문서가 포함되는지, 첫 번째 결과가 실제로 유용한지, 다른 테넌트 문서가 섞이지 않는지 확인합니다. 생성 단계까지 포함하면 LLM이 인용된 청크만으로 답했는지, 근거가 없을 때 모른다고 했는지, 오래된 문서보다 최신 유효 문서를 우선했는지도 봅니다. 이 평가를 배포 전과 모델·인덱스·청킹 변경 후에 반복하면, ‘검색이 빨라졌다’와 ‘검색 품질이 유지됐다’를 구분할 수 있습니다.

장애 시나리오도 작성해야 합니다. 임베딩 생성 API가 느리거나 실패할 때 문서 등록은 중단할지, 벡터 없이 원문만 먼저 저장하고 비동기로 재처리할지 결정합니다. 벡터 인덱스가 재빌드 중일 때 검색은 정확 검색으로 폴백할지, 읽기 전용 기존 인덱스를 유지할지 정합니다. 질문 임베딩과 저장 임베딩의 모델 버전이 맞지 않을 때는 조용히 결과를 내기보다 요청을 거부하거나 호환되는 인덱스를 선택해야 합니다. 이 정책이 없으면 장애는 단순한 500 오류가 아니라 ‘그럴듯하지만 근거 없는 답변’으로 나타날 수 있습니다.

## 관계형 필터는 성능 최적화 이전에 보안 정책이다

벡터 검색 설명에서 `WHERE tenant_id = :tenant_id` 같은 조건은 자주 성능 최적화 예시로만 등장합니다. 하지만 실제로는 가장 중요한 보안 경계일 수 있습니다. 권한 없는 청크가 상위 검색 결과에 한 번이라도 들어가면, LLM에 전달되거나 로그에 남거나 캐시에 저장될 수 있습니다. 나중에 화면에서 결과를 숨겨도 이미 데이터 노출 경계는 넘은 셈입니다.

따라서 검색 요청을 만드는 API는 사용자·조직·역할·문서 상태·유효 기간을 신뢰할 수 있는 서버 측 정보로 계산하고 SQL 바인드 변수로 전달해야 합니다. 클라이언트가 보낸 `tenant_id`나 `visibility`를 그대로 믿으면 다른 테넌트 데이터를 검색하도록 조작될 수 있습니다. Oracle의 VPD(Virtual Private Database), 행 수준 보안, 애플리케이션 컨텍스트 같은 기존 보안 기능을 쓰는 환경이라면 벡터 테이블과 인덱스 조회에도 정책이 일관되게 적용되는지 테스트해야 합니다.

성능 때문에 필터를 검색 뒤로 미루는 설계는 특히 조심해야 합니다. 인덱스가 많은 후보를 빠르게 찾더라도, 그 후보 중 권한이 있는 결과가 적으면 사용자에게 빈 결과나 낮은 품질 결과가 돌아올 수 있습니다. 반대로 관계형 조건이 매우 선택적이면 파티션·일반 인덱스·벡터 인덱스를 어떻게 조합할지 실행 계획을 검토해야 합니다. 보안 요구와 성능 최적화는 분리된 일이 아니라 같은 SQL을 설계하는 문제입니다.

## 도입 순서: 작은 평가 데이터로 기준선을 만든다

처음부터 모든 사내 문서를 임베딩하고 고가용성 인덱스를 만들기보다, 접근 권한이 명확한 작은 문서 묶음과 실제 질문 30~50개 정도로 시작하는 편이 좋습니다. 먼저 정확 검색 결과를 기준선으로 저장하고, 청킹·모델·거리 지표를 바꾸었을 때 상위 결과와 인용 위치가 어떻게 달라지는지 비교합니다. 이 단계에서 문서 누락, 날짜 메타데이터 오류, 권한 필터 누락을 발견하면 인덱스 튜닝보다 먼저 데이터 파이프라인을 고쳐야 합니다.

운영 전에는 문서 삭제·권한 회수·모델 교체·인덱스 재구성·복구 리허설의 책임자를 정합니다. 벡터 검색이 새 기능이더라도 원본 문서의 변경 관리와 보안 정책을 우회해서는 안 됩니다. DBA와 데이터 소유자, 애플리케이션 담당자가 같은 평가 결과를 보고 적용 범위를 넓히는 방식이 가장 안전합니다.

검색 품질이 기대보다 낮을 때도 인덱스 파라미터부터 바꾸지 않습니다. 먼저 원문이 수집됐는지, 청크가 질문의 조건을 보존했는지, 질의와 문서가 호환되는 임베딩 모델로 생성됐는지, SQL의 권한·기간 필터가 의도대로 적용됐는지 확인합니다. 이 순서를 지키면 AI 기능처럼 보이는 문제를 데이터 품질·권한·운영 문제로 정확히 분리할 수 있습니다. 기준 질의와 변경 이력을 함께 보존합니다. 이 기록은 다음 모델 교체의 출발점이 됩니다.

## 한계와 적용 기준 Q&A

### Q. 기존 Oracle에 문서가 있으니 벡터 열만 추가하면 RAG가 되나요?

A. 저장은 시작일 뿐입니다. 문서를 어떤 단위로 나눌지, 어떤 모델로 임베딩할지, 질문과 문서에 같은 모델을 쓸지, 권한과 유효 기간을 어디서 강제할지, 검색 결과가 없을 때 어떻게 답할지 정해야 합니다. 특히 오래된 문서와 폐기 문서를 그대로 넣으면 검색은 잘 되어도 업무상 잘못된 답의 근거가 될 수 있습니다.

### Q. HNSW와 IVF 중 무엇을 선택해야 하나요?

A. 데이터 규모와 변경량, 메모리, 목표 recall, 질의 지연, 재구성 방식에 따라 다릅니다. 작은 데이터에서는 정확 검색이 가장 단순한 기준선일 수 있습니다. 운영 후보를 고르려면 실제 질문 세트로 정확 검색 대비 recall과 지연을 측정하고, 데이터 갱신 뒤 정확도 유지와 재빌드 비용까지 비교해야 합니다. 인덱스 이름만 보고 선택하지 않는 것이 중요합니다.

### Q. 벡터 거리 점수가 높으면 LLM 답변도 신뢰해도 되나요?

A. 아닙니다. 거리 점수는 선택한 임베딩 모델 공간에서의 가까움입니다. 질문의 전제가 틀렸거나, 문서가 오래됐거나, 청크에 예외 조건이 빠졌다면 가까운 문서도 잘못된 근거가 될 수 있습니다. 답변에는 원문 인용을 붙이고, 중요한 의사결정에는 원문 검토·업무 규칙·사람의 승인을 남겨야 합니다.

### Q. 벡터 데이터는 암호화나 마스킹을 신경 쓰지 않아도 되나요?

A. 아니오. 임베딩은 원문을 그대로 읽기 어렵게 만들지만, 민감한 정보에서 파생된 데이터이며 접근 통제·보관·외부 전송 정책의 대상입니다. Oracle VECTOR 타입의 기능 제약도 별도로 확인해야 합니다. 원문 권한, 검색 SQL의 필터, API 로그, 외부 모델 호출, 백업본을 한 흐름으로 검토해야 합니다.

## 마무리

Oracle AI Vector Search는 관계형 데이터와 의미 검색을 같은 SQL·권한·트랜잭션 경계에서 다룰 수 있게 해 주는 기능입니다. 그러나 성공 여부는 벡터 인덱스 DDL 한 줄보다 문서 품질, 임베딩 일관성, 거리 지표, 권한 필터, 운영 관측, 평가 세트에 달려 있습니다. 정확 검색을 기준선으로 만들고, HNSW·IVF·하이브리드 검색을 실제 업무 질문으로 비교하며, 인덱스와 모델의 수명주기를 DBMS 운영 항목으로 관리하는 방식이 안전한 출발점입니다.
