LLM 기능을 배포한 뒤 품질이 좋아졌는지 묻는 질문은 생각보다 어렵습니다. 모델을 바꾸고 답변이 더 자연스러워 보인다고 해도, 중요한 고객 문의를 잘못 처리하거나 근거 없는 내용을 자신 있게 말한다면 실제 품질은 낮아질 수 있습니다. 프롬프트 한 줄, 검색 문서, 모델 버전, 도구 호출 정책처럼 여러 요소가 함께 답변을 바꾸기 때문에 전통적인 단위 테스트의 단일 정답 비교만으로는 충분하지 않을 때가 많습니다.

**LLM evaluation(Evals)** 은 모델 또는 LLM 애플리케이션이 요구한 행동을 얼마나 만족하는지 반복 가능하게 측정하는 과정입니다. 평가는 모델 순위를 매기는 행사가 아니라, 제품이 반드시 지켜야 할 규칙을 배포 전후에 확인하는 품질 장치입니다. 이 글은 평가셋을 무엇으로 만들지, 정확한 정답이 없는 답변을 어떻게 채점할지, 자동 평가와 사람 검토를 어떻게 나눌지, 프롬프트·RAG 변경을 회귀 테스트로 다루는 방법을 정리합니다.

## 먼저 알아둘 기반 기술

**생성형 AI** 는 입력을 분류하는 데서 끝나지 않고 다음 토큰을 예측해 문장·코드·도구 호출을 생성합니다. 같은 질문에도 temperature, 모델 버전, 시스템 프롬프트, 검색 결과 순서에 따라 답변이 달라질 수 있습니다. 따라서 “항상 같은 문자열이 나오는가”만 검사하면 창의적인 표현 차이를 오류로 볼 수 있고, 반대로 사실 오류를 놓칠 수 있습니다.

**RAG(Retrieval-Augmented Generation)** 는 질문과 관련된 문서를 검색해 모델의 입력 맥락으로 제공하는 구조입니다. RAG 품질은 모델의 문장 능력뿐 아니라 검색된 문서가 맞는지, 문서가 최신인지, 답변이 제공된 근거를 벗어나지 않는지에 좌우됩니다. LLM 평가에서는 생성 결과와 검색 결과를 분리해 볼 수 있어야 원인을 좁힐 수 있습니다.

**회귀 테스트(regression test)** 는 변경 뒤 이미 동작하던 중요한 행동이 나빠지지 않았는지 확인합니다. LLM 애플리케이션에서는 모델 교체, 프롬프트 수정, 검색 인덱스 갱신, 도구 API 변경이 회귀 원인이 될 수 있습니다. 평가는 한 번의 데모가 아니라 이 변경들을 안전하게 반복하기 위한 기준선입니다.

## 무엇을 평가할지 먼저 제품 계약으로 번역한다

평가를 시작할 때 “답변 품질”이라는 큰 목표만 쓰면 측정이 흔들립니다. 대신 사용자가 완료하려는 작업과 금지된 행동을 문장으로 적습니다. 예를 들어 사내 정책 검색 봇이라면 “최신 승인 문서의 근거를 인용해 답하고, 근거가 없으면 추측하지 않고 담당 부서를 안내한다”가 계약입니다. 일정 관리 에이전트라면 “사용자 확인 없이 외부 일정을 생성하지 않으며, 생성 전 대상·시간·시간대를 명확히 확인한다”가 계약입니다.

한 계약은 보통 여러 평가 항목으로 나뉩니다. 검색 봇에는 문서 검색 적합성, 인용의 정확성, 답변 완결성, 근거 없는 주장 금지, 개인정보 노출 금지가 있을 수 있습니다. 에이전트에는 도구 선택, 인자 검증, 권한 확인, 실패 시 안전한 중단, 최종 사용자 메시지가 포함됩니다. 평균 하나로 합치기 전에 어떤 항목이 실패하면 배포를 막아야 하는지 정해야 합니다.

평가 항목은 실제 위험에 비례해야 합니다. 블로그 문체가 조금 달라지는 문제와 권한 없는 사용자가 다른 사람의 데이터를 조회하는 문제는 같은 가중치를 가질 수 없습니다. 사용자가 피해를 보거나 법적·보안 문제가 될 수 있는 행동은 정확한 통계 점수보다 명확한 통과 조건과 사람 검토를 우선합니다.

## 평가셋: 사용자의 현실을 작게 대표한다

좋은 평가셋은 질문을 많이 모은 파일이 아니라, 제품이 마주칠 중요한 상황을 대표하는 사례 모음입니다. 시작점은 실제 사용 로그, 고객 문의, 장애 회고, FAQ, 정책 변경입니다. 다만 개인정보·비밀 정보는 제거하거나 합성해야 합니다. 실제 로그를 그대로 평가셋에 넣으면 재현성은 높아 보여도 데이터 보안과 보존 정책을 위반할 수 있습니다.

각 사례에는 입력만이 아니라 맥락과 기대 기준을 기록합니다. RAG라면 사용할 수 있는 문서 집합과 문서 버전, 정답 또는 반드시 포함할 사실, 금지할 주장, 필요한 인용을 함께 둡니다. 에이전트라면 초기 상태, 허용 도구, 권한, 기대 도구 호출 또는 금지 호출, 최종 상태를 적습니다. 이런 메타데이터가 있어야 평가 실패가 모델 문제인지 검색·권한·도구 정책 문제인지 구분할 수 있습니다.

평가셋은 고정된 시험지가 아닙니다. 새 기능·새 문서·새로운 오용 사례가 생기면 사례를 추가하고, 더 이상 현실을 대표하지 않는 사례는 이유와 함께 교체합니다. 단, 점수가 나쁘다는 이유로 어려운 사례를 삭제하면 평가는 좋아 보이지만 제품은 좋아지지 않습니다. 실패 사례는 개선해야 할 계약을 보여 주는 자산입니다.

## 정답 비교와 기준 기반 채점

구조화된 출력에는 비교적 명확한 자동 평가를 만들 수 있습니다. JSON schema를 만족하는지, 지정한 필드를 빠뜨리지 않았는지, 도구 호출 인자가 유효한지, 답변에 필수 정책 문구가 있는지를 검사합니다. 이런 평가는 빠르고 재현 가능하며 LLM을 채점자로 쓰지 않아도 됩니다. 가능한 한 먼저 이런 결정적 검사를 만듭니다.

문장형 답변은 정확히 같은 정답 문장을 요구하기 어렵습니다. 이때는 **rubric(채점 기준)** 을 사용합니다. 예를 들어 “근거 문서의 결론을 정확히 말했는가”, “근거에 없는 수치를 만들지 않았는가”, “불확실할 때 모른다고 말했는가”, “사용자가 요구한 형식으로 답했는가”처럼 관찰 가능한 질문으로 나눕니다. 하나의 막연한 ‘좋음’ 점수보다 기준별 합격·불합격과 근거를 남기는 편이 개선에 유리합니다.

LLM-as-a-judge는 다른 LLM에게 rubric에 따라 답변을 평가하게 하는 방법입니다. 사람 검토 비용을 줄이는 데 도움이 될 수 있지만, judge도 편향·환각·문체 선호를 가질 수 있습니다. 따라서 judge의 판단이 사람 평가와 어느 정도 일치하는지 검증하고, 민감한 안전 gate를 judge 한 번의 점수에만 의존하지 않습니다. 평가 모델과 대상 모델이 같은 오류를 공유할 가능성도 고려합니다.

## RAG 평가는 검색과 생성을 나눠 본다

RAG 답변이 틀렸을 때 모델만 탓하면 해결이 늦어집니다. 먼저 retrieval 단계에서 정답 근거 문서가 상위 결과에 들어왔는지, 오래된 문서가 더 높게 나온 것은 아닌지, chunk가 필요한 문맥을 잘라 버리지 않았는지 평가합니다. 이 단계의 지표는 recall@k처럼 필요한 문서가 상위 k개 안에 있는지, 또는 사람이 정의한 관련성 기준을 만족하는지로 볼 수 있습니다.

그 다음 generation 단계에서 모델이 제공된 근거를 충실히 사용했는지 평가합니다. 문서에 없는 주장을 덧붙이지 않았는지, 서로 다른 문서의 조건을 섞지 않았는지, 인용이 실제 문장을 뒷받침하는지를 봅니다. 검색 실패와 생성 실패를 분리하면 인덱스를 개선해야 할지, 프롬프트를 바꿔야 할지, 문서를 정리해야 할지 판단할 수 있습니다.

문서 변경도 회귀 원인입니다. 정책 문서가 새로 승인되거나 폐기됐을 때, 평가셋의 문서 버전과 정답 기준을 함께 갱신해야 합니다. 과거 문서를 기준으로 모델을 평가하면 최신 답변을 오답으로 만들 수 있습니다. RAG 평가는 모델 평가이면서 동시에 지식 관리 품질 점검이기도 합니다.

## 에이전트 평가는 결과뿐 아니라 경로를 본다

도구를 쓰는 에이전트는 최종 문장만 평가하면 부족합니다. 같은 “예약 완료” 답변이라도 실제로는 잘못된 사람의 일정을 수정했거나, 사용자 확인 없이 외부 API를 호출했을 수 있습니다. 따라서 평가에는 선택한 도구, 호출 순서, 인자, 권한 검사, 실패 처리, 최종 상태를 포함합니다.

안전한 에이전트 평가는 금지 경로를 명시합니다. 예를 들어 모호한 요청에는 일정 생성 도구를 호출하지 않아야 하고, 읽기 권한만 가진 사용자는 수정 도구를 호출하지 않아야 하며, 도구 오류가 나면 성공했다고 말하지 않아야 합니다. 이런 평가는 “도구를 성공적으로 사용했는가”뿐 아니라 “사용하지 말아야 할 때 멈췄는가”를 확인합니다.

도구 호출 테스트는 가능한 경우 테스트 환경의 fake API나 샌드박스를 사용합니다. 실제 고객 데이터와 실제 결제·메일·삭제 작업을 평가 루프에서 반복하면 비용과 위험이 커집니다. fake가 실제 API 계약에서 멀어지지 않도록 계약 테스트를 병행하고, 소수의 승인된 통합 시나리오만 실제 샌드박스에서 확인합니다.

## 한계와 적용 기준 Q&A

### Q. 공개 벤치마크 점수가 높으면 제품 품질도 높은가요?

A. 아닙니다. 공개 벤치마크는 일반 능력을 가늠하는 신호일 뿐, 우리 문서·언어·권한·도구·사용자 흐름을 대표하지 않을 수 있습니다. 제품 계약을 담은 자체 평가셋이 필요합니다.

### Q. 모든 답변을 사람이 읽어야 하나요?

A. 결정적 형식 검사와 rubric 기반 자동 평가는 넓게 적용할 수 있습니다. 다만 안전·법무·금전·고객 영향이 큰 사례, 자동 평가가 불일치하는 사례, 새 정책 영역은 사람 검토를 우선합니다.

### Q. 평가 점수는 어느 정도면 배포 가능한가요?

A. 보편적인 숫자는 없습니다. 기능별 기준선을 정하고, 중요한 안전 항목은 평균과 무관하게 0건 실패를 요구할 수 있습니다. 이전 안정 버전보다 개선됐는지와 실패 사례의 심각도를 함께 봅니다.

### Q. 프롬프트를 조금 바꿨는데도 전체 평가를 돌려야 하나요?

A. 사용자 행동이나 도구 선택, 근거 제시에 영향을 줄 수 있다면 회귀 평가 대상입니다. 변경 범위에 맞는 빠른 핵심 suite와 배포 전 전체 suite를 나누면 비용을 조절할 수 있습니다.

## 마무리

LLM 평가는 답변을 점수로 줄 세우는 일이 아니라, 제품이 어떤 행동을 약속하는지 테스트 가능한 기준으로 바꾸는 일입니다. 실제 사용자 상황을 대표하는 평가셋, 결정적 검사와 rubric, 검색·생성·도구 경로의 분리, 사람 검토의 안전망을 함께 설계해야 합니다. 작은 핵심 사례부터 시작해 변경마다 같은 기준으로 비교하면, 모델과 프롬프트를 바꾸는 속도와 사용자에게 지키는 품질을 함께 높일 수 있습니다.

## 평가셋을 구성하는 네 종류의 사례

평가셋은 행복 경로만 모아서는 제품을 보호하지 못합니다. 첫째는 **대표 정상 사례**입니다. 실제 사용자가 자주 하는 질문과 작업을 담아, 기본 기능이 변했을 때 빠르게 회귀를 잡습니다. 둘째는 **경계 사례**입니다. 질문이 짧거나 길고, 날짜·단위·언어가 섞이고, 여러 조건이 충돌하는 상황처럼 해석이 어려운 입력을 포함합니다. 셋째는 **안전 사례**입니다. 근거가 없을 때 추측하지 않는지, 민감 정보를 요구받았을 때 거절하고 대안을 안내하는지, 권한 없는 도구 호출을 하지 않는지 확인합니다. 넷째는 **과거 실패 사례**입니다. 실제 장애·고객 이슈·검토에서 발견한 잘못된 답변을 재발 방지 테스트로 남깁니다.

각 사례가 너무 비슷하면 점수는 안정적으로 보여도 일반화된 품질을 말하지 못합니다. 예를 들어 정책 검색 봇이 동일한 문서의 문장만 바꾼 질문에 잘 답한다고 해서, 문서가 없거나 서로 상충하는 정책에도 안전하게 행동한다는 뜻은 아닙니다. 질문 유형, 문서 상태, 사용자 권한, 언어, 입력 길이, 실패 유형을 분포로 보면서 빈 영역을 채웁니다.

사례 수를 늘릴 때는 출처와 버전을 함께 관리합니다. 사용 로그에서 유래한 사례인지, 사람이 작성한 합성 사례인지, 어떤 정책 문서 버전을 기준으로 정답을 만들었는지 기록합니다. 이 정보가 없으면 문서가 바뀌었을 때 모델 회귀와 평가셋 노후화를 구별할 수 없습니다. 평가셋도 코드처럼 리뷰·버전 관리·변경 이력이 필요합니다.

## 평가 기준을 점수표가 아니라 판정 규칙으로 쓴다

좋은 rubric은 “도움이 되는가?”처럼 추상적이지 않습니다. 예를 들어 내부 HR 정책 질문에는 (1) 최신 승인 문서에서 답을 찾았는가, (2) 정책의 조건과 예외를 빠뜨리지 않았는가, (3) 근거 문서에 없는 내용을 사실처럼 말하지 않았는가, (4) 불확실하면 담당 부서를 안내했는가, (5) 개인정보를 노출하지 않았는가처럼 나눌 수 있습니다. 각 기준은 평가자나 judge가 답할 수 있는 질문이어야 합니다.

등급도 제품 결정에 맞게 단순화합니다. 형식·권한·근거 없는 행동처럼 절대 허용하지 않는 항목은 pass/fail로 두고, 문체·간결성처럼 선호가 섞이는 항목은 1~5점 또는 pairwise 비교로 둘 수 있습니다. 평균 점수가 높아도 치명적인 fail이 하나 있으면 배포를 막아야 하는 경우가 있으므로, 합계 점수와 gate를 분리합니다.

자동 judge를 사용할 때는 prompt 자체도 평가 대상입니다. judge에게 정답 근거, 평가 rubric, 출력 형식, 금지할 추측을 충분히 제공하고, 일부 표본을 사람이 이중 평가해 judge와의 일치도를 봅니다. judge가 길고 자신감 있는 답변을 무조건 높게 주거나, 특정 모델의 표현을 선호한다면 점수는 품질 대신 문체를 측정할 수 있습니다. judge 결과에는 점수뿐 아니라 근거와 인용한 문장을 남겨 검토 가능하게 합니다.

## 변경 종류별 회귀 평가 전략

모델 버전을 바꾸면 모든 답변이 달라질 수 있으므로 전체 평가셋을 비교합니다. 하지만 프롬프트의 문구 하나, 검색 chunk 크기, tool schema처럼 작은 변경마다 모든 비용이 큰 평가를 돌리기는 어렵습니다. 이때는 빠른 **smoke suite** 와 더 넓은 **release suite** 를 나눕니다. smoke suite에는 권한·도구 호출·핵심 업무·최근 장애처럼 절대 깨지면 안 되는 사례를 넣고, pull request 단계에서 빠르게 실행합니다. release suite는 언어·경계·장기 회귀 사례를 넓게 포함해 배포 전 또는 정기적으로 실행합니다.

변경 전 기준선도 보존합니다. 새 모델이 전체 평균은 좋아졌지만 한국어 정책 질문과 특정 안전 사례에서 나빠질 수 있습니다. 이전 안정 버전과 새 후보를 같은 입력·같은 문서·가능하면 같은 추론 설정에서 비교하고, 차이가 난 사례를 사람이 확인합니다. “새 모델이 더 좋아 보인다”가 아니라 어떤 사용자 작업이 좋아지고 어떤 위험이 생겼는지를 기록해야 합니다.

비용과 지연도 평가에 포함할 수 있습니다. 답변 품질이 약간 올랐지만 평균 응답 시간이 두 배가 되거나 도구 호출 횟수가 급증하면 제품 요구에 맞지 않을 수 있습니다. 다만 비용 지표만으로 짧은 답변을 선호하게 만들지 않도록, 정확성·안전·완결성 gate를 먼저 통과한 후보끼리 효율을 비교하는 순서가 좋습니다.

## 실제 서비스 신호와 오프라인 평가의 관계

오프라인 평가셋은 변경 전 비교를 빠르게 만들지만, 모든 실제 사용 패턴을 담지는 못합니다. 배포 뒤에는 사용자의 재질문 비율, 작업 완료율, 도구 오류, 사람 상담으로 전환된 비율, 부정 피드백 같은 온라인 신호를 봅니다. 하지만 사용자가 재질문하지 않았다고 만족했다는 뜻은 아닐 수 있고, 클릭 지표가 사실성을 보장하지도 않습니다. 온라인 지표는 오프라인 평가를 대체하지 않고, 평가셋의 빠진 사례를 찾는 보완 신호입니다.

사용자 피드백 버튼도 평가 데이터의 일부로 다룰 수 있습니다. 단순 좋아요·싫어요보다 “근거가 틀림”, “최신 정보 아님”, “답변이 없음”, “안전하지 않음” 같은 선택지를 제공하면 어떤 평가 기준을 보강해야 할지 알기 쉽습니다. 피드백에 사용자 개인정보와 비밀 텍스트가 섞일 수 있으므로 보존 기간·접근 권한·마스킹 정책을 먼저 정해야 합니다.

새로운 실패가 발견되면 모델을 즉시 바꾸기보다 원인을 분리합니다. 검색 문서가 없었는지, 시스템 프롬프트가 우선순위를 잘못 전달했는지, tool API가 실패했는지, 사용자의 질문이 모호했는지 확인합니다. 그 뒤 해당 유형을 최소 재현 평가 사례로 만들고, 어떤 변경이 이를 고치는지 비교합니다. 이 순환이 없으면 같은 오류를 다른 표현으로 반복할 가능성이 큽니다.

## 사람 검토를 효율적으로 배치하기

사람 검토는 자동화가 실패한 뒤에만 하는 벌이 아닙니다. 제품의 정의가 아직 불분명하거나, 안전·법무·도메인 전문성이 필요한 영역에서는 사람이 정답 기준을 만드는 과정이 핵심입니다. 검토자는 가능한 한 rubric과 근거 문서를 공유하고, 사례의 출처와 사용자 맥락을 보며 판단해야 합니다. “좋다/나쁘다”만 남기면 다음 모델·프롬프트 개선으로 연결하기 어렵습니다.

둘 이상의 검토자가 같은 사례를 다르게 판단하는 것은 실패가 아니라 계약이 모호하다는 신호일 수 있습니다. 일치하지 않는 사례를 모아 정책·제품 담당자와 기준을 합의하고, 그 결과를 rubric과 예시로 되돌립니다. 평가자 간 일치도는 자동 평가를 신뢰할 수 있는지와 제품 기준이 충분히 명확한지를 함께 점검하는 도구입니다.

검토 비용이 큰 경우에는 위험 기반 샘플링을 합니다. 새 모델에서 점수 차이가 큰 사례, judge가 불확실하다고 표시한 사례, 민감 도메인, 신규 도구 호출, 실제 사용자 불만이 있었던 영역을 우선 검토합니다. 모든 답변을 사람이 읽지 않아도, 사람이 봐야 할 답변을 놓치지 않는 설계를 만들 수 있습니다.

## 운영 환경의 안전 장치

평가에서 통과한 모델도 운영에서는 예측하지 못한 입력을 받습니다. 답변 길이 제한, 허용된 도구 목록, 인자 검증, 외부 작업 전 사용자 확인, rate limit, 감사 로그 같은 실행 경계가 필요합니다. eval은 이 경계가 요구대로 동작하는지 검증하지만, 경계 자체를 대신하지는 않습니다. 특히 권한·삭제·결제·메일 발송처럼 되돌리기 어려운 도구에는 사람이 승인하거나 명시적 확인을 받는 흐름을 기본으로 둡니다.

프롬프트 인젝션처럼 검색 문서나 사용자 입력이 모델 행동을 바꾸려는 경우도 평가 사례로 포함합니다. 신뢰하지 않는 텍스트에 있는 “이전 지시를 무시하라” 같은 문구를 도구 호출 권한으로 해석하지 않고, 시스템 정책과 허용 도구 범위를 유지하는지 확인합니다. 완벽한 차단을 약속하기보다, 입력을 신뢰 경계별로 분리하고 위험 도구에 추가 검증을 두는 것이 현실적인 방어입니다.

운영 로그에는 평가와 연결 가능한 버전 정보를 남깁니다. 모델 ID, 시스템 프롬프트 버전, 검색 인덱스 버전, tool schema 버전, 안전 정책 버전을 기록하면, 특정 오류가 어떤 조합에서 늘었는지 추적할 수 있습니다. 단, 원문 대화와 도구 인자에는 민감 정보가 있을 수 있으므로 최소 수집·마스킹·보존 기간을 지켜야 합니다.

## 도입 순서

처음부터 수천 개 사례와 복잡한 judge 파이프라인을 만들 필요는 없습니다. 먼저 서비스의 가장 중요한 작업 다섯~스무 개를 골라, 입력·근거·기대 행동·금지 행동을 명시합니다. JSON 형식, tool 호출 여부, 필수 문구처럼 결정적으로 검사할 수 있는 항목을 먼저 자동화합니다. 다음으로 사실성·완결성처럼 문맥이 필요한 항목에 작은 rubric과 사람 검토를 붙입니다.

그 후 변경 전후 비교를 CI에 연결합니다. 작은 변경에는 핵심 suite를, 출시 후보에는 넓은 suite를 실행하고, 결과에서 새 fail과 기존 fail을 구분합니다. 실패 사례를 숨기지 않고 backlog와 평가셋에 남기며, 사람 검토 결과로 기준을 다듬습니다. 평가 시스템도 한 번에 완성되는 플랫폼이 아니라 제품과 함께 자라는 테스트 자산입니다.

가장 중요한 것은 점수를 목표로 만들지 않는 것입니다. 점수가 올라가도 사용자의 핵심 작업이 실패하거나 안전한 중단이 사라지면 품질은 나빠진 것입니다. 평가가 제품 계약을 비추는 거울로 남도록, 숫자 뒤의 사례와 실패 이유를 항상 함께 봐야 합니다.

## 평가 결과를 읽고 의사결정하는 방법

평가 실행이 끝났을 때 평균 점수 하나만 보고 모델을 고르기 쉽습니다. 그러나 평균은 서로 다른 실패를 가릴 수 있습니다. 예를 들어 백 개 사례 중 아흔아홉 개의 문체 점수가 조금 올랐어도, 한 개의 권한 검증 실패가 새로 생겼다면 해당 후보는 배포하면 안 될 수 있습니다. 결과 화면은 전체 점수와 함께 필수 gate의 실패 수, 이전 버전에서 새로 실패한 사례, 기존에 실패했지만 개선된 사례를 분리해서 보여 주어야 합니다.

실패 사례는 우선 영향도와 재현성으로 분류합니다. 특정 문서가 바뀌어 정답 기준이 낡은 경우, 검색 인덱스가 문서를 찾지 못한 경우, 모델이 제공된 근거를 왜곡한 경우, 도구 호출 정책을 어긴 경우는 해결 방식이 다릅니다. 같은 “오답”이라는 라벨 아래에 모두 모으면 프롬프트만 계속 고치게 됩니다. 사례의 입력, 사용한 문서·도구 버전, 실제 출력, rubric 항목, 담당자를 남기면 다음 변경에서 같은 실패를 확인할 수 있습니다.

배포 기준도 등급으로 정합니다. 예를 들어 매 pull request에서는 JSON 형식·권한·도구 호출 같은 결정적 gate와 핵심 업무 사례를 통과해야 합니다. 출시 직전에는 더 넓은 언어·경계 사례를 포함하고, 안전 항목은 새 실패가 없어야 한다고 정할 수 있습니다. 정기 평가는 문서와 모델 변경이 없더라도 judge drift나 외부 도구 동작 변화, 축적된 실패 사례를 점검하는 역할을 합니다. 이렇게 기준을 나누면 빠른 개발과 무분별한 배포 사이에서 선택할 근거가 생깁니다.

## 재현 가능한 평가 실행 기록

LLM 출력은 샘플링, 도구 응답, 검색 인덱스, 시간에 따라 달라질 수 있습니다. 그래서 “지난주에는 통과했다”는 말만으로는 원인을 찾기 어렵습니다. 가능한 범위에서 모델 이름과 버전, 시스템 프롬프트 버전, temperature 같은 생성 설정, 평가셋 커밋, 검색 문서 스냅샷, tool schema 버전, 실행 시각을 한 실행 결과에 묶어 기록합니다. 완전히 동일한 출력을 보장하지 못하더라도, 무엇이 달랐는지는 추적할 수 있어야 합니다.

외부 도구를 사용하는 에이전트는 테스트용 응답을 고정할 필요가 있습니다. 환율·재고·일정처럼 실시간으로 바뀌는 API를 그대로 쓰면 모델이 아니라 외부 상태 때문에 평가가 흔들립니다. 읽기 전용 fixture나 샌드박스 계정으로 정상·오류·권한 거부 응답을 재현하고, 실제 통합 환경 확인은 별도 소수 시나리오로 제한합니다. 테스트 fixture가 실제 API 계약에서 벗어나지 않도록, schema와 오류 형식을 주기적으로 비교하는 계약 테스트도 필요합니다.

기록에는 민감한 사용자 원문을 무분별하게 넣지 않습니다. 평가 사례와 로그에서 개인식별정보, 인증 토큰, 내부 비밀을 마스킹하고, 원본 접근 권한과 보존 기간을 명확히 합니다. 품질 평가를 위한 데이터 수집이 또 다른 개인정보 사고가 되지 않도록, 최소한의 재현 정보만 남기는 것이 원칙입니다.

## 작은 팀을 위한 첫 번째 평가 파이프라인

초기 팀이라면 복잡한 플랫폼보다 버전 관리되는 JSONL 또는 YAML 파일과 간단한 실행 스크립트로 시작할 수 있습니다. 한 사례에는 `input`, `context`, `expected_behavior`, `forbidden_behavior`, `checks` 정도만 두어도 됩니다. `checks`에는 schema 통과, 필수 도구 호출 없음, 특정 근거 포함, 금지 문구 없음처럼 명확히 검사할 수 있는 조건을 넣습니다. 사람만 판단할 수 있는 사실성은 결과 표본을 rubric으로 검토하는 방식으로 보완합니다.

CI에서는 변경된 코드가 핵심 사례를 통과했는지만 빠르게 확인하고, 더 많은 사례와 사람 검토는 출시 후보 단계에 둡니다. 점수 임계값을 처음부터 정교하게 고집할 필요는 없습니다. 현재 안정 버전을 기준선으로 저장하고, 새 실패가 무엇인지 알려 주는 보고부터 만들면 됩니다. 평가가 실패했을 때 모델을 바꾸기 전에 사례·계약·근거 문서 자체가 올바른지 함께 확인하는 문화가 장기적으로 더 중요합니다.

이 접근은 거대 모델을 자체 학습하는 조직에만 필요한 일이 아닙니다. 외부 API를 호출하는 간단한 사내 챗봇, 문서 요약 기능, 고객 지원 자동화도 프롬프트·검색·도구·정책 중 하나를 바꾸는 순간 사용자 행동이 달라질 수 있습니다. 작고 명확한 평가셋은 그 변화를 추측이 아니라 증거로 논의하게 해 줍니다.

평가를 도입한 뒤에도 결과를 한 번 보고 잊지 않는 것이 중요합니다. 매 배포에서 반복되는 실패 유형, 새 기능에서 자주 빠지는 계약, 사람이 자주 판정을 번복하는 rubric을 주기적으로 검토합니다. 이 검토는 모델 점수를 올리는 작업보다 먼저 제품의 약속을 명확히 하는 작업입니다. 기준이 분명해질수록 자동화할 수 있는 검사는 늘고, 사람이 판단해야 하는 위험한 사례도 더 선명해집니다.
