Kubernetes 보안 이야기를 시작하면 흔히 네트워크 정책, 이미지 스캔, RBAC(Role-Based Access Control)부터 떠올립니다. 모두 중요하지만 컨테이너가 이미 실행된 뒤에 어떤 프로세스를 실행했고, 민감한 파일을 읽었는지, 예상하지 못한 외부 주소로 연결했는지까지 보려면 다른 관점이 필요합니다. 배포 시점의 YAML 검사만으로는 런타임의 실제 행위를 모두 알 수 없기 때문입니다.

Cilium Tetragon은 Linux의 eBPF(extended Berkeley Packet Filter)를 이용해 프로세스 실행, 파일 접근, 네트워크 연결 같은 커널 수준 이벤트를 관찰하고, 조건에 따라 반응할 수 있게 하는 오픈 소스 도구입니다. Kubernetes의 namespace·Pod·컨테이너 같은 맥락을 이벤트에 연결해 “이 노드에서 무슨 일이 있었나”를 넘어 “어느 워크로드가 어떤 행위를 했나”라는 질문을 하도록 돕습니다.

이 글은 Tetragon을 특정 운영 환경에 직접 배포해 얻은 결과가 아닙니다. 공식 문서와 공개된 정책 예시를 바탕으로, 런타임 보안이 무엇을 확인하고 무엇을 보장하지 않는지, 처음 도입할 때 왜 관찰 모드부터 시작해야 하는지를 정리합니다. 차단 기능은 프로세스를 종료하거나 시스템 호출 결과에 영향을 줄 수 있으므로, 명확한 근거 없이 곧바로 운영 클러스터에 적용하면 안 됩니다.

## 먼저 알아둘 기반 기술: 컨테이너, 커널, eBPF, 런타임 보안

컨테이너는 애플리케이션과 라이브러리를 묶어 실행 환경을 일관되게 만드는 방식이지만, 각 컨테이너가 별도의 운영체제 커널을 갖는 것은 아닙니다. 같은 Linux 노드 위의 컨테이너는 보통 호스트 커널을 공유합니다. namespace와 cgroup은 프로세스·네트워크·파일 시스템·자원을 분리하는 데 도움을 주지만, 실제 `execve`, `open`, `connect` 같은 시스템 호출은 결국 커널을 통과합니다. 따라서 컨테이너 내부에서 일어난 행위를 커널 관점에서 관찰하면 애플리케이션 로그만으로는 보이지 않는 정보를 얻을 수 있습니다.

**eBPF**는 Linux 커널 안에서 제한된 프로그램을 안전하게 실행할 수 있게 하는 기술입니다. 원래 패킷 필터링에서 시작했지만, 현재는 네트워크 관찰, 성능 분석, 보안 이벤트 수집 등으로 넓게 쓰입니다. eBPF 프로그램이 무제한 커널 코드를 마음대로 실행하는 것은 아닙니다. 커널의 verifier가 접근 가능한 메모리와 실행 경로를 검사하고, 허용된 helper 함수를 통해 필요한 정보를 얻습니다. 그래도 커널 수준 기능인 만큼 Linux 버전, BTF(BPF Type Format) 정보, 권한, 배포 방식의 제약을 받습니다.

**런타임 보안(runtime security)** 은 이미지가 빌드된 뒤, Pod가 스케줄된 뒤, 실제 프로세스가 실행되는 순간의 행동을 관찰·탐지·대응하는 영역입니다. 이미지 스캔은 알려진 취약 패키지와 잘못된 설정을 찾는 데 유용하지만, 공격자가 컨테이너 안에서 `curl`을 실행해 외부로 데이터를 보내려는지, 쉘을 실행했는지, 예상 밖의 민감 파일을 읽는지는 실행 전 스캔만으로 알 수 없습니다. 반대로 런타임 이벤트가 있다는 사실만으로 공격이라고 단정할 수도 없습니다. 배포 자동화나 운영 배치도 프로세스 실행과 네트워크 연결을 만들기 때문입니다.

Kubernetes 관점에서 **워크로드 정체성(identity)** 도 중요합니다. 단순 PID(Process ID)나 IP 주소만 기록하면 Pod가 재시작된 뒤 무엇이었는지 알아보기 어렵습니다. namespace, Pod 이름, 컨테이너 이름, label, ServiceAccount는 어느 팀·서비스·환경의 행위인지 연결하는 단서입니다. Tetragon은 이런 Kubernetes 메타데이터와 커널 이벤트를 함께 다루려 합니다. 하지만 label은 사용자가 붙이는 메타데이터이므로, 보안 판단을 label 하나에 전적으로 의존하기보다 RBAC·네트워크 경계·이미지 신뢰와 함께 사용해야 합니다.

## Tetragon이 관찰하는 질문

애플리케이션 로그는 개발자가 기록한 이벤트를 보여 줍니다. “주문 생성이 완료됐다”, “외부 결제 응답이 500이었다” 같은 업무 맥락에는 매우 좋습니다. 그러나 공격자나 예상 밖의 라이브러리가 쉘을 실행했을 때 애플리케이션이 로그를 남긴다는 보장은 없습니다. Tetragon은 프로세스 실행, 파일 열기·쓰기, 네트워크 connect, capability 변경처럼 보안적으로 의미 있는 커널 이벤트를 관찰 대상으로 삼습니다.

예를 들어 웹 API 컨테이너가 평소에는 PostgreSQL과 내부 결제 서비스에만 연결해야 한다고 가정해 봅시다. 배포 뒤 컨테이너에서 `curl`이 실행되어 알 수 없는 외부 IP로 TLS 연결을 시도했다면, 다음 질문을 연결해야 합니다. 어느 namespace와 Pod에서 시작됐는가? 부모 프로세스는 무엇인가? 실행 파일과 인자는 무엇인가? 어떤 destination으로 연결하려 했는가? 이 이미지 버전과 배포 변경은 무엇인가? Tetragon 이벤트는 이 조사에 필요한 낮은 수준의 사실을 제공할 수 있습니다. 하지만 그 이벤트만으로 유출 여부나 공격자의 의도를 확정할 수는 없습니다. 애플리케이션 로그, 감사 로그, 네트워크 로그, 배포 이력과 함께 조사해야 합니다.

Tetragon 문서가 강조하는 장점 중 하나는 필터링을 가능한 한 커널 안에서 수행한다는 점입니다. 모든 `read`나 `write` 이벤트를 사용자 공간으로 올려 보내면 이벤트 양과 context switch가 커질 수 있습니다. 대상 binary, 파일 경로, namespace, capability, 소켓 조건처럼 필요한 필터를 eBPF에서 적용해 관련 이벤트만 내보내는 방향입니다. 이것은 “부하가 없다”는 뜻이 아닙니다. 넓은 정책, 많은 노드, 높은 빈도의 시스템 호출은 여전히 자원과 저장 비용을 만들 수 있으므로, 어떤 질문에 필요한 이벤트인지 먼저 좁혀야 합니다.

## 구성 요소: DaemonSet, Operator, 정책, 내보내기

Kubernetes에 Tetragon을 설치하면 보통 각 노드에서 동작하는 에이전트와 정책 리소스를 관리하는 구성 요소를 만나게 됩니다. **DaemonSet** 은 클러스터의 각 대상 노드에 Pod 하나씩을 배치하는 Kubernetes 워크로드입니다. 노드에서 발생하는 커널 이벤트를 보려면 노드마다 관찰 구성 요소가 있어야 하므로 이런 배포 형태가 자연스럽습니다. Tetragon은 호스트의 `/proc`, 커널 tracing 관련 파일 시스템 등 런타임 관찰에 필요한 접근을 요구할 수 있습니다. 따라서 일반 애플리케이션 Pod보다 더 높은 권한을 가질 수 있으며, 설치 자체가 보안 검토 대상입니다.

**Operator** 는 Kubernetes의 사용자 정의 리소스(CRD, Custom Resource Definition)를 읽고 필요한 리소스를 조정하는 컨트롤러입니다. Tetragon의 정책을 YAML로 선언하면 Operator와 에이전트가 이를 배포·갱신하는 흐름을 지원합니다. Kubernetes에서 YAML이 있다는 사실만으로 정책이 즉시 모든 노드에서 동일하게 적용됐다고 단정하지 말고, 상태·이벤트·에이전트 로그·대상 노드 범위를 확인해야 합니다.

**TracingPolicy** 는 어떤 커널 이벤트를 어떤 조건으로 관찰하거나 반응할지를 정의하는 Tetragon의 정책 개념입니다. 여기서 tracing이라는 단어는 애플리케이션의 OpenTelemetry trace와 같은 의미가 아닙니다. 이 정책은 예컨대 특정 바이너리 실행, 특정 파일 접근, 특정 네트워크 연결을 대상으로 삼고, namespace·Pod·인자 같은 필터를 더할 수 있습니다. 정책 이름은 보안 규칙처럼 보이지만, 실제로는 커널 함수와 조건에 연결되는 기술적 정의이므로 공식 레퍼런스와 정책 라이브러리를 확인해 작성해야 합니다.

마지막은 **event export(이벤트 내보내기)** 입니다. Tetragon 이벤트를 터미널에서 보는 것만으로 운영을 끝낼 수는 없습니다. SIEM(Security Information and Event Management), 로그 저장소, Prometheus 메트릭, 경보 시스템에 어떤 형식으로 전달할지 정해야 합니다. 이벤트에 Pod·namespace·노드·정책 이름·프로세스 정보를 넣으면 조사에 도움이 되지만, 명령 인자나 환경 정보에 비밀값이 섞일 가능성도 검토해야 합니다. 수집 범위와 보존 기간, 접근 권한은 런타임 보안 도구의 일부입니다.

## 관찰 모드와 차단 모드는 다른 책임이다

Tetragon은 보안상 의미 있는 이벤트를 기록하는 관찰 모드뿐 아니라, 정책 위반에 반응하는 enforcement 기능도 제공합니다. 예를 들어 조건에 맞는 시스템 호출의 반환값을 바꾸거나, 프로세스에 신호를 보내 종료하는 방식이 문서에 설명됩니다. 이 차이는 매우 중요합니다. 경보를 남기는 정책의 오탐은 조사 비용을 만들지만, 프로세스를 종료하는 정책의 오탐은 고객 요청 실패와 데이터 처리 중단으로 이어질 수 있습니다.

프로세스에 `SIGKILL`을 보낸다고 해서 이미 시작된 모든 작업이 항상 원자적으로 되돌아가는 것도 아닙니다. Tetragon 공식 enforcement 문서는 signal 방식이 프로세스를 종료하지만, 예를 들어 `write()` 중 보낸 신호가 파일 쓰기가 완료되지 않았음을 보장하지는 않는다고 설명합니다. 어떤 시스템 호출은 return value override로 호출 자체를 막는 방식이 더 적합할 수 있고, 어떤 작업은 애초에 정책으로 차단하기보다 알림과 수동 대응이 더 안전할 수 있습니다.

따라서 정책의 성숙도는 “차단을 켰는가”로 측정하면 안 됩니다. 먼저 다음을 관찰해야 합니다. 정상 배포·배치·백업·헬스체크가 어떤 이벤트를 만드는가? 개발·스테이징·운영에서 같은 워크로드가 다른 외부 연결을 하는가? 긴급 장애 조치용 디버그 컨테이너를 어떤 절차로 허용하는가? 정책이 실패했을 때 누구에게 어떤 맥락으로 알릴 것인가? 이 질문에 답하지 못한 상태에서 block 정책을 넓게 적용하는 것은 보안을 강화하기보다 장애 원인을 추가할 수 있습니다.

## 정책을 읽는 최소 예시

아래 YAML은 특정 namespace의 컨테이너에서 예상 밖의 바이너리 실행을 관찰하는 정책을 표현하는 방식의 개념 예시입니다. 정확한 필드와 지원되는 hook은 Tetragon 버전과 CRD 레퍼런스를 확인해야 하며, 복사해 운영에 적용하는 명령이 아닙니다.

```yaml
apiVersion: cilium.io/v1alpha1
kind: TracingPolicyNamespaced
metadata:
  name: observe-shell-execution
  namespace: payments
spec:
  kprobes:
    - call: "do_execveat_common"
      syscall: false
      args:
        - index: 0
          type: "string"
      selectors:
        - matchBinaries:
            - operator: "In"
              values: ["/bin/sh", "/bin/bash"]
          matchActions:
            - action: Post
```

이 예시에서 `TracingPolicyNamespaced`는 범위를 namespace로 제한하려는 의도를 나타냅니다. `kprobes`는 커널 함수에 연결할 관찰 지점을 뜻하고, `matchBinaries`는 어떤 실행 파일에 관심이 있는지 정합니다. `Post` 액션은 행위 뒤 이벤트를 기록하는 방향의 예입니다. 다만 실제 `do_execveat_common`의 인자·hook 지원 여부, `string`으로 얻는 정보의 의미, selector 조합은 Tetragon의 공식 정책 레퍼런스에 맞춰 검증해야 합니다.

더 중요한 것은 `/bin/sh` 실행이 곧 침해라는 결론이 아니라는 점입니다. init script, 패키지 설치, 운영 스크립트, 진단 명령도 쉘을 사용할 수 있습니다. 좋은 첫 정책은 “쉘은 무조건 kill”이 아니라, 허용된 서비스에서 언제·어떤 부모 프로세스가·어떤 인자로 쉘을 실행하는지 기준선을 얻는 정책입니다. 그 뒤 업무상 필요 없는 namespace에서만 경보를 높이거나, 승인 절차가 있는 예외를 분리할 수 있습니다.

## NetworkPolicy, Kyverno, Falco와 비교해 위치 잡기

도구 이름이 많아지면 각각이 무엇을 대체하는지 혼란스럽습니다. **Kubernetes NetworkPolicy** 는 지원하는 CNI(Container Network Interface) 구현 위에서 Pod 간 ingress·egress 통신 허용 범위를 선언하는 API입니다. 예를 들어 `payments` Pod가 PostgreSQL Service에만 나갈 수 있도록 만들 수 있습니다. 하지만 NetworkPolicy는 프로세스가 `curl`을 실행했다는 사실이나 파일을 읽은 사실을 자세히 보여 주는 도구는 아닙니다.

**Kyverno** 는 Kubernetes 리소스가 API 서버에 들어올 때 정책으로 검사·변형·검증하는 도구입니다. privileged Pod 금지, 이미지 레지스트리 제한, label 강제처럼 배포 전 설정을 다룹니다. 이미 실행 중인 컨테이너가 무엇을 했는지는 Kyverno의 핵심 대상이 아닙니다. 반면 Tetragon은 배포 후 실행 행위를 보는 쪽에 가깝습니다. 둘을 같이 쓰면 “위험한 Pod 설정을 애초에 막기”와 “정상처럼 보였지만 런타임에서 이상한 행위를 감지하기”를 다른 층에서 다룹니다.

**Falco** 역시 런타임 보안 이벤트를 탐지하는 널리 쓰이는 프로젝트입니다. Tetragon과 같은 문제 영역에 있지만 이벤트 수집 방법, 규칙 언어, 생태계, 배포·운영 방식이 다릅니다. 특정 도구가 항상 우월하다고 말하기보다 이미 쓰는 보안 이벤트 파이프라인, Linux·Kubernetes 지원 범위, 팀의 규칙 작성 역량, 커널 요구사항을 기준으로 평가해야 합니다. 한 클러스터에 여러 도구를 섞을 때는 중복 이벤트·권한·리소스 비용도 고려합니다.

| 문제 층 | 대표 질문 | 주로 쓰는 도구 예 | 놓치기 쉬운 점 |
| --- | --- | --- | --- |
| 배포 전 | 이 Pod 설정과 이미지를 허용할 것인가 | Kyverno, admission policy, 이미지 스캔 | 실행 중인 실제 행위는 알 수 없음 |
| 네트워크 경계 | 어느 Pod가 어느 서비스로 통신 가능한가 | NetworkPolicy, Cilium policy | 프로세스·파일 단위의 맥락은 제한적 |
| 런타임 관찰 | 어느 프로세스가 무엇을 실행·접근했는가 | Tetragon, Falco | 이벤트가 공격인지 판단하려면 맥락 필요 |
| 조사·대응 | 누가 보고 어떤 조치를 할 것인가 | SIEM, alerting, runbook | 탐지만 연결하고 대응 절차를 빼먹기 쉬움 |

## 오탐을 줄이는 정책 설계

런타임 보안 이벤트는 데이터가 많을수록 좋은 것이 아닙니다. `exec`, `open`, `connect`를 아무 조건 없이 전부 내보내면 보안 팀은 평소 정상 행위에 묻히고, 저장 비용과 조사 시간이 늘어납니다. “모든 것을 수집한 뒤 나중에 보자”는 방식은 작은 실험에는 가능해도 지속적인 운영 정책으로는 유지하기 어렵습니다.

첫 번째 기준은 **대상 워크로드를 좁히기** 입니다. 모든 namespace 대신 인터넷에 노출되는 API, 개인정보를 다루는 서비스, 권한이 높은 배치처럼 위험과 영향이 큰 워크로드부터 시작합니다. 두 번째는 **행위 조건을 좁히기** 입니다. 모든 프로세스 실행 대신 package manager, shell, curl, nc 같은 예상 밖의 binary; 모든 파일 대신 service account token, SSH key, 민감 설정 경로처럼 명확한 보호 대상을 고릅니다. 세 번째는 **맥락을 보강하기** 입니다. Pod label, 이미지 digest, ServiceAccount, 배포 버전, 부모 프로세스를 함께 보내야 같은 `curl`도 정상 헬스체크와 의심스러운 다운로드를 구분할 실마리가 생깁니다.

정책을 만들 때 예외 목록을 무한히 늘리는 것도 위험합니다. 예외가 많다는 것은 기준이 너무 넓거나 서비스별 모델이 다른 신호일 수 있습니다. 예를 들어 모든 서비스에서 `/bin/sh`를 차단하려다 예외가 늘어난다면, shell 자체보다 “웹 요청 처리 프로세스가 shell을 실행하는가”처럼 부모·컨테이너 역할을 포함한 조건이 더 적절할 수 있습니다. 예외마다 소유자와 만료일을 두고, 장기간 남는 예외는 설계를 다시 봅니다.

## 설치 전 검토: 권한과 커널 호환성

Tetragon은 노드의 커널 이벤트를 보기 때문에 일반 애플리케이션보다 강한 권한과 host path 접근이 필요할 수 있습니다. 이를 “보안 도구니까 예외”로 처리하지 말고, 어떤 ServiceAccount와 ClusterRole이 필요한지, 어떤 host path를 마운트하는지, DaemonSet이 어느 노드에 배치되는지, 이미지를 누가 공급·서명하는지 검토합니다. 런타임 보안 도구 자체가 침해되면 넓은 관찰 권한이 악용될 수 있기 때문입니다.

eBPF 호환성도 사전에 확인합니다. Linux 커널 버전, 배포판 설정, BTF 제공 여부, 관리형 Kubernetes 노드에서 허용되는 capability가 제품마다 다릅니다. Tetragon 문서는 BTF 관련 문제와 host `/proc` 접근 조건을 안내합니다. 로컬 kind 클러스터에서 예제가 된다고 관리형 운영 클러스터에서도 같은 방식으로 된다고 가정하면 안 됩니다. 운영 클러스터의 노드 OS, 업그레이드 정책, 보안 정책, CNI 구성을 목록으로 만들고 지원 매트릭스와 대조해야 합니다.

이벤트 데이터의 민감성도 잊기 쉽습니다. 명령 인자에는 토큰·이메일·파일 경로가 포함될 수 있고, 네트워크 대상에는 내부 시스템 구조가 드러날 수 있습니다. 보안 이벤트 저장소의 접근 제어, 보존 기간, 마스킹 규칙, 사고 대응 시 열람 절차를 로그 정책에 포함합니다. 모든 세부 정보를 영구히 저장하는 것이 항상 더 안전한 것은 아닙니다.

## 단계적 도입 절차

첫 단계는 **질문 하나를 정하는 것** 입니다. “결제 namespace에서 웹 프로세스가 실행한 자식 프로세스를 알고 싶다” 또는 “민감 설정 파일에 접근하는 Pod를 조사하고 싶다”처럼 구체적으로 씁니다. “침해를 탐지한다”는 목표만으로는 어떤 이벤트와 어떤 성공 기준이 필요한지 결정할 수 없습니다.

두 번째 단계는 격리된 개발 또는 스테이징 환경에서 관찰 정책을 적용하는 것입니다. 정상 배포, 배치, 롤링 업데이트, 헬스체크, 장애 복구를 한 번씩 지나게 하면서 이벤트를 수집합니다. 이때 테스트를 위해 공격처럼 보이는 명령을 실행할 경우에도 승인된 격리 환경에서만 하고, 실제 비밀이나 외부 서비스를 건드리지 않아야 합니다. 관찰 결과에서 정상 행위를 문서화하고, 의심 이벤트가 발생했을 때 어떤 추가 로그를 확인할지 runbook을 만듭니다.

세 번째는 경보 임계값과 소유자를 정하는 것입니다. 특정 이벤트 한 건에 즉시 PagerDuty를 울릴지, 동일 Pod에서 반복될 때 티켓을 만들지, 보안 팀과 서비스 팀 중 누가 1차 분류를 하는지 결정합니다. “경보가 왔는데 아무도 책임지지 않는다”는 상태는 탐지 없는 상태보다 나을 것이 없습니다. 알림에는 최소한 정책 이름, namespace·Pod, node, 프로세스·인자, 시간, 관련 배포 버전을 넣어야 조사 시작이 가능합니다.

네 번째가 제한된 enforcement입니다. 이미 충분히 관찰했고 정상 사용 사례가 거의 없으며, 위반 시 즉시 중단해도 안전한 행위만 고릅니다. 예를 들어 특정 격리된 워크로드에서 명백히 금지된 외부 egress를 막는 사례를 생각할 수 있습니다. 이때도 정책 범위, 롤백 방법, 서비스 영향 알림, 예외 승인 절차를 먼저 검증합니다. 차단은 최종 목적이 아니라 위험과 복구 가능성을 고려한 하나의 대응 수단입니다.

## 조사 흐름의 예시

운영 경보가 “payments namespace의 API Pod에서 `/usr/bin/curl` 실행”이라고 알려 왔다고 가정해 보겠습니다. 첫 번째 조사 질문은 그 Pod가 정상 배포나 진단 작업 중이었는지입니다. Deployment 변경 이력, 이미지 digest, Pod 생성 시각, ServiceAccount, 담당 팀의 배포 공지를 확인합니다. 두 번째는 부모 프로세스와 인자입니다. 애플리케이션 프로세스가 웹 요청 중 쉘을 실행했는지, init script가 시작 단계에서 실행했는지에 따라 위험도는 다릅니다.

세 번째는 목적지와 데이터 흐름입니다. curl이 내부 health endpoint를 호출했는지, 승인된 외부 API인지, 예상하지 못한 IP인지 확인합니다. DNS·네트워크·프록시 로그와 함께 보지 않으면 URL 하나만으로 판단하기 어렵습니다. 네 번째는 범위입니다. 같은 이미지 digest를 쓰는 다른 Pod에서도 같은 이벤트가 있었는지, 동일 ServiceAccount로 다른 권한 변경이 있었는지 살핍니다. 다섯 번째는 대응입니다. 차단할지, Pod를 격리할지, 토큰을 회전할지, 단순히 정책 예외로 분류할지는 서비스 영향과 증거 수준을 바탕으로 결정합니다.

이 흐름에서 Tetragon은 판단을 대신하는 탐정이 아니라, 낮은 수준의 사실을 정체성과 연결해 주는 센서에 가깝습니다. 센서가 낸 이벤트를 누가 어떤 순서로 검토할지까지 설계해야 런타임 보안이 실제 운영에 도움이 됩니다.

## 정책을 코드처럼 관리하는 이유

TracingPolicy는 YAML 파일이지만, 실제로는 서비스 동작과 보안 대응에 영향을 주는 실행 가능한 규칙입니다. 따라서 운영자가 콘솔에서 한 번 적용하고 잊어버리는 설정이 아니라 Git 저장소에서 변경 이력·리뷰·승인·배포 범위를 관리하는 대상에 가깝습니다. 어떤 binary와 파일 경로를 대상으로 했는지, 어느 namespace에 적용되는지, 관찰만 하는지 제한 동작이 있는지, 정책 작성자가 무엇을 근거로 삼았는지를 PR 설명에 남기면 나중에 경보를 해석하기 쉬워집니다.

정책 리뷰는 문법 확인만으로 충분하지 않습니다. 우선 “이 규칙이 막거나 기록하려는 실제 위험은 무엇인가”를 한 문장으로 씁니다. 다음으로 정상 업무에서 이 행위가 일어나는지 확인합니다. 이어서 대상 namespace와 label selector가 너무 넓지 않은지, Pod 재시작·롤링 배포 때도 같은 정체성으로 해석되는지, 이벤트에 필요한 맥락이 포함되는지 검토합니다. 마지막으로 policy를 제거하거나 완화해야 할 때 어떤 Git 변경과 배포 절차를 밟는지 정합니다. 긴급하게 차단을 해제할 수 있어야 하지만, 누가 왜 해제했는지 감사 흔적도 남아야 합니다.

정책 버전과 Tetragon 버전의 호환성도 관리해야 합니다. 특정 hook이나 action이 새 버전에서 지원된다고 해서 이전 노드에 그대로 적용할 수 있는 것은 아닙니다. Kubernetes 클러스터 업그레이드, 노드 이미지 교체, Tetragon Helm chart 변경을 하나의 변경 창으로 묶어 검증할지, 호환 기간을 둘지 계획합니다. 운영에서 “이 YAML은 어제까지 됐는데 오늘은 적용되지 않는다”는 문제를 줄이려면 정책 코드와 에이전트 버전을 함께 기록하는 것이 좋습니다.

## 이벤트 품질을 확인하는 방법

탐지 규칙의 품질은 이벤트 수가 아니라 조치 가능한 정보의 비율로 판단하는 편이 좋습니다. 경보 한 건을 받은 담당자가 추가 질문 없이 바로 볼 수 있는 정보가 무엇인지 생각해 봅니다. 최소한 발생 시각, cluster·node, namespace·Pod·container, 정책 이름·버전, 실행 파일과 부모 프로세스, 파일·소켓 대상, 관련 배포 버전 정도가 연결되어야 합니다. 그래도 개인정보와 비밀값을 과도하게 저장하지 않도록 인자와 경로의 마스킹 기준을 정해야 합니다.

관찰 단계에서는 event sample을 정기적으로 검토하는 시간이 필요합니다. 보안 담당자만 보는 것이 아니라 해당 서비스를 운영하는 개발자와 함께 보아야, 정상 배치·마이그레이션·백업 작업을 공격으로 분류하는 실수를 줄일 수 있습니다. 정상으로 확인된 이벤트를 단순히 모두 ignore하기보다, 왜 정상인지와 언제 다시 검토할지를 기록합니다. 이미지 교체, 외부 연동 추가, 운영 도구 변경 뒤에는 이전 기준선이 더 이상 맞지 않을 수 있습니다.

정책의 성공 지표도 차단 건수로 두지 않습니다. 예를 들어 “중요 namespace에서 승인되지 않은 외부 연결 시도의 조사 시간이 줄었는가”, “새 이미지 배포 뒤 예상하지 못한 shell 실행을 빠르게 발견했는가”, “오탐 경보가 담당 팀의 대응 가능 범위에 머무르는가”처럼 운영 질문에 연결합니다. 수집량이 너무 커졌다면 이벤트를 버리는 대신 대상을 좁히거나, 특정 경로·워크로드에 샘플링과 보존 정책을 다르게 적용하는 방법을 검토합니다.

## 장애 대응과 정책 롤백을 함께 준비하기

차단 정책을 켜기 전에는 실패 시나리오를 적어 보는 것이 좋습니다. 정책이 정상 배치의 외부 연결을 차단하면 어떤 서비스 지표가 먼저 악화되는가, 알림은 어느 팀으로 가는가, 빠르게 관찰 모드로 되돌리는 명령과 승인 경로는 무엇인가, 차단을 푼 뒤 남은 데이터 처리나 재시작이 필요한가를 확인합니다. 정책이 좋은 의도로 만들어졌더라도 고객 주문·정산·백업을 중단시키면 즉시 이해하고 복구할 수 있어야 합니다.

롤백은 Git에서 YAML 한 줄을 되돌리는 것보다 넓은 일일 수 있습니다. 이미 종료된 Pod는 자동으로 다시 올라오지 않을 수 있고, 프로세스 종료로 중단된 작업은 멱등성 키나 보상 절차가 필요할 수 있습니다. 따라서 enforcement를 검증할 때는 정상 상태 복구까지 테스트 시나리오에 포함합니다. 관찰 모드에서 기준선을 만들고, 작고 되돌리기 쉬운 대상에서만 차단을 실험하라는 이유가 여기에 있습니다.

사고 대응에서 Tetragon 이벤트가 증거의 전부가 되어서는 안 됩니다. 시간 동기화가 맞는지, 이벤트 전달 파이프라인에 누락이 없는지, 노드가 다운된 기간은 없는지 확인하고 감사 로그·클라우드 활동 로그·애플리케이션 로그와 시간대를 맞춥니다. 런타임 센서는 조사 시작을 빠르게 하지만, 법적·보안적 결론을 내릴 때 필요한 증거 보존 정책은 조직의 별도 절차를 따라야 합니다.

## 마무리: 차단보다 먼저, 맥락 있는 관찰을 설계하기

Cilium Tetragon은 Kubernetes 안에서 실행 중인 워크로드의 행위를 커널 이벤트와 Kubernetes 정체성으로 연결해 볼 수 있게 합니다. 그 강점은 “모든 이벤트를 많이 모으는 것”이 아니라, 기존 로그로 답하기 어려웠던 구체적인 질문에 필요한 신호를 좁혀 수집하는 데 있습니다.

좋은 도입은 작은 관찰 정책 하나에서 시작합니다. 정상 기준을 만들고, 이벤트의 소유자와 조사 절차를 정하고, 영향이 명확한 경우에만 좁은 차단 정책을 고려합니다. eBPF는 보안을 자동으로 완성하는 마법이 아니라, 런타임의 사실을 더 가까이에서 볼 수 있게 하는 기반 기술입니다.
