## 먼저 답하기

### Q. SQL이 느리면 EXPLAIN 결과에서 `ALL`만 없애면 되나요?

A. 아닙니다. `ALL`은 전체 테이블 스캔 가능성을 알려 주는 한 신호일 뿐이고, 작은 기준 테이블을 모두 읽는 것이 합리적인 경우도 있습니다. 실행 계획은 데이터 양, 필터 조건, 조인 순서, 인덱스, 통계에 근거한 옵티마이저의 선택입니다. 좋은 조사는 특정 키워드를 금지하는 일이 아니라, 예상한 행 수와 실제 읽은 행 수, 실행 시간, 업무에 필요한 결과의 관계를 함께 확인하는 일입니다.

느린 화면이 있다는 보고를 받았을 때 즉시 인덱스를 추가하면 빨라질 때도 있습니다. 하지만 모든 느린 SQL의 원인이 인덱스 부족은 아닙니다. 조건이 너무 넓을 수 있고, 함수 때문에 인덱스를 쓸 수 없을 수 있고, 조인 뒤에 행이 폭증할 수 있으며, 통계가 실제 분포와 달라 잘못된 접근 경로를 고를 수 있습니다. 같은 인덱스라도 쓰기 비용과 저장 공간을 늘리므로, 실행 계획을 읽지 않고 하는 튜닝은 다른 쿼리를 더 느리게 만들 위험이 있습니다.

## 먼저 알아둘 기반 기술

### 관계형 질의와 옵티마이저

애플리케이션이 `SELECT` 문을 보내면 DBMS는 SQL 문장을 그대로 한 줄씩 실행하지 않습니다. 파서가 문법과 객체를 확인하고, 옵티마이저가 가능한 접근 경로와 조인 순서를 비교한 뒤, 실행기가 선택된 계획을 수행합니다. 옵티마이저는 테이블 통계, 인덱스의 구성, 조건의 선택도, 예상 비용을 이용해 가장 비용이 낮을 것으로 보이는 계획을 고릅니다. 여기서 비용은 보통 상대적인 계산 값이지 사용자가 체감하는 밀리초를 그대로 뜻하지는 않습니다.

선택도(selectivity)는 조건이 전체 행 중 얼마나 적은 행을 남기는지 나타내는 관점입니다. 주문 테이블에서 `status = 'PAID'`가 대부분의 행에 해당한다면 이 조건만으로는 많은 행을 줄이지 못합니다. 반대로 특정 고객 ID와 최근 일주일 조건을 함께 사용하면 후보가 크게 줄 수 있습니다. 인덱스는 원하는 행을 빨리 찾게 하지만, 조건이 너무 넓거나 반환해야 하는 행이 대부분이라면 인덱스를 거쳐 테이블 행을 다시 읽는 비용보다 순차적으로 읽는 편이 나을 수 있습니다.

### InnoDB 인덱스와 클러스터드 인덱스

MySQL에서 널리 쓰는 InnoDB는 기본 키를 중심으로 행 데이터를 정리하는 클러스터드 인덱스 구조를 가집니다. 보조 인덱스(secondary index)는 인덱스 컬럼 값과 기본 키 값을 함께 가리킵니다. 따라서 보조 인덱스로 후보를 찾은 뒤, SELECT에 필요한 다른 컬럼을 얻으려면 기본 키를 통해 다시 행을 읽을 수 있습니다. 이를 이해하면 인덱스가 있는데도 많은 무작위 읽기가 생기는 이유와, 필요한 컬럼이 인덱스에 모두 들어 있는 covering index가 왜 일부 읽기에서 이점이 되는지 설명할 수 있습니다.

그러나 covering index를 만들겠다고 모든 반환 컬럼을 인덱스에 넣으면 인덱스가 지나치게 커지고 INSERT·UPDATE·DELETE 비용이 증가합니다. 인덱스는 읽기만 위한 무료 기능이 아니라 데이터 변경 때 함께 관리해야 하는 구조입니다. 업무에서 자주 쓰는 조회 조건, 정렬, 반환 열, 쓰기 빈도를 함께 고려해야 합니다.

### 추정과 실제의 차이

`EXPLAIN`은 실행 전에 옵티마이저가 예상한 계획을 보여 줍니다. 따라서 `rows`는 실제로 읽은 행 수가 아니라 추정치입니다. MySQL 8.0의 `EXPLAIN ANALYZE`는 쿼리를 실제로 실행하고 iterator별 실제 행 수와 시간 정보를 보여 줍니다. 두 도구의 차이는 중요합니다. EXPLAIN만 보고 "행이 천 개일 것"이라고 판단했는데 실제 실행에서는 수백만 행이 나오면, 통계나 데이터 편중 또는 조건 상관관계를 다시 의심해야 합니다.

`EXPLAIN ANALYZE`는 대상 SQL을 실행한다는 사실도 반드시 기억해야 합니다. SELECT라 해도 큰 테이블을 읽고 정렬·임시 테이블을 만들 수 있으며, 운영 시스템에 부담을 줄 수 있습니다. UPDATE나 DELETE처럼 데이터를 바꾸는 문장에는 조사 목적의 무심한 실행이 더 위험합니다. 운영 장애 중에는 복제본, 제한된 시간 창, 대표 파라미터, DBA 승인 같은 안전한 경계를 먼저 정해야 합니다.

## EXPLAIN 출력에서 먼저 볼 것

다음 주문 조회를 예로 들겠습니다.

```sql
EXPLAIN
SELECT o.id, o.created_at, o.total_amount
FROM orders AS o
WHERE o.customer_id = 42
  AND o.created_at >= '2026-10-01'
ORDER BY o.created_at DESC
LIMIT 50;
```

결과의 `table`은 어느 테이블 또는 임시 결과를 읽는지, `type`은 접근 방식의 대략적인 종류를 보여 줍니다. `possible_keys`는 사용할 수 있었던 인덱스 후보, `key`는 실제로 선택한 인덱스, `key_len`은 인덱스의 어느 부분을 썼는지, `ref`는 비교 대상, `rows`는 예상 읽기 행 수, `Extra`는 정렬·임시 테이블·인덱스만으로 처리 가능한지 같은 추가 정보를 제공합니다. 한 컬럼만 보고 좋고 나쁨을 판정하지 말고 이 정보를 한 묶음으로 읽습니다.

예를 들어 `key`가 비어 있어도 작은 코드 테이블을 한 번 읽는 경우라면 문제가 아닐 수 있습니다. 반대로 `key`가 있어도 `rows`가 수백만이고 `Extra`에 `Using filesort`가 나오며 응답이 수 초라면, 인덱스를 쓴다는 사실만으로 충분하지 않습니다. `Using filesort`는 디스크 파일을 반드시 쓴다는 뜻이 아니라 정렬을 위해 인덱스 순서를 그대로 이용하지 못했다는 신호입니다. 원인은 ORDER BY와 인덱스의 열 순서, 범위 조건, 조인 순서 등에 따라 달라집니다.

### 인덱스 열 순서를 조건과 함께 읽는다

위 쿼리에는 `(customer_id, created_at)` 인덱스가 자연스러운 후보가 될 수 있습니다. 먼저 고객으로 범위를 좁히고, 그 안에서 생성 시각 순서를 읽어 최신 50건에서 멈출 수 있기 때문입니다. 반대로 `(created_at, customer_id)`는 최근 기간 전체를 먼저 훑은 뒤 고객 조건을 비교해야 할 수 있습니다. 어느 쪽이 항상 정답이라는 뜻은 아닙니다. 실제로 자주 실행되는 질의 묶음과 데이터 분포, 정렬 방향, 다른 조건을 고려해야 합니다.

SQL에서 인덱스 컬럼에 함수를 씌우는 습관도 계획을 바꿉니다. `DATE(created_at) = '2026-11-04'`는 날짜 함수 결과를 비교하므로 일반적인 `created_at` 범위 인덱스를 효율적으로 쓰기 어렵게 만들 수 있습니다. 같은 의미를 시간 범위로 표현하면 조건이 더 명확해집니다.

```sql
WHERE created_at >= '2026-11-04 00:00:00'
  AND created_at <  '2026-11-05 00:00:00'
```

시간대와 업무 기준일은 이 예시에서 별도로 합의해야 합니다. UTC 저장인지, 사용자 지역 시간 기준인지가 불분명한 상태에서 쿼리만 바꾸면 성능은 좋아져도 날짜 경계의 데이터가 틀릴 수 있습니다. 성능 튜닝은 업무 의미를 유지한다는 전제 위에서만 유효합니다.

## EXPLAIN ANALYZE로 가설을 확인하는 법

분석은 "인덱스를 추가하자"가 아니라 질문에서 시작합니다. 주문 상세 화면이 느리다면 첫 질문은 어떤 파라미터에서 느린가입니다. 주문이 적은 고객과 수백만 건을 가진 고객의 실행 시간이 같은지, 특정 기간이나 상태에서만 악화되는지, 페이지 번호가 뒤로 갈수록 느려지는지를 분리합니다. 그 다음 같은 파라미터로 EXPLAIN을 보고 예상 읽기 행과 계획을 기록합니다. 안전한 환경에서 EXPLAIN ANALYZE를 실행해 실제 행 수와 시간 분포를 비교합니다.

실제 행 수가 추정치보다 크게 많으면 통계가 오래됐거나 데이터가 한 값에 편중됐거나 조건 컬럼 사이에 강한 관계가 있을 수 있습니다. 반대로 추정은 커도 실제 결과가 빨리 끝난다면 LIMIT로 빨리 멈추는지, 캐시나 현재 데이터 상태의 영향을 받는지 살펴야 합니다. 한 번의 실행 시간만으로 결론을 내리지 말고, 대표적인 정상·경계·대용량 파라미터를 정해 비교합니다. 직접 성능 측정을 했다고 주장하는 것이 아니라, 조직에서 조사할 때 재현 가능하게 설계해야 한다는 뜻입니다.

`EXPLAIN ANALYZE` 출력은 실행기의 반복 구조를 보여 주므로 맨 아래의 총 시간만 보지 말고 어느 iterator에서 행이 불어나거나 반복 횟수가 커졌는지 확인합니다. Nested Loop 조인이 작은 바깥 집합과 인덱스 탐색의 조합이면 좋은 선택일 수 있지만, 바깥에서 수십만 번 반복되면 안쪽 조회가 누적되어 병목이 될 수 있습니다. 조인 조건에 인덱스가 있는지, 먼저 읽는 테이블을 줄일 필터가 있는지, 애플리케이션이 한 번의 넓은 조인 대신 N+1 쿼리를 만들고 있지는 않은지 함께 봅니다.

## 조인·정렬·페이징에서 자주 놓치는 지점

조인 성능은 두 테이블에 인덱스가 있다는 사실만으로 결정되지 않습니다. `orders.customer_id = customers.id`처럼 관계를 맺는 열, 먼저 필터링되는 테이블, 최종 반환하는 열, 조인 뒤 추가되는 조건을 함께 봐야 합니다. 사용자 이름으로 고객을 찾고 주문을 최근순으로 보여 준다면 사용자 이름 조건으로 고객을 하나로 줄인 뒤 주문의 고객 ID와 생성 시각을 이용하는 경로가 자연스러울 수 있습니다. 그러나 이름이 중복되거나 조직 단위 필터가 먼저라면 계획은 달라집니다.

정렬은 특히 자주 오해됩니다. 정렬 키가 인덱스에 있어도 앞쪽 조건과 인덱스 순서가 맞지 않으면 옵티마이저는 후보를 모은 뒤 정렬해야 할 수 있습니다. `ORDER BY created_at DESC, id DESC`를 쓰는 커서 기반 페이지라면 동점 시 순서를 안정적으로 만드는 `id`의 역할도 중요합니다. OFFSET이 매우 큰 페이지는 앞의 많은 행을 건너뛰어야 하므로 시간이 갈수록 비용이 커질 수 있습니다. 무한 스크롤이나 대용량 이력 조회에는 마지막으로 본 정렬 키를 넘기는 keyset pagination을 검토할 수 있습니다.

```sql
SELECT id, created_at, total_amount
FROM orders
WHERE customer_id = 42
  AND (created_at, id) < ('2026-11-04 09:30:00', 9912)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

이 방식은 모든 화면에 자동으로 적용할 규칙은 아닙니다. 사용자가 임의 페이지 번호로 바로 이동해야 하는 보고서라면 OFFSET이 필요한 경우도 있습니다. 핵심은 페이지 기능의 UX 요구와 데이터 규모를 분리해, 쿼리 문법만으로 문제를 해결하려 하지 않는 것입니다.

## 실행 계획을 읽는 순서: 한 번에 바꾸지 않기

실행 계획을 처음 열면 컬럼과 용어가 많아 어디부터 봐야 할지 막막할 수 있습니다. 이때는 다음 순서로 좁히면 됩니다. 첫째, 사용자에게 느린 기능과 실제 SQL, 바인드 값, 실행 시각을 연결합니다. 둘째, 결과 행 수와 정렬 순서처럼 바뀌면 안 되는 업무 계약을 적습니다. 셋째, EXPLAIN에서 테이블별 접근 경로와 예상 행 수를 읽습니다. 넷째, 안전한 환경에서 실제 행 수와 시간을 확인합니다. 다섯째, 가장 큰 차이를 보이는 한 가설만 바꾸고 같은 입력으로 결과·계획·부작용을 비교합니다.

이 순서를 지키면 "인덱스를 세 개 넣고 쿼리를 다시 쓰고 서버 설정도 바꾸자" 같은 복합 변경을 피할 수 있습니다. 여러 가지를 동시에 바꾸면 빨라졌을 때 무엇이 원인이었는지 알 수 없고, 느려졌을 때 되돌릴 지점도 불명확합니다. 특히 운영 데이터베이스의 인덱스 생성과 통계 갱신은 다른 쿼리에도 영향을 줄 수 있으므로, 작은 변경과 명확한 관측이 안전합니다.

### 실제 결과와 실행 비용을 따로 확인한다

튜닝 전후 비교에서 첫 번째 검사는 결과 동등성입니다. 행 수만 같아도 순서, 중복, NULL 처리, 집계 값, 권한 필터가 달라질 수 있습니다. 가능하다면 대표 입력마다 결과의 기본 키 목록과 주요 집계 값을 비교하고, 페이지가 있는 화면에서는 첫 페이지와 마지막 경계의 중복·누락도 봅니다. 성능을 높인다는 이유로 `DISTINCT`나 조인을 삭제해 우연히 더 적은 데이터를 반환했다면, 그것은 개선이 아니라 기능 변경입니다.

두 번째 검사는 자원 비용입니다. 응답 시간이 줄어도 CPU 사용량, 디스크 읽기, 임시 테이블, 잠금 대기, 복제 지연 같은 다른 비용이 증가할 수 있습니다. 단일 쿼리의 실행 시간과 동시에 여러 요청이 들어온 상황은 다릅니다. 따라서 성능 변경을 검토할 때는 요청량, 데이터 성장, 쓰기 경합, 백업·배치 시간대와의 관계를 함께 기록해야 합니다. 여기서 숫자를 임의로 약속하기보다 서비스의 SLO(Service Level Objective), 배치 창, 자원 예산을 기준으로 합격선을 정합니다.

### 조건의 암묵적 형 변환을 의심한다

인덱스가 있어도 조건의 자료형이 맞지 않으면 예상과 다르게 동작할 수 있습니다. 숫자 컬럼에 문자열을 비교하거나, 문자 집합과 정렬 규칙이 다른 컬럼을 조인하거나, 날짜를 불명확한 문자열로 넘기면 MySQL이 변환을 수행할 수 있습니다. 변환 자체가 항상 인덱스를 막는다고 단정할 수는 없지만, 계획과 결과의 예측 가능성을 낮춥니다. 애플리케이션 바인드 변수와 테이블 정의의 타입을 일치시키고, EXPLAIN에서 실제 선택 경로를 확인하는 습관이 중요합니다.

문자열 검색도 마찬가지입니다. `LIKE '%키워드%'`는 앞부분이 와일드카드라 일반 B-tree 인덱스를 이용해 시작 위치를 빠르게 찾기 어렵습니다. 사용자가 포함 검색을 요구한다면 전체 텍스트 검색, 별도 검색 시스템, 데이터 모델 변경 등 요구에 맞는 도구를 검토해야 할 수 있습니다. 단순히 컬럼에 인덱스를 추가해도 문제를 해결하지 못한다는 점을 실행 계획이 보여 줍니다. 반대로 `LIKE '키워드%'`처럼 접두어 검색인 경우에도 collation과 길이, 선택도, 반환량을 고려해야 합니다.

## 복합 인덱스의 설계와 검증

복합 인덱스는 여러 조건이 함께 나오는 쿼리에 효과적일 수 있지만, "WHERE에 있는 열을 모두 순서대로 넣는다"는 기계적 규칙으로 설계하면 실패하기 쉽습니다. 동등 비교 조건, 범위 조건, ORDER BY, GROUP BY, 조인 열, 반환 열 사이에는 상호작용이 있습니다. 예를 들어 조직 ID로 한 조직을 먼저 제한하고 상태를 같은 값으로 제한한 뒤 생성 시각 범위와 최신순 정렬을 한다면, 조직 ID와 상태가 앞쪽 후보가 될 수 있습니다. 하지만 상태가 대부분 같은 값이고 조직 ID도 대형 조직 하나라면 선택도는 기대보다 낮을 수 있습니다.

인덱스를 제안할 때는 해당 인덱스가 지원할 SQL을 한두 개 명시하세요. 어떤 조건으로 범위를 좁히고, 어떤 정렬을 피하며, 어떤 쓰기에 비용을 더하는지 설명할 수 있어야 합니다. `idx_orders_a_b_c` 같은 이름보다 `idx_orders_customer_created_at`처럼 열과 목적을 드러내면 리뷰가 쉬워집니다. 기존 인덱스와 접두어가 겹치는지도 확인해야 합니다. 새 인덱스가 이미 있는 인덱스를 완전히 대체하는지는 즉시 단정하지 말고, 다른 쿼리와 외래 키, 제약·운영 도구가 사용하는 경로까지 조사합니다.

인덱스 변경 뒤에는 EXPLAIN의 `key`가 새 인덱스로 바뀌었는지만 보지 말고, 예상 `rows`와 정렬·임시 테이블 정보가 실제로 달라졌는지 확인합니다. 옵티마이저가 새 인덱스를 선택하지 않는다면 강제로 쓰게 하기 전에 이유를 알아야 합니다. 데이터가 적거나 선택도가 낮거나, 기존 계획의 비용이 더 낮다고 판단했을 수 있습니다. MySQL은 힌트를 무시하거나 다른 선택을 할 수 있는 이유가 있으며, 사람이 생각한 "좋은 인덱스"가 현재 쿼리에 항상 좋은 것은 아닙니다.

## 조인 계획에서 보는 cardinality

조인에서는 한 단계의 행 수가 다음 단계의 반복 횟수가 됩니다. 이를 cardinality, 즉 행 수의 규모 관점에서 읽을 수 있습니다. 한 고객이 주문을 여러 개 가지고, 각 주문이 주문 항목을 여러 개 가지고, 각 항목이 할인 규칙 여러 개와 연결된다면 단순 조인만으로 행이 빠르게 증가합니다. 화면에는 주문별 합계만 필요했는데 항목과 할인 규칙을 모두 펼쳐 조인하면, DB는 필요 이상의 중간 결과를 만들 수 있습니다.

해결책은 늘 인덱스가 아닙니다. 필요한 수준에서 먼저 집계하고 조인하거나, 상세 정보는 사용자가 펼칠 때 별도 조회하거나, 존재 여부만 필요할 때 `EXISTS`를 검토하는 식으로 데이터 요구 자체를 줄일 수 있습니다. 단, 쿼리 형태를 바꿀 때 NULL과 중복의 의미가 바뀌지 않는지 확인해야 합니다. `INNER JOIN`을 `EXISTS`로 바꾸면 중복 제거 효과가 생길 수 있고, `LEFT JOIN`의 WHERE 조건 위치를 바꾸면 외부 조인이 사실상 내부 조인이 될 수 있습니다. 실행 계획을 개선하는 동안 관계형 의미를 잃지 않는 것이 핵심입니다.

### N+1 쿼리와 단일 대형 조인의 경계

ORM(Object-Relational Mapping)을 쓰는 애플리케이션은 목록을 읽은 뒤 각 행의 연관 데이터를 다시 읽는 N+1 쿼리를 만들기 쉽습니다. 이를 피하려고 모든 연관 데이터를 한 번의 조인으로 합치면, 이번에는 결과 행 중복과 메모리 사용량이 커질 수 있습니다. 두 선택지 중 하나를 절대 규칙으로 고르지 말고, 목록의 최대 크기, 연관 데이터의 평균·최대 개수, 화면이 실제로 표시하는 정보, 캐시 가능성을 기준으로 비교합니다.

조사 시에는 데이터베이스 슬로우 쿼리 로그나 애플리케이션 트레이스를 통해 같은 요청에서 몇 개의 SQL이 발생하는지 확인할 수 있습니다. 다만 로그에 민감한 바인드 값이 남을 수 있으므로 수집 정책과 마스킹을 적용해야 합니다. EXPLAIN은 하나의 SQL을 설명하지만, 사용자가 느끼는 지연은 네트워크 왕복, 연결 대기, 직렬화, 여러 쿼리의 합일 수 있습니다. 따라서 실행 계획 분석은 전체 요청 분석의 중요한 일부이지 전부는 아닙니다.

## 인덱스 조건 푸시다운과 반환 열

InnoDB는 경우에 따라 보조 인덱스를 읽는 과정에서 인덱스에 있는 조건을 먼저 검사해, 기본 키 행을 다시 읽는 횟수를 줄일 수 있습니다. 이를 인덱스 조건 푸시다운이라고 부릅니다. 이 기능이 보인다고 무조건 최적이라는 뜻은 아니지만, 보조 인덱스에서 무엇을 걸러 내고 어떤 시점에 전체 행을 읽는지 생각하는 데 도움이 됩니다. SELECT 목록을 필요 이상으로 넓게 가져오면 covering index가 어려워지고 네트워크·애플리케이션 메모리 비용도 늘어납니다.

반대로 `SELECT *`를 모두 금지하는 식의 규칙도 맥락이 필요합니다. 관리자 상세 화면이 실제로 모든 컬럼을 보여 주고 행이 하나라면 가독성을 위해 허용할 수 있습니다. 수만 행을 반환하는 목록 API에서 습관적으로 모든 열을 가져오는 경우가 문제입니다. 조회 목적에 맞는 DTO와 SQL 선택 목록을 사용하면 성능뿐 아니라 API 계약도 명확해집니다. 실행 계획은 데이터베이스 내부에서 읽은 양을, API 설계는 그 데이터를 왜 외부로 보내는지를 설명합니다.

## 안전한 변경과 롤백 계획

인덱스 생성은 테이블과 MySQL 버전에 따라 잠금과 자원 사용에 영향을 줄 수 있습니다. 운영 테이블에 변경을 적용하기 전에는 지원되는 온라인 DDL 방식, 예상 소요 시간, 디스크 여유, 복제 환경, 장시간 트랜잭션을 확인해야 합니다. 변경 창이 필요하다면 사용자 영향과 관찰 방법을 정하고, 문제가 생겼을 때 취소 또는 이전 인덱스로 돌아갈 수 있는 절차를 준비합니다. 명령 하나가 실행됐다는 사실보다 영향 범위를 이해하는 것이 DBA 작업의 핵심입니다.

배포 뒤에는 새 계획이 실제로 선택되는지, 슬로우 쿼리 비율과 오류가 변하지 않는지, 쓰기 경로가 악화되지 않았는지 일정 시간 관찰합니다. 인덱스는 생성 직후에는 좋아 보여도 데이터가 늘고 workload가 바뀌면 효과가 달라질 수 있습니다. 그래서 변경 이유, 대상 SQL, 측정 환경, 되돌림 기준을 짧게라도 남겨 두는 편이 좋습니다. 다음 담당자가 인덱스를 삭제하려 할 때도 왜 존재하는지 판단할 수 있습니다.

## 점검 체크리스트

느린 SQL을 개선하기 전에는 다음 질문을 순서대로 확인할 수 있습니다.

1. 이 SQL이 반환해야 하는 정확한 행, 정렬, 권한 규칙은 무엇인가?
2. 어떤 입력 값과 데이터 규모에서 사용자가 지연을 경험하는가?
3. EXPLAIN은 어떤 테이블을 어떤 순서로 읽고, 몇 행을 예상하는가?
4. 안전한 환경의 EXPLAIN ANALYZE에서 실제 행 수와 시간은 어떻게 다른가?
5. 조건의 자료형, 함수, LIKE 패턴, 조인 의미가 인덱스 이용을 막지는 않는가?
6. 인덱스·SQL·페이징 변경이 결과 정확성과 다른 쓰기 경로에 주는 영향은 무엇인가?
7. 적용 뒤 어떤 지표를 보고, 어떤 상태에서 되돌릴 것인가?

이 체크리스트는 모든 SQL을 느리게 분석하라는 지시가 아닙니다. 변경 비용이 큰 인덱스나 쿼리 재작성 전에, 추측을 재현 가능한 근거로 바꾸기 위한 최소 질문입니다. 간단한 쿼리는 단순하게 두고, 사용자 영향과 데이터 규모가 큰 곳에 조사 시간을 집중하는 것이 좋습니다.

또한 계획은 고정된 진실이 아니라 현재 데이터와 서버 조건에서 나온 선택입니다. MySQL 업그레이드, 통계 갱신, 인덱스 변경, 데이터 성장 뒤에는 중요한 SQL의 계획이 달라질 수 있습니다. 그래서 정기 점검은 모든 쿼리의 출력을 보관하는 일이 아니라, 고객 영향이 큰 대표 쿼리와 변경 이력이 있는 쿼리를 대상으로 계획·실행 시간·오류를 다시 확인하는 일에 가깝습니다. 문제를 빠르게 찾는 관측과, 성급하게 고정하지 않는 변경 관리가 함께 필요합니다.

성능 문제를 발견한 사람이 혼자 모든 결정을 맡을 필요도 없습니다. 개발자는 기능의 결과와 호출 맥락을, DBA는 데이터 분포와 변경 위험을, 제품 담당자는 허용 가능한 대기와 화면 요구를 설명할 수 있습니다. 이 정보를 한 번에 모으면 더 적은 시행착오로 안전한 선택을 할 수 있습니다.

## 통계와 플랜 안정성

옵티마이저의 선택은 데이터 분포에 대한 정보에 의존합니다. 대량 적재·삭제 뒤에 통계가 현실과 달라지면 같은 SQL도 전과 다른 계획을 선택할 수 있습니다. 통계를 갱신하면 특정 쿼리가 좋아질 수 있지만, 다른 쿼리의 계획도 바뀔 수 있습니다. 그래서 운영에서 통계 관리나 인덱스 변경은 하나의 느린 SQL만 보고 즉시 적용하기보다, 영향받는 주요 쿼리와 변경 창, 되돌릴 방법을 함께 준비해야 합니다.

힌트는 옵티마이저가 잘못된 선택을 한다는 증거가 충분하고, 더 나은 경로가 안정적으로 검증됐을 때 제한적으로 고려합니다. 힌트는 현재 데이터 분포와 버전에 맞는 결정을 코드에 고정할 수 있습니다. 시간이 지나 데이터가 변하거나 MySQL 버전이 바뀌면 과거의 힌트가 새 병목이 될 수 있습니다. 우선은 조건을 명확히 하고, 적절한 인덱스와 통계를 검토하며, 앱에서 불필요한 행을 요청하지 않는지 확인하는 편이 유지보수에 유리합니다.

## 업무 예시: 관리자 주문 검색의 느린 두 번째 페이지

관리자가 고객명, 상태, 기간으로 주문을 검색한다고 가정합니다. 첫 화면은 빨리 열리는데 두 번째 이후 페이지에서 늦다는 보고가 있습니다. 조사자는 먼저 문제의 파라미터를 복사하고 개인정보를 마스킹한 대표 값을 준비합니다. SQL이 `customers`를 이름으로 찾은 뒤 `orders`를 상태·기간으로 걸러 정렬하는지, 또는 주문 전체를 기간으로 읽은 뒤 고객과 조인하는지 EXPLAIN으로 확인합니다. `rows`가 커지는 위치와 선택한 인덱스를 기록합니다.

다음으로 안전한 복제 환경에서 EXPLAIN ANALYZE를 실행해 예상과 실제가 다른 구간을 찾습니다. 고객명 조건이 너무 넓어 고객 수가 많다면 검색 UX와 조건을 재검토할 수 있습니다. 주문의 상태와 생성 시각, 고객 ID가 함께 쓰인다면 실제 질의 패턴에 맞는 복합 인덱스를 검토합니다. 정렬과 페이징이 비용을 키운다면 커서 방식이 화면 요구에 맞는지 제품 담당자와 논의합니다. 이 과정에서 데이터 정합성, 날짜 기준, 권한 필터가 유지되는지를 테스트합니다.

변경 후에는 같은 파라미터에서 결과 행과 순서가 동일한지, 빈 결과와 동점 시각, 권한 없는 주문이 섞이지 않는지도 확인해야 합니다. 실행 시간이 줄었다고 해서 정렬 안정성이나 접근 권한이 깨진 변경을 배포하면 안 됩니다. 성능 테스트의 합격 기준은 빠른 숫자 하나가 아니라, 정확한 결과를 안전한 자원 범위에서 제공하는 것입니다.

## 한계와 적용 기준 Q&A

### Q. `type=ALL`이면 무조건 인덱스를 만들어야 하나요?

A. 아닙니다. 작은 테이블, 대부분의 행을 반환해야 하는 쿼리, 인덱스를 타는 비용이 더 큰 경우에는 전체 스캔이 합리적일 수 있습니다. 반환 행 수, 예상·실제 읽기 행, 응답 시간, 쓰기 비용을 함께 보고 판단하세요.

### Q. EXPLAIN ANALYZE를 운영 DB에서 실행해도 되나요?

A. 실제로 쿼리를 실행하므로 무조건 안전하다고 볼 수 없습니다. 데이터 변경 문장은 특히 피하고, 대용량 SELECT도 부하를 만들 수 있습니다. 가능하면 복제본이나 검증 환경에서 대표 파라미터로 확인하고, 운영에서 필요하다면 권한·시간 제한·영향 범위를 정한 절차를 따르세요.

### Q. 인덱스를 추가했는데 느린 쿼리가 그대로입니다. 왜인가요?

A. 조건의 선택도가 낮거나, 함수·형 변환 때문에 인덱스를 활용하지 못했거나, 조인·정렬·큰 OFFSET이 병목일 수 있습니다. EXPLAIN에서 실제 선택된 `key`와 `Extra`를, EXPLAIN ANALYZE에서 실제 행 수와 반복을 다시 확인해야 합니다. 새 인덱스가 존재한다는 것만으로 사용되거나 효과가 보장되지는 않습니다.

### Q. 힌트로 원하는 인덱스를 강제하면 빨리 해결되지 않나요?

A. 단기적으로는 가능할 수 있지만 데이터와 버전 변화에 취약한 고정 정책이 됩니다. 먼저 SQL 의미, 통계, 인덱스 열 순서, 반환 범위를 조사하세요. 힌트를 쓴다면 왜 필요한지, 어떤 데이터 조건에서 유효한지, 제거·재검토 시점이 무엇인지 문서화해야 합니다.

## 마무리

MySQL 실행 계획은 느린 SQL에 즉시 정답을 주는 화면이 아니라, 옵티마이저가 어떤 가정으로 어떤 경로를 택했는지 보여 주는 조사 도구입니다. EXPLAIN으로 가설을 세우고, 안전한 범위에서 EXPLAIN ANALYZE로 추정과 실제를 비교하며, 인덱스·조인·정렬·페이징·통계를 함께 읽으세요. 그러면 `ALL`이나 `filesort` 같은 단어에 반응하는 튜닝 대신, 업무 결과와 운영 비용을 같이 지키는 개선을 할 수 있습니다.
