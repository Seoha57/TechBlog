서비스가 나뉘면 API 변경은 한 저장소의 코드 변경으로 끝나지 않습니다. 주문 화면이 결제 API의 `status` 값을 읽고, 배치가 같은 API의 날짜 형식을 파싱하며, 모바일 앱이 오류 코드를 분기할 수 있습니다. 제공자 팀이 응답 필드를 삭제하거나 값의 의미를 바꿨을 때, 제공자 단위 테스트는 통과하지만 다른 팀의 배포가 깨질 수 있습니다. 소비자 주도 계약 테스트(Consumer-Driven Contract Testing, CDC)는 이 문제를 “누가 실제로 어떤 약속을 쓰는가”에서 출발해 다룹니다.

핵심은 소비자가 모든 제공자 API를 복제해 테스트하는 것이 아닙니다. 소비자는 자신이 의존하는 최소 요청·응답 기대를 계약으로 만들고, 제공자는 그 계약을 실제 구현에 대해 검증합니다. 이 구조는 변경 자체를 막지 않습니다. 대신 호환성 깨짐을 배포 전 가까운 곳에서 발견하고, 어느 소비자가 영향을 받는지 보여 주는 데 목적이 있습니다.

## 먼저 알아둘 기반 기술

API(Application Programming Interface)는 한 프로그램이 다른 프로그램에 기능이나 데이터를 요청하는 접점입니다. HTTP API에서는 클라이언트가 URL, method, header, body를 보내고 서버가 status code, header, body를 돌려줍니다. 계약(contract)은 이 통신에서 양쪽이 기대하는 형식과 의미입니다. `GET /orders/42`가 200과 주문 번호를 준다는 것뿐 아니라, `status`가 어떤 값일 수 있는지, 없는 주문은 어떤 오류인지까지 포함할 수 있습니다.

Mock은 실제 외부 시스템 대신 미리 정한 응답을 주는 테스트 대역입니다. Stub은 정해진 입력에 고정 응답을 주는 단순 대역이고, Spy는 호출 여부와 인자를 관찰합니다. 계약 테스트의 소비자 쪽 mock은 “제공자가 이 응답을 반드시 이렇게 준다”는 선언을 만들기 위한 도구입니다. 이 mock이 실제 제공자와 같다는 가정으로 끝나면 위험하지만, 제공자 검증 단계까지 연결하면 계약이 양쪽에 공통된 테스트 자료가 됩니다.

호환성(backward compatibility)은 새 버전이 이전 소비자를 깨지 않게 하는 성질입니다. 일반적으로 필드를 추가하는 변경은 소비자가 알지 못하는 값을 무시할 수 있다면 안전한 편이고, 필드 삭제·이름 변경·타입 변경·enum 값 의미 변경은 위험합니다. 그러나 “추가니까 안전하다”도 절대 규칙은 아닙니다. 소비자가 엄격한 schema 검증을 하거나 새 값에서 예외를 낼 수 있으므로 실제 소비자 계약과 배포 정책을 확인해야 합니다.

## 계약은 누가 작성하는가

소비자 주도라는 말은 제공자 팀이 API 설계를 포기한다는 뜻이 아닙니다. 제공자는 도메인 모델, 보안, 성능, 전체 API 일관성을 책임지고 OpenAPI 같은 명세를 관리할 수 있습니다. 소비자는 그중 자신이 실제로 사용하는 경로와 필드, 오류 처리 기대를 실행 가능한 계약으로 표현합니다. 예를 들어 주문 UI는 목록 화면에 필요한 `id`, `displayName`, `status`만 요구할 수 있고, 정산 배치는 `settledAt`의 시간대 형식까지 요구할 수 있습니다.

계약을 너무 크게 만들면 제공자의 내부 표현을 고정해 변경이 어려워집니다. 반대로 너무 작게 만들면 실제 사용 중인 오류 코드나 null 처리 같은 중요한 경계를 놓칩니다. 좋은 계약은 소비자가 업무를 수행하기 위해 정말 필요한 관찰 가능한 행동만 포함합니다. 데이터베이스 컬럼 순서, 제공자의 내부 클래스 이름, 사용하지 않는 응답 필드까지 계약에 넣지 않는 이유입니다.

소비자 팀도 계약을 작성한 뒤 방치하면 안 됩니다. 화면에서 더 이상 쓰지 않는 필드를 계약에 남기면 제공자는 불필요한 호환성 부담을 지게 됩니다. 소비자 배포에서 사용 지점을 제거하고 계약을 갱신하며, 어떤 버전의 소비자가 아직 운영 중인지 관리해야 합니다. 계약은 문서 한 장이 아니라 코드·테스트·배포 상태와 함께 수명 주기를 갖는 산출물입니다.

## 구체적 업무 예시: 주문 요약 카드

웹의 주문 요약 카드가 주문 API를 호출한다고 하겠습니다. 화면은 성공 시 `id`, `status`, `totalAmount`, `currency`를 표시하고, 주문이 없으면 404를 받아 빈 상태 화면을 보여 줍니다. 소비자 테스트는 실제 제공자 서버가 없어도 이 기대를 mock으로 확인합니다. 화면이 `totalAmount`를 숫자가 아닌 문자열로 처리하거나 404를 예외 화면으로 보내는 실수를 빠르게 찾을 수 있습니다.

계약에는 요청과 최소 응답을 적습니다. 같은 주문 ID 요청에 200, JSON body의 필요한 필드와 값 범위가 오는 경우, 존재하지 않는 ID에는 404와 정해진 오류 형식이 오는 경우를 포함할 수 있습니다. 모든 주문 상태와 모든 금액을 나열할 필요는 없지만, 소비자가 `PAID`와 `CANCELLED`를 다르게 표시한다면 두 상태가 계약 또는 별도 사례에 드러나야 합니다. 중요한 것은 화면 코드가 실제로 분기하는 조건을 계약이 반영하는 것입니다.

제공자 파이프라인은 이 계약을 받아 실제 API 구현에 실행합니다. 실제 DB를 모두 준비하지 않아도 제공자 테스트 fixture나 테스트용 데이터로 기대한 주문을 만들고, router·serializer·error handler를 거친 응답이 계약과 맞는지 확인합니다. 이 검증이 실패하면 제공자는 필드 이름을 바꿨는지, enum을 제거했는지, 인증 미들웨어가 테스트를 막는지 구체적으로 조사할 수 있습니다.

## 계약 테스트의 흐름

흐름은 보통 네 단계입니다. 첫째, 소비자가 mock을 대상으로 자신의 사용 코드를 테스트하고 계약 파일을 만듭니다. 둘째, 계약을 공유 저장소나 broker에 게시합니다. 셋째, 제공자가 계약을 내려받아 실제 구현을 대상으로 검증합니다. 넷째, 배포 도구가 어떤 소비자 버전과 제공자 버전의 조합이 검증됐는지 보고 배포 가능 여부를 판단합니다. 도구마다 파일 형식과 명령은 다르지만 이 책임 분리는 같습니다.

공유 broker는 단순 파일 저장소 이상으로 쓸 수 있습니다. 어떤 계약이 어느 소비자 버전에서 만들어졌는지, 제공자 검증이 어느 commit에서 성공했는지, 특정 조합을 배포해도 되는지 기록하는 근거가 됩니다. 하지만 broker가 있다고 자동으로 안전해지지는 않습니다. 소비자·제공자 빌드가 계약을 게시·검증하는지, 버전에 branch나 tag 정책이 있는지, 오래된 계약을 언제 정리하는지 정해야 합니다.

로컬 개발에서는 소비자가 제공자 환경을 기다리지 않고 mock으로 작업할 수 있다는 장점이 있습니다. 그러나 mock이 제공자의 모든 실제 동작을 재현한다고 믿으면 안 됩니다. 계약은 필요한 HTTP 경계를 검증하고, 실제 통합 테스트는 인증서·네트워크·데이터·성능 같은 다른 위험을 검증합니다. 빠른 계약 테스트와 적은 수의 실제 통합 테스트를 함께 두는 이유입니다.

## 변경 유형별 판단 기준

응답 필드 추가는 많은 JSON 소비자에게 호환될 수 있지만, 소비자가 unknown field를 금지하는 schema를 쓴다면 실패할 수 있습니다. 필드 삭제는 소비자가 아직 읽고 있다면 명백한 호환성 깨짐입니다. nullable을 허용하는 변경도 소비자가 null을 처리하지 않으면 화면 오류가 될 수 있습니다. 숫자를 문자열로 바꾸거나 날짜 형식을 바꾸는 것은 JSON 문법상 유효해도 업무 의미를 바꿀 수 있으므로 계약에서 타입과 예시를 확인해야 합니다.

요청 변경은 더 조심해야 합니다. 새 필수를 추가하면 이전 소비자는 요청을 만들지 못하고, 기존 enum 값을 폐기하면 오래된 앱이 서버에서 거절될 수 있습니다. 제공자가 새 요구를 도입해야 한다면 optional 기간, 기본값, 새 endpoint 또는 새 버전, 소비자 이전 기한을 정합니다. 계약 테스트는 이러한 이전 계획이 실제 소비자 버전에서 가능한지 검증하는 입력이 됩니다.

오류 응답도 계약입니다. 성공 body만 검증하면 제공자가 validation 오류 형식을 바꿨을 때 소비자는 사용자에게 이해하기 어려운 메시지를 보여 줄 수 있습니다. 인증 실패, 권한 거절, 입력 오류, 리소스 없음, 일시적 장애 중 소비자가 분기하는 사례를 고르고 status·오류 code·재시도 가능 여부를 계약에 넣으세요. 내부 stack trace나 DB 오류 문자열처럼 안정적이지 않고 민감한 값은 계약 대상이 아닙니다.

## API 명세와 계약 테스트를 함께 쓰는 법

OpenAPI는 제공자 중심의 전체 표면을 설명하는 데 좋습니다. endpoint, parameter, schema, 인증 방식, 문서 예시를 한 곳에 보여 주므로 새 소비자가 API를 발견하고 설계 리뷰를 할 수 있습니다. lint와 schema validation은 명세 자체의 오류, 누락, 일관성 문제를 찾는 데 도움을 줍니다. 그러나 OpenAPI만으로 “현재 웹 화면이 이 오류 형식을 실제로 처리한다”는 사실까지 증명되지는 않습니다.

소비자 계약은 실제 의존을 작고 실행 가능한 사례로 표현합니다. 따라서 명세와 계약의 필드 이름이 달라지거나, 계약이 명세에 없는 endpoint를 요구하면 어느 쪽이 최신 약속인지 검토할 신호가 됩니다. 두 문서를 자동으로 완전히 변환하려 하기보다, API 변경 pull request에서 OpenAPI diff와 관련 소비자 계약을 함께 확인하는 방식이 현실적입니다.

문서의 예시는 계약의 유일한 근거가 되면 안 됩니다. 예시는 설명을 위해 단순화되며 실제 데이터의 null, 빈 배열, 오류 경계를 빠뜨릴 수 있습니다. 반대로 계약은 모든 API 동작을 설명하는 사용자 문서가 아닙니다. 명세는 발견성과 공통 규칙을, 계약은 실제 의존과 회귀 검증을, 통합 테스트는 실행 환경의 위험을 맡도록 역할을 분리하면 중복을 줄일 수 있습니다.

## 계약 품질을 높이는 테스트 설계

계약 사례 이름은 업무 행동을 드러내야 합니다. “case 1”보다 “결제 완료 주문을 조회하면 카드 표시에 필요한 금액과 통화를 반환한다”가 실패 원인을 이해하기 쉽습니다. matcher는 너무 고정된 값보다 의미 있는 범위를 표현해야 합니다. 매번 달라지는 UUID나 생성 시각을 정확한 문자열로 고정하면 무의미한 실패가 생기고, 아무 값이나 허용하면 타입 변경을 놓칠 수 있습니다.

상태를 준비하는 방식도 제공자 팀과 합의합니다. 계약의 provider state는 “결제 완료 주문이 존재함” 같은 업무 조건을 말해야지 “orders 테이블에 3번 행 삽입” 같은 내부 구현을 말하면 안 됩니다. 제공자 검증 코드는 이 상태를 테스트 fixture, factory, 격리된 DB 등 환경에 맞는 방식으로 준비할 수 있어야 합니다. 이 경계가 지켜져야 제공자가 저장소를 리팩터링해도 소비자 계약이 불필요하게 깨지지 않습니다.

비동기 API와 이벤트도 같은 원리로 다룰 수 있습니다. 메시지 producer가 어떤 event name, key, payload를 발행하고 consumer가 무엇을 기대하는지 계약으로 검증합니다. 다만 메시지는 중복 전달·순서 변경·지연이 가능하므로 한 번의 payload 형식뿐 아니라 idempotency와 버전 처리도 테스트에 넣어야 합니다. HTTP 계약 도구의 편리한 흐름을 그대로 복사하기보다 브로커와 소비자 특성에 맞는 검증을 설계하세요.

## 인증·권한·테넌트 경계도 계약이다

API 계약을 성공 응답 body로만 한정하면 실제 서비스의 중요한 경계를 놓칩니다. 동일한 `GET /orders/42`라도 로그인하지 않은 요청은 401, 다른 조직의 주문은 403 또는 존재하지 않는 것처럼 처리하는 404, 올바른 조직의 사용자는 200을 받아야 할 수 있습니다. 소비자가 이 status에 따라 로그인 화면, 권한 안내, 빈 상태 화면을 다르게 보여 준다면 그 분기도 계약 사례가 됩니다. 제공자 구현이 권한 미들웨어를 바꾸었을 때 화면이 민감한 존재 정보를 노출하지 않는지 확인할 수 있습니다.

멀티테넌트 API에서는 같은 resource ID가 다른 조직에서 보이는지, list API가 조직 필터를 잃지 않는지, pagination token이 다른 조직에 재사용되지 않는지도 위험한 경계입니다. 모든 보안 테스트를 계약 테스트로 해결할 수는 없지만, 소비자가 신뢰하는 공개 동작을 계약에 담으면 제공자 변경이 접근 제어를 우회했을 때 빠르게 알 수 있습니다. 단, 계약 파일에는 실제 고객 이름, token, 권한 정책의 내부 세부 정보를 넣지 않고 합성 식별자와 행동 중심의 기대를 사용합니다.

인증 방식 자체를 OAuth 토큰에서 다른 방식으로 옮기거나, header 이름을 바꾸는 변경은 소비자 배포 순서가 특히 중요합니다. 새 방식을 먼저 optional로 받는 제공자 배포, 소비자의 전환, 이전 방식의 관찰 기간, 제거 순서를 정합니다. 계약 검증은 새 header를 포함한 요청과 이전 소비자의 요청이 필요한 기간에 모두 동작하는지 증명할 수 있습니다. 보안 강화를 이유로 갑자기 모든 오래된 클라이언트를 끊지 않도록, 위험도와 이전 기한을 명확히 해야 합니다.

## Pagination·정렬·시간은 작은 차이로 깨진다

목록 API는 응답 배열만 맞으면 되는 것처럼 보이지만 pagination과 정렬 규칙이 달라지면 소비자의 중복 표시·누락·무한 스크롤 오류로 이어질 수 있습니다. cursor 기반인지 offset 기반인지, 다음 페이지 token이 없는 경우를 어떻게 표현하는지, 정렬 기준과 동률 처리 방식이 무엇인지 소비자가 의존하는 범위를 계약에 적습니다. 특히 새 레코드가 중간에 들어오는 상황에서 페이지 간 중복을 어느 정도 허용하는지 제품 정책을 정해야 합니다.

시간 값도 호환성 문제를 자주 만듭니다. `2026-10-27T08:30:00Z`처럼 시간대가 포함된 ISO 8601 문자열을 주는지, null일 수 있는지, 서버 시간이 아니라 업무 발생 시간을 뜻하는지 소비자가 알아야 합니다. 표시 UI는 사용자 시간대로 변환하고, 배치는 날짜 경계로 집계할 수 있습니다. 제공자가 날짜만 내려주도록 바꾸거나 timezone을 생략하면 문법은 맞아도 특정 지역에서 업무 날짜가 달라질 수 있습니다. 계약에는 형식뿐 아니라 필요한 경우 의미 있는 예시와 null 경계를 포함합니다.

금액과 decimal 값도 마찬가지입니다. JSON number를 쓰는지 문자열을 쓰는지, 통화 코드와 소수점 자릿수를 어떻게 다루는지, 합계가 세금 전인지 후인지 소비자가 표시·계산을 한다면 명시해야 합니다. 계약 테스트는 회계 정확성을 전부 증명하지는 않지만, 제공자가 `12000`을 `120.00`으로 해석하게 만드는 단위 변경 같은 위험한 회귀를 발견하는 데 도움을 줍니다.

## 실패를 조사할 수 있는 계약 파이프라인

계약 검증이 실패했을 때 개발자가 가장 먼저 알아야 할 것은 ‘무슨 계약의 어느 상호작용이 어떤 제공자 버전에서 깨졌는가’입니다. CI 출력에 소비자 이름, 계약 버전, request 요약, 기대한 status·필드, 실제 응답의 안전한 차이를 남깁니다. body 전체나 authorization header를 로그에 남기면 빠른 분석과 맞바꾸어 민감 정보를 노출할 수 있으므로, 필요한 값만 마스킹하고 상세 조회는 접근 통제된 저장소에서 하도록 합니다.

제공자 검증 실패를 flaky하게 만들지 않는 것도 중요합니다. 계약 검증 fixture가 현재 시각, 공유 테스트 DB, 외부 네트워크, 임의 생성 데이터에 따라 달라지면 팀은 실패를 신뢰하지 않게 됩니다. clock을 고정하고, provider state를 격리하며, 외부 호출은 제어 가능한 대역으로 바꾸고, 테스트가 끝난 뒤 상태를 정리합니다. 계약 테스트는 빠른 피드백이 장점이므로, 환경 준비가 느린 거대한 E2E 파이프라인으로 변하지 않게 범위를 관리해야 합니다.

실패 추세도 관찰합니다. 특정 endpoint 계약이 자주 깨진다면 제공자 API가 실제 소비자 요구와 분리되어 있거나, 팀이 배포 순서 없이 제거 변경을 하고 있다는 신호일 수 있습니다. 반대로 오랫동안 한 번도 실패하지 않는 계약은 안정적인 경계일 수도 있지만, 소비자 코드가 더 이상 그 경로를 쓰지 않는 죽은 테스트일 수도 있습니다. 실패 횟수만 평가 지표로 삼지 말고, 변경을 막은 실제 사례와 유지 비용을 함께 검토하세요.

## 계약 버전과 지원 종료 정책

계약 파일에는 생성한 소비자 버전과 branch, 제공자 검증 버전을 연결할 수 있습니다. 이 정보가 없으면 제공자 팀은 실패한 계약이 현재 운영 중인 앱인지, 이미 폐기된 feature branch인지 판단하기 어렵습니다. release tag 또는 배포 환경의 버전을 일관된 방식으로 기록하고, 임시 branch 계약은 병합·폐기 시 정리하는 정책을 둡니다.

지원 종료는 기술 문제가 아니라 제품·고객·운영의 결정입니다. 오래된 모바일 앱이나 외부 파트너가 이전 endpoint를 계속 쓴다면, 제공자는 제거 전 공지와 측정 기간을 가져야 합니다. access log, API key 사용량, 계약 broker의 배포 기록으로 실제 사용 여부를 확인하되, 로그만으로 모든 숨은 소비자를 찾을 수 있다고 과신하지 않습니다. 위험한 제거는 compatibility shim, 새 버전 병행, 명시적 종료 날짜를 통해 단계적으로 수행합니다.

계약 테스트는 이 과정에서 ‘언제 지워도 된다’를 자동으로 결정하지 않습니다. 대신 알려진 소비자와의 호환성 증거를 제공하고, 팀이 남은 불확실성을 문서화하게 합니다. 이 한계를 인정하면 계약 도구의 결과를 과도한 승인 도장으로 쓰지 않고, 배포 의사결정에 필요한 한 가지 강한 근거로 사용할 수 있습니다.

## 배포 순서와 can-i-deploy 판단

호환성 변경의 가장 안전한 순서는 보통 확장, 이전, 정리입니다. 제공자가 새 optional 필드나 새 endpoint를 먼저 배포하고, 소비자가 새 기능을 쓰도록 배포하며, 운영 중인 오래된 소비자가 사라진 뒤에만 이전 필드를 제거합니다. 이를 expand-and-contract라고 부르기도 합니다. 계약 검증 결과는 “이 제공자 버전을 지금 운영 중인 소비자와 함께 배포해도 되는가”를 판단하는 근거가 됩니다.

하지만 배포 가능 판정이 절대적인 승인 도장은 아닙니다. 계약에 등록되지 않은 외부 소비자, 수동 스크립트, 오래된 모바일 앱, 데이터 마이그레이션, feature flag 조합은 별도로 관리해야 합니다. 배포 도구에 모든 것을 맡기기보다 API 소유자 목록과 지원 버전 정책을 문서화하고, 위험한 제거 변경에는 공지·관찰 기간·rollback 계획을 둡니다.

계약 검증이 실패하면 무조건 제공자 코드를 이전으로 되돌리기보다 어떤 계약이 왜 깨졌는지 봅니다. 소비자가 더 이상 사용하지 않는 기대라면 계약을 갱신해야 하고, 제공자가 실수로 공개 약속을 깨뜨렸다면 제공자 변경을 수정해야 합니다. 두 팀이 같은 실패 결과를 보고 대화할 수 있다는 점이 계약 테스트의 큰 가치입니다. 실패를 남 탓의 증거가 아니라 변경 영향의 증거로 다루는 문화가 필요합니다.

## 한계와 적용 기준 Q&A

### Q. 소비자마다 계약을 만들면 너무 많아지지 않나요?

A. 실제로 사용하지 않는 계약을 쌓으면 관리 비용이 늘어납니다. 소비자별 화면·배치가 중요한 분기를 쓰는 경우에만 최소 계약을 만들고, 사용이 끝난 계약은 소비자 코드 제거와 함께 정리하세요. 같은 API의 전체 schema를 소비자마다 복제하는 것은 계약 테스트의 목적과 맞지 않습니다.

### Q. 제공자가 계약을 모두 만족해야 새 기능을 못 만드는 것 아닌가요?

A. 기존 소비자를 보호하는 것과 새 기능을 막는 것은 다릅니다. optional 확장, 새 endpoint, 명시적 버전, 지원 종료 기간을 사용하면 새 기능을 도입하면서 이전 소비자를 이동시킬 수 있습니다. 계약이 알려 주는 것은 변경 불가능성이 아니라 지금 깨질 소비자가 있다는 사실입니다.

### Q. 프론트엔드와 백엔드가 같은 저장소면 필요 없나요?

A. 같은 저장소라도 배포 주기와 책임이 다르거나, API를 배치·모바일·외부 연동이 함께 쓴다면 계약 검증이 도움이 될 수 있습니다. 반대로 한 팀이 한 번에 바꾸고 충분한 통합 테스트를 유지한다면 별도 도구 비용이 과할 수 있습니다. 조직 구조와 변경 위험을 기준으로 선택하세요.

## 도입 체크리스트

계약을 작성할 때 null·빈 값·경계값을 의식적으로 고르세요. 이름이 없는 고객, 주문 항목이 빈 배열인 주문, 최대 길이에 가까운 메모, 지원하지 않는 enum 값, pagination 마지막 페이지는 소비자 코드가 자주 놓치는 경계입니다. 모든 조합을 계약에 넣을 필요는 없지만, 소비자가 화면·계산·분기를 실제로 다르게 처리하는 값은 대표 사례로 남겨야 합니다. 제공자는 이 사례를 통해 serializer나 validation 변경이 단순한 리팩터링인지 공개 행동 변경인지 구분할 수 있습니다.

계약의 matcher도 코드 리뷰 대상입니다. 너무 엄격한 matcher는 임의 ID와 시간 값이 바뀔 때마다 실패해 신뢰를 떨어뜨리고, 너무 느슨한 matcher는 문자열이 숫자로 바뀌거나 필수 필드가 사라져도 통과시킬 수 있습니다. 업무 의미가 있는 타입, 형식, 최소 길이, enum 범위, 배열의 핵심 요소를 표현하되 제공자의 불필요한 구현 세부를 고정하지 않는 균형이 필요합니다. 실패가 발생했을 때 ‘이 제약이 소비자 업무에 왜 필요한가’를 설명할 수 있어야 합니다.

마지막으로 계약 검증은 배포 전 gate일 뿐 아니라 설계 피드백입니다. 같은 제공자 API에 서로 충돌하는 소비자 기대가 반복되면 endpoint 목적이 너무 넓거나, 표현 모델이 여러 업무를 섞고 있을 수 있습니다. 이때 계약을 억지로 모두 만족시키기보다, 읽기 모델을 분리하거나 새 endpoint를 만들고 이전 계획을 세우는 것이 장기적으로 더 단순할 수 있습니다.

계약 테스트를 코드 리뷰에 연결할 때는 질문을 단순하게 유지합니다. 이 API 변경을 실제로 쓰는 소비자는 누구인가, 삭제·타입 변경·새 필수값이 있는가, 성공뿐 아니라 소비자가 처리하는 오류 계약이 바뀌는가, 제공자 검증은 어느 commit에서 성공했는가를 확인합니다. 질문이 너무 길면 형식적인 체크가 되므로, 변경 위험이 높은 API부터 적용하고 팀이 실제 실패 사례를 통해 필요한 항목을 보완하는 편이 좋습니다.

계약 artifact의 신뢰도도 관리합니다. CI가 소비자 코드와 같은 commit에서 계약을 만들었는지, 제공자 검증이 실제 배포 후보 구현을 대상으로 했는지, 테스트 환경이 다른 응답을 섞지 않았는지 확인해야 합니다. 오래된 artifact를 새것처럼 쓰거나, 로컬에서 만든 파일을 수동으로 올리면 검증 결과가 현재 코드의 증거가 아닐 수 있습니다. build metadata와 commit SHA를 연결하면 이 위험을 줄일 수 있습니다.

외부 파트너 API처럼 계약을 직접 공유하기 어려운 경우에는 계약 테스트의 원리를 적용하되 운영 모델을 다르게 가져갑니다. 파트너가 제공한 공식 sandbox, schema, 변경 공지, 합성 테스트 계정으로 핵심 요청·응답을 정기 검증하고, 실제 production 호출의 오류·지연·응답 형식 변화를 관찰합니다. 상대 시스템의 내부 build를 검증할 수 없다는 한계를 문서화하고, timeout·fallback·지원 연락 경로를 서비스 설계에 넣어야 합니다.

계약 테스트가 잘 작동하는 조직에서는 QA가 단순히 실패 결과를 받아보는 사람이 아니라 계약의 위험도를 함께 정의합니다. 어떤 필드가 화면 문구를 바꾸는지, 어떤 오류가 고객 행동을 막는지, 이전 앱 버전이 얼마나 남아 있는지, 배포 뒤 어떤 지표를 봐야 하는지를 개발·운영과 같은 언어로 정리합니다. 이 협업이 있어야 실행 가능한 계약이 실제 고객 경험을 보호하는 테스트가 됩니다.

계약 파일과 검증 결과는 변경 이력의 일부이므로, 누가 언제 어떤 이유로 기대를 바꿨는지 pull request에서 읽을 수 있어야 합니다. 이렇게 남은 근거는 새 팀원이 API를 이해하고, 장애 뒤 호환성 판단을 되짚으며, 지원 종료를 합의할 때도 유용합니다.

처음에는 장애 비용이 큰 API 하나와 실제 소비자 하나를 고릅니다. 소비자가 필요한 성공·오류 사례를 계약으로 만들고, 제공자가 CI에서 검증하며, 계약과 검증 결과의 버전을 연결합니다. 이후 필드 삭제나 타입 변경 같은 위험한 pull request에서 계약 실패가 실제로 도움이 되는지 확인하세요. 모든 API를 한 번에 이전하기보다, 변경이 잦고 소비자가 여러 개인 경계에서 먼저 가치를 확인하는 편이 낫습니다.

소비자 주도 계약 테스트는 API 명세, 단위 테스트, 통합 테스트, 운영 모니터링을 대체하지 않습니다. 대신 팀 사이의 “암묵적으로 쓰고 있던 약속”을 작고 실행 가능한 테스트로 바꿉니다. 계약의 범위를 소비자 업무에 맞게 유지하고, 호환성 변경을 배포 순서와 함께 설계하면 API 변경은 예측할 수 없는 연쇄 장애보다 검증 가능한 협업 작업에 가까워집니다.

처음부터 모든 endpoint를 계약화하려 하기보다, 독립 배포되는 팀이 둘 이상이고 변경 비용이 큰 경계 하나를 선택하세요. 실패가 발생했을 때 어떤 소비자와 어떤 약속이 영향을 받았는지를 몇 분 안에 설명할 수 있다면, 계약 테스트는 이미 문서보다 한 단계 강한 안전망 역할을 하고 있는 것입니다.

이 안전망은 배포를 멈추게 하는 장벽이 아니라, 변경 전 필요한 대화와 검증을 앞당기는 장치입니다. 계약이 작고 최신 상태로 유지될수록 팀은 더 빠르게 바꾸면서도 소비자 영향을 숨기지 않을 수 있습니다.

검증 가능한 약속은 협업 비용도 줄입니다.

작은 변화부터 시작하세요.
