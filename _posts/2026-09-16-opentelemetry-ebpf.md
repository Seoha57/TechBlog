서비스가 여러 개로 나뉘면 장애 원인을 찾는 일이 어려워집니다. 사용자의 요청이 어느 API로 들어왔는지, 어떤 서비스로 전달됐는지, 데이터베이스 응답이 느렸는지를 하나의 흐름으로 연결해야 하기 때문입니다. OpenTelemetry는 traces, metrics, logs처럼 시스템 상태를 보여주는 관측 데이터를 표준 형식으로 수집·처리·전달하기 위한 오픈 소스 프로젝트입니다. Trace는 한 요청의 이동 경로, metric은 수치화된 상태, log는 사건의 상세 기록이라고 생각하면 됩니다.

조금 더 쉽게 말하면 OpenTelemetry는 서비스의 동작을 기록해 장애가 어느 구간에서 발생했는지 추적하게 해주는 공통 수집 체계입니다. 사용자가 상품을 조회하면 요청은 상품 API, 재고 서비스, 데이터베이스를 차례로 거칠 수 있습니다. 이때 Trace는 각 구간을 하나의 요청으로 연결하고, Metric은 요청 수와 오류율·응답 시간을 수치로 남기며, Log는 특정 시점의 상세 메시지를 기록합니다. 예를 들어 로그에 “상품 조회 실패”만 남는 대신 `상품 API 80ms → 재고 서비스 120ms → PostgreSQL 2,300ms`처럼 병목 구간을 파악할 수 있습니다.

OpenTelemetry 자체가 완성된 모니터링 화면을 제공하는 제품은 아닙니다. 데이터를 일정한 형식으로 수집하고 Jaeger, Prometheus, Grafana, Datadog 같은 관측 도구로 전달하는 표준과 구성 요소에 가깝습니다. 따라서 “OpenTelemetry를 설치하면 대시보드가 바로 생긴다”기보다, 애플리케이션과 인프라에서 신호를 수집해 기존 관측 시스템에 연결한다고 이해하는 편이 정확합니다.

문제는 모든 애플리케이션에 SDK를 직접 추가하는 일이 쉽지 않다는 점입니다. 오래된 서비스, 소유 팀이 다른 서비스, 재빌드가 어려운 바이너리, 여러 언어가 섞인 환경에서는 코드 기반 계측을 일관되게 적용하기 어렵습니다. eBPF는 Linux 커널 안에서 실행되는 작은 프로그램을 안전하게 연결해 네트워크나 프로세스 이벤트를 관찰하는 기술입니다. OpenTelemetry eBPF Instrumentation(OBI)은 이를 활용해 프로세스 외부에서 기본 관측 신호를 수집하는 접근입니다.

## OpenTelemetry와 자동 계측

OpenTelemetry는 traces, metrics, logs를 수집·처리·내보내기 위한 오픈 소스 관측성 프레임워크입니다. 여기서 중요한 것은 특정 모니터링 제품의 기능이 아니라, 데이터를 표현하고 전달하는 공통 규약을 제공한다는 점입니다. 애플리케이션이 어떤 언어로 작성됐는지와 관계없이 수집된 신호를 같은 생태계 안에서 다룰 수 있습니다.

일반적인 SDK 기반 계측은 개발자가 코드에 tracer와 span을 추가하는 방식입니다. 예를 들어 결제 함수의 시작과 종료를 span으로 감싸고, 주문번호나 결제수단 같은 속성을 추가할 수 있습니다. 이 방식은 서비스의 업무 의미를 가장 정확하게 표현할 수 있지만, 코드 변경과 배포가 필요합니다.

자동 계측은 애플리케이션 내부에 최소한의 변경을 가하거나, 런타임에 계측 모듈을 연결해 공통 프레임워크의 요청을 수집합니다. 하지만 언어·라이브러리·버전에 따라 지원 범위가 달라질 수 있습니다. OpenTelemetry eBPF Instrumentation은 이 부담을 줄이기 위해 프로세스 외부에서 프로토콜 수준의 정보를 관찰하는 방식을 사용합니다. [OpenTelemetry 공식 발표](https://opentelemetry.io/blog/2025/obi-announcing-first-release/)는 OBI가 eBPF를 기반으로 동작하고, 코드 변경이나 애플리케이션 의존성 추가 없이 기본 telemetry를 수집하는 방향을 설명합니다.

이 차이를 이해하면 eBPF 자동 계측을 과장하지 않게 됩니다. HTTP 요청이 어느 서비스로 들어갔고 얼마나 오래 걸렸는지는 관찰할 수 있어도, 그 요청 안에서 “회원 등급 계산”이라는 특정 비즈니스 단계가 있었다는 사실은 애플리케이션 코드의 의미를 알지 못하면 표현하기 어렵습니다.

## eBPF는 어디에서 관측하는가

eBPF는 Linux 커널에서 안전하게 실행할 수 있는 프로그램을 이용해 네트워크와 프로세스의 동작을 관찰하는 기술입니다. 자동 계측 도구는 애플리케이션 코드에 직접 span을 삽입하는 대신, 시스템 호출이나 네트워크 프로토콜, 프로세스 정보를 활용해 요청 흐름을 추론합니다.

예를 들어 서비스 A가 서비스 B로 HTTP 요청을 보내면, 네트워크 계층에서 연결과 요청·응답의 흐름을 관찰할 수 있습니다. 이 정보를 서비스 이름, 요청 경로, 응답 코드, 지연시간과 연결하면 RED 지표와 서비스 그래프를 구성할 수 있습니다. OpenTelemetry 공식 자료는 OBI가 이런 기본적인 metrics와 traces를 빠르게 확보하는 용도로 활용될 수 있다고 설명합니다.

이 방식의 장점은 적용 범위입니다. 애플리케이션 언어마다 SDK를 설치하고 버전을 맞추지 않아도 공통 네트워크 흐름을 관찰할 수 있습니다. 여러 팀이 운영하는 클러스터에서 일부 서비스에만 계측이 되어 있거나, 오래된 바이너리를 다시 빌드하기 어려운 경우 특히 유용할 수 있습니다.

하지만 커널 수준에서 얻을 수 있는 정보에는 한계가 있습니다. 함수 내부의 업무 단계, 사용자가 선택한 상품의 의미, 특정 SQL의 비즈니스 목적은 네트워크 정보만으로 알기 어렵습니다. 또한 암호화된 트래픽, 지원되지 않는 프로토콜, 비표준 라이브러리에서는 기대한 신호가 나오지 않을 수 있습니다.

따라서 eBPF 자동 계측은 “관측성의 완성품”이라기보다 빈 곳을 빠르게 채우는 계층으로 보는 편이 적절합니다. 이미 SDK 계측이 된 서비스에서는 중복 수집을 피하고, 계측되지 않은 서비스에는 공통적인 요청 흐름을 제공하는 식으로 조합할 수 있습니다.

## SDK 계측과 eBPF 계측 비교

SDK 계측과 eBPF 계측은 경쟁 관계라기보다 서로 다른 질문에 답합니다. SDK는 “이 코드 안에서 어떤 업무 단계가 진행됐는가”에 강합니다. eBPF는 “이 프로세스와 서비스 사이에서 어떤 요청이 오갔는가”를 빠르게 파악하는 데 강합니다.

예를 들어 API 요청의 전체 지연시간이 2초라고 가정해 보겠습니다. eBPF 기반 신호는 해당 요청이 인증 서비스에서 200ms, 상품 서비스에서 1.5초, 데이터베이스 연결에서 250ms를 사용했다는 식의 흐름을 제공할 수 있습니다. 그러면 조사 범위를 상품 서비스로 좁힐 수 있습니다.

그러나 상품 서비스 내부에서 캐시 조회가 50ms이고 재고 계산이 1.4초였다는 정보까지 필요하다면 코드 기반 span이 필요합니다. 개발자가 직접 `inventory.calculate` 같은 구간에 span을 추가해야 업무 의미가 보존됩니다. 두 계층을 함께 사용하면 인프라 수준의 넓은 관측성과 애플리케이션 수준의 상세한 설명을 연결할 수 있습니다.

| 기준 | SDK 계측 | eBPF 자동 계측 |
|---|---|---|
| 코드 변경 | 필요할 수 있음 | 기본 신호는 코드 변경 없이 수집하는 방향 |
| 비즈니스 의미 | 상세하게 표현 가능 | 제한적 |
| 적용 범위 | 라이브러리와 언어에 영향 | 커널·프로토콜·실행 환경에 영향 |
| 배포 부담 | 애플리케이션 재배포 필요 | 별도 에이전트·권한 검토 필요 |
| 적합한 용도 | 핵심 업무 흐름과 세부 span | 서비스 그래프와 기본 요청 지표 |

표의 내용은 도구와 버전에 따라 달라질 수 있습니다. 실제 지원 범위는 사용하는 OBI 릴리스와 운영체제, 프로토콜 목록을 확인해야 합니다. OpenTelemetry 프로젝트도 eBPF 계측을 다른 OpenTelemetry 기술과 함께 사용할 때 더 효과적이라고 설명합니다.

## 적용 전 확인할 조건

첫 번째 조건은 커널과 실행 환경입니다. eBPF는 Linux 커널 기능과 권한 정책의 영향을 받습니다. Kubernetes에서 DaemonSet으로 배포한다면 노드마다 필요한 권한과 host 네임스페이스 접근 범위를 검토해야 합니다. 보안 정책이 강한 환경에서는 관측 에이전트가 요구하는 capability를 허용할 수 있는지부터 확인해야 합니다.

두 번째 조건은 수집 데이터의 민감도입니다. 요청 경로, 헤더, 데이터베이스 쿼리, 프로세스 정보에는 개인정보나 인증 정보가 포함될 수 있습니다. 원본 데이터를 모두 수집하는 대신 필요한 속성만 남기고, 민감한 헤더를 마스킹하며, 보존 기간을 정하는 정책이 필요합니다.

세 번째 조건은 중복 신호와 비용입니다. 이미 SDK가 trace를 만들고 있는데 eBPF가 같은 흐름을 별도로 수집하면 중복 span과 서비스 그래프가 생길 수 있습니다. OpenTelemetry 자료에서는 이미 계측된 애플리케이션을 감지해 중복을 피하는 방향을 설명하지만, 실제 파이프라인에서 resource attribute와 trace context가 어떻게 합쳐지는지는 확인해야 합니다.

네 번째 조건은 관측 데이터의 해석입니다. 자동 계측으로 많은 지표를 수집해도 알람 기준이 없으면 운영 부담만 커질 수 있습니다. 요청 오류율, 지연시간, 요청량, 서비스 간 dependency를 어떤 SLO와 연결할지 먼저 정해야 합니다. “데이터를 수집할 수 있다”와 “장애를 빠르게 판단할 수 있다”는 서로 다른 문제입니다.

OpenTelemetry eBPF 자동 계측은 코드 변경을 줄이면서 서비스 흐름을 파악할 수 있는 새로운 선택지입니다. 그렇다고 SDK 계측이나 기존 모니터링을 모두 대체하는 기술은 아닙니다. eBPF가 제공하는 넓은 관측 범위와 SDK가 제공하는 업무 의미를 구분하고, 보안 권한과 데이터 수집 범위를 함께 설계해야 합니다.
