## 먼저 알아둘 기반 기술

LLM(Large Language Model, 대규모 언어 모델)은 입력으로 받은 token을 순서대로 처리해 다음 token을 생성합니다. token은 글자 하나와 정확히 같지는 않지만, 텍스트를 모델이 계산하는 단위로 나눈 것입니다. 긴 system prompt, 제품 문서, 정책, 대화 이력, 도구 결과를 매 요청마다 다시 넣으면 입력 처리 시간과 비용이 커질 수 있습니다. 특히 같은 지시문과 같은 참조 문서를 수많은 사용자 요청에 반복하면 앞부분 계산이 상당히 중복됩니다.

프롬프트 캐싱은 반복되는 입력 prefix의 계산 결과를 일정 조건에서 다시 쓰는 기능 또는 설계 방식입니다. 제공자가 모델 내부 처리 결과를 재사용할 수도 있고, 애플리케이션이 문서 전처리·요약·검색 결과를 cache할 수도 있습니다. 둘 다 “같은 결과를 저장한다”는 일반 캐시와 닮았지만, LLM의 출력은 sampling, 모델 version, 도구 호출, 최신 데이터에 따라 달라질 수 있으므로 정확성과 격리 조건을 더 신중하게 다뤄야 합니다.

cache key는 어떤 요청이 이전 결과나 prefix와 같은지 판단하는 기준입니다. URL 캐시에서 경로와 query parameter가 key가 되듯, LLM에서는 모델 이름과 version, system prompt, tool schema, 문서 version, 언어, tenant, 권한, 프롬프트 순서가 key의 일부가 될 수 있습니다. 너무 넓은 key는 서로 다른 요청을 같은 것으로 취급해 잘못된 문맥을 재사용할 수 있고, 너무 좁은 key는 hit가 거의 나지 않아 복잡성만 남깁니다.

## 무엇을 캐시할지 먼저 나누기

가장 재사용하기 좋은 대상은 많은 요청에서 공통으로 유지되는 안정적인 prefix입니다. 제품의 역할과 금지 규칙을 담은 system prompt, 변하지 않는 출력 형식, 고정된 tool schema, version이 명확한 제품 매뉴얼 요약 등이 예가 될 수 있습니다. 이런 내용은 요청마다 앞부분에 같은 순서로 배치하고, 사용자 질문과 최신 도구 결과는 뒤쪽에 둡니다. 캐시를 기대하는 내용과 매번 달라지는 내용을 섞어 앞에 두면 hit 조건을 만족하기 어렵습니다.

반대로 사용자별 프로필, 접근 권한, 실시간 가격, 개인 문서 원문, 현재 주문 상태는 신중해야 합니다. 이런 데이터를 prefix에 넣어 공유 캐시의 이점을 노리면 hit보다 정보 격리 문제가 더 커질 수 있습니다. 사용자별 데이터는 인증된 요청 뒤에 결합하고, 서버는 응답을 생성하기 전에 권한 filter를 다시 적용해야 합니다. 캐시가 있다고 해서 authorization check를 생략하면 안 됩니다.

RAG(Retrieval-Augmented Generation)는 관련 문서를 검색해 LLM에 함께 주는 방식입니다. 검색된 chunk는 질문마다 달라지므로 모델 prefix cache와 항상 잘 맞지는 않습니다. 다만 문서 collection의 공통 안내, citation 형식, 고정된 분류 체계는 재사용할 수 있습니다. 검색 결과 자체는 문서 version, query, tenant, filter를 포함한 별도 cache로 관리할 수 있으며, 이 cache와 모델 입력 cache를 같은 것으로 혼동하지 않는 것이 좋습니다.

## 프롬프트 순서는 성능 설계다

많은 제공자의 prefix caching은 입력 앞부분이 동일할 때 효과를 기대할 수 있습니다. 따라서 prompt를 무작위로 문자열 이어 붙이듯 만들면 작은 timestamp나 사용자 이름 변화 때문에 공통 prefix가 깨질 수 있습니다. 안정된 순서를 정합니다. 예를 들어 모델 역할과 안전 규칙, 출력 schema, 제품 공통 지식, tenant별 정책, 검색 문서, 사용자 질문 순서를 고정할 수 있습니다. 실제 제공자의 캐시 조건은 모델과 API별로 다르므로 문서를 확인해야 합니다.

하지만 성능 때문에 중요한 현재 정보를 뒤로 미루는 것은 위험합니다. 사용자 권한이나 요청의 정책 경계가 prompt 앞에 있어야 모델이 일관되게 준수한다면, 캐시 hit보다 정확성을 우선합니다. 더 나은 방법은 권한을 prompt에만 맡기지 않고 retrieval filter와 tool server authorization에서 강제하는 것입니다. prompt 순서는 모델 행동을 안내하지만 보안 경계의 유일한 구현이 되어서는 안 됩니다.

동일한 prefix를 만들기 위해 공백과 key 순서, 날짜 표현, 문서 정렬을 안정적으로 만드는 것도 도움이 됩니다. 그러나 사람이 읽기 어려운 문자열 최적화를 먼저 하지 않습니다. prompt template을 versioned source로 관리하고, 어떤 필드가 안정적이며 어떤 필드가 요청별로 바뀌는지 주석과 테스트로 보여 주는 편이 유지보수에 좋습니다. 캐시 hit 수치가 낮을 때도 먼저 의도한 구조가 지켜지는지 확인합니다.

## 구체적 업무 예시: 사내 운영 도우미

운영 도우미가 장애 안내와 runbook 검색을 돕는다고 가정해 보겠습니다. 매 요청에는 공통 역할 지시문, 답변 형식, 서비스 용어집, 안전 규칙, 도구 schema, 사용자 질문, 검색된 runbook 문단이 들어갑니다. 역할 지시문과 형식, 용어집, schema는 자주 바뀌지 않으므로 안정된 prefix 후보입니다. 반면 현재 장애 번호, 사용자 권한, 검색 결과, 도구 호출 결과는 요청별 문맥으로 둡니다.

팀은 prompt template에 `policy_version`, `glossary_version`, `tool_schema_version`을 명시합니다. 정책을 바꾸면 version이 달라져 이전 prefix를 재사용하지 않게 하고, 변경 이력도 추적할 수 있습니다. runbook 문단에는 문서 ID와 수정 시각을 붙이며, 검색 cache는 query와 권한 범위, 문서 index version을 포함해 관리합니다. 이렇게 하면 답변이 이상할 때 모델 탓만 하지 않고 어떤 문맥 버전이 사용됐는지 조사할 수 있습니다.

같은 장애 질문이 여러 번 와도 응답 전체를 무조건 cache하지 않습니다. 현재 상태와 권한에 따라 안내가 달라질 수 있고, 도구 조회 결과는 시간이 지나면 바뀝니다. 대신 안전한 읽기 전용 문서 요약이나 변하지 않는 설명은 재사용하고, 실시간 상태는 다시 조회합니다. 캐싱의 목표는 대답을 영구히 고정하는 것이 아니라 중복 계산을 줄이면서 최신성과 안전을 유지하는 것입니다.

## 비용과 지연은 따로 관찰한다

입력 token 비용이 줄어도 사용자가 느끼는 전체 지연이 같은 비율로 줄어들지는 않습니다. 모델의 첫 token 생성, 네트워크 왕복, queue 대기, tool 호출, 검색, output token 생성 시간이 함께 있기 때문입니다. 프롬프트 캐싱을 평가할 때는 cache hit·miss, 입력 token 수, cache 관련 비용, TTFT(Time To First Token, 첫 token까지의 시간), 전체 응답 시간, tool 호출 시간, 오류율을 분리해 봅니다.

cache hit가 높아도 output이 길거나 외부 도구가 느리면 전체 사용자 경험은 개선되지 않을 수 있습니다. 반대로 hit가 낮아도 긴 공통 문서를 제거하거나 요약 품질을 개선해 입력 자체를 줄이는 편이 더 효과적일 수 있습니다. 숫자를 보기 전에 어떤 병목을 줄이고 싶은지 정합니다. 비용 절감인지, 대화의 첫 응답 속도인지, rate limit 여유인지에 따라 성공 지표가 달라집니다.

평가는 동일한 대표 요청 집합으로 합니다. 짧은 질문과 긴 질문, 한국어와 영어, 검색 결과가 많은 질문, tool 호출이 필요한 질문, 권한 없는 문서를 요청하는 질문, cache miss가 의도된 신규 정책 버전을 함께 넣습니다. 평균값 하나 대신 높은 지연 구간과 오류 사례를 보고, 실험 날짜·모델·prompt version·트래픽 조건을 기록합니다. 제공자 응답의 cache 관련 사용량 필드가 있다면 관찰하되, 그것만으로 답변 정확성을 판단하지 않습니다.

## 무효화는 문서와 정책의 생명주기다

캐시 설계에서 가장 어려운 질문은 언제 버릴 것인가입니다. 운영 규칙, 가격, 권한, 제품 정책, 문서가 바뀌면 과거 prefix나 검색 결과가 더 이상 적절하지 않을 수 있습니다. 단순 TTL(Time To Live, 보존 시간)만으로는 긴급 정책 변경을 즉시 반영하기 어렵고, 모든 항목을 즉시 삭제하면 캐시 이점이 사라질 수 있습니다. 그래서 version을 key에 넣는 방식이 유용합니다.

정책 template을 바꾸면 `policy_version`을 올리고, tool schema가 바뀌면 `tool_schema_version`을 올리며, 문서 index를 재생성하면 `index_version`을 바꿉니다. 새 요청은 새 version을 쓰고, 이전 version의 cache는 자연스럽게 사용되지 않게 할 수 있습니다. version 수가 너무 많아지면 관찰과 비용이 복잡해지므로, 무엇이 답변 의미를 바꾸는 변경인지 기준을 정해야 합니다. 오타 수정처럼 의미가 없는 변경까지 매번 전체 cache를 갈아엎을 필요는 없습니다.

긴급 중단 경로도 필요합니다. 잘못된 정책 문구나 민감한 문서가 prompt에 포함된 사실을 발견했다면 다음 배포까지 기다리지 않고 해당 feature를 끄거나 참조 문서를 제외할 수 있어야 합니다. 캐시 삭제 기능이 있더라도 이미 생성된 응답과 downstream log, 사용자 화면에 남은 정보는 별도로 조사해야 합니다. 무효화는 cache 서버의 명령 하나가 아니라 데이터 처리 사고 대응의 일부입니다.

## 개인정보와 tenant 격리를 기본값으로 두기

프롬프트에 넣은 내용은 모델 제공자, 애플리케이션 로그, trace, cache 계층 등 여러 곳에 남을 가능성이 있습니다. 사용자의 이름, 이메일, 고객 계약, 비밀값, access token을 “모델이 더 잘 답하도록” 무심코 넣지 않습니다. 필요 최소한의 식별자와 마스킹된 값만 사용하고, 실제 답변에 필요하지 않은 개인 프로필은 제거합니다. 데이터 처리 위치와 보존 조건은 사용하는 제공자와 계약, 조직 정책을 확인해야 합니다.

multi-tenant 서비스에서는 tenant ID를 단순 prompt 문장으로만 넣어서는 안 됩니다. 검색 단계에서 tenant filter를 강제하고, tool API에서도 인증된 tenant와 resource의 관계를 확인하며, cache key와 cache namespace도 tenant 경계를 반영해야 합니다. 캐시 hit가 좋아 보인다는 이유로 다른 tenant의 공통 문서를 섞어 쓰면, 작은 설정 실수가 정보 노출로 이어질 수 있습니다.

사용자별 응답 cache를 만들 때에는 권한 변경도 고려합니다. 어제 접근할 수 있던 문서를 오늘은 볼 수 없을 수 있고, 계정이 비활성화됐을 수 있습니다. 응답을 재사용하기 전에도 현재 authorization을 확인하고, 고위험 정보는 응답 cache 자체를 사용하지 않는 것이 안전할 수 있습니다. 캐시는 접근 제어의 결과를 저장하는 편의 기능이지 접근 제어를 대체하는 기능이 아닙니다.

## 오류와 fallback을 설계하기

cache 계층이 느리거나 사용할 수 없을 때 모델 요청 전체가 실패할 필요는 없습니다. cache miss는 정상 경로로 모델을 호출하는 이유일 수 있고, cache 읽기 오류는 안전하게 miss로 처리할 수 있습니다. 다만 장애를 숨기기 위해 무제한 재시도하거나, 오래된 prefix를 몰래 사용해서는 안 됩니다. 사용한 version과 hit·miss·오류 상태를 trace에 남기고, 성능 저하와 정확성 위험을 구분해 대응합니다.

제공자별 캐시 기능은 조건과 보존 시간이 다를 수 있으므로 특정 구현에 강하게 묶지 않습니다. 애플리케이션은 같은 prompt를 만들 수 있는 template과 version, 사용량을 측정하는 interface를 관리하고, 제공자 응답의 세부 표시는 관찰값으로 취급합니다. 모델을 바꾸거나 제공자 기능이 달라질 때 cache hit만 비교하지 말고 출력 형식, 안전 규칙 준수, 비용, latency를 함께 평가합니다.

fallback에서 중요한 것은 결과의 의미를 바꾸지 않는 것입니다. cached summary가 없다고 원문 문서를 무시하거나, 권한 검증이 실패했는데 이전 응답을 보여 주면 안 됩니다. 성능 기능이 꺼져도 기본 정확성·보안·감사 경로가 살아 있어야 합니다. 이를 위해 cache on과 off 모두에서 같은 대표 평가를 실행하고, cache가 없는 환경에서도 서비스가 동작하는지 확인합니다.

## 한계와 적용 기준 Q&A

### Q. 프롬프트 전체 응답을 cache하는 것과 prefix cache는 같은가요?

A. 다릅니다. prefix cache는 반복 입력의 계산을 재사용해 모델 호출을 계속 수행하는 경우가 많고, 응답 cache는 같은 요청의 결과 텍스트를 재사용합니다. 응답 cache는 빠를 수 있지만 최신 데이터, sampling, 사용자 권한, 도구 결과가 달라지는 질문에는 부적절할 수 있습니다. 무엇을 저장하는지와 정확성 조건을 분리해 설계해야 합니다.

### Q. cache hit가 낮으면 prompt 순서만 바꾸면 되나요?

A. 먼저 낮은 hit가 실제 비용이나 지연 문제인지 확인해야 합니다. 각 요청의 문맥이 본질적으로 다르다면 낮은 hit는 정상일 수 있습니다. 성능 때문에 권한 정보나 최신 데이터를 부자연스럽게 뒤로 보내지 말고, 안정된 공통 지시문을 분리하거나 입력을 줄이는 방법을 검토합니다.

### Q. 캐시가 있으면 RAG 검색을 줄여도 되나요?

A. 변경되는 문서와 사용자별 권한이 있는 경우에는 위험합니다. 고정된 제품 설명은 재사용할 수 있어도, 최신 runbook·공지·주문 상태처럼 근거가 바뀌는 정보는 검색과 filter를 다시 해야 합니다. cache는 retrieval의 정확성 검증을 생략하는 이유가 아닙니다.

## 도입 순서와 점검표

먼저 현재 prompt를 안정된 공통 부분, version이 있는 정책, 요청별 사용자 문맥, 실시간 도구 결과로 나눕니다. 입력 token과 지연이 큰 요청 하나를 골라 공통 prefix를 일정한 순서로 만들고, cache on/off의 비용·첫 token 지연·정확성 평가를 비교합니다. 처음부터 모든 대화와 모든 문서를 cache하지 않습니다.

다음으로 key와 version, 보존 시간, tenant 격리, 권한 변경, 긴급 무효화 경로를 문서화합니다. 로그에는 prompt 원문이나 secret 대신 version, token 수, hit·miss, request ID 같은 안전한 메타데이터를 남깁니다. 정책 또는 문서가 바뀌었을 때 어떤 version을 올리고 어떤 평가를 다시 실행하는지 release 절차에 넣습니다.

프롬프트 캐싱의 성공은 hit 비율이 높다는 사실만으로 판단할 수 없습니다. 사용자가 더 빨리 정확한 근거를 받고, 조직이 비용과 데이터 경계를 설명할 수 있으며, cache가 꺼져도 안전한 기본 경로가 유지될 때 가치가 있습니다. 이 기준을 지키면 캐싱은 단순한 비용 옵션이 아니라 LLM 시스템의 문맥을 더 명확하게 관리하는 계기가 됩니다.

## 캐시 키를 설계하는 구체적인 질문

캐시 키에는 같은 의미의 입력을 같은 것으로 묶는 정보만 넣어야 합니다. 모델 이름이나 모델 snapshot, system prompt version, 출력 형식 version, tool schema version, 언어 정책처럼 모델의 해석을 바꾸는 값은 키 또는 namespace에 반영합니다. 반면 request ID나 현재 시각처럼 답변 의미와 무관한 값을 공통 prefix 앞에 넣으면 hit를 불필요하게 깨뜨립니다. 어떤 필드가 안정적인지 목록으로 관리해야 합니다.

문서 기반 서비스에서는 문서 자체의 version이 핵심입니다. 같은 제목의 runbook이라도 내용이 수정됐으면 이전 요약이나 prefix를 재사용하면 안 될 수 있습니다. 문서 collection 전체에 index version을 부여하고, 개별 문서에는 content hash나 revision을 둘 수 있습니다. 다만 모든 문서 변경이 모든 답변을 바꾸는 것은 아니므로, 서비스 구조에 따라 collection version과 문서 단위 version 중 어떤 범위를 key로 쓸지 선택합니다.

지역과 언어도 결과를 바꿀 수 있습니다. 한국어 사용자에게 한국 법령의 최신 버전을 안내하는 서비스와 영어 제품 문서를 요약하는 서비스는 같은 system prompt라도 필요한 안전 문구와 citation 형식이 다를 수 있습니다. locale을 key에 반영하거나, 공통 prefix와 locale별 지시문을 명확히 나눕니다. 단순 번역 문자열만 바꾸는 경우와 업무 규칙이 바뀌는 경우를 구분하면 cache 범위를 과도하게 쪼개지 않을 수 있습니다.

사용자 질문의 정규화도 신중하게 합니다. 공백이나 대소문자 차이를 제거해 동일 질문 cache를 높일 수 있지만, 숫자·부정 표현·날짜·단위가 달라지면 의미가 달라질 수 있습니다. “환불 가능”과 “환불 불가능”을 비슷한 문장으로 취급하거나, 주문 번호를 제거해 다른 주문의 결과를 재사용하는 것은 위험합니다. 고위험 업무에서는 질문 문자열을 억지로 정규화하기보다 prefix cache와 안전한 검색 cache를 분리하는 편이 낫습니다.

## 출력 캐시를 쓸 수 있는 경우와 피해야 할 경우

출력 cache는 동일한 입력에 대해 이전 답변 텍스트를 바로 돌려주므로 매우 빠를 수 있습니다. 자주 묻는 공개 제품 설명, version이 고정된 사용법, 변하지 않는 교육 자료처럼 현재 상태·권한·개인화와 무관한 질문에는 검토할 수 있습니다. 이 경우에도 답변에 사용한 문서 version과 생성 시각을 표시하면, 운영자가 오래된 결과를 발견했을 때 무효화 범위를 찾기 쉽습니다.

반면 주문 상태, 계정 권한, 결제 금액, 장애 현황, 고객별 계약, 최신 정책처럼 사실이 바뀌거나 개인마다 다른 질문은 출력 cache의 위험이 큽니다. 모델 입력의 공통 prefix를 재사용하더라도 최종 답은 현재 조회 결과를 바탕으로 새로 만들어야 할 수 있습니다. 빠른 응답이 정확하지 않은 안내보다 가치 있다고 가정하면 사용자 신뢰를 잃기 쉽습니다.

응답을 cache하더라도 부정확한 답을 반복 배포하지 않도록 피드백과 수정 경로가 필요합니다. 사용자가 답변의 근거가 오래됐다고 신고하면 어떤 cache key와 문서 version이 사용됐는지 추적하고, 해당 범위의 cache를 사용 중지하거나 version을 올릴 수 있어야 합니다. cache hit가 높은데 같은 오류가 반복된다면 모델 성능 문제가 아니라 잘못된 근거가 효율적으로 재사용되는 문제일 수 있습니다.

## 프롬프트 템플릿을 코드처럼 검증하기

프롬프트 template은 문자열이지만 시스템의 정책과 기능 계약을 담고 있습니다. source code와 같이 version control에 두고, 변경 전후 diff를 리뷰하며, 대표 입력에 대해 어떤 최종 prompt 구조가 만들어지는지 test합니다. 이 test에는 실제 고객 문서나 secret을 넣지 않고, 가짜 tenant·문서·도구 결과를 사용합니다. 목적은 모델의 창의성을 평가하는 것이 아니라 순서와 필수 policy block이 사라지지 않았는지 확인하는 것입니다.

template test는 cache 관점에서도 유용합니다. 공통 prefix가 매 요청에서 같은 위치와 형식으로 만들어지는지, 사용자별 필드가 공통 block 앞에 끼어들지 않는지, version 값이 변경 때만 달라지는지 검증할 수 있습니다. 작은 리팩터링으로 JSON key 순서가 바뀌거나 불필요한 timestamp가 들어가면 성능 지표가 갑자기 나빠질 수 있습니다. 사람이 결과 답변만 보고 원인을 찾기는 어렵기 때문에 구조 검사가 필요합니다.

도구 호출 schema를 바꾸면 prompt와 cache를 동시에 봅니다. 새 tool parameter를 추가했는데 이전 schema version의 prefix를 재사용하면 모델이 존재하지 않는 필드를 보내거나 필요한 안전 규칙을 누락할 수 있습니다. schema version을 명확하게 올리고, 정상 호출·잘못된 인자·권한 거절·도구 timeout에서 cache on/off 결과가 같은 안전 경계를 지키는지 검사합니다.

## 실무 평가 세트를 만드는 방법

캐싱 변경을 평가할 때 단순히 긴 prompt 한 개를 반복 호출하지 않습니다. 실제 서비스의 요청 분포를 대표하는 질문을 만듭니다. 공통 정책과 문서를 많이 공유하는 질문, tenant별 문서가 달라 cache를 분리해야 하는 질문, 매번 도구 결과가 달라지는 질문, 최신 문서가 필요한 질문, 권한 없는 정보를 요구하는 질문을 포함합니다. 각 질문에 기대 근거와 금지된 근거를 기록하면 속도와 정확성을 함께 평가할 수 있습니다.

평가 결과에는 정확성뿐 아니라 cache 행동을 기록합니다. 어떤 version이 사용됐는지, 예상한 hit 또는 miss가 발생했는지, 입력 token과 출력 token이 얼마나 되는지, 첫 token과 전체 응답 시간은 어떤지, fallback이 발생했는지 남깁니다. cache가 잘 작동한다는 것은 모든 요청이 hit가 된다는 뜻이 아니라, 공통 문맥은 재사용하고 요청별·권한별 문맥은 분리된다는 뜻입니다.

평가는 release 전에만 하지 않습니다. 문서 corpus가 커지거나 system prompt가 길어지고, 새로운 모델이나 제공자로 바꾸고, tool이 늘어나면 cache 조건도 달라질 수 있습니다. 일정한 대표 세트를 versioned fixture로 유지하고, 큰 template 변경 후에 비교합니다. 단, benchmark 결과가 좋아도 실제 사용자 query의 언어와 약어, 오타, 업무 흐름을 대표하지 못할 수 있으므로 feedback과 운영 지표를 함께 봅니다.

## 비용 한도와 공정 사용을 설계하기

캐시는 비용을 낮출 수 있지만, 캐시가 있다는 이유로 무제한으로 긴 prompt를 보내면 안 됩니다. 공통 문서를 매번 모두 넣는 설계는 문서가 늘수록 context window와 품질을 압박합니다. 불필요한 과거 대화, 사용하지 않는 tool schema, 중복된 정책 문구를 제거하고, 검색과 요약으로 필요한 근거만 선택하는 것이 먼저입니다. cache는 좋은 입력 설계를 보완하는 기능입니다.

사용자나 tenant별 비용 한도도 필요할 수 있습니다. 한 사용자가 매우 긴 파일을 반복 업로드하거나 자동화가 같은 질문을 대량 요청하면 cache hit가 있어도 output 비용과 tool 비용이 커질 수 있습니다. 요청 크기 제한, concurrency limit, 일별 예산, 경고 기준을 두고, 한 tenant의 실수가 다른 tenant의 서비스 품질을 해치지 않게 합니다. 비용 차단은 단순히 요청을 거절하는 기능이 아니라 사용자가 원인을 이해할 수 있는 오류 안내와 함께 설계합니다.

캐시 성능을 높이려고 여러 tenant의 데이터를 넓게 공유하는 선택은 비용보다 더 큰 보안 비용을 만들 수 있습니다. 공통 공개 문서와 tenant 전용 문서를 논리적으로 분리하고, cache namespace와 로그 접근 권한도 같은 경계를 따릅니다. 저장 비용이 조금 늘더라도 데이터 격리가 명확한 구조가 사고 조사와 규제 대응에는 더 유리할 수 있습니다.

## 장애 대응에서 확인할 순서

응답 지연이 늘었을 때 첫 질문은 “cache hit가 떨어졌는가”가 아니라 어느 단계가 느린가입니다. 입력 구성, cache 조회, 모델 queue, 모델 입력 처리, 첫 token 생성, 검색, 도구 호출, 출력 전송을 분리해 관찰합니다. hit가 줄었다면 최근 template version, 문서 index version, 요청별 필드 위치, 제공자 상태를 확인합니다. hit는 정상인데 느리다면 tool 또는 모델 출력이 원인일 수 있습니다.

정확성 incident에서는 cache를 성급하게 전부 비우기보다 영향을 받는 정책·문서·tenant 범위를 확인합니다. 잘못된 version이 특정 namespace에서만 사용됐는지, 이전 응답이 외부에 노출됐는지, 현재 요청에도 같은 근거가 들어가는지 조사합니다. 필요한 경우 해당 기능을 제한하거나 안전한 fallback으로 전환하고, 사용자에게 사실과 다음 조치를 안내합니다. cache purge는 조사와 커뮤니케이션을 대신하지 않습니다.

운영자는 cache 관련 metric만 보지 않고 사용자 피드백, citation 오류, 권한 거절률, tool 실패율을 같이 봅니다. 속도 그래프가 좋아도 사용자가 근거 없는 답을 받거나 다른 문서를 보게 된다면 시스템 품질은 나빠진 것입니다. 프롬프트 캐싱은 LLM 운영의 한 계층이며, 검색·도구·권한·관찰성의 책임을 가져가지는 않습니다.

## 팀의 운영 계약으로 남기기

마지막으로 cache 정책은 개발자 몇 명의 암묵적 지식으로 두지 않습니다. 어떤 prompt block이 공유 가능한지, 어떤 데이터는 절대 cache하지 않는지, version을 올리는 변경은 무엇인지, hit와 비용을 어느 dashboard에서 보는지, 긴급 무효화 권한은 누구에게 있는지 문서화합니다. 새 모델이나 provider를 추가할 때 이 질문을 설계 검토에 넣으면 비용 기능 때문에 보안과 정확성을 나중에 고치는 일을 줄일 수 있습니다.

작은 도입은 공통 system prompt 하나와 안전한 공개 문서 하나에서 시작할 수 있습니다. cache on/off 평가와 version 로그, tenant 격리 검사를 붙이고, 실제로 비용이나 첫 응답 시간이 개선되는지 확인합니다. 효과가 불명확하면 기능을 넓히지 않습니다. 반대로 효과가 확인되면 문서 version과 권한 경계가 명확한 영역부터 확장합니다.

좋은 프롬프트 캐싱은 모델 호출을 덜 하는 기법이면서 동시에 문맥의 소유자와 변경 시점을 명확하게 만드는 설계입니다. 무엇이 공통이고 무엇이 요청별이며, 무엇이 최신이어야 하고 무엇이 공유될 수 없는지를 구분할수록 성능·비용·안전의 균형을 설명할 수 있습니다.

## 최종 적용 기준

프롬프트 캐싱은 긴 공통 지시문이나 고정된 형식이 반복되고, 입력 비용 또는 첫 응답 지연이 실제 문제이며, 정책·문서·권한의 version을 관리할 수 있을 때 적합합니다. 요청마다 완전히 다른 문서를 읽거나 실시간 도구 결과가 대부분인 서비스에서는 hit가 낮아도 이상하지 않습니다. 이때는 캐시를 억지로 늘리기보다 검색 품질, 문서 크기, 도구 지연, 출력 길이를 먼저 개선하는 편이 낫습니다.

도입 전에는 현재 처리 조건을 확인합니다. 제공자가 cache를 어떤 범위에서 보존하는지, 어떤 요청 형식이 hit 조건인지, 사용량을 어떻게 반환하는지, 데이터 처리 약관과 조직 정책이 맞는지 검토합니다. 응답이 빨라진다는 기대만으로 사용자 문서나 비밀값을 공통 prefix에 넣어서는 안 됩니다. 성능 실험은 안전한 fixture와 대표 질의로 시작해야 합니다.

운영 중에는 cache hit·miss, 입력 비용, 첫 token 지연, 전체 지연, 오류율, citation 정확도와 권한 문제를 함께 봅니다. 정책이나 tool schema가 바뀌면 version을 올리고 평가를 다시 실행합니다. cache가 비활성화돼도 정확한 기본 호출 경로와 접근 제어가 유지된다면, 이 기능은 비용 최적화를 넘어 LLM 서비스의 문맥 구조를 건강하게 만드는 도구가 됩니다.

### 변경 전 마지막 점검

배포 전에는 공통 prefix에 실제 고객 정보나 비밀값이 없는지, tenant와 권한 filter가 cache 밖에서도 강제되는지, 정책·문서·도구 schema의 version이 key에 반영되는지 확인합니다. 또한 cache hit가 없거나 제공자 기능이 일시적으로 실패해도 응답이 같은 안전 규칙을 지키는지 대표 시나리오로 검증합니다. 빠른 응답을 만드는 최적화가 정확성과 접근 제어를 약화시키지 않는다는 증거가 있어야 합니다.

운영 문서에는 어떤 cache가 성능용이고 어떤 데이터는 절대 공유하지 않는지, version을 올리는 조건과 긴급 중지 경로를 함께 남깁니다. 이 정보가 있어야 비용 최적화 변경도 보안·품질 검토 안에서 관리할 수 있습니다.

작은 측정부터 시작해 효과와 위험을 함께 확인하는 것이 가장 안전합니다.
