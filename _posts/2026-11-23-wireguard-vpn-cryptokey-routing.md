## 먼저 답하기

### Q. WireGuard는 무엇인가요?

A. WireGuard(와이어가드)는 두 대 이상의 장비 사이에 암호화된 사설 네트워크 통로를 만들어 주는 VPN(Virtual Private Network, 가상 사설망) 프로토콜이자 구현입니다. 리눅스 커널에는 5.6 버전부터 들어가 있고, 윈도우·macOS·안드로이드·iOS용 구현도 있습니다. 설정은 "내 개인키, 상대방 공개키, 상대에게 보낼 주소 범위"가 핵심입니다. 설정 파일이 수십 줄이 아니라 보통 열 줄 안팎이고, 코드 규모도 기존 VPN 소프트웨어보다 훨씬 작게 설계되었습니다. 이 글은 공식 문서와 논문을 바탕으로 개념과 설정 방법을 정리한 학습 자료이며, 제가 직접 서버를 운영하며 성능을 측정한 결과가 아닙니다.

### Q. 기존 VPN과 무엇이 다른가요?

A. 가장 큰 차이는 "단순함을 설계 목표로 삼았다"는 점입니다. IPsec(Internet Protocol Security)이나 OpenVPN은 암호 알고리즘을 협상하는 단계가 있고 설정 항목도 많습니다. WireGuard는 암호 알고리즘 조합을 하나로 고정하고, 알고리즘이 위험해지면 프로토콜 버전을 올려 대체하는 방식을 택했습니다. 협상할 것이 없으니 설정과 코드가 줄고, 점검해야 할 표면도 줄어듭니다. 또 "피어(peer, 통신 상대)의 신원은 공개키"라는 SSH 비슷한 모델이어서 인증서 발급 체계(PKI, Public Key Infrastructure) 없이도 시작할 수 있습니다.

### Q. 그럼 항상 WireGuard를 쓰면 되나요?

A. 아닙니다. WireGuard는 사용자 계정·그룹별 접근 정책, 중앙 인증 연동, 동적 주소 배정 같은 기능을 프로토콜 자체에 담지 않았습니다. 이런 기능이 필요하면 별도 관리 도구나 상위 제품을 얹어야 합니다. 또 UDP(User Datagram Protocol)만 사용하므로 UDP를 막는 네트워크에서는 별도 우회가 필요합니다. 아래 "한계와 적용 기준 Q&A"에서 선택 기준을 정리합니다.

## 먼저 알아둘 기반 기술

이 절은 본문을 읽는 데 필요한 네트워크·암호 지식을 가장 밑바닥(IP 주소와 라우팅)부터 WireGuard 직전(Noise 핸드셰이크)까지 순서대로 쌓습니다. 각 소절 끝에는 그 개념이 본문의 어느 절에서 다시 쓰이는지 적어 두었고, 절 마지막에 전체 연결 지도를 표로 정리했습니다.

### IP 주소, CIDR, 라우팅 테이블

IP 주소(Internet Protocol address)는 네트워크에서 장비를 찾아가는 주소입니다. 여러 주소를 한 덩어리로 표현할 때는 CIDR(Classless Inter-Domain Routing, 클래스 없는 도메인 간 라우팅) 표기를 씁니다. `10.8.0.0/24`에서 `/24`는 "앞 24비트가 같은 주소 전부"라는 뜻이어서 `10.8.0.0`부터 `10.8.0.255`까지 256개 주소를 가리킵니다. `/32`는 주소 딱 하나, `/0`은 모든 주소입니다. 운영체제는 패킷을 보낼 때 라우팅 테이블(routing table)을 보고 "이 목적지는 어느 인터페이스, 어느 다음 장비로 보낼지"를 정합니다. 여러 규칙이 겹치면 범위가 가장 좁은(접두사가 가장 긴) 규칙이 이깁니다. 이를 최장 접두사 일치(longest prefix match)라 합니다. 리눅스에서는 다음처럼 확인합니다.

```bash
ip route
# default via 192.168.0.1 dev eth0          <- 나머지 모든 목적지(0.0.0.0/0)
# 10.8.0.0/24 dev wg0 scope link            <- 터널 대역은 wg0로
ip route get 10.8.0.1                       # 특정 목적지가 어느 경로를 타는지 확인
```

우편 분류함에 비유하면 CIDR은 "서울시 강남구 전체" 같은 지역 묶음이고, 라우팅 테이블은 "강남구 우편물은 3번 트럭에"라고 적힌 분류표입니다. WireGuard의 `AllowedIPs`는 바로 이 CIDR 목록이며 송신 시 라우팅 테이블처럼 동작하므로, CIDR과 최장 접두사 일치를 모르면 설정 한 줄이 어떤 트래픽을 터널로 보내는지 읽을 수 없습니다. 이 개념은 아래 「암호키 라우팅(cryptokey routing)」 절에서 피어 선택 규칙으로, 「3단계: 노트북 설정 파일」에서 분할·전체 터널링의 차이로, 「주소 설계」와 「구조와 AllowedIPs 설계」 절에서 대역이 겹치지 않게 나누는 기준으로 쓰입니다.

### UDP와 TCP, 포트

TCP(Transmission Control Protocol)와 UDP(User Datagram Protocol)는 IP 위에서 데이터를 실어 나르는 두 가지 대표 방식입니다. TCP는 연결을 먼저 맺고(3-way handshake), 빠진 데이터를 재전송하고, 순서를 맞춰 주는 등기 우편 같은 방식입니다. UDP는 연결 과정 없이 데이터그램(datagram, 독립된 패킷 하나)을 그냥 보내는 일반 우편 같은 방식으로, 가볍지만 도착 보장은 하지 않습니다. 포트(port)는 한 장비 안에서 어느 프로그램에게 전달할지 구분하는 번호로, WireGuard는 관례적으로 UDP 51820을 씁니다. 서버가 듣고 있는지는 `ss -ulpn`으로 확인합니다.

WireGuard는 UDP만 사용합니다. 재전송과 순서 보장은 터널 안쪽의 TCP(예: SSH, HTTP)가 이미 해 주므로 바깥에서 또 할 필요가 없기 때문입니다. 반대로 TCP 위에 TCP를 다시 얹으면 두 계층이 동시에 재전송을 시도해 지연이 크게 늘 수 있습니다(TCP-over-TCP 문제). 또 UDP에는 연결 수립 응답이 없으므로, 서버가 잘못된 패킷에 답하지 않으면 바깥에서는 포트가 열렸는지조차 알기 어렵습니다. 이 개념은 아래 「핸드셰이크와 세션 키」 절에서 포트 스캔에 응답하지 않는 "조용함"으로, 「2단계: 서버 설정 파일」의 `ListenPort`로, 「네트워크 문제 점검 절차」와 「핸드셰이크가 없을 때」 절에서 UDP 포트 차단을 의심하는 근거로 쓰입니다.

### NAT와 연결 유지(keepalive)

NAT(Network Address Translation, 네트워크 주소 변환)는 사설 주소를 쓰는 여러 장비가 공인 주소 하나를 함께 쓰도록 주소를 바꿔 주는 기능입니다. 집 공유기가 대표적입니다. 노트북(`192.168.0.10`)이 밖으로 패킷을 보내면 공유기는 출발지를 자기 공인 주소와 임의의 포트(예: `198.51.100.24:49822`)로 바꾸고, 이 대응 관계를 매핑 표에 잠깐 기억해 두었다가 답장이 오면 다시 노트북으로 돌려줍니다. 아파트 경비실이 "502호 택배"라는 메모를 붙여 두었다가 답장을 전달해 주는 것과 비슷합니다. 문제는 UDP에는 "연결 종료" 신호가 없어서 NAT 장비가 일정 시간 조용하면 매핑을 지워 버린다는 점입니다. 그러면 바깥에서 먼저 보내는 패킷은 더 이상 들어오지 못합니다. 이를 막으려고 주기적으로 작은 패킷을 보내 매핑을 살려 두는 것을 keepalive(연결 유지)라 합니다.

NAT는 이 글에서 두 가지 모습으로 등장합니다. 하나는 클라이언트가 공유기 뒤에 있어서 생기는 매핑 만료 문제이고, 다른 하나는 게이트웨이가 일부러 출발지 주소를 바꿔 주는 마스커레이드(MASQUERADE) 설정입니다. NAT를 모르면 왜 `PersistentKeepalive`가 필요한지, 왜 서버 로그에 모든 접속이 게이트웨이 주소로 찍히는지 이해할 수 없습니다. 이 개념은 아래 「PersistentKeepalive」와 「로밍과 Endpoint」 절에서 매핑 유지와 출발지 주소 갱신으로, 「게이트웨이 설정」 절의 `MASQUERADE`로, 「겹치는 대역 문제」 절에서 겹치는 대역을 변환으로 우회하는 방법으로 쓰입니다.

### 방화벽과 IP 포워딩

방화벽(firewall)은 정해진 규칙에 따라 패킷을 통과시키거나 버리는 장치 또는 기능입니다. 리눅스에서는 커널의 netfilter를 `iptables`나 그 후속인 `nftables`로 설정합니다. 규칙은 "어느 인터페이스로 들어와, 어느 주소에서 어느 주소로, 어떤 프로토콜·포트인가"를 보고 `ACCEPT`(허용) 또는 `DROP`(버림)을 정합니다. 클라우드에서는 보안 그룹(security group)이 같은 역할을 합니다. IP 포워딩(IP forwarding)은 한 장비가 자기에게 온 것이 아닌 패킷을 다른 인터페이스로 넘겨주는 기능, 즉 장비를 라우터처럼 동작하게 하는 스위치입니다. 리눅스는 기본으로 꺼져 있으며 다음처럼 확인하고 켭니다.

```bash
sysctl net.ipv4.ip_forward          # 0이면 꺼짐, 1이면 켜짐
sudo sysctl -w net.ipv4.ip_forward=1
```

건물에 비유하면 방화벽은 출입문의 보안 요원, IP 포워딩은 "다른 층으로 가는 사람도 통과시켜 주는" 연결 통로입니다. VPN 게이트웨이는 터널(`wg0`)로 들어온 패킷을 사내망 인터페이스로 넘겨야 하므로 포워딩이 필수이고, 누가 어느 서버에 갈 수 있는지는 방화벽이 정합니다. 이 둘을 모르면 "핸드셰이크는 되는데 사내 서버에 안 닿는" 상황을 진단할 수 없습니다. 이 개념은 아래 「게이트웨이 설정」 절의 `PostUp` 명령으로, 「접근 범위 좁히기」 절에서 피어별 방화벽 규칙으로, 「네트워크 문제 점검 절차」와 「핸드셰이크는 되는데 통신이 안 될 때」 절에서 포워딩·방화벽 점검 단계로 쓰입니다.

### VPN과 터널

VPN은 공용 인터넷 위에서 마치 사설 회선처럼 통신하도록 만드는 기술입니다. 핵심 동작은 터널링(tunneling)입니다. 원래 보내려던 패킷(안쪽 패킷)을 통째로 암호화한 뒤, 다른 패킷(바깥 패킷)의 내용물로 담아 보내고, 받는 쪽이 바깥 껍질을 벗겨 안쪽 패킷을 꺼냅니다. 편지를 봉투에 넣고, 그 봉투를 다시 금고 상자에 넣어 택배로 보내는 것과 비슷합니다. 택배 기사(공용 인터넷의 라우터들)는 상자의 겉면 주소만 보고 내용물은 볼 수 없습니다.

WireGuard에서는 안쪽 패킷이 `10.8.0.2 → 10.20.0.10` 같은 사설 주소를, 바깥 패킷이 `198.51.100.24:49822 → 203.0.113.10:51820` 같은 공인 주소와 UDP 포트를 가집니다. 앞에서 본 라우팅·UDP·NAT는 바깥 패킷에, 방화벽 규칙과 `AllowedIPs`는 주로 안쪽 패킷에 적용된다는 구분이 중요합니다. 이 구분이 없으면 "어느 주소를 어디에 적어야 하는지"가 계속 헷갈립니다. 이 개념은 아래 「WireGuard 동작 원리」 절 전체의 바탕이 되며, 특히 「암호키 라우팅(cryptokey routing)」 절에서 안쪽 패킷의 목적지·출발지 주소를 검사하는 동작으로 쓰입니다.

### MTU와 조각화

MTU(Maximum Transmission Unit, 최대 전송 단위)는 한 번에 보낼 수 있는 패킷의 최대 크기입니다. 일반 이더넷은 1500바이트가 흔합니다. 이보다 큰 패킷은 조각으로 나누는 조각화(fragmentation)를 하거나, "나누지 말라(DF, Don't Fragment)" 표시가 있으면 버려집니다. 터널은 안쪽 패킷에 바깥 IP·UDP·WireGuard 헤더를 덧붙이므로, 같은 1500바이트 회선을 지나려면 안쪽 패킷은 그만큼 작아야 합니다. 바깥 헤더가 IPv6 기준 약 80바이트라고 하면 안쪽은 1500 − 80 = 1420바이트가 되는데, 이것이 `wg-quick`의 기본 MTU 값과 같습니다. 택배 상자 규격이 정해져 있는데 포장재를 두껍게 감으면 안에 넣을 물건이 작아져야 하는 것과 같습니다.

MTU 문제는 증상이 독특해서 미리 알아 두지 않으면 원인을 찾기 어렵습니다. 작은 패킷인 ping은 잘 되는데, 큰 패킷이 오가는 웹 페이지 로딩이나 파일 전송만 멈추기 때문입니다. 이 개념은 아래 「큰 파일 전송만 멈출 때: MTU」 절에서 `ping -M do -s` 명령으로 통과 한계를 찾고 MTU 값을 낮추는 방법으로, 「네트워크 문제 점검 절차」 표의 7단계로, 「wg-quick과 wg의 차이」 절에서 `MTU`가 `wg-quick` 전용 항목인 이유로 쓰입니다.

### 가상 네트워크 인터페이스

운영체제가 패킷을 보낼 때는 네트워크 인터페이스(network interface)를 거칩니다. 실제 랜카드가 아니라 소프트웨어로 만든 가상 인터페이스를 둘 수 있고, WireGuard는 `wg0` 같은 이름의 가상 인터페이스를 만듭니다. 이 인터페이스로 나가는 패킷은 WireGuard가 암호화해 UDP로 감싸 실제 랜카드로 내보내고, 반대로 들어온 UDP 패킷은 복호화해 `wg0`에서 올라온 것처럼 운영체제에 넘깁니다. 그래서 `ip route`로 어떤 목적지를 `wg0`로 보낼지 정하는 방식과 자연스럽게 맞물립니다.

```bash
ip -br link show            # 인터페이스 목록: lo, eth0, wg0 ...
ip -br address show wg0     # wg0에 붙은 터널 주소 확인
```

이 개념이 중요한 이유는 WireGuard 설정이 "인터페이스 단위"로 이루어지기 때문입니다. 키·포트·피어 목록은 `wg0`라는 인터페이스에 붙고, 주소와 경로는 운영체제의 일반 네트워크 도구로 그 인터페이스에 붙입니다. 이 둘을 구분하지 못하면 `wg`와 `wg-quick`, `ip` 명령의 역할이 뒤섞여 보입니다. 이 개념은 아래 「wg-quick과 wg의 차이」 절에서 세 도구의 역할 분담으로, 「4단계: 활성화와 상태 확인」 절에서 `wg-quick up wg0`가 하는 일로, 「암호키 라우팅(cryptokey routing)」 절에서 인터페이스마다 피어 목록을 갖는 구조로 쓰입니다.

### 공개키 암호와 키 교환

공개키 암호(public-key cryptography)에서는 한 쌍의 키를 만듭니다. 개인키(private key)는 자기만 보관하고, 공개키(public key)는 상대에게 알려 줍니다. WireGuard는 타원곡선 Curve25519를 이용한 키 교환(ECDH, Elliptic-Curve Diffie-Hellman)을 사용합니다. 두 장비가 서로의 공개키를 알고 있으면, 각자 자기 개인키와 상대 공개키로 같은 비밀 값을 계산해 낼 수 있고, 이 값에서 실제 통신용 대칭키를 만듭니다. 중요한 점은 개인키가 네트워크를 지나가지 않는다는 것입니다. 우편함에 비유하면 공개키는 누구나 넣을 수 있는 투입구, 개인키는 우편함 주인만 가진 열쇠입니다.

WireGuard에서 피어의 신원은 곧 공개키입니다. 사용자 이름이나 인증서가 아니라 44자 정도의 공개키 문자열이 "이 장비가 누구인가"를 정합니다. 그래서 개인키가 유출되면 그 장비를 사칭할 수 있고, 장비를 폐기할 때는 그 공개키를 피어 목록에서 지우는 것이 곧 접근 회수가 됩니다. 이 개념은 아래 「1단계: 설치와 키 생성」 절의 `wg genkey`·`wg pubkey` 명령으로, 「근무자 한 명이 퇴사하거나 노트북을 분실했을 때」 절의 피어 제거로, 「개인키 관리」와 「키 교체 절차」 절에서 정적 키 쌍을 다루는 원칙으로 쓰입니다.

### Noise 프레임워크와 암호 구성

WireGuard의 핸드셰이크(handshake, 서로 신원을 확인하고 세션 키를 만드는 첫 교환)는 Noise 프로토콜 프레임워크의 `Noise_IKpsk2` 패턴을 기반으로 합니다. 데이터 암호화에는 ChaCha20-Poly1305(스트림 암호와 메시지 인증 코드를 결합한 AEAD, Authenticated Encryption with Associated Data 방식), 해시에는 BLAKE2s, 키 파생에는 HKDF를 씁니다. 이름을 모두 외울 필요는 없습니다. "협상 없이 고정된 현대적 조합"이라는 사실이 중요합니다. 하드웨어 AES 가속이 없는 소형 장비에서도 ChaCha20이 비교적 효율적이라는 점이 설계 배경으로 알려져 있습니다.

패턴 이름의 `IK`는 개시자가 응답자의 정적 공개키를 미리 알고(K, Known) 자기 정적 공개키는 첫 메시지에 암호화해 보낸다(I, Immediately)는 뜻이고, `psk2`는 사전 공유 키(pre-shared key)를 두 번째 메시지 단계에서 섞는다는 뜻입니다. 앞 소절의 공개키 교환이 "누구와 통신하는가"를 정한다면, 이 소절의 핸드셰이크는 "이번 세션에 쓸 임시 키를 어떻게 만들고 언제 바꾸는가"를 정합니다. 정적 키와 세션 키를 구분하지 못하면 "키는 자동으로 바뀐다"와 "키는 사람이 바꿔야 한다"는 본문의 두 문장이 모순처럼 보입니다. 이 개념은 아래 「핸드셰이크와 세션 키」 절에서 1-RTT 교환과 2분 주기 키 교체로, 「사전 공유 키(PresharedKey)」 절에서 `psk2`의 실제 설정으로, 「4단계: 활성화와 상태 확인」 절에서 `latest handshake` 값을 읽는 기준으로 쓰입니다.

### 암호키 라우팅(cryptokey routing)

WireGuard의 가장 독특한 개념은 암호키 라우팅입니다. 앞서 기반 기술에서 본 가상 인터페이스(`wg0`)마다 "피어 목록"을 가지고, 각 피어는 기반 기술에서 본 공개키 암호의 공개키와 `AllowedIPs`(허용 IP 목록)를 갖습니다. 이 목록은 두 가지 역할을 합니다.

- 송신: 패킷의 목적지 IP가 어느 피어의 `AllowedIPs`에 속하는지 보고, 그 피어의 키로 암호화해 UDP 패킷에 담아 보냅니다(앞서 기반 기술에서 본 터널링). 즉 앞서 기반 기술에서 본 라우팅 테이블 역할입니다.
- 수신: 복호화에 성공한 패킷의 출발지 IP가 그 피어의 `AllowedIPs`에 속할 때만 받아들입니다. 즉 접근 제어 목록 역할입니다.

예를 들어 서버가 노트북 피어에 `AllowedIPs = 10.8.0.2/32`를 설정했다면, 그 노트북 키로 암호화된 패킷이라 해도 출발지가 `10.8.0.5`라면 버려집니다. 한 피어가 다른 피어의 주소를 사칭하는 일을 이 규칙이 막아 줍니다. 한 가지 주의할 점은 `AllowedIPs`의 이름이 "허용 목록"이지만 라우팅 표이기도 하므로, 같은 대역을 두 피어에 겹쳐 넣으면 가장 구체적인(긴 접두사) 쪽이 우선하고 같은 범위를 중복 지정하면 마지막 설정이 이전 설정을 대체한다는 것입니다.

### 핸드셰이크와 세션 키

처음 패킷을 보낼 때(또는 기존 세션이 오래되었을 때) 두 장비는 앞서 기반 기술에서 본 Noise 기반 핸드셰이크를 합니다. 개시자가 첫 메시지를 보내고, 응답자가 응답하면 양쪽이 세션 키를 갖게 되어 1 왕복(1-RTT)으로 끝납니다. 이 세션 키는 일정 시간마다 새로 만들어집니다. 공식 프로토콜 문서에는 약 2분이 지나면 새 핸드셰이크를 시작하는 규칙(REKEY_AFTER_TIME 120초)이 정해져 있고, 오래된 키는 폐기됩니다. 덕분에 한 세션 키가 노출되더라도 그 이전과 이후의 통신까지 한꺼번에 풀리지 않는 순방향 비밀성(forward secrecy)을 얻습니다.

또 하나의 특징은 "조용함"입니다. 올바른 공개키로 만든 유효한 메시지가 아니면 WireGuard는 응답하지 않습니다. 앞서 기반 기술에서 본 것처럼 UDP에는 연결 수립 응답이 없으므로, 포트 스캔을 해도 닫힌 포트처럼 보이므로, 서버의 존재를 쉽게 드러내지 않습니다. 다만 이것이 보안의 전부는 아니며, 공개키 유출 관리와 앞서 기반 기술에서 본 방화벽 설계는 여전히 필요합니다.

### 로밍과 Endpoint

피어 설정의 `Endpoint`(상대의 IP:포트)는 처음 접속할 주소를 알려 주는 용도입니다. 서버는 노트북의 `Endpoint`를 미리 알 필요가 없고, 노트북이 보낸 유효한 패킷이 도착하면 그 출발지 주소를 해당 피어의 현재 Endpoint로 갱신합니다. 그래서 노트북이 카페 와이파이에서 모바일 핫스팟으로 옮겨 IP가 바뀌어도, 다음 유효한 패킷이 도착하는 순간 서버는 새 주소로 답장합니다. 이를 로밍(roaming)이라고 합니다. 반대로 서버의 주소가 바뀌면 클라이언트는 새 주소를 설정으로 알아야 하므로, 서버는 고정 IP나 DNS 이름을 갖는 쪽이 일반적입니다.

### PersistentKeepalive

앞서 기반 기술에서 본 것처럼, 가정이나 사무실 공유기 뒤의 장비는 NAT(Network Address Translation, 주소 변환) 장치를 통과합니다. NAT는 안쪽에서 먼저 나간 통신의 매핑 정보를 잠깐 기억하다가 지웁니다. 이 시간이 지나면 바깥에서 들어오는 패킷이 전달되지 않습니다. `PersistentKeepalive = 25`는 25초마다 빈 패킷을 보내 매핑을 유지하라는 설정입니다. 항상 필요한 것은 아니고, NAT 뒤의 장비가 서버 쪽에서 먼저 연락을 받아야 할 때 켭니다. 모바일처럼 배터리가 중요한 장비는 불필요하게 켜지 않는 편이 낫습니다.

## 실습 예시: 서버와 노트북 연결하기

아래 실습은 리눅스 서버 한 대와 노트북 한 대를 연결해 `10.8.0.0/24` 사설 대역을 만드는 예시입니다. 주소는 문서용 예약 대역(`203.0.113.0/24`)과 임의의 사설 대역을 썼습니다. 실제로 실행할 때는 본인 환경의 주소로 바꾸고, 운영 서버에서는 반드시 변경 작업 절차에 따라 진행하세요.

### 1단계: 설치와 키 생성

```bash
# Debian/Ubuntu 계열 예시
sudo apt-get update
sudo apt-get install -y wireguard wireguard-tools

# 키는 장비마다 각각 만든다. umask로 개인키 파일 권한을 제한한다.
umask 077
wg genkey | tee /etc/wireguard/server.key | wg pubkey > /etc/wireguard/server.pub

# 확인: 개인키는 화면에 불필요하게 출력하지 않고 공개키만 본다.
cat /etc/wireguard/server.pub
ls -l /etc/wireguard
```

`wg genkey`는 무작위 개인키를 만들고 `wg pubkey`는 그 개인키에서 공개키를 계산합니다. 개인키 파일의 권한이 `-rw-------`인지 반드시 확인하세요. 개인키가 유출되면 누구든 해당 피어를 사칭할 수 있습니다.

### 2단계: 서버 설정 파일

```ini
# /etc/wireguard/wg0.conf  (서버)
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <서버 개인키 값>

# 노트북 한 대에 하나의 [Peer] 블록을 둔다.
[Peer]
PublicKey = <노트북 공개키 값>
AllowedIPs = 10.8.0.2/32
```

서버는 `Endpoint`를 적지 않았습니다. 노트북이 먼저 접속해 오면 그 주소를 학습하기 때문입니다. `AllowedIPs = 10.8.0.2/32`는 "이 피어는 터널 안에서 `10.8.0.2` 한 개 주소만 쓴다"는 뜻입니다.

### 3단계: 노트북 설정 파일

```ini
# /etc/wireguard/wg0.conf  (노트북)
[Interface]
Address = 10.8.0.2/32
PrivateKey = <노트북 개인키 값>

[Peer]
PublicKey = <서버 공개키 값>
Endpoint = 203.0.113.10:51820
AllowedIPs = 10.8.0.0/24
PersistentKeepalive = 25
```

여기서 노트북의 `AllowedIPs = 10.8.0.0/24`는 "터널 안의 사설 대역으로 가는 트래픽만 서버로 보낸다"는 뜻으로, 이를 분할 터널링(split tunneling)이라고 부릅니다. 반대로 `AllowedIPs = 0.0.0.0/0`으로 두면 모든 인터넷 트래픽이 서버를 거치는 전체 터널링(full tunneling)이 됩니다. 이 경우 서버가 앞서 기반 기술에서 본 NAT와 IP 포워딩을 설정해야 하며, 서버의 대역폭과 책임 범위가 달라지므로 신중히 고르세요.

### 4단계: 활성화와 상태 확인

```bash
# 양쪽 장비에서 실행
sudo wg-quick up wg0

# 서버에서 상태 확인
sudo wg show

# 노트북에서 서버 터널 주소로 통신 확인
ping -c 3 10.8.0.1

# 부팅 시 자동 시작(systemd 사용 환경)
sudo systemctl enable --now wg-quick@wg0
```

`wg show`의 출력 예시는 다음과 같은 모양입니다. 값은 설명을 위한 가상의 예시입니다.

```text
interface: wg0
  public key: (서버 공개키)
  private key: (hidden)
  listening port: 51820

peer: (노트북 공개키)
  endpoint: 198.51.100.24:49822
  allowed ips: 10.8.0.2/32
  latest handshake: 41 seconds ago
  transfer: 3.21 KiB received, 2.80 KiB sent
```

가장 먼저 볼 줄은 `latest handshake`입니다. 값이 없거나 몇 분 이상 지났다면 암호화 통로가 한 번도 만들어지지 않았거나 끊어졌다는 신호입니다. 반대로 `transfer`는 늘어나는데 핸드셰이크가 없는 경우는 거의 없습니다. 핸드셰이크 없이는 데이터가 오갈 수 없기 때문입니다.

## wg-quick과 wg의 차이

초보자가 자주 헷갈리는 부분입니다. `wg`는 WireGuard 인터페이스의 키와 피어 같은 "암호 설정"만 다루는 저수준 도구이고, `wg-quick`은 설정 파일을 읽어 인터페이스 생성, IP 주소 부여, 라우팅 추가, DNS 설정, 방화벽 훅 실행까지 한꺼번에 해 주는 편의 스크립트입니다. `wg-quick`의 설정 파일에만 있는 항목(`Address`, `DNS`, `MTU`, `PostUp`, `PostDown` 등)은 `wg setconf`로 읽을 수 없습니다.

| 도구 | 하는 일 | 설정 파일 항목 |
|---|---|---|
| `wg` | 키·피어·포트 설정과 상태 조회 | `PrivateKey`, `ListenPort`, `PublicKey`, `AllowedIPs`, `Endpoint` 등 |
| `wg-quick` | 인터페이스 생성, 주소·라우팅·DNS 적용 | 위 항목 + `Address`, `DNS`, `MTU`, `Table`, `PostUp`, `PostDown` |
| `ip` | 인터페이스·주소·라우팅 직접 조작 | (설정 파일 없음, 명령어로 수행) |

설정 파일 없이 수동으로 만들고 싶다면 아래처럼 개별 명령을 조합할 수 있습니다. 동작 원리를 이해하는 데 도움이 되지만, 일상 운영에서는 `wg-quick`이나 systemd-networkd 같은 선언적 방식이 실수를 줄입니다.

```bash
# 수동 구성 예시 (서버 측, 이해용)
sudo ip link add dev wg0 type wireguard
sudo ip address add 10.8.0.1/24 dev wg0
sudo wg set wg0 listen-port 51820 private-key /etc/wireguard/server.key
sudo wg set wg0 peer <노트북 공개키 값> allowed-ips 10.8.0.2/32
sudo ip link set up dev wg0
```

## 업무 예시: 재택 근무자가 사내 개발 서버에 접근하기

### 시나리오

작은 개발 팀이 있다고 가정합니다. 사내 개발용 서버(`10.20.0.0/24` 대역)는 외부에 직접 공개하지 않고, 사무실 게이트웨이 한 대에만 UDP 51820 포트를 열었습니다. 재택 근무자 세 명이 이 게이트웨이를 통해 사내 대역에 접속해야 합니다. 이는 설명을 위한 가상의 시나리오이며, 실제 규모나 성능 수치는 포함하지 않았습니다.

### 주소 설계

| 장비 | 터널 주소 | AllowedIPs(게이트웨이 측 피어 설정) |
|---|---|---|
| 게이트웨이 | 10.8.0.1/24 | (인터페이스 자신) |
| 근무자 A 노트북 | 10.8.0.11/32 | 10.8.0.11/32 |
| 근무자 B 노트북 | 10.8.0.12/32 | 10.8.0.12/32 |
| 근무자 C 노트북 | 10.8.0.13/32 | 10.8.0.13/32 |

터널 주소는 사내 대역(`10.20.0.0/24`)과 겹치지 않게 별도 대역(`10.8.0.0/24`)으로 잡았습니다. 대역이 겹치면 라우팅이 모호해져 접속이 되다 안 되다 하는 문제가 생깁니다. 근무자 가정의 공유기 대역(흔히 `192.168.0.0/24`나 `10.0.0.0/24`)과도 겹치지 않는지 확인해야 합니다.

### 게이트웨이 설정

```ini
# /etc/wireguard/wg0.conf  (사무실 게이트웨이)
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <게이트웨이 개인키 값>

# 터널에서 사내 대역으로 포워딩을 허용하고 NAT 처리(사내 서버가 터널 대역으로의 복귀 경로를 모를 때)
PostUp = sysctl -w net.ipv4.ip_forward=1
PostUp = iptables -A FORWARD -i %i -d 10.20.0.0/24 -j ACCEPT
PostUp = iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -d 10.20.0.0/24 -j MASQUERADE
PostDown = iptables -D FORWARD -i %i -d 10.20.0.0/24 -j ACCEPT
PostDown = iptables -t nat -D POSTROUTING -s 10.8.0.0/24 -d 10.20.0.0/24 -j MASQUERADE

[Peer]
# 근무자 A
PublicKey = <A 공개키 값>
AllowedIPs = 10.8.0.11/32

[Peer]
# 근무자 B
PublicKey = <B 공개키 값>
AllowedIPs = 10.8.0.12/32
```

`PostUp`과 `PostDown`은 터널을 올리고 내릴 때 실행되는 명령입니다. `%i`는 인터페이스 이름(`wg0`)으로 치환됩니다. 위 예시는 `iptables`를 썼지만 최근 배포판은 nftables가 기본인 경우가 많으므로 환경에 맞는 도구를 쓰세요. `MASQUERADE`는 터널 대역의 출발지 주소를 게이트웨이 주소로 바꿔서, 사내 서버가 따로 복귀 경로를 설정하지 않아도 응답이 돌아오게 하는 방법입니다. 대신 사내 서버 로그에는 모든 접속이 게이트웨이 주소로 찍혀 누가 접속했는지 구분하기 어렵습니다. 감사 로그가 중요하다면 NAT 대신 사내 라우터에 터널 대역 경로를 추가하는 방식을 고려하세요.

### 근무자 노트북 설정

```ini
[Interface]
Address = 10.8.0.11/32
PrivateKey = <A 개인키 값>
DNS = 10.20.0.2

[Peer]
PublicKey = <게이트웨이 공개키 값>
Endpoint = vpn.example.com:51820
AllowedIPs = 10.8.0.0/24, 10.20.0.0/24
PersistentKeepalive = 25
```

`AllowedIPs`에 터널 대역과 사내 대역 두 개를 적었으므로, 이 두 대역으로 가는 트래픽만 터널을 타고 나머지 인터넷 접속은 근무자의 일반 회선으로 나갑니다. `DNS` 항목은 사내 이름 서버를 쓰도록 `wg-quick`이 시스템 DNS 설정을 바꾸는 값입니다. 사내 DNS 서버 주소가 `AllowedIPs` 범위에 포함되어야 질의가 터널로 갑니다.

### 근무자 한 명이 퇴사하거나 노트북을 분실했을 때

WireGuard에는 서버가 중앙에서 사용자를 지우는 계정 기능이 없으므로, 해당 피어 항목을 제거하는 것이 폐기 절차입니다. 실행 중인 인터페이스에서는 아래처럼 즉시 반영할 수 있습니다.

```bash
# 분실된 노트북의 피어를 즉시 제거
sudo wg set wg0 peer <A 공개키 값> remove

# 설정 파일에서도 해당 [Peer] 블록을 삭제해야 재시작 후에도 되살아나지 않는다.
sudo wg show wg0 peers
```

이 절차에서 알 수 있듯이 피어 수가 늘어나면 설정 파일 관리가 부담이 됩니다. 이를 보완하려고 설정을 코드로 관리(Ansible 등)하거나, 피어 관리 기능을 얹은 제품과 오픈소스 도구를 검토하는 팀이 많습니다. 어떤 도구를 쓰든 개인키는 사용자 장비에서 생성하고 서버에는 공개키만 전달하는 흐름이 원칙에 가깝습니다.

## 네트워크 문제 점검 절차

터널이 안 될 때는 계층별로 좁혀 가는 것이 효율적입니다.

| 단계 | 확인 사항 | 명령 예시 |
|---|---|---|
| 1 | 인터페이스가 올라와 있는가 | `ip -br address show wg0` |
| 2 | 서버가 UDP 포트를 듣고 있는가 | `sudo ss -ulpn | grep 51820` |
| 3 | 방화벽·보안 그룹이 UDP를 허용하는가 | `sudo nft list ruleset` 또는 클라우드 콘솔 |
| 4 | 핸드셰이크가 되었는가 | `sudo wg show` 의 `latest handshake` |
| 5 | AllowedIPs가 맞는가 | `sudo wg show wg0 allowed-ips` |
| 6 | 포워딩이 켜졌는가(게이트웨이 구성) | `sysctl net.ipv4.ip_forward` |
| 7 | 큰 패킷만 실패하는가(MTU) | `ping -M do -s 1372 10.8.0.1` |

### 핸드셰이크가 없을 때

원인은 대개 세 가지입니다. 첫째, 공개키를 잘못 복사했거나 한쪽만 등록한 경우입니다. 공개키는 영문·숫자·기호로 된 44자 정도의 문자열이라 줄바꿈이나 공백이 섞이기 쉽습니다. 둘째, UDP 포트가 방화벽이나 클라우드 보안 그룹에서 막힌 경우입니다. 셋째, `Endpoint` 주소나 포트가 틀린 경우입니다. 서버는 유효하지 않은 패킷에 응답하지 않으므로, 클라이언트 입장에서는 "아무 일도 일어나지 않는" 것처럼 보입니다. 이런 침묵 때문에 서버 쪽에서 패킷 캡처로 실제 도착 여부를 보는 것이 가장 빠릅니다.

```bash
# 서버에서 UDP 51820 도착 여부 확인 (tcpdump 설치 필요)
sudo tcpdump -ni any udp port 51820
```

패킷이 도착하는데도 핸드셰이크가 안 된다면 키 불일치를, 패킷이 아예 안 보이면 네트워크 경로나 방화벽을 의심합니다.

### 핸드셰이크는 되는데 통신이 안 될 때

이 경우는 거의 `AllowedIPs`나 라우팅, 포워딩 문제입니다. 서버 쪽에서 해당 피어의 `AllowedIPs`에 클라이언트의 터널 주소가 들어 있는지, 클라이언트 쪽에서는 목적지 대역이 서버 피어의 `AllowedIPs`에 있는지 확인하세요. 한쪽에서만 포함되면 "보내기만 되고 받기는 안 되는" 현상이 생깁니다. 사내 서버로 접근하는 구성이라면 사내 서버가 터널 대역으로 가는 복귀 경로를 알고 있는지도 확인합니다.

### 큰 파일 전송만 멈출 때: MTU

앞서 기반 기술에서 본 MTU 계산처럼, 터널은 원래 패킷에 헤더를 덧붙이므로 안쪽 패킷이 담을 수 있는 최대 크기(MTU, Maximum Transmission Unit)가 줄어듭니다. `wg-quick`의 기본 MTU는 1420으로 알려져 있으며, 이는 IPv6 위에서도 1500 바이트 이더넷을 통과할 수 있도록 여유를 둔 값입니다. 하지만 PPPoE 회선이나 이중 터널 같은 환경에서는 이 값도 크게 느껴질 수 있고, 증상은 ping은 되고 웹 로딩이나 SSH 접속이 중간에 멈추는 모양으로 나타납니다.

```bash
# 터널 안으로 조각화 금지 비트를 세워 ping: 크기를 줄여 가며 통과 한계를 찾는다.
ping -M do -s 1392 -c 3 10.8.0.1
ping -M do -s 1372 -c 3 10.8.0.1

# 해결: 설정 파일의 [Interface]에 MTU를 낮춰 지정
# MTU = 1380
```

찾은 한계 값에 IP·ICMP 헤더 28바이트를 더하면 대략의 경로 MTU가 나옵니다. 이는 일반적인 진단 요령이며, 정확한 값은 회선 환경에서 직접 확인해야 합니다.

## 보안 운영 시 고려할 점

### 개인키 관리

개인키는 장비 밖으로 나가면 안 됩니다. 파일 권한을 `600`으로 하고, 백업에 포함될 때는 암호화 저장소에 둡니다. 설정 파일 하나에 개인키가 그대로 들어 있으므로, 설정 저장소(Git 등)에 평문으로 올리지 않도록 주의합니다. 키를 자동 배포 도구로 관리한다면 시크릿 관리 기능을 이용하세요. 개인키 유출이 의심되면 키 쌍을 새로 만들고 상대편의 피어 항목을 교체하는 수밖에 없습니다.

### 사전 공유 키(PresharedKey)

각 피어 쌍에 선택적으로 `PresharedKey`를 추가할 수 있습니다. 공개키 암호 부분이 장래에 양자 컴퓨터로 깨지는 경우를 대비해 대칭키 비밀을 한 겹 더 섞는 용도로 설계 문서가 설명하는 기능입니다. 사용하려면 양쪽이 같은 값을 공유해야 하므로 관리 부담이 늘어납니다. 위협 모델(공격자가 지금 트래픽을 저장해 두었다가 먼 미래에 푸는 경우를 걱정하는지)에 따라 선택하세요.

### 접근 범위 좁히기

VPN에 접속했다고 사내 전체에 접근할 수 있게 하는 것은 위험합니다. `AllowedIPs`는 터널 안에서의 주소 사칭을 막을 뿐, 터널 안에서 어느 사내 서버에 갈 수 있는지는 게이트웨이의 방화벽 규칙이 정합니다. 개발 팀은 개발 서버 대역만, 운영 팀은 운영 서버 대역만 열도록 피어별 터널 주소를 기준으로 방화벽 규칙을 나누는 설계를 권합니다.

```bash
# 예시: 근무자 A(10.8.0.11)는 개발 서버 10.20.0.10의 SSH(22)만 허용
sudo iptables -A FORWARD -i wg0 -s 10.8.0.11 -d 10.20.0.10 -p tcp --dport 22 -j ACCEPT
sudo iptables -A FORWARD -i wg0 -s 10.8.0.11 -j DROP
```

### 로그와 감사

WireGuard는 기본적으로 연결 로그를 남기지 않습니다. 이는 개인정보 측면의 장점이지만, 기업 환경에서는 "누가 언제 접속했는가"를 알아야 할 때가 많습니다. `latest handshake` 값을 주기적으로 수집해 모니터링 시스템에 기록하거나, 방화벽 로그를 이용하는 식으로 보완할 수 있습니다. 어느 수준의 감사가 필요한지는 조직의 보안 정책과 법적 요구 사항에 따라 정하세요.

## 확장 시나리오: 두 사무실을 잇는 사이트 간 연결

### 구조와 AllowedIPs 설계

원격 근무자 접속이 "한 점과 한 대역"을 잇는 것이라면, 사이트 간(site-to-site) 연결은 "한 대역과 다른 대역"을 잇는 것입니다. 본사 대역을 `10.20.0.0/24`, 지사 대역을 `10.30.0.0/24`라 하고 양쪽 게이트웨이를 WireGuard로 연결한다고 가정하겠습니다. 이때 각 게이트웨이의 피어 설정에서 `AllowedIPs`에는 상대편 게이트웨이의 터널 주소뿐 아니라 상대편 사내 대역 전체를 넣습니다. 본사 게이트웨이 입장에서 지사 게이트웨이 피어의 `AllowedIPs`는 `10.8.0.2/32, 10.30.0.0/24`가 됩니다. 앞에서 설명한 암호키 라우팅 때문에 이 한 줄이 "지사 대역으로 가는 패킷은 이 피어로 암호화해 보낸다"는 송신 규칙과 "지사 게이트웨이가 보낸 패킷 중 출발지가 지사 대역인 것만 받는다"는 수신 규칙을 동시에 만듭니다.

```ini
# 본사 게이트웨이 /etc/wireguard/wg0.conf
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <본사 개인키 값>

[Peer]
# 지사 게이트웨이
PublicKey = <지사 공개키 값>
Endpoint = branch.example.com:51820
AllowedIPs = 10.8.0.2/32, 10.30.0.0/24
PersistentKeepalive = 25
```

양쪽 사내 장비들이 상대 대역으로 가는 경로를 자기 게이트웨이로 보내도록 라우터에 정적 경로를 추가해야 합니다. 게이트웨이 사이의 터널만 만들어 놓고 사내 라우터에 경로가 없으면, 사내 PC가 보낸 패킷이 인터넷 쪽 기본 경로로 나가 버립니다. 이 단계에서 가장 흔한 실수가 "터널은 올라왔는데 사내 PC끼리는 통신이 안 된다"는 상황입니다.

### 겹치는 대역 문제

두 사무실이 모두 `192.168.0.0/24`를 쓰는 경우처럼 대역이 겹치면 `AllowedIPs`로 해결할 수 없습니다. 어느 쪽 주소인지 모호하기 때문입니다. 해결 방법은 한쪽 대역을 재설계하거나, 변환(NAT)을 사용해 서로 다른 가상 대역으로 보이게 하는 것입니다. 변환은 장애 분석을 어렵게 하므로, 가능하면 처음부터 사내 대역 배정 표를 만들어 겹치지 않게 관리하는 편이 좋습니다.

## 설정을 코드로 관리하고 키를 교체하기

### 선언적으로 관리하는 방법

수작업으로 설정 파일을 고치면 서버마다 내용이 달라지기 쉽습니다. 설정을 템플릿화해 Ansible 같은 구성 관리 도구로 배포하면 피어 추가·제거가 코드 리뷰와 이력 관리 대상이 됩니다. 이 경우에도 개인키는 템플릿에 평문으로 넣지 말고 시크릿 저장소에서 주입하세요. 또 설정 변경을 적용할 때 연결을 끊지 않으려면 `wg syncconf`를 쓰는 방법이 있습니다. `wg-quick down`과 `up`을 반복하면 모든 피어의 연결이 잠시 끊기지만, `syncconf`는 변경된 피어만 갱신합니다.

```bash
# wg-quick 전용 항목(Address, DNS 등)을 제거한 설정만 추출해 무중단 반영
sudo wg syncconf wg0 <(sudo wg-quick strip wg0)

# 반영 결과 확인
sudo wg show wg0 peers
```

`wg-quick strip`은 `wg-quick` 전용 항목을 뺀 순수 WireGuard 설정을 출력합니다. 이 명령은 `wg-quick` 매뉴얼에 설명된 기능이며, 실제 적용 전에는 시험 환경에서 먼저 동작을 확인하세요.

### 키 교체 절차

WireGuard의 세션 키는 자동으로 계속 바뀌지만, 장비의 정적 키 쌍은 사람이 바꿔야 합니다. 정기 교체나 유출 의심 시에는 다음 순서를 권합니다. 먼저 장비에서 새 키 쌍을 만들고, 새 공개키를 상대에게 전달해 상대 설정에 임시로 추가하거나 교체할 준비를 합니다. 그다음 같은 변경 창구에서 한쪽씩 교체하고 `latest handshake`가 새로 찍히는지 확인합니다. 한쪽만 먼저 바꾸면 연결이 끊기므로, 사전에 콘솔 접근 같은 복구 경로를 확보해야 합니다. 원격 서버의 터널 위에서 SSH로 작업 중이라면 더욱 그렇습니다.

```bash
# 새 키 쌍 생성 (기존 키 파일은 덮어쓰지 않고 별도 이름으로)
umask 077
wg genkey | tee /etc/wireguard/server-new.key | wg pubkey > /etc/wireguard/server-new.pub

# 교체 전후 비교: 핸드셰이크 시각 확인
sudo wg show wg0 latest-handshakes
```

### 간단한 상태 수집 스크립트

핸드셰이크 시각을 주기적으로 읽어 오래된 피어를 찾는 스크립트 예시입니다. `wg show wg0 latest-handshakes`는 피어 공개키와 유닉스 시각(초)을 탭으로 구분해 출력하며, 핸드셰이크가 없으면 0을 출력합니다.

```bash
#!/usr/bin/env bash
# 3분(180초)보다 오래 핸드셰이크가 없는 피어를 출력한다.
now=$(date +%s)
sudo wg show wg0 latest-handshakes | while read -r peer ts; do
  age=$(( now - ts ))
  if [ "$ts" -eq 0 ] || [ "$age" -gt 180 ]; then
    echo "STALE peer=$peer last_handshake_age=${age}s"
  fi
done
```

주의할 점은 `PersistentKeepalive`를 쓰지 않는 피어는 통신이 없으면 핸드셰이크도 일어나지 않으므로, 이 스크립트가 정상 휴면 상태를 장애로 오탐할 수 있다는 것입니다. 임계값은 피어의 사용 패턴에 맞게 정하고, 경보는 "연속으로 여러 번 오래됨" 같은 조건으로 완화하세요.

## 한계와 적용 기준 Q&A

### Q. WireGuard는 사용자 로그인이나 MFA를 지원하나요?

A. 프로토콜 자체는 지원하지 않습니다. 인증의 단위는 장비가 가진 키 쌍입니다. 따라서 "이 사용자가 이 시점에 로그인했는가", 다중 인증(MFA, Multi-Factor Authentication), 단말 상태 검사 같은 요구가 있다면 WireGuard 위에 중앙 인증과 정책을 얹은 별도 솔루션을 쓰거나, 인증 기능이 있는 다른 VPN 방식과 비교해야 합니다.

### Q. UDP가 막힌 환경에서는 어떻게 하나요?

A. WireGuard는 UDP만 사용합니다. 일부 엄격한 방화벽은 UDP 51820뿐 아니라 임의의 UDP를 막기도 합니다. 서버 포트를 443 같은 흔한 UDP 포트로 바꿔 보는 방법이 있지만 항상 통하지는 않습니다. TCP로 감싸는 우회 도구가 존재하나 지연과 재전송이 겹치는 TCP-over-TCP 문제가 생길 수 있어, 필수 요건이면 TCP를 지원하는 VPN과 비교 검토가 필요합니다.

### Q. 모든 트래픽을 터널로 보내려면 `0.0.0.0/0`만 쓰면 되나요?

A. 클라이언트 설정만으로는 부족합니다. 서버에서 IP 포워딩을 켜고 NAT 또는 라우팅을 구성해야 하며, DNS 누수(터널 밖으로 DNS 질의가 새는 현상)도 점검해야 합니다. 또 `wg-quick`이 서버 `Endpoint` 자신으로 가는 트래픽이 터널로 되돌아가 순환하지 않도록 경로 예외를 자동으로 추가하는지, 사용하는 구현체가 어떻게 처리하는지도 확인해야 합니다.

### Q. 피어가 수백 개가 되면 어떻게 되나요?

A. 프로토콜은 피어 수에 엄격한 제한을 두지 않지만 운영 부담이 문제가 됩니다. 설정 파일에 피어를 일일이 적는 방식은 수십 개를 넘어가면 실수가 늘고, 키 교체·폐기 절차도 복잡해집니다. 설정 생성을 자동화하고, 주소 배정 대장을 별도 관리하며, 접근 정책은 방화벽이나 상위 관리 도구에서 선언하는 구조를 설계하는 편이 안전합니다. 구체적인 한계 수치는 제가 측정한 바 없으므로 자체 부하 시험으로 확인하세요.

### Q. 서버가 하나뿐인데 그 서버가 죽으면 어떻게 하나요?

A. 허브 앤 스포크(hub-and-spoke) 구조에서는 허브가 단일 장애 지점이 됩니다. 허브를 두 대 이상 두고 클라이언트가 두 허브 피어를 모두 가지게 하거나, 지역별 게이트웨이를 두는 방식이 있습니다. 다만 두 허브가 같은 대역을 광고하면 `AllowedIPs` 충돌이 생기므로, 대역 분리나 별도 라우팅 프로토콜 등 설계가 필요합니다. 도입 초기에는 단순한 구성으로 시작하고 장애 시 복구 절차를 문서화하는 것을 우선하세요.

### Q. WireGuard가 IPsec이나 OpenVPN보다 항상 빠른가요?

A. 항상은 아닙니다. 논문과 공식 성능 페이지는 리눅스 커널 구현이 많은 시험 환경에서 유리했다고 설명하지만, CPU의 AES 하드웨어 가속 여부, 패킷 크기, 구현체, 커널 버전에 따라 결과가 달라집니다. 이 글에서 성능 수치는 제시하지 않았고, 도입 결정에는 자기 장비와 회선에서 `iperf3` 같은 도구로 직접 비교한 결과를 쓰는 것이 합리적입니다.

```bash
# 서버에서
iperf3 -s -B 10.8.0.1
# 노트북에서 (터널 위에서의 처리량 확인)
iperf3 -c 10.8.0.1 -t 30
```

### Q. 도입 전에 체크리스트가 있나요?

A. 다음 항목을 정해 두면 시행착오가 줄어듭니다.

| 항목 | 질문 |
|---|---|
| 목적 | 사이트 간 연결인가, 원격 근무자 접속인가, 서버 간 보호인가 |
| 대역 | 터널 대역이 사내·가정 대역과 겹치지 않는가 |
| 정책 | 누가 어디에 접근하는지 방화벽 규칙으로 표현했는가 |
| 키 | 개인키 생성·보관·폐기 절차가 있는가 |
| 가용성 | 게이트웨이 장애 시 복구 방안이 있는가 |
| 가시성 | 핸드셰이크 시각 등 상태를 모니터링하는가 |
| 네트워크 | UDP를 허용하는 경로인가, MTU는 점검했는가 |

## 마무리

WireGuard는 "공개키로 피어를 식별하고, `AllowedIPs` 표로 보낼 곳과 받을 것을 동시에 정하는" 단순한 모델로 VPN을 구성합니다. 암호 구성을 고정해 협상 단계를 없앴고, 핸드셰이크와 키 교체가 자동이며, 로밍을 지원해 이동하는 장비에도 맞습니다. 반면 사용자 계정, MFA, 동적 주소 배정, 상세 감사 로그 같은 기능은 직접 설계하거나 상위 도구에 맡겨야 합니다.

처음 접한다면 서버 한 대와 노트북 한 대로 위 실습을 따라 해 `wg show`의 `latest handshake`를 직접 확인해 보세요. 그다음 `AllowedIPs`를 바꿔 보며 어떤 트래픽이 터널로 가는지 관찰하고, 방화벽 규칙으로 접근 범위를 좁히는 순서로 확장하면 개념을 안전하게 익힐 수 있습니다. 어떤 도구를 고르든 중요한 것은 목적, 접근 정책, 키 관리 절차를 먼저 정하는 일입니다.
