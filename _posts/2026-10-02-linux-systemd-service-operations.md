리눅스 서버에서 애플리케이션을 띄우는 일은 명령어 한 줄로 시작할 수 있습니다. 그러나 SSH 세션이 끊긴 뒤에도 살아 있어야 하고, 서버 재부팅 뒤 올바른 순서로 시작해야 하며, 실패했을 때 어디서 이유를 확인할지 알 수 있어야 합니다. 이 문제를 매번 셸 스크립트와 개인의 기억으로 해결하면 운영 품질이 사람에게 묶입니다. **systemd(System and Service Manager, 리눅스의 시스템·서비스 관리자)** 는 이러한 프로세스의 생명주기와 의존 관계, 로그, 권한 경계를 선언적으로 관리하도록 널리 쓰이는 초기화·서비스 관리 시스템입니다.

이 글은 Linux에서 systemd를 처음 만나는 개발자와 운영자를 위한 개념 글입니다. 특정 서버에서 직접 장애를 해결하거나 성능을 측정한 경험을 주장하지 않습니다. 배포판과 systemd 버전에 따라 설정 항목과 기본값은 다를 수 있으므로, 실제 변경 전에는 해당 서버의 `man systemd.service`, `man systemd.exec`, 배포판 문서를 함께 확인해야 합니다. 핵심은 unit 파일 문법을 많이 외우는 것이 아니라, 어떤 프로세스를 어떤 계정으로 언제 시작하고, 실패·로그·의존성을 누구의 책임으로 볼지 명확히 하는 것입니다.

## 먼저 알아둘 기반 기술: 프로세스, PID, 신호, 부팅

**프로세스(process)** 는 운영체제가 실행 중인 프로그램을 관리하는 단위입니다. 실행 파일 하나가 시작되면 운영체제는 메모리, 파일 핸들, 네트워크 소켓, 권한, 고유한 번호를 할당합니다. 이 번호가 **PID(Process Identifier, 프로세스 식별자)** 입니다. 웹 서버 프로세스가 PID 1234로 실행 중이라고 해서 그 번호가 다음 재시작 뒤에도 같다는 보장은 없습니다. 운영 자동화가 특정 PID를 파일에 적어 두고 영구 신원처럼 다루면 재사용된 번호를 잘못 제어할 위험이 있습니다.

프로세스는 종료 요청을 **신호(signal)** 로 받습니다. `SIGTERM`은 정상 종료를 요청할 때 흔히 사용하고, 프로그램은 이를 받아 새 요청을 멈추고 연결을 정리하고 파일을 닫을 기회를 가질 수 있습니다. `SIGKILL`은 프로세스가 처리할 기회 없이 즉시 종료시키는 강한 신호입니다. 장애 대응에서 `kill -9`가 항상 빠른 해결책처럼 보이지만, 쓰기 중인 파일과 연결 정리, 임시 자원 회수 관점에서는 마지막 수단으로 보는 편이 좋습니다. systemd는 서비스 중지 시 어떤 신호를 보내고 얼마나 기다릴지 관리할 수 있습니다.

리눅스가 부팅되면 커널 뒤에 사용자 공간 서비스가 순서대로 준비됩니다. 네트워크, 파일 시스템, 시간 동기화, 로그, 원격 접속, 애플리케이션이 서로 의존하기 때문입니다. systemd는 이 과정을 **unit(유닛)** 이라는 구성 단위로 모델링합니다. 서비스만 있는 것이 아니라 소켓, 타이머, 마운트, 타깃 같은 여러 unit이 있고, 서로의 시작 순서와 필요 관계를 선언합니다. 그래서 “부팅이 끝난 뒤 스크립트를 실행한다”는 막연한 방식보다 어떤 조건 뒤에 어떤 서비스를 시작할지 표현하기 쉽습니다.

**데몬(daemon)** 은 보통 백그라운드에서 오래 실행되며 요청을 받는 프로세스를 말합니다. 웹 서버, 데이터베이스, SSH 서버, 로그 수집기가 예입니다. 예전에는 데몬이 스스로 백그라운드로 두 번 분기(fork)하고 PID 파일을 만드는 패턴이 흔했지만, systemd는 가능한 한 주 프로세스를 직접 추적하는 방식을 선호합니다. 애플리케이션이 스스로 백그라운드로 숨으면 systemd가 실제 생명주기를 정확히 알기 어려울 수 있으므로, 서비스 유형과 프로그램의 실행 방식이 맞아야 합니다.

## systemd가 해결하려는 운영 문제

첫째는 **소유권**입니다. 어떤 프로세스를 누가 시작했고, 어떤 설정으로 실행됐으며, 누가 멈춰야 하는지 모르면 장애 대응은 셸 이력과 `ps` 출력에 의존하게 됩니다. systemd unit 파일은 실행 명령, 실행 계정, 환경 파일, 작업 디렉터리, 재시작 정책을 서버 설정으로 남깁니다. 이는 모든 설정을 unit 파일 하나에 넣으라는 뜻은 아닙니다. 비밀 값은 적절한 비밀 관리 수단을 쓰고, 공통 설정은 배포 도구로 관리하되, 런타임 생명주기의 기준점은 unit에 두자는 뜻입니다.

둘째는 **의존성과 순서**입니다. 애플리케이션이 네트워크가 준비되기 전에 외부 API에 연결하려 하거나, 필요한 마운트가 아직 붙기 전에 파일을 열면 부팅 때만 재현되는 실패가 생깁니다. systemd의 `After=`는 시작 순서를, `Requires=`와 `Wants=`는 어떤 unit을 필요하거나 함께 시작하고 싶은지 표현합니다. 이 세 키워드는 비슷해 보이지만 실패 전파와 활성화 관계가 달라서, 무조건 많이 넣는 방식은 오히려 부팅을 복잡하게 만듭니다.

셋째는 **관찰 가능성**입니다. 백그라운드 실행 명령 뒤 표준 출력이 사라지면 프로세스가 왜 실패했는지 찾기 어렵습니다. systemd는 서비스의 표준 출력과 오류 출력을 journal에 보내고, `journalctl`로 unit과 시간 범위에 따라 볼 수 있게 합니다. 로그가 있다는 사실만으로 운영이 끝나는 것은 아닙니다. 요청 ID, 오류 원인, 민감 값 마스킹, 보존 기간, 중앙 수집 여부를 애플리케이션과 인프라 관점에서 함께 정해야 합니다.

## unit 파일의 세 구역을 읽는 법

가장 흔한 `*.service` unit 파일은 `[Unit]`, `[Service]`, `[Install]` 세 구역으로 읽을 수 있습니다. `[Unit]`에는 사람이 읽는 설명과 의존성·순서 관계를 둡니다. `[Service]`에는 실제 실행 명령, 사용자, 환경, 종료·재시작 정책을 둡니다. `[Install]`에는 `systemctl enable`로 부팅 시 연결할 타깃을 둡니다. 파일에 `WantedBy=multi-user.target`가 있다고 서비스가 즉시 실행되는 것은 아닙니다. enable은 부팅 시 시작될 연결을 만들고, start는 지금 이 서비스를 시작합니다.

아래 예시는 포트 8080에서 실행되는 가상의 Java 애플리케이션을 전용 계정으로 실행하는 최소 예입니다. 경로와 사용자, 환경 파일은 실제 환경에 맞게 바꿔야 하며, 비밀 값을 unit 파일에 직접 넣는 예가 아닙니다.

```ini
[Unit]
Description=Example order API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=orderapi
Group=orderapi
WorkingDirectory=/opt/order-api
EnvironmentFile=/etc/order-api/order-api.env
ExecStart=/usr/bin/java -jar /opt/order-api/order-api.jar
Restart=on-failure
RestartSec=5
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
```

`Description=`은 단순한 장식이 아닙니다. 장애 중 `systemctl status`를 볼 사람이 어떤 서비스인지 빠르게 이해하게 합니다. `After=network-online.target`은 네트워크가 온라인으로 간주된 뒤 시작 순서를 잡으려는 의도이고, `Wants=`는 그 타깃을 함께 활성화하려는 약한 관계입니다. 단, 네트워크가 온라인이라고 외부 데이터베이스나 DNS, 인증 서비스가 반드시 준비됐다는 뜻은 아닙니다. 애플리케이션은 연결 재시도와 타임아웃을 스스로 가져야 하며, unit 의존성으로 외부 시스템의 준비를 완벽하게 표현하려 하면 부팅이 취약해집니다.

`Type=simple`은 `ExecStart`로 시작한 프로세스를 서비스의 주 프로세스로 취급하는 흔한 형태입니다. 애플리케이션이 백그라운드로 분기하지 않고 포그라운드에서 실행될 때 맞습니다. 어떤 소프트웨어는 준비 완료를 systemd에 알리는 `Type=notify`를 지원하고, 한 번 실행하고 끝나는 배치 작업에는 `Type=oneshot`이 맞을 수 있습니다. 유형을 프로그램의 실제 동작과 다르게 고르면 systemd가 시작 완료나 실패를 잘못 판단할 수 있으므로, 제품 공식 문서와 unit 예시를 확인합니다.

## start, enable, reload를 구분하기

`systemctl start order-api.service`는 지금 서비스를 시작합니다. `systemctl stop`은 중지를 요청하고, `restart`는 중지 뒤 다시 시작합니다. `systemctl enable`은 부팅 타깃에 연결을 만들어 다음 부팅부터 자동 시작되게 합니다. 따라서 새 서버에서 enable만 하고 현재 상태를 확인하지 않거나, start만 하고 재부팅 후 사라지는 문제를 만들 수 있습니다. 시작과 부팅 자동 시작은 서로 다른 동작입니다.

unit 파일을 수정한 뒤에는 `systemctl daemon-reload`가 필요합니다. 이 명령은 systemd 관리자에게 unit 정의를 다시 읽으라고 알립니다. 그러나 이미 실행 중인 애플리케이션 프로세스의 환경과 명령을 자동으로 바꾸지는 않습니다. `daemon-reload` 뒤 필요한 경우 `restart` 또는 제품이 지원하는 안전한 reload 절차를 수행하고, 상태와 로그를 확인합니다. 설정 파일을 수정했는데 서비스가 이전 설정으로 동작하는 문제는 이 구분을 놓칠 때 자주 생깁니다.

`reload`는 프로세스를 죽이지 않고 설정을 다시 읽도록 요청하는 동작을 뜻할 수 있지만, 모든 프로그램이 지원하지는 않습니다. 웹 서버는 reload 중 새 연결을 점진적으로 넘길 수 있어도, 애플리케이션 프레임워크는 재시작이 필요할 수 있습니다. systemd unit에 reload 명령을 억지로 만들기보다, 그 제품이 실제로 어떤 신호나 관리 API를 지원하는지 확인합니다. 특히 데이터베이스·메시지 브로커·보안 에이전트는 잘못된 reload가 구성 불일치나 연결 실패를 만들 수 있습니다.

## 로그는 journalctl에서 시작하고 끝나지 않는다

**journal**은 systemd-journald가 수집하는 구조화된 로그 저장소입니다. `journalctl -u order-api.service`는 특정 서비스 unit의 로그를 보는 기본적인 방법입니다. `-f`를 붙이면 새 로그를 따라가고, `--since "10 minutes ago"`로 시간 범위를 좁힐 수 있습니다. 장애 중 전체 시스템 로그를 끝없이 보는 대신 unit·부팅·시간 조건을 좁히면 원인과 증상을 구분하기 쉬워집니다.

```bash
sudo systemctl status order-api.service
sudo journalctl -u order-api.service --since "30 minutes ago"
sudo journalctl -u order-api.service -f
sudo journalctl -b -p warning
```

`systemctl status`는 최근 로그 일부와 활성 상태, 주 PID, 종료 상태를 함께 보여 줄 수 있습니다. 그러나 “active (running)”은 애플리케이션의 업무 기능이 정상이라는 뜻이 아닙니다. 프로세스가 떠 있어도 데이터베이스 연결이 끊겼거나, 모든 요청이 500 오류를 반환하거나, 큐가 쌓일 수 있습니다. 프로세스 생존 확인, 포트·헬스 엔드포인트 확인, 핵심 의존성 확인, 사용자 관점의 기능 확인을 단계별로 구분합니다.

로그에 토큰, 비밀번호, 세션 쿠키, 고객 정보, 전체 요청 본문을 남기지 않는 것도 중요합니다. journal은 서버 관리자나 중앙 로그 수집 시스템에서 읽힐 수 있고, 보존 설정에 따라 오래 남을 수 있습니다. 디버깅을 위해 민감 값을 출력해야 한다는 요구가 생기면, 먼저 마스킹·샘플링·접근 권한·짧은 보존 기간으로 목적을 달성할 수 있는지 검토합니다. 로그는 편리한 진단 도구지만 별도의 데이터 저장소이기도 합니다.

## 재시작 정책은 복구와 폭주 사이의 균형이다

`Restart=on-failure`는 비정상 종료나 특정 실패 상황에서 서비스를 다시 시작하도록 합니다. 일시적인 네트워크 오류나 프로세스 충돌에서 회복하는 데 도움이 될 수 있습니다. 하지만 실행 직후 설정 오류로 종료되는 프로그램이라면, 재시작은 같은 오류를 빠르게 반복하며 로그와 CPU를 소비할 수 있습니다. systemd에는 시작 시도 횟수를 제한하는 설정이 있으며, 실제 환경에서는 서비스 특성과 알림 정책에 맞춰 검토해야 합니다.

재시작 간격 `RestartSec=`도 의미가 있습니다. 0초에 가까운 즉시 재시작은 빠르게 회복되는 것처럼 보이지만, 의존 시스템이 아직 복구되지 않았거나 잘못된 인증 요청이 반복되는 상황에서는 피해를 키울 수 있습니다. 반대로 너무 긴 간격은 장애 시간을 늘릴 수 있습니다. 재시작 횟수, 대기 시간, 실패 시 알림은 시스템의 RTO와 의존성 특성에 맞춰 정하며, 하나의 기본값을 모든 서비스에 복사하지 않습니다.

헬스 체크도 두 층으로 나눕니다. systemd는 프로세스의 실행 상태를 알 수 있지만, 애플리케이션 내부의 업무 준비 상태까지 자동으로 알지는 못합니다. 애플리케이션이 준비 상태와 라이브 상태를 구분해 노출할 수 있다면, 외부 모니터링은 실제 의존성 연결·필수 설정·핵심 기능의 가능 여부를 더 잘 판단할 수 있습니다. 단, 헬스 엔드포인트가 매 요청마다 무거운 데이터베이스 질의를 하면 모니터링 자체가 부하가 될 수 있으므로 가볍고 목적이 분명해야 합니다.

## 최소 권한으로 실행하기

`User=`와 `Group=`은 서비스 프로세스가 어느 운영체제 계정으로 실행될지 정합니다. 애플리케이션마다 전용 계정을 만들고 필요한 디렉터리·소켓·인증서에만 접근을 주면, 애플리케이션의 취약점이나 설정 실수가 시스템 전체 권한으로 확대되는 위험을 줄일 수 있습니다. 전용 계정은 로그인 셸이 필요 없을 수 있고, 배포 경로와 로그 경로의 소유권도 그 계정의 필요에 맞게 설계합니다.

systemd에는 파일 시스템과 프로세스 권한을 더 좁힐 수 있는 여러 실행 샌드박스 옵션이 있습니다. 예를 들어 `NoNewPrivileges=yes`는 실행 중 새 권한을 얻는 경로를 제한하려는 설정이고, `PrivateTmp=yes`는 서비스에 별도의 임시 디렉터리 뷰를 제공할 수 있습니다. `ProtectSystem=`, `ProtectHome=`, `ReadWritePaths=` 같은 옵션도 파일 시스템 접근을 줄이는 데 도움을 줄 수 있습니다. 그러나 옵션 이름만 복사하면 애플리케이션이 필요한 인증서·소켓·업로드 경로를 읽지 못해 장애가 날 수 있으므로, 테스트 환경에서 실제 접근 목록을 확인하며 단계적으로 강화합니다.

권한 경계는 unit 파일뿐 아니라 환경 파일에도 적용됩니다. `EnvironmentFile=`은 설정 값을 읽는 편리한 방법이지만, 그 파일의 소유자·권한·백업·배포 로그에 비밀이 노출되지 않는지 따져야 합니다. API 키와 데이터베이스 비밀번호를 일반 사용자가 읽는 파일에 두거나, 명령줄 인수로 넘겨 프로세스 목록에 보이게 하면 안 됩니다. 조직에서 비밀 관리 시스템을 사용한다면 서비스 시작 시 비밀을 전달하는 방식과 회전 시 재시작 절차를 함께 설계합니다.

## 소켓, 포트, 네트워크 문제를 구분하기

서비스가 시작 직후 종료되는 흔한 원인 중 하나는 포트 충돌입니다. 이미 다른 프로세스가 8080 포트를 쓰고 있으면 새 웹 서버는 바인드에 실패할 수 있습니다. 이때 systemd가 문제를 만든 것이 아니라 애플리케이션의 오류 로그와 운영체제 소켓 상태가 원인을 알려 줍니다. `ss -ltnp` 같은 도구로 어떤 주소와 포트를 누가 듣는지 확인하되, 운영 환경에서 무작정 기존 프로세스를 종료하기보다 서비스 소유자와 배포 상태를 먼저 확인합니다.

네트워크 의존성은 더 미묘합니다. DNS 이름이 해석되지 않는지, 방화벽이 막는지, 인증서가 만료됐는지, 원격 데이터베이스가 느린지 모두 애플리케이션에는 “연결 실패”로 보일 수 있습니다. unit의 `After=network-online.target`은 호스트의 네트워크 준비 순서에 도움을 주지만, 외부 서비스가 건강하다는 보증은 아닙니다. 애플리케이션에는 연결 타임아웃, 제한된 재시도, 명확한 오류 로그, 실패 시 안전한 동작이 필요합니다.

systemd의 **socket activation(소켓 활성화)** 은 systemd가 먼저 소켓을 열고, 연결이 올 때 서비스를 시작하거나 소켓을 전달하는 방식입니다. 일부 서비스에서는 필요할 때만 프로세스를 띄우고, 재시작 중에도 소켓 소유권을 관리하는 데 쓸 수 있습니다. 하지만 일반적인 웹 애플리케이션에 무조건 도입할 기본값은 아닙니다. 서비스가 이 방식을 지원하는지, 연결 지연과 운영 복잡성이 허용되는지를 보고 선택합니다.

## 타이머로 배치 작업을 관리할 때의 기준

매일 새벽 정산, 임시 파일 정리, 인증서 갱신처럼 주기적으로 실행하는 작업은 cron으로도 만들 수 있습니다. systemd의 `.timer` unit은 관련 `.service` unit과 함께 실행 일정·지연·누락 실행 처리·로그를 관리하는 선택지입니다. 예를 들어 `backup-report.timer`가 `backup-report.service`를 실행하게 하면, 서비스와 타이머의 상태를 `systemctl list-timers`와 journal에서 함께 볼 수 있습니다.

타이머가 cron보다 항상 낫다는 뜻은 아닙니다. 이미 안정적으로 운영되는 cron 작업을 이유 없이 옮기면 운영 표면만 넓어집니다. 반대로 서비스 unit과 같은 권한·로그·의존성을 공유해야 하거나, 부팅 중 놓친 실행을 어떻게 다룰지 선언적으로 관리하고 싶다면 타이머가 자연스러울 수 있습니다. 중요한 것은 스케줄 문법보다 중복 실행 방지, 실패 알림, 실행 시간 제한, 데이터 변경 작업의 멱등성입니다.

배치 작업도 `Type=oneshot`처럼 시작하고 끝나는 성격을 명확히 표현합니다. 작업이 10분 이상 걸릴 수 있다면 다음 실행이 겹쳤을 때 어떤 일이 생기는지 결정해야 합니다. 두 번 실행해도 안전한지, 잠금 파일이나 데이터베이스 락이 필요한지, 한 번 실패하면 다음 날까지 기다려도 되는지, 수동 재실행은 어떤 승인 아래 가능한지를 문서화합니다. 타이머는 실행을 예약할 뿐 업무 결과의 정합성을 보장하지 않습니다.

## 실무 예시: API 서비스 배포 뒤 확인 순서

가상의 주문 API를 새 버전으로 배포했다고 가정합니다. JAR 파일만 교체하고 `systemctl restart`를 실행한 뒤 화면에서 한 번 접속되는 것을 보고 끝내면, 재부팅 자동 시작·권한·환경 파일·로그가 모두 맞는지 알기 어렵습니다. 아래는 특정 제품의 절차가 아니라 일반적인 확인 순서입니다.

```text
1. 배포 파일의 버전과 소유권, 읽기·실행 권한을 확인한다.
2. unit과 환경 파일을 검토하고 민감 값이 명령줄이나 로그에 노출되지 않는지 확인한다.
3. unit을 바꿨다면 daemon-reload를 수행한다.
4. restart 뒤 systemctl status로 주 프로세스와 종료 상태를 확인한다.
5. journalctl로 시작 구간의 오류, 포트 바인드, 설정 로드 결과를 확인한다.
6. 헬스 엔드포인트와 핵심 의존성 연결을 정해진 기준으로 확인한다.
7. 배포 버전, 시각, 검증 결과, 롤백 조건을 기록한다.
```

이 순서에서 “프로세스가 떴다”와 “배포가 성공했다”는 다른 판단입니다. 예를 들어 환경 파일의 데이터베이스 주소가 비어 있으면 Java 프로세스는 살아 있어도 모든 주문 요청이 실패할 수 있습니다. 반대로 일시적으로 외부 연동이 느릴 때 재시작만 반복하면 원인 분석이 더 어려워질 수 있습니다. 배포 검증 기준을 상태·로그·의존성·업무 기능으로 나누면, 어떤 팀이 무엇을 확인해야 하는지 분명해집니다.

## 장애 대응에서 피해야 할 단축키

서비스가 이상하다고 무조건 `restart`부터 반복하는 습관은 원인을 가릴 수 있습니다. 재시작 전후의 로그와 종료 코드를 확보하지 않으면, 메모리 부족·권한 오류·인증 실패·포트 충돌을 모두 “일시적 오류”로 기록하게 됩니다. 물론 서비스가 완전히 멈춰 고객 영향이 큰 상황에서는 복구 행동이 먼저일 수 있습니다. 그때도 가능한 범위에서 시간, 명령, 상태, 로그 위치를 남기고, 복구 뒤 원인 분석으로 돌아와야 같은 장애를 반복하지 않습니다.

`sudo systemctl edit`로 만든 드롭인(drop-in) 설정과 패키지가 제공한 원본 unit, `/etc/systemd/system`의 사용자 정의 unit이 어디에 있는지 혼동하는 것도 위험합니다. 패키지 업데이트가 원본 파일을 바꿀 수 있고, 로컬 수정은 다음 담당자가 찾지 못할 수 있습니다. 가능한 한 배포 방식에 맞는 오버라이드 경로를 사용하고, 왜 필요한 변경인지 버전 관리 또는 운영 문서에 남깁니다. 운영 서버에서만 손으로 고친 설정은 다음 배포나 장애 때 사라질 수 있습니다.

마지막으로 systemd 로그를 보기 위해 애플리케이션 로그 설정을 모두 제거할 필요는 없습니다. systemd journal과 애플리케이션의 구조화 로그, 중앙 로그 수집은 서로 다른 목적을 가질 수 있습니다. 중요한 것은 같은 오류가 여러 장소에서 중복·누락되지 않게 상관관계 ID와 보존 정책을 정하는 것입니다. 도구를 줄이는 것보다 진단 경로를 명확히 하는 편이 운영에는 더 낫습니다.

## 리소스 제한과 종료 시간을 함께 설계하기

서비스가 다른 프로세스의 CPU와 메모리를 모두 차지하지 않도록 운영체제 수준의 경계를 두는 일도 필요합니다. systemd는 cgroup(control group, 프로세스 묶음의 자원 사용을 관리하는 커널 기능)을 활용해 서비스 단위로 자원을 추적하고 제한하는 기능과 연결됩니다. 예를 들어 메모리 누수가 의심되는 서비스에 한도를 검토할 수 있지만, 낮은 값을 임의로 지정하면 정상적인 부하에서도 종료될 수 있습니다. 제한값은 애플리케이션의 평소·피크 사용량, 노드 여유, 장애 격리 목표를 근거로 정하고, 적용 뒤 메트릭과 종료 이유를 확인해야 합니다.

종료 시간도 자원 관리와 연결됩니다. 새 배포나 서버 종료 때 systemd가 `SIGTERM`을 보낸 뒤 `TimeoutStopSec=`만큼 기다릴 수 있습니다. 이 시간 동안 애플리케이션은 새 요청을 받지 않고 진행 중 요청을 마치며, 데이터베이스 연결과 파일을 정리할 수 있습니다. 너무 짧으면 강제 종료가 늘고, 너무 길면 배포와 장애 복구가 지연됩니다. 로드 밸런서에서 트래픽을 먼저 빼는 절차, 애플리케이션의 graceful shutdown 지원 여부, 가장 긴 정상 요청 시간을 함께 고려합니다. 시간 초과를 크게 만드는 것만으로 안전한 종료가 보장되지는 않습니다.

자원 제한은 모니터링과 함께 읽어야 합니다. systemd가 서비스를 재시작했다는 사실만 보지 말고, 메모리 부족 종료인지 애플리케이션 예외인지, 요청 폭증인지 배포 직후 설정 문제인지 분류합니다. cgroup 단위의 사용량과 애플리케이션 메트릭, journal 로그, 호스트 전체 자원을 함께 보면 한 서비스의 문제와 노드 전체의 압박을 구분할 수 있습니다. 이 구분 없이 단순히 제한을 올리면 문제를 다른 서비스로 옮길 수 있습니다.

## unit 변경을 배포 변경으로 취급하기

unit 파일은 서버에서 실행되는 코드의 일부입니다. `ExecStart` 경로를 바꾸거나 `User=`를 수정하거나 환경 파일 위치를 옮기는 일은 애플리케이션 배포만큼 영향이 큽니다. 따라서 변경 내용을 리뷰 가능한 저장소나 구성 관리 도구에 남기고, 테스트·스테이징 환경에서 `systemd-analyze verify` 같은 검증 도구와 실제 시작 확인을 거친 뒤 운영에 적용하는 편이 좋습니다. 단일 문법 검사가 런타임 문제를 모두 잡지는 않지만, 오타와 잘못된 지시문을 더 이른 시점에 발견할 수 있습니다.

롤백 기준도 미리 정의합니다. 새 버전이 시작되지만 핵심 헬스 체크가 실패했을 때 어떤 버전으로 되돌릴지, 이전 환경 파일과 unit 정의가 준비돼 있는지, 재시작 전에 로그를 어떻게 보존할지 정합니다. 롤백은 "이전 파일을 다시 복사한다"는 말보다 더 넓습니다. 데이터베이스 마이그레이션, 비밀 회전, 프록시 설정, API 호환성처럼 되돌릴 수 없는 변경이 있는지 확인해야 합니다. systemd는 프로세스를 시작·중지해 주지만, 애플리케이션 배포의 호환성 판단까지 대신하지는 않습니다.

운영 문서에는 최소한 서비스 이름, 소유 팀, 실행 계정, 배포 경로, 설정과 비밀의 제공 경로, 정상 상태를 판단하는 지표, 첫 번째 확인 명령, 안전한 재시작 조건, 연락 경로를 남깁니다. 이런 정보는 긴 설명보다 장애 중 더 유용할 수 있습니다. 새로운 담당자가 `systemctl status` 결과를 보고 다음 행동을 결정할 수 있다면, unit 파일은 단순한 시작 스크립트가 아니라 재현 가능한 운영 계약이 됩니다.

변경 뒤에는 재부팅 상황도 한 번 생각합니다. 평상시에는 수동으로 시작한 서비스가 살아 있어도, 부팅 타깃 연결이나 의존성 순서가 잘못되면 유지보수 재부팅 뒤에만 문제가 나타날 수 있습니다. 실제 운영 재부팅을 가볍게 실행하라는 뜻은 아닙니다. 승인된 검증 환경에서 enable 상태와 시작 로그를 확인하고, 재부팅이 필요한 작업의 점검 창과 롤백 계획을 운영 절차에 포함하자는 뜻입니다. 부팅은 드물지만 systemd 설정의 중요한 실행 경로입니다.

## 마무리: 프로세스를 사람이 아니라 선언으로 운영하기

systemd의 가치는 `systemctl restart` 명령 하나에 있지 않습니다. 서비스가 어떤 사용자로, 어떤 파일과 네트워크 의존성을 가지고, 실패했을 때 어떻게 관찰·복구되고, 재부팅 뒤 어디에 연결되는지를 선언으로 남기는 데 있습니다. 이 선언은 배포 자동화, 보안 검토, 장애 인수인계의 공통 언어가 됩니다.

처음에는 작은 서비스 하나를 전용 계정과 명확한 unit으로 옮기고, `status`와 `journalctl`로 시작·실패 로그를 읽는 습관부터 만들면 충분합니다. 그다음 재시작 정책, 환경 파일 권한, 헬스 체크, 타이머, 샌드박스를 실제 위험과 필요에 맞게 추가합니다. 모든 옵션을 채우는 것이 목표가 아니라, 서비스의 실패 모드와 책임 경계를 다음 사람이 읽을 수 있게 만드는 것이 목표입니다.
