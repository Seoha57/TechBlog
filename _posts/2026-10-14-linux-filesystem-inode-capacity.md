서비스가 `No space left on device`를 내면 큰 파일부터 지우고 싶어집니다. 하지만 Linux의 저장 공간 문제는 파일 바이트 합계만 보는 문제가 아닙니다. 파일 내용을 저장하는 블록(block), 파일의 이름·권한·크기 같은 메타데이터를 담는 **inode(index node)**, 이름은 지워졌지만 프로세스가 계속 열고 있는 파일, 컨테이너 레이어와 로그가 서로 다른 방식으로 공간을 점유할 수 있습니다. 그래서 “지웠는데도 공간이 안 늘어난다” 또는 “사용률이 낮은데 새 파일을 못 만든다”는 상황이 생깁니다.

이 글의 목적은 급한 상황에서 무작정 삭제하는 방법이 아닙니다. 어떤 파일시스템이 막혔는지, 블록과 inode 중 무엇이 부족한지, 누가 파일을 열고 있는지, Docker나 Kubernetes가 어느 경로에 쓰고 있는지를 증거로 좁힌 뒤 안전하게 복구하는 흐름을 만드는 것입니다. 장애 중 로그·코어 덤프·감사 자료를 성급히 지우면 원인을 잃을 수 있으므로 삭제 전에는 보존 정책과 서비스 영향부터 확인해야 합니다.

## 먼저 알아둘 기반 기술

**파일시스템(filesystem)** 은 디스크 장치 위에서 파일과 디렉터리를 이름으로 다루게 해 주는 규칙과 자료구조입니다. ext4, XFS 같은 파일시스템은 파일 내용을 저장할 블록과 파일의 메타데이터를 저장할 inode를 관리합니다. 사용자는 `/var/log/app.log`라는 경로를 보지만, 커널은 디렉터리 항목으로 이름을 찾고 inode에서 소유자·권한·시간·데이터 블록 위치를 확인합니다. inode는 일반적으로 파일·디렉터리·심볼릭 링크마다 필요하므로, 파일이 아주 작아도 inode는 하나씩 소비됩니다.

**마운트(mount)** 는 특정 파일시스템을 디렉터리에 연결하는 일입니다. `/`, `/var`, `/home`, `/data`가 같은 서버에서 보이더라도 서로 다른 장치·논리 볼륨·네트워크 스토리지일 수 있습니다. 그래서 `/var`가 가득 찼을 때 `/home`의 여유 공간은 문제 해결에 직접 도움이 되지 않습니다. `df`는 마운트된 파일시스템 관점의 사용량을, `du`는 지정한 디렉터리 아래에서 보이는 파일 크기 합계를 보여 줍니다.

**파일 디스크립터(file descriptor)** 는 프로세스가 연 파일·소켓·파이프를 가리키는 번호입니다. 파일 이름을 `rm`으로 지워도 프로세스가 디스크립터를 닫기 전까지 실제 데이터 블록이 즉시 해제되지 않을 수 있습니다. 이름을 찾는 연결(link)은 사라졌지만 실행 중인 프로세스가 내용을 참조하기 때문입니다. 삭제와 공간 회수가 항상 같은 시점에 일어난다고 가정하면 진단을 잘못할 수 있습니다.

## 먼저 확인할 것은 어느 파일시스템이 막혔는가다

오류 메시지 하나만 보고 서버 전체를 청소하지 말고, 오류가 난 경로가 어느 마운트에 속하는지부터 확인합니다. 다음 명령은 읽기 전용 진단 용도입니다.

```bash
df -hT
df -i
findmnt -T /var/log/my-service
du -xhd1 /var/log 2>/dev/null | sort -h
```

`df -hT`는 사람이 읽기 쉬운 단위와 파일시스템 종류를, `df -i`는 inode 사용량을 보여 줍니다. `findmnt -T`는 특정 경로가 실제로 어느 마운트에 속하는지 확인합니다. `du -x`의 `-x`는 다른 파일시스템 경계를 넘지 않도록 하므로 분석 대상이 `/var`일 때 별도 마운트된 영역까지 섞여 혼동되는 일을 줄입니다. 권한 오류를 숨기기 위해 무조건 높은 권한으로 실행하기보다 필요한 권한과 실행 주체를 런북에 명확히 하는 편이 안전합니다.

확인할 때는 수치만 캡처하지 말고 시간도 함께 기록합니다. 80% 사용률 자체보다 10분 사이에 20GB가 증가한 사실이 더 중요한 경우가 많습니다. 오류가 난 서비스, 배포·배치·백업 같은 직전 변경, 마운트별 사용량과 inode 사용량을 한 묶음으로 기록하면 다른 담당자도 같은 가설에서 출발할 수 있습니다.

## 블록 고갈과 inode 고갈은 다른 장애다

블록 사용량이 100%라면 큰 로그, 백업, 덤프, 이미지 레이어, 임시 파일처럼 바이트가 큰 대상이 흔한 원인입니다. 반면 inode가 100%라면 수 바이트짜리 파일이라도 새로 만들 수 없습니다. 메일 큐, 세션 파일, 캐시 키, 잘게 쪼갠 업로드, 빌드 산출물처럼 아주 많은 작은 파일이 문제를 만들 수 있습니다.

예를 들어 배치 프로그램이 실패한 요청마다 빈 재시도 파일을 남기고 이를 수백만 개 쌓으면 바이트 사용량은 작아도 inode가 먼저 소진됩니다. 이 경우 큰 파일 하나를 지워도 새 파일 생성 실패가 계속됩니다. 원인 디렉터리의 파일 수 증가율, 생성 주체, 보존 기간을 확인하고 재발 방지 규칙을 수정해야 합니다. 파일시스템마다 inode 할당 방식과 조정 가능 범위가 다르므로, 사고 순간에는 안전한 정리와 서비스 복구에 집중하고 사후에는 파일 수 예측·파티션 설계·보존 정책을 검토합니다.

작은 파일 문제는 디렉터리 하나가 수십만 개 엔트리를 품을 때 검색·백업·삭제 시간까지 늘릴 수 있습니다. 날짜나 고객 단위의 하위 디렉터리로 분산하는 것, 오래된 세션을 TTL(Time To Live) 정책으로 제거하는 것, 파일 대신 적절한 저장소나 큐를 쓰는 것은 용량뿐 아니라 운영 작업 시간도 줄입니다. 하지만 구조 변경은 응용 프로그램의 동시성·권한·복구 방식에 영향을 주므로 장애 중 임시 처방과 장기 설계를 구분해야 합니다.

## df와 du가 맞지 않을 때: 삭제됐지만 열린 파일

애플리케이션 로그를 지웠는데 `df`가 줄지 않는다면 삭제 파일을 프로세스가 열어 둔 경우를 의심합니다. `lsof`는 열린 파일을 나열하는 도구이며, `+L1`은 이름이 사라진 열린 파일을 찾는 데 사용할 수 있습니다.

```bash
sudo lsof +L1
sudo lsof +L1 /var
```

출력에는 프로세스 이름, PID, 열린 파일 크기, `(deleted)` 표시가 나타날 수 있습니다. 여기서 곧바로 PID를 종료하는 것은 정답이 아닙니다. 결제·DB·배치 작업을 강제 종료하면 데이터 일관성이 깨질 수 있습니다. 서비스의 graceful restart 지원 여부, 작업 진행 상태, 장애 조치 절차를 확인하고 안전한 재시작이 가능할 때 파일 디스크립터를 닫습니다.

로그 회전도 함께 점검합니다. `logrotate`가 rename 뒤 애플리케이션에 재열기 신호를 보내는 방식인지, 애플리케이션이 자체 롤링을 하는지 확인해야 합니다. 회전 파일을 지웠다는 사실보다 프로세스가 새 파일로 전환했는지가 핵심입니다. 삭제된 열린 파일은 복구 조치와 동시에 “왜 파일이 닫히지 않았는가”라는 원인 분석 항목으로 남겨야 합니다.

`df`와 `du`의 차이는 열린 파일만으로 설명되지 않습니다. 분석한 경로가 다른 마운트에 걸쳐 있거나, 권한 때문에 일부 디렉터리를 읽지 못했거나, bind mount와 컨테이너 네임스페이스 때문에 같은 저장소가 다른 위치에서 보일 수도 있습니다. 그래서 한 명령 결과만 믿지 말고 오류 경로를 기준으로 마운트 표와 프로세스·컨테이너 정보를 교차 확인해야 합니다.

## 컨테이너 환경에서는 레이어·볼륨·로그를 분리한다

Docker의 OverlayFS는 여러 이미지 레이어를 하나의 디렉터리처럼 보이게 하는 union filesystem입니다. 이미지의 읽기 전용 lower layer와 컨테이너가 쓰는 upper layer를 합쳐 보며, 수정 시 copy-on-write가 발생합니다. 그래서 컨테이너 내부에 임시 파일·캐시·로그를 많이 쓰면 writable layer가 예상보다 커질 수 있습니다. 공유 이미지 레이어가 효율적이더라도 애플리케이션의 쓰기 패턴이 사라지는 것은 아닙니다.

```bash
docker system df
docker info --format '{{.Driver}}'
docker ps --size
```

`docker system df`는 이미지·컨테이너·로컬 볼륨·빌드 캐시의 사용량을 구분해 보여 줍니다. 볼륨은 데이터베이스·업로드 데이터를 담을 수 있으므로 “미사용” 결과만 보고 자동 삭제하지 말고 소유 서비스와 백업 상태를 확인해야 합니다. Docker 문서도 `/var/lib/docker/overlay2` 같은 내부 경로를 직접 조작하지 말라고 안내합니다. Docker Engine 버전과 설치 방식에 따라 containerd image store나 snapshotter가 쓰일 수 있으므로, 경로를 가정하기보다 `docker info`로 현재 드라이버와 데이터 루트를 확인합니다.

컨테이너 로그도 주요 원인입니다. 표준 출력 로그 수집, 로그 드라이버의 회전 정책, 애플리케이션 내부 파일 로그가 중복되어 있으면 같은 내용이 여러 위치에 남을 수 있습니다. 로그를 줄이는 것은 단순히 보존 기간을 짧게 만드는 문제가 아니라, 장애 분석·감사·개인정보 마스킹 요구와 균형을 맞추는 일입니다. 서비스별 로그 종류, 최대 크기, 보관 기간, 외부 전송 성공 여부를 문서화해야 합니다.

Kubernetes에서는 컨테이너 writable layer, 로그, `emptyDir` 같은 임시 볼륨이 노드의 **ephemeral storage(일시 저장소)** 를 소비합니다. Pod의 메모리 제한만 보고 디스크를 잊으면 노드 압박과 eviction이 발생할 수 있습니다. 애플리케이션 로그를 표준 출력으로 보낼지, 파일 로그를 쓸지, 캐시를 어디에 둘지를 배포 방식과 함께 결정해야 합니다. 하나의 Pod가 노드 전체의 디스크를 밀어내지 않도록 요청·제한과 노드 모니터링을 함께 설계합니다.

## 사고 대응 흐름: 지우기 전에 증거를 좁힌다

첫째, 오류 발생 시각과 실패한 경로를 기록합니다. 둘째, `df -hT`, `df -i`, `findmnt -T`로 문제의 마운트·블록·inode를 구분합니다. 셋째, `du -xhd1`로 보이는 큰 디렉터리를 찾고, 필요하면 서비스별 로그·백업·임시 작업 경로를 세분화합니다. 넷째, `df`와 `du`가 다르면 `lsof +L1`으로 열린 삭제 파일을 조사합니다. 다섯째, 컨테이너 호스트면 Docker 또는 Kubernetes가 차지한 영역을 별도로 확인합니다.

여섯째, 조치 후보마다 데이터 손실·서비스 중단·보안 감사 영향·복구 가능성을 적습니다. 예를 들어 오래된 압축 로그는 보존 기한과 백업 완료를 확인하고 삭제할 수 있지만, 최신 오류 로그와 코어 덤프는 원인 분석이 끝나기 전 보관해야 합니다. 일곱째, 조치 후 같은 명령으로 사용량 변화와 서비스 쓰기 성공을 다시 확인합니다. 공간이 돌아왔다고 끝내지 말고 어떤 파일이 어떤 속도로 다시 늘어나는지 관찰해야 재발을 막을 수 있습니다.

장애 중에는 “무엇을 하지 않을지”도 중요합니다. 광범위한 재귀 삭제, Docker 내부 디렉터리 직접 수정, 살아 있는 데이터 파일의 이동, 근거 없는 서비스 강제 종료는 빠른 공간 확보처럼 보여도 복구 비용을 키울 수 있습니다. 실제 삭제가 필요하다면 정확한 대상, 보존 근거, 백업 상태, 승인자, 예상 회수량을 확인하고 되돌릴 수 없는 조치임을 기록합니다.

## 모니터링과 런북: 사용률 하나로 끝내지 않는다

용량 알림은 블록 사용률, inode 사용률, 증가 속도, 남은 예상 시간으로 나누면 더 유용합니다. 90%라는 한 숫자는 대용량 디스크와 작은 파티션에 다른 의미를 갖습니다. 짧은 시간에 급증하는 로그는 70%여도 위험할 수 있고, 오랫동안 92%지만 증가하지 않는 아카이브는 계획된 확장으로 다룰 수 있습니다. 마운트별로 책임 서비스와 소유 팀을 연결하면 알림을 받은 사람이 어디부터 볼지 빠르게 판단할 수 있습니다.

삭제된 열린 파일, 컨테이너 writable layer 증가, inode 급증은 일반적인 `disk_used_percent` 하나로는 구분되지 않습니다. 각 환경에서 수집 가능한 지표와 진단 명령 결과를 런북에 적고 실제 장애 때 승인·백업·재시작 순서를 확인하도록 합니다. 자동 정리는 편리하지만 대상이 잘못되면 데이터 삭제가 되므로, 파괴적 조치는 보존 기간·라벨·소유권·dry-run을 포함한 별도 절차로 제한하는 편이 낫습니다.

정기적인 점검에서는 백업이 실제로 다른 저장소에 복사됐는지, 로그 회전 뒤 열린 파일이 남지 않는지, 컨테이너 이미지와 빌드 캐시 증가가 예상 범위인지 확인합니다. 이 점검은 운영 경험을 과장하려는 것이 아니라, 장애가 나기 전에 가설을 줄이기 위한 기본 예방 작업입니다.

## 재발 방지는 용량 확장만으로 끝나지 않는다

용량을 늘리는 것은 유효한 복구 수단이지만, 증가 원인을 설명하지 못하면 문제의 시간을 늦추는 데 그칠 수 있습니다. 서비스별로 어떤 데이터가 어느 마운트에 쌓이는지, 정상적인 하루 증가량은 얼마인지, 보존 기간 이후 누가 정리하는지, 백업이 별도 위치에 있는지를 연결해 봐야 합니다. 예를 들어 하루 한 번 생성되는 보고서가 30일만 보관돼야 한다면, 생성 위치·파일명·삭제 기준·백업 성공 확인을 함께 설계해야 합니다. 단순 cron 삭제는 실패한 업로드나 법적 보존 대상까지 지울 수 있으므로 대상 조건과 확인 로그가 필요합니다.

용량 계획에는 복구 시간도 포함됩니다. 95%가 된 뒤 사람의 판단과 승인, 백업 확인, 안전한 재시작이 필요하다면 경고는 그보다 충분히 앞서 와야 합니다. 디스크를 확장할 수 있는 환경인지, 확장 뒤 파일시스템을 온라인으로 늘릴 수 있는지, 재시작이나 장애 조치가 필요한지에 따라 대응 시간은 달라집니다. 인프라 담당자만 아는 절차가 아니라 서비스 담당자와 공유된 실행 순서가 있어야 야간 장애에서도 위험한 지름길을 피할 수 있습니다.

테스트 환경도 예외가 아닙니다. CI의 작업 공간, 테스트 데이터, 컨테이너 이미지와 캐시는 운영 서버보다 짧은 수명으로 보이지만, 실패한 파이프라인과 병렬 실행이 쌓이면 먼저 가득 찰 수 있습니다. 테스트 실패의 원인이 코드인지 공간 부족인지 구분할 수 있도록, 러너의 디스크와 inode 지표를 별도로 관찰하고 정리 정책을 테스트 산출물 보존 정책과 함께 관리해야 합니다.

## 용량 문제를 서비스 설계로 되돌려 보기

저장소가 반복해서 가득 찬다면 운영자가 정리하지 못해서가 아니라 애플리케이션이 데이터 수명 주기를 명확히 표현하지 못한 것일 수 있습니다. 파일을 만들 때 누가 소유하는지, 언제 읽기가 끝나는지, 어디로 이전되는지, 어떤 실패 경로에서 남는지, 언제 안전하게 삭제할 수 있는지를 서비스 설계에서 정해야 합니다. 예를 들어 사용자가 올린 파일은 DB 레코드와 객체 저장소의 실제 객체가 함께 생성·삭제되어야 하며, 둘 중 하나만 남는 고아 데이터의 탐지와 정리 책임도 있어야 합니다.

캐시는 더 짧은 수명을 가져야 합니다. 캐시 키와 파일이 영구 데이터처럼 쌓이면 ‘임시’라는 이름만으로는 공간을 보호하지 못합니다. 최대 크기, TTL, 접근 빈도, 삭제 실패 시 행동을 명시하고 실제 정리가 실행되는지 관찰해야 합니다. 백업도 마찬가지입니다. 백업의 목적은 복구 가능성이지 같은 마운트에 복사본을 무한히 쌓는 일이 아닙니다. 원격 보관 완료와 복구 시험, 로컬 보존 개수를 연결해야 합니다.

개발·운영 환경이 다를 때는 경로와 권한, 컨테이너 런타임, 로그 수집 방식의 차이도 기록합니다. 개발 환경에서만 잘 지워지는 파일이 운영에서는 권한이나 열린 핸들 때문에 남을 수 있습니다. 반대로 운영의 대용량 데이터와 긴 실행 시간은 로컬에서 재현되지 않을 수 있습니다. 이 차이를 인지하고 작은 실험 환경에서 용량 경보와 회전·재시작 절차를 점검하면 실제 장애에서 불필요한 파괴 조치를 줄일 수 있습니다.

용량 장애 대응은 DBMS, 네트워크, 애플리케이션, 보안 담당자의 협력이 필요한 경우가 있습니다. 디스크가 찼다는 결과는 하나지만 원인은 과도한 요청, 실패한 배치 재시도, 로그 레벨 변경, 백업 전송 실패, 컨테이너 배포 정책 등 여러 계층에 있을 수 있습니다. 따라서 최종 보고에는 삭제한 파일의 목록뿐 아니라 증가를 만든 변경과 방지 조치를 남겨야 합니다. 그래야 다음 알림이 왔을 때 같은 디렉터리를 다시 지우는 대신 원인을 먼저 확인할 수 있습니다.

## 예비 공간과 복구 여유를 남긴다

파일시스템은 100%가 되기 전에 운영 여유를 가져야 합니다. 공간이 부족해지면 로그 기록, 임시 파일 생성, 배포 롤백, DB 복구 같은 정상적인 보호 동작도 실패할 수 있습니다. 서비스별로 최소 여유 공간을 정하고, 그 선을 넘기기 전에 증설·보관 이전·생성량 감소 중 어떤 조치를 할지 정합니다. 단순히 최대 용량을 크게 잡는 것보다, 여유가 줄어드는 이유와 대응 책임자를 정하는 것이 중요합니다.

장애가 끝난 뒤에는 실제 회수량과 복구 시간을 되짚습니다. 예상보다 적은 공간이 풀렸다면 열린 파일·다른 마운트·스냅샷·컨테이너 레이어 같은 가설을 다시 검증합니다. 이 학습을 런북에 반영해야 같은 증상이 다음번에는 더 짧은 진단으로 이어집니다.

용량 회복 뒤에는 단순히 알림을 닫지 말고, 같은 마운트에서 파일 생성과 로그 기록, 컨테이너 동작이 정상으로 돌아왔는지 확인합니다. 회수한 공간이 다음 배치나 로그 폭증에 다시 소진되지 않는지 초기 추세도 관찰해야 합니다.

사후 기록에는 명령의 출력뿐 아니라 그 출력으로 어떤 판단을 했는지와, 다음번에는 어느 시점에 알림을 보낼지를 남깁니다. 그래야 숫자를 보는 사람이 바뀌어도 대응 품질이 유지됩니다.

가장 중요한 것은 공간을 확보했다는 결과보다, 다음에도 같은 원인을 같은 순서로 확인할 수 있는 대응 기준을 남기는 일입니다. 마운트와 파일시스템, 블록과 inode, 열린 파일과 컨테이너 저장소를 분리해 보는 습관은 작은 개발 서버와 대규모 운영 환경 모두에서 유효합니다.

## 한계와 적용 기준 Q&A

### Q. du에서 큰 디렉터리를 찾았으니 바로 지워도 되나요?

A. 아닙니다. 로그·백업·업로드·데이터 파일 중 무엇인지와 보존·복구 요구를 먼저 확인해야 합니다. 특히 DB 데이터 경로, Docker 관리 경로, 코어 덤프는 임의 삭제가 더 큰 장애를 만들 수 있습니다.

### Q. inode가 부족하면 큰 디스크를 추가하면 해결되나요?

A. 새 디스크가 실제로 문제 마운트를 대체하거나 확장하고 적절한 inode 정책을 가진 경우에만 도움이 됩니다. 작은 파일을 무한히 만드는 원인을 고치지 않으면 새 공간도 같은 방식으로 소진됩니다.

### Q. 삭제된 열린 파일은 파일을 다시 만들면 공간이 풀리나요?

A. 아닙니다. 기존 파일을 열고 있는 프로세스가 디스크립터를 닫아야 합니다. 안전한 재열기·재시작·장애 조치 계획을 확인한 뒤 처리합니다.

### Q. 컨테이너를 쓰면 호스트 디스크 관리는 필요 없나요?

A. 필요합니다. 컨테이너의 쓰기 레이어, 이미지, 볼륨, 로그는 결국 호스트 또는 원격 스토리지를 소비합니다. 논리적 격리가 물리적 용량 책임을 없애지는 않습니다.

### Q. 디스크 알림 임계값을 높이면 오탐을 줄일 수 있지 않나요?

A. 임계값 하나를 높이는 방식은 급격한 증가와 inode 고갈을 놓칠 수 있습니다. 사용률·증가 속도·파일 수와 함께 서비스별 복구 시간을 고려해 알림을 설계하는 편이 낫습니다.

## 마무리

Linux 용량 장애는 “파일을 많이 지운다”가 아니라 “어떤 파일시스템의 어떤 자원이 왜 줄었는가”를 확인하는 문제입니다. 블록과 inode를 함께 보고, `df`와 `du`의 관점 차이를 이해하며, 삭제됐지만 열린 파일과 컨테이너 저장소를 별도 축으로 조사하면 복구 속도와 안전성을 함께 높일 수 있습니다.

오늘의 조치 결과를 마운트·원인·영향·복구·재발 방지로 기록해 두세요. 장애 대응의 목표는 여유 공간을 잠시 만드는 데 그치지 않고, 다음 담당자가 추측 대신 증거로 시작할 수 있게 하는 것입니다. 용량은 인프라의 뒷부분에 있는 숫자가 아니라 애플리케이션의 쓰기, 배포, 관측, 백업 정책이 만나는 운영 계약입니다.

## 파일시스템별 운영 경계를 이해한다

ext4와 XFS처럼 널리 쓰이는 파일시스템도 공간을 보고하는 방식과 inode 관리 방식, 예약 영역, 스냅샷·볼륨 도구와의 결합이 다를 수 있습니다. 따라서 다른 서버에서 본 명령 결과를 그대로 해석하지 말고, 현재 마운트의 파일시스템 종류와 스토리지 계층을 확인해야 합니다. LVM(Logical Volume Manager), 클라우드 블록 스토리지, 네트워크 파일시스템, 암호화 계층이 중간에 있으면 확장·스냅샷·복구의 책임 경계도 달라집니다.

특히 데이터베이스나 메시지 브로커가 쓰는 마운트는 단순한 로그 디렉터리와 같은 방식으로 정리하면 안 됩니다. 쓰기 중인 데이터 파일과 WAL·redo·archive 로그, 백업 산출물은 서로 다른 보존과 복구 절차를 가집니다. 용량이 급하다는 이유로 데이터 디렉터리를 직접 만지는 대신, 제품별 관리 명령과 담당자 승인 절차를 따르는 것이 원칙입니다. 디스크 용량 장애는 스토리지 문제가 될 수 있지만, 그 조치가 데이터 정합성 문제로 바뀌어서는 안 됩니다.

예약 블록이나 권한, quota(할당량)도 사용자가 보는 여유 공간과 실제 쓰기 가능 공간을 다르게 만들 수 있습니다. 특정 서비스 계정에만 파일 생성 실패가 발생한다면 전체 `df` 결과뿐 아니라 사용자·프로젝트 단위 제한과 디렉터리 권한을 함께 봐야 합니다. 전체 서버를 재부팅하거나 파일시스템을 재마운트하는 방식은 이 원인을 해결하지 못할 수 있습니다.

## 로그 설계가 용량 장애를 줄이는 방식

로그는 장애 진단에 필요하지만 제한 없이 쌓이면 다음 장애의 원인이 됩니다. 애플리케이션은 구조화된 로그에 요청 ID, 오류 코드, 필요한 업무 식별자만 남기고, 민감 정보는 마스킹해야 합니다. 운영 환경에서는 로그 레벨을 상황에 따라 조정할 수 있어야 하며, 디버그 로그를 장기간 켠 채로 두지 않도록 만료 기준을 둡니다. 같은 예외가 초당 수천 번 반복되는 경우에는 샘플링이나 집계도 고려합니다.

회전 정책에는 최대 크기, 기간, 압축, 보관 개수, 외부 수집 성공 후 삭제 조건이 포함됩니다. 이 값은 모든 서비스에 하나로 맞추기보다 오류 분석 기간과 트래픽, 규제 요구, 저장 비용에 따라 정합니다. 회전이 동작하는지 확인할 때는 파일 이름만 보지 말고 프로세스가 새 파일 핸들로 바뀌었는지, 수집기가 회전 전 파일을 놓치지 않는지, 압축이 CPU와 I/O를 과도하게 쓰지 않는지도 확인합니다.

배치 작업의 임시 파일도 같은 관점이 필요합니다. 성공·실패·중단 어느 경로에서 정리되는지, 동시 실행 시 파일 이름이 충돌하지 않는지, 오래 실행된 작업이 남긴 잔여 파일을 누가 판단하는지 정해야 합니다. 임시 파일을 삭제하는 코드가 있다고 해서 항상 정리되는 것은 아닙니다. 강제 종료, 권한 변경, 네트워크 오류, 재배포가 정리 경로를 건너뛸 수 있다는 전제로 보존 기간과 주기 점검을 설계합니다.

## 컨테이너 이미지와 빌드 캐시의 책임

컨테이너 이미지는 재현 가능한 배포에 도움이 되지만, 태그만 보고 같은 이미지라고 생각하면 위험합니다. 오래된 태그, 중간 빌드 단계, 실패한 CI 산출물, 사용하지 않는 레이어가 호스트에 남아 용량을 누적시킬 수 있습니다. 빌드 캐시를 무조건 지우면 다음 빌드가 느려지고 네트워크 사용량이 늘 수 있으므로, 개발 머신·CI 러너·운영 노드의 보존 정책을 분리하는 것이 좋습니다.

운영 노드에서 이미지를 정리할 때는 현재 실행 중인 컨테이너와 롤백 가능한 이전 배포가 의존하는 이미지를 먼저 파악합니다. 배포 도구가 오래된 이미지를 참조할 수 있는 기간, 장애 시 얼마나 빠르게 이전 버전으로 돌아가야 하는지, 이미지 레지스트리에서 재다운로드 가능한지를 기준으로 정리 범위를 정합니다. 용량 회수와 배포 회복력은 같은 결정을 공유합니다.

## 런북 예시: 질문과 증거를 연결한다

런북에는 단순한 명령 목록보다 질문의 순서를 적는 편이 좋습니다. ‘어느 경로에서 오류가 났는가’, ‘그 경로의 마운트는 무엇인가’, ‘블록과 inode 중 무엇이 가득 찼는가’, ‘보이는 파일인가 열린 삭제 파일인가’, ‘컨테이너·로그·백업 중 어느 책임 영역인가’, ‘삭제 전에 보존해야 하는가’라는 순서입니다. 각 질문의 답을 어디서 확인하고, 답에 따라 누구에게 연결할지를 같이 적습니다.

예를 들어 새 파일 생성 실패가 inode 고갈로 확인되면, 큰 파일을 찾아 지우라는 절차가 아니라 파일 수가 급증한 디렉터리·서비스를 찾는 절차로 분기해야 합니다. 열린 삭제 파일이면 삭제 명령이 아니라 안전한 로그 재열기·서비스 재시작 절차로 분기합니다. Docker 용량이면 내부 경로 삭제가 아니라 Docker CLI와 배포 소유자를 확인하는 절차로 분기합니다. 이런 분기는 자동화보다 먼저 사고를 줄이는 안전장치입니다.

용량 진단의 결과를 팀이 공유할 때는 사용률 그래프만 남기지 말고, 실제 장애를 만든 파일 종류와 생성 경로, 프로세스·배포·백업과의 연결을 함께 남깁니다. 이 정보가 있어야 다음 증설 요청과 로그 정책, 컨테이너 운영 기준이 같은 문제를 반복하지 않도록 바뀔 수 있습니다.
