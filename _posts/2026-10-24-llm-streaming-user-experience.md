LLM 기반 채팅에서 답변이 한 글자씩 나타나는 화면은 익숙합니다. 많은 구현이 “서버에서 받은 토큰을 화면에 붙인다”로 시작하지만, 실제 제품에서는 그보다 많은 결정이 필요합니다. 사용자가 기다린 시간은 얼마나 표시할지, 취소 버튼을 누르면 서버 작업도 멈추는지, 연결이 끊기면 부분 답변을 보존할지, 모델이 안전 정책 때문에 완료하지 못하면 무엇을 보여 줄지, 같은 질문을 다시 보내도 되는지를 정해야 합니다.

스트리밍은 장식이 아니라 지연 시간을 관리하는 인터페이스입니다. 이 글은 LLM 생성이 왜 기다림을 만들고, SSE(Server-Sent Events) 같은 전송 방식이 어떤 역할을 하며, 사용자에게 신뢰할 수 있는 진행 상태를 제공하려면 무엇을 분리해야 하는지 설명합니다.

## 먼저 알아둘 기반 기술

LLM은 보통 답 전체를 한 번에 만드는 대신 토큰이라는 작은 단위로 다음 값을 예측하며 생성합니다. 요청을 받은 뒤 모델이 입력을 읽고 준비하는 시간, 첫 토큰을 내기까지의 시간, 이후 토큰을 계속 생성하는 시간이 있습니다. TTFT(Time To First Token)는 사용자가 첫 응답을 보는 데 걸린 시간을 가리키고, 생성 속도는 이후 초당 생성되는 토큰 수와 관계가 있습니다. 긴 답변에서 전체 완료 시간이 같아도 TTFT가 짧으면 사용자는 시스템이 반응한다고 느낄 수 있습니다.

HTTP의 일반 요청·응답은 서버가 결과를 모두 만든 뒤 한 번에 돌려주는 방식입니다. SSE는 서버가 하나의 HTTP 연결을 유지하면서 텍스트 이벤트를 순서대로 보낼 수 있게 하는 웹 표준입니다. 브라우저는 이벤트를 받는 즉시 화면을 업데이트할 수 있습니다. WebSocket도 양방향 통신에 쓸 수 있지만, 서버에서 클라이언트로 순차 결과를 보내는 단순한 요구에는 SSE가 구현과 운영 면에서 충분한 경우가 많습니다. 선택은 제품의 양방향 제어, 인프라 프록시 지원, 재연결 정책에 따라 달라집니다.

## 스트리밍 프로토콜에서 필요한 이벤트

좋은 스트리밍 API는 문자열 조각만 보내지 않습니다. 최소한 요청 식별자, 텍스트 delta, 완료 상태, 오류 상태를 구분할 수 있어야 합니다. 도구 호출이나 인용, 사용량, 안전 검사 결과가 있는 제품이라면 그것도 별도 이벤트로 보냅니다. 클라이언트가 모든 이벤트를 일반 텍스트로 합치면, 완료 전에는 출처가 없는 문장을 확정 답으로 보여 주거나 도구 실행 중인 내용을 사용자 답변으로 착각할 수 있습니다.

예를 들어 `message.delta`, `message.completed`, `message.error` 같은 이벤트 타입을 두면 UI는 delta를 임시 버퍼에 쌓고, completed를 받아야 최종 답변 상태로 전환할 수 있습니다. error가 오면 부분 응답을 지울지, “연결이 끊겨 답변이 완료되지 않았습니다”라고 표시할지 제품 정책을 적용합니다. 이 구분은 나중에 대화 저장, 평가 로그, 피드백 수집에서도 중요합니다. 완료되지 않은 답변을 정상 답변처럼 저장하면 사용자는 다음 대화에서 불완전한 문맥을 보게 됩니다.

```text
event: message.delta
data: {"request_id":"r-42","text":"리소스 request는"}

event: message.completed
data: {"request_id":"r-42","finish_reason":"stop"}
```

## 취소는 화면만 멈추는 기능이 아니다

사용자가 Stop 버튼을 누른 상황을 생각해 보세요. 화면 렌더링만 멈추고 서버의 LLM 요청을 계속 두면 비용과 시스템 자원을 쓰고, 도구 호출이 계속 실행될 수 있습니다. 가능한 경우 클라이언트 연결 종료 또는 명시적 취소 요청을 서버가 감지하고, 서버는 모델 호출과 하위 작업의 cancellation signal을 전달해야 합니다. 이미 완료된 외부 작업을 되돌릴 수 없는 경우도 있으므로, 취소는 “아무 일도 없었다”가 아니라 현재까지 어떤 작업이 시작됐는지 명확히 보여 주는 설계가 필요합니다.

취소된 응답은 실패와 다릅니다. 사용자가 충분히 읽고 중단했을 수 있고, 질문을 바꾸려 했을 수 있습니다. UI는 부분 답변을 남기되 ‘중단됨’ 상태를 표시하고, 복사와 재생성의 의미를 분리할 수 있습니다. 서버 로그도 사용자의 취소, 네트워크 단절, 시간 제한, 공급자 오류를 서로 다른 종료 사유로 기록해야 지연과 비용 문제를 올바르게 분석할 수 있습니다.

## 마크다운과 부분 렌더링의 함정

LLM은 표, 코드 블록, 링크, 목록처럼 마크다운을 생성할 수 있습니다. 토큰 단위로 렌더링하면 아직 닫히지 않은 코드 펜스나 링크가 순간적으로 깨진 HTML을 만들 수 있습니다. 특히 HTML을 허용하는 마크다운 렌더러는 XSS(Cross-Site Scripting) 위험을 만들 수 있으므로 사용자에게 보여 주는 HTML을 신뢰해서는 안 됩니다. 스트리밍 중에는 평문 또는 안전하게 sanitize된 제한된 렌더링을 쓰고, completed 뒤에 최종 마크다운을 파싱하는 전략을 고려할 수 있습니다.

코드 블록이 길면 화면이 매 토큰마다 재배치되어 스크롤이 흔들릴 수 있습니다. 일정 시간 또는 일정 글자 단위로 화면을 갱신하는 buffering은 렌더링 비용을 줄입니다. 이것은 모델 생성 속도와 별개의 클라이언트 성능 문제입니다. 사용자가 이전 메시지를 읽고 있을 때 자동 스크롤을 강제하지 않고, 최신 위치에 있을 때만 따라가도록 하는 것도 채팅 UX에서 중요합니다.

## 구체적 업무 예시: 사내 문서 도우미

사내 문서 RAG 도우미가 “휴가 규정에서 병가 증빙은 무엇인가?”라는 질문을 받는다고 가정해 보겠습니다. 서버는 먼저 권한 필터를 적용해 문서 조각을 검색하고, LLM에 근거와 질문을 전달합니다. 스트리밍 화면은 바로 문장 일부를 보여 줄 수 있지만, 출처는 검색이 끝난 뒤 별도 이벤트로 보내거나 완료 메시지와 함께 표시해야 합니다. 출처가 오기 전의 답변은 확정 규정처럼 보이지 않게 ‘답변 생성 중’ 상태로 둘 수 있습니다.

만약 검색 결과가 없으면 모델이 일반 지식으로 추측하게 두기보다, `no_context` 같은 완료 사유를 보내고 “현재 권한으로 확인 가능한 규정이 없습니다”라고 말하는 편이 안전합니다. 공급자 timeout이 발생했다면 사용자가 다시 시도할 수 있게 하되, 이미 생성된 반 문장을 공식 답변으로 저장하지 않습니다. 사용자가 Stop을 누르면 서버가 모델 요청을 취소하고, UI는 부분 답변에 중단 표시를 남깁니다. 이 흐름은 단순한 타이핑 효과보다 사용자의 신뢰와 비용 통제에 직접 영향을 줍니다.

## 관찰해야 할 지표

스트리밍 시스템은 평균 응답 시간 하나만 보면 부족합니다. TTFT, 전체 완료 시간, 초당 출력 토큰, 취소율, 연결 단절률, 오류 유형, 재시도율, 완료되지 않은 메시지 비율을 분리해 봅니다. TTFT가 길면 검색·권한·프롬프트 구성·모델 대기 중 어디가 병목인지 조사할 수 있고, 출력 속도가 낮으면 모델·지역·용량·응답 길이 제한을 봐야 합니다. 취소율이 높으면 답이 느린 것인지, 사용자가 원치 않는 장황한 답을 받는지, UI가 진행 상태를 잘못 보여 주는지 확인합니다.

로그에는 질문 원문과 민감 문서 내용을 무분별하게 저장하지 않도록 주의해야 합니다. request ID, 시간, 종료 사유, 지연 구간, 모델 이름, 토큰 수처럼 운영에 필요한 최소 정보를 남기고 접근 권한과 보존 기간을 정하세요. 보안·개인정보 정책이 있는 조직에서는 스트리밍 이벤트 자체가 브라우저 개발자 도구와 프록시 로그에 남을 수 있다는 점도 고려해야 합니다.

## 한계와 적용 기준 Q&A

### Q. 스트리밍이면 응답 시간이 항상 줄어드나요?

A. 전체 생성 시간은 같거나 오히려 전송 오버헤드가 더해질 수 있습니다. 대신 첫 내용을 빨리 보여 주어 대기 체감을 줄일 수 있습니다. 사용자에게 중요한 것이 즉시성인지, 완성된 표·정확한 인용인지에 따라 스트리밍이 맞는지 판단해야 합니다.

### Q. 네트워크가 끊기면 마지막 이벤트부터 이어 받을 수 있나요?

A. 요청 식별자와 이벤트 순서, 서버 버퍼, 재연결 정책이 있다면 일부 설계를 할 수 있지만, 모든 모델 호출이 임의 시점 재개를 지원하는 것은 아닙니다. 기본 정책으로는 부분 답변을 중단 상태로 표시하고 사용자가 재생성하게 하는 편이 단순하고 안전할 수 있습니다.

### Q. 답변을 스트리밍하면 안전 필터를 적용할 수 없나요?

A. 가능합니다. 다만 생성 전·중·후 어느 시점에 어떤 정책을 적용하는지에 따라 이미 일부 텍스트가 사용자에게 보일 수 있습니다. 위험 도메인에서는 완성 후 검토가 필요한 답변을 스트리밍하지 않거나, 제한된 형식과 근거 기반 응답을 쓰는 등 별도 정책이 필요합니다.

## 서버 구현에서 분리해야 할 책임

스트리밍 endpoint 하나가 검색, 프롬프트 구성, 모델 호출, 도구 실행, 이벤트 변환, 대화 저장을 모두 직접 처리하면 오류를 구분하기 어렵습니다. 요청 검증과 인증은 입구에서 처리하고, 대화 상태와 권한 있는 문서 검색은 별도 서비스로 두며, 모델 provider의 delta를 제품의 이벤트 형식으로 바꾸는 adapter를 두는 방식이 이해하기 쉽습니다. 특정 공급자의 이벤트 명칭이 UI와 데이터베이스까지 퍼지지 않도록 하면 모델을 교체하거나 여러 모델을 쓸 때 변경 범위를 줄일 수 있습니다.

이벤트에는 순서와 식별자가 필요합니다. 브라우저가 재연결하거나 같은 사용자가 동시에 두 질문을 보내면, 늦게 도착한 delta가 다른 대화 버블에 붙지 않아야 합니다. `conversation_id`, `message_id`, `request_id`, sequence 번호를 구분하고, 클라이언트는 현재 활성 요청과 맞는 이벤트만 반영합니다. 네트워크가 중간에 끊겼을 때도 서버가 완료된 요청과 진행 중 요청을 구분할 수 있어야 비용·저장·재시도 정책을 정할 수 있습니다.

도구 호출이 있는 에이전트라면 텍스트 delta와 도구 상태를 더 엄격히 분리합니다. “고객 정보를 조회합니다”라는 모델 문장과 실제 조회 API 호출은 다릅니다. UI는 도구가 실행 중임을 보여 줄 수 있지만, 도구의 민감한 입력과 전체 결과를 그대로 노출하면 안 됩니다. 도구 실패·권한 거절·시간 초과는 사용자에게 이해 가능한 상태로 바꾸고, 모델이 실패한 도구 결과를 사실인 것처럼 서술하지 않도록 제어해야 합니다.

### 재시도와 중복 요청

사용자는 로딩이 길면 새로 고침하거나 같은 질문을 다시 보내기 쉽습니다. 서버가 이를 별도 요청으로 모두 실행하면 비용이 중복되고, 도구 호출이 데이터 변경을 일으키는 경우 더 큰 문제가 생길 수 있습니다. 읽기 전용 채팅에서도 동일 요청 식별자를 일정 시간 동안 deduplicate할지, 사용자가 명시적으로 재생성을 누른 경우만 새 요청으로 할지 정책이 필요합니다. 쓰기 도구가 연결된 에이전트라면 idempotency key와 사용자 확인 단계를 별도로 설계해야 합니다.

재시도는 오류 종류별로 다르게 다뤄야 합니다. 클라이언트 연결 단절은 요청이 실제로 취소됐는지 알 수 없을 수 있고, provider의 일시적 429는 지연 뒤 재시도가 가능할 수 있으며, 잘못된 입력이나 권한 거절은 재시도해도 성공하지 않습니다. 모든 오류에 자동 재시도를 붙이면 지연과 비용을 키우고 사용자의 의도를 왜곡할 수 있습니다. 종료 사유를 구조화해 남기고, UI에는 사용자가 취할 수 있는 다음 행동만 간결하게 보여 주세요.

## 사용자 경험에서 지켜야 할 경계

스트리밍 화면은 시스템이 생각하고 있다는 인상을 줄 수 있지만, 실제로 무엇이 진행 중인지 과장해서는 안 됩니다. 모델이 답을 생성 중인지, 문서를 검색 중인지, 도구 실행을 기다리는지 구분할 수 있다면 짧고 사실적인 상태 문구가 도움이 됩니다. 반대로 내부 추론이나 민감한 시스템 프롬프트를 노출하는 진행 문구는 보안과 사용자 신뢰에 해가 될 수 있습니다. 필요한 상태만 제공하고, 확정되지 않은 결과를 완료된 작업처럼 표현하지 않는 원칙이 중요합니다.

접근성도 고려해야 합니다. 매 토큰마다 화면 읽기 도구가 긴 문장을 읽으면 사용성이 나빠질 수 있으므로 `aria-live` 영역을 제한하거나 완료 시점에 요약 상태를 알리는 방식을 검토합니다. 색상 변화만으로 스트리밍·오류·중단 상태를 표현하지 말고 텍스트와 아이콘을 함께 사용하세요. 모바일 네트워크에서는 연결이 흔들릴 수 있으므로 Stop·재시도·복사 버튼의 상태가 명확해야 합니다.

### 평가를 스트리밍 흐름에 넣기

LLM 응답 품질 평가는 완료된 텍스트만 비교하는 것으로 끝나지 않습니다. 사용자가 취소하기 전에 유해하거나 틀린 문장을 보았는지, 출처가 최종 답에 붙었는지, 오류 뒤에 불완전한 메시지가 저장됐는지, 긴 코드 블록에서 UI가 멈추지 않는지도 시나리오로 검증합니다. 테스트에는 정상 완료, 빈 검색 결과, provider timeout, 중간 연결 단절, 사용자 취소, 안전 정책 차단, 도구 실패를 포함하세요.

이 평가는 실서비스 사용자 데이터를 그대로 재생하지 않아도 됩니다. 합성 질문과 고정된 provider 응답 스트림을 만들어 클라이언트 상태 전환을 테스트하고, 서버는 이벤트 순서와 종료 사유를 assertion으로 검증할 수 있습니다. 실제 provider와 연결하는 테스트는 제한된 수로 두되, 프로토콜 변화와 인증 문제를 놓치지 않게 유지합니다. 이 구조는 빠른 UI 테스트와 실제 통합 검증의 균형을 만듭니다.

## 지연을 구성 요소별로 나누어 보기

사용자가 느끼는 대기 시간은 모델 추론 시간 하나가 아닙니다. 브라우저에서 요청을 보내는 시간, 인증과 rate limit 확인, 대화 이력과 시스템 지침을 읽는 시간, RAG 검색과 권한 필터 시간, 프롬프트 직렬화, 모델 큐 대기, 첫 토큰 생성, 네트워크 전송, 클라이언트 렌더링 시간이 이어집니다. TTFT가 길다는 현상만 보고 모델을 바꾸면 실제 병목을 놓칠 수 있습니다. 각 구간에 trace 또는 구조화된 타이밍을 남기면 무엇을 개선해야 하는지 알 수 있습니다.

예를 들어 문서 RAG를 붙인 뒤 첫 토큰이 느려졌다면 검색 top-k를 무조건 줄이기 전에 벡터 검색, 메타데이터 필터, 재순위화, 원문 fetch 중 무엇이 긴지 확인합니다. top-k를 줄이면 빨라질 수 있지만 근거가 부족한 답이 늘 수 있습니다. 대화 이력이 길어져 프롬프트 구성이 느리거나 비용이 커진다면 요약·보존 정책을 검토합니다. 모델 호출 전의 작업과 모델 생성 중 작업을 분리해 측정하는 것이 사용자 경험 개선의 출발점입니다.

출력 길이도 지연에 직접 영향을 줍니다. 사용자가 짧은 사실 확인을 원할 때 긴 배경 설명을 스트리밍하면 첫 토큰은 빨라도 완료까지 오래 걸리고, 사용자는 중간에 취소할 수 있습니다. UI에서 간결한 답과 자세한 설명의 선택지를 주거나, 시스템 지침에서 질문 유형에 맞는 길이를 요청하는 방법을 고려할 수 있습니다. 다만 응답 길이를 너무 강하게 제한하면 필요한 안전 고지나 조건이 빠질 수 있으므로 도메인별 평가가 필요합니다.

### backpressure와 느린 클라이언트

모델은 토큰을 빠르게 내보내지만 사용자의 브라우저나 중간 프록시가 느릴 수 있습니다. 서버가 이벤트를 무한히 버퍼링하면 메모리 사용량이 늘고, 오래 끊어진 연결에 계속 모델 출력을 생성할 수 있습니다. 전송이 막혔을 때 어떤 크기와 시간에 연결을 취소할지, 서버 내부 버퍼를 얼마나 허용할지, 클라이언트가 백그라운드 탭이 되었을 때 어떻게 처리할지를 운영 정책으로 정해야 합니다.

SSE 연결은 일부 로드 밸런서와 CDN에서 idle timeout, buffering, connection limit의 영향을 받을 수 있습니다. 개발 환경에서 잘 되던 스트리밍이 운영 프록시를 지나며 한 번에 도착하거나 중간에 끊기는 일이 생길 수 있습니다. 배포 전에는 실제 경로에서 response header와 buffering 설정, timeout, 다수 동시 연결의 행동을 확인하세요. 모델 API와 프런트엔드만 테스트하고 중간 인프라를 빼면 가장 흔한 장애 지점을 놓칩니다.

## 데이터 저장과 감사의 기준

스트리밍 응답을 저장할 때는 최종 확정본과 전송 중 조각을 구분합니다. 모든 delta를 데이터베이스에 개별 행으로 넣으면 쓰기 부하와 개인정보 노출 면적이 커질 수 있습니다. 반대로 완료 뒤의 텍스트만 저장하면 중간 오류와 취소 이유를 분석하기 어렵습니다. 보통은 요청 메타데이터와 종료 사유, 최소한의 타이밍을 별도로 남기고, 대화 내용은 제품의 보존·삭제 정책에 맞게 저장합니다. 어떤 필드가 평가와 운영에 필요한지부터 정해야 합니다.

사용자가 대화를 삭제했을 때 캐시, 검색 로그, 오류 추적 도구, 분석 시스템에서도 무엇이 제거되는지 확인해야 합니다. 스트리밍은 이벤트가 여러 계층을 지나기 때문에 원문이 예상보다 많은 곳에 남을 수 있습니다. 고객 정보나 사내 문서를 다루는 제품은 마스킹과 접근 제어, 보존 기간, 감사 기록을 처음 설계에 포함해야 합니다. 나중에 로그를 지우는 비용은 처음 구조화하는 비용보다 큰 경우가 많습니다.

## 장애 대응 시나리오

provider가 429 또는 5xx를 반환할 때 서버는 이미 보낸 delta가 있는지에 따라 다르게 동작할 수 있습니다. 아직 어떤 텍스트도 보내지 않았다면 사용자에게 재시도 가능한 오류를 보여 주기 쉽습니다. 일부 delta를 보낸 뒤 실패했다면, 부분 답변을 남기고 완료되지 않았음을 표시하며 출처·도구 결과가 확정되지 않았을 수 있음을 알려야 합니다. 이 상태를 성공 대화로 저장하면 후속 질문에서 잘못된 전제를 만들 수 있습니다.

서버 재배포나 인스턴스 교체 중의 연결도 고려합니다. long-lived SSE 연결을 즉시 끊을지, 새 요청을 받지 않고 기존 요청에 유예 시간을 줄지, 클라이언트가 어느 오류에서 재시도를 제안할지를 정합니다. 무중단 배포를 하더라도 모델 호출이 외부에서 계속 진행 중일 수 있으므로, 프로세스 종료 신호와 cancellation 전파를 테스트해야 합니다. 인프라의 readiness와 LLM 요청 수명 주기가 만나는 지점입니다.

이런 시나리오를 문서와 테스트로 남기면 온콜 담당자는 “채팅이 느리다”라는 넓은 신고를 TTFT 증가, 스트림 단절, 모델 오류, 렌더링 문제, 권한 검색 지연으로 나눌 수 있습니다. 사용자는 짧고 정직한 오류 메시지와 재시도 선택지를 받고, 팀은 같은 사고를 반복하지 않을 근거를 얻습니다.

## 스트리밍 API의 보안 경계

브라우저가 오래 열린 연결을 유지한다고 해서 인증을 한 번만 확인하면 된다는 뜻은 아닙니다. 요청을 시작할 때 사용자의 세션과 권한을 확인하고, 서버가 검색·도구 호출을 할 때도 그 권한 컨텍스트를 잃지 않아야 합니다. 사용자의 권한이 스트림 도중 바뀌는 상황을 어디까지 즉시 반영할지는 제품 정책이 필요하지만, 적어도 다른 사용자의 request ID를 추측해 이벤트를 받거나 취소할 수 없도록 해야 합니다.

SSE는 일반 HTTP이므로 CORS, CSRF, cookie, access token 정책의 영향을 받습니다. EventSource의 인증 방식과 브라우저 제약을 이해하지 못한 채 URL에 민감한 토큰을 넣으면 로그와 브라우저 기록에 비밀이 남을 수 있습니다. 서버가 어떤 인증 헤더와 cookie를 허용하는지, 프록시가 이를 전달하는지, 오류 응답에 내부 정보를 과도하게 포함하지 않는지 검토하세요. 전송 형식이 텍스트라는 이유로 보안 경계가 약해지는 것은 아닙니다.

### rate limit과 공정성

스트리밍 요청은 짧은 JSON API보다 연결을 오래 점유할 수 있습니다. 한 사용자가 여러 탭에서 긴 생성을 시작하면 provider 동시성, 서버 worker, 브라우저 연결 수를 모두 소비할 수 있습니다. 사용자·조직·모델별로 동시 요청과 토큰 예산을 제한하고, 초과 시 어떤 요청을 취소하거나 대기열에 넣을지 정해야 합니다. 이 정책은 단순 비용 제한이 아니라 다른 사용자의 응답성을 지키는 공정성 정책입니다.

제한을 사용자에게 숨기면 ‘멈춘 채팅’처럼 보입니다. 대기열에 들어갔는지, 잠시 후 재시도해야 하는지, 현재 생성 중인 요청을 취소하면 새 질문을 보낼 수 있는지를 명확히 알려 주세요. 다만 정확한 내부 큐 길이나 인프라 세부 정보를 노출할 필요는 없습니다. 사용자 행동에 필요한 사실만 정직하게 표현하는 것이 좋습니다.

## 모델과 UI를 독립적으로 변경하기

모델 공급자가 이벤트 포맷을 바꾸거나 새로운 tool call 방식을 추가할 수 있습니다. 프런트엔드가 provider의 raw event를 직접 해석하면 이런 변화가 UI 전체에 퍼집니다. 서버에서 제품 고유의 안정적인 이벤트 계약으로 변환하고, 버전을 붙이며, 알 수 없는 이벤트는 안전하게 무시하거나 오류로 기록하는 편이 좋습니다. 이 계층은 미래를 위한 과도한 추상화가 아니라 외부 API 변화를 한곳에 격리하는 경계입니다.

UI도 모델이 생성한 텍스트와 시스템 상태를 분리해 렌더링합니다. 예를 들어 ‘검색 중’, ‘출처 준비 중’, ‘답변 완료’는 서버 이벤트의 상태이고, 답변 본문은 모델 출력입니다. 본문에 상태 문구를 섞으면 저장·복사·재생성에서 혼란이 생깁니다. 분리하면 모델을 바꿔도 동일한 UX 정책을 유지하고, 장애 시에도 어느 단계가 실패했는지 명확히 보여 줄 수 있습니다.

## 출시 전 점검 목록

첫째, 정상적인 짧은 답과 긴 답에서 TTFT와 완료 처리가 정상인지 확인합니다. 둘째, 사용자가 Stop을 누른 뒤 서버 작업과 도구 호출이 의도대로 취소되는지 확인합니다. 셋째, 네트워크 단절·새로 고침·재연결에서 다른 요청의 내용이 섞이지 않는지 확인합니다. 넷째, 마크다운과 링크가 안전하게 렌더링되고 코드 블록이 중간에도 화면을 망가뜨리지 않는지 확인합니다. 다섯째, 빈 검색 결과·권한 거절·안전 정책 차단·provider 오류가 서로 구분되는 메시지인지 확인합니다.

여섯째, 로그와 analytics에 질문 원문·문서 본문·토큰이 과도하게 남지 않는지, 삭제 요청이 필요한 시스템으로 전파되는지 검토합니다. 일곱째, 실제 CDN과 load balancer를 지나는 환경에서 timeout과 buffering을 확인합니다. 여덟째, 스크린 리더와 키보드만으로 Stop·재시도·복사 기능을 사용할 수 있는지 확인합니다. 이 목록은 모든 기능을 한 번에 완성하라는 뜻이 아니라, 스트리밍을 사용자에게 공개할 때 놓치기 쉬운 실패 모드를 드러내는 도구입니다.

## 점진적 출시와 회귀 방지

스트리밍을 기존의 한 번에 받는 응답과 동시에 제공할 수 있다면, 작은 사용자 집단이나 내부 계정에서 먼저 TTFT·오류율·취소율·만족도 차이를 관찰할 수 있습니다. 이때 단순히 스트리밍이 더 빨라 보인다는 평가보다, 출처 표시·오류 처리·모바일 연결에서 회귀가 없는지를 함께 확인해야 합니다. 문제가 생기면 non-streaming 경로로 되돌릴 수 있게 feature flag나 명확한 fallback을 두는 것도 운영 안전성에 도움이 됩니다.

회귀 테스트에는 provider가 정상적으로 한 글자씩 보내는 이상적인 경우만 넣지 마세요. 빈 delta, 중복 event, 완료 뒤의 늦은 event, 순서가 맞지 않는 event, 잘린 JSON, 완료 신호 없는 연결 종료처럼 실제 네트워크와 adapter 경계에서 생길 수 있는 입력을 넣습니다. 클라이언트는 이런 이벤트를 받고도 다른 메시지를 깨뜨리지 않고, 서버는 오류를 기록하며, 사용자는 무슨 일이 일어났는지 알 수 있어야 합니다. 스트리밍 품질은 모델 문장 품질과 별개의 신뢰성 요구입니다.

스트리밍을 잘 설계했다는 것은 화면에 글자가 움직인다는 뜻이 아닙니다. 사용자가 언제 답이 확정됐는지, 언제 중단됐는지, 언제 다시 시도해야 하는지 알 수 있고, 서버가 그 상태를 비용·보안·데이터 보존 정책과 일관되게 처리한다는 뜻입니다. 이 기준을 지키면 모델이나 전송 기술이 바뀌어도 사용자 경험의 핵심은 유지됩니다.

### 운영 문서에 남길 내용

스트리밍 기능의 runbook에는 request ID로 상태를 찾는 방법, 정상 완료와 취소·단절·provider 오류의 종료 코드, TTFT와 전체 시간의 대시보드 위치, timeout·동시성 제한 값, 재배포 시 연결 처리 원칙을 포함하세요. 이런 정보가 없으면 장애 때 화면 문제인지 모델 문제인지 네트워크 문제인지 추측하게 됩니다. 반대로 최소한의 공통 언어가 있으면 프런트엔드, 백엔드, 플랫폼 담당자가 같은 사건을 같은 상태로 설명할 수 있습니다.

사용자 피드백도 종료 상태와 연결해 보세요. 답변이 부정확하다는 피드백과 연결이 중단됐다는 피드백은 다른 개선을 요구합니다. 전자는 검색·프롬프트·모델 평가가 필요하고, 후자는 timeout·취소·프록시·렌더링을 봐야 합니다. 스트리밍을 관찰 가능한 기능으로 만들면 두 종류의 문제를 섞지 않고 개선할 수 있습니다.

## 마무리

LLM 스트리밍은 모델의 토큰을 화면에 붙이는 기능을 넘어, 사용자가 기다림과 불확실성을 이해하도록 만드는 제품 설계입니다. TTFT와 완료 시간을 분리해 관찰하고, delta·완료·오류 이벤트를 구분하며, 취소와 네트워크 단절을 정상 흐름으로 다루세요. 부분 답변과 출처, 안전 검사, 저장 상태를 명확히 구분하면 더 빠르게 느껴질 뿐 아니라 더 신뢰할 수 있는 AI 경험을 만들 수 있습니다.
