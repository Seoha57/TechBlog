## 먼저 답하기

**Q. 인덱스가 있는데도 MariaDB 쿼리가 느리면 히스토그램을 만들면 해결되나요?**
항상 그렇지는 않습니다. 히스토그램 통계는 MariaDB 옵티마이저가 특정 값이나 범위가 얼마나 많은 행을 반환할지 추정하는 데 도움을 주는 정보입니다. 잘못된 행 수 추정 때문에 비효율적인 조인 순서나 접근 방식을 고른 경우에는 도움이 될 수 있지만, 인덱스 부재, 대량 반환, 잠금, 디스크 자원, 비효율적인 애플리케이션 호출을 대신 해결하지는 않습니다.

**Q. 히스토그램은 그래프를 저장하는 기능인가요?**
아닙니다. 여기서 히스토그램은 값 분포를 구간 또는 빈도 형태로 요약한 통계입니다. MariaDB는 이 요약을 바탕으로 `WHERE 상태 = '배송중'` 같은 조건이 전체 행 중 어느 정도를 걸러낼지 추정할 수 있습니다. 사용자가 보는 차트 기능이 아니라 실행 계획을 고르는 내부 판단 자료에 가깝습니다.

**Q. 운영 데이터베이스에서 ANALYZE TABLE을 바로 실행해도 되나요?**
무조건 바로 실행하기보다 MariaDB 버전, 스토리지 엔진, 실행 시간, 잠금 영향, 통계 갱신 정책을 확인해야 합니다. 공식 문서의 동작과 현재 운영 정책을 먼저 읽고, 가능하면 검증 환경과 관찰 가능한 시간대에서 영향 범위를 확인하세요. 이 글은 특정 환경에서의 실행 결과를 주장하지 않으며, 판단에 필요한 개념과 절차를 설명합니다.

## 느린 쿼리의 원인은 실행 계획의 추정에서 시작되기도 한다

관계형 데이터베이스 관리 시스템은 SQL(Structured Query Language, 데이터를 조회·변경하기 위한 선언형 언어)을 받으면 사람이 적어 둔 순서대로만 처리하지 않습니다. **옵티마이저(optimizer)**는 가능한 접근 경로와 조인 순서를 비교해 비용이 낮을 것으로 예상하는 실행 계획을 고릅니다. 이때 비용은 실제 미래를 아는 값이 아니라 테이블 크기, 인덱스, 조건 선택도, 통계 정보를 바탕으로 한 추정입니다.

예를 들어 주문 테이블에 수천만 행이 있고 `status` 열에는 `배송완료`가 대부분, `결제실패`가 극히 일부라고 가정해 보겠습니다. `WHERE status = '결제실패'`는 아주 적은 행을 돌려줄 수 있지만, 모든 값이 고르게 분포한다고 추정하면 옵티마이저는 이 조건이 충분히 선택적이지 않다고 판단할 수 있습니다. 반대로 특정 상태가 갑자기 대량으로 쌓였는데 오래된 통계가 이를 모르면, 작은 결과를 기대하고 비싼 반복 접근을 선택할 수도 있습니다.

여기서 **선택도(selectivity)**는 조건이 전체 행 중 얼마나 적은 부분을 남기는지 나타내는 개념입니다. 선택도가 높은 조건이라는 표현은 문맥에 따라 혼동될 수 있으므로, 실무 문서에서는 "많이 걸러낸다" 또는 "반환 행 비율이 낮다"처럼 구체적으로 쓰는 편이 안전합니다. 중요한 것은 옵티마이저가 이 비율을 얼마나 현실에 가깝게 추정하는가입니다.

통계가 부정확하다고 해서 모든 느린 쿼리의 원인이 통계인 것은 아닙니다. 쿼리가 실제로 너무 많은 행을 반환하거나, 인덱스가 조건과 맞지 않거나, 함수 적용 때문에 인덱스를 쓰기 어렵거나, 조인 키의 자료형이 다르거나, 애플리케이션이 같은 쿼리를 과도하게 호출할 수도 있습니다. 히스토그램은 진단의 한 가지 가설이며, 실행 시간만 보고 즉시 적용할 설정이 아닙니다.

## 먼저 알아둘 기반 기술

### MariaDB와 쿼리 옵티마이저

**MariaDB**는 MySQL과 같은 계열에서 발전해 온 오픈 소스 관계형 데이터베이스 관리 시스템입니다. SQL로 데이터를 다루고, 내부적으로는 요청을 해석한 뒤 여러 실행 방법 중 하나를 선택합니다. `EXPLAIN`은 MariaDB가 어떤 접근 방식과 조인 순서를 계획했는지 보여 주는 명령입니다. 실행 전 추정 중심의 정보를 보여 주므로, 실제 수행 시간이나 실제 반환 행 수와 완전히 같다고 가정해서는 안 됩니다.

실행 계획에서 자주 보는 `type`, `key`, `rows`, `filtered` 같은 열은 힌트입니다. `key`에 인덱스 이름이 보인다고 반드시 좋은 계획은 아니고, 인덱스가 보이지 않는다고 반드시 잘못도 아닙니다. 작은 테이블을 전부 읽는 편이 더 저렴할 수 있기 때문입니다. 특히 `rows`는 추정 행 수이므로, 실제 데이터 분포와 크게 차이 나는지가 통계 문제를 의심하는 출발점이 될 수 있습니다.

### 인덱스와 통계의 다른 역할

**인덱스(index)**는 특정 열 값을 기준으로 관련 행을 빠르게 찾기 위한 자료 구조입니다. 책의 색인처럼 생각할 수 있지만, 실제 데이터베이스에서는 정렬, 범위 검색, 조인, 정렬 처리에도 영향을 줍니다. 인덱스가 없으면 히스토그램이 있어도 특정 값을 빠르게 찾아가는 길이 생기지 않습니다.

반면 **통계(statistics)**는 옵티마이저가 어느 길을 선택할지 판단하도록 돕는 요약 정보입니다. 인덱스는 경로 자체이고, 통계는 그 경로를 이용했을 때 얼마나 많은 데이터를 만날지에 대한 지도입니다. 좋은 지도가 있어도 길이 없으면 목적지까지 빠르게 갈 수 없고, 좋은 길이 있어도 잘못된 지도면 우회할 수 있습니다.

### 카디널리티와 데이터 분포

**카디널리티(cardinality)**는 문맥에 따라 행 수 또는 서로 다른 값의 수를 뜻합니다. 인덱스 통계 문맥에서는 한 열에 얼마나 다양한 값이 있는지를 뜻하는 경우가 많습니다. 성별처럼 값 종류가 적은 열과 주문 번호처럼 거의 모든 행에서 값이 다른 열은 카디널리티가 다릅니다. 하지만 서로 다른 값의 개수만으로는 값이 한쪽에 몰렸는지까지 알기 어렵습니다.

예를 들어 상태 값이 다섯 종류라는 정보만으로는 각 상태가 20%씩인지, 한 상태가 99%인지 알 수 없습니다. **히스토그램**은 이런 분포 정보를 더 세밀하게 표현하려는 통계입니다. 값이 어떻게 분포하는지 알면 옵티마이저는 등호 조건, 범위 조건, 조인 전 필터의 결과 크기를 더 나은 근거로 예측할 수 있습니다.

## MariaDB의 히스토그램 기반 통계

MariaDB 공식 문서에서 설명하는 히스토그램 기반 통계는 주로 인덱스가 없는 열의 값 분포에 관한 정보를 옵티마이저에 제공하기 위한 기능입니다. 인덱스가 없는 열에도 `WHERE`, `JOIN`, `GROUP BY` 조건이 자주 걸릴 수 있고, 이때 단순 추정만으로는 조인 순서가 불리하게 선택될 수 있습니다. 히스토그램이 있다고 해서 해당 열에 인덱스가 만들어지는 것은 아니라는 점이 핵심입니다.

문서에서 다루는 설정에는 `histogram_size`, `histogram_type`, `use_stat_tables` 등이 있습니다. 정확한 기본값과 사용 가능 범위는 MariaDB 버전에 따라 달라질 수 있으므로, 운영 시스템에 적용하기 전에는 반드시 현재 버전의 공식 문서를 확인해야 합니다. 블로그 예제를 그대로 복사해 전역 설정을 바꾸는 일은 피하세요. 통계는 쿼리 선택에 폭넓게 영향을 줄 수 있어, 한 쿼리를 고치려다 다른 쿼리의 계획이 달라질 수 있습니다.

히스토그램 유형으로는 높이를 기준으로 구간을 나누는 형태와 값 빈도를 다루는 형태가 논의됩니다. 어떤 유형과 크기가 적합한지는 열의 자료형, 값의 개수, 분포의 치우침, 갱신 빈도에 따라 달라집니다. 버킷(bucket)이 많을수록 항상 정확해지는 것도 아닙니다. 통계 수집·저장 비용, 오래된 통계가 주는 오해, 운영 복잡도까지 함께 고려해야 합니다.

통계는 데이터의 스냅샷입니다. 이벤트 기간에 특정 상태가 급증하거나, 테넌트 하나가 대량 데이터를 적재하거나, 파티션이 새로 추가되는 상황에서는 과거 분포가 현재와 다를 수 있습니다. 따라서 "한 번 ANALYZE TABLE을 실행했으니 끝"이 아니라, 어떤 테이블에서 어떤 변화가 있을 때 통계를 재검토할지 운영 기준을 정하는 편이 좋습니다.

## ANALYZE TABLE은 무엇을 하는가

`ANALYZE TABLE`은 테이블에 대한 키 분포나 엔진별 통계 정보를 갱신하도록 요청하는 SQL 명령입니다. MariaDB 공식 문서는 동작이 스토리지 엔진과 옵션에 따라 다를 수 있음을 설명합니다. 따라서 특정 엔진의 문서를 다른 엔진에 그대로 적용하면 안 됩니다. 운영 환경에서 명령을 실행하기 전에는 대상 테이블 크기, 복제 구성, 백업·배치 시간, 장시간 실행 가능성을 점검해야 합니다.

기본 형태는 다음과 같습니다. 이 명령은 학습용 예시이며, 실제 대상 테이블·옵션·실행 시점은 해당 서비스의 변경 절차에 따라 결정해야 합니다.

```sql
ANALYZE TABLE orders;
```

MariaDB에서 히스토그램을 포함한 통계 사용을 검토할 때는 첫째, 어떤 쿼리의 어떤 조건이 잘못 추정된다고 의심하는지 명확히 합니다. 둘째, 현재 실행 계획과 데이터 분포를 확인합니다. 셋째, 안전한 환경에서 통계를 갱신한 뒤 계획 변화와 결과 정합성을 비교합니다. 넷째, 운영 반영 후에는 해당 쿼리만이 아니라 관련 대시보드와 오류율을 관찰할 기준을 마련합니다. 이 순서를 생략하고 `ANALYZE TABLE`을 만능 튜닝 명령처럼 쓰면 원인과 결과를 연결하기 어려워집니다.

통계 갱신은 데이터 변경과 별개의 관리 작업입니다. 대량 적재 직후, 삭제·보관 정책 수행 후, 값 분포가 크게 바뀌는 기능 출시 후에는 재검토 후보가 될 수 있습니다. 그러나 모든 쓰기 작업 뒤에 수동 분석을 실행하는 자동화는 필요 이상의 부담을 만들 수 있습니다. 데이터 변화의 성격과 성능 민감도를 기준으로 주기를 정하고, 실제 영향은 서비스 환경에서 관찰해야 합니다.

## EXPLAIN으로 가설을 검증하는 법

성능 문제를 만났을 때 다음처럼 실행 계획을 먼저 확인할 수 있습니다.

```sql
EXPLAIN
SELECT o.id, o.created_at, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE o.status = 'PAYMENT_FAILED'
  AND o.created_at >= '2026-11-01';
```

이 결과에서 주목할 것은 특정 숫자 하나가 아니라 이야기의 흐름입니다. `orders`를 먼저 읽는지 `customers`를 먼저 읽는지, 어떤 인덱스를 후보로 보고 선택했는지, 추정 행 수가 조건을 지나며 어떻게 줄어드는지, 임시 테이블이나 파일 정렬이 필요한지 등을 함께 읽습니다. `EXPLAIN`의 표시 형식과 제공 정보는 MariaDB 버전에 따라 달라질 수 있으므로, 현재 버전의 문서를 함께 보세요.

통계 문제가 의심되는 전형적인 신호는 "실제 결과는 몇 행인데 계획은 매우 많은 행을 예상"하거나 그 반대인 경우입니다. 다만 이 비교는 실제 운영 쿼리를 무심코 반복 실행해서 얻어서는 안 됩니다. 읽기 부하가 큰 쿼리라면 복제본, 제한된 기간, 검증 환경, 샘플링 같은 안전한 방법을 선택해야 합니다. 계획 추정과 실제 관찰의 차이는 조사 단서일 뿐, 통계 갱신을 강제하는 증명은 아닙니다.

`EXPLAIN` 결과를 공유할 때는 SQL 전체를 그대로 붙여 민감한 테이블명·고객 식별자·값을 노출하지 않도록 주의합니다. 구조를 이해하는 데 필요한 열, 인덱스, 조건의 형태는 남기고 개인 정보나 영업 정보를 마스킹하세요. 성능 진단 문서에는 실행 시각, 대상 환경, 데이터 규모의 대략적인 구간, 설정 변경 여부도 함께 기록하면 나중에 비교하기 좋습니다.

## 업무 예시: 상태 값이 치우친 주문 조회

고객 상담 도구가 최근 실패 주문을 찾는 화면을 운영한다고 가정합니다. 주문 테이블의 대부분은 완료 상태이고, 실패 상태는 드뭅니다. 화면은 실패 상태와 최근 30일이라는 두 조건으로 주문을 조회하고 고객 테이블과 조인합니다. 어느 날 데이터 적재 방식이 바뀐 뒤 화면이 느려졌다면, 원인을 "상태 열에 인덱스가 없어서"라고 즉시 결론 내리지 않습니다.

먼저 요구사항을 확인합니다. 상담 화면은 최대 몇 건을 보여 주는지, 시간 순 정렬이 필요한지, 고객 정보 전부가 필요한지, 실패 상태의 정의가 하나인지 여러 개인지 확인합니다. 다음으로 현재 인덱스와 쿼리 계획을 봅니다. `status`만의 인덱스, `created_at`만의 인덱스, 두 열을 함께 고려한 복합 인덱스 중 무엇이 규칙과 조회 패턴에 맞는지는 실제 조건과 정렬에 따라 달라집니다. 통계는 이 선택지의 비용을 판단하는 재료 중 하나입니다.

만약 인덱스 없는 부가 조건, 예를 들어 판매 채널 또는 캠페인 코드가 조인 순서에 영향을 준다면 히스토그램 통계를 검토할 여지가 있습니다. 그러나 조회 화면이 매번 수십만 행을 응답으로 전송한다면 통계보다 페이지 크기·검색 조건·집계 전략이 먼저일 수 있습니다. 이 예시는 히스토그램이 인덱스 설계의 대체재가 아니라, 데이터 분포에 대한 옵티마이저의 시야를 보완하는 수단임을 보여 줍니다.

검증 환경에서는 동일한 스키마와 가능한 한 유사한 분포를 준비합니다. 분석 전후에 `EXPLAIN`을 저장하고, 같은 파라미터로 결과 행의 정합성을 확인합니다. 계획이 바뀌었다는 사실만으로 개선이라고 판단하지 말고, 서비스 수준 목표와 안전한 관찰 절차에 따라 응답 시간·자원 사용·다른 핵심 쿼리의 변화도 봐야 합니다. 여기서의 관찰 항목은 점검 계획이지, 이 글이 어떤 수치를 측정했다는 뜻이 아닙니다.

## 히스토그램을 고려할 때와 피할 때

다음 상황에서는 히스토그램 기반 통계를 검토해 볼 수 있습니다.

- 인덱스가 없는 열의 분포가 심하게 치우쳐 있고, 그 열이 필터나 조인 조건에 반복 등장한다.
- `EXPLAIN`의 행 수 추정과 안전한 환경에서 확인한 실제 결과 크기 사이에 큰 차이가 반복된다.
- 쿼리와 인덱스 설계는 요구사항에 맞지만, 조인 순서 또는 접근 방식이 데이터 분포를 무시하는 듯한 근거가 있다.
- 통계 갱신의 영향 범위를 검증할 환경과 변경·되돌리기 절차가 있다.

다음 상황에서는 히스토그램부터 적용하지 않는 편이 좋습니다.

- 반환해야 할 행이 본질적으로 너무 많거나 `SELECT *`로 불필요한 큰 열을 가져온다.
- 조건에 맞는 인덱스가 전혀 없고, 데이터 접근 경로 자체가 문제다.
- 함수·암묵적 형 변환 때문에 기존 인덱스를 활용하기 어려운 쿼리다.
- 데이터가 매우 빠르게 변해 수집 직후의 통계도 의미를 잃을 수 있는데 갱신 전략이 없다.
- 어떤 쿼리를 개선하려는지, 어떤 계획이 문제인지 근거 없이 전역 설정만 바꾸려 한다.

이 구분은 히스토그램을 피하자는 뜻이 아닙니다. 성능 튜닝에서 도구를 문제에 맞게 쓰자는 뜻입니다. 특히 운영 데이터베이스의 전역 설정은 여러 서비스가 공유할 수 있으므로, 한 팀의 단기 문제를 해결하기 위한 변경이 다른 워크로드에 미칠 영향을 고려해야 합니다.

## 통계와 인덱스 설계를 함께 보는 기준

인덱스를 추가하기 전에 먼저 질문할 것은 이 쿼리가 어떤 패턴으로 사용되는가입니다. 동등 조건, 범위 조건, 조인, 정렬, 그룹화가 섞이면 복합 인덱스의 열 순서가 중요해집니다. 하지만 "자주 쓰는 열을 전부 복합 인덱스에 넣자"는 방식은 쓰기 비용과 저장 공간을 키우고, 유사한 인덱스를 중복할 수 있습니다. 쿼리 패턴과 실행 계획을 근거로 후보를 비교해야 합니다.

히스토그램은 인덱스가 없는 열에 대해서도 추정 정보를 줄 수 있다는 점에서 유용하지만, B-Tree 같은 인덱스 접근의 탐색 비용을 없애 주지는 않습니다. 반대로 좋은 인덱스가 있어도 통계가 현실과 멀면 옵티마이저가 그 인덱스의 장점을 낮게 볼 수 있습니다. 따라서 진단 순서는 흔히 요구사항 확인, SQL 단순화, 결과량 제한, 인덱스 적합성 점검, 통계·추정 점검, 자원·동시성 점검처럼 여러 층을 오갑니다.

특정 계획을 강제로 고정하는 힌트나 설정은 최후의 수단에 가깝습니다. 데이터 분포와 버전이 바뀌면 어제의 최적 선택이 오늘의 병목이 될 수 있기 때문입니다. 힌트를 써야 한다면 왜 자동 선택이 실패했는지, 제거 조건은 무엇인지, 정기 검토 책임자는 누구인지 남겨 두는 편이 낫습니다. 통계 개선은 이런 강제 수단을 줄일 수 있는 한 가지 방법일 수 있지만, 결과는 반드시 환경별로 검증해야 합니다.

## 데이터 분포를 읽는 실무 관점

히스토그램을 이해하려면 먼저 테이블 전체 행 수와 업무에서 의미 있는 값의 분포를 구분해야 합니다. 주문 테이블이 커졌다는 사실만으로 특정 조건의 추정이 틀렸다고 말할 수는 없습니다. 예를 들어 주문 상태가 다섯 가지라도, 최근 7일 조회에서는 한 상태가 절반을 차지하고 전체 기간에서는 1%일 수 있습니다. 쿼리의 시간 조건, 테넌트 조건, 보관 정책이 결합되면 열 하나의 전역 분포만으로는 설명하기 어려운 편향도 생깁니다.

따라서 조사 문서에는 "어떤 열이 치우쳤다"보다 "어떤 쿼리의 어떤 범위에서 추정이 실제 업무 분포와 어긋난다고 보았는가"를 쓰는 편이 낫습니다. 데이터베이스에 큰 집계 쿼리를 새로 던져 운영 부하를 만들기보다, 이미 수집하는 모니터링, 제한된 표본, 검증 환경 데이터를 활용할 수 있는지 먼저 검토하세요. 데이터 분포를 알아야 한다는 이유가 개인 정보나 고객별 매출 정보를 광범위하게 열람할 근거가 되지는 않습니다.

분포의 변화 원인도 함께 추적할 가치가 있습니다. 새로운 판매 채널을 붙였는지, 특정 배치가 실패해 상태가 쌓였는지, 과거 데이터를 보관 테이블로 이동했는지, 애플리케이션이 값을 기본값으로 저장하기 시작했는지에 따라 대응이 달라집니다. 통계 갱신은 현재 모습을 반영할 수 있지만, 잘못된 데이터 적재나 상태 전이 오류를 고치지는 않습니다. 성능 이상이 데이터 품질 이상을 드러내는 경우도 있습니다.

## 복제와 변경 관리에서의 주의점

운영 MariaDB는 단일 서버가 아니라 복제본, 읽기 분산, 백업, 배치 작업과 함께 구성되는 경우가 많습니다. 이때 통계 수집과 관련 설정 변경이 어느 노드에서 어떤 방식으로 이뤄지는지 확인해야 합니다. 쓰기 원본에서만 분석할지, 읽기 복제본의 실행 계획도 별도로 점검할지, 버전과 설정이 같은지에 따라 관찰 결과가 달라질 수 있습니다. 구체적인 복제 동작은 MariaDB 버전과 구성에 따라 다르므로, 여기서는 특정 전파 방식을 단정하지 않습니다.

변경 요청에는 최소한 대상 테이블, 목적 쿼리, 현재 가설, 적용 명령, 예상 영향, 관찰 지표, 되돌리기 기준을 포함하세요. "통계 갱신"은 겉으로 작아 보이는 작업이지만, 옵티마이저의 선택이 바뀌면 여러 조회의 지연 특성이 달라질 수 있습니다. 배포와 마찬가지로 담당자·실행 창·연락 방법을 정하면 예상치 못한 계획 변경에 대응하기 쉽습니다.

되돌리기는 단순히 명령 하나를 반대로 실행하는 문제만은 아닙니다. 갱신 전 통계를 그대로 복원할 수 있는지, 계획 변화가 캐시나 동시 부하에 의해 일시적으로만 보이는지, 인덱스 변경이 함께 섞였는지에 따라 판단이 필요합니다. 그래서 통계 수집과 인덱스 추가, SQL 변경을 한 번의 큰 변경으로 묶기보다 가능한 한 원인을 구분해 기록하는 편이 좋습니다. 다만 서비스 위험이 커서 하나의 승인된 변경 창에 묶어야 한다면, 각각의 가설과 검증 항목은 분리해 두세요.

## 안전한 검증 환경을 준비하는 법

성능 진단에는 운영과 비슷한 데이터 분포가 중요하지만, 운영 데이터를 그대로 복제하는 것이 항상 정답은 아닙니다. 개인정보, 결제 정보, 계약 정보가 포함될 수 있으므로 마스킹·가명 처리·접근 권한·보존 기간을 먼저 정해야 합니다. 행 수만 비슷하고 값의 분포가 전혀 다르면 통계 관련 가설을 검증하기 어렵고, 반대로 원본 데이터를 무단으로 복사하면 보안 문제가 됩니다. 필요한 특성만 보존한 검증 데이터를 설계하는 일이 DBA와 보안 담당자의 공동 과제가 됩니다.

검증 환경에서는 데이터베이스 버전, 콜레이션, 문자 집합, 스토리지 엔진, 주요 설정, 인덱스 정의가 운영과 얼마나 다른지도 기록합니다. MariaDB에서 문자열 비교와 정렬 규칙은 선택도와 인덱스 사용 양상에 영향을 줄 수 있습니다. 따라서 운영과 다른 기본값을 쓰는 개발용 컨테이너에서 얻은 결과를 운영의 확정 결론처럼 다루지 않는 것이 좋습니다.

실험은 한 번에 하나의 핵심 가설을 확인하도록 설계합니다. 예를 들어 먼저 SQL의 불필요한 조인을 제거해 놓고, 다음에 인덱스를 추가하고, 또 통계를 갱신하면 어느 변화가 계획을 바꿨는지 알기 어렵습니다. 현실에서 완벽한 통제는 어려워도, 변경 순서와 전후 `EXPLAIN` 결과를 남기는 것만으로도 진단 품질이 크게 좋아집니다. 결과가 기대와 다르면 실패가 아니라 가설을 수정할 근거가 됩니다.

## 관찰 지표를 미리 정하기

통계 변경 후 "빨라진 것 같다"는 감상만 남기면 다음 데이터 변화에서 판단을 재현할 수 없습니다. 목표 쿼리에는 응답 시간의 대표값과 상위 지연, 반환 행 수, 오류율, 타임아웃 수, 데이터베이스 자원 사용처럼 서비스에 맞는 지표를 미리 정합니다. 단, 단일 실행 시간은 캐시·동시 접속·네트워크 영향을 받으므로 한 번의 숫자만으로 결론 내리지 않습니다.

관련 쿼리도 살펴봐야 합니다. 옵티마이저가 테이블을 접근하는 방식이 바뀌면 같은 테이블을 사용하는 검색, 배치, 관리자 화면의 계획도 달라질 수 있습니다. 모든 쿼리를 전수 측정하기 어렵다면, 영향이 큰 상위 쿼리와 배치 작업을 선정해 관찰 대상 목록으로 만드세요. 이는 통계를 두려워해서가 아니라, 변경의 이득과 부작용을 같은 기준으로 비교하기 위한 방법입니다.

관찰 기간은 업무 주기와 데이터 변화 속도에 맞춰 정합니다. 월말에만 발생하는 분포, 특정 행사 기간에만 급증하는 상태, 야간 배치 직후의 읽기 패턴은 평상시의 짧은 테스트로 나타나지 않을 수 있습니다. 이 글은 특정 기간을 권고하지 않지만, 최소한 어떤 상황을 관찰하지 못했는지를 기록하면 과도한 일반화를 줄일 수 있습니다.

## 팀 간 역할을 연결하기

MariaDB 통계 문제는 DBA만의 전문 영역으로 보이기 쉽지만, 입력 데이터와 SQL을 만드는 애플리케이션 개발자, 검색 조건을 정의하는 기획자, 경보를 설정하는 운영 담당자의 정보가 모두 필요합니다. 개발자는 어떤 파라미터 조합이 자주 오는지, 기획자는 상태 값의 업무 의미가 어떻게 바뀌었는지, 운영자는 어느 시간대에 부하가 몰리는지 알고 있을 수 있습니다. DBA는 이 정보를 실행 계획과 자원 관점에서 연결합니다.

협업 문서에서 유용한 형식은 "증상-증거-가설-변경-확인"입니다. 증상은 상담 화면 지연처럼 사용자 영향으로 쓰고, 증거는 마스킹한 SQL 구조와 계획·관찰 지표로 남깁니다. 가설은 `status` 분포를 잘못 추정해 조인 순서가 불리하다는 식으로 검증 가능하게 씁니다. 변경은 통계 갱신, 인덱스 후보, SQL 수정 중 무엇인지 분리하고, 확인은 어느 지표가 어떤 방향으로 변해야 하는지 적습니다. 이 형식은 결과가 예상과 달라도 팀이 같은 사실에서 다음 가설을 세울 수 있게 합니다.

새로 입문하는 사람에게는 히스토그램 설정 값을 먼저 외우기보다, 실행 계획이 추정의 결과라는 점을 이해하는 것이 더 중요합니다. 인덱스가 있느냐 없느냐라는 이분법에서 벗어나, 데이터가 어떻게 분포하고 옵티마이저가 무엇을 알고 있는지 질문해 보세요. 그 질문이 쿼리 튜닝, 스키마 설계, 데이터 품질, 운영 관찰을 연결하는 출발점이 됩니다.

## 운영 점검 체크리스트

1. 느리다고 보고된 SQL과 사용자 영향 범위를 수집한다.
2. 결과량, 정렬, 페이지 처리, 불필요한 열 조회처럼 SQL 자체의 문제를 먼저 살핀다.
3. `EXPLAIN`으로 접근 방식·조인 순서·추정 행 수를 기록한다.
4. 인덱스의 존재만이 아니라 조건과 열 순서가 사용 패턴에 맞는지 검토한다.
5. 데이터 분포가 치우쳤는지, 통계가 오래됐을 가능성이 있는지 확인한다.
6. 히스토그램 또는 `ANALYZE TABLE` 변경은 검증 환경과 변경 절차에서 먼저 평가한다.
7. 반영 후에는 대상 쿼리와 연관된 핵심 쿼리의 계획·오류·자원 지표를 정해진 기간 관찰한다.
8. 변경 이유, 실행 시각, 사용한 SQL, 되돌리기 방법을 운영 기록에 남긴다.

이 체크리스트는 특정 명령을 실행하라는 승인 목록이 아닙니다. DBA(Database Administrator, 데이터베이스의 성능·가용성·보안을 관리하는 역할), 개발자, 서비스 운영자가 같은 문제를 서로 다른 단어로 논의하지 않도록 돕는 공통 언어입니다.

## 한계와 적용 기준 Q&A

**Q. 히스토그램을 만들면 모든 인덱스 없는 조건이 빨라지나요?**
아닙니다. 히스토그램은 접근 속도보다 행 수 추정을 돕습니다. 전체 테이블을 읽어야 하는 쿼리의 물리적 비용, 네트워크 전송량, 정렬·집계 비용은 그대로 남을 수 있습니다. 먼저 필요한 결과량과 인덱스 설계를 점검하고, 잘못된 추정이라는 근거가 있을 때 통계를 검토하세요.

**Q. ANALYZE TABLE을 자주 실행할수록 좋나요?**
아닙니다. 갱신 비용과 운영 영향, 데이터 변화 속도를 함께 봐야 합니다. 분포가 거의 변하지 않는 작은 테이블과 대량 적재가 이어지는 이벤트 테이블은 같은 주기를 쓸 이유가 없습니다. MariaDB 버전과 엔진의 동작을 공식 문서에서 확인하고, 서비스의 변경 관리 절차에 맞는 정책을 정하세요.

**Q. EXPLAIN에서 rows가 커 보이면 바로 통계를 갱신해야 하나요?**
아닙니다. `rows`는 추정이며, 큰 테이블을 읽는 것이 실제로 합리적일 수도 있습니다. 조건의 선택도, 반환 행 수, 적절한 인덱스, 조인 조건, 통계의 최신성까지 함께 봐야 합니다. 개선 전후를 같은 조건에서 비교하지 않으면 우연한 캐시·부하 차이를 튜닝 효과로 오해할 수 있습니다.

**Q. MariaDB 문서의 설정값을 전역으로 적용해도 되나요?**
전역 설정은 다른 데이터베이스와 쿼리에도 영향을 줄 수 있으므로 신중해야 합니다. 현재 버전에서의 의미, 영속화 방법, 되돌리기 방법, 복제 환경과의 관계를 확인하지 않았다면 운영에 바로 적용하지 마세요. 테스트 환경에서 가설과 영향 범위를 먼저 확인하는 편이 안전합니다.

## 마무리

MariaDB의 히스토그램 기반 통계는 옵티마이저가 값 분포를 더 잘 추정하도록 돕는 도구입니다. 이것은 인덱스를 대신 만들거나 쿼리의 본질적인 작업량을 없애는 기능이 아닙니다. `ANALYZE TABLE`, `EXPLAIN`, 인덱스 설계, 데이터 변화 관찰을 연결해 사용해야 의미가 있습니다.

처음에는 문제가 되는 SQL 하나를 골라 결과량과 실행 계획을 읽는 연습부터 해 보세요. 그다음 통계가 어떤 판단에 영향을 줄 수 있는지 가설을 적고, 안전한 환경에서 전후 차이를 검증하세요. 숫자 하나나 명령 하나를 외우는 것보다, 옵티마이저의 추정과 실제 데이터 분포 사이의 차이를 질문하는 습관이 DBA 역량의 출발점이 됩니다.
