사내 규정과 매뉴얼을 답하는 챗봇이 틀린 답을 하면 “모델을 학습시키면 되지 않을까?”라는 생각이 자연스럽게 나옵니다. 반대로 답변 형식이 매번 달라지고 특정 분류 규칙을 잘 지키지 못하면 “문서를 더 많이 검색해 넣으면 되지 않을까?”라고도 생각합니다. 두 접근은 각각 **Fine-tuning(파인튜닝, 추가 학습)** 과 **RAG(Retrieval-Augmented Generation, 검색 증강 생성)** 로 이어지지만, 해결하는 문제가 같지 않습니다.

Fine-tuning은 기존 언어 모델에 입력과 바람직한 출력의 예시를 추가로 학습시켜 특정 작업의 행동·형식·판단 패턴을 더 일관되게 만드는 방법입니다. RAG는 질문과 관련된 문서를 그때그때 검색해 모델의 입력 문맥에 넣고 답하게 만드는 시스템 설계입니다. 전자는 모델의 **행동 방식**을 조정하는 데 가깝고, 후자는 답변에 쓸 **외부 지식**을 선택해 제공하는 데 가깝습니다. 실제 서비스에서는 둘 중 하나만 고르는 경우도 있지만, 프롬프트와 RAG부터 검증한 뒤 정말 필요한 행동 차이에만 Fine-tuning을 적용하거나, 두 방식을 함께 쓰기도 합니다.

이 차이를 놓치면 최신 취업 규정, 제품 가격, 장애 runbook처럼 자주 바뀌는 사실을 학습 데이터에 고정해 놓고 갱신 비용을 감당하게 됩니다. 반대로 고객 문의 분류처럼 출력 형식과 미묘한 판정 기준이 핵심인 일을 검색 결과만 늘려 해결하려다 응답이 길고 불안정해질 수 있습니다. 이 글은 API 공급자나 특정 프레임워크에 종속되지 않는 선택 기준을 설명합니다. OpenAI 같은 상용 API를 쓰든 로컬 모델을 쓰든, 모델을 바꾸기 전에 데이터·평가·권한 경계를 먼저 설계하는 데 목적이 있습니다.

## 먼저 알아둘 기반 기술: LLM·프롬프트·토큰·임베딩·검색

**LLM(Large Language Model, 대규모 언어 모델)** 은 대량의 텍스트 패턴을 바탕으로 다음 토큰을 예측하는 모델입니다. 여기서 **토큰(token)** 은 문장 전체가 아니라 모델이 처리하는 텍스트 조각입니다. 모델은 질문을 읽고 데이터베이스처럼 정확한 행을 찾아오는 것이 아니라, 제공된 입력과 학습된 패턴에서 다음에 올 가능성이 높은 토큰을 생성합니다. 그래서 그럴듯하지만 근거 없는 답, 즉 hallucination(환각)이 발생할 수 있으며, 이를 단순히 “모델이 거짓말한다”고만 보면 해결책을 찾기 어렵습니다.

**프롬프트(prompt)** 는 모델에 주는 지시와 문맥입니다. “당신은 인사 규정 도우미다. 근거 문서에 없는 내용은 모른다고 답하고, 답변은 JSON으로 반환하라” 같은 시스템 지시, 사용자의 질문, 검색된 문서 조각이 함께 프롬프트를 이룹니다. 좋은 프롬프트는 모델에게 역할과 출력 제약을 알려주지만, 최신 문서를 모델 내부에 저장하지는 않습니다. 문맥 창(context window)의 길이에도 제한이 있으므로 모든 문서를 통째로 넣는 방식은 비용과 정확도 모두에서 한계가 있습니다.

**임베딩(embedding)** 은 텍스트·이미지 등의 의미적 특징을 숫자 벡터로 바꾼 표현입니다. “연차 휴가 이월”과 “남은 휴가를 다음 해로 넘길 수 있나”는 문자열이 다르지만 의미가 가까울 수 있습니다. 문서 조각과 질문을 같은 임베딩 공간의 벡터로 만들고 거리 또는 유사도를 계산하면 키워드가 정확히 같지 않아도 관련 후보를 찾을 수 있습니다. 벡터 검색은 정답을 보장하는 마법이 아니라 후보를 고르는 방법입니다. 잘못 쪼갠 문서, 오래된 인덱스, 권한 없는 문서가 검색되면 생성 모델이 아무리 좋아도 답변 품질은 흔들립니다.

**검색(retrieval)** 은 질문에 관련된 문서 조각을 인덱스에서 고르는 단계입니다. 일반적인 RAG 파이프라인은 문서를 수집하고, 제목·작성일·권한 같은 메타데이터를 붙이고, 적절한 크기로 chunk(청크)로 나누고, 임베딩을 만들고, 질문 때 후보를 검색하고, 필요하면 키워드 검색과 재순위화(reranking)를 결합한 뒤, 선택된 근거를 모델 입력에 넣습니다. 마지막 답변이 틀렸을 때는 모델만 보지 말고 수집·청킹·검색·권한·생성 중 어느 단계가 실패했는지 분해해야 합니다.

## Fine-tuning은 무엇을 바꾸는가

Fine-tuning은 이미 학습된 기반 모델(base model)에 추가 학습 예시를 제공해 특정 작업에서 기대하는 입력→출력 관계를 더 잘 따르게 하는 과정입니다. 예를 들어 고객 상담 내용을 `배송 지연`, `환불`, `계정 접근`, `기타`로 분류하고, 반드시 정해진 JSON 스키마로 결과를 반환해야 하는 업무를 생각해 보겠습니다. 프롬프트 예시 몇 개만으로도 시작할 수 있지만, 문의 표현이 다양하고 라벨 경계가 조직 정책에 따라 미세하며 대량 요청에서 형식을 안정적으로 지켜야 한다면 품질 좋은 학습 예시가 유의미할 수 있습니다.

중요한 것은 Fine-tuning이 “회사 지식을 업로드하는 버튼”이 아니라는 점입니다. 학습 데이터는 모델 가중치에 통계적 패턴으로 반영됩니다. 특정 규정 문장 하나를 언제나 정확하게 인용하게 만들거나, 오늘 바뀐 정책을 즉시 반영하거나, 어떤 사용자가 어떤 문서를 볼 수 있는지 실행 시점에 구분하는 장치로 적합하지 않습니다. 모델이 학습 예시를 문자 그대로 저장·검색한다고 가정하면, 변경 관리와 삭제 요구에서 위험한 설계를 하게 됩니다.

Fine-tuning이 잘 맞는 신호는 다음과 같습니다.

1. 출력 구조가 중요하다. 예를 들어 코드가 아니라 엄격한 JSON, 정해진 필드, 제한된 라벨, 특정 톤을 꾸준히 만들어야 한다.
2. 좋은 답의 기준이 비교적 안정적이다. 같은 업무 규칙과 예시가 몇 주 뒤에도 유효하다.
3. 대표 입력과 정답 출력이 충분히 있고, 개인정보·비밀정보를 제거하거나 사용 권한을 확인할 수 있다.
4. 프롬프트와 모델 선택만으로는 반복 평가에서 개선이 정체됐다는 근거가 있다.
5. 학습 후에도 별도 평가 세트와 롤백 가능한 배포 절차를 운영할 수 있다.

반대로 문서의 최신성, 출처 표시, 접근 권한, 질문마다 다른 사실 확인이 핵심이면 Fine-tuning만으로 해결하려 하지 않는 편이 좋습니다. “2026년 10월 현재 배포 절차는?” 같은 질문에는 오늘의 runbook을 검색해 근거로 넣는 흐름이 자연스럽습니다. 학습 데이터에 지난달 runbook을 넣어 모델이 기억하기를 기대하면 오래된 답을 자신 있게 말할 위험이 있습니다.

### 학습 데이터는 정답 모음이 아니라 행동 명세다

Fine-tuning 데이터에서 가장 비싼 일은 파일 형식 변환이 아니라 **정답 기준 합의**입니다. 상담 분류라면 서로 다른 검토자가 같은 입력에 같은 라벨을 내리는지, 여러 이슈가 섞인 문의를 어떻게 처리하는지, 불확실할 때 `unknown`으로 보내는지부터 정해야 합니다. 이 합의 없이 과거 답변을 대량 수집하면, 모델은 조직의 모순과 편향을 더 일관되게 재현할 수 있습니다.

학습 예시는 실제 운영 입력의 분포를 대표해야 합니다. 짧고 정제된 예시만 넣고 실제의 오탈자·혼합 언어·누락된 정보·공격적 지시를 빼면 offline 평가에서는 좋아 보여도 배포 후 흔들립니다. 또한 훈련(training), 검증(validation), 테스트(test) 데이터는 역할을 나눠야 합니다. 특히 test set을 반복적으로 보고 학습 예시를 고치면 모델 선택에 test 결과가 새어 들어가 실제 일반화 성능을 알기 어렵습니다.

```json
{
  "messages": [
    {"role": "system", "content": "당신은 고객 문의 분류기다. 허용 라벨 중 하나만 JSON으로 반환한다."},
    {"role": "user", "content": "결제는 됐는데 주문 내역이 보이지 않아요."},
    {"role": "assistant", "content": "{\"label\":\"주문 조회\",\"needs_human\":false}"}
  ]
}
```

위 예시는 형식의 예일 뿐입니다. 실제 학습 전에는 `needs_human`이 필요한 기준, 민감한 문의를 처리하는 별도 큐, JSON 유효성 검사, 모델이 허용하지 않는 라벨을 냈을 때의 fallback을 애플리케이션에 구현해야 합니다. Fine-tuning은 입력 검증과 업무 승인 규칙을 대신하지 않습니다.

## RAG는 무엇을 바꾸는가

RAG는 모델의 가중치를 바꾸지 않고, 질문에 관련된 외부 문서를 찾아 프롬프트에 넣습니다. 이름을 풀면 Retrieval(검색)로 근거를 고르고, Augmented(증강)된 문맥을 모델에 제공해 Generation(생성)을 수행하는 방식입니다. 여기서 핵심은 생성 모델이 아니라 **검색 결과의 품질과 권한 경계**입니다.

사내 인사 챗봇을 예로 들면 문서 수집 단계는 인트라넷·PDF·위키의 원문과 버전·작성일·문서 소유자를 연결합니다. 청킹 단계는 제목과 문맥을 잃지 않도록 문서를 나눕니다. 인덱싱 단계는 각 chunk의 임베딩과 `department`, `classification`, `effective_date` 같은 메타데이터를 저장합니다. 질의 단계에서는 사용자의 신원과 조직을 기준으로 먼저 필터링하고, 그 안에서 후보를 검색합니다. 마지막으로 모델은 선택된 문서의 인용 정보를 포함해 답하거나, 근거가 부족하면 답변을 보류합니다.

이 흐름에서 흔한 실수는 권한 필터를 모델 프롬프트에만 적는 것입니다. “당신은 비밀 문서를 말하지 마라”라고 모델에 지시해도 검색 단계에서 비밀 chunk가 들어오면 노출 위험이 생깁니다. 접근 제어는 검색 전에 메타데이터 필터와 원문 시스템의 권한으로 강제해야 합니다. RAG는 검색 정확도뿐 아니라 **누가 어떤 근거를 검색할 수 있는가**를 설계하는 보안 문제입니다.

### 청킹과 메타데이터가 답변의 근거를 만든다

문서를 200자씩 기계적으로 자르면 표의 헤더와 값, 예외 조항과 본문, 제목과 규칙이 분리될 수 있습니다. 반대로 chunk가 너무 크면 관련 없는 문맥이 많이 섞여 검색과 토큰 비용이 나빠집니다. 적절한 크기는 문서 유형과 질문에 따라 달라집니다. 정책 문서는 조항·제목·개정일을 함께 유지하는 것이 중요할 수 있고, API 문서는 endpoint·요청·응답·제약을 함께 두는 것이 중요할 수 있습니다.

메타데이터는 필터와 운영을 가능하게 합니다. 최소한 원문 URL 또는 문서 ID, 제목, 버전, 마지막 수정일, 적용 시작일, 소유 팀, 분류 등급, 접근 그룹, chunk 위치를 보존하는 편이 좋습니다. 답변에 인용을 표시할 때도 이 정보가 필요합니다. “검색 결과 3번”보다 “휴가 규정 v4, 2026-09-01 적용, 제7조”가 사용자가 검토할 수 있는 근거입니다.

```text
질문
  → 인증된 사용자와 조직/권한 확인
  → 권한·유효기간 메타데이터로 후보 범위 제한
  → 키워드 + 벡터 검색으로 후보 생성
  → 재순위화와 중복 제거
  → 근거 chunk와 출처를 포함한 프롬프트 구성
  → 모델 답변
  → 인용·불확실성·피드백을 함께 반환
```

RAG에서 “검색 결과가 있었는데 답이 틀렸다”는 한 종류의 결함이 아닙니다. 관련 문서가 애초에 수집되지 않았을 수 있고, 청킹이 문맥을 잘랐을 수 있으며, 임베딩이 동의어를 놓쳤을 수 있고, 재순위화가 좋은 후보를 밀어냈을 수 있고, 모델이 주어진 근거를 무시했을 수 있습니다. 평가 로그에는 적어도 질문, 기대 근거, 실제 검색 상위 결과, 최종 답변, 인용, 사용자 권한 맥락을 남겨 원인을 분리할 수 있어야 합니다. 단, 민감한 질문·문서를 로그에 그대로 남기는 행위도 개인정보·비밀정보 정책의 대상입니다.

## 선택 기준: 지식 문제와 행동 문제를 먼저 나눈다

Fine-tuning과 RAG를 비교할 때 “어느 것이 더 똑똑한가”라는 질문은 도움이 적습니다. 먼저 실패를 다음 네 종류로 분해해 보세요.

| 실패 신호 | 먼저 검토할 접근 | 이유 |
| --- | --- | --- |
| 규정·가격·매뉴얼이 자주 바뀌어 최신 근거가 필요함 | RAG | 인덱스와 원문을 갱신해 실행 시점 지식을 제공할 수 있음 |
| 답변이 근거 문서를 인용해야 함 | RAG | 검색한 source와 문서 버전을 응답에 연결하기 쉬움 |
| 정해진 라벨·JSON·작성 양식을 일관되게 지켜야 함 | 프롬프트 후 Fine-tuning 검토 | 안정적 행동 예시를 학습 데이터로 표현할 수 있음 |
| 복잡한 업무 판단이 사람마다 다름 | 기준 합의와 평가 우선 | 학습·검색 어느 쪽도 모호한 정답을 대신 정의하지 못함 |
| 사용자 권한마다 보이는 지식이 달라짐 | 권한 필터가 있는 RAG | 요청마다 접근 가능한 문서가 달라야 함 |
| 도구 호출 순서와 실패 처리의 일관성이 중요함 | 워크플로·검증·평가 우선 | 모델만 학습시키지 말고 애플리케이션의 상태·승인 경계를 설계해야 함 |

실무의 좋은 시작은 대개 “프롬프트만 있는 baseline”입니다. 대표 질문 50~200개와 기대 답·근거·금지 조건을 모으고, 현재 모델이 어디서 실패하는지 봅니다. 다음으로 소수 문서를 가진 작은 RAG를 만들어 검색 재현율과 인용 정확도를 측정합니다. 이 단계에서 해결되는 문제라면 Fine-tuning 비용을 피할 수 있습니다. 출력 형식·분류·말투·도구 선택에서 실패가 남고, 안정적인 정답 예시가 충분할 때만 Fine-tuning 실험을 추가합니다.

## 예시: IT 헬프데스크를 두 흐름으로 나누기

한 회사의 IT 헬프데스크가 “VPN이 연결되지 않아요”, “노트북 교체 신청은 어디서 하나요?”, “퇴사자 계정은 언제 비활성화되나요?”를 처리한다고 하겠습니다. 여기에는 서로 다른 두 문제가 섞여 있습니다.

첫째, 최신 절차를 답하는 문제입니다. VPN 클라이언트 버전, 신청 링크, 계정 비활성화 기준은 문서가 바뀔 수 있고, 조직과 직군에 따라 보이는 문서도 달라질 수 있습니다. 이 부분은 권한을 필터링한 RAG가 어울립니다. 답변은 최신 runbook에서 찾은 단계와 링크를 인용하고, 검색된 근거가 없으면 티켓 생성 또는 담당자 연결로 보냅니다.

둘째, 티켓을 분류하고 우선순위를 정하는 문제입니다. 예를 들어 보안 사고 의심 문구가 있으면 즉시 `security_incident` 라우팅, 일반 설치 요청은 `standard_request`, 정보가 부족하면 `needs_clarification`을 반환한다는 규칙입니다. 이 부분은 프롬프트·규칙 엔진·스키마 검증으로 시작하고, 충분한 라벨 예시가 있으며 표현 다양성 때문에 일관성이 부족할 때 Fine-tuning을 검토할 수 있습니다.

두 흐름을 하나의 “AI 챗봇”으로 뭉뚱그리면 실패를 진단할 수 없습니다. 사용자가 잘못된 VPN 절차를 받았다면 검색한 문서가 오래됐는지, 권한 필터가 다른 조직 문서를 골랐는지, 모델이 근거를 무시했는지를 봐야 합니다. 티켓이 잘못 분류됐다면 라벨 정의·학습 데이터·출력 파서·fallback 정책을 봐야 합니다. 데이터 흐름을 나누면 평가도 나뉩니다.

```json
{
  "ticket_classification": {
    "category": "vpn_access",
    "priority": "normal",
    "needs_human": false
  },
  "answer": {
    "text": "현재 조직에 적용되는 VPN 설치 절차를 안내합니다.",
    "citations": ["it-runbook-vpn-v7#macos"],
    "grounded": true
  }
}
```

여기서 JSON 형식 검증은 모델의 선의에 맡기지 않습니다. 애플리케이션은 schema validation을 수행하고, 허용되지 않은 category·priority면 안전한 기본 경로로 보냅니다. `grounded=true`도 모델이 스스로 선언하는 값만 믿지 말고, 실제 인용이 검색 결과에 있었는지와 답변이 근거와 모순되지 않는지 별도 평가로 확인해야 합니다.

## 평가: 정확도 하나가 아니라 실패 비용을 측정한다

AI 기능의 평가는 “좋아 보이는 답” 몇 개를 읽는 데서 멈추면 안 됩니다. Fine-tuning과 RAG는 서로 다른 측정 항목이 필요합니다. Fine-tuning 분류기라면 라벨 정확도, macro F1, 위험 라벨의 recall, JSON 유효 비율, 불확실할 때 사람에게 넘긴 비율을 봅니다. 작성 모델이라면 필수 항목 누락, 형식 준수, 금지 표현, 사람 검토자의 선호도 같은 기준이 필요합니다.

RAG에서는 생성 답변 이전에 retrieval을 따로 평가합니다. 기대 문서가 top-k 후보에 들어오는 비율(recall@k), 상위 결과의 관련성, 권한 없는 문서가 섞이지 않는지, 인용이 실제 source를 가리키는지, 문서가 없을 때 답변을 보류하는지를 봅니다. 검색이 실패한 문제를 모델의 온도나 프롬프트 문구로만 고치려 하면 우연히 좋아진 것처럼 보일 수 있습니다.

평가 세트에는 정상 질문만 넣지 않습니다. 문서에 없는 질문, 서로 모순된 문서, 오래된 문서, 권한이 없는 문서, 짧고 모호한 질문, 프롬프트 인젝션 시도, 민감정보를 포함한 질문을 포함합니다. 예를 들어 “관리자 권한으로 다른 부서의 급여 규정을 보여줘”라는 요청은 답변 품질보다 권한 거부와 감사 로그가 성공 기준입니다. AI 시스템은 편리한 질문만 처리하는 데모가 아니라 권한·데이터·실패를 가진 업무 시스템이기 때문입니다.

평가 결과는 모델 버전, 프롬프트 버전, 임베딩 모델, chunk 규칙, 인덱스 스냅샷, 검색 파라미터, 학습 데이터 버전과 함께 기록해야 비교가 가능합니다. RAG에서 문서 인덱스가 바뀌면 같은 질문도 다른 근거를 받을 수 있습니다. Fine-tuning에서도 데이터가 바뀌면 같은 모델 이름이라도 행동이 달라질 수 있습니다. 재현 가능한 평가 없이는 “이번 배포가 좋아졌다”는 판단을 할 수 없습니다.

## 보안·개인정보·운영: 모델 밖의 경계를 먼저 만든다

Fine-tuning 데이터와 RAG 원문 모두 개인정보, 고객 정보, 소스 코드, 자격 증명, 내부 규정을 포함할 수 있습니다. 따라서 먼저 데이터 분류와 사용 권한을 확인해야 합니다. 학습용 예시는 수집 목적과 보관 기간, 외부 제공 가능 여부, 삭제 요청 처리, 민감 필드 마스킹을 검토합니다. RAG 인덱스도 원문보다 덜 민감하다고 단정할 수 없습니다. 임베딩은 원문을 복원하기 어렵다는 주장만으로 비밀정보 취급을 면제받지 않습니다.

권한은 입력·검색·출력 세 지점에서 생각합니다. 입력에서는 사용자의 인증과 조직 정보를 신뢰할 수 있는 서버 세션에서 받아야 합니다. 검색에서는 ACL(Access Control List, 접근 제어 목록) 또는 그룹 메타데이터로 후보 범위를 제한합니다. 출력에서는 인용·링크가 권한 없는 원문으로 우회하지 않는지, 모델이 검색되지 않은 민감정보를 추측해 말하지 않는지 정책과 검증을 둡니다. 모델에 “보안을 지켜라”라고 지시하는 것은 보조 장치일 뿐 접근 제어가 아닙니다.

운영 비용도 요청 비용만 보면 안 됩니다. RAG에는 문서 수집 실패, 변경 감지, 삭제 전파, 인덱스 재생성, 검색 지연, 임베딩 모델 교체, 권한 동기화가 있습니다. Fine-tuning에는 라벨링, 품질 검토, 학습 데이터 버전 관리, 배포·롤백, 모델별 평가, 데이터 사용 계약 확인이 있습니다. 더 적은 컴포넌트가 항상 더 싼 것도 아니고, 더 최신 모델이 항상 더 안전한 것도 아닙니다. 팀이 실제로 모니터링하고 복구할 수 있는 단순한 흐름부터 시작해야 합니다.

### 변경과 삭제도 데이터 파이프라인의 기능이다

RAG는 문서를 처음 넣는 순간보다 문서가 바뀌고 사라질 때 더 많은 운영 판단을 요구합니다. 원문에서 퇴직자 연락처가 삭제되었는데 벡터 인덱스에는 남아 있다면, 검색 결과가 오래된 개인정보를 다시 노출할 수 있습니다. 따라서 수집 파이프라인에는 원문 버전·수집 시각·삭제 이벤트를 추적하고, 변경된 문서만 재임베딩하거나 삭제된 chunk를 인덱스에서 제거하는 흐름이 필요합니다. 이 작업이 즉시 반영되는지, 일정 간격으로 반영되는지, 실패하면 누가 알림을 받는지도 서비스의 최신성 정의에 포함됩니다.

Fine-tuning도 삭제와 변경에서 자유롭지 않습니다. 학습 예시에 잘못된 라벨이나 사용하면 안 되는 정보가 들어갔다면, 단순히 원본 파일을 지웠다고 배포된 fine-tuned model의 행동이 자동으로 되돌아가지는 않습니다. 어느 데이터 버전으로 어떤 모델을 만들었는지 추적하고, 필요하면 데이터 정정·재학습·새 모델 배포·이전 모델 종료의 절차를 밟아야 합니다. 이 비용 때문에 자주 바뀌는 사실을 학습 데이터에 넣는 선택은 더 신중해야 합니다.

작은 팀이라도 문서 ID와 버전, 인덱스 생성 시각, 모델·프롬프트 버전, 평가 세트 버전만 기록해도 큰 차이를 만듭니다. 사용자로부터 “어제는 맞았는데 오늘은 왜 다르냐”는 문의를 받았을 때, 이 정보가 없으면 모델 탓으로 추측할 수밖에 없습니다. 정보가 있으면 문서 개정, 검색 인덱스 지연, 프롬프트 변경, 모델 교체 중 어디서 달라졌는지 확인할 수 있습니다.

## 결과를 사용자에게 안전하게 보여 주는 방법

검색 근거가 있는 답변이라도 확신에 찬 문장만 보여 주면 사용자는 자동화된 결과를 공식 결정으로 오해할 수 있습니다. 답변 화면에는 원문 제목·버전·링크와 함께, 현재 문서에서 찾지 못한 내용은 추측하지 않았다는 표시를 둘 수 있습니다. 규정 해석, 인사 조치, 보안 사고처럼 사람의 승인과 책임이 필요한 업무에서는 “참고 안내”와 “최종 결정 주체”를 분명히 분리해야 합니다.

또한 사용자의 피드백 버튼을 단순 만족도 수집으로 끝내지 않는 편이 좋습니다. ‘근거가 오래됨’, ‘관련 문서가 누락됨’, ‘권한이 맞지 않음’, ‘형식이 잘못됨’, ‘위험한 답변’처럼 실패 유형을 선택하게 하면 다음 개선의 우선순위를 정할 수 있습니다. RAG라면 문서·검색·인용 개선으로, Fine-tuning이라면 라벨 정의·학습 예시·출력 검증 개선으로 연결합니다. 사용자 피드백 자체에도 민감한 업무 정보가 들어갈 수 있으므로 보관 기간과 접근 권한을 정해야 합니다.

이런 UI와 운영 장치는 모델 성능이 높을 때도 필요합니다. 모델이 좋은 답을 자주 낸다는 사실은 특정 한 번의 답이 최신 근거·사용자 권한·업무 승인 조건을 만족한다는 증거가 아닙니다. AI 기능을 신뢰할 수 있게 만드는 것은 정답처럼 보이는 문장을 더 길게 생성하는 일이 아니라, 사용자가 근거와 한계를 확인하고 안전하게 다음 행동을 선택하도록 돕는 일입니다.

## 도입 순서: 학습보다 먼저 작게 증명한다

1. **업무 결정을 정의한다.** 사용자가 얻어야 할 결과, 허용 가능한 오류, 사람이 승인해야 하는 행동, 답변하지 말아야 할 범위를 문장으로 적습니다.
2. **평가 세트를 만든다.** 실제 요청을 비식별화하거나 승인받은 예시로 모으고, 정답·근거·금지 조건을 사람이 합의합니다.
3. **프롬프트 baseline을 만든다.** 모델이 이미 할 수 있는 것과 못 하는 것을 측정합니다. 이 단계 없이 Fine-tuning을 하면 개선 폭을 알 수 없습니다.
4. **지식 최신성이 필요하면 작은 RAG를 만든다.** 문서 수집·청킹·메타데이터·권한 필터·인용을 최소 범위에서 끝까지 연결합니다.
5. **검색과 생성 결과를 분리 평가한다.** 기대 근거가 검색됐는지, 근거를 사용해 답했는지, 근거가 없을 때 보류했는지를 각각 봅니다.
6. **행동 문제만 남았을 때 Fine-tuning 실험을 한다.** 안정적인 라벨·형식·작성 규칙과 충분한 검토된 예시가 있는지 확인합니다.
7. **배포 후 피드백과 롤백을 운영한다.** 실패 사례는 다음 데이터·프롬프트·문서 개선으로 연결하고, 위험한 자동 실행은 사람 승인 뒤에만 수행합니다.

이 순서는 느려 보이지만, 실제로는 잘못된 문제에 학습 비용을 쓰는 일을 줄입니다. 예를 들어 최신 문서를 답하게 하고 싶었던 요구를 Fine-tuning으로 시작하면, 데이터 수집·학습 뒤에도 출처와 권한이 해결되지 않아 RAG를 다시 만들게 될 수 있습니다. 반대로 단순 분류를 위해 거대한 벡터 DB와 복잡한 agent를 먼저 만들면, 고정된 라벨과 규칙만으로 해결할 문제를 과도하게 복잡하게 만듭니다.

## 한계와 적용 기준 Q&A

### Q. Fine-tuning을 하면 모델이 사내 문서를 절대 잊지 않나요?

A. 그렇지 않습니다. 추가 학습은 특정 예시의 패턴을 더 잘 따르도록 만드는 것이지, 버전이 바뀌는 문서를 정확한 검색 가능한 지식베이스로 보관하는 방식이 아닙니다. 최신성·출처·권한이 중요한 문서는 원문 관리와 RAG 또는 다른 조회 시스템을 사용하고, 필요할 때 학습은 형식·행동 보정에 한정하는 편이 안전합니다.

### Q. RAG에서 top-k 값을 크게 하면 정확도가 늘어나나요?

A. 관련 후보를 놓칠 확률은 줄 수 있지만, 관련 없는 문맥이 늘어 모델을 혼란스럽게 하고 토큰 비용과 지연을 키울 수 있습니다. 검색 결과의 관련성, chunk 품질, 재순위화, 권한 필터, 모델이 근거를 제대로 사용하는지 평가해 적절한 값을 정해야 합니다. 값 하나를 모든 문서 유형에 고정하지 않는 편이 좋습니다.

### Q. 모델이 JSON을 반환하니 애플리케이션 검증은 필요 없나요?

A. 필요합니다. 모델 출력은 잘못된 enum, 누락 필드, 추가 텍스트, 권한 없는 행동 제안을 포함할 수 있습니다. 서버는 JSON schema·타입·허용값을 검증하고, 실패하면 재시도·사람 검토·안전한 기본 경로로 보내야 합니다. 특히 결제·계정·배포 같은 도구 호출은 모델이 아니라 권한 있는 애플리케이션이 최종 실행해야 합니다.

### Q. 작은 팀도 RAG와 Fine-tuning을 동시에 도입해야 하나요?

A. 아닙니다. 질문이 적고 문서도 작다면 원문 링크를 안내하는 검색 페이지와 좋은 프롬프트만으로 충분할 수 있습니다. 최신 지식과 인용이 필요하면 작은 RAG부터, 반복되는 행동·형식 실패가 평가로 확인되면 Fine-tuning을 추가합니다. 운영할 수 없는 복잡성은 품질 기능이 아니라 새로운 장애 원인입니다.

## 마무리

Fine-tuning과 RAG는 경쟁하는 유행어가 아니라 서로 다른 실패를 다루는 도구입니다. RAG는 실행 시점에 최신 근거와 권한에 맞는 문서를 제공하는 데 강점이 있고, Fine-tuning은 안정적인 예시를 통해 출력 형식·분류·행동 패턴을 조정하는 데 쓸 수 있습니다. 어느 쪽도 모호한 업무 규칙, 권한 검증, 데이터 품질, 평가와 롤백을 대신하지는 않습니다.

따라서 먼저 질문을 “모델이 어떤 사실을 알아야 하는가?”와 “모델이 어떤 방식으로 행동해야 하는가?”로 나누세요. 전자에는 원문·검색·권한·인용을, 후자에는 명확한 라벨·검토된 예시·스키마 검증을 준비합니다. 작은 평가 세트와 baseline에서 시작해 실패를 단계별로 관찰하면, 필요 없는 학습이나 과도한 검색 인프라를 피하면서도 업무에 설명 가능한 AI 기능을 만들 수 있습니다.
