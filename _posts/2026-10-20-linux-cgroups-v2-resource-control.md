서버가 느려졌을 때 CPU 사용률을 보면 특정 프로세스가 자원을 많이 쓰고 있다는 사실은 알 수 있습니다. 그러나 “이 배치 작업은 웹 서비스의 응답 시간을 해치지 않는 범위에서만 CPU를 써야 한다”, “한 컨테이너가 메모리를 과도하게 써도 노드 전체가 죽으면 안 된다”처럼 **프로세스 집합의 자원 경계**를 만들려면 단순한 프로세스 우선순위만으로는 부족합니다. Linux의 **cgroups(control groups)** 는 바로 이 문제를 해결하기 위한 커널 기능입니다.

cgroups v2는 프로세스를 계층으로 묶고 CPU, 메모리, I/O, PID 같은 자원 사용을 관찰·제한·분배하는 통합 인터페이스입니다. Docker와 Kubernetes를 쓰면 직접 설정 파일을 만질 일이 적어 보이지만, 컨테이너의 CPU request/limit, OOMKilled, systemd 서비스의 MemoryMax 같은 현상은 결국 cgroups 위에서 동작합니다. 이 글은 v1과 v2의 차이부터 controller, 메모리 회수, CPU weight와 quota, systemd·컨테이너 적용 순서까지 설명합니다.

## 먼저 알아둘 기반 기술

운영체제는 CPU 시간, 물리 메모리, 디스크와 네트워크 I/O처럼 유한한 자원을 여러 프로세스에 배분합니다. 프로세스 하나의 PID와 사용량을 보는 것만으로는 웹 서버의 worker 열 개, 백그라운드 worker 다섯 개, 보조 프로세스가 합쳐서 얼마나 자원을 쓰는지 제어하기 어렵습니다. **프로세스 그룹** 단위로 예산과 우선순위를 정해야 하는 이유입니다.

**namespace** 는 프로세스가 보는 PID, 네트워크 인터페이스, 마운트 지점 같은 관점을 분리합니다. 반면 **cgroups** 는 프로세스가 실제로 쓸 수 있는 자원을 분배하고 제한합니다. Docker 컨테이너가 격리되어 보이는 것은 namespace 덕분이지만, `--memory`나 `--cpus` 같은 옵션이 효과를 내는 것은 cgroups 덕분입니다. 둘은 함께 자주 쓰이지만 같은 기술은 아닙니다.

**controller** 는 특정 종류의 자원을 다루는 cgroup 하위 시스템입니다. cgroups v2에는 CPU, memory, io, pids, cpuset 같은 controller가 있습니다. controller는 단순히 “제한 숫자”를 넣는 기능이 아니라, 누구에게 우선순위를 줄지, 초과 시 어떤 회수·대기·실패가 일어날지를 정의합니다. 따라서 운영 기준은 숫자 하나보다 초과했을 때 서비스가 어떻게 보일지를 먼저 정해야 합니다.

## cgroups v1과 v2의 차이

cgroups v1은 controller별로 서로 다른 계층을 만들 수 있었습니다. CPU는 A 그룹, 메모리는 B 그룹처럼 같은 프로세스가 controller마다 다른 구조에 놓일 수 있어 유연했지만 운영 관점에서는 해석이 복잡했습니다. 파일과 설정의 의미도 controller마다 달라, 도구와 문서가 혼재하는 문제가 있었습니다.

cgroups v2는 하나의 통합 계층(unified hierarchy)을 중심으로 controller를 다루는 방향입니다. 프로세스 그룹의 위치와 자원 정책 관계를 더 일관되게 만들고, 압박 신호와 위임(delegation) 모델을 개선했습니다. v1에서 보던 `cpu.shares`나 `memory.limit_in_bytes`와 v2의 `cpu.weight`, `memory.max`는 이름이 비슷해 보여도 의미와 적용 환경을 확인해야 합니다. 기존 명령을 그대로 복사하기보다 서버가 어떤 cgroup 버전을 사용 중인지 먼저 확인하는 습관이 필요합니다.

Linux 배포판·커널·컨테이너 런타임·Kubernetes 버전에 따라 v1, v2 또는 혼합 환경이 남아 있을 수 있습니다. 그래서 운영 문서에는 “cgroups를 쓴다”가 아니라 어떤 버전과 어떤 런타임 드라이버를 쓰는지 적어야 합니다. 경로가 `/sys/fs/cgroup` 아래에 있다고 해서 모든 controller와 기능이 동일하게 활성화된 것은 아닙니다.

## 계층과 위임: 누가 자원 정책을 정하는가

cgroups는 트리 구조입니다. 상위 cgroup이 자원을 배분하고 하위 cgroup이 그 범위 안에서 다시 나눌 수 있습니다. 예를 들어 호스트 전체 아래에 `system.slice`, `user.slice`, `kubepods.slice` 같은 큰 그룹이 있고, 그 아래에 서비스·Pod·컨테이너가 위치할 수 있습니다. 상위 그룹이 가진 제한을 하위 그룹이 초과할 수 없으므로, 노드 전체 예산과 애플리케이션 예산을 연결해 생각할 수 있습니다.

**delegation** 은 상위 관리자가 특정 하위 트리의 관리 권한을 런타임이나 사용자에게 넘기는 방식입니다. systemd가 서비스 단위의 cgroup을 만들고 컨테이너 런타임이 그 아래 컨테이너를 관리하는 환경에서는, 서로 다른 도구가 같은 트리를 무질서하게 수정하지 않도록 경계를 지켜야 합니다. 호스트 관리자가 컨테이너 내부의 cgroup 파일을 직접 덮어쓰면 런타임의 상태와 실제 커널 상태가 달라질 수 있습니다.

따라서 운영 변경은 소유한 계층에서 수행합니다. systemd 서비스라면 systemd unit의 자원 옵션을, Kubernetes Pod라면 resource requests/limits와 kubelet 설정을, 컨테이너 실험이라면 런타임 옵션을 우선 사용합니다. `/sys/fs/cgroup` 파일을 직접 쓰는 실험은 동작 원리를 배우는 데 유용하지만, 장기 운영의 선언적 설정을 대체하지 않습니다.

## CPU: weight와 max는 다른 질문에 답한다

CPU controller에서 **weight** 는 CPU가 부족할 때 상대적인 배분 비율을 나타냅니다. 두 서비스가 모두 CPU를 원할 때 높은 weight를 가진 그룹이 더 많은 CPU 시간을 받을 수 있지만, 경쟁이 없으면 낮은 weight 그룹도 CPU를 쓸 수 있습니다. 따라서 weight는 “평상시에는 유연하게 쓰되, 경쟁 시 우선순위를 주고 싶다”는 요구에 맞습니다.

반면 `cpu.max` 같은 quota 기반 제한은 일정 기간에 사용할 CPU 시간을 상한으로 정합니다. 예를 들어 배치 작업이 노드의 CPU를 모두 잠식하지 않게 만들 수 있지만, 실제 계산이 더 필요한 순간에는 **throttling** 이 발생해 작업 시간이 길어질 수 있습니다. 웹 요청 처리처럼 지연에 민감한 서비스에 너무 낮은 quota를 주면 평균 CPU는 낮아 보여도 p99 응답 시간이 크게 나빠질 수 있습니다.

CPU 제한을 정할 때는 코어 수만 보지 말고 스레드 모델, GC, burst 트래픽, CPU throttling 지표를 함께 봅니다. Java·Go처럼 런타임이 CPU 수를 인식해 worker 수를 정하는 애플리케이션은 cgroup 한도와 런타임 설정이 어긋날 수 있습니다. 과도한 제한은 이웃 워크로드 보호라는 이득보다 사용자의 지연이라는 비용을 만들 수 있으므로, 우선순위(weight)와 강한 상한(quota)을 구분해 사용합니다.

## 메모리: limit은 보호 장치이자 실패 정책이다

메모리 controller의 `memory.max`는 cgroup이 사용할 수 있는 메모리의 강한 상한을 나타냅니다. 한도를 넘는 할당이 계속되면 커널은 회수를 시도하고, 더 이상 해결하지 못하면 해당 cgroup과 관련된 프로세스가 OOM 상황을 맞을 수 있습니다. 그래서 메모리 limit은 “사용량 그래프를 예쁘게 만드는 숫자”가 아니라, 초과 시 어떤 작업이 실패할지 정하는 정책입니다.

`memory.high`는 절대 차단보다 먼저 압박과 회수를 유도하는 경계로 활용할 수 있습니다. 애플리케이션이 반복적으로 high를 넘는다면 정상 부하가 아니라 메모리 누수·캐시 크기·동시성 설정을 조사할 신호입니다. `memory.current`, `memory.events`, PSI(Pressure Stall Information) 같은 관찰값을 보면 단순 사용량 외에 reclaim과 OOM 관련 사건을 확인하는 데 도움이 됩니다.

컨테이너에서 OOMKilled가 보이면 limit이 작다는 결론부터 내리지 않습니다. heap, page cache, native memory, 임시 버퍼, sidecar의 사용량을 분리해 봅니다. limit을 단순히 올리면 당장의 종료는 줄어들 수 있지만, 노드 전체 여유를 줄여 다른 Pod의 eviction이나 전역 OOM 위험을 높일 수 있습니다. 실패를 피하는 방법과 노드를 보호하는 방법을 함께 계산해야 합니다.

## I/O와 PID: 흔하지만 놓치는 경계

CPU와 메모리만 제한해도, 한 배치가 디스크를 과도하게 읽고 쓰면 데이터베이스·로그·이미지 레이어가 기다리면서 서비스가 느려질 수 있습니다. v2의 io controller는 장치별 I/O 가중치·최대 처리량 같은 정책을 제공할 수 있지만, 블록 장치·파일 시스템·가상화 계층에 따라 관찰과 효과가 다릅니다. 특히 네트워크 스토리지나 관리형 디스크에서는 호스트 cgroup 설정만으로 기대한 수준의 제어가 되지 않을 수 있습니다.

`pids.max`는 cgroup 안에서 만들 수 있는 태스크 수를 제한합니다. 프로세스 폭주나 fork bomb가 노드 전체 PID를 고갈시키는 위험을 줄이지만, 너무 낮으면 worker pool, 브라우저 테스트, 짧은 프로세스를 많이 만드는 배치가 정상적으로 실패할 수 있습니다. PID 제한은 보안·안정성 관점의 유용한 보호막이지만, 애플리케이션의 동시성·자식 프로세스 구조를 이해하고 설정해야 합니다.

I/O와 PID 문제는 CPU 사용률 그래프에 잘 드러나지 않습니다. 서버가 느린데 CPU·메모리는 여유 있어 보인다면 iowait, 디스크 latency, process count, cgroup events를 함께 확인해야 합니다. 자원 제어는 특정 controller 하나를 튜닝하는 일이 아니라, 병목이 어느 자원에 있는지 찾아 적절한 경계를 만드는 일입니다.

## systemd에서의 적용

systemd는 서비스와 사용자 세션을 cgroup으로 관리합니다. `systemctl status`에서 보이는 서비스는 보통 자체 cgroup을 가지며, unit 파일이나 drop-in 설정으로 `CPUWeight=`, `CPUQuota=`, `MemoryHigh=`, `MemoryMax=`, `TasksMax=` 같은 정책을 선언할 수 있습니다. 이렇게 하면 재부팅과 재배포 뒤에도 정책이 남고, 서비스 정의와 자원 경계를 함께 코드 리뷰할 수 있습니다.

예를 들어 야간 보고서 생성 서비스가 낮에도 CPU를 많이 쓰는 문제라면 우선 CPUWeight를 낮춰 경쟁 시 웹 서비스에 우선권을 줄 수 있습니다. 그래도 노드 안정성을 해칠 만큼 폭주한다면 quota나 스케줄링 분리를 검토합니다. 메모리 누수가 의심되는 서비스에 MemoryMax를 바로 강하게 걸기보다, high에서 압박 신호와 사용량 추세를 관찰한 뒤 재시작·수정·limit 중 어떤 대응이 맞는지 정합니다.

systemd 설정을 바꿀 때는 서비스가 실제로 해당 unit cgroup에 속하는지와 reload·restart 뒤 값이 적용됐는지를 확인합니다. shell에서 직접 실행한 프로세스는 서비스 cgroup에 들어가지 않을 수 있습니다. 자원 제한이 동작하지 않는 것처럼 보이면, 숫자보다 먼저 프로세스 트리와 cgroup 경로를 확인해야 합니다.

## Docker와 Kubernetes에서의 의미

Docker의 `--cpus`, `--memory`, `--pids-limit` 옵션은 런타임이 cgroup 설정으로 변환하는 대표적인 인터페이스입니다. Kubernetes에서는 컨테이너 resource request와 limit, QoS class, kubelet의 cgroup driver가 관련됩니다. request는 스케줄러가 노드 배치를 판단하는 입력이고, limit은 런타임에서 실제 사용 상한과 연결됩니다. 둘을 같은 숫자로 둔다고 항상 안정적이라는 뜻은 아니며, 워크로드의 burst와 노드의 overcommit 정책을 고려해야 합니다.

Kubernetes에서 메모리 limit을 넘은 컨테이너가 재시작되는 현상은 애플리케이션 오류처럼 보일 수 있지만, 실제로는 cgroup 메모리 경계의 결과일 수 있습니다. 반대로 CPU limit은 종료보다 throttling으로 나타나기 쉬워, Pod가 살아 있지만 응답이 느린 상태를 만들 수 있습니다. `kubectl top`의 순간 사용량만 보고 원인을 단정하지 말고, throttling·memory events·애플리케이션 latency를 연결해야 합니다.

컨테이너 런타임, kubelet, systemd가 모두 cgroup 트리에 관여하는 환경에서는 드라이버 설정 불일치도 문제를 만들 수 있습니다. 운영 클러스터의 cgroup 버전과 드라이버는 플랫폼 팀이 표준화하고, 애플리케이션 팀은 Pod 명세를 통해 의도를 표현하는 분업이 바람직합니다. 노드의 cgroup 파일을 직접 수정해 일시적으로 고치는 방식은 다음 재스케줄·재시작에서 사라질 수 있습니다.

## 한계와 적용 기준 Q&A

### Q. 모든 서비스에 동일한 CPU·메모리 limit을 주면 안전한가요?

A. 아닙니다. 요청 처리량, burst 특성, 캐시, 런타임, 중요도가 다릅니다. 동일한 limit은 설정 관리는 쉬워도 어떤 서비스에는 과도한 throttling을, 다른 서비스에는 낭비를 만들 수 있습니다. 측정한 사용량과 실패 시 영향으로 등급을 나누는 편이 낫습니다.

### Q. OOMKilled가 발생하면 memory limit만 올리면 되나요?

A. 우선 어떤 메모리가 늘었는지 확인해야 합니다. 누수·대용량 요청·캐시·native memory·sidecar 중 원인이 다를 수 있습니다. limit 상향은 노드 여유와 다른 워크로드의 안전을 함께 검토한 뒤 선택합니다.

### Q. cgroups로 네트워크 대역폭도 완전히 제어할 수 있나요?

A. cgroups 자체의 핵심 controller는 CPU·메모리·I/O·PID 등이며, 네트워크 제어는 tc, eBPF, CNI, 클라우드 네트워크 정책 등과 함께 설계하는 경우가 많습니다. 요구가 패킷 정책인지 대역폭 보장인지 먼저 구분해야 합니다.

### Q. v1에서 v2로 바꾸면 설정 파일만 이름을 바꾸면 되나요?

A. 아닙니다. 계층 모델과 controller의 의미, 런타임·systemd 호환성을 확인해야 합니다. 지원하는 커널과 배포판 문서, 현재 workload의 관찰 지표를 기준으로 단계적으로 전환합니다.

## 마무리

cgroups v2는 프로세스를 묶어 자원을 제한하는 기능을 넘어, 한 워크로드의 폭주가 다른 서비스와 노드 전체를 해치지 않게 만드는 운영 경계입니다. CPU는 경쟁 시 비율과 절대 상한을 구분하고, 메모리는 초과 시 실패 정책으로 이해하며, I/O와 PID도 병목·안정성 관점에서 확인해야 합니다. 작은 배치 서비스나 비핵심 Pod 하나부터 사용량·압박·실패 신호를 관찰하고, 그 결과를 systemd나 Kubernetes의 선언적 설정으로 옮겨 보세요. 이것이 컨테이너 자원 옵션을 숫자 암기가 아닌 운영 설계로 쓰는 방법입니다.

## 자원 값을 정하는 실제 순서

limit 값을 먼저 정하고 모니터링을 붙이면 숫자가 근거처럼 보이지만, 더 안전한 순서는 반대입니다. 우선 정상 트래픽과 피크 트래픽에서 CPU, RSS, page cache, I/O 대기, 프로세스 수를 관찰합니다. 그 다음 정상적인 burst를 감당할 여유와, 폭주했을 때 다른 서비스에 남겨야 할 여유를 따로 정합니다. 마지막으로 변경 전후의 지연·오류·throttling·OOM 이벤트를 비교합니다. 이 순서는 값이 완벽하다는 보장은 없지만, 설정이 왜 존재하는지 설명할 근거를 만듭니다.

예를 들어 웹 API가 평소 0.3 CPU를 쓰지만 트래픽 급증 때 1.2 CPU가 필요하고, 같은 노드의 배치가 CPU를 많이 쓰는 상황을 생각해 봅시다. 웹 API에는 경쟁 시 우선권을 주는 weight를 높이고, 배치에는 낮은 weight 또는 적절한 quota를 줄 수 있습니다. 그러나 API에 너무 낮은 quota를 주면 burst를 처리하지 못해 queue가 쌓입니다. 이때 답은 단순히 quota를 없애는 것이 아니라, 노드 분리·autoscaling·worker 수 조정·배치 시간 이동 중 무엇이 병목을 가장 작게 해결하는지 비교하는 것입니다.

메모리도 평균값보다 상위 사용량과 증가 패턴을 봅니다. JVM의 heap 설정, Python worker의 동시 요청, 이미지 처리 버퍼, 파일 cache, sidecar가 함께 쓰는 메모리를 구분합니다. 메모리 사용량이 천천히 계속 증가하면 limit 상향보다 누수 조사와 재시작 정책이 우선일 수 있습니다. 급격한 spike가 정상 작업의 일부라면 request와 limit의 차이, 큐잉, 작업 분할을 검토합니다.

## 관찰 항목과 경보를 연결하는 법

cgroups 설정이 제대로 동작하는지 확인하려면 CPU·메모리 사용률만으로는 부족합니다. CPU 정책에서는 throttling 횟수와 throttled time, 요청 지연, run queue를 함께 봅니다. CPU 사용률이 40%여도 quota 때문에 짧은 기간마다 멈추면 사용자는 느린 서비스를 경험할 수 있습니다. 메모리 정책에서는 `memory.current`와 `memory.events`, OOM 관련 이벤트, PSI의 memory pressure, 컨테이너 재시작 수를 연결합니다.

I/O 정책은 디스크 latency, queue depth, iowait, 작업별 처리 시간을 같이 봅니다. PID 정책은 현재 태스크 수와 생성 실패 로그를 연결합니다. 경보는 단순히 “limit의 80%”로 통일하지 않습니다. 캐시가 커졌다가 회수되는 서비스와 memory.high를 지속적으로 넘는 서비스의 위험은 다릅니다. 중요한 것은 어떤 신호가 사람의 조사 또는 자동 완화를 요구하는지 정하는 것입니다.

관찰 데이터에는 cgroup 경로·서비스 이름·Pod 이름처럼 원인을 찾을 수 있는 식별자가 필요하지만, 무제한 label은 모니터링 시스템의 카디널리티를 높일 수 있습니다. 짧게 살아나는 Job ID나 전체 파일 경로를 메트릭 label로 쓰기보다, 상세 사건은 로그·trace에 남기고 메트릭은 서비스·노드·controller 단위로 집계합니다. 자원 관리의 관찰도 데이터 비용과 개인정보 원칙을 따릅니다.

## 장애 분석 예시

한 Pod가 간헐적으로 OOMKilled 되고 있다고 가정해 봅시다. 먼저 Pod limit과 실제 종료 시점의 memory current, 애플리케이션 heap·native memory, sidecar 사용량, 노드의 memory pressure를 확인합니다. 특정 요청 뒤에만 종료된다면 payload 크기나 동시 요청 수가 원인일 수 있고, 장시간 뒤에만 종료된다면 누수 또는 cache의 무제한 증가를 의심할 수 있습니다. 원인이 확인되기 전 limit만 두 배로 올리면 장애 시점은 늦춰도 노드 위험은 커질 수 있습니다.

다른 예로, CPU가 여유인데 API p99가 나빠진다면 cgroup CPU throttling을 봅니다. Pod의 사용률이 limit에 닿지 않아 보이는 것은 집계 간격의 착시일 수 있습니다. 짧은 주기의 quota 소진과 재개가 반복되면 요청은 처리되지만 꼬리가 길어집니다. throttling이 확인되면 limit 상향만이 아니라 worker concurrency, GC, 다른 Pod와의 배치, CPU weight, HPA 지표를 함께 검토합니다.

배치가 데이터베이스를 느리게 한다면 배치 프로세스가 CPU보다 I/O를 과도하게 쓰는지 살핍니다. 같은 디스크에 DB 로그와 대량 파일 처리가 공존하면 cgroup의 io 정책 또는 스토리지 분리, 배치 시간 조정이 필요할 수 있습니다. 이 분석의 목표는 “제한을 더 세게 걸기”가 아니라, 어떤 공유 자원 때문에 서로 영향을 주는지 확인하는 것입니다.

## 운영 변경과 롤백

자원 limit은 배포 설정의 일부로 관리합니다. 누가 어떤 이유로 값을 바꿨는지, 어떤 부하에서 검증했는지, 초과하면 어떤 현상이 예상되는지를 변경 기록에 남깁니다. 즉석에서 cgroup 파일을 바꿔 장애를 완화했다면, 효과와 부작용을 확인한 뒤 systemd unit·Helm chart·Pod manifest 같은 선언적 설정에 반영합니다. 그렇지 않으면 다음 재시작에서 사라지거나 다른 노드와 설정이 달라집니다.

롤백도 값 하나를 원래대로 돌리는 일만은 아닙니다. 낮은 메모리 limit 때문에 재시작이 늘었다면 limit을 올린 뒤 누수·부하 원인 조사를 계속해야 합니다. CPU quota를 풀어 지연이 회복됐다면 이웃 서비스가 영향을 받지 않는지 확인합니다. 변경 전후의 핵심 지표와 사용자의 오류율을 정해 두면, 롤백 여부를 감이 아니라 관찰값으로 판단할 수 있습니다.

Kubernetes 환경에서는 workload manifest 변경, scheduler 배치, autoscaler, 노드 여유가 함께 변할 수 있습니다. canary Pod 또는 일부 deployment에서 먼저 적용하고, 충분한 기간 동안 peak와 비정상 종료를 관찰한 뒤 확대합니다. cgroups는 커널 수준 기능이지만 안전한 변경 방식은 일반 애플리케이션 배포와 같습니다.

## cgroups가 해결하지 않는 문제

cgroups는 자원 경계를 만들지만 애플리케이션의 메모리 누수, 느린 SQL, 무한 재시도, 잘못된 queue 설계를 고치지는 않습니다. limit을 걸어 노드를 보호할 수는 있어도 사용자 요청이 실패하는 근본 원인은 남을 수 있습니다. 따라서 cgroups 이벤트는 종종 더 깊은 원인을 조사하라는 신호입니다.

또한 노드에 충분한 자원이 없으면 모든 cgroup 정책을 잘 설정해도 기대한 성능을 만들 수 없습니다. request를 합산하면 노드 용량을 넘고, 여러 workload가 같은 외부 데이터베이스·네트워크·스토리지를 공유하면 CPU·메모리 경계만으로 격리되지 않습니다. 자원 제어는 capacity planning, 애플리케이션 backpressure, 배치 설계, 관측성과 함께 사용해야 합니다.

특히 컨테이너 limit을 보안 격리의 전부로 생각하면 안 됩니다. cgroups는 자원 사용을 제어하지만 파일·네트워크·권한·커널 공격면을 격리하는 기능은 namespace, capabilities, seccomp, SELinux/AppArmor, 네트워크 정책 같은 다른 계층이 담당합니다. 어떤 문제를 어떤 경계로 막는지 구분하는 것이 안전한 운영의 출발점입니다.

## 호스트에서 확인할 최소 진단 절차

문제가 난 순간에 설정을 바꾸기보다, 먼저 해당 프로세스가 어느 cgroup에 속하는지 확인합니다. v2 환경에서는 `/proc/<PID>/cgroup`과 `/sys/fs/cgroup` 아래의 경로를 통해 위치를 확인할 수 있습니다. 그 다음 그 경로의 `cpu.stat`, `memory.current`, `memory.events`, `pids.current`처럼 controller별 상태 파일을 읽습니다. 이 값은 운영체제와 런타임 구성에 따라 달라질 수 있으므로, 아래 명령은 원리를 익히기 위한 예시이며 서비스 소유 도구의 상태 화면도 함께 봐야 합니다.

```bash
# 현재 호스트가 cgroups v2 통합 계층을 쓰는지 확인
stat -fc %T /sys/fs/cgroup

# 특정 프로세스가 속한 cgroup 경로 확인
cat /proc/12345/cgroup

# 확인한 경로에서 CPU throttling과 메모리 이벤트를 조회
cat /sys/fs/cgroup/<경로>/cpu.stat
cat /sys/fs/cgroup/<경로>/memory.current
cat /sys/fs/cgroup/<경로>/memory.events
```

숫자를 읽는 순서도 중요합니다. `cpu.stat`의 throttling 관련 값이 증가하는데 요청 지연도 함께 늘면 CPU quota가 원인 후보가 됩니다. 반대로 CPU throttling이 없고 `memory.events`의 high 또는 oom 관련 값이 늘면 메모리 압박을 더 먼저 봐야 합니다. 상태 파일 하나가 비어 있거나 원하는 controller가 없다면 실패한 것이 아니라, 해당 controller가 활성화되지 않았거나 상위 계층에서 위임되지 않은 것일 수 있습니다. 권한 오류를 우회하려고 무조건 root로 파일을 쓰는 대신, 서비스의 systemd unit·컨테이너 명세·플랫폼 정책을 확인하는 편이 안전합니다.

## 선언적 설정으로 옮기는 예시

systemd가 관리하는 사내 배치 서비스라면 일회성 shell 명령 대신 drop-in에 의도를 기록할 수 있습니다. 다음 값은 모든 서비스에 적용할 권장값이 아니라, 경쟁 시 우선순위를 낮추고 메모리 폭주를 관찰하려는 예시입니다. 특히 `MemoryMax`는 초과하면 작업 실패로 이어질 수 있으므로, 사전 관찰 없이 복사하면 안 됩니다.

```ini
# /etc/systemd/system/report-worker.service.d/resources.conf
[Service]
CPUWeight=50
MemoryHigh=1G
MemoryMax=1500M
TasksMax=512
```

설정 후에는 `systemctl daemon-reload`와 서비스 재시작이 필요한지 운영 절차에 따라 판단하고, 서비스가 다시 시작되어도 그 cgroup에 들어가는지 확인합니다. 오류가 발생했을 때는 설정 파일을 지우는 것만이 롤백이 아닙니다. 메모리 제한을 완화했다면 어떤 작업이 한도를 넘었는지 기록하고, CPU weight를 되돌렸다면 다른 서비스의 지연이 악화되지 않았는지 비교해야 합니다. 설정값은 애플리케이션 팀, 플랫폼 팀, SRE가 서로 다른 이유로 볼 수 있으므로 변경 목적과 예상 실패 형태를 함께 남기는 것이 좋습니다.

Kubernetes에서도 같은 원칙이 적용됩니다. request는 스케줄러에게 필요한 최소 용량을 알리고, limit은 실행 중 사용할 수 있는 경계를 만듭니다. 아래처럼 request와 limit을 적어도, CPU limit이 있는 환경에서는 burst 시 throttling이 생길 수 있고 메모리 limit은 종료로 나타날 수 있습니다. 따라서 매니페스트 리뷰에서 숫자뿐 아니라 피크 부하, 재시도 정책, 수평 확장, 우선순위를 함께 논의해야 합니다.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

## 팀이 합의해야 할 자원 경계

자원 제한은 개발팀이 숫자를 적고 플랫폼팀이 승인하는 형식적 절차가 되기 쉽습니다. 하지만 실제로는 서비스 계약입니다. 제품 담당자는 어느 정도의 지연과 재시도가 허용되는지, 개발팀은 프로세스·캐시·동시성 모델이 어떤지, 플랫폼팀은 노드의 여유와 다른 워크로드의 중요도가 어떤지 알고 있습니다. 이 세 정보가 만나야 “메모리 1Gi”가 의미 있는 값이 됩니다.

우선 서비스별로 실패 우선순위를 정할 수 있습니다. 결제가 멈추는 일이 가장 위험한 API라면 경쟁 시 CPU weight를 더 높게 주고, 대량 재처리 배치는 언제든 늦어질 수 있도록 별도 노드나 낮은 우선순위로 둘 수 있습니다. 반대로 메모리를 많이 쓰는 분석 작업은 일정 시간 안에 끝나야 할 수 있으므로, 무조건 limit을 낮추기보다 전용 노드·큐·작업 분할을 고려해야 합니다. cgroups는 이 선택을 구현하는 도구이지, 우선순위를 대신 정해 주지 않습니다.

용량 계획과의 연결도 빼놓을 수 없습니다. 모든 Pod의 limit 합계가 노드 용량보다 크다고 바로 잘못은 아니지만, 동시에 burst가 일어나는 상황을 감당할 수 있는지는 별도 질문입니다. request 합계, 실제 상위 사용량, 노드 reserve, eviction 정책, 외부 의존성의 병목을 함께 검토해야 합니다. 자원 정책을 정기적으로 되돌아보면 오래된 limit이 새 기능이나 트래픽 변화에 맞지 않는 문제를 조기에 발견할 수 있습니다.

## 부하 시험에서 확인할 질문

cgroups 정책은 평상시 그래프만 보고 확정하기 어렵습니다. 작은 범위에서 부하를 늘리며 “무엇을 보호하려는가”를 확인하는 시험이 도움이 됩니다. 웹 서비스라면 처리량을 조금씩 올릴 때 평균 응답 시간뿐 아니라 p95·p99 지연, 오류율, CPU throttling, 메모리 압박, 재시작 횟수를 함께 봅니다. 배치라면 총 처리 시간과 I/O 대기, 다른 서비스의 지연을 같이 비교합니다. 목표는 최고 처리량을 기록하는 것이 아니라, 경계를 넘었을 때 어떤 사용자가 어떤 방식으로 영향을 받는지 알아내는 것입니다.

시험은 실제 고객 데이터를 그대로 쓰지 않고, 승인된 테스트 환경과 대표 데이터로 수행해야 합니다. 개발 환경의 단일 컨테이너 결과를 운영 노드 전체의 보장으로 해석하면 안 됩니다. CPU 코어 수, 스토리지 성능, 다른 워크로드, 런타임 버전, 오토스케일 조건이 다르면 결과도 달라집니다. 대신 환경 차이를 기록해 두면, 운영에서 관찰한 현상이 테스트와 달라졌을 때 어떤 가정을 다시 확인할지 알 수 있습니다.

예를 들어 메모리 상한을 새로 도입할 때는 낮은 값부터 실패를 유도하려는 것이 아니라, 정상적인 최대 요청과 비정상적인 대용량 요청을 구분할 수 있는 시나리오를 준비합니다. 정상 요청에서 `memory.high`를 지속적으로 넘는다면 캐시·동시성·상한이 맞지 않을 수 있습니다. 비정상 요청 하나가 상한을 넘을 때 서비스가 명확한 오류를 돌려주는지, 재시도 폭풍이 생기지 않는지, 노드의 다른 서비스가 보호되는지 확인합니다. 이 결과를 바탕으로 limit, 요청 크기 제한, 큐, 작업 분할 중 어느 조합이 필요한지 정할 수 있습니다.

마지막으로 시험 결과는 설정값과 분리하지 않습니다. 어떤 controller를 켰는지, 상위 cgroup 정책은 무엇인지, 동시 사용자 수와 데이터 크기는 얼마였는지, 관찰한 지표는 무엇인지 남깁니다. 그래야 다음 분기 트래픽이 늘거나 애플리케이션 런타임이 바뀌었을 때 과거 값의 맥락을 복원할 수 있습니다. cgroups v2의 중요한 가치는 제한 파일 자체보다, 자원 예산과 실패 방식에 대해 팀이 검증 가능한 언어로 대화하게 만드는 데 있습니다.
