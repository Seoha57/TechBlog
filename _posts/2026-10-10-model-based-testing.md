테스트 케이스가 늘어날수록 빠지기 쉬운 것은 화면 하나가 아니라 **순서**입니다. 로그인 → 장바구니 담기 → 결제 대기 → 결제 승인 → 취소 → 환불처럼 시스템은 이전 행동에 따라 다음에 가능한 행동이 달라집니다. 각 API를 따로 호출해 성공 응답을 확인해도, 이미 취소된 주문을 다시 취소할 때 어떤 오류가 나야 하는지, 결제 승인 전에 배송 처리가 가능한지, 세션이 만료된 뒤 어느 화면으로 돌아가야 하는지는 놓치기 쉽습니다. 테스트 케이스를 사람이 하나씩 나열하면 대표 경로는 잘 작성할 수 있어도 상태와 전이의 조합이 늘어날수록 누락을 발견하기 어려워집니다.

**MBT(Model-Based Testing, 모델 기반 테스트)** 는 시스템이 어떻게 행동해야 하는지를 모델로 표현하고, 그 모델에서 테스트 경로를 만들거나 실제 시스템의 동작을 모델과 비교하는 테스트 접근입니다. 가장 익숙한 모델은 FSM(Finite State Machine, 유한 상태 머신)입니다. 상태는 `로그인됨`, `결제 대기`, `취소됨`처럼 관찰 가능한 조건을, 전이는 `로그인`, `결제 승인`, `취소 요청`처럼 상태를 바꾸는 행동을 뜻합니다. 테스트는 그래프의 한 경로가 되어 여러 행동의 순서를 실행하고, 매 단계에서 실제 시스템이 기대한 상태에 도달했는지 확인합니다.

MBT는 테스트 케이스를 자동으로 많이 만드는 기술로만 이해하면 안 됩니다. 먼저 모델 자체가 요구사항을 명확하게 해야 합니다. 잘못된 모델에서 생성한 수천 경로는 수천 개의 잘못된 테스트일 수 있습니다. 반대로 모델이 너무 상세하면 애플리케이션 구현을 다시 만드는 비용이 들어 유지하기 어렵습니다. 이 글은 모델을 어디까지 만들고, 어떤 경로를 생성하며, 기존 단위·통합·탐색적 테스트와 어떻게 역할을 나눌지를 설명합니다.

## 먼저 알아둘 기반 기술: 상태·전이·가드·오라클·커버리지

**상태(state)** 는 시스템이 지금 어떤 조건에 있는지 나타내는 관찰 가능한 모습입니다. 주문 시스템에서 `결제 대기`, `결제 완료`, `배송 중`, `취소 완료`가 상태가 될 수 있습니다. 상태는 데이터베이스의 한 컬럼 값과 항상 일치할 필요는 없습니다. 예를 들어 `결제 승인됨 + 재고 예약됨 + 배송지 검증됨`처럼 여러 데이터와 외부 작업의 조합이 하나의 업무 상태를 만들 수 있습니다. 좋은 상태 이름은 구현 테이블이 아니라 사용자·업무 담당자가 이해하는 규칙을 말합니다.

**전이(transition)** 는 상태를 바꾸는 사건 또는 행동입니다. 사용자의 버튼 클릭, API 호출, 스케줄러 작업, 외부 결제사의 콜백이 전이가 될 수 있습니다. 전이에는 시작 상태, 종료 상태, 입력, 기대 결과를 둡니다. `결제 대기 → 결제 완료` 전이는 단순히 상태 문자열을 바꾸는 일이 아니라 결제 승인 응답, 재고 확정, 영수증 발행 같은 부수 효과를 동반할 수 있습니다. MBT에서 중요한 것은 전이가 가능한 경우뿐 아니라 **가능하면 안 되는 경우**를 모델에 드러내는 일입니다.

**가드(guard)** 는 전이가 허용되는 조건입니다. 예를 들어 `배송 시작`은 결제가 완료되고 재고가 확보된 주문에서만 가능하다는 조건이 가드가 될 수 있습니다. 가드는 입력값·권한·시간·외부 상태에 따라 달라질 수 있습니다. 모델에 모든 세부 조건을 집어넣으면 복잡해지므로, 테스트 목적에 맞는 수준으로 추상화해야 합니다. 중요한 업무 제약은 가드로 표현하고, 개별 입력 검증은 별도 단위·API 테스트에 맡기는 방식이 흔합니다.

**테스트 오라클(test oracle)** 은 실제 결과가 맞는지 판단하는 기준입니다. 모델이 `취소됨` 상태라고 말해도 실제 시스템에서 무엇을 읽어 확인할지 정하지 않으면 테스트가 끝나지 않습니다. API 응답 코드, 화면의 상태 라벨, DB 조회, 이벤트 발행 여부, 외부 mock 호출 횟수처럼 관찰 가능한 증거를 전이에 연결합니다. ‘상태가 됐을 것’이라고 추측하는 테스트보다, 각 전이가 남겨야 하는 관찰 결과를 명시하는 테스트가 신뢰할 수 있습니다.

**커버리지(coverage)** 는 모델의 어느 부분을 실행했는지를 나타냅니다. 상태 커버리지는 모든 상태를 한 번 이상 방문했는지, 전이 커버리지는 모든 전이를 한 번 이상 실행했는지 봅니다. 경로 커버리지는 가능한 경로를 얼마나 탐색했는지 보지만, 루프와 분기가 있는 모델에서는 모든 경로가 폭발적으로 늘 수 있습니다. 그래서 ‘모든 경로’라는 말 대신, 위험한 전이 우선·모든 전이 1회·최대 길이 N·필수 요구사항 태그 같은 종료 조건을 정해야 합니다.

## 모델은 구현 다이어그램이 아니라 업무 규칙의 압축본이다

MBT 모델을 만들 때 화면·클래스·DB 테이블을 모두 그대로 그리면 모델이 코드의 그림자가 됩니다. 코드가 바뀔 때마다 모델도 같이 바꿔야 하고, 모델이 결함을 발견하기보다 같은 구현 가정을 반복할 가능성이 큽니다. 반대로 너무 추상적으로 `성공`과 `실패` 두 상태만 두면 순서 오류를 발견하지 못합니다. 모델은 테스트하려는 위험을 설명할 만큼 구체적이면서, 구현 변경에 끌려가지 않을 만큼 업무 중심이어야 합니다.

예를 들어 주문의 상태를 다음처럼 작게 시작할 수 있습니다.

```text
[장바구니]
  ├─ 주문 생성 ──> [결제 대기]
  │                   ├─ 결제 승인 ──> [결제 완료] ── 배송 시작 ──> [배송 중]
  │                   ├─ 결제 실패 ──> [결제 실패]
  │                   └─ 취소 요청 ──> [취소됨]
  └─ 장바구니 비움 ─> [장바구니]

[결제 완료] ── 취소 요청(가드: 출고 전) ──> [환불 대기] ── 환불 완료 ──> [취소됨]
```

이 모델은 모든 결제 수단·쿠폰·세금·배송 옵션을 표현하지 않습니다. 대신 `결제 대기에서 취소가 가능한가`, `배송 뒤에 취소 전이로 바로 갈 수 있는가`, `환불은 결제 완료 이후에만 가능한가`처럼 순서의 위험을 드러냅니다. 세금 계산의 경계값은 별도 단위 테스트, 쿠폰 조합은 Property-Based Testing, 결제사와의 메시지 형식은 계약 테스트가 더 잘 다룰 수 있습니다. 한 모델이 모든 테스트 역할을 맡지 않게 분리하는 것이 유지보수에 좋습니다.

모델을 검토할 때는 개발자만 보지 말고 PO(Product Owner), 기획자, 운영 담당자처럼 상태 전이의 규칙을 아는 사람과 함께 봅니다. `결제 실패` 뒤 재시도가 가능한지, `배송 중`에서도 부분 환불이 가능한지, 예약 만료는 어느 상태에서 일어나는지 같은 질문은 코드보다 업무 정책에서 답을 찾아야 할 때가 많습니다. 그림을 만드는 활동이 곧 요구사항의 빈틈을 발견하는 활동이 될 수 있습니다.

## 경로 생성: 무작위가 아니라 목적을 가진 탐색

모델 그래프가 준비되면 도구나 테스트 코드가 전이 경로를 만들 수 있습니다. GraphWalker 같은 도구는 상태를 vertex, 전이를 edge로 둔 그래프를 읽고, 무작위·가중치·최단 경로·모든 edge 방문 같은 전략으로 경로를 생성합니다. 그러나 생성 알고리즘을 선택하기 전에 ‘무엇을 보장하려는가’를 정해야 합니다.

**모든 상태 방문**은 화면 또는 업무 상태가 최소 한 번은 도달 가능한지 보기에 좋습니다. 하지만 상태에 들어오는 한 경로만 검사하고, 다른 전이가 빠질 수 있습니다. **모든 전이 방문**은 허용·차단 행동을 더 넓게 시험하지만, 전이가 많아지면 실행 시간이 늘어납니다. **위험 가중 경로**는 결제 취소·권한 변경·재시도·만료처럼 결함 비용이 큰 전이를 더 자주 선택하도록 할 수 있습니다. **최단 경로**는 특정 상태에 빠르게 도달해 재현 시나리오를 만들기 좋지만, 루프·반복·예외 경로를 거의 보지 못합니다.

무작위 경로는 예상하지 못한 조합을 찾는 데 도움이 되지만 재현성을 갖춰야 합니다. 생성 seed, 모델 버전, 선택한 전이, 입력 데이터, 실제 응답을 남기지 않으면 CI에서 한 번 실패한 경로를 개발자가 다시 만들기 어렵습니다. Property-Based Testing의 shrink처럼 MBT도 실패 경로를 더 짧게 줄여 ‘로그인 → 주문 생성 → 취소 → 배송 시작’ 같은 최소 반례로 남길 수 있으면 조사 비용이 줄어듭니다.

경로의 길이에도 상한이 필요합니다. 무한 재시도, 장바구니 추가/삭제 루프, 페이지 이동 루프가 있는 모델에서 제한 없이 생성하면 유용한 새 동작 없이 시간만 소비할 수 있습니다. 최대 전이 수, 시간 제한, 요구사항 커버리지 달성, 특정 상태 도달 같은 stop condition을 조합합니다. 단, 길이를 짧게 제한했을 때 장기 시퀀스에서만 드러나는 만료·누적·중복 처리 문제를 놓치지 않는지 별도 테스트 전략으로 보완해야 합니다.

## 온라인 실행과 오프라인 생성: 둘은 다른 운영 방식이다

MBT를 쓰는 방식은 크게 두 가지로 나뉩니다. **오프라인 생성**은 모델에서 사람이 읽을 수 있는 테스트 시나리오 또는 자동화 스크립트 후보를 먼저 만들고, 이를 검토한 뒤 실행하는 방식입니다. 도메인 전문가가 경로를 리뷰하기 쉽고, 기존 테스트 관리 도구에 시나리오를 넣기 좋습니다. 대신 모델이 바뀔 때 생성물을 다시 정리해야 할 수 있습니다.

**온라인 실행**은 테스트 러너가 현재 모델 상태를 들고 실제 시스템을 조작하면서 다음 전이를 선택하는 방식입니다. API를 호출하고 응답을 확인한 뒤 다음 행동을 정할 수 있어 동적 흐름에 유리합니다. 하지만 테스트 실행기가 인증·테스트 데이터·비동기 대기·재시도·정리까지 책임져야 하므로 구현 난이도가 높습니다. 모델이 맞아도 실행 어댑터가 잘못되면 false failure가 생길 수 있습니다.

처음 도입할 때는 오프라인으로 상태·전이·가드를 검토하고, 반복되는 핵심 경로 몇 개를 기존 API 또는 브라우저 자동화에 연결하는 방식이 안전합니다. 테스트가 안정된 뒤에야 무작위·가중 경로를 야간 회귀에 넣는 것이 좋습니다. 모든 모델을 즉시 CI의 배포 차단 게이트로 올리면, 모델 결함·테스트 데이터·외부 의존성 때문에 실패 원인이 불분명한 상태에서 팀이 결과를 무시하게 될 수 있습니다.

## API와 UI를 연결할 때: 한 모델, 서로 다른 증거

같은 주문 상태 모델이라도 API 테스트와 UI 테스트는 다른 증거를 봅니다. API 계층에서는 상태 전이 요청의 HTTP 상태 코드, 응답 body, 도메인 이벤트, DB의 최종 상태를 확인할 수 있습니다. 예를 들어 `POST /orders/{id}/cancel`이 결제 대기에서는 성공하지만 배송 중에는 문서화한 오류 코드를 주는지 확인합니다. 이 계층은 빠르고 실패 원인을 좁히기 좋습니다.

UI 계층에서는 사용자가 실제로 전이를 만들 수 있는지와 화면이 상태를 정확하게 표현하는지를 봅니다. 결제 대기 상태에서 취소 버튼이 보이는지, 배송 중 상태에서는 잘못된 버튼이 숨겨지거나 안내 문구가 나오는지, 브라우저 새로고침 뒤 상태가 유지되는지를 확인합니다. UI만으로 모든 경로를 탐색하면 느리고 불안정해질 수 있으므로, 모델의 대부분은 API에서 실행하고 대표 사용자 경로만 UI로 보강하는 방식이 현실적입니다.

또한 API 명세와 사용자 흐름이 완전히 같지 않다는 점을 주의해야 합니다. API는 형식상 유효한 여러 조합을 받을 수 있지만, UI는 약관 동의·재고 확인·인증을 거친 뒤에만 요청을 보낼 수 있습니다. MBT 모델을 만들 때 ‘백엔드가 거부해야 하는 잘못된 전이’와 ‘UI에서 만들 수 없어야 하는 전이’를 구분합니다. 그렇지 않으면 API는 의도적으로 400을 주는데 모델은 실패로 보거나, UI의 접근 제어 결함을 API 성공 경로로 오해할 수 있습니다.

## 가상의 업무 예시: 계정 잠금과 복구 흐름

가상의 관리자 시스템에서 사용자는 비밀번호를 여러 번 틀리면 계정이 잠깁니다. 상태는 `활성`, `로그인 실패 누적`, `잠김`, `본인 확인 대기`, `복구 완료`로 둘 수 있습니다. 전이는 `로그인 성공`, `로그인 실패`, `잠금 해제 요청`, `본인 확인 성공`, `복구 만료`처럼 정의합니다. 여기서 핵심 위험은 올바른 비밀번호를 입력해도 잠긴 계정이 바로 활성화되면 안 되는지, 복구 링크를 두 번 쓰면 어떻게 되는지, 관리자가 해제한 뒤 이전 세션이 계속 유효한지 같은 순서 의존성입니다.

모델은 먼저 실패 횟수를 정확한 숫자로 모두 표현하지 않고 `임계값 전`과 `잠김`처럼 업무적으로 중요한 상태로 압축할 수 있습니다. 경계값 4회·5회·6회는 별도 API 테스트로 확인합니다. MBT 경로에서는 `실패 → 실패 → 잠김 → 성공 비밀번호 입력 → 여전히 잠김`, `잠김 → 복구 요청 → 링크 만료 → 복구 시도 실패`, `잠김 → 관리자 해제 → 로그인 성공`처럼 상태 순서의 규칙을 실행합니다.

이 예시에서 오라클은 단순한 화면 문구가 아닙니다. 로그인 토큰이 발급되지 않는지, 감사 이벤트가 남는지, 계정 상태가 변경됐는지, 관리자가 해제할 권한이 있는지, 기존 세션이 정책대로 폐기됐는지를 확인해야 합니다. 이 중 일부는 API, 일부는 DB·이벤트, 일부는 UI·권한 테스트로 나눠 검증합니다. 모델 하나가 모든 검증 코드를 품는 대신, 같은 상태 언어로 서로 다른 계층의 테스트를 연결해 주는 역할을 합니다.

## 모델 커버리지와 코드 커버리지를 혼동하지 않는다

모델의 모든 전이를 실행했다고 해서 애플리케이션 코드의 모든 분기가 실행된 것은 아닙니다. 한 전이가 여러 구현 분기와 외부 장애 처리를 숨길 수 있고, 데이터 값에 따라 전혀 다른 코드 경로를 탈 수 있습니다. 반대로 코드 커버리지가 높다고 해서 업무 상태 전이가 모두 검증된 것도 아닙니다. 테스트가 내부 함수를 여러 번 실행해도 `결제 완료 뒤 취소 금지` 같은 규칙을 한 번도 확인하지 않았을 수 있습니다.

그래서 MBT 보고에는 상태·전이·요구사항 커버리지를, 코드 테스트 도구에는 line·branch 커버리지를 각각 기록하는 편이 좋습니다. 요구사항 ID를 모델의 상태나 전이에 태그로 붙이면, 어떤 정책이 어느 경로에서 실행됐는지 추적하는 데 도움이 됩니다. 다만 숫자를 100%로 만들기 위해 의미 없는 상태·전이를 쪼개면 모델이 읽기 어려워집니다. 커버리지는 빈칸을 찾는 도구이지 테스트 품질의 자동 증명서는 아닙니다.

부정 전이도 커버리지에 포함해야 합니다. `배송 중 → 배송 시작` 같은 중복 행동, `취소됨 → 결제 승인`, 권한 없는 사용자의 관리자 해제는 허용되면 안 되는 전이입니다. 이를 모델에서 아예 그리지 않으면 생성기는 시험하지 못합니다. ‘금지 전이’에 대한 API 오류·UI 비노출·감사 이벤트를 별도 경계로 표현하면 업무 규칙의 반대편도 검증할 수 있습니다.

## 모델 유지보수: 테스트 자동화보다 요구사항 변경을 먼저 추적한다

상태 전이는 기능 변경 때 자주 바뀝니다. 부분 취소가 추가되거나, 결제 수단별 승인 단계가 달라지거나, 새 권한 역할이 생기면 모델의 상태·가드·오라클이 변합니다. 모델 파일을 테스트 코드와 멀리 두면 제품 변경은 끝났는데 모델은 옛 정책을 말하는 상황이 생길 수 있습니다. 모델을 소스와 같은 저장소에서 버전 관리하고, 정책 변경 Pull Request에 모델 변경 여부를 확인하는 항목을 두는 이유입니다.

그러나 모든 버그 수정에 모델 변경을 강제할 필요는 없습니다. 구현 오류가 모델의 기존 전이를 위반한 것이라면 모델은 그대로 두고 실행 어댑터나 애플리케이션만 고치면 됩니다. 반대로 새로운 상태나 전이가 업무 요구에 추가됐다면 모델도 바뀌어야 합니다. 이 구분을 하면 모델은 코드 복사본이 아니라 살아 있는 규칙 문서로 남습니다.

모델이 커져서 한 장의 그래프로 읽기 어려워지면 도메인 경계를 나눕니다. 주문, 결제, 배송, 환불을 하나의 거대한 모델로 합치기보다, 공유 이벤트나 상태로 연결된 작은 모델 여러 개로 관리할 수 있습니다. GraphWalker도 공유 상태를 통한 다중 모델 조합을 지원합니다. 다만 너무 이르게 모델을 쪼개면 전역 흐름의 결함을 놓칠 수 있으므로, 실제로 독립된 소유 팀·배포 주기·업무 경계가 있는지 보고 나눕니다.

## 비동기 전이와 시간: 버튼 클릭이 곧 상태 변경은 아니다

현대 시스템의 많은 전이는 즉시 끝나지 않습니다. 결제 승인 요청을 보낸 뒤 외부 결제사의 webhook을 기다리거나, 파일 업로드 뒤 바이러스 검사를 기다리거나, 주문 취소 뒤 환불 배치를 기다릴 수 있습니다. 이때 `취소 요청됨`과 `취소 완료됨`을 하나의 상태로 합치면 테스트는 API 응답만 보고 성공했다고 판단하지만, 실제로는 비동기 작업이 실패해 주문 상태가 뒤늦게 어긋나는 결함을 놓칠 수 있습니다.

비동기 흐름은 요청을 보낸 상태, 대기 상태, 성공 상태, 실패·타임아웃 상태를 필요에 따라 나눕니다. 예를 들어 `환불 요청됨 → 환불 처리 중 → 환불 완료/환불 실패`로 표현할 수 있습니다. 전이의 오라클도 HTTP 202 응답 하나가 아니라, outbox 이벤트가 기록됐는지, 소비자가 처리했는지, 최종 주문 상태와 결제 상태가 일치하는지, 실패 시 재시도 또는 운영자 알림이 발생하는지를 포함해야 합니다. 단, 모든 큐·재시도 횟수를 모델에 그대로 넣으면 상태 수가 급격히 늘므로, 테스트 목적상 중요한 재시도·만료·보상 경계만 모델링합니다.

시간도 상태 전이의 입력입니다. 예약이 15분 뒤 만료되는 서비스에서 `예약됨`은 시간과 분리할 수 없습니다. 테스트가 실제 15분을 기다리면 느리고 flaky해지므로, 시계(clock)를 주입하거나 테스트 환경에서 시간을 제어하는 방식을 고려합니다. `만료 전`과 `만료 후`를 모델 상태로 두고, 현재 시간을 명시적으로 전이에 넘기면 재현성이 좋아집니다. 실제 시스템 시간이 필요한 통합 시험은 별도 좁은 시나리오로 두고, 모델 경로 대부분은 제어 가능한 시간으로 실행하는 편이 좋습니다.

외부 webhook과 메시지 큐는 중복·순서 뒤바뀜도 만들 수 있습니다. 같은 결제 승인 이벤트가 두 번 오거나, 취소 이벤트가 승인 이벤트보다 먼저 도착할 수 있습니다. 모델에 `중복 이벤트 수신`, `지연 이벤트 수신` 같은 전이를 추가하면 멱등성·보상 규칙을 시험할 수 있습니다. 이때 오라클은 상태 문자열뿐 아니라 같은 이벤트 ID가 두 번 처리돼도 환불이 두 번 나가지 않는지, 감사 로그가 어떤 상태를 남기는지, 재처리 결과가 안정적인지를 확인해야 합니다.

## 테스트 데이터와 모델 상태를 섞지 않는 법

모델의 상태는 `결제 완료`처럼 행동 규칙을 나타내고, 테스트 데이터는 상품 가격·사용자 역할·재고 수량·쿠폰 만료일처럼 전이를 가능한지 바꾸는 재료입니다. 둘을 모두 상태 이름에 넣으면 `결제완료_관리자_재고있음_쿠폰유효` 같은 읽기 어려운 그래프가 됩니다. 반대로 데이터를 무시하면 특정 역할이나 재고 조건에서만 생기는 전이 오류를 놓칩니다.

실용적인 방법은 모델에는 업무적으로 중요한 조건만 guard 또는 작은 변수로 두고, 세부 값은 데이터 생성기·fixture·파라미터화된 테스트로 분리하는 것입니다. 예를 들어 주문 취소 모델에는 `출고 전`과 `출고 후`만 두고, 정확한 출고 시각·상품 수량·세금은 전이 실행기가 준비한 데이터로 다룰 수 있습니다. 권한 모델에는 `권한 있음/없음`을 두되, 실제 역할 목록과 정책 조합은 별도의 권한 매트릭스 테스트로 검증합니다.

테스트 데이터의 수명도 관리해야 합니다. 온라인 MBT가 긴 경로를 실행하면서 같은 주문·계정을 재사용하면, 앞 단계의 부수 효과가 다음 경로를 오염시킬 수 있습니다. 실행마다 고유 식별자를 만들고, 가능한 경우 트랜잭션 롤백·테스트 테넌트·격리된 환경을 사용하며, 정리 실패가 났을 때 조사할 로그를 남겨야 합니다. ‘모델이 잘못됐다’고 보이는 실패가 실제로는 이전 실행의 잔여 데이터 때문인 경우가 많습니다.

## 요구사항 추적과 릴리스 기준: 경로가 아니라 위험을 보고한다

MBT의 결과를 팀에 전달할 때 “오늘 500개 경로가 통과했다”는 말만으로는 의미가 부족합니다. 어떤 상태·전이·요구사항·위험 태그가 실행됐고, 어떤 경로는 왜 제외됐는지 설명할 수 있어야 합니다. 전이에 `PAYMENT-CANCEL`, `AUTH-LOCK`, `REFUND-TIMEOUT`처럼 요구사항 또는 위험 식별자를 붙이고, CI에서 그 태그의 커버리지를 출력하면 릴리스 판단에 도움이 됩니다.

릴리스 기준도 모든 전이를 같은 무게로 보지 않습니다. 결제·권한·개인정보 상태 전이는 작은 UI 문구 전이보다 높은 증거가 필요할 수 있습니다. 핵심 전이는 API·DB·이벤트까지 확인한 결정적 경로를 PR마다 실행하고, 넓은 무작위 경로는 야간 또는 배포 전 환경에서 실행하는 식으로 계층을 둡니다. 이렇게 하면 느린 경로 생성이 모든 개발자의 피드백을 막지 않으면서도, 순서 결함을 발견할 기회를 유지할 수 있습니다.

요구사항이 바뀌었는데 모델 커버리지가 떨어지면 실패로 보기보다, 새 정책이 아직 모델·테스트에 반영되지 않았다는 신호로 다룹니다. 모델은 품질의 결과물이면서 요구사항 변경의 영향도를 보여 주는 지도입니다. 제품 변경 회의에서 새 상태와 금지 전이를 먼저 확인하면, 테스트는 개발이 끝난 뒤의 검사보다 설계 단계의 검토 도구가 될 수 있습니다.

모델의 가치를 정기적으로 되짚는 것도 필요합니다. 몇 달 동안 한 번도 실패를 설명하지 못하고, 요구사항 변경 때마다 코드보다 늦게 수정되며, 팀이 그래프를 읽지 않는다면 모델의 범위가 맞지 않을 수 있습니다. 반대로 장애 분석에서 ‘이 전이는 모델에 없었다’가 반복된다면 상태·금지 전이·비동기 경계를 보강할 근거가 됩니다. MBT는 한 번 만든 뒤 커버리지 숫자만 지키는 산출물이 아니라, 실제 결함과 정책 변화에 따라 크기와 역할을 조정해야 하는 테스트 자산입니다.

## 한계와 적용 기준 Q&A

### Q. MBT를 도입하면 수동 탐색 테스트는 필요 없나요?

A. 필요합니다. 모델은 알려진 규칙과 상태를 체계적으로 탐색하지만, 모델에 없는 사용자 행동·문구 혼란·성능 체감·새로운 위험을 발견하는 데는 탐색적 테스트가 강합니다. 탐색에서 발견한 실제 흐름을 모델의 상태·전이 또는 회귀 시나리오로 반영하면 두 방식이 서로를 강화합니다.

### Q. 상태가 너무 많으면 모든 경로를 어떻게 테스트하나요?

A. 모든 경로를 목표로 삼지 않습니다. 전이·요구사항·위험 커버리지, 최대 길이, 필수 상태 도달 같은 명시적인 종료 조건을 둡니다. 상태를 업무적으로 의미 있는 수준으로 추상화하고, 입력값 조합은 경계값·Property-Based·결정표 테스트로 분리합니다. 경로 폭발은 도구 성능 문제가 아니라 모델링 범위를 조정하라는 신호일 때가 많습니다.

### Q. 모델과 실제 동작이 다르면 무엇이 버그인가요?

A. 자동으로 어느 쪽이 틀렸다고 정할 수 없습니다. 모델이 최신 요구사항을 반영하지 못했을 수도 있고, 구현이 정책을 위반했을 수도 있으며, 요구사항 자체가 모호할 수도 있습니다. 실패를 발견하면 제품·개발·QA가 함께 의도된 전이를 확인하고, 그 결정에 따라 모델·코드·문서를 같은 변경으로 갱신해야 합니다.

### Q. 작은 서비스에도 MBT가 가치가 있나요?

A. 상태·순서 규칙이 단순하다면 큰 모델은 과할 수 있습니다. 다만 로그인·권한·결제·예약처럼 적은 화면이라도 잘못된 순서가 큰 문제를 만드는 영역에는 작은 상태 다이어그램과 핵심 전이 테스트만으로도 가치가 있습니다. 모델을 만들기 위한 모델을 만들지 말고, 지금 놓치기 쉬운 전이를 줄일 수 있을 때 사용합니다.

## 마무리

Model-Based Testing은 테스트 케이스 수를 늘리는 방법이 아니라, 시스템이 어떤 상태에서 어떤 행동을 허용·거부해야 하는지 실행 가능한 모델로 합의하는 방법입니다. 상태를 업무 언어로 작게 정의하고, 전이에 관찰 가능한 오라클을 연결하며, 모든 경로 대신 위험과 요구사항에 맞는 커버리지를 선택해야 합니다. 결제·권한·워크플로처럼 순서가 결함을 만드는 영역부터 시작해 기존 API·UI·단위 테스트와 역할을 나눌 때, MBT는 복잡한 흐름을 설명 가능하고 반복 가능한 품질 기준으로 바꿉니다.
