Linux 서버를 운영하다 보면 “443 포트만 열어 주세요”, “DB는 애플리케이션 서버에서만 접속하게 해 주세요”, “새 방화벽 규칙을 넣었더니 SSH가 끊겼습니다” 같은 요청을 만납니다. 이런 요청은 단순히 포트 번호 몇 개를 허용하는 작업처럼 보이지만, 실제로는 패킷이 어느 인터페이스로 들어오고 나가는지, 이미 맺어진 연결의 응답은 어떻게 돌려보낼지, 컨테이너·로드밸런서·NAT(Network Address Translation, 네트워크 주소 변환)가 어느 계층에서 규칙과 만나는지까지 결정해야 합니다.

**nftables**는 Linux 커널의 Netfilter 기능을 제어하는 현대적인 방화벽 프레임워크입니다. 예전 `iptables` 명령에 익숙한 사람도 많지만, nftables는 table·chain·rule 구조를 일관된 규칙 집합으로 표현하고 set·map·원자적 교체 같은 기능을 제공해 복잡한 정책을 관리하기 좋게 설계됐습니다. 그렇다고 nftables가 “iptables 명령만 다른 버전”이라는 뜻은 아닙니다. 패킷이 커널을 지나가는 경로와 연결 상태를 먼저 이해하지 않으면, 규칙 문법을 외워도 의도와 다른 차단이나 허용을 만들 수 있습니다.

이 글의 목표는 인터넷에 노출된 서버에 그대로 복사할 규칙 한 묶음을 제공하는 것이 아닙니다. 환경마다 관리용 접속 경로, IPv6 사용 여부, 클라우드 보안 그룹, Kubernetes·Docker의 규칙 생성 방식, 로드밸런서 상태가 다르기 때문입니다. 대신 “어떤 트래픽을 어떤 이유로 허용·차단하는가”를 설계하고, 변경 중 자기 접속을 잃지 않으며, 문제 발생 시 어디를 확인해야 하는지의 기준을 설명합니다.

## 먼저 알아둘 기반 기술: 패킷·포트·프로토콜·상태 기반 방화벽

네트워크 통신은 데이터를 작은 단위로 나눈 **패킷(packet)** 이 여러 장비와 운영체제 계층을 지나 목적지에 도달하는 과정입니다. IP 주소는 어느 호스트 또는 네트워크로 갈지를, TCP(Transmission Control Protocol)·UDP(User Datagram Protocol)는 어떤 전송 방식을 쓸지를 나타냅니다. **포트(port)** 는 한 호스트 안에서 어떤 서비스가 데이터를 받을지 구분하는 번호입니다. HTTPS는 흔히 TCP 443, SSH는 흔히 TCP 22를 사용하지만, 포트 번호 자체가 서비스의 신원이나 안전성을 보장하지는 않습니다.

방화벽은 정해진 조건에 따라 패킷을 허용(accept), 차단(drop), 거부(reject)하거나 다른 곳으로 변환·전달하는 정책입니다. `drop`은 응답 없이 버려 상대가 시간 초과를 겪게 하고, `reject`는 거부 응답을 보내 더 빨리 실패를 알릴 수 있습니다. 어느 쪽이 항상 더 안전하거나 친절한 것은 아닙니다. 서비스 특성, 진단 필요성, 외부 노출 정도에 따라 결정해야 합니다. 중요한 것은 규칙의 기본 동작과 예외가 문서화돼 있어야 한다는 점입니다.

**상태 기반(stateful) 방화벽**은 패킷 하나만 보고 판단하지 않고, 그것이 이미 허용된 연결의 일부인지도 봅니다. TCP로 사용자가 웹 서버에 접속하면 클라이언트에서 서버로 가는 요청뿐 아니라 서버에서 클라이언트로 돌아가는 응답 패킷이 생깁니다. 입력 체인에서 새 HTTPS 연결만 허용하고 응답 연결을 고려하지 않으면, 서버가 보내는 패킷이나 뒤따르는 패킷이 예상과 다르게 차단될 수 있습니다. Linux의 **conntrack(connection tracking, 연결 추적)** 은 패킷 흐름을 연결 상태로 기록해 `new`, `established`, `related`, `invalid` 같은 분류를 제공합니다.

`established`는 이미 알려진 연결에 속한 패킷, `related`는 기존 연결과 연관된 보조 연결을 의미합니다. 예를 들어 일부 프로토콜의 제어 연결과 데이터 연결이 관련 상태로 잡힐 수 있습니다. `invalid`는 추적 상태와 맞지 않거나 해석할 수 없는 패킷일 수 있습니다. 다만 conntrack은 무한한 기억 장치가 아닙니다. 연결 추적 테이블이 가득 차거나 비대칭 라우팅 때문에 왕복 패킷이 다른 장비를 지나면 기대한 상태가 나오지 않을 수 있습니다. 상태 규칙을 넣는 것과 상태 문제를 관측하는 것은 별개의 운영 작업입니다.

## Netfilter와 nftables: 명령어가 아니라 커널 패킷 경로를 본다

**Netfilter**는 Linux 커널에서 네트워크 패킷을 처리할 때 특정 지점(hook)에 규칙을 연결할 수 있게 하는 프레임워크입니다. nftables의 `nft` 명령은 사용자 공간에서 규칙을 작성해 netlink를 통해 커널에 전달합니다. 즉 `nft`가 패킷을 직접 필터링하는 것이 아니라, 커널의 Netfilter hook에 연결된 규칙이 실제 패킷을 판단합니다. Linux Kernel 문서는 nftables 설정을 위한 netlink 인터페이스도 별도로 설명합니다.

서버로 들어오는 패킷만 생각하면 규칙이 단순해 보이지만, 실제 경로는 더 많습니다. 이 호스트 자체가 목적지인 패킷은 대체로 input 경로를 지나고, 이 호스트에서 만들어져 외부로 나가는 패킷은 output 경로를 지납니다. 라우터·프록시·컨테이너 호스트처럼 다른 목적지로 전달하는 패킷은 forward 경로를 지날 수 있습니다. 주소 변환은 prerouting·postrouting처럼 다른 hook에서 일어날 수 있습니다. 같은 ‘443 포트’라도 패킷이 호스트 프로세스로 들어오는지, 컨테이너로 전달되는지, NAT 뒤로 넘어가는지에 따라 봐야 할 chain이 다릅니다.

```text
외부 패킷
   │
   ├─ prerouting: 주소 변환·초기 분류가 일어날 수 있음
   │
   ├─ 이 호스트가 목적지 ────────────────> input ──> 로컬 서비스
   │
   └─ 다른 곳으로 전달 ────────────────> forward ──> postrouting ──> 다음 네트워크

로컬 프로세스가 만든 패킷 ─────────────> output ──> postrouting ──> 외부
```

이 그림은 개념 모델입니다. 실제 우선순위, NAT 처리, 브리지·가상 인터페이스, 컨테이너 런타임의 체인은 환경에 따라 달라집니다. 따라서 장애가 났을 때 “input에 443 허용을 넣었는데 왜 안 되지?”라고 묻기 전에, 패킷이 정말 로컬 input으로 오는지, 앞단 보안 그룹이나 로드밸런서가 먼저 차단하는지, 목적지가 컨테이너로 DNAT되는지부터 확인해야 합니다.

## table·chain·rule: nftables 규칙 집합을 읽는 세 단위

nftables에서 **table**은 chain, set, map, counter 같은 객체를 담는 최상위 컨테이너입니다. table에는 `ip`, `ip6`, `inet`, `arp`, `bridge`, `netdev` 같은 **family**가 연결됩니다. `inet` family는 IPv4와 IPv6를 함께 다룰 때 자주 사용하지만, 모든 표현식이 두 프로토콜에서 똑같이 동작한다고 가정하면 안 됩니다. IPv6를 실제로 서비스한다면 규칙·ICMPv6·주소·보안 그룹을 별도로 검토해야 합니다.

**chain**은 rule의 순서 있는 묶음입니다. 특히 Netfilter hook에 연결된 **base chain**은 들어오는 패킷을 실제 처리할 시작점입니다. nftables에서는 iptables처럼 이름이 미리 정해진 INPUT 체인만 쓰는 것이 아니라, 체인의 이름을 정하고 어느 hook에 연결할지 명시합니다. 이 유연성은 장점이지만, hook·priority·policy를 빠뜨린 체인은 패킷을 전혀 보지 못할 수 있다는 뜻이기도 합니다.

**rule**은 조건과 동작의 조합입니다. `tcp dport 443 accept`는 TCP 목적지 포트가 443이면 허용하라는 규칙입니다. 규칙은 위에서 아래로 평가되는 경우가 많으므로 순서가 정책의 일부입니다. 앞에서 광범위하게 `accept`한 뒤 아래에 세밀한 `drop`을 두면 아래 규칙은 도달하지 못할 수 있습니다. 반대로 기본 정책을 drop으로 두고 필요한 예외를 위에 나열하면 최소 허용(allowlist) 모델을 표현하기 쉽지만, 누락 하나가 서비스 장애가 될 수 있습니다.

아래는 학습용으로 매우 제한적인 로컬 서버 모델을 표현한 예입니다. 그대로 적용하기 전에 원격 콘솔, 관리 포트, IPv6, 모니터링·백업·DNS, 컨테이너 런타임과의 관계를 반드시 확인해야 합니다.

```nft
table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;

    iifname "lo" accept
    ct state established,related accept
    ct state invalid drop

    tcp dport 22 ip saddr 192.0.2.0/24 accept
    tcp dport { 80, 443 } accept

    counter drop
  }
}
```

`iifname "lo" accept`는 로컬 루프백 인터페이스를 허용합니다. 이를 빼면 같은 서버 안의 프로세스끼리 `localhost`로 통신하는 기능이 깨질 수 있습니다. `ct state established,related accept`는 이미 시작한 정상 연결의 후속 패킷을 통과시키기 위한 대표 규칙입니다. SSH는 예시 네트워크에서만 허용했으며, 실제 환경에서는 고정 관리자 망·VPN·bastion host·클라우드 관리 채널을 어떻게 쓸지에 맞춰야 합니다. 관리 포트를 인터넷 전체에 열어 두는 것은 운영 편의와 별개로 공격 표면을 크게 만듭니다.

## 기본 차단은 목표가 아니라 정책의 결과다

`policy drop`은 “명시적으로 허용하지 않은 입력을 차단한다”는 기본 정책입니다. 인터넷에 노출된 단일 목적 서버에서는 좋은 출발점이 될 수 있습니다. 그러나 기본 차단을 설정했다는 사실만으로 정책이 완성되지는 않습니다. 이 서버가 어떤 역할인지, 누가 어느 네트워크에서 접속하는지, 헬스 체크는 어느 IP에서 오는지, 백업 에이전트·모니터링·DNS·시간 동기화·인증서 갱신이 어느 방향으로 통신하는지 목록이 있어야 합니다.

특히 input, output, forward의 기본 정책을 동시에 drop으로 바꾸는 작업은 영향 범위가 큽니다. output을 차단하면 서버가 DNS를 조회하지 못하거나 패키지 업데이트·원격 로그 전송·인증서 갱신·데이터베이스 접속에 실패할 수 있습니다. forward를 차단하면 컨테이너나 가상 머신의 통신이 끊길 수 있습니다. “모든 방향 기본 drop”은 더 안전해 보이지만, 실제 필요한 흐름을 정확히 알고 검증할 수 있을 때에만 설계해야 합니다. 처음에는 외부에서 로컬 서비스로 들어오는 input 경계를 명확히 하고, 나머지는 관측과 요구사항 정리 뒤 단계적으로 다루는 편이 낫습니다.

포트 기준 규칙도 충분하지 않을 수 있습니다. 예를 들어 DB 포트 5432 또는 8629를 열어야 한다면, 포트만 보지 말고 출발지 주소·인터페이스·VPN·애플리케이션 서브넷을 함께 제한할 수 있습니다. 하지만 IP allowlist만으로 인증·권한 관리를 없앨 수는 없습니다. 내부 네트워크가 침해되거나 주소가 재사용될 수 있고, 잘못된 서비스가 허용된 네트워크에서 연결할 수 있기 때문입니다. 네트워크 경계와 DBMS 계정·TLS·애플리케이션 권한은 서로 다른 방어층입니다.

## set·map·counter: 규칙을 복사하지 않고 정책을 읽기 좋게 만들기

여러 IP나 여러 포트를 같은 방식으로 다룰 때 규칙을 반복하면 수정 누락이 생기기 쉽습니다. nftables의 **set**은 값의 집합을 이름으로 묶을 수 있습니다. 예를 들어 관리자 네트워크 여러 개를 `admin_v4` set으로 두고 SSH 규칙에서 참조하면, 정책 의도가 더 명확해집니다.

```nft
table inet filter {
  set admin_v4 {
    type ipv4_addr
    flags interval
    elements = { 192.0.2.0/24, 198.51.100.10 }
  }

  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" accept
    ct state established,related accept
    ip saddr @admin_v4 tcp dport 22 accept
    tcp dport { 80, 443 } accept
  }
}
```

set은 데이터를 규칙과 분리해 주지만, 변경 권한도 함께 고려해야 합니다. 동적으로 IP를 추가하는 자동화가 있다면 누가 그 set을 바꾸는지, 오래된 임시 IP를 어떻게 만료시키는지, 잘못된 값이 들어오면 어떤 검증과 감사가 가능한지 정해야 합니다. 공격 탐지 결과를 자동으로 차단 set에 넣는 구성도 가능하지만, 오탐으로 정상 고객이나 운영자를 막을 위험이 있으므로 만료 시간·승인·로그·복구 절차를 둬야 합니다.

**counter**는 규칙에 닿은 패킷·바이트 수를 세는 데 도움이 됩니다. 차단 규칙에 counter를 붙이면 “정책이 동작했다”는 신호를 얻을 수 있지만, 카운터가 증가했다고 공격인지 장애인지 단정할 수는 없습니다. 특정 배포 뒤 counter가 급증하면 로드밸런서 헬스 체크 경로를 막았는지, 스캐너가 늘었는지, 잘못된 클라이언트 설정이 생겼는지를 서비스 로그·네트워크 흐름과 함께 확인해야 합니다.

**map**과 verdict map은 조건에 따라 값 또는 verdict를 연결하는 더 복잡한 정책에 사용할 수 있습니다. 예를 들어 포트별로 다른 정책을 매핑할 수 있지만, 처음부터 map으로 모든 규칙을 압축하면 장애 시 읽기 어려워질 수 있습니다. 방화벽은 보안 장치이면서 장애 원인이 되기도 하므로, 팀이 실제로 검토·복구할 수 있는 명료함이 최적화보다 중요합니다.

## iptables와 공존할 때: 같은 커널을 여러 관리자가 만질 수 있다

nftables를 도입할 때 가장 위험한 가정은 “내가 `nft list ruleset`에서 본 내용이 호스트 전체 네트워크 정책의 전부다”라는 생각입니다. 클라우드 보안 그룹·네트워크 ACL, 호스트의 nftables/iptables, firewalld 또는 ufw, Docker·Kubernetes CNI(Container Network Interface), 프록시·로드밸런서가 각자 정책을 만들 수 있습니다. 앞단에서 차단하면 호스트 규칙까지 도달하지 않고, 호스트에서 허용해도 애플리케이션이 리슨하지 않으면 연결은 실패합니다.

또한 iptables가 nft backend를 사용하거나, 오래된 xtables 규칙과 nft 규칙이 혼재할 수 있습니다. 컨테이너 런타임과 Kubernetes는 NAT·forward 규칙을 자동 생성할 수 있으며, 사람이 `flush ruleset`을 실행하면 그 규칙까지 지워 서비스가 멈출 수 있습니다. nftables 공식 위키도 ruleset 단위 작업과 원자적 교체, 기존 xtables에서의 이전을 별도 주제로 다룹니다. 따라서 운영 호스트에서 규칙을 정리할 때는 먼저 어떤 서비스가 무엇을 관리하는지 인벤토리로 만들고, 직접 소유하지 않은 체인은 건드리지 않는 원칙이 필요합니다.

다음 조회는 변경 전 상태를 보존하는 출발점이 될 수 있습니다.

```bash
sudo nft list ruleset
sudo nft list ruleset -a
sudo iptables -S
sudo ip6tables -S
sudo ss -lntup
ip route
```

`nft list ruleset -a`는 규칙 handle을 함께 보여 줘 특정 rule을 조사할 때 유용합니다. 하지만 명령 출력만 모아 놓는다고 실제 흐름이 설명되지는 않습니다. `ss -lntup`으로 서비스가 어떤 주소·포트에서 리슨하는지, `ip route`로 왕복 경로가 어떤지, 클라우드 제어 평면에서 어떤 보안 규칙이 있는지 같이 확인해야 합니다. 특히 `0.0.0.0:443`에 리슨하는 것과 `127.0.0.1:443`에만 리슨하는 것은 방화벽 규칙과 별개로 전혀 다른 노출 상태입니다.

## 안전한 변경 절차: 규칙을 쓰기 전에 되돌릴 방법을 만든다

원격 서버 방화벽 변경의 가장 중요한 산출물은 새 ruleset 자체가 아니라 **접속이 끊겨도 복구할 경로**입니다. 콘솔·iDRAC·클라우드 serial console 같은 out-of-band 접근이 가능한지 확인합니다. 가능하지 않다면 적어도 두 개의 SSH 세션을 열고, 한 세션에서 변경한 뒤 다른 세션에서 새 연결과 서비스 동작을 시험해야 합니다. 기존 연결이 살아 있다고 해서 새 연결이 열리는 것은 아닙니다. established 규칙은 현재 연결을 살릴 수 있지만 new SSH 연결은 차단될 수 있습니다.

변경 전에는 현재 ruleset을 파일로 저장하고, 새 파일을 문법 검사한 뒤 로드합니다. nftables는 파일 단위로 ruleset을 다룰 수 있고, 문서화된 구성 파일을 `nft -f`로 읽는 방식이 셸에서 명령을 여러 번 실행하는 것보다 변경 단위를 명확히 합니다. 다만 `-c` 검사 통과가 실제 통신 성공을 뜻하지는 않습니다. 인터페이스 이름, 출발지 주소, 앞단 장비, 서비스 리슨 상태가 달라지면 문법이 맞아도 서비스는 끊깁니다.

```bash
sudo nft list ruleset > /root/nftables.backup.nft
sudo nft -c -f /etc/nftables.conf
sudo nft -f /etc/nftables.conf
sudo nft list ruleset
```

백업 파일의 경로와 접근 권한에도 주의해야 합니다. 규칙에는 내부 IP 대역·관리 포트 같은 운영 정보가 들어갈 수 있습니다. 또한 운영 중인 시스템에서 구성 파일의 경로와 서비스 이름은 배포판마다 다릅니다. `/etc/nftables.conf`가 일반적일 수 있어도, 실제로는 firewalld나 구성 관리 도구가 원천일 수 있습니다. 변경 원천이 Ansible, 이미지 빌드, systemd unit이라면 그 원천을 고치지 않고 호스트에서 수동 수정해도 다음 배포에 덮어써질 수 있습니다.

더 안전한 방법은 제한된 시간 뒤 이전 규칙을 복구하는 작업을 별도 세션에서 예약하고, 새 연결·헬스 체크·핵심 업무 흐름이 확인되면 그 작업을 취소하는 것입니다. 단, 예약 명령을 무조건 복사해 실행하는 방식은 시스템의 권한·스케줄러·파일 경로에 따라 오히려 위험할 수 있습니다. 조직의 변경 관리 도구, 콘솔 접근, 승인 절차가 있다면 그 통제 안에서 되돌리기를 설계해야 합니다. 방화벽 변경은 ‘명령이 성공했다’가 아니라 ‘관리 접근과 서비스 접근이 모두 검증됐고 롤백도 가능한 상태’여야 완료입니다.

## 가상의 업무 예시: 웹·애플리케이션·DB를 분리한 세 계층

가상의 서비스가 세 네트워크 구간으로 나뉘어 있다고 가정해 보겠습니다. 외부 사용자는 로드밸런서를 통해 웹 서버에 HTTPS로 들어옵니다. 웹 서버는 내부 애플리케이션 서버의 API 포트에 요청을 전달하고, 애플리케이션 서버만 DB 서버의 포트에 접속합니다. 이 구조에서 DB 서버에 `tcp dport 8629 accept`만 넣으면, 같은 네트워크에 있는 모든 호스트가 DB 포트에 시도할 수 있습니다. 실제 Tibero·Oracle·PostgreSQL의 포트와 서비스 구성은 다르더라도, 원칙은 같습니다. DB는 애플리케이션 서브넷 또는 정해진 중계 호스트에서 오는 연결만 받도록 네트워크 경계를 좁히고, DBMS 내부에서도 사용자·TLS·권한을 분리합니다.

웹 서버에서는 외부 input에 80·443을 허용할 수 있지만, 관리자 SSH는 회사 VPN 또는 bastion의 주소 대역에만 허용합니다. 애플리케이션 서버는 외부 인터넷에서 직접 새 연결을 받을 이유가 없다면, 로드밸런서·웹 서버 서브넷에서 필요한 포트만 받습니다. DB 서버는 애플리케이션 서버 대역에서만 DB 포트를 받습니다. 이 세 문장은 간단하지만, 실제 구현 전에는 NAT 뒤 원본 IP가 어디서 보이는지, health check의 출발지가 어디인지, 배치·백업·모니터링이 DB에 접속해야 하는지, 장애 시 운영자가 어느 경로로 들어오는지를 목록으로 확인해야 합니다.

이 예시에서 모든 서버의 output을 막는다고 가정하면 문제가 더 복잡해집니다. 웹 서버는 인증서 갱신을 위해 외부에 나가야 할 수 있고, 애플리케이션은 외부 결제 API 또는 메일 서비스에 접속할 수 있으며, DB는 원격 백업이나 모니터링에 연결할 수 있습니다. 그래서 단순한 3계층 그림을 실제 규칙으로 바꾸려면 허용해야 할 egress 목록, DNS 해석, 프록시 경유 여부, 장애 중 필요한 관리 통신까지 정리해야 합니다. 네트워크 다이어그램과 방화벽 규칙은 서로 일치해야 하며, 한쪽만 최신이면 다른 쪽은 잘못된 운영 문서가 됩니다.

## 장애 분석: 차단 규칙만 보지 말고 흐름 전체를 추적한다

접속이 안 될 때 흔히 방화벽부터 의심하지만, 원인은 DNS, 라우팅, 보안 그룹, 서비스 미기동, 인증서, 애플리케이션 오류일 수 있습니다. 반대로 방화벽이 원인인데도 `curl`의 시간 초과만 보고 웹 서버 문제로 오해할 수 있습니다. 조사 순서는 “클라이언트에서 이름이 올바른 IP로 해석되는가 → TCP 연결이 어느 지점까지 가는가 → 서버가 해당 주소·포트에서 리슨하는가 → 앞단/호스트 정책이 패킷을 통과시키는가 → 애플리케이션이 요청을 처리하는가”처럼 계층을 나눠야 합니다.

`nft monitor trace`는 조건에 맞는 패킷이 어느 규칙을 지나 verdict에 도달했는지 추적하는 데 도움이 될 수 있습니다. 그러나 운영 트래픽에서 무분별하게 추적하면 출력이 많아지고 민감한 네트워크 정보를 다룰 수 있습니다. 좁은 테스트 트래픽·짧은 시간·승인된 환경에서 사용하고, 로그와 아티팩트 접근 권한을 관리해야 합니다. 규칙에 counter를 붙이고 `nft list ruleset`으로 증가를 보는 방식도 출발점이 될 수 있지만, 패킷이 그 체인에 도달했는지와 애플리케이션이 성공했는지는 다른 질문입니다.

conntrack 상태도 원인 분석에 유용하지만, 모든 실패를 conntrack으로 설명하면 안 됩니다. 예를 들어 비대칭 라우팅에서는 요청과 응답이 서로 다른 경로를 지나 상태가 기대와 다를 수 있습니다. 대량 연결이 있는 환경에서는 테이블 용량·타임아웃·NAT 사용량도 살펴야 합니다. 문제를 해결하려고 conntrack 테이블을 즉시 비우면 정상 연결까지 끊을 수 있으므로, 증상·범위·영향을 확인하지 않은 파괴적 조치는 피해야 합니다.

## 로그·감사·배포 원천: 보안 규칙도 소프트웨어처럼 관리한다

방화벽 규칙은 운영 중 바뀌는 코드와 같습니다. 누가 언제 왜 8443을 열었는지, 임시 허용은 언제 만료되는지, 구성 파일의 변경은 리뷰됐는지 알 수 있어야 합니다. Git 같은 버전 관리에 선언 파일을 두고, 인프라 자동화나 구성 관리로 배포하며, Pull Request에서 정책 변경을 검토하는 방식은 방화벽에도 적용할 수 있습니다. 물론 규칙 파일에 비밀 토큰이나 실제 고객 IP 목록이 포함된다면 저장소 접근 권한과 비밀 분리도 함께 설계해야 합니다.

로그 정책에도 균형이 필요합니다. 모든 drop 패킷을 무제한 기록하면 인터넷 스캔만으로 로그 저장소와 분석 비용이 커질 수 있습니다. 반대로 차단 로그가 전혀 없으면 정상 서비스가 왜 실패하는지 조사하기 어렵습니다. rate limit, 중요한 체인만의 로깅, 중앙 수집, 알람 기준을 함께 정해야 합니다. 로그에는 출발지 주소와 포트처럼 개인정보 또는 민감한 운영 정보가 포함될 수 있으므로 보존 기간·접근 통제도 고려합니다.

배포 후에는 rule이 로드됐다는 사실만 확인하지 말고, 허용돼야 하는 경로와 차단돼야 하는 경로를 모두 시험합니다. 예를 들어 관리자 VPN에서는 SSH가 되고 외부망에서는 안 되는지, 로드밸런서 health check가 통과하는지, 애플리케이션이 DB에 연결되는지, IPv6 경로가 의도와 같은지 확인합니다. 가능하면 스테이징 또는 별도 노드에서 먼저 검증하고, 운영은 작은 대상부터 점진 적용합니다. 네트워크 정책은 한 글자 차이로 전면 장애를 만들 수 있으므로, 빠른 배포보다 관측 가능한 배포가 중요합니다.

## IPv6와 ICMPv6: IPv4 규칙을 복사하면 생기는 빈틈

서버가 IPv6 주소를 갖고 있다면 IPv4 방화벽 규칙만 검토해서는 안 됩니다. 외부 사용자가 IPv4로만 접속한다고 생각해도 DNS의 AAAA 레코드, 클라우드의 기본 IPv6 할당, 내부 네트워크의 이중 스택 구성 때문에 다른 경로가 열려 있을 수 있습니다. `inet` table을 쓰는 것은 IPv4와 IPv6 정책을 한 곳에서 볼 수 있게 하는 좋은 출발점이지만, 주소 형식·프로토콜 헤더·ICMP 종류까지 자동으로 같아지는 것은 아닙니다. 허용할 서비스, 관리 경로, 로그·관측 기준을 두 프로토콜에서 각각 시험해야 합니다.

특히 **ICMPv6(Internet Control Message Protocol for IPv6)** 는 단순한 ping 기능만이 아닙니다. 이웃 탐색(Neighbor Discovery), 라우터 광고처럼 IPv6 네트워크가 주소와 경로를 설정하는 데 필요한 메시지가 포함됩니다. IPv4에서 ICMP를 전부 막던 습관을 그대로 옮겨 ICMPv6를 광범위하게 drop하면, 연결이 간헐적으로 실패하거나 큰 패킷 전송이 깨지는 원인을 만들 수 있습니다. 반대로 모든 ICMPv6를 아무 조건 없이 열어도 되는지는 네트워크 역할과 보안 정책에 따라 검토해야 합니다.

따라서 IPv6 정책은 “IPv4 규칙의 두 번째 사본”이 아니라 별도 검증 항목으로 둡니다. AAAA 레코드가 있는지, 서비스가 IPv6 소켓에도 리슨하는지, 로드밸런서·보안 그룹·host firewall이 모두 의도한 경로를 허용하는지, PMTU(Path Maximum Transmission Unit) 문제와 이웃 탐색이 정상인지 점검합니다. IPv6를 사용하지 않기로 했다면 주소·라우팅·DNS·클라우드 설정에서 실제로 비활성화됐는지도 확인해야 합니다. 방화벽 규칙 하나만으로 사용하지 않는 프로토콜의 노출이 사라진다고 가정하면 안 됩니다.

## 규칙 검토 체크리스트: 포트보다 흐름을 먼저 확인한다

방화벽 Pull Request나 변경 요청을 검토할 때는 `accept` 한 줄을 보고 끝내지 않는 편이 좋습니다. 그 연결의 출발지와 목적지, 프로토콜·포트, 어느 인터페이스로 들어오는지, 응답은 어떤 경로로 나가는지, 필요한 기간과 소유자가 누구인지가 함께 있어야 합니다. 임시 장애 대응으로 열었던 포트는 만료일과 제거 책임자가 없으면 영구 예외가 되기 쉽습니다.

- 이 트래픽은 input, output, forward 중 어느 경로를 지나는가?
- source IP·네트워크·인터페이스를 포트와 함께 제한할 수 있는가?
- 기존 연결과 새 연결을 구분하는 conntrack 규칙은 있는가?
- IPv4·IPv6, health check, 관리자 접근, DNS·백업·모니터링 흐름을 확인했는가?
- 구성의 원천은 무엇이며, 다음 배포에서 수동 변경이 덮어써지지 않는가?
- 새 연결 시험, 핵심 기능 시험, 롤백 경로를 실제로 확인했는가?

이 목록은 규칙을 복잡하게 만들기 위한 것이 아니라, 방화벽이 시스템 경계라는 사실을 드러내기 위한 최소 질문입니다. 답할 수 없는 항목이 있다면 더 넓은 허용 규칙을 서두르기보다, 서비스 소유자와 네트워크 흐름을 먼저 확인하는 편이 안전합니다.

## 한계와 적용 기준 Q&A

### Q. nftables를 쓰면 클라우드 보안 그룹은 필요 없나요?

A. 필요할 수 있습니다. 클라우드 보안 그룹은 가상 네트워크 경계에서, nftables는 호스트 커널에서 정책을 적용합니다. 서로 다른 위치와 장애·침해 시나리오를 다루므로 한쪽이 다른 쪽을 자동으로 대체하지 않습니다. 다만 동일한 규칙을 무계획하게 중복하면 장애 분석이 어려워지므로, 어느 계층이 어떤 책임을 갖는지 문서화해야 합니다.

### Q. 모든 포트를 막고 필요한 포트만 여는 것이 항상 최선인가요?

A. 외부 노출 서비스에는 최소 허용이 좋은 기본 원칙이 될 수 있지만, 실제 정책은 서비스의 통신 요구와 복구 요구를 반영해야 합니다. 특히 output과 forward까지 일괄 차단하면 DNS, 업데이트, 인증서, 백업, 컨테이너 통신이 끊길 수 있습니다. 위험이 큰 경계부터 명확히 하고, 필요한 흐름을 관측·문서화하며 넓히는 방식이 안전합니다.

### Q. Docker나 Kubernetes 호스트에서 nftables 규칙을 직접 수정해도 되나요?

A. 가능 여부보다 소유권 확인이 먼저입니다. Docker, kube-proxy, CNI, firewalld가 자동으로 만든 체인과 NAT 규칙을 사람이 지우거나 덮어쓰면 컨테이너 통신이 끊길 수 있습니다. 플랫폼이 제공하는 NetworkPolicy, 보안 그룹, 런타임 설정을 우선 사용하고, 호스트 nftables가 꼭 필요하다면 생성 주체·적용 순서·업그레이드 시 동작을 테스트 환경에서 확인해야 합니다.

### Q. 방화벽에서 허용됐는데도 접속이 실패합니다. nftables 문제인가요?

A. 아닐 수 있습니다. 서비스가 해당 주소에 리슨하지 않거나, 라우팅·DNS·NAT·앞단 보안 그룹·TLS·애플리케이션 인증에서 실패할 수 있습니다. 패킷이 어느 지점까지 갔는지와 서비스 로그를 함께 확인해야 합니다. 방화벽은 네트워크 흐름의 한 계층이므로, `accept` 규칙 하나만으로 종단 간 성공을 보장하지 않습니다.

## 마무리

nftables는 Linux 호스트에서 네트워크 접근 경계를 명시하는 강력한 도구입니다. 하지만 안전한 방화벽은 포트 목록으로 끝나지 않습니다. 패킷이 input·output·forward 중 어디를 지나는지, 연결 추적이 어떤 역할을 하는지, 규칙의 실제 소유자가 누구인지, 허용해야 하는 정상 흐름과 복구 경로가 무엇인지를 함께 알아야 합니다. 처음에는 서비스 역할이 분명한 서버의 input 정책부터 시작하고, 현재 ruleset을 보존한 뒤 문법 검사·새 연결·핵심 기능·롤백을 모두 확인하는 습관을 갖추는 것이 좋습니다. 명료한 정책, 작은 변경, 관측 가능한 검증이 방화벽을 보안 장치이자 안정적인 운영 도구로 만듭니다.
