## 먼저 답하기

### Q. 느린 SQL이 보이면 세션을 바로 종료하면 되나요?

A. 바로 종료하면 안 됩니다. 대기 중인 세션이 아니라 잠금을 잡고 있는 세션을 잘못 끊을 수 있고, 진행 중인 업무 트랜잭션이 롤백되면서 더 큰 영향이 생길 수 있습니다. 먼저 어떤 세션이 무엇을 기다리는지, 누가 잠금을 보유하는지, 해당 작업이 정상 배치인지 오류 상태인지, 얼마나 오래 지속됐는지를 확인해야 합니다.

### Q. 잠금은 데이터베이스 오류인가요?

A. 잠금은 여러 사용자가 같은 데이터를 동시에 바꿀 때 정합성을 지키기 위한 정상적인 동시성 제어 장치입니다. 문제가 되는 것은 잠금이 필요한 범위를 넘어 오래 유지되거나, 트랜잭션 순서가 서로 반대여서 대기가 길어지거나, 인덱스와 SQL 조건 때문에 예상보다 많은 행에 영향을 주는 경우입니다. 따라서 잠금을 없애는 것이 아니라 필요한 범위와 시간을 관리하는 것이 목표입니다.

## 먼저 알아둘 기반 기술

### 트랜잭션과 ACID

트랜잭션(transaction)은 여러 SQL 작업을 하나의 업무 단위로 묶는 방식입니다. 주문 생성과 재고 차감처럼 함께 성공하거나 함께 실패해야 하는 작업을 생각하면 됩니다. ACID는 원자성, 일관성, 격리성, 지속성이라는 트랜잭션의 성질을 요약한 용어입니다. 잠금은 이 가운데 여러 작업이 동시에 실행될 때 서로의 중간 상태를 망가뜨리지 않도록 돕는 장치입니다.

애플리케이션이 UPDATE를 실행한 뒤 COMMIT 또는 ROLLBACK을 하지 않은 채 오래 머물면, 다른 세션은 같은 데이터 또는 관련 자원에 접근할 때 기다릴 수 있습니다. 개발 화면에서는 빠르게 끝나는 작업도 운영에서는 외부 API 호출, 대량 처리, 사용자 입력 대기, 네트워크 지연 때문에 트랜잭션이 길어질 수 있습니다. 잠금 대기를 조사할 때 SQL 문장 하나가 아니라 트랜잭션 전체의 시작과 종료를 봐야 하는 이유입니다.

### 세션·프로세스·연결 풀

세션(session)은 클라이언트가 DBMS에 연결해 SQL을 실행하는 논리적 작업 단위입니다. 애플리케이션의 HTTP 요청 하나와 데이터베이스 세션 하나가 항상 일대일인 것은 아닙니다. 연결 풀(connection pool)은 매 요청마다 연결을 새로 만들지 않고, 미리 만든 연결을 빌려 주고 돌려받는 방식입니다. 풀을 쓰면 성능은 좋아질 수 있지만, 트랜잭션을 끝내지 않은 연결이 풀에 돌아가거나 세션 상태가 예상과 다르면 문제를 추적하기 어려워질 수 있습니다.

따라서 DB 세션을 볼 때는 사용자 이름과 프로그램 이름, 호스트, 모듈, client identifier, 접속 시각, 마지막 SQL, 트랜잭션 시작 시각 같은 문맥이 필요합니다. 단순히 SID가 크거나 오래 연결됐다는 사실만으로 비정상이라고 판단하면 안 됩니다. 야간 배치, 보고서 생성, 승인 대기 화면처럼 오래 지속되는 정상 업무와 비정상 대기를 구분해야 합니다.

### 잠금·대기·교착 상태

잠금(lock)은 어떤 자원을 변경하거나 보호하기 위해 세션이 얻는 제어권입니다. 대기(wait)는 다른 세션이 가진 잠금이나 I/O, 네트워크, CPU 같은 자원을 기다리는 상태입니다. 교착 상태(deadlock)는 둘 이상의 트랜잭션이 서로 상대가 가진 자원을 기다려 더 이상 진행할 수 없는 순환 상태입니다. DBMS는 교착 상태를 발견하면 보통 한 트랜잭션을 실패시켜 순환을 끊지만, 어떤 작업이 왜 충돌했는지는 애플리케이션과 DBA가 조사해야 합니다.

잠금 대기와 교착 상태를 혼동하면 대응이 달라집니다. 잠금 대기는 먼저 시작한 짧은 트랜잭션이 곧 끝나면 자연스럽게 해소될 수 있습니다. 교착 상태는 기다려도 순환이 깨지지 않으므로 실패한 작업을 재시도할 수 있는 설계와 일관된 자원 접근 순서가 필요합니다. 둘 다 화면에서 느림이나 오류로 보일 수 있지만 원인과 예방책은 다릅니다.

## 진단의 출발점: 대기 체인 만들기

사용자가 주문 수정 화면이 멈춘다고 보고했다고 가정합니다. 첫 질문은 "어떤 SQL이 느린가"가 아니라 "현재 이 요청은 무엇을 기다리는가"입니다. 세션 모니터링 뷰에서 대기 이벤트, 대기 시간, 현재 SQL, blocker 후보를 확인합니다. 다음으로 blocker 세션이 어떤 트랜잭션을 열어 두었는지, 마지막 활동이 무엇이었는지, 같은 애플리케이션 인스턴스 또는 배치에서 온 것인지 봅니다. waiter와 blocker를 화살표로 연결한 lock chain을 만들면, 단순한 느린 쿼리 목록보다 대응 우선순위를 정하기 쉽습니다.

Tibero의 동적 성능 뷰는 인스턴스·세션 상태를 조사하는 데 쓰일 수 있습니다. 설치 버전과 권한에 따라 제공되는 컬럼과 접근 방식은 다를 수 있으므로, 실제 운영에서는 조직의 Tibero 버전 문서와 권한 정책을 확인해야 합니다. 다음 SQL은 특정 뷰와 컬럼을 운영에 바로 복사하라는 뜻이 아니라, 세션 상태·대기·현재 SQL을 함께 연결해 본다는 조사 방향의 예시입니다.

```sql
-- 예시: 권한이 있는 진단 계정에서 세션 문맥을 확인하는 형태
SELECT sid, serial#, status, username, program, event, wait_time
FROM v$session
WHERE status = 'ACTIVE';
```

조회 결과는 한 순간의 스냅샷입니다. 1초 뒤에는 대기가 사라지거나 blocker가 바뀔 수 있습니다. 그래서 심각한 대기라면 일정 간격의 샘플, 애플리케이션 요청 ID, 배치 실행 이력, 로그 시각을 함께 모아야 합니다. 단, 진단 쿼리 자체가 운영 인스턴스에 부담을 주지 않게 범위와 빈도를 제한하고, 민감한 SQL bind 값이나 개인정보를 무단으로 수집하지 않아야 합니다.

## 원인을 나누어 보는 방법

### 긴 트랜잭션

가장 흔한 원인 중 하나는 트랜잭션 안에서 오래 걸리는 작업을 하는 경우입니다. 사용자가 입력을 확인할 때까지 트랜잭션을 열어 두거나, 외부 HTTP 호출·파일 업로드·대량 계산을 UPDATE와 COMMIT 사이에 넣으면 잠금 보유 시간이 길어집니다. 해결은 timeout을 무작정 늘리는 것이 아니라, 트랜잭션 안에 반드시 있어야 하는 데이터 변경만 남기고 외부 작업과 긴 계산을 앞뒤로 분리하는 것입니다.

예를 들어 결제 승인 API를 호출한 뒤 주문 상태를 갱신해야 한다고 해도, 주문 행을 잠근 상태에서 provider 응답을 오래 기다리는 설계는 경합을 키울 수 있습니다. 업무 정합성 요구에 맞게 예약 상태, 멱등 키, outbox 이벤트 같은 패턴을 검토하고, 잠금이 필요한 구간을 줄이는 방법을 찾습니다. 어떤 분리가 가능한지는 업무 규칙에 따라 다르므로, SQL 성능만 보고 자동으로 바꾸면 안 됩니다.

### 넓은 조건과 인덱스 부재

UPDATE 또는 SELECT FOR UPDATE의 WHERE 조건이 적절한 인덱스를 쓰지 못하면 많은 행을 읽고 더 넓은 범위에 영향을 줄 수 있습니다. 특히 상태와 날짜 조건으로 오래된 주문을 한꺼번에 갱신하는 배치가 낮 시간에 실행되면, 온라인 주문 처리와 경합할 수 있습니다. 실행 계획을 보고 실제 접근 경로와 예상 행 수를 확인한 뒤, 배치 단위를 나누거나 인덱스·실행 시간을 조정하는 방법을 검토합니다.

인덱스를 추가한다고 잠금 문제가 항상 없어지지는 않습니다. 쓰기 인덱스가 많아지면 UPDATE 때 유지해야 할 구조도 늘고, 특정 hot row를 여러 요청이 동시에 바꾸는 문제는 인덱스로 해결되지 않습니다. 고객별 순번, 재고 수량, 단일 집계 행처럼 한 곳에 요청이 집중되는 구조라면 업무 모델, 큐잉, 낙관적 잠금, 작업 분할 같은 대안을 함께 고려해야 합니다.

### 일관되지 않은 접근 순서

두 업무가 같은 두 행을 서로 다른 순서로 갱신하면 교착 상태 위험이 커집니다. 주문 취소는 주문을 먼저 갱신하고 재고를 갱신하는데, 재고 조정 배치는 재고를 먼저 갱신하고 주문을 갱신한다면 순환 대기가 생길 수 있습니다. 모든 코드 경로에서 자원 접근 순서를 가능한 한 일관되게 정하면 위험을 줄일 수 있습니다. 이는 DB 설정만의 문제가 아니라 도메인 서비스와 배치 설계의 계약입니다.

교착 상태가 발생할 수 있다는 사실을 완전히 제거하기 어려운 시스템도 있습니다. 이때는 실패한 트랜잭션을 안전하게 재시도할 수 있어야 합니다. 재시도 횟수와 backoff를 제한하고, 외부 결제·이메일 발송처럼 중복 부수 효과가 생길 수 있는 작업은 멱등성 키와 상태 확인을 함께 사용합니다. 데이터베이스 오류를 애플리케이션에서 무한 반복하면 경합을 더 키울 수 있으므로, 재시도 정책에도 종료 기준이 필요합니다.

## 안전한 대응 순서

대기 체인을 확인했다고 해서 blocker 세션을 즉시 kill하는 것은 마지막 수단에 가깝습니다. 먼저 blocker가 정상적인 장기 배치인지, 잠시 후 commit할 작업인지, 비정상적으로 멈춘 연결인지 해당 서비스 담당자와 확인합니다. 정상 배치라면 대기 요청을 줄이거나 실행 창을 조정하는 편이 낫습니다. 비정상 세션이 확실하고 업무 영향이 크다면, 영향을 받을 트랜잭션과 롤백 시간을 예상한 뒤 승인된 절차에 따라 종료를 검토합니다.

세션 종료 뒤에는 문제가 사라졌다는 사실만 보지 말고, 롤백으로 인해 어떤 업무가 실패했는지와 재시도가 필요한지 확인해야 합니다. 연결 풀은 끊긴 연결을 다시 만들 수 있고, 애플리케이션은 같은 요청을 재시도할 수 있습니다. 그래서 종료 조치는 대기 증상만 잠시 없애고 원인을 남길 수 있습니다. 종료 전후의 세션 문맥, SQL, 배치 ID, 영향받은 요청을 기록해야 재발을 막을 수 있습니다.

운영 권한도 분리해야 합니다. 세션 상태를 읽는 권한, SQL 계획을 보는 권한, 세션을 종료하는 권한, 데이터·파라미터를 바꾸는 권한은 위험 수준이 다릅니다. 장애 조사라는 이유로 넓은 관리자 권한을 공유하면 다른 사고를 만들 수 있습니다. 진단 역할에는 읽기 권한을 우선 주고, 높은 영향의 조치는 승인·감사·변경 창을 거치게 하는 편이 안전합니다.

## 업무 예시: 재고 차감과 정산 배치의 경합

온라인 주문이 재고 수량을 줄이는 동안, 정산 배치가 같은 상품의 수량과 판매 집계를 갱신한다고 가정합니다. 주문 API는 상품 행을 잠근 뒤 주문 행을 쓰고, 배치는 주문을 먼저 집계한 뒤 상품 행을 갱신한다면 특정 시간대에 교착 상태가 생길 수 있습니다. 먼저 두 흐름이 실제로 같은 행을 어떤 순서로 잠그는지 트레이스와 SQL로 확인합니다. 단순히 오류 코드 하나만 보고 재시도 횟수를 늘리는 것은 충분하지 않습니다.

개선 방향은 여러 가지일 수 있습니다. 두 흐름의 접근 순서를 일치시키거나, 정산 배치를 작은 범위로 나누고 온라인 트래픽이 적은 시간에 실행하거나, 집계를 즉시 갱신하지 않고 이벤트 기반 비동기 처리로 옮기는 방법을 검토할 수 있습니다. 어느 방법이 맞는지는 재고 정확성, 주문 응답 시간, 정산 마감 시간, 복구 절차에 따라 달라집니다. 변경 전에는 결과 집계가 동일한지와 장애 시 재처리할 수 있는지를 확인해야 합니다.

## 애플리케이션에서 줄일 수 있는 경합

잠금 문제의 상당수는 DBMS 파라미터보다 애플리케이션의 트랜잭션 경계에서 시작합니다. 요청을 처리하는 동안 화면 렌더링, 외부 API 호출, 대용량 파일 생성, 메시지 발송을 하나의 트랜잭션 안에 묶지 않는지 확인하세요. 데이터 정합성에 필요한 UPDATE와 검증만 짧게 수행하고 COMMIT한 뒤, 오래 걸리는 후속 작업은 별도 단계로 분리할 수 있는지 검토합니다. 다만 너무 일찍 commit하면 부분 실패와 보상 처리가 필요할 수 있으므로, 업무 상태 전이를 명확히 설계해야 합니다.

연결 풀 설정도 점검 대상입니다. 최대 연결 수를 크게 잡아 대기 요청을 모두 DB로 밀어 넣으면, 잠금 경합과 CPU·I/O 부하가 함께 커질 수 있습니다. 반대로 풀이 너무 작으면 DB에는 문제가 없어도 애플리케이션이 연결을 기다릴 수 있습니다. pool acquire timeout, transaction timeout, SQL timeout, HTTP deadline이 어떤 순서로 만료되는지 맞추고, timeout 오류를 무조건 재시도하지 않도록 합니다. 여러 계층의 timeout이 모순되면 사용자는 오래 기다린 뒤 원인을 알 수 없는 실패를 받습니다.

낙관적 잠금(optimistic locking)은 같은 행을 동시에 수정할 가능성이 있지만 실제 충돌은 많지 않을 때 고려할 수 있는 방법입니다. 행 버전 값을 조건에 포함해 UPDATE하고, 갱신 행 수가 0이면 다른 변경이 먼저 일어났다고 판단합니다. 이 방식은 긴 비관적 잠금을 줄일 수 있지만, 충돌한 사용자가 무엇을 다시 해야 하는지와 재시도·병합 규칙을 애플리케이션이 제공해야 합니다. 모든 업무에 자동으로 바꿀 수 있는 기법은 아닙니다.

## 모니터링과 경보 기준

잠금 대기는 일시적으로 정상일 수 있으므로, 단순히 대기 세션이 하나 생겼다는 이유로 즉시 경보를 울리면 경보 피로가 생깁니다. 대신 대기 시간이 일정 기준을 넘는 세션 수, 같은 SQL의 반복적인 timeout, 특정 모듈의 교착 상태 횟수, 연결 풀 대기 증가, 주문 처리 지연처럼 사용자 영향과 연결된 신호를 정합니다. 임계값은 데이터베이스의 이론값이 아니라 서비스의 평소 패턴과 SLO를 바탕으로 정해야 합니다.

대시보드에는 전체 세션 수만 아니라 active·idle·waiting 상태, 상위 대기 이벤트, 오래 열린 트랜잭션, blocker 후보, 모듈·서비스별 연결 수를 구분해 보여 줄 수 있습니다. 그러나 세션 SQL이나 bind 값을 그대로 넓은 대시보드에 노출하면 개인정보와 비밀 정보가 유출될 수 있습니다. 운영 조사에 필요한 사람만 원문에 접근하고, 일반 대시보드에는 집계·마스킹된 정보를 보여 주는 경계를 둡니다.

## 변경을 검증하는 시나리오

잠금 개선 뒤에는 정상 응답 시간이 줄었는지만 보지 말고, 동시 요청에서 데이터 정합성이 유지되는지 확인합니다. 같은 재고를 동시에 구매하는 요청, 동일 주문을 취소와 수정하는 요청, 배치와 온라인 요청이 겹치는 시간을 재현해 결과가 하나의 업무 규칙을 따르는지 봅니다. 테스트 환경에서 barrier나 동기화 도구로 두 트랜잭션이 같은 지점에서 만나게 하면 우연한 실행 순서에 의존하지 않고 경합을 확인할 수 있습니다.

테스트 결과에는 어떤 데이터 크기와 격리 수준, 인덱스, 세션 설정을 사용했는지 남깁니다. 직접 측정한 운영 성과라고 주장하지 않더라도, 팀 내부에서 같은 현상을 다시 확인할 수 있어야 변경의 의미를 판단할 수 있습니다. 장애를 재현하기 위해 운영 데이터를 그대로 복사하지 말고, 개인정보를 제거한 합성 데이터와 제한된 환경을 사용해야 합니다.

## SQL과 트랜잭션 경계를 함께 읽기

잠금 조사는 긴 SQL 하나를 찾는 일로 축소되기 쉽지만, 실제로는 SQL 사이의 시간도 중요합니다. 트랜잭션이 `UPDATE`를 수행하고 10초 동안 애플리케이션에서 외부 응답을 기다린 뒤 다른 SQL을 실행한다면, 첫 UPDATE 자체는 빨라도 잠금은 10초 이상 유지됩니다. APM이나 애플리케이션 trace에서 데이터베이스 호출의 시작·종료와 전체 요청 시간을 함께 보면, DB 안의 실행 시간과 트랜잭션 보유 시간을 구분할 수 있습니다.

autocommit 설정도 확인해야 합니다. 자동 commit이 켜진 단순 문장은 각 문장이 별도 트랜잭션이 될 수 있지만, 명시적인 트랜잭션 블록과 프레임워크의 transaction annotation은 여러 호출을 묶을 수 있습니다. 개발자가 SQL을 짧게 보았다고 해도 ORM flush 시점이나 예외 처리 경로에서 commit이 늦어질 수 있습니다. 실제 connection에서 트랜잭션이 언제 시작되고 끝나는지 로그와 코드 경로로 대조하는 것이 필요합니다.

읽기 쿼리도 무관하지 않습니다. 격리 수준과 문장 형태에 따라 일관된 읽기, 잠금 읽기, 갱신 대기와의 관계가 달라질 수 있습니다. `SELECT ... FOR UPDATE`는 이후 갱신을 안전하게 하기 위해 명시적으로 잠금을 얻는 도구이지만, 단순 조회처럼 넓은 범위에 사용하면 경합을 만들 수 있습니다. 왜 잠금 읽기가 필요한지, 다른 조건부 UPDATE나 version check로 같은 업무 규칙을 표현할 수 없는지 검토해야 합니다.

## 배치 작업을 온라인 작업과 분리하는 법

대량 정리·집계·마이그레이션 배치는 온라인 요청과 같은 테이블을 사용할 때 특히 주의가 필요합니다. 한 번의 트랜잭션으로 수백만 행을 갱신하면 롤백과 로그, 잠금, 복제·백업에 부담을 줄 수 있습니다. 업무적으로 허용된다면 작은 batch size로 나누고 각 묶음마다 commit하며, 다음 범위를 찾을 수 있는 안정적인 키를 사용합니다. 단, 중간 실패 뒤 같은 범위를 다시 처리해도 정확한지, 누락·중복이 없는지, 진행 상태를 어떻게 기록할지 함께 설계해야 합니다.

배치 실행 시간도 단순한 야간 여부보다 실제 온라인 부하·백업·다른 배치와의 관계로 정합니다. 야간에 고객이 적어도 정산·백업·색인 작업이 몰리면 더 큰 경합이 생길 수 있습니다. scheduler에는 동시 실행 방지와 최대 실행 시간, 실패 알림, 안전한 재시작 규칙을 둡니다. 긴급하게 배치를 중단해야 할 때 어떤 작업이 commit됐고 어떤 작업이 남았는지 판단할 수 있는 checkpoint가 있어야 합니다.

## 재시도와 사용자 경험

데드락 또는 일시적인 잠금 timeout은 제한된 재시도로 회복할 수 있지만, 사용자에게 보이는 행동을 고려해야 합니다. 동일 주문 생성 요청을 재시도할 때 주문 번호가 두 개 만들어지거나 이메일이 두 번 발송되면 데이터베이스 오류는 사라져도 업무 오류가 남습니다. 멱등 키, 고유 제약, 상태 조회를 이용해 이미 처리된 요청인지 확인하고, 사용자에게는 "처리 중입니다" 또는 "다시 시도해 주세요"처럼 실제 상태에 맞는 결과를 알려야 합니다.

backoff는 여러 요청이 동시에 재시도하며 다시 충돌하는 현상을 줄이는 데 도움이 됩니다. 그러나 너무 긴 재시도는 연결 풀과 작업자 스레드를 붙잡고, 너무 많은 반복은 장애를 확대할 수 있습니다. 최대 횟수와 전체 deadline을 정하고, 한도를 넘으면 재시도 가능한 오류와 운영자 개입이 필요한 오류를 구분합니다. 재시도 결과도 요청 ID·오류 종류·시도 횟수와 함께 관찰하면 반복되는 경합을 조기에 발견할 수 있습니다.

## 사후 분석에 남길 정보

잠금 장애가 끝난 뒤에는 시간대, 영향받은 기능, waiter와 blocker의 서비스·세션 문맥, 관련 SQL의 형태, 트랜잭션 지속 시간, 실행 계획, 배포·배치 이력, 취한 조치와 결과를 정리합니다. 이 정보가 있어야 다음 사건에서 같은 패턴인지 비교할 수 있습니다. 단, SQL의 bind 값이나 사용자 정보에는 민감 데이터가 포함될 수 있으므로 로그를 공유하기 전에 마스킹하고 접근 권한을 제한해야 합니다.

근본 원인은 하나가 아닐 수 있습니다. 인덱스가 부족해 스캔 범위가 넓었고, 동시에 배치가 긴 트랜잭션을 열었으며, 애플리케이션이 timeout을 무한 재시도했다면 세 요소가 합쳐져 증상이 커집니다. 개선 작업도 SQL, 인덱스, batch, retry 정책, 관찰성으로 나뉠 수 있습니다. 가장 눈에 띄는 세션 하나를 kill한 뒤 사건을 닫지 말고, 재발 방지 항목의 책임자와 확인 방법을 남기는 것이 중요합니다.

## 진단 권한과 안전한 도구 사용

잠금 문제를 조사하려면 동적 성능 뷰와 세션 정보를 볼 수 있어야 하지만, 이 정보에는 다른 사용자의 SQL과 접속 정보가 포함될 수 있습니다. 따라서 진단용 계정에는 필요한 조회 권한을 최소로 부여하고, 결과를 티켓이나 채팅에 붙일 때는 계정·호스트·bind 값·개인정보를 마스킹합니다. 세션 종료나 파라미터 변경 권한은 별도 역할과 승인 절차로 분리하는 편이 좋습니다. 빠른 장애 대응과 과도한 권한 부여는 같은 문제가 아닙니다.

운영 runbook에는 어떤 대기 시간과 영향에서 조사할지, 누가 서비스 담당자에게 연락할지, 어떤 증거를 수집할지, 세션 종료 전 어떤 승인이 필요한지를 적습니다. runbook이 없으면 숙련자가 우연히 기억한 SQL과 권한에 의존하게 됩니다. 반대로 runbook에 모든 상황의 명령을 적어 두고 맥락 없이 실행하게 해도 위험합니다. 관찰 항목과 의사결정 순서를 중심으로 작성하고, 각 명령은 버전·권한·영향을 확인한 뒤 사용하도록 합니다.

## 구조적 재발 방지 기준

잠금 문제가 같은 테이블에서 반복된다면 특정 사건의 SQL만 고치기보다 데이터 모델을 다시 볼 필요가 있습니다. 하나의 카운터 행에 모든 요청이 몰리는지, 상태 전이가 너무 많은 테이블을 동시에 갱신하게 하는지, 보고용 집계가 온라인 거래 테이블을 계속 읽고 쓰는지, tenant·조직별로 작업을 분리할 수 있는지 검토합니다. 대량 경합을 큐나 partition, 비동기 집계로 옮길 때는 새 시스템의 순서 보장과 재처리 규칙도 함께 설계해야 합니다.

성공 기준은 잠금 이벤트가 완전히 사라지는 것이 아닐 수 있습니다. 정상적인 동시 갱신에서는 짧은 대기가 발생할 수 있습니다. 중요한 것은 대기가 사용자 SLO를 넘지 않고, 교착 상태와 timeout이 안전하게 처리되며, 원인을 찾을 관찰 정보와 대응 절차가 있는 상태입니다. 이 기준을 서비스별로 합의하면 DBA와 애플리케이션 팀이 서로 다른 지표를 보고도 같은 목표를 향해 개선할 수 있습니다.

### 데이터 변경 배포와 잠금

스키마 변경이나 대량 데이터 보정은 평소보다 넓은 범위에 영향을 줄 수 있습니다. DDL과 DML이 같은 시간에 실행될 때 어떤 잠금과 대기가 생길 수 있는지, 현재 장기 트랜잭션이 있는지, 배포 도구가 실패하면 재시도하는지 확인해야 합니다. 변경을 작은 단계로 나누고, 실행 전후 세션·오류·응답 시간을 관찰하면 문제가 생겼을 때 원인을 좁히기 쉽습니다. 대규모 변경은 애플리케이션 기능 배포와 분리해 위험을 줄이는 방법도 검토할 수 있습니다.

장애 대응 중에도 데이터 정합성이 우선입니다. 빨리 끝내기 위해 commit되지 않은 작업의 의미를 확인하지 않고 세션을 종료하거나, 잠금 오류를 숨기도록 예외를 무시하면 나중에 더 어려운 복구 작업이 남습니다. 잠금을 조사하는 목적은 기다림을 없애는 것이 아니라, 올바른 업무 상태를 안전하게 회복하는 것입니다.

### 용량 계획과 동시성의 관계

동시 요청 수가 늘어날수록 같은 hot row나 인덱스 범위에서 경합이 드러날 가능성도 커집니다. 단순히 database connection 수와 애플리케이션 worker 수를 늘리면 처리량이 증가할 수 있지만, 잠금·CPU·디스크·로그 기록이 포화된 상황에서는 대기열만 길어질 수 있습니다. 부하 증가를 예상한다면 최대 동시 작업 수, 큐 길이, 요청 제한, batch 병렬도와 데이터베이스 용량을 같이 계획해야 합니다. HPA나 자동 확장은 요청을 더 많이 보내는 도구이지, 단일 데이터 행의 동시 수정 능력을 무한히 늘리는 도구가 아닙니다.

부하 테스트에서도 평균 응답 시간만 보지 말고, 긴 꼬리 지연과 timeout·deadlock·재시도 비율을 함께 확인하세요. 평균은 정상 요청이 가려 줄 수 있지만, 일부 사용자가 잠금 때문에 오래 기다리면 서비스 신뢰는 크게 떨어집니다. 어떤 수준의 경합까지 허용할지와 그 이상에서 어떤 보호 조치를 할지 정하면, 증상이 커지기 전에 대응할 수 있습니다.

## 한계와 적용 기준 Q&A

### Q. 잠금 대기가 길면 timeout을 크게 늘리면 되나요?

A. timeout을 늘리면 사용자는 더 오래 기다리고 연결 풀·스레드가 묶일 수 있습니다. 먼저 어떤 세션이 왜 잠금을 오래 보유하는지, 좁힐 수 있는 트랜잭션·인덱스·배치 범위가 있는지 조사하세요. timeout은 정상적으로 기다릴 수 있는 상한을 정하는 장치이지 구조적 병목을 해결하는 방법은 아닙니다.

### Q. 교착 상태는 DBMS 버그인가요?

A. 보통은 여러 트랜잭션의 접근 순서와 동시 실행에서 생기는 정상적인 동시성 현상입니다. DBMS가 한 작업을 중단시켜 순환을 끊는 것은 데이터 정합성을 지키기 위한 동작일 수 있습니다. 원인 SQL과 업무 흐름을 조사하고, 순서 통일·짧은 트랜잭션·안전한 제한 재시도로 대응하세요.

### Q. blocker 세션을 죽이면 다른 사용자 요청이 바로 정상화되나요?

A. blocker가 롤백되는 동안에도 자원이 유지될 수 있고, 영향을 받은 요청은 오류나 timeout으로 이미 실패했을 수 있습니다. 또한 같은 코드가 다시 긴 트랜잭션을 만들면 문제가 반복됩니다. 세션 종료는 영향 확인·기록·원인 개선과 함께 하는 긴급 조치로 봐야 합니다.

### Q. 잠금 진단은 DBA만 할 수 있나요?

A. 동적 성능 뷰와 세션 제어는 DBA 권한이 필요할 수 있지만, 애플리케이션 팀은 트랜잭션 경계, 연결 풀 설정, SQL 호출 순서, 멱등 재시도, 업무 영향 정보를 제공해야 합니다. 잠금은 데이터베이스와 애플리케이션의 경계에서 생기므로 두 역할이 함께 봐야 빠르게 해결할 수 있습니다.

잠금과 대기 지표는 서비스의 실제 사용 패턴과 업무 중요도를 반영해 정기적으로 조정해야 합니다. 같은 숫자라도 결제·재고·보고 기능에서 허용 가능한 영향은 다릅니다.

## 마무리

Tibero 잠금 대기는 단순히 느린 SQL 하나를 고치는 문제가 아니라, 여러 트랜잭션이 같은 데이터를 어떤 순서와 시간 동안 다루는지 이해하는 문제입니다. waiter와 blocker의 체인을 만들고, 긴 트랜잭션·넓은 접근 범위·순서 불일치를 나누어 조사하며, 세션 종료는 영향과 복구를 고려한 마지막 수단으로 사용하세요. 이렇게 하면 장애를 급히 끄는 데서 멈추지 않고 같은 경합이 다시 생기는 구조를 개선할 수 있습니다.
