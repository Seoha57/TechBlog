웹 화면은 기능 테스트가 통과해도 망가질 수 있습니다. 결제 버튼의 글자가 배경색과 같아졌거나, 긴 상품명이 카드 밖으로 밀려났거나, 모바일에서 안내 문구가 고정 헤더에 가려졌어도 `POST /orders`가 200을 반환하고 버튼의 click handler가 호출되면 일반적인 API·DOM 테스트는 성공할 수 있습니다. 사람이 브라우저를 열어 확인하면 보이지만, 화면과 브라우저 조합이 늘수록 모든 변경을 눈으로 점검하는 일은 금방 감당하기 어려워집니다.

**시각 회귀 테스트(Visual Regression Testing, VRT)** 는 승인된 화면의 기준 이미지(baseline screenshot)와 현재 화면의 이미지를 비교해 의도하지 않은 모양 변화를 찾는 테스트 방식입니다. 테스트는 정해진 URL·데이터·뷰포트에서 스크린샷을 만들고, 이전에 승인한 이미지와 픽셀 또는 지각적 차이를 비교합니다. 차이가 임계값을 넘으면 실패하고, 개발자나 디자이너가 그 차이가 제품 변경인지 결함인지 검토합니다. 즉 VRT는 “화면이 예쁜가”를 자동으로 판단하는 기능이 아니라, **바뀐 곳을 빠뜨리지 않고 보여 주는 변경 감지 장치**입니다.

이 글은 Playwright의 screenshot assertion을 예로 들지만, 특정 제품을 도입하라는 글은 아닙니다. 기준 이미지를 누가 승인하는지, 시간·데이터·폰트·광고 같은 변동 요소를 어떻게 통제하는지, 시각 비교가 기능·접근성 테스트를 대체하지 않는 이유를 먼저 이해하는 것이 중요합니다. 특히 취업 준비생이 “스크린샷을 찍는 테스트”를 단순한 E2E 테스트의 장식으로 오해하지 않도록, 데이터와 리뷰 흐름까지 함께 설명합니다.

## 먼저 알아둘 기반 기술: 렌더링·DOM·스크린샷·스냅샷

브라우저가 화면을 그리는 과정부터 구분해 보겠습니다. HTML은 문서의 구조를, CSS는 색·크기·배치 규칙을, JavaScript는 데이터 로딩과 상호작용을 담당합니다. 브라우저는 이 정보를 해석해 DOM(Document Object Model, 문서 객체 모델)과 스타일 정보를 만들고, layout과 paint 과정을 거쳐 실제 픽셀을 그립니다. 같은 DOM이라도 CSS가 바뀌면 화면은 달라질 수 있고, 같은 CSS라도 폰트·브라우저 엔진·뷰포트·운영체제에 따라 줄바꿈과 안티앨리어싱이 달라질 수 있습니다.

**스크린샷(screenshot)** 은 특정 시점의 렌더링 결과를 이미지로 캡처한 것입니다. **스냅샷(snapshot)** 은 비교를 위해 저장해 둔 기준 결과라는 더 넓은 개념입니다. 텍스트 스냅샷, JSON 스냅샷, 이미지 스냅샷이 모두 있을 수 있습니다. 시각 회귀 테스트에서 기준 이미지는 “이 화면이 현재 의도한 모습”이라는 합의의 산출물입니다. 코드와 별개로 취급하면 안 됩니다. 기준 이미지가 왜 바뀌었는지 PR(Pull Request, 변경 제안)에서 설명하고 리뷰할 수 있어야 합니다.

**픽셀 차이(pixel diff)** 는 기준 이미지와 현재 이미지의 같은 좌표에 있는 색 값을 비교하는 방법입니다. 차이가 난 픽셀의 수나 전체 대비 비율을 측정해 허용 범위를 정할 수 있습니다. 하지만 모든 픽셀 차이가 결함은 아닙니다. 서브픽셀 렌더링, 폰트 힌팅, 그림자, 애니메이션의 한 프레임 차이도 픽셀 차이를 만들 수 있습니다. 그래서 일부 도구는 사람이 인지하는 색 차이에 가까운 threshold를 제공하고, 팀은 일정 환경에서 이미지를 생성하거나 동적 영역을 가리는 규칙을 둡니다.

**E2E(End-to-End, 종단 간) 테스트** 는 사용자가 로그인하고 상품을 장바구니에 넣고 결제하는 것처럼 여러 시스템 경계를 지나는 행동을 확인합니다. 시각 테스트는 E2E 흐름 중 특정 상태에서 실행될 수 있지만, 목적은 다릅니다. 예를 들어 주문 생성 API를 mock한 상태에서 “장바구니가 비어 있음” 컴포넌트만 빠르게 캡처할 수도 있습니다. 모든 시각 테스트가 실제 결제 시스템까지 호출할 필요는 없고, 오히려 고정된 fixture가 비교를 더 안정적으로 만들 수 있습니다.

## 무엇을 잡고 무엇을 놓치는가

VRT가 잘 잡는 문제는 눈으로 보는 결과가 계약인 경우입니다. 반응형 breakpoint에서 메뉴가 두 줄로 깨지는 문제, 버튼 텍스트와 배경의 대비가 의도치 않게 변한 문제, modal이 header 뒤로 숨는 z-index 문제, 길어진 번역 문구가 잘리는 문제, 카드 목록의 간격이 무너지는 문제는 DOM selector가 존재하고 API가 성공해도 남을 수 있습니다. 디자인 시스템의 버튼·입력창·알림 같은 공용 컴포넌트를 캡처하면 한 번의 CSS 변경이 여러 화면에 미치는 영향을 빨리 찾는 데도 도움이 됩니다.

반대로 VRT가 단독으로 잘 못하는 일도 명확합니다. 스크린샷이 정상처럼 보여도 키보드로 focus를 이동할 수 없을 수 있고, screen reader가 버튼의 이름을 읽지 못할 수 있으며, 클릭 뒤에 잘못된 금액이 저장될 수 있습니다. 색 대비가 이미지상 비슷하게 보여도 WCAG(Web Content Accessibility Guidelines, 웹 콘텐츠 접근성 지침) 계산 기준을 만족한다는 뜻은 아닙니다. 따라서 접근성은 semantic HTML, ARIA, keyboard test, contrast 검사로 따로 확인하고, 기능은 API·통합·E2E 테스트로 확인해야 합니다.

다음 표처럼 질문을 나누면 도구를 과대평가하지 않게 됩니다.

| 확인하려는 질문 | 우선 테스트 | 시각 회귀 테스트의 역할 |
| --- | --- | --- |
| 주문이 중복 생성되지 않는가 | 단위·통합·API 테스트 | 결과 화면의 오류 메시지 배치 확인 |
| 키보드만으로 모달을 닫을 수 있는가 | 접근성·키보드 E2E | focus ring이 가려지지 않는지 보조 확인 |
| 모바일에서 가격 버튼이 잘리지 않는가 | 시각 회귀 테스트 | 여러 뷰포트에서 직접 감지 |
| 서버가 느릴 때 loading에서 error로 전환되는가 | 네트워크 제어 E2E | loading/error 상태의 모양 비교 |
| 디자인 변경이 의도된 것인가 | 사람 리뷰 | 변경 부위를 빠르게 보여 주는 증거 |

## 기준 이미지가 제품 계약이 되려면

첫 실행에서 만들어진 이미지를 곧바로 정답으로 취급하면 안 됩니다. 그 이미지는 테스트 도구가 우연히 찍은 파일일 뿐입니다. 기준선을 만들 때는 제품·디자인·QA가 같은 질문에 답해야 합니다. 어느 URL과 사용자 상태를 캡처하는가, 데이터는 무엇으로 고정하는가, desktop과 mobile의 너비는 얼마인가, 언어는 무엇인가, 로딩 완료를 무엇으로 판단하는가, 시간·날짜·광고·추천·알림은 어떻게 다루는가를 정합니다.

예를 들어 “상품 상세”라는 하나의 화면도 로그인 사용자와 비로그인 사용자가 보는 가격·버튼이 다르고, 재고가 0인 경우와 있는 경우가 다릅니다. 무작위 추천 상품을 API에서 받아 온다면 매 실행마다 카드 이미지와 제목이 바뀔 수 있습니다. 이런 상태를 한 스냅샷에 전부 섞으면 실패 원인을 알기 어렵습니다. `상품 상세 - 재고 있음 - 한국어 - 1280px`, `상품 상세 - 품절 - 한국어 - 390px`처럼 업무 상태를 이름에 드러내고, API 응답이나 fixture를 고정하는 편이 좋습니다.

기준 이미지의 승인 규칙도 중요합니다. 승인 가능한 변경은 디자인 티켓·요구사항과 연결되고, 이미지 diff를 본 사람이 근거를 남깁니다. 승인 불가 변경은 CSS 수정, 상태 데이터 정정, 비교 마스크 조정으로 되돌립니다. 단순히 “baseline update” 커밋이 반복되면 누구도 이미지 변경을 읽지 않고, 결국 실패 알림이 무시됩니다. 기준 이미지는 테스트 산출물이지만 동시에 사용자 경험의 versioned artifact입니다.

## Playwright 예시: 작은 화면 하나부터 시작하기

Playwright Test는 `expect(page).toHaveScreenshot()`으로 이미지 비교를 제공합니다. 공식 문서는 첫 실행에서 기준 스크린샷을 만들고, 다음 실행부터 현재 이미지와 비교한다고 설명합니다. 아래 예시는 실제 쇼핑몰 대신 고정된 로컬 fixture를 제공하는 `/products/42` 화면을 가정합니다. 외부 API·실시간 데이터가 아니라 테스트용 응답을 사용해, 실패가 네트워크 변동인지 CSS 변경인지 구분하기 쉽게 만듭니다.

```ts
import { test, expect } from '@playwright/test';

test('상품 상세의 품절 상태는 모바일에서 버튼이 겹치지 않는다', async ({ page }) => {
  await page.route('**/api/products/42', async route => {
    await route.fulfill({
      contentType: 'application/json',
      body: JSON.stringify({
        id: 42,
        name: '테스트용 긴 상품명입니다. 줄바꿈을 확인합니다.',
        price: 12000,
        stock: 0
      })
    });
  });

  await page.setViewportSize({ width: 390, height: 844 });
  await page.goto('/products/42');
  await expect(page.getByRole('heading', { name: /테스트용 긴 상품명/ })).toBeVisible();
  await expect(page).toHaveScreenshot('product-out-of-stock-mobile.png', {
    fullPage: true,
    animations: 'disabled'
  });
});
```

이 예시에는 기능 assertion과 이미지 assertion이 함께 있습니다. heading이 보인다는 확인 없이 바로 스크린샷을 찍으면, 로딩 중 화면을 기준으로 저장하거나 오류 페이지와 비교할 수 있습니다. 반대로 heading 확인만 하면 “텍스트가 보인다”는 사실은 알 수 있어도 버튼이 화면 밖으로 나갔는지는 알기 어렵습니다. 목적이 다른 두 assertion을 함께 두면 실패 메시지도 더 읽기 쉬워집니다.

팀 공통 설정은 개별 테스트에 같은 값을 반복하는 대신 test configuration에 둘 수 있습니다. 단, 허용치를 넓게 잡아 실패를 줄이는 것은 안정화가 아닙니다. `maxDiffPixels`나 `maxDiffPixelRatio`는 사람이 검토한 작은 렌더링 오차를 다루기 위한 안전판이지, 화면 절반이 바뀌어도 통과시키는 장치가 아닙니다.

```ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  expect: {
    toHaveScreenshot: {
      animations: 'disabled',
      maxDiffPixelRatio: 0.001
    }
  },
  projects: [
    { name: 'chromium-desktop', use: { ...devices['Desktop Chrome'] } },
    { name: 'chromium-mobile', use: { ...devices['iPhone 13'] } }
  ]
});
```

이 설정의 숫자는 예시입니다. 어떤 임계값이 적절한지는 폰트·OS·renderer·화면 위험도에 따라 다릅니다. 첫 도입에서 여러 browser와 OS를 모두 비교하려 하기보다, 기준 이미지를 만든 CI 환경 하나와 핵심 viewport 몇 개를 먼저 고정하는 편이 운영하기 쉽습니다.

## 불안정성의 원인: 테스트가 아니라 입력이 흔들리는 경우

시각 테스트가 flaky하다는 말은 종종 테스트 도구 탓으로 끝납니다. 그러나 상당수의 실패는 화면 입력이 비결정적이기 때문에 발생합니다. 현재 시간, 사용자별 추천, A/B 실험, 광고 iframe, web font 로딩, CSS animation, 네트워크 지연, 스크롤 위치, 브라우저·OS 차이는 같은 테스트가 다른 픽셀을 만들 수 있는 대표 원인입니다. Playwright 공식 문서도 기준 이미지와 비교 이미지를 같은 환경에서 생성해야 한다고 안내합니다.

가장 먼저 할 일은 threshold를 키우는 것이 아니라 변동 원인을 명시적으로 통제하는 것입니다.

1. **시간과 timezone을 고정한다.** “오늘”, 상대 시간, 날짜 포맷이 화면에 있으면 테스트 시계와 locale을 정하거나 표시를 fixture로 바꾼다.
2. **데이터를 고정한다.** 가격·재고·추천 목록·사용자 이름을 API mock, seed 데이터, 테스트 계정으로 일정하게 만든다.
3. **로딩 완료 조건을 정한다.** 단순 sleep 대신 heading, skeleton 제거, 특정 API 응답, 이미지 load처럼 화면 준비를 의미하는 신호를 기다린다.
4. **애니메이션을 제어한다.** 테스트에서 의미 없는 transition·caret blink·자동 carousel은 끄거나 안정된 상태에서 캡처한다.
5. **폰트와 환경을 고정한다.** CI container와 browser version을 lock하고, 필요한 web font가 로드된 뒤 캡처한다.
6. **외부 영역을 분리한다.** 지도·광고·채팅 위젯처럼 소유하지 않는 영역은 mask 또는 test double로 바꾸고, 그 결정 자체를 문서화한다.

mask는 편리하지만 무조건 좋은 해법은 아닙니다. 결제 총액처럼 자주 바뀌는 값이 아니라, 실제로 중요한 값이 가려지면 테스트 가치가 사라집니다. “무엇을 가렸는가”와 “왜 그 영역을 UI 계약에서 제외했는가”를 코드 리뷰에서 볼 수 있어야 합니다. 외부 광고 영역을 가리는 것은 합리적일 수 있지만, 사내 알림 배너를 가리는 것은 결함을 숨길 수 있습니다.

## 컴포넌트·페이지·여정 중 어디를 캡처할까

시각 회귀 테스트의 범위를 넓게 잡을수록 커버리지는 커 보이지만 리뷰 비용과 불안정성도 증가합니다. 그래서 세 계층을 나누어 생각하면 좋습니다. **컴포넌트 수준**에서는 버튼, 입력창, 오류 메시지, 카드처럼 디자인 시스템의 공용 조각을 여러 상태로 확인합니다. 빠르고 실패 위치가 명확합니다. **페이지 수준**에서는 상품 상세, 로그인, 장바구니처럼 한 화면의 반응형 배치와 상태 조합을 확인합니다. **여정 수준**에서는 로그인 후 결제 확인 화면까지 이동해 실제 흐름 중 핵심 checkpoint만 캡처합니다.

처음 도입할 팀이라면 전부를 캡처하지 말고, 사용자 영향과 변경 빈도를 기준으로 고릅니다. 예를 들어 로그인의 오류 상태, 결제 금액 요약, 모바일 내비게이션, 공용 modal은 작은 변경도 사용자에게 크게 보이므로 후보가 됩니다. 관리자가 한 달에 한 번 보는 설정 페이지나 변동이 심한 분석 차트는 후순위일 수 있습니다. 테스트 목록은 “예쁜 화면”보다 실패 비용이 큰 화면을 우선해야 합니다.

```text
1단계: 공용 버튼·폼·오류 상태를 컴포넌트 단위로 고정한다.
2단계: 구매·가입·로그인 같은 핵심 페이지를 desktop/mobile에서 캡처한다.
3단계: 실제 사용자 여정의 전환 지점만 E2E 흐름에서 캡처한다.
4단계: 실패율과 리뷰 시간을 보고, 가치가 낮거나 불안정한 스냅샷은 제거하거나 범위를 줄인다.
```

이 순서는 모든 화면을 자동화했다는 숫자보다 실패를 읽고 행동할 수 있는 상태를 우선합니다. 검토하지 않는 1,000장의 스크린샷은 품질 보증이 아니라 저장 비용과 알림 피로가 됩니다.

## CI와 코드 리뷰에서 차이를 다루는 방법

VRT의 결과물은 pass/fail 문자열만이 아니라 기준·실제·diff 이미지입니다. CI(Continuous Integration, 지속적 통합)는 PR마다 정해진 브라우저와 뷰포트에서 테스트를 실행하고, 실패하면 세 이미지를 artifact로 남깁니다. 리뷰어는 변경 부위를 보고 다음을 판단합니다. 요구사항이 의도한 변경인가, 다른 컴포넌트에 파급된 부작용인가, 데이터 또는 로딩 타이밍의 흔들림인가, 기준 이미지 갱신이 필요한가입니다.

기준 갱신을 별도 책임으로 두는 방식도 효과적입니다. 개발자가 테스트를 고치고 기준 이미지를 바꿀 수는 있지만, 관련 디자인·QA 리뷰가 없으면 merge하지 않는 규칙을 둘 수 있습니다. 중요한 화면은 diff 이미지 링크를 PR 설명에 넣고, 의도적 변경이면 요구사항 번호를 연결합니다. 이는 도구가 자동으로 품질을 승인하는 흐름이 아니라, 사람이 바뀐 결과를 빠르게 이해하게 만드는 흐름입니다.

실패 triage는 세 갈래로 나눕니다. 첫째 **진짜 회귀**라면 CSS·컴포넌트·data handling을 수정하고 기존 기준과 다시 비교합니다. 둘째 **의도한 변경**이라면 요구사항을 확인하고 기준을 갱신합니다. 셋째 **테스트 불안정성**이라면 시간·폰트·외부 데이터·대기 조건을 고칩니다. 세 번째를 기준 이미지 갱신으로 처리하면 다음 실행에서 같은 실패가 반복됩니다. 반대로 첫 번째를 threshold 확대로 처리하면 실제 사용자 결함이 통과합니다.

## 디자인 시스템과 VRT를 함께 운영하는 방법

디자인 시스템을 쓰는 팀에서는 페이지마다 스크린샷을 늘리기 전에 공용 component의 상태를 기준선으로 만들면 효율이 좋습니다. 예를 들어 Button에는 기본·hover·disabled·loading·긴 텍스트·아이콘만 있는 상태가 있고, Input에는 빈 값·오류·도움말·긴 label·focus 상태가 있습니다. 이 상태가 여러 페이지에서 반복되므로 component 수준에서 먼저 잡으면 CSS token 하나의 변경이 어떤 상태를 흔드는지 빠르게 확인할 수 있습니다.

**design token(디자인 토큰)** 은 색·간격·폰트 크기·border radius처럼 반복되는 시각 값을 이름으로 관리하는 방식입니다. `--color-brand-primary`를 바꿨을 때 버튼뿐 아니라 링크·badge·focus ring까지 바뀔 수 있습니다. token 변경은 의도적으로 넓은 diff를 만들 수 있으므로, PR에 “brand primary를 어느 값에서 어느 값으로 바꾸며 어느 화면이 바뀌는가”를 기록하고 대표 component 스냅샷을 함께 검토합니다. 이때 VRT의 역할은 token의 값이 규정에 맞는지 판단하는 것이 아니라, 예상하지 못한 소비자를 찾는 것입니다.

component snapshot이 page snapshot을 완전히 대체하지는 않습니다. 실제 페이지에는 grid, container query, header, localization, permission에 따른 조건부 렌더링이 있기 때문입니다. 다만 공용 component → 대표 페이지 → 핵심 여정 순서로 계층을 두면 같은 CSS 결함을 수십 페이지의 diff에서 반복해서 보는 일을 줄일 수 있습니다. 독립 component가 없고 모든 UI가 page 안에 얽혀 있다면, VRT 도입 전에 component 경계를 정리할 기회가 되기도 합니다. 하지만 테스트를 위해 대규모 리팩터링을 먼저 할 필요는 없습니다. 현재 가장 자주 깨지는 화면의 selector와 fixture부터 만들면 됩니다.

## 테스트 데이터와 개인정보의 경계

스크린샷에는 생각보다 많은 정보가 들어갑니다. 고객 이름·이메일·주소·주문 번호, 관리자 메뉴, 사내 프로젝트명, 오류 stack trace가 artifact나 Git 기준 이미지에 남을 수 있습니다. 기준 이미지는 코드 리뷰에서 넓게 공유될 수 있고, CI artifact의 보관 기간과 접근 권한도 운영 환경과 다를 수 있습니다. 따라서 VRT의 fixture는 가상의 이름·가격·식별자를 사용하고, test account의 권한을 최소화하며, 실제 production API를 캡처 대상으로 삼지 않는 것이 안전합니다.

개인정보를 가리기 위해 mask를 쓰는 방법도 있지만, 원본 이미지가 생성·업로드되는 경로를 먼저 확인해야 합니다. 도구가 캡처 전에 mask를 적용하는지, artifact에 원본도 남기는지, 외부 SaaS에 DOM·asset을 전송하는지를 검토합니다. 특히 제3자 visual testing 서비스는 CI에서 접근하는 preview URL과 정적 asset, 화면 데이터가 서비스 외부로 나갈 수 있는지 계약·보안 정책과 함께 판단해야 합니다. “이미지니까 데이터가 아니다”라는 가정은 위험합니다.

테스트 데이터는 기능 fixture와 같은 원칙을 따릅니다. 재현 가능해야 하고, 테스트 목적에 필요한 최소 정보만 가져야 하며, reset 방법이 있어야 합니다. 장바구니의 긴 상품명·품절·할인 상태처럼 레이아웃을 흔들 수 있는 값을 의도적으로 넣되, 매 실행마다 값이 달라지는 생성기나 실제 고객 데이터를 쓰지 않습니다. 이 원칙은 test flake를 줄이는 동시에 정보 노출 위험도 낮춥니다.

## 실패율로 테스트 건강도를 판단한다

VRT 도입 성과를 “스크린샷 수”로만 측정하면 가치 없는 테스트가 늘기 쉽습니다. 더 유용한 지표는 실패한 diff 중 실제 결함 비율, 의도적 기준 갱신 비율, 환경 변동으로 재실행만 한 비율, PR당 리뷰 시간, 사용자에게 영향을 준 UI 회귀를 얼마나 일찍 발견했는가입니다. 반복적으로 같은 font load 때문에 실패한다면 테스트 수가 많아도 신뢰도는 낮습니다. 반대로 아주 적은 핵심 스냅샷이 모바일 결제 버튼 겹침을 배포 전에 잡는다면 높은 가치를 가집니다.

매주 또는 매 sprint에 실패를 짧게 분류해 보세요. 특정 컴포넌트에서 의도하지 않은 diff가 반복되면 CSS ownership이나 design token 사용 규칙을 개선할 신호입니다. 특정 페이지가 항상 외부 widget 때문에 흔들리면 더 좁은 component snapshot으로 바꾸거나 안정된 test double을 제공합니다. 기준 이미지 갱신이 너무 잦다면 제품이 빠르게 바뀌어서일 수도 있지만, 기준선·fixture·뷰포트 정의가 불명확한 것일 수도 있습니다. 테스트를 삭제하는 것도 정상적인 유지보수 선택입니다. 검토하지 않는 불안정한 snapshot은 품질 신호가 아닙니다.

## 도입 순서: 하루 안에 끝낼 수 있는 작은 시작

처음부터 visual test 플랫폼을 도입하거나 전 페이지의 이미지를 생성할 필요는 없습니다. 한 화면에서 다음 순서를 따라도 충분히 가치를 확인할 수 있습니다.

1. 최근 UI 회귀가 있었거나 실패 비용이 큰 화면 하나를 고른다. 모바일 로그인 오류, 결제 요약, 공용 alert처럼 범위가 작은 것이 좋다.
2. 필요한 사용자 상태와 API 응답을 fixture로 고정하고, desktop과 mobile 중 실제 위험이 큰 한 뷰포트를 선택한다.
3. 화면 준비 조건 하나와 screenshot assertion 하나를 작성한다. 외부 widget은 우선 test double로 바꾸고, mask가 필요하면 이유를 남긴다.
4. 기준 이미지를 처음 생성한 뒤 디자이너 또는 해당 기능 책임자와 함께 승인한다.
5. CI에서 diff artifact를 볼 수 있게 하고, 첫 달에는 실패 이유를 진짜 회귀·의도 변경·flake로 분류한다.

이 작은 흐름에서 안정적으로 동작한다면 공용 component와 핵심 페이지로 확장합니다. 반대로 기준 이미지가 매일 바뀌거나 리뷰어가 diff를 보지 않는다면 수를 늘리지 말고 data·환경·리뷰 흐름부터 고쳐야 합니다. 시각 회귀 테스트는 자동화 도구를 추가하는 프로젝트라기보다, UI 변경을 승인하는 팀의 습관을 만드는 작업입니다.

## 업무 예시: 장바구니 할인 배너가 모바일에서 사라진 사건

가상의 쇼핑 서비스가 프로모션 배너를 장바구니 상단에 추가했다고 가정해 보겠습니다. desktop에서는 정상이고, 기능 테스트도 장바구니 금액이 정확하며 쿠폰 API가 호출되는 것을 확인합니다. 하지만 390px viewport에서 긴 할인 문구와 닫기 버튼이 한 줄에 배치되면서 버튼이 오른쪽 화면 밖으로 밀렸습니다. 사용자는 배너를 닫을 수 없고, 금액 요약까지 아래로 밀려 결제 버튼이 잘 보이지 않습니다.

이 결함은 API 테스트만으로는 찾기 어렵습니다. 모바일 장바구니의 고정 fixture—긴 한국어 문구, 적용된 쿠폰, 여러 상품—를 준비하고, 핵심 금액 요약과 배너가 보이는 상태에서 스크린샷을 비교하면 CSS flex 변경이나 글꼴 크기 변경 때 diff가 발생합니다. 여기서 “diff가 났다”는 사실만으로 결함이 확정되지는 않습니다. 리뷰어는 요구된 배너 모양인지, 닫기 버튼이 실제로 접근 가능한지, 결제 행동에 영향을 주는지를 함께 확인합니다.

수정 후에는 이미지 assertion 외에 `닫기` 버튼이 보이고 keyboard focus를 받으며 click 뒤 배너가 사라지는 E2E assertion을 추가할 수 있습니다. 이 조합이 핵심입니다. 이미지로 위치·겹침을, role 기반 locator와 keyboard test로 상호작용·접근성을, API 테스트로 할인 계산을 나누어 확인합니다. 한 종류의 테스트가 모든 품질 특성을 증명한다고 기대하지 않는 설계입니다.

## 브라우저와 언어를 늘릴 때의 기준

같은 화면이라도 Chrome, Firefox, WebKit은 폰트 렌더링과 layout의 세부 결과가 다를 수 있습니다. 다국어 서비스는 한국어보다 긴 독일어, 오른쪽에서 왼쪽으로 읽는 언어, 숫자·통화 포맷이 다른 locale에서 줄바꿈과 overflow가 달라질 수 있습니다. 그렇다고 모든 browser·언어·해상도의 조합을 매 PR마다 캡처하면 CI 시간과 기준 이미지가 폭발합니다.

실제 사용자 비중과 실패 비용을 근거로 대표 조합을 정합니다. 예를 들어 모바일 결제가 중요한 서비스라면 가장 많이 쓰는 mobile browser와 긴 번역문이 나오는 locale을 우선하고, 공용 컴포넌트는 desktop Chromium과 WebKit을 별도 nightly job에서 확인할 수 있습니다. 지원하지 않는 browser를 테스트로 암묵적으로 약속하지 않도록, 제품의 browser support policy와 VRT project 목록을 맞춰 두는 것도 필요합니다. 테스트 범위는 커버리지 숫자가 아니라 고객 약속을 표현해야 합니다.

기준 이미지 변경 권한과 승인 책임도 화면 위험도에 따라 구분할 수 있습니다. 결제·인증처럼 영향이 큰 화면은 diff와 요구사항을 함께 검토하고, 사소한 내부 관리 화면은 더 가벼운 절차를 적용합니다. 중요한 점은 기준선이 테스트 도구의 캐시가 아니라 제품 의사결정의 기록이라는 사실입니다.

## 한계와 적용 기준 Q&A

### Q. 픽셀 차이가 0이어야 가장 좋은 테스트 아닌가요?

A. 항상 그렇지는 않습니다. 동일한 CI 이미지·browser·폰트·시간을 고정했다면 중요한 컴포넌트는 매우 엄격하게 비교할 수 있습니다. 하지만 OS 렌더링·폰트·안티앨리어싱이 다른 환경을 같은 baseline으로 비교하면 사소한 차이로 실패가 늘 수 있습니다. 해결은 무조건 허용치를 높이는 것이 아니라 비교 환경을 고정하고, 필요한 경우에만 검토된 작은 허용 범위를 두는 것입니다.

### Q. 기준 이미지를 Git에 같이 커밋해도 괜찮나요?

A. 보통은 코드와 함께 version control하여 어떤 변경이 기준을 바꿨는지 추적하는 방식이 유용합니다. 다만 이미지 용량과 저장 정책, 제품 스크린샷에 포함된 개인정보·실제 고객 데이터 여부를 확인해야 합니다. fixture와 테스트 계정으로 민감정보가 없는 기준 이미지를 만들고, 큰 산출물은 팀의 artifact 저장 정책을 따릅니다.

### Q. 시각 회귀 테스트가 통과하면 접근성 검사를 생략해도 되나요?

A. 안 됩니다. 스크린샷은 screen reader 이름, 키보드 tab 순서, semantic heading 구조, 색 대비 계산, focus trap의 동작을 충분히 알려 주지 못합니다. 접근성 전용 검사와 수동 보조기술 점검, 기능 E2E를 함께 운영해야 합니다. VRT는 시각적 결과를 다루는 한 계층입니다.

### Q. 외부 광고·지도·차트는 전부 mask하면 되나요?

A. 화면 계약에 속하지 않는 제3자 광고처럼 변동을 소유하지 않는 영역은 mask가 합리적일 수 있습니다. 하지만 사용자가 실제로 써야 하는 지도·차트·사내 알림을 가리면 중요한 결함을 숨길 수 있습니다. 해당 영역을 별도 테스트 환경에서 deterministic하게 만들 수 있는지 먼저 검토하고, mask를 사용한 이유와 범위를 코드 리뷰에서 확인해야 합니다.

## 마무리

시각 회귀 테스트의 목표는 모든 픽셀을 영원히 고정하는 것이 아닙니다. 사용자에게 보이는 결과가 바뀌었을 때, 그 변화가 의도된 변경인지 결함인지 사람이 빠르게 판단할 수 있게 만드는 것입니다. 이를 위해서는 기준 이미지, 고정 데이터, 뷰포트, 브라우저 환경, 리뷰 규칙을 함께 관리해야 합니다.

처음에는 가장 위험한 컴포넌트와 핵심 모바일 페이지 몇 개만 고르고, 기능·접근성 테스트와 역할을 분리하세요. 실패를 기준 이미지 갱신으로 덮지 않고 데이터·로딩·CSS 중 원인을 고치면, 스크린샷 비교는 불안정한 장식이 아니라 UI 변경을 신뢰할 수 있게 만드는 QA 신호가 됩니다.
