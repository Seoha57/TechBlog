애플리케이션은 `127.0.0.1:8080`에서 잘 열리는데, 외부 도메인으로 접속하면 인증서 경고가 뜨거나 502 Bad Gateway가 난다고 가정해 봅시다. 서버 프로세스는 살아 있어도 사용자는 도메인, DNS(Domain Name System, 이름을 IP 주소로 찾는 체계), 방화벽, TLS(Transport Layer Security, 통신 내용을 암호화하고 서버 신원을 확인하는 규약), 웹 서버를 차례로 지나야 합니다. 이 앞단을 이해하지 못하면 “애플리케이션은 정상인데 왜 접속이 안 되지?”라는 문제를 좁히기 어렵습니다.

**리버스 프록시(reverse proxy)** 는 사용자의 HTTP 요청을 먼저 받아 내부 애플리케이션 서버로 전달하고, 응답을 다시 사용자에게 돌려주는 앞단 서버입니다. Caddy는 웹 서버이자 리버스 프록시 소프트웨어로, 호스트 이름을 설정하면 공개 인증서 발급·갱신과 HTTP에서 HTTPS로의 리다이렉트를 자동화할 수 있습니다. 편리한 기본값이 있다고 해서 DNS, 포트, 보안 경계가 자동으로 올바르게 되는 것은 아닙니다. 이 글은 Caddy 공식 문서를 바탕으로 동작 원리와 운영 판단 기준을 설명하는 학습 글이며, 특정 환경에서 직접 운영하거나 성능을 측정한 경험을 주장하지 않습니다.

## 먼저 알아둘 기반 기술: DNS, TCP, HTTP, TLS, 프록시

사용자는 `service.example.com` 같은 **도메인 이름**으로 접속합니다. DNS는 이 이름을 서버의 IP(Internet Protocol, 네트워크에서 장치를 식별하는 주소) 주소로 찾습니다. A 레코드는 보통 IPv4 주소를, AAAA 레코드는 IPv6 주소를 가리킵니다. 브라우저가 DNS에서 얻은 IP로 연결을 시도할 때 서버까지의 길에는 공유기, 클라우드 로드 밸런서, 방화벽, 보안 그룹이 있을 수 있습니다. Caddy 설정을 고치기 전에 이름이 의도한 IP를 가리키는지부터 확인하는 이유입니다.

**TCP(Transmission Control Protocol)** 는 두 프로그램 사이에 순서와 전달을 관리하는 연결형 통신 방식입니다. 웹의 HTTP(Hypertext Transfer Protocol, 웹에서 요청과 응답을 주고받는 규약)는 보통 TCP 위에서 동작합니다. 80번 포트는 일반 HTTP의 관례적 포트이고, 443번 포트는 HTTPS의 관례적 포트입니다. 포트는 같은 IP에서 어떤 서버 프로그램에 연결할지를 구분하는 번호입니다. 애플리케이션이 8080에서 듣고 있다고 해도, 외부 사용자가 443으로 들어온 요청을 8080으로 전달할 앞단이 없으면 도메인 HTTPS 접속은 되지 않습니다.

HTTPS는 HTTP 메시지를 TLS로 보호해, 브라우저가 올바른 서버와 통신하는지 확인하고 전송 중 내용을 암호화하게 합니다. TLS 인증서는 도메인 이름과 공개키를 연결하는 증명서입니다. 브라우저는 인증서가 신뢰하는 CA(Certificate Authority, 인증서를 발급하는 기관)에 의해 발급됐는지, 요청한 도메인과 이름이 맞는지, 유효 기간이 지나지 않았는지 확인합니다. 자물쇠 모양은 애플리케이션의 권한 설계나 입력 검증까지 안전하다는 뜻이 아니라, 연결 상대와 전송 경로에 관한 보장을 뜻합니다.

**프록시(proxy)** 는 요청을 대신 전달하는 중간 서버입니다. 클라이언트 앞에 있어 외부로 나가는 요청을 대신하는 포워드 프록시와 달리, 리버스 프록시는 서비스 서버 앞에 있어 들어오는 요청을 대신 받습니다. 리버스 프록시는 TLS 종료, 정적 파일 제공, 압축, 요청 크기 제한, 접근 로그, 여러 백엔드로의 분산 같은 일을 한곳에 모을 수 있습니다. 애플리케이션은 비즈니스 로직에 집중하고, 외부 접점의 공통 문제는 프록시가 맡게 되는 구조입니다.

## 요청은 어떤 경로로 흐르나

브라우저가 `https://app.example.com/orders`를 연다고 생각해 봅시다. 먼저 DNS 조회 결과로 얻은 공인 IP의 443 포트에 TCP 연결을 만들고 TLS 핸드셰이크(handshake, 암호화 통신 전에 신원과 키를 합의하는 과정)를 합니다. Caddy는 `app.example.com`에 맞는 인증서를 제시합니다. 연결이 성립하면 브라우저는 HTTP 요청의 경로, 헤더, 쿠키를 Caddy에 보냅니다. Caddy는 설정에 따라 요청을 `127.0.0.1:8080` 또는 내부 서비스 이름으로 전달하고, 백엔드 응답을 사용자에게 반환합니다.

이 구조에서 Caddy는 외부 HTTPS를 끝내고 백엔드와는 HTTP로 통신할 수 있습니다. 이를 **TLS 종료(termination)** 라고 부릅니다. 같은 서버의 loopback 주소 `127.0.0.1`로만 백엔드를 열고 운영체제 권한도 적절히 분리됐다면, 백엔드 구간은 짧은 로컬 신뢰 경계입니다. 하지만 Caddy와 애플리케이션이 다른 VM(Virtual Machine, 가상 서버), 다른 Kubernetes 노드, 다른 네트워크에 있다면 패킷이 더 넓은 경계를 지납니다. 이때 HTTP를 쓸지 내부 TLS를 쓸지, 서비스 신원을 어떻게 검증할지는 네트워크 설계와 위협 모델을 기준으로 결정해야 합니다.

요청이 애플리케이션에 도착했을 때 원래 사용자가 HTTPS로 접속했다는 정보와 원래 호스트 이름이 중요할 수 있습니다. 예를 들어 애플리케이션이 로그인 후 `https://app.example.com/callback`으로 리다이렉트 URL을 만들거나, 보안 쿠키에 `Secure` 속성을 붙여야 할 수 있습니다. 프록시가 전달하는 `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` 같은 헤더는 이런 맥락을 전달합니다. 그러나 애플리케이션이 인터넷에서 직접 들어온 임의의 forwarded 헤더까지 믿으면 사용자가 IP나 HTTPS 여부를 위조할 수 있습니다. 신뢰하는 프록시에서 들어온 요청만 이 헤더를 해석하도록 설정해야 합니다.

## Caddy의 자동 HTTPS가 하는 일과 전제 조건

Caddy는 사이트 주소에 공개 도메인 이름이 포함되면 자동 HTTPS를 활성화할 수 있습니다. 공식 문서에 따르면 Caddy는 공개 ACME CA(Automated Certificate Management Environment를 사용하는 인증서 발급 기관)에서 인증서를 얻고 갱신하며, 기본적으로 HTTP 요청을 HTTPS로 리다이렉트합니다. **ACME** 는 서버가 도메인 제어 권한을 증명하고 인증서를 자동 발급받는 표준 프로토콜입니다. 인증서 파일을 손으로 복사하고 만료일을 달력에 적던 운영 부담을 줄이는 것이 자동화의 장점입니다.

하지만 자동화는 조건 위에서만 동작합니다. 도메인의 A 또는 AAAA 레코드가 해당 서버를 가리켜야 하고, 외부에서 80과 443 포트가 Caddy에 도달해야 하며, Caddy 프로세스가 그 포트에 바인드(bind, 포트를 열어 연결을 받는 행위)할 수 있어야 합니다. 인증서와 키를 저장하는 데이터 디렉터리도 지속적이고 쓰기 가능해야 합니다. 컨테이너를 재시작할 때마다 저장소가 사라지면 인증서를 반복해서 요청해 CA의 발급 제한에 걸릴 수 있습니다. “컨테이너는 무상태”라는 원칙과 “인증서 상태는 보존돼야 한다”는 요구를 구분해야 합니다.

공개 도메인 대신 `localhost`나 사설 이름으로 개발할 때는 상황이 다릅니다. Caddy는 로컬 이름에도 HTTPS를 제공할 수 있지만, 공개 CA가 발급하는 인증서 대신 자체 로컬 CA를 만들어 사용합니다. 개발 머신의 신뢰 저장소에 Caddy의 로컬 루트 인증서를 설치해야 브라우저 경고 없이 접속할 수 있습니다. 이 인증서는 그 로컬 신뢰 경계에서만 의미가 있으며, 다른 사용자 컴퓨터나 공용 인터넷에서 공개 도메인 인증서처럼 신뢰되는 것은 아닙니다.

## 가장 작은 Caddyfile과 그 의미

**Caddyfile**은 Caddy 설정을 사람이 읽기 쉬운 형식으로 적는 파일입니다. 아래 예시는 `app.example.com`으로 들어온 요청을 로컬 8080 포트의 애플리케이션으로 전달합니다.

```caddyfile
app.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

첫 줄의 도메인은 Caddy에게 어떤 Host 요청을 받을지와 자동 HTTPS 대상 이름을 알려 줍니다. `reverse_proxy`는 뒤의 주소를 업스트림(upstream, 프록시가 요청을 넘기는 백엔드)으로 지정합니다. 이 간단한 설정은 Caddy가 DNS·포트·권한·저장소 조건을 만족할 때 인증서를 관리하고 HTTP를 HTTPS로 보내는 기본 동작을 얻는 출발점입니다. 애플리케이션을 외부 `0.0.0.0:8080`에 무심코 열 필요가 없다는 점도 중요합니다. Caddy와 같은 호스트라면 백엔드는 loopback만 듣게 하여 직접 접근 경로를 줄일 수 있습니다.

정적 사이트와 API를 함께 제공한다면 경로별로 책임을 나눌 수 있습니다. 예를 들어 `/api/*`만 애플리케이션으로 넘기고 나머지는 정적 파일로 제공할 수 있습니다. 하지만 경로 규칙이 많아질수록 `/api`와 `/api/`의 처리, SPA(Single Page Application, 브라우저에서 화면 전환을 처리하는 앱)의 fallback, 캐시 정책, 업로드 크기 제한을 명시해야 합니다. 처음부터 모든 기능을 프록시 설정에 넣기보다 실제 서비스 경로와 요구 사항이 생길 때 한 항목씩 추가하는 편이 오류를 줄입니다.

```caddyfile
app.example.com {
    handle /api/* {
        reverse_proxy 127.0.0.1:8080
    }

    handle {
        root * /srv/site
        file_server
    }
}
```

이 예시는 구조를 설명할 뿐, 모든 SPA에 그대로 맞는 정답은 아닙니다. API 경로를 애플리케이션이 어떤 형태로 기대하는지, 정적 파일의 권한과 배포 방식이 무엇인지에 따라 달라집니다. 설정을 바꾼 뒤에는 구문 검증과 설정 재로딩을 분리하고, 실제 외부 도메인에서 HTTP 리다이렉트·HTTPS 인증서·대표 API를 각각 확인합니다.

## 헤더, 원래 클라이언트 IP, 리다이렉트의 함정

리버스 프록시를 두면 백엔드가 TCP 연결의 상대방으로 보는 IP는 실제 사용자 대신 Caddy일 수 있습니다. 실제 사용자 IP는 보통 forwarded 헤더로 전달됩니다. 로그인 실패 제한, 감사 로그, 지역 기반 정책처럼 IP를 쓰는 기능은 이 차이를 고려해야 합니다. 다만 프록시 밖에서 애플리케이션 포트가 접근 가능하면 공격자가 `X-Forwarded-For` 헤더를 직접 넣어 보낼 수 있습니다. 그래서 백엔드 포트를 네트워크로 제한하고, 애플리케이션의 trusted proxy 목록을 Caddy 또는 로드 밸런서의 주소로 좁히는 것이 중요합니다.

HTTPS 종료 뒤 무한 리다이렉트가 생기는 경우도 흔합니다. 백엔드는 실제 연결이 HTTP이므로 “HTTPS가 아니니 HTTPS로 이동하라”고 판단하고, 프록시는 다시 HTTP로 넘겨 같은 판단이 반복될 수 있습니다. 애플리케이션이 신뢰할 수 있는 프록시가 붙인 `X-Forwarded-Proto: https`를 해석하도록 설정하면 이 문제를 피할 수 있습니다. 반대로 모든 요청 헤더를 신뢰하는 설정은 보안 문제를 만들 수 있으니, 문제 해결을 위해 신뢰 범위를 넓히는 방식은 피합니다.

쿠키도 프록시 구조의 영향을 받습니다. 외부 사용자가 HTTPS를 쓰면 세션 쿠키에는 일반적으로 `Secure`, `HttpOnly`, 적절한 `SameSite` 속성이 필요합니다. 프록시 뒤 애플리케이션이 외부 스킴을 HTTP로 오해하면 Secure 쿠키를 누락하거나 잘못된 URL을 만들 수 있습니다. 이 문제는 Caddy가 “쿠키를 자동으로 안전하게 만든다”는 문제가 아니라 애플리케이션과 프록시가 요청 맥락을 합의하지 못한 문제입니다. 브라우저 개발자 도구와 응답 헤더를 함께 확인하면 원인을 좁힐 수 있습니다.

## 장애를 계층별로 나누어 조사하기

외부에서 접속이 안 되면 먼저 오류 화면 하나만 보고 애플리케이션을 재시작하지 않습니다. DNS 단계에서는 `dig`나 DNS 조회 도구로 도메인이 기대한 IP를 가리키는지 확인합니다. 연결 단계에서는 80·443 포트가 방화벽과 보안 그룹을 통과하는지, Caddy 프로세스가 실제로 포트를 듣는지 봅니다. TLS 단계에서는 브라우저의 인증서 상세 정보와 Caddy 로그에서 어떤 도메인 인증서 발급·갱신이 실패했는지 확인합니다. HTTP 단계에서는 Caddy 접근 로그의 상태 코드와 업스트림 오류를 봅니다.

**502 Bad Gateway**는 프록시가 백엔드에서 유효한 응답을 받지 못했다는 뜻으로 자주 쓰입니다. 백엔드 프로세스가 죽었는지, 주소나 포트가 틀렸는지, 방화벽이 막았는지, 백엔드가 TLS를 기대하는데 Caddy가 HTTP로 연결했는지 등을 점검합니다. 반면 404 Not Found는 요청이 Caddy에 도달했지만 경로 규칙이나 백엔드 라우팅이 맞지 않을 수 있음을 뜻합니다. 301 또는 308 리다이렉트가 반복되면 스킴 헤더와 애플리케이션의 외부 URL 설정을 의심합니다. 같은 “접속 안 됨”도 응답 코드와 어느 계층에서 나왔는지에 따라 다음 조치가 달라집니다.

헬스 체크(health check, 백엔드가 요청을 처리할 준비가 됐는지 확인하는 검사)도 구분합니다. 프로세스가 살아 있다는 liveness와, 데이터베이스 연결·필수 설정까지 준비됐다는 readiness는 다릅니다. 여러 업스트림을 두는 경우 Caddy의 능동·수동 헬스 체크를 활용할 수 있지만, 단일 백엔드에서 체크 설정을 늘린다고 장애가 사라지지는 않습니다. 먼저 애플리케이션이 의미 있는 `/health` 또는 `/ready` 응답을 제공하는지, 그 응답이 민감한 내부 정보를 노출하지 않는지 설계합니다.

## 보안과 운영에서 피해야 할 선택

가장 피해야 할 설정 중 하나는 업스트림 HTTPS 인증서 검증을 끄는 것입니다. Caddy 문서는 `tls_insecure_skip_verify`가 TLS 검증을 꺼 중간자 공격에 취약하게 만들 수 있으므로 운영에 권장하지 않는다고 설명합니다. 내부 CA를 신뢰하도록 구성하거나, 같은 제한된 호스트에서 HTTP를 쓰는 것이 실제 요구에 맞는지 판단해야 합니다. “인증서 오류를 빨리 없애기” 위해 검증을 끄면 암호화가 주는 서버 신원 확인을 잃습니다.

인증서 데이터 디렉터리를 공유 파일 시스템에 여러 인스턴스가 동시에 쓰게 할 때도 문서와 저장소 특성을 확인해야 합니다. 여러 Caddy 인스턴스, 컨테이너 교체, 자동 확장 환경에서는 누가 인증서를 관리하고 잠금을 어떻게 보장하는지가 운영 문제입니다. 단일 서버용 설정을 복제본 수만 늘려 적용하면 인증서 요청과 갱신이 충돌할 수 있습니다. 고가용성이 필요해지는 시점에는 Caddy 구성뿐 아니라 로드 밸런서, 공유 저장소, 장애 조치 방식을 함께 설계합니다.

마지막으로 리버스 프록시는 인증·인가를 자동으로 해결하지 않습니다. Caddy 앞에서 TLS가 정상이어도 관리 API가 인터넷에 열려 있거나, 업스트림이 forwarded 헤더를 믿어 권한을 우회하거나, 업로드 제한이 없어 저장소가 고갈될 수 있습니다. 공개할 경로, 인증이 필요한 경로, 내부에서만 열 경로를 애플리케이션과 네트워크 정책 양쪽에서 표현합니다. 로그에도 Authorization 헤더, 세션 쿠키, 개인정보가 그대로 남지 않게 마스킹 정책을 확인합니다.

## 언제 Caddy가 잘 맞고 언제 다른 선택이 나은가

Caddy는 단일 서비스나 소수의 서비스에 도메인 기반 HTTPS와 리버스 프록시를 빠르게 구성하고 싶은 경우에 잘 맞습니다. 운영자가 인증서 발급·갱신 작업을 줄이고, 읽기 쉬운 Caddyfile로 기본 라우팅을 관리하고 싶을 때 특히 출발점이 좋습니다. 로컬 개발에서도 `localhost` HTTPS를 재현해야 하거나, 작은 팀이 Nginx 설정의 세부 문법보다 명시적인 기본값을 선호할 때 선택할 수 있습니다.

반면 조직에 이미 표준 Ingress, API Gateway, WAF(Web Application Firewall, 웹 요청을 검사하는 방화벽), 중앙 인증·로그 체계가 있고 여러 팀이 공유하는 환경이라면 개별 서버마다 Caddy를 도입하는 것이 일관성을 해칠 수 있습니다. 수천 개의 고객 도메인을 동적으로 다루거나, 복잡한 전역 트래픽 정책, 특정 상용 장비 연동이 필요하면 요구 사항과 지원 체계를 비교해야 합니다. 도구의 문법이 짧다는 이유만으로 기존 보안·관측성·배포 경계를 새로 만드는 선택은 피합니다.

## 배포 전과 배포 후에 확인할 최소 점검 순서

리버스 프록시 설정은 한 파일을 수정하는 일처럼 보이지만, 실제 확인 대상은 네트워크와 애플리케이션을 가로지릅니다. 배포 전에 먼저 도메인 이름이 어느 IP를 가리켜야 하는지 적고, 그 IP에서 80·443이 어디로 전달되는지 확인합니다. 클라우드라면 보안 그룹과 네트워크 ACL(Network Access Control List, 네트워크 통신 규칙 목록), 온프레미스라면 방화벽과 NAT(Network Address Translation, 사설 주소와 공인 주소를 변환하는 장치) 규칙이 포함될 수 있습니다. 이 경로를 모른 채 인증서 발급 오류만 반복해서 보면 원인을 늦게 찾게 됩니다.

다음으로 백엔드를 프록시와 같은 서버에서 직접 확인합니다. 예를 들어 Caddy가 `127.0.0.1:8080`으로 넘길 예정이라면, 서버에서 해당 주소에 HTTP 요청을 보내 기대한 상태 코드와 응답을 받는지 봅니다. 이 검사는 외부 DNS나 TLS 문제를 제외하고 애플리케이션 자체가 요청을 처리하는지 확인하는 단계입니다. 백엔드가 컨테이너라면 호스트의 `127.0.0.1`과 컨테이너 내부의 `127.0.0.1`이 같은 곳을 뜻하지 않는다는 점도 주의합니다. 컨테이너 내부 loopback은 그 컨테이너 자신입니다.

설정 파일은 적용 전에 Caddy가 제공하는 검증 기능으로 구문과 변환 결과를 확인합니다. YAML이나 JSON을 읽을 수 있다고 해서 라우팅 우선순위가 의도한 대로라는 뜻은 아니므로, 특히 여러 `handle` 블록과 경로 매처가 있으면 대표 URL을 표로 적어 봅니다. `/`, `/api/orders`, `/api`, 존재하지 않는 정적 파일, 인증이 필요한 경로를 어느 핸들러가 처리하는지 명시하면 뒤늦은 404와 잘못된 fallback을 줄일 수 있습니다.

배포 뒤에는 외부 네트워크에서 HTTP와 HTTPS를 구분해 확인합니다. HTTP 요청이 HTTPS로 한 번 이동하는지, 최종 인증서의 도메인 이름과 만료일이 맞는지, 대표 정적 페이지와 API가 각각 기대한 응답을 주는지 봅니다. 로그인 같은 상태 변경 요청은 테스트 계정과 안전한 데이터로 확인하고, 운영 주문이나 실제 고객 데이터로 점검하지 않습니다. 마지막으로 Caddy 접근 로그와 애플리케이션 로그의 요청 ID, 시간, 상태 코드를 비교할 수 있는지 확인하면 문제가 생겼을 때 두 층을 연결하기 쉬워집니다.

## 업스트림을 여러 개 둘 때 알아야 할 것

`reverse_proxy`에는 하나 이상의 업스트림을 둘 수 있습니다. 예를 들어 동일한 버전의 애플리케이션 두 인스턴스를 등록하면 Caddy는 요청을 나누어 보낼 수 있습니다. 그러나 단지 주소 두 개를 나열했다고 무중단 배포나 고가용성이 완성되는 것은 아닙니다. 두 인스턴스가 같은 세션을 읽을 수 있는지, 업로드 파일과 캐시가 공유되는지, 데이터베이스 마이그레이션 중 구버전과 신버전이 함께 동작하는지까지 확인해야 합니다.

**로드 밸런싱(load balancing)** 은 여러 업스트림에 요청을 분산하는 방식입니다. 라운드 로빈(round robin, 순서대로 번갈아 보내는 방식)은 단순하지만 각 요청의 처리 시간과 연결 수가 크게 다르면 부하가 균등하지 않을 수 있습니다. 세션을 메모리에만 저장하는 애플리케이션은 사용자가 첫 요청과 다음 요청에서 다른 인스턴스로 가면 로그인이 풀린 것처럼 보일 수 있습니다. 이를 해결하려고 무조건 sticky session(같은 사용자를 같은 서버로 보내는 방식)을 켜기보다, 세션 저장 위치와 애플리케이션의 무상태 설계를 먼저 검토합니다.

헬스 체크도 실제 사용 가능한 상태를 반영해야 합니다. `/health`가 단순히 프로세스가 실행 중이라는 200만 돌려주면 데이터베이스 연결이 끊긴 인스턴스도 정상으로 남을 수 있습니다. 반대로 모든 외부 의존성을 깊게 검사하면 외부 서비스의 잠깐 지연 때문에 건강한 인스턴스까지 제외할 수 있습니다. liveness와 readiness를 어떤 목적에 쓸지 구분하고, Caddy의 능동 헬스 체크를 쓸 때는 검사 경로, 간격, 실패 횟수, timeout을 서비스의 실제 복구 시간에 맞춥니다. 너무 짧은 timeout은 느린 정상 응답을 장애로 만들 수 있습니다.

배포는 새 인스턴스를 먼저 준비 상태로 만들고, 트래픽에 넣고, 기존 인스턴스를 뺀 뒤 종료하는 순서를 생각합니다. 이른 종료는 처리 중인 업로드나 결제 요청을 끊을 수 있습니다. Caddy 앞단의 설정이 정상이어도 애플리케이션이 graceful shutdown(새 요청은 받지 않고 진행 중 요청을 마치는 종료)을 지원하지 않으면 사용자 오류가 생길 수 있습니다. 프록시 설정만으로 해결하려 하지 말고 애플리케이션 종료 신호와 배포 도구의 대기 시간을 함께 맞춥니다.

## 관측성과 로그에서 보는 신호

리버스 프록시는 외부 요청이 처음 모이는 지점이어서 관측성의 좋은 출발점입니다. 접근 로그에는 요청 시간, 메서드, 경로, 응답 상태, 처리 시간, 업스트림 주소처럼 문제를 분류하는 데 필요한 정보가 남을 수 있습니다. 하지만 모든 요청 본문, 쿠키, Authorization 헤더까지 남기면 비밀과 개인정보가 로그 저장소로 확산됩니다. 무엇을 남길지와 무엇을 마스킹할지는 기능 개발 뒤의 선택이 아니라 처음부터 정해야 하는 운영 요구입니다.

상태 코드 비율을 단순하게 보더라도 유용한 신호가 됩니다. 4xx 응답이 갑자기 늘면 잘못된 클라이언트 배포, 인증 정책 변경, 공격성 트래픽을 살펴볼 수 있습니다. 5xx가 늘면 업스트림 연결, 애플리케이션 예외, 데이터베이스 지연, 배포 시점을 함께 봅니다. 다만 404가 하나라도 나오면 알림을 울리게 하면 탐색 로봇과 오타 때문에 소음이 커집니다. 서비스의 정상적인 404 범위와 실제로 알림이 필요한 경로를 구분해야 합니다.

**상관관계 ID(correlation ID)** 는 한 사용자 요청을 여러 서비스와 로그에서 연결하는 식별자입니다. 앞단에서 ID를 만들거나 전달하고, Caddy 로그와 애플리케이션 로그가 같은 값을 기록하면 “사용자는 502를 받았는데 백엔드에는 어떤 요청이 있었나”를 찾기 쉬워집니다. 신뢰할 수 없는 외부 헤더 값을 그대로 내부 상관관계 ID로 쓰면 로그 오염이나 추적 혼선을 만들 수 있으므로 생성·검증 위치를 정합니다. 이미 조직의 API Gateway나 관측성 플랫폼이 ID를 관리한다면 Caddy에서 별도 체계를 중복 구축할 필요는 없습니다.

메트릭(metric, 시간에 따라 수치로 쌓는 관측 데이터)도 최소한으로 시작합니다. 초당 요청 수, 상태 코드별 응답 수, 응답 시간 분포, 업스트림 실패 수 정도면 처음 장애 분석에 도움이 됩니다. 대시보드를 수십 개 만들기보다 “사용자가 실패를 보는가”, “어느 경로에서 느린가”, “프록시와 백엔드 중 어디가 실패하는가”에 답하는 그래프부터 둡니다. 알림은 평균 응답 시간 하나보다 오류 비율과 사용자 영향, 지속 시간을 함께 고려해야 일시적인 잡음에 덜 흔들립니다.

## Docker와 함께 쓸 때의 경계

Docker는 애플리케이션과 의존 파일을 이미지로 묶어 일관된 실행 환경을 만드는 도구입니다. Caddy와 앱을 각각 컨테이너로 실행할 수 있지만, 컨테이너가 곧 보안 경계 전체를 해결한다는 뜻은 아닙니다. Caddy 컨테이너는 80·443 포트를 호스트에 공개하고, 앱 컨테이너는 같은 내부 네트워크에서만 이름으로 접근하게 두는 구성이 흔합니다. 이때 앱 포트를 호스트에 함께 공개하면 리버스 프록시를 우회하는 경로가 생길 수 있습니다.

인증서 저장소는 볼륨(volume, 컨테이너가 재시작돼도 데이터를 보존하는 저장 공간)으로 유지해야 합니다. Caddy 컨테이너가 사라질 때 인증서와 계정 상태도 함께 사라지면 매 배포마다 새 인증서 요청을 시도할 수 있습니다. 설정 파일을 읽기 전용으로 마운트하는 것과, Caddy 데이터 디렉터리를 쓰기 가능한 영속 볼륨에 두는 것은 서로 다른 요구입니다. 또한 컨테이너 내부 시간과 호스트 시간이 크게 어긋나면 TLS 검증과 로그 분석에 문제가 생길 수 있으므로 시간 동기화도 운영 전제에 포함합니다.

Docker Compose는 소수 컨테이너의 관계를 선언하기 편하지만, `depends_on`만으로 앱이 실제 요청을 받을 준비가 됐다고 보장하지는 않습니다. 데이터베이스가 포트를 열었어도 마이그레이션이 끝나지 않았을 수 있고, 앱이 시작됐어도 캐시 연결이 준비되지 않았을 수 있습니다. Caddy가 시작 순서만 믿고 오류를 숨기지 않게, 애플리케이션의 readiness와 프록시의 실패 응답을 확인하는 배포 점검이 필요합니다.

## 작은 장애 사례로 보는 조사 순서

새 도메인을 연결한 뒤 브라우저에서 인증서 오류가 난 상황을 생각해 봅시다. 첫 행동은 Caddyfile을 여러 번 고치는 것이 아니라 DNS가 새 서버를 가리키는지 확인하는 것입니다. DNS는 맞는데 Caddy 로그에 ACME 검증 실패가 있다면, 외부 80 포트가 Caddy에 도달하는지, 다른 웹 서버가 이미 포트를 쓰는지, 로드 밸런서가 HTTP 요청을 가로채지 않는지 확인합니다. 인증서 저장 디렉터리 권한 오류라면 프로세스 사용자와 볼륨 마운트를 점검합니다. 각 단계는 서로 다른 증거를 봅니다.

두 번째 사례로, 인증서는 정상인데 `/api/orders`만 502가 난다고 해 봅시다. Caddy 접근 로그에서 경로와 업스트림 오류를 확인하고, 같은 서버 또는 같은 네트워크에서 업스트림 주소에 직접 요청해 봅니다. 앱이 8080이 아니라 8000에서 듣고 있거나, 컨테이너 이름을 호스트에서 `localhost`로 잘못 해석했거나, 백엔드가 HTTPS만 받는데 프록시가 HTTP로 연결했을 수 있습니다. 오류를 숨기기 위해 TLS 검증을 끄는 것이 아니라 주소·스킴·신뢰할 CA를 정확히 맞춥니다.

세 번째 사례는 로그인 직후 무한 리다이렉트입니다. 브라우저의 Network 탭에서 Location 헤더가 같은 주소를 반복하는지 확인하고, 백엔드 로그에서 요청 스킴을 무엇으로 보는지 봅니다. 프록시 뒤라는 사실을 모르는 앱이 HTTP를 HTTPS로 바꾸려 반복할 수 있습니다. trusted proxy 범위와 forwarded proto 처리, 애플리케이션의 public base URL 설정을 함께 확인합니다. 문제의 위치를 Caddy 또는 앱 하나로 성급히 단정하지 않는 것이 핵심입니다.
