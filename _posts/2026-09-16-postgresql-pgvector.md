AI 검색이나 추천 기능을 이야기할 때 벡터 데이터베이스라는 말을 자주 듣게 됩니다. 그런데 이미 PostgreSQL을 운영하고 있다면 새로운 저장소를 바로 추가해야 할까요? 모든 경우에 그렇지는 않습니다. PostgreSQL 확장인 pgvector를 사용하면 기존 데이터와 벡터를 한 데이터베이스 안에서 함께 관리하고, SQL로 유사도 검색을 구성할 수 있습니다.

이 글은 PostgreSQL과 pgvector의 구조를 새롭게 학습하는 관점에서 정리한 글입니다. 특정 환경에서 직접 실행해 측정한 결과가 아니라, pgvector 공식 문서와 공개 기술 자료를 바탕으로 개념·예시·적용 판단 기준을 설명합니다. 실제 성능은 데이터 크기, 임베딩 차원, 하드웨어, 필터 조건, 인덱스 설정에 따라 달라집니다.

## 1. 벡터 검색은 무엇을 검색하는가

일반적인 SQL 검색은 값이나 단어의 일치 관계를 찾는 데 강합니다. 예를 들어 제목에 `장애`라는 단어가 포함된 문서를 찾으려면 `LIKE`나 PostgreSQL Full Text Search를 사용할 수 있습니다. 하지만 “데이터베이스 연결이 끊겼을 때 확인할 것”과 “DB 접속 오류를 진단하는 방법”처럼 표현은 다르지만 의미가 가까운 문서를 찾는 일은 단어 일치만으로 충분하지 않을 수 있습니다.

벡터 검색은 문장이나 이미지 같은 데이터를 숫자 배열로 표현하고, 두 배열 사이의 거리를 계산해 의미적으로 가까운 대상을 찾습니다. 이 숫자 배열을 보통 임베딩이라고 부릅니다. 예를 들어 다음과 같은 문장이 있다고 해보겠습니다.

```text
문서 A: PostgreSQL 연결 오류를 확인하는 방법
문서 B: 데이터베이스 접속 실패 원인과 점검 순서
문서 C: Kubernetes Ingress 라우팅 규칙
```

검색어가 “DB 접속이 안 될 때 어디부터 확인하나요?”라면 단어가 정확히 일치하지 않아도 A와 B가 가까운 후보가 될 수 있습니다. 다만 어떤 임베딩 모델을 사용했는지, 문서를 어떻게 나누었는지에 따라 결과가 달라집니다. 벡터 검색은 의미를 마법처럼 이해하는 기능이 아니라, 모델이 만든 표현 공간에서 가까운 값을 찾는 계산입니다.

## 2. pgvector가 제공하는 것

pgvector는 PostgreSQL에서 벡터를 저장하고 유사도 검색을 수행하기 위한 오픈 소스 확장입니다. 공식 저장소는 `vector`, `halfvec`, `bit`, `sparsevec` 같은 타입과 L2 거리, 내적, 코사인 거리 등의 연산을 설명합니다. 일반적인 예시는 다음과 같습니다.

```sql
CREATE EXTENSION vector;

CREATE TABLE documents (
    id bigserial PRIMARY KEY,
    title text NOT NULL,
    content text NOT NULL,
    embedding vector(1536)
);
```

여기서 `vector(1536)`의 차원 수는 사용하는 임베딩 모델의 출력 차원과 맞아야 합니다. 모델이 768차원 벡터를 반환하는데 데이터베이스 컬럼을 1536차원으로 만들면 저장 단계에서 문제가 생깁니다. 따라서 모델 선택과 데이터베이스 스키마를 따로 결정하기보다 함께 관리하는 편이 안전합니다.

벡터가 저장되면 다음처럼 가까운 문서를 조회할 수 있습니다.

```sql
SELECT id, title, content,
       embedding <=> '[0.12, -0.44, 0.31, ...]' AS distance
FROM documents
WHERE embedding IS NOT NULL
ORDER BY embedding <=> '[0.12, -0.44, 0.31, ...]'
LIMIT 5;
```

`<=>`는 코사인 거리를 계산하는 연산자입니다. 거리 값이 작을수록 더 가깝다는 의미로 해석할 수 있습니다. 실제 SQL에는 벡터의 모든 차원 값을 넣어야 하므로 위 배열은 설명을 위한 축약 예시입니다. pgvector 공식 README는 거리 함수별 연산자와 인덱스 연산자 클래스를 구분해 설명하므로, 사용하는 거리 기준에 맞는 인덱스를 선택해야 합니다. [pgvector 공식 README](https://github.com/pgvector/pgvector)를 기준으로 확인하는 것이 좋습니다.

## 3. 정확한 검색과 근사 검색

pgvector는 기본적으로 정확한 최근접 이웃 검색을 수행합니다. 모든 후보를 비교하기 때문에 이론적으로 재현율을 온전히 확보할 수 있지만, 데이터가 커지면 계산량과 응답 시간이 부담이 될 수 있습니다. 이를 줄이기 위해 HNSW나 IVFFlat 같은 근사 최근접 이웃 인덱스를 사용할 수 있습니다.

근사 검색은 일부 후보만 빠르게 살펴보는 대신, 정확한 검색과 결과가 달라질 가능성을 받아들이는 방식입니다. 따라서 “인덱스를 만들었으니 무조건 빨라졌다”가 아니라 “속도와 재현율 사이에서 어떤 지점을 선택했는가”로 이해해야 합니다.

## 4. HNSW와 IVFFlat의 차이

HNSW는 여러 층의 그래프를 만들어 가까운 후보를 찾아가는 방식입니다. pgvector 공식 문서는 HNSW가 IVFFlat보다 속도·재현율 절충에서 더 나은 검색 성능을 보일 수 있지만, 인덱스 생성 시간이 더 길고 메모리를 더 사용할 수 있다고 설명합니다. 또한 별도의 학습 단계가 없어 데이터가 없는 상태에서도 인덱스 생성이 가능하다는 특징이 있습니다.

예시는 다음과 같습니다.

```sql
CREATE INDEX documents_embedding_hnsw
ON documents USING hnsw (embedding vector_cosine_ops);
```

IVFFlat은 벡터를 여러 목록으로 나누고, 검색 시 가까운 목록 일부만 살펴보는 방식입니다. HNSW보다 인덱스 생성이 빠르고 메모리 사용이 적을 수 있지만, 목록 수와 검색할 probe 수를 적절히 정해야 합니다.

```sql
CREATE INDEX documents_embedding_ivfflat
ON documents USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

BEGIN;
SET LOCAL ivfflat.probes = 10;
SELECT id, title
FROM documents
ORDER BY embedding <=> '[0.12, -0.44, 0.31, ...]'
LIMIT 5;
COMMIT;
```

공식 문서의 시작점은 데이터 규모에 따라 `lists`를 정하는 경험칙을 제시하지만, 이 값이 모든 환경에 맞는 정답은 아닙니다. 데이터가 추가되거나 검색 필터가 붙으면 적절한 값이 달라질 수 있습니다. 인덱스 선택은 벤치마크 없이 단정하기보다 정확한 검색 결과와 근사 검색 결과의 차이를 비교하면서 결정해야 합니다.

| 기준 | 정확한 검색 | HNSW | IVFFlat |
| --- | --- | --- | --- |
| 결과 재현율 | 가장 높음 | 설정에 따라 달라짐 | 설정에 따라 달라짐 |
| 인덱스 필요 | 없음 | 필요 | 필요 |
| 메모리 부담 | 상대적으로 낮음 | 상대적으로 높을 수 있음 | HNSW보다 낮을 수 있음 |
| 생성 특징 | 별도 생성 없음 | 학습 단계 없음 | 데이터와 lists 설정의 영향이 큼 |
| 주요 조정값 | 병렬 처리 등 | `ef_search`, `ef_construction`, `m` | `lists`, `probes` |

표의 내용은 pgvector 버전과 데이터 조건에 따라 달라질 수 있습니다. 공식 문서는 HNSW와 IVFFlat을 동일한 기준으로 단순 우열 비교하지 않고, 속도·재현율·생성 비용·메모리의 절충으로 설명합니다.

## 5. 관계형 필터와 함께 검색하기

PostgreSQL에서 pgvector를 사용하는 가장 큰 이유 중 하나는 벡터와 일반 데이터를 같은 SQL 흐름에서 다룰 수 있다는 점입니다. 문서의 `tenant_id`, `category_id`, `created_at`, 접근 권한 같은 조건을 함께 적용해야 하는 경우가 많습니다.

```sql
SELECT id, title
FROM documents
WHERE tenant_id = 42
  AND category_id = 7
ORDER BY embedding <=> '[0.12, -0.44, 0.31, ...]'
LIMIT 10;
```

하지만 근사 인덱스에서 필터가 적용되는 위치를 주의해야 합니다. pgvector 공식 문서는 근사 인덱스 검색에서 먼저 후보를 일정 수 찾은 뒤 필터가 적용될 수 있기 때문에, 필터 조건이 강하면 최종 결과가 부족해질 수 있다고 설명합니다. `WHERE category_id = 7`에 맞는 일반 인덱스를 추가하는 것만으로 해결되는 경우도 있지만, 선택도와 데이터 분포에 따라 방법이 달라집니다.

예를 들어 전체 데이터의 1%만 특정 테넌트에 속한다면 후보를 넉넉히 확보하지 못하고 필터에서 대부분 탈락할 수 있습니다. 이때는 `hnsw.ef_search`나 iterative scan 설정을 검토하거나, 테넌트별 분리 전략과 정확 검색을 함께 비교해야 합니다. 중요한 것은 벡터 인덱스만 보고 판단하지 않고, 실제 SQL의 필터·정렬·LIMIT 조합을 기준으로 확인하는 것입니다.

## 6. RAG와 추천에 어떻게 연결되는가

RAG에서는 질문과 문서를 임베딩으로 변환한 뒤, 질문과 가까운 문서 조각을 검색하고 그 결과를 생성 모델의 참고 문맥으로 전달합니다. PostgreSQL과 pgvector는 이 중 검색 저장소 역할을 할 수 있습니다.

예를 들면 다음 흐름입니다.

1. 문서를 적당한 크기의 조각으로 나눕니다.
2. 각 조각을 임베딩 모델로 변환합니다.
3. 본문, 문서 ID, 권한 정보, 임베딩을 저장합니다.
4. 사용자의 질문을 같은 모델로 임베딩합니다.
5. pgvector에서 가까운 조각을 조회합니다.
6. 권한과 최신성 조건을 확인한 뒤 생성 모델에 전달합니다.

여기서 pgvector는 답변의 사실성을 보장하지 않습니다. 검색 결과가 틀렸거나 문서가 오래됐거나 권한 필터가 빠지면 모델은 잘못된 문맥을 바탕으로 답할 수 있습니다. 따라서 DBA 관점에서는 벡터 검색 자체뿐 아니라 문서 갱신, 임베딩 재생성, 삭제 전파, 권한 필터, 인덱스 유지보수까지 데이터 생명주기로 봐야 합니다.

## 7. 운영 전에 확인할 것

첫째는 차원과 저장 공간입니다. pgvector README는 `vector` 타입의 저장 크기가 차원 수에 비례한다고 설명합니다. 임베딩 차원이 커질수록 테이블뿐 아니라 인덱스와 메모리 작업 집합도 커집니다. 차원이 높다는 이유만으로 품질이 항상 좋아지는 것은 아니므로 모델의 특성과 검색 품질을 함께 봐야 합니다.

둘째는 임베딩 모델 변경입니다. 기존 문서가 모델 A로 임베딩되어 있는데 새 질문은 모델 B로 변환하면 같은 공간에서 거리를 비교하기 어렵습니다. 모델을 바꿀 때는 버전 컬럼을 두거나 새 컬럼·새 테이블에 재생성하고, 전환 시점을 관리해야 합니다.

셋째는 삭제와 개인정보입니다. 원문에서 개인정보를 삭제했는데 임베딩과 검색 메타데이터가 남아 있으면 데이터 삭제가 완결되지 않을 수 있습니다. 원문, 임베딩, 캐시, 인덱스가 같은 삭제 정책을 따르는지 확인해야 합니다.

넷째는 정확도와 지연시간을 함께 측정하는 기준입니다. 근사 검색을 사용한다면 정답 후보 집합과 비교해 recall@k 같은 지표를 정의할 수 있습니다. 동시에 p95 지연시간, 메모리 사용량, 인덱스 생성 시간, 쓰기 부하도 봐야 합니다. 이 글에서는 특정 환경의 수치를 제시하지 않으며, 공개 문서가 설명하는 특성과 측정 방법을 적용 환경에서 별도로 확인해야 합니다.

## 마무리

PostgreSQL에 pgvector를 붙이는 방식은 기존 관계형 데이터와 벡터 검색을 하나의 운영 경계 안에서 다루고 싶을 때 검토할 만한 선택지입니다. 문서 메타데이터와 권한 조건을 SQL로 함께 처리할 수 있고, 별도 검색 시스템을 추가하지 않고도 RAG나 유사도 검색의 첫 구조를 만들 수 있습니다.

반대로 벡터 검색이 필요한 이유와 품질 기준이 정리되지 않은 상태에서 확장부터 설치하면 운영 복잡성만 늘어날 수 있습니다. 먼저 정확한 검색과 근사 검색의 차이, 모델 버전, 필터 조건, 삭제 정책을 정하고 작은 범위의 평가 데이터로 비교하는 것이 좋습니다.

DBA 관점에서 pgvector는 단순한 AI 기능이 아니라 새로운 데이터 타입과 인덱스, 저장 공간, 유지보수 주기를 PostgreSQL 운영 안에 포함하는 일입니다. 따라서 “어떤 벡터 DB가 더 빠른가?”보다 “우리 데이터의 관계형 조건과 검색 품질을 어떤 경계에서 관리할 것인가?”를 먼저 질문하는 편이 더 현실적인 출발점입니다.
