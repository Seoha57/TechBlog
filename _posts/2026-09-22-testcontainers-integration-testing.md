애플리케이션 테스트에서 가장 난감한 문장 중 하나는 “내 PC에서는 통과하는데 CI에서는 실패한다”입니다. 데이터베이스 버전이 다르거나, 개발용 Redis에 이전 데이터가 남아 있거나, 로컬에서만 켜 둔 메시지 브로커가 우연히 응답하면 테스트는 같은 코드인데도 다른 결론을 냅니다. 이 문제를 해결하려고 테스트용 서버를 하나 고정해 공유하면, 이번에는 누가 데이터를 지웠는지와 동시에 실행한 테스트가 왜 서로를 망가뜨렸는지가 새로운 문제가 됩니다.

Testcontainers는 이때 테스트 코드가 Docker 컨테이너를 필요할 때 띄우고, 준비가 끝났는지 확인한 뒤, 테스트가 끝나면 정리하도록 돕는 라이브러리 모음입니다. PostgreSQL, MySQL, Redis, Kafka 같은 실제 제품 이미지를 테스트 중에 사용할 수 있다는 점이 핵심입니다. 단위 테스트의 빠름과 외부 시스템을 포함한 통합 테스트의 현실성 사이에서, 어떤 부분을 실제 의존성으로 확인할지 선택하게 해 줍니다.

이 글은 특정 환경에서 직접 실행한 성능 보고서가 아닙니다. Testcontainers와 Docker 공식 문서, 공개된 테스트 사례를 바탕으로 의존성 격리의 원리와 설계 기준을 설명합니다. 컨테이너가 있다는 이유만으로 모든 테스트가 통합 테스트가 되어야 하는 것은 아니며, 빠른 피드백과 신뢰도 사이의 경계를 먼저 정하는 것이 중요합니다.

## 먼저 알아둘 기반 기술: 단위 테스트, 통합 테스트, Docker

테스트의 이름부터 구분해 보겠습니다. **단위 테스트(unit test)** 는 함수나 클래스처럼 작은 단위의 규칙을 외부 환경 없이 확인하는 테스트입니다. 할인 금액 계산, 날짜 형식 검사, 권한 판정처럼 입력과 출력이 분명한 규칙은 데이터베이스 없이도 충분히 검증할 수 있습니다. 빠르고 실패 원인을 좁히기 쉽다는 장점이 있습니다. 반면 실제 데이터베이스의 SQL 문법, 인덱스, 트랜잭션 격리 수준, 네트워크 타임아웃은 단위 테스트만으로 알 수 없습니다.

**통합 테스트(integration test)** 는 둘 이상의 구성 요소가 약속대로 연결되는지 확인합니다. 예를 들어 애플리케이션이 PostgreSQL에 마이그레이션을 적용하고, ORM(Object-Relational Mapping)이 만든 SQL이 실제 스키마에서 동작하며, HTTP 요청이 JSON 응답으로 직렬화되는지를 묻습니다. 통합 테스트는 더 많은 것을 확인하지만 준비할 대상이 늘고 실행 시간이 길어집니다. 그래서 “통합 테스트가 단위 테스트보다 상위”라기보다 서로 다른 실패를 찾는 도구라고 이해해야 합니다.

Docker는 애플리케이션과 필요한 실행 환경을 **이미지(image)** 라는 묶음으로 만들고, 그 이미지를 **컨테이너(container)** 라는 격리된 프로세스로 실행하는 기술입니다. PostgreSQL을 설치 파일로 PC에 계속 설치하는 대신, 정해진 버전의 PostgreSQL 이미지를 내려받아 필요한 동안만 컨테이너로 실행할 수 있습니다. 컨테이너는 가상 머신과 달리 호스트 운영체제의 커널을 공유하지만, 파일 시스템·네트워크·프로세스 공간을 어느 정도 분리합니다. 따라서 “가볍다”는 말은 “보안 경계가 완전히 같다”는 뜻이 아니며, 이미지 출처와 권한은 여전히 검토 대상입니다.

테스트에서 중요한 세 번째 개념은 **테스트 격리(isolation)** 입니다. 테스트 A가 주문 테이블에 `paid` 데이터를 넣고, 테스트 B가 빈 테이블을 전제로 하면 실행 순서에 따라 결과가 달라집니다. 한 테스트가 외부 상태를 만들었다면 다음 테스트가 그 상태를 보지 않도록 되돌리거나, 처음부터 분리된 상태를 제공해야 합니다. 컨테이너를 테스트마다 새로 만들 수 있고, 한 컨테이너를 공유하되 트랜잭션 롤백·스키마 삭제·고유한 데이터 키로 격리할 수도 있습니다. 어느 쪽이 맞는지는 테스트 수와 데이터베이스 특성에 따라 달라집니다.

마지막으로 **CI(Continuous Integration, 지속적 통합)** 는 변경을 합칠 때 빌드·테스트·정적 분석을 자동으로 실행하는 흐름입니다. 개발자 노트북의 Docker와 CI 러너의 Docker는 같은 것이 아닐 수 있습니다. CPU 아키텍처, 메모리 제한, 캐시, 인터넷 접근, Docker 소켓 권한이 다를 수 있습니다. Testcontainers를 도입할 때는 로컬 통과만 확인하지 말고 CI가 이미지를 받을 수 있는지와 실패 로그를 남길 수 있는지를 함께 설계해야 합니다.

## Testcontainers는 무엇을 자동화하는가

Testcontainers를 쓰지 않아도 Docker Compose를 수동으로 켜고, 테스트가 끝난 뒤 데이터베이스를 지우는 방식은 가능합니다. 하지만 이 방식은 테스트 명령보다 준비 절차를 기억해야 하고, 병렬 실행에서 포트와 데이터가 충돌하기 쉽습니다. Testcontainers는 테스트 프레임워크와 연결되어 컨테이너의 생성·대기·연결 정보 전달·정리를 코드 수명 주기에 묶습니다.

가령 Java의 JUnit, Python의 pytest, Node.js의 Jest나 Vitest처럼 언어별 테스트 도구에서 PostgreSQL 컨테이너를 선언합니다. 라이브러리는 이미지를 가져오고 임의의 호스트 포트를 할당한 뒤, 데이터베이스가 실제 연결을 받을 준비가 됐는지 기다립니다. 테스트 코드는 하드코딩한 `localhost:5432`가 아니라 실행 중인 컨테이너가 제공한 URL·포트·사용자·비밀번호를 받아 애플리케이션 설정에 주입합니다. 그래서 같은 테스트를 여러 개발자나 CI에서 실행해도 고정 포트 충돌을 줄일 수 있습니다.

여기서 **wait strategy(대기 전략)** 가 특히 중요합니다. 컨테이너 프로세스가 시작됐다는 사실과 서비스가 요청을 받을 준비가 됐다는 사실은 다릅니다. PostgreSQL 프로세스는 살아 있지만 초기화가 끝나지 않았을 수 있고, Kafka는 브로커가 뜬 뒤 토픽 생성까지 시간이 걸릴 수 있습니다. 단순히 몇 초를 `sleep`하는 것은 느린 환경에서 실패하고 빠른 환경에서 시간을 낭비합니다. 로그 한 줄, 열린 포트, HTTP health endpoint, 실제 SQL 연결처럼 서비스 특성에 맞는 준비 조건을 선택해야 합니다.

컨테이너를 띄운다고 테스트 데이터가 자동으로 올바른 상태가 되지는 않습니다. 이미지가 제공하는 기본 데이터베이스는 빈 그릇일 뿐입니다. 마이그레이션 도구(Flyway, Liquibase 등)를 애플리케이션과 같은 방식으로 실행할지, SQL 초기화 스크립트를 적용할지, 테스트용 fixture를 API로 넣을지 결정해야 합니다. 실제 운영 스키마와 다른 임시 SQL을 쓰면 통합 테스트의 장점이 크게 줄어듭니다. 특히 컬럼 추가나 제약 조건 변경을 발견하고 싶다면, CI에서 마이그레이션을 처음부터 적용하는 경로를 포함하는 것이 좋습니다.

## 테스트 더블과 실제 의존성의 경계

테스트 더블(test double)은 실제 협력 객체 대신 테스트를 돕는 대역입니다. mock은 호출 여부나 반환값을 미리 정하고, stub은 정해진 응답을 제공하며, fake는 단순화한 동작을 구현합니다. 예를 들어 결제 승인 API를 테스트할 때 실제 카드사 API를 매번 호출하면 비용·개인정보·승인 취소·네트워크 장애가 테스트를 오염시킬 수 있습니다. 이 경우에는 HTTP mock 서버나 제공사의 sandbox가 더 적절합니다.

반대로 PostgreSQL의 JSONB 연산, 시간대 처리, 유니크 제약, 트랜잭션 롤백을 확인하고 싶은데 메모리 DB나 repository mock으로 바꾸면 질문 자체가 사라집니다. H2 같은 대체 데이터베이스가 특정 SQL을 받아준다고 해서 PostgreSQL에서도 같은 결과가 나온다는 보장은 없습니다. Testcontainers는 바로 이 간극, 즉 **실제 제품의 동작은 확인하고 싶지만 공용 개발 환경은 의존하고 싶지 않을 때** 유용합니다.

다음 기준으로 나누면 처음 도입할 때 과도한 통합 테스트를 피하기 쉽습니다.

| 확인하려는 질문 | 더 알맞은 방식 | 이유 |
| --- | --- | --- |
| 할인율 계산이 올바른가 | 단위 테스트 | 외부 시스템이 규칙에 영향을 주지 않음 |
| PostgreSQL의 제약·쿼리·마이그레이션이 맞는가 | Testcontainers 통합 테스트 | 실제 DB 엔진의 동작이 핵심 |
| 외부 결제사가 특정 오류를 주면 재시도하는가 | mock 또는 sandbox | 비용·부작용과 외부 가용성을 통제해야 함 |
| Kafka 메시지 직렬화와 소비자 설정이 맞는가 | Testcontainers 통합 테스트 | 실제 브로커 프로토콜과 설정을 확인해야 함 |
| 브라우저에서 버튼을 눌러 주문이 완료되는가 | E2E 테스트 | 화면·네트워크·백엔드 흐름을 함께 확인해야 함 |

이 표는 도구를 한 가지로 통일하라는 뜻이 아닙니다. 한 주문 기능에도 단위 테스트, Testcontainers 기반 repository 테스트, mock 기반 외부 연동 테스트, 브라우저 E2E 테스트가 모두 있을 수 있습니다. 각 층이 발견하는 오류가 다르므로, 같은 시나리오를 네 번 복사하기보다 어떤 위험을 어느 층에서 가장 빠르게 발견할지 정합니다.

## PostgreSQL 통합 테스트를 구성하는 예시

아래는 Node.js 환경에서 컨테이너가 제공한 연결 정보를 애플리케이션에 전달하는 개념 예시입니다. 라이브러리의 정확한 API는 언어와 버전에 따라 다르므로, 프로젝트에 맞는 공식 모듈 문서를 함께 확인해야 합니다.

```ts
const postgres = await new PostgreSqlContainer("postgres:16-alpine")
  .withDatabase("app_test")
  .withUsername("test")
  .withPassword("test")
  .start();

process.env.DATABASE_URL = postgres.getConnectionUri();
await runMigrations();

try {
  const response = await request(app)
    .post("/orders")
    .send({ productId: "p-100", quantity: 2 });

  expect(response.status).toBe(201);
} finally {
  await postgres.stop();
}
```

예시의 핵심은 이미지 이름이나 계정명이 아니라 책임의 순서입니다. 첫째, 테스트가 어떤 **버전의 PostgreSQL** 을 검증하는지 명시합니다. `latest` 태그는 시간이 지나면 다른 버전을 가리킬 수 있으므로 재현성을 떨어뜨립니다. 둘째, 애플리케이션이 실제 운영과 같은 마이그레이션을 실행합니다. 셋째, 테스트는 컨테이너가 준 URL을 사용하므로 다른 로컬 DB를 실수로 건드리지 않습니다. 넷째, `finally` 블록처럼 실패해도 정리 경로가 남습니다.

테스트를 한 건 실행할 때마다 컨테이너 하나를 만들면 상태 격리는 강해집니다. 그러나 스키마 초기화가 비싼 프로젝트에서는 실행 시간이 늘 수 있습니다. 반대로 테스트 클래스나 파일 범위에서 하나의 컨테이너를 공유하면 빨라질 수 있지만 데이터 격리를 별도로 책임져야 합니다. 트랜잭션 롤백이 가능한 API라면 각 테스트를 트랜잭션으로 감싸고, 비동기 작업·별도 커넥션·DDL이 있으면 롤백으로 충분한지 다시 확인합니다.

데이터 정리 방법도 서비스 특성에 맞춰야 합니다. `TRUNCATE`는 빠를 수 있지만 외래 키 순서와 시퀀스 재설정을 고려해야 합니다. 테스트마다 데이터베이스를 새로 만들면 명확하지만 권한과 시간이 더 듭니다. 테넌트 ID나 테스트 실행 ID를 모든 행에 넣고 범위 삭제하는 방법은 병렬 테스트에서 도움이 되지만, 실제 쿼리와 모델에 테스트용 개념을 섞는 비용이 있습니다. “가장 빠른 한 가지”를 찾기보다 실패가 재현되고 데이터가 남지 않는 방식을 선택합니다.

## 마이그레이션을 테스트에 포함해야 하는 이유

스키마 변경은 애플리케이션 코드와 분리되어 보이지만 배포 시에는 함께 만나야 합니다. 개발자가 새 컬럼을 읽는 코드를 만들었는데 운영 DB에 마이그레이션이 누락되면, 단위 테스트는 모두 통과해도 런타임에서 오류가 납니다. Testcontainers는 빈 데이터베이스에 마이그레이션을 적용하게 하므로, 누락된 파일·잘못된 SQL 문법·실행 순서·이미 존재하는 제약 조건 같은 문제를 비교적 이른 시점에 드러낼 수 있습니다.

마이그레이션 테스트에는 두 질문을 나눠 넣는 것이 좋습니다. 첫 번째는 **처음부터 최신 버전까지 적용되는가** 입니다. 새 환경이나 재해 복구 환경을 가정합니다. 두 번째는 **이전 실제 버전에서 한 단계씩 안전하게 올라가는가** 입니다. 이미 데이터가 있는 운영 환경을 가정합니다. 후자는 오래된 스키마 fixture와 변환 로직이 필요할 수 있어 모든 PR에서 실행하기 무거울 수 있습니다. 그래서 핵심 릴리스 후보나 야간 파이프라인으로 분리하는 선택도 가능합니다.

마이그레이션이 통과했다고 롤백이 자동으로 안전해지는 것은 아닙니다. 컬럼 삭제나 데이터 변환처럼 되돌릴 수 없는 변경은 애플리케이션 배포 순서, feature flag, 백필 작업, 백업 계획이 필요합니다. Testcontainers는 안전한 실험장을 만들지만, 운영 변경 관리 자체를 대신하지는 않습니다. 특히 대형 테이블의 인덱스 생성 시간, lock, 복제 지연은 작은 컨테이너의 결과만으로 단정하면 안 됩니다.

## 네트워크와 외부 시스템을 다룰 때의 주의점

컨테이너 안의 서비스가 떠도 애플리케이션이 접속할 네트워크 경로는 따로 확인해야 합니다. 테스트 프로세스가 호스트에서 실행되는지, 다른 컨테이너에서 실행되는지, CI의 service container를 쓰는지에 따라 `localhost`의 의미가 달라집니다. 컨테이너 내부에서 `localhost`는 대개 그 컨테이너 자신입니다. Testcontainers가 반환한 host와 mapped port를 사용해야 하는 이유입니다.

Kafka, RabbitMQ, Elasticsearch처럼 여러 포트와 초기 설정이 필요한 의존성은 준비 조건을 더 신중히 잡아야 합니다. 단지 포트가 열렸다고 토픽·큐·인덱스가 준비됐다는 뜻은 아닙니다. 테스트 시작 전에 관리 API로 필요한 리소스를 만들고, 테스트마다 consumer group이나 큐 이름을 고유하게 만들면 병렬 실행 충돌을 줄일 수 있습니다. 다만 운영과 다른 자동 생성 옵션을 켜 두면 배포 뒤에만 나는 오류를 숨길 수 있으므로 테스트 설정 차이를 문서화해야 합니다.

외부 SaaS를 컨테이너로 완전히 대체하려는 시도도 한계가 있습니다. AWS S3, Stripe, OAuth 제공자처럼 인증·과금·리전·관리형 기능이 결합된 서비스는 로컬 에뮬레이터가 일부 API만 구현할 수 있습니다. 에뮬레이터는 애플리케이션의 요청 형식과 재시도 로직을 확인하는 데 도움이 되지만 실제 서비스와 동등하다고 가정해서는 안 됩니다. 핵심 연동은 제공사의 sandbox, 계약 테스트, 제한된 승인 환경 테스트를 별도로 계획합니다.

## CI에서 실패하지 않게 만드는 운영 기준

첫째, 이미지 태그를 고정합니다. `postgres:16.4-alpine`처럼 패치 버전까지 고정할지, `postgres:16-alpine`처럼 마이너 업데이트를 허용할지는 팀의 보안 업데이트 정책에 따라 정합니다. 중요한 것은 의도하지 않은 변경이 테스트 결과를 바꾸지 않도록 갱신 책임을 명확히 하는 것입니다. 이미지의 공급자와 digest를 확인하는 정책도 민감한 조직에서는 필요합니다.

둘째, CI 캐시는 편의 기능이지 정답의 근거가 아닙니다. 이미지 캐시가 있는 러너에서는 빠르다가 새로운 러너에서 실패할 수 있습니다. 네트워크가 느린 상황, 레지스트리 인증 실패, 이미지 pull 제한을 고려해 로그에 이미지 이름과 시작 실패 원인을 남깁니다. 비밀값을 로그로 출력하지 않도록 컨테이너 환경 변수와 연결 URL 마스킹도 확인합니다.

셋째, 병렬 실행 전략을 정합니다. 단순히 테스트 워커 수를 늘리면 CPU·메모리·Docker 데몬이 포화될 수 있고, 공유 데이터베이스와 포트가 충돌할 수 있습니다. 처음에는 핵심 통합 테스트만 직렬 또는 낮은 병렬도로 돌리고, 실행 시간과 실패율을 관찰한 뒤 범위를 넓히는 편이 안전합니다. 시간 제한을 늘려 실패를 숨기기보다, 어느 준비 단계가 병목인지 로그와 메트릭으로 분리합니다.

넷째, 실패 때 조사할 정보를 남깁니다. 컨테이너 로그, 사용한 이미지 버전, 테스트가 연결한 호스트·포트의 비밀 제거 버전, 마이그레이션 로그, 남은 컨테이너 목록이 있으면 재현 시간이 줄어듭니다. 단, 테스트 종료 뒤 자동 정리가 정상이라면 모든 컨테이너를 무조건 보존할 필요는 없습니다. 실패한 경우에만 로그를 artifact로 올리는 방식이 저장 비용과 조사 가능성의 균형을 맞출 수 있습니다.

## 흔한 실패 패턴

첫 번째 실패 패턴은 Testcontainers를 도입하면서 모든 HTTP 호출까지 실제 인터넷으로 연결하는 것입니다. 테스트는 로컬 네트워크, DNS, 외부 API 장애, 과금 정책에 묶이게 됩니다. 실제 DB나 브로커가 필요한 부분은 컨테이너로, 외부 제공자 경계는 mock·sandbox·계약 테스트로 나누는 편이 좋습니다.

두 번째는 테스트가 공용 개발 데이터베이스를 가리키는 것입니다. 환경 변수 기본값이 잘못되어 컨테이너 URL이 아니라 개발 URL을 사용하면, 테스트가 실제 개발 데이터를 삭제하거나 결과가 데이터 상태에 따라 변할 수 있습니다. 테스트 시작 시 연결 문자열의 DB 이름·호스트를 검증하고, 개발·운영 계정으로 접속할 수 없는 별도 자격 증명을 사용하는 것이 안전합니다.

세 번째는 컨테이너 재사용(reuse)을 무조건 켜는 것입니다. 개발 환경에서 반복 실행을 빠르게 하는 데 도움이 될 수 있지만, 남은 데이터와 설정이 다음 실행에 영향을 줍니다. 재사용은 로컬 개발 편의에 한정하고, CI나 신뢰가 필요한 테스트에서는 깨끗한 시작 상태를 우선하는 팀도 많습니다. 재사용을 쓴다면 데이터를 어떻게 초기화하는지와 문제가 생겼을 때 어떻게 끄는지를 문서화합니다.

네 번째는 컨테이너가 떠 있으니 E2E까지 검증됐다고 생각하는 것입니다. Testcontainers 기반 테스트는 애플리케이션과 의존성의 연결을 검증하지만, 브라우저 렌더링·사용자 접근성·CDN·실제 인증 흐름을 모두 대신하지 않습니다. QA 전략에서 각 테스트의 범위를 이름과 보고서에 명확히 써 두면, 통과 결과를 과대해석하는 일을 줄일 수 있습니다.

## 도입 순서: 작은 위험부터 실제 의존성으로

처음부터 전체 테스트 스위트를 바꾸지 말고, 실제 엔진 차이 때문에 장애가 났거나 날 가능성이 큰 경로 하나를 고릅니다. 예를 들어 PostgreSQL 전용 JSONB 쿼리, 유니크 제약을 포함한 가입 처리, Flyway 마이그레이션처럼 mock으로는 의미가 줄어드는 부분이 좋습니다. 그 경로의 단위 테스트는 유지하고, Testcontainers 통합 테스트를 추가해 어떤 실패를 새로 잡는지 확인합니다.

다음으로 실행 위치를 정합니다. 개발자가 PR마다 반드시 받아야 하는 짧은 통합 테스트와, 오래 걸리지만 폭넓은 매트릭스를 확인하는 scheduled 테스트를 나눌 수 있습니다. 데이터베이스 버전 두 개를 지원한다면 모든 PR에서 둘 다 돌릴지, 주 버전은 PR에서 보장하고 보조 버전은 정기 실행에서 확인할지도 선택해야 합니다. 테스트가 느리다는 이유만으로 삭제하기 전에, 실패를 얼마나 이르게 발견하는지와 배포 비용을 비교합니다.

마지막으로 팀의 기준을 글로 남깁니다. “repository 테스트는 실제 PostgreSQL 컨테이너를 사용한다”, “외부 결제는 sandbox를 호출하지 않고 mock 계약으로 검증한다”, “마이그레이션은 빈 DB와 이전 릴리스 fixture에서 검증한다”처럼 짧은 문장이면 충분합니다. 도구 선택보다 중요한 것은 새 구성원이 어떤 테스트를 어디에 추가해야 하는지 예측할 수 있게 만드는 것입니다.

## 테스트 데이터를 신뢰할 수 있게 만드는 세부 규칙

컨테이너가 깨끗하게 시작한다고 해서 테스트 데이터가 좋은 것은 아닙니다. 특히 테스트 데이터가 업무 규칙을 지나치게 단순화하면, 실제 오류가 나는 조건을 계속 지나칠 수 있습니다. 주문 테이블을 예로 들면 “주문 하나, 상품 하나, 성공 상태 하나”만 넣는 fixture는 재고 부족, 부분 취소, 다른 통화, 중복 요청, 권한 없는 사용자 같은 경계를 설명하지 못합니다. 통합 테스트에서는 실제 데이터베이스를 쓰는 만큼, 어떤 상태를 만들고 어떤 상태가 남아야 하는지도 테스트의 기대값으로 적어야 합니다.

fixture는 읽는 사람이 의도를 알 수 있게 이름을 붙이는 편이 좋습니다. `user1`, `item2` 같은 이름보다 `expiredCouponOrder`, `otherTenantCustomer`, `cancelledSubscription`처럼 왜 필요한지 드러나는 이름이 조사 시간을 줄입니다. 다만 fixture를 너무 많은 SQL 파일로 복사하면 스키마 변경 때 전부 깨질 수 있습니다. 공통적으로 필요한 최소 생성 함수와 특정 시나리오의 명시적인 데이터만 남기고, 모든 테스트에 거대한 기본 데이터를 넣는 방식은 피합니다. 데이터가 많아질수록 실패 원인이 business rule인지 초기화 순서인지 구분하기 어려워집니다.

시간도 흔한 함정입니다. 테스트가 `now()`를 여러 번 호출하면 자정, 시간대, 비동기 지연 때문에 기대값이 흔들릴 수 있습니다. 애플리케이션에 clock 추상화가 이미 있다면 고정된 시각을 주입하고, 데이터베이스가 생성 시각을 책임진다면 DB의 시간대를 명확히 확인합니다. 여기서 Testcontainers는 PostgreSQL의 실제 시간 함수와 타입을 확인하게 해 주지만, 테스트 자체가 현재 시각에 우연히 의존하지 않도록 설계하는 책임까지 가져가지는 않습니다.

동시성도 단순 fixture만으로 놓치기 쉽습니다. 같은 쿠폰을 동시에 두 번 쓰거나, 두 요청이 같은 재고를 차감하는 경우는 단건 API 테스트에서 재현되지 않을 수 있습니다. 이런 위험이 있는 도메인이라면 두 연결을 만들고 트랜잭션의 시작·커밋 순서를 제어하는 통합 테스트를 별도로 둡니다. 이때 테스트가 한 번 통과했다고 실제 운영의 모든 부하를 재현한 것은 아닙니다. 유니크 제약, lock timeout, isolation level 같은 설계가 의도대로 동작하는 최소 시나리오를 확인한다는 범위를 분명히 해야 합니다.

## 보안과 공급망 관점에서 보는 테스트 이미지

테스트 전용이라는 이유로 아무 Docker 이미지를 내려받아도 되는 것은 아닙니다. 컨테이너 이미지는 빌드 과정에서 실행 파일과 라이브러리를 포함하므로, 신뢰하지 않는 이미지는 개발자 PC와 CI 환경의 공급망 위험이 될 수 있습니다. PostgreSQL·Redis처럼 널리 쓰이는 공식 이미지나 조직이 승인한 내부 레지스트리를 우선하고, 이미지 태그와 digest, 취약점 스캔, 업데이트 담당자를 정합니다. 특히 `latest`는 오늘과 다음 달의 내용이 다를 수 있으므로 재현성에도 좋지 않습니다.

비밀값 처리도 확인합니다. 테스트 컨테이너의 임시 사용자·비밀번호는 운영 비밀과 달라야 하며, 운영 DB URL이 테스트 환경 변수의 fallback이 되지 않게 합니다. 실패 로그에 연결 문자열을 그대로 남기면 임시 비밀번호라도 다른 정보와 결합되어 위험할 수 있습니다. 로그에서 비밀번호·토큰을 마스킹하고, CI에서 Docker 데몬 접근 권한을 가진 job이 불필요한 다른 컨테이너까지 읽거나 제어하지 못하도록 runner의 신뢰 경계를 검토합니다.

팀이 이미지 업데이트를 할 때는 테스트 성공만 보지 말고 라이선스와 지원 수명도 확인합니다. 테스트가 오래된 DB 버전에 고정되어 있으면 운영 업그레이드 때 SQL·확장·인증 방식 차이를 늦게 발견할 수 있습니다. 반대로 모든 패치 업데이트를 즉시 자동 반영하면 원인 모를 flaky test가 늘 수 있습니다. 정기적으로 의도된 버전 상승 PR을 만들고, 변경 로그와 테스트 결과를 함께 검토하는 방식이 두 위험 사이의 균형을 잡습니다.

## 마무리: 실제 의존성은 좁고 분명하게 테스트하기

Testcontainers의 가치는 Docker를 테스트 코드에서 편하게 띄우는 데서 끝나지 않습니다. 테스트가 어떤 버전의 어떤 의존성에 기대는지 선언하고, 공유 개발 환경의 우연한 상태에서 벗어나게 해 준다는 데 있습니다. 단위 테스트가 업무 규칙을 빠르게 보호한다면, 컨테이너 기반 통합 테스트는 실제 엔진·프로토콜·마이그레이션이라는 경계에서 생기는 오류를 찾습니다.

가장 좋은 시작점은 모든 테스트를 바꾸는 것이 아니라, mock으로는 확인할 수 없는 위험 하나를 실제 컨테이너로 옮기는 것입니다. 준비 조건, 데이터 초기화, CI 권한, 실패 로그를 함께 설계하면 Testcontainers는 느린 장난감이 아니라 재현 가능한 통합 검증 환경이 될 수 있습니다.

테스트가 지키는 경계와 실패했을 때 확인할 정보를 작게라도 문서화해 두면, 도입 뒤 유지 비용도 훨씬 예측하기 쉬워집니다.
