MariaDB Galera Cluster는 여러 MariaDB 노드가 같은 데이터 변경을 공유하도록 구성하는 복제 방식입니다. 단일 primary 서버가 모든 쓰기를 받는 일반 복제와 달리, 여러 노드가 클라이언트 쓰기 요청을 받을 수 있다는 점 때문에 고가용성 구조로 자주 검토됩니다. 하지만 “여러 노드가 있으니 자동으로 빠르고 안전하다”는 설명은 위험합니다. 쓰기 충돌, 네트워크 분할, 느린 노드, 복구 순서가 결과에 직접 영향을 줍니다.

이 글은 Galera를 설치 명령 모음으로 설명하지 않습니다. 어떤 데이터 변경이 어떻게 다른 노드로 전달되는지, quorum이 왜 필요한지, 느린 노드가 왜 전체 처리량에 영향을 줄 수 있는지, 장애에서 어떤 기준으로 판단해야 하는지를 먼저 설명합니다. 이 원리를 알아야 애플리케이션의 연결·재시도·쓰기 경로와 운영 절차를 현실적으로 정할 수 있습니다.

## 먼저 알아둘 기반 기술

복제(replication)는 한 데이터베이스의 변경을 다른 데이터베이스에 전달하는 기술입니다. 비동기 복제는 primary가 변경을 확정한 뒤 replica가 나중에 따라올 수 있어 지연이 생길 수 있습니다. 동기라는 말은 구현마다 의미가 다르지만, Galera는 쓰기 트랜잭션을 commit하기 전에 cluster 구성원과 변경 집합을 조정하려는 certification 기반 방식을 사용합니다. 따라서 지연과 네트워크 품질은 쓰기 경로에 더 직접적으로 영향을 줍니다.

트랜잭션(transaction)은 함께 성공하거나 실패해야 하는 데이터 변경 묶음입니다. write set은 트랜잭션이 바꾼 행과 관련 메타데이터를 복제·충돌 검증에 사용할 수 있게 표현한 변경 집합입니다. certification은 노드가 commit하려는 write set이 이미 확정된 다른 write set과 충돌하는지 확인하는 과정입니다. 충돌하면 애플리케이션은 transaction rollback 또는 certification failure를 받을 수 있으므로 재시도와 멱등성 설계가 필요합니다.

quorum은 cluster가 어느 쪽이 계속 서비스할 수 있는 다수인지 판단하는 원칙입니다. 네트워크가 둘로 갈라졌을 때 양쪽이 모두 쓰기를 받으면 서로 다른 데이터가 생길 수 있습니다. 다수 구성원을 가진 쪽만 Primary Component로 계속 동작하게 하려는 이유가 여기에 있습니다. 노드 세 대는 한 대 장애를 견디는 구성을 만들 수 있지만, 두 노드만으로는 한 노드가 사라졌을 때 어느 쪽이 안전한 다수인지 판단하기 어렵습니다.

## 쓰기 흐름과 certification

애플리케이션이 한 Galera 노드에 `UPDATE`를 보내면 해당 노드는 로컬에서 transaction을 실행하고 변경 내용을 write set으로 만듭니다. commit 단계에서 이 변경은 cluster에 전달되고, 다른 노드는 최근에 확정된 변경과 충돌하지 않는지 검사합니다. 충돌이 없으면 같은 순서로 적용될 수 있도록 합의하고 transaction이 확정됩니다. 이 설명은 단순화한 것이며 실제 처리에는 네트워크와 provider 상태가 관여하지만, 중요한 점은 쓰기가 다른 노드와 완전히 무관한 로컬 작업이 아니라는 사실입니다.

예를 들어 두 사용자가 서로 다른 노드에서 같은 재고 행을 동시에 줄이려 하면, 둘 다 처음 읽기는 성공할 수 있습니다. 하지만 나중에 certification 단계에서 한 transaction이 충돌로 실패할 수 있습니다. 전통적인 단일 DB의 row lock 대기와 사용자 경험이 다를 수 있으므로, 애플리케이션은 특정 오류를 일시적 충돌로 분류하고 제한된 재시도를 고려해야 합니다. 단, 외부 결제나 이메일처럼 DB transaction 밖의 부수 효과가 있다면 재시도가 중복을 만들지 않게 업무 ID와 상태를 함께 설계해야 합니다.

쓰기 충돌을 줄이는 첫 방법은 업무 모델을 보는 것입니다. 모든 요청이 같은 카운터 행이나 마지막 재고 행을 갱신하면 어떤 cluster도 충돌을 완전히 없애지 못합니다. hot row를 분산할 수 있는지, 조건부 update로 표현할 수 있는지, 쓰기 순서를 정할 수 있는지, 일부 집계 작업을 비동기로 바꿀 수 있는지 검토합니다. 인프라 구조를 추가하기 전에 실제 경합 지점을 줄이는 것이 더 간단한 해결일 수 있습니다.

## 구체적 업무 예시: 여러 노드의 예약 요청

예약 서비스가 두 Galera 노드 뒤에 있고, 로드 밸런서가 요청을 번갈아 보낸다고 해 보겠습니다. 사용자는 마지막 좌석 하나를 예약하려 하고, 거의 동시에 다른 사용자도 같은 좌석을 요청합니다. 두 요청이 서로 다른 노드에 가더라도 업무 규칙은 하나만 성공해야 합니다. DB의 unique constraint, 조건부 update, transaction 범위가 이 규칙을 표현하고, Galera certification failure가 발생하면 애플리케이션은 어떤 요청을 재시도하고 어떤 요청을 ‘이미 매진’으로 끝낼지 결정해야 합니다.

테스트는 단순히 두 노드에서 같은 SELECT가 되는지만 확인하면 부족합니다. barrier로 두 예약 요청을 동시에 시작해 최종 예약 수와 좌석 상태가 맞는지, 실패 요청이 결제·알림을 중복 실행하지 않는지, 재시도 뒤에도 하나의 예약만 남는지 확인합니다. 각 요청의 node ID, transaction 오류, 업무 ID, 재시도 횟수를 남기면 충돌이 실제로 어느 경로에서 발생했는지 나중에 분석할 수 있습니다.

이 사례에서 중요한 선택은 모든 실패를 자동 재시도하지 않는 것입니다. 사용자가 이미 다른 좌석을 고를 수 있는 화면이라면 최신 상태를 보여 주는 편이 낫고, 짧은 내부 갱신이라면 제한된 재시도가 적절할 수 있습니다. Galera 오류 코드를 인프라 예외로만 처리하지 말고 업무 상태와 사용자 다음 행동으로 연결해야 합니다.

## 노드 가입과 상태 전송

새 노드가 cluster에 참여하거나 오래 떨어져 있던 노드가 돌아오면 기존 데이터와 변경 기록을 따라잡아야 합니다. Galera 환경에서는 변경 집합을 이용한 증분 상태 전송과, 필요한 경우 전체 상태 전송 같은 복구 경로를 검토하게 됩니다. 어떤 경로가 선택되는지는 노드가 떠 있던 기간, 다른 노드의 변경 기록 보존, 설정과 환경에 영향을 받습니다. 따라서 단순 재시작을 무해한 작업으로 보지 말고, 복구 중 네트워크·디스크·기존 노드 부하가 어떻게 변하는지 관찰해야 합니다.

상태 전송이 오래 걸리면 새 노드는 서비스 대상에 넣지 않아야 합니다. 로드 밸런서와 Kubernetes 같은 오케스트레이터를 쓴다면, process가 떠 있다는 사실이 아니라 Galera가 Synced 상태이고 읽기·쓰기를 안전하게 처리할 준비가 됐는지를 readiness 기준으로 사용합니다. 복구 중인 노드가 일부 오래된 데이터를 읽거나 요청을 받으면 사용자에게 일관성 없는 결과가 보일 수 있습니다.

데이터가 큰 환경에서는 전체 상태 전송의 시간과 네트워크 비용이 장애 복구 목표를 좌우할 수 있습니다. 백업·복구 전략, 변경 기록 보존, 디스크 공간, donor 노드 선정 기준을 미리 정합니다. 특정 노드가 복구를 도와 주는 동안 그 노드의 응답 지연이 커지는지, 여러 노드가 동시에 복구하지 않도록 제어하는지도 운영 계획에 포함합니다.

## Flow Control과 느린 노드

Galera의 flow control은 뒤처진 노드가 너무 많이 밀리지 않게 cluster의 복제 흐름을 조절하려는 메커니즘입니다. 한 노드의 디스크 I/O가 느리거나 CPU가 포화되면 그 노드는 write set 적용을 따라가지 못할 수 있습니다. 이때 빠른 노드만 계속 쓰기를 확정하면 나중에 복구할 변경량이 커지고 일관성 관리가 어려워질 수 있습니다. flow control은 이런 상황에서 전체 처리량을 늦출 수 있습니다.

따라서 특정 노드의 성능 문제는 그 노드만의 문제가 아닐 수 있습니다. 평균 API 응답 시간이 늘고 쓰기 지연이 올라갈 때, 애플리케이션 서버만 보지 말고 각 DB 노드의 apply queue, 디스크 대기, CPU, 네트워크 지연, 긴 transaction을 함께 확인해야 합니다. 느린 노드를 단순히 제거하면 일시적으로 빨라질 수 있지만 quorum과 복구 가능성에 주는 영향도 판단해야 합니다.

용량 계획에서는 노드 수를 늘리면 쓰기 성능이 선형으로 늘어난다고 가정하지 않습니다. 읽기 분산은 도움이 될 수 있지만, 모든 쓰기는 cluster 통신과 인증 비용을 갖습니다. 멀리 떨어진 리전에 노드를 추가하면 재해 복구 관점에는 이점이 있을 수 있어도 network round trip이 commit 지연에 영향을 줄 수 있습니다. 지연 목표, 장애 도메인, 실제 쓰기 비율을 기준으로 topology를 선택해야 합니다.

## 네트워크 분할과 quorum 판단

네트워크 분할은 노드가 실제로 죽지 않았지만 서로 통신할 수 없는 상태입니다. 이때 두 그룹이 모두 계속 쓰면 split brain, 즉 서로 다른 사실을 동시에 받아들이는 문제가 생길 수 있습니다. quorum 규칙은 다수 그룹만 Primary Component로 쓰기를 계속하게 해 이 위험을 줄입니다. 운영자는 “응답이 안 되는 노드”와 “다수에서 분리된 노드”를 구분하고, 후자를 임의로 bootstrap해 독립 cluster를 만들지 않도록 주의해야 합니다.

특히 전체 cluster가 멈춘 뒤 재기동할 때 어느 노드에서 bootstrap할지는 데이터 최신성과 상태를 근거로 판단해야 합니다. 가장 먼저 켜지는 노드를 무조건 기준으로 삼으면 최신 변경을 잃거나 다른 노드와 충돌할 수 있습니다. 제품 문서의 safe-to-bootstrap 절차와 조직의 runbook을 따르고, 판단 근거·시각·노드 상태를 기록합니다. 긴급 상황에서도 명령 하나를 외우는 것보다 왜 그 노드가 기준인지 확인하는 과정이 중요합니다.

네트워크 장비의 짧은 packet loss, DNS 문제, 방화벽 규칙 변경도 cluster 관점에서는 큰 영향이 될 수 있습니다. 데이터베이스 노드 간 통신 포트와 애플리케이션 접속 포트를 구분하고, health check가 단순 TCP 연결만 보는지 실제 Galera 상태도 보는지 확인하세요. 네트워크 장애 테스트는 실제 production 분할을 만들지 않는 격리 환경에서 계획적으로 수행해야 합니다.

## 백업·복구와 읽기 경로

cluster가 있다고 백업이 필요 없어지는 것은 아닙니다. 논리적 오류, 잘못된 삭제, 애플리케이션 버그는 모든 노드로 복제될 수 있습니다. 백업은 특정 시점으로 되돌리는 수단이고, 고가용성 cluster는 노드·프로세스 장애에서 서비스를 계속하기 위한 수단입니다. 복구 목표 시간(RTO)과 복구 시점 목표(RPO)을 정하고, 백업 파일을 실제로 복원해 보는 검증을 정기적으로 해야 합니다.

읽기를 여러 노드로 분산할 때도 업무 일관성을 확인합니다. Galera 노드가 정상 Synced 상태라면 읽기 분산을 고려할 수 있지만, transaction 격리, 세션 일관성, 방금 쓴 데이터를 어느 노드에서 읽는지, 긴 읽기 작업이 apply를 방해하는지에 따라 정책이 달라집니다. 모든 SELECT를 무조건 아무 노드로 보내기보다, 쓰기 직후 확인·관리 작업·분석 쿼리의 요구를 분리합니다.

분석 쿼리가 긴 시간 실행되면 DB 자원과 transaction 관리에 영향을 줄 수 있습니다. 운영 데이터베이스에서 무거운 보고를 실행할지, 별도 분석 환경·replica·export를 쓸지 판단합니다. Galera를 고가용성의 해답으로 도입한 뒤 분석 부하 때문에 node가 뒤처지는 상황은 피해야 합니다.

## 애플리케이션 연결과 재시도 설계

애플리케이션은 cluster가 여러 노드라는 사실을 사용자에게 그대로 드러내지 않아야 합니다. connection pool 또는 database proxy가 어느 노드로 연결할지 선택하더라도, 연결이 끊겼을 때 요청이 안전하게 재시도 가능한지와 쓰기 직후 읽기가 어떤 일관성을 요구하는지를 서비스가 결정해야 합니다. 단순 SELECT는 다른 healthy node로 다시 연결할 수 있어도, commit 직전 끊긴 주문 요청은 서버가 이미 확정했는지 알 수 없으므로 업무 ID와 조회 경로가 필요합니다.

certification failure나 일시적 네트워크 오류를 재시도할 때는 transaction 전체를 새로 시작합니다. 일부 SQL만 재실행하면 이미 읽었던 오래된 값이나 rollback된 상태를 사용하게 될 수 있습니다. 재시도 횟수는 제한하고 짧은 backoff를 두며, 같은 업무 요청이 두 번 결제·알림·이벤트 발행을 만들지 않게 멱등 키와 outbox 같은 경계를 적용합니다. Galera가 DB 변경을 조정한다고 해서 외부 시스템까지 한 번만 호출해 주는 것은 아닙니다.

읽기와 쓰기의 endpoint를 나누는 경우에는 failover 후에도 애플리케이션이 올바른 node를 선택하는지 테스트합니다. 어떤 proxy는 unhealthy node를 제거할 수 있지만, Galera가 아직 joiner·donor·desynced 상태인지까지 애플리케이션 관점의 health check와 맞춰야 합니다. 연결 성공만으로 쓰기 가능한 상태라고 가정하면 복구 중 node로 요청을 보내는 문제가 생길 수 있습니다.

## Schema 변경과 배포 순서

Galera cluster에서 schema migration은 단순히 한 노드에 DDL을 실행하는 작업이 아닙니다. 긴 DDL, table lock, metadata lock, 서로 다른 애플리케이션 버전의 SQL이 동시에 존재하는 상황이 cluster 흐름에 영향을 줄 수 있습니다. 먼저 변경이 online 방식으로 가능한지, 큰 테이블에서 얼마나 오래 걸릴지, 변경 중 기존 코드와 새 코드가 함께 동작하는지 확인합니다. 데이터 형식 변경은 확장·이전·정리 순서를 사용하면 위험을 줄일 수 있습니다.

예를 들어 새 필드를 추가할 때는 먼저 nullable 또는 기본값을 가진 schema를 배포하고, 애플리케이션이 새·이전 필드를 모두 읽을 수 있게 한 뒤, backfill과 검증을 수행하고, 오래된 코드가 사라진 후 제약을 강화합니다. 이 과정은 단일 DB에서도 유용하지만 여러 노드에서 DDL과 복제가 얽힐 때 더 중요합니다. 한 번에 필드를 rename하고 모든 앱을 바꾸는 방식은 rollback을 어렵게 만듭니다.

migration 중에는 node 상태, apply queue, lock wait, 디스크 공간, 애플리케이션 오류율을 관찰합니다. 문제가 생겼을 때 DDL을 중단하거나 이전 schema로 돌아갈 수 있는지, 이미 실행된 데이터 변환은 어떻게 처리할지 미리 정합니다. “배포가 끝났다”는 로그보다 모든 node가 정상 상태로 돌아왔고 읽기·쓰기 시나리오가 통과했다는 검증이 중요합니다.

## 관찰 지표와 장애 조사 순서

Galera를 운영할 때는 cluster 구성 상태, 노드별 Synced 여부, wsrep 관련 queue와 flow control 신호, certification failure, apply 지연, 네트워크 오류, 디스크·CPU 포화를 함께 봅니다. 지표 이름을 외우는 것보다 어떤 증상이 어떤 계층의 문제인지 연결하는 것이 중요합니다. 예를 들어 write latency가 늘고 flow control이 증가하면 느린 node·디스크·긴 transaction을 후보로 보고, 특정 업무만 certification failure가 늘면 hot row와 동시 쓰기 경로를 조사합니다.

장애 조사에서는 먼저 사용자 영향과 cluster 전체 상태를 확인합니다. 몇 노드가 Primary Component인지, 어느 노드가 desynced인지, 최근 network·배포·backup 작업이 있었는지, 애플리케이션 오류가 어느 endpoint에서 시작됐는지 시간을 연결합니다. 다음으로 node를 재시작하거나 제거하기 전에 그 조치가 quorum과 데이터 복구에 어떤 영향을 줄지 검토합니다. 눈앞의 지연을 없애는 조치가 더 큰 분할을 만들지 않도록 runbook을 따릅니다.

로그에는 transaction의 전체 SQL과 민감 파라미터를 무조건 남기지 않습니다. request ID, 업무 ID, node ID, 오류 코드, 영향 행 수, 재시도 횟수처럼 원인을 연결할 수 있는 최소 정보를 구조화해 남깁니다. 이 정보는 DB 운영자와 애플리케이션 개발자가 같은 사건을 다른 관점에서 조사할 수 있게 합니다.

## 보안과 운영 권한

cluster 노드 간 통신은 신뢰할 수 있는 네트워크와 인증·암호화 정책 위에서만 운영해야 합니다. 방화벽은 application client 접속 포트와 Galera 통신·상태 전송에 필요한 경로를 구분하고, 불필요한 외부 노출을 막습니다. 비밀번호·인증서·백업 파일·상태 전송 계정은 secret 관리 체계에 두고, 로그와 runbook에 평문으로 복사하지 않습니다.

운영 권한도 분리합니다. 애플리케이션 팀이 일상적인 schema 변경을 요청할 수 있어도, 전체 cluster bootstrap이나 노드 강제 제거 같은 위험한 조치는 제한된 운영자와 승인 절차가 맡는 편이 안전합니다. 긴급 상황에서는 속도가 필요하지만, 누가 어떤 근거로 조치했는지 기록하지 않으면 나중에 데이터 정합성을 확인하기 어렵습니다. 권한 분리는 업무를 느리게 만드는 장치가 아니라 큰 변경의 영향 범위를 줄이는 장치입니다.

## 성능 테스트와 용량 계획

성능 검증은 단일 노드 benchmark 결과를 그대로 cluster 용량으로 환산하지 않습니다. 읽기·쓰기 비율, transaction 크기, 동시성, network round trip, 인덱스, disk latency, node 간 거리, flow control이 서로 영향을 줍니다. 실제 업무와 비슷한 데이터 분포로 정상 부하, 피크 부하, 느린 노드, 노드 하나 이탈 시나리오를 나누어 측정하고, p95 write latency와 오류율·queue·CPU를 함께 봅니다.

용량 여유는 평균 처리량만이 아니라 복구와 장애 동안의 여유를 포함해야 합니다. 한 노드가 내려가도 남은 노드가 트래픽과 상태 전송을 처리할 수 있는지, backup이나 대량 batch가 겹칠 때 지연이 어디까지 허용되는지 정합니다. 단순히 노드를 늘리기보다 hot table·큰 transaction·불필요한 retry를 줄이는 것이 먼저일 수 있습니다. 측정 조건과 결론을 문서화하면 나중에 hardware·버전·업무 비율이 바뀌었을 때 다시 검증할 기준이 생깁니다.

## 운영 연습과 복구 검증

고가용성은 문서에만 있으면 장애 때 작동하지 않습니다. 정기적인 연습에서 노드 하나를 계획적으로 중지했을 때 cluster가 어떤 상태로 변하는지, 애플리케이션 연결이 어떻게 failover하는지, 쓰기 요청과 읽기 요청의 사용자 경험이 어떤지 확인합니다. 이 연습은 실제 고객 트래픽과 격리된 환경 또는 승인된 낮은 위험 구간에서 수행하고, 시작·종료 조건과 되돌릴 절차를 미리 정합니다.

복구 검증에는 백업 복원도 포함됩니다. 특정 시점 백업을 별도 환경에 복원하고, 필요한 테이블·권한·애플리케이션 호환성이 맞는지, 복원 후 데이터 정합성을 어떤 쿼리로 확인할지 점검합니다. cluster 노드가 여러 개라는 이유로 잘못된 삭제나 논리 오류를 되돌릴 수 있는 것은 아닙니다. RPO와 RTO가 실제 복원 시간과 백업 주기로 충족되는지 측정하지 않으면 목표는 숫자만 남습니다.

runbook은 모든 설정값을 나열하는 문서보다 판단 순서가 중요합니다. 알림을 받았을 때 확인할 cluster 상태, quorum, node 역할, 최근 변경, application 영향, 금지할 위험한 조치, escalation 기준을 짧게 적습니다. 전체 cluster가 중단된 상황의 bootstrap 절차는 별도로 두고, 실제 담당자가 접근할 수 있는 최신 제품 문서와 연락 경로를 연결합니다. 연습 뒤에는 누락된 권한·모니터링·시간 정보를 보완합니다.

## 데이터 정합성 점검

장애 뒤에는 node가 다시 보인다는 사실만으로 복구가 끝난 것이 아닙니다. 예약·결제·재고처럼 중요한 업무 테이블에서 기대한 건수와 상태 전이를 대조하고, 실패한 transaction의 재시도가 중복 결과를 만들지 않았는지 확인합니다. 이벤트 outbox나 외부 결제 provider가 있다면 DB 상태와 외부 상태의 차이를 조사할 수 있는 업무 ID가 필요합니다. 이 점검은 Galera 자체의 오류 여부를 넘어 서비스가 사용자 약속을 지켰는지 확인하는 단계입니다.

정합성 점검을 일회성 수동 작업으로 두면 사고 때 잊기 쉽습니다. 일별 대조, 배치 완료 검증, 중요한 상태 전이의 불변식 검사처럼 자동화 가능한 항목을 정하고, 차이가 났을 때 자동 수정하지 말고 먼저 분류·승인·감사 절차를 거치게 합니다. 빠른 복구를 위해 데이터를 다시 쓰는 행동이 오히려 이중 처리나 증거 훼손을 만들 수 있기 때문입니다.

## 팀 적용 기준

Galera 환경의 장애 알림은 node 수가 줄었다는 사실만 전달하기보다, 현재 Primary Component 여부, Synced node 수, flow control·apply queue 변화, 애플리케이션 write 오류율, 최근 배포·네트워크 변경을 함께 보여 주는 편이 좋습니다. 당번자는 이 정보로 단순 경고인지 즉시 사용자 영향이 있는지 판단할 수 있습니다. 알림이 너무 많으면 중요한 quorum 경고가 묻히므로, 조치 가능성과 사용자 영향에 맞춰 등급을 나눕니다.

노드 교체도 일상적 운영 절차로 준비합니다. 새 노드의 운영체제·MariaDB 버전·설정·time synchronization·디스크 성능이 기존 node와 호환되는지 확인하고, cluster에 join한 뒤 Synced 상태와 읽기·쓰기 검증을 마친 다음에만 트래픽을 받게 합니다. 노드를 제거할 때도 quorum 여유와 상태 전송 가능성을 확인하며 한 번에 여러 대를 내리지 않습니다. 하드웨어 교체가 데이터베이스 변경으로 이어진다는 사실을 runbook에 명시하세요.

업그레이드는 더 보수적으로 다룹니다. provider와 MariaDB 버전, OS library, 설정 값이 cluster 호환성에 영향을 줄 수 있으므로, 지원되는 upgrade path와 롤링 업그레이드 가능 여부를 공식 문서에서 확인합니다. staging에서 같은 topology와 핵심 transaction을 검증하고, production에서는 한 node씩 진행하며 상태·성능·오류율을 관찰합니다. 문제 발생 시 다음 node로 진행하지 않고 현재 cluster 안정성을 먼저 회복합니다.

## 도입 선택 기준

Galera는 읽기 분산과 고가용성이 필요하고, 노드 간 network latency가 낮으며, 쓰기 충돌을 관리할 수 있는 업무에 적합할 수 있습니다. 반면 하나의 primary 쓰기 경로로 충분하거나, 리전 간 긴 지연을 가진 동기 commit을 피해야 하거나, hot row가 매우 많은 시스템이라면 다른 복제·샤딩·비동기 처리 전략이 더 단순할 수 있습니다. 제품 이름이 아니라 쓰기 패턴·장애 목표·운영 역량을 기준으로 선택하세요.

도입 책임도 명확히 합니다. DBA는 topology, backup, node 상태, schema 운영을, 애플리케이션 팀은 transaction 경계와 멱등 재시도를, 플랫폼 팀은 network·secret·monitoring을 맡을 수 있습니다. 하지만 장애 시 이 경계가 서로 책임을 넘기는 이유가 되면 안 됩니다. request ID와 업무 ID, node 상태를 공유하며 함께 문제를 재현하고 해결할 수 있는 runbook과 훈련이 cluster 기술보다 더 중요합니다.

운영 성숙도도 선택 기준입니다. 노드 상태·network·backup을 관찰할 도구와 담당자가 없고, 장애 runbook을 검증할 시간도 없다면 단일 primary와 검증된 백업·failover 절차가 더 안전할 수 있습니다. 반대로 이미 여러 노드와 독립된 장애 도메인을 운영하고, write conflict를 업무 수준에서 처리하며, 정기 복구 훈련을 할 수 있다면 Galera의 장점을 현실적인 가용성으로 바꿀 수 있습니다. 기술 선택은 기능 목록보다 이 운영 약속을 지킬 수 있는지로 판단해야 합니다.

도입 후에는 초기 설정값을 영구 정답으로 보지 않습니다. 트래픽이 늘거나 transaction 형태가 바뀌면 certification failure, flow control, 상태 전송 시간, backup 윈도우가 달라질 수 있습니다. 분기별 또는 큰 배포 뒤에 실제 관찰값과 장애 연습 결과를 검토해 topology·용량·runbook을 갱신하세요. 이 검토가 있어야 cluster는 설치 당시의 설계가 아니라 살아 있는 운영 시스템이 됩니다.

## 한계와 적용 기준 Q&A

### Q. 두 노드만으로 Galera cluster를 구성해도 되나요?

A. 가능 여부와 별개로 quorum과 장애 판단이 어려워질 수 있습니다. 두 노드 중 하나가 사라졌을 때 남은 한 노드가 계속 쓰기를 받아도 되는지 판단할 제3의 투표자나 운영 절차가 필요할 수 있습니다. 목표 가용성과 장애 도메인을 기준으로 노드 수와 arbitrator 사용 여부를 설계하세요.

### Q. Galera를 쓰면 deadlock이나 쓰기 충돌이 없어지나요?

A. 아닙니다. 로컬 DB 잠금과 transaction 설계 문제는 남고, 여러 노드에서 동시에 쓴 변경은 certification conflict가 될 수 있습니다. hot row를 줄이고 transaction을 짧게 유지하며, 재시도 가능한 오류와 외부 부수 효과의 경계를 설계해야 합니다.

### Q. 장애가 나면 노드를 바로 다시 시작하면 되나요?

A. 단일 노드 재시작은 상태 전송과 quorum에 영향을 줄 수 있습니다. 먼저 남은 cluster의 상태, 해당 노드가 얼마나 오래 떨어져 있었는지, 데이터 최신성, 네트워크 원인을 확인하세요. 전체 정지 뒤 bootstrap은 특히 runbook과 제품 문서의 절차를 따라야 합니다.

## 도입 체크리스트

도입 전에는 쓰기 비율과 hot row, 허용 가능한 commit 지연, 데이터센터·리전 간 network latency, 장애 시 필요한 가용성, 백업·복구 목표를 적습니다. 이어서 세 노드 중 한 노드 장애, 느린 노드, 동시 쓰기 충돌, 상태 전송, 네트워크 분할을 테스트 환경에서 재현하고 사용자·업무 결과를 확인합니다. 단순 ping 성공이 아니라 예약 수·결제 상태·이벤트 수처럼 실제 정합성 결과를 봐야 합니다.

MariaDB Galera Cluster는 여러 노드에 데이터를 복사하는 기술이면서, 쓰기와 장애 판단을 cluster 규칙에 맞게 바꾸는 운영 모델입니다. certification, quorum, flow control, 상태 전송의 의미를 이해하고 애플리케이션 재시도·백업·모니터링·runbook을 함께 설계하면, 노드 수만 늘린 복잡한 환경 대신 검증 가능한 고가용성 경계를 만들 수 있습니다.

특히 장애 대응에서 가장 중요한 것은 빠른 명령 실행보다 현재 cluster가 어떤 다수 상태인지와 데이터가 어떤 경로로 회복되는지를 확인하는 일입니다. 노드·네트워크·애플리케이션의 신호를 같은 시간축에서 보고, 복구 뒤 업무 정합성을 대조하는 습관이 있어야 자동화된 failover도 신뢰할 수 있습니다. 작은 장애 연습과 복원 검증을 반복하면, 실제 장애의 불확실성을 줄이고 담당자가 바뀌어도 같은 판단을 재현할 수 있습니다.

운영 지표를 해석할 때도 한 수치만 보고 결론내리지 않습니다. flow control 증가와 commit 지연, node의 디스크 대기, 애플리케이션 retry가 같은 시간에 나타나는지 확인하면 병목을 더 정확히 좁힐 수 있습니다. 반대로 한 노드의 일시적 경고가 사용자 오류로 이어지지 않았다면, 무리하게 topology를 바꾸기보다 원인과 재발 조건을 기록해 다음 점검에 반영합니다. 고가용성은 장애를 없애는 약속이 아니라, 장애가 일어나도 데이터와 서비스의 회복 경로를 통제하는 설계입니다.

이 원칙을 문서와 연습으로 반복해야 합니다.

작은 점검이 큰 데이터 사고를 예방합니다.

운영자는 변경 전에 영향 범위와 되돌릴 방법을 확인하고, 변경 뒤에는 node 상태뿐 아니라 실제 업무 결과를 반드시 대조해야 합니다.
