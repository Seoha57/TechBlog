같은 커밋, 같은 테스트인데 어떤 날은 통과하고 어떤 날은 실패한다면 그 테스트는 제품의 품질을 알려 주지 못합니다. 이런 테스트를 **Flaky Test** 라고 합니다. flaky는 단순히 불편한 CI 오류가 아닙니다. 실패 경보를 믿지 못하게 만들고, 개발자가 실제 결함을 “또 테스트 문제겠지”라고 넘기게 하며, 결국 테스트를 재실행하는 문화로 이어집니다.

중요한 점은 flaky를 “한 번 실패했지만 다시 돌리면 되었다”로 정의하지 않는다는 것입니다. 테스트의 같은 입력·같은 코드·같은 의도 아래 결과가 환경, 실행 순서, 시간, 네트워크, 공유 상태 때문에 달라지는 **비결정성(nondeterminism)** 이 핵심입니다. 이 글은 재시도를 늘리는 방법이 아니라, 왜 결과가 흔들리는지 분류하고 어디까지 격리·수정·보류해야 신뢰를 회복할 수 있는지를 다룹니다.

## 먼저 알아둘 기반 기술

**결정적 테스트(deterministic test)** 는 같은 전제 조건과 입력에서 같은 결과가 나오는 테스트입니다. 테스트 코드는 제품 코드와 달리 실행 횟수가 많고 병렬 실행되므로, 외부 상태를 통제하지 않으면 작은 우연이 결과를 바꿉니다. 테스트의 목적은 실패를 많이 만드는 것이 아니라, 제품의 변경이 약속을 깨뜨렸을 때만 실패하도록 만드는 데 있습니다.

**테스트 격리(test isolation)** 는 한 테스트의 데이터·시간·프로세스·환경 설정이 다른 테스트에 영향을 주지 않도록 분리하는 원칙입니다. 예를 들어 모든 테스트가 `test@example.com` 계정을 공유하면, 한 테스트가 삭제하거나 권한을 바꾼 뒤 다른 테스트가 실패할 수 있습니다. 병렬 실행에서는 이런 문제가 순서에 따라 나타나므로 로컬에서 한 번 돌릴 때는 보이지 않고 CI에서만 보이기도 합니다.

**CI(Continuous Integration)** 는 변경을 자동 빌드·테스트해 빠르게 피드백하는 과정입니다. CI의 실패는 팀의 행동을 바꿉니다. 실패 원인이 신뢰할 만하면 사람은 멈춰서 조사하지만, 반복되는 오경보가 많으면 재실행 버튼을 누르거나 실패를 무시합니다. flaky 관리는 테스트 코드만의 문제가 아니라 배포 안전장치의 신뢰를 지키는 일입니다.

## flaky를 먼저 분류해야 하는 이유

간헐 실패를 하나의 목록으로만 관리하면 해결 순서가 흐려집니다. 동일 테스트가 제품 코드와 무관하게 실패하는지, 테스트 환경이 불안정한지, 실제 제품의 경쟁 조건인지에 따라 담당자와 조치가 달라집니다. 예를 들어 외부 SaaS API의 timeout은 테스트 더블이나 계약 테스트로 경계를 바꾸는 문제일 수 있고, 주문이 두 번 생성되는 현상은 제품 동시성 결함일 수 있습니다.

가장 실용적인 분류는 원인 축으로 시작하는 것입니다. 첫째는 **공유 상태** 입니다. DB 행, 파일, 포트, 사용자 계정, 캐시 키, 환경 변수가 테스트 사이에 남거나 동시에 수정됩니다. 둘째는 **시간과 비동기 처리** 입니다. 고정 sleep, 타임존, 자정 경계, 타이머, UI 렌더링 완료를 추측하는 코드가 여기에 속합니다. 셋째는 **외부 의존성** 입니다. 네트워크, DNS, 결제 샌드박스, 브라우저 다운로드, 클라우드 자원이 불안정하거나 한도를 공유합니다. 넷째는 **무작위성과 순서** 입니다. 난수 seed, 컬렉션 순서, 테스트 실행 순서가 결과에 영향을 줍니다.

분류는 완벽한 라벨링이 아니라 첫 조사 방향을 정하는 도구입니다. 실패한 빌드에서 테스트 이름만 남기지 말고 실행 순서, worker, seed, 시간대, 브라우저 버전, 관련 로그·trace·스크린샷을 함께 남기면 분류의 근거가 생깁니다. “재실행하니 통과”는 증상이지만 원인 분류는 아닙니다.

## 공유 상태를 없애는 방법

가장 흔한 flaky 원인은 테스트가 같은 자원을 공유하는 것입니다. 데이터베이스 테스트에서 고정된 사용자 ID나 주문 번호를 쓰면, 테스트 A가 데이터를 만들고 테스트 B가 그 데이터를 기대하지 않은 시점에 읽을 수 있습니다. 해결은 단순히 삭제 코드를 마지막에 넣는 것만이 아닙니다. 테스트마다 고유한 식별자를 만들고, 가능하면 트랜잭션 롤백·스키마 분리·테스트 전용 데이터베이스처럼 시작 상태를 독립적으로 만드는 방식이 더 안전합니다.

파일 시스템과 포트도 같은 원리입니다. 임시 디렉터리는 테스트 실행마다 새로 만들고 종료 때 정리하며, 고정 포트 대신 운영체제가 할당한 사용 가능한 포트를 사용합니다. 환경 변수나 전역 싱글턴은 테스트마다 초기화합니다. 정리 코드가 실패했을 때도 다음 테스트가 오염되지 않게 하는 방식을 생각해야 합니다. 실패한 테스트는 teardown까지 실행되지 않을 수 있기 때문입니다.

병렬 실행을 끄는 것은 빠른 회피책이 될 수 있지만 근본 해결은 아닙니다. 순차 실행에서도 전 테스트가 남긴 상태에 의존하면 테스트 순서를 바꿨을 때 깨질 수 있습니다. 병렬화는 숨겨진 결합을 드러내는 검사 도구가 될 수 있습니다. 당장 고치기 어려운 경우에는 영향을 받는 묶음만 임시로 직렬화하고, 왜 격리가 깨졌는지와 제거 계획을 이슈로 남겨야 합니다.

## 시간과 비동기 처리를 추측하지 않는다

`sleep(1000)`은 “1초면 충분할 것”이라는 추측입니다. 개발자 노트북에서는 맞아도 CI의 느린 worker, 브라우저 부하, GC, 네트워크 지연에서는 틀릴 수 있습니다. UI 테스트는 고정 시간을 기다리는 대신 버튼이 enabled 되었는지, 응답이 완료됐는지, 특정 상태가 화면에 나타났는지처럼 **관찰 가능한 조건** 을 기다려야 합니다. 조건 기반 대기는 실제로 준비되면 즉시 끝나고, timeout이 나면 무엇을 기다렸는지 알려 주기 때문에 더 빠르고 읽기 쉽습니다.

현재 시각은 주입하거나 고정해야 합니다. 만료일 계산, 월말 정산, 하루 시작 시각 같은 로직은 테스트 실행 시간에 따라 결과가 바뀌지 않도록 fake clock을 사용합니다. 타임존도 명시합니다. 개발 환경은 KST, CI는 UTC라면 날짜 문자열과 자정 경계 테스트가 달라질 수 있습니다. “로컬에서는 통과한다”는 말 대신 테스트가 사용하는 clock과 timezone을 코드·환경 설정에 드러내야 합니다.

비동기 이벤트는 완료 신호를 기준으로 검증합니다. 메시지 소비, 배치 작업, webhook 처리처럼 결과가 나중에 나타나는 기능은 충분히 오래 기다리는 방식보다 제한 시간 안에 원하는 상태에 도달하는지를 폴링하거나 테스트용 완료 이벤트를 관찰합니다. timeout은 실패를 숨기는 시간이 아니라, 서비스 수준에서 허용하는 지연을 테스트에 표현하는 값이어야 합니다.

## 난수·순서·데이터 정렬을 통제한다

난수는 좋은 입력 다양성을 주지만 재현 정보 없이 사용하면 실패 원인을 잃습니다. 속성 기반 테스트나 임의 데이터 생성기를 쓸 때는 seed를 출력해 같은 입력을 다시 만들 수 있어야 합니다. 난수로 생성한 값도 유효한 업무 범위를 지켜야 합니다. 존재하지 않는 국가 코드나 불가능한 날짜를 무작위로 만들면 제품 결함이 아니라 잘못된 fixture가 실패를 만들 수 있습니다.

데이터베이스 쿼리에 명시적 `ORDER BY`가 없으면 반환 순서를 보장하지 않습니다. API 테스트가 배열의 첫 번째 항목만 보고 통과한다면 인덱스 변경·통계·DBMS 버전에 따라 flaky해질 수 있습니다. 순서가 계약이면 서버가 정렬 기준을 명시하고 테스트가 그것을 검증합니다. 순서가 계약이 아니면 배열을 집합으로 비교하거나 필요한 속성만 확인합니다. 마찬가지로 JavaScript 객체 순서나 병렬 요청의 완료 순서를 업무 규칙처럼 가정하지 않습니다.

테스트 runner가 순서를 섞을 수 있다면 그 설정을 CI에 적용해 숨은 결합을 조기에 찾을 수 있습니다. 다만 매 빌드마다 난수를 바꿔 실패를 많이 만드는 것이 목적은 아닙니다. 실패가 나면 seed·순서·worker 정보를 확보하고, 최소 재현 사례로 줄여 원인을 제거하는 과정이 뒤따라야 합니다.

## 외부 의존성은 신뢰 경계를 분리한다

결제, 이메일, 지도, 인증 제공자처럼 팀이 제어하지 못하는 서비스에 E2E 테스트가 매번 연결되면 네트워크 지연·rate limit·상대 서비스 점검이 우리 CI 실패로 보일 수 있습니다. 단위·통합 테스트에서는 검증 가능한 fake, stub, 테스트 서버를 사용하고, 실제 외부 서비스와의 연결은 소수의 계약 테스트 또는 별도 통합 환경에서 수행하는 편이 일반적입니다.

여기서 mock을 많이 쓰는 것이 목표는 아닙니다. 요청 형식·서명·오류 처리가 실제 계약과 맞는지 확인하지 않으면 fake가 현실과 달라질 수 있습니다. 외부 서비스의 샌드박스를 이용하는 테스트는 실행 횟수·계정·정리·재시도 정책을 별도로 관리하고, 일반 CI의 merge gate와 분리할지 결정합니다. “외부가 느렸다”와 “우리 재시도 로직이 잘못됐다”를 같은 실패로 처리하지 않아야 합니다.

테스트에서 내려받는 브라우저, 컨테이너 이미지, 패키지 저장소도 외부 의존성입니다. 캐시와 버전 고정은 속도를 높일 수 있지만 오래된 의존성이나 손상된 캐시가 실패 원인이 될 수 있습니다. 캐시 hit/miss, 이미지 digest, runner 버전을 로그로 남기고, 실패 때 캐시를 비운 재현 경로를 준비하면 환경 문제를 제품 문제와 분리하기 쉽습니다.

## retry는 치료가 아니라 관측 장치다

Playwright 같은 테스트 도구의 retry 기능은 일시적 실패를 포착하고 trace를 남기는 데 유용합니다. 그러나 retry 뒤 통과한 테스트를 완전한 성공으로 취급하면 실패 신호가 사라집니다. retry가 발생한 횟수, 최초 실패 시의 로그, 재시도 뒤 상태를 별도 지표로 모으고, 일정 횟수를 넘은 테스트는 원인 분석 대상이 되게 해야 합니다.

merge를 막을지 여부는 위험도에 따라 정합니다. 결제·권한·데이터 손실과 관련된 테스트는 flaky라는 이유로 오래 격리하면 안 됩니다. 반면 UI 환경의 일시적 브라우저 다운로드 오류처럼 제품 코드와 명백히 분리된 문제는 짧은 기간 quarantine할 수 있습니다. quarantine에는 소유자, 만료일, 원인 가설, 재활성화 조건을 기록합니다. 영구적으로 제외된 테스트는 품질 신호를 늘리는 것이 아니라 빚을 숨기는 결과가 됩니다.

retry 횟수를 늘리는 것보다 좋은 질문은 “첫 실패가 발생했을 때 원인을 재현할 증거가 남는가”입니다. 스크린샷, video, network log, 서버 로그, database 상태, trace ID를 상황에 맞게 남기면 재실행은 단순 통과 버튼이 아니라 비교 가능한 실험이 됩니다.

## flaky rate를 어떻게 읽을 것인가

flaky rate는 같은 테스트가 일정 기간에 실패했다가 재실행에서 통과한 비율처럼 정의할 수 있습니다. 숫자 하나로 팀을 평가하면 사람들이 재시도 기록을 숨기거나 테스트를 제외할 위험이 있습니다. 더 유용한 지표는 상위 flaky 테스트, 실패가 집중되는 runner·브라우저·시간대, 평균 복구 시간, quarantine의 만료 상태입니다.

테스트가 1,000개인데 실패가 1개라는 사실보다 그 1개가 배포를 매일 멈추는지, 중요 기능을 가리는지, 담당자가 있는지가 운영 우선순위를 정합니다. 대시보드는 실패 수를 세는 용도보다 어떤 원인군이 증가하는지와 해결 후 재발하지 않는지를 보는 용도로 만듭니다. 지표가 문제 해결 행동을 돕지 못하면 수집 비용만 늘어납니다.

## 한계와 적용 기준 Q&A

### Q. 실패한 테스트를 바로 quarantine해도 되나요?

A. 영향이 큰 흐름은 바로 제외하지 않는 편이 안전합니다. 우선 재현 정보와 소유자를 붙이고, 제품 결함 가능성을 확인합니다. 정말 환경 문제로 분리해야 한다면 만료일과 복구 기준을 둔 임시 조치로 운영합니다.

### Q. 모든 E2E 테스트를 병렬로 실행해야 하나요?

A. 병렬화는 피드백을 빠르게 하지만 공유 계정·데이터·외부 한도가 있는 환경에서는 격리 설계가 먼저입니다. 병렬 실행 가능 여부를 테스트 종류별로 정하고, 직렬화가 필요한 이유를 명시하는 편이 낫습니다.

### Q. timeout을 크게 주면 안정적이지 않나요?

A. 느린 환경에서 통과할 가능성은 높아지지만, 실제로 멈춘 작업을 더 늦게 발견하고 CI 시간을 늘립니다. 무엇을 기다리는지 조건으로 표현하고, timeout은 서비스와 환경의 허용 범위에 맞춰 설정합니다.

### Q. flaky와 실제 경쟁 조건 버그는 어떻게 구분하나요?

A. 실패 당시의 입력·로그·trace·DB 상태를 모아 같은 작업이 제품에서 재현되는지 확인합니다. 테스트 코드만 바꿔 사라졌다고 결론 내리지 말고, 제품의 동시성·멱등성 계약도 검토해야 합니다.

## 마무리

flaky test를 줄이는 가장 빠른 길은 재실행을 습관으로 만들지 않는 것입니다. 테스트마다 시작 상태·시간·순서·외부 경계를 통제하고, 실패 시 재현할 증거를 남기며, 임시 격리에는 만료일을 둡니다. 신뢰할 수 있는 실패만이 팀이 멈춰서 조사할 가치가 있습니다. CI의 녹색 표시보다 “이 실패는 실제로 무엇을 의미하는가”를 설명할 수 있는 상태가 테스트 자동화의 목표입니다.

## 실패를 재현 가능한 사건으로 바꾸는 절차

간헐 실패를 발견한 날 가장 먼저 할 일은 테스트를 지우거나 retry를 늘리는 일이 아닙니다. 실패한 실행의 커밋 SHA, 테스트 파일과 케이스 이름, 시작·종료 시각, runner 이미지, 브라우저·DB 버전, 병렬 worker 번호를 보존합니다. UI 테스트라면 스크린샷과 trace, 네트워크 실패가 있었다면 요청·응답의 메타데이터, 서버 테스트라면 해당 요청의 trace ID와 로그를 연결합니다. 개인정보나 토큰이 포함될 수 있는 원문 payload는 수집 정책에 맞게 마스킹합니다.

그 뒤 같은 커밋을 같은 환경에서 여러 번 실행해 재현 빈도를 확인합니다. 단, “열 번 중 한 번 실패”를 얻었다고 원인을 안 것은 아닙니다. 실행 순서를 고정했을 때와 섞었을 때, 단독 실행과 전체 suite 실행, 병렬 worker 수를 바꿨을 때 차이를 봅니다. 특정 앞선 테스트 뒤에만 실패하면 공유 상태를, 시간이 오래 걸린 worker에서만 실패하면 자원·timeout을, 특정 브라우저에서만 실패하면 selector·렌더링·호환성을 우선 조사할 수 있습니다.

실패를 줄이는 과정에서는 최소 재현 사례를 만듭니다. 수백 개의 fixture와 전체 API를 띄운 상태에서만 실패한다면, 어떤 데이터·요청·대기 조건이 필요한지 하나씩 걷어 냅니다. 재현 사례가 작아지면 제품 결함인지 테스트 격리 문제인지 코드 리뷰에서 논의하기 쉬워지고, 고친 뒤 회귀 테스트도 빠르게 만들 수 있습니다. 이 과정의 기록은 다음 flaky를 더 빨리 다루는 팀 자산이 됩니다.

## API와 데이터베이스 테스트의 안정성

API 테스트는 HTTP 상태 코드만 맞으면 안정적인 것처럼 보이지만, 실제로는 인증 토큰, 시간, DB 트랜잭션, 비동기 이벤트, 테스트 데이터가 결과를 바꿉니다. 테스트마다 요청 식별자와 사용자 계정을 고유하게 만들고, 응답의 생성 시각·UUID처럼 본질이 아닌 값을 전체 비교에서 제외하거나 명시적으로 검증합니다. 반대로 주문 상태·권한·금액처럼 제품 약속인 값은 느슨하게 비교하지 않습니다. 안정성을 위해 검증을 약하게 만들면 flaky는 줄어도 결함 탐지력이 사라집니다.

데이터베이스는 테스트 시작 상태를 명확히 만드는 것이 핵심입니다. migration이 완료된 빈 데이터베이스를 매 실행 준비할지, 각 케이스를 트랜잭션으로 감싸 롤백할지, 스키마·테넌트를 분리할지를 테스트 비용과 병렬성에 맞춰 결정합니다. 어느 방식을 쓰든 fixture가 이미 존재하는 행을 전제로 하지 않게 하고, cleanup 실패를 조용히 무시하지 않습니다. 특히 sequence 값이나 auto-increment ID를 정확한 숫자로 단언하면 다른 테스트 실행 순서에 따라 쉽게 흔들립니다. ID 자체가 아니라 생성된 객체의 관계와 소유권을 확인하는 편이 낫습니다.

비동기 이벤트가 DB 상태를 나중에 바꾼다면, 테스트는 이벤트가 처리됐다는 관찰 지점을 가져야 합니다. 임의의 5초 sleep 대신 특정 상태가 될 때까지 제한 시간 동안 조회하고, 초과하면 현재 상태·대기한 이벤트·관련 로그를 남깁니다. polling 간격과 timeout도 제품의 실제 처리 기대치에 맞춰야 합니다. 테스트가 지나치게 긴 timeout으로 통과한다면, 그 자체가 처리 지연 또는 관찰 설계 부족을 드러내는 신호일 수 있습니다.

## UI 자동화에서 흔들리는 지점

UI 테스트는 브라우저의 렌더링, 애니메이션, 네트워크, 로그인 리다이렉트, selector 품질을 동시에 다루기 때문에 flaky가 자주 나타납니다. 안정적인 selector는 화면 문구의 위치나 CSS class가 아니라 사용자가 인식하는 역할·레이블·고유한 test id를 바탕으로 설계합니다. 다만 test id를 무분별하게 모든 div에 붙이면 구현 구조에 결합됩니다. 버튼 클릭, 오류 메시지, 저장 완료처럼 테스트가 실제로 관찰해야 하는 요소부터 선택합니다.

페이지 이동이나 저장 뒤에는 “요청이 끝났을 것이다”라고 추측하지 말고 화면이 사용 가능한 상태가 됐는지 확인합니다. 예를 들어 저장 버튼이 다시 enabled 되었고 성공 메시지가 보이며 목록에 새 항목이 나타났는지를 조합할 수 있습니다. API 응답 하나만 기다리면 화면 렌더링이 끝나기 전에 다음 행동을 해 race condition을 만들 수 있고, 텍스트 하나만 기다리면 이전 테스트의 stale 화면을 놓칠 수 있습니다. 사용자 행동과 결과 사이의 의미 있는 상태를 기다리는 것이 핵심입니다.

로그인과 결제처럼 외부 리다이렉트가 있는 흐름은 모든 경우를 브라우저 E2E로 검증하지 않습니다. 대부분의 규칙은 API·컴포넌트 계층에서 빠르게 검증하고, UI E2E는 대표 성공 흐름과 실패 안내, 세션 복구처럼 브라우저에서만 의미 있는 위험에 집중합니다. 테스트 피라미드를 지키는 이유는 E2E가 나쁘기 때문이 아니라, 모든 규칙을 가장 느리고 불안정한 계층에 몰아넣지 않기 위해서입니다.

## 팀 프로세스: flaky를 소유하지 않으면 사라지지 않는다

flaky 테스트에는 담당 소유자가 필요합니다. 실패를 처음 본 사람이 모든 원인을 알아내야 한다는 뜻은 아니지만, 어느 팀·컴포넌트가 조사와 재활성화를 책임지는지 명확해야 합니다. CI가 실패했을 때 같은 테스트가 최근에도 재시도됐는지, 알려진 quarantine인지, 제품 결함으로 연결된 이력이 있는지를 빠르게 볼 수 있으면 “누가 다시 돌려 볼까”에서 시간을 낭비하지 않습니다.

새 테스트를 추가하는 리뷰에서는 정상 흐름뿐 아니라 격리와 시간도 봅니다. 고정 계정·고정 날짜·전역 환경 변수·고정 포트·무조건 sleep이 들어갔는지, 실패했을 때 필요한 증거가 남는지, 정리 과정이 실패를 숨기지 않는지를 체크합니다. 이 검토는 QA만의 책임이 아닙니다. 애플리케이션 설계가 시간과 외부 의존성을 주입 가능하게 만들수록 테스트도 더 결정적이 됩니다.

마지막으로 flaky 개선의 완료 기준을 정합니다. “최근 세 번 통과”는 약한 기준일 수 있습니다. 원인이 제거됐는지, 관련 테스트가 병렬·순서 변경에서도 안정적인지, retry가 발생하지 않는지, 격리했던 테스트가 실제 gate에 다시 들어왔는지를 확인합니다. 해결 후에는 원인과 예방 규칙을 짧게 남겨 같은 유형의 새 테스트가 만들어지는 것을 막습니다. 신뢰도는 한 번의 재실행이 아니라 이 반복 가능한 과정에서 회복됩니다.

## 실패 유형별 조사 질문

**데이터를 찾지 못했다**는 실패는 먼저 테스트가 어떤 데이터를 만들었는지와 그 데이터의 소유자를 확인합니다. 생성 요청이 비동기라면 조회가 너무 빨랐을 수 있고, 병렬 worker가 같은 키를 재사용했을 수 있으며, cleanup이 다른 테스트의 데이터를 지웠을 수 있습니다. 데이터베이스 쿼리와 애플리케이션 응답을 같은 trace ID 또는 고유 접두사로 연결하면 “없다”는 증상을 생성 실패·가시성 지연·잘못된 조회 조건으로 나눌 수 있습니다.

**요소를 찾지 못했다**는 UI 실패는 selector를 보기 전에 실제 페이지가 기대한 상태인지 확인합니다. 로그인 세션이 만료됐는지, 권한이 다른 계정으로 실행됐는지, 앞선 요청이 실패해 오류 화면으로 이동했는지, modal이 화면을 가리고 있는지가 원인일 수 있습니다. element가 없다는 예외만 저장하지 말고 URL, 접근성 트리의 핵심 부분, network failure, 콘솔 오류를 함께 남기면 selector 자체의 문제와 화면 상태 문제를 구분할 수 있습니다.

**timeout** 은 가장 해석하기 어려운 실패 중 하나입니다. 서버가 느렸는지, 테스트가 잘못된 조건을 기다렸는지, 이벤트가 유실됐는지, runner 자원이 부족했는지 알기 위해 기다리던 조건과 마지막 관측 상태를 출력해야 합니다. timeout을 두 배로 키운 뒤 통과했다면 문제를 해결한 것이 아니라 병목을 더 오래 허용한 것입니다. 정상 응답 시간의 분포와 서비스 목표를 기준으로 timeout을 정하고, 초과 시 어떤 신호를 수집할지 미리 설계합니다.

**간헐적인 assertion 불일치** 는 제품 경쟁 조건일 가능성을 진지하게 다뤄야 합니다. 두 요청이 동시에 같은 자원을 바꿀 수 있는지, 캐시 무효화와 조회가 엇갈리는지, 읽기 replica 지연 때문에 직후 조회가 다른 결과를 보는지 점검합니다. 테스트가 재시도 뒤 통과했다고 해서 제품 오류가 아니라고 판단하지 않습니다. 실제 사용자도 같은 순서와 시간 차이를 만들 수 있다면, 테스트는 불편한 경보가 아니라 중요한 재현 사례입니다.

## 안정성을 해치지 않는 테스트 데이터 전략

고유한 데이터는 단순히 UUID를 붙이는 것보다 수명 주기를 정하는 일이 중요합니다. 각 테스트 run에 공통 접두사를 두고 그 안에서 케이스별 키를 만들면 실패 뒤 남은 데이터를 추적하기 쉽습니다. 그러나 운영과 가까운 공유 환경에서 무제한 fixture를 쌓으면 데이터베이스 용량과 검색 결과를 오염시킬 수 있습니다. 실행이 끝난 뒤 정리하는 작업, 오래된 run을 안전하게 삭제하는 작업, 정리에 실패했을 때 알림을 보내는 작업을 함께 둡니다.

개인정보·실제 고객 데이터는 테스트 fixture로 복사하지 않습니다. 마스킹했더라도 재식별 위험과 보존 정책을 확인해야 하며, 가능하면 도메인 규칙을 만족하는 합성 데이터를 만듭니다. 테스트의 안정성과 보안은 충돌하지 않습니다. 오히려 데이터 출처·소유자·수명 주기가 분명한 fixture가 공유 상태와 규정 위반을 동시에 줄여 줍니다.

테스트 데이터가 너무 복잡해 새 기능마다 수십 개 테이블을 준비해야 한다면, fixture builder나 API 수준의 준비 경로를 검토할 수 있습니다. 다만 편의를 위해 운영 내부 테이블을 직접 수정하는 습관은 마이그레이션과 무결성 규칙을 우회할 수 있습니다. 어떤 계층에서 데이터를 만들지, 무엇을 검증하려는지에 따라 가장 작은 준비 경로를 선택합니다.

## 테스트 신뢰도를 배포 의사결정에 반영하기

CI가 배포를 막는 기준이라면 테스트 결과의 신뢰도도 배포 위험의 일부입니다. 재시도 뒤 통과한 중요 테스트가 있었는지, 현재 quarantine된 케이스가 어떤 기능을 가리는지, 최근 환경 장애가 제품 실패와 구분됐는지를 배포 화면에서 볼 수 있어야 합니다. 그렇다고 모든 경고를 배포 중단으로 연결하면 다시 무시되는 경보가 늘어납니다. 데이터 손실·보안·금전처럼 위험이 큰 영역은 엄격하게, 도구 다운로드처럼 외부 환경의 일시 오류는 별도 경로로 다루는 기준이 필요합니다.

릴리스 뒤 같은 flaky가 실제 장애로 이어졌다면 회고에는 “테스트가 있었는가”보다 “왜 그 실패 신호를 신뢰하지 않았는가”를 남깁니다. 테스트가 너무 자주 흔들렸는지, 소유자가 없었는지, 로그가 부족했는지, 우회 규칙이 만료되지 않았는지를 검토합니다. 이 질문은 비난을 위한 것이 아니라 다음에는 실제 위험을 더 빨리 구분하기 위한 것입니다. 신뢰할 수 없는 자동화는 검사 비용만 만들지만, 신뢰를 회복한 자동화는 배포 속도와 안정성을 함께 높입니다.

결국 flaky 제거는 테스트 실행 횟수를 줄이는 작업이 아니라, 실패 하나가 팀의 행동을 바꿀 수 있게 만드는 작업입니다. 그 원칙을 지키면 자동화의 속도와 신뢰도를 함께 높일 수 있습니다.

작은 불안정성도 기록하고 해결하면, 테스트는 다시 믿을 수 있는 안전망이 됩니다.

그 안전망은 실패를 숨기지 않고, 실패의 의미를 분명하게 전달합니다.

테스트 환경을 바꾸거나 runner 이미지를 올릴 때도 같은 원칙을 적용합니다. 변경 전후에 실패율, 실행 시간, retry 수를 비교하고, 특정 운영체제·브라우저에서만 변한 신호가 없는지 확인합니다. 환경 변경을 제품 변경과 분리해 기록하면 나중에 flaky가 늘었을 때 조사 범위를 빠르게 좁힐 수 있습니다. 안정성은 한 번 만든 설정이 아니라, 변경될 때마다 다시 확인하는 운영 속성입니다.
