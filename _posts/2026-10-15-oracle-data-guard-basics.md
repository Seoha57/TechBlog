중요한 데이터베이스는 백업만으로 충분하지 않을 때가 있습니다. 백업은 과거 시점으로 복구하는 데 필수지만, 주 서버 장애 뒤 마지막 백업 이후의 변경과 서비스를 다시 열기까지의 시간을 줄여 주지는 않습니다. **Oracle Data Guard** 는 Primary Database의 변경을 하나 이상의 standby database에 전달하고 적용해, 계획된 전환과 재해 복구를 지원하는 Oracle Database의 고가용성 기능입니다.

Data Guard를 “복제본 하나를 만드는 기능”으로만 이해하면 운영 판단이 어려워집니다. 어떤 변경을 어디까지 잃어도 되는지(RPO), 어느 시간 안에 서비스를 복구해야 하는지(RTO), 전환 중 애플리케이션 연결을 어떻게 바꿀지, 백업과 복구 테스트를 어떻게 나눌지가 함께 결정돼야 합니다. 이 글은 Data Guard의 구성 요소와 동작을 먼저 설명하고, 실제 운영에서 흔히 혼동하는 보호 모드·역할 전환·모니터링 기준을 정리합니다.

## 먼저 알아둘 기반 기술

Oracle Database는 데이터 파일에 변경을 바로 기록하기 전에 **redo** 라는 변경 기록을 생성합니다. redo log는 인스턴스 장애 뒤 복구에 필요한 순서와 변경을 보존하는 핵심 정보입니다. 로그 스위치가 일어나면 온라인 redo log의 내용이 archive log로 보관될 수 있으며, 이를 **archivelog mode** 라고 합니다. Data Guard는 이 redo 정보를 standby로 전달해 같은 변경을 재현합니다.

**RPO(Recovery Point Objective)** 는 장애가 나도 잃어도 되는 데이터의 최대 범위입니다. “최대 5분 전 데이터까지는 복구돼도 된다”는 요구는 5분 RPO의 예입니다. **RTO(Recovery Time Objective)** 는 서비스를 다시 사용할 수 있을 때까지 허용하는 시간입니다. 이 둘은 기술 옵션이 아니라 업무의 합의입니다. Data Guard의 전송 방식과 보호 모드, standby의 준비 상태, 애플리케이션 연결 전환 절차는 이 목표를 만족하도록 정합니다.

**재해 복구(Disaster Recovery, DR)** 는 한 서버의 프로세스 장애만이 아니라 스토리지·가용 영역·데이터센터처럼 넓은 범위의 실패를 가정하는 체계입니다. Primary와 standby를 같은 장애 영역에 두면 장비 장애에는 도움이 될 수 있어도 사이트 장애에는 취약합니다. 반대로 너무 먼 지역에 두면 네트워크 지연과 비용, 동기 전송의 영향이 커질 수 있습니다. 복제 구성은 위치와 연결 품질을 포함해 설계해야 합니다.

## Data Guard의 구성: Primary, standby, transport, apply

**Primary database** 는 애플리케이션의 쓰기 요청을 처리하는 현재 운영 데이터베이스입니다. Primary에서 생성된 redo는 Data Guard transport 서비스로 standby에 전달됩니다. **Standby database** 는 받은 redo를 적용(apply)해 Primary와 일관된 상태에 가까워지도록 유지합니다. 전송 지연은 redo가 아직 standby에 도착하지 않은 시간이고, apply 지연은 도착했지만 아직 적용되지 않은 시간입니다. 두 지연을 구분하지 않으면 네트워크 문제와 standby 처리 문제를 혼동하게 됩니다.

일반적인 구성에서 standby redo log는 Primary가 아직 archive log를 완성하기 전의 redo도 받을 수 있게 합니다. Real-Time Apply는 standby redo log에 도착한 redo를 archive 완료까지 기다리지 않고 적용할 수 있어 지연을 줄이는 데 도움을 줍니다. 하지만 이 기능을 켰다는 사실만으로 지연이 항상 작아지는 것은 아닙니다. 네트워크 대역폭, I/O 성능, redo 생성량 급증, apply process 상태를 함께 봐야 합니다.

Data Guard는 여러 standby를 둘 수 있습니다. 하나는 근거리에서 높은 보호 수준을 노리고, 다른 하나는 원거리 DR 목적으로 두는 식의 설계가 가능하지만, standby 수가 늘수록 전송 경로·관리·테스트·비용도 늘어납니다. “복제본이 많으니 안전하다”가 아니라 각 standby가 어떤 장애 시나리오를 담당하는지와 실제로 전환 가능한 상태인지가 중요합니다.

## Physical standby와 logical standby의 차이

**Physical standby database** 는 redo apply를 통해 Primary의 물리적 데이터 블록 변경을 재현하는 방식입니다. Primary와 같은 데이터베이스 구조를 유지하며, 재해 복구의 기본 선택지로 널리 사용됩니다. 복구와 역할 전환의 예측 가능성이 장점이지만, Primary와 다른 스키마로 데이터를 가공해 쓰려는 목적에는 맞지 않습니다.

**Logical standby database** 는 SQL apply를 이용해 논리적으로 변경을 재현하는 방식입니다. 특정 목적의 데이터 활용이나 구조적 차이를 고려할 수 있지만, 지원되는 데이터 형식과 작업, 운영 제약을 세밀하게 검토해야 합니다. 단순히 “읽기 전용 복제본이 필요하다”는 이유라면 물리 standby와 Active Data Guard 등 다른 선택지를 먼저 비교하는 편이 낫습니다. 실제 지원 범위는 도입할 Oracle Database 버전의 공식 문서로 확인해야 합니다.

이 구분은 성능 비교표의 문제가 아닙니다. 물리 standby는 복구와 전환을 단순하게 만드는 방향이고, 논리 standby는 적용 방식과 활용 유연성을 바꾸는 선택입니다. 요구가 “장애 때 서비스를 빠르게 열기”인지 “다른 형태로 데이터를 소비하기”인지 먼저 적으면 기술 선택이 명확해집니다.

## redo 전송 방식과 보호 모드

redo transport는 동기(synchronous) 또는 비동기(asynchronous) 방식으로 구성할 수 있습니다. 동기 전송은 Primary의 commit 경로가 standby의 확인을 기다리도록 구성해 데이터 유실 위험을 낮추는 방향입니다. 대신 네트워크 지연이나 standby 문제의 영향을 Primary 트랜잭션 지연으로 가져올 수 있습니다. 비동기 전송은 Primary의 처리 지연을 줄이는 대신 장애 순간에 standby에 도달하지 못한 redo가 있을 수 있습니다.

Data Guard의 protection mode는 대표적으로 **Maximum Performance**, **Maximum Availability**, **Maximum Protection** 으로 설명됩니다. Maximum Performance는 일반적으로 성능 영향을 최소화하는 비동기 전송을 사용해 널리 선택되며, 장애 순간의 RPO는 전송 지연 영향을 받을 수 있습니다. Maximum Availability는 정상 조건에서 동기 전송을 이용해 높은 보호를 목표로 하되, standby에 문제가 생겼을 때 Primary 가용성을 유지하기 위한 동작을 고려합니다. Maximum Protection은 데이터 유실 방지를 가장 강하게 요구하는 구성으로, 필요한 standby 확인을 받지 못하면 Primary가 계속 쓰기를 처리하지 않도록 하는 선택과 연결됩니다.

이 이름만 보고 모드를 정하면 위험합니다. 네트워크 왕복 시간, standby 장애 시 Primary를 계속 열어 둘지 여부, 업무의 데이터 손실 허용 범위, 테스트 결과를 함께 검토해야 합니다. “무조건 무손실”이라는 표현은 장애 종류와 실제 구성·전환 시점에 따라 달라질 수 있으므로, 서비스 요구를 RPO·RTO 문장으로 바꾸고 그 문장을 검증 시나리오에 넣는 편이 안전합니다.

## 계획 전환과 장애 전환은 다르다

**Switchover** 는 Primary와 standby가 모두 정상일 때 역할을 계획적으로 교환하는 작업입니다. 정기 점검, 운영 사이트 이전, DR 절차 검증에 사용합니다. 정상적인 switchover는 데이터 일관성을 유지하며 기존 Primary가 standby 역할로 전환될 수 있게 합니다. 하지만 데이터베이스 역할만 바뀐다고 애플리케이션이 자동으로 새 Primary를 사용하는 것은 아닙니다. 서비스 이름, connect descriptor, DNS·로드밸런서, 커넥션 풀 재연결을 함께 확인해야 합니다.

**Failover** 는 Primary가 사용할 수 없을 때 standby를 새 Primary로 승격하는 장애 대응입니다. 계획 전환보다 판단과 복구 작업이 더 복잡하며, 장애 시점의 redo 전송·적용 상태에 따라 데이터 손실 가능성도 검토해야 합니다. 장애 난 뒤 사람마다 다른 명령을 실행하면 split brain, 즉 두 곳에서 쓰기를 받는 위험으로 이어질 수 있습니다. 따라서 누가 Primary의 쓰기를 차단하는지, 어떤 근거로 failover를 선언하는지, 애플리케이션 트래픽을 어디로 보낼지, 옛 Primary를 어떻게 재가입시키는지를 runbook으로 합의해야 합니다.

Failover 뒤 옛 Primary를 단순히 다시 열어 쓰기 트래픽에 연결하면 안 됩니다. Data Guard는 상황에 따라 flashback과 reinstate 같은 복구 절차를 지원할 수 있지만, 가능한지 여부는 구성과 장애 시점, 보존 정책에 따라 달라집니다. 확신이 없을 때는 백업·복구 및 재구성 절차를 따르고, 두 데이터베이스가 독립적으로 쓰기를 받지 않도록 서비스 경계를 우선 통제합니다.

## Data Guard Broker와 운영 자동화의 경계

**Data Guard Broker** 는 구성의 상태를 관리하고 role transition을 수행하는 Oracle의 관리 프레임워크입니다. DGMGRL 같은 인터페이스에서 Primary·standby 관계와 보호 상태를 확인하고 표준화된 절차를 사용할 수 있습니다. 이는 사람이 여러 파라미터와 프로세스를 수동으로 맞추는 위험을 줄이는 데 도움이 됩니다.

그러나 Broker가 운영 의사결정을 대신하지는 않습니다. 예를 들어 observer와 Fast-Start Failover 같은 자동 failover 기능을 도입할 때는 네트워크 분할과 Primary 실제 장애를 구분할 기준, 잘못된 failover의 비용, 애플리케이션 연결 전환, 알림·승인 절차를 먼저 결정해야 합니다. 자동화는 반복 단계를 줄이지만, 판단 조건과 복구 책임을 명확히 했을 때만 안전해집니다.

자동화 도입 전에는 수동 절차를 한 번도 쓰지 말라는 뜻이 아닙니다. 오히려 테스트 환경에서 switchover·failover·재가입을 단계별로 수행하며 각 명령이 어떤 상태 변화를 만드는지 이해해야 합니다. 그런 다음 사람이 실수하기 쉬운 순서와 상태 확인을 Broker와 runbook으로 표준화하는 편이 좋습니다.

## 애플리케이션 연결 설계가 복구 시간을 결정한다

Data Guard 전환 후 데이터베이스가 새 Primary가 되어도 애플리케이션 커넥션 풀은 기존 주소에 연결을 시도할 수 있습니다. 이때 RTO는 데이터베이스 전환 시간만이 아니라 장애 감지, DNS·리스너·서비스 등록, 커넥션 timeout, 재시도 backoff, 읽기·쓰기 트래픽 분리 시간까지 포함합니다. DBA만의 전환 절차로 RTO를 약속할 수 없는 이유입니다.

서비스 이름과 connect descriptor는 역할 기반 서비스를 사용하도록 설계할 수 있습니다. 애플리케이션은 “서버 A”가 아니라 현재 Primary 역할을 제공하는 서비스에 연결해야 합니다. 다만 실제 연결 문자열, SCAN·로드밸런서·DNS TTL, 드라이버의 failover 옵션은 환경마다 다릅니다. 장애 시 새 연결이 얼마나 빨리 회복되는지와 기존 트랜잭션이 어떤 오류를 받는지는 반드시 실제 클라이언트로 검증해야 합니다.

쓰기 요청의 재시도도 중요합니다. 데이터베이스 연결이 끊긴 시점에는 서버가 commit을 처리했지만 응답이 애플리케이션에 도착하지 않았을 수 있습니다. 무조건 같은 요청을 재시도하면 중복 주문·중복 결제가 생길 수 있습니다. idempotency key, 업무 식별자, 중복 처리 정책을 애플리케이션과 함께 설계해야 Data Guard 전환이 업무 무결성까지 보호할 수 있습니다.

## 모니터링: 지연 숫자 하나만 보지 않는다

기본 점검에는 transport lag, apply lag, redo apply 상태, destination 오류, archive gap, standby redo log 상태가 포함됩니다. transport lag가 커지면 네트워크·전송 프로세스·destination 오류를, apply lag가 커지면 I/O·apply resource·redo 폭증·standby 상태를 분리해 봅니다. 수치가 0이 아니라고 즉시 장애라고 판단할 수는 없지만, 평소 기준선과 비교해 급격히 증가한 변화는 조사해야 합니다.

또한 standby가 열려 있다는 사실만으로 전환 준비가 끝난 것은 아닙니다. 역할 전환 가능한 상태인지, 필요한 archive log gap이 없는지, 데이터 파일·control file·flashback 설정이 복구 정책과 맞는지, 백업이 실제로 복구 가능한지 확인합니다. 경보는 단순히 지연 임계값만 두기보다 “전송이 멈춤”, “apply가 중단”, “destination 오류”, “보호 모드가 예상과 다름”처럼 행동이 필요한 상태에 연결하는 편이 좋습니다.

## 백업, 복구, 테스트를 함께 설계하기

standby는 Primary의 논리적 실수까지 자동으로 막아 주지 않습니다. 잘못된 `DELETE`나 애플리케이션 결함으로 생성된 잘못된 데이터도 redo를 통해 복제될 수 있습니다. 이 때문에 RMAN 백업, 보존 정책, point-in-time recovery, 데이터 정정 절차가 Data Guard와 별개로 필요합니다. “standby가 있으니 백업을 줄여도 된다”는 판단은 복구 목표를 오해한 결과가 될 수 있습니다.

정기 테스트는 단순히 `switchover` 성공 메시지를 보는 데서 끝내지 않습니다. 전환 전후에 쓰기·읽기 서비스가 올바른 역할에 붙는지, 애플리케이션이 연결 오류를 어떻게 처리하는지, 배치 작업이 두 번 실행되지 않는지, 모니터링과 백업 대상이 새 Primary로 바뀌는지 확인해야 합니다. 테스트 결과에는 실제 걸린 시간뿐 아니라 사람의 승인·DNS 반영·커넥션 회복에서 지연된 지점도 기록합니다.

## 한계와 적용 기준 Q&A

### Q. Data Guard를 쓰면 백업 주기를 늘려도 되나요?

A. 자동으로 그렇지 않습니다. Data Guard는 가용성과 재해 복구 시간을 줄이는 수단이며, 논리 오류·장기 보관·감사 요구를 위한 백업과 보존 정책은 별도로 설계해야 합니다. 복구 연습은 standby 전환 연습과 다르게 수행해야 합니다.

### Q. 모든 시스템에 Maximum Protection이 맞나요?

A. 아닙니다. 데이터 손실을 매우 엄격히 제한해야 하는 업무에는 검토할 수 있지만, 동기 전송과 standby 가용성 조건이 Primary 쓰기 가용성에 미치는 영향을 감수해야 합니다. 지연·장애 시의 업무 선택을 포함해 판단합니다.

### Q. Standby를 읽기 전용 조회 서버로 항상 쓸 수 있나요?

A. 구성과 Oracle 라이선스·기능 조건, 적용 방식에 따라 달라집니다. 특히 redo apply와 읽기 서비스를 동시에 사용할 수 있는지, 조회 부하가 복구 지연에 미치는 영향이 어떤지는 버전과 계약 조건을 공식 문서·라이선스 문서로 확인해야 합니다.

### Q. Failover를 자동화하면 야간 대응이 필요 없어지나요?

A. 아닙니다. 자동 failover는 감지와 역할 전환 일부를 줄일 수 있지만, 애플리케이션 오류 처리, 데이터 정합성 확인, 옛 Primary 재가입, 원인 분석은 여전히 필요합니다. 오히려 오탐 failover의 영향을 먼저 연습해야 합니다.

### Q. 가장 먼저 검증할 시나리오는 무엇인가요?

A. 정상 switchover와 애플리케이션 재연결부터 시작한 뒤, Primary 접속 불가·네트워크 단절·전송 지연·standby apply 중단을 구분해 연습하는 것이 좋습니다. 각 시나리오에서 RPO·RTO 목표를 실제로 만족하는지 측정합니다.

## 마무리

Oracle Data Guard의 가치는 standby를 하나 더 두는 데 있지 않습니다. redo 전송과 apply 상태를 이해하고, 업무의 RPO·RTO에 맞는 보호 모드를 선택하며, 데이터베이스·애플리케이션·네트워크가 함께 전환하는 절차를 검증하는 데 있습니다. 먼저 “무엇이 실패했을 때 얼마만큼의 데이터와 시간 손실을 허용할 수 있는가”를 문장으로 합의하세요. 그 문장이 있어야 Data Guard 구성과 운영 점검, 복구 훈련이 같은 목표를 향하게 됩니다.

## 구성 전 결정해야 할 질문

Data Guard 설계 문서는 제품 옵션보다 실패 시나리오에서 시작하는 편이 좋습니다. 첫 질문은 Primary의 어떤 실패를 견딜 것인가입니다. 데이터베이스 인스턴스 프로세스만 멈춘 경우에는 같은 서버의 재시작과 RAC 같은 고가용성 구성이 먼저 해결책일 수 있습니다. 반면 스토리지 손상, 사이트 정전, 리전 장애를 견디려면 물리적으로 분리된 standby와 통신 경로가 필요합니다. 하나의 기능에 모든 장애를 맡기지 않고 계층별 책임을 나누는 것이 중요합니다.

둘째는 복구 우선순위입니다. 모든 테이블과 서비스가 같은 RPO·RTO를 가져야 하는 것은 아닐 수 있습니다. 결제 원장처럼 유실 허용이 거의 없는 데이터, 조회 서비스처럼 잠시 지연돼도 되는 데이터, 재생성 가능한 캐시성 데이터는 복구 기대치가 다릅니다. 데이터베이스 단위의 보호 수준을 정할 때는 가장 엄격한 업무 요구가 전체 쓰기 경로에 미치는 영향도 함께 검토합니다. 업무별 요구 차이가 크다면 별도 데이터 경계나 서비스 설계가 필요한 신호일 수 있습니다.

셋째는 책임자와 의사결정입니다. Primary가 응답하지 않는다고 해서 즉시 failover하는 것이 항상 올바른 것은 아닙니다. 네트워크 단절로 Primary가 살아 있지만 관찰 지점에서만 보이지 않을 수 있기 때문입니다. 누가 장애 선언을 하고, 어떤 모니터링 근거를 확인하며, Primary의 쓰기를 어떻게 차단할지, 변경 승인 없이 자동 전환을 허용할 상황은 무엇인지를 운영 문서에 적습니다. 이 질문에 답하지 못하면 기술 구성이 좋아도 실제 장애에서 판단이 늦어집니다.

## 로그 전송 지연을 해석하는 방법

redo 전송과 적용이 밀렸다는 알림을 받았을 때는 하나의 숫자를 줄이려 하기보다 어느 구간에서 병목이 생겼는지 나눕니다. Primary에서 redo 생성량이 평소보다 늘었는지 확인합니다. 대량 배치, 인덱스 작업, 데이터 적재, 통계 작업처럼 합법적인 작업도 일시적으로 많은 redo를 만들 수 있습니다. 생성량이 정상인데 transport lag가 늘면 네트워크 연결, destination 상태, archive 전송 프로세스 오류를 살핍니다.

transport는 정상인데 apply lag만 늘면 standby의 I/O, CPU, apply 프로세스 상태, datafile 복구 오류를 검토합니다. 조회 부하가 standby 자원을 점유하고 있거나, archive gap이 생겼거나, 특정 로그 파일 접근에 문제가 있을 수 있습니다. 이때 lag를 강제로 0으로 만들겠다는 목표보다, 현재 적용 중인 로그와 대기 중인 로그, 오류 메시지, 복구 가능성을 정확히 파악하는 것이 먼저입니다. 무리한 프로세스 재시작은 조사 단서를 잃게 하거나 상태를 더 복잡하게 만들 수 있습니다.

경보 기준에는 절대 시간뿐 아니라 추세를 넣습니다. 야간 배치가 매일 10분 정도 지연을 만들지만 곧 회복되는 패턴이라면 0이 아닌 값을 항상 경보로 만들 필요는 없습니다. 반대로 평소 0초이던 전송 지연이 2분으로 계속 증가하고 destination 오류가 동반되면 작은 수치여도 즉시 조사해야 합니다. 업무의 허용 RPO를 넘는 예상 시점과 현재 상승 속도를 보여 주면 담당자가 우선순위를 더 잘 판단할 수 있습니다.

## 전환 연습에서 확인할 애플리케이션 항목

switchover 훈련에서는 데이터베이스 명령의 성공 여부보다 사용자 기능의 회복을 확인해야 합니다. 우선 기존 연결이 끊겼을 때 웹·배치·ETL·관리 도구가 어떤 오류를 내는지 기록합니다. 새 Primary에 대한 새로운 연결이 열리는 시간, 커넥션 풀의 재시도 횟수와 timeout, 읽기 전용 트래픽이 잘못된 인스턴스로 가지 않는지를 확인합니다. 이 결과가 실제 RTO의 일부입니다.

다음은 진행 중인 작업입니다. 전환 시점에 실행 중이던 트랜잭션은 성공, 롤백, 불확실한 결과 중 무엇을 보일 수 있는지 애플리케이션 팀이 알아야 합니다. 결제·주문·메시지 발행처럼 한 요청이 여러 시스템을 바꾸는 업무는 요청 식별자와 조회 API를 이용해 결과를 재확인하는 절차가 필요합니다. 단순한 자동 재시도보다 “이미 처리됐는가”를 판별하는 업무 키가 중요합니다.

마지막은 주변 시스템입니다. 백업 작업, 모니터링 대상, 리포트 배치, 데이터 적재, 권한 점검, DB 링크가 역할 전환 후에도 올바른 대상에 연결되는지 봅니다. 특히 사람의 노트북에 저장된 고정 접속 문자열이나 오래된 배치 설정은 실제 전환에서 뒤늦게 발견되기 쉽습니다. 훈련 결과를 체크리스트로 남기고 다음 훈련에서 같은 항목을 반복 확인해야 RTO가 개인의 숙련도에 의존하지 않습니다.

## 보안과 변경 관리

Data Guard 구성에는 데이터베이스 간 통신과 관리자 권한이 필요합니다. redo transport에 사용하는 네트워크 경로, 암호화·인증 설정, 비밀 정보의 보관 위치, 관리자 계정의 사용 범위를 최소 권한 원칙으로 검토합니다. 재해 복구를 이유로 보호가 약한 별도 접속 경로를 만들면 평상시 보안 경계가 약해질 수 있습니다. DR 환경도 운영 환경과 같은 수준의 접근 통제와 감사가 필요합니다.

파라미터 변경과 패치도 Primary·standby 쌍으로 평가합니다. 한쪽만 패치하거나 설정을 바꾸면 전송·apply·역할 전환 가능성에 영향을 줄 수 있습니다. 변경 전에는 Oracle의 해당 버전 지원 문서를 확인하고, 적용 순서·롤백 방법·전환 가능 여부를 정합니다. 변경 후에는 단순 접속 확인을 넘어 redo 전송·apply·서비스 연결·경보가 정상인지 검증합니다.

## 테스트 결과를 서비스 목표로 바꾸기

DR 테스트는 “성공했다”는 한 줄보다 관측값을 남겨야 다음 설계 개선으로 이어집니다. Primary 쓰기 중단 시각, standby 승격 시각, 애플리케이션 최초 성공 요청 시각을 분리해 기록하면 데이터베이스 전환과 서비스 복구의 차이를 알 수 있습니다. 예상보다 오래 걸렸다면 그 시간이 승인 절차 때문인지 DNS 전파인지 커넥션 timeout인지 나눠 개선할 수 있습니다.

데이터 검증도 샘플 쿼리 하나로 끝내지 않습니다. 전환 직전의 업무 식별자를 정해 쓰기 결과가 새 Primary에 존재하는지, 시퀀스·배치 상태·미완료 작업이 기대대로 이어지는지 확인합니다. 다만 운영 데이터에 불필요한 테스트 거래를 만들지 않도록 사전에 테스트 키와 정리 절차를 정합니다. DR 훈련 자체가 데이터 품질 사고가 되지 않게 하는 것이 중요합니다.

이렇게 쌓인 결과는 다음 투자 판단의 근거가 됩니다. 요구 RTO를 충족하지 못했다면 단순히 더 강한 보호 모드로 바꾸기보다 어느 단계가 느렸는지 먼저 봅니다. 요구 RPO가 너무 엄격해 동기 전송의 지연을 감당하기 어렵다면 업무 담당자와 허용 범위를 다시 합의합니다. Data Guard는 설정 화면에서 끝나는 제품 기능이 아니라, 복구 목표를 측정하고 개선하는 운영 체계입니다.

## 운영 문서에 남길 최소 정보

사고가 났을 때 담당자가 알아야 할 정보는 긴 제품 설명보다 현재 구성을 빠르게 판단할 수 있는 사실입니다. Primary와 각 standby의 역할·서비스 이름·접속 경로, protection mode, transport와 apply의 정상 기준선, 마지막 정상 전환 시험 일시, 담당자와 승인 경로를 한 문서에서 확인할 수 있어야 합니다. 이 정보가 여러 위키와 개인 메모에 흩어져 있으면 장애 시간에 오래된 설정을 따라갈 위험이 큽니다.

runbook은 명령 목록만 적지 않습니다. 각 단계의 **진입 조건** 과 **중단 조건** 을 적습니다. 예를 들어 failover 전에는 Primary의 쓰기 트래픽이 차단됐다는 근거를 확인하고, standby가 전환 가능한 상태인지 점검하며, 전환 뒤에는 애플리케이션의 쓰기·읽기·배치 세 경로를 확인합니다. 예상과 다른 오류가 보이면 다음 명령을 무조건 실행하지 않고 누구에게 판단을 넘길지도 명시합니다. 이런 분기는 문서가 길어서가 아니라, 데이터 무결성 사고를 막기 위해 필요합니다.

모니터링 알림에는 링크와 맥락을 넣습니다. “apply lag 높음”만 알리는 대신 현재 transport lag, apply lag, destination 오류, 최근 redo 생성량, 해당 구성의 RPO 목표를 함께 볼 수 있으면 야간 대응에서도 조사 방향을 빨리 잡을 수 있습니다. 경보를 받은 사람이 매번 쿼리를 새로 찾아야 한다면 자동화된 모니터링의 이점이 줄어듭니다.

## 비용과 용량을 놓치지 않는다

standby는 라이선스와 서버 수만 늘리는 구성이 아닙니다. redo 전송을 위한 네트워크 대역폭, archive log 보관 공간, standby redo log와 datafile의 스토리지, 백업 대상, 모니터링·운영 인력까지 고려해야 합니다. Primary의 대량 적재·배치 작업이 redo를 얼마나 생성하는지 모르면 standby의 저장소가 예상보다 빨리 차거나 apply가 장시간 뒤처질 수 있습니다. 용량 계획에는 평상시 평균뿐 아니라 월말·마이그레이션·복구 작업의 피크를 포함합니다.

원거리 DR에서는 회선 장애와 비용도 설계 변수입니다. 동기 전송의 왕복 시간이 업무 응답 시간에 미칠 영향을 부하 시험으로 확인하고, 비동기 전송을 선택했다면 장애 때 어느 정도의 데이터 차이가 남을 수 있는지 이해관계자에게 명확히 알립니다. 비용을 줄이려 standby를 너무 작게 만들면 평상시 apply 지연과 장애 시 전환 실패라는 더 큰 비용으로 돌아올 수 있습니다.

## Data Guard를 피하거나 보완해야 하는 경우

단일 인스턴스 장애만 빠르게 넘기려는 요구에는 로컬 고가용성 구성이 더 단순할 수 있습니다. 반대로 여러 서비스가 서로 다른 DBMS와 메시지 시스템을 함께 사용한다면 Oracle Data Guard만으로 전체 업무의 일관된 재해 복구를 보장할 수 없습니다. 데이터베이스 전환과 애플리케이션 배포, 큐 소비자, 외부 결제의 처리 상태를 함께 설계해야 합니다.

또한 사람이 논리적으로 잘못 입력한 값을 빠르게 되돌려야 하는 요구에는 독립 백업, 보존 정책, 감사 로그, 승인 절차가 더 직접적인 해법일 수 있습니다. Data Guard는 Primary의 변경을 성실히 전파하는 기술이므로, 올바른 변경과 잘못된 변경을 스스로 구분하지 않습니다. 기능의 경계를 이해할수록 복구 체계 전체를 과신하지 않게 됩니다.

## 역할 전환 전 체크리스트

계획된 switchover 직전에는 업무 변경을 잠시 제한하고, Primary와 standby의 health를 같은 시점에 확인합니다. 적용되지 않은 gap이나 destination 오류가 있으면 먼저 원인을 해결합니다. 실행 중인 장기 배치와 대량 적재가 있는지도 확인합니다. 전환 명령 자체는 짧게 끝나더라도, 그 사이에 만들어진 업무 요청을 어떤 시스템이 처리할지 애플리케이션 담당자와 합의하지 않으면 전환 뒤의 데이터 검증이 어려워집니다.

전환 중에는 명령 출력뿐 아니라 서비스 관점의 시간표를 기록합니다. 기존 Primary의 쓰기를 중지한 시각, 새 Primary가 열렸다고 확인한 시각, 첫 애플리케이션 쓰기 성공 시각을 남기면 다음 훈련에서 개선 대상을 찾을 수 있습니다. 전환 뒤에는 새 standby가 정상적으로 redo를 받는지도 확인합니다. 역할이 바뀐 두 데이터베이스가 모두 올바른 상태라는 확인이 있어야 훈련이 끝납니다.

## 장애 선언 후의 우선순위

Primary 장애가 의심될 때는 먼저 업무 트래픽이 어느 곳에 쓰이고 있는지 통제합니다. 모니터링 화면 하나가 응답하지 않는다는 이유만으로 standby를 승격하면, 실제 Primary가 살아 있는 네트워크 분할 상황에서 두 쓰기 지점이 생길 수 있습니다. 가능한 관찰 경로를 교차 확인하고, 확실하지 않을 때는 Primary의 쓰기 경로를 차단하는 조치를 우선합니다.

그 다음에는 데이터 손실 가능성과 서비스 중단 비용을 의사결정권자에게 같은 언어로 전달합니다. “standby가 30초 늦다”보다 “마지막 30초의 committed transaction이 새 Primary에 없을 수 있다”가 업무 판단에 도움이 됩니다. 이 설명은 사고 중 새로 만들기 어렵기 때문에, 정상 시에 protection mode와 예상 RPO를 문서화해 두어야 합니다.

## 관리자 권한과 감사

Data Guard 전환 권한은 일상적인 조회 권한과 분리하는 것이 좋습니다. 비상 상황을 이유로 공유 관리자 계정을 사용하면 누가 어떤 전환·설정 변경을 했는지 추적하기 어렵습니다. 개인 계정, 최소 권한, 명령 감사, 비상 접근 절차를 정하고 정기 훈련에서도 같은 경로를 써야 실제 사고에 익숙한 절차가 됩니다.

운영 문서와 로그에는 접속 비밀번호, 개인 식별 정보, 전체 connect descriptor를 무분별하게 남기지 않습니다. 장애 분석에 필요한 구성 식별자와 상태 정보는 보존하되 비밀 정보는 안전한 비밀 관리 도구에서 참조하게 합니다. 재해 복구는 가용성 기능이지만, 복구 과정에서 보안 경계가 약해지지 않게 하는 것도 같은 수준의 요구입니다.
