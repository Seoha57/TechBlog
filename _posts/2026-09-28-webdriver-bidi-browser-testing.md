주문 버튼을 누른 뒤 화면에 “완료”가 보인다고 해서 테스트가 모두 끝난 것은 아닙니다. 브라우저가 결제 API(Application Programming Interface, 프로그램이 서버 기능을 호출하는 접점)에 요청을 두 번 보냈을 수도 있고, 화면은 정상처럼 보이지만 JavaScript(웹페이지 동작을 구현하는 프로그래밍 언어) 오류가 콘솔에 남았을 수도 있습니다. 새 창에서 인증을 마친 뒤 원래 탭으로 돌아오는 흐름도 최종 문구 하나만 검사하면 중간 실패를 놓치기 쉽습니다. 이런 문제를 조사할 때 개발자 도구를 사람 손으로 열어 네트워크와 콘솔을 확인하곤 합니다. 자동 테스트도 같은 종류의 사건을 시간 순서대로 받을 수 있다면, 화면 밖에서 벌어진 실패를 더 분명하게 설명할 수 있습니다.

**WebDriver BiDi(Bidirectional WebDriver, 양방향 웹드라이버)** 는 테스트 프로그램과 브라우저 사이에 양방향 통신을 추가하는 브라우저 자동화 프로토콜입니다. WebDriver는 브라우저를 조작하는 공통 명령 규약입니다. 테스트가 명령을 보내고 응답을 기다리는 것에 더해, 브라우저가 네트워크 요청·응답, 콘솔 메시지, 스크립트 오류, 탭 생성 같은 이벤트를 발생한 시점에 보내도록 합니다. WebDriver를 만든 W3C(World Wide Web Consortium, 웹 표준을 논의하는 국제 단체)의 작업 초안으로 발전 중이며, 브라우저와 자동화 도구의 실제 지원 범위는 계속 바뀝니다. 따라서 표준 문서에 기능이 있다고 해서 모든 브라우저·언어 바인딩에서 동일하게 쓸 수 있다고 가정하면 안 됩니다.

이 글은 Selenium(여러 브라우저를 자동 조작하는 도구 모음)의 공개 문서와 W3C 명세를 바탕으로 동작과 적용 기준을 정리한 학습 글입니다. 특정 사이트에서 직접 측정한 속도나 안정성 결과가 아닙니다. 예시는 테스트 설계의 형태를 보여 주며, 실제 코드에 옮길 때는 사용하는 브라우저·드라이버·Selenium 버전의 API를 확인해야 합니다.

## 먼저 알아둘 기반 기술: 브라우저, WebDriver, 이벤트, WebSocket

브라우저 자동화 테스트는 사람이 주소를 입력하고 버튼을 누르는 과정을 프로그램이 대신 수행하게 하는 방법입니다. 테스트 프로그램은 브라우저 프로세스를 직접 조작하는 대신 **WebDriver**라는 표준 인터페이스를 통해 탐색, 클릭, 입력, 요소 찾기 같은 명령을 전달할 수 있습니다. Selenium은 여러 언어에서 WebDriver를 사용하게 해 주는 자동화 도구 모음입니다. 브라우저 자체와 테스트 라이브러리, 그 사이의 통신 규약은 서로 다른 층입니다. 테스트 코드에서 Selenium 메서드를 호출하면 그 아래에서 브라우저와 드라이버가 명령을 처리한다고 생각하면 됩니다.

기존 WebDriver의 기본 모델은 요청과 응답입니다. 예를 들어 “버튼을 클릭하라”는 명령을 보내고 성공 또는 오류 응답을 받은 다음, “완료 문구를 찾아라”는 명령을 보냅니다. 단계가 순서대로 진행되므로 대부분의 화면 조작에는 이해하기 쉽고 안정적인 모델입니다. 하지만 버튼을 누르는 사이 브라우저가 서버에 어떤 요청을 보냈는지, 콘솔에 어떤 오류가 찍혔는지는 별개의 비동기 사건입니다. 테스트가 매 순간 브라우저에 “방금 새 오류가 있었나요?”라고 묻는 방식만으로는 발생 시점과 순서를 다루기 어렵습니다.

**이벤트(event)** 는 시스템에서 어떤 일이 발생했다는 알림입니다. 네트워크 요청 시작, 응답 완료, 스크립트 오류, 새 탭 생성이 예입니다. **구독(subscription)** 은 특정 종류의 이벤트가 생길 때 전달해 달라고 등록하는 행위입니다. 이벤트를 구독한 뒤 사용자 동작을 실행하면, 테스트는 결과 화면과 함께 그 동작 중 일어난 사건을 모을 수 있습니다. 구독 이전에 이미 발생한 사건은 원칙적으로 관찰 대상이 아닐 수 있으므로, 테스트에서 등록 순서가 중요합니다.

**WebSocket**은 하나의 연결에서 양쪽이 메시지를 주고받을 수 있게 하는 통신 방식입니다. 일반적인 HTTP(Hypertext Transfer Protocol, 웹 요청과 응답에 쓰는 통신 규약) 요청·응답만으로는 브라우저가 사건이 생길 때마다 테스트 프로그램에 바로 메시지를 보내기 불편합니다. WebDriver BiDi는 세션에서 제공하는 WebSocket 연결을 이용해 명령, 응답, 이벤트를 전달합니다. 여기서 “양방향”은 버튼 클릭 명령을 역순으로 실행한다는 뜻이 아니라, 테스트가 브라우저에 명령을 보낼 때 브라우저도 비동기 사건을 테스트에 전달할 수 있다는 뜻입니다.

## 왜 새 프로토콜이 필요했나

화면 요소를 찾아 클릭하는 검증만으로는 현대 웹 애플리케이션의 실패 원인을 모두 설명하기 어렵습니다. 검색창에 문자를 넣으면 추천 API가 연속 호출되고, 결제 버튼은 외부 인증 탭을 열 수 있으며, 화면은 사용자에게 보이지 않는 곳에서 실시간 연결을 유지합니다. 결과 문구는 같아도 네트워크 요청 횟수, 오류 처리, 새 탭 연결 상태가 다르면 실제 사용자 경험과 운영 결과는 달라집니다. QA(Quality Assurance, 품질 보증) 담당자는 오류가 보이지 않는 화면을 보고도 로그와 네트워크를 다시 열어 원인을 추적해야 했습니다.

브라우저별 개발자 도구 프로토콜을 이용하는 길도 있습니다. **CDP(Chrome DevTools Protocol, 크롬 개발자 도구 프로토콜)** 는 Chrome(구글의 웹 브라우저) 계열 브라우저의 네트워크·콘솔·성능 데이터에 접근할 수 있게 합니다. Chrome만 대상으로 한다면 유용하지만, 같은 테스트를 Firefox 등 다른 브라우저에 적용할 때는 별도 구현이나 조건 분기가 필요해질 수 있습니다. W3C의 BiDi 작업은 이벤트 중심 자동화를 브라우저 간 공통 언어로 설명하려는 시도입니다. 표준화의 목표와 현재 모든 기능의 완전한 상호 운용성은 다른 문제이므로, 도입 판단은 실제 지원 표를 기준으로 해야 합니다.

비슷한 이름의 도구를 혼동하지 않는 것도 중요합니다. Playwright나 Puppeteer는 자체 API와 브라우저 연결 방식을 제공하는 자동화 도구입니다. WebDriver BiDi는 그런 테스트 프레임워크를 통째로 대체하는 제품명이 아니라 프로토콜입니다. Selenium을 쓰는 팀은 BiDi 지원 API를 Selenium 테스트에 추가할 수 있고, 다른 도구는 자체 방식으로 같은 문제를 풀 수 있습니다. 도구를 선택할 때는 팀의 기존 언어·브라우저 범위·테스트 인프라와 필요한 이벤트 기능을 함께 보아야 합니다.

## 세션 안에서 명령과 이벤트는 어떻게 흐르나

테스트는 먼저 브라우저 세션을 열고 BiDi 연결을 요청합니다. Selenium 문서에는 브라우저 옵션에서 `webSocketUrl` 기능을 활성화하는 예가 있습니다. 브라우저와 드라이버가 이를 지원하면 세션에 WebSocket 주소가 제공되고, 라이브러리가 그 연결을 관리합니다. 테스트 작성자가 WebSocket 프레임을 직접 만들 필요는 없는 경우가 많습니다. 다만 연결을 켰다는 사실만으로 모든 이벤트가 자동 저장되는 것은 아닙니다. 관심 있는 이벤트를 구독하고, 끝날 때 구독을 해제해야 합니다.

예를 들어 주문 제출 검증은 `network.beforeRequestSent`처럼 요청 시작을 나타내는 이벤트와 `network.responseCompleted`처럼 응답 완료를 나타내는 이벤트를 구독한 뒤 버튼을 누르는 흐름으로 생각할 수 있습니다. 테스트는 수신한 사건 중 주문 API 경로와 관련된 것만 골라 요청 횟수와 응답 상태를 확인합니다. 이벤트 이름은 프로토콜 층의 표현이며, Selenium의 언어별 고수준 메서드명은 다를 수 있습니다. 명세의 이벤트 이름을 테스트 코드의 메서드명으로 그대로 추측하지 않는 편이 안전합니다.

브라우저는 여러 탭과 프레임을 동시에 다룹니다. BiDi 명세의 **browsing context(탐색 컨텍스트)** 는 탭이나 프레임처럼 문서가 표시되는 환경을 식별하는 개념입니다. 같은 주소로 나간 요청이라도 광고 프레임이 보낸 것과 결제 화면 탭이 보낸 것은 의미가 다릅니다. 이벤트에서 대상 컨텍스트를 함께 확인하면 “어떤 화면의 어떤 동작에서 발생했는가”를 구분할 수 있습니다. 이 식별자를 무시하면 다른 탭의 배경 요청을 현재 테스트의 실패로 오해할 수 있습니다.

시간 순서도 설계의 일부입니다. 구독을 시작하기 전에 클릭하면 클릭 직후의 요청을 놓칠 수 있고, 클릭 후 무조건 3초만 기다리면 느린 환경에서는 응답이 늦어 실패하며 빠른 환경에서는 불필요하게 기다립니다. 의미 있는 종료 조건은 “관련 요청이 한 번 시작되고 그 요청의 완료 이벤트가 왔다”처럼 사건과 연결돼야 합니다. 요청이 전혀 시작되지 않는 경우를 위한 제한 시간도 필요합니다. 시간 제한은 영원히 대기하는 테스트를 막는 안전장치이지, 성공을 대신 증명하는 값이 아닙니다.

## 업무 예시: 결제 버튼의 중복 요청 찾기

한 쇼핑몰의 결제 버튼은 한 번 클릭하면 주문 생성 요청을 한 번만 보내야 한다고 가정해 봅시다. 화면에는 “주문 접수”가 한 번만 뜨지만, 사용자가 버튼을 연속해서 누르거나 재시도 코드가 중복 동작하면 서버에는 요청이 두 번 갈 수 있습니다. 이런 경우 화면 텍스트 검사만으로는 핵심 결함을 놓칩니다. 테스트는 먼저 주문 생성 경로와 HTTP 메서드를 정하고, 버튼 클릭 전에 네트워크 이벤트 구독을 시작합니다.

검증 절차는 다음처럼 정리할 수 있습니다. 예시는 특정 Selenium 언어 바인딩의 실행 코드가 아니라 테스트 조건을 표현한 의사 코드입니다.

```text
주문 생성 요청 시작 이벤트를 구독한다
결제 버튼을 한 번 클릭한다
해당 탭에서 POST /api/orders 요청이 완료될 때까지 기다린다
동일한 사용자 동작에 속한 POST /api/orders 요청 수가 1인지 확인한다
응답 결과와 화면의 주문 번호가 서로 맞는지 확인한다
구독을 해제한다
```

여기서 요청 수만 보면 안 됩니다. 네트워크가 끊겼다가 클라이언트가 자동 재시도한 경우, 중복 요청이지만 서버가 멱등성 키를 사용해 하나의 주문만 생성했을 수 있습니다. 반대로 요청은 하나지만 서버가 실패를 반환했고 화면이 오래된 성공 상태를 보여 줄 수도 있습니다. **멱등성(idempotency)** 은 같은 작업을 다시 보내도 의도치 않은 추가 결과가 생기지 않게 하는 성질입니다. 결제에서는 테스트가 “요청은 정확히 한 번인가”, “같은 키로 재시도해도 주문은 하나인가”, “사용자에게 결과가 올바르게 보이는가”를 나누어 확인해야 합니다. BiDi는 첫 번째와 두 번째 질문에 필요한 브라우저 측 증거를 제공하지만 서버 데이터의 진실을 대신하지는 않습니다.

요청 URL(Uniform Resource Locator, 웹 주소)에 동적으로 붙는 식별자나 추적 매개변수도 주의해야 합니다. 전체 URL 문자열을 고정해서 비교하면 정상적인 환경 차이 때문에 깨집니다. 메서드, 경로, 필요한 헤더와 본문 필드처럼 계약에 중요한 부분만 비교하고, 주문 번호 같은 동적 값은 응답과 화면 사이의 관계를 확인하는 데 사용합니다. 네트워크 이벤트에 토큰이나 개인정보가 포함될 수 있으므로 실패 로그에 요청 본문 전체를 무조건 저장하지 않는 것도 기본입니다.

## 콘솔과 스크립트 오류를 품질 신호로 쓰기

브라우저 콘솔은 개발자가 남긴 진단 메시지와 실행 오류를 보여 줍니다. BiDi의 로그 관련 이벤트를 구독하면 특정 사용자 여정에서 발생한 JavaScript 예외나 콘솔 메시지를 테스트 결과에 연결할 수 있습니다. 예를 들어 상품 상세에서 장바구니 버튼을 누른 뒤 화면은 정상으로 보이지만, 추천 상품 위젯이 예외를 냈다면 그 사건을 기록할 수 있습니다. 오류가 결제 기능과 직접 관련이 없어도 새로운 배포에서 시작된 문제인지 알아보는 단서가 됩니다.

다만 `console.error` 한 줄을 곧바로 전체 테스트 실패로 연결하는 정책은 신중해야 합니다. 외부 분석 스크립트, 브라우저 확장, 개발 환경의 의도된 경고가 섞일 수 있습니다. 먼저 테스트가 소유한 도메인과 컨텍스트에서 나온 메시지인지, 같은 코드가 반복 발생하는지, 사용자 여정의 주요 기능과 관련되는지 분류합니다. 회귀 테스트에서는 새 오류의 수와 종류를 기록하고, 품질 기준이 정리된 뒤 명확한 오류만 차단 조건으로 삼을 수 있습니다. “콘솔이 조용하다”는 것이 모든 비즈니스 동작이 맞다는 뜻도 아닙니다.

오류를 재현할 때는 메시지만 남기지 말고 사용자 동작 단계와 함께 묶어야 합니다. 로그인 전부터 발생한 경고인지, 쿠폰 버튼을 누른 직후 발생한 예외인지에 따라 조사 방향이 달라집니다. 여러 탭을 열었다면 해당 이벤트의 컨텍스트도 기록합니다. 테스트 실패 메시지에 “쿠폰 적용 클릭 후, 결제 탭에서, 주문 관련 스크립트 예외 발생”처럼 맥락을 남기면 원인을 찾는 시간이 줄어듭니다. 반면 콘솔에 있는 사용자 입력·토큰을 그대로 출력하면 테스트 로그 자체가 정보 노출 경로가 될 수 있습니다.

## 새 탭과 팝업을 관찰하는 경우

사내 시스템이 외부 인증 페이지를 새 탭으로 열고 완료 후 원래 화면으로 돌아온다고 가정합시다. 테스트가 새 탭의 표시 여부만 검사하면 잘못된 도메인으로 이동했거나 인증 후 원래 세션과 연결되지 않은 문제를 놓칠 수 있습니다. 탐색 컨텍스트 생성과 이동 이벤트를 활용하면 어떤 탭이 언제 생성됐고 어떤 주소로 이동했는지 추적할 수 있습니다. 이때 주소 검증은 전체 쿼리 문자열보다 허용된 호스트와 예상 경로를 중심으로 해야 합니다. 인증 코드처럼 일회성 값은 테스트 보고서에 저장하지 않습니다.

하지만 팝업을 검증하는 모든 테스트에 BiDi가 필수인 것은 아닙니다. 새 창으로 전환해 제목과 URL을 확인하고 다시 원래 창으로 돌아오는 정도는 기존 WebDriver의 창 핸들로도 가능합니다. BiDi가 필요한 시점은 “새 탭이 생성된 순간을 놓치지 않아야 한다”, “여러 탭의 네트워크와 로그를 구분해야 한다”, “리디렉션 경로의 사건을 수집해야 한다”처럼 이벤트 자체가 검증 대상이 될 때입니다. 단순한 창 전환 테스트라면 기존 API가 더 읽기 쉽습니다.

## 네트워크 가로채기와 관찰은 다른 작업이다

네트워크 이벤트를 받는 것과 응답을 바꾸는 것은 다릅니다. **관찰**은 실제 요청과 응답을 기록해 제품이 어떻게 동작했는지 확인하는 일입니다. **가로채기(interception)** 는 요청이나 응답을 중간에서 지연·수정·차단해 조건을 만드는 일입니다. BiDi 명세와 Selenium 문서는 네트워크 관련 기능을 다루지만, 어떤 조작이 특정 브라우저에서 동작하는지는 별도로 확인해야 합니다. 제품의 실제 API 계약을 확인하는 테스트에서는 가로챈 가짜 응답을 사용하면 중요한 결함을 숨길 수 있습니다.

예를 들어 “재고 없음” 화면을 검증하려고 항상 서버 응답을 가짜로 바꾸면 프런트엔드의 오류 화면은 확인할 수 있습니다. 하지만 실제 서버가 재고 없음 상태를 올바른 상태 코드와 본문으로 반환하는지는 검증하지 못합니다. 따라서 테스트 목적에 맞춰 가짜 응답을 쓰는 화면 단위 검증과 실제 백엔드를 연결한 계약·통합 검증을 구분합니다. 요청을 지연해 로딩 상태를 확인할 때도 지연 시간이 테스트의 본질인지, 아니면 특정 이벤트까지 기다리면 되는지 먼저 따져 봅니다.

외부 서비스 장애를 재현할 때는 범위를 좁힙니다. 결제 승인 API 한 경로만 지연하거나 실패시키고, 다른 정적 파일과 인증 요청은 정상 흐름을 유지해야 원인과 결과가 선명해집니다. 가로채기 규칙을 테스트 종료 때 해제하지 않으면 다음 테스트가 이전 실패 조건을 이어받을 수 있습니다. 자동화 코드에서는 구독과 가로채기를 만든 시나리오가 정리까지 책임지게 하고, 병렬 실행에서는 세션과 탭 범위를 명확히 해야 합니다.

## 도입할 때 확인할 호환성과 운영 비용

가장 먼저 테스트가 실제로 사용하는 조합을 적습니다. 브라우저 종류와 버전, 드라이버, Selenium 언어 바인딩, 원격 브라우저를 제공하는 Grid(여러 실행 컴퓨터에 브라우저 테스트를 분산하는 Selenium 구성 요소)나 클라우드 서비스가 각각 BiDi 연결을 지원해야 합니다. 로컬에서는 되지만 원격 환경의 프록시가 WebSocket 연결을 넘기지 못하면 CI(Continuous Integration, 코드 변경마다 자동 검증하는 과정)에서는 실패할 수 있습니다. 이때 페이지 로딩 문제로 오인하지 않도록 세션 생성 결과와 WebSocket 연결 오류를 분리해서 진단합니다. 표준 명세의 존재만으로 배포 환경 전체의 지원이 보장되지는 않습니다.

두 번째는 이벤트 양입니다. 상품 목록을 열면 이미지, 글꼴, 분석 요청까지 많은 네트워크 사건이 생깁니다. 모든 사건의 전체 본문을 테스트 보고서에 저장하면 결과를 읽기 어렵고 민감 데이터가 남을 수 있습니다. 처음에는 한 사용자 동작, 한 탭, 한 API 경로처럼 좁은 범위에서 필요한 속성만 수집합니다. 실패할 때만 추가 정보를 남기고 성공 때는 간단한 요약을 남기는 정책도 가능합니다. 다만 조사에 필요한 식별자와 시간 정보까지 없애면 사건의 순서를 재구성하기 어려워집니다.

세 번째는 테스트의 책임 범위입니다. “화면에 주문 완료가 보인다”는 최종 사용자 결과, “POST가 한 번 전송된다”는 브라우저 행동, “DB(Database, 데이터를 저장하는 시스템)에 주문 한 건이 있다”는 서버 상태입니다. BiDi를 붙였다고 세 층이 하나의 검증으로 합쳐지는 것은 아닙니다. 각 층의 실패 원인과 데이터 소유자가 다르므로 중요한 업무 흐름에서는 필요한 층을 골라 별도 주장으로 적습니다. 반대로 모든 테스트가 네트워크·콘솔·DB를 다 확인하면 유지 비용이 커집니다. 위험이 큰 주문 생성, 결제, 인증 같은 시나리오부터 적용하는 편이 합리적입니다.

## 마무리

WebDriver BiDi는 브라우저를 조작하는 테스트에 브라우저가 스스로 보내는 사건을 연결합니다. 명령과 응답만으로 충분했던 화면 조작은 그대로 두고, 네트워크 요청 횟수, 스크립트 오류, 새 탭 생성처럼 시간 순서가 중요한 질문에 이벤트 구독을 사용하면 됩니다. 먼저 한 업무 시나리오에서 “화면 밖의 어떤 사건을 알아야 실패를 설명할 수 있는가”를 정하고, 그 사건에 필요한 최소 이벤트만 수집해 보세요.

도입의 성공 기준은 이벤트를 많이 모으는 것이 아니라 검증 문장이 더 정확해지는 것입니다. 요청 시작과 응답 완료를 구분하고, 탭과 프레임을 식별하며, 실제 서버 결과와 가짜 응답을 혼동하지 않는 테스트라야 도움이 됩니다. 브라우저와 도구의 지원 범위를 확인하고, 민감 정보가 로그에 남지 않도록 수집 범위를 제한하는 일까지 포함해 설계해야 합니다.
