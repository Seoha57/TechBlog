리눅스 서버가 느려졌을 때 흔히 하는 일은 애플리케이션 로그를 보거나 CPU·메모리 그래프를 확인하는 것입니다. 하지만 “어느 요청이 지연됐는가”, “네트워크 패킷이 어느 지점에서 버려졌는가”, “파일을 열 때 왜 이렇게 많은 시스템 호출이 발생하는가”는 로그와 일반 지표만으로 곧바로 답하기 어렵습니다. 애플리케이션을 다시 빌드하거나 커널을 수정하지 않고도 이런 실행 경로를 관찰하려는 요구에서 **eBPF(extended Berkeley Packet Filter)** 가 주목받습니다.

eBPF는 사용자 프로그램이 커널의 정해진 지점에 작은 프로그램을 연결하고, 안전성 검증을 통과한 뒤 제한된 방식으로 실행하게 하는 리눅스 기술입니다. “커널 안에서 코드를 실행한다”는 말만 들으면 위험하게 느껴지지만, eBPF의 핵심은 아무 코드나 올릴 수 있게 하는 것이 아니라 검증기, 허용된 helper 함수, 권한, 자원 제한으로 실행 범위를 좁히는 데 있습니다. 이 글은 eBPF를 멋진 관찰 도구로만 소개하지 않고, 어떤 데이터를 어디서 얻는지와 운영에서 무엇을 경계해야 하는지를 함께 정리합니다.

## 먼저 알아둘 기반 기술

**커널(kernel)** 은 프로세스, 메모리, 파일, 네트워크 장치를 관리하는 운영체제의 핵심입니다. 애플리케이션은 보통 사용자 공간(user space)에서 실행되고 파일 읽기나 소켓 전송처럼 커널의 도움이 필요한 작업은 **시스템 호출(system call)** 을 통해 요청합니다. 웹 API가 데이터베이스 연결을 열고 패킷을 보낼 때도 애플리케이션 코드, 라이브러리, 시스템 호출, 네트워크 드라이버를 거치는 여러 단계가 있습니다.

**관찰 가능성(observability)** 은 시스템의 내부 상태를 외부 신호로 이해할 수 있는 성질입니다. 로그는 “무슨 일이 있었는가”를 문장과 속성으로 남기고, 메트릭(metric)은 CPU 사용률·요청 수처럼 숫자의 추이를 보여 주며, 트레이스(trace)는 하나의 요청이 여러 서비스와 작업을 거친 경로를 연결합니다. eBPF는 이 세 신호를 대체하기보다, 기존 계측만으로 비어 있던 커널 수준의 지점을 보완합니다. 예를 들어 요청 지연이 애플리케이션 코드인지 DNS 질의인지 TCP 재전송인지 파일 I/O 대기인지 구분하는 데 사용할 수 있습니다.

**이벤트와 hook** 은 “언제 실행할 것인가”를 정하는 개념입니다. 시스템 호출 진입·종료, 함수 실행, 네트워크 패킷 수신, 스케줄러 전환처럼 커널이 제공하는 사건에 프로그램을 붙일 수 있습니다. 모든 사건을 수집하면 상세해 보이지만 서버 비용과 데이터 양이 폭발합니다. 따라서 질문을 먼저 정하고 그 질문에 필요한 hook만 선택하는 것이 eBPF 사용의 출발점입니다.

## BPF에서 eBPF로: 왜 커널 관찰 방식이 바뀌었나

초기의 BPF는 패킷 필터 표현을 위해 만들어졌습니다. `tcpdump`가 “특정 포트의 TCP 패킷만 보여 달라”는 조건을 커널에 전달하면, 커널이 모든 패킷을 사용자 공간으로 복사하지 않고 먼저 걸러 주는 방식입니다. eBPF는 이 모델을 확장해 네트워크 필터뿐 아니라 추적, 성능 분석, 보안, 제어 그룹 정책 등 여러 종류의 커널 이벤트를 다룰 수 있게 했습니다.

과거에는 커널 동작을 자세히 보려면 소스에 디버그 로그를 넣고 재배포하거나, 커널 모듈을 개발하거나, `strace`·`perf` 같은 도구를 선택해야 했습니다. 각각 유용하지만 운영 중 원인을 좁히기에는 변경 비용, 관찰 범위, 오버헤드, 권한의 제약이 있습니다. eBPF는 미리 정의된 실행 지점과 데이터를 이용해 필요한 순간에만 작은 관찰 프로그램을 붙일 수 있다는 점에서 다릅니다.

다만 eBPF가 만능 디버거는 아닙니다. 커널 내부 구조와 함수 이름은 버전에 따라 바뀔 수 있고, 관찰하려는 값을 모두 안전하게 읽을 수 있는 것도 아닙니다. 애플리케이션의 비즈니스 문맥은 여전히 애플리케이션 계측이 필요합니다. eBPF는 “로그가 없는 곳을 모두 해결하는 기술”이 아니라, 커널과 애플리케이션 사이의 빈 구간을 의도적으로 관찰하는 기술로 이해하는 편이 정확합니다.

## eBPF 프로그램은 어디에 붙고 무엇을 하는가

eBPF 프로그램은 보통 C와 유사한 코드로 작성한 뒤 eBPF 바이트코드로 컴파일합니다. loader가 이를 커널에 전달하면 커널의 **verifier(검증기)** 가 모든 실행 경로를 분석해 허용되지 않는 메모리 접근, 종료하지 않을 수 있는 흐름, 허용 범위를 벗어난 helper 호출 등을 거릅니다. 통과한 프로그램은 필요에 따라 JIT(Just-In-Time) 컴파일되어 기계 코드로 실행될 수 있습니다. 이 절차 덕분에 운영자는 소스 코드가 아니라 “커널이 허용한 안전한 프로그램인가”를 우선 확인할 수 있습니다.

대표적인 연결 지점은 다음과 같습니다.

- **tracepoint** 는 커널이 비교적 안정적인 관찰 지점으로 제공하는 이벤트입니다. 시스템 호출, 프로세스 생성, 스케줄러 변경을 추적할 때 시작점으로 좋습니다.
- **kprobe/kretprobe** 는 커널 함수의 시작 또는 반환에 연결합니다. 세밀하지만 내부 함수명과 인자 변화에 더 민감합니다.
- **uprobe/uretprobe** 는 사용자 공간 바이너리나 라이브러리의 함수에 연결합니다. 코드 수정 없이 특정 함수 호출을 관찰할 수 있지만 심볼과 배포 버전을 관리해야 합니다.
- **XDP(eXpress Data Path)** 는 네트워크 드라이버 가까이에서 패킷을 처리합니다. 매우 이른 단계에서 드롭·전달·리다이렉션을 결정할 수 있어 고성능 패킷 처리에 쓰입니다.
- **TC(Traffic Control)** 는 네트워크 인터페이스의 ingress·egress 경로에서 패킷을 다룹니다. 패킷 정책과 관찰을 결합할 때 사용합니다.
- **cgroup hook** 은 컨테이너나 서비스 단위의 네트워크·시스템 자원 정책과 연결하는 데 쓰입니다.

관찰 질문에 비해 너무 낮은 계층을 선택하지 않는 것이 중요합니다. “어떤 프로세스가 connect를 가장 많이 실패하는가”는 tracepoint나 시스템 호출 추적으로 충분할 수 있습니다. 반면 “패킷이 NIC를 통과하기 전에 드롭되는가”는 XDP나 드라이버 경로를 봐야 할 수 있습니다. 낮은 단계일수록 정보량은 많아지지만 해석과 호환성 비용도 함께 커집니다.

## Map과 이벤트 전달: 커널에서 얻은 데이터를 밖으로 가져오는 법

eBPF 프로그램은 실행할 때마다 사용자 공간에 마음대로 로그를 출력하지 않습니다. 프로그램 간 또는 사용자 공간과 커널 간에 상태를 주고받기 위해 **BPF map** 이라는 자료구조를 사용합니다. hash map은 PID별 호출 수처럼 키-값 통계를, per-CPU map은 CPU별 카운터처럼 경합을 줄이는 집계를, LRU map은 최근 항목 중심의 제한된 캐시를 표현할 수 있습니다.

짧은 사건을 스트리밍할 때는 ring buffer나 perf event buffer를 사용합니다. 예를 들어 특정 오류가 발생한 소켓의 PID, 목적지, errno, 시각을 이벤트로 내보내고 사용자 공간의 수집기가 이를 구조화 로그나 메트릭으로 변환합니다. 반대로 모든 syscall을 이벤트로 내보내면 수집기가 병목이 되고 중요한 사건이 묻힙니다. 운영용 프로그램은 커널에서 먼저 필터링하고, 필요한 속성만 내보내며, 집계 가능한 값은 map에서 집계한 뒤 주기적으로 읽는 편이 안전합니다.

데이터 설계에는 개인정보와 보안도 포함됩니다. 명령행 인자, HTTP payload, 파일 경로에는 토큰·계정·개인정보가 섞일 수 있습니다. eBPF로 읽을 수 있다는 사실은 수집해도 된다는 뜻이 아닙니다. 목적에 필요한 최소 필드만 선택하고, 샘플링·마스킹·접근 통제·보존 기간을 기존 로그 정책과 같은 수준으로 적용해야 합니다.

## Verifier, helper, 권한: “안전하다”는 말의 실제 범위

eBPF verifier는 프로그램이 임의 주소를 읽거나 커널을 멈추게 할 수 있는 무한 실행을 하지 못하도록 제한합니다. 하지만 verifier가 통과했다고 해서 업무 운영에 안전하다는 뜻은 아닙니다. 높은 빈도의 hook에서 무거운 계산을 하거나 큰 이벤트를 대량 전송하면 CPU 사용량과 메모리 압박을 만들 수 있습니다. 검증기는 메모리 안전과 제한된 실행을 다루고, 운영자는 용량·권한·데이터·변경 통제를 다룹니다.

eBPF 프로그램은 kernel helper 함수를 통해 시간, PID, 소켓 정보, map 등에 접근합니다. 어떤 helper를 쓸 수 있는지는 프로그램 종류와 커널 버전에 따라 달라집니다. 로드 권한도 중요합니다. 배포 환경에 따라 CAP_BPF, CAP_PERFMON, CAP_NET_ADMIN 또는 더 강한 권한이 필요할 수 있으며, 컨테이너에 광범위한 capability를 주는 선택은 호스트 관찰 권한 확대와 연결될 수 있습니다. “관찰 도구니까 읽기 전용”이라고 단정하지 말고, 누가 어떤 프로그램을 로드하고 pin된 객체를 변경할 수 있는지 운영 정책에 명시해야 합니다.

Linux Security Module, 커널 설정, 배포판의 보안 정책은 eBPF 기능을 제한할 수 있습니다. 이 제한은 단순 장애가 아니라 보안 경계일 수 있으므로 무조건 우회하지 않습니다. 필요한 사용 사례와 권한을 최소화하고, 전용 에이전트가 로드하며 일반 사용자가 임의 프로그램을 추가하지 못하도록 분리하는 방식이 일반적입니다.

## BTF와 CO-RE: 커널 버전 차이를 다루는 방법

eBPF 프로그램이 커널 구조체의 필드를 직접 읽으면 커널 버전·배포판·설정 차이에서 쉽게 깨집니다. **BTF(BPF Type Format)** 는 커널과 프로그램의 타입 정보를 담는 형식이고, **CO-RE(Compile Once – Run Everywhere)** 는 이 타입 정보를 활용해 한 번 컴파일한 프로그램을 여러 호환 커널에서 재배치하는 접근입니다. libbpf가 대표적으로 이 방식을 지원합니다.

CO-RE는 배포 부담을 크게 줄이지만 “모든 커널에서 같은 동작”을 보장하지는 않습니다. 필요한 BTF가 없거나 특정 hook·helper가 존재하지 않을 수 있고, 벤더 커널의 backport 수준도 차이가 납니다. 따라서 배포 전에는 지원할 최소 커널 목록을 정하고, 기능 탐지와 graceful fallback을 준비해야 합니다. 개발 노트북에서 동작한 `bpftrace` 스크립트를 운영 클러스터 전체에 같은 방식으로 배포하는 것은 별도의 호환성 검증이 필요한 일입니다.

## 성능 진단에 적용하는 순서

예를 들어 API 서버의 p99 응답 시간이 높아졌다고 가정해 봅시다. 먼저 서비스 메트릭에서 어느 엔드포인트·인스턴스·시간대가 영향을 받는지 좁힙니다. 그 다음 CPU 포화, run queue, 디스크 대기, TCP 재전송, DNS 지연 중 어떤 가설을 확인할지 선택합니다. eBPF는 가설 없이 모든 이벤트를 수집하는 장비가 아니라, 이 단계의 질문을 빠르게 검증하는 도구입니다.

CPU가 원인처럼 보이면 off-CPU 시간을 살펴볼 수 있습니다. 프로세스가 실제로 CPU를 쓰지 못하고 어떤 커널 대기 지점에서 잠들었는지, 실행 대기열에 얼마나 머물렀는지를 관찰합니다. 파일 I/O가 의심되면 파일 열기·읽기·block I/O 이벤트를 표본으로 보고, 네트워크가 의심되면 connect 실패, retransmit, accept queue, 소켓 상태를 연결합니다. 결과는 “eBPF에서 X가 보였다”로 끝내지 말고 애플리케이션 trace ID, 배포 시각, 인프라 변경과 함께 해석해야 합니다.

이때 측정 자체가 문제를 만들지 않는지 확인합니다. 처음에는 한 노드, 짧은 기간, 제한된 프로세스 또는 cgroup만 대상으로 하고 baseline을 남깁니다. 샘플 수, 이벤트 드롭 수, 수집기 CPU 사용량을 함께 관찰합니다. 관찰 도구가 서버를 더 느리게 만드는 상황을 피하는 것이 진단 품질의 일부입니다.

## 네트워크와 보안에서의 활용

네트워크 경로는 애플리케이션에서 보기 어려운 영역입니다. 서비스 메시, 프록시, 컨테이너 네트워크, 노드 방화벽이 겹치면 요청이 어느 계층에서 실패했는지 찾기 어렵습니다. eBPF는 소켓 생성·연결·재전송, 패킷의 ingress·egress, cgroup 기반 연결 정책을 관찰해 “연결이 애플리케이션까지 왔는가”, “어느 노드에서 드롭됐는가” 같은 질문을 지원할 수 있습니다.

Cilium처럼 eBPF를 활용하는 프로젝트는 Kubernetes 네트워킹과 네트워크 정책, 로드밸런싱을 구현합니다. 이는 eBPF가 패킷 관찰만 하는 기술이 아니라 제어 경로에도 쓰일 수 있음을 보여 줍니다. 그러나 직접 XDP나 TC 프로그램을 작성하는 일과 Cilium을 운영하는 일은 난이도가 다릅니다. 제품이 제공하는 정책 모델·업그레이드 절차·관찰 도구를 먼저 이용하고, 커스텀 프로그램은 그것으로 해결되지 않는 명확한 문제에서만 검토하는 편이 유지 보수에 유리합니다.

보안 탐지에서는 새 프로세스 실행, 권한 변경, 비정상 네트워크 연결처럼 행위를 관찰할 수 있습니다. 다만 “이상”의 기준은 eBPF가 제공하지 않습니다. 오탐 기준, 대응 권한, 증거 보존, 민감 데이터 처리까지 포함한 탐지 설계가 필요합니다. eBPF 이벤트 하나만으로 사용자나 프로세스를 자동 차단하면 정상 배포·배치 작업을 사고로 오인할 수 있습니다.

## 도구 선택: bpftrace, BCC, libbpf 그리고 제품

**bpftrace** 는 짧은 추적 스크립트를 작성해 현상을 탐색하기에 좋습니다. 운영 진단에서 특정 syscall이나 tracepoint를 빠르게 관찰할 수 있지만, 스크립트의 권한·호환성·출력량을 통제해야 합니다. **BCC(BPF Compiler Collection)** 는 Python 기반 도구와 예제가 풍부해 학습과 프로토타입에 유용합니다. **libbpf** 는 C 기반 loader와 CO-RE 배포에 널리 쓰이는 라이브러리로, 제품 수준의 eBPF 프로그램을 만들 때 자주 선택됩니다.

어떤 도구가 “정답”인 것은 아닙니다. 일회성 장애 분석에는 검토된 bpftrace 스크립트가 충분할 수 있고, 지속적인 제품 기능에는 버전 관리·테스트·권한 분리가 가능한 에이전트가 필요할 수 있습니다. Prometheus exporter나 OpenTelemetry Collector로 내보낼 지표의 이름과 카디널리티를 먼저 설계하지 않으면, 좋은 eBPF 데이터도 대시보드에서 사용할 수 없는 잡음이 됩니다.

## 배포와 롤백을 위한 운영 기준

운영에 eBPF를 도입할 때는 프로그램 파일만 배포하지 말고 질문, 대상, 권한, 종료 조건을 함께 정합니다. 예를 들어 “결제 API를 처리하는 cgroup에서 30분 동안 TCP 연결 실패의 errno와 목적지 포트만 집계한다”처럼 범위를 적습니다. 성공 기준은 문제 원인을 좁힐 정보가 얻어지는 것이고, 중단 기준은 CPU 증가·이벤트 드롭·민감 정보 노출 가능성처럼 구체적으로 둡니다.

pinning은 eBPF 객체를 bpffs에 유지해 여러 프로세스가 재사용하게 할 수 있지만, 객체 수명과 소유권을 명확히 하지 않으면 재배포 뒤 오래된 map과 프로그램이 남을 수 있습니다. 배포 도구는 어떤 객체를 만들고 갱신하고 제거하는지 추적해야 하며, 롤백 시 이전 프로그램과 map 스키마가 호환되는지도 확인해야 합니다. 관찰 프로그램도 애플리케이션처럼 버전·변경 사유·테스트 결과를 남기는 편이 안전합니다.

컨테이너 환경에서는 노드 커널을 공유한다는 점을 특히 조심해야 합니다. 특정 Pod만 보고 싶어도 호스트 차원의 hook에서 다른 워크로드 정보가 섞일 수 있습니다. cgroup, namespace, PID 필터를 사용하고 결과를 테넌트 경계에 맞게 분리해야 합니다. 개발·스테이징에서 우선 검증하고, 프로덕션은 canary 노드에서 시작해 배포 범위를 단계적으로 넓히는 방식을 권합니다.

## 한계와 적용 기준 Q&A

### Q. eBPF만으로 APM을 대체할 수 있나요?

A. 대체보다는 보완에 가깝습니다. eBPF는 코드 변경 없이 네트워크·시스템 호출·스케줄러 신호를 보완하지만, 업무 트랜잭션 이름, 사용자 맥락, 도메인 오류는 애플리케이션의 OpenTelemetry 계측과 로그가 더 정확합니다. 두 데이터를 시간·서비스·프로세스 기준으로 연결하는 것이 효과적입니다.

### Q. 커널 함수에 kprobe를 붙이면 항상 좋은가요?

A. 아닙니다. 내부 함수는 커널 버전과 빌드 옵션에 따라 변할 수 있습니다. 먼저 tracepoint처럼 안정적인 인터페이스가 있는지 찾고, kprobe가 꼭 필요하다면 지원 커널과 fallback을 문서화해야 합니다.

### Q. XDP는 빠르다는데 모든 방화벽 정책에 쓰면 되나요?

A. XDP는 이른 패킷 경로에서 동작해 강력하지만, 사용할 수 있는 컨텍스트와 helper가 제한되고 운영·디버깅 난이도가 올라갑니다. 단순한 L7 인증·업무 정책까지 XDP에 넣는 것은 적합하지 않습니다. 처리량이 병목인 명확한 L3/L4 문제부터 검토합니다.

### Q. verifier가 있으니 성능 테스트는 생략해도 되나요?

A. 안 됩니다. verifier는 안전하지 않은 메모리 접근과 프로그램 제약을 검사할 뿐, 특정 트래픽에서의 CPU 비용·map 경합·이벤트 폭주를 대신 측정하지 않습니다. 대상 노드와 트래픽을 제한한 검증이 필요합니다.

### Q. 어떤 팀부터 도입하면 좋을까요?

A. 커널·네트워크 관찰의 빈틈 때문에 반복적으로 원인 분석 시간이 길어지는 팀이 적합합니다. 반대로 기본 로그, 메트릭, 배포 추적이 없는 상태라면 먼저 그 기반을 갖추는 편이 문제 해결 속도를 더 크게 높일 수 있습니다.

## 마무리

eBPF는 커널 안에서 무엇이 일어나는지 더 가까이 볼 수 있게 하지만, 좋은 진단을 자동으로 만들어 주지는 않습니다. 관찰할 질문을 좁히고, 안정적인 hook을 선택하고, map과 이벤트 양을 제한하며, 애플리케이션 신호와 연결할 때 비로소 실무 가치가 생깁니다. 처음에는 한 가지 장애 가설과 한 노드에서 시작하세요. “어떤 이벤트를 왜 수집하며, 언제 중단할 것인가”가 명확한 eBPF 사용은 강력한 도구를 위험하지 않게 쓰는 가장 현실적인 방법입니다.

## 장애 분석 예시: 느린 요청을 커널 신호와 연결하기

한 서비스의 응답 시간이 늘어났다고 해서 곧바로 eBPF 프로그램부터 올릴 필요는 없습니다. 먼저 서비스 대시보드에서 시작 시각, 영향을 받는 인스턴스, 오류율 변화를 확인합니다. 예를 들어 특정 노드에서만 p99가 올라가고 CPU 평균은 낮은데 요청 처리 스레드 수가 줄었다면, CPU 부족보다 대기 상태를 의심할 근거가 생깁니다. 이때 스케줄러 지연과 block I/O 대기, TCP 재전송 중 무엇을 먼저 볼지 정합니다.

만약 데이터베이스 연결을 기다리는 것으로 추정된다면 애플리케이션 커넥션 풀 지표와 함께 `connect`·`accept` 실패, 소켓 상태, DNS 질의 시간을 제한적으로 봅니다. 재전송이 늘어난 노드와 목적지 조합이 확인되면 네트워크 팀에는 “네트워크가 느리다”가 아니라 발생 시각, 노드, 대상 IP·포트, 재전송 비율이라는 재현 가능한 단서를 전달할 수 있습니다. 반대로 네트워크 신호가 정상인데 off-CPU 시간이 파일 시스템 경로에 몰리면 스토리지·로그 회전·디스크 포화 가설로 전환합니다.

이 과정에서 eBPF 결과 하나를 원인으로 단정하지 않는 태도가 중요합니다. 예를 들어 `connect` 실패가 관찰됐다고 해도 애플리케이션이 연결 한계를 초과했는지, 상대 서비스가 재시작 중인지, DNS가 다른 주소를 돌려줬는지까지는 별도 증거가 필요합니다. eBPF 이벤트는 가설을 좁히는 관측값이며, 애플리케이션 로그·배포 이력·인프라 변경과 교차 확인할 때 진단 근거가 됩니다.

## 지표 설계: 카디널리티와 샘플링을 먼저 결정한다

eBPF로 얻은 데이터를 Prometheus 같은 시계열 시스템에 내보낼 때 가장 흔한 문제는 레이블(label)을 너무 세분화하는 것입니다. PID, 전체 파일 경로, 원본 URL, 클라이언트 IP를 레이블로 넣으면 가능한 조합 수가 빠르게 증가합니다. 이 현상을 **높은 카디널리티(cardinality)** 라고 하며, 수집 서버 메모리와 쿼리 성능을 악화시킬 수 있습니다. 필요한 경우에는 서비스명·노드·오류 종류처럼 유한한 값만 메트릭 레이블로 쓰고, 개별 요청·경로는 제한된 로그 또는 trace event로 보냅니다.

샘플링도 관찰 목적에 맞춰야 합니다. 용량 계획처럼 장기 추세가 목적이면 일정 비율의 요청만 표본으로 보고 분 단위 집계로 충분할 수 있습니다. 반면 보안 사고나 특정 오류를 조사할 때는 일시적으로 조건을 엄격히 걸고 누락 없는 이벤트를 확보해야 할 수 있습니다. 두 경우 모두 수집 기간, 최대 이벤트 수, 이벤트 드롭 시 행동을 문서화합니다. “필요하면 더 본다”는 운영 기준은 실제 장애에서 데이터 폭주를 막아 주지 못합니다.

메트릭 이름에도 원인을 단정한 단어를 넣지 않는 편이 좋습니다. `tcp_retransmit_total`처럼 관찰 사실을 나타내고, 그것이 지연의 원인인지 여부는 대시보드와 분석 문서에서 해석합니다. 이렇게 하면 같은 지표를 네트워크 장애, 원격 서비스 과부하, MTU 설정 문제 등 여러 가설에 재사용할 수 있습니다.

## 검증 환경에서 확인할 최소 항목

첫 번째는 **기능 호환성**입니다. 지원하려는 커널 버전에서 프로그램이 verifier를 통과하는지, 필요한 BTF·hook·helper가 있는지 확인합니다. 두 번째는 **격리**입니다. 지정한 cgroup 또는 PID만 관찰하는지, 다른 테넌트와 민감한 명령행·패킷 데이터가 섞이지 않는지 봅니다. 세 번째는 **부하**입니다. 예상 이벤트율보다 높은 부하에서 CPU, 메모리, ring buffer 드롭, 수집기 지연이 허용 범위인지 확인합니다.

네 번째는 **실패 방식**입니다. 수집기가 재시작하거나 map 읽기에 실패했을 때 애플리케이션 트래픽에는 영향이 없어야 합니다. 관찰 데이터가 일부 유실될 수 있다는 상태를 메트릭으로 드러내고, 유실된 데이터를 정상으로 해석하지 않도록 대시보드에 표시합니다. 다섯 번째는 **제거와 롤백**입니다. loader를 중지했을 때 pin된 프로그램과 map이 어떻게 처리되는지, 이전 버전으로 내렸을 때 map 구조가 충돌하지 않는지 확인합니다.

이 검증 항목은 eBPF만의 절차가 아닙니다. 운영 경로에 상주하는 모든 관찰 에이전트가 가져야 할 기본 조건입니다. eBPF는 커널에 가깝다는 이유로 더 강력한 권한과 더 많은 데이터를 다룰 수 있으므로, 평소의 에이전트 배포보다 더 명확한 변경 관리가 필요합니다.

## 학습과 도입의 현실적인 순서

처음 eBPF를 학습할 때는 패킷을 조작하거나 커스텀 보안 정책을 만드는 일부터 시작하지 않는 편이 좋습니다. 먼저 `ps`, `ss`, `top`, `perf`, 애플리케이션 메트릭처럼 익숙한 도구로 현재 질문에 답할 수 있는지 확인합니다. 그 다음 tracepoint 기반의 읽기 전용 관찰로 프로세스 생성, 파일 열기, TCP 연결처럼 이해하기 쉬운 사건을 본 뒤, map과 사용자 공간 수집기가 어떻게 연결되는지 살펴보면 좋습니다. 이 순서는 eBPF 문법보다 관찰 결과를 해석하는 능력을 먼저 길러 줍니다.

팀 도입에서는 한 번의 데모보다 재사용 가능한 런북이 중요합니다. 런북에는 목적, 대상 노드·프로세스, 프로그램 버전, 필요한 capability, 수집 필드, 예상 이벤트율, 중단·롤백 방법을 적습니다. 또한 같은 질문을 기본 도구·로그·eBPF 중 어디에서 확인할지 구분합니다. 예를 들어 파일 시스템 용량은 일반 지표로, 특정 syscall 지연은 eBPF로, 사용자가 본 오류 문구는 애플리케이션 로그로 확인하는 식입니다.

이 경계를 정하면 eBPF를 도입하지 않는 결정도 설명할 수 있습니다. 관찰하려는 값이 이미 OpenTelemetry span 속성으로 충분히 수집되고 있고 커널 수준 해석이 필요 없다면, 새 권한과 에이전트를 추가하는 비용이 이득보다 클 수 있습니다. 반대로 노드별 네트워크·스케줄러 문제를 반복해서 겪고 기존 지표가 원인 구분을 못 한다면, 작은 eBPF 관찰부터 시작할 근거가 됩니다. 중요한 것은 최신 기술을 쓰는 일이 아니라 문제를 더 빠르고 안전하게 좁히는 일입니다.

운영 회고에는 관찰을 통해 **배제한 가설**도 남깁니다. 예를 들어 재전송·디스크 대기·스케줄러 지연이 모두 정상 범위였다는 사실은 다음 장애에서 같은 방향을 먼저 조사하지 않아도 되는 근거가 됩니다. 반대로 수집기에서 이벤트 드롭이 발생했다면 “관찰되지 않은 사건이 없었다”라고 결론 내릴 수 없다는 제한도 같이 기록해야 합니다. 좋은 관측은 데이터를 많이 남기는 일이 아니라, 결과를 어느 범위까지 믿을 수 있는지 분명히 남기는 일입니다.

eBPF의 결과는 대시보드 한 장으로 끝나지 않습니다. 누가 그 데이터를 볼 수 있는지, 어떤 경보가 사람의 검토를 요구하는지, 프로그램을 갱신할 때 어떤 테스트를 다시 해야 하는지까지 정해질 때 운영 도구가 됩니다. 이 기본을 지키면 eBPF는 커널을 어렵게 만드는 기술이 아니라, 기존 관찰 체계의 빈 부분을 메우는 실용적인 선택지가 됩니다.

특히 장애 중에는 새 프로그램을 즉석에서 만들기보다, 사전에 검토한 진단 도구와 쿼리를 사용해야 합니다. 급한 상황에서 권한과 수집 범위를 넓히면 문제 원인보다 2차 위험이 더 커질 수 있습니다. 평시에 안전한 관찰 절차를 준비하는 일이 eBPF 활용의 가장 큰 투자입니다.

이 원칙은 학습 환경에도 같습니다. 작은 VM에서 프로그램의 로드, 이벤트 집계, 제거를 한 번씩 경험한 뒤 실제 서버의 권한·보안 정책과 차이를 확인하면, 도구 이름만 아는 상태보다 훨씬 안전하게 운영 질문으로 연결할 수 있습니다.

기술 선택의 기준은 화려한 기능이 아니라, 더 나은 판단을 만드는가입니다.

그리고 그 판단은 항상 사람과 기존 운영 절차 안에서 검토되어야 합니다.
