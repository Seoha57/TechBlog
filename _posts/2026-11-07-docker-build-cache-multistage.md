## 먼저 답하기

### Q. Dockerfile 명령 순서만 바꾸면 빌드가 항상 빨라지나요?

A. 명령 순서는 캐시 재사용에 큰 영향을 주지만, 항상 같은 효과를 내지는 않습니다. 빌드 컨텍스트의 크기, 의존성 설치 방식, 원격 캐시, 베이스 이미지 변경, 빌더 환경도 함께 작용합니다. 핵심은 자주 바뀌는 파일과 거의 바뀌지 않는 파일을 분리해, 비싼 작업을 불필요하게 다시 실행하지 않게 하는 것입니다.

### Q. Multi-stage build를 쓰면 이미지가 자동으로 안전해지나요?

A. 최종 이미지에서 컴파일러와 소스 파일을 제외해 크기와 공격 표면을 줄이는 데 도움이 되지만, 취약한 베이스 이미지·의존성·비밀 값·과도한 root 권한을 자동으로 해결하지는 않습니다. 빌드와 실행의 책임을 분리한 뒤에도 태그 고정, SBOM, 서명, 런타임 권한, 업데이트 정책을 함께 설계해야 합니다.

## 먼저 알아둘 기반 기술

### 컨테이너 이미지와 레이어

컨테이너 이미지는 실행에 필요한 파일 시스템과 설정을 여러 레이어로 쌓은 읽기 전용 패키지입니다. Dockerfile의 `FROM`, `RUN`, `COPY` 같은 명령은 보통 새 레이어 또는 빌드 단계의 결과를 만듭니다. 컨테이너를 실행할 때는 이미지 레이어 위에 쓰기 가능한 얇은 계층이 더해집니다. 이 구조 덕분에 여러 이미지가 같은 베이스 레이어를 공유할 수 있고, 변경되지 않은 빌드 결과를 다시 활용할 수 있습니다.

하지만 레이어는 단순한 파일 묶음이 아닙니다. 한 레이어에 비밀 파일을 복사했다가 다음 레이어에서 삭제해도 이전 레이어 기록에 남을 수 있습니다. 큰 파일을 한 번 추가하면 다음 명령에서 지워도 이미지 전송 비용이 바로 사라지지 않을 수 있습니다. 따라서 이미지를 작게 만든다는 것은 마지막 파일 목록만 정리하는 일이 아니라, 각 빌드 단계에 어떤 입력을 넣는지 설계하는 일입니다.

### Build Context와 .dockerignore

`docker build`가 시작될 때 Docker CLI는 보통 지정한 디렉터리를 build context로 빌더에게 보냅니다. 프로젝트 루트에 node_modules, git 이력, 테스트 산출물, 로컬 비밀 파일, 대용량 다운로드가 있으면 Dockerfile에서 쓰지 않아도 전송 비용과 캐시 무효화에 영향을 줄 수 있습니다. `.dockerignore`는 context에서 제외할 경로를 지정하는 파일입니다. `.gitignore`와 목적이 비슷해 보이지만 Git 추적과 Docker 빌드 입력은 다른 문제이므로 별도로 관리해야 합니다.

좋은 `.dockerignore`는 모든 것을 무조건 제외하지 않습니다. 빌드에 필요한 lock 파일, 소스, 생성 규칙은 남기고, 로컬 의존성 디렉터리, 테스트 결과, IDE 설정, 환경 변수 파일, 인증서·토큰 같은 민감 정보를 제외합니다. 제외 규칙을 바꾼 뒤에는 CI에서 실제 빌드가 되는지 확인해야 합니다. 개발자 컴퓨터에만 있던 파일을 우연히 쓰고 있었다면 context를 줄인 뒤 빌드가 실패할 수 있고, 그 실패는 오히려 재현성 문제를 드러내는 신호입니다.

### 재현 가능한 빌드와 의존성 고정

재현 가능한 빌드는 같은 입력과 같은 도구 버전으로 빌드했을 때 같은 결과를 얻기 쉬운 상태를 뜻합니다. 패키지 관리자의 lock 파일은 의존성 버전을 고정하는 데 중요한 역할을 합니다. `npm install` 대신 lock 파일을 엄격하게 따르는 명령을 사용하거나, Python·Java·Go의 의존성 해석 결과를 기록하면 오늘 빌드와 다음 달 빌드가 다른 라이브러리를 받는 위험을 줄일 수 있습니다.

베이스 이미지도 입력입니다. `node:latest`나 `python:3`처럼 넓은 태그는 시간이 지나 다른 이미지를 가리킬 수 있습니다. 의미 있는 버전 태그를 쓰고, 보안·재현성이 특히 중요하다면 digest로 실제 이미지를 고정하는 방법을 검토할 수 있습니다. 다만 digest를 고정하면 보안 업데이트가 자동으로 들어오지 않으므로, 업데이트를 감지하고 검토해 바꾸는 운영 절차가 필요합니다.

## 캐시를 이해하는 방법

### 캐시 키가 바뀌는 이유

Docker 빌더는 이전 단계의 결과와 명령·입력을 비교해 같은 결과를 재사용할 수 있는지 판단합니다. 의존성 설치 전에 애플리케이션의 모든 소스를 `COPY . .`로 복사하면, 문서 한 줄만 바뀌어도 이후의 의존성 설치 단계가 다시 실행될 수 있습니다. 반대로 package manifest와 lock 파일만 먼저 복사하고 의존성을 설치한 뒤 소스를 복사하면, 의존성이 바뀌지 않은 소스 수정에는 설치 결과를 재사용하기 쉬워집니다.

```dockerfile
FROM node:22-bookworm AS build
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npm run build
```

이 예시는 구조를 보여 주기 위한 것입니다. 실제 명령은 프로젝트의 패키지 관리자와 lock 파일에 맞춰야 합니다. 중요한 점은 캐시를 위해 의존성 파일을 먼저 복사하더라도, lock 파일이 없거나 설치 명령이 버전을 다시 해석하면 재현성은 약해진다는 것입니다. 빠른 빌드와 일관된 빌드는 함께 설계해야 합니다.

### 캐시가 틀린 결과를 만들 수 있는 경우

캐시는 결과가 같을 때만 이롭습니다. 빌드가 현재 시간, 네트워크에서 받은 최신 파일, 숨은 환경 변수, 이전 단계의 임시 파일에 의존하면 캐시가 재사용됐을 때 기대와 다른 결과를 얻을 수 있습니다. 반대로 캐시를 무조건 끄면 느린 빌드와 외부 저장소 부하가 생깁니다. 해결은 캐시를 포기하는 것이 아니라 입력을 명시적으로 만드는 것입니다.

예를 들어 다운로드한 도구의 버전과 checksum을 Dockerfile 또는 빌드 스크립트에 기록하고, 필요한 경우에만 캐시를 무효화합니다. 비밀 토큰으로 private registry에 접근해야 한다면 토큰을 `ARG`나 `ENV`로 이미지에 남기지 말고 빌더가 제공하는 secret mount 같은 일회성 전달 방식을 검토합니다. 비밀이 캐시나 레이어에 남으면 이후 이미지를 받는 사람에게 노출될 수 있습니다.

### 원격 캐시와 CI

개발자 노트북의 로컬 캐시는 CI runner와 공유되지 않는 경우가 많습니다. BuildKit과 레지스트리·CI 캐시를 이용하면 이전 빌드의 레이어를 원격에서 가져와 반복 빌드를 줄일 수 있습니다. 그러나 캐시는 신뢰 경계이기도 합니다. 누구나 쓰기 가능한 캐시에서 예상하지 못한 결과를 가져오지 않는지, 캐시가 private dependency나 비밀을 포함하지 않는지, branch별 캐시 격리가 필요한지 확인해야 합니다.

CI의 성공 기준은 빌드 시간이 짧다는 것만이 아닙니다. 깨끗한 runner에서 빌드되는지, lock 파일과 실제 설치 결과가 맞는지, 최종 이미지에 테스트 도구·소스·비밀이 남지 않는지, 취약점과 라이선스 검사를 어떤 시점에 하는지 함께 봐야 합니다. 캐시가 빠른 빌드를 돕더라도 정기적으로 cache 없는 빌드 또는 격리된 빌드로 재현성을 점검할 이유가 있습니다.

## Multi-stage build로 책임 나누기

Multi-stage build는 Dockerfile에 여러 `FROM` 단계를 두고, 앞 단계의 산출물만 마지막 단계로 복사하는 방식입니다. 예를 들어 프런트엔드 빌드에는 Node.js, 패키지 관리자, 소스와 dev dependency가 필요하지만, 정적 파일을 제공하는 단계에는 웹 서버와 생성된 파일만 필요할 수 있습니다. Go 서비스도 빌드 단계의 컴파일러와 모듈 캐시를 최종 실행 이미지에 넣지 않을 수 있습니다.

```dockerfile
FROM node:22-bookworm AS build
WORKDIR /src
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /src/dist /usr/share/nginx/html
```

이 구조는 최종 이미지를 작게 만들 수 있지만, 빌드 단계에 있던 파일이 자동으로 안전해지는 것은 아닙니다. 빌드 로그, CI artifact, 캐시, registry의 intermediate image 정책도 확인해야 합니다. 또한 alpine 기반 이미지를 항상 선택해야 한다는 뜻도 아닙니다. libc 호환성, 디버깅 도구, 조직의 베이스 이미지 정책, 취약점 대응 속도를 비교해 서비스에 맞는 런타임을 고릅니다.

## 런타임 권한과 설정 분리

이미지 안에 환경별 설정을 굽는 방식은 배포마다 이미지를 다시 만들게 하고 비밀 노출 위험을 키울 수 있습니다. 일반적으로 이미지는 여러 환경에서 같은 실행물을 사용하고, 환경별 endpoint·기능 flag·비밀은 안전한 배포 설정으로 주입하는 편이 낫습니다. 단, 설정이 너무 많아지면 어떤 이미지가 어떤 값으로 실행됐는지 추적하기 어려우므로 image digest, 배포 manifest, 설정 버전을 연결해 기록해야 합니다.

컨테이너 프로세스는 가능한 한 root가 아닌 사용자로 실행하고, 쓰기 가능한 디렉터리를 최소화하며, 필요한 포트와 capability만 사용합니다. Dockerfile의 `USER` 지시는 좋은 출발점이지만, 실제 Kubernetes securityContext, 볼륨 권한, 임시 파일 경로와 맞는지도 확인해야 합니다. 빌드에서 작아진 이미지가 런타임에서 과도한 권한을 갖고 있다면 공급망 위험은 그대로 남습니다.

## 업무 예시: 웹 API 이미지 빌드 개선

Node.js 기반 주문 API가 있다고 가정합니다. 기존 Dockerfile은 프로젝트 전체를 먼저 복사하고 `npm install`을 실행하며, 테스트 도구와 소스 파일이 포함된 이미지를 production에 배포합니다. README만 바꿔도 의존성 설치가 다시 실행되고, 로컬 `.env`가 context에 들어갈 위험도 있습니다. 개선은 먼저 `.dockerignore`로 불필요한 입력을 줄이고, package manifest와 lock 파일을 먼저 복사해 `npm ci`를 수행하며, 빌드 결과만 runtime 단계로 전달하는 식으로 시작할 수 있습니다.

변경 뒤에는 단순히 이미지 크기와 빌드 시간만 비교하지 않습니다. 깨끗한 CI runner에서 lock 파일대로 설치되는지, final image에 소스와 테스트 도구가 남지 않는지, 애플리케이션이 non-root 사용자로 시작하는지, 환경별 설정을 image rebuild 없이 주입할 수 있는지 확인합니다. private registry 인증이 필요하다면 토큰이 image history와 로그에 남지 않는지도 검토합니다.

## 빌드 검증과 배포 검증을 분리하기

이미지가 만들어졌다는 사실은 애플리케이션이 정상 실행된다는 증거가 아닙니다. 빌드 단계에서는 Dockerfile 문법, 의존성 설치, 정적 분석, 단위 테스트, 산출물 생성 여부를 확인할 수 있습니다. 이미지 단계에서는 tag와 digest, 파일 목록, 실행 사용자, 취약점·라이선스 검사, SBOM(Software Bill of Materials) 생성을 확인할 수 있습니다. 배포 단계에서는 실제 환경 변수, 네트워크, 데이터베이스 연결, readiness, 권한, resource limit이 맞는지 확인합니다. 각 단계의 실패 원인을 섞지 않으면 문제가 생겼을 때 더 빨리 좁힐 수 있습니다.

이미지를 registry에 push할 때도 tag만 믿지 않는 편이 좋습니다. `release`나 `latest` 태그는 시간이 지나 다른 digest를 가리킬 수 있으므로, 배포 기록에는 실제 digest를 남깁니다. 그러면 장애 때 어떤 실행물을 배포했는지 확인하고 이전 실행물로 정확히 돌아가기 쉬워집니다. 사람이 읽기 좋은 버전 태그와 기계가 비교하는 digest는 서로 다른 목적을 가집니다.

서명은 이미지가 승인된 빌드 파이프라인에서 나왔는지 확인하는 데 도움을 줄 수 있습니다. 하지만 서명을 붙였다고 그 안의 애플리케이션이 안전하거나 버그가 없다는 뜻은 아닙니다. 서명 키의 보관, 검증 정책, 어느 환경에서 서명 없는 이미지를 거절할지, 긴급 상황의 예외 절차를 함께 정해야 합니다. 공급망 보안은 한 도구를 추가하는 일이 아니라 신뢰할 입력과 배포 규칙을 명시하는 일입니다.

## 언어별 의존성의 차이

Node.js, Python, Java, Go는 의존성을 설치하고 산출물을 만드는 방식이 다릅니다. Node.js는 lock 파일과 npm cache, Python은 wheel·가상 환경·시스템 라이브러리, Java는 Maven 또는 Gradle cache와 JRE, Go는 모듈 cache와 정적 또는 동적 링크를 고려할 수 있습니다. 같은 Dockerfile 패턴을 모든 언어에 복사하면 캐시가 효과가 없거나 runtime에 필요한 파일이 빠질 수 있습니다. 프로젝트의 공식 빌드 명령과 산출물 구조를 먼저 확인하세요.

네이티브 모듈은 특히 주의가 필요합니다. 빌드 단계의 libc, CPU 아키텍처, 컴파일러 버전과 실행 단계가 다르면 컨테이너 안에서 모듈을 불러오지 못할 수 있습니다. multi-stage build가 빌더와 runtime을 분리하는 만큼, 필요한 공유 라이브러리와 플랫폼 호환성을 테스트해야 합니다. 로컬 x86 환경에서만 빌드가 성공하고 ARM runner에서 실패하는 문제도 아키텍처와 의존성 산출물을 함께 확인해야 찾을 수 있습니다.

## 캐시 무효화 규칙을 문서화하기

캐시 문제를 만났을 때 `--no-cache`를 습관적으로 쓰면 빌드가 느려지고 원인을 배우기 어렵습니다. 어떤 입력이 바뀌면 어느 단계가 다시 실행되어야 하는지 Dockerfile과 빌드 로그로 설명할 수 있어야 합니다. package lock 변경은 설치 단계 무효화가 맞고, 애플리케이션 소스 변경은 compile 단계 무효화가 맞습니다. 반면 README 변경이 production dependency 설치를 다시 하게 만든다면 context 또는 COPY 순서를 개선할 기회입니다.

CI의 cache key에는 OS·아키텍처·패키지 관리자 버전·lock 파일 해시처럼 결과에 영향을 주는 값을 넣을 수 있습니다. 너무 넓은 key는 오래된 결과를 재사용할 위험이 있고, 너무 좁은 key는 매번 miss가 나서 cache의 가치를 잃습니다. 캐시 키 변경도 코드 변경처럼 리뷰하고, cache hit·miss가 실제 빌드 시간과 실패율에 어떤 영향을 주는지 관찰하세요.

## 한계와 적용 기준 보충

이미지 빌드 최적화는 모든 CI 시간을 해결하지 않습니다. 통합 테스트, 원격 dependency, 취약점 스캔, artifact 업로드가 전체 시간을 차지할 수 있습니다. 먼저 병목이 build인지 테스트인지 registry 전송인지 관찰하고, 가장 큰 문제부터 해결하세요. 빠른 이미지를 만들기 위해 테스트를 건너뛰거나 검사를 약화시키면 단기 시간은 줄어도 배포 실패와 복구 비용이 커질 수 있습니다.

또한 운영 디버깅을 위해 shell과 도구를 final image에 넣고 싶은 요구가 있을 수 있습니다. production 이미지를 무겁게 만들기보다, 별도 debug image 또는 승인된 ephemeral debug container를 사용하는 방법을 검토할 수 있습니다. 어떤 선택이든 운영자가 필요한 진단을 할 수 있는지와 공격 표면을 함께 평가해야 합니다.

## 빌드 입력을 감사 가능하게 만들기

빌드가 외부에서 내려받는 모든 것은 공급망 입력입니다. 패키지 registry, OS 패키지 저장소, Git dependency, 코드 생성기, 플러그인, 다운로드한 바이너리의 출처와 버전을 알 수 있어야 합니다. 단순히 URL을 Dockerfile에 적는 대신, 공식 배포처인지, checksum 또는 서명이 있는지, 네트워크 실패 때 어떤 결과가 남는지 확인합니다. 재현성이 필요한 빌드는 최신 버전을 매번 내려받는 편의보다 검증 가능한 입력을 우선합니다.

빌드 로그와 artifact도 민감 정보를 담을 수 있습니다. verbose 모드가 registry 토큰이나 private package URL을 출력하지 않는지, 실패한 명령이 환경 변수를 그대로 보여 주지 않는지, CI가 로그를 얼마나 오래 보관하고 누가 읽을 수 있는지 점검합니다. 빌드 실패를 조사하기 위해 비밀을 노출하는 것보다, 필요한 식별자와 오류 코드만 남기고 승인된 비밀 관리 도구에서 값을 참조하는 편이 안전합니다.

개발 환경과 CI 환경의 차이도 빌드 결함을 만듭니다. 로컬에는 우연히 설치된 compiler나 cache가 있어 성공했는데 깨끗한 runner에서는 실패한다면, Dockerfile이 필요한 입력을 표현하지 못한 것입니다. 새 구성원이 같은 명령으로 빌드할 수 있는지, CI에서 cache를 비웠을 때도 성공하는지, 여러 아키텍처를 지원한다면 각각에서 산출물이 맞는지를 정기적으로 확인하세요.

## 태그·버전·배포 이력

이미지 이름에는 보통 서비스명과 버전 태그가 붙습니다. 사람이 읽기 좋은 태그는 release note와 문제 조사에 편하지만, 같은 태그를 덮어쓰는 정책이면 정확한 실행물을 식별하기 어렵습니다. 배포 시스템은 image digest와 Git commit, 빌드 시간, dependency lock 파일 해시, SBOM 위치를 연결해 기록할 수 있습니다. 이 연결이 있으면 취약점 공지가 나왔을 때 어떤 배포가 영향을 받는지, 문제가 생겼을 때 어느 산출물로 돌아가야 하는지 판단하기 쉬워집니다.

버전 전략은 조직의 release 방식과 맞아야 합니다. 매 commit마다 immutable tag를 만들지, 검증된 release에만 태그를 붙일지, development와 production registry를 나눌지 선택할 수 있습니다. 중요한 것은 사용자가 보는 버전, CI가 만드는 artifact, 실제 cluster가 실행하는 digest가 서로 추적 가능해야 한다는 점입니다. 최신 태그 하나에만 의존하면 rollback과 감사가 어려워집니다.

## Dockerfile 리뷰 체크리스트

리뷰할 때는 먼저 build context에 무엇이 들어오는지 봅니다. 다음으로 lock 파일과 패키지 설치 명령이 일관적인지, cache를 무효화하는 COPY 순서가 합리적인지, 빌드 산출물만 final stage로 전달되는지 확인합니다. final image에서는 불필요한 package·source·비밀이 없는지, root가 아닌 사용자로 실행되는지, 필요한 포트와 writable path가 명시됐는지 봅니다. 마지막으로 base image의 업데이트·취약점 대응·배포 digest 추적이 운영 절차에 연결되는지 확인합니다.

이 체크리스트는 모든 Dockerfile을 똑같이 만들기 위한 규칙이 아닙니다. 정적 사이트와 네이티브 모듈을 쓰는 API, 데이터 처리 작업자는 필요한 도구와 위험이 다릅니다. 리뷰의 목표는 유행하는 한 줄을 추가하는 것이 아니라, 어떤 입력으로 어떤 실행물이 만들어지고 어떤 권한으로 실행되는지 설명할 수 있게 하는 것입니다.

## 베이스 이미지를 의존성으로 관리하기

`FROM` 뒤의 이미지는 Dockerfile의 배경이 아니라 애플리케이션이 의존하는 실행 환경입니다. 운영체제 라이브러리, CA 인증서, 셸, 런타임, 기본 사용자 설정이 모두 베이스 이미지에서 옵니다. `node:22`처럼 움직이는 태그는 편리하지만 오늘과 다음 달에 같은 digest를 가리킨다는 보장이 없습니다. 반대로 digest로 완전히 고정하면 같은 빌드는 재현하기 쉽지만, 새 보안 패치가 자동으로 들어오지는 않습니다.

실무에서는 두 문제를 분리해 다루는 편이 좋습니다. 배포하는 순간에는 검토한 digest를 기록해 같은 실행물을 재현하고, 별도의 정기 작업으로 베이스 이미지 갱신 후보를 찾아 빌드·테스트·취약점 검사를 거칩니다. 즉 ``최신 태그를 신뢰한다``와 ``오래된 digest를 영원히 쓴다`` 사이에서 하나를 고르는 것이 아니라, 갱신을 발견하는 흐름과 승인된 산출물을 고정하는 흐름을 함께 둡니다.

조직에서 제공하는 표준 베이스 이미지가 있다면 그 이미지를 써야 하는 이유도 확인합니다. 단지 패키지가 적어서가 아니라, 누가 패치를 관리하는지, 지원 종료일은 언제인지, 긴급 취약점이 공개됐을 때 어떤 팀이 새 digest를 제공하는지, 라이선스 목록을 어떻게 받는지가 중요합니다. 외부 공개 이미지를 임의로 추가하면 출처와 유지보수 책임이 불명확해질 수 있습니다.

### 운영 가능한 업데이트 판단 기준

베이스 이미지 업데이트는 CVE 개수 하나만 보고 바로 배포할 일이 아닙니다. 해당 취약점이 컨테이너에서 실제로 도달 가능한지, 서비스가 사용하는 라이브러리와 관련 있는지, 수정 이미지가 호환성 문제를 만들 가능성은 없는지, 긴급 완화책이 있는지를 함께 판단합니다. 그렇다고 위험도를 낮게 보려고 취약점 보고를 무시해서도 안 됩니다. 판단 근거, 대상 digest, 테스트 결과, 배포 시점을 남겨 두면 나중에 왜 갱신을 했거나 미뤘는지 설명할 수 있습니다.

예를 들어 Java 애플리케이션의 JRE 베이스를 갱신했을 때는 애플리케이션 단위 테스트만 성공했다고 끝내지 않습니다. TLS 연결, 시간대 데이터, 문자 인코딩, 네이티브 라이브러리, start script의 셸 호환성처럼 런타임 경계에서 바뀔 수 있는 부분을 확인합니다. 업데이트가 곧바로 위험하다는 뜻이 아니라, 이미지 교체를 일반 라이브러리 의존성 업데이트와 같은 변경으로 취급하자는 뜻입니다.

## 실행 계약: ENTRYPOINT, CMD, 종료 신호

이미지를 실행하는 사람과 오케스트레이터는 Dockerfile에 적힌 실행 방식을 계약처럼 사용합니다. `ENTRYPOINT`는 컨테이너가 기본으로 실행할 프로그램을, `CMD`는 기본 인수 또는 대체 가능한 명령을 표현하는 데 쓸 수 있습니다. 둘을 어떻게 조합할지는 서비스마다 다르지만, 중요한 것은 개발 환경·CI·Kubernetes manifest가 같은 의도를 해석하도록 만드는 것입니다. shell 형식 명령은 변수 확장에 편할 수 있지만 신호 전달과 인수 처리가 예상과 달라질 수 있으므로, 특별한 이유가 없다면 exec 형식의 배열 표기를 검토합니다.

컨테이너의 PID 1 프로세스는 종료 신호를 받아 정리하고 종료할 책임이 있습니다. HTTP 서버가 새 요청을 받지 않고 진행 중인 요청을 마무리할 시간을 주려면, 애플리케이션과 종료 유예 시간, load balancer의 연결 해제 순서가 맞아야 합니다. Dockerfile만 바꿔 해결되는 문제는 아니지만, start script가 신호를 가로채거나 자식 프로세스를 회수하지 않는 구조라면 배포 중 요청이 끊기거나 프로세스가 남을 수 있습니다.

`HEALTHCHECK`도 실행 계약의 일부입니다. 단순히 프로세스가 떠 있는지, 실제로 요청을 받을 준비가 되었는지, 외부 의존성이 잠깐 불안정할 때 컨테이너를 무한 재시작해야 하는지를 구분해야 합니다. Kubernetes를 쓴다면 Docker의 healthcheck와 liveness·readiness probe를 중복해 무조건 넣기보다, 어느 신호가 어떤 복구 행동을 일으키는지 정합니다. 준비되지 않은 인스턴스를 트래픽에서 빼는 check와, 멈춘 프로세스를 재시작하는 check는 같은 질문이 아닙니다.

## BuildKit cache mount를 쓸 때의 경계

BuildKit의 cache mount는 패키지 다운로드처럼 결과물 이미지에 넣을 필요 없는 중간 파일을 단계 간에 재사용하게 해 줍니다. 예를 들어 패키지 관리자의 다운로드 cache를 mount하면 lock 파일은 바뀌지 않았는데 매번 원격에서 같은 archive를 받는 일을 줄일 수 있습니다. 그러나 mount 자체가 의존성 버전을 고정하지는 않습니다. 버전을 고정하는 주체는 lock 파일과 설치 명령이고, cache는 그 결과를 더 빨리 얻도록 도울 뿐입니다.

cache mount에는 무엇을 저장하는지 먼저 확인해야 합니다. package manager가 인증 정보, private registry URL, 컴파일 산출물, 운영체제나 CPU에 종속적인 바이너리를 cache에 넣을 수 있습니다. 서로 다른 운영체제·아키텍처·권한 수준의 runner가 같은 저장소를 공유하면 호환성 오류나 정보 노출이 생길 수 있습니다. cache ID를 서비스·플랫폼·패키지 관리자 기준으로 나누고, 민감한 값은 cache가 아니라 secret 전달 경로로 다루는 편이 안전합니다.

또한 cache hit가 정상이라는 가정만으로 CI를 설계하면 깨끗한 환경에서 깨지는 Dockerfile을 놓칠 수 있습니다. 새 runner나 장애 복구 시에는 cache가 없다는 조건이 기본이 될 수 있습니다. 정기적으로 cache를 비운 빌드가 성공하는지, 외부 registry가 일시적으로 느릴 때 실패가 명확한지, 실패한 설치 결과가 다음 빌드에 재사용되지 않는지를 확인하면 cache가 편의 기능을 넘어 장애 원인이 되는 일을 줄일 수 있습니다.

## 산출물 승격과 롤백의 흐름

개발·검증·운영 환경마다 이미지를 새로 빌드하면 같은 소스 commit이라도 시간·외부 dependency·베이스 이미지 차이로 결과가 달라질 수 있습니다. 검증을 통과한 image digest 하나를 다음 환경으로 승격하는 방식은 이 차이를 줄입니다. 여기서 승격은 이미지를 복사하거나, 승인된 digest를 다음 배포 manifest가 참조하게 하는 일입니다. 환경마다 설정은 달라도 실행 파일 자체는 같다는 점이 핵심입니다.

롤백도 태그 이름을 이전 값으로 바꾸는 것만으로 충분하지 않을 수 있습니다. 이전 digest가 실제로 보관돼 있는지, 그 이미지가 현재 데이터베이스 스키마와 호환되는지, feature flag나 환경 변수 변경을 함께 되돌려야 하는지 확인해야 합니다. 특히 데이터 migration이 들어간 릴리스는 애플리케이션 이미지의 되돌림과 데이터의 되돌림을 별도로 계획해야 합니다. 이미지 빌드의 품질은 배포 성공뿐 아니라 문제가 생겼을 때 어떤 상태로 안전하게 복귀할 수 있는지까지 포함합니다.

릴리스 기록에는 사람이 읽는 버전, Git commit, image digest, 빌드 파이프라인 실행 ID, SBOM 위치, 적용한 환경 설정의 식별자를 연결할 수 있습니다. 모든 값을 로그에 과하게 복사할 필요는 없지만, 장애 조사자가 어느 시스템에서 관계를 따라갈 수 있는지는 정해야 합니다. 이 연결이 없으면 취약점 공지나 장애가 났을 때 ``어떤 이미지가 실행 중인가``부터 다시 추측하게 됩니다.

## 팀이 합의할 최소 빌드 정책

Dockerfile 품질을 개인의 숙련도에만 맡기면 서비스마다 context 처리, 비밀 전달, 태그 정책이 달라집니다. 처음부터 복잡한 플랫폼을 만들기보다, 팀이 합의한 작은 정책을 코드 리뷰와 CI에 적용하는 것으로 시작할 수 있습니다. 예를 들어 lock 파일이 있는 프로젝트는 결정적 설치 명령을 사용한다, `.env`와 키 파일은 build context에서 제외한다, production 이미지는 root로 실행하지 않는다, 배포 기록은 digest를 남긴다처럼 검증 가능한 문장으로 정합니다.

정책에는 예외 절차도 필요합니다. 레거시 애플리케이션이 root 권한이나 특정 진단 도구를 당장 필요로 한다면, 금지 규칙을 몰래 우회하기보다 이유·영향·완화책·재검토 시점을 기록합니다. 모든 컨테이너를 같은 모습으로 만드는 것이 목표가 아니라, 예외가 위험을 숨기지 않게 하는 것이 목표입니다. 작은 정책을 실제 실패 사례와 함께 다듬으면 체크리스트가 형식적인 문서가 되는 일을 피할 수 있습니다.

## 한계와 적용 기준 Q&A

### Q. 이미지를 가장 작게 만들면 가장 안전한가요?

A. 작은 이미지는 전송·저장 비용과 불필요한 도구를 줄이는 데 도움이 되지만, 안전성을 단독으로 보장하지 않습니다. 취약한 라이브러리, root 실행, 비밀 노출, 잘못된 네트워크 권한은 작은 이미지에도 있을 수 있습니다. 크기·재현성·취약점·런타임 권한을 함께 보세요.

### Q. Docker build cache를 CI에서 공유해도 되나요?

A. 가능하지만 캐시 저장소의 쓰기 권한과 격리를 확인해야 합니다. 신뢰하지 않는 branch나 외부 기여자가 캐시를 오염시킬 수 있는지, 비밀이 cache layer에 포함되는지, cache miss가 발생해도 깨끗한 빌드가 되는지를 점검하세요.

### Q. Multi-stage build는 모든 애플리케이션에 필요한가요?

A. 컴파일·번들링 도구가 최종 실행에 필요 없고 최종 산출물이 명확할 때 특히 유용합니다. 이미 작은 interpreter runtime이 필요하거나 debug 도구가 운영 절차상 필요한 경우도 있으므로, 관례로 강제하지 말고 최종 이미지에 필요한 파일을 기준으로 판단하세요.

### Q. 이미지 태그를 digest로 고정하면 업데이트를 놓치지 않나요?

A. digest 고정은 같은 입력의 재현성을 높이지만 업데이트를 자동으로 받지 않습니다. 베이스 이미지 갱신을 감지하고 검토·테스트·배포하는 별도 프로세스가 있어야 합니다. 고정과 최신 보안 패치 사이의 균형을 운영 절차로 해결해야 합니다.

## 마무리

Docker 이미지 빌드는 배포 직전의 포장 작업이 아니라, 어떤 입력을 신뢰하고 어떤 결과를 실행할지 정하는 공급망 단계입니다. build context를 줄이고, lock 파일과 캐시를 올바르게 사용하며, build와 runtime을 분리하고, 비밀·권한·업데이트를 함께 관리하세요. 그러면 더 빠른 빌드뿐 아니라 같은 코드를 더 예측 가능하고 안전하게 배포할 수 있습니다.
