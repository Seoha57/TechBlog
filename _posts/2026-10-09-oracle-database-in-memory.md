보고서 쿼리가 느리다는 이유만으로 테이블을 다른 데이터베이스로 옮겨야 할까? 운영 데이터베이스에는 주문 처리처럼 한 행을 빠르게 찾고 바꾸는 OLTP(Online Transaction Processing, 온라인 트랜잭션 처리) 작업과, 많은 행을 읽어 합계·그룹화·필터링하는 분석 작업이 함께 있을 수 있습니다. 전자는 행 단위 접근이 편하고, 후자는 필요한 열만 대량으로 훑는 열 단위 접근이 유리합니다. 한 가지 저장 형식만으로 두 성격의 일을 모두 가장 잘 처리하기는 어렵습니다.

**Oracle Database In-Memory**는 이 문제를 해결하기 위해 Oracle Database 안에 IM Column Store(In-Memory Column Store, 메모리 내 열 저장소)를 추가하는 기능 집합입니다. 원래 테이블·인덱스·버퍼 캐시를 버리고 별도 데이터베이스를 만드는 방식이 아닙니다. 디스크와 버퍼 캐시에 있는 행 형식(row format)을 유지하면서, 선택한 테이블·파티션·열의 트랜잭션 일관된 열 형식 사본을 SGA(System Global Area, Oracle 인스턴스가 공유하는 메모리 영역)에 유지합니다. Oracle은 실행하는 SQL의 성격에 따라 행 형식과 열 형식 중 적절한 경로를 사용할 수 있습니다.

여기서 “메모리에 있으니 무조건 빠르다”라고 이해하면 곤란합니다. IM Column Store는 용량 제한이 있는 SGA를 사용하고, 처음 채우는 시간, 압축 방식, 갱신 빈도, 어떤 열을 대상으로 할지, 라이선스·서비스 조건, Oracle RAC와 재시작 뒤의 상태까지 고려해야 합니다. 이 글은 특정 환경의 성능 수치를 주장하지 않고, 어떤 쿼리와 객체가 후보인지부터 운영에서 확인해야 할 경계까지 설명합니다.

## 먼저 알아둘 기반 기술: SGA·버퍼 캐시·행 저장·열 저장·실행 계획

Oracle 인스턴스의 **SGA(System Global Area)** 는 데이터베이스 프로세스가 공유하는 메모리 영역입니다. 여기에는 데이터 블록을 보관하는 buffer cache, SQL·PL/SQL 정보를 관리하는 shared pool, redo 관련 영역 등 여러 구성 요소가 있습니다. 버퍼 캐시는 디스크에서 읽은 데이터 블록을 재사용해 I/O를 줄이는 역할을 합니다. 중요한 점은 버퍼 캐시가 기본적으로 테이블의 **행(row)** 을 포함한 블록을 다룬다는 것입니다. 고객 한 명의 주문을 찾는 쿼리는 고객 행과 관련 인덱스 블록을 빠르게 찾는 방식에 잘 맞습니다.

행 저장은 한 레코드의 열을 가까이 둡니다. `orders` 테이블에서 주문 하나를 조회해 상태를 변경하려면 주문번호·고객·금액·상태 같은 열을 함께 읽고 쓰므로 행 형식이 자연스럽습니다. 반면 “지난 1년의 주문에서 지역별 월 매출과 평균 할인율을 계산한다”는 쿼리는 수백만 행의 모든 열이 아니라 `order_date`, `region`, `amount`, `discount` 정도만 필요할 수 있습니다. 행 형식으로 전체 행을 많이 읽으면 쓰지 않는 열까지 메모리·CPU 경로를 지나게 됩니다.

**열 저장(columnar format)** 은 같은 열의 값을 함께 보관해 필요한 열만 빠르게 읽고, 값 분포에 맞는 압축과 벡터화된 처리에 유리하게 만드는 방식입니다. 분석 쿼리의 `WHERE`, `GROUP BY`, `SUM`, `COUNT`는 특정 열을 넓게 스캔하는 일이 많으므로 열 형식과 잘 맞습니다. 하지만 열 저장이 언제나 우수한 것은 아닙니다. 단건 행 조회, 자주 변경되는 좁은 행, 작은 테이블은 기존 버퍼 캐시·인덱스가 이미 충분히 효율적일 수 있습니다.

**실행 계획(execution plan)** 은 옵티마이저가 SQL을 처리하기 위해 선택한 접근·조인·정렬·집계의 절차입니다. 같은 SQL도 통계, 바인드 값, 인덱스, 메모리 상태, 객체 population 여부에 따라 다른 계획을 택할 수 있습니다. Database In-Memory를 켠 뒤에는 “이 기능을 사용했다”는 설정만 보지 말고 `EXPLAIN PLAN`, `DBMS_XPLAN` 등으로 실제 계획에 `TABLE ACCESS IN MEMORY FULL` 같은 연산이 나타나는지 확인해야 합니다. 계획이 바뀌지 않았다면 원인은 쿼리 성격, 객체 선택, 메모리 부족, 통계, 다른 더 저렴한 접근 경로일 수 있습니다.

## Database In-Memory의 핵심: 하나의 데이터에 두 접근 경로를 둔다

Database In-Memory의 핵심은 **이중 형식(dual-format)** 입니다. 데이터 파일의 영구 저장 형식이나 buffer cache의 행 형식을 열 형식으로 교체하는 것이 아니라, 선택된 객체의 열 형식 사본을 In-Memory Area에 population합니다. 원본 테이블에 `INSERT`, `UPDATE`, `DELETE`가 발생해도 기존 Oracle의 undo·redo와 버퍼 캐시 기반 처리 방식은 유지됩니다. 쿼리는 일관된 결과를 받아야 하므로, 열 형식 사본과 원본의 변경 사항을 내부적으로 조합해 읽습니다.

이 구조는 OLTP와 분석을 모두 같은 데이터베이스에서 처리하려는 조직에 의미가 있습니다. 주문을 생성하는 트랜잭션은 기존 행 형식·인덱스 경로를 계속 쓰고, 주문 이력을 분석하는 대시보드는 열 형식에서 필요한 열을 빠르게 읽을 수 있습니다. 애플리케이션 SQL을 전면 재작성하지 않고도 분석 쿼리가 혜택을 볼 수 있다는 점이 장점입니다. 그러나 “분석 전용 컬럼형 DB를 완전히 대체한다”는 뜻은 아닙니다. 동시 사용자 수, 데이터 크기, ETL, 리소스 격리, 비용, 운영 모델까지 포함한 전체 아키텍처 판단은 별도로 해야 합니다.

IM Column Store는 전통적인 Oracle 데이터 블록을 그대로 모아 둔 공간이 아니라, 열 데이터와 메타데이터를 최적화된 저장 단위로 관리합니다. 문서에서는 **IMCU(In-Memory Compression Unit)** 를 열 압축 단위로 설명합니다. IMCU에는 여러 열의 값과 메타데이터가 들어가며, 조건에 맞지 않는 저장 단위를 건너뛰는 pruning에도 활용됩니다. 예를 들어 특정 기간의 매출만 찾을 때 해당 기간이 전혀 없는 IMCU를 읽지 않을 수 있습니다. 이는 인덱스 하나를 새로 만들었다는 것과 다른 방식의 최적화입니다.

## 시작점은 DDL이 아니라 후보 쿼리 분류다

Database In-Memory를 도입할 때 흔한 실수는 큰 테이블에 바로 `INMEMORY`를 붙이는 것입니다. 먼저 어떤 SQL이 병목인지, 그 SQL이 정말 대량 스캔·필터·조인·집계를 하는지 확인해야 합니다. 자동화된 보고서, BI 대시보드, 월말 집계, 여러 열을 훑는 운영 조회가 좋은 후보가 될 수 있습니다. 반대로 PK(Primary Key, 기본 키)로 한 행을 찾는 API, 아주 작은 코드성 테이블, 이미 선택도가 높은 인덱스를 효율적으로 쓰는 쿼리는 효과가 제한적일 수 있습니다.

다음처럼 후보를 분류해 볼 수 있습니다.

- 넓은 기간의 사실 테이블을 읽고 소수 열을 집계하는가?
- `WHERE` 조건으로 많은 행을 제거하고 `GROUP BY` 또는 조인을 수행하는가?
- 같은 분석 SQL이 반복되며, 응답 시간이 업무 화면·보고서 마감에 영향을 주는가?
- 객체가 너무 커서 전체를 메모리에 올릴 수 없을 때 파티션·열 단위로 좁힐 수 있는가?
- 해당 객체의 DML 빈도와 갱신 지연 허용 범위는 어떤가?
- 메모리를 추가로 확보해도 buffer cache·PGA·다른 Oracle 기능과 경합하지 않는가?

후보를 고른 다음에야 객체 수준의 설정을 검토합니다. `INMEMORY` 절은 테이블, 파티션·서브파티션, materialized view, 경우에 따라 열 수준으로 지정할 수 있습니다. 파티션 테이블이라면 최근 3개월 파티션만 분석 화면에서 자주 읽는지, 과거 전체를 월말에만 읽는지에 따라 대상이 달라집니다. 모든 파티션을 같은 우선순위로 메모리에 올리는 것보다, 실제 접근 패턴을 따라 범위를 좁히는 것이 SGA 사용과 재population 시간을 통제하는 데 유리합니다.

## INMEMORY_SIZE와 Population: 켰다는 것과 채워졌다는 것은 다르다

IM Column Store를 사용하려면 초기화 파라미터 **`INMEMORY_SIZE`** 를 0보다 크게 설정해 In-Memory Area를 확보합니다. Oracle 문서에 따르면 기본값 0은 비활성 상태를 뜻하며, 이 크기는 인스턴스의 메모리 계획 안에서 고려해야 합니다. 초기화 파라미터 변경과 인스턴스 재시작이 필요한 조건, 서비스·라이선스별 제한은 사용하는 Oracle 버전과 배포 형태의 공식 문서를 확인해야 합니다.

메모리 크기만 정해도 데이터가 자동으로 모두 들어가는 것은 아닙니다. **population** 은 원본 행 형식 데이터를 열 형식으로 IM Column Store에 채우는 과정입니다. `INMEMORY` 속성을 준 객체라도 실제 population이 끝나기 전에는 원하는 열 형식 접근을 하지 못할 수 있습니다. 재시작 뒤에도 다시 population 시간이 들 수 있습니다. 그래서 부팅 직후 대시보드가 느려졌다는 현상을 단순한 “캐시 미스”로만 보지 말고, population 상태·우선순위·객체 크기·동시 부하를 확인해야 합니다.

아래 DDL은 의미를 보여 주는 예시입니다. 운영 데이터베이스에 적용할 때는 변경 승인, 메모리 산정, 롤백·검증 계획을 먼저 갖춰야 합니다.

```sql
ALTER TABLE sales_fact INMEMORY;

ALTER TABLE sales_fact
  MODIFY PARTITION sales_2026_q4 INMEMORY PRIORITY HIGH;

ALTER TABLE sales_fact
  INMEMORY MEMCOMPRESS FOR QUERY LOW;
```

`PRIORITY`는 어떤 객체를 먼저 population할지에 영향을 주는 정책 도구입니다. 모든 객체에 높은 우선순위를 주면 우선순위라는 정보가 사라집니다. 보고서 시작 직후 반드시 필요한 작은 집계 테이블, 사용자 화면에서 반복 접근하는 최근 파티션처럼 이유가 명확한 대상에만 사용하고, 우선순위와 대상 선정 근거를 운영 문서에 남기는 편이 좋습니다.

객체가 메모리보다 크면 일부만 population될 수 있습니다. 이 경우 Oracle은 한 쿼리 안에서도 In-Memory와 buffer cache 경로를 함께 쓸 수 있습니다. 이것은 오류가 아니라 용량·접근 패턴에 따른 동작일 수 있습니다. 다만 성능을 판단할 때는 “테이블에 INMEMORY가 붙었는가”가 아니라 “필요한 파티션·열이 population됐는가, 실제 SQL은 어느 경로를 얼마나 썼는가”를 구분해야 합니다.

## 압축의 목표는 디스크 절약만이 아니다

IM Column Store의 압축은 메모리 사용량과 스캔 성능 사이의 균형을 조정합니다. 일반적으로 더 높은 압축은 적은 메모리로 더 많은 데이터를 담는 데 유리할 수 있지만, 쿼리 실행 때 CPU 비용이 커질 수 있습니다. 반대로 query 성능에 유리한 선택은 더 많은 메모리를 쓸 수 있습니다. Oracle 문서는 `FOR CAPACITY`와 `FOR QUERY` 계열을 이러한 트레이드오프 관점에서 설명합니다.

따라서 “가장 강한 압축”이나 “가장 빠른 압축”이라는 답을 전 테이블에 적용하면 안 됩니다. 매일 대량 스캔하는 매출 사실 테이블과 거의 조회하지 않는 과거 이력 테이블은 접근 빈도·열 분포·메모리 가치가 다릅니다. 같은 테이블 안에서도 분석에 필요한 일부 열만 대상으로 삼을 수 있다면, 전체 테이블을 통째로 올리는 것보다 합리적일 수 있습니다. 압축 정책은 테이블의 이름이 아니라 쿼리와 데이터의 실제 사용 패턴을 기준으로 정해야 합니다.

메모리 산정도 데이터 파일 크기만 보고 계산할 수 없습니다. 행 형식 크기, 선택한 열·파티션, 압축 방식, 메타데이터, 동시 population, SGA의 다른 구성 요소를 함께 보아야 합니다. 운영 전에 테스트 환경이나 대표 워크로드에서 후보 객체별 footprint와 쿼리 계획을 확인하고, `V$INMEMORY_AREA`, `V$IM_SEGMENTS` 등 해당 버전에서 제공하는 동적 성능 뷰로 실제 사용 상태를 관찰하는 절차를 세웁니다. 뷰의 열과 권한은 버전에 따라 확인해야 하며, 모니터링 계정에 과도한 권한을 주지 않는 것도 중요합니다.

## 실행 계획과 통계를 같이 본다

Database In-Memory를 활성화했다고 해서 옵티마이저가 무조건 full scan을 선택해야 하는 것은 아닙니다. 조건의 선택도가 매우 높고 적절한 인덱스가 있으면 index range scan이 더 저렴할 수 있습니다. 반대로 분석 SQL은 `TABLE ACCESS IN MEMORY FULL` 같은 연산을 통해 열 형식 접근의 혜택을 받을 수 있습니다. 한 SQL의 전후 계획을 비교할 때는 elapsed time 하나보다 logical reads, CPU, I/O, row count, 조인 방식, 병렬 실행 여부, 바인드 값 분포를 함께 봐야 합니다.

통계가 오래되었거나 데이터 분포가 바뀌면, 좋은 IM Column Store가 있어도 옵티마이저가 적절하지 않은 계획을 고를 수 있습니다. 이는 In-Memory 기능의 실패가 아니라 통계·SQL 설계·인덱스·리소스 경합이 얽힌 데이터베이스 문제일 수 있습니다. 성능 문제가 있을 때 `INMEMORY`를 더 넓게 적용하는 것보다, 먼저 실제 SQL과 계획을 확보해 병목이 스캔인지 조인인지 정렬·TEMP인지 잠금인지 구분해야 합니다.

```sql
SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));
```

이 명령은 최근 커서의 실행 통계를 보는 데 쓰일 수 있지만, 운영 환경에서 누구의 커서를 보는지와 진단 권한을 주의해야 합니다. 임의의 고비용 SQL을 재실행하거나 전체 통계를 수집하는 식의 조치는 다른 세션에 영향을 줄 수 있습니다. 성능 분석은 재현 가능한 식별자(SQL ID), 관찰 시간대, 대표 바인드 값, 변경 전후를 기록하는 방식이 안전합니다.

## DML·일관성·재시작: 분석 전용 사본이라고 방치하면 안 된다

Database In-Memory는 갱신 가능한 운영 테이블에도 적용할 수 있으며, Oracle은 열 형식 사본을 트랜잭션 일관되게 유지합니다. 그렇다고 DML이 많은 모든 테이블을 IM Column Store에 올리는 것이 공짜라는 뜻은 아닙니다. 대량 적재·삭제·갱신이 빈번한 객체는 population·변경 추적·메모리 자원과 관련한 비용을 평가해야 합니다. 보고서 성능만 보고 적용했다가 주문 처리의 CPU·메모리 여유를 줄이면 시스템 전체에는 손해일 수 있습니다.

특히 ETL(Extract, Transform, Load) 배치가 끝난 직후 분석이 시작되는 환경에서는 로드 시점, population 완료 시점, 보고서 시작 시점을 함께 설계해야 합니다. 배치가 끝나자마자 무거운 집계를 시작하면 아직 원하는 파티션이 충분히 population되지 않았을 수 있습니다. 반대로 오래된 고정 이력처럼 거의 바뀌지 않는 파티션은 안정적인 후보가 될 수 있습니다. 업무 시간대, 배치 창, 재시작 뒤 warm-up 시간을 운영 절차에 포함해야 합니다.

RAC(Real Application Clusters)에서는 인스턴스별 IM Column Store와 객체 분배 정책까지 추가로 고려해야 합니다. 한 인스턴스에서만 관찰한 population 상태를 클러스터 전체 상태로 일반화하면 안 됩니다. 고가용성·standby 구성에서 어떤 인스턴스에 얼마를 할당하고 장애 조치 뒤 어떤 성능 변화를 허용할지 역시 아키텍처 수준의 결정입니다. 기능 설정값보다 서비스 수준 목표와 장애 시 운영 시나리오가 먼저입니다.

## 가상의 업무 예시: 주문 사실 테이블의 최근 분기 보고서

한 쇼핑 서비스에 `sales_fact`라는 큰 주문 사실 테이블이 있다고 가정해 보겠습니다. 웹 주문을 생성·취소하는 API는 주문번호로 한 행을 찾아 갱신합니다. 동시에 운영 대시보드는 최근 90일의 주문을 지역·채널·상품군으로 묶어 5분마다 집계합니다. API와 대시보드는 같은 테이블을 보지만, 접근 방식은 다릅니다.

첫 단계는 대시보드 SQL의 실제 계획과 실행 빈도를 확인하는 것입니다. 최근 파티션을 넓게 읽고 날짜·지역·금액·할인 열만 쓴다면 최근 분기 파티션과 그 분석 열이 In-Memory 후보가 될 수 있습니다. 반면 5년치 이력 파티션을 모두 올리면 SGA를 과도하게 쓰고 재시작 뒤 population 시간만 늘어날 수 있습니다. 특정 분기 파티션에 `INMEMORY`를 적용하고, 그 파티션이 population됐는지 확인한 뒤 대표 대시보드 SQL의 계획·응답·CPU·다른 OLTP 지표를 비교합니다.

성공 기준도 “INMEMORY 절을 붙였다”가 아니라 “대시보드의 목표 응답 시간과 주문 API의 지연·오류 목표가 함께 유지된다”로 둡니다. 대시보드가 빨라져도 buffer cache가 줄어 API의 물리 I/O가 늘거나, population이 업무 시작 시간에 CPU를 과도하게 쓰면 조정이 필요합니다. 부족하면 대상 파티션, 압축, 우선순위, 메모리 크기, 대시보드 SQL 자체를 다시 검토합니다. Database In-Memory는 병목을 관측한 뒤 적용할 수 있는 선택지이지, SQL·인덱스·파티션 설계·용량 계획을 대신하는 버튼이 아닙니다.

## 도입 순서: 작게 선택하고, 실제 접근을 검증하고, 넓힌다

안전한 도입은 다음 순서로 요약할 수 있습니다. 먼저 workload를 OLTP·분석·배치로 분류하고, 분석 쿼리 중 비용과 빈도가 높은 후보를 찾습니다. 둘째, 메모리 예산을 세워 SGA의 다른 구성 요소와 충돌하지 않는지 검토합니다. 셋째, 작은 테이블 또는 최근 파티션부터 `INMEMORY`를 지정하고 population 상태·실행 계획·시스템 지표를 관찰합니다. 넷째, 재시작·장애 조치·배치 직후에도 기대한 경로가 유지되는지 검증합니다. 마지막으로 근거가 있는 대상만 단계적으로 넓힙니다.

이 과정에는 롤백도 포함해야 합니다. INMEMORY 속성을 되돌리는 방법, `INMEMORY_SIZE` 변경의 영향과 재시작 조건, 성능 문제 때 확인할 SQL·뷰·지표, 변경 소유자를 문서화합니다. 장애 중에 메모리가 부족하다고 무작정 파라미터를 줄이면 더 넓은 성능 변화를 만들 수 있습니다. 데이터베이스 메모리는 기능별로 독립된 통이 아니라 전체 SGA와 운영 부하 안에서 경합한다는 사실을 기억해야 합니다.

## 파티션·열 단위 선택: 큰 테이블을 한 덩어리로 보지 않는다

대부분의 큰 운영 테이블은 시간이나 업무 단위로 접근 온도가 다릅니다. 최근 7일 주문은 고객 화면과 운영 대시보드에서 계속 읽지만, 3년 전 주문은 감사나 월간 분석 때만 읽을 수 있습니다. 이때 테이블 전체를 In-Memory 대상으로 삼으면 오래된 데이터까지 SGA 예산을 사용하게 됩니다. 파티션을 사용한다면 최근 파티션에 더 높은 population 우선순위를 주고, 과거 파티션은 필요할 때만 접근하거나 다른 분석 경로를 쓰는 식으로 구분할 수 있습니다.

분석 SQL이 사용하는 열도 중요합니다. 사실 테이블에 수십 개 열이 있어도 대시보드가 날짜·지역·상품군·금액·할인만 읽는다면, 그 외 대용량 텍스트·감사 열까지 같은 가치로 올릴 이유가 없을 수 있습니다. 단, 열 선택을 지나치게 공격적으로 하면 새 보고서가 다른 열을 읽을 때 In-Memory 이점을 잃고, 운영자가 왜 일부 열만 빠른지 이해하기 어려워질 수 있습니다. 따라서 ‘현재 쿼리에서 쓴 열’만 기계적으로 고르기보다, 안정적인 보고서 모델과 변경 예정, 메모리 예산을 함께 검토해야 합니다.

파티션 교체나 월 단위 적재가 있는 환경에서는 새 파티션이 언제 만들어지고 `INMEMORY` 속성이 어떻게 상속되는지도 확인합니다. 템플릿·테이블스페이스·DDL 배포 방식에 따라 새 객체가 의도한 정책을 따르지 않을 수 있습니다. 월초에 새 파티션이 분석 대상인데 population 후보에서 빠졌다면, 평소에는 보지 못하던 성능 저하가 발생할 수 있습니다. 객체 속성 검증을 배치 완료 체크리스트나 배포 점검에 넣고, 특정 파티션이 실제로 IM Column Store에 들어왔는지 관찰하는 이유입니다.

또한 파티션 pruning과 In-Memory pruning은 관련 있지만 같은 기능이 아닙니다. 파티션 pruning은 조건에 맞지 않는 파티션 자체를 읽지 않는 것이고, In-Memory에서의 pruning은 대상 파티션 안에서 조건과 맞지 않는 저장 단위를 줄이는 데 도움을 줄 수 있습니다. 좋은 파티션 키와 SQL 조건은 여전히 중요합니다. `TRUNC(order_date)`처럼 컬럼에 함수를 씌워 파티션 조건을 흐리게 만들거나, 바인드·통계 문제로 너무 넓은 범위를 스캔하면 In-Memory만으로 설계 문제가 사라지지 않습니다.

## 관측 항목: 메모리 사용량과 비즈니스 쿼리를 같은 시간축에 둔다

운영에서 확인할 것은 In-Memory 영역의 사용량 하나가 아닙니다. 먼저 어떤 객체가 population됐고, 어떤 객체가 아직 아니며, 어떤 이유로 밀려났는지 봅니다. 둘째, 대표 SQL이 실제로 In-Memory 접근을 하는지와 그 SQL의 실행 시간·CPU·논리 읽기를 확인합니다. 셋째, 동일 시점에 buffer cache hit, 물리 I/O, TEMP 사용, PGA, host memory pressure, CPU run queue, OLTP 지연·오류율이 어떻게 바뀌는지 함께 봅니다.

예를 들어 `V$IM_SEGMENTS`에서 원하는 파티션이 population된 것을 확인했더라도 대시보드가 느릴 수 있습니다. 조인 순서가 나쁘거나, 대량 정렬이 TEMP를 쓰거나, 다른 세션이 CPU를 포화시키는 문제일 수 있습니다. 반대로 쿼리 하나가 빨라졌는데 API 지연이 증가했다면 SGA 여유가 줄었거나 CPU 경쟁이 늘었는지 조사해야 합니다. IM Column Store 지표는 기능 상태를, SQL·서비스·OS 지표는 사용자 영향을 보여 줍니다. 둘 중 하나만 보면 잘못된 결론을 내릴 수 있습니다.

관측에서 또 하나 중요한 것은 **population 완료까지의 시간**입니다. 인스턴스 재시작, 패치 후 재기동, 노드 장애 조치, 대량 데이터 적재 직후에는 평소 steady state와 다릅니다. 운영 대시보드가 업무 시작 5분 안에 준비돼야 한다면, 재시작 후 30분 동안 느린 것은 허용되지 않을 수 있습니다. 이 시간 목표를 정한 뒤 population priority·대상 범위·메모리 크기·재기동 절차를 시험해야 합니다. 단순히 “평상시 SQL이 빨랐다”는 검증으로는 충분하지 않습니다.

모니터링 계정의 권한도 설계해야 합니다. 성능 뷰를 보려면 권한이 필요하지만, 넓은 딕셔너리 접근 권한을 모든 운영 도구에 주는 것은 별도의 보안 위험입니다. 누가 SQL 텍스트·바인드 값·세션 정보를 볼 수 있는지, 민감한 식별자가 모니터링 로그에 남는지, 대시보드에서 원문을 얼마나 오래 보존하는지를 함께 검토합니다. 성능 관측은 기능을 쓰기 위한 부수 작업이 아니라 데이터 접근 경계의 일부입니다.

## Query Rewrite와 Materialized View를 대체하지 않는 이유

분석 성능을 개선하는 방법은 Database In-Memory 하나가 아닙니다. **Materialized View**는 복잡한 집계·조인 결과를 미리 계산해 두는 방법이고, query rewrite는 옵티마이저가 SQL을 적절한 materialized view로 바꿔 읽도록 돕는 기능입니다. ETL로 별도 분석 저장소를 만들거나, 파티션·인덱스·SQL을 개선하는 방법도 있습니다. 이들은 서로 배타적인 선택지가 아닙니다.

같은 집계를 수천 번 반복하고 결과의 갱신 지연을 허용할 수 있다면 materialized view가 더 직접적인 해법일 수 있습니다. 반대로 사용자가 필터·그룹을 다양하게 바꿔 미리 모든 집계 결과를 만들기 어렵다면 In-Memory 열 형식 스캔이 더 유연할 수 있습니다. 실시간성이 필요해도 모든 쿼리가 In-Memory에 적합한 것은 아닙니다. 어떤 계층이 어떤 비용을 떠안는지—적재 시 계산, SGA 메모리, 디스크, 운영 복잡도—를 비교해야 합니다.

이 비교는 기능 우열을 가르는 논쟁이 아니라, 데이터 제품의 요구를 구체화하는 과정입니다. 보고서가 몇 초 안에 보여야 하는지, 어느 시점의 데이터를 보여야 하는지, 새 필터 추가가 얼마나 잦은지, 배치 창은 얼마인지, 장애 때 어떤 성능 저하를 허용하는지를 먼저 합의하면 Database In-Memory를 어디에 둘지 판단하기 쉬워집니다.

## 변경 관리와 장애 대응: 메모리 기능도 서비스 계약의 일부다

`INMEMORY_SIZE`나 객체 속성 변경은 DBA 혼자만의 튜닝으로 끝나지 않을 수 있습니다. 메모리 재배분이 다른 워크로드에 영향을 줄 수 있고, 보고서팀은 응답 시간을 기대하게 되며, 인프라팀은 노드 용량·장애 조치 시간을 관리해야 합니다. 변경 요청에는 대상 객체, 예상 population 크기, 대표 SQL, 성공·실패 기준, 되돌리는 방법, 배포·재시작 창을 함께 적는 편이 좋습니다.

장애 중에는 우선 어떤 서비스 목표가 깨졌는지 확인합니다. 분석 쿼리만 느린지, OLTP도 영향을 받는지, 특정 인스턴스에서만 population이 부족한지, 재시작·적재·통계 수집 같은 사건 직후인지 분리합니다. 그러고 나서 메모리 설정·population 상태·실행 계획·OS 압력을 차례대로 봅니다. `INMEMORY_SIZE`를 급하게 확대하거나 전체 객체를 flush하는 조치는 다른 워크로드를 더 흔들 수 있으므로, 원인과 롤백 경로를 모른 채 실행하면 안 됩니다.

Database In-Memory의 가치는 빠른 스캔 자체뿐 아니라, 어떤 분석 부하를 메모리·열 형식 계층으로 옮길지 명시적으로 선택하게 해 준다는 데 있습니다. 그 선택을 성능 실험과 운영 책임으로 연결하면 기능은 안정적인 도구가 됩니다. 반대로 대상을 정하지 않은 채 SGA만 키우면, 비싼 메모리와 복잡한 상태만 늘고 왜 빨라졌거나 느려졌는지 설명하기 어려워집니다.

## 한계와 적용 기준 Q&A

### Q. 모든 테이블에 INMEMORY를 지정하면 더 빠르지 않나요?

A. 아닙니다. IM Column Store는 제한된 메모리 자원을 쓰며, 객체가 많아질수록 필요한 데이터를 제때 population하지 못할 수 있습니다. 단건 조회·작은 테이블·접근 빈도가 낮은 이력까지 모두 올리면 메모리 가치가 낮아집니다. 대량 스캔·집계가 반복되는 객체와 실제 필요한 파티션·열부터 선택해야 합니다.

### Q. In-Memory를 쓰면 인덱스와 파티션 설계는 필요 없나요?

A. 필요합니다. PK 조회, 높은 선택도의 필터, 제약 조건, 조인 경로, 데이터 수명 관리에는 인덱스와 파티션이 여전히 중요합니다. In-Memory는 특정 분석 접근을 가속할 수 있지만, 부정확한 통계·비효율 SQL·TEMP 병목·잠금 문제를 자동으로 해결하지 않습니다. 실행 계획과 업무 쿼리의 성격에 따라 역할을 나눠야 합니다.

### Q. 재시작 뒤 성능이 느려진다면 장애인가요?

A. 객체가 다시 population되는 동안에는 기대한 열 형식 접근이 충분히 준비되지 않았을 수 있습니다. 이것이 항상 장애는 아니지만, 업무 시작 직후 성능 목표를 못 맞춘다면 population 우선순위·대상·메모리·부팅 절차를 조정해야 합니다. 재시작과 장애 조치 시나리오를 정상 운영 검증에 포함하는 이유입니다.

### Q. 라이선스와 Base Level은 어떻게 확인해야 하나요?

A. 버전·배포 형태·에디션·서비스에 따라 사용 가능 기능과 제한이 달라질 수 있습니다. Oracle의 현재 Licensing Information과 해당 Database In-Memory 가이드를 확인하고, 계약·구매 담당자와 함께 적용 범위를 결정해야 합니다. 기술 문서의 예제만 보고 유료 옵션 사용을 전제하면 안 됩니다.

## 마무리

Oracle Database In-Memory는 운영 데이터의 행 형식을 버리지 않고도 분석 쿼리에 열 형식 접근을 제공하려는 기능입니다. 핵심은 메모리를 크게 잡는 일이 아니라, 어떤 SQL이 어떤 열과 파티션을 반복 스캔하는지 이해하고 그 객체가 실제로 population·실행 계획에서 활용되는지 검증하는 데 있습니다. OLTP와 분석의 균형, SGA 예산, 압축·재시작·RAC 운영, 라이선스 조건까지 함께 검토할 때 IM Column Store는 무작정 빠른 기능이 아니라 측정 가능한 데이터베이스 설계 도구가 됩니다.
