애플리케이션 개발자는 주문 한 건을 고객 정보·배송지·주문 항목·결제 상태가 중첩된 JSON 객체로 받고 싶어 합니다. 반면 DBMS 운영자는 주문, 주문 항목, 상품, 고객을 정규화한 테이블로 관리하고 싶어 합니다. 전자는 화면과 API에서 바로 쓰기 편하고, 후자는 중복을 줄이고 조인·제약 조건·분석 쿼리를 다루기 좋습니다. 둘 중 하나만 선택하면 다른 쪽은 변환 코드나 중복 저장소를 떠안기 쉽습니다.

Oracle Database의 **JSON Relational Duality Views**는 같은 관계형 테이블 데이터를 JSON 문서 형태와 테이블·열 형태로 모두 접근하게 하는 기능입니다. Duality View 자체가 JSON을 따로 저장하는 복사본은 아닙니다. 기본 테이블에 저장된 행을 읽을 때 JSON 계층으로 조립하고, 허용된 JSON 문서를 갱신할 때는 관련 테이블의 행으로 분해해 반영합니다. 따라서 API를 만드는 팀은 문서 중심의 객체를 사용할 수 있고, 보고서·배치·DBA는 같은 원본 데이터를 SQL로 다룰 수 있습니다.

이 기능은 “관계형 DB를 문서 DB로 완전히 바꾸는 버튼”이 아닙니다. 어떤 JSON 필드가 어떤 테이블·열을 뜻하는지, insert·update·delete를 어디까지 허용할지, 동시에 수정한 문서를 어떻게 감지할지, 기존 ORM과 REST 계층을 어떻게 연결할지는 별도 설계입니다. 특히 테이블 설계가 불분명한 상태에서 JSON 모양만 먼저 고정하면, duality view는 복잡한 매핑을 가리는 층이 될 수 있습니다.

이 글은 Oracle 환경에서 직접 실행한 성능 측정이나 운영 사례 보고서가 아닙니다. Oracle 공식 문서를 바탕으로 관계형·문서 모델의 차이와 duality view의 동작, 적용 판단 기준을 설명합니다. 실제 사용 가능 버전, 라이선스, ORDS·드라이버·GoldenGate 연동 범위는 조직이 쓰는 Oracle Database 에디션과 릴리스 문서를 별도로 확인해야 합니다.

## 먼저 알아둘 기반 기술: 관계형 모델, 정규화, JSON, View

**관계형 데이터베이스(relational database)** 는 데이터를 행과 열로 구성된 테이블에 저장하고, primary key·foreign key 같은 관계로 테이블을 연결하는 방식입니다. 주문 정보를 예로 들면 `orders`에는 주문 번호·고객 번호·상태를, `order_items`에는 주문 번호·상품 번호·수량을 둡니다. 고객 이름을 모든 주문 행에 복사하지 않고 `customers` 테이블에 한 번 보관하면 변경과 중복을 줄일 수 있습니다. SQL의 join은 이렇게 나뉜 데이터를 조회 목적에 맞춰 결합합니다.

**정규화(normalization)** 는 같은 사실을 여러 곳에 중복 저장해 불일치가 생기는 일을 줄이려는 설계 원칙입니다. 예를 들어 상품 이름을 모든 주문 항목에 적으면 상품명 변경 뒤 과거 주문을 어떻게 볼지, 어느 행을 고칠지 문제가 생깁니다. 다만 모든 데이터를 최대한 쪼개는 것이 항상 정답은 아닙니다. 조회 패턴·무결성·갱신 빈도·분석 요구에 따라 일부 값을 함께 저장하거나 별도 읽기 모델을 둘 수도 있습니다. 핵심은 데이터가 왜 중복됐고 어느 쪽이 원본인지 명확히 하는 일입니다.

**JSON(JavaScript Object Notation)** 은 객체·배열·문자열·숫자·불리언·null로 계층 데이터를 표현하는 텍스트 형식입니다. 웹 API에서 주문 한 건을 반환할 때 `items` 배열 안에 여러 항목을 넣는 모양이 자연스럽습니다. 하지만 JSON 문서가 편하다고 해서 관계와 무결성이 사라지는 것은 아닙니다. 같은 고객 주소가 여러 문서에 복제되거나, 문서 간 참조가 복잡해지면 업데이트와 조회가 어려워질 수 있습니다. JSON은 표현 형식이며, 저장·제약·트랜잭션 설계는 별도의 문제입니다.

DBMS의 **view(뷰)** 는 하나 이상의 테이블에 대한 질의를 이름 붙인 가상 테이블처럼 제공하는 기능입니다. 일반 view는 보통 `SELECT` 결과를 보여 주고, 어떤 경우에는 갱신도 가능하지만 조인·집계·계산식에 따라 제약이 생깁니다. JSON generation 함수로 JSON을 만들어 반환하는 read-only view도 만들 수 있습니다. Oracle 문서는 갱신 가능한 JSON 표현이 필요할 때 JSON-Relational Duality View를 별도로 사용하도록 구분합니다. 즉 JSON을 반환한다는 사실과 JSON 문서 단위로 안전하게 갱신할 수 있다는 사실은 다릅니다.

마지막으로 **API 표현 모델**과 **저장 모델**을 구분해야 합니다. 앱 화면에 필요한 JSON에는 고객 이름, 주문 상태, 배송지, 항목 배열이 한 번에 들어갈 수 있습니다. 하지만 저장소에서는 고객·주소·상품·주문 항목을 각각 제약 조건과 수명 주기에 맞게 관리할 수 있습니다. API의 편한 모양을 위해 저장 구조를 무조건 한 문서로 납작하게 만들거나, 반대로 저장 테이블을 그대로 API에 노출하면 두 쪽 모두 불편해질 수 있습니다. Duality View는 이 간극을 선언적으로 메우려는 한 가지 방법입니다.

## Duality View는 같은 데이터를 어떻게 두 번 보게 하는가

Duality View 정의에는 루트가 되는 테이블과 그 테이블에 연결된 관계, JSON 필드와 기본 열의 매핑이 들어갑니다. 예를 들어 `orders`를 루트로 잡고 `order_items`를 배열로 중첩하면 하나의 주문 행과 여러 주문 항목 행을 하나의 JSON 문서로 조립할 수 있습니다. 애플리케이션은 주문 문서를 읽고 수정하는 것처럼 보지만, Oracle은 정의된 매핑을 통해 관련 행을 읽고 씁니다.

이때 문서의 `_id`는 문서를 식별하는 역할을 합니다. 기본 테이블 primary key와 연결되는 경우가 일반적이며, 문서 단위의 조회·갱신·동시성 확인에 기준이 됩니다. 문서에서 보이지 않는 기본 열도 있을 수 있습니다. 예를 들어 내부 감사용 상태나 권한 확인에 필요한 열을 JSON 응답에 노출하지 않을 수 있습니다. 반대로 하나의 기본 열을 문서 안의 여러 표현에 활용할 수도 있으므로, 어떤 필드가 실제 원본 열인지 정의를 읽을 수 있어야 합니다.

문서를 읽는 흐름은 대략 다음과 같습니다. 클라이언트가 주문 `_id`를 요청하면 DB는 `orders` 행을 찾고, 정의된 관계를 따라 `order_items` 행을 가져오며, 지정한 속성 이름과 중첩 구조로 JSON 객체·배열을 만듭니다. 문서가 새 테이블에 영구 저장되어 있다가 복사되는 것이 아닙니다. 그래서 기본 테이블을 SQL로 직접 수정하면 다음 JSON 읽기에서도 변경이 반영됩니다. 반대로 문서 업데이트가 허용됐다면, DB는 바뀐 필드를 해당 테이블과 열의 변경으로 해석합니다.

다른 애플리케이션이 같은 테이블 위에 서로 다른 JSON 계층을 필요로 할 수도 있습니다. 고객 서비스는 주문 중심 문서가 필요하고, 상품 운영 도구는 상품 중심 문서가 필요할 수 있습니다. Duality View는 같은 기본 테이블들 위에 다른 JSON hierarchy를 정의할 수 있습니다. 이는 매우 편리하지만, view마다 같은 사실을 다른 필드명·다른 규칙으로 노출하면 API 계약이 분열될 위험도 있습니다. DB 객체를 만든 팀과 API 계약을 만든 팀이 필드의 의미·소유자·변경 정책을 합의해야 하는 이유입니다.

## 읽기 전용 JSON View와 갱신 가능한 Duality View의 차이

SQL/JSON 생성 함수로 `JSON_OBJECT`, `JSON_ARRAYAGG` 같은 결과를 만들어 API에 반환하는 방식은 오래전부터 가능합니다. 이 방식은 보고서나 조회 API에서 유용하고, 원하는 쿼리를 직접 작성해 JSON 모양을 제어할 수 있습니다. 하지만 일반적으로 그런 JSON generation view는 읽기 중심입니다. 문서를 받아 역으로 여러 테이블 행을 안전하게 갱신하려면 별도 DML·프로시저·트리거·애플리케이션 매핑 코드를 만들어야 할 수 있습니다.

Duality View는 어떤 문서·필드·기본 테이블에 insert, update, delete를 허용할지 선언하는 쪽에 초점이 있습니다. Oracle 문서 예시의 `WITH UPDATE INSERT DELETE` 같은 선언은 해당 view가 지원하는 문서 연산 범위를 나타냅니다. 모든 필드를 수정 가능하게 열어 두는 것이 기본 목표는 아닙니다. 예를 들어 주문의 배송 메모는 바꿀 수 있어도 확정된 결제 금액이나 감사 상태는 API에서 바꾸지 못하게 할 수 있습니다. JSON 문서가 한 덩어리로 보인다고 해서 그 안의 모든 데이터가 같은 변경 권한을 가져야 하는 것은 아닙니다.

읽기 전용 view가 더 좋은 경우도 많습니다. 레거시 테이블을 외부 시스템에 JSON으로 보여 주되 외부가 원본을 바꾸면 안 되는 경우, 분석·대시보드에서 복잡한 조인 결과를 JSON으로 직렬화하는 경우, 아직 데이터 소유권과 변경 규칙이 정리되지 않은 경우에는 갱신 권한을 열지 않는 편이 안전합니다. `POST`와 `PUT`를 빨리 만들기 위해 관계형 무결성 규칙을 문서 매핑으로 숨기면, 오류 원인과 롤백 경계가 더 흐려질 수 있습니다.

반대로 앱 객체가 자연스럽게 한 루트와 그 하위 항목으로 묶이고, 기본 테이블의 primary/foreign key 관계가 명확하며, 문서 단위의 생성·수정·삭제 권한을 설계할 수 있다면 duality view가 매핑 코드를 줄일 수 있습니다. 예를 들어 프로젝트와 하위 task를 한 문서로 관리하되 task의 소유·상태·정렬 규칙이 관계형 테이블 제약과 잘 맞는 경우입니다. 이때도 대량 분석, 복잡한 cross-document 조회, 배치 갱신은 기존 SQL 경로가 더 자연스러울 수 있습니다.

## 최소 예시로 보는 문서와 테이블의 매핑

다음 예시는 `orders`와 `order_items`의 관계를 주문 JSON으로 표현한다는 개념 예시입니다. 실제 문법과 지원 어노테이션은 Oracle 버전에 따라 확인해야 하며, 운영 데이터에 그대로 실행하는 DDL이 아닙니다.

```sql
CREATE JSON RELATIONAL DUALITY VIEW order_dv AS
  orders @insert @update
  {
    _id       : order_id,
    orderedAt : ordered_at,
    status    : status,
    items     : order_items @insert @update @delete
                [ { itemId : order_item_id,
                    productId : product_id,
                    quantity : quantity } ]
  };
```

이 정의가 표현하려는 JSON은 다음과 비슷합니다.

```json
{
  "_id": 9012,
  "orderedAt": "2026-09-25T08:30:00Z",
  "status": "PAID",
  "items": [
    { "itemId": 1, "productId": 130, "quantity": 2 },
    { "itemId": 2, "productId": 215, "quantity": 1 }
  ]
}
```

JSON이 편하다는 이유만으로 `status`를 아무 문자열로 바꾸게 하면 안 됩니다. 기본 테이블에 check constraint가 있다면 허용되지 않은 값은 거부돼야 하고, 재고·결제·배송 상태처럼 여러 테이블의 규칙이 얽힌 변경은 단순 문서 update가 아닌 저장 프로시저나 도메인 서비스가 담당하는 편이 나을 수 있습니다. Duality View는 데이터 모양의 변환을 돕지만, 업무 규칙을 새로 정의하지는 않습니다.

또한 주문 항목 배열의 의미를 정해야 합니다. 배열에서 항목 하나를 빼면 해당 `order_items` 행을 삭제하라는 뜻인지, 화면에서만 숨기라는 뜻인지, 이미 결제가 끝난 주문에서는 삭제를 금지해야 하는지에 따라 DML 권한이 달라집니다. 배열 순서가 업무적으로 중요하다면 정렬 열과 고유 식별자를 어떻게 유지할지도 설계해야 합니다. 문서 전체를 교체하는 API는 편해 보여도, 부분 수정과 경쟁 업데이트가 섞이면 의도하지 않은 항목이 사라질 수 있습니다.

## ETAG와 동시성: 마지막 저장이 모든 것을 덮지 않게 하기

두 사용자가 같은 주문 문서를 읽었다고 가정해 보겠습니다. 상담원 A는 배송 메모를 바꾸고, 상담원 B는 주문 항목 수량을 바꿉니다. A가 먼저 저장한 뒤 B가 오래된 문서 전체를 저장하면, B의 요청이 A의 메모를 이전 값으로 되돌릴 수 있습니다. 이런 문제를 **lost update(갱신 유실)** 라고 부릅니다. 관계형 DB의 트랜잭션 격리 수준과 별개로, API가 문서를 읽고 나중에 다시 쓰는 흐름에는 낙관적 동시성 제어가 필요할 수 있습니다.

Oracle duality view는 문서의 특정 시점 상태를 나타내는 **ETAG**를 활용해 갱신 충돌을 감지하는 방식을 지원합니다. 클라이언트는 읽을 때 받은 ETAG를 갱신 요청과 함께 보내고, DB는 그 뒤 관련 데이터가 바뀌었는지 확인합니다. ETAG가 일치하지 않으면 서버는 오래된 문서를 기반으로 한 수정임을 알려 주고, 클라이언트는 재조회·병합·사용자 확인 중 하나를 해야 합니다. ETAG는 잠금이 아니라 충돌을 알아차리는 장치입니다.

어떤 필드가 ETAG 계산에 참여하는지 결정하는 일은 중요합니다. 단순히 화면에 보이지 않는 감사 시간 변경까지 매번 충돌을 만들면 사용자는 너무 자주 재시도해야 합니다. 반대로 실제 업무 의미가 있는 가격·상태·항목 변경을 ETAG에서 제외하면 충돌을 놓칠 수 있습니다. Oracle 문서의 `@nocheck` 같은 어노테이션은 특정 필드를 ETAG 계산에서 제외하는 데 사용될 수 있는데, “충돌이 귀찮다”는 이유로 넓게 적용하면 데이터 보호 장치를 약하게 만들 수 있습니다.

ETAG가 있다고 해서 모든 병합을 DB가 알아서 해 주는 것은 아닙니다. A가 배송 메모를 바꾸고 B가 주문 항목을 바꿨다면 기계적으로 병합할 수도 있지만, 두 사람이 같은 수량을 서로 다른 값으로 바꿨다면 어느 쪽이 맞는지 업무 판단이 필요합니다. API는 `409 Conflict` 같은 응답으로 재시도 규칙을 안내할 수 있고, UI는 변경된 필드를 보여 주거나 작업을 다시 시작하게 할 수 있습니다. DBA와 백엔드 팀은 이 동작을 계약으로 문서화하고 테스트해야 합니다.

## JSON Schema, flex column, 그리고 유연성의 경계

문서 모델의 매력 중 하나는 필드를 빠르게 추가할 수 있다는 점입니다. Oracle 문서는 기본 테이블의 JSON 타입 열을 duality view에 매핑해, 일부 영역을 유연한 JSON 데이터로 남길 수 있다고 설명합니다. **flex column**은 미리 정의하지 않은 필드를 특정 JSON 객체에 저장하도록 지원하는 방식입니다. 예를 들어 상품의 핵심 식별자·가격·재고는 관계형 열로 강하게 관리하면서, 판매 채널별 부가 속성은 JSON으로 남길 수 있습니다.

하지만 유연성은 무제한 키-값 저장소를 뜻하지 않습니다. 필드가 실제로 조회·정렬·조인·권한 판단·감사 기준에 쓰이기 시작하면 관계형 열과 제약으로 승격해야 할 가능성이 큽니다. `country`, `taxType`, `approvalStatus`처럼 업무 규칙과 분석에 중요한 값을 flex 영역에만 계속 쌓으면 인덱스·검증·데이터 품질·마이그레이션이 어려워집니다. 반대로 거의 쓰지 않는 외부 공급사 메타데이터까지 매번 테이블 열과 DDL로 만들면 개발 속도가 떨어질 수 있습니다.

**JSON Schema**는 JSON에서 허용하는 property 이름·타입·필수 여부·값 범위를 정의하는 형식입니다. DB에 JSON을 저장할 때 schema validation을 적용하면 자유로운 문서에도 최소한의 구조 계약을 둘 수 있습니다. 다만 JSON Schema가 업무 트랜잭션 규칙까지 표현하는 것은 아닙니다. “수량은 1 이상”은 표현할 수 있어도 “결제가 PAID면 배송지는 특정 절차로만 변경 가능” 같은 규칙은 테이블 제약, 트리거, 애플리케이션 로직, 승인 흐름 중 적절한 계층에 둬야 합니다.

## DBA와 개발 팀이 함께 확인할 운영 항목

Duality View를 만드는 일은 API 팀만의 작업도, DBA만의 작업도 아닙니다. 먼저 원본 테이블과 data owner를 정해야 합니다. 기본 테이블을 직접 수정하는 배치·관리 화면·기존 애플리케이션이 있는지, 그 변경이 JSON API 사용자에게 언제 보이는지 확인합니다. 두 접근 경로가 같은 데이터를 공유하는 것이 장점인 만큼, 변경 이력과 잠금·트랜잭션 경계도 공유됩니다.

둘째, 권한을 나눠야 합니다. 어떤 DB 계정 또는 애플리케이션 role이 duality view를 읽고, 누가 update·insert·delete할 수 있는지, 기본 테이블 직접 접근은 누구에게 열려 있는지 정합니다. view가 민감한 열을 숨긴다고 해도 기본 테이블 권한이 넓으면 우회가 가능합니다. 반대로 API 계정에 필요한 view 권한만 주고 테이블 직접 DML을 제한하면 노출 경계를 더 분명하게 만들 수 있습니다. 권한은 JSON 필드 이름이 아니라 실제 DB 객체와 DML 경로를 기준으로 검토합니다.

셋째, 성능은 문서 크기와 조회 패턴으로 검증합니다. 한 주문에 항목이 5개일 때와 5,000개일 때 같은 JSON 문서를 만들면 네트워크 전송·메모리·직렬화 비용이 달라집니다. 모든 하위 관계를 한 문서에 무제한 중첩하면 앱에는 편해도 페이징과 캐시가 어려워질 수 있습니다. API가 항상 필요한 일부 필드만 읽는다면 테이블·인덱스·SQL 조회가 더 효율적일 수 있습니다. “JSON이라서 느리다” 또는 “관계형이라서 느리다” 같은 일반화 대신 대표 문서 크기와 동시 요청으로 실행 계획·지연·자원 사용을 확인해야 합니다.

넷째, 백업·복구·복제의 단위를 생각합니다. 데이터의 원본은 기본 테이블이므로 백업과 복구는 여전히 관계형 데이터와 트랜잭션 로그 중심으로 계획합니다. JSON 문서를 외부 시스템으로 내보내거나 GoldenGate 같은 복제를 고려할 때는 문서 형태와 테이블 형태 중 어떤 계약을 소비자가 기대하는지 확인해야 합니다. 외부 시스템이 JSON 문서만 받는다고 해서 원본 테이블 스키마 변경의 영향이 사라지는 것은 아닙니다. View 정의와 API 계약의 버전 관리가 필요합니다.

## API 계약으로 쓸 때의 버전 관리와 변경 규칙

Duality View의 JSON 모양은 DB 내부 객체이면서 동시에 API 소비자가 의존하는 계약이 될 수 있습니다. `status` 필드의 이름을 `orderStatus`로 바꾸거나, 문자열 상태를 객체로 감싸거나, items 배열의 정렬 기준을 바꾸면 기본 테이블이 그대로여도 앱·모바일 클라이언트·ETL·외부 파트너가 깨질 수 있습니다. 따라서 view DDL 변경을 단순 스키마 변경으로만 다루지 말고 API 호환성 변경으로도 검토해야 합니다.

호환되는 변경과 호환되지 않는 변경을 구분하는 기준을 미리 정하면 좋습니다. 선택 필드를 추가하는 것은 소비자가 알 수 없는 키를 무시하도록 설계됐다면 대개 영향이 작습니다. 하지만 필수 필드를 제거하거나 타입을 숫자에서 문자열로 바꾸거나, 기존 enum 값을 없애거나, 배열의 의미를 바꾸는 것은 기존 소비자에게 큰 변경입니다. JSON Schema를 API 계약으로 관리한다면 view 정의뿐 아니라 Schema·예시 payload·클라이언트 타입·계약 테스트를 함께 갱신해야 합니다.

새 JSON 표현이 필요할 때 기존 view를 즉시 수정하기보다 `order_dv_v2`처럼 새 계약을 병행하는 선택도 있습니다. 이때 두 view가 같은 원본 테이블을 보더라도 update 권한을 양쪽에 열면 서로 다른 규칙이 충돌할 수 있습니다. 한쪽을 읽기 전용으로 두거나, 새 view가 안정될 때까지 쓰기 경로를 하나로 제한하는 편이 안전할 수 있습니다. 버전 전환 기간에는 어떤 소비자가 어떤 view를 사용하는지 관찰하고, 사용 중인 이전 계약을 임의로 삭제하지 않도록 deprecation 날짜와 소유자를 정합니다.

문서의 필드명이 DB 열 이름을 그대로 노출해야 하는 것도 아닙니다. API는 `orderedAt`, DB는 `ORDERED_AT`처럼 각 계층의 명명 규칙을 가질 수 있습니다. 다만 표현 이름을 바꿨다고 데이터 분류와 권한이 바뀌는 것은 아닙니다. `internalRiskScore`를 문서에서 숨겼더라도 기본 테이블 권한, 로그, 복제 대상에 남아 있을 수 있습니다. 어떤 속성이 외부 계약에 노출되는지와 어떤 계정이 실제 열에 접근할 수 있는지를 분리해 점검해야 합니다.

## 도입 전 검증: 매핑 테스트, 무결성 테스트, 장애 테스트

새 duality view를 만들 때는 보기 좋은 JSON 한 건을 확인하는 데서 끝내면 안 됩니다. 먼저 **매핑 테스트**로 기본 테이블의 값과 JSON 필드가 의도대로 대응하는지 확인합니다. null인 열은 필드를 생략할지 `null`로 낼지, 날짜·timestamp와 time zone은 어떤 문자열로 표현할지, 숫자의 소수점과 큰 정수는 클라이언트 언어에서 안전한지, 빈 하위 관계는 `[]`인지 필드 생략인지 정해야 합니다. 이러한 차이는 프론트엔드와 외부 API에서 종종 장애 원인이 됩니다.

그다음 **무결성 테스트**가 필요합니다. 문서에 없는 product ID, 허용되지 않은 주문 상태, 중복된 하위 항목, 부모 없는 자식, 삭제가 금지된 확정 주문처럼 실패해야 하는 입력을 준비합니다. 기본 테이블의 PK·FK·NOT NULL·CHECK 제약이 기대대로 오류를 내는지, 오류가 API에서 이해 가능한 코드로 변환되는지 확인합니다. JSON 문서의 모양은 맞지만 관계형 제약을 위반하는 경우를 반드시 포함해야 duality view가 무결성 규칙을 우회하지 않는다는 확신을 가질 수 있습니다.

**동시성 테스트**는 ETAG를 실제 흐름으로 확인합니다. 두 클라이언트가 같은 문서를 읽은 뒤 서로 다른 필드를 수정하고, 먼저 저장한 쪽과 나중에 저장한 쪽의 결과를 봅니다. 일치하지 않는 ETAG가 어떤 오류로 나타나는지, 클라이언트가 재조회할 수 있는지, 자동 재시도가 무한 반복되지 않는지, 사람이 병합해야 하는 화면은 무엇인지 검증합니다. 부하 테스트와 다른 질문이므로, 요청 수가 작아도 고의로 경쟁 상태를 만들어 보는 것이 중요합니다.

마지막으로 **장애·복구 시나리오**를 확인합니다. 트랜잭션 중 오류가 발생하면 부모와 자식 테이블 변경이 함께 롤백되는지, 외부 메시지 발행과 DB 갱신의 순서가 어떻게 되는지, view DDL을 배포·롤백할 때 연결 중인 API가 어떤 오류를 받는지 살펴야 합니다. Duality view가 애플리케이션 코드 일부를 줄일 수는 있어도, 원자성·재시도·idempotency 같은 분산 시스템 문제를 자동으로 해결하지는 않습니다.

## 다른 DBMS와 비교할 때 피해야 할 단순화

Oracle의 JSON Relational Duality Views를 소개할 때 “관계형 DB와 문서 DB의 장점만 합쳤다”는 표현은 직관적이지만 지나치게 단순합니다. 문서 DB도 트랜잭션·스키마 검증·관계 참조를 지원할 수 있고, 관계형 DB도 오래전부터 JSON 타입·함수·ORM·REST 계층을 제공해 왔습니다. 실제 차이는 어느 기능이 어떤 버전과 배포 방식에서 지원되는지, JSON 문서 갱신이 기본 테이블과 어떻게 동기화되는지, 인덱스·복제·권한·운영 도구가 무엇인지에 있습니다.

Tibero를 포함한 다른 상용 DBMS나 PostgreSQL·MySQL 같은 제품에도 JSON 열, JSON 함수, view, trigger, API 프레임워크가 있을 수 있습니다. 그러나 `CREATE JSON RELATIONAL DUALITY VIEW`와 같은 문법이나 문서 단위 ETAG 모델, GraphQL subset 기반 정의를 같은 이름으로 기대하면 안 됩니다. 제품을 비교할 때는 “JSON을 저장할 수 있는가” 하나만 묻지 말고, 문서와 관계형 원본의 이중 접근·갱신 규칙·동시성·스키마 유연성·운영 지원이 실제로 어떤 방식인지 확인해야 합니다.

## 적용 전 체크리스트

도입 결정을 내리기 전에 다섯 가지 질문을 적어 보는 것이 좋습니다. 첫째, JSON 문서의 루트가 되는 업무 객체와 기본 테이블 primary key가 명확한가? 둘째, JSON 필드마다 원본 열·계산 값·숨김 값·flex 영역 중 무엇인지 설명할 수 있는가? 셋째, 어떤 클라이언트가 읽기만 하고 어떤 클라이언트가 어느 필드를 수정하는가? 넷째, 동시에 수정했을 때 ETAG 충돌을 누가 어떻게 해결하는가? 다섯째, API 계약을 변경·폐기할 owner와 테스트가 있는가? 이 질문에 답하지 못한다면 기능을 쓰기 전에 데이터 모델과 소유권을 먼저 정리하는 편이 낫습니다.

작은 PoC에서는 주문 한 건처럼 관계가 단순한 도메인을 골라, SQL 조회와 JSON 조회가 같은 사실을 보여 주는지부터 확인할 수 있습니다. 그다음 의도적으로 잘못된 JSON, 경쟁 갱신, 권한 없는 DML, 대량 하위 배열을 넣어 봅니다. 성공 사례만 보여 주는 데모보다 실패가 어디에서 막히는지를 확인해야 실제 API에 적용할 경계를 정할 수 있습니다.

운영 전에는 모니터링과 장애 대응 담당도 정합니다. view 정의 오류, 제약 조건 위반, ETAG 충돌, 권한 거부를 애플리케이션이 서로 다른 오류로 기록하는지 확인하고, JSON 요청 전문이 민감 정보를 포함할 때는 로그 마스킹 기준을 둡니다. 데이터 표현을 바꾸는 기능은 개발 생산성뿐 아니라 감사·지원·복구 절차에도 영향을 준다는 점을 놓치지 않아야 합니다.

## 마무리

Oracle JSON Relational Duality Views는 관계형 테이블의 무결성과 문서 중심 API의 편의 사이에서 하나를 포기하지 않게 해 주는 접근입니다. 동일한 기본 데이터를 SQL과 JSON 양쪽에서 다루되, 문서 구조·갱신 가능 범위·ETAG·권한·유연한 필드의 경계를 선언적으로 드러냅니다. 이 기능의 가치는 JSON을 반환한다는 사실보다, 복사본을 만들지 않고 같은 원본에 대한 두 계약을 명시한다는 데 있습니다.

처음에는 읽기 중심의 주문·카탈로그 같은 한 도메인에서, 테이블 모델과 원하는 JSON 모양을 함께 그려 보는 편이 좋습니다. 그 뒤 문서 전체 갱신이 정말 필요한지, 어떤 필드가 충돌 감지에 참여해야 하는지, 기존 SQL 사용자와 API 사용자의 변경이 어떻게 만나는지를 확인합니다. JSON의 편리함과 관계형 모델의 강점은 자동으로 합쳐지지 않습니다. 매핑과 운영 경계를 명확히 할 때 두 방식이 함께 유용해집니다.
