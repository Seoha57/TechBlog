테스트를 작성할 때 우리는 보통 입력 하나와 기대 결과 하나를 짝지어 둡니다. `쿠폰 10%를 적용하면 9,000원이 된다`, `빈 이름으로 가입하면 400을 돌려준다` 같은 방식입니다. 이런 **예제 기반 테스트(example-based testing)** 는 읽기 쉽고, 제품 요구사항을 문서처럼 남길 수 있으며, 반드시 필요합니다. 다만 사람이 직접 떠올린 몇 개의 입력만으로는 경계값, 조합, 순서, 긴 문자열, 예상하지 못한 특수문자를 모두 다루기 어렵습니다. 특히 금액 계산·날짜·정렬·문자열 처리·직렬화처럼 입력 공간이 넓은 기능에서는 “대표 예제는 모두 통과하는데 특정 조합에서만 실패하는” 결함이 남기 쉽습니다.

**PBT(Property-Based Testing, 속성 기반 테스트)** 는 입력 몇 개를 직접 나열하는 대신, 기능이 많은 입력에 걸쳐 항상 지켜야 할 성질(property)을 선언하고 도구가 다양한 입력을 만들어 검사하게 하는 방식입니다. 예를 들어 정렬 함수에는 “결과가 오름차순이어야 한다”, “입력에 있던 원소가 사라지거나 새로 생기면 안 된다”라는 성질이 있습니다. 할인 계산에는 “할인 후 금액은 음수가 될 수 없다”, “같은 주문과 같은 정책이면 같은 결과가 나와야 한다”라는 성질이 있을 수 있습니다. PBT는 사람이 테스트 데이터를 하나씩 상상하는 역할을 줄이고, 사람이 정한 **규칙 자체**를 넓은 입력에 대입합니다.

여기서 중요한 선을 먼저 긋겠습니다. PBT는 테스트 케이스를 자동으로 완성하는 만능 도구가 아닙니다. 잘못 정의한 속성은 수천 번 실행해도 잘못된 결론만 반복합니다. 또한 사용자 흐름, 화면 문구, 권한 승인, 외부 시스템 계약처럼 구체적인 사례가 중요한 테스트를 대체하지 않습니다. 이 글은 “무작위 값을 많이 넣는 테스트”가 아니라, 무엇을 규칙으로 선언하고 어디까지 맡길지를 판단하는 방법을 설명합니다.

## 먼저 알아둘 기반 기술: 테스트 오라클·경계값·불변식·결정성

테스트는 프로그램을 실행하는 일만이 아닙니다. 실행 결과가 맞는지 판정할 기준이 필요합니다. 이 기준을 **테스트 오라클(test oracle)** 이라고 부릅니다. 주문 합계가 12,000원이어야 한다는 기대값, 응답이 특정 JSON Schema를 만족해야 한다는 규칙, 두 구현이 같은 결과를 내야 한다는 비교가 모두 오라클이 될 수 있습니다. PBT도 결국 오라클을 더 일반적인 문장으로 표현하는 방식입니다. `sort([3, 1, 2])`가 `[1, 2, 3]`인지 보는 것은 예제 오라클이고, 모든 목록에 대해 결과가 정렬돼 있으며 원소의 개수가 보존되는지 보는 것은 속성 오라클입니다.

**경계값(boundary value)** 은 규칙이 바뀌는 지점 근처의 입력입니다. 최소 주문금액이 10,000원이라면 9,999원, 10,000원, 10,001원이 경계값입니다. 날짜 구간이 종료일을 포함한다면 자정, 월말, 윤년 2월 29일도 경계가 됩니다. 예제 테스트에서는 사람이 경계값을 골라야 합니다. PBT에서는 생성기가 작은 수, 큰 수, 빈 값, 중복값처럼 경계에 가까운 값을 충분히 만들도록 설계할 수 있습니다. 그렇다고 도구가 도메인 경계를 자동으로 알지는 않습니다. “최소 주문금액”이라는 업무 규칙을 생성 범위와 속성에 넣는 사람의 판단이 필요합니다.

**불변식(invariant)** 은 처리 전후나 어느 실행 시점에도 유지돼야 하는 성질입니다. 예를 들어 계좌 이체에서는 성공한 이체 전후 두 계좌 잔액의 합이 같아야 한다는 규칙을 생각할 수 있습니다. 재고 예약이라면 예약 수량이 음수가 되지 않고, 확정 수량과 취소 수량의 관계가 맞아야 합니다. 불변식은 구현 세부보다 제품 규칙에 가깝기 때문에 리팩터링 뒤에도 유지될 가능성이 큽니다. 다만 불변식 하나가 모든 요구를 대변하지는 않습니다. 잔액 합이 같아도 잘못된 계좌로 이체될 수 있으므로, 권한·대상·감사 기록 같은 다른 속성과 사례 테스트가 함께 필요합니다.

**결정성(determinism)** 은 같은 입력과 같은 조건에서 실행하면 같은 결과가 나오는 성질입니다. PBT는 생성된 입력을 다시 실행해 실패를 재현해야 하므로 결정성이 특히 중요합니다. 현재 시간, 난수, 네트워크, 파일 순서, 공유 데이터베이스 상태가 결과에 섞이면 같은 seed로도 실패가 사라질 수 있습니다. 시계는 주입 가능한 값으로 바꾸고, 난수는 seed를 기록하며, 외부 호출은 계약된 테스트 대역으로 분리하는 것이 PBT 이전에 갖춰야 할 테스트 설계입니다.

## 예제에서 속성으로 옮겨 보기: 무엇이 항상 맞아야 하는가

예제 테스트는 보통 다음처럼 시작합니다.

```ts
expect(calculateShippingFee(40_000)).toBe(0);
expect(calculateShippingFee(39_999)).toBe(3_000);
```

이 테스트는 무료 배송 경계가 40,000원이라는 사실을 훌륭하게 설명합니다. 그러나 금액이 음수일 때, 소수점이 들어왔을 때, 큰 정수일 때, 통화 단위가 잘못 섞였을 때 어떻게 해야 하는지는 별도로 정해야 합니다. PBT로 바꾼다고 위 테스트를 삭제할 필요는 없습니다. 그 옆에 “유효한 원화 정수 주문금액에서 배송비는 음수가 아니다”, “주문금액이 증가했는데 배송비가 더 커지는 구간은 정책상 허용되는가”처럼 넓은 규칙을 추가할 수 있습니다.

속성은 대체로 다음 다섯 가지 틀에서 찾기 쉽습니다.

- **범위**: 결과가 허용 범위 안에 있는가? 예를 들어 할인 후 결제액은 0 이상이고 원 주문금액 이하여야 합니다.
- **보존**: 변환 뒤에도 유지되는 정보가 있는가? 정렬 뒤 목록 길이와 원소의 다중집합(multiset)은 같아야 합니다.
- **멱등성(idempotence)**: 같은 작업을 두 번 해도 한 번 한 결과와 같은가? 공백 정리 함수나 설정 정규화가 대표적입니다.
- **역연산 또는 왕복**: 직렬화 후 역직렬화하면 원래 의미로 돌아오는가? 다만 시간대·정밀도처럼 의도적으로 손실되는 필드는 명시해야 합니다.
- **단조성·관계**: 입력을 특정 방향으로 바꾸면 결과가 어떤 관계를 유지하는가? 예를 들어 권한 집합을 줄였을 때 접근 가능한 리소스가 늘어나면 안 됩니다.

“항상”이라는 말은 주의해서 써야 합니다. 배송비는 주문금액이 높아질수록 항상 줄어든다고 단정하기 어렵습니다. 도서산간·새벽배송·묶음 조건이 있다면 예외가 생길 수 있습니다. 이때 좋은 속성은 현실을 억지로 단순화하지 않고, 적용 조건을 드러냅니다. 예를 들어 “동일 지역, 동일 배송수단, 쿠폰과 추가비용이 없는 주문”처럼 생성기의 전제를 좁히거나, 추가비용을 포함한 더 정확한 규칙을 만듭니다. 실패를 피하려고 속성을 느슨하게 만드는 대신, 업무 조건을 코드에서 명확히 만드는 편이 낫습니다.

## 생성기(generator)는 테스트 데이터 정책이다

PBT의 **생성기(generator)** 는 값 하나를 무작위로 내는 편의 기능이 아니라, 어떤 입력 세계를 탐색할지 결정하는 테스트 데이터 정책입니다. 문자열 생성기가 영문 소문자만 만든다면 한글, 이모지, 조합형 유니코드, 제어 문자, 공백, 매우 긴 입력에서 생기는 문제를 발견할 수 없습니다. 반대로 아무 문자열이나 만들면 업무상 불가능한 값이 대부분이어서 실패 원인을 이해하기 어려울 수 있습니다.

그래서 생성기는 보통 세 단계로 나누는 편이 좋습니다. 첫째, 타입 수준의 값입니다. 정수, 문자열, 날짜, 배열처럼 언어가 표현하는 값입니다. 둘째, 형식 수준의 값입니다. 이메일처럼 보이는 문자열, ISO 8601 날짜 문자열, UUID처럼 문법을 만족하는 값입니다. 셋째, 도메인 수준의 값입니다. 활성 상태의 고객, 재고가 있는 상품, 유효 기간 안의 쿠폰처럼 업무 제약까지 만족하는 값입니다. API가 어떤 단계까지 책임지는지를 먼저 정하지 않으면 생성기도 섞입니다.

예를 들어 주문 생성 API의 요청 본문을 테스트한다고 해 보겠습니다. 컨트롤러의 형식 검증을 확인하려면 잘못된 타입·빈 배열·누락 필드를 생성하는 **비정상 입력 생성기**가 필요합니다. 반면 가격 계산 서비스의 속성을 확인하려면 수량이 1 이상이고 상품 가격이 0 이상인 **유효 도메인 생성기**가 필요합니다. 같은 `Order`라는 이름을 쓰더라도 목적에 따라 생성기가 달라집니다. 유효한 주문만 생성하면서 400 응답을 기대하거나, 잘못된 주문을 생성하면서 총액 보존을 기대하면 테스트가 무엇을 검증하는지 흐려집니다.

JavaScript와 TypeScript에서는 [fast-check](https://fast-check.dev/docs/introduction/)가 잘 알려진 PBT 라이브러리입니다. 아래는 주문 항목의 부분 합과 전체 합이 일치해야 한다는 작은 예시입니다. 실제 서비스에서는 세금·할인·통화 반올림을 추가하고, 그 규칙을 속성에 명시해야 합니다.

```ts
import fc from 'fast-check';

type Line = { unitPrice: number; quantity: number };

const total = (lines: Line[]) =>
  lines.reduce((sum, line) => sum + line.unitPrice * line.quantity, 0);

const lineArbitrary = fc.record({
  unitPrice: fc.integer({ min: 0, max: 1_000_000 }),
  quantity: fc.integer({ min: 1, max: 100 }),
});

fc.assert(
  fc.property(fc.array(lineArbitrary, { maxLength: 30 }), (lines) => {
    const result = total(lines);
    return result >= 0 && result === lines.reduce(
      (sum, line) => sum + line.unitPrice * line.quantity,
      0,
    );
  }),
);
```

위 예시는 계산식이 사실상 같은 식을 두 번 쓴다는 한계가 있습니다. 같은 오류를 두 곳에 복사하면 통과할 수 있습니다. 더 나은 방법은 독립된 기준 구현을 만들거나, 결과 범위·항목 순서 변경·항목 분할/병합 뒤의 관계처럼 다른 관점의 속성을 조합하는 것입니다. 예컨대 한 줄의 수량 2를 같은 가격의 두 줄 수량 1로 나눠도 할인 조건이 같다면 총액이 같아야 한다는 관계는 구현 내부와 다른 방향에서 결함을 찾을 수 있습니다.

## Shrink: 실패를 작게 만들어 설명 가능한 결함으로 바꾸기

PBT가 실무에서 유용한 이유는 많은 값을 시도한다는 점만이 아닙니다. **shrink(축소)** 는 어떤 입력에서 실패했을 때, 실패를 유지하면서 더 작은 입력을 찾는 과정입니다. 예를 들어 200개 상품과 긴 한글 문자열이 섞인 주문에서 오류가 났다면, 도구는 두 개 항목과 빈 문자열에 가까운 값까지 줄여 볼 수 있습니다. 최종적으로 “빈 쿠폰 코드와 수량 0이 동시에 들어오면 예외가 난다”처럼 사람이 읽을 수 있는 반례(counterexample)를 보여 주는 것이 목표입니다.

축소 결과가 항상 도메인상 자연스럽지는 않습니다. 날짜를 축소하는 과정에서 아주 이른 날짜가 나오거나, 문자열이 빈 값이 될 수 있습니다. 이 값이 API에서 허용하면 안 되는 값이라면 두 가지를 분리해야 합니다. 입력 검증 테스트에서는 그 값에 400을 기대합니다. 유효 도메인 속성 테스트에서는 생성기가 그런 값을 만들지 않게 하거나, 사전 조건(precondition)을 둡니다. 실패를 없애려고 `try/catch`로 모든 예외를 통과시키는 것은 shrink가 알려 준 유용한 신호를 버리는 일입니다.

실패를 재현하려면 적어도 seed, 실행 횟수, 라이브러리 버전, 축소된 입력, 테스트 대상의 버전을 남겨야 합니다. CI 출력에 seed만 있고 생성기 구현이 바뀌었다면 나중에 같은 입력을 얻지 못할 수 있습니다. 반대로 실패 입력 전체를 로그에 무심코 남기면 개인정보나 비밀값이 유출될 수 있습니다. 실제 고객 데이터를 생성기의 seed로 쓰지 말고, 민감한 필드는 마스킹하거나 합성 값만 쓰며, CI 아티팩트 접근 권한도 관리해야 합니다.

## Metamorphic Testing: 정답을 직접 모르더라도 관계를 검사하는 법

어떤 문제는 한 입력의 정확한 정답을 계산하기 어렵습니다. 검색 순위, 추천, 이미지 처리, 복잡한 변환처럼 오라클을 만들기 비싼 경우가 그렇습니다. 이때 **메타모픽 테스트(metamorphic testing)** 는 입력을 변형한 뒤 결과 사이에 기대되는 관계를 검사합니다. PBT와 자주 함께 쓰이지만 같은 뜻은 아닙니다. PBT는 생성과 속성 중심의 방법이고, 메타모픽 테스트는 변형 전후 관계라는 오라클 설계 기법입니다.

예를 들어 검색 API에서 문서 집합에 검색어와 전혀 관련 없는 문서를 하나 더 넣었다고 해 보겠습니다. 특정 필터와 고정된 정렬 기준 아래에서 기존 최상위 결과가 완전히 사라지면 원인을 조사할 만합니다. 이미지 업로드 API에서는 같은 이미지를 메타데이터만 바꿔 재업로드했을 때 픽셀 처리 결과가 같아야 할 수 있습니다. 금액 계산에서는 주문 항목의 순서를 바꿔도 항목 간 규칙이 순서에 의존하지 않는 한 합계가 같아야 합니다.

다만 관계가 성립하는 조건을 빠뜨리면 오탐이 됩니다. 검색 결과는 동점 처리, 개인화, 최신성 점수에 따라 달라질 수 있습니다. 주문 항목 순서는 ‘첫 구매 상품 할인’처럼 실제 정책에 영향을 줄 수 있습니다. 따라서 메타모픽 테스트를 쓸 때는 “왜 이 변형이 의미를 보존해야 하는가”, “어떤 설정에서는 보존되지 않는가”를 테스트 이름과 설명에 적어 두는 편이 좋습니다. 관계형 속성은 복잡한 시스템의 정답을 우회하는 수단이지, 도메인 이해를 건너뛰는 수단이 아닙니다.

## API·DB·UI에서 어디까지 적용할 수 있나

PBT는 순수 함수에서 가장 시작하기 쉽습니다. 입력과 출력이 명확하고 외부 상태가 없어서 실패 재현이 간단하기 때문입니다. 하지만 API, 데이터베이스, UI까지 확장할 수 없다는 뜻은 아닙니다. 다만 계층마다 생성기와 오라클의 책임을 달리해야 합니다.

API 계층에서는 요청 필드 조합, 길이, 유니코드, 정렬 파라미터, 페이지 크기 같은 입력을 넓게 생성할 수 있습니다. 이때 속성은 “서버가 절대 500으로 종료하지 않는다”처럼 너무 약하게 두기보다, 유효 입력은 정해진 스키마의 성공 응답을, 무효 입력은 문서화한 4xx 오류 형식을 준다는 식으로 나눕니다. [OpenAPI](https://spec.openapis.org/oas/latest.html) 명세가 있다면 타입·필수 필드·응답 구조의 기준으로 쓸 수 있습니다. 그러나 사용자가 화면에서 만들 수 없는 상태 조합까지 API에 보낼 수 있다는 점은 기억해야 합니다. 명세 검증과 실제 사용자 시나리오 검증은 서로 다른 질문입니다.

데이터베이스 계층에서는 삽입·갱신·조회 뒤의 제약을 확인할 수 있습니다. 예를 들어 같은 외부 주문 키로 요청을 여러 번 보내도 중복 주문이 하나만 생겨야 한다는 멱등성은 API와 DB 제약을 함께 시험하는 좋은 속성입니다. 하지만 공유 테스트 DB에 생성 입력을 무한히 넣으면 테스트가 느려지고 서로 영향을 줍니다. 트랜잭션 롤백, 테스트 스키마 격리, 실행별 식별자, 정리 실패 시 조사 절차를 먼저 갖춰야 합니다. PBT가 많은 시도를 한다는 특성은 DB 테스트 비용을 작게 만들지 않습니다.

UI에서는 모든 생성 입력을 브라우저로 흘려보내는 방식이 비쌀 수 있습니다. 화면 레이아웃과 비동기 대기까지 포함하면 실패 원인을 좁히기도 어렵습니다. UI에는 대표 사용자 흐름과 접근성·시각 회귀 테스트를 중심으로 두고, 입력 정규화·가격 계산·URL 쿼리 직렬화 같은 순수 로직을 PBT로 분리하는 편이 실용적입니다. 브라우저까지 PBT를 확장해야 한다면 실행 횟수를 제한하고, 실패 시 DOM·네트워크·스크린샷을 남기는 별도 전략이 필요합니다.

## 가상의 업무 예시: 쿠폰 정책에서 반례를 찾는 과정

가상의 쇼핑 서비스가 있다고 하겠습니다. 정책은 ‘상품 합계가 30,000원 이상이고 쿠폰이 유효하면 10% 할인, 단 할인액은 5,000원을 넘지 않는다’입니다. 대표 예제 세 개는 30,000원, 50,000원, 100,000원에서 기대 금액을 검증합니다. 그런데 수량이 여러 개인 항목, 이미 품절된 항목, 쿠폰 적용 제외 상품, 배송비 포함 여부가 동시에 들어오면 총액 계산 경로가 갈라집니다.

먼저 유효 주문 생성기는 가격 0 이상, 수량 1 이상, 쿠폰 적용 가능 여부를 가진 항목 배열을 만듭니다. 속성 하나는 `0 <= 할인액 <= 5,000`입니다. 두 번째 속성은 쿠폰을 적용하지 않은 총액보다 쿠폰 적용 총액이 커지지 않는다는 것입니다. 세 번째는 항목 순서를 섞어도 결과가 같다는 것입니다. 여기서 세 번째가 실패했다면 단순히 “버그”라고 결론내리기 전에 정책을 확인해야 합니다. 특정 상품부터 할인 한도를 소비하도록 명시했다면 순서가 의미 있을 수 있고, 그렇지 않다면 배열 순회 순서에 따라 cap을 적용한 구현 결함일 수 있습니다.

다음으로 비정상 요청 생성기를 별도로 만듭니다. 수량 0, 음수 가격, 누락된 쿠폰 코드, 지나치게 긴 문자열, 잘못된 통화 코드가 대상입니다. 이 그룹의 속성은 할인 계산값이 맞는지가 아니라 “API가 정의된 오류 응답을 반환하고 주문 레코드를 만들지 않는다”입니다. 테스트 실패를 줄였더니 `quantity: 0`과 `coupon: ''` 조합에서 500이 나온다고 가정해 보겠습니다. 이 반례는 검증 순서나 null 처리의 결함을 빠르게 보여 줍니다. 이후에는 이 축소 입력을 고정 예제 회귀 테스트로 추가해, 라이브러리의 생성 방식이 달라져도 해당 장애가 다시 나타나지 않게 합니다.

이 흐름은 PBT가 예제 테스트를 밀어내는 것이 아니라 예제 테스트의 재료를 만든다는 점도 보여 줍니다. 처음에는 넓은 입력에서 예상하지 못한 반례를 찾고, 확인된 결함은 이름 있는 회귀 시나리오로 남깁니다. 팀원이 나중에 실패 이유를 읽을 때에도 `빈 쿠폰과 수량 0일 때 500을 내면 안 된다`라는 고정 테스트가 더 직접적인 문서가 될 수 있습니다.

## 실행 횟수와 비용: 많이 돌리는 것이 항상 좋은가

PBT는 기본 실행 횟수를 높일수록 더 많은 입력을 만납니다. 하지만 실행 횟수를 무작정 늘리면 CI 시간이 길어지고, 외부 I/O가 있는 테스트는 비용과 불안정성도 커집니다. ‘몇 번이면 충분한가’라는 보편 숫자는 없습니다. 입력 공간, 생성기 품질, 위험도, 테스트 계층, 피드백 시간 목표에 따라 달라집니다.

처음에는 순수 함수와 작은 도메인부터 시작해 로컬과 PR에서 짧게 실행합니다. 오류가 자주 발견되는 규칙, 보안·금액처럼 위험이 높은 규칙, 시간이 걸려도 되는 야간 회귀에서는 더 넓은 실행을 고려할 수 있습니다. 단, 실행 횟수만 지표로 삼지 말고 어떤 경계와 조합을 생성했는지 확인해야 합니다. 모든 생성 값이 평균적인 양수만 나온다면 10,000번을 실행해도 음수·빈 배열·최대 길이 같은 위험은 보지 못합니다.

재현성을 위해 CI에서는 seed를 출력하고 실패 시 복사해 로컬에서 실행할 명령을 문서화합니다. 병렬 실행을 쓸 경우에는 어떤 워커가 어떤 seed를 썼는지 남깁니다. 시간·네트워크·공유 데이터베이스에 의존하는 속성은 flaky test가 되기 쉽습니다. 실패한 테스트를 단순 재실행으로 통과시키기보다, 생성 입력과 외부 상태를 분리할 수 있는지 먼저 확인해야 합니다. 실패율이 높은 PBT는 많은 결함을 잡는 도구가 아니라 팀이 무시하게 되는 알람이 될 수 있습니다.

## 속성을 리뷰하는 법: 구현을 다시 쓰지 않았는지 확인한다

PBT를 처음 도입할 때 자주 나오는 실수는 테스트 안에 운영 코드를 거의 그대로 다시 쓰는 것입니다. `calculateTotal()`의 결과가 `price * quantity`의 합과 같은지 검사하려고 테스트에도 똑같이 `price * quantity`를 누적하면, 곱셈 순서·반올림·할인 적용 위치의 동일한 실수를 두 곳에 복사할 수 있습니다. 이를 **동일 구현 오라클(same implementation oracle)** 문제라고 생각할 수 있습니다. 테스트가 독립된 판정 기준이 되지 못하는 상태입니다.

이를 피하는 완벽한 공식은 없지만, 속성을 검토할 때 다음 질문이 도움이 됩니다. 첫째, 이 속성은 사용자가 기대하는 규칙을 문장으로 말하는가, 아니면 구현의 현재 루프를 다른 문법으로 복사한 것인가? 둘째, 결과값 하나가 아니라 입력 변형 전후의 관계나 범위·보존 성질을 볼 수 있는가? 셋째, 실패했을 때 제품·도메인 담당자가 “이 규칙은 맞다/예외다”를 판단할 수 있는가? 넷째, 규칙이 적용되지 않는 예외 조건을 생성기 또는 테스트 이름에 드러냈는가?

가령 문자열 정규화 함수에 대해 `normalize(normalize(x)) === normalize(x)`라는 멱등성은 구현 세부를 몰라도 말할 수 있는 좋은 출발점입니다. 그러나 그것만으로 출력이 올바른지 증명하지는 않습니다. 모든 문자열을 빈 문자열로 바꾸는 함수도 멱등성은 만족합니다. 그래서 대표 예제로 공백 처리와 유니코드 처리를 확인하고, 속성으로는 멱등성과 특정 허용 문자 보존을 추가하는 식의 조합이 필요합니다. 하나의 속성에 모든 기대를 몰아넣기보다, 서로 다른 실패 이유를 설명하는 작은 속성 여러 개가 유지보수하기 좋습니다.

속성 이름도 중요합니다. `property 1`보다 `할인액은 최대 할인 한도를 넘지 않는다`, `정렬은 입력 원소의 다중집합을 보존한다`처럼 도메인 언어로 쓰면 실패 보고가 곧 규칙 위반 보고가 됩니다. 속성에 대응하는 요구사항 번호, 정책 문서, API 명세 링크를 가까이 두면 변경 요청이 왔을 때 생성기·예제·속성 중 무엇을 바꿔야 하는지도 추적하기 쉬워집니다. PBT는 랜덤 입력 도구이기 전에, 암묵적인 규칙을 팀이 검토 가능한 문장으로 만드는 활동입니다.

## 도입 체크리스트: 첫 테스트를 작고 믿을 수 있게 시작하기

처음부터 모든 서비스에 생성 테스트를 붙이면 테스트 시간과 실패 해석 비용만 늘어날 수 있습니다. 첫 대상은 입력 조합이 많지만 외부 의존성이 작은 함수가 좋습니다. 통화 금액의 정규화, 날짜 범위 계산, 권한 집합 병합, URL 쿼리 직렬화, 목록 정렬·필터링처럼 실패를 재현하기 쉬운 영역이 적합합니다. 이후 발견된 반례와 회귀 결함을 바탕으로 적용 범위를 넓힙니다.

- 도메인 담당자와 함께 “절대 깨지면 안 되는 규칙”을 한두 문장으로 적는다.
- 유효 입력과 비정상 입력 생성기를 분리하고, 각 생성기의 책임을 이름으로 드러낸다.
- 작은 실행 횟수로 로컬·PR에서 먼저 돌리고 seed와 축소 입력을 확인한다.
- 실패 반례가 확인되면 고정 예제 회귀 테스트와 원인 설명을 추가한다.
- 외부 시간·네트워크·DB 때문에 재현이 흔들리면 범위를 줄이거나 의존성을 분리한다.

이 순서는 빠른 성과를 약속하기 위한 절차가 아닙니다. 테스트가 신뢰를 얻으려면 실패가 났을 때 개발자가 이해하고 고칠 수 있어야 하기 때문입니다. 한 번도 읽지 않는 거대한 생성 테스트보다, 특정 계산 규칙의 반례를 꾸준히 드러내고 설명할 수 있는 작은 속성 테스트가 더 큰 품질 자산이 됩니다.

## 한계와 적용 기준 Q&A

### Q. Property-Based Testing만 있으면 요구사항 예제는 필요 없나요?

A. 필요합니다. 속성은 넓은 규칙을 검증하지만, 제품이 약속한 구체적인 사례를 가장 잘 보여 주는 것은 예제입니다. ‘VIP 고객의 특정 쿠폰과 배송비가 이렇게 계산된다’, ‘권한 없는 사용자는 이 화면을 볼 수 없다’처럼 비즈니스와 사용자 흐름을 설명해야 하는 경우에는 이름 있는 예제 테스트가 적합합니다. 두 방식은 대체 관계가 아니라 서로 다른 빈틈을 메웁니다.

### Q. 생성기가 만든 비현실적 입력에서 실패하면 무시해도 되나요?

A. 먼저 그 입력이 어느 계층에 도달할 수 있는지 확인해야 합니다. 외부 API는 악의적이거나 잘못된 클라이언트의 입력을 받을 수 있으므로, 화면에서 만들 수 없다는 이유만으로 500 오류를 허용하면 안 됩니다. 반면 도메인 서비스가 입력 검증을 통과한 값만 받는 것이 명확하다면 생성기 범위를 유효 도메인으로 제한할 수 있습니다. 무시하기 전에 입력 경계를 문서화하는 것이 핵심입니다.

### Q. 기존 코드가 외부 시간·DB·네트워크에 얽혀 있어도 도입할 수 있나요?

A. 가능하지만 시작 지점을 작게 잡는 편이 좋습니다. 계산·파싱·정규화처럼 외부 의존성이 적은 함수를 먼저 분리하고, 시계·난수·HTTP 클라이언트는 주입 가능한 의존성으로 바꿉니다. DB나 API까지 한 번에 생성 테스트를 붙이면 실패 원인이 비즈니스 규칙인지 환경인지 구별하기 어렵습니다. 순수 로직에서 검증 가능성을 쌓은 뒤 통합 계층으로 넓히는 것이 안전합니다.

### Q. PBT에서 통과한 코드는 안전하다고 말할 수 있나요?

A. 아닙니다. 통과는 정의한 생성기와 속성의 범위에서 반례를 찾지 못했다는 뜻입니다. 누락된 업무 규칙, 잘못된 오라클, 생성하지 못한 입력, 외부 연동 문제는 남을 수 있습니다. 대표 예제·계약·보안·탐색적 테스트·리뷰와 함께 사용해야 하며, 중요한 변경에는 전체 회귀와 배포 후 관측도 필요합니다.

## 마무리

Property-Based Testing은 테스트를 많이 실행하는 기법이 아니라, 사람이 머릿속에만 두던 규칙을 실행 가능한 속성으로 바꾸는 방법입니다. 예제 기반 테스트가 제품의 중요한 장면을 선명하게 보여 준다면, PBT는 그 장면 사이의 넓은 공간을 탐색합니다. 시작할 때는 가장 복잡한 API나 UI가 아니라 금액·날짜·문자열·정렬처럼 입력 조합이 넓고 불변식을 말하기 쉬운 순수 로직 하나를 고르는 편이 좋습니다. 좋은 생성기, 설명 가능한 shrink 결과, 재현 가능한 seed, 그리고 예제·통합 테스트와의 역할 분담이 갖춰질 때 PBT는 우연한 반례를 지속 가능한 품질 지식으로 바꿉니다.
