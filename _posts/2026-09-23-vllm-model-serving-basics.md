로컬 PC에서 모델 하나를 실행해 질문에 답하게 하는 것과, 여러 사람이 동시에 호출하는 API로 모델을 제공하는 것은 다른 문제입니다. 전자는 모델을 메모리에 올리고 한 요청을 처리하면 충분할 수 있습니다. 후자는 요청이 겹칠 때 GPU 메모리를 어떻게 나눌지, 긴 프롬프트가 짧은 요청을 막지 않게 할지, 어떤 모델·토큰 수·오류를 사용자에게 약속할지, 장애와 비용을 어떻게 관찰할지까지 설계해야 합니다.

vLLM은 대규모 언어 모델(LLM, Large Language Model)을 GPU 환경에서 효율적으로 추론하고, HTTP API로 제공하기 위한 오픈 소스 서빙 엔진입니다. OpenAI 호환 API 형태를 지원해 기존 애플리케이션이 요청 형식을 크게 바꾸지 않고 자체 모델 서버를 호출하게 도울 수 있습니다. 그러나 API 모양이 같다고 OpenAI 모델의 품질·안전 기능·도구 호출·사용 정책이 자동으로 같아지는 것은 아닙니다.

이 글은 vLLM 공식 문서와 공개된 설계 자료를 바탕으로 모델 서빙의 개념을 설명합니다. 특정 GPU나 모델에서 직접 측정한 처리량을 주장하지 않습니다. LLM 서버는 프롬프트와 응답에 민감 정보가 들어갈 수 있고 GPU 자원을 크게 사용하므로, 개인 실습 서버와 조직의 고객 대상 서비스는 서로 다른 보안·운영 기준으로 다뤄야 합니다.

## 먼저 알아둘 기반 기술: LLM 추론, 토큰, GPU 메모리, API

LLM은 문장을 한 번에 완성된 답으로 만드는 대신, 보통 **토큰(token)** 이라는 단위로 다음 조각의 확률을 계산하며 생성합니다. 토큰은 단어와 정확히 같지 않습니다. 한국어 한 글자나 어절, 영어 단어 일부, 기호가 모델의 tokenizer 규칙에 따라 여러 토큰이 될 수 있습니다. 사용자가 보낸 입력은 prompt token, 모델이 생성한 답은 output token이라고 부릅니다. 긴 문서와 긴 답을 허용할수록 계산 시간과 메모리 사용량이 늘어납니다.

**추론(inference)** 은 이미 학습된 모델 가중치로 입력에 대한 출력을 계산하는 단계입니다. 학습(training)은 대량 데이터로 가중치를 바꾸지만, 추론은 보통 가중치를 읽기 전용으로 GPU 메모리에 올려 반복 사용합니다. 모델 크기가 클수록 가중치 자체가 GPU VRAM(Video Random Access Memory)을 많이 차지합니다. 남은 VRAM은 요청마다 달라지는 중간 상태와 KV Cache에 쓰입니다. 따라서 “GPU 메모리가 모델 파일 크기보다 조금 크다”만으로 안정적인 동시 API 서버가 된다고 볼 수 없습니다.

**KV Cache(Key-Value Cache)** 는 transformer가 앞 토큰을 계산하면서 만든 key와 value 중간 결과를 저장하는 공간입니다. 답변을 한 토큰 더 생성할 때 앞의 모든 토큰을 처음부터 다시 계산하지 않도록 돕습니다. 긴 대화·문서에서 매우 중요하지만, 요청마다 cache가 쌓여 메모리를 차지합니다. 동시 사용자가 늘고 각 사용자의 문맥이 길어지면 cache 관리가 서버 용량의 핵심 문제가 됩니다.

HTTP API는 애플리케이션이 모델 서버에 JSON 요청을 보내고 응답을 받는 인터페이스입니다. 예를 들어 채팅 앱은 사용자 메시지와 system instruction을 서버로 보내고, 서버는 생성 텍스트·사용 토큰 수·종료 이유 등을 돌려줄 수 있습니다. **OpenAI-compatible API** 는 널리 쓰이는 OpenAI API의 endpoint와 데이터 형식 일부를 따르는 인터페이스입니다. 이것은 SDK 교체 비용을 줄일 수 있지만, 모든 매개변수와 모델 기능, 오류 코드, safety behavior가 동일하다는 보증은 아닙니다.

## vLLM이 해결하려는 서빙 문제

모델을 단순한 Python 스크립트로 실행하면 한 요청이 끝날 때까지 다음 요청을 기다리게 만들기 쉽습니다. 요청 A가 4,000토큰의 긴 답을 생성하는 동안, 짧은 질문 B도 GPU가 비기를 기다리면 사용자 체감 지연이 커집니다. 모든 요청을 한 번에 큰 배치로 묶는 방식도 해결책이 완전하지 않습니다. 새 요청이 계속 들어오는 서버에서는 배치가 언제 닫히는지, 길이가 다른 요청을 어떻게 맞추는지, 이미 생성 중인 요청과 새 요청을 어떻게 섞는지가 문제가 됩니다.

vLLM은 요청을 스케줄하고, 생성 단계마다 활성 요청의 배치를 조정하는 **continuous batching** 또는 iteration-level scheduling 접근을 사용합니다. 긴 요청이 아직 생성 중이어도, 다음 생성 iteration에 짧은 새 요청을 함께 넣을 수 있습니다. 목표는 GPU가 빈 시간을 줄이고 여러 요청의 응답성을 관리하는 것입니다. 다만 스케줄러가 있다고 요청 우선순위·tenant 격리·rate limit·비용 상한이 자동으로 해결되는 것은 아닙니다. 서비스 운영자는 어떤 요청을 먼저 처리할지와 과도한 요청을 어떻게 거절할지 별도로 정해야 합니다.

vLLM의 대표적인 아이디어인 **PagedAttention**은 KV Cache를 OS의 가상 메모리 페이지처럼 고정 크기 block으로 관리하는 방식입니다. 연속된 큰 메모리 덩어리를 요청마다 미리 잡는 대신 block을 필요에 따라 할당·공유해 낭비와 fragmentation을 줄이려는 설계입니다. 여기서 page라는 이름 때문에 운영체제의 swap을 사용하는 것으로 오해하면 안 됩니다. 핵심은 GPU 메모리 안에서 attention cache를 block 단위로 다루는 방법입니다.

같은 긴 system prompt나 문서를 여러 사용자가 공유할 때는 **prefix caching** 이 도움이 될 수 있습니다. 예를 들어 모든 요청 앞에 같은 제품 매뉴얼 요약과 정책을 붙이면, 공통 prefix의 계산 결과를 재사용할 여지가 있습니다. 그러나 prefix가 조금만 달라져도 재사용이 되지 않을 수 있고, tenant가 다른 민감한 문맥을 잘못 공유하면 안 됩니다. 캐시 효율은 프롬프트 템플릿을 표준화할 동기가 될 수 있지만, 보안 경계보다 우선해서는 안 됩니다.

## 모델, tokenizer, template는 한 세트다

모델 서버를 만들 때 흔히 모델 가중치 파일만 생각하지만, tokenizer와 chat template도 결과를 크게 바꿉니다. tokenizer는 문자열을 token ID로 바꾸고, chat template는 `system`, `user`, `assistant` 역할의 메시지를 실제 모델 입력 문자열로 조립합니다. 특정 instruction-tuned 모델은 정해진 특수 토큰과 역할 구분을 기대합니다. 임의의 템플릿으로 요청을 보내면 모델이 답변 대신 프롬프트 형식을 반복하거나, 도구 호출 형식을 망가뜨릴 수 있습니다.

따라서 모델을 바꿀 때는 “API의 `model` 이름만 교체”하지 말고, 모델 카드(model card), 라이선스, context window, 권장 chat template, 지원 언어, tool calling·structured output 지원 여부를 함께 봅니다. 모델 카드의 벤치마크 점수는 특정 데이터셋과 프롬프트 조건의 결과입니다. 한국어 고객 문의, 사내 용어, 긴 문서 요약, JSON 생성에서 같은 품질을 보장하지 않습니다. 실제 도입 전에 대표 입력을 선정해 안전성·형식 준수·환각·지연을 평가하는 이유입니다.

모델 가중치의 라이선스도 운영 설계의 일부입니다. 공개적으로 내려받을 수 있다고 상업 서비스·재배포·파인튜닝이 모두 허용되는 것은 아닙니다. Hugging Face repository의 license, 모델 제공자의 acceptable use policy, 파생 모델 조건을 확인해야 합니다. 특히 사용자 프롬프트와 응답을 저장해 추가 학습에 쓰려면 개인정보와 계약상의 별도 근거가 필요합니다.

## OpenAI 호환 서버를 이해하는 예시

vLLM 서버는 보통 OpenAI API와 비슷한 채팅 endpoint를 제공할 수 있습니다. 아래 명령은 형태를 설명하기 위한 예시이며, 실제 모델 이름·GPU 옵션·network 공개 범위는 환경에 맞춰 선택해야 합니다.

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --host 127.0.0.1 \
  --port 8000 \
  --api-key "$VLLM_API_KEY"
```

`127.0.0.1`로 바인딩하면 같은 머신에서만 접근하게 할 수 있어 개인 실습의 기본값으로 안전합니다. `0.0.0.0`으로 열면 네트워크의 다른 장비에서도 접근할 수 있으므로 방화벽, reverse proxy, TLS, 인증, 접근 로그가 필요합니다. API key 옵션도 키가 있다는 사실만으로 충분하지 않습니다. 키를 소스 코드·Docker image·클라이언트 번들에 넣지 말고, secret manager 또는 환경 주입으로 관리하고, 유출 시 교체할 수 있어야 합니다.

클라이언트는 endpoint URL을 자체 서버로 바꾸어 요청할 수 있습니다.

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",
    api_key="local-development-key",
)

response = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "HTTP API를 한 문장으로 설명해줘."}],
    max_tokens=120,
)
print(response.choices[0].message.content)
```

이 예시는 SDK의 호출 모양이 비슷할 수 있음을 보여 줍니다. 하지만 모델 이름은 공급자 모델 이름이고, 사용량 과금·moderation·파일 검색·관리형 tool execution 등 클라우드 API의 부가 기능은 같은 endpoint가 있다고 해서 생기지 않습니다. 애플리케이션은 “OpenAI SDK를 쓴다”와 “OpenAI 서비스를 호출한다”를 구분해야 합니다. endpoint와 모델의 capabilities를 설정·테스트·문서에서 명확히 표시하는 편이 좋습니다.

## GPU 메모리와 병렬성의 현실

서빙에서 GPU는 CPU보다 많은 행렬 계산을 병렬 처리하는 장치입니다. 그러나 GPU가 하나 있다고 항상 모델 하나를 안정적으로 서비스할 수 있는 것은 아닙니다. 가중치 정밀도(FP16, BF16, INT8, INT4 등), 모델 파라미터 수, context length, 동시 요청 수, KV Cache block, CUDA와 드라이버 버전이 함께 VRAM 요구량을 만듭니다. 모델을 로드할 수 있어도 첫 긴 요청에서 out-of-memory가 나면 서비스 용량을 잘못 잡은 것입니다.

**양자화(quantization)** 는 가중치나 계산 표현의 비트 수를 줄여 메모리와 계산량을 낮추는 방법입니다. 모델을 작은 GPU에 올리게 해 줄 수 있지만, 모델·양자화 방식·하드웨어에 따라 품질과 성능, 지원 연산이 달라집니다. “4비트면 무조건 반으로 줄고 품질도 같다”는 식의 판단은 위험합니다. 특히 구조화된 JSON, 한국어 고유명사, 코드 생성처럼 형식 정확도가 중요한 업무는 후보 모델과 양자화 설정을 별도 평가해야 합니다.

여러 GPU에 모델을 나누는 tensor parallelism도 만능이 아닙니다. GPU 사이 통신 대역폭, 토폴로지, 동일한 GPU 모델 여부, 배포 프레임워크가 영향을 줍니다. GPU 수를 늘리면 처리량이 선형으로 늘어난다고 가정하기보다, 하나의 모델이 필요한 메모리와 요청 패턴부터 측정합니다. 처음에는 단일 GPU·작은 모델·제한된 동시성에서 시작하고, 실제 대기열과 GPU 사용량을 보고 확장하는 편이 장애를 줄입니다.

## latency와 throughput을 함께 읽기

사용자는 첫 글자가 빨리 보이는지와 답이 모두 끝나는 시간을 다르게 느낍니다. **TTFT(Time To First Token)** 는 스트리밍 응답에서 첫 토큰이 도착하기까지의 시간이고, 전체 생성 시간은 output token 수와 생성 속도에 영향을 받습니다. **throughput**은 일정 시간에 처리한 token 또는 요청 수를 말합니다. 긴 요청을 많이 묶으면 GPU 전체 처리량은 좋아질 수 있지만, 짧은 요청의 TTFT는 나빠질 수 있습니다.

그래서 LLM API의 SLO(Service Level Objective)는 평균 응답 시간 하나만 두기보다 입력 길이·출력 길이·스트리밍 여부·우선순위에 따라 나눠 보는 편이 좋습니다. 예를 들어 대화형 UI는 p95 첫 토큰 시간, 야간 문서 요약은 작업 완료 시간과 실패율, 배치 embedding은 처리량을 다르게 볼 수 있습니다. vLLM이 제공하는 메트릭과 reverse proxy 로그, 애플리케이션의 요청 ID를 연결하면 대기열이 문제인지 모델 생성이 문제인지 구분하는 데 도움이 됩니다.

부하 시험에서는 실제 업무와 비슷한 prompt 길이와 동시성 분포를 준비해야 합니다. 짧은 영어 문장만 반복하면 긴 한국어 문서 요약·RAG 검색 결과·tool schema가 들어가는 실제 요청을 대표하지 못합니다. 또한 warm-up 뒤의 cache 상태와 서버 재시작 직후를 분리해서 기록하고, 오류·timeout·취소된 stream도 포함합니다. 이 글에서 특정 수치를 제시하지 않는 이유도 GPU와 workload가 다르면 결과가 크게 달라질 수 있기 때문입니다.

## 보안과 개인정보: 모델 서버도 API 서버다

자체 LLM 서버를 열면 프롬프트, 검색 문서, 생성 결과가 네트워크와 로그를 통과합니다. 내부 모델이라고 해서 데이터를 아무렇게나 넣어도 되는 것은 아닙니다. 요청 본문에 개인정보·계정번호·접근 토큰이 있는지, 어떤 팀이 어느 endpoint를 호출할 수 있는지, 프롬프트와 응답을 저장할지, 디버그 로그의 보존 기간은 얼마인지 정해야 합니다. 모델이 로컬에서 실행된다는 사실은 외부 전송 경로를 줄일 수 있지만, 접근 통제·보존 정책을 자동으로 해결하지는 않습니다.

모델 endpoint를 사내 네트워크에 공개할 때는 TLS termination, 사용자 또는 서비스 인증, rate limit, 요청 크기 제한, tenant별 quota를 고려합니다. API key 하나를 모든 애플리케이션이 공유하면 누가 비용과 장애를 만들었는지 알기 어렵고, 유출되었을 때 범위가 넓습니다. 서비스별 credential과 최소 scope, proxy 수준의 감사 로그를 사용하면 원인을 분리하기 쉽습니다. 다만 prompt 전문을 로그에 저장하면 보안 사고가 될 수 있으므로 메타데이터 중심의 관찰이 필요합니다.

프롬프트 인젝션도 모델 서버만의 문제가 아닙니다. 모델이 외부 문서를 읽고 도구를 호출하는 애플리케이션에서는 문서 안의 악의적 지시가 시스템 정책을 우회하려 할 수 있습니다. vLLM은 추론 엔진이지 도구 실행 권한을 대신 통제하는 보안 제품이 아닙니다. 도구 호출은 별도의 allowlist, 입력 검증, 사용자 권한 확인, 민감 작업 승인 흐름으로 보호해야 합니다.

## 운영 시작 순서

첫 번째 단계는 하나의 좁은 업무를 정하는 것입니다. 예를 들어 공개 문서의 초안 요약, 개발 환경의 코드 설명, 승인된 내부 FAQ 검색처럼 데이터 등급과 실패 영향이 낮은 경로가 좋습니다. “사내 모든 챗봇을 대체한다”는 목표는 모델·GPU·보안·비용의 질문을 한꺼번에 키웁니다. 성공 기준도 정답률이라는 모호한 단어 대신, 대표 질문의 근거 포함률, JSON 형식 통과율, p95 TTFT, 민감정보 누출 여부처럼 구체화합니다.

두 번째는 모델과 서버를 분리해 평가하는 것입니다. 같은 모델을 다른 serving configuration으로 실행했을 때 지연과 오류가 어떻게 달라지는지 보고, 다른 모델을 같은 프롬프트로 비교해 품질을 봅니다. 모델이 답을 잘못했는데 GPU 설정을 계속 바꾸거나, 서버가 과부하인데 prompt engineering만 하는 식의 혼동을 피할 수 있습니다. 설정 파일과 모델 revision, GPU·드라이버 정보, 평가 prompt 버전을 함께 기록하면 결과를 재현하기 쉽습니다.

세 번째는 점진 공개입니다. 개발자 몇 명의 내부 사용, 읽기 전용 기능, 제한된 요청량 순서로 열고, 과도한 입력·긴 출력·동시 burst·모델 로드 실패·GPU OOM·다운스트림 timeout을 미리 연습합니다. 장애가 나면 자동으로 더 작은 모델로 전환할지, 관리형 API로 fallback할지, 기능을 잠시 비활성화할지 제품 요구와 비용을 함께 고려합니다. fallback도 데이터를 어느 제공자에 보내는지 바꾸므로 사용자 고지와 데이터 정책을 확인해야 합니다.

## 요청 제한과 공정성은 모델 밖에서 설계한다

vLLM의 스케줄러는 GPU에서 생성 작업을 효율적으로 배치하지만, 어떤 사용자가 서비스를 얼마나 사용할 수 있는지에 대한 제품 정책을 자동으로 결정하지는 않습니다. 한 사용자가 수십만 token의 문서를 반복해서 보내면, 다른 사용자의 짧은 질문이 대기열에서 오래 기다릴 수 있습니다. `max_model_len`, 요청당 최대 input·output token, 동시 stream 수, 분당 요청 수, 사용자별 일일 quota 같은 제한을 API gateway 또는 애플리케이션 경계에서 정해야 합니다.

제한을 설정할 때는 단순히 “길면 나쁘다”라고 생각하지 않습니다. 문서 요약은 긴 입력과 짧은 답이 필요할 수 있고, 코드 생성은 짧은 입력과 긴 답이 필요할 수 있습니다. 각 기능이 쓰는 input·output token 예산을 명시하고, 초과하면 무엇을 할지 정합니다. 요청을 거절할지, 사용자가 문서를 나누도록 안내할지, 비동기 작업으로 전환할지, 더 작은 모델로 보낼지를 제품 흐름에 맞춰 선택합니다. 무한히 긴 context window를 허용하는 것은 사용자 친화적으로 보이지만 GPU 메모리와 대기 시간에서 다른 사용자를 해칠 수 있습니다.

멀티테넌트 환경에서는 cache와 로그도 경계가 됩니다. prefix caching은 같은 prefix를 재사용해 효율을 높일 수 있지만, 서로 다른 조직의 민감한 prompt가 같은 cache key 또는 디버그 화면에서 섞이지 않도록 구현·운영 범위를 확인해야 합니다. cache가 어떤 데이터를 보관하고 언제 해제하는지, 모니터링에서 tenant ID를 어떤 수준으로 기록할지, 지원 엔지니어가 요청 내용을 열람할 수 있는지를 데이터 분류 정책과 맞춥니다. 성능 최적화가 접근 권한의 예외가 되면 안 됩니다.

스트리밍 취소도 자원 관리 문제입니다. 사용자가 브라우저 탭을 닫거나 모바일 네트워크가 끊긴 뒤에도 서버가 계속 2,000토큰을 생성하면 GPU 시간이 낭비됩니다. reverse proxy와 애플리케이션이 client disconnect를 어떻게 전달하는지, vLLM 요청 취소가 어떤 시점에 반영되는지, 취소된 요청의 token 사용량을 어떻게 기록할지 시험합니다. 반대로 네트워크 연결이 잠깐 끊겼다고 중요 배치 작업을 무조건 취소하면 재처리 비용이 커질 수 있으므로 대화형과 비동기 job의 취소 정책을 분리합니다.

## 평가 세트와 회귀 검증을 운영에 연결하기

LLM 품질은 배포 직전에 사람이 몇 질문 던져 보는 방식으로 안정적으로 관리하기 어렵습니다. 모델 revision, tokenizer, chat template, sampling temperature, system prompt, RAG 문서가 바뀌면 같은 모델 이름이라도 답변 형식과 정확도가 달라질 수 있습니다. 따라서 실제 업무에서 허용된 대표 질문을 익명화하거나 새로 만든 **평가 세트(eval set)** 로 관리합니다. 답변이 정확해야 하는 질문, 반드시 인용을 해야 하는 질문, JSON schema를 지켜야 하는 질문, 답변을 거부해야 하는 질문을 함께 넣습니다.

평가의 결과는 하나의 평균 점수보다 실패 유형으로 읽습니다. 예를 들어 JSON이 파싱되지 않는 비율, 근거 없는 정책 답변 비율, 한국어 용어를 영어로 잘못 변환하는 사례, 민감 요청을 과도하게 답하는 사례, tool argument가 스키마를 벗어나는 사례를 분리합니다. 자동 채점은 형식·키워드·정답 집합에는 유용하지만, 법무·인사·의료처럼 맥락이 중요한 결과는 담당자의 검토가 필요할 수 있습니다. 평가 모델을 또 사용하는 경우에도 평가 모델의 편향과 비용을 인지해야 합니다.

서빙 설정 변경에도 회귀 검증이 필요합니다. GPU driver를 업데이트하거나 vLLM 버전을 올리고, 양자화 방법을 바꾸고, `max_num_seqs` 같은 스케줄링 설정을 조정하면 품질뿐 아니라 timeout·OOM·stream 종료 방식이 달라질 수 있습니다. 변경 전후에 같은 eval set, 같은 입력 길이 분포, 같은 API contract test를 실행하고 결과와 설정을 함께 저장합니다. 단순한 curl 성공은 모델 서버가 시작됐음을 알려 줄 뿐, 제품 기능이 유지됐다는 증명은 아닙니다.

## 배포와 관찰의 최소 단위

모델 서버 배포는 컨테이너 image, 모델 artifact, GPU node, endpoint 설정 네 가지를 분리해서 보는 편이 좋습니다. 애플리케이션 코드가 바뀌지 않았어도 모델 repository의 revision이 바뀌면 결과가 달라질 수 있고, 같은 image라도 CUDA driver가 다른 노드에서 실패할 수 있습니다. 어느 요청이 어떤 모델 revision과 어떤 template로 처리됐는지를 최소한의 메타데이터로 남기면, 품질 이슈와 장애를 다시 조사할 수 있습니다. 단, 원문 prompt를 무조건 저장하지 말고 해시·길이·분류·에러 코드처럼 필요한 정보를 우선합니다.

관찰 지표는 서버·GPU·제품 레벨을 나눕니다. 서버 레벨에서는 요청 수, 오류율, 대기열 길이, TTFT, 전체 생성 시간, 취소율을 봅니다. GPU 레벨에서는 VRAM 사용량, utilization, OOM, temperature와 throttling을 봅니다. 제품 레벨에서는 기능 성공률, 사용자 재시도, fallback 비율, token 예산 사용량을 봅니다. GPU utilization이 높다는 사실만으로 좋은 서비스는 아니며, 낮다고 해서 곧 낭비도 아닙니다. 사용자 지연과 비용, 안정성을 함께 읽어야 합니다.

모델을 새 버전으로 바꿀 때는 canary 또는 제한된 경로로 먼저 보내는 전략을 검토합니다. 같은 사용자의 대화 맥락이 서로 다른 모델로 오가면 경험이 흔들릴 수 있으므로, 대화 세션 또는 tenant 단위로 일관된 routing이 필요한 경우도 있습니다. 문제가 생겼을 때는 이전 image와 model revision으로 되돌릴 수 있어야 하며, model cache를 지우거나 새 GPU 노드를 붙이는 과정도 runbook에 넣습니다. 대형 모델 파일을 매번 새로 받는 배포는 시간과 레지스트리 대역폭을 크게 쓸 수 있습니다.

## 비용과 환경 영향을 판단하는 방법

자체 모델 서빙의 비용은 GPU 시간만이 아닙니다. GPU 인스턴스 또는 장비 감가, 전력과 냉각, 모델 저장 공간, 네트워크, 보안 패치, 온콜, 평가와 데이터 거버넌스가 포함됩니다. 관리형 API는 token당 가격이 보이지만 자체 서빙은 유휴 시간과 운영 인력이 비용에 포함됩니다. 반대로 요청량이 예측 가능하고 데이터가 외부로 나갈 수 없으며 같은 모델을 많이 공유한다면 자체 서빙이 유리할 수 있습니다. 어느 쪽이 싸다고 일반화하기보다 월별 요청 분포와 필요한 품질을 기준으로 계산합니다.

에너지와 장비 수명도 장기적으로는 고려할 요소입니다. 사용량이 적은데 큰 GPU를 상시 켜 두면 유휴 비용이 크고, 피크를 위해 작은 서버를 과도하게 늘리면 운영 복잡성이 증가합니다. batch 가능한 업무를 야간에 모으거나, 낮은 우선순위 요청에는 작은 모델을 쓰거나, 사람이 검토해야 하는 단계에서는 생성 token을 제한하는 것처럼 제품 설계로 자원을 줄일 수도 있습니다. 효율은 무조건 가장 큰 모델을 쓰는 데 있지 않고, 업무에 필요한 품질과 지연을 명확히 정하는 데서 시작합니다.

## 장애 상황을 기능 요구사항으로 바꾸기

LLM 서버는 일반 API 서버와 같은 방식으로 실패합니다. 모델 다운로드가 끝나지 않거나, GPU driver와 CUDA 라이브러리 조합이 맞지 않거나, 모델 가중치가 VRAM에 들어가지 않거나, 요청이 너무 길어 OOM이 날 수 있습니다. 여기에 생성 모델 특유의 실패도 더해집니다. 모델은 HTTP 200을 반환했지만 JSON을 깨뜨릴 수 있고, stream이 중간에 끊길 수 있으며, 같은 질문에도 sampling 설정 때문에 다른 답을 낼 수 있습니다. 그러므로 health check 하나가 통과했다고 제품이 준비됐다고 보지 않습니다.

운영 runbook에는 모델을 올리지 못했을 때와 요청을 처리하지 못했을 때를 나눠 적습니다. 모델 load 실패라면 새 요청을 받지 않고 이전 안정 revision으로 되돌릴지, 제한된 fallback 제공자로 보낼지, 기능을 숨길지 결정합니다. 개별 요청 OOM이라면 입력 길이 제한 오류를 줄지, 문서를 분할해 다시 시도하도록 안내할지, 대기열에서 제거할지 정합니다. GPU node 하나가 사라졌을 때 connection draining과 요청 재시도가 어떻게 되는지도 확인합니다. 이 선택은 모델 엔진 옵션보다 사용자 경험과 데이터 정책에 더 직접적인 영향을 줄 수 있습니다.

생성 결과가 불확실하다는 점도 장애 모델에 넣습니다. 사용자가 비어 있는 답, 중복된 token, schema와 다른 JSON, 근거 없는 확신을 받았을 때 애플리케이션이 어떻게 보일지 정해야 합니다. JSON이 필요한 자동화라면 문법 파싱, schema validation, 필요한 필드 확인 후에만 다음 단계로 넘깁니다. 불완전한 생성 결과를 데이터베이스 업데이트나 외부 도구 호출에 바로 쓰지 않고, 검증 실패를 재시도·사람 검토·안전한 중단 중 어디로 보낼지 설계합니다.

모델 서버의 업그레이드도 rollback 가능한 배포여야 합니다. 새 vLLM image와 모델 revision을 배포하기 전에 이전 조합을 다시 실행할 수 있는지, GPU 메모리 캐시와 모델 파일이 디스크를 얼마나 쓰는지, 기존 stream을 끊지 않고 traffic을 전환할 수 있는지 확인합니다. 변경 로그에는 모델·tokenizer·template·양자화·서버 버전·주요 제한값을 함께 남깁니다. 이런 기록이 없으면 며칠 뒤 품질이 바뀌었을 때 프롬프트 탓인지 모델 탓인지 알기 어렵습니다.

## API 계약을 명확히 하기

내부 vLLM endpoint도 소비자가 있는 API입니다. 어떤 모델 ID를 허용하는지, `max_tokens` 상한은 무엇인지, stream 형식은 SSE(Server-Sent Events)인지, timeout과 429·5xx 오류에서 클라이언트가 재시도해도 되는지 문서화합니다. OpenAI 호환 형식은 출발점일 뿐이므로, 지원하지 않는 parameter를 조용히 무시하는지 오류로 돌려주는지와 tool calling·structured output의 지원 범위를 실제 contract test로 확인합니다.

버전 정책도 필요합니다. `assistant-default` 같은 별칭을 새 모델로 바꾸면 편하지만, 평가가 끝나지 않은 모델 변경이 모든 사용자에게 즉시 영향을 줄 수 있습니다. 반면 model revision을 완전히 고정하면 보안 패치와 개선을 늦게 받습니다. 서비스별로 안정 별칭과 실험 별칭을 나누고, 기본 모델 변경 전 eval·성능·데이터 정책 검토를 거치는 방법이 균형을 잡습니다. API client가 모델 이름을 하드코딩하는지, 응답의 모델 ID를 저장하는지도 확인합니다.

마지막으로 서비스 경계를 너무 크게 잡지 않습니다. 모델 서버가 문장을 생성하는 역할과, 검색·권한 판정·업무 시스템 변경을 실행하는 역할은 다릅니다. vLLM은 토큰을 생성하지만 사용자가 특정 주문을 환불할 권한이 있는지 판단하지 않습니다. 모델 결과를 도구 호출로 연결한다면 별도 백엔드가 사용자 권한·입력 schema·승인·감사 로그를 책임져야 합니다. 이 분리가 있어야 모델 오류가 곧바로 업무 데이터 오류로 번지는 일을 줄일 수 있습니다.

## 마무리: API 호환성보다 먼저, 서빙 경계를 설계하기

vLLM은 공개 가중치 모델을 다수의 API 요청으로 제공할 때 GPU 메모리와 요청 스케줄링을 다루는 강력한 선택지입니다. PagedAttention과 continuous batching은 그 안의 중요한 아이디어지만, 모델 품질·데이터 보호·권한·운영 지표를 대신해 주지는 않습니다.

처음에는 로컬 또는 제한된 내부 네트워크에서 하나의 모델과 하나의 업무를 연결해 보세요. 요청 길이, 동시성, 모델 라이선스, GPU 메모리, 프롬프트 보존 정책을 명시하면 “자체 AI 서버”라는 큰 말을 실제로 운영 가능한 작은 경계로 바꿀 수 있습니다.
