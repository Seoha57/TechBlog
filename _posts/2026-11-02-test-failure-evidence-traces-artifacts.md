## 먼저 알아둘 기반 기술

테스트 결과에는 pass와 fail만 있는 것처럼 보이지만, 실제 품질 판단에는 세 종류의 정보가 필요합니다. 첫째는 **기대값**입니다. 주문 취소 API가 409를 반환해야 하는지, 버튼이 비활성화돼야 하는지처럼 테스트가 무엇을 확인했는지입니다. 둘째는 **관찰값**입니다. 실제 응답, 화면, 데이터 상태, 예외 메시지입니다. 셋째는 **맥락**입니다. 어느 빌드와 브라우저, 어떤 테스트 데이터, 어떤 요청 순서에서 관찰값이 나왔는지입니다. 기대값만 있으면 실패를 선언할 수는 있어도 원인을 설명할 수는 없습니다.

로그(log)는 프로그램이 남긴 시간순 기록입니다. Trace는 하나의 사용자 요청이나 테스트 실행을 따라가며 여러 이벤트를 연결한 기록입니다. Artifact는 테스트 실행 뒤에 남겨 검토할 수 있는 파일 묶음으로, 스크린샷·비디오·HTML·네트워크 캡처·서버 로그·테스트 결과 XML이 될 수 있습니다. 이 용어를 구분하면 “로그를 더 남기자”보다 “실패한 클릭과 그 직전 API 응답을 같은 실행 ID로 연결하자”처럼 구체적인 설계가 가능해집니다.

CI(Continuous Integration, 지속적 통합)는 변경마다 정해진 환경에서 빌드와 테스트를 자동 실행하는 과정입니다. CI의 테스트는 개발자 노트북과 다른 CPU, 병렬 실행 수, 시간대, 네트워크, 브라우저 버전을 가질 수 있습니다. 그러므로 실패 증거는 단지 오류를 예쁘게 보여 주는 기능이 아니라, 서로 다른 사람이 같은 실패를 같은 조건으로 이해하게 만드는 계약입니다.

## 왜 오류 한 줄만으로는 부족한가

예를 들어 E2E(End-to-End, 종단 간) 테스트가 “결제 완료 문구를 찾지 못했다”고 실패했다고 하겠습니다. 이 메시지는 문구가 바뀌었는지, API가 500을 반환했는지, 로딩이 끝나기 전에 검증했는지, 테스트 계정의 장바구니가 비어 있었는지 알려 주지 않습니다. 개발자는 화면 코드를 의심하고, 백엔드 담당자는 데이터베이스를 의심하며, QA는 재실행을 누르게 됩니다. 같은 정보를 각자 새로 모으면 실패 하나가 긴 대화와 중복 조사로 변합니다.

좋은 실패 증거는 범인을 자동으로 지목한다는 뜻이 아닙니다. 대신 다음 질문을 빠르게 좁혀 줍니다. 테스트가 실제로 어느 URL과 계정으로 시작했는가, 어떤 화면 상태를 보았는가, 실패 직전 어떤 요청이 오갔는가, 서버가 어떤 correlation ID로 무엇을 처리했는가, 이전 성공 실행과 무엇이 다른가를 확인할 수 있어야 합니다. 이 질문에 답할 수 있으면 재현 가능한 제품 결함, 테스트 자체의 동기화 결함, 환경 장애를 분리하기 쉬워집니다.

반대로 증거가 너무 많아도 문제입니다. 매 성공 실행마다 모든 네트워크 body와 full video를 저장하면 저장소 비용이 커지고, 비밀값과 개인정보가 artifact에 남을 위험이 있습니다. 같은 오류 메시지가 수천 줄 반복되면 중요한 이벤트는 묻힙니다. 목표는 모든 것을 보관하는 감시가 아니라, 의사결정에 필요한 최소 증거를 안전하게 연결하는 것입니다.

## 실패 증거의 네 층을 나누기

첫 번째 층은 **테스트 의도**입니다. 테스트 이름만 `should work`라고 두지 말고 “이미 취소된 주문을 다시 취소하면 중복 환불 없이 409를 보여 준다”처럼 업무 규칙을 드러냅니다. assertion에는 기대 상태와 핵심 식별자를 남기되, 비밀번호·토큰·전체 고객 정보는 넣지 않습니다. 누군가 결과 화면만 보아도 무엇이 깨졌는지 알 수 있어야 합니다.

두 번째 층은 **클라이언트 관찰값**입니다. 브라우저 테스트라면 실패 시점의 스크린샷, 현재 URL, DOM 일부, console error, 네트워크 실패 요약이 여기에 속합니다. 화면이 깨졌다고 해서 스크린샷 하나만 보면 충분하지 않습니다. URL이 권한 없는 페이지로 바뀌었는지, 버튼이 disabled인지, 로딩 overlay가 남았는지, 클릭 대상이 다른 요소에 가려졌는지도 판단할 수 있어야 합니다.

세 번째 층은 **서비스 경계의 trace**입니다. browser request ID, HTTP method와 status, 응답 시간, API의 request ID, 비동기 메시지 ID를 연결합니다. JSON body 전체를 남기는 대신 허용된 필드 목록·응답 코드·오류 코드·데이터 크기 같은 요약을 기본값으로 둡니다. 특히 결제·인증·개인정보처럼 민감한 경계는 식별자를 해시하거나 test fixture ID로 바꿔야 합니다.

네 번째 층은 **실행 환경**입니다. 커밋 SHA, CI run URL, 테스트 파일과 재시도 횟수, 브라우저와 드라이버 버전, 운영체제 이미지, 병렬 worker 번호, 시간대, feature flag, seed data 버전을 남깁니다. 이는 개발자가 같은 명령을 다시 실행할 수 있게 하는 재현성 정보입니다. 환경 정보가 없으면 “내 컴퓨터에서는 된다”는 말과 CI 실패를 비교할 근거가 없습니다.

## Trace는 타임라인을 만드는 도구다

Trace를 도입할 때 흔한 오해는 분산 추적 시스템을 먼저 크게 구축해야 한다는 생각입니다. 테스트 관점의 첫 단계는 간단합니다. 한 테스트 실행에 run ID를 만들고, 브라우저 로그·API 요청 헤더·서버 로그·artifact 이름에 같은 값을 넣는 것입니다. 예를 들어 `ci-812-order-cancel-03` 같은 값이 화면 오류, API access log, 비동기 worker 로그에 함께 남으면 사람이 문자열 하나로 시간선을 따라갈 수 있습니다.

웹 테스트 도구의 trace viewer는 클릭, 입력, DOM snapshot, console, request를 시간 순서로 묶어 보여 줄 수 있습니다. 이것은 동영상보다 강점이 있습니다. 동영상은 “무슨 일이 보였는가”에는 좋지만, 실패 직전 POST 요청의 status와 응답 대기 시간을 찾기 어렵습니다. 반대로 trace만 보면 시각적 layout 오류를 놓칠 수 있습니다. UI 흐름에서는 trace와 실패 스크린샷을 서로 보완하는 자료로 둡니다.

trace ID가 있다고 자동으로 전체 시스템이 연결되는 것은 아닙니다. 프런트엔드가 새 header를 만들고 gateway가 버리거나, 비동기 queue가 message header를 전달하지 않으면 연결은 중간에서 끊깁니다. 동기 HTTP뿐 아니라 예약 작업·webhook·메시지 소비자의 경계에서 ID를 어떻게 전달할지 정해야 합니다. ID를 전달할 수 없는 외부 서비스라면 내부 호출 ID와 provider의 응답 ID를 함께 기록해 수동 대조가 가능하게 합니다.

## 구체적 업무 예시: 주문 취소 화면의 간헐 실패

주문 취소 버튼을 누른 뒤 “취소 완료” toast를 기다리는 테스트가 CI에서만 가끔 실패한다고 가정해 보겠습니다. 처음에는 기다리는 시간을 3초에서 10초로 늘리고 재시도 횟수를 올리기 쉽습니다. 그러나 이것은 실패를 늦출 뿐 원인을 가리지 못합니다. 테스트는 우선 주문 ID와 fixture version, 버튼 클릭 시각, 현재 URL, 화면 스크린샷, trace 파일, `POST /orders/{id}/cancel`의 status와 duration을 artifact로 남깁니다.

API는 요청의 correlation ID, 주문 상태 전이 전후 값, 외부 환불 요청 여부, transaction 결과를 구조화 로그로 남깁니다. 이때 카드 번호나 고객 이름을 로그에 넣지 않습니다. 테스트 fixture의 가짜 주문 ID와 내부 event ID면 충분합니다. worker가 환불 처리 뒤 화면이 읽는 조회 모델을 갱신한다면, message publish와 consume 시각, 처리 결과도 같은 ID로 묶습니다.

실패 artifact를 보면 버튼 클릭은 성공했고 API는 202를 반환했지만, 화면은 3초 안에 완료 상태를 받지 못했다고 할 수 있습니다. 다음에는 worker가 지연됐는지, polling request가 실패했는지, 화면의 대기 조건이 잘못됐는지 조사합니다. 만약 API가 409를 반환했다면 test data가 이미 취소된 상태였는지 seed reset을 봅니다. 이 흐름은 재시도 성공률만 보는 것보다 문제의 소유 경계를 명확하게 만듭니다.

## 로그는 구조화하고 민감 정보는 줄이기

사람이 읽기 좋은 문장 로그는 조사 초기에는 편하지만, CI 수백 실행에서 같은 필드를 찾기 어렵습니다. JSON 같은 구조화 로그에 `timestamp`, `level`, `run_id`, `test_case`, `request_id`, `event`, `duration_ms`, `error_code`를 두면 검색과 집계가 쉬워집니다. 필드 이름은 팀마다 조금씩 달라도 되지만, 같은 뜻의 ID를 서비스마다 `trace`, `requestId`, `cid`로 제각각 만들면 연결 비용이 커집니다.

로그 레벨도 목적에 맞춰 사용합니다. 정상적인 상태 전이마다 error를 남기면 진짜 오류가 묻힙니다. 반대로 예외 객체를 버리고 `failed`만 남기면 stack trace와 원인 체인을 잃습니다. 테스트 실행에서는 실패 판단에 필요한 입력 요약과 상태 전이, 외부 호출 결과를 info 또는 debug로 남기고, 예상 밖 예외와 데이터 정합성 위반은 error로 구분하는 기준을 합의합니다.

가장 중요한 원칙은 secret과 개인정보를 기본적으로 기록하지 않는 것입니다. Authorization header, session cookie, access token, 결제 정보, 실제 이메일, 전체 요청 body를 artifact에 넣으면 테스트 편의 때문에 보안 경계를 낮추게 됩니다. 필요한 경우에는 fixture용 가짜 값만 쓰고, allowlist한 필드만 기록하며, artifact 접근 권한·보존 기간·삭제 절차를 CI 설정에 둡니다. mask가 있다는 이유만으로 원본 로그를 오래 보관하는 선택도 다시 검토해야 합니다.

## Artifact 정책: 언제 무엇을 남길까

가장 작은 정책은 “실패한 테스트에만 진단 artifact를 남긴다”입니다. 실패 스크린샷과 trace, 핵심 로그를 하나의 압축 파일 또는 CI artifact 링크로 묶으면 성공 실행의 저장 비용을 낮출 수 있습니다. flaky test를 조사하는 기간에는 재시도된 실행도 남길 수 있지만, 기간과 대상 테스트를 정하지 않으면 저장량이 계속 증가합니다.

성공 실행은 아무 증거도 남기지 말라는 뜻은 아닙니다. 테스트 결과 요약, 소요 시간, 실행 환경, commit SHA, coverage 또는 test report 같은 작은 메타데이터는 추세 비교에 필요합니다. 중요한 사용자 경로는 기준 screenshot이나 API contract 결과를 versioned fixture로 보관할 수 있습니다. 다만 기준선 자체가 정답인지도 리뷰해야 하며, 실패를 없애려고 기준 이미지를 무심코 갱신해서는 안 됩니다.

artifact 이름은 사람이 찾을 수 있게 만듭니다. 날짜만 넣은 `result.zip`보다 `run-812/payment-cancel/chrome-2/trace.zip`처럼 CI run, 테스트 케이스, worker 정보를 포함하는 편이 낫습니다. CI 화면에는 실패 assertion, artifact 링크, 재실행 링크, 관련 trace ID를 가까이 배치합니다. 다른 시스템의 URL을 복사하고 파일을 다운로드해 다시 검색해야 한다면 좋은 정보도 잘 쓰이지 않습니다.

## 재시도는 증거를 대체하지 않는다

재시도 후 통과한 테스트를 성공으로만 처리하면 flaky test가 쌓입니다. 재시도는 외부 sandbox의 일시 오류처럼 통제할 수 없는 경우에 유용할 수 있지만, 먼저 실패한 첫 실행의 증거를 보존해야 합니다. 첫 실패와 재실행의 브라우저·worker·응답 시간·환경이 어떻게 달랐는지 비교하지 않으면, 재시도는 결함을 숨기는 장치가 될 수 있습니다.

테스트 결과에는 최초 시도 결과, 재시도 횟수, 최종 결과를 구분합니다. 팀은 flaky 비율, 실패가 특정 worker나 시간대에 몰리는지, 평균 실행 시간이 늘어나는지, 어떤 외부 의존성이 자주 timeout되는지를 추세로 봅니다. 재시도 한 번으로 통과한 사례가 많아지면 대기 조건·테스트 데이터 격리·공유 환경 용량을 조사할 신호입니다.

## 실패를 분류하는 기준을 먼저 만들기

실패 artifact가 있어도 분류 기준이 없으면 매번 다른 사람이 다른 이름을 붙입니다. 가장 실용적인 시작은 제품 결함, 테스트 결함, 환경 결함, 미확인 네 가지로 나누는 것입니다. 제품 결함은 구현이 약속한 업무 규칙을 지키지 않은 경우입니다. 테스트 결함은 잘못된 selector, 불안정한 시간 대기, 누수된 공유 상태처럼 테스트 코드나 fixture가 원인인 경우입니다. 환경 결함은 CI runner 부족, test database 장애, 인증서 만료, 외부 sandbox 문제처럼 제품 코드 밖에서 생긴 경우입니다.

미확인이라는 상태도 필요합니다. 실패한 순간에 API가 500을 돌려줬다고 해서 곧바로 제품 결함으로 확정할 수는 없습니다. 테스트가 이미 잘못된 데이터로 요청했거나, 배포 중인 다른 버전과 통신했을 가능성이 있기 때문입니다. 증거가 충분하지 않은 사건을 억지로 분류하면 이후 지표와 우선순위가 왜곡됩니다. 미확인에는 추가로 확인할 artifact와 담당 경계를 적고, 다음 실행에서 같은 ID나 환경 조건이 반복되는지 확인합니다.

분류는 책임을 전가하기 위한 라벨이 아닙니다. 제품 결함이면 어떤 회귀 테스트를 추가할지, 테스트 결함이면 어떤 대기 조건이나 데이터 격리를 고칠지, 환경 결함이면 어떤 용량 경보나 복구 절차를 만들지 결정하기 위한 입력입니다. 회고에서 “누구의 잘못인가”만 남기면 로그는 방어용 기록이 되지만, “다음에는 어떤 증거가 더 빨리 원인을 좁힐까”를 묻는다면 artifact 품질이 올라갑니다.

## 시간과 순서를 신뢰할 수 있게 만들기

분산된 시스템에서는 서로 다른 서버의 시계가 완전히 같다고 가정하면 안 됩니다. 브라우저의 시간, CI runner의 시간, API server의 시간, message broker의 시간은 조금씩 다를 수 있습니다. 로그를 합쳐 볼 때는 가능하면 UTC 기준의 표준 형식을 쓰고, event가 발생한 시각과 수집된 시각을 구분합니다. 시간이 뒤섞였을 때는 trace의 부모·자식 관계, 요청 ID, 메시지 offset 같은 인과 관계를 함께 사용해야 합니다.

비동기 테스트에서는 특히 “요청을 보냈다”와 “상태가 완료됐다”를 구분합니다. 버튼 클릭 직후 API가 202를 반환하는 시스템이라면 테스트가 확인해야 할 대상은 요청 수신이 아니라 최종 상태 전이와 사용자가 보는 결과일 수 있습니다. 이때 polling 횟수, 마지막으로 본 상태, 메시지 소비 여부를 남기면 단순 timeout보다 훨씬 좋은 단서가 됩니다. 반대로 너무 짧은 간격으로 상태를 조회하면 서비스에 불필요한 부하를 만들 수 있으므로 대기 전략도 기록합니다.

순서가 중요한 업무에서는 ID만으로 부족할 수 있습니다. 같은 주문에 취소와 환불 이벤트가 연달아 오면 어느 이벤트가 먼저 처리됐는지, 중복 이벤트를 어떻게 무시했는지 알아야 합니다. event sequence나 version을 artifact에 넣고, 테스트가 기대한 상태 전이 표와 실제 전이 표를 비교합니다. 테스트는 화면 문구 하나를 기다리는 코드를 넘어, 비즈니스 상태가 허용된 경로를 밟았는지 검증하는 도구가 됩니다.

## 데이터 준비와 정리도 증거의 일부다

많은 실패는 검증 단계가 아니라 준비 단계에서 시작합니다. 테스트가 어떤 사용자, 어떤 주문, 어떤 권한, 어떤 feature flag를 만들었는지 알 수 없으면 화면과 로그를 봐도 의미를 해석하기 어렵습니다. fixture에는 사람이 읽을 수 있는 안전한 식별자와 상태를 사용하고, artifact에는 fixture version과 생성 결과를 남깁니다. 실제 고객 데이터의 복사본을 쉽게 가져오는 방식은 조사 편의보다 개인정보와 재현성 위험이 더 큽니다.

공유 database를 쓰는 테스트는 앞선 실행이 남긴 상태 때문에 실패할 수 있습니다. cleanup이 실패했는지, 병렬 worker가 같은 키를 사용했는지, clock을 고정하지 않아 날짜 경계에서 결과가 달라졌는지도 확인해야 합니다. 모든 테스트를 직렬로 돌리는 것은 쉬운 회피책처럼 보이지만 실행 시간이 길어지고 경쟁 조건을 가릴 수 있습니다. 가능하면 실행마다 namespace, tenant, schema, 식별자 접두사를 분리하고, 실패해도 어느 데이터가 어느 run에 속하는지 찾을 수 있게 합니다.

정리 작업 자체도 관찰합니다. 예를 들어 테스트가 만든 주문을 삭제하지 못했으면 다음 실행의 유일성 제약 오류가 원래 결함처럼 보일 수 있습니다. cleanup 실패는 본문 실패와 별개로 기록하고, 유지보수 작업이 쌓일 때 경보를 둡니다. 다만 정리 오류를 숨기기 위해 production 수준의 삭제 권한을 CI에 광범위하게 주어서는 안 됩니다. 테스트 전용 계정과 짧은 보존 정책, 명시적 범위 조건을 함께 사용합니다.

## 실패 보고를 읽는 사람의 동선을 설계하기

좋은 CI 화면은 첫 화면에서 세 가지를 보여 줍니다. 무엇이 기대와 달랐는지, 어디서 실행됐는지, 다음 증거를 어디서 열 수 있는지입니다. 긴 raw log를 처음부터 끝까지 읽게 만드는 대신, 실패 assertion과 테스트 이름, 현재 단계, 핵심 오류 코드, 스크린샷·trace·서버 로그의 링크를 요약에 둡니다. 상세 로그는 필요할 때만 열 수 있게 하되, 요약과 다른 정보를 말해서는 안 됩니다.

실패한 테스트 케이스에는 소유자와 runbook을 연결할 수 있습니다. 예를 들어 결제 sandbox 오류는 payment integration 문서로, 브라우저 selector 오류는 UI test 가이드로, test database 용량 문제는 platform runbook으로 안내할 수 있습니다. 이 연결은 담당자를 자동으로 비난하는 표가 아니라, 처음 조사하는 사람이 올바른 질문과 접근 권한을 찾도록 돕는 길잡이입니다. 소유자가 바뀌면 링크와 설명도 함께 갱신해야 합니다.

협업 도구에 실패를 공유할 때 artifact 전체를 공개 채널로 올리지 않습니다. CI run URL, 짧은 오류 요약, correlation ID, 민감하지 않은 스크린샷 정도를 공유하고, 제한된 artifact는 권한 있는 사람이 열도록 합니다. 실제 token이나 고객 식별자를 발견하면 단순히 메시지를 삭제하는 데서 끝내지 않고, artifact 보존본·로그 수집 규칙·노출 범위를 확인해야 합니다. 테스트 증거는 품질 자료이면서 동시에 보안 자료입니다.

## 테스트 계층마다 필요한 증거는 다르다

단위 테스트는 보통 실패한 입력, 기대값, 실제값, stack trace가 핵심입니다. 값 객체 비교가 어려우면 차이를 읽기 좋은 형태로 출력하고, 무작위 값이 쓰였다면 seed를 남깁니다. 단위 테스트에 브라우저 동영상이나 전체 서버 로그를 붙이면 신호보다 잡음이 커집니다. 빠르게 원인을 찾고 개발자가 로컬에서 한 번에 재현할 수 있는 정보가 우선입니다.

통합 테스트는 database, message broker, 파일 저장소 같은 실제 의존성의 버전과 상태가 중요합니다. 어떤 container image, migration version, seed 데이터, 포트 구성이었는지 남기고, 테스트가 끝난 뒤 필요한 범위에서 query 결과나 broker 이벤트를 수집합니다. 외부 provider를 mock이나 sandbox로 대체했다면 그 사실도 명시합니다. 통합 테스트 통과가 실제 provider의 모든 정책을 보장한다고 오해하지 않기 위해서입니다.

브라우저 E2E 테스트는 사용자 동선, 화면 상태, 네트워크, 비동기 완료 조건을 함께 봅니다. 모바일 viewport나 locale, timezone이 다르면 같은 화면도 다르게 보일 수 있으므로 실행 설정을 artifact에 넣습니다. 시각 회귀 테스트는 기준 이미지의 version과 비교 결과를 남기되, 작은 anti-aliasing 차이를 제품 결함처럼 과장하지 않도록 허용 범위와 mask 규칙을 문서화합니다.

성능·부하 테스트는 요청 수만 남겨서는 부족합니다. 동시 사용자 수, 데이터 크기, warm-up, cache 상태, error rate, 높은 지연 구간, database·CPU·네트워크 자원, 테스트 도구 버전을 함께 기록합니다. 성능 결과는 한 번의 숫자보다 같은 조건에서 비교할 수 있는 실험 기록이어야 합니다. 테스트 환경이 production과 다르면 어떤 차이가 결과 해석을 제한하는지도 남겨야 합니다.

## 증거 수집 기능도 테스트해야 한다

테스트가 실패했을 때만 실행되는 artifact 업로드 경로는 평소에 잘 보이지 않아 깨지기 쉽습니다. 권한 변경으로 업로드가 실패하거나, 파일 경로가 바뀌거나, 용량 제한을 넘으면 가장 필요한 순간에 자료가 사라집니다. 의도적으로 작은 실패를 만든 뒤 스크린샷, trace, 로그, 메타데이터가 모두 생성되고 권한 있는 사용자가 열 수 있는지 주기적으로 확인합니다.

민감정보 mask도 검증 대상입니다. 가짜 bearer token, 이메일, 주문 번호를 포함한 fixture를 사용해 로그와 screenshot, trace에 어떤 값이 보이는지 확인합니다. 단, 실제 비밀값을 검증용으로 넣어서는 안 됩니다. allowlist 방식으로 기록 필드를 제한하고, mask 규칙이 바뀌면 기존 artifact를 다시 검토합니다. 보안 필터가 오류를 내서 조사에 필요한 모든 정보를 지워 버리지 않는지도 균형 있게 확인해야 합니다.

artifact의 수명도 테스트 범위에 넣습니다. 보존 기간이 지나면 자동 삭제되는지, 삭제된 링크가 오해를 만들지 않는지, 사고 조사에 필요한 기간과 법적·보안 정책이 충돌하지 않는지 확인합니다. 영구 보관은 편하지만 위험과 비용을 늘립니다. 팀이 실제로 몇 일 안에 flaky test를 조사하는지, 릴리스 추적에 어느 기간이 필요한지 근거를 두고 기간을 정합니다.

이러한 설계는 처음부터 완벽할 필요는 없습니다. 중요한 흐름 한 곳에서 실패 증거를 열어 보고, 조사한 사람이 부족했던 정보와 쓸모없었던 정보를 기록하며 개선합니다. 결과적으로 테스트는 통과 여부를 판정하는 자동 문이 아니라, 실패가 발생했을 때 다음 행동을 안내하는 신뢰할 수 있는 관찰 지점이 됩니다.

## 한계와 적용 기준 Q&A

### Q. 단위 테스트에도 스크린샷과 trace가 필요한가요?

A. 보통은 아닙니다. 입력과 기대값, stack trace, 핵심 상태 값이 잘 보이는 assertion이면 충분한 경우가 많습니다. trace와 시각 artifact는 브라우저·네트워크·비동기 처리처럼 상태가 여러 경계를 넘는 테스트에 우선 적용합니다. 모든 테스트에 무거운 수집을 붙이면 속도와 읽기 쉬움을 잃을 수 있습니다.

### Q. production 로그를 테스트 artifact에 복사하면 더 정확하지 않나요?

A. 실제 고객 데이터와 secret이 섞일 위험이 있어 기본 선택으로 적절하지 않습니다. 테스트 실행의 correlation ID로 production 관찰 도구에서 제한적으로 조회할 수 있는 절차를 만들고, 필요한 메타데이터만 연결하는 편이 안전합니다. 고객 영향이 있는 incident 조사는 접근 권한과 보존 정책이 다른 별도 절차로 다룹니다.

### Q. trace가 있으면 실제 버그와 테스트 버그를 자동으로 구분할 수 있나요?

A. 아닙니다. trace는 사실을 시간순으로 보여 주는 자료입니다. 기대 규칙이 맞는지, fixture가 유효한지, 서비스가 약속한 timeout과 비동기 완료 기준이 무엇인지는 사람이 검토해야 합니다. 다만 추측 대신 같은 증거를 보며 토론하게 해 분류 속도를 높입니다.

## 도입 순서와 점검표

처음부터 전 테스트에 관찰 도구를 붙이지 말고, CI에서 자주 실패하거나 고객 영향이 큰 사용자 흐름 하나를 고릅니다. 그 흐름에 명확한 테스트 이름, 실패 스크린샷, trace, 요청 ID, 환경 메타데이터를 연결합니다. 다음으로 artifact가 실제로 열리는지, 민감한 값이 없는지, 담당자가 10분 안에 재현 단서를 찾을 수 있는지 실패 사례를 가지고 점검합니다.

점검표에는 다음 질문을 넣을 수 있습니다. 실패 assertion이 업무 규칙을 설명하는가, 실패 화면과 URL이 남는가, client request와 server log가 하나의 ID로 연결되는가, artifact가 만료되기 전 조사할 수 있는가, secret과 고객 데이터가 빠졌는가, 재시도 전 첫 실패가 보존되는가, 환경과 fixture version을 다시 만들 수 있는가입니다. 이 질문에 모두 답할 수 있다면 테스트 증거는 단순한 CI 첨부 파일이 아니라 품질 팀과 개발 팀이 함께 쓰는 진단 도구가 됩니다.

테스트 관찰성의 성공 기준은 로그 줄 수가 아닙니다. 실패한 변경을 보고 누군가가 재현 조건과 다음 조사 대상을 설명할 수 있는지가 기준입니다. 필요한 증거는 업무와 위험에 따라 달라지므로, artifact를 늘리기 전에 어떤 판단을 빠르게 만들고 싶은지부터 정하세요. 그 원칙을 지키면 테스트 실패는 막연한 빨간 표시가 아니라 개선 가능한 기술 정보가 됩니다.

## 실패 증거를 릴리스 판단에 연결하기

테스트 artifact는 실패를 조사할 때만 쓰는 자료가 아닙니다. 배포 전에는 어떤 테스트가 어떤 commit과 설정에서 통과했는지, 실패했던 테스트가 재실행으로만 통과한 것은 아닌지 확인하는 근거가 됩니다. 특히 결제·권한·데이터 변경처럼 되돌리기 어려운 기능은 최종 성공 표시만 보지 말고, 실패 뒤 재시도가 있었는지와 그 실패가 분류됐는지를 살펴야 합니다. 통과한 결과가 신뢰할 수 있는 과정에서 나온 것인지가 중요합니다.

릴리스 후보의 증거는 제품 배포와 함께 영구 보관할 필요는 없지만, 언제 어떤 검증이 실행됐는지 추적할 수 있는 요약은 남겨야 합니다. commit SHA, 배포 artifact version, 테스트 suite version, 핵심 사용자 흐름 결과, 알려진 제외 항목을 release note나 변경 기록에 연결합니다. 이후 incident가 발생했을 때 “테스트가 있었는가”가 아니라 “무슨 가정 아래 어떤 범위를 확인했는가”를 다시 볼 수 있습니다.

다만 테스트 evidence를 배포 승인 도구처럼 과신하지 않습니다. 테스트 환경의 데이터 규모, 외부 제공자 sandbox, feature flag 조합은 production과 다를 수 있습니다. artifact가 모든 화면과 로그를 보여도 실제 고객 traffic의 모든 변형을 증명하지는 못합니다. 따라서 배포 뒤에도 오류율·지연·업무 지표를 관찰하고, 테스트에서 확인하지 못한 위험을 운영 경보와 rollback 계획으로 보완해야 합니다.

## 팀 규칙을 작게 시작하는 방법

처음 합의할 규칙은 길 필요가 없습니다. “브라우저 테스트 실패에는 screenshot과 trace를 남긴다”, “모든 API 테스트는 run ID를 header와 로그에 전달한다”, “artifact에는 token과 고객 원본 데이터를 넣지 않는다”, “재시도 전 첫 실패를 삭제하지 않는다” 정도면 출발할 수 있습니다. 규칙이 실제 CI에서 자동으로 지켜지는지 확인하고, 반복된 조사에서 도움이 되지 않는 항목은 줄이며 부족했던 항목만 추가합니다.

새 구성원이 실패 보고를 열어도 같은 순서로 확인할 수 있게 하는 것이 목표입니다. 먼저 assertion과 테스트 의도를 읽고, 화면 또는 응답을 보고, trace ID로 서비스 경계를 확인하고, 환경과 fixture를 대조한 뒤 필요하면 재현을 시도하는 흐름입니다. 이 순서가 문서와 CI 화면에 녹아 있으면 개인의 경험에 의존하지 않고도 결함 조사가 빨라집니다.

결국 좋은 테스트는 버그를 잡는 코드와 버그가 잡혔을 때 설명할 수 있는 증거를 함께 제공합니다. 실패가 빨간 결과 한 줄로 끝나지 않고 재현 가능한 학습 자료가 되면, 팀은 재시도 횟수를 늘리는 대신 불확실성을 줄이는 방향으로 품질을 개선할 수 있습니다.
